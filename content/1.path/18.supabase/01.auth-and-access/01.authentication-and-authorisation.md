Something that knows who is asking and what they are allowed to see. Those are
two separate questions, they get confused constantly, and the confusion is
usually where the vulnerability is.

## Why this matters in a job

Because every application has this, because getting it wrong exposes people's
data, and because the difference between 401 and 403 is a standard interview
question that is really asking whether you know these are different problems.

## The two questions

::compare{caption="Different questions, different failures, different status codes."}
  :::compare-side{label="Authentication — who are you?" verdict="neutral"}
  Proving identity. A password, a magic link, a Google sign-in. Fails with
  **401**, which is badly named: it means unauthenticated.
  :::
  :::compare-side{label="Authorisation — may you?" verdict="neutral"}
  What this known person is permitted to do. Fails with **403**: I know exactly
  who you are and you may not.
  :::
::

::pull-quote
Authentication happens once per session. Authorisation happens on every single
request, for every single row.
::

That second sentence is the one that matters, and it is where most junior systems
are wrong: they authenticate carefully and then authorise once, in the interface.

## How a session actually works

::flow{numbered direction="vertical" caption="Sign-in to a protected page. Six steps, and step three is where passwords go wrong."}
  :::flow-step{label="They submit email and password" icon="i-lucide-key"}
  Over HTTPS, always. Over plain HTTP this is a password sent in readable text
  through every router in between.
  :::
  :::flow-step{label="You look up the user" icon="i-lucide-search"}
  And if there is no such user, take the same amount of time as if there were.
  A faster "no such user" tells an attacker which addresses are registered.
  :::
  :::flow-step{label="You compare a HASH, never the password" icon="i-lucide-lock" highlight}
  bcrypt, scrypt or argon2, which are deliberately slow. **Never** SHA-256,
  which is designed to be fast and can therefore be brute-forced at billions of
  guesses a second.
  :::
  :::flow-step{label="You create a session and give them a token" icon="i-lucide-ticket"}
  In an HttpOnly, Secure, SameSite cookie. `HttpOnly` means JavaScript cannot
  read it, so a cross-site scripting bug cannot steal it.
  :::
  :::flow-step{label="Every later request carries it" icon="i-lucide-repeat"}
  The browser attaches the cookie automatically. HTTP is stateless, from the
  networks track, so identity travels with each request or not at all.
  :::
  :::flow-step{label="You check it, every time" icon="i-lucide-shield-check"}
  Not once at login. On every request, before anything else happens.
  :::
::

```java [PasswordService.java]
// Storing. bcrypt includes a random salt in the output, so identical
// passwords produce different hashes and a precomputed table is useless.
String hash = BCrypt.hashpw(plainPassword, BCrypt.gensalt(12));

// Checking. Constant time, so response timing reveals nothing.
boolean correct = BCrypt.checkpw(submitted, storedHash);
```

::caution{icon="i-lucide-octagon-alert"}
**Never store a password.** Never log one. Never email one. Never write your own
hashing, and never use SHA-256 or MD5 for this — they are fast, which is exactly
the wrong property. A leaked database of bcrypt hashes is an incident; a leaked
database of SHA-256 hashes is a list of passwords, because people reuse them
across sites.
::

## Authorisation, done three ways

```java [Authorisation.java]
// 1. Role: is this person a registrar at all?
if (!user.hasRole(Role.REGISTRAR)) throw new ForbiddenException();

// 2. Scope: are they a registrar FOR THIS PROGRAMME?
if (!user.getDepartmentId().equals(programme.getDepartmentId())) {
  throw new ForbiddenException();
}

// 3. Ownership: is this student asking about their OWN result?
if (!result.getStudentId().equals(user.getStudentId())) {
  throw new ForbiddenException();
}
```

::warning{icon="i-lucide-alert-triangle"}
Number three is the one that gets missed, and it has a name: **insecure direct
object reference**. The screen only ever links to your own result, so nobody
tests changing the number in the URL. A student changes
`/results/4182` to `/results/4183` and reads somebody else's marks. It is the
most common serious vulnerability in student and customer portals, and the fix
is one line that nobody wrote.
::

## Row-level security, which moves the check

Every check above is in application code, so it protects you from your
application. It does not protect you from the import script, the analytics
query, or the second application written against the same database in two years.

```sql [rls.sql]
ALTER TABLE ExamResult ENABLE ROW LEVEL SECURITY;

-- A student sees only their own results.
CREATE POLICY student_own_results ON ExamResult
  FOR SELECT
  USING (student_id = current_setting('app.current_student_id')::bigint);

-- A head of department sees their own department's.
CREATE POLICY hod_department_results ON ExamResult
  FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM Subject s
       WHERE s.subject_id = ExamResult.subject_id
         AND s.department_id = current_setting('app.current_department_id')::bigint
    )
  );
```

Now `SELECT * FROM ExamResult` returns different rows depending on who is
connected. A developer who forgets a `WHERE` clause leaks nothing, because the
database will not return the rows at all.

::pull-quote
A permission in your code protects you from your code. A permission in the
database protects you from everything, including the query somebody writes in two
years having never read your code.
::

::side-note{kind="go-deeper"}
This is the model Supabase exposes directly: the browser talks to PostgreSQL
through an API, and row-level security is the *only* thing standing between a
user and the table. That sounds alarming and it is exactly as safe as your
policies are, which is a clearer place to put the safety than scattered across
forty route handlers. It also means a policy bug is a serious bug, so policies
get tested like code.
::

## What you should not build yourself

::feature-list{columns="2"}
  :::feature{icon="i-lucide-x" title="Password hashing"}
  Use bcrypt or argon2 through a library. There is no version of this where your
  own is better.
  :::
  :::feature{icon="i-lucide-x" title="Session management"}
  Token generation, rotation, expiry, revocation. Every framework has this and
  every subtlety in it is a vulnerability you would have to rediscover.
  :::
  :::feature{icon="i-lucide-x" title="OAuth and sign-in with Google"}
  The specification is long and the mistakes are silent. Use a library.
  :::
  :::feature{icon="i-lucide-check" title="What IS yours"}
  Your authorisation rules. Who may shortlist for which programme, who may see
  which student's marks. Nobody can write those for you because they are your
  domain, and they are where your attention belongs.
  :::
::

## What you can do now

You can tell the two questions apart, explain how a session works including why
bcrypt rather than SHA-256, and name the vulnerability that comes from checking
permission in the interface rather than per row.

## Your turn

Design the permissions for the university system. For each, say who may do it and
where the check lives.

1. A student views their own exam results.
2. A lecturer enters marks for a subject they teach.
3. A head of department views every result in their department.
4. The registrar shortlists applicants for any programme.
5. A student views another student's results.
6. Anybody views the list of programmes on offer.

::accordion
  :::accordion-item{label="Answers, and the two that are not obvious" icon="i-lucide-check"}
  **1.** Authenticated student, own rows only. **Row-level security**, not an
  application check, because this is exactly the case where a forgotten `WHERE`
  leaks marks.

  **2.** Authenticated lecturer, scoped to subjects they are assigned to. Check
  the assignment, not the role: "is a lecturer" is not "teaches this subject".

  **3.** Role plus scope, and a policy in the database rather than a `WHERE`
  clause in one report, because there will be six reports.

  **4.** Role. And note that "any programme" is a decision somebody made: if a
  departmental registrar exists, this becomes scoped and the whole shape changes.
  Ask.

  **5. Explicitly forbidden**, and this is the one to test by hand. Log in as one
  student and change the id in the URL. If it returns data, you have the
  vulnerability. **Return 404 rather than 403**, so the response does not confirm
  that a result for that id exists.

  **6.** No authentication at all. Which is worth saying out loud, because the
  reflex is to protect everything, and a login wall in front of a public
  prospectus costs the university applications. **Not everything needs a
  permission, and deciding that deliberately is part of the design.**
  :::
::

## The interview question this answers

**"How does authentication work, and how is it different from authorisation?"**

Who you are against what you may do; once per session against every request and
every row. Then the mechanism: a hash compared with bcrypt or argon2 rather than
the password, a token in an HttpOnly Secure SameSite cookie, and a check on every
request because HTTP is stateless.

Then the part that separates the answer: insecure direct object reference. The
screen only links to your own record, so nobody tests changing the id, and a
student reads another student's marks. Saying that unprompted, with the fix being
a row-level policy rather than another `if`, is the strongest available finish.
