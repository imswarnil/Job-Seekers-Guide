HTML is treated as the easy part and the questions about it are not about tags.
They are about whether you know who cannot use what you built.

::accordion
  :::accordion-item{label="1. What is semantic HTML and why does it matter?" icon="i-lucide-message-circle"}
  Four audiences, and naming all four is the answer: a screen reader gets
  landmarks and structure to navigate by, a keyboard gets focus and activation
  for free, a search engine gets meaning, and your own code gets selectors that
  survive a class rename.

  Then one concrete example rather than a principle: `<div class="button">`
  cannot be reached with Tab and does not fire on Enter, so the feature does not
  exist for somebody who cannot use a mouse.
  :::

  :::accordion-item{label="2. A link or a button?" icon="i-lucide-message-circle"}
  A link navigates; a button performs an action. The test that settles it: if
  middle-clicking to open in a new tab would make sense, it is a link.

  Then why it matters: `<a href="#" onclick>` is in the tab order but announces
  itself as a link and does nothing on middle click, and a `<div>` with a click
  handler is not in the tab order at all.
  :::

  :::accordion-item{label="3. How do you make a form accessible?" icon="i-lucide-message-circle"}
  Labels tied with `for`, correct `type` so the right keyboard appears,
  `autocomplete`, hints tied with `aria-describedby`, related fields in a
  `fieldset` with a `legend`, errors next to the field and announced, and focus
  moved to the first error on submit.

  Then the test that proves it, which is what makes the answer sound lived-in:
  complete the whole form using only the keyboard. If you cannot, it is not
  accessible whatever an audit tool says.
  :::

  :::accordion-item{label="4. What does alt text say?" icon="i-lucide-message-circle"}
  What the image *conveys*, not what it depicts. For a chart, that means the
  numbers, not "chart of applications".

  And the distinction people miss: `alt=""` is correct for a decorative image
  and means "skip this". Omitting `alt` entirely makes a screen reader read the
  file name aloud.
  :::

  :::accordion-item{label="5. You have client-side validation. Why validate on the server?" icon="i-lucide-message-circle"}
  Because everything in the browser can be bypassed with developer tools or by
  skipping the page and calling the endpoint directly. The front-end check
  exists so an honest user is told immediately; the back-end check exists so the
  data is correct.

  Say the test: `curl` the endpoint with a percentage of 780. If it is accepted,
  your validation is decoration.
  :::

  :::accordion-item{label="6. What is progressive enhancement?" icon="i-lucide-message-circle"}
  It works without JavaScript and is better with it. A real `<form>` with an
  `action` submits and reloads; with JavaScript it is upgraded to a fetch with
  no reload. One piece of code, both paths.

  The reason it matters is not users who disable JavaScript, who are rare. It is
  slow connections where the script has not arrived, crawlers that will not run
  it, and a CDN that failed. All three are common.
  :::

  :::accordion-item{label="7. How would you test this for accessibility?" icon="i-lucide-message-circle"}
  An automated pass first, Lighthouse or axe, and then say what it cannot
  catch, which is the point of the question. It will not tell you the focus
  order is illogical, that your alt text is useless but present, or that an
  error is visible and not announced.

  So: Tab through the whole page, then turn on VoiceOver or NVDA and try to
  complete the main task without looking. Ten minutes, and it finds what the
  tool cannot.
  :::
::
