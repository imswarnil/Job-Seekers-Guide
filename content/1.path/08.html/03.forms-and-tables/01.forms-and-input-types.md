A form is where the user talks back. Before labels and validation, you need to
know what a form actually does when somebody presses submit, because nearly
every interview question about forms is really about that.

## Why this matters in a job

Every login, search box, fee payment and admission application on the internet
is a form. In a Java web interview the questions come from both sides: "GET or
POST, and why?" is asked with HTML and asked again with servlets and Spring.
The `name` attribute, the one that decides what the server receives, is the
detail freshers most often forget, and forgetting it produces a form that
"works" and sends nothing.

## A form is an envelope

Think of the paper admission form at a college office. The printed boxes are the
inputs. The label next to each box says what goes in it. The office address on
top is where it goes. And there are two ways of sending it: written on the
**outside** of the envelope where anyone can read it (GET), or sealed **inside**
(POST).

In HTML:

- `<form action="...">` is the address the data is sent to.
- `method="get"` or `method="post"` is how.
- Each input's `name` is the label the server sees. **An input without a
  `name` is not sent at all.**
- Pressing a submit button packages every named value as `name=value` pairs and
  sends them.

## How it works

```html [enquiry.html]
<form action="/search-courses" method="get">
  <label for="q">Search courses</label>
  <input id="q" name="q" type="search">
  <button type="submit">Search</button>
</form>
```

```text [What the browser requests when you search for "data science"]
GET /search-courses?q=data+science HTTP/1.1
```

With GET, the values go into the **URL** as a query string. With POST they go
in the **request body**:

```html [admission.html]
<form action="/applications" method="post">
  <label for="name">Full name</label>
  <input id="name" name="fullName" type="text">

  <label for="email">Email</label>
  <input id="email" name="email" type="email">

  <button type="submit">Apply</button>
</form>
```

```text [The request, when Anita Rao applies]
POST /applications HTTP/1.1
Content-Type: application/x-www-form-urlencoded

fullName=Anita+Rao&email=anita%40example.com
```

::compare{caption="GET and POST, the comparison interviewers want."}
  :::compare-side{label="GET" verdict="neutral"}
  Data in the URL. Visible in history, logs and bookmarks. Length is limited in
  practice (a few thousand characters). Can be cached and bookmarked. Should not
  change anything on the server. Use for **searching and filtering**.
  :::
  :::compare-side{label="POST" verdict="neutral"}
  Data in the body. Not in the URL or history. No practical size limit, so it
  can carry files. Not cached. Meant to change something. Use for **creating,
  logging in, paying, uploading**.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
POST is not encryption. The body is as readable as the URL to anyone who can see
the traffic. What protects a password is HTTPS, from the networks track. POST
only keeps it out of the address bar, the browser history and server logs.
::

### The input types

Run this and try each field, on a phone if you can: the keyboard changes.

::runner{lang="html"}
```html
<form>
  <p><label>Name <input type="text" name="name" maxlength="60"></label></p>
  <p><label>Email <input type="email" name="email"></label></p>
  <p><label>Password <input type="password" name="password"></label></p>
  <p><label>Class XII % <input type="number" name="marks" min="0" max="100" step="0.01"></label></p>
  <p><label>Date of birth <input type="date" name="dob"></label></p>
  <p><label>Mobile <input type="tel" name="phone"></label></p>
  <p><label>Portfolio <input type="url" name="site"></label></p>
  <p><label>Hostel needed <input type="checkbox" name="hostel" value="yes"></label></p>
  <fieldset>
    <legend>Category</legend>
    <label><input type="radio" name="category" value="general"> General</label>
    <label><input type="radio" name="category" value="obc"> OBC</label>
    <label><input type="radio" name="category" value="sc-st"> SC/ST</label>
  </fieldset>
  <p><label>Marksheet <input type="file" name="marksheet" accept=".pdf,image/*"></label></p>
  <p><label>Expected attendance % <input type="range" name="att" min="0" max="100"></label></p>
  <p><label>Programme
    <select name="programme">
      <option value="">Choose one</option>
      <option value="cse">B.Tech Computer Science</option>
      <option value="ece">B.Tech Electronics</option>
    </select></label></p>
  <p><label>Why this college? <textarea name="why" rows="3"></textarea></label></p>
  <input type="hidden" name="source" value="website">
  <button type="submit">Submit</button>
  <button type="reset">Clear</button>
  <button type="button">Save draft</button>
</form>
```
::

| Type | What it gives you |
| --- | --- |
| `text` | A plain single-line box. The default if `type` is missing. |
| `email` | Checks for an `@`; the phone keyboard shows `@`. |
| `password` | Hides the characters. Does not encrypt anything. |
| `number` | Spinner arrows; `min`, `max`, `step` enforced. |
| `date` | A date picker; the value is always sent as `YYYY-MM-DD`. |
| `tel` | A phone keypad. No format is checked, because phone formats vary. |
| `url` | Checks for a scheme such as `https://`. |
| `checkbox` | On or off. Sent only when ticked, as `name=value`. |
| `radio` | One of a group. Radios with the **same `name`** form the group. |
| `file` | A file picker. Needs `method="post"` and `enctype="multipart/form-data"`. |
| `range` | A slider. Imprecise, so only for values where precision does not matter. |
| `hidden` | Sent with the form, not shown. Not secret: visible in the source. |

### The three button types

- `type="submit"` sends the form. **This is the default** for a `<button>`
  inside a form.
- `type="reset"` clears every field back to its initial value. Rarely wanted;
  people press it by accident.
- `type="button"` does nothing on its own. Used for buttons that run
  JavaScript.

## Real use case

A fee payment form that uploads a receipt. Three details make it work, and
missing any one is a real bug report:

```html [fee-receipt.html]
<form action="/fees/receipts" method="post" enctype="multipart/form-data">
  <label for="roll">Roll number</label>
  <input id="roll" name="rollNo" type="text" required>

  <label for="receipt">Bank receipt (PDF, up to 2 MB)</label>
  <input id="receipt" name="receipt" type="file" accept="application/pdf" required>

  <button type="submit">Upload</button>
</form>
```

On the server, in a Spring Boot controller, those `name` values are exactly what
the code reads:

```java [FeeReceiptController.java]
@PostMapping("/fees/receipts")
public String upload(@RequestParam("rollNo") String rollNo,
                     @RequestParam("receipt") MultipartFile receipt) {
    // rollNo = "CS21001", receipt = the uploaded PDF
    return "redirect:/fees/thank-you";
}
```

Without `enctype="multipart/form-data"` the server receives only the file's
**name**, not its contents. Without `name="receipt"` it receives nothing.

## What confuses people here

- **`id` versus `name`.** `id` is for the page (labels, CSS, JavaScript) and
  must be unique. `name` is for the server and is what gets sent. Radio buttons
  in a group share one `name` and have different `id`s.
- **A `<button>` inside a form with no `type` submits the form.** Add
  `type="button"` to a "Show password" button or it will submit every time it is
  clicked.
- **An unticked checkbox sends nothing**, not `hostel=no`. The server must
  treat a missing value as false.
- **`disabled` fields are not sent; `readonly` fields are.**

## Interview questions

::accordion
  :::accordion-item{label="Difference between GET and POST?" icon="i-lucide-message-circle"}
  GET sends form data in the URL query string; it is visible, bookmarkable,
  cacheable, limited in length, and should not change server state. POST sends
  it in the request body; it is not in the URL or history, can carry files and
  large data, and is used for actions that change something. Neither is secure
  without HTTPS.
  :::
  :::accordion-item{label="What is the name attribute for? How is it different from id?" icon="i-lucide-message-circle"}
  `name` is the key the value is submitted under; inputs without it are not
  sent. `id` identifies the element in the page for labels, CSS and JavaScript
  and must be unique. Radio buttons share a `name` so only one can be chosen.
  :::
  :::accordion-item{label="What are the button types, and which is the default?" icon="i-lucide-message-circle"}
  `submit`, `reset` and `button`. Inside a form, a `<button>` with no type is
  `submit`, which is why a button meant for JavaScript often submits the form by
  accident.
  :::
  :::accordion-item{label="How do you upload a file with a form?" icon="i-lucide-message-circle"}
  `<input type="file" name="...">`, the form's `method="post"`, and
  `enctype="multipart/form-data"`. `accept` limits which files the picker
  offers, but the server must still check the type and size.
  :::
  :::accordion-item{label="Checkbox versus radio button?" icon="i-lucide-message-circle"}
  Checkboxes are independent: any number can be ticked. Radio buttons with the
  same `name` are a group where exactly one can be selected.
  :::
::
