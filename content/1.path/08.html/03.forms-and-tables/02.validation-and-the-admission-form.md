The form sends data. Now picture who is sending it: an applicant, eleven at
night, on a phone, with a bad connection, getting it wrong. This lesson is about
making a form that works for that person.

## Why this matters in a job

Forms are where users actually meet software, and a form that is hard to
complete costs a college applications. Almost every form on the internet has the
same eight mistakes, listed below. In interviews, "how do you make a form
accessible?" and "you have client-side validation, why does the server need it
too?" are the two questions that follow GET versus POST.

## Built-in validation

Think of the clerk at the admissions counter who glances at your form before
accepting it: "you have left the date of birth blank", "this percentage cannot
be 780". Built-in validation is that clerk, living in the browser. It checks the
form before it is sent, with no JavaScript at all.

The attributes:

| Attribute | Rule | Example |
| --- | --- | --- |
| `required` | Must not be empty | `<input name="fullName" required>` |
| `min`, `max` | Range for `number`, `date`, `range` | `min="0" max="100"` |
| `step` | Allowed increments | `step="0.01"` for two decimals |
| `minlength`, `maxlength` | Length of text | `maxlength="60"` |
| `pattern` | A regular expression the whole value must match | `pattern="[0-9]{10}"` |
| `type` | The type's own rule | `type="email"` needs an `@` |

The browser blocks submission, shows its own message next to the first invalid
field, and applies the CSS pseudo-classes `:invalid` and `:valid`, which you can
style. `novalidate` on the `<form>` turns all of this off, which you do when
JavaScript is going to show its own messages.

## How it works

Try submitting this empty, then with 780 in the percentage, then with a
nine-digit mobile number.

::runner{lang="html"}
```html
<form>
  <p>
    <label for="full-name">Full name</label>
    <input id="full-name" name="fullName" type="text"
           autocomplete="name" required maxlength="60">
  </p>
  <p>
    <label for="phone">Mobile number</label>
    <input id="phone" name="phone" type="tel" inputmode="numeric"
           autocomplete="tel" required pattern="[6-9][0-9]{9}"
           aria-describedby="phone-help">
    <span id="phone-help">10 digits, starting with 6, 7, 8 or 9.</span>
  </p>
  <p>
    <label for="marks">Class XII percentage</label>
    <input id="marks" name="marks" type="number"
           min="0" max="100" step="0.01" required>
  </p>
  <button type="submit">Submit application</button>
</form>
<style>input:invalid:not(:placeholder-shown){border-color:#dc2626}</style>
```
::

```text [What happens]
Empty submit:          "Please fill out this field." under Full name. Nothing is sent.
Marks = 780:           "Value must be less than or equal to 100."
Phone = 987654321:     "Please match the requested format."
All valid:             The form submits.
```

(The exact wording is the browser's, and differs between Chrome, Firefox and
Safari.)

### The full admission form

```html [apply.html]
<form method="post" action="/applications">
  <h1>Application for admission, 2026</h1>

  <fieldset>
    <legend>Your details</legend>

    <p>
      <label for="full-name">Full name</label>
      <input id="full-name" name="fullName" type="text"
             autocomplete="name" required>
    </p>

    <p>
      <label for="email">Email address</label>
      <input id="email" name="email" type="email"
             autocomplete="email" required
             aria-describedby="email-help">
      <span id="email-help">We will send your application number here.</span>
    </p>
  </fieldset>

  <fieldset>
    <legend>Programme</legend>

    <p>
      <label for="programme">Programme applied for</label>
      <select id="programme" name="programmeId" required>
        <option value="">Choose a programme</option>
        <option value="1">B.Tech Computer Science</option>
        <option value="2">B.Tech Electronics</option>
      </select>
    </p>
  </fieldset>

  <button type="submit">Submit application</button>
</form>
```

::feature-list{columns="2"}
  :::feature{icon="i-lucide-tag" title="label with for"}
  Not a caption. It makes the **label clickable**, which enlarges the target on
  a phone, and it is what a screen reader announces when the field is focused.
  Without it the user hears "edit text, blank".
  :::
  :::feature{icon="i-lucide-smartphone" title="type and inputmode"}
  `type="email"` gives a phone keyboard with `@` on it. `inputmode="numeric"`
  gives a number pad. On a phone this is the difference between eight taps and
  three.
  :::
  :::feature{icon="i-lucide-wand" title="autocomplete"}
  Lets the browser fill name, email and phone from what the user already has
  stored. Omitting it is the most common unforced error in forms.
  :::
  :::feature{icon="i-lucide-info" title="aria-describedby"}
  Ties the hint text to the field so a screen reader reads it with the label.
  :::
  :::feature{icon="i-lucide-group" title="fieldset and legend"}
  Groups related fields and announces the group name. Essential for radio
  buttons, where the question itself is the legend.
  :::
  :::feature{icon="i-lucide-send" title="A real form and a submit button"}
  Enter submits, the browser can restore the data, and it works before
  JavaScript loads. A `div` with a click handler does none of that.
  :::
::

### Errors that help

::compare{caption="The same invalid email, two experiences."}
  :::compare-side{label="What most forms do" verdict="wrong"}
  Submit. Page reloads. Every field is empty again. A red bar at the top says
  "Invalid input". The user does not know which field, does not know why, and
  has to retype everything on a phone.
  :::
  :::compare-side{label="What to do" verdict="right"}
  The error appears next to the field, after the user has finished with it
  rather than while typing, says what is wrong **and what is expected**, the
  field is marked `aria-invalid`, focus moves to the first error on submit, and
  nothing the user typed is lost.
  :::
::

```html [error.html]
<p>
  <label for="marks">Class XII percentage</label>
  <input id="marks" name="marks" type="number" min="0" max="100"
         aria-invalid="true" aria-describedby="marks-error">
  <span id="marks-error" role="alert">
    Enter a percentage between 0 and 100. You entered 780, did you mean 78.0?
  </span>
</p>
```

That message says the rule, repeats what they typed, and guesses the likely
mistake. A generic "invalid input" does none of the three.

::warning{icon="i-lucide-alert-triangle"}
**Client-side validation is a kindness, never a rule.** Every attribute here can
be removed by anybody with developer tools open, or skipped entirely by sending
the request with `curl`. The browser check exists so an honest user is told
immediately; the server check exists so the data is correct. Forgetting the
server check is the most common serious mistake in junior work.
::

## Real use case

This is how a team tests a form before it goes live. Six checks, and in my
experience four of them are skipped:

::flow{numbered direction="vertical" caption="Six tests. Four of them nobody runs."}
  :::flow-step{label="Complete it using only the keyboard" icon="i-lucide-keyboard" highlight}
  Tab through every field, choose a programme, submit, with the mouse
  untouched. If you cannot, neither can a real user.
  :::
  :::flow-step{label="Complete it on a real phone" icon="i-lucide-smartphone"}
  Not a resized browser window. Check the keyboard that appears for each field.
  :::
  :::flow-step{label="Submit it empty" icon="i-lucide-circle-slash"}
  Every error should be visible and specific, and focus should land on the
  first one.
  :::
  :::flow-step{label="Submit it invalid, and check nothing is lost" icon="i-lucide-undo"}
  Percentage 780, a malformed email. The valid fields must still be filled.
  :::
  :::flow-step{label="Submit it twice, fast" icon="i-lucide-copy"}
  One application, not two. Enforced by a unique constraint in the database, as
  in the DBMS track, not only by disabling the button.
  :::
  :::flow-step{label="Bypass the browser entirely" icon="i-lucide-shield"}
  Send the request yourself with a percentage of 780. The server must refuse.
  :::
::

```bash [bypass.sh]
curl -X POST https://college.example/applications \
  -d "fullName=Test&marks=780"
```

```text [Output, from a server that validates]
HTTP/1.1 400 Bad Request
{"error":"marks must be between 0 and 100"}
```

If that command returns `201 Created`, the form's validation was decoration.

### The eight mistakes

::feature-list{columns="2"}
  :::feature{icon="i-lucide-x" title="Placeholder instead of label"}
  The placeholder vanishes the moment they type, and usually fails contrast.
  :::
  :::feature{icon="i-lucide-x" title="Validating while typing"}
  "Invalid email" after the first character. Validate on blur or on submit.
  :::
  :::feature{icon="i-lucide-x" title="Clearing the form on error"}
  Unforgivable on a phone. Return what they typed.
  :::
  :::feature{icon="i-lucide-x" title="No autocomplete"}
  Forces typing what the browser already knows, which is slower and produces
  typos.
  :::
  :::feature{icon="i-lucide-x" title="A strict regular expression for emails"}
  Most in circulation reject valid addresses. Check for an `@` with something
  either side, and confirm by sending mail.
  :::
  :::feature{icon="i-lucide-x" title="Disabling submit without saying why"}
  The user is stuck with no feedback. Let them submit and tell them what is
  wrong.
  :::
  :::feature{icon="i-lucide-x" title="No protection against a double submit"}
  They tap twice on a slow connection and apply twice. Fix it in the database.
  :::
  :::feature{icon="i-lucide-x" title="Losing everything on a dropped connection"}
  Save a draft in the browser as they type, and restore it. The last lesson of
  the next chapter shows where.
  :::
::

## What confuses people here

- **`pattern` must match the whole value**, not part of it. `pattern="[0-9]"`
  accepts only a single digit.
- **`maxlength` stops typing; `max` does not.** `max="100"` on a number lets you
  type 780 and complains on submit.
- **`required` on a checkbox** means it must be ticked, which is how "I accept
  the terms" is done.
- **A label that wraps its input** (`<label>Name <input></label>`) works without
  `for`, but `for` and `id` is clearer and works with any layout.

## Interview questions

::accordion
  :::accordion-item{label="What HTML attributes validate a form without JavaScript?" icon="i-lucide-message-circle"}
  `required`, `min`, `max`, `step`, `minlength`, `maxlength`, `pattern`, and the
  input `type` itself (`email`, `url`, `number`). The browser blocks submission
  and shows a message. `novalidate` on the form turns it off.
  :::
  :::accordion-item{label="You have client-side validation. Why validate on the server too?" icon="i-lucide-message-circle"}
  Because anything in the browser can be bypassed: remove the attribute in
  developer tools, or send the request directly with `curl` or Postman. Client
  validation is for the user's convenience; server validation is for the data's
  correctness and security.
  :::
  :::accordion-item{label="How do you make a form accessible?" icon="i-lucide-message-circle"}
  Every input has a `label` tied with `for`; correct types so the right keyboard
  appears; `autocomplete`; hints and errors tied with `aria-describedby`; radio
  groups in a `fieldset` with a `legend`; errors announced and focus moved to the
  first one. Then prove it: complete the form using only the keyboard.
  :::
  :::accordion-item{label="Why is a placeholder not a label?" icon="i-lucide-message-circle"}
  It disappears when the user types, so they lose the prompt; it is often too
  low in contrast; and some screen readers do not announce it reliably.
  :::
  :::accordion-item{label="Write a pattern for a 10-digit Indian mobile number." icon="i-lucide-message-circle"}
  `pattern="[6-9][0-9]{9}"`: first digit 6–9, then nine more digits. The
  pattern is implicitly anchored, so it must match the whole value.
  :::
::
