The last lesson of the networks track ended with a server replying `200 OK` and
a body of text. Open that body and it is HTML: a document that tells the browser
what each piece of the page *is*. This lesson starts with the thing most people
get wrong about it.

## Why this matters in a job

HTML is treated as the trivial part, and it is the layer that decides whether a
page works for somebody using a screen reader, whether Google can read it, and
whether your JavaScript can find anything. Getting it wrong is invisible to you
and total for somebody else.

In interviews, "what is semantic HTML?" is one of the three most common opening
questions for a fresher web role. I heard it in more than one walk-in in BTM, and
my first answer ("it means using the right tags") was the answer everybody else
gave.

## HTML describes meaning, not appearance

Think of a college notice board. The principal's circular has a heading, a date,
numbered points and a signature. Nobody reads it by font size: you know the
heading is the heading because of where and how it sits. HTML is that structure
written down so a machine can see it too. How it *looks* is a separate job,
done later by CSS.

The real thing: HTML (HyperText Markup Language) is a set of **elements**, each
with a name that says what the content is. `<h1>` is the main heading.
`<table>` is tabular data. `<button>` is a control that does something. The
browser has built-in behaviour for each, and so do screen readers and search
engines.

```html [wrong.html]
<div class="title">Exam results</div>
<div class="row">
  <div class="cell">Anita Rao</div>
  <div class="cell">78</div>
</div>
<div class="button" onclick="publish()">Publish</div>
```

```html [right.html]
<h1>Exam results</h1>
<table>
  <caption>Semester 3, computer science</caption>
  <thead>
    <tr><th scope="col">Student</th><th scope="col">Marks</th></tr>
  </thead>
  <tbody>
    <tr><td>Anita Rao</td><td>78</td></tr>
  </tbody>
</table>
<button type="button">Publish</button>
```

Both can be made to look identical. Everything else about them differs.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-accessibility" title="A screen reader"}
  Announces "table, 2 columns, 60 rows" and lets the user jump between rows and
  hear the column heading with each cell. The `div` version is read as a
  continuous stream of words with no structure at all.
  :::
  :::feature{icon="i-lucide-keyboard" title="A keyboard"}
  `<button>` is focusable, reachable with Tab, and activates on Enter **and**
  Space. `<div class="button">` is none of those, so the feature does not
  exist for somebody who cannot use a mouse.
  :::
  :::feature{icon="i-lucide-search" title="A search engine"}
  Reads `<h1>` as the page's subject. A `div` with a class called `title` means
  nothing to it, because a class name is your private vocabulary.
  :::
  :::feature{icon="i-lucide-code" title="Your own code"}
  `document.querySelectorAll('tbody tr')` works on any correct table forever.
  `.row` works until somebody renames the class.
  :::
::

::pull-quote
The right element is not a style choice. It is the difference between a feature
existing and not existing for a person using a keyboard or a screen reader.
::

## How it works

Run this. It is the same results table twice, once as `div`s and once as a real
table, and it looks almost the same.

::runner{lang="html"}
```html
<h2>As divs</h2>
<div>Student Marks</div>
<div>Anita Rao 78</div>
<div>Vikram Shah 64</div>

<h2>As a table</h2>
<table border="1">
  <caption>Semester 3, computer science</caption>
  <thead>
    <tr><th scope="col">Student</th><th scope="col">Marks</th></tr>
  </thead>
  <tbody>
    <tr><th scope="row">Anita Rao</th><td>78</td></tr>
    <tr><th scope="row">Vikram Shah</th><td>64</td></tr>
  </tbody>
</table>
```
::

What you see is two blocks of text. What a screen reader hears on the cell "78"
is completely different:

```text [What a screen reader announces on the cell 78]
Divs:   "Anita Rao 78"
Table:  "Semester 3, computer science, table, 2 columns, 3 rows.
         Row 2, Anita Rao. Marks, 78."
```

The table version says **"Marks"** before "78", because `scope="col"` told it
which heading governs that cell. In the `div` version the user hears a number
with no idea what it is. That is the whole of why semantic HTML matters, in one
cell.

## Real use case

Every serious front-end codebase has a rule, usually enforced by a linter such
as `eslint-plugin-jsx-a11y` or an automated accessibility check in the test
suite, that fails the build on `<div onClick>` without a role and keyboard
handler. Teams add it because the same mistake keeps coming back in code review.

```html [results-page.html]
<!-- The shape a college results page takes in a real codebase -->
<main>
  <h1>Semester 3 results</h1>
  <table>
    <caption>Computer science, 60 students</caption>
    <thead>
      <tr><th scope="col">Roll no.</th><th scope="col">Student</th><th scope="col">Marks</th></tr>
    </thead>
    <tbody>
      <tr><td>CS21001</td><th scope="row">Anita Rao</th><td>78</td></tr>
    </tbody>
  </table>
  <a href="/results/semester-3.pdf">Download the PDF</a>
  <button type="button">Print this page</button>
</main>
```

Notice the last two lines. A link **goes** somewhere (a file, another page). A
button **does** something on this page. The test that settles it: if
middle-clicking it to open in a new tab would make sense, it is a link.

## What confuses people here

That a `div` with enough CSS and JavaScript is "the same" as the real element.
It is not. You can bolt on `tabindex="0"`, `role="button"` and a keydown handler
for Enter and Space, and you have rebuilt a button badly with four attributes and
will still have missed something (form submission, disabled state, the correct
announcement). Use the element that already means the thing.

The second trap: thinking HTML has anything to do with size or colour. `<h1>` is
not "big text"; it is "the main heading". If it is too big, that is a CSS
problem.

## Your turn

Rewrite this. There are six problems.

```html [fix-me.html]
<div class="page">
  <div class="header">Department of Computer Science</div>
  <div class="nav">
    <span onclick="go('/faculty')">Faculty</span>
  </div>
  <div class="content">
    <div class="h1">Placements 2026</div>
    <div class="h3">Companies visiting</div>
    <img src="/chart.png">
    <div class="list">
      <div>Infosys: 42 offers</div>
      <div>Accenture: 35 offers</div>
    </div>
    <div class="btn" onclick="exportCsv()">Export</div>
  </div>
</div>
```

::accordion
  :::accordion-item{label="The six, and the rewrite" icon="i-lucide-check"}
  1. No landmarks: `header`, `nav`, `main` are all `div`s, so there is nothing
     to navigate by.
  2. The nav item is a `span` with a click handler: not focusable, not
     keyboard-operable, not a link.
  3. Headings are classes, so the outline does not exist, and `h1` to `h3` skips
     a level.
  4. The image has no `alt`, so its file name is read aloud.
  5. A list of items is a set of `div`s rather than a list, so the count is not
     announced.
  6. The button is a `div`, so it cannot be reached or activated by keyboard.

  ```html
  <body>
    <header>
      <p>Department of Computer Science</p>
      <nav aria-label="Main">
        <a href="/faculty">Faculty</a>
      </nav>
    </header>

    <main>
      <h1>Placements 2026</h1>
      <h2>Companies visiting</h2>

      <img src="/chart.png"
           alt="Offers by company: Infosys 42, Accenture 35">

      <ul>
        <li>Infosys: 42 offers</li>
        <li>Accenture: 35 offers</li>
      </ul>

      <button type="button">Export</button>
    </main>
  </body>
  ```
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="What is semantic HTML and why does it matter?" icon="i-lucide-message-circle"}
  Using elements whose names describe the content (`<nav>`, `<table>`,
  `<button>`) instead of generic `<div>`s. It matters to four audiences: a screen
  reader gets structure and landmarks, a keyboard gets focus and activation for
  free, a search engine gets meaning, and your own code gets selectors that do
  not break when a class is renamed.

  Then one concrete example: `<div class="button">` cannot be reached with Tab
  and does not activate on Enter, so the feature does not exist for somebody who
  cannot use a mouse.
  :::
  :::accordion-item{label="Is HTML a programming language?" icon="i-lucide-message-circle"}
  No. It is a markup language: it describes structure and has no variables,
  conditions or loops. Saying so plainly, and adding that the logic lives in
  JavaScript and the appearance in CSS, is the answer.
  :::
  :::accordion-item{label="Link or button: how do you decide?" icon="i-lucide-message-circle"}
  A link navigates (`<a href>`); a button performs an action on the page
  (`<button>`). If opening it in a new tab makes sense, it is a link.
  `<a href="#" onclick="...">` is the classic wrong answer: it announces itself
  as a link and does nothing useful on middle-click.
  :::
  :::accordion-item{label="Why is a div with onclick not the same as a button?" icon="i-lucide-message-circle"}
  Three ways: it is not in the tab order, it does not respond to Enter or Space,
  and a screen reader does not announce it as a control. Adding `tabindex`,
  `role` and key handlers rebuilds a button badly.
  :::
::
