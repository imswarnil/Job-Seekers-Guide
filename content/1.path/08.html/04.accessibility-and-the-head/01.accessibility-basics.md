Twice now the reason for a choice has been "a screen reader user". This lesson
is about that user and three others, and the short list of rules that covers
most of what they need.

## Why this matters in a job

Accessibility (often written **a11y**: a, eleven letters, y) means a page can be
used by people with disabilities: blind or low-vision users, people who cannot
use a mouse, deaf users, people with tremors or cognitive differences. Around
one in six people has some disability, and everybody has temporary ones: a
broken wrist, a bright sun on a phone screen, a noisy bus.

At work it shows up as a requirement. Government and university sites in many
countries must meet a standard called **WCAG** (Web Content Accessibility
Guidelines), level AA. Large clients write it into
contracts, and teams run accessibility checks before a release. In interviews, "what is accessibility and how do you make a
page accessible?" is a common follow-up to semantic HTML.

## Four people using the same page

::feature-list{columns="2"}
  :::feature{icon="i-lucide-ear" title="A blind student with a screen reader"}
  Software (NVDA on Windows, VoiceOver on Mac and iPhone, TalkBack on Android)
  reads the page aloud and lets them jump by heading, landmark, link or form
  field. Needs: semantic elements, alt text, labels, a sensible heading outline.
  :::
  :::feature{icon="i-lucide-keyboard" title="A faculty member who cannot use a mouse"}
  Moves with Tab, Shift+Tab, Enter, Space and arrow keys. Needs: every control
  reachable, a visible focus ring, a logical order.
  :::
  :::feature{icon="i-lucide-eye" title="A parent with low vision"}
  Zooms to 200% or more. Needs: enough contrast, text that reflows rather than
  overflowing, nothing that relies on colour alone.
  :::
  :::feature{icon="i-lucide-volume-x" title="A deaf applicant"}
  Watches the campus tour video. Needs: captions.
  :::
::

## How it works

The rules that cover most of it, in the order I would check them:

::steps
### Use the native element
`button`, `a`, `input`, `select`, `table`, `nav`, `main`. They come with
keyboard support and correct announcements for free.

### Give every image an alt, and every input a label
`alt` carries the information; `alt=""` for decoration. `label for` on every
field.

### Keep the heading outline and landmarks
One `h1`, no skipped levels, `header`, `nav`, `main`, `footer`, and
`lang` on `html`.

### Make everything work with the keyboard, visibly
Tab reaches every control, in reading order, and you can see where focus is.

### Do not rely on colour alone, and keep contrast high
Red for "failed" also needs the word "Failed". Body text needs a contrast ratio
of at least **4.5:1** against its background for WCAG AA.

### Use ARIA only when HTML cannot say it
ARIA (Accessible Rich Internet Applications) adds attributes like `role`,
`aria-label`, `aria-expanded`. The first rule of ARIA is: do not use ARIA if a
native element does the job.
::

### Keyboard focus

::runner{lang="html"}
```html
<p><a href="#">Timetable</a></p>
<p><button type="button">Download hall ticket</button></p>
<div onclick="alert('clicked')" style="border:1px solid #999;padding:4px;width:12em">Fake button (div)</div>
<div role="button" tabindex="0" style="border:1px solid #999;padding:4px;margin-top:8px;width:12em">div with tabindex=0</div>
<p><input placeholder="Search notices"></p>
<p>Click in this frame, then press Tab repeatedly and watch where focus goes.</p>
```
::

```text [What Tab visits, in order]
1. Timetable (link)
2. Download hall ticket (button)
   (the fake div button is skipped)
3. div with tabindex=0
4. Search notices (input)
```

- **Focus order follows the DOM order**, so the source order should match the
  visual order.
- `tabindex="0"` puts a non-interactive element into the tab order.
  `tabindex="-1"` makes it focusable by script but not by Tab. **Positive
  values (`tabindex="3"`) are almost always a mistake**, because they jump the
  queue and break the natural order.
- The outline you see on focus is the **focus ring**. The single most damaging
  line of CSS for keyboard users is `outline: none` with nothing in its place.

### ARIA, when it is needed

Sometimes HTML has no element for what you need. A "show more details"
toggle is one:

```html [toggle.html]
<button type="button" aria-expanded="false" aria-controls="fee-details">
  Show fee breakdown
</button>
<div id="fee-details" hidden>
  Tuition ₹85,000 · Hostel ₹60,000 · Exam fee ₹2,500
</div>
```

`aria-expanded` tells a screen reader whether the section is open, and
JavaScript flips it to `"true"` when it opens. Notice it is still a real
`button`: ARIA adds the one fact HTML could not express and nothing more. (For
this exact case, `<details>` and `<summary>` do it with no ARIA at all.)

A common ARIA attribute is `aria-label`, which names an element that has no
visible text:

```html [icon-button.html]
<button type="button" aria-label="Close notice">×</button>
```

Without it, a screen reader announces "button, times".

## Real use case

This is how accessibility is checked at work. An automated tool first, then
people:

```bash [audit.sh]
npx @axe-core/cli https://college.example/admissions
```

```text [Output, trimmed]
Violation of "image-alt" with 2 occurrences!
  Ensure <img> elements have alternate text or a role of none or presentation
Violation of "color-contrast" with 5 occurrences!
  Ensure the contrast between foreground and background colors meets WCAG 2 AA
Violation of "label" with 1 occurrences!
  Ensure every form element has a label
```

Chrome's Lighthouse panel runs the same kind of checks with a score. What these
tools **cannot** catch, and what a person checks next:

- whether the alt text is useful or only present,
- whether the focus order makes sense,
- whether an error message is announced when it appears,
- whether the task can actually be completed without a mouse.

So the second step is always manual: unplug the mouse and complete the main task
with Tab, then turn on VoiceOver (`Cmd + F5` on a Mac) or NVDA (free on
Windows) and try again without looking. Ten minutes, and it finds what the tool
cannot.

## What confuses people here

- **"Accessibility is for a few users."** It is legally required in many places
  and helps everybody: captions, keyboard shortcuts and high contrast are used by
  far more people than those who need them.
- **Adding ARIA makes it more accessible.** Wrong ARIA is worse than none.
  `role="button"` on a `div` promises keyboard behaviour the `div` does not have.
- **`aria-label` on everything.** It replaces the visible text for screen
  readers, so a mismatch confuses users of voice control, who say what they see.
- **`display: none` versus visually hidden.** `display: none` and `hidden` hide
  content from everybody, screen readers included. To hide something only
  visually (a skip link until focused), a "visually hidden" CSS class is used.

## Interview questions

::accordion
  :::accordion-item{label="What is web accessibility? How do you make a page accessible?" icon="i-lucide-message-circle"}
  Making a page usable by people with disabilities: screen reader users,
  keyboard-only users, low-vision and deaf users. Semantic HTML, alt text,
  labels on inputs, a heading outline and landmarks, full keyboard support with a
  visible focus ring, sufficient contrast, captions on video, and ARIA only where
  HTML cannot express something. Then test with the keyboard and a screen
  reader, not only with Lighthouse.
  :::
  :::accordion-item{label="What is ARIA? When should you use it?" icon="i-lucide-message-circle"}
  Accessible Rich Internet Applications: attributes (`role`, `aria-label`,
  `aria-expanded`, `aria-describedby`, `aria-live`) that give assistive
  technology information HTML cannot. Use it only when no native element does
  the job; the first rule of ARIA is to prefer native HTML.
  :::
  :::accordion-item{label="What does tabindex do?" icon="i-lucide-message-circle"}
  `0` adds an element to the natural tab order; `-1` makes it focusable only by
  script (for moving focus to an error or a dialog); a positive number forces an
  order and should be avoided.
  :::
  :::accordion-item{label="What is WCAG, and what does AA mean?" icon="i-lucide-message-circle"}
  The Web Content Accessibility Guidelines, from the W3C. Levels A, AA and AAA;
  AA is the level most laws and contracts require, including a 4.5:1 contrast
  ratio for normal text.
  :::
  :::accordion-item{label="Why should you never remove the focus outline?" icon="i-lucide-message-circle"}
  It is how a keyboard user sees where they are. Without it, they are
  navigating blind. If the design needs a different look, replace it with a
  custom visible style, for example with `:focus-visible`.
  :::
::
