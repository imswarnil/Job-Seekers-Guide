Twenty-five questions answered aloud. Now the other skill: finding what is wrong
in a page that looks fine, and building markup from a blank file against a
clock. Attempt each one before opening the answer.

## Why this matters in a job

In a machine round, and in your first code reviews, nobody asks you to define
`scope`. They hand you a page and ask what is wrong with it, or ask you to build
one in twenty minutes. Every broken example below renders perfectly in a
browser, which is the point: the only way to see the problem is to know what the
markup means.

::tip
Test each one the way the accessibility lesson says: unplug your mouse, or turn
on VoiceOver with `Cmd + F5` on a Mac. Two minutes of that teaches more than any
amount of reading.
::

## Part one: find what is broken

### 1. The button that is not one

```html
<div class="btn" onclick="publishResult(4211)">Publish result</div>
```

::accordion
  :::accordion-item{label="What breaks, and the fix" icon="i-lucide-check"}
  Three things, all invisible with a mouse:

  - It is not in the tab order, so a keyboard user can never reach it.
  - It does not respond to Enter or Space.
  - A screen reader announces "Shortlist" as plain text, with no indication that
    it does anything.

  ```html
  <button type="button" onclick="publishResult(4211)">Publish result</button>
  ```

  People sometimes patch the div with `tabindex="0"`, `role="button"` and a
  keydown handler. That is four attributes reimplementing a built-in element,
  and it will still be missing something. **Use the element that already means
  the thing.**
  :::
::

### 2. The form nobody can fill in

```html
<p>Full name</p>
<input type="text" name="fullName">
<p>Email</p>
<input type="text" name="email">
```

::accordion
  :::accordion-item{label="What breaks, and the fix" icon="i-lucide-check"}
  No `<label>`, so a screen reader reaching the input announces "edit text,
  blank" with no idea what it wants. Clicking the text does not focus the field
  either, which is a real usability loss on a phone.

  ```html
  <label for="fullName">Full name</label>
  <input id="fullName" type="text" name="fullName" autocomplete="name">

  <label for="email">Email</label>
  <input id="email" type="email" name="email" autocomplete="email"
         inputmode="email">
  ```

  Three additions worth noticing. `for` and `id` must match. `type="email"`
  gives a phone the right keyboard. `autocomplete` lets a browser fill it, which
  is the single biggest improvement to form completion rates there is.
  :::
::

### 3. The error nobody hears

```html
<input id="email" type="email" class="error">
<p class="error-text">That email does not look right</p>
```

::accordion
  :::accordion-item{label="What breaks, and the fix" icon="i-lucide-check"}
  The error is visible and is not connected to anything. A screen reader user
  submits, hears nothing change, and has no way to find which of six fields is
  wrong.

  ```html
  <input id="email" type="email" aria-invalid="true"
         aria-describedby="email-error">
  <p id="email-error" role="alert">That email does not look right</p>
  ```

  `aria-invalid` marks the field as wrong. `aria-describedby` ties the message
  to it, so it is read out when focus lands there. `role="alert"` makes it
  announced the moment it appears.

  Three attributes, and it is the difference between a form somebody can correct
  and one they abandon.
  :::
::

### 4. The heading that is not a heading

```html
<div class="page-title">Placements 2026</div>
<div class="section-title">Companies visiting</div>
<h4>Offers made</h4>
```

::accordion
  :::accordion-item{label="What breaks, and the fix" icon="i-lucide-check"}
  Screen reader users navigate by jumping between headings, the way you skim
  with your eyes. This page has one heading, at level 4, under nothing.

  ```html
  <h1>Placements 2026</h1>
  <h2>Companies visiting</h2>
  <h2>Offers made</h2>
  ```

  Two rules: **one `h1` per page**, and **do not skip levels**. Heading level is
  structure, not size. If `h2` is too big, that is what CSS is for.
  :::
::

### 5. The image that says nothing

```html
<img src="/chart-funnel.png">
<img src="/decorative-swirl.svg" alt="decorative swirl">
```

::accordion
  :::accordion-item{label="What breaks, and the fix" icon="i-lucide-check"}
  Both are wrong, in opposite directions.

  The first has no `alt` at all, so a screen reader reads out the filename,
  which is noise. The second describes a decoration that carries no information,
  which is also noise.

  ```html
  <img src="/chart-funnel.png"
       alt="Placement drive: 310 sat the test, 88 interviewed, 42 selected">
  <img src="/decorative-swirl.svg" alt="">
  ```

  The rule: `alt` carries **the information the image carries**, not a
  description of the picture. "Chart" is useless; the numbers are the point. And
  `alt=""` is correct and deliberate for decoration, which is different from
  omitting it.
  :::
::

### 6. The layout built from nothing

```html
<div class="header">...</div>
<div class="nav">...</div>
<div class="content">
  <div class="card">...</div>
</div>
<div class="footer">...</div>
```

::accordion
  :::accordion-item{label="What breaks, and the fix" icon="i-lucide-check"}
  Nothing visually. What is lost is every structural shortcut: a screen reader
  user cannot jump to the main content, skip the navigation, or ask what regions
  the page has.

  ```html
  <header>...</header>
  <nav aria-label="Main">...</nav>
  <main>
    <article class="card">...</article>
  </main>
  <footer>...</footer>
  ```

  Same appearance, same CSS if you want it. `<main>` in particular gives you the
  "skip to content" behaviour for free.

  Then add the one thing that helps everybody, as the first element in `<body>`:

  ```html
  <a href="#main" class="skip-link">Skip to content</a>
  ```

  Visible on focus, hidden otherwise. A keyboard user saves twelve tab presses
  on every page.
  :::
::

## Part two: build it from a blank file

Twenty minutes each, no copying from the lessons. Then compare.

### 7. The exam timetable

Build this as one table: three days (Monday to Wednesday) across the top, two
time slots (10:00–13:00, 14:00–17:00) down the side. Monday afternoon and
Tuesday afternoon are one combined "Placement seminar". Wednesday has one
practical exam running all day. Give it a caption. A screen reader on any
cell should announce both the day and the time.

::accordion
  :::accordion-item{label="One correct answer" icon="i-lucide-check"}
  ```html
  <table>
    <caption>End-semester timetable, B.Tech CSE, semester 3</caption>
    <thead>
      <tr>
        <th scope="col">Time</th>
        <th scope="col">Monday</th>
        <th scope="col">Tuesday</th>
        <th scope="col">Wednesday</th>
      </tr>
    </thead>
    <tbody>
      <tr>
        <th scope="row">10:00–13:00</th>
        <td>Operating Systems</td>
        <td>Computer Networks</td>
        <td rowspan="2">DBMS practical</td>
      </tr>
      <tr>
        <th scope="row">14:00–17:00</th>
        <td colspan="2">Placement seminar</td>
      </tr>
    </tbody>
  </table>
  ```

  Check: the second body row has only two cells written. If you wrote three,
  the grid has an extra column sticking out on the right.
  :::
::

### 8. The hostel application form

Fields: full name, roll number (format `CS` followed by five digits), email,
mobile, date of joining, room type (single, double, triple: exactly one), "I
need a vegetarian mess" (yes or no), and a scanned ID card (PDF or image). It
must upload the file and validate every field in the browser without
JavaScript.

::accordion
  :::accordion-item{label="One correct answer, and what people miss" icon="i-lucide-check"}
  ```html
  <form action="/hostel/applications" method="post" enctype="multipart/form-data">
    <p>
      <label for="name">Full name</label>
      <input id="name" name="fullName" type="text" autocomplete="name" required maxlength="60">
    </p>
    <p>
      <label for="roll">Roll number</label>
      <input id="roll" name="rollNo" type="text" required pattern="CS[0-9]{5}"
             aria-describedby="roll-help">
      <span id="roll-help">For example CS21001.</span>
    </p>
    <p>
      <label for="email">Email</label>
      <input id="email" name="email" type="email" autocomplete="email" required>
    </p>
    <p>
      <label for="phone">Mobile</label>
      <input id="phone" name="phone" type="tel" inputmode="numeric"
             autocomplete="tel" required pattern="[6-9][0-9]{9}">
    </p>
    <p>
      <label for="join">Date of joining</label>
      <input id="join" name="joiningDate" type="date" required>
    </p>
    <fieldset>
      <legend>Room type</legend>
      <label><input type="radio" name="roomType" value="single" required> Single</label>
      <label><input type="radio" name="roomType" value="double"> Double</label>
      <label><input type="radio" name="roomType" value="triple"> Triple</label>
    </fieldset>
    <p>
      <label><input type="checkbox" name="vegMess" value="yes"> I need a vegetarian mess</label>
    </p>
    <p>
      <label for="id-card">ID card (PDF or image)</label>
      <input id="id-card" name="idCard" type="file" accept="application/pdf,image/*" required>
    </p>
    <button type="submit">Apply for hostel</button>
  </form>
  ```

  What people miss: `enctype` (the file arrives as a name only), the shared
  `name` on the radios (all three can be selected), `required` on one radio
  (makes the group required), and the `fieldset` with a `legend` (the question
  "Room type" is never announced).
  :::
::

### 9. The head that does nothing on a phone

A college notice page looks fine on a laptop. On a phone it is tiny, the tab
says "Untitled", a WhatsApp share shows no preview, and the page is blank for
two seconds on a slow connection. Here is its head. Fix it.

```html [notice.html]
<head>
  <script src="/js/notices.js"></script>
  <script src="https://analytics.example/a.js"></script>
  <meta name="keywords" content="college, notice, results">
</head>
```

::accordion
  :::accordion-item{label="The fixed head" icon="i-lucide-check"}
  ```html
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Semester 3 results published · LNCT Computer Science</title>
    <meta name="description" content="Semester 3 results are on the portal from 10 am Monday.">
    <meta property="og:title" content="Semester 3 results published">
    <meta property="og:image" content="https://college.example/og/results.png">
    <link rel="stylesheet" href="/css/site.css">
    <script src="/js/notices.js" defer></script>
    <script src="https://analytics.example/a.js" async></script>
  </head>
  ```

  The viewport fixes the phone. The title fixes the tab. Open Graph fixes the
  preview. `defer` and `async` stop the scripts blocking the page. The keywords
  tag is gone because search engines ignore it.
  :::
::

## The test that catches most of it

::steps
### Unplug the mouse
Tab through the whole page. Can you reach everything? Can you see where you are?
If the focus ring is invisible, that is a bug, and `outline: none` in a
stylesheet is the usual cause.

### Turn the stylesheet off
The page should still read as a sensible document in order. If it does, your
markup is carrying the meaning. If it becomes nonsense, the CSS was.

### Read it with a screen reader for sixty seconds
`Cmd + F5` on a Mac, NVDA on Windows. Uncomfortable, and it will find something
no checklist would.
::

## Real use case

Part one is a code review. Every one of those six turned up in real pull
requests, and a reviewer who knows HTML leaves exactly the comments in the
answers. Part two is the machine round: training institutes in Bangalore and
some walk-in drives give you a blank editor and a task like the
timetable or the form, and judge the markup, not the colours.

::pull-quote
Nearly every problem in part one came from using a `div` where a real element
existed. You get most of accessibility for free by using the element that already
means the thing you want.
::

## Interview questions

::accordion
  :::accordion-item{label="You are given a page that looks right. How do you check its HTML is right?" icon="i-lucide-message-circle"}
  Tab through it with the mouse unplugged, turn off CSS and read it as a
  document, check the heading outline and landmarks in the accessibility tree in
  developer tools, run Lighthouse or axe, and try the main task with a screen
  reader. The W3C validator catches syntax errors on top of that.
  :::
  :::accordion-item{label="A button made of a div works with a mouse. What would you change, and why?" icon="i-lucide-message-circle"}
  Replace it with `<button type="button">`. The div is not focusable, not
  operable with Enter or Space, and not announced as a control, so the feature
  does not exist for keyboard and screen reader users.
  :::
  :::accordion-item{label="Why did the radio group allow three selections?" icon="i-lucide-message-circle"}
  The radios had different `name` values. Radios are grouped by `name`, so all
  three must share one.
  :::
::
