The dean asked how many, what the average was, and which programme is doing
worst. None of those is a row. `GROUP BY` is how rows become answers.

## Why this matters in a job

Because every report, dashboard and analytics question in existence is a
`GROUP BY`, and because the one rule about what you may put in `SELECT` is where
almost every beginner error in this topic comes from.

## The shape

::runner{lang="sql"}
```sql
SELECT   p.code,
         COUNT(*)              AS applications,
         ROUND(AVG(a.score),1) AS average_score,
         MAX(a.score)          AS highest
FROM     Application a
JOIN     Programme   p ON p.programme_id = a.programme_id
WHERE    a.intake = '2026'
  AND    a.status <> 'WITHDRAWN'
GROUP BY p.code
ORDER BY applications DESC;
```
::

```text [Output]
 code       | applications | average_score | highest
------------+--------------+---------------+---------
 BTECH-CSE  |          412 |          74.2 |      98
 BTECH-ECE  |          288 |          71.8 |      95
 BTECH-MECH |          201 |          68.4 |      91
```

Two thousand rows became three, and each output row is an answer to a question.

## The one rule

**Every column in `SELECT` must either be in `GROUP BY` or wrapped in an
aggregate.**

```sql [Illegal.sql]
-- Which full_name? There are 412 of them in the CSE group.
SELECT p.code, ap.full_name, COUNT(*)
FROM   Application a JOIN Programme p USING (programme_id)
                     JOIN Applicant ap USING (applicant_id)
GROUP BY p.code;
```

```text [Output]
ERROR: column "ap.full_name" must appear in the GROUP BY clause
or be used in an aggregate function
```

The error is exactly right: the group is a programme, and a programme has many
names, so asking for "the name" is meaningless. You have to say which one you
mean, `MAX(ap.full_name)`, or the top scorer, which needs a window function.

::warning{icon="i-lucide-alert-triangle"}
MySQL historically allowed this and returned an arbitrary row's value, which
produced reports that were wrong in a way nobody could reproduce. Modern MySQL
rejects it by default like every other database. If you meet an old system that
allows it, treat every such query as suspect.
::

## The aggregates

| Function | Does | With NULL |
| --- | --- | --- |
| `COUNT(*)` | Counts **rows** | Counts them all |
| `COUNT(col)` | Counts **non-null values** | Skips nulls |
| `COUNT(DISTINCT col)` | Counts distinct non-null values | Skips nulls |
| `SUM(col)` | Total | Skips nulls; returns `NULL` if every row is null |
| `AVG(col)` | Mean | Skips nulls, and **divides by the non-null count** |
| `MIN` / `MAX` | Extremes | Skip nulls |
| `STRING_AGG` / `GROUP_CONCAT` | Joins values into one string | Skips nulls |

::pull-quote
Every aggregate except `COUNT(*)` ignores nulls. That is almost always what you
want and almost never what the label on the dashboard says.
::

## WHERE against HAVING

The distinction that gets asked, and it falls straight out of the evaluation
order from the first chapter.

::compare{caption="Both filter. They filter different things at different times."}
  :::compare-side{label="WHERE: before grouping" verdict="neutral"}
  Removes **rows**. Runs before `GROUP BY`, so it cannot see an aggregate.
  ```sql
  WHERE a.status <> 'WITHDRAWN'
  ```
  Withdrawn applications never enter any group.
  :::
  :::compare-side{label="HAVING: after grouping" verdict="neutral"}
  Removes **groups**. Runs after, so it can see aggregates.
  ```sql
  HAVING COUNT(*) >= 100
  ```
  Programmes with fewer than 100 applications disappear from the output.
  :::
::

```sql [Both.sql]
SELECT   p.code, COUNT(*) AS applications, ROUND(AVG(a.score),1) AS average
FROM     Application a JOIN Programme p USING (programme_id)
WHERE    a.intake = '2026'          -- rows: only this intake
  AND    a.score IS NOT NULL        -- rows: only marked ones
GROUP BY p.code
HAVING   COUNT(*) >= 100            -- groups: only substantial programmes
     AND AVG(a.score) < 70          -- groups: only the ones doing badly
ORDER BY average ASC;
```

::tip
Put a condition in `WHERE` whenever you can. It removes rows before grouping, so
there is less to group. A condition that could go in either but is written in
`HAVING` makes the database do more work for the same answer, and an interviewer
may ask you why you chose one.
::

## Grouping by more than one thing

::runner{lang="sql"}
```sql
SELECT   p.code, a.status, COUNT(*) AS applications
FROM     Application a JOIN Programme p USING (programme_id)
WHERE    a.intake = '2026'
GROUP BY p.code, a.status
ORDER BY p.code, a.status;
```
::

```text [Output]
 code      | status      | applications
-----------+-------------+--------------
 BTECH-CSE | ACCEPTED    |           58
 BTECH-CSE | RECEIVED    |          180
 BTECH-CSE | REJECTED    |          120
 BTECH-CSE | SHORTLISTED |           54
 BTECH-ECE | ACCEPTED    |           41
```

One row per combination that actually occurs. Combinations with no rows are
absent altogether, which matters: a programme with no rejections has no `REJECTED`
row at all, and a report that expects five rows per programme will be wrong.

## Conditional aggregation

The technique that turns that long output into one row per programme, and it is
genuinely useful.

::runner{lang="sql"}
```sql
SELECT   p.code,
         COUNT(*)                                                AS total,
         COUNT(*) FILTER (WHERE a.status = 'SHORTLISTED')        AS shortlisted,
         COUNT(*) FILTER (WHERE a.status = 'ACCEPTED')           AS accepted,
         SUM(CASE WHEN a.score >= 75 THEN 1 ELSE 0 END)          AS above_75
FROM     Application a JOIN Programme p USING (programme_id)
WHERE    a.intake = '2026'
GROUP BY p.code;
```
::

```text [Output]
 code      | total | shortlisted | accepted | above_75
-----------+-------+-------------+----------+----------
 BTECH-CSE |   412 |          54 |       58 |      148
 BTECH-ECE |   288 |          38 |       41 |       96
```

`FILTER` is the standard form and PostgreSQL supports it; the
`SUM(CASE WHEN ... THEN 1 ELSE 0 END)` version works everywhere and is what you
will see in older code. Both turn a long narrow result into a wide readable one,
which is what a dashboard actually wants.

## The two-pass shape of a real report

Almost every report you will be asked for has this shape: summarise, then compare
each row against the summary.

```sql [Report.sql]
-- Each programme's average, and how far it is from the overall average.
WITH programme_averages AS (
  SELECT programme_id, AVG(score) AS average, COUNT(*) AS applications
  FROM   Application
  WHERE  intake = '2026' AND score IS NOT NULL
  GROUP BY programme_id
),
overall AS (
  SELECT AVG(score) AS average FROM Application
  WHERE  intake = '2026' AND score IS NOT NULL
)
SELECT p.code,
       ROUND(pa.average, 1)                       AS programme_average,
       ROUND(o.average, 1)                        AS university_average,
       ROUND(pa.average - o.average, 1)           AS difference
FROM   programme_averages pa
CROSS JOIN overall o
JOIN   Programme p ON p.programme_id = pa.programme_id
ORDER BY difference ASC;
```

A `WITH` clause: a common table expression, names an intermediate result. It is
the single most useful readability tool in SQL: instead of one query nested four
deep, you get named steps that read top to bottom.

::side-note{kind="go-deeper"}
`CROSS JOIN` with a one-row table is the idiom for "attach this single value to
every row". It looks alarming because a cross join usually means an accident, and
against exactly one row it produces exactly one row per input, which is what is
wanted here.
::

## Your turn

::runner{lang="sql"}
```sql
-- 1. Applications per city, highest first, cities with at least 20 only.

-- 2. Per programme: total applications, how many are shortlisted,
--    and the shortlisting rate as a percentage to one decimal place.

-- 3. Why does this fail? Give two different fixes.
SELECT p.code, ap.full_name, MAX(a.score)
FROM   Application a
JOIN   Programme p USING (programme_id)
JOIN   Applicant ap USING (applicant_id)
GROUP BY p.code;

-- 4. Why might the average here be higher than the registrar expects?
SELECT AVG(score) FROM Application WHERE intake = '2026';
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  ```sql
  -- 1
  SELECT   ap.city, COUNT(*) AS applications
  FROM     Application a JOIN Applicant ap USING (applicant_id)
  WHERE    a.intake = '2026'
  GROUP BY ap.city
  HAVING   COUNT(*) >= 20
  ORDER BY applications DESC;
  ```

  ```sql
  -- 2
  SELECT   p.code,
           COUNT(*)                                          AS applications,
           COUNT(*) FILTER (WHERE a.status = 'SHORTLISTED')  AS shortlisted,
           ROUND(100.0 * COUNT(*) FILTER (WHERE a.status = 'SHORTLISTED')
                 / COUNT(*), 1)                              AS rate_pct
  FROM     Application a JOIN Programme p USING (programme_id)
  WHERE    a.intake = '2026'
  GROUP BY p.code
  ORDER BY rate_pct DESC;
  ```
  Note `100.0` rather than `100`: integer division would give 0, which is the
  Java lesson appearing in SQL.

  **3.** `full_name` is neither grouped nor aggregated, and a programme has many
  applicants. Two fixes, and they answer *different questions*:

  ```sql
  -- (a) The highest score per programme AND per applicant
  GROUP BY p.code, ap.full_name

  -- (b) The top scorer's name per programme — needs a window function
  SELECT code, full_name, score FROM (
    SELECT p.code, ap.full_name, a.score,
           ROW_NUMBER() OVER (PARTITION BY p.code ORDER BY a.score DESC) AS rn
    FROM   Application a JOIN Programme p USING (programme_id)
                         JOIN Applicant ap USING (applicant_id)
  ) ranked WHERE rn = 1;
  ```
  (b) is almost certainly what was wanted, and it is the next lesson.

  **4. Three reasons, and all three are this track so far.** Withdrawn
  applications are not excluded. `AVG` skips the 200 unmarked ones, so it is over
  1,840 rather than 2,040 and the label does not say so. And it averages
  *applications*, so somebody who applied to three programmes counts three times,
  weighting the result toward people who applied a lot. All three are invisible
  in the output.
  :::
::

## The interview question this answers

**"What is the difference between WHERE and HAVING?"**: a near-certainty in a
SQL round.

`WHERE` filters rows before grouping; `HAVING` filters groups after. Then make it
useful rather than memorised: that is why `WHERE` cannot reference an aggregate,
and why a condition that could go in either should go in `WHERE`, because it
removes rows before the grouping work happens.

Follow-up to have ready: the `GROUP BY` rule, explained by what a group is, a
programme has 412 names, so "the name" is not a question with an answer.
