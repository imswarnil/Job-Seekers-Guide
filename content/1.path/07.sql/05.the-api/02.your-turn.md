Ten weeks of SQL, and an API that only `curl` can call. Before the part a person

## 1. The count that is too high

```sql
SELECT p.name, COUNT(*) AS applications
FROM   Program p
LEFT JOIN Application a ON a.program_id = p.program_id
GROUP BY p.name;
```

A programme with no applications reports 1. Why?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  The `LEFT JOIN` keeps the programme and fills the application columns with
  nulls, producing **one row**. `COUNT(*)` counts rows, and there is one.

  ```sql
  COUNT(a.application_id) AS applications
  ```

  `COUNT(column)` counts non-null values, so the unmatched row contributes zero.

  This is the single most common quiet bug in reporting SQL, and it is quiet
  because 1 is a plausible number. Nobody investigates a 1.
  :::
::

## 2. The average that misleads

```sql
SELECT AVG(score) AS average_score
FROM   Application
WHERE  status = 'SHORTLISTED';
```

Returns 71.4. The registrar sets a cutoff from it. What is wrong?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Nothing, arithmetically. `AVG` ignores nulls and divides by the count of
  non-null scores. If 400 are shortlisted and 120 are marked, this is the
  average of 120 people.

  The bug is the **label**, not the query.

  ```sql
  SELECT ROUND(AVG(score), 1) AS average_score,
         COUNT(score)         AS marked,
         COUNT(*)             AS shortlisted
  FROM   Application
  WHERE  status = 'SHORTLISTED';
  ```

  `71.4, from 120 of 400 marked`. Same computation, and now it cannot be used to
  set a cutoff by mistake.
  :::
::

## 3. The join that multiplies money

```sql
SELECT s.roll_number, SUM(f.amount_paise) AS paid
FROM   Student s
JOIN   FeePayment f ON f.student_id = s.student_id
JOIN   Attendance a ON a.student_id = s.student_id
GROUP BY s.roll_number;
```

Every total is enormous. Why?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Fan-out.** A student with 2 payments and 90 attendance rows produces 180
  rows, so each payment is summed 90 times.

  The fix is not `DISTINCT`, which people reach for and which gives a different
  wrong answer when two payments happen to be equal.

  Aggregate separately:

  ```sql
  SELECT s.roll_number, f.paid, a.held
  FROM   Student s
  LEFT JOIN (SELECT student_id, SUM(amount_paise) AS paid
             FROM FeePayment GROUP BY student_id) f USING (student_id)
  LEFT JOIN (SELECT student_id, COUNT(*) AS held
             FROM Attendance GROUP BY student_id) a USING (student_id);
  ```

  The rule to say in an interview: **joining to a table with several matching
  rows multiplies your aggregates.** Aggregate each side first, then join.
  :::
::

## 4. The filter that undoes the join

```sql
SELECT ap.full_name, a.status
FROM   Applicant ap
LEFT JOIN Application a ON a.applicant_id = ap.applicant_id
WHERE  a.status = 'REJECTED';
```

Applicants who never applied have vanished, and this was supposed to be a
`LEFT JOIN`.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  The `LEFT JOIN` produced rows with `a.status` null, and `WHERE a.status =
  'REJECTED'` is `NULL = 'REJECTED'`, which is `UNKNOWN`, which is not `TRUE`,
  so the row is dropped. The left join has been turned back into an inner join.

  If the condition belongs to the join, put it there:

  ```sql
  LEFT JOIN Application a
         ON a.applicant_id = ap.applicant_id AND a.status = 'REJECTED'
  ```

  **A condition on the right table in `WHERE` cancels a `LEFT JOIN`. In `ON` it
  does not.** That sentence is worth memorising exactly.
  :::
::

## 5. The NOT IN that returns nothing

```sql
SELECT full_name FROM Applicant
WHERE  applicant_id NOT IN (SELECT applicant_id FROM Application);
```

Zero rows, and you know there are applicants who never applied.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  One `NULL` in the subquery. `x NOT IN (1, 2, NULL)` asks `x <> 1 AND x <> 2
  AND x <> NULL`, and the last is `UNKNOWN`, so the whole thing is never `TRUE`
  for any `x`.

  ```sql
  SELECT ap.full_name FROM Applicant ap
  WHERE  NOT EXISTS (SELECT 1 FROM Application a
                     WHERE a.applicant_id = ap.applicant_id);
  ```

  `NOT EXISTS` is immune, reads as what it means, and can stop at the first
  match. Use it by default and `NOT IN` only against a literal list you wrote.
  :::
::

## 6. Top three per programme

Write it. Top three scores in each programme, ties broken by earliest
application.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  ```sql
  WITH ranked AS (
    SELECT a.application_id, a.program_id, a.score, ap.full_name,
           ROW_NUMBER() OVER (PARTITION BY a.program_id
                              ORDER BY a.score DESC, a.applied_on ASC) AS rn
    FROM   Application a
    JOIN   Applicant ap USING (applicant_id)
    WHERE  a.score IS NOT NULL
  )
  SELECT program_id, full_name, score FROM ranked WHERE rn <= 3;
  ```

  Two things to say out loud. The filter is **outside** the CTE because `WHERE`
  runs before the window is computed, so `WHERE rn <= 3` in the same query is a
  syntax error.

  And `a.applied_on ASC` is a deliberate, stated tie-break. If rank decides who
  gets a seat, "the database picked one" is not an answer you can give a parent.
  :::
::

## 7. The seat that goes twice

```sql
-- Two admins, at the same moment:
SELECT seats_filled, seats FROM Program WHERE program_id = 7;   -- 119, 120
UPDATE Program SET seats_filled = 120 WHERE program_id = 7;
```

Both succeed. 121 students in 120 seats.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  A **lost update**, allowed at every major database's default isolation level.

  The cheapest correct fix, since clashes here are rare:

  ```sql
  UPDATE Program SET seats_filled = seats_filled + 1
   WHERE program_id = 7 AND seats_filled < seats;
  ```

  Then **check the row count**. Zero means somebody took the seat, and you tell
  the admin rather than pretending it worked.

  And underneath it, because application logic can be bypassed by a script or a
  person with a terminal:

  ```sql
  ALTER TABLE Program ADD CONSTRAINT seats_not_exceeded
    CHECK (seats_filled <= seats);
  ```
  :::
::

## 8. The query that will not use the index

```sql
CREATE INDEX ON Application (applied_on);

SELECT * FROM Application WHERE EXTRACT(YEAR FROM applied_on) = 2026;
```

`EXPLAIN` shows a sequential scan over four million rows.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  The index holds `applied_on`, not `EXTRACT(YEAR FROM applied_on)`. Applying a
  function to the column means the index cannot be consulted.

  Rewrite as a range, which is what the index is good at:

  ```sql
  WHERE applied_on >= DATE '2026-01-01' AND applied_on < DATE '2027-01-01'
  ```

  The five cases where an index is ignored, worth being able to list: a function
  on the column, a leading wildcard in `LIKE`, skipping the leading column of a
  composite index, a value that is not selective enough to be worth it, and a
  type mismatch.

  And always: `EXPLAIN ANALYZE`, then look at `Rows Removed by Filter`. Four
  million removed to return two thousand is the entire diagnosis.
  :::
::

## The pattern in all eight

::pull-quote
Not one of these throws an error. Six return a plausible number and two return
the wrong rows. SQL almost never tells you that you were wrong, which is why
checking the result against something you already know is part of writing the
query rather than something you do afterwards.
::
