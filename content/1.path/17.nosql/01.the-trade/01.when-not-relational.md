A relational database is the right default and it is not the only choice. This
lesson is about what the alternatives actually trade away, because the answer is
never "it is faster".

## Why this matters in a job

Because "should we use MongoDB" is a real question you will be asked, because the
usual reasons given for it are wrong, and because there is one alternative —
Redis — you will almost certainly use whatever else you choose.

## The four kinds

::feature-list{columns="2"}
  :::feature{icon="i-lucide-file-json" title="Document — MongoDB, DynamoDB"}
  Stores JSON-shaped documents. Good when each record is naturally a whole
  nested thing read together, and when the shape genuinely varies.
  :::
  :::feature{icon="i-lucide-zap" title="Key-value — Redis, Memcached"}
  A key, a value, in memory. Microsecond reads. Caches, sessions, rate limits,
  queues. **You will use one of these.**
  :::
  :::feature{icon="i-lucide-search" title="Search — Elasticsearch, OpenSearch"}
  Full-text search with ranking, stemming and fuzziness. `LIKE '%rao%'` is not
  search, and this is what people mean when they say search.
  :::
  :::feature{icon="i-lucide-share-2" title="Graph — Neo4j"}
  Relationships are the data. "Who supervised somebody who supervised this
  student" is four joins in SQL and one traversal here. Genuinely specialised.
  :::
::

## What a document store actually trades

```javascript [mongo.js]
// One document. Everything about an application, read in one operation.
{
  _id: ObjectId("..."),
  applicantName: "Anita Rao",
  email: "anita@university.edu",
  programme: { code: "BTECH-CSE", name: "B.Tech Computer Science", fee: 4500000 },
  score: 78,
  status: "SHORTLISTED",
  payments: [
    { receipt: "RCP-2026-0417", amountPaise: 1500000, paidOn: "2026-03-01" },
    { receipt: "RCP-2026-0892", amountPaise: 1000000, paidOn: "2026-04-01" }
  ]
}
```

One read gives you the whole application with its payments. No joins. On a screen
that shows exactly this, it is genuinely faster and simpler.

Now the trades.

::compare{caption="The programme's fee changes from ₹45,000 to ₹48,000."}
  :::compare-side{label="Relational" verdict="right"}
  One `UPDATE` on one row in `Programme`. Every application referring to it is
  now correct, because they refer to it rather than containing it.
  :::
  :::compare-side{label="Embedded in the document" verdict="wrong"}
  The fee is copied into 40,000 documents. Update all of them, in a script, and
  hope it finishes. This is the update anomaly from the DBMS track, and it is
  the thing normalisation exists to prevent.
  :::
::

::pull-quote
"Schema-less" is the least true claim in this subject. The schema still exists.
It has moved from the database, where it was enforced for everybody, into your
application code, where it is a convention that the next application written
against the same data will not know about.
::

```javascript [drift.js]
// Three years of one collection, written by four developers.
{ name: "Anita Rao",   score: 78 }
{ fullName: "Vikram",  score: "64" }        // string, not number
{ fullName: "Priya",   marks: 81 }          // different field entirely
{ full_name: "Rahul",  score: null }
```

Nothing rejected any of these. Every query and every report now has to handle
four shapes, forever, and nobody can tell you which shapes exist without reading
all 40,000 documents.

::warning{icon="i-lucide-alert-triangle"}
If you use a document store, define and enforce a schema in the application,
from the first day, with something like Mongoose or a validation library. The
freedom to skip it is the feature people choose it for and the reason those
projects become unmaintainable. MongoDB has server-side schema validation and
essentially nobody enables it.
::

## The reasons people give, examined

::pros-cons
---
title: "It scales better"
pros:
  - Genuinely true for horizontal sharding at very large scale
  - Some workloads do map badly onto a single relational node
cons:
  - PostgreSQL handles a workload larger than almost any application will ever have
  - Most projects choosing this for scale never reach a scale where it mattered
  - They do reach the day the fee changed in 40,000 documents
---
::

::pros-cons
---
title: "We do not know the shape yet"
pros:
  - Early prototyping is genuinely quicker without migrations
  - Sparse or genuinely varying data is awkward in a fixed schema
cons:
  - "We do not know the shape" usually means "we have not asked the registrar"
  - A migration is an hour; unpicking four shapes across 40,000 documents is a quarter
  - PostgreSQL has a JSONB column, so you can have the flexible part without giving up the rest
---
::

::tip
That last point is the answer in most real situations, and it is the one worth
giving in an interview: keep the structured data relational and put the genuinely
variable part in a `JSONB` column, which PostgreSQL can index and query. You get
the flexibility exactly where it is needed and constraints everywhere else,
rather than trading all of one for all of the other.
::

## Redis, which you will actually use

Not a replacement for your database. A layer beside it.

```javascript [redis.js]
// Cache: do not hit the database for a page that changes hourly.
const cached = await redis.get(`dashboard:${intake}`);
if (cached) return JSON.parse(cached);

const summary = await db.query(expensiveDashboardQuery, [intake]);
await redis.setex(`dashboard:${intake}`, 300, JSON.stringify(summary));  // 5 min
return summary;
```

```javascript [redis.js]
// Sessions: shared by every server, so a user does not log out when the
// load balancer sends them elsewhere. This is the static-field lesson
// from the operating systems track, solved properly.
await redis.setex(`session:${token}`, 3600, JSON.stringify(user));

// Rate limiting: three attempts a minute per IP.
const attempts = await redis.incr(`login:${ip}`);
if (attempts === 1) await redis.expire(`login:${ip}`, 60);
if (attempts > 3) throw new TooManyRequestsError();
```

::warning{icon="i-lucide-alert-triangle"}
Redis is in memory, so anything in it can vanish. It is a cache and a scratchpad,
never the only copy of something you need. "The Redis instance restarted and we
lost the fee payments" is a sentence that has been said, and the design error was
upstream of the restart.
::

## What you can do now

You can say what each kind of store trades away, argue against the usual reasons
for choosing one, and name the case where a relational database with a `JSONB`
column is the better answer.

## Your turn

For each, say which store and why. At least two answers should be "relational".

1. Applicants, applications, programmes, fees and results.
2. Session data for logged-in staff, across four servers.
3. Full-text search across the prospectus, circulars and notices.
4. A log of every action taken on an application, written constantly, read rarely.
5. "Which faculty have co-supervised a student with Dr Iyer, up to three degrees
   of separation?"

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1. Relational, emphatically.** Highly related data with real constraints,
  money, and reports that need joins and aggregates. This is the case relational
  databases were invented for and choosing otherwise needs a strong argument.

  **2. Redis.** In-memory, expiring by design, and shared across servers. Losing
  it logs everybody out, which is annoying and not a data loss.

  **3. A search engine**, alongside the relational database rather than instead
  of it. `LIKE '%deadline%'` cannot rank, stem or handle a typo. Documents live
  in the database and an index is built into Elasticsearch — or, for a smaller
  system, PostgreSQL's own full-text search, which is often enough and one fewer
  thing to run.

  **4. An audit log is the interesting one.** Write-heavy, append-only, rarely
  read, and it grows without limit. A document store is defensible; so is a
  separate relational table partitioned by month; so is writing to a file and
  shipping it elsewhere. **The right first question is how long it must be kept
  and who has to read it**, because a legal retention requirement changes the
  answer completely. Asking that is the mark here.

  **5. A graph database**, genuinely. Three degrees of separation is a
  self-join three deep in SQL and it gets worse with each degree. This is the
  one case in the list where the specialised store is clearly right, and it is
  also rare enough that most engineers never meet it.
  :::
::

## The interview question this answers

**"SQL or NoSQL?"**

A weak answer picks a side. A strong one names the trade: a document store gives
up joins, cross-document transactions and enforced constraints, in exchange for
reading a whole nested thing in one operation and sharding more easily.

Then the two things that show judgement. "Schema-less" means the schema moved
into your application where it is not enforced, which is how four shapes of the
same record end up in one collection. And for most real cases the better answer
is a relational database with a `JSONB` column: flexibility where it is needed,
constraints everywhere else.
