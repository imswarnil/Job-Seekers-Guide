Questions about tools. These six are the situations, and none of them has a
command as the answer. All of them are judgement.

## 1. The dependency for one function

You need to check whether a string is a valid email. A package does it in 2KB
with 400 lines of edge cases, and you could write a regular expression in one.

::accordion
  :::accordion-item{label="What a competent developer does" icon="i-lucide-check"}
  Neither, and the reasoning matters more than the choice.

  A regular expression for email is famously wrong in both directions: it
  rejects valid addresses and accepts invalid ones. The genuinely correct
  pattern is thousands of characters and still cannot tell you the address
  exists.

  The package is a dependency, its dependencies, a supply-chain surface and a
  build cost, for one function.

  What to actually do: a loose check that it has an `@` with something either
  side, then **send a confirmation email**. Delivery is the only real
  validation, and it is what you needed anyway for the enquiry form.

  The general rule to state: add a dependency when getting it right yourself is
  genuinely hard (dates, timezones, password hashing, cryptography) and write it
  yourself when the package is doing something you could verify in an afternoon.
  :::
::

## 2. The lock file in the diff

Your pull request changes three source files and `package-lock.json` by 4,000
lines. A reviewer asks you to remove it.

::accordion
  :::accordion-item{label="What a competent developer does" icon="i-lucide-check"}
  Push back, politely, and explain.

  The lock file records the **exact** version of every package including
  transitive ones. It is what makes your machine, the reviewer's machine and CI
  install identical trees. Removing it from version control means the build is
  not reproducible and a patch release of something four levels deep can break
  production with no commit to point at.

  What is reasonable is asking **why** it changed by 4,000 lines for a
  three-file change. Usually somebody ran `npm install` on a different major
  version of the tool, or `npm update` by accident. Regenerate it cleanly:

  ```bash
  git checkout main -- package-lock.json
  npm ci                 # installs exactly what the lock file says
  npm install some-package@1.2.3   # then the one intended change
  ```

  `npm ci` rather than `npm install` is the detail worth knowing: it installs
  from the lock file exactly and fails if they disagree, which is what CI should
  always use.
  :::
::

## 3. The review you do not understand

You are asked to review 900 lines touching a part of the system you have never
seen.

::accordion
  :::accordion-item{label="What a competent developer does" icon="i-lucide-check"}
  Say so, and review it anyway at the level you can.

  "I do not know this area, so I cannot judge whether the approach is right.
  Here is what I did check: the tests cover the two boundary cases, the error
  path returns a message rather than swallowing, and there are three places the
  null case is not handled. I would want somebody who knows the module to look
  at the approach."

  That is a useful review and an honest one. Approving something you did not
  understand is the actual failure, and it happens constantly because people are
  embarrassed to say they do not know.

  Then the thing worth raising separately: 900 lines is too large to review
  properly, and saying so is part of the job. Ask whether it can be split.
  :::
::

## 4. The build that works on your machine

CI fails with an error you cannot reproduce locally.

::accordion
  :::accordion-item{label="What a competent developer does" icon="i-lucide-check"}
  Work through the differences in order of likelihood:

  1. **Node or tool version.** Check what CI uses against your local. This is
     the cause more often than everything else combined, and the fix is pinning
     it in the repository so the question cannot arise again.
  2. **A dependency not installed from the lock file.** CI should run `npm ci`,
     not `npm install`.
  3. **Case sensitivity.** macOS is case-insensitive and Linux is not.
     `import Applicant from './applicant'` works on your machine and fails in
     CI. This one catches everybody once.
  4. **Environment variables.** Present in your `.env` and absent in CI.
  5. **Test order or timing.** A test that passes alone and fails in a suite is
     sharing state with another test.

  The rule to take away: **"works on my machine" is a statement about your
  machine, not about the code.** The fix is making the environments match
  rather than winning the argument.
  :::
::

## 5. The pull request nobody wants to read

You have finished four days of work. 1,400 lines across 23 files: a refactor,
the feature, a bug fix you noticed, and some formatting.

::accordion
  :::accordion-item{label="What a competent developer does" icon="i-lucide-check"}
  Split it into four, in this order:

  1. **Formatting alone.** Zero-risk, reviewed in ten seconds, and it stops the
     other three being full of noise.
  2. **The refactor**, with no behaviour change. The reviewer can check that
     nothing moved that should not have.
  3. **The bug fix**, with a test that fails without it.
  4. **The feature.**

  The reason is not politeness. A 1,400-line review gets an approval without
  being read, because nobody can hold it in their head, and the whole value of
  review is lost. Four small ones each get read properly.

  Then write the description for somebody who was not there:

  ```md
  ## What
  Adds duplicate detection to the enquiry form.

  ## Why
  The office is getting two enquiries per applicant on slow connections.

  ## How
  Flags rather than blocks: a repeat within an hour is marked
  `possible_duplicate` so a human decides. A unique index backs it up.

  ## What I am unsure about
  Whether an hour is the right window. Happy to change it.
  ```

  That last heading is the one that gets you good reviews, because it tells the
  reviewer exactly where to spend their attention.
  :::
::

## 6. The formatting argument

Half the team wants two-space indentation, half wants four. It has come up
three times.

::accordion
  :::accordion-item{label="What a competent developer does" icon="i-lucide-check"}
  End it with a tool rather than a decision.

  ```bash
  npm install -D prettier
  echo '{}' > .prettierrc
  npx prettier --write .
  ```

  Commit the reformat as its own commit, add it to `.git-blame-ignore-revs` so
  it does not pollute blame, and run it in CI so the question can never be
  raised in a review again.

  Which option wins does not matter and never did. What matters is that nobody
  spends attention on it again, and that no review comment is ever about
  whitespace.

  The wider principle, and it is worth saying in an interview: **automate the
  disagreements that have no right answer.** Linting, formatting and import
  order are all in that category. Save review attention for the things that
  actually differ in value.
  :::
::

## The pattern

::pull-quote
Not one of these six is answered by knowing a command. They are answered by
knowing what the tool is for, which is the difference between somebody who has
used a toolchain and somebody who has only installed one.
::
