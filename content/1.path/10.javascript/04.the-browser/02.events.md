A click on a button inside a row inside a table is not only a click on the
button. The browser delivers it to the button, then to the row, then to the
table, then all the way up to `document`. That journey is why one listener on
the table can handle every button in it, and it is the core of this lesson.

## Why this matters in a job

Because every interaction on a page is an event: clicks, typing, submitting a
form, pressing Escape to close a dialog. Getting events wrong is how a form
reloads the page and loses what was typed, how a dropdown closes the moment it
opens, and how a table of 400 rows ends up with 400 listeners that do not work
for the row added a second later. In interviews, **event bubbling**, **event
delegation**, and **`preventDefault` against `stopPropagation`** are asked in
almost every front-end round.

## A notice passed up the chain of command

An **event** is a message from the browser: "this happened, here". A
**listener** (or **handler**) is a function you register to be called when a
particular event reaches a particular element.

Think of a complaint slip dropped in a classroom. It first travels **down**
from the principal's office to the classroom (so anybody on the way can
intercept it early), then it is read **in** the classroom, then it travels
back **up**: to the head of department, then the principal. Anyone on the way
can act on it, and anyone can say "stop, do not pass this further".

Those are the three **phases** of every event:

::flow{numbered direction="vertical" caption="A click on a button inside a table row"}
  :::flow-step{label="Capturing: document down to the target" icon="i-lucide-arrow-down"}
  Listeners registered with `{ capture: true }` run here, outermost first.
  Rarely used.
  :::
  :::flow-step{label="Target: the button itself" icon="i-lucide-mouse-pointer-click"}
  Listeners on the element that was actually clicked.
  :::
  :::flow-step{label="Bubbling: the target up to document" icon="i-lucide-arrow-up" highlight}
  The button's row, then the table, then `body`, then `document`. Ordinary
  listeners run here, innermost first. This is the phase delegation uses.
  :::
::

## How it works

```javascript [listen.js]
const button = document.querySelector("#mark-present");

function handleClick(event) {
  console.log(event.type);            // "click"
  console.log(event.target);          // the element actually clicked
  console.log(event.currentTarget);   // the element this listener is on
}

button.addEventListener("click", handleClick);
button.removeEventListener("click", handleClick);   // needs the SAME function
button.addEventListener("click", handleClick, { once: true }); // removes itself
```

The **event object** is the details slip: `type`, `target` (where it
started), `currentTarget` (where it is now), `key` for keyboard events, and the
two methods below.

The events you will use most: `click`, `input` (every change to a text box),
`change` (when a select or checkbox changes, or a text box loses focus),
`submit` (a form is sent), `keydown`, `focus` and `blur`, and
`DOMContentLoaded` (the HTML has been parsed).

### Watching bubbling and capturing

```html [phases.html]
<table id="table">
  <tr id="row"><td>Anita Rao</td><td><button id="btn">Present</button></td></tr>
</table>

<script>
  const log = where => console.log(where);
  document.querySelector("#table").addEventListener("click", () => log("capture: table"), { capture: true });
  document.querySelector("#btn").addEventListener("click", () => log("bubble: button"));
  document.querySelector("#row").addEventListener("click", () => log("bubble: row"));
  document.querySelector("#table").addEventListener("click", () => log("bubble: table"));
</script>
```

```text [Output]
capture: table
bubble: button
bubble: row
bubble: table
```

That is what the console shows after one click on the button.

### Event delegation

Instead of a listener on every button, put **one** on the container and ask
what was clicked. Try it: click the buttons, then add a student and click the
new one.

::runner{lang="html"}
```html
<table id="students">
  <tr data-roll="CSE001"><td>Anita Rao</td><td><button data-action="present">Present</button></td></tr>
  <tr data-roll="CSE002"><td>Vikram Shah</td><td><button data-action="present">Present</button></td></tr>
</table>
<button id="add">Add a student</button>
<pre id="log"></pre>

<style>
  tr.present td:first-child { text-decoration: line-through; color: gray; }
</style>

<script>
  const table = document.querySelector("#students");
  const log = message => { document.querySelector("#log").textContent += message + "\n"; };

  // One listener for every row, including rows that do not exist yet.
  table.addEventListener("click", event => {
    const button = event.target.closest("[data-action='present']");
    if (!button) return;                       // clicked something else in the table

    const row = button.closest("tr");
    row.classList.add("present");
    button.disabled = true;
    log(row.dataset.roll + " marked present");
  });

  let next = 3;
  document.querySelector("#add").addEventListener("click", () => {
    const roll = "CSE00" + next++;
    const row = document.createElement("tr");
    row.dataset.roll = roll;
    row.innerHTML = '<td></td><td><button data-action="present">Present</button></td>';
    row.firstChild.textContent = "New student " + roll;   // text, not markup
    table.append(row);
  });
</script>
```
::

```text [Output]
CSE001 marked present
CSE003 marked present
```

(That is the log after clicking Anita's button, adding a student, and clicking
the new row's button.)

`event.target.closest(...)` matters: if the button had an icon inside it, a
click on the icon reports the icon as the `target`. `closest` walks up from
there to the nearest ancestor matching the selector.

### preventDefault against stopPropagation

Two methods on the event object that people mix up constantly.

::compare{caption="They stop different things"}
  :::compare-side{label="event.preventDefault()" verdict="neutral"}
  Stops the **browser's own action** for this event: a form submitting and
  reloading the page, a link navigating, a checkbox ticking. The event still
  bubbles to every other listener.
  :::
  :::compare-side{label="event.stopPropagation()" verdict="neutral"}
  Stops the event **travelling** any further up (or down) the tree. The
  browser's default action still happens. Use it rarely: it breaks every
  delegated listener above you, including analytics.
  :::
::

## Real use case

Every form on the web that validates before sending does this. Without
`preventDefault`, the browser submits the form and reloads the page the moment
the user presses Enter, and your checks never matter.

::runner{lang="html"}
```html
<form id="enquiry">
  <label>Name <input name="name"></label>
  <label>Marks in 12th (%) <input name="marks"></label>
  <button>Send enquiry</button>
</form>
<p id="message"></p>

<script>
  const form = document.querySelector("#enquiry");
  const message = document.querySelector("#message");

  form.addEventListener("submit", event => {
    event.preventDefault();                          // no reload, stay on the page

    const data = new FormData(form);
    const name = data.get("name").trim();
    const marks = Number(data.get("marks"));        // form values are strings

    if (name === "") {
      message.textContent = "Please enter your name.";
    } else if (Number.isNaN(marks) || marks < 0 || marks > 100) {
      message.textContent = "Marks must be a number from 0 to 100.";
    } else {
      message.textContent = `Thank you, ${name}. We will call you about the ${marks >= 60 ? "B.Tech" : "diploma"} programme.`;
    }
  });
</script>
```
::

```text [Output]
Marks must be a number from 0 to 100.
```

(That is the message after typing "Anita" and "abc" and pressing Send.) The
same checks must run again on the server, because anyone can skip the page and
send the request directly. Checks in the browser are a courtesy to honest
users, never security.

## What confuses people here

**`target` against `currentTarget`.** `target` is where the event started
(possibly an icon inside your button). `currentTarget` is the element whose
listener is running now. In delegation they are different on purpose.

**`removeEventListener` needs the same function.** Writing
`removeEventListener("click", () => save())` removes nothing, because that
arrow function is a new function, not the one you added. Keep a reference.

**Not every event bubbles.** `focus` and `blur` do not (their bubbling versions
are `focusin` and `focusout`), which is why a delegated `focus` listener never
fires.

## Interview questions

::accordion
  :::accordion-item{label="What is event bubbling?" icon="i-lucide-message-circle"}
  After an event fires on the element where it happened, it travels up through
  each ancestor to `document`, running their listeners for the same event
  type, innermost first. A click on a button inside a row runs the button's
  listeners, then the row's, then the table's.
  :::

  :::accordion-item{label="Bubbling against capturing?" icon="i-lucide-message-circle"}
  Capturing is the first phase: the event travels from `document` down to the
  target, and only listeners added with `{ capture: true }` run. Then the
  target phase, then bubbling back up, where ordinary listeners run. So a
  capture listener on the table runs before the button's own listener.
  :::

  :::accordion-item{label="What is event delegation, and why use it?" icon="i-lucide-message-circle"}
  One listener on a parent handles events for all its children, using
  `event.target.closest(selector)` to find which child was involved. It relies
  on bubbling. Two benefits: fewer listeners (one instead of 400), and it works
  for children added later, which per-child listeners do not.
  :::

  :::accordion-item{label="preventDefault or stopPropagation?" icon="i-lucide-message-circle"}
  `preventDefault` stops the browser's default action (a form submit, a link
  navigation) but lets the event keep bubbling. `stopPropagation` stops the
  event reaching other elements but does not stop the default action. To stop a
  form reloading the page, you want `preventDefault`.
  :::

  :::accordion-item{label="Difference between the input and change events?" icon="i-lucide-message-circle"}
  `input` fires on every change to a text box's value, keystroke by keystroke.
  `change` fires when the value is committed: when a text box loses focus after
  being edited, or immediately for checkboxes, radio buttons and selects. Live
  search uses `input`; saving a setting often uses `change`.
  :::
::
