The DOM is rebuilt from the HTML on every load, so anything your code changed
on the page is gone after a refresh. The browser does give each website a small
notebook that survives: **Web Storage**, in two flavours, `localStorage` and
`sessionStorage`.

## Why this matters in a job

Because "remember what the user chose" is a constant request: the dark theme,
the last filter on the student table, half a typed enquiry form that should not
vanish if the tab crashes. It is also a classic interview comparison:
"difference between `localStorage`, `sessionStorage` and cookies?" And it has a
security edge that a good answer mentions without being asked: never keep a
login token or a password there.

## A notebook per website, in the browser's drawer

Every website (strictly, every **origin**: the scheme, host and port, such as
`https://college.example:443`) gets its own notebook in the browser. Your code
can write short notes in it and read them back later. Another website cannot
read yours.

- `localStorage` is a notebook that **stays** until your code or the user
  clears it. Close the browser, restart the laptop, come back next week: still
  there.
- `sessionStorage` is a notebook for **one tab**. Reloading keeps it; closing
  the tab throws it away, and a second tab gets a separate one.

Both hold **strings only**, roughly 5 MB per origin, and both are
**synchronous** (reading or writing blocks your code until it is done, which is
fine for small notes and wrong for large data).

## Syntax

```javascript [storage.js]
localStorage.setItem("theme", "dark");        // write
console.log(localStorage.getItem("theme"));   // read
console.log(localStorage.getItem("missing")); // a key that does not exist
localStorage.removeItem("theme");             // delete one
localStorage.clear();                         // delete everything for this origin

// Only strings. Anything else is converted, badly.
localStorage.setItem("attendance", 92);
console.log(typeof localStorage.getItem("attendance"));

localStorage.setItem("student", { name: "Anita" });
console.log(localStorage.getItem("student"));

// Objects go through JSON in both directions.
localStorage.setItem("student", JSON.stringify({ name: "Anita", roll: "CSE042" }));
const student = JSON.parse(localStorage.getItem("student"));
console.log(student.roll);
```

```text [Output]
dark
null
string
[object Object]
CSE042
```

The runner on this site cannot use storage (it runs your code in a sealed
frame with no origin of its own), so try these in your browser's console on any
page: F12, then Console. Application, then Local Storage, in the same panel
shows the notebook itself.

### Which one to use

| | `localStorage` | `sessionStorage` | Cookie |
| --- | --- | --- | --- |
| Lasts | Until cleared | Until the tab closes | Until its expiry date |
| Shared between tabs | Yes | No | Yes |
| Sent to the server | Never | Never | **With every request** |
| Size | About 5 MB | About 5 MB | About 4 KB |
| Readable by JavaScript | Yes | Yes | Yes, unless `HttpOnly` |

The row that matters most is the third. A cookie travels to the server on every
request, which is how the server knows who you are. Storage never leaves the
browser.

## Real use case

A marks-entry page where a faculty member types sixty marks. If the tab
crashes at student 45, the work should not be lost. The draft is saved on every
keystroke and restored on load.

```javascript [marks-draft.js]
const DRAFT_KEY = "marks-draft:DBMS:sem5";

function saveDraft(marks) {
  localStorage.setItem(DRAFT_KEY, JSON.stringify(marks));
}

function loadDraft() {
  try {
    return JSON.parse(localStorage.getItem(DRAFT_KEY)) ?? {};
  } catch {
    return {};                  // corrupted, or storage blocked: start clean
  }
}

// On load
const draft = loadDraft();
console.log(`Restored ${Object.keys(draft).length} marks`);

// On every change
draft["CSE001"] = 78;
draft["CSE002"] = 35;
saveDraft(draft);

// After a successful submit to the server
localStorage.removeItem(DRAFT_KEY);
```

```text [Output]
Restored 0 marks
```

(On a later visit, before submitting, the first line would say `Restored 2
marks`.) Three habits in there: a specific key so two subjects do not
overwrite each other, JSON in both directions, and a `try`/`catch`, because
`JSON.parse` throws on a damaged value and some browsers block storage
altogether in private mode.

::side-note{kind="security"}
Anything in `localStorage` can be read by any script running on your page. If
an attacker gets one line of JavaScript onto the page (the XSS from the DOM
lesson), they can read every key. That is why login tokens belong in a cookie
marked `HttpOnly`, which JavaScript cannot read at all, and why passwords,
card numbers and personal data never go into storage.
::

## What confuses people here

**`getItem` returns `null` for a missing key**, not `undefined`, and
`JSON.parse(null)` is `null`, which is why `?? {}` after it works.

**Storing a number gives back a string.** `"92" + 1` is `"921"`. Convert on the
way out, or store everything as JSON.

**sessionStorage is per tab, not per browser session.** Opening the same page
in a second tab starts with an empty `sessionStorage`.

## Interview questions

::accordion
  :::accordion-item{label="Difference between localStorage, sessionStorage and cookies?" icon="i-lucide-message-circle"}
  `localStorage` persists until cleared and is shared across tabs of the same
  origin. `sessionStorage` lasts only for one tab. Both hold about 5 MB of
  strings and are never sent to the server. Cookies are small (about 4 KB),
  have an expiry, and are sent with every request to their domain, which is
  why sessions use them.
  :::

  :::accordion-item{label="How do you store an object in localStorage?" icon="i-lucide-message-circle"}
  Convert it to a string with `JSON.stringify` when saving and back with
  `JSON.parse` when reading. Storing the object directly saves the text
  `"[object Object]"`.
  :::

  :::accordion-item{label="Is it safe to store a login token in localStorage?" icon="i-lucide-message-circle"}
  It is risky. Any script on the page can read it, so a single XSS bug leaks
  it. The safer pattern is a cookie with `HttpOnly` (invisible to JavaScript),
  `Secure` (HTTPS only) and `SameSite` set.
  :::

  :::accordion-item{label="Is localStorage synchronous or asynchronous?" icon="i-lucide-message-circle"}
  Synchronous. Each call blocks until it finishes. That is fine for small
  settings and a problem for large data, where IndexedDB, the browser's
  asynchronous database, is the right tool.
  :::
::
