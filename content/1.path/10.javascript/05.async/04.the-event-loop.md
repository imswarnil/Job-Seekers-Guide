Three lessons in a row have said "the callback goes in a queue and runs when
your code has finished". This lesson draws that queue, and the loop that empties
it. It is a small mechanism, and once you can draw it you can answer every
"in what order does this print?" question you will ever be given.

## Why this matters in a job

Because it explains real behaviour you will hit: why the page freezes while a
big loop runs, why a spinner you showed does not appear until the work is done,
why `setTimeout(fn, 0)` is not immediate. In interviews, "explain the event
loop" is asked in nearly every JavaScript round, usually with a snippet mixing
`console.log`, `setTimeout` and a promise, and the interviewer is waiting for
two specific words: **microtask** and **macrotask**.

## One cook, a counter, and two trays of order slips

The canteen has **one cook** (the single thread). The cook works on one order
at a time and never stops in the middle of one.

- The order being made right now, and the steps inside it, are on the **call
  stack**.
- Slow things (the rice cooker's timer, the delivery boy fetching milk) are
  handled by **helpers** outside the kitchen: the browser's timers and network.
  When a helper is done, he does not interrupt the cook. He drops a slip in a
  tray.
- There are **two trays**. The **urgent tray** (the **microtask queue**) holds
  promise callbacks. The **ordinary tray** (the **task queue**, also called the
  macrotask queue) holds timer callbacks, click events and network events.
- The rule: finish the current order. Then empty the **whole** urgent tray,
  including any urgent slips added while emptying it. Then take **one** slip
  from the ordinary tray. Repeat forever. That repeating is the **event loop**.

::flow{numbered direction="vertical" caption="One turn of the event loop"}
  :::flow-step{label="Run one task to completion" icon="i-lucide-play"}
  The whole script at first; later one timer callback, one click handler, one
  network callback. Nothing interrupts it.
  :::
  :::flow-step{label="Empty the microtask queue" icon="i-lucide-zap" highlight}
  Every promise callback (`.then`, `.catch`, the code after an `await`), and
  any new microtasks they add, until the queue is empty.
  :::
  :::flow-step{label="Let the browser paint" icon="i-lucide-paintbrush"}
  If the screen needs updating, it happens here, between tasks. Never in the
  middle of your code.
  :::
  :::flow-step{label="Take the next task" icon="i-lucide-repeat"}
  The oldest slip in the task queue, and back to the top.
  :::
::

| Goes in the **microtask** queue | Goes in the **task** (macrotask) queue |
| --- | --- |
| `.then`, `.catch`, `.finally` callbacks | `setTimeout`, `setInterval` callbacks |
| The rest of an `async` function after `await` | Events: click, input, keydown |
| `queueMicrotask(fn)` | Network and message callbacks |

## How it works

The puzzle, in the form it is usually asked. Write your answer down before you
look.

```javascript [event-loop.js]
console.log("1: script start");

setTimeout(() => console.log("2: timeout"), 0);

Promise.resolve()
  .then(() => console.log("3: promise 1"))
  .then(() => console.log("4: promise 2"));

(async () => {
  console.log("5: async start");
  await null;
  console.log("6: after await");
})();

console.log("7: script end");
```

```text [Output]
1: script start
5: async start
7: script end
3: promise 1
6: after await
4: promise 2
2: timeout
```

The short version you say out loud: **synchronous code first, then all
microtasks, then one macrotask.** Every variant of this question is that
sentence applied carefully.

## Real use case

The page freezes. A principal clicks "Build report" on 200,000 attendance rows,
and for four seconds nothing responds: no scrolling, the "Working…" message you
set never appears, the Cancel button does nothing. All of that is the event
loop: your loop is one task, and painting and clicks wait until it finishes.

You can see the waiting directly. A timer asks to run after 0 ms, and then the
thread is kept busy for 200 ms:

```javascript [blocked.js]
const start = Date.now();

setTimeout(() => {
  const late = Math.round((Date.now() - start) / 100) * 100;
  console.log(`timer asked for 0 ms, ran after about ${late} ms`);
}, 0);

// 200 ms of synchronous work: nothing else can run meanwhile.
while (Date.now() - start < 200) {}

console.log("busy loop finished");
```

```text [Output]
busy loop finished
timer asked for 0 ms, ran after about 200 ms
```

The fix for real heavy work is to stop being one long task: split it into
chunks and give the loop a turn between them, so the browser can paint and
handle clicks.

```javascript [chunked.js]
async function buildReport(rows) {
  const status = document.querySelector("#status");
  let below75 = 0;

  for (let i = 0; i < rows.length; i += 5000) {
    for (const row of rows.slice(i, i + 5000)) {
      if (row.attendance < 75) below75++;
    }
    status.textContent = `Processed ${Math.min(i + 5000, rows.length)} of ${rows.length}`;
    await new Promise(resolve => setTimeout(resolve, 0));   // a new TASK: the browser paints here
  }
  status.textContent = `${below75} students below 75%`;
}
```

Notice the pause uses `setTimeout`, not `await Promise.resolve()`. A resolved
promise continues as a **microtask**, and microtasks all run before the browser
paints, so the page would still freeze. For truly heavy work the better tool
is a **Web Worker**, a second thread with no access to the DOM.

## What confuses people here

**`setTimeout(fn, 0)` means "at least 0 ms, as a new task", not "now".** It
always waits for the current code and every microtask. Nested timers are also
clamped to a minimum of about 4 ms by browsers.

**JavaScript is single-threaded, the browser is not.** Timers, network requests
and rendering are done by the browser on other threads. Only your JavaScript
runs on one.

**Microtasks can starve the page.** A promise callback that keeps queueing
another promise callback never lets the loop reach the task queue or the
paint step. That is rare, but it is why the order matters.

## Interview questions

::accordion
  :::accordion-item{label="Explain the event loop." icon="i-lucide-message-circle"}
  JavaScript runs on one thread with a call stack. Slow work (timers, network,
  events) is handled by the browser, which queues a callback when it is done.
  There are two queues: microtasks (promise callbacks, code after `await`) and
  tasks (timers, events). The loop runs one task to completion, then empties
  the entire microtask queue, lets the browser paint, and takes the next task.
  So: synchronous code, then all microtasks, then the next macrotask.
  :::

  :::accordion-item{label="What is the difference between a microtask and a macrotask?" icon="i-lucide-message-circle"}
  Microtasks are promise reactions (`then`, `catch`, `finally`, the rest of an
  async function after `await`, `queueMicrotask`). Macrotasks (tasks) are
  `setTimeout`, `setInterval`, and events. After each task, all microtasks run
  before the next task, which is why a resolved promise's callback always beats
  a `setTimeout(fn, 0)`.
  :::

  :::accordion-item{label="What does this print? console.log('A'); setTimeout(() => console.log('B'), 0); Promise.resolve().then(() => console.log('C')); console.log('D');" icon="i-lucide-message-circle"}
  `A`, `D`, `C`, `B`. `A` and `D` are synchronous. `C` is a microtask, run as
  soon as the script finishes. `B` is a task, run after all microtasks, even
  with a delay of 0.
  :::

  :::accordion-item{label="Why does a long loop freeze the page?" icon="i-lucide-message-circle"}
  The loop is one task on the only thread, and the browser only paints and
  handles clicks between tasks. Until the loop finishes, nothing else can run.
  Fix it by splitting the work into chunks with `setTimeout` between them, or
  moving it to a Web Worker.
  :::

  :::accordion-item{label="Is JavaScript single-threaded? Then how does it do async work?" icon="i-lucide-message-circle"}
  Your JavaScript runs on one thread. The waiting is done elsewhere: the
  browser (or Node.js) handles timers, network and file operations on its own
  threads and queues your callback when each finishes. The event loop runs
  those callbacks one at a time on your thread.
  :::
::
