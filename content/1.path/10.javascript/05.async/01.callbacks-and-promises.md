JavaScript runs your code on **one thread**. If that thread stood still for
the three seconds a slow server takes to answer, the whole page would freeze:
no scrolling, no typing, no clicking. So it never stands still. Anything slow
is started, handed to the browser, and your code carries on. The question this
chapter answers is how you get the result back when it finally arrives.

## Why this matters in a job

Because every page talks to a server, and a server call is always
asynchronous. The single most common bug in fresher front-end code is using a
value before it has arrived: an empty table, an `undefined` name, a total of
zero. Interviews go straight at it: "what is a promise?", "what are its
states?", "difference between `Promise.all` and `Promise.allSettled`?", and
code that chains `.then` calls with the question "in what order does this
print?"

## A token at the canteen counter

You order a dosa at the college canteen. The man at the counter does not make
you stand at the counter until it is ready. He gives you a **token** and you go
and sit down, talk, check your phone. When the dosa is ready, your number is
called, and you collect it. Or the number is called and you are told they have
run out.

A **promise** is that token. It is an object that stands for a value which
does not exist yet. It is always in one of three **states**:

::flow{numbered direction="vertical" caption="The three states of a promise. Once settled, it never changes again."}
  :::flow-step{label="pending" icon="i-lucide-hourglass"}
  The dosa is being made. No value yet.
  :::
  :::flow-step{label="fulfilled" icon="i-lucide-circle-check" highlight}
  Ready. The promise holds its value, and the functions you gave to `.then`
  are called with it.
  :::
  :::flow-step{label="rejected" icon="i-lucide-circle-x"}
  Failed. The promise holds an error, and the function you gave to `.catch` is
  called with it.
  :::
::

Fulfilled and rejected together are called **settled**. A promise settles
exactly once.

### Before promises: callbacks

The older way was to pass a function to be called when the work finished, a
**callback**, as in the functions lesson. It works, until one slow step depends
on another:

```javascript [callback-pyramid.js]
getStudent("CSE042", (err, student) => {
  if (err) return showError(err);
  getMarks(student.roll, (err, marks) => {
    if (err) return showError(err);
    getHallTicket(student.roll, marks, (err, ticket) => {
      if (err) return showError(err);
      print(ticket);
    });
  });
});
```

Every step pushes the code one level to the right, every level repeats its own
error check, and nothing stops a buggy function calling your callback twice.
That shape has a name, **callback hell**, and promises were added in 2015 to
flatten it.

## How it works

`new Promise` takes a function with two arguments: `resolve` to fulfil it and
`reject` to reject it. Here are two pretend server calls, slowed down with
`setTimeout` so you can see the timing.

```javascript [promises.js]
function getStudent(roll) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (roll.startsWith("CSE")) resolve({ roll, name: "Anita Rao" });
      else reject(new Error("No student with roll " + roll));
    }, 300);
  });
}

function getMarks(roll) {
  return new Promise(resolve => {
    setTimeout(() => resolve([78, 82, 91]), 200);
  });
}

console.log("1. asking for the student");

getStudent("CSE042")
  .then(student => {
    console.log("2. got " + student.name);
    return getMarks(student.roll);         // returning a promise: the chain waits for it
  })
  .then(marks => console.log("3. marks " + marks.join(", ")))
  .catch(error => console.log("error: " + error.message))
  .finally(() => console.log("4. finished, success or not"));

console.log("5. carried on without waiting");
```

```text [Output]
1. asking for the student
5. carried on without waiting
2. got Anita Rao
3. marks 78, 82, 91
4. finished, success or not
```

Line 5 prints **second**. `getStudent` returned a pending promise immediately,
`.then` only registered what to do later, and the code carried on. Three
hundred milliseconds later the student arrives, then two hundred after that,
the marks.

Change the roll to `"ME007"` and the output becomes:

```text [Output]
1. asking for the student
5. carried on without waiting
error: No student with roll ME007
4. finished, success or not
```

The rejection skips every `.then` below it and lands in the nearest `.catch`.
One `.catch` at the end handles a failure at any step, which is the thing
callback hell could not do.

::code-trace{caption="The three rules of a .then chain"}
```javascript [promises.js]
  .then(student => {
    return getMarks(student.roll);
  })
  .then(marks => console.log("3. marks " + marks.join(", ")))
  .catch(error => console.log("error: " + error.message))
```

  :::code-trace-step{lines="1-3" caption="Every .then returns a NEW promise. If its function returns a promise, the new one waits for it and takes its value."}
  :::
  :::code-trace-step{lines="4" caption="If its function returns a plain value, the next .then receives that value straight away. If it throws, the chain jumps to the catch."}
  :::
  :::code-trace-step{lines="5" caption="catch handles a rejection from ANY step above it. After a catch the chain carries on as fulfilled, which is why finally still runs."}
  :::
::

### Running several at once

A student's dashboard needs attendance, marks and fee status from three
different services. Asking one after another wastes time. These four helpers
run promises together, and each behaves differently when one of them fails.

```javascript [combinators.js]
const after = (value, ms) => new Promise(resolve => setTimeout(() => resolve(value), ms));
const failAfter = (message, ms) =>
  new Promise((_, reject) => setTimeout(() => reject(new Error(message)), ms));

Promise.all([after("attendance", 300), after("marks", 100)])
  .then(values => console.log("all:", values.join(", ")));

Promise.allSettled([after("attendance", 300), failAfter("fee server down", 100)])
  .then(results => console.log("allSettled:", results.map(r => r.status).join(", ")));

Promise.race([after("attendance", 300), after("marks", 100)])
  .then(value => console.log("race:", value));

Promise.all([after("attendance", 300), failAfter("fee server down", 100)])
  .catch(error => console.log("all failed:", error.message));

Promise.any([failAfter("fee server down", 100), after("marks", 200)])
  .then(value => console.log("any:", value));
```

```text [Output]
race: marks
all failed: fee server down
any: marks
all: attendance, marks
allSettled: fulfilled, rejected
```

| Method | Fulfils when | Rejects when |
| --- | --- | --- |
| `Promise.all` | **All** fulfil, with values in the original order | **Any one** rejects, immediately |
| `Promise.allSettled` | All have settled, with a status for each | Never |
| `Promise.race` | The **first to settle** fulfils | The first to settle rejects |
| `Promise.any` | The **first to fulfil** | All of them reject |

Notice `all:` lists attendance first although marks arrived first. The results
are in the order you asked, not the order they came back.

## Real use case

The dashboard, with the one rule real code follows: if a single section fails,
show the rest. `Promise.all` would blank the whole page because the fee
service is down; `allSettled` shows attendance and marks and an apology for
fees.

```javascript [dashboard.js]
const after = (value, ms) => new Promise(resolve => setTimeout(() => resolve(value), ms));
const failAfter = (message, ms) =>
  new Promise((_, reject) => setTimeout(() => reject(new Error(message)), ms));

const sections = ["Attendance", "Marks", "Fees"];

Promise.allSettled([
  after("92%", 150),
  after("78, 82, 91", 250),
  failAfter("fee service timed out", 100)
]).then(results => {
  results.forEach((result, i) => {
    if (result.status === "fulfilled") {
      console.log(`${sections[i]}: ${result.value}`);
    } else {
      console.log(`${sections[i]}: unavailable (${result.reason.message})`);
    }
  });
});
```

```text [Output]
Attendance: 92%
Marks: 78, 82, 91
Fees: unavailable (fee service timed out)
```

## What confuses people here

**A promise does not make code run in parallel.** Your JavaScript still runs
on one thread. What happens at the same time is the **waiting**: the browser
does the network work, and three requests can be in flight at once.

**Forgetting to return inside `.then`.** If the first `.then` calls
`getMarks(...)` without `return`, the next `.then` does not wait and receives
`undefined`. This is the most common promise bug.

**A missing `.catch`.** A rejection nobody handles becomes an "Uncaught (in
promise)" error in the console, and whatever was supposed to show on screen
never does.

## Interview questions

::accordion
  :::accordion-item{label="What is a promise?" icon="i-lucide-message-circle"}
  An object representing a value that will be available later, or an error.
  It is pending, then settles once as fulfilled (with a value) or rejected
  (with a reason). You react with `.then` for the value, `.catch` for the
  error and `.finally` for either. It replaced nested callbacks with a flat
  chain and one place to handle errors.
  :::

  :::accordion-item{label="What are the states of a promise?" icon="i-lucide-message-circle"}
  Pending, fulfilled and rejected. Fulfilled and rejected are together called
  settled. A promise moves from pending to one of the other two exactly once
  and never changes after that; calling `resolve` a second time does nothing.
  :::

  :::accordion-item{label="What is callback hell, and how do promises help?" icon="i-lucide-message-circle"}
  Nested callbacks where each asynchronous step depends on the previous one:
  the code drifts right, every level repeats its error handling, and it is hard
  to read. Promises chain instead of nest, `.then(...).then(...)`, with one
  `.catch` at the end for a failure at any step. `async`/`await` flattens it
  further.
  :::

  :::accordion-item{label="Difference between Promise.all and Promise.allSettled?" icon="i-lucide-message-circle"}
  `Promise.all` fulfils with every value when all fulfil, but rejects as soon as
  any one rejects, and you lose the other results. `Promise.allSettled` always
  fulfils, with an array of `{ status, value }` or `{ status, reason }`, one per
  promise. Use `allSettled` when partial results are still useful.
  :::

  :::accordion-item{label="Difference between Promise.race and Promise.any?" icon="i-lucide-message-circle"}
  `race` settles like whichever promise settles first, even if that one is a
  rejection. `any` fulfils with the first promise that fulfils, ignoring
  rejections, and only rejects (with an `AggregateError`) if all of them
  reject. `race` is used for timeouts: race the request against a timer that
  rejects.
  :::
::
