`async` and `await` let you write "get the student, then get the marks, then
print them" as three lines, top to bottom, the way you think it. Underneath
they are exactly the promises from the last lesson. Nothing new happens at
runtime; only the way you write it changes.

## Why this matters in a job

Because this is how nearly all modern JavaScript is written, in the browser and
in Node.js. You will read `async function` in every codebase you join. And the
two mistakes this lesson names (awaiting things one at a time when they could
run together, and `await` inside `forEach`) are exactly the kind of thing a
reviewer catches and an interviewer asks about: "what does `async` return?",
"how do you handle errors with `await`?", "how would you make these three calls
faster?"

## Pausing one recipe, not the kitchen

Back to the canteen. A cook is making your order: dosa, then chutney, then
plate it. When the dosa goes on the pan, the cook does not stand frozen
staring at it. Your order is **paused** at "wait for the dosa", and the cook
works on other orders until it is ready, then comes back and continues your
order from exactly where it stopped.

- `async` in front of a function marks it as a recipe that can pause. An
  `async` function **always returns a promise**, even if you return a plain
  value.
- `await` in front of a promise pauses **this function only** until the
  promise settles, then gives you its value (or throws its error). The rest of
  the page keeps running.

## How it works

The chain from the last lesson, rewritten:

```javascript [await.js]
function getStudent(roll) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (roll.startsWith("CSE")) resolve({ roll, name: "Anita Rao" });
      else reject(new Error("No student with roll " + roll));
    }, 300);
  });
}
const getMarks = roll => new Promise(resolve => setTimeout(() => resolve([78, 82, 91]), 200));

async function showResult(roll) {
  try {
    const student = await getStudent(roll);        // pause until the student arrives
    const marks = await getMarks(student.roll);    // then pause for the marks
    console.log(`${student.name}: ${marks.join(", ")}`);
  } catch (error) {                                // a rejected await throws here
    console.log("Could not load: " + error.message);
  } finally {
    console.log("done for " + roll);
  }
}

async function passMark() {
  return 40;                                       // wrapped in a promise automatically
}

console.log(passMark() instanceof Promise);
passMark().then(value => console.log("pass mark " + value));

showResult("CSE042").then(() => showResult("ME007"));
```

```text [Output]
true
pass mark 40
Anita Rao: 78, 82, 91
done for CSE042
Could not load: No student with roll ME007
done for ME007
```

Errors work the way they do in Java: a rejected promise makes `await` **throw**,
so an ordinary `try`/`catch` catches it. No `.catch` needed.

### In sequence against in parallel

Each `await` waits for the previous one to finish. That is right when the
second call needs the first one's answer (you need the student's roll before
you can ask for the marks). It is wasteful when the calls are independent.

```javascript [timing.js]
const after = (value, ms) => new Promise(resolve => setTimeout(() => resolve(value), ms));
const elapsed = start => Math.round((Date.now() - start) / 100) * 100;

async function oneAfterAnother() {
  const start = Date.now();
  const attendance = await after("92%", 300);
  const marks = await after("78, 82", 300);
  console.log(`one after another: ${elapsed(start)} ms`);
}

async function together() {
  const start = Date.now();
  const [attendance, marks] = await Promise.all([after("92%", 300), after("78, 82", 300)]);
  console.log(`together: ${elapsed(start)} ms`);
}

(async () => {
  await oneAfterAnother();
  await together();
})();
```

```text [Output]
one after another: 600 ms
together: 300 ms
```

In the second version both requests are **started** first (calling `after`
starts the timer), and only then does the function wait, once, for both.

::code-trace{caption="Why the first version is twice as slow"}
```javascript [timing.js]
  const attendance = await after("92%", 300);
  const marks = await after("78, 82", 300);
  const [attendance, marks] = await Promise.all([after("92%", 300), after("78, 82", 300)]);
```

  :::code-trace-step{lines="1" caption="The attendance request starts, and the function pauses for 300 ms."}
  :::

## Real use case

Saving attendance for a whole class, one request per student. The version
most people write first reports success before anything is saved.

```javascript [save-attendance.js]
const save = roll => new Promise(resolve => setTimeout(() => resolve(roll), 100));

async function saveWithForEach(rolls) {
  rolls.forEach(async roll => {                  // forEach does not wait for async callbacks
    await save(roll);
    console.log("saved " + roll);
  });
  console.log("forEach version: all saved?");
}

async function saveTogether(rolls) {
  const saved = await Promise.all(rolls.map(roll => save(roll)));
  console.log(`Promise.all version: saved ${saved.length} students`);
}

(async () => {
  await saveWithForEach(["CSE001", "CSE002"]);
  await saveTogether(["CSE001", "CSE002", "CSE003"]);
})();
```

```text [Output]
forEach version: all saved?
saved CSE001
saved CSE002
Promise.all version: saved 3 students
```

Read that output slowly. "All saved?" prints before anything is saved. The
`await saveWithForEach(...)` line did not wait either: the next function had
already started its own requests before the two "saved" lines arrived. `forEach`
calls each async callback, gets a promise back, throws it away, and returns.
Nothing awaits those promises, so an error in one of them would not be caught
anywhere.

Two correct versions: `for (const roll of rolls) { await save(roll); }` saves
one at a time, in order; `await Promise.all(rolls.map(save))` saves them all
at once. On a real server, prefer one request that saves the whole class if the
API offers it, because sixty requests at once can overwhelm a small server.

## What confuses people here

**`await` does not freeze the page.** It pauses the `async` function it is
in. Everything else (clicks, other code, animations) carries on.

**`await` only works inside an `async` function**, or at the top level of a
module. In an ordinary function it is a `SyntaxError`.

**Calling an `async` function without `await` gives you a promise, not the
value.** `const marks = getMarksAsync(); console.log(marks.length)` logs
`undefined`, because `marks` is a promise.

## Interview questions

::accordion
  :::accordion-item{label="What does an async function return?" icon="i-lucide-message-circle"}
  Always a promise. `return 40` inside it gives a promise that fulfils with 40;
  a `throw` inside it gives a promise that rejects. So the caller either
  `await`s it or uses `.then`.
  :::

  :::accordion-item{label="How do you handle errors with async/await?" icon="i-lucide-message-circle"}
  With `try`/`catch`. A rejected promise makes `await` throw, so the `catch`
  block receives the error, and `finally` runs either way. Without a
  `try`/`catch`, the error rejects the promise the async function returned, so
  its caller must handle it.
  :::

  :::accordion-item{label="Three independent API calls take 1 second each. How do you make them take 1 second in total?" icon="i-lucide-message-circle"}
  Start all three before awaiting, with `Promise.all`:

  ```javascript
  const [student, marks, fees] = await Promise.all([
    getStudent(roll), getMarks(roll), getFees(roll)
  ]);
  ```

  Three `await`s in a row take 3 seconds, because each call only starts after
  the previous one has finished. Use `Promise.allSettled` if one failing should
  not lose the other two.
  :::

  :::accordion-item{label="Why doesn't await work inside forEach?" icon="i-lucide-message-circle"}
  It does run, but `forEach` ignores the promise each async callback returns,
  so the code after `forEach` does not wait. Use `for...of` with `await` to go
  one by one, or `await Promise.all(items.map(async item => ...))` to run them
  together and wait for all.
  :::

  :::accordion-item{label="async/await or .then: which is better?" icon="i-lucide-message-circle"}
  They do the same thing; `async`/`await` is built on promises. `await` reads
  top to bottom and uses ordinary `try`/`catch`, so it is the default in modern
  code. `.then` is still handy for a short one-off, or with `Promise.all` and
  friends. You will see both, often in the same file.
  :::
::
