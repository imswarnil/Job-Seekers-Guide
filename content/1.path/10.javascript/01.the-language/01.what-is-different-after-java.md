The page looks right and clicking anything does nothing, because HTML and CSS
cannot listen. The language that listens is the third one the browser speaks,
and the first one you already half know, because you learned to program once in
Java and everything after that is a dialect.

So this first lesson is not a language course. It is the list of differences,
and the rest of the track takes them one at a time.

## Why this matters in a job

Because coming to JavaScript from Java, the syntax is familiar enough to lull
you and the behaviour differs in five places that produce real bugs. Those same
five places are what a fresher web interview is built from: "what does this
print?", "what is the difference between `==` and `===`?", "what is a closure?",
"explain the event loop". If you know where the differences are, you know where
the questions will come from.

## The five differences

Think of Java and JavaScript as two cousins who share a surname and very little
else. The name was a marketing decision in 1995. The languages were designed by
different people for different jobs: Java for large programs checked by a
compiler, JavaScript for small scripts that make a web page respond, written in
ten days and never allowed to break old pages since.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-shuffle" title="1. Types move"}
  A variable has no fixed type. The same `let score` can hold a number, then a
  string, then `null`. There is no compiler to stop you.
  :::
  :::feature{icon="i-lucide-equal" title="2. Equality converts"}
  `==` converts types before comparing, so `78 == "78"` is `true`. `===` does
  not. You will use `===`.
  :::
  :::feature{icon="i-lucide-circle-slash" title="3. Zero is false"}
  `0`, `''`, `null`, `undefined` and `NaN` all count as false in an `if`. A
  student who scored 0 looks the same as a student with no mark.
  :::
  :::feature{icon="i-lucide-pointer" title="4. this depends on the call"}
  In Java, `this` is always the object. In JavaScript it depends on how the
  function was called, which is why callbacks lose it.
  :::
  :::feature{icon="i-lucide-hourglass" title="5. Nothing waits"}
  One thread runs your code. A network call returns immediately with a promise,
  not the data, and the code after it carries on.
  :::
::

## How it works

Here are all five in one file. Read it top to bottom and predict each line
before you look at the output.

```javascript [differences.js]
// 1. Types move. Legal, with no error, ever.
let score = 78;
score = "seventy-eight";
console.log(typeof score);

// 2. Equality converts.
console.log(78 == "78", 78 === "78");

// 3. Zero is falsy, so a real mark of 0 is lost.
const marks = [78, 0, null, 75];
console.log(marks.filter(m => m).length);        // wrong: drops the 0
console.log(marks.filter(m => m != null).length); // right: keeps the 0

// 4. this depends on the call.
const course = {
  title: "Data Structures",
  describe() { return "Course: " + this.title; }
};
const describe = course.describe;                 // detached from the object
console.log(course.describe());
console.log(String(describe()));                  // `this` is no longer course

// 5. Nothing waits.
console.log("before");
setTimeout(() => console.log("timer"), 0);
console.log("after");
```

```text [Output]
string
true false
2
3
Course: Data Structures
Course: undefined
before
after
timer
```

Line by line, what surprised you:

- `typeof score` is `"string"` now. The variable did not care.
- `78 == "78"` converted the string to a number first.
- `marks.filter(m => m)` kept 78 and 75 and threw away the genuine zero along
  with the `null`.
- `describe()` called on its own has no object in front of the dot, so `this`
  is not `course` any more and `this.title` is `undefined`.
- `timer` prints last even with a delay of zero, because the timer's callback
  waits in a queue until all the ordinary code has finished.

The syntax you do know carries over almost untouched:

```javascript [familiar.js]
const cutoff = 75;                        // like final
let shortlisted = 0;                      // an ordinary variable

function isEligible(mark) { return mark >= cutoff; }
const isEligibleArrow = mark => mark >= cutoff;   // the same thing, shorter

const students = ["Anita", "Vikram", "Priya"];   // an array, like a List
const attendance = { anita: 92, vikram: 64 };    // an object, a bit like a Map

for (let i = 0; i < students.length; i++) {
  if (attendance[students[i].toLowerCase()] >= 75) shortlisted++;
}
console.log(shortlisted);
```

```text [Output]
1
```

Anita has 92, Vikram has 64, and Priya has no entry at all, so
`attendance["priya"]` is `undefined`, and `undefined >= 75` is `false`. No
exception, no warning. That quiet `undefined` is the sixth difference, and it
runs through all five.

## Real use case

Every value that arrives from a form, a URL or an HTTP response is a **string**.
This is the bug that follows from differences one and two in real code, taken
from a marks-entry screen:

```javascript [marks-entry.js]
// The input box gives a string, always.
const entered = "8";

// Bug: comparing a string with a string compares character by character.
console.log(entered > "70");          // true, because "8" comes after "7"

// Fix: convert once, where the data enters, and check the conversion worked.
const mark = Number(entered);
if (Number.isNaN(mark)) {
  console.log("Not a number");
} else {
  console.log(mark > 70);             // false, which is right
}
```

```text [Output]
true
false
```

The rule working developers follow: convert at the boundary, once, and never
trust that a value which looks like a number is one.

## What confuses people here

That JavaScript is "Java for the browser". It is not, and assuming it is causes
the bugs above. The loops, `if`, `switch`, `try`/`catch` and operators look the
same; the type system, equality, `this` and the timing model do not. Also, `var`
exists and behaves strangely. You will meet it in old code and in interview
questions. You will not write it.

## Your turn

::runner{lang="javascript"}
```javascript
const results = [
  { name: "Anita Rao",   mark: 78 },
  { name: "Vikram Shah", mark: 0 },
  { name: "Rahul Verma", mark: null },
  { name: "Priya Nair",  mark: 75 }
];

// 1. This misses Vikram. Why? Fix it.
const marked = results.filter(r => r.mark);
console.log(marked.length);

// 2. Predict before running.
console.log("75" == 75, "75" === 75, "8" > 70, "8" > "70");

// 3. Names of everyone at or above 75, alphabetical, as one string.
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** `0` is falsy, so Vikram's genuine mark of zero is filtered out along
  with Rahul's `null`. Fix: `results.filter(r => r.mark != null)`, which matches
  both `null` and `undefined` and keeps 0. It prints 3.

  **2.** `true false false true`. `"8" > 70` converts `"8"` to the number 8, and
  8 is not greater than 70. `"8" > "70"` compares two strings character by
  character, and `"8"` comes after `"7"`. Both are surprising and both vanish if
  you convert at the boundary.

  **3.**

  ```javascript
  const names = results
    .filter(r => r.mark != null && r.mark >= 75)
    .map(r => r.name)
    .sort()
    .join(", ");
  console.log(names);          // Anita Rao, Priya Nair
  ```
  :::

## Interview questions

::accordion
  :::accordion-item{label="Is JavaScript related to Java?" icon="i-lucide-message-circle"}
  Only by name. JavaScript is dynamically typed (types are checked while the
  program runs, not by a compiler), single-threaded with an event loop, and
  its functions are values that can be passed around. Java is statically typed,
  compiled to bytecode and multi-threaded. Show one difference with code:
  `let x = 5; x = "five";` is legal in JavaScript and a compile error in Java.
  :::

  :::accordion-item{label="Is JavaScript compiled or interpreted?" icon="i-lucide-message-circle"}
  Both, in practice. You ship source code with no compile step, and the
  browser's engine (V8 in Chrome, SpiderMonkey in Firefox) parses it and
  compiles hot parts to machine code while it runs. That is called just-in-time
  (JIT) compilation. The fresher answer that is safe: "it is interpreted from
  the programmer's point of view, and modern engines JIT-compile it."
  :::

  :::accordion-item{label="Why does setTimeout(fn, 0) not run immediately?" icon="i-lucide-message-circle"}
  Because the callback is put in a queue, and the queue is only processed once
  all the ordinary code has finished. `console.log("before")`, the timer,
  `console.log("after")` prints `before`, `after`, then the timer. The event
  loop lesson draws the whole picture.
  :::

  :::accordion-item{label="What are the falsy values in JavaScript?" icon="i-lucide-message-circle"}
  `false`, `0`, `-0`, `0n`, `''`, `null`, `undefined` and `NaN`. Everything else
  is truthy, including `"0"`, `"false"`, `[]` and `{}`. Then the consequence:
  `if (mark)` is wrong for a mark of 0, and `mark != null` is the check you want.
  :::
::
