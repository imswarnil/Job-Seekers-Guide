Clicking "Shortlist" reloads the page. The language that fixes that is the third
one you have met and the first you already half know, because you learned to
program once and everything after it is a dialect.

So this is not a language course. It is the list of differences.

## Why this matters in a job

Because coming to JavaScript from Java, the syntax is familiar enough to lull you
and the semantics differ in exactly three places that produce real bugs.

## The differences that do not matter much

```javascript [familiar.js]
const cutoff = 75;                 // final
let shortlisted = 0;               // a normal variable
var old = 1;                       // never use this. See below.

function shortlist(applications, cutoff) { ... }
const shortlist = (applications, cutoff) => { ... };   // the same thing

const applicants = ['Anita', 'Vikram'];                // a List
const scores = { anita: 78, vikram: 64 };              // a Map, sort of

applications
  .filter(a => a.score !== null && a.score >= cutoff)
  .map(a => a.applicant.fullName)
  .sort();                                             // streams, built in
```

If you can read Java, you can read that. `const` and `let` are block-scoped like
Java's variables; `var` is function-scoped and behaves surprisingly, and the
only reason to know it exists is to recognise it in old code.

## Difference one: types move

```javascript [types.js]
let score = 78;
score = "seventy-eight";     // legal. No compiler, no error, ever.
score = null;
score = undefined;           // a SECOND kind of nothing
```

Two kinds of nothing is the first real surprise. `null` means "deliberately
empty"; `undefined` means "never set", and they appear in different situations.

```javascript [nothing.js]
const applicant = { name: 'Anita Rao' };
applicant.score        // undefined — the property does not exist
applicant.score = null // null — it exists and is deliberately empty

const [first, second] = ['Anita'];
second                 // undefined — nothing was there
```

## Difference two: equality lies

The one that causes real bugs.

```javascript [equality.js]
78 == "78"        // true   ← converts types before comparing
78 === "78"       // false  ← compares type AND value

0 == false        // true
'' == false       // true
null == undefined // true
[] == false       // true   ← genuinely
```

::pull-quote
Use `===` and `!==`, always, with one exception: `x == null` is a useful idiom
that matches both null and undefined. Everything else about `==` is a source of
bugs that only appear with real data.
::

```javascript [form.js]
// The bug this actually causes.
const marks = form.get('marks');       // a STRING from a form, always
if (marks == 75) { ... }               // true for "75". Seems fine.
if (marks > 70) { ... }                // "8" > 70 is FALSE — string comparison

// Convert at the boundary, once.
const marks = Number(form.get('marks'));
if (Number.isNaN(marks)) { /* they typed something that is not a number */ }
```

Every value arriving from a form, a URL or an HTTP response is a string. Convert
it once, at the edge, and check the conversion worked. Skipping that is the most
common source of arithmetic that silently does the wrong thing.

## Difference three: falsy values

```javascript [falsy.js]
// Falsy: false, 0, -0, '', null, undefined, NaN. Everything else is truthy.

if (applicant.score) { ... }      // FALSE for a score of 0, which is a real mark
if (applicant.score != null) { }  // right: distinguishes 0 from missing

const name = input || 'Unknown';  // replaces '' too, which may not be wanted
const name = input ?? 'Unknown';  // ?? only replaces null and undefined
```

That first one is the `NULL`-versus-zero distinction from the DBMS track,
appearing for the third time in this course. A student who scored 0 is not a
student with no score, and `if (score)` cannot tell them apart.

## Difference four: `this` is not what you expect

```javascript [this.js]
const shortlister = {
  cutoff: 75,

  check(application) {
    return application.score >= this.cutoff;   // fine: called as a method
  },

  checkAll(applications) {
    return applications.filter(function (a) {
      return a.score >= this.cutoff;           // BROKEN: `this` is not the object
    });
  },

  checkAllFixed(applications) {
    return applications.filter(a => a.score >= this.cutoff);   // arrow: `this` is kept
  }
};
```

In a regular `function`, `this` depends on **how it was called**, not where it
was written. An arrow function has no `this` of its own and uses the one from the
surrounding scope, which is nearly always what you meant.

::tip
The practical rule: use arrow functions for callbacks, and regular methods in
object and class definitions. That covers essentially every case correctly and
means you can stop thinking about `this`, which is what modern JavaScript did
deliberately.
::

## Difference five, and it is the big one: nothing waits

```java [Java.java]
// Java: this line blocks until the database answers.
List<Application> applications = repository.findAll();
System.out.println(applications.size());       // runs after
```

```javascript [Wrong.js]
// JavaScript: fetch returns immediately with a PROMISE, not the data.
const applications = fetch('/api/applications');
console.log(applications.length);              // undefined. It has not happened yet.
```

There is **one thread** running your code. If it waited for the network, the
whole page would freeze, so nothing waits. Anything slow returns a promise: a
placeholder for a value that will exist later.

```javascript [Right.js]
async function loadApplications() {
  const response = await fetch('/api/applications?intake=2026');

  if (!response.ok) {                          // 404 and 500 do NOT throw
    throw new Error(`Failed: ${response.status}`);
  }

  const applications = await response.json();  // also async: parsing takes time
  return applications;
}
```

::warning{icon="i-lucide-alert-triangle"}
`fetch` only rejects on a **network** failure. A 404 or a 500 is a successful
fetch of an error response, so `await fetch(...)` succeeds and you carry on with
an error page as your data. Checking `response.ok` is not optional, and forgetting
it is the single most common `fetch` bug.
::

::flow{numbered direction="vertical" caption="Why the order surprises you. One thread, and a queue."}
  :::flow-step{label="Your code runs to the end" icon="i-lucide-play"}
  Everything synchronous finishes first, without interruption.
  :::
  :::flow-step{label="Slow things were handed off" icon="i-lucide-send"}
  The network request, the timer, the file read. The browser does these
  elsewhere while your code carries on.
  :::
  :::flow-step{label="Their callbacks queue" icon="i-lucide-list" highlight}
  When one finishes, its continuation is put in a queue. It does **not**
  interrupt.
  :::
  :::flow-step{label="The queue runs when your code is done" icon="i-lucide-repeat"}
  Which is why `console.log` after a `fetch` prints before the response
  arrives, and why a long synchronous loop freezes the entire page including
  scrolling.
  :::
::

```javascript [order.js]
console.log('1');
setTimeout(() => console.log('2'), 0);      // zero milliseconds!
Promise.resolve().then(() => console.log('3'));
console.log('4');
```

```text [Output]
1
4
3
2
```

Even with a timeout of zero. The synchronous code finishes first, then promises,
then timers. Being able to explain that output is a standard interview question
and it is entirely this diagram.

## What you can do now

You can read and write JavaScript knowing where it differs from Java, and you
know the three differences that cause real bugs: `==`, falsy zero, and nothing
waiting.

## Your turn

::runner{lang="javascript"}
```javascript
const applications = [
  { name: 'Anita Rao',   score: 78 },
  { name: 'Vikram Shah', score: 0  },
  { name: 'Rahul Verma', score: null },
  { name: 'Priya Nair',  score: 75 }
];

// 1. This misses Vikram. Why, and fix it.
const marked = applications.filter(a => a.score);
console.log(marked.length);

// 2. Predict this before running.
console.log('75' == 75, '75' === 75, '8' > 70);

// 3. Shortlist at or above 75, names only, alphabetical.

// 4. Predict the order.
console.log('a');
setTimeout(() => console.log('b'), 0);
Promise.resolve().then(() => console.log('c'));
console.log('d');
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** `0` is falsy, so Vikram's genuine score of zero is filtered out along
  with Rahul's null. Fix: `a.score != null`, which matches both null and
  undefined and correctly keeps 0. This is the zero-versus-missing distinction
  again, and it is worth noticing that it has now appeared in SQL, in Java and in
  JavaScript.

  **2.** `true`, `false`, `false`. The third is the interesting one: `'8' > 70`
  is false, because... actually `'8'` is converted to the number 8 here, and
  8 > 70 is false. Compare `'8' > '70'` and you get `true`, because two strings
  are compared character by character and `'8'` comes after `'7'`. Both results
  are surprising, and both disappear if you convert at the boundary.

  **3.**
  ```javascript
  const shortlisted = applications
    .filter(a => a.score != null && a.score >= 75)
    .map(a => a.name)
    .sort();                                    // ['Anita Rao', 'Priya Nair']
  ```

  **4.** `a`, `d`, `c`, `b`. All synchronous code first, then promise callbacks,
  then timers, even at zero milliseconds.
  :::
::

## Check yourself

1. Why does `if (score)` behave wrongly for a student who scored zero?
2. **An interviewer asks: "what is the difference between `==` and `===`?"** and
   then **"why does `setTimeout(fn, 0)` not run immediately?"**

## The interview question this answers

**"Explain the event loop."** Asked in essentially every JavaScript interview.

One thread runs your code. Slow operations are handed to the browser and their
callbacks are queued. The queue is only processed once the current code has run
to completion, which is why `setTimeout(fn, 0)` runs after everything
synchronous, and why one long loop freezes the entire page including scrolling.

Then the practical consequence, which is what separates the answer: it is also
why you cannot "wait" for data, and therefore why `async`/`await` exists at all.
