`0 == ""` is `true`. That is coercion again, the language converting types for
you, and `==` is where it does the most damage, because an `if` that looks
correct passes for data it should have rejected.

## Why this matters in a job

Because a check like `if (mark == 0)` also passes for an empty text box, and
nothing tells you. Code review at nearly every company will flag `==` on sight,
and a linter rule called `eqeqeq` exists only to forbid it. In interviews,
"difference between `==` and `===`" is asked in almost every JavaScript round,
usually followed by a line like `[] == ![]` and the question "what does this
give, and why?"

## Two ways to ask "are these the same?"

Imagine two clerks checking a roll number on an admission form against the
list.

- The **strict** clerk (`===`) checks the number **and** that it is written the
  same way. `42` typed as a number and `"42"` written as text are different.
  No guessing.
- The **loose** clerk (`==`) is helpful. If the two are written differently, he
  converts one into the other first, then compares. Most of the time he is
  right. Some of the time his conversion rules produce an answer nobody would
  have chosen.

`===` is **strict equality**: same type and same value, no conversion.
`==` is **loose equality**: if the types differ, convert, then compare.
`!==` and `!=` are their opposites.

## How it works

`==` follows a short set of rules when the types differ:

::flow{numbered direction="vertical" caption="What == does when the two sides are different types"}
  :::flow-step{label="null and undefined" icon="i-lucide-circle-off"}
  They are equal to each other and to nothing else. `null == 0` is `false`.
  :::
  :::flow-step{label="A boolean is turned into a number" icon="i-lucide-toggle-left"}
  `true` becomes 1, `false` becomes 0, and the comparison starts again.
  :::
  :::flow-step{label="A string against a number" icon="i-lucide-hash" highlight}
  The string is turned into a number. `"42" == 42` is `true`; `"" == 0` is
  `true`, because an empty string becomes 0.
  :::
  :::flow-step{label="An object against a primitive" icon="i-lucide-box"}
  The object is turned into a primitive, for an array usually by joining its
  items into a string. `[]` becomes `""`, `[7]` becomes `"7"`.
  :::
::

```javascript [equality.js]
console.log(42 === "42", 42 == "42");
console.log(0 == "", 0 == "0", "" == "0");
console.log(null == undefined, null === undefined);
console.log(null == 0, null >= 0);
console.log(true == 1, true == "true");
console.log([] == false, [] == ![]);
console.log(NaN == NaN);

// Objects are compared by reference: is it the SAME object?
const a = { roll: 42 };
const b = { roll: 42 };
const c = a;
console.log(a === b, a == b, a === c);
console.log([78] === [78]);
```

```text [Output]
false true
true true false
true false
false true
true false
true true
false
false false true
false
```

::runner{lang="javascript"}
```javascript
console.log(0 == "", 0 == "0", "" == "0");
```

Walking through the famous ones:

| Expression | Result | Why |
| --- | --- | --- |
| `0 == ""` | `true` | `""` becomes 0 |
| `0 == "0"` | `true` | `"0"` becomes 0 |
| `"" == "0"` | `false` | Both strings, so no conversion: different text |
| `null == 0` | `false` | `null` equals only `undefined` under `==` |
| `null >= 0` | `true` | `>=` is not `==`: it converts `null` to 0 |
| `true == "true"` | `false` | `true` becomes 1, `"true"` becomes `NaN` |
| `[] == false` | `true` | `false` becomes 0, `[]` becomes `""` then 0 |
| `[] == ![]` | `true` | `![]` is `false` (an array is truthy), then as above |
| `NaN == NaN` | `false` | `NaN` equals nothing, including itself |
| `{} === {}` | `false` | Two different objects, even with the same contents |

Look at the first three rows together. `0` equals `""` and `0` equals `"0"`,
but `""` does not equal `"0"`. Loose equality is not even consistent with
itself, which is the strongest argument for never relying on it.

## Real use case

Using `===` does not remove the need to think about types. It moves the bug
from "passes when it should not" to "fails when it should pass", which is
easier to notice. A very common case: an ID read from the URL is a string, and
the same ID in data from the server is a number.

```javascript [student-page.js]
const students = [
  { id: 41, name: "Anita Rao" },
  { id: 42, name: "Vikram Shah" }
];

// From a URL like /students?id=42 the value is ALWAYS a string.
const idFromUrl = "42";

const wrong = students.find(s => s.id === idFromUrl);
console.log(String(wrong));                        // not found: "42" is not 42

// The fix is to convert once, not to switch to ==.
const id = Number(idFromUrl);
const right = students.find(s => s.id === id);
console.log(right.name);

// The one place == is idiomatic: "is it null or undefined?"
const middleName = undefined;
console.log(middleName == null);                   // same as === null || === undefined
```

```text [Output]
undefined
Vikram Shah
true
```

## What confuses people here

That `===` is "slower" or "stricter" in a way that causes problems. It is
neither slower nor harder; it only refuses to guess. The other confusion is
comparing objects: two arrays with the same numbers are **not** `===`, because
`===` on objects asks "is this the same object in memory?", the same as `==` on
two objects in Java. To compare contents you compare the fields, or for simple
data, `JSON.stringify(a) === JSON.stringify(b)`, which only works when the keys
are in the same order.

For the two edge cases where even `===` is odd (`NaN === NaN` is `false` and
`0 === -0` is `true`) there is `Object.is(a, b)`, which gets both right. You
will rarely need it.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between == and ===?" icon="i-lucide-message-circle"}
  `===` compares type and value with no conversion. `==` converts the types
  first if they differ, then compares. So `42 == "42"` is `true` and
  `42 === "42"` is `false`. Always use `===`, with one deliberate exception:
  `x == null` is a short way to check for both `null` and `undefined`.
  :::

  :::accordion-item{label="What does [] == ![] give, and why?" icon="i-lucide-message-circle"}
  `true`. `![]` is `false`, because an array is truthy. Now it is `[] == false`.
  The boolean becomes 0. The array becomes a primitive by joining its items,
  which gives `""`, and `""` becomes 0. `0 == 0` is `true`.
  :::

  :::accordion-item{label="Why is null == 0 false but null >= 0 true?" icon="i-lucide-message-circle"}
  They use different rules. `==` has a special case: `null` is only loosely
  equal to `undefined`. The relational operators (`<`, `>`, `<=`, `>=`)
  convert both sides to numbers, and `Number(null)` is 0, so `0 >= 0` is `true`.
  :::

  :::accordion-item{label="Why is {} === {} false?" icon="i-lucide-message-circle"}
  Objects are compared by reference, not by contents. Each `{}` creates a new
  object at a different place in memory, so they are two objects. `const a =
  {}; const b = a; a === b` is `true`, because both names point at one object.
  :::

  :::accordion-item{label="What is Object.is?" icon="i-lucide-message-circle"}
  A third comparison that behaves like `===` except in two cases:
  `Object.is(NaN, NaN)` is `true` and `Object.is(0, -0)` is `false`. It exists
  for code that must tell those apart; ordinary comparisons use `===`.
  :::
::
