They are not gone. When a function is created inside another function, it
keeps a live link to the variables it could see at that moment, and it keeps
that link for as long as the inner function exists. That link is a
**closure**, and it is the single most asked JavaScript interview topic after
the event loop.

## Why this matters in a job

Because you write closures every day without the word. A click handler that
uses a variable from the function that attached it is a closure. So is every
callback passed to `setTimeout`, every `debounce`, and every factory function
that hands back a configured helper. When one of them holds a stale value, or
the loop bug below prints the same number three times, knowing the mechanism is
the difference between a five-minute fix and an afternoon.

In interviews the question comes in three forms: "what is a closure?", "write
a counter using a closure", and a `for` loop with `var` and `setTimeout` with
"what does this print?"

## A backpack the function carries

When a function is created, it packs a **backpack** containing the variables
of the scope it was written in. Not copies of their values: the variables
themselves. Wherever the function goes afterwards, it carries the backpack, and
every time it runs it can open it, read the variables, and change them.

In real terms: a **closure** is a function together with the scope it was
created in. Because of lexical scope, the inner function can see the outer
function's variables. Because the inner function still refers to them, the
engine does not throw them away when the outer function returns.

## How it works

```javascript [roll-numbers.js]
function makeRollNumberGenerator(prefix) {
  let next = 1;                                   // lives in the backpack

  return function () {
    const roll = prefix + String(next).padStart(3, "0");
    next++;
    return roll;
  };
}

const cseRoll = makeRollNumberGenerator("CSE");
const eceRoll = makeRollNumberGenerator("ECE");

console.log(cseRoll());
console.log(cseRoll());
console.log(eceRoll());
console.log(cseRoll());
console.log(typeof next);                          // not visible out here
```

```text [Output]
CSE001
CSE002
ECE001
CSE003
undefined
```

That last line of output is also the point: `next` cannot be reached from
outside. The only way to change it is to call the function. That is **private
state**, which JavaScript objects did not have for most of their history, and
closures were how you got it.

::runner{lang="javascript"}
```javascript
function makeFeeAccount(balance) {
  return {
    pay(amount) { balance -= amount; return balance; },
    getBalance() { return balance; }
  };
}

const anita = makeFeeAccount(45000);
anita.pay(20000);
console.log(anita.getBalance());
console.log(String(anita.balance));   // there is no such property
```

### The loop bug

This is the one you will be given on paper.

```javascript [loop-var.js]
for (var i = 1; i <= 3; i++) {
  setTimeout(() => console.log("Semester " + i), 100);
}
```

```text [Output]
Semester 4
Semester 4
Semester 4
```

Three functions, and each closes over `i`. But `var` is function scoped, so
there is only **one** `i` for the whole loop. By the time the timers fire,
100 milliseconds later, the loop has finished and that one `i` is 4. Closures
capture the **variable**, not the value it had when the function was made.

Two fixes, and you should be able to give both:

```javascript [loop-fixed.js]
// Fix 1: let. A for loop with let makes a NEW i for every pass.
for (let i = 1; i <= 3; i++) {
  setTimeout(() => console.log("Semester " + i), 100);
}

// Fix 2, the pre-2015 way: an IIFE gives each pass its own scope.
for (var j = 1; j <= 3; j++) {
  (function (semester) {
    setTimeout(() => console.log("Semester " + semester), 200);
  })(j);
}
```

```text [Output]
Semester 1
Semester 2
Semester 3
Semester 1
Semester 2
Semester 3
```

The same bug without a timer, so you can run it here:

::runner{lang="javascript"}
```javascript
const withVar = [];
for (var i = 1; i <= 3; i++) {
  withVar.push(() => i);
}
console.log(withVar.map(f => f()).join(", "));

const withLet = [];
for (let k = 1; k <= 3; k++) {
  withLet.push(() => k);
}
console.log(withLet.map(f => f()).join(", "));
```
::

```text [Output]
4, 4, 4
1, 2, 3
```

## Real use case

**Debounce.** A student-search box calls the server on every keystroke.
Typing "Anita" sends five requests, and on a slow connection they can come back
out of order, so the list shows results for "Ani" after the results for
"Anita". Debouncing means "wait until the user stops typing for 300
milliseconds, then run once". It is a closure holding a timer.

```javascript [debounce.js]
function debounce(fn, delay) {
  let timerId;                                  // in the backpack, shared by every call

  return function (...args) {
    clearTimeout(timerId);                      // cancel the previous wait
    timerId = setTimeout(() => fn(...args), delay);
  };
}

const searchStudents = debounce(query => {
  console.log("Searching for " + query);
}, 300);

searchStudents("A");
searchStudents("An");
searchStudents("Ani");
searchStudents("Anit");
searchStudents("Anita");
```

```text [Output]
Searching for Anita
```

Five calls, one search. Every call reaches into the same backpack and cancels
the timer the previous call set. Only the last one survives its 300
milliseconds. In a real page, `searchStudents` is what you attach to the input
box's `input` event, and lodash's `debounce` is the library version of these
seven lines.

## What confuses people here

That a closure copies values. It does not. It keeps the variables, which is
why the `var` loop prints 4 three times and why the fee account's balance
changes between calls.

The second confusion is memory. A closure keeps its variables alive as long as
the function exists. Attach a closure that holds a large array to an element,
remove the element but not the listener, and the array cannot be freed. That is
the usual shape of a memory leak in front-end code.

## Interview questions

::accordion
  :::accordion-item{label="What is a closure?" icon="i-lucide-message-circle"}
  A function together with the variables of the scope it was created in. The
  inner function keeps access to those variables even after the outer function
  has returned. Prove it with a counter:

  ```javascript
  function counter() {
    let count = 0;
    return () => ++count;
  }
  const next = counter();
  console.log(next(), next(), next());   // 1 2 3
  ```
  :::

  :::accordion-item{label="What does a for loop with var and setTimeout print, and how do you fix it?" icon="i-lucide-message-circle"}
  `for (var i = 0; i < 3; i++) setTimeout(() => console.log(i), 0);` prints
  `3 3 3`. There is one `i` for the whole loop and the callbacks run after the
  loop has finished. Fix with `let`, which creates a new binding each pass
  (`0 1 2`), or wrap the body in an IIFE that takes `i` as a parameter.
  :::

  :::accordion-item{label="Give a practical use of closures." icon="i-lucide-message-circle"}
  Private state (a counter or account that can only be changed through its
  functions), function factories (`atLeast(60)` returning a checker), event
  handlers that remember their row, and `debounce` or `throttle`, which hold a
  timer in a closure. Naming debounce and writing it is the answer that stands
  out.
  :::

  :::accordion-item{label="Can closures cause memory leaks?" icon="i-lucide-message-circle"}
  Yes. A closure keeps every variable it refers to alive while the function
  itself is reachable. A long-lived event listener or timer holding a closure
  over a large object keeps that object in memory. The fix is to remove the
  listener (`removeEventListener`) or clear the timer when it is no longer
  needed.
  :::

  :::accordion-item{label="What does this print? function f() { let x = 1; return () => x++; } const g = f(); g(); console.log(g());" icon="i-lucide-message-circle"}
  `2`. The first `g()` returns 1 and moves `x` to 2. The second returns the
  current value, 2, and moves `x` to 3. `x++` returns the value before
  increasing it.
  :::
