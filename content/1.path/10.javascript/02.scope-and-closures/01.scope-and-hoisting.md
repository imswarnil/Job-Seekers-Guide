`grade` worked above its own line, and a `const` arrow function in the same
place would have thrown. The reason is that JavaScript reads your code twice:
once to find every name and decide where it lives, and once to run it. Where a
name lives is its **scope**. What happens in that first read is **hoisting**.

## Why this matters in a job

Because "what does this print?" questions are almost always scope and hoisting
questions in disguise, and they are the most common written test in a fresher
JavaScript round. At work, scope is how you stop two scripts on one page
overwriting each other's variables, and how you read a bug where a value is
`undefined` when it "clearly" has been set.

## Rooms inside rooms

Picture the college building. The campus has a notice board everybody can
read. Each department has its own board, readable only inside the department.
Each lab inside a department has a board too.

- Standing in a lab, you can read the lab's board, the department's board and
  the campus board. You look **nearest first**.
- Standing on the campus, you cannot read a lab's board.
- If the lab and the department both have a notice called `timetable`, the lab's
  one hides the other while you are in the lab.

In JavaScript those are the three scopes:

- **Global scope**: names declared outside every function and block. Visible
  everywhere.
- **Function scope**: names declared inside a function. Visible only inside it.
  `var` always lives here.
- **Block scope**: names declared with `let` or `const` inside `{ }`. Visible
  only inside that block.

Looking a name up **nearest first, then outwards** is the **scope chain**.
Hiding an outer name with an inner one of the same name is **shadowing**. And
the rooms are decided by **where the code is written**, not where it is called
from. That is called **lexical scope**, and it is what makes closures possible
in the next lesson.

## How it works

Before a single line runs, JavaScript goes through each scope and registers
every declaration in it. That first pass is hoisting. What each declaration
looks like after it:

| Declaration | After the first pass | Using it before its line |
| --- | --- | --- |
| `function grade() {}` | Exists, with its whole body | Works |
| `var total = 100` | Exists, set to `undefined` | Gives `undefined` |
| `let` / `const` / `class` | Exists, but uninitialised | `ReferenceError` |

That last row has a name. The stretch of code between the start of the scope
and the line where a `let` or `const` is declared is the **temporal dead
zone** (TDZ). The variable exists, it is blocking the name, and touching it
throws.

Now four puzzles, the kind you will be given on paper. Predict each one.

```javascript [hoisting.js]
// 1. var before its line
console.log(String(total));
var total = 100;

// 2. A declaration before its line
console.log(typeof calculateGpa);
function calculateGpa() { return 8.2; }

// 3. A local var shadows the global one, from the top of the function
var dept = "CSE";
function showDept() {
  console.log(String(dept));
  var dept = "ECE";
}
showDept();

// 4. A local let: the temporal dead zone, not the outer value
let section = "A";
function showSection() {
  try {
    console.log(section);
  } catch (error) {
    console.log(error.name);
  }
  let section = "B";
}
showSection();

// 5. A function and a var with the same name
console.log(typeof college);
var college = "LNCT";
function college() {}
console.log(typeof college);
```

```text [Output]
undefined
function
undefined
ReferenceError
function
string
```

Puzzle 4 is the same shape with `let`, and the answer is not `"A"`. The local
`section` exists from the top of the function, in its dead zone, so it hides
the global one and throws.

adds nothing because the name already exists; then the assignment runs and
replaces the function with a string.

## Real use case

In a browser, every `var` and every function declaration at the top level of a
plain script becomes a property of the global `window` object. That is shared by
every script on the page, including third-party ones, and some names are
already taken. Typed at the top level of a script in Chrome:

```javascript [global.js]
var name = 42;
console.log(typeof name);
```

```text [Output]
string
```

`window.name` already exists, and anything assigned to it is converted to a
string. Your number is gone, and nothing warned you. With `let name = 42` the
output is `number`, because `let` and `const` at the top level do not become
properties of `window`.

This is why real front-end code is written in **modules** (files loaded with
`<script type="module">` or through a bundler). Each module has its own scope,
so nothing leaks into `window` unless you put it there deliberately. Before
modules existed, the same effect was got by wrapping a whole file in a function
that runs immediately, an **IIFE** (immediately invoked function expression):

```javascript [iife.js]
(function () {
  var attendanceCache = {};          // private to this file
  console.log(typeof attendanceCache);
})();
console.log(typeof attendanceCache); // not visible out here
```

```text [Output]
object
undefined
```

You will see IIFEs in older libraries and in interview questions.

## What confuses people here

That hoisting "moves code to the top". Nothing moves. The declarations are
registered before execution; the **assignments stay on their own line**. That
is why `var total = 100` is `undefined` before its line and not 100.

The second confusion: that `let` and `const` are not hoisted. They are, which
is why puzzle 4 throws instead of reading the outer `section`. The difference is
that they are not initialised, so the dead zone protects you from reading them
early.

## Interview questions

::accordion
  :::accordion-item{label="What is hoisting?" icon="i-lucide-message-circle"}
  Before running a scope, JavaScript registers every declaration in it.
  Function declarations are registered with their body, so they can be called
  before their line. `var` is registered as `undefined`. `let`, `const` and
  `class` are registered but uninitialised, so using them early throws a
  `ReferenceError`. Only declarations are hoisted, never assignments.
  :::

  :::accordion-item{label="What is the temporal dead zone?" icon="i-lucide-message-circle"}
  The part of a scope before a `let` or `const` declaration line. The variable
  exists there (it shadows any outer variable of the same name) but reading or
  writing it throws `ReferenceError: Cannot access 'x' before initialization`.
  Even `typeof x` throws inside the dead zone.
  :::

  :::accordion-item{label="What does this print? var a = 1; function f() { console.log(a); var a = 2; } f();" icon="i-lucide-message-circle"}
  `undefined`. The `var a` inside `f` is hoisted to the top of `f` as
  `undefined`, and it shadows the global `a`. The assignment of 2 has not run
  yet when the log happens.
  :::

  :::accordion-item{label="What is lexical scope?" icon="i-lucide-message-circle"}
  A function's access to variables is decided by where the function is
  **written** in the code, not where it is called from. A function written
  inside another can read the outer one's variables, wherever it is later
  called. That is the rule closures rely on.
  :::

  :::accordion-item{label="What is the scope chain?" icon="i-lucide-message-circle"}
  The order in which JavaScript looks for a name: the current block, then the
  enclosing function, then each outer function, then the global scope. The
  first match wins. If there is no match anywhere, it is a `ReferenceError`.
  :::
::
