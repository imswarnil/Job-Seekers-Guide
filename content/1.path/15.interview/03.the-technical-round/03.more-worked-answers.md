Yes, the same five steps hold for all three. A SQL question gets a query as its
example. An OS question gets a small program and a real-life picture. A DSA
question bends the steps slightly, because "definition" becomes restating the
problem, but the shape is identical.

## Why it matters

These three are the kinds freshers answer worst. SQL, because people describe a
join in words instead of showing rows. OS, because the answers are memorised
lists with no example. DSA, because people start coding before saying anything.
The format fixes all three in the same way.

## A worked example: SQL, what is the difference between INNER JOIN and LEFT JOIN?

**1. Definition.** "A join combines rows from two tables using a matching
column. An INNER JOIN keeps only the rows that match in both tables. A LEFT JOIN
keeps every row from the left table, and fills the right side with NULL where
there is no match."

**2. How it works.** "For each row in the left table, the database looks for
rows in the right table where the join condition is true. With INNER, a left row
with no match is dropped. With LEFT, it is kept once, with NULLs for the right
table's columns."

**3. Example.** "Three students, and exam results for only two of them."

::runner{lang="sql"}
```sql
CREATE TABLE student (id INT PRIMARY KEY, name TEXT);
CREATE TABLE exam_result (student_id INT, subject TEXT, marks INT);
INSERT INTO student VALUES (101, 'Anita'), (102, 'Vikram'), (103, 'Priya');
INSERT INTO exam_result VALUES (101, 'DBMS', 78), (102, 'DBMS', 64);

-- INNER: only students who have a result
SELECT s.name, r.marks
FROM student s
INNER JOIN exam_result r ON r.student_id = s.id
ORDER BY s.id;

-- LEFT: every student, NULL where there is no result
SELECT s.name, r.marks
FROM student s
LEFT JOIN exam_result r ON r.student_id = s.id
ORDER BY s.id;
```
::

```text [Output]
INNER JOIN            LEFT JOIN
name    | marks       name    | marks
--------+------       --------+------
Anita   | 78          Anita   | 78
Vikram  | 64          Vikram  | 64
                      Priya   | NULL
```

"Priya has no result yet. The INNER JOIN silently leaves her out; the LEFT JOIN
shows her with NULL."

**4. Where it is used, and the trade-off.** "LEFT JOIN is how you find what is
missing: add `WHERE r.student_id IS NULL` and you get every student with no
result, which is a real report a college runs before results day. The trap is
that an INNER JOIN drops rows without any error, so a count of 'students' from
an INNER JOIN can be quietly wrong."

**5. Stop.**

::tip
The follow-up is often "write a query for students with no result". If you said
step 4, you have already said it.
::

## A worked example: OS, what is a deadlock?

**1. Definition.** "A deadlock is when two or more processes or threads are each
waiting for a resource that another one is holding, so none of them can ever
continue."

**2. How it works.** "Four conditions have to hold at the same time, the Coffman
conditions. Mutual exclusion: a resource can be held by only one at a time. Hold
and wait: a thread holds one resource while waiting for another. No pre-emption:
nobody can forcibly take a resource away. Circular wait: A waits for B, B waits
for A. Break any one and deadlock cannot happen."

**3. Example.** "In real life: two students in a library each holding one of the
two books the other needs for the same assignment, and neither will put theirs
down first. In code, two threads locking the same two records in opposite
order:"

```java [RecordDeadlock.java]
public class RecordDeadlock {
    static final Object feeRecord = new Object();
    static final Object hostelRecord = new Object();

    public static void main(String[] args) {
        Thread clerk1 = new Thread(() -> {
            synchronized (feeRecord) {
                System.out.println("Clerk 1 holds fee record, waiting for hostel record");
                pause();
                synchronized (hostelRecord) {
                    System.out.println("Clerk 1 updated both");
                }
            }
        });
        Thread clerk2 = new Thread(() -> {
            synchronized (hostelRecord) {
                System.out.println("Clerk 2 holds hostel record, waiting for fee record");
                pause();
                synchronized (feeRecord) {
                    System.out.println("Clerk 2 updated both");
                }
            }
        });
        clerk1.start();
        clerk2.start();
    }

    static void pause() {
        try { Thread.sleep(100); } catch (InterruptedException e) { }
    }
}
```

```text [Output]
Clerk 1 holds fee record, waiting for hostel record
Clerk 2 holds hostel record, waiting for fee record
(nothing else is ever printed; the program never exits)
```

The first two lines can appear in either order. What never appears is "updated
both".

"The fix is to break circular wait: every thread locks the fee record first and
the hostel record second. Then the second clerk waits at the first lock instead
of grabbing the other record."

**4. Where it is used, and the trade-off.** "Databases see this with
transactions updating the same rows in different orders. They detect the cycle
and abort one transaction, which then has to retry. In code, the usual cure is a
fixed lock order or a timeout with `tryLock`. The trade-off is that prevention
limits how you write code, and detection costs a retry."

**5. Stop.**

## A worked example: DSA, explain your approach

"Explain your approach" is a different kind of question: there is no definition
to give. The five steps bend, and still hold.

| Usual step | For a coding problem |
| --- | --- |
| Definition | Restate the problem and ask what is unclear |
| How it works | The brute-force approach first, then the better one |
| Example | Dry-run the better one on a small input |
| Used / trade-off | Time and space complexity, and what you gave up |
| Stop | Ask "shall I write it?" |

**The problem:** "Given a list of roll numbers from an online form, return the
first roll number that was submitted twice."

**1. Restate and clarify.** "So I scan the list in order and return the first
roll number that appears for the second time. Can the list be empty? What should
I return if there is no duplicate? Is 'first' the first one whose second
appearance comes earliest?" The interviewer says: yes it can be empty, return
null, and yes.

**2. The approach.** "The brute force is: for each roll number, check every
earlier one. That is O(n²). Better: walk the list once and keep a HashSet of what
I have seen. The first roll number that is already in the set is the answer.
That is one pass."

**3. Dry run.** "For 104, 101, 107, 101, 104: add 104, add 101, add 107, then
101 is already in the set, return 101. The second 104 is never reached."

```java [DuplicateRoll.java]
import java.util.HashSet;
import java.util.List;
import java.util.Set;

public class DuplicateRoll {
    static Integer firstDuplicate(List<Integer> rolls) {
        Set<Integer> seen = new HashSet<>();
        for (int roll : rolls) {
            if (!seen.add(roll)) {   // add() returns false if it was already there
                return roll;
            }
        }
        return null;
    }

    public static void main(String[] args) {
        System.out.println(firstDuplicate(List.of(104, 101, 107, 101, 104)));
        System.out.println(firstDuplicate(List.of(101, 102, 103)));
        System.out.println(firstDuplicate(List.of()));
    }
}
```

```text [Output]
101
null
null
```

**4. Complexity and trade-off.** "O(n) time and O(n) extra space for the set. I
could get O(1) extra space by sorting first, but that is O(n log n) and loses the
order, so it would not give the first duplicate any more."

**5. Stop.** "Shall I write it?", or, if you already have, "shall I run another
case?"

::note
Freshers most often skip step 1 and step 4. Step 1 is where the interviewer
learns you ask before you assume. Step 4 is the question they will ask anyway,
and volunteering it is better than being asked.
::

## Common mistakes

- **A SQL answer with no rows.** Show a tiny table and what comes out. It is
  faster than any explanation.
- **Listing the four deadlock conditions with no example.** That is the answer
  of everybody who read the same page. The example is what is yours.
- **Coding before explaining the approach.** If the approach is wrong, you find
  out after ten minutes of typing. Said out loud, the interviewer corrects it in
  ten seconds.
- **Getting the complexity of your own code wrong.** Worse than a slow solution.
  Count the loops before you say it.

## How to practise

One question from each of SQL, OS and DSA every day for a week, in the five
steps, out loud. For SQL, run your example in the runner above or in any SQL
tool, so the rows you describe are rows you have seen.
