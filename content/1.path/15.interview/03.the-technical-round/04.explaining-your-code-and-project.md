You know your project better than anybody in the room, which is exactly why it
goes wrong. You skip the sentence that would have made the rest make sense. This
page is how to say it in the order a listener needs.

## Why it matters

In most fresher technical rounds, the project is the longest single topic, often
10 to 20 minutes. It is also the only topic where the interviewer cannot check
your answer against a textbook, so they check it against itself: they push on
one part until you either get more precise or get vague.

## The two-minute walkthrough

Almost every candidate starts with the technology. Start with the problem.

::compare{caption="The same project, two openings."}
  :::compare-side{label="Starts with the stack" verdict="wrong"}
  "So I used Java for the backend, JDBC to connect, MySQL for the database, and
  HTML and CSS for the front end, and Eclipse as the IDE, and…"

  The listener has no idea what the thing does, so none of that means anything
  yet. And they now have a list to remember.
  :::
  :::compare-side{label="Starts with the problem" verdict="right"}
  "In my college, marks were entered in a spreadsheet by each lecturer, and the
  office calculated grades by hand at the end of term, which took a week and
  had mistakes.

  So I built a result system: lecturers enter marks, and it calculates each
  student's percentage and grade in one SQL query per class.

  It's Java with JDBC on MySQL, three tables.

  The hardest part was stopping bad data. A lecturer typed 780 instead of 78, and
  it went straight into the average. I added a CHECK constraint in the database
  so marks above the maximum are rejected, whoever inserts them."
  :::
::

::pull-quote
Problem, what you built, the stack, the hard part. Four parts, in that order, and
the fourth is the one that gets you remembered.
::

```text [project-walkthrough.txt]
PROBLEM     Who had what problem? "[Who] used to [how it was done], which
            [what went wrong]."
BUILT       "So I built [what], which [does what], for [how many / how much]."
STACK       "It's [language] with [framework / library] on [database]." One line.
HARD PART   "The hardest part was [a specific problem with a name]. I [what you
            did], because [why]. Now I'd also [one thing you'd change]."
```

## Choosing the hard part

The hard part is the part the interviewer will spend the next ten minutes on.
Choose it deliberately.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-search" title="Something with a name"}
  "Marks above the maximum getting in", "two students with the same roll number",
  "the grade query was slow". Never "learning Java" and never "all of it".
  :::
  :::feature{icon="i-lucide-scale" title="Include what you decided against"}
  "I could have checked it in Java, but then a script inserting directly would
  skip it, so I put the rule in the database." A rejected alternative is the
  clearest signal of judgement there is.
  :::
  :::feature{icon="i-lucide-wrench" title="Name one thing you would change"}
  "I store the grade in the table; I'd calculate it instead, because if the
  grading rule changes, the stored grades are wrong." Honest criticism of your
  own work lands well.
  :::
  :::feature{icon="i-lucide-users" title="Say which part was yours"}
  In a team project, the hard part must be from your part. They will ask
  follow-ups only the person who wrote it can answer.
  :::
::

## Explaining a piece of your code

Sometimes they say "share your screen and show me some code", or "write the part
that saves the marks". Explain it in the order it runs, and say *why* at each
block, not *what*. They can read the what.

```java [ResultDao.java]
public void saveMarks(int studentId, int subjectId, int marks) throws SQLException {
    String sql = "INSERT INTO exam_result (student_id, subject_id, marks) VALUES (?, ?, ?)";
    try (Connection con = DriverManager.getConnection(URL, USER, PASSWORD);
         PreparedStatement ps = con.prepareStatement(sql)) {
        ps.setInt(1, studentId);
        ps.setInt(2, subjectId);
        ps.setInt(3, marks);
        ps.executeUpdate();
    }
}
```

::compare{caption="Explaining the same eleven lines."}
  :::compare-side{label="Reading it aloud" verdict="wrong"}
  "Here I create a string sql, then I get a connection, then I prepare the
  statement, then I set int one, set int two, set int three, then execute
  update."

  Every word is visible on the screen. The interviewer learns nothing about
  whether you understood it.
  :::
  :::compare-side{label="Explaining the decisions" verdict="right"}
  "This saves one mark. I use a PreparedStatement with question marks instead of
  joining the values into the string, so a value can never be run as SQL, which
  is how SQL injection is prevented. The try-with-resources closes the
  connection and statement even if the insert fails, so connections do not leak.
  If the marks break the CHECK constraint, `executeUpdate` throws, and the
  caller shows the lecturer the error."
  :::
::

## The questions every project gets

::accordion
  :::accordion-item{label="1. Walk me through your project." icon="i-lucide-message-circle"}
  The four parts above. Two minutes. Then stop and let them choose.
  :::
  :::accordion-item{label="2. Why did you use X and not Y?" icon="i-lucide-message-circle"}
  If it was a real decision, say the reason and the alternative. If the honest
  answer is "it was what the course used", say that, and then show you thought
  about it: "that was the default. Since then I've read about Y, and I'd consider
  it when…" Pretending a default was a decision is transparent.
  :::
  :::accordion-item{label="3. What was the hardest part?" icon="i-lucide-message-circle"}
  The hard part you chose. Something with a name, what you did, what you
  rejected.
  :::
  :::accordion-item{label="4. Draw the tables." icon="i-lucide-message-circle"}
  Know your schema by heart: the tables, the primary keys, the foreign keys. For
  a Java and SQL project, this is asked more than anything else. Three tables
  drawn on paper in thirty seconds is a strong answer by itself.
  :::
  :::accordion-item{label="5. What would you do differently?" icon="i-lucide-message-circle"}
  A decision, not a bug. "I'd calculate the grade instead of storing it."
  :::
  :::accordion-item{label="6. Was it a team project? What was your part?" icon="i-lucide-message-circle"}
  Say your part exactly. "Four of us. I built the login and the marks entry
  screen, and the JDBC layer under both." Knowing the rest well enough to explain
  it is a bonus. Claiming it is a risk.
  :::
  :::accordion-item{label="7. Did anyone use it?" icon="i-lucide-message-circle"}
  If somebody did, it is your best material. If nobody did, say so. Inventing
  users is the worst risk to take, because the follow-up questions are endless
  and specific.
  :::
::

## Common mistakes

- **Starting with the technology.** Problem first, always.
- **Not knowing your own tables.** For a database project, this ends the
  conversation.
- **"We did" for everything, or "I did" for everything.** Both are wrong. Say
  exactly which part was yours.
- **A project you cannot run.** Have it open, running, on the file you want to
  discuss, before the interview starts.

## How to practise

::steps
### Write the four-part walkthrough
Problem, built, stack, hard part. Time it at two minutes.

### Draw your tables from memory
On paper. Check against the real schema. Repeat until they match.

### Explain one file out loud
The one with a real decision in it. Say why at every block, never only what.

### Ask a friend to say "why?" after every sentence
The place you run out of answers is what to study tonight.
::
