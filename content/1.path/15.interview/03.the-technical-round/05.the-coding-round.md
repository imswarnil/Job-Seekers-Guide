One problem, somebody watching, and a reputation for testing algorithms. At
fresher level it mostly tests something else: whether you can be worked with on
a problem. That is a performance you can rehearse.

## Why it matters

In a fresher round the coding part is usually 10 to 30 minutes: reverse a
string, count vowels, second largest in an array, find duplicates, a pattern
printing loop, or a SQL query. At product companies and startups there is often
a separate 45 to 60 minute coding round, sometimes on a platform like HackerRank
before you meet anybody.

::pull-quote
Two candidates get the same problem. One solves it silently in fifteen minutes.
One talks through their thinking, gets 80% of the way, and says what they would
do next. The second one is hired more often than people believe.
::

## What is being marked

::feature-list{columns="2"}
  :::feature{icon="i-lucide-message-circle-question" title="Do you ask before you code"}
  The problem is often deliberately vague. Starting to type immediately fails
  the first thing being tested.
  :::
  :::feature{icon="i-lucide-mic" title="Can I hear you think"}
  Silence is the most common way this round is lost. The interviewer cannot help
  you and cannot give partial credit for thinking they never heard.
  :::
  :::feature{icon="i-lucide-move-horizontal" title="Do you consider the edges"}
  Empty input, one element, duplicates, null, negative numbers. Naming these
  unprompted is worth more than an optimal solution.
  :::
  :::feature{icon="i-lucide-gauge" title="Do you know what it costs"}
  You will be asked the time complexity. Getting it wrong about your own code is
  worse than a slow solution.
  :::
::

## What to do: the five steps

In this order, every time, out loud.

::flow{numbered direction="vertical" caption="Do not start at step four."}
  :::flow-step{label="1. Clarify: repeat it back and ask" icon="i-lucide-help-circle" highlight}
  Say the problem in your own words and ask two or three questions. Can the
  input be empty? Can there be duplicates? Is the boundary included? Two minutes,
  and the highest-value thing in the round.
  :::
  :::flow-step{label="2. Work one example by hand" icon="i-lucide-pencil"}
  Four or five values including an awkward one, and the expected output. You now
  have a test, and you catch a misunderstanding before it costs twenty minutes.
  :::
  :::flow-step{label="3. Brute force first, then optimise" icon="i-lucide-route"}
  "The obvious way is a nested loop, O(n²). With a set I think it is O(n). Shall
  I write that?" This is where they redirect you if you are heading somewhere
  wrong, and it costs nothing.
  :::
  :::flow-step{label="4. Write it, narrating" icon="i-lucide-code"}
  Say why, not what. "Skipping nulls first, because comparing a null would
  throw."
  :::
  :::flow-step{label="5. Dry run, then state the complexity" icon="i-lucide-check-check"}
  Walk your example through the code line by line. Then the empty input. Then
  "O(n) time, O(n) space." Volunteering it is better than being asked.
  :::
::

## A worked example

**The problem:** "Given a list of entrance test entries, each a student's name
and marks, return the names of students who scored at or above a cutoff."

```text [Step 1, out loud]
"So: a list of entries, each with a name and marks, and a cutoff. I return the
names of those at or above it.

Three questions. Can marks be missing, meaning not marked yet? Can the same
student appear twice, if they took the test twice? And does 'at or above'
include exactly the cutoff?"
```

The interviewer says: yes, marks can be missing; yes, students can repeat; yes,
inclusive. You have avoided three bugs, and they know you would ask rather
than guess.

```text [Step 2]
"With cutoff 75:
   Anita, 78   → in
   Vikram, 64  → out
   Anita, 76   → in, but she's already there, so once
   Rahul, none → out, not marked
   Priya, 75   → in, exactly the cutoff
 Expected: Anita, Priya."
```

```text [Step 3]
"Brute force: collect everyone over the cutoff, then for each name scan the
result list to see if it is already there. That is O(n²) in the worst case.
Better: one pass, skip missing marks, check the cutoff, and add the name to a
LinkedHashSet, which ignores duplicates and keeps the order. O(n). Shall I
write that?"
```

```java [Shortlist.java]
import java.util.ArrayList;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

public class Shortlist {
    record Entry(String name, Integer marks) {}

    static List<String> shortlist(List<Entry> entries, int cutoff) {
        if (entries == null) return List.of();
        Set<String> names = new LinkedHashSet<>();   // no duplicates, keeps order
        for (Entry e : entries) {
            if (e.marks() == null) continue;           // not marked yet
            if (e.marks() >= cutoff) {                 // inclusive
                names.add(e.name());
            }
        }
        return new ArrayList<>(names);
    }

    public static void main(String[] args) {
        List<Entry> entries = List.of(
            new Entry("Anita", 78), new Entry("Vikram", 64),
            new Entry("Anita", 76), new Entry("Rahul", null),
            new Entry("Priya", 75));
        System.out.println(shortlist(entries, 75));
        System.out.println(shortlist(List.of(), 75));
    }
}
```

```text [Output]
[Anita, Priya]
[]
```

```text [Step 5, out loud]
"Dry run: Anita 78 added, Vikram 64 skipped, Anita 76 already in the set so it
stays once, Rahul has no marks so skipped, Priya 75 added because it's >=.
Gives Anita and Priya. An empty list gives an empty list.

O(n) time, O(n) space for the set.

One thing I'd ask in a real system: whether 'at or above' is really the rule,
because the students on exactly 75 will be the ones who phone the office."
```

That last sentence is the one that gets remembered.

## When you are stuck

You will be. Being stuck is normal. Being stuck silently is what loses the
round.

::compare{caption="The same forty seconds of not knowing."}
  :::compare-side{label="Silence" verdict="wrong"}
  You stare at the screen. The interviewer cannot tell whether you are thinking
  or lost, cannot help, and starts writing something down.
  :::
  :::compare-side{label="Narrated" verdict="right"}
  "I'm stuck on keeping the order while removing duplicates. A HashSet loses the
  order. I think there is a LinkedHashSet. If not, I'd use an ArrayList with a
  HashSet beside it to check membership. Does that sound reasonable?"

  They say "LinkedHashSet is right", and you have lost twenty seconds.
  :::
::

## Common mistakes

- **Typing in the first minute.** Clarify first. Every time.
- **Going silent for more than about ten seconds.** Say what you are
  considering, even if it is "I'm working out whether I need to sort this".
- **Skipping the brute force.** Saying it first shows you can solve it at all,
  and gives you something to improve.
- **Never testing.** Almost nobody dry-runs their own code, and it is free marks.
- **Forgetting method names and freezing.** "I don't remember the exact method.
  The idea is X. Can I write it as `isPresent()` and move on?" is fine.

## How to practise

::steps
### Fifty problems, not five hundred
For fresher rounds: arrays, strings, hash maps, two pointers, sorting, basic
recursion, and SQL queries on two tables. That covers most of what is asked.
Trees, graphs and dynamic programming matter for top product companies and can
wait until you are aiming at one. The [DSA track](/dsa) covers the patterns.

### Every one out loud, timed
Use the five steps, even alone. Speaking while you code is a separate skill from
coding, and it only improves by doing it.

### Record one a week and listen back
Count two things: the longest silence, and how many questions you asked before
writing code. Aim for under ten seconds, and at least two.

### On paper, sometimes
Many walk-ins still use paper. Without an IDE, you find out which method names
you actually know.
::
