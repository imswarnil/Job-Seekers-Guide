The pieces, made concrete. This lesson sets up the exact stack the University
Management App runs on, and the reason for each choice is a property rather than
a brand.

## Why this matters in a job

Because "I deployed it" and "I set up a pipeline where every pull request gets
its own URL and its own copy of the database" are different sentences, and the
second one is a thing very few candidates can say.

## The stack, and why each piece

::feature-list{columns="2"}
  :::feature{icon="i-lucide-database" title="Neon: Postgres"}
  Managed Postgres that **scales to zero**, so a portfolio project costs
  nothing while nobody is looking at it. `pgvector` is available, so the
  retrieval work from the AI track needs no second datastore.
  :::
  :::feature{icon="i-lucide-git-branch" title="Neon branching"}
  The reason to choose it. A database **branch** is a copy-on-write copy of
  production data, made in about a second. Every pull request gets one.
  :::
  :::feature{icon="i-lucide-cloud" title="Vercel: the front end"}
  Git push deploys. A preview URL per branch, certificates and CDN handled, and
  the Next.js path is the one it is built for.
  :::
  :::feature{icon="i-lucide-server" title="Railway: the Java API"}
  A long-running Spring process with a real port and a health check, which is
  what a serverless platform is awkward about.
  :::
::

## Neon, and the branch that makes it worth it

```bash [Terminal]
npm i -g neonctl && neonctl auth

neonctl projects create --name university
neonctl connection-string main
# postgresql://user:pass@ep-xyz.ap-southeast-1.aws.neon.tech/university?sslmode=require
```

```bash [Terminal]
# A copy of production, with the data, in about a second.
neonctl branches create --name pr-142 --parent main
neonctl connection-string pr-142
```

::pull-quote
That branch is a full copy of the data, created in a second and costing almost
nothing, because it is copy-on-write. You can run a migration against it, break
it, inspect the result and throw it away.
::

::compare{caption="Testing a migration that adds a NOT NULL column."}
  :::compare-side{label="Without a branch" verdict="wrong"}
  Run it against a seeded development database with 40 rows. It passes. Run it
  against production's 40,000 rows, nine of which have a null in that column
  from an import three years ago, and it fails half way through at 2 a.m.
  :::
  :::compare-side{label="Against a branch of production" verdict="right"}
  The same nine rows are in the branch, so it fails **in the pull request**,
  where failing is free. You add the backfill, it passes, and the production run
  is the third time you have executed it rather than the first.
  :::
::

```sql [migrations/004_add_intake_year.sql]
-- Additive, in the order from the hosting lesson. Every step reversible.
ALTER TABLE Application ADD COLUMN intake_year INT;                    -- 1. add
UPDATE Application SET intake_year = CAST(intake AS INT)               -- 2. backfill
 WHERE intake_year IS NULL AND intake ~ '^\d{4}$';
-- 3. deploy code that writes both, then reads the new one
-- 4. only then: ALTER TABLE Application ALTER COLUMN intake_year SET NOT NULL;
```

## Vercel, and previews

```bash [Terminal]
npm i -g vercel && vercel login
vercel link
vercel env add DATABASE_URL production
vercel env add DATABASE_URL preview
```

Push a branch and you get a URL for it. That is the feature: a reviewer opens the
change rather than imagining it, and "looks fine to me" becomes a thing somebody
actually did.

```yaml [.github/workflows/preview.yml]
name: Preview
on: pull_request

jobs:
  database:
    runs-on: ubuntu-latest
    steps:
      # A database branch per pull request, named for it.
      - uses: neondatabase/create-branch-action@v5
        id: branch
        with:
          project_id: ${{ secrets.NEON_PROJECT_ID }}
          branch_name: pr-${{ github.event.number }}
          api_key: ${{ secrets.NEON_API_KEY }}

      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', cache: maven }

      # Migrations run against the branch, not against anything real.
      - run: mvn --batch-mode flyway:migrate
        env:
          FLYWAY_URL: ${{ steps.branch.outputs.db_url }}

      - run: mvn --batch-mode verify
        env:
          DATABASE_URL: ${{ steps.branch.outputs.db_url }}
```

```yaml [.github/workflows/cleanup.yml]
# Delete the branch when the pull request closes, or you will have ninety.
name: Cleanup
on:
  pull_request:
    types: [closed]
jobs:
  delete:
    runs-on: ubuntu-latest
    steps:
      - uses: neondatabase/delete-branch-action@v3
        with:
          project_id: ${{ secrets.NEON_PROJECT_ID }}
          branch: pr-${{ github.event.number }}
          api_key: ${{ secrets.NEON_API_KEY }}
```

::warning{icon="i-lucide-alert-triangle"}
A branch per pull request is only free if they are deleted. The cleanup workflow
is not optional tidiness; without it you accumulate branches, each holding a
reference to the data they diverged from, and the storage is eventually a bill.
::

## Secrets, across three places

```bash [Terminal]
# Locally: a file, never committed.
echo "DATABASE_URL=postgresql://..." >> .env.local

# Vercel: per environment, so preview and production differ.
vercel env add ANTHROPIC_API_KEY production

# GitHub Actions: repository secrets, referenced as ${{ secrets.X }}
gh secret set NEON_API_KEY
```

::caution{icon="i-lucide-octagon-alert"}
Three separate places, which is three chances to paste a production key into a
preview environment. The rule that prevents it: **a preview never gets a
production credential.** A preview points at a database branch and, where you
can, a separate API key with its own spending limit. Then a mistake in a preview
costs a branch rather than your data and your budget.
::

## The acceptance criteria

::feature-list{columns="2"}
  :::feature{icon="i-lucide-link" title="A pull request gets a URL"}
  And the URL points at its own database branch, not at production.
  :::
  :::feature{icon="i-lucide-shield" title="A preview cannot touch production"}
  Prove it: run a `DELETE` in a preview and confirm production is unchanged.
  :::
  :::feature{icon="i-lucide-arrow-up" title="A migration fails in the PR"}
  Write a deliberately bad one, watch CI go red, and confirm nothing real moved.
  :::
  :::feature{icon="i-lucide-trash-2" title="Branches are cleaned up"}
  Close a pull request and check the branch is gone.
  :::
  :::feature{icon="i-lucide-undo" title="You have rolled back once"}
  On Vercel it is one click; time it so you know.
  :::
  :::feature{icon="i-lucide-database-backup" title="You have restored once"}
  Neon's point-in-time restore, into a branch, and confirm the row count.
  :::
::

## Your turn

Set it up, then do the rehearsal: open a pull request with a migration that will
fail, and confirm four things happen in order, CI goes red, the preview URL
still builds, production is untouched, and closing the pull request removes the
branch.

::accordion
  :::accordion-item{label="What usually goes wrong the first time" icon="i-lucide-bug"}
  **The preview has the production connection string**, because it was added
  once and applied to every environment. This is the mistake worth being
  paranoid about, and it is why the environment is selected explicitly on every
  `vercel env add`.

  **Migrations run on merge rather than in the pull request**, which means the
  first time they meet real data is on the main branch. The whole value of a
  database branch is that this happens earlier.

  **Cleanup is forgotten** and there are forty branches by month two.

  **And the one that is not a mistake:** the first time you run a migration
  against a branch of production and it fails on nine rows you did not know
  existed, that is the system working. Those nine rows were always there and
  were always going to break it. Meeting them on a Tuesday in a pull request is
  the entire point.
  :::
::

## The interview question this answers

**"Walk me through your deployment pipeline."**

Most fresher answers stop at "it deploys when I push". The one that lands
describes what happens to the **data**: a branch of production per pull request,
migrations run against real-shaped data where failure is free, tests against that
branch rather than a 40-row fixture, a preview URL the reviewer opens, and the
branch deleted on close.

Then the reason, in one sentence: the code can be rolled back and the database
cannot, so the database is the thing that needs rehearsing.
