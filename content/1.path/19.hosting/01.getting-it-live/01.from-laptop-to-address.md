It exists only on your laptop. Everything in this course has been building toward
a URL somebody else can open, and that URL is what turns a project into evidence.

## Why this matters in a job

Because a live link on a CV is worth more than the code behind it — it is
checkable, and half the projects on any CV were never finished. And because
deployment is where the networks and operating systems tracks stop being theory.

::real-life{title="What the link is actually doing on your CV" source="Any reviewer, thirty seconds in"}
They open it. If it loads, you have proved you can finish something, configure a
domain, handle a certificate and keep a service running. Nobody says that out
loud and everybody registers it. If it 404s or shows a certificate warning, that
is registered too.
::

## The pieces

::flow{numbered direction="vertical" caption="Six things between your laptop and a stranger's browser. Every one is a track you have already done."}
  :::flow-step{label="A domain" icon="i-lucide-globe"}
  About ₹800 a year. `university-demo.in` beats
  `app-final-v2.somehost.app` on a CV by a distance.
  :::
  :::flow-step{label="DNS pointing at your server" icon="i-lucide-signpost"}
  An `A` record to an IP, or a `CNAME` to a host. From the networks track:
  lower the TTL **before** you move anything.
  :::
  :::flow-step{label="Somewhere to run" icon="i-lucide-server"}
  A platform, a container host, or a plain virtual machine. See below.
  :::
  :::flow-step{label="A certificate" icon="i-lucide-lock" highlight}
  Let's Encrypt, free, issued automatically, renewed automatically. The
  automatic renewal is the part that matters: a certificate expires at midnight
  and everything stops at once.
  :::
  :::flow-step{label="A database that is not on the same box" icon="i-lucide-database"}
  Managed, with backups you have actually restored once. A database on the
  application server dies with it.
  :::
  :::flow-step{label="A way to know it is broken" icon="i-lucide-activity"}
  Before a user tells you. This is the step everybody skips.
  :::
::

## Where to run it

::pros-cons
---
title: A platform — Vercel, Netlify, Railway, Render
pros:
  - Push to a branch and it deploys. Certificates and scaling are handled.
  - Preview deployments per pull request, which is genuinely useful
  - Free tiers that are enough for a portfolio project
cons:
  - You learn less about what is underneath
  - Costs rise sharply past the free tier
  - Constrained: long-running processes and background workers can be awkward
---
::

::pros-cons
---
title: A virtual machine — a ₹400 a month droplet
pros:
  - You configure nginx, systemd, certbot and a firewall, which is real knowledge
  - Complete control, predictable cost, and it runs anything
  - Genuinely good for an interview: "I set up the server" is a sentence with substance
cons:
  - Security updates are now yours, forever
  - You will break it at 2 a.m. and nobody is coming
  - More time on infrastructure than on the thing you were building
---
::

::note
For a portfolio project, a platform is the right call: it is free, it is reliable
and the point is the application. Then, once, set up a virtual machine by hand
for the experience. Being able to say "the platform handles this, and here is
what it is doing on my behalf" is a better answer than either alone.
::

## Secrets

```bash [.env.local]
# NEVER committed. Add .env* to .gitignore before you write the first one.
DATABASE_URL=postgresql://user:password@host:5432/university
JWT_SECRET=a-long-random-string
SMTP_PASSWORD=...
```

```bash [Terminal]
# On the platform, set as environment variables rather than in a file.
railway variables set DATABASE_URL=...
```

::caution{icon="i-lucide-octagon-alert"}
**A secret committed to git is compromised**, even if you delete it in the next
commit, because git keeps everything. If it is a public repository, assume it was
scraped within minutes — there are bots watching GitHub's event stream for
exactly this. The recovery is to **rotate the secret**, not to delete the commit,
and doing it in that order is the difference between an embarrassment and an
incident.
::

::tip
Commit a `.env.example` with the **names** and no values. It documents what the
application needs, it is what a new joiner copies, and it is the difference
between a fifteen-minute setup and an afternoon of asking.
::

## A deploy you can undo

::compare{caption="Two ways to ship a change."}
  :::compare-side{label="Replace it" verdict="wrong"}
  Stop the old version, copy the new one, start it. The site is down for the
  gap, and if the new version is broken the way back is another deploy under
  pressure at the worst moment.
  :::
  :::compare-side{label="Start the new one beside it" verdict="right"}
  Start the new version, check it responds, switch traffic, keep the old one for
  ten minutes. No downtime, and a rollback is switching back rather than
  deploying again. Every platform does this by default and it is worth knowing
  what it is called: a blue-green or rolling deploy.
  :::
::

**The database is the part that cannot be rolled back**, which is why migrations
need their own discipline:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-plus" title="Additive first"}
  Add the new column, deploy code that writes both, backfill, then deploy code
  that reads the new one. Only then remove the old. Four deploys, and every one
  is reversible.
  :::
  :::feature{icon="i-lucide-x" title="Never drop in the same deploy"}
  Drop a column the running version still reads and you have broken production
  in a way rolling the code back does not fix.
  :::
::

## Knowing it is broken

::flow{numbered direction="vertical" caption="Four things, in order of value. Most projects have none."}
  :::flow-step{label="A health endpoint" icon="i-lucide-heart-pulse"}
  `/health` returning 200 only if the database answers. Then a free uptime
  monitor checking it every five minutes and emailing you. Ten minutes of work.
  :::
  :::flow-step{label="Logs you can search" icon="i-lucide-scroll-text" highlight}
  Structured, with a request id, so you can follow one request through. Logs you
  cannot search are logs you do not have.
  :::
  :::flow-step{label="Error reporting" icon="i-lucide-bug"}
  Sentry or similar, free at this scale, which emails you the stack trace with
  the user's context. Finding out from a user is finding out late.
  :::
  :::flow-step{label="One dashboard" icon="i-lucide-activity"}
  Requests per minute, error rate, response time, database connections. Four
  numbers. When something is wrong, these say which layer.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
A health check that returns 200 unconditionally is worse than none, because it
reports healthy while the database is unreachable. It must actually check the
dependency it claims to. This is a real and common mistake, and it is why an
orchestrator sometimes happily keeps a completely broken service in rotation.
::

## The acceptance criteria

::feature-list{columns="2"}
  :::feature{icon="i-lucide-globe" title="A real domain, over HTTPS"}
  With automatic renewal, and a redirect from plain HTTP.
  :::
  :::feature{icon="i-lucide-git-branch" title="Push to main, and it deploys"}
  With the tests running first, and a failing build not deploying.
  :::
  :::feature{icon="i-lucide-undo" title="You have rolled back once"}
  Deliberately, on purpose, as a rehearsal. A rollback you have never performed
  is a rollback you do not have.
  :::
  :::feature{icon="i-lucide-database" title="Backups, and one restore"}
  Also as a rehearsal. An untested backup is a hope.
  :::
  :::feature{icon="i-lucide-bell" title="You find out before a user does"}
  Health check, monitor, alert. Test it by stopping the database.
  :::
  :::feature{icon="i-lucide-file-text" title="A README a stranger can follow"}
  Clone, install, configure, run. If somebody cannot get it running from the
  README, the project is not finished.
  :::
::

## Your turn

Ship it. Then do the three rehearsals, which is where the learning is.

1. **Break it on purpose.** Stop the database. Does the health check go red? Do
   you get an email? Does the site show a useful error or a stack trace?
2. **Roll back on purpose.** Deploy something broken, then roll back. Time it.
3. **Restore a backup on purpose**, into a scratch database, and confirm the row
   count.

::accordion
  :::accordion-item{label="What these three usually reveal" icon="i-lucide-search"}
  **The health check is lying.** It returns 200 because it only checks that the
  web process is up. The fix is one query inside it.

  **The error page is a stack trace**, showing file paths, library versions and
  sometimes a connection string. That is information disclosure, and the fix is
  a generic error page in production with the detail going to your logs instead.

  **The rollback took eleven minutes** because you had to find the previous
  commit, rebuild and redeploy. Knowing it takes eleven minutes is itself useful;
  a platform's one-click rollback takes thirty seconds and is worth setting up
  before you need it.

  **And the backup restore is the one people discover too late.** A backup job
  that has been silently failing for three months looks exactly like one that
  works until the day you need it.
  :::
::

## Check yourself

1. Why must you not drop a column in the same deploy as the code that stops
   using it?
2. **An interviewer asks: "you push a change and the site breaks. What do you
   do?"**

## The interview question this answers

**"Walk me through how you would deploy an application."**

The pieces: domain, DNS, a host, an automatically renewing certificate, a managed
database, secrets as environment variables and never in git. Then the parts
almost no fresher mentions, which is where the marks are: a deploy that can be
rolled back, additive migrations across several deploys so the database is never
the thing you cannot undo, and a health check that actually checks its
dependency.

And for the follow-up — the site breaks — the answer is: roll back first, then
diagnose. Restoring service and finding the cause are two different jobs and
doing them in that order is what separates somebody who has been on call.
