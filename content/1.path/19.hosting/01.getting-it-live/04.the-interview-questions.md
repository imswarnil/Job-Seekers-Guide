title: Interview questions
description: Five deployment questions, including the one whose answer is a sequence rather than a fact.
minutes: 7
kind: quiz
---

::accordion
  :::accordion-item{label="1. Walk me through deploying an application" icon="i-lucide-message-circle"}
  The pieces: a domain, DNS, somewhere to run, an automatically renewing
  certificate, a managed database, and secrets as environment variables rather
  than in git.

  Then the parts almost no fresher mentions, which is where the marks are: a
  deploy that can be rolled back, additive migrations across several deploys so
  the database is never the thing you cannot undo, and a health check that
  actually checks its dependency.
  :::

  :::accordion-item{label="2. You push a change and the site breaks. What do you do?" icon="i-lucide-message-circle"}
  **Roll back first, then diagnose.** Restoring service and finding the cause
  are two different jobs and doing them in that order is what separates somebody
  who has been on call.

  Then: read the error, check what changed, reproduce it somewhere that is not
  production. And if the change included a migration, say so, because that is
  the part the rollback did not undo.
  :::

  :::accordion-item{label="3. How do you test a migration before it runs on production?" icon="i-lucide-message-circle"}
  Against a branch of production data, per pull request, so it meets the nine
  rows with a null in that column from an import three years ago on a Tuesday in
  a review rather than at midnight.

  Then the sequence that makes a migration reversible: add the column, deploy
  code that writes both, backfill, deploy code that reads the new one, and only
  then remove the old. Four deploys, every one of them undoable.
  :::

  :::accordion-item{label="4. How do you know something is broken?" icon="i-lucide-message-circle"}
  Before a user tells you. A health endpoint that returns 200 only if the
  database answers, an uptime monitor hitting it from outside your
  infrastructure, error reporting with the stack trace and the user's context,
  and four numbers on one dashboard: requests, errors, latency, connections.

  Then the trap: a health check that returns 200 unconditionally is worse than
  none, because it reports healthy while the database is unreachable and an
  orchestrator happily keeps a broken service in rotation.
  :::

  :::accordion-item{label="5. Where do secrets live?" icon="i-lucide-message-circle"}
  Environment variables, set per environment, with a committed `.env.example`
  holding the names and no values.

  Then the recovery, which is the part being tested: a secret committed to git
  is compromised even if the next commit deletes it, because git keeps
  everything and bots watch the public event stream. You **rotate the secret**;
  you do not rewrite history and hope. And a preview environment never gets a
  production credential, so a mistake there costs a branch rather than your
  data.
  :::
::
