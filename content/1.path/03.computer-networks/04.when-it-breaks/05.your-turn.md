Eight answers you could give. This is the part nobody does, and it is the
difference between saying "I would check DNS first" as a thing you read and as a
thing you have done.

Open a terminal. Every one of these is real and takes under a minute.

## 1. Watch DNS resolve

```bash
dig github.com +noall +answer
dig github.com +trace | tail -20
```

::accordion
  :::accordion-item{label="What to look for" icon="i-lucide-check"}
  The first shows the answer and the **TTL** in seconds, which is how long a
  resolver may cache it. Run it twice and watch the TTL count down, which is
  proof the answer is cached rather than fetched.

  The second walks the hierarchy from the root servers down. That output is what
  "DNS is a distributed hierarchy" actually looks like, and seeing it once makes
  the concept permanent.

  Try `dig imswarnil.com` and a domain behind a CDN like `dig www.bbc.co.uk`.
  The second returns a `CNAME` chain, often several deep. That chain is why a
  `CNAME` at the root of a domain is a problem worth knowing about.
  :::
::

## 2. Split a request into its phases

```bash
curl -w "dns: %{time_namelookup}s  connect: %{time_connect}s  tls: %{time_appconnect}s  first byte: %{time_starttransfer}s  total: %{time_total}s\n" \
     -o /dev/null -s https://github.com
```

::accordion
  :::accordion-item{label="What to look for" icon="i-lucide-check"}
  Five numbers, and the gaps between them are the phases. Run it twice: the
  second is faster because DNS is cached.

  This is the command behind interview answer 5. Time-to-first-byte minus TLS
  time is the server thinking. If that is the big number, the network is
  innocent and you should be looking at the database.

  Try it against a server far away and one close. The difference is latency and
  no amount of bandwidth affects it.
  :::
::

## 3. Prove HTTP is text

```bash
curl -v https://example.com 2>&1 | head -30
```

::accordion
  :::accordion-item{label="What to look for" icon="i-lucide-check"}
  Lines starting `>` are what your machine sent, `<` is what came back, and `*`
  is curl narrating the connection and TLS handshake.

  The request is four lines of text. That is the whole protocol, and seeing it
  once removes most of the mystery from the word "API".
  :::
::

## 4. Read a certificate

```bash
openssl s_client -connect github.com:443 -servername github.com < /dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

::accordion
  :::accordion-item{label="What to look for" icon="i-lucide-check"}
  The subject is the domain it vouches for. The issuer is the authority that
  signed it. The dates are its validity window.

  Now the exercise that teaches the lesson: find any site with a valid
  certificate whose name is nothing like the organisation it claims to be. They
  are trivially easy to find, and that is interview answer 3 demonstrated rather
  than asserted.
  :::
::

## 5. Find what is holding a port

```bash
lsof -i :3000          # macOS and Linux
kill <pid>
```

::accordion
  :::accordion-item{label="Why this one matters most" icon="i-lucide-check"}
  "Port already in use" is the single most common first-week problem in the
  industry, and almost always it is a previous run of your own thing that never
  exited when you closed the terminal window.

  Being the person who runs `lsof` rather than restarting the machine is a small
  thing that gets noticed immediately.
  :::
::

## 6. Watch a retry storm in miniature

```bash
for i in $(seq 1 20); do
  curl -s -o /dev/null -w "%{http_code} " https://httpstat.us/503
done; echo
```

::accordion
  :::accordion-item{label="What to look for, and what to add" icon="i-lucide-check"}
  Twenty immediate retries against a failing endpoint, as fast as your machine
  can manage. That is a retry storm at a scale of one client.

  Now add backoff and jitter:

  ```bash
  wait=1
  for i in $(seq 1 5); do
    code=$(curl -s -o /dev/null -w "%{http_code}" https://httpstat.us/503)
    echo "attempt $i: $code, waiting ${wait}s"
    sleep $(echo "$wait + $RANDOM % 2" | bc)
    wait=$((wait * 2))
  done
  ```

  Five attempts over about thirty seconds instead of twenty over two. Multiply
  by a thousand clients and that is the difference between a service recovering
  and a service being held down by its own users.
  :::
::

## 7. Trace the path

```bash
traceroute github.com      # or `tracepath` on some Linux systems
```

::accordion
  :::accordion-item{label="What to look for" icon="i-lucide-check"}
  Every hop between you and the server, with a round-trip time each. Usually
  between 10 and 20, and the first two or three are your own router and your
  provider.

  Watch where the times jump. That jump is usually the undersea cable or the
  intercontinental hop, and it is the physical reason latency exists.

  Rows of `* * *` are hops that do not reply to this kind of probe. That is
  normal and not a fault, which is worth knowing before you use it to diagnose
  something.
  :::
::

## The cheat-sheet

Everything this track used, one line each.

| Command | What it does |
| --- | --- |
| `dig <name>` | Resolve a name, and show the TTL |
| `dig <name> +trace` | Walk the DNS hierarchy from the root |
| `dig <name> CNAME` | Ask for a specific record type |
| `curl -v <url>` | Make a request and narrate every phase |
| `curl -i <url>` | Show response headers with the body |
| `curl -w "%{time_total}"` | Time the phases of a request |
| `openssl s_client -connect host:443` | Inspect a TLS certificate |
| `lsof -i :<port>` | What is holding a port |
| `netstat -an \| grep LISTEN` | Everything listening on this machine |
| `traceroute <host>` | Every hop along the path |
| `ping <host>` | Is it reachable, and how far away |
| `nc -zv <host> <port>` | Is that specific port open |

::tip
`ping` answers reachability and `nc -zv` answers whether a **service** is
listening. A machine that pings but refuses a port is running; the program is
not. Knowing which question you are asking is most of network debugging.
::
