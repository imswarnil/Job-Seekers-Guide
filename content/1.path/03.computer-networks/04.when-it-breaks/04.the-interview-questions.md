Forty terms you can define. Nobody asks for a definition, so here they are in
the shape they actually arrive in.

::accordion
  :::accordion-item{label="1. What happens when you type a URL and press Enter?" icon="i-lucide-message-circle"}
  The most-asked question in technical interviews, and it is not a networking
  question. It is a question about whether you can structure a long answer.

  The structure: DNS resolves the name to an address. TCP connects with a
  three-way handshake. TLS negotiates encryption and checks the certificate. The
  browser sends an HTTP request. The server responds. The browser parses,
  fetches sub-resources, and renders.

  Then **offer depth rather than taking it**: "I can go deeper on any of those.
  The DNS caching layers are interesting, and so is why the handshake costs a
  round trip." That sentence hands them the steering wheel and is the single
  best move available here.

  What fails: starting with "the browser makes a request", which skips the two
  most interesting steps.
  :::

  :::accordion-item{label="2. TCP or UDP, and when would you use each?" icon="i-lucide-message-circle"}
  Reliable, ordered, connection-based against send-and-hope.

  Then the part that shows judgement: the right choice depends on whether a late
  message is worse than a missing one. In video or voice it is, so UDP. For an
  API response it is not, so TCP.

  Then the depth: head-of-line blocking is the cost of TCP's ordering, one lost
  segment stalls everything behind it, and that is exactly why HTTP/3 went back
  to UDP and rebuilt reliability per stream on top.
  :::

  :::accordion-item{label="3. What does the padlock actually prove?" icon="i-lucide-message-circle"}
  Two things and no more: the connection is encrypted, and the server controls
  that domain name.

  What it does **not** prove: that the site is honest, safe, or who you assume.
  A phishing site can hold a perfectly valid certificate for
  `secure-yourbank-login.com`, and most do, because certificates are free now.

  This one is worth answering crisply, because the wrong answer, "it means the
  site is secure", is a security misunderstanding rather than a gap.
  :::

  :::accordion-item{label="4. Explain DNS." icon="i-lucide-message-circle"}
  Names to addresses, resolved before any HTTP happens. Then the layers of
  caching, because that is where the real behaviour lives: the browser, the
  operating system, the resolver, then the authoritative server.

  The detail that marks experience: **TTL**, and lowering it before a migration.
  "I would drop the TTL to sixty seconds a day before moving, then raise it
  afterwards" is a sentence from somebody who has actually moved a domain.

  And: a `CNAME` cannot exist at the root of a domain. That single fact solves a
  surprising number of real problems.
  :::

  :::accordion-item{label="5. The API is slow. How do you find out why?" icon="i-lucide-message-circle"}
  A sequence, and the point is that it is layered.

  Is it slow for everybody or one client? Is it DNS, connection, first byte, or
  transfer? `curl -w` splits those apart. If time-to-first-byte is the problem,
  it is the server or the database and the network is innocent. If the handshake
  is the problem, look at connection reuse and how far away the server is.

  Say what you would not do: add a cache before knowing which phase is slow.
  :::

  :::accordion-item{label="6. What is idempotency and why does it matter?" icon="i-lucide-message-circle"}
  Repeating the request has the same effect as making it once.

  Then connect it to something real, because the definition alone is worth
  little: a payment request that times out leaves you unable to tell whether it
  succeeded. If it is idempotent, with a key the server recognises, you retry
  safely. If not, you either risk charging twice or risk not charging at all.

  That is the reason `POST` needs an idempotency key and `PUT` does not.
  :::

  :::accordion-item{label="7. A service is struggling. Everybody retries. What happens?" icon="i-lucide-message-circle"}
  A retry storm, and the service is finished off by the retries rather than the
  original load.

  The fix has three parts and naming all three is the answer: exponential
  backoff, **jitter**, and a ceiling. Jitter is the one people leave out, and
  without it a thousand clients that failed together retry together, so you have
  synchronised the stampede rather than prevented it.

  Then the circuit breaker: after enough failures, stop calling for a while, so
  you fail fast and the service gets room to recover.
  :::

  :::accordion-item{label="8. What is the difference between latency and bandwidth?" icon="i-lucide-message-circle"}
  How long one message takes, against how much flows per second.

  The example that lands: a server in Frankfurt is about 120 milliseconds from
  Bangalore and no amount of bandwidth changes that, because it is distance and
  the speed of light. Which is why the fix for a slow page is usually fewer
  round trips rather than a bigger pipe.

  Then the connection to something you built: keep-alive exists precisely
  because the handshake costs a round trip, and paying it once instead of per
  file is a latency fix, not a bandwidth one.
  :::
::

## What every answer above has in common

::feature-list{columns="2"}
  :::feature{icon="i-lucide-layers" title="It names the layer"}
  "That is a TCP problem, not an HTTP one" is a sentence that immediately places
  you. Most people describe symptoms; naming the layer describes a diagnosis.
  :::
  :::feature{icon="i-lucide-scale" title="It names what the guarantee costs"}
  Reliability costs head-of-line blocking. Encryption costs a handshake.
  Retrying costs a storm. Every guarantee in networking is bought with
  something, and knowing the price is the whole subject.
  :::
::
