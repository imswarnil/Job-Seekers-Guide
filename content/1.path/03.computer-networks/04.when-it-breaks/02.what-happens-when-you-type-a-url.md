The question. It is asked constantly because it is unbounded: you can answer it
in thirty seconds or in forty minutes, and how far you go shows exactly how deep
you are. There is no bluffing in it.

You now know every step. This lesson is about assembling them.

## The thirty-second version

For when it is an opening question and they want to move on.

> The browser resolves the domain name to an IP address through DNS, opens a TCP
> connection to that address on port 443, and negotiates TLS so the connection is
> encrypted and the server's identity is verified. Then it sends an HTTP GET
> request. The server runs its application code, probably queries a database, and
> returns HTML. The browser parses that, requests the stylesheets, scripts and
> images it refers to, and renders the page.

Six sentences, correct, complete in outline. If they want more they will ask, and
now the conversation is on ground you chose.

## The four-minute version

::flow{numbered direction="vertical" caption="Ten steps. Each one is a lesson you have already read."}
  :::flow-step{label="The browser parses the URL" icon="i-lucide-link"}
  Scheme, host, port, path, query. `https://university.edu/applicants?minScore=60`
  means port 443 implicitly. If what you typed is not a URL, it goes to a search
  engine instead.
  :::
  :::flow-step{label="DNS resolution" icon="i-lucide-search"}
  Browser cache, then the operating system, then `/etc/hosts`, then the resolver,
  then root → `.edu` → the authoritative server. Answers are cached with a TTL,
  which is why a change is not instant.
  :::
  :::flow-step{label="TCP handshake" icon="i-lucide-handshake"}
  SYN, SYN-ACK, ACK. One full round trip before any data, about 140 ms if the
  server is in another continent.
  :::
  :::flow-step{label="TLS handshake" icon="i-lucide-lock"}
  The server presents a certificate; the client checks the name, the expiry and
  the chain to a trusted root, and both derive a shared key. One more round trip
  in TLS 1.3.
  :::
  :::flow-step{label="The HTTP request" icon="i-lucide-send"}
  Request line, `Host` header, cookies, `Accept`. Text, and you have sent one by
  hand with `nc`.
  :::
  :::flow-step{label="It arrives at a proxy first" icon="i-lucide-shuffle"}
  Almost never straight at your application. A load balancer or reverse proxy
  terminates TLS and picks one of several application servers. This is why you
  see 502 and 504 rather than your own 500.
  :::
  :::flow-step{label="The application runs" icon="i-lucide-server" highlight}
  Routing, authentication, authorisation, then the work: usually a database
  query. Everything in the next three tracks of this course lives in this single
  step.
  :::
  :::flow-step{label="The response comes back" icon="i-lucide-download"}
  Status line, headers, body. `Cache-Control` here decides whether the browser
  even asks next time.
  :::
  :::flow-step{label="The browser parses and fetches more" icon="i-lucide-file-code"}
  HTML into a DOM tree, CSS into style rules, and a fresh request for every
  stylesheet, script, font and image. One URL, dozens of round trips.
  :::
  :::flow-step{label="Render" icon="i-lucide-monitor"}
  Layout, paint, and then JavaScript runs and often fetches data again. The first
  thing the user sees can be several seconds after step one, and almost all of
  that is round trips rather than bytes.
  :::
::

## The version that gets you the job

Depth is not the differentiator once you are past four minutes. What separates
candidates is **naming what can go wrong at each step**, because that is what the
question is really screening for: have you ever debugged this?

| Step | What breaks | What you see |
| --- | --- | --- |
| DNS | Record missing, stale cache, resolver down | `UnknownHostException`, or the old server keeps answering |
| TCP | Nothing listening | `Connection refused`, good news, the machine was reached |
| TCP | Firewall dropping silently | `Connection timed out`, packets leave, nothing returns |
| TLS | Expired, wrong name, missing intermediate | Handshake failure; and the intermediate case works in a browser and fails from Java |
| Proxy → app | The app is down | `502 Bad Gateway` |
| Proxy → app | The app is slow | `504 Gateway Timeout` |
| Application | Unhandled exception | `500`, and a stack trace in a log somewhere |
| Application | Authentication vs authorisation | `401` versus `403`, and they are not the same |
| Response | Wrong `Cache-Control` | A change deployed and users still see the old page |

::real-life{title="What an interviewer is actually listening for" source="Interviews I have sat on"}
Not the number of steps. The moment somebody says "and if that step fails you see
this specific error" is the moment their answer stops sounding like a blog post
they read. One well-chosen failure is worth four extra steps of detail.
::

## Your turn

Say it out loud, twice, recorded.

**Once in thirty seconds.** Six sentences, no hedging, no "um, I think".

**Once in four minutes.** Ten steps, and pick three of them to name a failure
for.

::accordion
  :::accordion-item{label="What to listen for when you play it back" icon="i-lucide-ear"}
  Three things, and they are all fixable in one more take.

  **Did you hedge?** "I think it does a DNS lookup?". You know this. Say it.

  **Did you go in order?** Jumping back to mention DNS caching after you reached
  rendering is what nerves do, and it reads as reconstruction rather than
  knowledge.

  **Did you stop?** The answer ends. A candidate who keeps adding detail into
  silence sounds unsure, and the interviewer has other questions. Finish, and let
  them choose where to dig.
  :::
::

## Check yourself

1. Give the thirty-second version from memory, without looking.
2. **Name one thing that can fail at each of the first five steps**, and what the
   client sees for each.

## The interview question this answers

This one. Along with, depending on where they dig: what is DNS, how does HTTPS
work, what is the difference between 502 and 504, why is our API slow from
another country, and what are the layers of the network stack.

That is five questions from one preparation. There is no better return available
in interview practice, which is why this is the last page of the track rather
than a footnote in it.
