One pass over the words. Eight weeks introduced about forty terms, and half of
them will come back at you across a table.

## Deciding

::field-group
  :::field{name="Requirement" type="document"}
  What the system must do, written as jobs from the actor's side with the reason
  attached. Not a feature list.
  :::
  :::field{name="Actor" type="person"}
  A kind of person who uses the system. Applicant, student, faculty, admin. Four
  here, and they never collapse into "users".
  :::
  :::field{name="Acceptance criteria" type="test"}
  A sentence somebody else could test without asking what you meant. "Done"
  means every criterion passes, not that the code exists.
  :::
  :::field{name="Scope boundary" type="document"}
  What is explicitly not in this version, written down. The thing that stops the
  project changing shape every Tuesday.
  :::
  :::field{name="Decision record" type="document"}
  Four lines: the decision, the alternative rejected, the reason, and the
  condition under which it stops being right. The fourth line is the one nobody
  writes and the one interviewers notice.
  :::
::

## The data

::field-group
  :::field{name="Normalisation" type="design"}
  Storing each fact once, so it cannot be updated in one place and become
  inconsistent with another.
  :::
  :::field{name="Denormalisation" type="design"}
  Deliberately storing a fact twice for read performance, having measured that
  you needed to. `ApplicationEvent` duplicating the current status is the
  example here.
  :::
  :::field{name="Frozen value" type="design"}
  Not denormalisation, despite looking identical. `FeePayment.amount_paise` is a
  different fact from `FeeStructure.amount_paise`: what was actually paid, which
  must not change when next year's fee does.
  :::
  :::field{name="Surrogate key" type="key"}
  A generated id with no meaning, like `student_id`. Preferred because a roll
  number can be reissued or corrected and a foreign key cannot follow it.
  :::
  :::field{name="Natural key" type="key"}
  A real-world identifier used as the primary key. Still `UNIQUE`, still
  indexed, not what other tables point at.
  :::
  :::field{name="Composite unique" type="constraint"}
  A uniqueness rule across several columns. `UNIQUE (student_id, subject_id,
  held_on)` is what makes a double-submitted register impossible.
  :::
  :::field{name="Idempotent" type="property"}
  An operation you can repeat safely with the same result. The attendance upsert
  is idempotent; a plain insert is not. This is what makes an operation survive
  a flaky network.
  :::
::

## Access

::field-group
  :::field{name="Authentication" type="security"}
  Proving who you are. Signing in.
  :::
  :::field{name="Authorisation" type="security"}
  What you may do once you have proved it. A different system, with a different
  failure mode.
  :::
  :::field{name="Row-level security" type="security"}
  A rule on the table itself deciding which rows a given user's query may see.
  The query does not fail; it returns fewer rows.
  :::
  :::field{name="Fails closed" type="security"}
  A design where forgetting the check returns nothing. The opposite, failing
  open, returns everything. Design so the mistake you will eventually make is
  the safe one.
  :::
  :::field{name="Access matrix" type="document"}
  Every table against every operation against every role. Boring, twenty
  minutes, and the only way to find the cell you had not thought about.
  :::
  :::field{name="Deactivation" type="design"}
  Marking somebody inactive rather than deleting them, so the audit trail
  survives and the access does not. Distinct from deletion, and needed far more
  often.
  :::
::

## Building

::field-group
  :::field{name="Server-rendered" type="architecture"}
  The page arrives containing its content. Faster on a slow connection, readable
  before JavaScript runs, and the authorisation happened where a user cannot
  reach it.
  :::
  :::field{name="Client-side validation" type="practice"}
  A kindness. It can be turned off, edited or skipped entirely.
  :::
  :::field{name="Server-side validation" type="practice"}
  The truth, because it is the only check running on a machine you control.
  :::
  :::field{name="Prepared statement" type="security"}
  Query text and values sent on separate paths, so a value can never be parsed
  as part of the statement. Not escaping, not validation. The whole answer to
  SQL injection.
  :::
  :::field{name="Transaction" type="database"}
  Several writes that all happen or none do. Two writes that must agree are one
  operation.
  :::
  :::field{name="Lost update" type="bug"}
  Two transactions read the same value, both decide, both write, and one
  overwrites the other. Allowed at every major database's default isolation
  level. The two-admins-one-seat bug.
  :::
  :::field{name="Optimistic locking" type="technique"}
  A version column. Nobody waits; the loser's update matches zero rows and
  retries. For rare clashes and long transactions.
  :::
  :::field{name="Pessimistic locking" type="technique"}
  `SELECT ... FOR UPDATE`. The second person waits. For frequent clashes, or
  when the decision needs several reads first.
  :::
  :::field{name="Upsert" type="database"}
  Insert, or update if it is already there. `ON CONFLICT ... DO UPDATE`. What
  makes the attendance register idempotent.
  :::
  :::field{name="Rate limiting" type="security"}
  Refusing too many requests from one source, with `429` and `Retry-After`.
  Limit by address and by identity, because address alone punishes a campus.
  :::
::

## Reading the result

::field-group
  :::field{name="Denominator" type="practice"}
  What a percentage is a percentage of. A number without it can start an
  argument between two correct reports.
  :::
  :::field{name="Empty state" type="interface"}
  What a screen shows with no data, and the first thing a reviewer sees. Build
  it as though it is the front page.
  :::
  :::field{name="Correlation" type="analysis"}
  Two things moving together. Not a cause, and a chart that does not say so will
  be read as one.
  :::
  :::field{name="Visual regression" type="testing"}
  A test that compares a rendered screen against a saved image. Worth it on the
  two screens where layout is the feature, and only after the design settles.
  :::
::

## The three people confuse

::compare{caption="Said interchangeably in interviews, and they are not the same."}
  :::compare-side{label="Denormalisation" verdict="neutral"}
  Storing the same fact twice, on purpose, for speed. You accept that a write
  must update both.
  :::
  :::compare-side{label="A frozen value" verdict="neutral"}
  Storing a **different** fact that happens to have the same value today. The
  receipt amount and the current fee are not the same fact, and next year they
  will not be the same number either.
  :::
::

The third is **caching**, which is neither: a copy you are willing to have be
stale, with a rule for when it is thrown away. If somebody asks you to
denormalise something and what they describe can go stale without anybody
minding, they mean a cache.
