Forty terms you can define. Nobody asks for a definition. They ask it sideways,
and these twelve are how the eight weeks you have just spent come back at you.

::accordion
  :::accordion-item{label="1. Tell me about something you built." icon="i-lucide-message-circle"}
  Problem with a person in it, one sentence of what it is, one decision argued
  with its rejected alternative, one thing you would change because somebody
  real complained. Two minutes, then stop.

  The failure is starting with the stack. Every candidate's project is a list of
  technologies; almost nobody's starts with an admissions office running an
  intake on a shared spreadsheet.
  :::

  :::accordion-item{label="2. Why a monolith and not microservices?" icon="i-lucide-message-circle"}
  Because services solve an **organisational** problem before a technical one:
  they let several teams deploy without coordinating. One developer and a few
  thousand users has no such problem.

  Then name the expiry: it stops being right the moment more than one team needs
  to deploy independently, and I would split on that boundary rather than a
  technical one.
  :::

  :::accordion-item{label="3. How do you stop one user reading another's data?" icon="i-lucide-message-circle"}
  The check goes as close to the data as it can: a row-level policy on the
  table, so the database returns only permitted rows whatever the query asked
  for.

  Then the part that wins it: name the failure mode you bought. A forgotten
  check returns too little rather than too much, and too little gets reported as
  a bug while too much gets reported as a breach.
  :::

  :::accordion-item{label="4. Two users click the same button at once." icon="i-lucide-message-circle"}
  Name the bug: **lost update**, and that every major database allows it at its
  default isolation level. Then three fixes and when each fits: a conditional
  `UPDATE` with the row count checked for rare clashes, `SELECT ... FOR UPDATE`
  when the decision needs several reads, a version column for long transactions.

  Close with the honest cause: most of these in practice are one person
  double-clicking, so a `UNIQUE` index fixes more of them than any locking
  strategy.
  :::

  :::accordion-item{label="5. Walk me through your database design." icon="i-lucide-message-circle"}
  Do not list tables. Take one decision and go deep: an applicant becomes a
  student, and they are separate tables because a person can apply three times,
  be rejected twice and admitted once, and every one of those needs a row.

  Then name a constraint and what it prevents. `UNIQUE (student_id, subject_id,
  attempt)` exists because students re-sit failed subjects, and without
  `attempt` the second result overwrites the first.
  :::

  :::accordion-item{label="6. What is the difference between authentication and authorisation?" icon="i-lucide-message-circle"}
  Proving who you are, against what you may do once you have. Then prove you
  have built both rather than read both: the session sets a connection variable
  the row-level policies read, so authentication happens in the application and
  authorisation happens in the database.

  The follow-up is usually where the role is stored. In the database keyed by
  session, never in the token, because a role in a token is a claim the browser
  is making about itself.
  :::

  :::accordion-item{label="7. How do you prevent SQL injection?" icon="i-lucide-message-circle"}
  Prepared statements, and say the mechanism: the query and the values travel on
  separate paths, so a value can never be parsed as part of the statement. Not
  escaping, not a denylist, not input validation.

  Then the judgement: no exceptions, not for internal tools, not for values I
  believe are numeric. The exception is where the breach comes from.
  :::

  :::accordion-item{label="8. Why validate on the server if the form already did?" icon="i-lucide-message-circle"}
  Because they are doing different jobs. The browser validates for kindness and
  can be turned off, edited or skipped. The server validates for truth, because
  it is the only check running on a machine I control.

  The example that makes it concrete: the programme id came from a list I
  supplied, and the server still checks it exists, because every id arriving
  from outside is a claim rather than a fact.
  :::

  :::accordion-item{label="9. How do you decide what to test?" icon="i-lucide-message-circle"}
  Never answer with a percentage. The rules where being wrong costs money or a
  place at the university, tested at their boundaries and with the nulls the
  schema allows.

  Then what you deliberately do not test, which is the half that shows
  judgement: layout, exact response shapes, anything that changes weekly for
  good reasons, because a suite that fails on every legitimate change gets
  ignored, and an ignored suite is worse than none.
  :::

  :::accordion-item{label="10. How would you scale it?" icon="i-lucide-message-circle"}
  Refuse, then plan. At a few thousand users on one Postgres instance there is
  no scaling problem, and most of what I could add is complexity with nothing
  measured behind it.

  If it grew: measure first, and my guess is the reporting queries hurt before
  anything else, so read replicas for dashboards and materialised views for the
  funnel. But I would want the slow query log before touching anything.
  :::

  :::accordion-item{label="11. What went wrong?" icon="i-lucide-message-circle"}
  The question everybody under-answers. Pick something real, with a person in
  it.

  I built the attendance register the obvious way, a row per student with
  present and absent buttons, and a lecturer told me it was slower than paper
  and she had gone back to paper. The fix was defaulting everybody to present
  and recording only the exceptions. Four taps per student became four taps per
  class.

  It works because it contains a real user, a real complaint, and a change you
  can state in one sentence.
  :::

  :::accordion-item{label="12. What would you do differently?" icon="i-lucide-message-circle"}
  Not the same question as eleven, though people answer it the same way. Eleven
  is a bug. This is a decision.

  Mine: I designed the schema before writing the access matrix, and did it in
  the other order on the next project. Several columns existed for a year before
  anybody asked who was allowed to read them, and working out the permissions
  first would have changed two tables.
  :::
::

## What every answer above has in common

::feature-list{columns="2"}
  :::feature{icon="i-lucide-user" title="There is a person in it"}
  A registrar, a lecturer, a parent on the phone. An answer with no human in it
  sounds like documentation, and documentation is not evidence that you built
  anything.
  :::
  :::feature{icon="i-lucide-scale" title="It names what it traded away"}
  The rejected alternative, the cost accepted, the condition under which the
  decision expires. Asserting a choice is a claim. Arguing one is engineering.
  :::
::
