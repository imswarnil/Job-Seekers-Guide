Six bugs found by six people using it, and you cannot keep finding them that
way. This lesson tests the four rules where being wrong costs the university
money or a place at it.

## Why this matters in a job

Because "do you write tests" is asked everywhere and answered badly everywhere.
The weak answer is a percentage. The answer that lands names **what** you test
and what you deliberately do not.

I did not write a test until my second year of working, and the thing that
converted me was not a lecture. It was a fee calculation I had changed on a
Friday, correctly, which broke a case from eighteen months earlier that nobody
remembered existed.

## What is worth testing here

::pros-cons
---
title: Testing every line versus testing the rules
pros:
  - A rule has a right answer somebody can state, so a failing test is unambiguous
  - The four rules below are read by every screen, so one test protects many
  - They change rarely and break expensively, which is exactly the right profile
cons:
  - Coverage percentage stays low, and some interviewers ask about the number
  - A screen can still break without any test failing
  - Somebody has to decide what a rule is, and that judgement is not automatable
---
::

::pull-quote
Test the things that are expensive to get wrong and cheap to state. A test that
asserts a button is blue costs more to maintain than the bug it prevents.
::

## The four rules

::tabs
  :::tabs-item{label="Eligibility" icon="i-lucide-check-check"}
  ```java [EligibilityTest.java]
  @Test void scoreExactlyAtCutoffIsEligible() {
    assertTrue(rules.isEligible(score(78.5), program(cutoff(78.5))));
  }

  @Test void unmarkedApplicationIsNotEligible() {
    // Null is not zero and it is not a pass. It is "we do not know yet".
    assertFalse(rules.isEligible(score(null), program(cutoff(78.5))));
  }
  ```
  The boundary case and the null case. Those two catch nearly everything, and
  both are cases a person clicking around would never produce.
  :::
  :::tabs-item{label="Shortlisting" icon="i-lucide-list-ordered"}
  ```java [ShortlistTest.java]
  @Test void tiesAtTheCutoffAreResolvedDeterministically() {
    var ranked = rules.shortlist(applicants(
        applicant("A", 78.0, applied("2026-06-02")),
        applicant("B", 78.0, applied("2026-06-01"))), seats(1));

    // Earlier application wins. Stated, not incidental.
    assertEquals("B", ranked.get(0).name());
  }
  ```
  This is the university deciding who gets a place. "The sort picked one" is not
  an answer you can give a parent, so the tie-break is a rule with a test.
  :::
  :::tabs-item{label="Fees" icon="i-lucide-receipt"}
  ```java [FeeTest.java]
  @Test void twoInstalmentsSumToTheFeeAtTimeOfAdmission() {
    var student = admitted(program("btech-cse"), year(2026));  // ₹45,000
    pay(student, paise(2_250_000), on("2026-07-01"));
    pay(student, paise(2_250_000), on("2026-12-01"));

    assertEquals(paise(0), fees.outstanding(student));
  }

  @Test void nextYearsFeeRiseDoesNotChangeLastYearsReceipt() {
    var student = admitted(program("btech-cse"), year(2026));
    pay(student, paise(4_500_000), on("2026-07-01"));
    feeStructure.set(program("btech-cse"), year(2027), paise(5_000_000));

    assertEquals(paise(4_500_000), receipts.of(student).get(0).amountPaise());
  }
  ```
  The second test is the frozen-amount denormalisation from the data model
  lesson, written as an assertion. That is what a deliberate design decision
  looks like once it is defended.
  :::
  :::tabs-item{label="The seat race" icon="i-lucide-users"}
  ```java [SeatTest.java]
  @Test void twoAdminsCannotFillOneSeat() throws Exception {
    var program = programWith(seats(1));
    var start   = new CountDownLatch(1);

    var a = submitAccept(program, start);
    var b = submitAccept(program, start);
    start.countDown();                       // both go at once

    assertEquals(1, succeeded(a, b));        // exactly one, never two
    assertEquals(1, enrolled(program));
  }
  ```
  A concurrency test, run against a real database rather than a mock, because
  the behaviour being tested **is** the database's.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
Mock the things at the edge, never the database. A mocked repository that
returns what you told it to proves your test is consistent with itself. The seat
race exists because of how Postgres handles two transactions, and a mock cannot
have that behaviour to reproduce.
::

## The two cases a human never clicks

Every one of the tests above is one of these, and it is the reason tests find
things that clicking does not.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-move-horizontal" title="The boundary"}
  Exactly at the cutoff. Exactly at 75% attendance. Exactly zero seats left.
  Exactly the last day. A person testing by hand types 80 and 60, never 78.5.
  :::
  :::feature{icon="i-lucide-circle-slash" title="The absence"}
  Null score, no phone number, no payments yet, a programme with no subjects.
  Every null you allowed in the schema is a case, and you allowed each one on
  purpose.
  :::
::

## What you are choosing not to test

Say this part out loud in an interview, because it is the half that shows
judgement.

No test asserts that a card is 16 pixels from the edge, that the heading is
bold, or that the API returns exactly this JSON shape. Those change for good
reasons weekly, and a test that fails every time somebody improves the design
gets deleted or, worse, ignored.

::side-note{kind="go-deeper"}
The exception is a **visual regression** test on the two or three screens where
layout is the feature, and even then only once the design has settled. Before
that it is a machine telling you your own changes happened.
::

## Done when

1. The four rules above have tests, including the boundary and the null case.
2. The tests run against a real database, seeded and torn down per run.
3. They run on every push, and a failure blocks the merge.
4. A new person can run them with one command after cloning.

Criterion 4 is not a formality. A test suite that needs six undocumented
environment variables is a test suite nobody runs.

## What you can do now

You can decide what is worth testing in a real system, write the cases a person
would never click, test a concurrency bug against a real database, and explain
what you deliberately left untested.

## Check yourself

1. Why is testing `score == cutoff` more valuable than testing `score > cutoff`?
2. **An interviewer asks: "what is your test coverage?"**

## The interview question this answers

**"How do you decide what to test?"**

Do not give a percentage. Say what you protect: the rules where being wrong
costs money or a place at the university, tested at their boundaries and with
the nulls the schema allows.

Then name what you do not test and why: layout, exact JSON shape, anything that
changes weekly for good reasons, because a test that fails on every legitimate
change gets ignored, and an ignored suite is worse than none.

If they press on coverage: coverage tells you which lines ran, not which
behaviours are correct. A suite can execute every line and assert nothing.
