Enquiries are arriving into a table nobody can read, and the office needs to get
in. This is the lesson where the system learns who somebody is, which is the
thing every policy you wrote in chapter one has been waiting for.

## Why this matters in a job

Because authentication is the one feature where "I wrote my own" is a warning
rather than a boast, and knowing that is itself the signal.

And because the row-level policies are useless without it. `current_student_id()`
appeared in every one of them, and nothing yet makes that function return
anything.

## Done when

1. Each role signs in and lands on their own home screen: `/me`, `/staff`,
   `/admin`.
2. An unauthenticated request to a protected route is refused **by the server**,
   not redirected by the browser.
3. A student hitting `/admin` gets 403, and the response body contains no data.
4. The session survives a page reload and expires after inactivity.
5. Signing out invalidates the session server-side, not only clears a cookie.
6. `current_student_id()` returns the right id inside a database query.

## Do not write this yourself

::pull-quote
Password storage, session handling, reset flows and lockout are a solved problem
with a long list of subtle ways to get it wrong, and every one of them has been
exploited in public.
::

Use the platform's authentication. What you must be able to explain is what it
is doing, because "the library handles it" is not an answer in a technical
round.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-lock" title="Passwords are never stored"}
  A slow, salted hash is. Slow on purpose: bcrypt or argon2, not SHA-256, which
  is fast and therefore wrong for this job. The salt means two people with the
  same password have different hashes.
  :::
  :::feature{icon="i-lucide-cookie" title="The session is a reference"}
  A random identifier in an `HttpOnly`, `Secure`, `SameSite` cookie. `HttpOnly`
  means JavaScript cannot read it, which is what stops a cross-site scripting
  bug becoming an account takeover.
  :::
::

## The three roles, and where they live

The role is **not** in the cookie, and this is the part worth getting right.

::compare{caption="Where the role is read from."}
  :::compare-side{label="From the token the browser sent" verdict="wrong"}
  The request carries `role: admin` and the server believes it.

  Silently wrong in a way that looks fine in every test you write, because your
  tests send the role your code put there. Somebody else sends a different one.
  :::
  :::compare-side{label="From the database, keyed by the session" verdict="right"}
  The cookie contains an opaque session id and nothing else. The server looks up
  who that is and what role they hold.

  Now the role is a fact in your database rather than a claim in somebody's
  browser.
  :::
::

```sql [The role, and one row per person]
CREATE TABLE AppUser (
  user_id     BIGSERIAL PRIMARY KEY,
  email       CITEXT NOT NULL UNIQUE,
  role        TEXT   NOT NULL CHECK (role IN ('STUDENT','FACULTY','ADMIN')),
  student_id  BIGINT REFERENCES Student,
  faculty_id  BIGINT REFERENCES Faculty,
  active      BOOLEAN NOT NULL DEFAULT true,
  -- A student user must point at a student, a faculty user at a lecturer.
  CHECK ((role = 'STUDENT' AND student_id IS NOT NULL)
      OR (role = 'FACULTY' AND faculty_id IS NOT NULL)
      OR (role = 'ADMIN'))
);
```

That `CHECK` is the schema refusing to hold a nonsensical user. A student
account with no student attached cannot exist, so no code downstream has to
handle it.

## Connecting it to the policies

This is the join between chapter one and now.

::code-trace{language="sql" caption="What makes current_student_id() work."}
```sql
CREATE FUNCTION current_student_id() RETURNS BIGINT AS $$
  SELECT student_id FROM AppUser
   WHERE user_id = current_setting('app.user_id')::BIGINT
     AND active;
$$ LANGUAGE SQL STABLE;
```
  :::code-trace-step{lines="1" caption="A function the policies already call. Until now it returned nothing, so every policy denied everything, which is the correct way round to fail."}
  :::
  :::code-trace-step{lines="3" caption="`current_setting` reads a value the application sets on the connection at the start of each request, from the session. The browser never sends this; it is derived server-side from the session id."}
  :::
  :::code-trace-step{lines="4" caption="`AND active`. The lecturer who left in March still has rows, and no longer has access. This one line is the exercise from chapter one, in production."}
  :::
::

::side-note{kind="security"}
Set the connection variable from the session at the **start** of the request and
clear it at the end. If a pooled connection keeps the previous request's user
id, the next request runs as somebody else, and every policy you wrote
faithfully enforces the wrong person's permissions. This is a real and
frequently-shipped bug.
::

## Protected routes

Criterion 2 says refused by the server. There is a reason that phrasing matters.

```text [Two ways to protect /admin]
Client:  the page loads, JavaScript checks the role, redirects to /me
         → the data was already in the response. Open the network tab and read it.

Server:  the request is checked before anything is rendered
         → 403, an empty body, and nothing to read anywhere.
```

A redirect is a suggestion. A refusal is a decision.

## What you can do now

You can sign three kinds of person in, keep the role somewhere a person cannot
edit it, connect a session to the database policies you wrote weeks ago, and
refuse a request on the server rather than redirecting it in the browser.

## Check yourself

1. Why is a fast hash like SHA-256 the wrong choice for a password, when it is
   the right choice for a file checksum?
2. **An interviewer asks: "where do you store the user's role, and why?"**

## The interview question this answers

**"How does authentication work in your project?"**

Say the flow: the password is checked against a slow salted hash, the server
creates a session row, and the browser gets an opaque id in an `HttpOnly`,
`Secure`, `SameSite` cookie. Every request looks the session up, so the role is
a fact in my database rather than a claim in the request.

Then the part that shows this is yours rather than a tutorial's: the session
also sets a connection variable that the row-level policies read, so
authorisation happens in the database. And the bug I watch for is a pooled
connection carrying the previous request's identity, which would make every
policy enforce the wrong person correctly.
