Five screens built. These six are the problems that arrive after the demo, when
real people start using it, and every one of them has happened.

## 1. The enquiry that vanished

An applicant swears they submitted the form. There is no row in `Enquiry`. The
server logs show a `200`.

Find it.

::accordion
  :::accordion-item{label="How to find it, and the two likely causes" icon="i-lucide-search"}
  Shrink the problem before theorising. Submit it yourself with the same
  programme and the same browser, and watch the network tab.

  **Cause one:** the row was written and rolled back. If the insert and a
  follow-up write share a transaction and the second one threw, the first
  disappears and the handler still returned `200` because the exception was
  caught and logged somewhere nobody reads. Look for a caught exception around
  the transaction boundary.

  **Cause two:** it was flagged as a duplicate. They submitted twice, the second
  one was marked `possible_duplicate`, and the screen the office uses filters
  those out. The row exists. Nobody can see it.

  Cause two is more common and is the more interesting bug, because nothing
  failed. A design decision made a row invisible, which is why "flag, do not
  drop" also requires "and show the flagged ones somewhere".
  :::
::

## 2. The funnel that lost a step

On a quiet Monday the pipeline screen shows four statuses instead of five.
`REJECTED` has disappeared.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  `GROUP BY status` returns one row per status **that exists in the data**. No
  rejections that week means no row, not a row with zero.

  Beginner fix: build the five keys in application code and fill the missing
  ones with zero. It works and it puts a piece of the schema, the list of valid
  statuses, into the front end where it will drift.

  The fix an experienced developer writes: join against the statuses.

  ```sql
  SELECT s.status, COUNT(a.application_id) AS applications
  FROM   UNNEST(ARRAY['RECEIVED','UNDER_REVIEW','SHORTLISTED',
                      'REJECTED','ACCEPTED']) AS s(status)
    LEFT JOIN Application a
           ON a.status = s.status AND a.applied_on >= :intake_start
  GROUP BY s.status;
  ```

  Note `COUNT(a.application_id)` and not `COUNT(*)`. After a `LEFT JOIN` the
  unmatched status still produces one row, so `COUNT(*)` would report 1 for a
  status with no applications. That is the single most common quiet bug in
  reporting SQL.
  :::
::

## 3. The lecturer who can still mark

Priya's colleague left in March. In May he marked attendance for a class he no
longer teaches.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  The `Faculty` row survived for the audit trail, correctly. The `Teaches` rows
  survived too, and every policy asks "does this person teach this subject",
  which is still true.

  The fix is the one from chapter one, and the reason it is worth repeating: the
  policy must ask two things, not one.

  ```sql
  USING (subject_id IN (SELECT subject_id FROM Teaches
                        WHERE faculty_id = current_faculty_id())
         AND current_faculty_is_active())
  ```

  The wider point, and the sentence to say in an interview: **deactivation and
  deletion are different operations.** Nearly every real system needs the first
  far more often, and almost every tutorial only teaches the second.
  :::
::

## 4. The attendance register that doubled

A lecturer on a slow connection tapped submit twice. Sixty students now have
120 attendance rows for one day, and every percentage is wrong.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  Except they do not, if you built the schema as written, because
  `UNIQUE (student_id, subject_id, held_on)` refuses the second set.

  What you get instead is an error on the second submit, which is its own
  problem: the lecturer sees a failure for something that worked. So the write
  becomes an upsert:

  ```sql
  INSERT INTO Attendance (student_id, subject_id, held_on, present)
  VALUES (:sid, :subj, :day, :present)
  ON CONFLICT (student_id, subject_id, held_on)
  DO UPDATE SET present = EXCLUDED.present;
  ```

  Now a double submit is harmless and a **correction** is the same operation,
  which is the real win: a lecturer who marked somebody absent by mistake fixes
  it by submitting again.

  This is idempotency, and it is worth knowing the word. An operation you can
  safely repeat is an operation that survives a flaky network, and flaky
  networks are the normal condition.
  :::
::

## 5. The number in the meeting

The dashboard says fee collection is at 82%. The finance office says it is 71%.
Both queried the same database.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  They are measuring different denominators, and neither is wrong.

  Yours: collected ÷ expected, where expected is `FeeStructure × enrolled
  students`. Theirs: collected ÷ expected, where expected excludes students who
  left, who are on scholarships, or whose fee was waived.

  The bug is not in either query. It is that your screen says "82%" and does not
  say of what.

  The fix is the label:
  `82% collected · ₹4.1 crore of ₹5.0 crore expected · 1,840 enrolled students`

  Now the finance office can see in three seconds that the difference is the
  student count, and the conversation is about the leavers process rather than
  about whose report is broken. **A number with its denominator attached cannot
  start this argument.**
  :::
::

## 6. The seat that went twice

Despite everything in the pipeline lesson, one programme has 121 students in 120
seats.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  Work backwards from what is guaranteed. If you added
  `CHECK (seats_filled <= seats)`, the database cannot hold this state, so
  `seats_filled` is not how admission is counted. Something admits a student
  without going through the service.

  The usual culprits, in order of likelihood:

  1. A one-off script or a manual `INSERT` run by a person fixing something.
  2. A bulk import that writes `Student` rows directly.
  3. An admin screen written later that forgot to call `moveTo`.

  All three are the same root cause: **the rule lived in application code, so
  anything that was not that application code bypassed it.**

  The durable fix is a constraint the database enforces regardless of who is
  writing. Count from the truth rather than a cached number:

  ```sql
  CREATE VIEW v_seat_usage AS
  SELECT p.program_id, p.seats, COUNT(s.student_id) AS filled
  FROM   Program p LEFT JOIN Student s ON s.program_id = p.program_id
  GROUP BY p.program_id, p.seats;
  ```

  Then a trigger, or a deferred constraint, that refuses an insert taking
  `filled` past `seats`. Slower, and correct for every writer that will ever
  exist, including the person with a terminal at 11pm.
  :::
::

## The pattern in all six

Five of these six are the same shape: **a rule that lived in one place, and
something else wrote to the data.**

::pull-quote
Ask of every rule you write: what happens when a script, a migration or a person
with a terminal does this instead of my code? The answer decides whether the
rule belongs in the application or in the database.
::
