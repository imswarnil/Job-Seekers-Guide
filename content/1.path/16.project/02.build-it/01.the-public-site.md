The repository is empty and the plan is on paper. The first thing anybody ever
sees is the public site, so it goes first, and it has to survive three things
your laptop hides from you.

## Why this matters in a job

Because it is the part a reviewer opens. Nobody reads your schema first. They
open the URL on a phone on a train, and whatever happens in the next two seconds
is the impression.

It also matters because "fast, accessible, responsive" are three words on every
job advert and almost nobody can demonstrate them. You are about to be able to.

## What you are building

Six routes, from the screen list.

```text [The routes]
/                      the university, and one call to action
/programmes            every programme, filterable
/programmes/:slug      one programme: seats, cutoff, subjects
/admissions            the process and the dates
/enquire               the form (next lesson)
/status/:reference     one application's step, no login
```

## Done when

Acceptance criteria, not a feeling:

1. The programme list renders on the server and is readable with JavaScript
   disabled.
2. Every page works from the keyboard alone, tab order matching reading order,
   with a visible focus ring.
3. Every page passes an audit at 95 or above for accessibility.
4. The programme page's title, description and social image come from the
   programme, not a template default.
5. A phone at 360px wide has no horizontal scroll on any page.
6. `/programmes` for 40 programmes transfers under 100KB.

::tip
Criterion 1 is the one that catches everything else. If it renders without
JavaScript, it renders fast, it renders for a screen reader, and it renders
when your bundle fails. It is a single test that proves four things.
::

## The three constraints

::feature-list{columns="3"}
  :::feature{icon="i-lucide-gauge" title="Fast on a bad connection"}
  Your laptop on office wifi is not the test. The applicant is on a phone, on
  mobile data, in a town with one mast.
  :::
  :::feature{icon="i-lucide-smartphone" title="Readable on a phone"}
  Not "does not break". Readable: tap targets you can hit, text you can read
  without zooming, a table that became cards.
  :::
  :::feature{icon="i-lucide-keyboard" title="Usable without a mouse"}
  Some people cannot use one. Everybody else uses one sometimes and tabs
  through a form always.
  :::
::

## The markup carries it

Most of this is won or lost in the HTML, before any CSS.

::compare{caption="A programme card, twice. Both look identical."}
  :::compare-side{label="Divs" verdict="wrong"}
  ```html
  <div class="card">
    <div class="title">B.Tech Computer Science</div>
    <div class="meta">120 seats</div>
    <div class="link" onclick="go()">View</div>
  </div>
  ```

  Silently wrong: `div` has no role, so a screen reader announces nothing
  useful, and the "link" cannot be reached by tab or activated by Enter. It
  works perfectly for everyone testing it with a mouse and eyes.
  :::
  :::compare-side{label="Elements that mean something" verdict="right"}
  ```html
  <article class="card">
    <h3><a href="/programmes/btech-cse">B.Tech Computer Science</a></h3>
    <p class="meta">120 seats</p>
  </article>
  ```

  The heading is a heading, so it appears in the screen reader's list of
  headings. The link is a link, so it is focusable, activates on Enter, opens
  in a new tab on middle click, and is understood by a search engine.
  :::
::

::pull-quote
Accessibility is mostly not a feature you add. It is what you get for free when
you use the element that already means the thing you are building.
::

## The part people skip

Metadata. `/programmes/btech-cse` shared into a WhatsApp group should show the
programme's name, not the university's homepage title.

```html [What the programme page must emit]
<title>B.Tech Computer Science · Admissions 2026</title>
<meta name="description" content="120 seats, cutoff 78.5. Eight semesters,
      with subjects listed. Applications close 30 June.">
<meta property="og:title" content="B.Tech Computer Science">
<meta property="og:image" content="https://.../og/btech-cse.png">
```

That is three lines per route and it is the difference between a link that gets
shared and one that gets ignored. It is also the single easiest thing to
demonstrate in an interview, because you paste the URL into the chat and the
preview appears.

## Seed the database first

Before building any of this, write `db/seed.sql`: four departments, twelve
programmes, sixty subjects, forty applicants at mixed statuses, thirty students
with attendance and results.

::warning{icon="i-lucide-alert-triangle"}
Build against realistic data or you will design for the wrong thing. Three
perfect rows hide the pagination you needed, the long programme name that
breaks the card, the applicant with no phone number, and the student with a null
score. Seed forty rows with the messiness real data has, including at least one
of each null you allowed in the schema.
::

## What you can do now

You can build a public site that is fast, works on a phone, works from a
keyboard, and previews correctly when shared. Those four are demonstrable in
sixty seconds, which is exactly how long you get.

## Check yourself

1. Why does "renders with JavaScript disabled" prove more than an accessibility
   audit score does?
2. **An interviewer asks: "how do you make a site accessible?"**

## The interview question this answers

**"How do you approach performance and accessibility?"**

The answer that separates you does not list tools. It names what you did: the
markup uses the elements that already mean the thing, so headings and links work
before any CSS; the page renders on the server so it is readable before the
bundle arrives; the table restructures into cards rather than scrolling
sideways; and I seeded forty realistic rows because three clean ones hide every
problem.

Then the honest limit: an audit score is a smoke test, not a proof. It cannot
tell you the tab order is nonsense or that the error message is announced to
nobody.
