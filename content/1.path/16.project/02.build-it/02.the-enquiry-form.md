A front door with no letterbox. This lesson gives the site its one write, and it
is the moment the project stops being a document and starts being exposed.

## Why this matters in a job

Because every input is hostile until proven otherwise, and this is the lesson
where that stops being a slogan. The form is the boundary between people you
have never met and thirteen tables of confidential data.

I got this wrong in my first paid job. I validated a phone number in the browser
with a neat little regular expression, felt professional about it, and somebody
posted 4,000 rows of garbage straight at the endpoint over a weekend. The form
was never involved.

## Done when

1. A stranger submits on a phone with no account, and sees a confirmation
   containing a reference they can use at `/status/:reference`.
2. A malformed email is refused **by the server**, with a message naming the
   field.
3. The row appears in `Enquiry` with its `source` recorded.
4. The same email and programme within an hour is flagged as a possible
   duplicate rather than silently creating a second row.
5. Thirty submissions from one address in a minute are refused.
6. The error message is announced by a screen reader, not only shown.

## Two validations, two different jobs

This is the idea of the lesson and it is worth stating flatly.

::compare{caption="The same rule, enforced in two places, for two unrelated reasons."}
  :::compare-side{label="In the browser" verdict="neutral"}
  **For kindness.** It tells somebody their email is missing an `@` before they
  wait for a round trip. It is a user-experience feature.

  It is not security. It can be turned off, edited, or skipped entirely by
  sending the request directly.
  :::
  :::compare-side{label="On the server" verdict="right"}
  **For truth.** It is the only check that exists, because it is the only one
  that runs on a machine you control.

  Everything the browser did was advisory. This is the one that decides what
  enters the database.
  :::
::

::pull-quote
Client-side validation is a kindness. Server-side validation is the truth. If
you only have time for one, it is not the one people can see.
::

## What the server actually checks

```java [EnquiryController.java]
public Response submit(EnquiryRequest body) {
  var errors = new ArrayList<FieldError>();

  // Presence and shape, restated on the server even though the form checked.
  if (isBlank(body.fullName()))        errors.add(of("fullName", "Tell us your name"));
  if (!EMAIL.matcher(body.email()).matches())
                                       errors.add(of("email", "That email does not look right"));

  // Existence. The browser could not have checked this one at all.
  if (!programs.exists(body.programId()))
                                       errors.add(of("programId", "Choose a programme"));

  // Length, because a text column with no bound is an invitation.
  if (body.message() != null && body.message().length() > 2000)
                                       errors.add(of("message", "Keep it under 2000 characters"));

  if (!errors.isEmpty()) return Response.unprocessable(errors);

  var reference = enquiries.record(body);       // parameterised, always
  return Response.created(reference);
}
```

Notice the third check. `programId` has to exist in the `Program` table, and
nothing the browser did could have established that, because the browser's list
of programmes came from you and can be edited. **Every id that arrives from
outside is a claim, not a fact.**

::side-note{kind="security"}
`enquiries.record` uses a prepared statement, with the values sent separately
from the query text. Not escaping, not a denylist, not "the input looked fine".
A prepared statement makes it structurally impossible for a value to be parsed
as part of the statement. No exceptions, not for internal tools, not for values
you believe are numeric.
::

## The duplicate nobody expects

Criterion 4 exists because of something real: people double-tap submit buttons
on slow connections. Then they wait, see nothing, and submit again.

::flow{numbered direction="vertical" caption="Three defences, in the order they should be built."}
  :::flow-step{title="Disable the button on submit"}
  Helps the honest case. Achieves nothing against a direct request, which is
  why it is first and least important.
  :::
  :::flow-step{title="Check for a recent match" highlight}
  Same email, same programme, within the hour: record it, mark it
  `possible_duplicate`, and tell the person it looks like they already applied.
  Do not silently drop it, because sometimes they meant it.
  :::
  :::flow-step{title="A constraint that cannot be argued with"}
  The database refuses two identical enquiries for the same day. Application
  logic can be bypassed. A `UNIQUE` index cannot.
  :::
::

::note
Flagging rather than blocking is the judgement call worth explaining out loud.
Blocking a genuine second enquiry makes the office ring the applicant. Flagging
it lets a human decide, and humans are good at this and databases are not.
::

## Rate limiting

Criterion 5. One address, thirty submissions a minute, refused.

```text [What the client gets]
HTTP/1.1 429 Too Many Requests
Retry-After: 60

We have had a lot of submissions from your connection. Try again in a minute.
```

The status code is the part to know: `429`, with `Retry-After`. Saying that
number in an interview costs you a second and marks you as someone who has read
the specification rather than copied a tutorial.

::warning{icon="i-lucide-alert-triangle"}
Rate limit by address **and** by email. Address alone punishes a whole campus
behind one connection, which is exactly the population you want applying. This
is a real trade-off and there is no clean answer; say that rather than pretending
there is.
::

## The error that nobody hears

Criterion 6, and the one almost every project fails.

```html [The field, wired properly]
<label for="email">Email</label>
<input id="email" name="email" type="email"
       aria-invalid="true"
       aria-describedby="email-error">
<p id="email-error" role="alert">That email does not look right</p>
```

Three attributes. `aria-invalid` says this field is wrong, `aria-describedby`
ties the message to the input so it is read out when focus lands there, and
`role="alert"` makes it announced the moment it appears.

Without them, a screen reader user submits the form, hears nothing change, and
has no way to find out which of six fields is the problem.

## What you can do now

You can take input from strangers safely: validate in both places for different
reasons, handle the duplicate a real person creates, rate limit without
punishing a campus, and report an error to somebody who cannot see it.

## Check yourself

1. The browser checked that `programId` was one of the twelve in the dropdown.
   Why does the server check it again?
2. **An interviewer asks: "how do you prevent SQL injection?"**

## The interview question this answers

**"Walk me through what happens when someone submits a form."**

The sequence: the browser validates for kindness, the request arrives, the
server validates everything again because nothing from outside is trusted,
including ids that came from a list I supplied. Values go to the database
through a prepared statement so a value can never become part of the statement.
A recent identical enquiry is flagged rather than dropped, and a unique index
backs that up because application logic can be bypassed.

Then the part that gets remembered: and the error comes back tied to the field
with `aria-describedby`, because a validation message nobody can hear is not a
validation message.
