The office can see the enquiries and cannot move them. This is the screen the
registrar has open all day, and it is where the system either becomes the thing
they work in or the thing they work around.

## Why this matters in a job

Because a status change looks like one line of code and is not. It is two writes
that must both happen, a permission check, an audit record, and a race between
two people clicking at the same time. Getting all four right is what separates a
demonstration from a system.

## Done when

1. An admin moves an application through the five statuses, and each move writes
   an `ApplicationEvent` with who and when.
2. A backwards move requires a note.
3. Both writes succeed together or neither happens.
4. A reviewer sees only applications assigned to them.
5. Two admins accepting the last seat at the same moment cannot both succeed.
6. The pipeline screen shows the funnel counts, computed in one query.

## The two writes

```java [ApplicationService.java]
@Transactional
public void moveTo(long applicationId, Status to, long actorId, String note) {
  var app = applications.lockForUpdate(applicationId);   // see the race, below

  if (isBackwards(app.status(), to) && isBlank(note)) {
    throw new NoteRequired("Moving back from " + app.status() + " needs a reason");
  }

  events.record(applicationId, app.status(), to, actorId, note);  // write one
  applications.setStatus(applicationId, to);                      // write two
}
```

`@Transactional` is the whole lesson in one annotation. Without it, the event
can be written and the status update can fail, and now the history says
`SHORTLISTED` while the application says `UNDER_REVIEW`. Nobody notices for a
month, and then nobody can work out which is true.

::pull-quote
Two writes that must agree are one operation. If your code can produce a state
where only half of it happened, you have not written a feature. You have written
a future support ticket with no explanation attached.
::

Three fixes, and being able to choose between them is the actual test.

::tabs
  :::tabs-item{label="One conditional update" icon="i-lucide-zap"}
  ```sql
  UPDATE Program
     SET seats_filled = seats_filled + 1
   WHERE program_id = :id
     AND seats_filled < seats;
  ```
  Then **check the row count**. Zero rows means somebody took the seat, and you
  tell the admin that rather than pretending it worked.

  Best when clashes are rare, which here they are. No locking, no extra round
  trip.
  :::
  :::tabs-item{label="SELECT FOR UPDATE" icon="i-lucide-lock"}
  ```sql
  SELECT seats, seats_filled FROM Program
   WHERE program_id = :id FOR UPDATE;
  ```
  The row is locked until the transaction ends, so the second admin waits.
  Correct, and it serialises everybody through that row.

  Best when the decision needs several reads before the write, which the real
  acceptance logic does.
  :::
  :::tabs-item{label="A version column" icon="i-lucide-git-compare"}
  ```sql
  UPDATE Program SET seats_filled = :new, version = version + 1
   WHERE program_id = :id AND version = :seen;
  ```
  Nobody waits. The loser gets zero rows updated and retries.

  Best when clashes are rare and the transaction is long.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
Then put a constraint underneath whichever you chose:
`CHECK (seats_filled <= seats)`. Application logic can be bypassed by a script,
a migration or a person with a terminal. The constraint cannot, and it turns a
silent over-admission into a loud failure.
::

## The funnel, in one query

Criterion 6. The screen shows five counts, and the beginner version runs five
queries.

```sql [One query, one pass]
SELECT status, COUNT(*) AS applications
FROM   Application
WHERE  applied_on >= :intake_start
GROUP BY status;
```

```text [Output]
 status        | applications
---------------+--------------
 RECEIVED      |          412
 UNDER_REVIEW  |          188
 SHORTLISTED   |           96
 REJECTED      |          104
 ACCEPTED      |           74
```

::note
A status with no applications is **absent** from these rows, not zero. The screen
must render all five statuses and fill missing ones with 0, or the funnel
silently loses a step on a quiet day. This is the `LEFT JOIN` against a list of
statuses that most people discover in production.
::

## The assignment rule

Criterion 4. A reviewer sees applications assigned to them, and you already know
where that rule goes.

```sql [policies.sql]
CREATE POLICY faculty_reads_assigned ON Application
  FOR SELECT
  USING (reviewer_id = current_faculty_id());
```

Not a `WHERE` clause in a controller. A policy on the table, so the reviewer
screen and the reports and the export and the endpoint you write next month all
inherit it without anybody remembering.

## What you can do now

You can build a state machine over real data: two writes in one transaction, an
audit record for every change, a note required for the unusual direction, and a
race condition handled with a named strategy rather than hope.

## Check yourself

1. The transaction wraps two writes. Describe the exact broken state you get
   without it, and why nobody notices for weeks.
2. **An interviewer asks: "two users click the same button at the same time.
   What happens?"**

## The interview question this answers

**"Tell me about a concurrency problem you have handled."**

Name the bug first: **lost update**, and that every major database allows it at
its default isolation level. That single sentence does more than any description
of your solution.

Then the three fixes and when each one fits: a conditional update with the row
count checked when clashes are rare, `SELECT FOR UPDATE` when the decision needs
several reads, a version column when transactions are long.

Then close with the constraint underneath, and the real cause: most of these in
practice are one person double-clicking, not two people racing, so a `UNIQUE`
index fixes more of them than any locking strategy.
