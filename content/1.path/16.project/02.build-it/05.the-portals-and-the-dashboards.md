The office works and the several thousand people it exists for have nowhere to
look. This lesson builds their side, and then the four numbers that decide
whether anybody keeps paying for the system.

## Why this matters in a job

Because the portals are where adoption is won or lost, and because a dashboard
is the easiest place in software to be confidently wrong. A number on a screen
carries authority it has not earned, and somebody makes a decision on it.

## Done when

1. A student sees their own results, attendance and fees, and no other
   student's, enforced by policy rather than by the query.
2. Attendance shows attended, total and a percentage to one decimal, with the
   75% threshold marked in **text as well as colour**.
3. A lecturer marks a full class in under a minute on a phone.
4. Marks entry records who entered them and when.
5. Every dashboard number states its own denominator.
6. The at-risk list is one query and names why each student is on it.

## The student side

Three screens, all reading, all trivial now, and that is the point: the policies
from chapter one mean the query has no `WHERE student_id = ?` in it at all.

```sql [What the attendance screen runs]
SELECT s.name AS subject,
       COUNT(*) FILTER (WHERE a.present) AS attended,
       COUNT(*)                          AS held,
       ROUND(100.0 * COUNT(*) FILTER (WHERE a.present) / COUNT(*), 1) AS pct
FROM   Attendance a
JOIN   Subject s ON s.subject_id = a.subject_id
GROUP BY s.name
ORDER BY pct;
```

```text [Output, for the student who is signed in]
 subject                | attended | held |  pct
------------------------+----------+------+------
 Operating Systems      |       21 |   32 | 65.6
 Database Systems       |       26 |   33 | 78.8
 Data Structures        |       30 |   34 | 88.2
```

No student filter anywhere, and it returns one student's rows. That is
row-level security doing its job, and the reason to notice it is that **the
query you would have written wrongly is now impossible**.

::warning{icon="i-lucide-alert-triangle"}
`ORDER BY pct` puts the subject they are failing at the top. That is a design
decision, not a default, and it is the kind of thing that makes a portal feel
like it was built by somebody who thought about the person using it.
::

## Colour is not a message

Criterion 2, and the accessibility rule that matters most in this whole project.

::compare{caption="The same attendance row, and only one of them works for everybody."}
  :::compare-side{label="A red row" verdict="wrong"}
  `Operating Systems · 65.6%` rendered in red.

  About one man in twelve cannot reliably distinguish it from the rows around
  it. Neither can anybody on a phone in sunlight, or anybody printing it.
  :::
  :::compare-side{label="Red, and the word" verdict="right"}
  `Operating Systems · 65.6% · Below the 75% requirement`

  The colour is still there and still useful. It is now redundant rather than
  load-bearing, which is the whole rule: **never encode meaning in colour
  alone.**
  :::
::

## The register, designed for a corridor

Criterion 3. Priya has sixty students and two minutes between classes.

::flow{numbered caption="Everybody present by default. This is the whole design, and it is four taps per class instead of four taps per student."}
  :::flow-step{title="Open the subject"}
  One tap. Today's date is already selected, because 95% of uses are today.
  :::
  :::flow-step{title="Tap the absent ones" highlight}
  Six taps for six absentees, large targets, no confirmation. The 54 present
  students needed no interaction at all.
  :::
  :::flow-step{title="Submit"}
  One tap. Writes 60 rows in one transaction, and the `UNIQUE (student_id,
  subject_id, held_on)` constraint makes a double submission a no-op instead of
  a doubled register.
  :::
::

::pull-quote
The default should be the common case. Sixty students, six absent, and a design
that asks about all sixty is a design that gets abandoned for paper by March.
::

## The four numbers

The registrar's Monday. Each one has a trap.

::tabs
  :::tabs-item{label="The funnel" icon="i-lucide-filter"}
  Applications at each status, and the conversion between them.

  **The trap:** conversion of what, over which period? "42% shortlisted" means
  nothing without the intake. Label it `42% of 412 applications, June intake`.
  :::
  :::tabs-item{label="Fee collection" icon="i-lucide-receipt"}
  Collected against expected, per programme, with a running total.

  **The trap:** expected comes from `FeeStructure × enrolled students`, and a
  student who left in week two is still enrolled unless somebody said otherwise.
  The number is only as honest as the leavers process.
  :::
  :::tabs-item{label="Attendance against results" icon="i-lucide-chart-scatter"}
  One point per student: attendance percentage against average marks.

  **The trap:** this shows a correlation and people will read it as a cause. Say
  so on the chart. Students who attend more do better is not the same claim as
  attending more makes you do better.
  :::
  :::tabs-item{label="The at-risk list" icon="i-lucide-triangle-alert"}
  Criterion 6. Students the university should contact this week.

  **The trap:** a list with no reason attached gets ignored. Every row names why
  it is there.
  :::
::

```sql [The at-risk list, one query, with its reason]
SELECT st.roll_number, st.student_id,
       CASE
         WHEN att.pct < 75            THEN 'Attendance ' || att.pct || '%'
         WHEN res.backlogs >= 2       THEN res.backlogs || ' backlogs'
         ELSE                              'Fees overdue'
       END AS reason
FROM   Student st
  LEFT JOIN v_attendance_pct att ON att.student_id = st.student_id
  LEFT JOIN v_backlogs      res ON res.student_id = st.student_id
  LEFT JOIN v_fee_overdue   fee ON fee.student_id = st.student_id
WHERE  att.pct < 75 OR res.backlogs >= 2 OR fee.days_overdue > 30
ORDER BY att.pct NULLS LAST;
```

::note
Those `v_` names are the SQL views from the database track, still running
underneath all of this. The reporting layer you wrote weeks ago did not get
replaced by the application. It got a front end.
::

## The label that stops a number lying

Criterion 5, and it is the single most valuable habit in this lesson.

```text [Two versions of the same true number]
  Average score of shortlisted applicants          71.4
  Average score of shortlisted applicants          71.4   from 120 of 400 marked
```

Same query. The first one gets used to set a cutoff in a meeting. The second one
gets the meeting to wait for the marking to finish.

## What you can do now

You can build the reading side of a system where the security is structural, a
data-entry screen designed around how it is actually used, and dashboards whose
numbers cannot quietly mislead the person reading them.

## Check yourself

1. The attendance query has no student filter. Explain why it returns one
   student's rows, and what happens if the policy is dropped.
2. **An interviewer asks: "how do you make sure a dashboard is telling the
   truth?"**

## The interview question this answers

**"What would you do differently if you built it again?"**

The trap is answering with a technology. The answer that works is a
specific decision with a specific consequence.

Mine: I built the attendance register the obvious way first, a row per student
with present and absent buttons, and a lecturer told me it was slower than
paper. The fix was defaulting everybody to present and only recording the
exceptions. I would now start by asking who uses a screen most and how long they
have, before designing any of it.

That answer works because it contains a real user, a real complaint, and a
change you can describe in one sentence.
