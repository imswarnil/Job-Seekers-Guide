Thirteen tables and no rules about who reads them. A student must not see
another student's marks, and the question is not whether you check. It is
**where** you check.

## Why this matters in a job

Because this is the failure that ends careers rather than sprints. A bug shows a
wrong number. A missing authorisation check shows one student another student's
results, and that is a letter from a parent, a regulator, and a story in a local
paper.

It is also asked constantly, because the difference between authentication and
authorisation is the cheapest way for an interviewer to find out whether you
have thought about security at all.

::note
**Authentication** is proving who you are. **Authorisation** is what you are
allowed to do once you have. Logging in is authentication. Not being able to
read somebody else's marks after logging in is authorisation. They are
different systems and they fail differently.
::

## The matrix

Write it out. Every table, every operation, every role. It is boring and it
takes twenty minutes, and it is the only way to find the row you had not thought
about.

| Table | Applicant | Student | Faculty | Admin |
| --- | --- | --- | --- | --- |
| `Applicant` | own row | own row | none | all |
| `Application` | own, read | own, read | assigned only | all |
| `ApplicationEvent` | none | none | insert on assigned | all |
| `Student` | none | own row | students they teach | all |
| `Subject` | read | read | read | all |
| `ExamResult` | none | **own, read** | insert and update for their subjects | all |
| `Attendance` | none | **own, read** | insert and update for their subjects | all |
| `FeeStructure` | read | read | none | all |
| `FeePayment` | none | **own, read** | none | all |
| `Placement` | none | own, read | none | all |
| `Program` | read | read | read | all |
| `Department` | read | read | read | all |
| `Faculty` | none | name only | own row | all |

::tip
The three bold cells are the ones that matter most and the ones a hand-rolled
check forgets. They are also the three a hostile person tries first, in that
order, and the attempt looks exactly like a normal request with a different id
in it.
::

## The insight: a request is not a page

Here is the thing beginners get wrong, and I got it wrong for a year.

Hiding a link does not hide the data. Disabling a button does not prevent the
action. The browser is not your program; it is a program on somebody else's
computer that you do not control, and anything it can ask for, a person can ask
for directly.

::code-trace{language="bash" caption="Nothing here involves the interface at all."}
```bash
curl https://university.example/api/results/4182 \
  -H "Cookie: session=<a real student's own valid session>"
```
  :::code-trace-step{lines="1" caption="A perfectly ordinary request. The session is genuine: this person is logged in, and authentication has succeeded completely."}
  :::
  :::code-trace-step{lines="1" caption="`4182` is somebody else's student id, typed by hand. There is no interface anywhere that would have produced this request, which is exactly why hiding the link achieved nothing."}
  :::
  :::code-trace-step{lines="2" caption="If authorisation lives in the page, this returns another student's marks. If it lives on the table, it returns nothing, and it returns nothing even when the route handler forgot to check."}
  :::
::

## Where the rule goes

On the table.

```sql [policies.sql]
ALTER TABLE ExamResult ENABLE ROW LEVEL SECURITY;

-- A student sees their own results. Not "the interface shows", the
-- database returns.
CREATE POLICY student_reads_own_results ON ExamResult
  FOR SELECT
  USING (student_id = current_student_id());

-- A lecturer sees results for subjects they actually teach.
CREATE POLICY faculty_reads_taught_subjects ON ExamResult
  FOR SELECT
  USING (subject_id IN (SELECT subject_id FROM Teaches
                        WHERE faculty_id = current_faculty_id()));
```

```text [What a query returns]
-- Logged in as student 9001, asking for everything:
SELECT * FROM ExamResult;
-- 6 rows. Student 9001's six subjects. No error, no refusal, no 403.
```

That last detail is worth sitting with. The query did not fail. It returned the
rows this person is allowed to see, which means **code that forgot to filter is
still correct**.

::side-note{kind="security"}
Fail closed, not open. Interface-level authorisation means a forgotten check
leaks data. Table-level means a forgotten check returns an empty list, somebody
files a bug saying "my results are missing", and you fix it on a Tuesday instead
of writing to a regulator.
::

## The one that is not a policy

Admin. Do not write a policy saying "admins see everything" and move on, because
the interesting question is not whether the registrar can read a student's fee
history. It is whether anyone can tell that they did.

That is what `ApplicationEvent` is for on the admissions side, and the same idea
applies to any admin read of a sensitive table: log who looked, at what, and
when. An audit trail is not a security control. It is what makes the security
control believable afterwards.

::real-life{title="The question that actually gets asked" source="A registrar's office, after a rejection"}
A parent rings. Their child was rejected and the family believes a mistake was
made. The office needs to answer three things: who reviewed it, what the score
was, and when the status changed.

Without `ApplicationEvent`, the honest answer is "the system says REJECTED and
we do not know who did it or why". That answer costs the university more than
any outage.
::

## What you can do now

You can write an access matrix for a real system, explain why authorisation
belongs in the database rather than in the interface, and say what happens when
the check is forgotten in each design.

## Your turn

A lecturer leaves the university in March. Their rows stay in `Faculty` because
`ApplicationEvent.changed_by` points at them and deleting would destroy the
audit trail.

What breaks, and what do you change?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  What breaks: every policy written as "the faculty member teaching this
  subject" still matches them if the `Teaches` rows remain, so a person who no
  longer works there can still read marks. Deleting the `Faculty` row is refused
  by the foreign key, which is the database correctly protecting the history.

  The change: `Faculty` gets `active BOOLEAN NOT NULL DEFAULT true` and every
  policy gains `AND current_faculty_is_active()`. The row survives for the audit
  trail, the access does not.

  The general principle, and the sentence to say out loud: **deactivation and
  deletion are different operations, and almost every real system needs the
  first far more than the second.** A person who leaves should stop being able
  to act while remaining able to be referred to.
  :::
::

## Check yourself

1. A route handler forgets its authorisation check. Describe exactly what
   happens under each of the two designs.
2. **An interviewer asks: "what is the difference between authentication and
   authorisation?"**

## The interview question this answers

**"How do you stop one user seeing another user's data?"**

The weak answer is "I check the user id in the controller". It is not wrong, it
is incomplete, and it describes a design that fails open.

The answer that lands: the check goes as close to the data as it can, as a
row-level policy on the table, so the database returns only permitted rows
whatever the query asked for. Then name the failure mode you are buying: a
forgotten check returns too little rather than too much, and too little gets
reported as a bug while too much gets reported as a breach.
