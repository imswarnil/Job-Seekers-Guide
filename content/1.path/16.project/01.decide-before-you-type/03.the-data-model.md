The schema. This is the expensive one, because every query, screen and report in
the system is written against it, and changing a table in month three means
changing forty things that read it.

## Why this matters in a job

Because a bad schema cannot be refactored away. Bad code in one file is an
afternoon. A table that cannot hold a fact the business needs is a migration,
a backfill, and every query rewritten, usually while the thing is live.

In 2018 I spent a month stuck on joins, and the real reason was not the join
syntax. It was that I was joining a schema that did not match reality, so no
query I wrote could be correct.

## The applicant problem

Here it is, the decision the requirements lesson warned about. An applicant
becomes a student. Do they become the same row, or a new one?

::compare{caption="Two schemas, and the second one is correct."}
  :::compare-side{label="One table, a flag" verdict="wrong"}
  `Applicant` grows a `is_student` column and a nullable `roll_number`, and half
  its columns are meaningless depending on the flag.

  It runs. It is silently wrong the first time somebody applies twice, to two
  programmes, in the same year. There is one row and two applications, and the
  row cannot hold two different statuses.
  :::
  :::compare-side{label="A person, and their roles" verdict="right"}
  `Applicant` is a **person who applied**. `Application` is one attempt at one
  programme. `Student` is a person who was admitted, and carries
  `applicant_id`.

  Now somebody can apply three times, be rejected twice and admitted once, and
  every one of those facts has a row that fits it.
  :::
::

::pull-quote
Model what happened, not what is currently true. "Currently true" is a query you
can always run against what happened. What happened cannot be recovered from a
flag somebody overwrote.
::

## The tables

Thirteen for the whole system. Fewer than people expect.

::tabs
  :::tabs-item{label="Admissions" icon="i-lucide-filter"}
  ```sql [schema.sql]
  CREATE TABLE Applicant (
    applicant_id  BIGSERIAL PRIMARY KEY,
    full_name     TEXT        NOT NULL,
    email         CITEXT      NOT NULL,
    phone         TEXT,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
  );

  CREATE TABLE Application (
    application_id BIGSERIAL PRIMARY KEY,
    applicant_id   BIGINT NOT NULL REFERENCES Applicant,
    program_id     BIGINT NOT NULL REFERENCES Program,
    status         TEXT   NOT NULL DEFAULT 'RECEIVED'
                   CHECK (status IN ('RECEIVED','UNDER_REVIEW',
                                     'SHORTLISTED','REJECTED','ACCEPTED')),
    score          NUMERIC(5,2) CHECK (score BETWEEN 0 AND 100),
    source         TEXT,
    reviewer_id    BIGINT REFERENCES Faculty,
    applied_on     DATE   NOT NULL DEFAULT CURRENT_DATE,
    -- One person cannot apply to the same programme twice in one intake.
    UNIQUE (applicant_id, program_id, applied_on)
  );

  CREATE TABLE ApplicationEvent (
    event_id       BIGSERIAL PRIMARY KEY,
    application_id BIGINT NOT NULL REFERENCES Application,
    from_status    TEXT,
    to_status      TEXT        NOT NULL,
    changed_by     BIGINT      NOT NULL,
    note           TEXT,
    changed_at     TIMESTAMPTZ NOT NULL DEFAULT now()
  );
  ```
  :::
  :::tabs-item{label="People" icon="i-lucide-users"}
  ```sql [schema.sql]
  CREATE TABLE Department (
    department_id BIGSERIAL PRIMARY KEY,
    name          TEXT NOT NULL UNIQUE
  );

  CREATE TABLE Program (
    program_id    BIGSERIAL PRIMARY KEY,
    department_id BIGINT NOT NULL REFERENCES Department,
    name          TEXT   NOT NULL,
    seats         INT    NOT NULL CHECK (seats > 0),
    cutoff        NUMERIC(5,2)
  );

  CREATE TABLE Student (
    student_id   BIGSERIAL PRIMARY KEY,
    applicant_id BIGINT NOT NULL REFERENCES Applicant,
    program_id   BIGINT NOT NULL REFERENCES Program,
    roll_number  TEXT   NOT NULL UNIQUE,
    admitted_on  DATE   NOT NULL
  );

  CREATE TABLE Faculty (
    faculty_id    BIGSERIAL PRIMARY KEY,
    department_id BIGINT NOT NULL REFERENCES Department,
    full_name     TEXT   NOT NULL,
    email         CITEXT NOT NULL UNIQUE
  );
  ```
  :::
  :::tabs-item{label="Academics" icon="i-lucide-graduation-cap"}
  ```sql [schema.sql]
  CREATE TABLE Subject (
    subject_id   BIGSERIAL PRIMARY KEY,
    program_id   BIGINT NOT NULL REFERENCES Program,
    code         TEXT   NOT NULL UNIQUE,
    name         TEXT   NOT NULL,
    semester     INT    NOT NULL CHECK (semester BETWEEN 1 AND 8)
  );

  CREATE TABLE ExamResult (
    result_id  BIGSERIAL PRIMARY KEY,
    student_id BIGINT NOT NULL REFERENCES Student,
    subject_id BIGINT NOT NULL REFERENCES Subject,
    attempt    INT    NOT NULL DEFAULT 1,
    marks      NUMERIC(5,2) CHECK (marks BETWEEN 0 AND 100),
    -- Attempt is in the key, because a failed subject is re-sat.
    UNIQUE (student_id, subject_id, attempt)
  );

  CREATE TABLE Attendance (
    attendance_id BIGSERIAL PRIMARY KEY,
    student_id    BIGINT NOT NULL REFERENCES Student,
    subject_id    BIGINT NOT NULL REFERENCES Subject,
    held_on       DATE   NOT NULL,
    present       BOOLEAN NOT NULL,
    UNIQUE (student_id, subject_id, held_on)
  );
  ```
  :::
  :::tabs-item{label="Money and after" icon="i-lucide-receipt"}
  ```sql [schema.sql]
  CREATE TABLE FeeStructure (
    fee_id     BIGSERIAL PRIMARY KEY,
    program_id BIGINT NOT NULL REFERENCES Program,
    academic_year INT  NOT NULL,
    amount_paise  BIGINT NOT NULL CHECK (amount_paise > 0),

  CREATE TABLE FeePayment (
    payment_id   BIGSERIAL PRIMARY KEY,
    student_id   BIGINT NOT NULL REFERENCES Student,
    fee_id       BIGINT NOT NULL REFERENCES FeeStructure,

    amount_paise BIGINT NOT NULL CHECK (amount_paise > 0),
    paid_on      DATE   NOT NULL,
    receipt_no   TEXT   NOT NULL UNIQUE
  );

  CREATE TABLE Placement (
    placement_id BIGSERIAL PRIMARY KEY,
    student_id   BIGINT NOT NULL REFERENCES Student,
    company      TEXT   NOT NULL,
    package_paise BIGINT CHECK (package_paise > 0),
    offered_on   DATE   NOT NULL
  );
  ```

## The two deliberate denormalisations

Everything above is normalised except two things, and both are on purpose. An
interviewer will ask, so know which is which.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-receipt" title="FeePayment stores the amount"}
  The amount is already on `FeeStructure`, so storing it again looks redundant.
  It is not. The fee **will** change next year, and a receipt from last year
  must still say what was actually paid. This is not denormalisation at all. It
  is a different fact that happens to have the same value today.
  :::
  :::feature{icon="i-lucide-history" title="ApplicationEvent duplicates status"}
  `Application.status` is the current status, and `ApplicationEvent` records
  every change. You could derive the current status from the last event, and it
  would be slower on the screen people look at most. The trade is a write that
  must update both, inside one transaction.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
Money is `BIGINT` paise, never `NUMERIC` rupees and absolutely never a floating
point type. `0.1 + 0.2` is not `0.3` in binary floating point, and a fee report
that is out by a few paise per row is out by thousands across a university, with
no bug to find because every individual line looks right.
::

## What the constraints are doing

Read the schema again and notice how much of the business is written into it:

- A score outside 0 to 100 cannot be stored, by anyone, ever.
- A status outside the five-step ladder cannot be stored.
- A programme cannot have zero seats.
- The same student cannot have two attendance rows for one subject on one day,
  which means a double-submitted register is refused rather than counted twice.
- `ExamResult` has `attempt` in its key, which is the schema admitting that
  students fail and re-sit.

Every one of those is a rule that would otherwise live in application code, be
forgotten in one place, and produce data nobody can trust.

## What you can do now

You can design a schema for a real domain, defend each key, and explain which
duplications are mistakes and which are deliberate.

## Your turn

The registrar asks for something the schema above cannot answer:
**"which applicants did we reject who later got admitted somewhere and were
placed?"**

Say what is missing and what you would add. Then say why you would probably
refuse.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  What is missing: nothing in this system knows anything about a person after a
  rejection. `Applicant` ends at the rejection, and `Placement` hangs off
  `Student`, who by definition was admitted here.

  To answer it you would need outcome data about people who are not your
  students, which means either asking them (a survey table, mostly empty) or
  buying it.

  Why you refuse: the question is a good one and the data does not exist. The
  honest reply is "we cannot answer that, and here is the nearest thing we can:
  of the applicants we rejected, what their scores were against the ones we
  admitted, so we can see whether the cutoff is defensible."

  Being able to say "that question cannot be answered with the data we have, and
  here is the adjacent one that can" is a genuine senior skill, and it is much
  rarer than schema design.
  :::
::

## Check yourself

1. Why does `ExamResult` have `attempt` in its unique key, and what breaks
   without it?
2. **An interviewer asks: "give me an example of when you denormalised on
   purpose."**

## The interview question this answers

**"How would you model this?"**

The sequence: nouns become entities, then what identifies each one and could
that value ever change, then cardinality so a many-to-many becomes a junction
table, then which facts must be frozen at a moment in time.

Then draw it and **name the constraints as you go**. "This is unique, this
cannot be deleted while children exist, this must be between 0 and 100." Naming
constraints while drawing is the most senior-sounding thing available in this
question, and almost nobody does it.
