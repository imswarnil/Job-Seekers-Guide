The shape. You have a document saying what the system must do, and nothing
saying what it is, so here are the four decisions that are painful to change
once there is code on top of them.

## Why this matters in a job

Because "why did you build it that way" is asked in every technical round, and
the answer "that is what the tutorial did" ends the conversation. An engineer is
somebody who can name the alternative they rejected.

It also matters because these four are genuinely hard to reverse. Everything
else in this system can be rewritten in an afternoon. These cannot.

::warning{icon="i-lucide-alert-triangle"}
This lesson argues for a specific set of choices, and they are right **for this
system at this size**. They are not universal. The reasoning is the transferable
part, not the conclusion, and an interviewer can tell the difference instantly.
::

## Decision one: one application, not several

::pros-cons
---
title: A monolith for the University Management App
pros:
  - One repository, one deploy, one place to look when something breaks
  - A change that touches admissions and fees is one commit and one review
  - Transactions work, because it is one database and one connection
  - You can run the whole thing on a laptop, which is most of your working life
cons:
  - Everything scales together, even the one screen nobody opens
  - A bad dependency can slow down pages that have nothing to do with it
  - One bad deploy takes down all of it
---
::

The honest version: services solve an **organisational** problem before they
solve a technical one. They let eight teams deploy without coordinating. A
university admissions system serving a few thousand people, built by one person,
has no such problem, and paying the cost of distributed systems to solve a
problem you do not have is the most common over-engineering in this industry.

::pull-quote
The number of people deploying the software is a better predictor of the right
architecture than the number of people using it.
::

Say that in an interview and mean it.

## Decision two: rendered on the server

The student portal is mostly reading: results, attendance, what you owe. A page
that arrives already containing its content is faster on a slow connection,
works before JavaScript loads, and is readable by a screen reader without
argument.

::compare{caption="The same attendance page, two ways, on a 3G connection in a campus corridor."}
  :::compare-side{label="Client-rendered" verdict="wrong"}
  The browser downloads an empty shell, then the bundle, then asks for the data,
  then draws. The student sees a spinner for four seconds and a blank page if
  the bundle fails.

  Silently wrong in a second way: the data was fetched by the browser, so
  anything the browser could ask for, a student could ask for directly.
  :::
  :::compare-side{label="Server-rendered" verdict="right"}
  The server reads the database, checks who is asking, and sends HTML containing
  this student's attendance. One round trip. It renders before any JavaScript
  runs, and the authorisation happened where a student cannot reach it.
  :::
::

The interactive parts still need the browser: marking a register, filtering the
pipeline. Those become islands of behaviour on a rendered page rather than the
page being an application.

## Decision three: one relational database

The data in a university is relentlessly relational. A student belongs to a
programme, which belongs to a department. An exam result belongs to a student
and a subject. A fee payment belongs to a student and a fee structure. Every
important question is a join.

PostgreSQL, and the constraints live in the database rather than in your code,
because your code is not the only thing that will ever write to that database.
A script, a migration and a person with a terminal will, and a `CHECK` survives
all three.

## Decision four: authorisation in the database

The one people find surprising, and the one worth the most in an interview.

A student must not see another student's marks. You could check that in the
route handler. Every route handler. Forever. Miss one, and the system is a
breach rather than a bug.

Instead the rule lives on the table, as a row-level policy, and the database
refuses. The route handler that forgets to check returns nothing rather than
everything.

::side-note{kind="security"}
The difference is the failure mode. Interface-level authorisation fails **open**:
forget the check and the data flows. Database-level fails **closed**: forget
everything and the query returns zero rows. Design so that the mistake you will
eventually make is the safe one.
::

## The record

Write these down. Four short entries, each with the decision, the alternative
you rejected, and the reason. Keep it in the repository as
`docs/decisions.md`.

It costs twenty minutes and it is the document you will read out loud in an
interview, because "I chose a monolith" is a claim and "here is what I wrote
when I chose a monolith, including what I was worried about" is evidence.

## What you can do now

You can state, and argue, four architectural decisions about a real system, and
name what you traded away in each. That is the difference between having built
something and having designed something.

## Check yourself

1. Give one honest reason this system might eventually need to be split into
   services, and say what would have to be true first.
2. **An interviewer asks: "why not microservices?"**

## The interview question this answers

**"Walk me through the architecture of something you built."**

Start with the constraint, not the diagram: one developer, a few thousand users,
every question is a join, and the data is confidential per row. Then the four
decisions fall out of that constraint rather than out of fashion, and each one
comes with its rejected alternative.

Finish with the limit, unprompted: this shape stops working when several teams
need to deploy independently, and I would split on that boundary rather than on
a technical one. Naming when your own design fails is the most senior thing you
can do in this answer.
