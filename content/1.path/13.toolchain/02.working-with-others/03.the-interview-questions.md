description: Six questions about tooling and working with other people, which for a fresher is the hardest round to answer and the easiest to prepare.

These are asked of freshers constantly, because they separate somebody who has
worked on something with other people from somebody who has only ever written
from scratch. You do not need employment to have the answers.

::accordion
  :::accordion-item{label="1. What is a lock file and why commit it?" icon="i-lucide-message-circle"}
  `^4.18.0` says what you would accept; the lock file records what you actually
  got, exactly, including every transitive dependency and its checksum. Commit
  it so every machine and the build server resolve identically.

  Then the sentence that shows you have been bitten: "it failed on CI so I
  deleted the lock file and it worked" is a real and common sequence, and what
  actually happened is that every transitive dependency was silently upgraded.
  :::

  :::accordion-item{label="2. How do you decide whether to add a library?" icon="i-lucide-message-circle"}
  Four questions, in thirty seconds. When was it last updated, because three
  years and open issues means you own it now. How many dependencies does it
  bring, because one package can add a thousand. Could I write this in twenty
  lines, in which case write them. And what happens if it disappears.

  Then the security note, which matters more now that install commands get
  copied out of model output: typosquatting. `expres`, `reqeusts`, published
  deliberately with a post-install script. Read the name twice.
  :::

  :::accordion-item{label="3. What makes a good pull request?" icon="i-lucide-message-circle"}
  Small enough to actually review, past roughly four hundred lines it gets
  approved rather than read, because nobody can hold it in their head and nobody
  wants to block it for three days. One change. A description that says what and
  why before any detail.

  And the section almost nobody writes: **what I am unsure about**. It points
  the reviewer at where their attention is worth most, and it makes you far
  easier to review.
  :::

  :::accordion-item{label="4. How do you handle a review comment you disagree with?" icon="i-lucide-message-circle"}
  What is being tested is whether you argue to win. Restate the reasoning so
  they know you understood it, give the reason you chose otherwise, and ask a
  question: "I chose the list deliberately because it is built once and never
  searched, so the hash overhead would cost more than it saves. Have I missed a
  place where we search it?"

  And say the other half, because it is the true half: most of the time the
  reviewer is right, and taking the comment is the answer.
  :::

  :::accordion-item{label="5. What is CI for?" icon="i-lucide-message-circle"}
  Not finding bugs. Removing a category of conversation: does it compile, do the
  tests pass, is it formatted. A reviewer arrives already knowing all three and
  can spend their attention on whether the change is *right*.

  Then the rule that keeps it useful: a red build gets fixed before anything
  else. A team that tolerates a failing build for two days has thrown the whole
  thing away, because everybody starts ignoring the result.
  :::

  :::accordion-item{label="6. Tell me about your experience working in a team" icon="i-lucide-message-circle"}
  The hard one for a fresher, and this track is the answer. You do not need a
  job to have the habits: one branch per change, small commits with messages
  that say why, pull requests with a real description, and CI that runs the
  tests before anybody looks.

  Say that you do this on your own project even though you are alone, and say
  why: writing the description finds things. Explaining what you changed makes
  you notice the case you did not handle, reliably, about one time in four.
  :::
::
