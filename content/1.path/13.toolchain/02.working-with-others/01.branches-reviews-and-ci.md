Somebody else has to change the same code at the same time, and neither of you
can lose work. This lesson is mostly about habits rather than commands, because
the commands are three and the habits are what make you easy to work with.

## Why this matters in a job

Because this is what your first week looks like, and because how you take a code
review is noticed considerably more than the code you submitted.

## The flow, in five commands

```bash [Terminal]
git switch -c fix/applicant-count            # a branch, named for the change
# ...work, commit in small pieces...
git push -u origin fix/applicant-count
# open a pull request
# ...review, changes, approval...
# merge, and the branch is deleted
```

::feature-list{columns="2"}
  :::feature{icon="i-lucide-git-branch" title="One branch, one change"}
  `fix/applicant-count`, not `swarnil-work`. If you cannot name the branch for
  one change, it is two branches.
  :::
  :::feature{icon="i-lucide-scissors" title="Small commits"}
  Each one doing one thing, with a message that says why. If something has to
  be undone later, this is what makes it possible.
  :::
  :::feature{icon="i-lucide-refresh-cw" title="Update from main regularly"}
  A branch that has not seen `main` for two weeks is a merge conflict with a
  date on it.
  :::
  :::feature{icon="i-lucide-trash-2" title="Delete it after merging"}
  A repository with ninety stale branches is one nobody can navigate.
  :::
::

## The pull request

It is an email to a reviewer, and the shape is the one from the English track:
what and why first, detail underneath.

```markdown [pull-request.md]
## Count applicants rather than applications on the dean's dashboard

The intake total read 2,040 where the registrar's own figure was 1,602. The
dashboard counted rows in `Application`, and one applicant can hold three, so
anybody applying to several programmes was counted several times.

Counting `DISTINCT applicant_id` now. Both numbers are legitimate and mean
different things, so the label says which: "1,602 applicants, 2,040
applications".

### What to look at
- `ApplicationRepository.countForIntake` — the query change
- The label in `DashboardSummary.vue`, which is arguably the real fix

### What I am unsure about
Whether withdrawn applications should be in either number. I have left them in
to match the registrar's current report, and it may be wrong.

### How I tested
Added a test with one applicant holding three applications. Checked the
dashboard against the registrar's report for the 2024 and 2025 intakes; both
match now.

Reported by the registrar's office, 12 March.
```

::pull-quote
"What I am unsure about" is the most valuable section and almost nobody writes
it. It directs the reviewer's attention to where it is worth most, and it makes
you far easier to review.
::

::warning{icon="i-lucide-alert-triangle"}
A 2,000-line pull request does not get reviewed. It gets approved, because
nobody can hold it in their head and nobody wants to be the person blocking it
for three days. Four hundred lines is roughly the limit of a genuine review.
Splitting a large change into three reviewable ones is more work for you and is
the difference between being reviewed and being rubber-stamped.
::

## Receiving a review

The part that is actually being assessed in your first months.

::compare{caption="The same comment: 'Why not use a Map here?'"}
  :::compare-side{label="Defensive" verdict="wrong"}
  "The list works fine, it is only 40,000 records."

  Technically true, dismissive of the point, and it closes a conversation the
  reviewer opened for a reason. Do this three times and people stop commenting,
  which feels like winning and is not.
  :::
  :::compare-side{label="Curious" verdict="right"}
  "Good point — `contains` on a list is O(n), so that loop is O(n²). I will
  switch it. Is there a reason to prefer `LinkedHashMap` here, or is ordering
  irrelevant?"

  You understood it, acted, and asked a follow-up. That exchange is how a
  reviewer decides you are worth spending time on.
  :::
::

And when you disagree, which you sometimes should:

```text [Disagreeing well]
"I thought about that and chose the list deliberately: the collection is built
once and only iterated, never searched, so the hash overhead would cost more
than it saves. Have I missed a place where we search it?"
```

Reasoning, a reason, and a question. Not "no".

## Giving a review

You will be asked to review within a few months, and most people are bad at it.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-message-circle-question" title="Ask, do not instruct"}
  "What happens if `applications` is empty?" beats "handle the empty case". The
  question makes them find it, which they will remember.
  :::
  :::feature{icon="i-lucide-tag" title="Say what is optional"}
  Prefix with `nit:` for preferences. Without it, every comment reads as
  blocking and a small suggestion costs a day.
  :::
  :::feature{icon="i-lucide-thumbs-up" title="Say what is good"}
  "This test is exactly the case I would have missed." Reviews that are
  exclusively criticism make people defensive, and it costs nothing to be
  accurate about the good parts.
  :::
  :::feature{icon="i-lucide-x" title="Do not review formatting"}
  That is a linter's job. A human review spent on spacing is a human review not
  spent on the off-by-one.
  :::
::

## Continuous integration

A pipeline that runs on every push, before a human looks.

```yaml [.github/workflows/ci.yml]
name: CI
on: [push, pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          cache: maven
      - run: mvn --batch-mode verify        # compile, test, package
      - run: mvn --batch-mode checkstyle:check
```

::pull-quote
CI does not find bugs. It removes an entire category of conversation: "does it
compile", "do the tests pass", "is it formatted". A reviewer arrives already
knowing the answer to all three and can spend their attention on whether the
change is right.
::

Four things worth having in a pipeline, in order of value:

::flow{numbered direction="vertical" caption="Each one removes a question a human would otherwise have to ask."}
  :::flow-step{label="It compiles" icon="i-lucide-hammer"}
  Sounds trivial, catches the file somebody forgot to commit constantly.
  :::
  :::flow-step{label="The tests pass" icon="i-lucide-check-check" highlight}
  On a clean machine, with no local state. This is where "works on my machine"
  dies.
  :::
  :::flow-step{label="The linter is happy" icon="i-lucide-list-checks"}
  So no review comment is ever about a space.
  :::
  :::flow-step{label="It builds the artefact" icon="i-lucide-package"}
  The jar, the container image. Finding out at deploy time that the build is
  broken is finding out late.
  :::
::

::tip
The one rule that keeps a pipeline useful: **a red build gets fixed before
anything else**. A team that tolerates a failing build for two days has thrown
the whole thing away, because everybody starts ignoring the result. Reverting
your change to make the build green and then fixing it properly is normal,
correct, and not an embarrassment.
::

## What you can do now

You can work on a shared codebase without losing anybody's work, write a pull
request somebody wants to review, and take a review in a way that makes people
want to keep reviewing you.

## Your turn

Do this properly on your own project, even though you are alone.

1. Branch for the next change you make.
2. Small commits, messages that say why.
3. Open a pull request against your own `main`, and write the full description
   including "what I am unsure about".
4. Add a CI workflow that runs your tests.
5. Break a test deliberately, push, and watch it go red.

::accordion
  :::accordion-item{label="Why do this alone, when there is nobody to review you" icon="i-lucide-help-circle"}
  Three reasons, and the third is the one that matters.

  **The habit forms now**, so in your first week you are not learning git flow
  and a codebase at the same time.

  **Writing the description finds things.** Explaining what you changed and why
  makes you notice the case you did not handle, reliably. I find something in
  about one description in four.

  **It is visible.** "Show me your GitHub" is a common request, and a repository
  with real pull requests, real descriptions and a green CI badge is startlingly
  rare from a fresher. It says more about how you would be to work with than the
  code does, because the code could have been generated and the process could
  not.
  :::
::

## Check yourself

1. Why does a 2,000-line pull request get approved rather than reviewed?
2. **An interviewer asks: "how do you handle a code review comment you disagree
   with?"**

## The interview question this answers

**"Tell me about your experience working in a team"** — hard for a fresher, and
this is the answer.

You do not need employment to have the habits: one branch per change, small
commits with messages that say why, pull requests with a description that names
what you are unsure about, and CI that runs the tests before anybody looks.

Then the review question, where what is being tested is whether you argue to win:
the answer is to restate the reasoning, give the reason you chose otherwise, and
ask a question. And say that you take the comment when the reviewer is right,
which they often are.
