Four hundred lines of your own code and forty thousand lines of somebody else's.
Every tool in this track exists because of one problem, and knowing which makes
the whole category stop being arbitrary.

## Why this matters in a job

Because on day one you will be handed a repository and told to run it, and the
difference between fifteen minutes and two days is knowing what these files are.

## The four problems

::feature-list{columns="2"}
  :::feature{icon="i-lucide-package" title="Somebody already wrote this"}
  You need to parse JSON, connect to PostgreSQL, hash a password. A **package
  manager** fetches those and their dependencies. npm, Maven, pip.
  :::
  :::feature{icon="i-lucide-lock" title="It must be the same everywhere"}
  Your machine, your colleague's, the build server. A **lock file** records the
  exact version of every package, including the ones you never asked for.
  :::
  :::feature{icon="i-lucide-cog" title="Source is not what ships"}
  TypeScript to JavaScript, many files to few, modern syntax to what old
  browsers understand. A **build tool**: Vite, Maven, Gradle.
  :::
  :::feature{icon="i-lucide-container" title="It works on my machine"}
  Different Java version, different database, a missing environment variable. A
  **container** packages the whole environment, and from the operating systems
  track you already know it is a process tree sharing the host's kernel.
  :::
::

## The lock file, which people delete

```json [package.json]
{ "dependencies": { "express": "^4.18.0" } }
```

`^4.18.0` means "4.18.0 or any later 4.x". So `npm install` today and in six
months give you different code, and a bug that appears only on the build server
is frequently this.

```json [package-lock.json]
{
  "node_modules/express": {
    "version": "4.18.2",
    "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
    "integrity": "sha512-5/PsL6iGPdfQ/lKM1UuielYgv3BUoJfz1aUwU9vHZ+J7gyvwdQXFEBIEIaxeGf0GIcreATNyBExtalisDbuMqQ=="
  }
}
```

The lock file pins the exact version **and its checksum**, for every package and
every package they depend on. Commit it. Never edit it by hand.

::warning{icon="i-lucide-alert-triangle"}
"It failed on the build server so I deleted the lock file and it worked" is a
real and common sequence, and what actually happened is that you silently
upgraded every transitive dependency in the project. If the versions genuinely
need to change, change them deliberately and read what moved.
::

## The dependency question nobody asks

Adding a package is a decision with a cost that arrives later.

```bash [Terminal]
npm install left-pad
```

```text [Output]
added 1 package
```

```bash [Terminal]
npm install some-ui-kit
```

```text [Output]
added 1,247 packages
```

::pros-cons
---
title: Adding a dependency
pros:
  - Somebody solved it, tested it, and handles the edge cases you have not thought of
  - Security fixes arrive without you doing anything
  - Writing your own date library or password hasher is how vulnerabilities are created
cons:
  - You now run their code with your permissions, and their dependencies too
  - It may be abandoned, or acquired by somebody with different intentions
  - Every package is a supply-chain risk and a build-time cost
  - A package you use for one function is a large amount of surface for one function
---
::

::flow{numbered direction="vertical" caption="Four questions, thirty seconds, before every install."}
  :::flow-step{label="When was it last updated?" icon="i-lucide-calendar"}
  Three years and open issues means you own it now.
  :::
  :::flow-step{label="How many dependencies does it bring?" icon="i-lucide-network" highlight}
  `npm info <package> dependencies`. One package can add a thousand, and you are
  responsible for all of them.
  :::
  :::flow-step{label="Could I write this in twenty lines?" icon="i-lucide-pencil"}
  Then write the twenty lines. Not for cryptography, dates or anything with
  edge cases, and yes for "capitalise a string".
  :::
  :::flow-step{label="What happens if it disappears?" icon="i-lucide-alert-triangle"}
  A package being unpublished has broken the internet's builds before. The lock
  file's checksum plus a private registry mirror is the real answer at scale.
  :::
::

::side-note{kind="security"}
The specific attack to know about: **typosquatting**. `expres` instead of
`express`, `reqeusts` instead of `requests`, published deliberately with a
post-install script that reads your environment variables. Read the package name
twice before installing, and be especially careful when copying an install
command out of a blog post or a model's output.
::

## Semantic versioning, read correctly

```text [4.18.2]
  4  MAJOR  — breaking. Reading the changelog is not optional.
 18  MINOR  — new features, backwards compatible.
  2  PATCH  — bug and security fixes only.
```

| Range | Accepts | Use for |
| --- | --- | --- |
| `4.18.2` | exactly that | Anything where surprises are unacceptable |
| `~4.18.2` | patches: 4.18.x | Conservative and sensible |
| `^4.18.2` | minor and patch: 4.x.x | The default. Fine **because** of the lock file. |
| `*` | anything | Never |

::note
`^` is safe in `package.json` **only because** the lock file pins the resolved
version. The range says what you would accept; the lock file says what you
actually got. That pair is the whole design, and it is why deleting the lock file
is such a destructive thing to do casually.
::

## Scripts, which are the interface to the project

```json [package.json]
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest run",
    "lint": "eslint .",
    "db:migrate": "node scripts/migrate.mjs"
  }
}
```

::tip
Every project should be runnable with `install`, then `dev`, then `test`, and a
README that says so in three lines. If a new joiner needs to be told six extra
steps verbally, those six steps belong in a script. Writing that script in your
first week is the highest-value contribution a new joiner can make, because the
existing team has forgotten what is hard.
::

## What you can do now

You can read a `package.json`, explain what a lock file prevents, and evaluate a
dependency before adding it rather than afterwards.

## Your turn

Open any project you have and answer:

1. How many direct dependencies, and how many total?
2. Which was last published more than two years ago?
3. Which could you remove by writing twenty lines?

```bash [Terminal]
npm ls --depth=0 | wc -l          # direct
npm ls --all | wc -l              # everything
npm outdated
npm audit
```

::accordion
  :::accordion-item{label="What the numbers usually look like, and what to do" icon="i-lucide-search"}
  A typical small project: 15 direct dependencies, 900 total. That ratio
  surprises people and it is normal.

  `npm audit` will report vulnerabilities. Read them rather than running
  `--force`, which upgrades across major versions and can break your build to
  fix a vulnerability in a package used only at build time.

  **The judgement worth developing:** a vulnerability in a build-time tool is not
  the same as one in code that serves requests. "Prototype pollution in a
  development-only linter plugin" is not a production incident, and being able to
  say that calmly rather than either panicking or ignoring it is a genuinely
  useful skill.
  :::
::

## Check yourself

1. What does a lock file prevent, and what happens when somebody deletes it?
2. **An interviewer asks: "how do you decide whether to add a library?"**

## The interview question this answers

**"How do you manage dependencies?"**

Lock files committed so every machine resolves identically; version ranges
understood, with `^` safe only because the lock file pins the result; and a
deliberate decision before each addition rather than after.

Then the four questions — last updated, how many it brings, could I write it,
what if it vanishes — and the security note about typosquatting. Very few
freshers treat adding a package as a decision at all, which is exactly why saying
so lands.
