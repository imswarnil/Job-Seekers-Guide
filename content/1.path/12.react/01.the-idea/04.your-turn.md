Six questions about the component model. These six are the bugs, and four of
them are the same mistake: treating state as though it were a variable.

## 1. The state that does not update

```jsx
function Pipeline() {
  const [apps, setApps] = useState([])

  function shortlist(id) {
    apps.find(a => a.id === id).status = "SHORTLISTED"
    setApps(apps)
  }
}
```

Nothing re-renders.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Two bugs, and they are the same bug.

  The array was **mutated in place**, then handed back. React compares the old
  and new values by reference, sees the same array, and concludes nothing
  changed.

  ```jsx
  setApps(apps.map(a =>
    a.id === id ? { ...a, status: "SHORTLISTED" } : a
  ))
  ```

  A new array, and a new object for the changed row. Everything else keeps its
  identity, so only the one row re-renders.

  **Never mutate state.** The methods that mutate are `push`, `pop`, `splice`,
  `sort`, `reverse` and direct assignment. The ones that return something new
  are `map`, `filter`, `concat`, `slice` and spread.
  :::
::

## 2. The counter that is one behind

```jsx
function shortlistTwo() {
  setCount(count + 1)
  setCount(count + 1)
}
```

Goes up by one.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `count` is captured from this render. Both lines compute the same value, so
  the second overwrites the first with an identical number.

  ```jsx
  setCount(c => c + 1)
  setCount(c => c + 1)
  ```

  The updater form receives the latest value, so they queue correctly.

  The rule: **if the next state depends on the current state, use the function
  form.** Not sometimes. Always, because you cannot reliably tell when a batch
  will happen.
  :::
::

## 3. The effect that never stops

```jsx
useEffect(() => {
  fetch("/api/applications").then(r => r.json()).then(setApps)
})
```

The network tab fills with requests.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  No dependency array, so the effect runs after **every** render. It fetches,
  sets state, causes a render, fetches again.

  ```jsx
  useEffect(() => {
    let cancelled = false
    fetch("/api/applications")
      .then(r => { if (!r.ok) throw new Error(r.status); return r.json() })
      .then(d => { if (!cancelled) setApps(d) })
      .catch(e => { if (!cancelled) setError(e) })
    return () => { cancelled = true }
  }, [])
  ```

  Three things. The `[]` means "once, on mount". The `cancelled` flag and the
  cleanup function stop a state update on a component that has already
  unmounted, which is the warning everybody sees and ignores. And `r.ok`,
  because `fetch` does not reject on a 404.
  :::
::

## 4. The list that loses what you typed

```jsx
{applications.map((a, i) => <Row key={i} application={a} />)}
```

Filtering the list moves the text somebody was typing into the wrong row.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `key={i}` tells React "the item at position 2 is the same item as before".
  When the list is filtered or sorted, position 2 is now a different applicant,
  so React reuses the existing component and its internal state, and the
  half-typed note moves to somebody else's row.

  ```jsx
  {applications.map(a => <Row key={a.applicationId} application={a} />)}
  ```

  A stable identity that belongs to the data.

  The index is only safe when the list never reorders, never filters and never
  has items removed from the middle, which is a list you probably did not need
  keys for anyway.
  :::
::

## 5. The state that is really a calculation

```jsx
const [apps, setApps] = useState([])
const [shortlisted, setShortlisted] = useState(0)

useEffect(() => {
  setShortlisted(apps.filter(a => a.status === "SHORTLISTED").length)
}, [apps])
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `shortlisted` is not state. It is a value derived from state, and holding it
  separately creates two things that can disagree.

  ```jsx
  const shortlisted = apps.filter(a => a.status === "SHORTLISTED").length
  ```

  One line, no effect, no extra render, and it cannot go stale.

  The rule worth saying in an interview: **if it can be calculated from existing
  state, it is not state.** Most unnecessary `useEffect` calls in React
  codebases are this mistake, and removing them removes a whole class of bug.

  Only reach for `useMemo` if you have measured that the calculation is slow.
  Filtering 400 rows is not slow.
  :::
::

## 6. The input that will not type

```jsx
<input value={query} />
```

Typing does nothing.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `value` makes it controlled: React insists the displayed value is `query`. You
  type, the DOM changes, React re-renders it back to `query`, which never
  changed.

  ```jsx
  <input value={query} onChange={e => setQuery(e.target.value)} />
  ```

  Related and worth knowing: `value={applicant.phone}` where `phone` is `null`
  produces the "changing an uncontrolled input to controlled" warning, because
  React reads `null` as "uncontrolled". Use `value={applicant.phone ?? ""}`.

  Which is the null-versus-empty distinction from the SQL track, arriving in the
  interface. `null` means "we do not know", and an input box cannot display
  that, so somebody has to decide what it looks like.
  :::
::

## The pattern in four of the six

::pull-quote
State is not a variable. It is a value belonging to one render, plus a request
to render again. Bugs 1, 2, 5 and 6 are all the same misunderstanding wearing
different clothes.
::

## The checklist

::feature-list{columns="2"}
  :::feature{icon="i-lucide-copy" title="Never mutate"}
  New array, new object. `map`, `filter`, spread. If you typed `push` or `=`
  on something in state, that is the bug.
  :::
  :::feature{icon="i-lucide-key" title="Keys come from the data"}
  A stable id that belongs to the row, never the index, unless the list truly
  never changes order.
  :::
::
