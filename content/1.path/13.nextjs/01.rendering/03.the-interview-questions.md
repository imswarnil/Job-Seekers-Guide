description: Five questions about rendering and the server-client boundary, including the trap that costs a codebase the benefit it adopted the framework for.

kind: quiz

::accordion
  :::accordion-item{label="1. Client-side or server-side rendering?" icon="i-lucide-message-circle"}
  Three reasons for the server, and give all three: the first paint is content
  rather than an empty div, a crawler sees the page, and the data arrives in the
  first response instead of a second round trip after JavaScript has loaded.

  Then the honest cost: the server does work per request, so it needs to be
  running and it needs caching, where a static build does not.
  :::

  :::accordion-item{label="2. When does a component need `'use client'`?" icon="i-lucide-message-circle"}
  When it needs state, an effect, an event handler or a browser API. The test:
  does it need to react to the user, or remember something between renders? If
  not, it is a server component.

  Then the trap, which is the real question: `'use client'` is a **boundary**,
  not a file. Everything imported below it becomes client code, so putting it in
  a layout because an error told you to turns the whole application back into a
  client application and loses the benefit you adopted the framework for.
  :::

  :::accordion-item{label="3. What is hydration, and what can go wrong?" icon="i-lucide-message-circle"}
  React attaching to server-rendered HTML to make it interactive. Between
  arrival and hydration the page looks ready and is not, which is why a button
  can appear and do nothing on a slow connection.

  The failure to name is a **mismatch**: the server rendered one thing and the
  client rendered another, usually because of `Date.now()`, `Math.random()` or
  reading `localStorage` during render. The fix is to make render deterministic
  and move the varying part into an effect.
  :::

  :::accordion-item{label="4. How do you mutate data?" icon="i-lucide-message-circle"}
  A server action: a function that runs on the server, called from a real
  `<form>`, so it works without JavaScript and is upgraded to a fetch when the
  script loads. One piece of code, both paths.

  Then the part that is actually being checked: a server action is a real HTTP
  endpoint whether or not it looks like one. Authenticate, authorise, validate,
  and never assume the form is the only caller.
  :::

  :::accordion-item{label="5. My data changed and the page did not. Why?" icon="i-lucide-message-circle"}
  Caching, and it is the most confusing thing about the framework for somebody
  new to it. Call `revalidatePath` or `revalidateTag` after a mutation, or mark
  a page `force-dynamic` if it must never be cached.

  And the detail worth adding, because it wastes real hours: caching behaves
  differently in development from production, so "it works locally" is not
  evidence.
  :::
::
