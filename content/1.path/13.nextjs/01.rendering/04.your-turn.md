Five questions about rendering. These five are the decisions, one per screen of
the University Management App, and one of them is a security question wearing a
performance costume.

::note
For each: decide where it renders and why, before opening the answer. The
reasoning is the point; several have more than one defensible choice.
::

## 1. The programmes page

`/programmes` lists twelve programmes with seats and cutoffs. Changes perhaps
twice a year. Must be findable by a search engine.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Static, rebuilt when the data changes.** Rendered once at build time and
  served as a file.

  Why: it is the same for everybody, it changes twice a year, and a search
  engine must see the content. Rendering it per request would mean a database
  query for every visitor to produce identical output.

  ```jsx
  export const revalidate = 3600   // or rebuild on a webhook when seats change
  ```

  The trap worth naming: seats and cutoffs feel dynamic because they are
  numbers, and "it might change" is not the same as "it changes per request".
  :::
::

## 2. The student's attendance

`/me/attendance` shows one student their own attendance. Confidential. Must be
current.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Server-rendered, per request, never cached.**

  Why: it is different for every user, it must be current, and it is
  confidential. That last one is the important part and the reason this question
  exists.

  The trap: caching it. A shared cache keyed by URL would serve one student's
  attendance to the next student who opens `/me/attendance`, and that is not a
  performance bug, it is a data breach.

  ```jsx
  export const dynamic = "force-dynamic"
  ```

  And the authorisation happens on the server, where a student cannot reach it,
  with the row-level policies as the backstop.
  :::
::

## 3. The admissions dashboard

`/admin` shows the funnel counts across 4,000 applications. Several staff open
it all day. Numbers do not need to be up to the second.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Server-rendered with a short revalidation window.**

  ```jsx
  export const revalidate = 60
  ```

  Why: the query aggregates thousands of rows, several people refresh it
  constantly, and nobody in an admissions meeting needs a sixty-second-old
  number to be fresher.

  The judgement to state out loud: I asked whether one minute stale was
  acceptable rather than assuming. If the registrar is watching a number move
  during a live decision, the answer changes and I would render it per request
  with the aggregation moved into a materialised view.

  And it is cached **per role**, not globally, because the admin funnel and a
  reviewer's view are different data.
  :::
::

## 4. The applicant search

An admin types into a box and the list filters across 4,000 applications.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Client-side interaction, server-side filtering.**

  The typing is instant and local, so the input must be a client component.
  The filtering is a database query, because sending 4,000 rows to the browser
  to filter them there is slow on a phone and sends data the person may not be
  allowed to see.

  So: a client component for the input, debounced by about 300ms, updating a
  URL search parameter, which the server component reads and queries with.

  Two benefits from the URL rather than local state: the filtered view is
  shareable and bookmarkable, and the back button works. Both are things people
  notice when missing and never mention when present.
  :::
::

## 5. The enquiry form

`/enquire`, public, one write, on a phone, often on a slow connection.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Static shell, server action for the submit.**

  The form itself never changes, so it is static and arrives instantly. The
  submission goes to the server, which does the real validation and the insert.

  The part that separates a good answer: **it must work before JavaScript
  loads.** A plain `<form action={...}>` posts natively if the bundle has not
  arrived, and progressively enhances when it has. On a bad connection that is
  the difference between an enquiry and a bounce.

  And the validation on the server is not a duplicate of the client's. The
  client's is a kindness; this is the only one that decides what enters the
  database.
  :::
::

## The decision, in one table

| The data is | It renders |
| --- | --- |
| Same for everyone, changes rarely | Static |
| Same for everyone, changes often | Server, short revalidate |
| Different per user, confidential | Server, per request, uncached |
| Responds to typing or dragging | Client, on top of server-rendered data |

::warning{icon="i-lucide-alert-triangle"}
The question that decides more than performance: **is this the same for every
user?** If not, it must not be in a shared cache, and getting that wrong is not
a slow page. It is one person seeing another person's data.
::

## The habit

::pull-quote
Render on the server by default and move to the client only for the specific
piece that needs to respond to a person. "Client component" should be a decision
about one input box, not about a page.
::
