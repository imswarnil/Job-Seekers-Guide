A file is not its name. To the kernel, a file is an **inode**: a numbered
record holding the file's size, owner, permissions, timestamps and the
locations of its data on disk. The name lives somewhere else entirely, in a
directory, which is itself a small file mapping names to inode numbers.

## Why this matters in a job

"What is an inode?", "hard link versus soft link?" and "what does a file system
do?" are the file-system questions freshers get, and the inode answer is the one
that sounds like you understand it rather than recited it. At work, it explains
a real and common production mystery: you delete a 20 GB log file and the disk
is still full.

## A name is only a pointer

Think of the college admissions office. Every applicant has a file in the
cabinet with a number on it: 4817. That file holds everything: marks,
documents, fee status. Separately, there is an index card box sorted by name:
"Asha Rao → 4817". The card is not the file. You can have two cards pointing at
4817 ("Asha Rao" and "A. Rao"). Throw away one card and the file is still there.
Only when no card points at 4817 does the file go to the shredder.

The index cards are **directory entries**. The numbered files are **inodes**.

| An inode holds | An inode does NOT hold |
| --- | --- |
| File type (regular, directory, link) | **The file's name** |
| Size in bytes | The path to it |
| Owner (uid) and group (gid) | |
| Permission bits | |
| Timestamps: modified, accessed, changed | |
| **Link count**: how many names point at it | |
| Pointers to the data blocks on disk | |

A **directory** is a file whose contents are a list of (name, inode number)
pairs. Opening `/home/asha/marks.csv` means: read the root directory, find
`home`'s inode, read that directory, find `asha`, read it, find `marks.csv`'s
inode number, read the inode, then read the data blocks.

### Hard links and symbolic links

::compare{caption="Two kinds of second name, and they fail differently."}
  :::compare-side{label="Hard link" verdict="neutral"}
  A second directory entry pointing at the **same inode**. Both names are equally
  real; neither is "the original". The link count goes to 2. Delete either name
  and the file survives. Cannot cross file systems, and normally cannot point at
  a directory.
  :::
  :::compare-side{label="Symbolic (soft) link" verdict="neutral"}
  A tiny separate file whose content is a **path**. Like a Windows shortcut.
  Can point anywhere, including directories and other disks. If the target is
  moved or deleted, the link is left **dangling** and fails.
  :::
::

### Directory structures, briefly

Textbooks list them in order of generality: **single-level** (one directory for
everybody, names clash), **two-level** (one directory per user), **tree**
(directories inside directories, what you use every day), and **acyclic graph**
(a tree plus links, so one file can appear in two places). A general graph
would allow cycles, which is why hard links to directories are forbidden.

## How it works

`ls -i` shows the inode number, and `stat` shows the whole inode:

```bash [Terminal]
echo "roll,marks" > marks.csv
ln marks.csv marks-backup.csv          # hard link: same inode
ln -s marks.csv marks-link.csv         # symbolic link: its own inode
ls -li marks*
```

```text [Output]
8812043 -rw-r--r--  2 asha  staff  11 Mar 12 09:14 marks-backup.csv
8812051 lrwxr-xr-x  1 asha  staff   9 Mar 12 09:14 marks-link.csv -> marks.csv
8812043 -rw-r--r--  2 asha  staff  11 Mar 12 09:14 marks.csv
```

`marks.csv` and `marks-backup.csv` have the same inode number (8812043) and a
link count of **2**. The symbolic link has its own inode and is 9 bytes long:
the nine characters of `marks.csv`. Now delete the original name:

```bash [Terminal]
rm marks.csv
cat marks-backup.csv
cat marks-link.csv
```

```text [Output]
roll,marks
cat: marks-link.csv: No such file or directory
```

The hard link still reads the data: the inode's link count dropped to 1, not 0.
The symbolic link points at a name that no longer exists.

The same from Java, where the inode number appears as the `fileKey`:

```java [InodeInfo.java]
import java.nio.file.*;
import java.nio.file.attribute.BasicFileAttributes;

public class InodeInfo {
  public static void main(String[] args) throws Exception {
    Path original = Path.of("attendance.csv");
    Files.writeString(original, "roll,present\n");
    Path link = Path.of("attendance-link.csv");
    Files.deleteIfExists(link);
    Files.createLink(link, original);                  // a hard link

    for (Path p : new Path[] {original, link}) {
      BasicFileAttributes a = Files.readAttributes(p, BasicFileAttributes.class);
      System.out.println(p + "  size=" + a.size() + "  key=" + a.fileKey());
    }
    System.out.println("Links: " + Files.getAttribute(original, "unix:nlink"));
  }
}
```

```text [Output, on Linux or macOS]
attendance.csv  size=13  key=(dev=1000004,ino=8812077)
attendance-link.csv  size=13  key=(dev=1000004,ino=8812077)
Links: 2
```

Same device, same inode: one file, two names.

## Real use case

::real-life{title="The log file that was deleted and still filled the disk" source="A production incident"}
A server's disk hit 100%. Somebody found a 20 GB log file and deleted it. `df`
still said 100%. The application still had the file open, and an open file
descriptor counts as a reference to the inode. The name was gone, the inode's
link count was 0, but the kernel does not free the blocks while any process
holds the file open. The space came back only when the application was
restarted.
::

The command that finds exactly this:

```bash [Terminal]
# Files that are deleted (link count 0) but still held open by a process.
sudo lsof +L1
```

```text [Output]
COMMAND   PID  USER  FD  TYPE DEVICE     SIZE/OFF NLINK    NODE NAME
java     4180  app   14w  REG  259,1  21474836480     0 1311022 /var/log/results/app.log (deleted)
```

The fix without a restart is to truncate the file through the open descriptor
(`: > /proc/4180/fd/14`) rather than delete it, and the lesson for next time is
to rotate logs with a tool that tells the application to reopen its file.

## What confuses people here

That deleting a file deletes the file. `rm` removes **a name**: it deletes one
directory entry and decrements the inode's link count. The data is freed only
when the link count is 0 **and** no process has it open. This is also why you can
delete a program's executable while it is running, and why "undelete" tools
sometimes work.

## Interview questions

::accordion
  :::accordion-item{label="What is an inode?" icon="i-lucide-message-circle"}
  The on-disk record for a file in Unix-like file systems: type, size, owner,
  group, permissions, timestamps, link count and pointers to the data blocks.
  Everything except the name, which lives in the directory entry that points at
  the inode number.
  :::

  :::accordion-item{label="What is the difference between a hard link and a soft link?" icon="i-lucide-message-circle"}
  A hard link is another directory entry for the same inode: equally real,
  survives deletion of the other name, same file system only, not for
  directories. A soft (symbolic) link is a separate small file containing a
  path: can cross file systems and point at directories, but dangles if the
  target moves or is deleted.
  :::

  :::accordion-item{label="What are the functions of a file system?" icon="i-lucide-message-circle"}
  Naming and organising files in directories; mapping files to disk blocks
  (allocation); tracking free space; storing metadata; enforcing permissions;
  and providing operations: create, open, read, write, seek, close, delete,
  rename. Examples: ext4 and XFS on Linux, NTFS on Windows, APFS on macOS,
  FAT32 on USB drives.
  :::

  :::accordion-item{label="You delete a large file but the disk space is not freed. Why?" icon="i-lucide-message-circle"}
  A process still has it open. Deleting removes the name; the inode and blocks
  are freed only when the link count is zero and no file descriptor refers to
  it. `lsof +L1` lists such files; restarting the process or truncating the file
  through its descriptor frees the space.
  :::
::
