You are a number. Not a name: the kernel knows you as a **user id**, and every
permission decision on the machine is arithmetic on three small numbers.

## Why this matters in a job

"How do file permissions work in Linux?" and "what does chmod 755 mean?" are asked
in operating systems and Linux rounds alike. And the first hour of your first
deployment will involve a permission error, because "the application cannot write to that directory" is one of the most
common production failures there is. It is also the model that row-level security
in a database and file permissions in a cloud bucket are both copied from.

## The three questions

Think of the college staff room. The locker with your name on it opens with your
key. The department cupboard opens for anyone in the department. The notice
board is for everybody. When you walk up to something, the only question that
matters is which of those three you are to it.

The real thing: every inode stores an owner (a user id), a group (a group id),
and three sets of permission bits.

When your program asks to open a file, the kernel asks three questions in order
and stops at the first one that matches.

::flow{numbered direction="vertical" caption="First match wins. This ordering produces one genuinely surprising result, below."}
  :::flow-step{label="Are you the owner?" icon="i-lucide-user"}
  If your user id equals the file's owner id, the **owner** bits decide. The
  group and other bits are not consulted at all.
  :::
  :::flow-step{label="Are you in the group?" icon="i-lucide-users"}
  If not the owner, but one of your groups is the file's group, the **group**
  bits decide.
  :::
  :::flow-step{label="Otherwise" icon="i-lucide-globe" highlight}
  The **other** bits decide. Everyone on the machine who is not the owner and not
  in the group.
  :::
::

## How it works

```bash [Terminal]
ls -l
```

```text [Output]
-rw-r--r--  1 swarnil  staff    4096 Mar 12 09:14 applicants.csv
drwxr-xr-x  5 swarnil  staff     160 Mar 12 09:10 exports
-rwx------  1 root     wheel    8192 Mar 01 11:22 reset-fees.sh
```

Take the first one apart.

::code-trace{caption="Ten characters, three groups of three, and one for the type."}
```text [Output]
-rw-r--r--  1 swarnil  staff  4096  applicants.csv
```

  :::code-trace-step{lines="1" caption="Character 1: the type. `-` is an ordinary file, `d` a directory, `l` a symbolic link. Not a permission at all."}
  :::
  :::code-trace-step{lines="1" caption="Characters 2 to 4, `rw-`: the OWNER may read and write, not execute. swarnil is the owner."}
  :::
  :::code-trace-step{lines="1" caption="Characters 5 to 7, `r--`: the GROUP, staff, may read only."}
  :::
  :::code-trace-step{lines="1" caption="Characters 8 to 10, `r--`: EVERYONE ELSE may read. On a shared machine, that is every user on it."}
  :::
::

The numeric form is the same thing in binary: read is 4, write is 2, execute is
1, added per group of three.

| Numeric | Means | Use it for |
| --- | --- | --- |
| `644` | Owner read+write, everyone read | An ordinary data file |
| `600` | Owner read+write, nobody else anything | A config file with a password in it |
| `755` | Owner everything, everyone read+execute | A script or a directory |
| `700` | Owner everything, nobody else anything | A private directory |
| `777` | Everyone everything | ⚠️ Almost never. See below. |

### The surprise

First-match-wins produces a result that catches everybody once.

```bash [Terminal]
# A file owned by you, where the group has more rights than you do.
chmod 044 fees.csv
ls -l fees.csv
cat fees.csv
```

```text [Output]
----r--r--  1 swarnil  staff  2048 Mar 12 fees.csv
cat: fees.csv: Permission denied
```

You own it. Your group can read it. You are in that group. And you cannot read
it, because the kernel matched on "owner" first, found `---`, and stopped. It
never looks at the group bits for the owner.

::side-note{kind="security"}
This is worth knowing because the same rule makes a common assumption false:
"the owner can always read their own file" is not true. It is also why you can
own a file you cannot read, which occasionally happens after a bad `chmod` and
looks like the file system is broken.
::

### What execute means on a directory

The one that produces the most confusing errors.

::compare{caption="On a directory, `r` and `x` mean different things and you usually need both."}
  :::compare-side{label="r without x" verdict="wrong"}
  You can **list** the names in the directory and cannot do anything with them.
  `ls exports` works; `cat exports/fees.csv` fails, even if that file is world
  readable.
  :::
  :::compare-side{label="x without r" verdict="neutral"}
  You can **traverse** it: reach a file inside if you already know its name, but
  `ls` gives you permission denied. This is how a shared parent directory is
  usually set up.
  :::
::


### What sudo actually does

Not "become an administrator". `sudo` runs one command as a different user,
normally root, after checking a configuration file that says you are allowed to.

```bash [Terminal]
id
sudo id
```

```text [Output]
uid=501(swarnil) gid=20(staff) groups=20(staff),12(everyone)
uid=0(root) gid=0(wheel) groups=0(wheel),1(daemon)
```

`uid=0` is what root means. Not a name the kernel respects, a number: user id
zero bypasses the permission checks entirely.

::warning{icon="i-lucide-alert-triangle"}
`chmod 777` is the most common way a beginner "fixes" a permission problem, and
it means every user and every process on the machine may read, write and execute
that file. On a server that is a genuine vulnerability, not a style issue. The
fix is almost always `chown` to the user that should own it, not `chmod` to let
everybody in.
::

## Real use case

::real-life{title="The deployment that could not write its logs" source="A first deployment, and everybody's"}
The application started, served requests, and logged nothing. The directory was
`drwxr-xr-x root root`, and the service ran as `appuser`. It had `r` and `x` on
the directory as "other", so it could list and traverse, and no `w`, so it could
not create a file. The application logged the failure to the log file it could
not create. The fix was `chown appuser:appuser /var/log/college`, and finding
it took two hours because the error had nowhere to go.
::

The diagnosis, as a sequence you can run on any server:

```bash [Terminal]
ps -o user= -p $(pgrep -f results-service)   # which user is the service?
ls -ld /var /var/log /var/log/college         # every directory in the path
id appuser                                    # which groups is that user in?
```

```text [Output]
appuser
drwxr-xr-x  14 root root   4096 Jan  3 10:12 /var
drwxrwxr-x  12 root syslog 4096 Mar 12 09:00 /var/log
drwxr-xr-x   2 root root   4096 Mar 12 09:10 /var/log/college
uid=998(appuser) gid=998(appuser) groups=998(appuser)
```

`appuser` is "other" on `/var/log/college`, and other has `r-x`: no `w`. The fix
is ownership, not `chmod 777`:

```bash [Terminal]
sudo chown appuser:appuser /var/log/college
```

## What confuses people here

That the owner can always read their own file. First match wins, so an owner
with `---` is locked out even when the group or everyone else may read. And
execute means something different on a directory (traverse) from on a file
(run): a permission error very often names the file you asked for when the
refusal was on a directory in its path.

## Your turn

Predict the outcome of each, then run them.

```bash [Terminal]
mkdir -p college/exports
echo "roll,marks" > college/exports/results.csv
chmod 644 college/exports/results.csv
chmod 600 college/exports
cat college/exports/results.csv
```

1. What happens on the last line, and why?
2. What is the smallest change that makes it work, without changing the file?
3. What would `chmod 000 college/exports/results.csv` do if you own it?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1. Permission denied.** The file is readable by everybody, and the
  *directory* lost its execute bit. Without `x` on a directory you cannot
  traverse into it to reach anything, whatever the file's own permissions say.
  A path check happens at every level, not only the last one.

  **2. `chmod 700 college/exports`**. You only need to put your own execute
  bit back. Note this is the recurring shape of real permission problems: the
  broken permission is on a directory in the path, not on the file named in the
  error.

  **3. Nothing you can read.** You own it, so the owner bits decide, and they are
  all zero. You would have to `chmod` it back first, which you are allowed to do
  because changing permissions is a property of ownership rather than of the
  permission bits.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="How do file permissions work on Linux?" icon="i-lucide-message-circle"}
  Three sets of bits (owner, group, other), each with read, write and execute,
  checked in that order with first match winning. Numeric form: read 4, write 2,
  execute 1, added per set. On a directory, read lists names, write creates and
  deletes entries, execute allows traversing into it.
  :::

  :::accordion-item{label="What do chmod 755 and chmod 644 mean?" icon="i-lucide-message-circle"}
  755: owner rwx (7), group r-x (5), other r-x (5), usual for scripts and
  directories. 644: owner rw- (6), group and other r-- (4), usual for data
  files. 600 is for secrets such as a config file with a password.
  :::

  :::accordion-item{label="Why is chmod 777 a bad fix?" icon="i-lucide-message-circle"}
  It lets every user and every process on the machine read, write and execute
  the file, which on a shared server is a genuine vulnerability. The right fix
  is `chown` to the user that needs access, or adding that user to the owning
  group.
  :::

  :::accordion-item{label="What does sudo do?" icon="i-lucide-message-circle"}
  Runs one command as another user, normally root (uid 0), after checking the
  sudoers configuration says you may. uid 0 bypasses the permission checks; it
  is a number, not a name, that the kernel treats specially.
  :::

  :::accordion-item{label="An application cannot write to a directory in production. How do you diagnose it?" icon="i-lucide-message-circle"}
  Find which user the process runs as (`ps -o user -p <pid>`), check `ls -ld`
  on the directory and every parent (execute is needed at each level), and `id`
  that user for its groups. Fix with `chown` or group membership, never
  `chmod 777`.
  :::
::
