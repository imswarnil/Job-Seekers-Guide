One fixed-size inode keeps track of four gigabytes by pointing at blocks that
point at more blocks. That is **indexed allocation**, the last of three ways a
file system can decide which disk blocks belong to a file. The other two are
simpler, and each fails in a way that explains the design of the third.

## Why this matters in a job

"Explain contiguous, linked and indexed allocation" is a standard file-system
question, and the inode maximum-file-size calculation (12 direct pointers, one
single, one double and one triple indirect) is a favourite written-round
numerical. At work, the same ideas explain why fragmentation slows a disk down,
why FAT32 USB drives cannot hold a file over 4 GB, and why databases
pre-allocate their files.

## Three ways to find a file's blocks

A disk, to the file system, is a long row of numbered blocks, typically 4 KB
each. Think of the college's bicycle stand with numbered slots, and a
department that needs to park thirty bicycles.

- **Contiguous:** park all thirty in slots 200 to 229. Finding any bicycle is
  instant. But you needed thirty free slots in a row, and if the department buys
  two more there may be no room next to them.
- **Linked:** park them anywhere, and tie a tag to each saying which slot the
  next one is in. Any free slot works. But to find the twentieth bicycle you
  walk from the first, one tag at a time.
- **Indexed:** park them anywhere, and keep one card listing all thirty slot
  numbers. Any free slot works, and you can go straight to the twentieth.

| Method | How the file's blocks are found | Good at | Bad at |
| --- | --- | --- | --- |
| **Contiguous** | Start block + length | Sequential and random access, both fast | External fragmentation; hard to grow a file |
| **Linked** | Each block holds a pointer to the next | No external fragmentation, easy to grow | Random access is slow (follow the chain); one bad pointer loses the rest of the file |
| **Indexed** | An index block lists all the file's blocks | No external fragmentation, fast random access | The index costs space; small files waste most of an index block |

**FAT** (file allocation table, used on USB drives and memory cards) is linked
allocation with the pointers moved out of the blocks and into one table at the
start of the disk, so the chain can be followed in memory. **Inodes** are
indexed allocation.

### The inode's pointers

An inode cannot list every block of a large file directly; it is a fixed size.
So the classic Unix inode holds 15 pointers:

::memory{kind="array" label="Pointers in one inode" caption="Twelve point at data. The last three point at blocks full of pointers."}
---
cells:
  - { value: "direct × 12", label: "pointers 0 to 11" }
  - { value: "single indirect", label: "pointer 12", state: "active" }
  - { value: "double indirect", label: "pointer 13" }
  - { value: "triple indirect", label: "pointer 14" }
---
::

The sum, with **4 KB blocks** and **4-byte block pointers**, so one block holds
4096 / 4 = **1,024 pointers**:

```text [Maximum file size]
direct:           12 × 4 KB                    =   48 KB
single indirect:  1,024 × 4 KB                 =    4 MB
double indirect:  1,024 × 1,024 × 4 KB         =    4 GB
triple indirect:  1,024 × 1,024 × 1,024 × 4 KB =    4 TB
                                        total  ≈    4 TB
```

The design is deliberate: most files are small, and a small file's blocks are
found straight from the inode with no extra reads. Only large files pay for
indirection. (ext4, the default Linux file system today, uses **extents**
instead: "blocks 5,000 to 9,000", a contiguous run recorded as start and length.
It is contiguous allocation, used in pieces.)

### Free-space management

The file system must also know which blocks are free:

- **Bitmap:** one bit per block, 1 for used, 0 for free. A 1 TB disk with 4 KB
  blocks needs 268 million bits, 32 MB, and finding a run of free blocks is fast.
- **Free list:** free blocks linked together, each pointing at the next. No
  extra space, slow to find contiguous runs.
- **Grouping and counting:** store "the next 200 blocks from 5,000 are free" as
  one entry.

## How it works

The maximum-file-size sum as a program, so you can change the block and pointer
sizes the way exam questions do:

```java [InodeSize.java]
public class InodeSize {
  public static void main(String[] args) {
    long block = 4096;                 // bytes per block
    long pointer = 4;                  // bytes per block address
    long perBlock = block / pointer;   // pointers that fit in one block

    long direct = 12 * block;
    long single = perBlock * block;
    long dbl    = perBlock * perBlock * block;
    long triple = perBlock * perBlock * perBlock * block;

    System.out.println("Pointers per block: " + perBlock);
    System.out.println("Direct:          " + human(direct));
    System.out.println("Single indirect: " + human(single));
    System.out.println("Double indirect: " + human(dbl));
    System.out.println("Triple indirect: " + human(triple));
    System.out.println("Maximum file:    " + human(direct + single + dbl + triple));
  }

  static String human(long bytes) {
    String[] units = {"B", "KB", "MB", "GB", "TB"};
    double v = bytes;
    int u = 0;
    while (v >= 1024 && u < units.length - 1) { v /= 1024; u++; }
    return String.format("%.2f %s", v, units[u]);
  }
}
```

```text [Output]
Pointers per block: 1024
Direct:          48.00 KB
Single indirect: 4.00 MB
Double indirect: 4.00 GB
Triple indirect: 4.00 TB
Maximum file:    4.00 TB
```

Change `block` to 1024 and it prints 256 pointers per block and a maximum of
about 16 GB: the typical variant of this question.

## Real use case

The allocation method decides real limits. FAT32 stores a file's size in a
32-bit field, so no file can exceed 4 GB, which is why copying a large lecture
recording onto an old USB drive fails with "file too large" while the drive shows
plenty of free space. Formatting it as exFAT or NTFS fixes it.

Databases fight fragmentation on purpose. They grow their data files in large
chunks and ask the file system to reserve the space up front, so the table's
pages are laid out contiguously:

```java [Preallocate.java]
import java.io.RandomAccessFile;

public class Preallocate {
  public static void main(String[] args) throws Exception {
    try (RandomAccessFile f = new RandomAccessFile("exam_results.dat", "rw")) {
      f.setLength(512L * 1024 * 1024);          // reserve 512 MB now, fill it later
      System.out.println("Reserved " + f.length() / (1024 * 1024) + " MB");
    }
  }
}
```

```text [Output]
Reserved 512 MB
```

## What confuses people here

That linked allocation has no fragmentation at all. It has no **external**
fragmentation (any free block can be used), but a file's blocks can be scattered
across the disk, so reading it sequentially on a spinning hard disk means a head
movement between blocks. That is what "defragmenting" used to fix: not wasted
space, but scattered placement. On an SSD, placement barely matters, which is
why nobody defragments SSDs.

## Interview questions

::accordion
  :::accordion-item{label="Explain contiguous, linked and indexed allocation." icon="i-lucide-message-circle"}
  Contiguous: each file occupies consecutive blocks (start + length); fast
  access, but external fragmentation and hard to grow. Linked: each block points
  to the next; no external fragmentation, but slow random access and fragile.
  Indexed: an index block holds all the file's block addresses; fast random
  access and no external fragmentation, at the cost of index space. Unix inodes
  are indexed; FAT is linked with a table.
  :::

  :::accordion-item{label="An inode has 12 direct, 1 single, 1 double and 1 triple indirect pointer. Blocks are 4 KB, pointers 4 bytes. Maximum file size?" icon="i-lucide-message-circle"}
  1,024 pointers per block. 12 × 4 KB + 1,024 × 4 KB + 1,024² × 4 KB + 1,024³ ×
  4 KB = 48 KB + 4 MB + 4 GB + 4 TB, about 4 TB.
  :::

  :::accordion-item{label="How is free space managed on a disk?" icon="i-lucide-message-circle"}
  A bitmap (one bit per block; compact and fast to search for runs), a linked
  free list (no extra space, slow), or grouping and counting (store runs of free
  blocks as start and length). Most modern file systems use bitmaps or
  extent-based trees.
  :::

  :::accordion-item{label="What is FAT?" icon="i-lucide-message-circle"}
  The file allocation table: a table with one entry per disk block holding the
  number of the next block in the file, or an end marker. It is linked
  allocation with the links kept in one table (which can be cached in memory),
  used by FAT32 and exFAT on removable drives.
  :::
::
