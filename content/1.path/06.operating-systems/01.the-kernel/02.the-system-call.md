The door is not free. Crossing from user mode into kernel mode and back is one of
the most expensive ordinary things a program does, and once you can see that
cost, a whole category of performance advice stops being folklore.

## Why this matters in a job

Because "read the file in blocks rather than a character at a time" is advice
everybody repeats and almost nobody can justify. The justification is this
lesson, and it generalises: the same reasoning explains why you batch database
writes, why you do not call an API in a loop, and why logging inside a tight loop
can dominate the runtime of a program.

## What a system call actually is

Think of the college office counter. You cannot walk into the records room and
pull out your own marksheet. You fill in a slip, hand it through the window, a
clerk checks it, fetches the file and passes a copy back. Every trip to the
window costs you a queue, whatever you asked for.

The real thing: your program cannot execute the instruction that talks to the disk. So it does
something else: it puts a number in a register saying which service it wants,
puts the arguments in more registers, and executes a special instruction that
**traps** into the kernel.

::flow{numbered direction="vertical" caption="One `read()`. Every step is real work, and it happens on every single call."}
  :::flow-step{label="Your program sets up the request" icon="i-lucide-edit"}
  Which file, where to put the bytes, how many. Cheap.
  :::
  :::flow-step{label="The trap instruction" icon="i-lucide-door-open"}
  The processor switches to kernel mode. Your program is suspended exactly where
  it is.
  :::
  :::flow-step{label="The kernel saves your state" icon="i-lucide-save"}
  Every register, so it can put you back exactly as you were. This is the part
  that costs.
  :::
  :::flow-step{label="The kernel does the work" icon="i-lucide-cog" highlight}
  Checks permissions, finds the data, copies it into your memory. If the data is
  not in memory yet, your program waits here for the disk, which is millions of
  times slower than everything above.
  :::
  :::flow-step{label="Restore and return" icon="i-lucide-undo"}
  Registers back, mode back to user, your program continues on the next line as
  though nothing happened.
  :::
::

That whole sequence costs on the order of one microsecond when nothing has to
wait for hardware. A microsecond sounds like nothing. Do it a million times and
it is a second of pure overhead, before any of your own work.

## How it works

A college attendance export with a million lines. Read it two ways.

```java [SlowRead.java]
// One system call per byte. The kernel door, a million times over.
try (FileInputStream in = new FileInputStream("attendance.csv")) {
  int b;
  long lines = 0;
  while ((b = in.read()) != -1) {     // unbuffered:: a read() syscall each time
    if (b == '\n') lines++;
  }
  System.out.println(lines + " lines");
}
```

```java [FastRead.java]
// The same work, with a buffer in front of it.
try (BufferedInputStream in =
         new BufferedInputStream(new FileInputStream("attendance.csv"), 8192)) {
  int b;
  long lines = 0;
  while ((b = in.read()) != -1) {     // reads from an 8 KB buffer in user memory
    if (b == '\n') lines++;
  }
  System.out.println(lines + " lines");
}
```

```text [Output, a 60 MB attendance export, same machine]
SlowRead   47.2 s
FastRead    0.38 s
```

The loop is identical. The counting is identical. The only difference is that the
second version crosses the kernel door **7,500 times instead of 60 million**,
because each crossing brings back 8,192 bytes instead of one.

::side-note{kind="performance"}
That is a 124× difference from one wrapper class, and it is the single cheapest
performance win in the language. It is also the reason `BufferedReader` exists
and why every tutorial tells you to use it without explaining why.
::

### Counting the doors yourself

You do not have to take my word for it. Linux and macOS will both show you every
system call a program makes.

::tabs
  :::tabs-item{label="Linux" icon="i-simple-icons-linux"}
  ```bash [Terminal]
  strace -c -e trace=read java SlowRead
  ```

  ```text [Output]
  % time     seconds  usecs/call     calls    errors syscall
  ------ ----------- ----------- --------- --------- ----------------
   99.87   41.203881           0  60174213           read
  ```
  :::

  :::tabs-item{label="macOS" icon="i-lucide-command"}
  ```bash [Terminal]
  sudo dtruss -c java SlowRead
  ```

  `dtruss` needs `sudo` because it is inspecting another process, which is
  exactly the kind of thing the kernel does not hand out freely. On recent macOS
  you may also need to disable System Integrity Protection, which is not worth
  doing for this exercise, read the Linux output above instead.
  :::
::

Sixty million calls in the first column. That number is the lesson.

## Real use case

The same arithmetic, one layer up. Saving a term's attendance for 3,000 students
into a database one row at a time crosses the network and the database's own
boundary 3,000 times. JDBC batching turns that into a handful of crossings:

```java [SaveAttendance.java]
String sql = "INSERT INTO attendance (student_id, course_id, present) VALUES (?, ?, ?)";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
  for (Attendance a : todaysAttendance) {
    ps.setLong(1, a.studentId());
    ps.setLong(2, a.courseId());
    ps.setBoolean(3, a.present());
    ps.addBatch();                    // queue it in user memory
  }
  int[] rows = ps.executeBatch();     // one round trip for the lot
  System.out.println("Saved " + rows.length + " rows");
}
```

```text [Output]
Saved 3000 rows
```

Salesforce, which is where I ended up at Accenture, is built around the same
idea: records are saved in batches of up to 200 at a time, and code that saves
them one by one inside a loop hits the platform's limits within a day. Different system, same door.

## What confuses people here

That this is about files. It is about **any crossing of a boundary**, and the
same arithmetic appears at every layer of the stack you will ever work on.

::compare{caption="The same mistake, three layers apart."}
  :::compare-side{label="One at a time" verdict="wrong"}
  A `read()` per byte. An `INSERT` per applicant. An HTTP request per row. Each
  one crosses a boundary that costs far more than the work being done inside it.
  :::
  :::compare-side{label="In batches" verdict="right"}
  8 KB per `read()`. One `INSERT` with a thousand rows. One request carrying the
  whole page. The work is identical; the number of crossings is not.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
The opposite mistake exists and is rarer: an enormous buffer. Reading a 60 MB
file into one 60 MB buffer works and then fails on the 6 GB file somebody imports
next year. 8 KB to 64 KB is the sensible range and the defaults are usually
right.
::

## Your turn

Predict, then measure. Which of these crosses the kernel door most often, and
roughly how many times each?

1. Printing a million lines with `System.out.println` inside a loop.
2. The same million lines built into one `StringBuilder` and printed once.
3. Reading a 10 MB file with `Files.readAllBytes`.

::accordion
  :::accordion-item{label="Answers, and the one that surprises people" icon="i-lucide-check"}
  **1. About a million.** `System.out` is line-buffered when attached to a
  terminal, so each `println` flushes. This is why a program that prints a lot
  is dominated by printing, and why removing debug output can make something ten
  times faster.

  **2. A handful.** One large write at the end. The catch is memory: a million
  lines in a `StringBuilder` is real memory, so this trades one problem for
  another. `BufferedWriter` is the version that does neither.

  **3. A few thousand.** `readAllBytes` reads in large chunks internally. It is
  also the one to be careful with for a different reason: a 6 GB file becomes a
  6 GB array, and that is an `OutOfMemoryError` rather than a slow program.

  The surprise is usually number one. Most beginners do not think of printing as
  input or output at all, and it is frequently the most expensive thing their
  program does.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="What is a system call? Give examples." icon="i-lucide-message-circle"}
  The only way a user-mode program can ask the kernel to do something it is not
  allowed to do itself. The program puts a number naming the service in a
  register and executes a trap instruction; the processor switches to kernel
  mode. Examples: `open`, `read`, `write`, `close`, `fork`, `exec`, `exit`,
  `wait`, `kill`. In Java you never call them directly; `FileInputStream.read`
  ends in `read`, `new ProcessBuilder(...).start()` ends in `fork` and `exec`.
  :::

  :::accordion-item{label="What happens when you call read()?" icon="i-lucide-message-circle"}
  Arguments into registers, trap, switch to kernel mode, the kernel saves your
  state, checks the file descriptor and permissions, copies bytes into your
  buffer (possibly waiting on the disk), restores your state, returns to user
  mode on the next instruction. Then the number: roughly a microsecond even when
  nothing waits, which is why an unbuffered read of a 60 MB file took 47 seconds
  and the buffered version under half a second.
  :::

  :::accordion-item{label="Why is BufferedReader faster than FileReader?" icon="i-lucide-message-circle"}
  Not "because it buffers". Because an unbuffered read is one system call per
  call, and a buffer turns 60 million crossings into 7,500 by bringing back 8 KB
  at a time and serving the rest from user memory. The same arithmetic is why
  you batch database inserts and why you do not call an HTTP API inside a loop.
  :::

  :::accordion-item{label="What is the difference between a system call and an interrupt?" icon="i-lucide-message-circle"}
  Both switch the processor into kernel mode. A system call (a trap) is
  **deliberate** and comes from the running program: it is asking for something.
  An interrupt comes from **hardware** (the disk finished, a key was pressed, the
  timer fired) and arrives whenever it arrives, regardless of what the program
  was doing. The timer interrupt is the one that makes scheduling possible, which
  is the subject of the next chapter.
  :::
::
