The OOPs track ended with design patterns: ways to arrange the objects inside one
program. Now step back one layer. Every one of those programs was started, given
memory, handed the processor and occasionally refused something by a single
program that owns the machine in a way your code never will. That program is the
operating system, and it was also the author of every `permission denied` you
have ever seen.

## Why this matters in a job

Because for the rest of your career, when something fails you will need to know
**which layer failed**. Your code, the language runtime, the operating system, or
the hardware. Four suspects, and people who cannot tell them apart debug by
changing things at random.

## The four jobs

Think of a college hostel warden. Forty students, one kitchen, one set of
keys, one washing machine. The warden decides who uses the kitchen when, who
gets which room, who may open which cupboard, and stops one student from walking
into another's room. None of the students can be trusted to do that fairly on
their own. An operating system is that warden for programs.

The real version: an operating system is the program that runs other programs.
It has four jobs and every one of them exists because programs cannot be
trusted.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-cpu" title="Share the processor"}
  Forty programs, one or eight processors. Somebody has to decide who runs, for
  how long, and who is interrupted. That somebody is the scheduler.
  :::
  :::feature{icon="i-lucide-memory-stick" title="Hand out memory"}
  Every program believes it has the machine's memory to itself. It does not, and
  keeping that illusion intact is most of what an operating system does.
  :::
  :::feature{icon="i-lucide-folder" title="Own the devices"}
  Disk, network, keyboard, screen. Your program never touches any of them. It
  asks, and the answer is sometimes no.
  :::
  :::feature{icon="i-lucide-shield" title="Keep programs apart"}
  Your program cannot read another program's memory, cannot open another user's
  files, cannot stop the machine. This is the job that produces "permission
  denied".
  :::
::

## How it works

Three commands, three refusals, three different reasons. Run them on any Linux
machine or Mac.

```bash [Terminal]
cat /etc/shadow
```

```text [Output]
cat: /etc/shadow: Permission denied
```

`cat` did not refuse. `cat` asked the kernel to open a file and the kernel
checked who you are against who owns it, and returned an error. The program is
blameless; it is reporting somebody else's decision.

```bash [Terminal]
kill -9 1
```

```text [Output]
-bash: kill: (1) - Operation not permitted
```

Process 1 is the first process the system started and the parent of everything.
You are not allowed to kill it, and the refusal is not a policy in `kill`. It is
in the kernel.

```bash [Terminal]
mkdir /college
```

```text [Output]
mkdir: /college: Read-only file system
```

A third kind of no. Not who you are, but what the device allows. Same shape:
your program asked, the kernel decided.

::pull-quote
Your program never does anything. It asks, and something with more authority
either does it or refuses.
::

In user mode, the instructions that would let a program talk to the disk
**literally do not work**. The processor refuses them. So your program's only
route to anything outside its own memory is to ask the kernel, and the asking has
a name: a **system call**.

## Real use case

::real-life{title="The four-hour bug that was one layer down" source="A deployment, year two"}
Our service would not start on a new server. The error was from our own code:
`Cannot bind to port 8080`. Two of us read our configuration for four hours.
The cause was an operating system rule: only one process may hold a port, an
old copy of the service still held 8080, and the message our framework printed described the
symptom rather than the layer. Once somebody ran `lsof -i :8080` it took nine
seconds.
::

The same layer shows up in Java code you have already written. Every one of these
is the kernel's decision, reported by the language:

```java [ReadMarks.java]
import java.nio.file.*;

public class ReadMarks {
  public static void main(String[] args) {
    try {
      Files.readAllLines(Path.of("/etc/shadow"));
    } catch (AccessDeniedException e) {
      // The JVM asked the kernel to open the file. The kernel said no.
      System.out.println("Kernel refused: " + e.getMessage());
    } catch (Exception e) {
      System.out.println("Something else: " + e);
    }
  }
}
```

```text [Output, on Linux]
Kernel refused: /etc/shadow
```

| What you see in Java | Which job of the operating system produced it |
| --- | --- |
| `AccessDeniedException` | Keeping programs apart: the permission check |
| `BindException: Address already in use` | Owning the devices: another process holds the port |
| A thread that waits in `Thread.sleep` | Sharing the processor: the scheduler took it off |
| `OutOfMemoryError: unable to create new native thread` | Handing out memory: the operating system said no more stacks |

## What confuses people here

That the operating system is "running alongside" your program. It is not a
program sitting next to yours. It is the thing that starts yours, decides when it
runs, holds its memory, and can stop it. There is no negotiation.

::side-note{kind="go-deeper"}
This is also why a crashing program does not crash the machine. Your Java program
dividing by zero is a fault inside one user-mode process; the kernel notices,
kills that process, and everything else continues. A fault inside the kernel is a
different matter entirely, and that is what a kernel panic or a blue screen is.
::

## Your turn

Run each of these and say, for each one, whether the refusal came from the
program, the kernel's permission check, or the device.

```bash [Terminal]
touch /usr/bin/hello
echo $?
ls --students
echo $?
```

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  `touch /usr/bin/hello` fails with `Permission denied`, exit status 1. That is
  the **kernel**: `/usr/bin` is owned by root and you are not root. `touch` asked
  and was refused.

  `ls --students` fails with `unrecognized option`, exit status 2 (or 1 on
  macOS). That is the **program**: `ls` read its own arguments, did not recognise
  one, and gave up before making any system call at all. The kernel was never
  involved.

  `echo $?` prints the exit status of the last command, which is the habit worth
  taking from this exercise: zero means success and anything else means a
  failure, and scripts everywhere depend on it.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="What is an operating system?" icon="i-lucide-message-circle"}
  **Weak:** "an interface between the user and the hardware." Memorised, and
  every candidate says it.

  **Strong:** the four jobs, with an example. "It shares the processor between
  programs, hands out memory, owns the devices, and keeps programs from touching
  each other. The last one is what you see when a command gives you permission
  denied: the command did not refuse, it asked the kernel to open a file and the
  kernel checked the owner against you."
  :::

  :::accordion-item{label="What is the kernel?" icon="i-lucide-message-circle"}
  The core of the operating system: the part that runs in kernel mode and
  actually owns the processor, memory and devices. The shell, the file manager
  and the settings window are programs that come with the operating system; the
  kernel is the part they all ask. It is not a process and never appears in `ps`.
  :::

  :::accordion-item{label="What is the difference between user mode and kernel mode?" icon="i-lucide-message-circle"}
  It is a **processor** feature, not a software convention. In user mode the
  privileged instructions do not execute, so a user-mode program physically
  cannot talk to the disk; it can only trap into the kernel and ask. The reason
  it exists: a bug in one program cannot take down the machine or read another
  program's data. That is why your Java program dividing by zero kills one
  process rather than the computer.
  :::

  :::accordion-item{label="Name some operating systems and what kind each is." icon="i-lucide-message-circle"}
  Linux, Windows and macOS are general-purpose, multi-user, multitasking systems.
  Android and iOS are mobile systems (Android runs on the Linux kernel). A
  real-time operating system (the kind in a car's airbag controller) guarantees a
  response within a fixed time rather than being fast on average. Batch systems,
  the oldest kind, ran jobs one after another with no interaction. Saying that
  most servers you will deploy to run Linux is a useful closing line.
  :::
::
