Every word from the track in one place. Read it the morning of an interview:
if a line surprises you, go back to that lesson. Each definition is written the
way you would say it out loud, not the way a textbook prints it.

## Why this matters in a job

Operating systems questions in a fresher round are short and come without
context: "what is a PCB?", "what is thrashing?", "what is a semaphore?". There is
no code in front of you to jog your memory. A one-line definition you can say
without hesitating, followed by one example, is what the interviewer is
listening for.

## The terms

### The kernel

| Term | In one line |
| --- | --- |
| **Operating system** | The program that runs other programs: it shares the processor, hands out memory, owns the devices and keeps programs apart. |
| **Kernel** | The core of the operating system, running in kernel mode. Not a process; never appears in `ps`. |
| **User mode / kernel mode** | Two processor states. In user mode the instructions that touch hardware do not work. |
| **System call** | The only doorway from a program into the kernel: `open`, `read`, `write`, `fork`, `exec`, `exit`. |
| **Trap** | The instruction that deliberately enters the kernel. A system call is made with one. |
| **Interrupt** | A signal from hardware (disk done, key pressed, timer fired) that makes the processor run kernel code. |
| **Bootloader** | The small program that loads the kernel into memory. GRUB on Linux. |
| **Process 1 (init)** | The first user-mode process, ancestor of all others. `systemd` on Linux, `launchd` on macOS. |
| **Buffer** | Memory in your program that holds data so you cross the kernel door once per block instead of once per byte. |

### Processes and threads

| Term | In one line |
| --- | --- |
| **Program** | A file on disk. Passive. |
| **Process** | One running instance of a program, with its own memory, file descriptors, registers and pid. |
| **Thread** | A line of execution inside a process. Own stack and registers; shares the heap, code and open files. |
| **Process states** | New, ready, running, waiting (blocked), terminated. Waiting goes to ready, never straight to running. |
| **PCB** | Process control block: the kernel's record of a process (pid, state, program counter, registers, priority, memory info, open files). |
| **Ready queue** | The PCBs of processes that could run if given a processor. |
| **Context switch** | Saving one process's or thread's state to its PCB and loading another's. Pure overhead. |
| **Dispatcher** | The kernel code that performs the switch to the process the scheduler chose. |
| **fork / exec / wait** | Copy the process; replace its program; wait for a child to finish. How a shell runs a command. |
| **Orphan** | A process whose parent exited first. Adopted by process 1. |
| **Zombie** | A finished process whose exit status its parent has not read. Only a row in the process table. |
| **Concurrency / parallelism** | In progress at once (possible on one core) / executing at the same instant (needs several cores). |

### CPU scheduling

| Term | In one line |
| --- | --- |
| **Arrival / burst time** | When a process becomes ready / how much processor time it needs. |
| **Completion time (CT)** | When it finishes. Read off the Gantt chart. |
| **Turnaround time** | CT - arrival. The whole stay. |
| **Waiting time** | Turnaround - burst. Time spent ready but not running. |
| **Response time** | First run - arrival. What an interactive user feels. |
| **Pre-emptive / non-pre-emptive** | The scheduler can / cannot take the processor away mid-burst. |
| **FCFS** | First come, first served. Simple; suffers the convoy effect. |
| **Convoy effect** | Short processes stuck behind one long one under FCFS. |
| **SJF** | Shortest job first, non-pre-emptive. Minimum average waiting time among non-pre-emptive algorithms. |
| **SRTF** | Shortest remaining time first: pre-emptive SJF. Lowest average waiting time of all. |
| **Round Robin** | Each process gets one time quantum in turn. Fair, good response, no starvation. |
| **Time quantum** | The slice length in Round Robin. Too large becomes FCFS; too small is all switching. |
| **Priority scheduling** | Run the highest-priority ready process. Can be pre-emptive or not. |
| **Starvation** | A ready process that is never chosen. |
| **Ageing** | Raising a process's priority the longer it waits. The fix for starvation. |
| **Multilevel feedback queue** | Several queues with different priorities and algorithms; processes move between them. |
| **Priority inversion** | A high-priority task waiting on a lock held by a low-priority one. Fixed by priority inheritance. |

### Synchronisation

| Term | In one line |
| --- | --- |
| **Race condition** | A result that depends on the order threads happened to run. `x++` is the example. |
| **Critical section** | Code that touches shared data and must not be run by two threads at once. |
| **Mutual exclusion, progress, bounded waiting** | The three requirements of any critical-section solution. |
| **Mutex** | A lock with an owner: one holder at a time, only the holder releases it. |
| **Semaphore** | An integer changed only by atomic `wait` (P, decrement or block) and `signal` (V, increment and wake). |
| **Binary / counting semaphore** | Values 0 and 1 / values 0 to N, for N identical resources. |
| **Spinlock** | A lock that busy-waits (loops) instead of sleeping. Good only for very short waits. |
| **Producer-consumer** | Bounded-buffer problem. Solved with `empty = N`, `full = 0`, `mutex = 1`. |
| **Readers-writers** | Many readers together, writers alone. |
| **Dining philosophers** | Five philosophers, five chopsticks: the textbook deadlock. |
| **Monitor** | Shared data plus the methods using it, one thread inside at a time, with condition variables. Every Java object is one. |
| **Atomic operation** | One that cannot be interrupted halfway, such as `AtomicInteger.incrementAndGet()`. |

### Deadlock

| Term | In one line |
| --- | --- |
| **Deadlock** | Each process in a set waits for a resource another holds. Nobody moves, ever. |
| **Four conditions** | Mutual exclusion, hold and wait, no pre-emption, circular wait. All four needed. |
| **Resource allocation graph** | Processes and resources with request and assignment edges. A cycle means deadlock (single instances) or possible deadlock (several instances). |
| **Prevention** | Design so one condition can never hold. Lock ordering breaks circular wait. |
| **Avoidance** | Grant a request only if the state stays safe. The banker's algorithm. |
| **Safe state** | One where some order exists in which every process can finish. |
| **Need matrix** | Max - Allocation, per process and resource. |
| **Detection and recovery** | Let deadlocks happen, find cycles in the wait-for graph, kill or roll back a victim. |
| **Ostrich algorithm** | Ignore deadlock. What most desktop operating systems do. |
| **Livelock** | Threads busy reacting to each other, making no progress. |

### Memory

| Term | In one line |
| --- | --- |
| **Contiguous allocation** | Each process in one continuous block of memory. |
| **First / best / worst fit** | Take the first, the smallest, or the largest hole that is big enough. |
| **Internal fragmentation** | Waste inside an allocated block (fixed sizes, the last page). |
| **External fragmentation** | Enough free memory in total, but in holes too small to use. |
| **Compaction** | Moving allocations together to merge the holes. |
| **Page / frame** | A fixed-size piece of logical memory / of physical memory, the same size. |
| **Page table** | Per-process map from page numbers to frame numbers. |
| **Logical / physical address** | The address the program uses / the real location in RAM. |
| **MMU** | The hardware that translates every address. |
| **TLB** | A small fast cache of recent translations. |
| **Effective access time** | Hit ratio × hit time + miss ratio × miss time. |
| **Segmentation** | Memory divided into variable-size logical segments, translated with base and limit. |
| **Virtual memory** | Every address is virtual and translated per process, so programs are isolated and can be larger than RAM. |
| **Demand paging** | Load a page only when it is first touched. |
| **Page fault** | An access to a page not present in memory. The kernel loads it or kills the process. |
| **Minor / major fault** | Resolved without disk / needs a disk read. |
| **FIFO, LRU, Optimal** | Evict the oldest-loaded / least recently used / not-needed-for-longest page. |
| **Belady's anomaly** | More frames giving more faults, possible under FIFO. |
| **Thrashing** | More time paging than working, because working sets do not fit in memory. |
| **Working set** | The pages a process used in its last Δ references. |
| **Locality of reference** | Programs reuse recent addresses and nearby ones. Why all caching works. |
| **Swap** | Disk space holding pages that were evicted from memory. |
| **RSS / virtual size** | Memory actually in RAM / address space reserved. |
| **Stack / heap** | Per-thread method frames / shared objects made with `new`. |
| **Memory leak, in Java** | An object still reachable but no longer needed. |

### File systems

| Term | In one line |
| --- | --- |
| **Inode** | A file's record: type, size, owner, permissions, timestamps, link count, block pointers. Not its name. |
| **Directory** | A file mapping names to inode numbers. |
| **Hard link** | A second name for the same inode. |
| **Symbolic link** | A small file containing a path. Dangles if the target moves. |
| **File descriptor** | A small integer naming an open file within one process. 0, 1, 2 are stdin, stdout, stderr. |
| **Contiguous / linked / indexed allocation** | Blocks in a row / each block points to the next / an index block lists them all. |
| **FAT** | Linked allocation with the links kept in one table. |
| **Direct / indirect pointers** | Inode pointers to data blocks / to blocks full of pointers. |
| **Bitmap** | One bit per block marking free or used. |
| **uid / gid** | The numbers the kernel checks. root is uid 0. |
| **rwx, 755, 644** | Read 4, write 2, execute 1, per owner, group and other. |
| **Execute on a directory** | Permission to traverse into it. |

## Real use case

This page is for revising, so use it like a flashcard deck: cover the right-hand
column and say each definition out loud, then the example you would give. In
the interviews I sat after moving to Bangalore, the questions that went badly
were never the hard ones. They were the easy ones I had read about and never
said aloud, so the words came out in the wrong order under pressure.

## What confuses people here

The pairs interviewers put side by side on purpose:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-split" title="Process vs thread"}
  Own everything vs share the heap and files, own only stack and registers.
  :::
  :::feature{icon="i-lucide-split" title="Ready vs waiting"}
  Needs only the processor vs needs an I/O or event first.
  :::
  :::feature{icon="i-lucide-split" title="Mutex vs semaphore"}
  Lock with an owner vs counter anyone may signal.
  :::
  :::feature{icon="i-lucide-split" title="Starvation vs deadlock"}
  Never chosen while the system moves vs nobody can move at all.
  :::
  :::feature{icon="i-lucide-split" title="Prevention vs avoidance"}
  Make a condition impossible vs check each request for safety.
  :::
  :::feature{icon="i-lucide-split" title="Internal vs external fragmentation"}
  Waste inside a block (paging) vs between blocks (segmentation).
  :::
  :::feature{icon="i-lucide-split" title="Paging vs segmentation"}
  Fixed, invisible pieces vs variable, logical pieces.
  :::
  :::feature{icon="i-lucide-split" title="Virtual memory vs swap"}
  Address translation, always on vs one use of it, pages on disk.
  :::
  :::feature{icon="i-lucide-split" title="LRU vs Optimal"}
  Looks backwards vs looks forwards.
  :::
  :::feature{icon="i-lucide-split" title="Hard link vs soft link"}
  Same inode vs a path to a name.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="Define, in one line each: PCB, context switch, semaphore, thrashing." icon="i-lucide-message-circle"}
  PCB: the kernel's record of a process, used to stop and resume it. Context
  switch: saving one process's state and loading another's. Semaphore: an
  integer changed only by atomic wait and signal, used to limit access or to
  signal. Thrashing: the system spending more time paging than executing.
  :::

  :::accordion-item{label="What is the difference between a mutex and a binary semaphore?" icon="i-lucide-message-circle"}
  A mutex has an owner and only the owner may unlock it; it is for mutual
  exclusion. A binary semaphore has no owner and any thread may signal it; it is
  for signalling between threads as well as exclusion.
  :::

  :::accordion-item{label="Is virtual memory the same as swap?" icon="i-lucide-message-circle"}
  No. Virtual memory is per-process address translation through page tables,
  always on. Swap is disk space for evicted pages, one consequence of it. A
  machine with no swap still uses virtual memory for every access.
  :::
::
