Paper first, then the machine. The first seven problems are the kind a written
round or a whiteboard interview sets, with full working in the answers. Do each
one before opening its answer; the point is to find out where your method slips,
and it will slip somewhere the first time. The last seven you run on your own
computer, and several of them give you a number you can quote in an interview.

::note
Run the machine exercises on your own computer, not on anything shared or
anything that matters. Two of them deliberately break things, and one
deliberately exhausts memory.
::

## Why this matters in a job

Reading a worked example and producing one under a clock are different skills.
Written rounds give you perhaps a minute and a half per question, and the
scheduling and page-replacement questions are the ones where a single slip (a
forgotten idle gap, a queue in the wrong order, looking backwards instead of
forwards) costs the whole mark.

## On paper

### 1. Four schedulers, one set

| Process | Arrival | Burst | Priority (1 = highest) |
| --- | --- | --- | --- |
| P1 | 0 | 5 | 3 |
| P2 | 1 | 3 | 1 |
| P3 | 2 | 1 | 4 |
| P4 | 4 | 2 | 2 |

Draw the Gantt chart and find the average waiting time for FCFS, SJF, SRTF and
Round Robin with quantum 2.

::accordion
  :::accordion-item{label="FCFS and SJF" icon="i-lucide-check"}
  **FCFS:** P1 0-5, P2 5-8, P3 8-9, P4 9-11. Waiting: P1 0, P2 5-1=4,
  P3 8-2=6, P4 9-4=5. Average 15 / 4 = **3.75**.

  **SJF:** P1 runs 0-5 (only one there at 0). At 5, bursts are P2 3, P3 1,
  P4 2: P3 5-6, P4 6-8, P2 8-11. Waiting: P1 0, P2 7, P3 3, P4 2. Average
  12 / 4 = **3.0**.
  :::

  :::accordion-item{label="SRTF" icon="i-lucide-check"}
  t0 P1 (5). t1 P2 arrives (3) < P1's 4 left: P2 runs. t2 P3 arrives (1) <
  P2's 2 left: P3 runs 2-3. t3: P1 4, P2 2: P2 runs 3-5 (P4 arrives at 4 with 2,
  not less than P2's 1 left). t5: P1 4, P4 2: P4 5-7. P1 7-11.

  ```text [Gantt chart]
  |P1|P2|P3| P2 | P4 |   P1   |
  0  1  2  3    5    7        11
  ```

  CT: P1 11, P2 5, P3 3, P4 7. Waiting = CT - AT - BT: P1 6, P2 1, P3 0, P4 1.
  Average 8 / 4 = **2.0**, the lowest.
  :::

  :::accordion-item{label="Round Robin, quantum 2" icon="i-lucide-check"}
  0-2 P1 (3 left). Arrived by 2: P2, P3, then P1 re-queued: queue P2, P3, P1.
  2-4 P2 (1 left). P4 arrived at 4, joins before P2: queue P3, P1, P4, P2.
  4-5 P3 done. 5-7 P1 (1 left): queue P4, P2, P1. 7-9 P4 done. 9-10 P2 done.
  10-11 P1 done.

  ```text [Gantt chart]
  | P1 | P2 |P3| P1 | P4 |P2|P1|
  0    2    4  5    7    9  10 11
  ```

  CT: P1 11, P2 10, P3 5, P4 9. Waiting: P1 6, P2 6, P3 2, P4 3. Average
  17 / 4 = **4.25**.
  :::
::

### 2. Priority, both ways

Same four processes. Priority scheduling, non-pre-emptive and then pre-emptive.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Non-pre-emptive:** P1 0-5. At 5: P2 (1), P3 (4), P4 (2): P2 5-8, P4 8-10,
  P3 10-11. Waiting: 0, 4, 8, 4. Average **4.0**.

  **Pre-emptive:** P1 0-1; P2 (priority 1) arrives and pre-empts, runs 1-4; at 4
  P4 (2) beats P1 (3): P4 4-6; P1 6-10; P3 10-11. Waiting: P1 5, P2 0, P3 8,
  P4 0. Average **3.25**. P3, the lowest priority, waits longest in both.
  :::
::

### 3. Page faults

Reference string **1, 2, 3, 4, 2, 1, 5, 6, 2, 1, 2, 3, 7, 6, 3, 2, 1, 2, 3, 6**.
Count the page faults for FIFO, LRU and Optimal with **3 frames**, then with
**4 frames**.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  | Frames | FIFO | LRU | Optimal |
  | --- | --- | --- | --- |
  | 3 | 16 | 15 | 11 |
  | 4 | 14 | 10 | 8 |

  A classic string, so these are worth memorising as a check. If your FIFO
  count with 3 frames is not 16, the most likely slip is moving a page to the
  back of the queue on a hit: FIFO never does that.
  :::
::

### 4. Address translation

Page size 2 KB (2,048 bytes). Page table: page 0 → frame 4, page 1 → frame 9,
page 2 → frame 1, page 3 → frame 6. Translate logical addresses **5,000** and
**9,000**.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **5,000:** page = 5000 ÷ 2048 = 2 (4,096 ≤ 5,000 < 6,144), offset = 5000 - 4096
  = 904. Frame 1. Physical = 1 × 2048 + 904 = **2,952**.

  **9,000:** page = 9000 ÷ 2048 = 4. The table has pages 0 to 3 only, so this is
  an invalid address: the hardware traps and the process gets a segmentation
  fault. Always check the page number is in range.
  :::
::

### 5. A segment table

Segment 0: base 219, limit 600. Segment 1: base 2300, limit 14. Segment 2:
base 90, limit 100. Translate (0, 430), (1, 10), (1, 15) and (2, 99).

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  (0, 430) → 219 + 430 = **649**. (1, 10) → 2300 + 10 = **2310**. (1, 15): 15 ≥
  14, **trap**. (2, 99) → 90 + 99 = **189** (99 < 100, the last valid byte).
  :::
::

### 6. Is it safe?

Three processes, one resource type with 12 instances. P0 holds 5 and may need
up to 10. P1 holds 2 and may need up to 4. P2 holds 2 and may need up to 9. Is
the state safe? If P2 asks for one more, should it get it?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Available = 12 - (5 + 2 + 2) = 3. Need: P0 5, P1 2, P2 7.

  Safety: P1 (needs 2 ≤ 3) finishes, Available 3 + 2 = 5. P0 (needs 5 ≤ 5)
  finishes, Available 10. P2 (needs 7 ≤ 10) finishes. **Safe: P1, P0, P2.**

  P2 requests 1: pretend Available 2, P2 holds 3, needs 6. P1 (2 ≤ 2) finishes,
  Available 4. P0 needs 5 > 4, P2 needs 6 > 4. **Unsafe, so P2 must wait**, even
  though a free instance exists.
  :::
::

### 7. How big can a file be?

An inode has 10 direct pointers, 1 single indirect and 1 double indirect. Blocks
are 1 KB and block addresses are 4 bytes. What is the largest file?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Pointers per block = 1024 / 4 = 256. Direct: 10 × 1 KB = 10 KB. Single:
  256 × 1 KB = 256 KB. Double: 256 × 256 × 1 KB = 65,536 KB = 64 MB. Total
  10 KB + 256 KB + 64 MB = **65,802 KB, about 64.3 MB**.
  :::
::

## On your machine

### 8. Count the processes that are actually running

```bash [Terminal]
ps ax | wc -l
ps axo stat | grep -c '^R'
```

**Write down both numbers.** On my laptop: 412 processes, 3 running. That ratio
is the answer to "how does my machine run all this at once" and almost nobody has
ever looked at it.

### 9. Measure the kernel door

Make a file of a million lines, then read it two ways.

```bash [Terminal]
seq 1 1000000 > /tmp/attendance.txt
```

```java [ReadTwoWays.java]
import java.io.*;

public class ReadTwoWays {
  public static void main(String[] args) throws Exception {
    time("unbuffered", () -> new FileInputStream("/tmp/attendance.txt"));
    time("buffered",   () -> new BufferedInputStream(
                                 new FileInputStream("/tmp/attendance.txt"), 8192));
  }

  interface Source { InputStream open() throws Exception; }

  static void time(String name, Source source) throws Exception {
    long start = System.nanoTime();
    long lines = 0;
    try (InputStream in = source.open()) {
      int b;
      while ((b = in.read()) != -1) if (b == '\n') lines++;
    }
    System.out.printf("%-12s %,d lines in %.2f s%n",
        name, lines, (System.nanoTime() - start) / 1e9);
  }
}
```

**Write down both times and the ratio.** Mine was 124×. That number is a good
answer to "why do we use BufferedReader" and it is yours rather than mine.

### 10. Lose an increment

```java [LoseCounts.java]
public class LoseCounts {
  static int received = 0;

  public static void main(String[] args) throws Exception {
    Runnable intake = () -> { for (int i = 0; i < 100_000; i++) received++; };
    Thread a = new Thread(intake), b = new Thread(intake);
    a.start(); b.start(); a.join(); b.join();
    System.out.println("Expected 200000, got " + received);
  }
}
```

Run it five times. Then fix it three ways, `synchronized`, `AtomicInteger`, and
per-thread counters summed at the end, and confirm all three give 200,000 every
time.

::accordion
  :::accordion-item{label="Then answer this" icon="i-lucide-help-circle"}
  Change `100_000` to `100`. Run it five times. It will almost certainly be
  correct every time.

  **That is the exercise.** The bug is invisible at small scale, which is exactly
  why these reach production: your test passes, your demonstration passes, and it
  fails on the day four thousand students load the page at once. Concurrency is
  reasoned about, not tested into correctness.
  :::
::

### 11. Cause a deadlock, then find it with a tool

```java [Deadlock.java]
public class Deadlock {
  static final Object cse = new Object();
  static final Object ece = new Object();

  public static void main(String[] args) {
    new Thread(() -> { synchronized (cse) { nap(); synchronized (ece) { } } }, "staff-A").start();
    new Thread(() -> { synchronized (ece) { nap(); synchronized (cse) { } } }, "staff-B").start();
  }

  static void nap() { try { Thread.sleep(100); } catch (InterruptedException e) { } }
}
```

It hangs. Now diagnose it without reading the code:

```bash [Terminal]
jps                 # find the pid of Deadlock
jstack <pid> | grep -A 20 "Found one Java-level deadlock"
```

**Write down what it prints.** The JVM names both threads and both locks. Knowing
this command exists is the difference between a two-minute diagnosis and an
afternoon, and it is worth saying in an interview.

### 12. Watch memory climb, and tell a leak from a size problem

```java [Leak.java]
import java.util.*;

public class Leak {
  static final Map<Long, byte[]> CACHE = new HashMap<>();   // no eviction

  public static void main(String[] args) throws Exception {
    for (long id = 0; ; id++) {
      CACHE.put(id, new byte[100_000]);                     // ~100 KB per "applicant"
      if (id % 100 == 0) {
        System.out.printf("%,d cached, heap used %,d MB%n", id,
            (Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory()) / 1_048_576);
      }
      Thread.sleep(5);
    }
  }
}
```

```bash [Terminal]
java -Xmx256m Leak
```

Let it run until it dies. While it runs, in another terminal:

```bash [Terminal]
jcmd <pid> GC.class_histogram | head -5
```

**Answer:** does used memory return to a baseline, or only climb? Which of the
three `OutOfMemoryError` messages did you get?

### 13. Break a permission on purpose, and fix it properly

```bash [Terminal]
mkdir -p /tmp/college/exports
echo "roll,marks" > /tmp/college/exports/results.csv
chmod 644 /tmp/college/exports/results.csv
chmod 600 /tmp/college/exports
cat /tmp/college/exports/results.csv
```

It fails, and the file is world readable. **Fix it with the smallest possible
change**, and write down why the error named the file when the problem was the
directory.

::accordion
  :::accordion-item{label="The answer, and the general shape" icon="i-lucide-key"}
  `chmod 700 /tmp/college/exports`: the directory needed its execute bit
  back, because execute on a directory means "may traverse into".

  The general shape, and the reason this exercise is here: **a permission error
  names the thing you asked for, not the thing that refused.** The kernel checks
  every component of the path, so when you hit one in production, check `ls -ld`
  on every parent directory before you touch the file.
  :::
::

### 14. Follow yourself up to process 1

```bash [Terminal]
ps -o pid,ppid,comm -p $$
# then repeat with each ppid until you reach 1
ps -o pid,comm -p 1
```

**Write down the chain.** Mine is three steps. Then answer: if you killed the
middle one, what happens to the bottom one?

### The command cheat sheet

| To find out | Run |
| --- | --- |
| What is running, and what is merely ready | `ps axo pid,stat,comm` |
| Which process holds a port | `lsof -i :8080` |
| How many system calls a program makes | `strace -c <cmd>` (Linux) |
| Memory, and whether it is swapping | `free -h` (Linux) · `vm_stat` (macOS) |
| Major page faults for one process | `ps -o pid,min_flt,maj_flt -p <pid>` |
| Java processes and their pids | `jps` |
| Every thread and what it waits on | `jstack <pid>` |
| What the heap actually contains | `jcmd <pid> GC.class_histogram` |
| Who owns a file, and who may do what | `ls -l`, `ls -ld` on each parent |
| Which user a process runs as | `ps -o user -p <pid>` |
| Who you are, to the kernel | `id` |


## Real use case

Every problem on this page came from something real. The scheduling arithmetic
is how you reason about a job queue that is making short reports wait behind a
long export. The page-fault counts are the reason your cache has an eviction
policy. The banker's check is the idea behind a connection pool that refuses to
hand out its last connection. The `jstack`, `jcmd` and `ls -ld` exercises are,
word for word, what you run in the first ten minutes of a production incident.

## What confuses people here

That practice means reading answers. It does not: you learn the method only when
your own answer is wrong and you find out where. For the paper problems, write
the ready queue (Round Robin) or the frame contents (page replacement) at every
step, even when it feels slow. Nearly every wrong answer in these topics comes
from doing one step in your head.

## Interview questions

::accordion
  :::accordion-item{label="Given four processes, how do you compute average waiting time quickly?" icon="i-lucide-message-circle"}
  Draw the Gantt chart first, read completion times off it, then use
  WT = CT - AT - BT for each process. Never add up gaps by eye; the formula
  handles pre-emption and idle time correctly.
  :::

  :::accordion-item{label="How would you find a deadlock in a running Java service?" icon="i-lucide-message-circle"}
  `jps` for the pid, then `jstack <pid>`. The JVM detects monitor cycles and
  prints "Found one Java-level deadlock" with both threads and both locks.
  :::

  :::accordion-item{label="How do you tell a memory leak from a sizing problem?" icon="i-lucide-message-circle"}
  Watch used heap after full collections over time: a leak climbs steadily; a
  sizing problem returns to a baseline and spikes during one job. A class
  histogram (`jcmd <pid> GC.class_histogram`) shows which objects are
  accumulating.
  :::
::
