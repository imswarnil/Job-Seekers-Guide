The table can point at memory that does not exist yet, and that is the most
elegant lie in computing. Every process on your machine believes it has a
private, continuous block of memory starting at address zero, often far larger
than the RAM in the machine. Four hundred processes, eight gigabytes, and all of
them are telling the truth about what they can see. That is **virtual memory**.

## Why this matters in a job

"What is virtual memory?" and "what is a page fault?" are asked in almost every
operating systems round, and most candidates answer the first one wrongly (it is
not "using the disk as RAM"). At work, three things you will meet constantly are
this one idea: why a process cannot read another's memory, why a program can
start instantly even though it is huge, and the difference between "my program
uses 2 GB" and "my machine has 2 GB free".

## The idea

Think of a hostel where every student is told "your room is Room 1". Each
student's key tag secretly maps "Room 1" to a real room number, which only the
warden knows, and some students' belongings are still in a storeroom until the
first time they ask for them. Every student's view is complete and consistent,
and none of them is the real building.

In a machine: every address your program uses is virtual. The hardware
translates it through the page table from the paging lesson.

A piece of hardware called the **MMU** (memory management unit) does the
translation on every single memory access. What makes it *virtual* memory rather
than plain paging is one extra bit in each page-table entry: **valid or not
present**. A page can be part of your address space without being in RAM at
all.

### Demand paging

Pages are loaded only when the program first touches them. Start a 500 MB
program and the kernel loads almost nothing: it sets up a page table in which
every page is marked "not present", and fetches each page the first time it is
used. That is **demand paging**, and it is why large programs start quickly and
why unused parts of a program never cost any RAM. A **lazy swapper** is the old
name for the same thing: never bring a page in until it is needed.

### What this buys

::feature-list{columns="2"}
  :::feature{icon="i-lucide-shield" title="Isolation, for free"}
  Process A's page table has no entry pointing at frame 22. So A cannot reach
  B's memory, not "is not allowed to", *cannot*, because the address does not
  translate to anything.
  :::
  :::feature{icon="i-lucide-shuffle" title="Continuous from scattered"}
  Your program sees one continuous block. The frames behind it are scattered all
  over physical memory. Nobody has to find a contiguous gap.
  :::
  :::feature{icon="i-lucide-hard-drive" title="More memory than you have"}
  A page that has not been touched recently can be written to disk and its frame
  given to somebody else. The program does not notice, except in time.
  :::
  :::feature{icon="i-lucide-copy" title="Sharing without copying"}
  Two processes running the same program can point at the *same* frames for the
  code. One copy of the JVM's instructions in memory, forty JVMs running.
  :::
::

## How it works

Your program touches an address whose page is not in physical memory. The MMU
cannot translate it, so it raises a **page fault**: an interrupt into the
kernel.

::flow{numbered direction="vertical" caption="A page fault. Steps 1 to 4 are microseconds; step 5 is milliseconds, which is why it matters."}
  :::flow-step{label="Your program reads an address" icon="i-lucide-mouse-pointer"}
  An ordinary instruction. Nothing special in your code.
  :::
  :::flow-step{label="The MMU finds no mapping" icon="i-lucide-x"}
  Page fault. The processor traps into the kernel, mid-instruction.
  :::
  :::flow-step{label="The kernel decides what kind" icon="i-lucide-git-branch"}
  Is this a page that was swapped out, a page of a file not read yet, or an
  address that is genuinely invalid?
  :::
  :::flow-step{label="Invalid → the program dies" icon="i-lucide-skull"}
  Segmentation fault. In Java you rarely see this, because the JVM checks first
  and gives you a `NullPointerException` instead.
  :::
  :::flow-step{label="Valid → fetch it, then resume" icon="i-lucide-download" highlight}
  Find a free frame, read the page in from disk, update the page table, restart
  the instruction. Your program continues, none the wiser, several milliseconds
  older.
  :::
::

::side-note{kind="performance"}
A page fault that has to read from disk costs roughly 100,000 times more than a
normal memory access. One is not a problem. A thousand a second is a machine
that has stopped working while still appearing busy.
::

### Measuring page faults from Java

A program that touches 200 MB for the first time causes tens of thousands of
page faults, one for each new 4 KB page, and the second pass over the same
memory causes almost none:

```java [TouchPages.java]
public class TouchPages {
  public static void main(String[] args) {
    byte[] marks = new byte[200 * 1024 * 1024];     // 200 MB, virtual so far
    for (int pass = 1; pass <= 2; pass++) {
      long start = System.nanoTime();
      for (int i = 0; i < marks.length; i += 4096) marks[i] = 1;   // touch each page once
      System.out.printf("Pass %d: %d ms%n", pass, (System.nanoTime() - start) / 1_000_000);
    }
  }
}
```

```text [Output, a Linux laptop, illustrative]
Pass 1: 61 ms
Pass 2: 4 ms
```

Same loop, same memory. The first pass pays for about 51,000 minor page faults
(the kernel finding a zeroed frame for each page); the second pays for none.
Run it under `/usr/bin/time -v java TouchPages` on Linux and the "Minor page
faults" line shows the count.

## Real use case

The difference between **virtual size** and **resident size** confuses almost
everybody the first time they look at a Java service in production:

```bash [Terminal]
ps -o pid,vsz,rss,comm -p $(pgrep -f results-service)
```

```text [Output]
  PID    VSZ   RSS COMM
 4180 6812344 612408 java
```

`VSZ` (virtual size) is 6.8 GB: everything the JVM has reserved in its address
space, including the whole `-Xmx` heap, thread stacks and libraries. `RSS`
(resident set size) is 612 MB: what is actually in RAM right now. The server has
4 GB of RAM and is perfectly healthy. The number to watch, and to set alerts on,
is RSS. Somebody who alerts on VSZ gets paged at 3 a.m. for nothing.

## What confuses people here

That "virtual memory" means "using the disk as memory". Swap (keeping some pages
on disk) is one *consequence* of virtual memory, not what it is. Virtual memory is the address translation, and
it is on all the time, on every machine, whether or not any swapping happens.

## Your turn

Look at your own machine's memory and answer two questions.

::tabs
  :::tabs-item{label="Linux" icon="i-simple-icons-linux"}
  ```bash [Terminal]
  free -h
  # Faults for one process: minor need no disk, major do.
  ps -o pid,comm,min_flt,maj_flt -p $$
  ```
  :::

  :::tabs-item{label="macOS" icon="i-lucide-command"}
  ```bash [Terminal]
  vm_stat
  # "Pageins" are pages fetched from disk. "Swapins" mean real pressure.
  sysctl vm.swapusage
  ```
  :::
::

1. Add up the memory used by every process in `ps aux`. Is it more than your
   machine has? Why is that not a contradiction?
2. What is the difference between a minor and a major page fault?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1. It is almost certainly far more**, often several times. Three reasons,
  and all of them are this lesson: shared pages are counted once per process but
  exist once in RAM; pages that have been allocated but never touched have no
  frame at all; and some pages are on disk rather than in memory. "Virtual size"
  is what a process *can* address, and "resident size" is what is actually in
  RAM. `RSS` in `ps` is the second one, and it is the number that matters.

  **2. A minor fault** is resolved without touching the disk: the page is
  already in memory, it was not yet mapped into this process yet: a shared
  library somebody else already loaded, or a page being allocated for the first
  time. Cheap, and there are millions of them.

  **A major fault** requires a disk read. Thousands of times more expensive.
  Thrashing is a machine doing nothing but major faults, which is why watching
  `maj_flt` climb is the direct way to confirm it.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="What is virtual memory?" icon="i-lucide-message-circle"}
  **Weak:** "using the disk as RAM." That is swap. **Strong:** every address a
  program uses is virtual and translated by hardware (the MMU) through a
  per-process page table. That gives isolation, a large continuous address space
  over scattered frames, sharing of read-only pages, demand paging, and the
  option of keeping cold pages on disk so programs can be larger than RAM.
  :::

  :::accordion-item{label="What is demand paging?" icon="i-lucide-message-circle"}
  Loading a page into memory only when it is first accessed, instead of loading
  the whole program at start. Pages begin marked "not present"; the first access
  causes a page fault and the kernel loads it. Fast start-up, and unused code
  never uses RAM.
  :::

  :::accordion-item{label="What happens during a page fault?" icon="i-lucide-message-circle"}
  The MMU finds the page marked not present and traps into the kernel. The
  kernel checks the address is valid (if not, the process gets a segmentation
  fault), finds a free frame (or evicts a page to make one), reads the page from
  disk, updates the page table, and restarts the faulting instruction.
  :::

  :::accordion-item{label="What is the difference between a minor and a major page fault?" icon="i-lucide-message-circle"}
  A minor fault is resolved without disk I/O: the page is already in RAM (a
  shared library another process loaded) or only needs a fresh zeroed frame. A
  major fault needs a disk read and costs roughly 100,000 times more. Thrashing
  is a machine doing nothing but major faults.
  :::

  :::accordion-item{label="Why can process A not read process B's memory?" icon="i-lucide-message-circle"}
  Not because it is forbidden, but because it is impossible: A's page table has
  no entry pointing at B's frames, so no virtual address A can produce
  translates to B's memory. Isolation is a property of the translation, enforced
  by hardware on every access.
  :::
::
