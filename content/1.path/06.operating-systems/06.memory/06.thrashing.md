It is called **thrashing**: a machine so short of memory that every process
page-faults almost as soon as it runs, and the system spends its time moving
pages between memory and disk instead of doing any work. Performance does not
degrade smoothly into it. It falls off a cliff.

## Why this matters in a job

"What is thrashing, what causes it and how do you prevent it?" is the question
that closes most memory-management rounds, and the answer (working set, page-fault
frequency, reduce the degree of multiprogramming) has a shape interviewers
listen for. At work, thrashing is the explanation for a server that becomes
unresponsive with its processor graph near zero, which otherwise looks like a
crash.

## When the pages stop fitting

Think of a college library with one reading table for twenty students, where
each student needs three reference books open to work. The table holds thirty
books. Ten students work happily. Let the twenty-first in and there is no room;
the librarian takes a book away from someone to make space, that student
immediately needs it back and takes someone else's, and within minutes everyone
is queueing at the shelf and nobody is reading. The librarian looks at the
empty chairs and, seeing people "not working", lets **more** students in.

That last sentence is how thrashing happens in a real operating system:

::flow{numbered direction="vertical" caption="The feedback loop that turns a busy machine into a stopped one."}
  :::flow-step{label="Memory gets tight" icon="i-lucide-memory-stick"}
  Processes together need more pages than there are frames.
  :::
  :::flow-step{label="Processes steal frames from each other" icon="i-lucide-shuffle"}
  Each fault evicts a page another process needs, so that process faults too.
  :::
  :::flow-step{label="Everyone waits on the disk" icon="i-lucide-hard-drive"}
  All processes are in the waiting state for page reads. The processor is idle.
  :::
  :::flow-step{label="The system sees low CPU use and admits more work" icon="i-lucide-trending-down" highlight}
  An old-fashioned scheduler raises the degree of multiprogramming to use the
  "idle" processor, which makes memory tighter still.
  :::
::

### The working set

The **working set** of a process is the set of pages it has used in its most
recent Δ (delta) references: the pages it needs right now. **Locality** is why
this works: a program spends most of its time in a small set of pages (a loop, a
function, the array it is processing), and that set shifts slowly as it moves
from one phase to the next.

The rule that follows: if the **sum of all processes' working-set sizes** is
more than the number of frames, thrashing is coming. So:

- **Working-set model:** track each process's working set. If the total exceeds
  the frames available, **suspend** a process (swap it out entirely) rather than
  let everyone thrash. Its frames go to the others.
- **Page-fault frequency (PFF):** a more direct control. Set an upper and lower
  bound on each process's fault rate. Above the upper bound, give it more frames;
  below the lower, take some away. If no frames are free to give, suspend a
  process.

And **local replacement** helps contain it: a process that faults may only evict
its own pages, so one thrashing process cannot drag everyone else down with it.

## How it works

A working set, computed. Reference string 1, 2, 1, 3, 4, 4, 4, 3, 4, 3 with a
window of Δ = 4:

```java [WorkingSet.java]
import java.util.TreeSet;

public class WorkingSet {
  public static void main(String[] args) {
    int[] refs = {1, 2, 1, 3, 4, 4, 4, 3, 4, 3};
    int delta = 4;
    for (int t = delta; t <= refs.length; t++) {
      TreeSet<Integer> ws = new TreeSet<>();
      for (int i = t - delta; i < t; i++) ws.add(refs[i]);   // the last delta references
      System.out.printf("t=%2d  working set %s  size %d%n", t, ws, ws.size());
    }
  }
}
```

```text [Output]
t= 4  working set [1, 2, 3]  size 3
t= 5  working set [1, 2, 3, 4]  size 4
t= 6  working set [1, 3, 4]  size 3
t= 7  working set [3, 4]  size 2
t= 8  working set [3, 4]  size 2
t= 9  working set [3, 4]  size 2
t=10  working set [3, 4]  size 2
```

The program moves from one phase (pages 1, 2, 3) into a tight loop over pages 3
and 4. From t = 7 it needs only two frames. Give it two and it will not fault;
give it one and it will fault on nearly every reference.

On a real machine you watch for thrashing with `vmstat`: the `si` and `so`
columns are pages swapped in and out per second, and `wa` is processor time
spent waiting on I/O.

```bash [Terminal]
vmstat 1 5
```

```text [Output, a Linux server while thrashing, illustrative]
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1 14 3981204  41220   812  60132 9120 8844  9340  8990 4210 6120  3  6  2 89  0
 0 16 3990112  39876   790  58988 9480 9302  9710  9410 4390 6502  2  5  1 92  0
```

Fourteen processes blocked (`b`), thousands of pages a second in both
directions, 89% of the time waiting on I/O and 3% doing user work. That is what
thrashing looks like as numbers.

## Real use case

::real-life{title="Why the server died at 40,000 rows and not at 4,000" source="A results export"}
An export loaded every `ExamResult` into a list before writing the file. At 4,000
rows it was 200 MB and fine. On results day it was 40,000 rows, about 2 GB, the
machine had 4 GB, and it began swapping. The job never finished and the whole
server became unresponsive, taking the student portal down with it. The fix was
to stream the rows instead of collecting them, a small change whose idea you met
in the Java track.
::

In code, the difference is holding the whole result set versus a working set of
one row at a time:

```java [ExportResults.java]
// Before: 40,000 ExamResult objects in memory at once.
List<ExamResult> all = resultRepository.findAll();
all.forEach(writer::write);

// After: the working set is one row, however big the table gets.
try (Stream<ExamResult> rows = resultRepository.streamAll()) {
  rows.forEach(writer::write);
}
```

This is also why production servers often run with little or no swap and a hard
memory limit per container: it is better for one process to be killed cleanly
than for the whole machine to thrash.

## What confuses people here

That thrashing means "the processor is overloaded". It is the opposite: the
processor is nearly **idle**, because every process is waiting for the disk. The
symptom is an unresponsive machine with a low CPU graph and a disk light that
never goes off. And adding more processes, the instinctive response to an idle
processor, makes it worse.

## Interview questions

::accordion
  :::accordion-item{label="What is thrashing?" icon="i-lucide-message-circle"}
  A state in which the system spends more time paging (moving pages between
  memory and disk) than executing, because processes do not have enough frames
  for their working sets. CPU utilisation drops sharply while disk activity is
  at its maximum.
  :::

  :::accordion-item{label="What causes thrashing?" icon="i-lucide-message-circle"}
  Too high a degree of multiprogramming for the memory available: the sum of
  the processes' working sets exceeds the number of frames. With global
  replacement, processes steal frames from each other and all fault constantly.
  A naive scheduler seeing low CPU use admits more processes, which makes it
  worse.
  :::

  :::accordion-item{label="How do you prevent or fix thrashing?" icon="i-lucide-message-circle"}
  Reduce the degree of multiprogramming (suspend or swap out whole processes),
  use the working-set model to only run processes whose working sets fit, control
  page-fault frequency by giving frames to processes faulting too often, use local
  replacement, and in the end add RAM. In application code, reduce the working
  set: stream rather than load everything.
  :::

  :::accordion-item{label="What is the working set model?" icon="i-lucide-message-circle"}
  The working set WS(t, Δ) is the set of distinct pages referenced in the last
  Δ references. It approximates the program's current locality. If the sum of
  working-set sizes exceeds available frames, the operating system suspends a
  process. Choosing Δ is the trade-off: too small misses the locality, too large
  spans several.
  :::

  :::accordion-item{label="What is locality of reference?" icon="i-lucide-message-circle"}
  Programs tend to access a small set of addresses repeatedly (temporal
  locality: the same data again soon) and addresses near recent ones (spatial
  locality: the next array element). It is why caches, TLBs, paging and the
  working-set model all work.
  :::
::
