Memory is full, a page fault needs a frame, and one page has to go. The rule
that picks it is the **page replacement algorithm**, and the only thing that
matters is how many page faults it causes: evict a page that is needed again
immediately and you pay for another fault straight away.

## Why this matters in a job

Page replacement is the memory question that is asked as arithmetic: "reference
string 7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2 with three frames; how many page
faults under FIFO, LRU and Optimal?" It takes four minutes with a grid and is
very easy to get wrong without one. "What is Belady's anomaly?" is the standard
follow-up. And LRU, as an idea, is what every cache you will ever write uses.

## Three ways to choose a victim

Think of a desk in the library with room for three books, and a stack of books
you will need in a known order. When the desk is full and you need a fourth:

- **FIFO** (first in, first out): put back the book that has been on the desk
  longest, whether you have used it recently or not.
- **LRU** (least recently used): put back the book you have not opened for the
  longest time. The recent past predicts the near future.
- **Optimal**: put back the book you will not need again for the longest time.
  Perfect, and impossible in real life, because it needs to see the future.

Optimal (also called OPT or MIN) cannot be implemented, but it gives the
**minimum possible** number of faults, so it is the yardstick the others are
measured against.

### The worked string

Reference string: **7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2**. Three frames, all
empty at the start. F marks a page fault. The first three references always
fault (the frames are empty): these are **compulsory** misses.

**FIFO: 10 faults**

| Reference | 7 | 0 | 1 | 2 | 0 | 3 | 0 | 4 | 2 | 3 | 0 | 3 | 2 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Frame 1 | 7 | 7 | 7 | 2 | 2 | 2 | 2 | 4 | 4 | 4 | 0 | 0 | 0 |
| Frame 2 |  | 0 | 0 | 0 | 0 | 3 | 3 | 3 | 2 | 2 | 2 | 2 | 2 |
| Frame 3 |  |  | 1 | 1 | 1 | 1 | 0 | 0 | 0 | 3 | 3 | 3 | 3 |
| Fault? | F | F | F | F |  | F | F | F | F | F | F |  |  |

At reference 3 the oldest page is 0 (loaded second), so 0 goes, even though it
was used one step earlier. FIFO does not care about use, only arrival. 0 is
needed again immediately: another fault.

**LRU: 9 faults**

| Reference | 7 | 0 | 1 | 2 | 0 | 3 | 0 | 4 | 2 | 3 | 0 | 3 | 2 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Frame 1 | 7 | 7 | 7 | 2 | 2 | 2 | 2 | 4 | 4 | 4 | 0 | 0 | 0 |
| Frame 2 |  | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 3 | 3 | 3 | 3 |
| Frame 3 |  |  | 1 | 1 | 1 | 3 | 3 | 3 | 2 | 2 | 2 | 2 | 2 |
| Fault? | F | F | F | F |  | F |  | F | F | F | F |  |  |

At reference 3, the frames hold 2, 0, 1. Looking **back**: 0 was used one step
ago, 2 two steps ago, 1 three steps ago. So 1 goes, and 0 stays, which saves the
fault FIFO took on the next reference.

**Optimal: 7 faults**

| Reference | 7 | 0 | 1 | 2 | 0 | 3 | 0 | 4 | 2 | 3 | 0 | 3 | 2 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Frame 1 | 7 | 7 | 7 | 2 | 2 | 2 | 2 | 2 | 2 | 2 | 2 | 2 | 2 |
| Frame 2 |  | 0 | 0 | 0 | 0 | 0 | 0 | 4 | 4 | 4 | 0 | 0 | 0 |
| Frame 3 |  |  | 1 | 1 | 1 | 3 | 3 | 3 | 3 | 3 | 3 | 3 | 3 |
| Fault? | F | F | F | F |  | F |  | F |  |  | F |  |  |

At reference 4, the frames hold 2, 0, 3. Looking **forward**: 2 is next needed
at position 9, 3 at position 10, 0 at position 11. So 0, the one needed furthest
in the future, goes. If a page is never needed again, it is the perfect victim.

| Algorithm | Faults | Hit ratio |
| --- | --- | --- |
| FIFO | 10 | 3 / 13 = 23% |
| LRU | 9 | 4 / 13 = 31% |
| Optimal | **7** | 6 / 13 = 46% |

### Belady's anomaly

You would expect more frames to mean fewer faults. For FIFO, not always. Take
the string **1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5**:

| Frames | FIFO faults |
| --- | --- |
| 3 | **9** |
| 4 | **10** |

One more frame, one more fault. That is **Belady's anomaly**. It happens to FIFO
because the set of pages in memory with 4 frames is not always a superset of the
set with 3. LRU and Optimal are **stack algorithms** (the pages held with n
frames are always a subset of those held with n + 1), so they can never show it.

## How it works

All three algorithms, counting faults on both strings:

```java [PageReplacement.java]
import java.util.ArrayList;
import java.util.List;

public class PageReplacement {
  public static void main(String[] args) {
    int[] refs = {7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2};
    for (String alg : new String[] {"FIFO", "LRU", "Optimal"}) {
      System.out.printf("%-8s %d faults%n", alg, faults(refs, 3, alg));
    }
    int[] belady = {1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5};
    System.out.println("FIFO, 3 frames: " + faults(belady, 3, "FIFO") + " faults");
    System.out.println("FIFO, 4 frames: " + faults(belady, 4, "FIFO") + " faults");
  }

  static int faults(int[] refs, int frames, String alg) {
    List<Integer> memory = new ArrayList<>();   // FIFO: oldest first. LRU: least recent first.
    int faults = 0;
    for (int i = 0; i < refs.length; i++) {
      int page = refs[i];
      if (memory.contains(page)) {
        if (alg.equals("LRU")) {                // a hit makes it the most recently used
          memory.remove(Integer.valueOf(page));
          memory.add(page);
        }
        continue;
      }
      faults++;
      if (memory.size() == frames) {
        if (alg.equals("Optimal")) memory.remove(furthestUse(memory, refs, i));
        else memory.remove(0);                  // FIFO and LRU both evict the front
      }
      memory.add(page);
    }
    return faults;
  }

  /** Index in memory of the page whose next use is furthest away (or never). */
  static int furthestUse(List<Integer> memory, int[] refs, int now) {
    int victim = 0, furthest = -1;
    for (int m = 0; m < memory.size(); m++) {
      int next = Integer.MAX_VALUE;
      for (int j = now + 1; j < refs.length; j++) {
        if (refs[j] == memory.get(m)) { next = j; break; }
      }
      if (next > furthest) { furthest = next; victim = m; }
    }
    return victim;
  }
}
```

```text [Output]
FIFO     10 faults
LRU      9 faults
Optimal  7 faults
FIFO, 3 frames: 9 faults
FIFO, 4 frames: 10 faults
```

The only difference between FIFO and LRU in the code is the three lines that
move a page to the back of the list on a hit. That is the whole difference in
the algorithms, too.

## Real use case

True LRU is too expensive for an operating system (it would need to record a
timestamp on every memory access), so kernels approximate it. The classic
approximation is the **second-chance** or **clock** algorithm: each page has a
**reference bit** that the hardware sets on use; the kernel sweeps round the
frames like a clock hand, clearing set bits and evicting the first page whose
bit is already clear. Linux uses two lists, active and inactive, which is the
same idea.

In application code, LRU is the default cache policy, and Java has it built in.
`LinkedHashMap` with access order is an LRU cache in five lines:

```java [RecentStudents.java]
Map<String, Student> recent = new LinkedHashMap<>(16, 0.75f, true) {   // true = access order
  @Override
  protected boolean removeEldestEntry(Map.Entry<String, Student> eldest) {
    return size() > 3;                        // three "frames"
  }
};
recent.put("CS101", asha);
recent.put("CS102", bilal);
recent.put("CS103", chitra);
recent.get("CS101");                           // Asha is now most recently used
recent.put("CS104", dev);                      // evicts CS102, the least recently used
System.out.println(recent.keySet());
```

```text [Output]
[CS103, CS101, CS104]
```

"Implement an LRU cache" is also one of the most common coding questions in
product-company interviews, and this is the answer they hope you know exists
before you write the hash map plus doubly linked list version by hand.

## What confuses people here

Looking the wrong way. **LRU looks backwards** (which page was used longest
ago?). **Optimal looks forwards** (which page will be used furthest in the
future?). **FIFO looks at neither**, only at when the page was loaded; a hit does
not change a page's place in the FIFO queue. Most wrong answers apply the right
rule in the wrong direction, so write "back" or "forward" above your grid before
you start.

## Interview questions

::accordion
  :::accordion-item{label="Compare FIFO, LRU and Optimal page replacement." icon="i-lucide-message-circle"}
  FIFO evicts the page loaded earliest: simple, ignores usage, suffers Belady's
  anomaly. LRU evicts the page unused for the longest time: good in practice,
  expensive to implement exactly, approximated by the clock algorithm. Optimal
  evicts the page not needed for the longest time in the future: minimum faults,
  impossible to implement, used as a benchmark. On 7, 0, 1, 2, 0, 3, 0, 4, 2, 3,
  0, 3, 2 with three frames: 10, 9 and 7 faults.
  :::

  :::accordion-item{label="What is Belady's anomaly?" icon="i-lucide-message-circle"}
  Increasing the number of frames increases the number of page faults, which
  can happen with FIFO. Reference string 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5: 9
  faults with 3 frames, 10 with 4. LRU and Optimal are stack algorithms and never
  show it.
  :::

  :::accordion-item{label="Why is Optimal page replacement not used?" icon="i-lucide-message-circle"}
  It needs to know the future reference string, which the operating system
  cannot know. It is used to measure how close a practical algorithm comes to the
  best possible.
  :::

  :::accordion-item{label="How is LRU approximated in real operating systems?" icon="i-lucide-message-circle"}
  With a hardware-set reference bit per page. The second-chance (clock)
  algorithm cycles through frames: if the bit is 1, clear it and move on (a
  second chance); if 0, evict. Pages used recently survive a full sweep.
  :::

  :::accordion-item{label="How would you implement an LRU cache in Java?" icon="i-lucide-message-circle"}
  `LinkedHashMap` with `accessOrder = true` and `removeEldestEntry` returning
  `size() > capacity`. By hand: a `HashMap` from key to node plus a doubly linked
  list ordered by use, so get and put are both O(1): move the node to the front
  on access, remove from the tail when full.
  :::
::
