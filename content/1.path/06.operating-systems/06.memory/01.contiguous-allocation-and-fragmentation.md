The simplest way to share memory is to give each process one continuous block
of it, wherever there is a gap large enough. That is **contiguous allocation**,
and it produces a kind of waste that no amount of cleverness removes. The fix
for that waste, paging, is the next lesson; this one is why it was needed.

## Why this matters in a job

"What is the difference between internal and external fragmentation?" is one of
the standard memory questions, and first fit / best fit / worst fit is a regular
numerical question in written rounds: given holes and processes, where does each
one go? It also explains, once you see it, why your Java heap needs a garbage
collector that moves objects around.

## One block each

Think of the long benches in an exam hall. Students from one class must sit
together on one bench. Early on it is easy. After a few classes have come and
gone, there are gaps of two seats here and three seats there. A class of five
arrives. There are nine empty seats in the hall, and nowhere for five people to
sit together.

That is exactly **external fragmentation**: enough free memory in total, but
not in one piece.

The real thing. Memory has free blocks, called **holes**, of different sizes.
When a process arrives the operating system picks a hole at least as big as the
process, gives it what it needs, and leaves the rest as a smaller hole. Three
ways to pick:

| Strategy | Picks | Idea |
| --- | --- | --- |
| **First fit** | The first hole big enough | Fastest to search |
| **Best fit** | The smallest hole big enough | Leaves the smallest leftover |
| **Worst fit** | The largest hole | Leaves the biggest leftover, hoping it stays useful |

### The worked example

Holes of **100, 500, 200, 300 and 600 KB**, in that order. Processes arrive
needing **212, 417, 112 and 426 KB**.

| Process | First fit | Best fit | Worst fit |
| --- | --- | --- | --- |
| 212 KB | 500 hole → 288 left | 300 hole → 88 left | 600 hole → 388 left |
| 417 KB | 600 hole → 183 left | 500 hole → 83 left | 500 hole → 83 left |
| 112 KB | 288 hole → 176 left | 200 hole → 88 left | 388 hole → 276 left |
| 426 KB | **must wait** | 600 hole → 174 left | **must wait** |

Best fit places all four here. Under first fit, the 426 KB process waits while
**959 KB** is free in total (100 + 176 + 200 + 300 + 183): external
fragmentation, measured. Best fit is not always the winner (it tends to leave
many tiny useless holes), which is why exam answers say "depends on the
sequence" and then show the working.

### Two kinds of waste

::compare{caption="The difference interviewers check: where the wasted memory is."}
  :::compare-side{label="Internal fragmentation" verdict="neutral"}
  Waste **inside** an allocated block. Memory is handed out in fixed sizes, a
  process gets more than it asked for, and the extra is unusable by anyone.
  Ask for 18 KB from fixed 20 KB partitions: 2 KB wasted inside yours.
  :::
  :::compare-side{label="External fragmentation" verdict="neutral"}
  Waste **between** allocated blocks. Plenty free in total, split into holes too
  small for any request. The first-fit example above: 959 KB free, 426 KB
  cannot be placed.
  :::
::

Fixes: **compaction** moves every process down to squeeze the holes into one
(expensive, and only possible if addresses can be changed while running), or
stop requiring one continuous block at all, which is paging.

## How it works

The three strategies as one Java program, on the same holes and processes:

```java [Placement.java]
public class Placement {
  public static void main(String[] args) {
    for (String strategy : new String[] {"First fit", "Best fit", "Worst fit"}) {
      int[] holes = {100, 500, 200, 300, 600};           // KB, in memory order
      int[] processes = {212, 417, 112, 426};
      System.out.println(strategy);
      for (int size : processes) {
        int chosen = -1;
        for (int i = 0; i < holes.length; i++) {
          if (holes[i] < size) continue;
          if (chosen == -1
              || (strategy.equals("Best fit")  && holes[i] < holes[chosen])
              || (strategy.equals("Worst fit") && holes[i] > holes[chosen])) {
            chosen = i;
            if (strategy.equals("First fit")) break;
          }
        }
        if (chosen == -1) {
          System.out.println("  " + size + " KB -> must wait");
        } else {
          System.out.printf("  %d KB -> hole %d (%d KB), %d KB left%n",
              size, chosen + 1, holes[chosen], holes[chosen] - size);
          holes[chosen] -= size;
        }
      }
    }
  }
}
```

```text [Output]
First fit
  212 KB -> hole 2 (500 KB), 288 KB left
  417 KB -> hole 5 (600 KB), 183 KB left
  112 KB -> hole 2 (288 KB), 176 KB left
  426 KB -> must wait
Best fit
  212 KB -> hole 4 (300 KB), 88 KB left
  417 KB -> hole 2 (500 KB), 83 KB left
  112 KB -> hole 3 (200 KB), 88 KB left
  426 KB -> hole 5 (600 KB), 174 KB left
Worst fit
  212 KB -> hole 5 (600 KB), 388 KB left
  417 KB -> hole 2 (500 KB), 83 KB left
  112 KB -> hole 5 (388 KB), 276 KB left
  426 KB -> must wait
```

## Real use case

Operating systems stopped allocating whole processes contiguously decades ago,
but the problem moved inside your process. The Java heap is one big region, and
objects are allocated in it contiguously. After millions of objects have been
created and collected, free space is scattered in small holes. Java's garbage
collectors solve this the way the textbook says: **compaction**. They move live
objects together and update every reference to them, so new objects can be
allocated from one large free block with a single pointer bump.

That is also why a `new int[50_000_000]` can throw `OutOfMemoryError` on a heap
that reports more than 200 MB free: an array must be contiguous, and if the
collector cannot compact enough space in one piece, the allocation fails.

```bash [Terminal]
# Ask the JVM to show when it compacts (G1 collector, Java 17+).
java -Xmx512m -Xlog:gc ReportBuilder
```

```text [Output, trimmed]
[0.412s][info][gc] GC(3) Pause Young (Normal) (G1 Evacuation Pause) 187M->42M(512M) 6.1ms
[2.905s][info][gc] GC(9) Pause Full (G1 Compaction Pause) 498M->301M(512M) 212.4ms
```

"Evacuation" and "Compaction" are both the collector copying live objects
together to remove fragmentation.

## What confuses people here

Which fragmentation paging fixes. Paging **eliminates external fragmentation**
(any free frame can hold any page, so there are no unusable holes between
processes) and **introduces a little internal fragmentation** (the last page of
a process is, on average, half empty). Segmentation, two lessons from now, does
the opposite. Getting that pair the right way round is the most common memory
question.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between internal and external fragmentation?" icon="i-lucide-message-circle"}
  Internal: wasted space inside an allocated block, because blocks come in fixed
  sizes larger than the request. External: enough free memory in total but split
  into holes too small for a request. Fixed partitions and paging suffer
  internal; variable partitions and segmentation suffer external.
  :::

  :::accordion-item{label="Explain first fit, best fit and worst fit." icon="i-lucide-message-circle"}
  First fit takes the first hole large enough (fast). Best fit takes the
  smallest hole large enough (least leftover, but leaves tiny unusable holes and
  must search everything). Worst fit takes the largest (leaves big leftovers).
  In simulations first fit and best fit beat worst fit on utilisation, and first
  fit is faster.
  :::

  :::accordion-item{label="What is compaction, and what does it require?" icon="i-lucide-message-circle"}
  Moving allocated blocks together so all free memory forms one large hole. It
  requires **dynamic relocation** (addresses translated at run time, so a process
  can be moved while it runs) and is expensive because everything must be copied.
  Java's garbage collectors compact the heap.
  :::

  :::accordion-item{label="Holes of 100, 500, 200, 300, 600 KB; processes 212, 417, 112, 426 KB. Which strategy places all four?" icon="i-lucide-message-circle"}
  Best fit: 212 → 300, 417 → 500, 112 → 200, 426 → 600. First fit and worst fit
  both leave the 426 KB process waiting, even though 959 KB (first fit) is free
  in total.
  :::
::
