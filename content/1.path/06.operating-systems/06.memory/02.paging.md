Cut every process into small equal pieces called **pages**, cut physical memory
into pieces of the same size called **frames**, and put any page in any free
frame. The table that records which page went into which frame is the **page
table**, and with it external fragmentation disappears entirely.

## Why this matters in a job

Paging is the centre of every memory-management question: "what is paging?",
"what is a page table?", "what is a TLB?", and in written rounds "translate this
logical address" or "compute the effective access time". It is also the
mechanism underneath virtual memory, the next-but-one lesson, which is how every
program you will ever run sees memory.

## Pages, frames and a table

Think of the college library's book storage. Instead of keeping each subject's
books together on one shelf (which leaves gaps nobody's subject fits into),
every book goes into whichever numbered slot is free. A register at the desk
says "Operating Systems, book 3, is in slot 7". A student asks for "book 3 of
Operating Systems"; the librarian looks up the register and walks to slot 7. The
student never needs to know the slot numbers.

The real thing:

- The **logical address** (what the program uses) is split into a **page
  number** `p` and an **offset** `d` within the page.
- The page table maps `p` to a **frame number** `f`.
- The **physical address** is frame `f`, same offset `d`.

```text [The formula]
page number   p = logical address ÷ page size   (whole number part)
offset        d = logical address mod page size
physical address = f × page size + d            (where f = pageTable[p])
```

### Translation by hand, in decimal

Page size **1 KB = 1,024 bytes**. A process's page table:

| Page | Frame |
| --- | --- |
| 0 | 5 |
| 1 | 2 |
| 2 | 9 |
| 3 | 7 |

Translate logical address **3,500**:

1. p = 3500 ÷ 1024 = **3** (3 × 1024 = 3072, and 4 × 1024 = 4096 is too big).
2. d = 3500 - 3072 = **428**.
3. pageTable[3] = frame **7**.
4. Physical = 7 × 1024 + 428 = 7168 + 428 = **7,596**.

### The same thing in binary

Page sizes are always powers of two, so the split is only a matter of bits. With a 16-bit
logical address and 4 KB pages (4,096 = 2¹² bytes), the low **12 bits** are the
offset and the high **4 bits** are the page number.

```text [Binary translation]
logical address  0x3ABC  =  0011 | 1010 1011 1100
                            page    offset
                            = 3     = 0xABC

pageTable[3] = 7  = 0111

physical address         =  0111 | 1010 1011 1100  =  0x7ABC
```

The offset bits are copied across unchanged. Only the top bits are looked up.
That is why the hardware can do it on every single memory access.

### The TLB, and why paging is not slow

Every memory access now needs **two** memory accesses: one to read the page
table, one for the data. That would halve the speed of every program. The fix is
a small, very fast hardware cache of recent translations, the **translation
lookaside buffer (TLB)**. Programs touch the same few pages over and over, so
nearly every lookup hits the TLB.

The sum that gets asked: TLB lookup 20 ns, memory access 100 ns, TLB hit ratio
80%.

```text [Effective access time]
hit:   20 (TLB) + 100 (data)               = 120 ns
miss:  20 (TLB) + 100 (table) + 100 (data) = 220 ns

EAT = 0.80 × 120 + 0.20 × 220 = 96 + 44 = 140 ns
```

140 ns against 100 ns with no paging: a 40% slowdown at 80% hits. Real TLBs hit
well over 99% of the time, which makes the cost close to nothing.

## How it works

The translation as a program, including what happens with an address beyond the
end of the table:

```java [Translate.java]
public class Translate {
  static final int PAGE_SIZE = 1024;
  static final int[] pageTable = {5, 2, 9, 7};      // page -> frame

  public static void main(String[] args) {
    for (int logical : new int[] {0, 1023, 1024, 3500, 5000}) {
      int page = logical / PAGE_SIZE;
      int offset = logical % PAGE_SIZE;
      if (page >= pageTable.length) {
        System.out.printf("%5d -> page %d is not in the table: trap to the kernel%n", logical, page);
        continue;
      }
      int frame = pageTable[page];
      int physical = frame * PAGE_SIZE + offset;
      System.out.printf("%5d -> page %d, offset %4d -> frame %d -> %5d%n",
          logical, page, offset, frame, physical);
    }
  }
}
```

```text [Output]
    0 -> page 0, offset    0 -> frame 5 ->  5120
 1023 -> page 0, offset 1023 -> frame 5 ->  6143
 1024 -> page 1, offset    0 -> frame 2 ->  2048
 3500 -> page 3, offset  428 -> frame 7 ->  7596
 5000 -> page 4 is not in the table: trap to the kernel
```

Logical addresses 1023 and 1024 are neighbours, and they end up in completely
different parts of physical memory. The program never knows.

## Real use case

Every modern machine pages, with 4 KB as the usual page size. You can ask yours:

```bash [Terminal]
getconf PAGESIZE
```

```text [Output]
4096
```

(Apple Silicon Macs print 16384: 16 KB pages.)

Page tables are big. A 32-bit address space with 4 KB pages has 2²⁰ pages, about
a million entries; at 4 bytes each, 4 MB of page table per process. So real
systems use **multi-level page tables** (a table of page tables, where unused
parts of the address space need no table at all). And databases care about page
size directly: PostgreSQL stores tables in 8 KB pages and MySQL's InnoDB in
16 KB pages, and "how many pages did this query read" is how their query plans
measure cost.

## What confuses people here

Pages and frames. A **page** is a piece of a process's logical memory; a
**frame** is a piece of physical RAM of the same size. Pages are placed into
frames. There is one page table **per process** (that is what keeps processes
apart), not one for the whole machine.

And paging has fragmentation too: internal, in the last page of each process.
With 4 KB pages a process of 10,000 bytes needs 3 pages (12,288 bytes) and wastes
2,288 bytes inside the last one.

## Interview questions

::accordion
  :::accordion-item{label="What is paging?" icon="i-lucide-message-circle"}
  A memory-management scheme that divides logical memory into fixed-size pages
  and physical memory into frames of the same size, and maps pages to any free
  frames through a per-process page table. It removes external fragmentation and
  the need for contiguous allocation, at the cost of a table lookup (made fast
  by the TLB) and some internal fragmentation in the last page.
  :::

  :::accordion-item{label="With 1 KB pages and page 3 in frame 7, what is the physical address of logical address 3500?" icon="i-lucide-message-circle"}
  Page = 3500 ÷ 1024 = 3, offset = 3500 - 3072 = 428. Physical = 7 × 1024 + 428
  = 7596.
  :::

  :::accordion-item{label="What is a TLB?" icon="i-lucide-message-circle"}
  The translation lookaside buffer: a small, fast hardware cache of recent
  page-to-frame translations. On a hit, translation needs no memory access; on a
  miss, the page table is read and the TLB updated. It is flushed (or tagged by
  process) on a context switch, which is part of why process switches cost more
  than thread switches.
  :::

  :::accordion-item{label="TLB 20 ns, memory 100 ns, hit ratio 80%. What is the effective access time?" icon="i-lucide-message-circle"}
  0.8 × (20 + 100) + 0.2 × (20 + 100 + 100) = 96 + 44 = 140 ns.
  :::

  :::accordion-item{label="Why are page tables multi-level?" icon="i-lucide-message-circle"}
  A single-level table for a 32-bit space with 4 KB pages needs a million
  entries (4 MB) per process, most of them for addresses the process never
  uses. A two-level table only allocates second-level tables for regions
  actually in use. 64-bit systems use four or five levels.
  :::
::
