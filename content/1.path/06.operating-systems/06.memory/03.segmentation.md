A programmer does not see a program as equal 4 KB slices. They see code, global
data, a stack and a heap, each a different size. **Segmentation** divides memory
along exactly those lines: each part of the program is a **segment** of whatever
length it needs, and each segment can be placed anywhere in memory on its own.

## Why this matters in a job

"Paging versus segmentation" is one of the most common memory questions, and a
segment-table translation with a base and a limit is a standard written-round
problem, usually with one address that is out of range to see if you notice. It
is also where the phrase "segmentation fault" comes from, which you will see
every time a C or C++ program crashes.

## Segments of different sizes

Think of the college's filing cabinet. Each student's file has separate folders:
application, marksheets, fee receipts, certificates. Each folder is as thick as
it needs to be, and they can be kept in different drawers. To find "page 3 of
the fee receipts folder", you look up where that folder is kept and count three
pages in; if the folder only has two pages, the request is wrong and you say so.

The real thing:

- A logical address is a pair: **(segment number, offset)**.
- The **segment table** has, for each segment, a **base** (where it starts in
  physical memory) and a **limit** (how long it is).
- If offset < limit, physical address = base + offset. Otherwise the hardware
  **traps**: an addressing error, delivered to the process as a segmentation
  fault.

### Translation by hand

The classic segment table:

| Segment | Holds | Base | Limit |
| --- | --- | --- | --- |
| 0 | code | 1400 | 1000 |
| 1 | stack | 6300 | 400 |
| 2 | global data | 4300 | 400 |
| 3 | heap | 3200 | 1100 |
| 4 | symbol table | 4700 | 1000 |

- **(2, 53)**: 53 < 400, so physical = 4300 + 53 = **4353**.
- **(3, 852)**: 852 < 1100, so physical = 3200 + 852 = **4052**.
- **(0, 1222)**: 1222 ≥ 1000. **Trap.** The code segment is only 1,000 bytes
  long, so this address does not exist.

Check the limit first, every time. That third case is the one the question is
really asking.

## How it works

```java [Segments.java]
public class Segments {
  static final int[] base  = {1400, 6300, 4300, 3200, 4700};
  static final int[] limit = {1000,  400,  400, 1100, 1000};

  public static void main(String[] args) {
    int[][] addresses = {{2, 53}, {3, 852}, {0, 1222}, {1, 399}};
    for (int[] a : addresses) {
      int segment = a[0], offset = a[1];
      if (offset >= limit[segment]) {
        System.out.printf("(%d, %4d) -> trap: offset beyond limit %d%n",
            segment, offset, limit[segment]);
      } else {
        System.out.printf("(%d, %4d) -> %d%n", segment, offset, base[segment] + offset);
      }
    }
  }
}
```

```text [Output]
(2,   53) -> 4353
(3,  852) -> 4052
(0, 1222) -> trap: offset beyond limit 1000
(1,  399) -> 6699
```

### Paging and segmentation side by side

| | Paging | Segmentation |
| --- | --- | --- |
| Pieces | Fixed size (pages) | Variable size (segments) |
| Divided by | The hardware, blindly | The program's logical structure |
| Visible to the programmer | No | Yes |
| Address | Single number, split into page and offset | Pair: (segment, offset) |
| Table entry | Frame number | Base and limit |
| Fragmentation | **Internal** (last page) | **External** (holes between segments) |
| Protection and sharing | Per page | Per segment: natural (share the code segment, make it read-only) |

Real systems on x86 historically combined them, **segmentation with paging**:
each segment is itself paged, so segments give the logical structure and
protection, and pages remove external fragmentation.

## Real use case

The name survived longer than the mechanism. Modern 64-bit Linux, Windows and
macOS use a flat memory model: segmentation is effectively switched off and
everything is done with paging. But the protection error kept its name: when a
C program touches memory it is not allowed to, the kernel sends it `SIGSEGV`,
"segmentation violation".

```c [results.c]
#include <stdio.h>

int main(void) {
    int *marks = NULL;          /* points at address 0, which no process may touch */
    printf("First mark: %d\n", marks[0]);
    return 0;
}
```

```bash [Terminal]
gcc results.c -o results && ./results
```

```text [Output]
Segmentation fault (core dumped)
```

In Java you never see this, because the JVM checks for `null` first and throws
`NullPointerException` instead. When you do see a JVM crash with `SIGSEGV` in
the log, it came from native code underneath Java, not from your Java code.

## What confuses people here

Which fragmentation goes with which. Paging: fixed-size pieces, so a little
wasted **inside** the last one (internal). Segmentation: variable-size pieces
placed into holes, so wasted space **between** them (external), exactly like the
contiguous allocation lesson, only per segment instead of per process.

## Interview questions

::accordion
  :::accordion-item{label="What is segmentation?" icon="i-lucide-message-circle"}
  A memory-management scheme where a program's address space is divided into
  variable-sized logical segments (code, data, stack, heap). Addresses are
  (segment, offset) pairs, translated through a segment table of base and limit
  values, with a trap if offset ≥ limit.
  :::

  :::accordion-item{label="What is the difference between paging and segmentation?" icon="i-lucide-message-circle"}
  Paging uses fixed-size pages invisible to the programmer and suffers internal
  fragmentation. Segmentation uses variable-size logical units visible to the
  programmer, gives natural protection and sharing per segment, and suffers
  external fragmentation. Segmentation with paging combines both.
  :::

  :::accordion-item{label="Segment 0 has base 1400 and limit 1000. Translate (0, 1222)." icon="i-lucide-message-circle"}
  1222 ≥ 1000, so it is an addressing error: the hardware traps to the operating
  system and the process receives a segmentation fault. No physical address is
  produced.
  :::

  :::accordion-item{label="What is a segmentation fault?" icon="i-lucide-message-circle"}
  The signal (`SIGSEGV`) a process gets when it accesses memory it is not
  allowed to: a null or freed pointer, an address outside its segments or
  pages, or a write to read-only memory. The name comes from segmentation; on
  modern systems it is usually a page-table check that fails.
  :::
::
