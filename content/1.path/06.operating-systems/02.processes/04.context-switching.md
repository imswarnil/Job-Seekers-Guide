Thousands of times a second, the kernel stops whatever is running, writes its
state into its PCB, and loads somebody else's. That is a **context switch**, and
it is the reason one processor can look like forty. It is also not free, and the
cost explains a mistake almost every team makes once.

## Why this matters in a job

"What is a context switch?" is asked in nearly every operating systems round,
usually right after the PCB, because it is the reason the PCB exists. At work it
is the reason "add more threads" sometimes makes a service slower, and
being able to say why puts you ahead of most people in that meeting.

## Saving one, loading another

Think of an invigilator marking answer sheets during an exam. A student raises
a hand. The invigilator puts a pencil mark where they stopped on the current
sheet, goes to help, and comes back to that exact line. The pencil mark is the
saved context. The walk across the hall is the overhead: time spent marking
nothing.

The real thing, step by step:

::flow{numbered direction="vertical" caption="A context switch. Between any two of your instructions, all of this can happen."}
  :::flow-step{label="Something triggers it" icon="i-lucide-timer"}
  The timer interrupt fires because the time slice is over, or the running
  process makes a blocking system call (a disk read), or a higher-priority
  process becomes ready.
  :::
  :::flow-step{label="The kernel saves the old context" icon="i-lucide-save"}
  Program counter and every register go into the old process's PCB. Its state
  becomes ready or waiting.
  :::
  :::flow-step{label="The scheduler chooses" icon="i-lucide-list-checks" highlight}
  Who runs next, from the ready queue. The next chapter is entirely about how.
  :::
  :::flow-step{label="The kernel loads the new context" icon="i-lucide-upload"}
  Registers and program counter from the new PCB. For a different process, its
  page table is switched in too.
  :::
  :::flow-step{label="Resume" icon="i-lucide-play"}
  The chosen process continues on the exact instruction it was stopped at, with
  no knowledge that forty other programs ran in between.
  :::
::

The time spent in steps two to four is **pure overhead**: no process does any
useful work during it. A switch costs a few microseconds directly. The larger
cost is indirect: the new process finds the processor's caches full of the old
one's data, and runs slowly for a while until they refill. A switch between two
threads of the **same** process is cheaper, because the memory map stays the
same.

::compare{caption="Two words that get used interchangeably and are not the same."}
  :::compare-side{label="Concurrency" verdict="neutral"}
  Several things **in progress** at once. Achievable on a single core by
  context switching fast. A single-core laptop in 2005 was concurrent.
  :::
  :::compare-side{label="Parallelism" verdict="neutral"}
  Several things **executing** at the same instant. Needs more than one core.
  Eight cores means at most eight-way parallelism, however many threads you
  start.
  :::
::

## How it works

You can count context switches. On Linux, every process has two counters:
**voluntary** switches (it blocked and gave the processor up) and
**involuntary** ones (the scheduler took it away).

```bash [Terminal]
# Linux: the two counters for your own shell
grep ctxt /proc/$$/status
```

```text [Output]
voluntary_ctxt_switches:        412
nonvoluntary_ctxt_switches:     9
```

A shell spends its life waiting for you to type, so nearly all its switches are
voluntary. A program crunching numbers shows the opposite.

The cost shows up when you start far more processor-bound threads than cores.
This program totals marks for a million students, split across a pool of
threads, and times it with different pool sizes:

```java [PoolSize.java]
import java.util.concurrent.*;

public class PoolSize {
  static long totalMarks(int from, int to) {
    long sum = 0;
    for (int roll = from; roll < to; roll++) {
      sum += (roll * 37L) % 101;           // stand-in for real per-student work
    }
    return sum;
  }

  public static void main(String[] args) throws Exception {
    int students = 400_000_000;
    for (int threads : new int[] {8, 64, 2000}) {
      ExecutorService pool = Executors.newFixedThreadPool(threads);
      int chunk = students / threads;
      long start = System.nanoTime();
      var parts = new java.util.ArrayList<Future<Long>>();
      for (int t = 0; t < threads; t++) {
        int from = t * chunk, to = from + chunk;
        parts.add(pool.submit(() -> totalMarks(from, to)));
      }
      long total = 0;
      for (var f : parts) total += f.get();
      pool.shutdown();
      System.out.printf("%5d threads: %d ms%n", threads,
          (System.nanoTime() - start) / 1_000_000);
    }
  }
}
```

```text [Output, an 8-core laptop, illustrative]
    8 threads: 410 ms
   64 threads: 436 ms
 2000 threads: 690 ms
```

The work is identical in all three runs. Eight cores can only ever run eight at
once, so the extra threads buy nothing but switching and stack memory. Your
numbers will differ; the shape will not.

## Real use case

::real-life{title="The service that got slower when it was given more threads" source="A load test"}
Response times were poor, so somebody raised the thread pool from 50 to 500. It
got worse. The work was processor-bound on an eight-core machine, so 500 threads
meant the same total work plus enormous context-switching overhead and far more
memory for stacks. Going down to 16 was faster than either. The rule of thumb:
for processor-bound work, about the number of cores; for work that spends its
time waiting on a database or a network, many more, because those threads are
waiting and not competing.
::

That rule is how thread pools are sized in real code:

```java [Pools.java]
int cores = Runtime.getRuntime().availableProcessors();

// Report generation: pure calculation, so roughly one thread per core.
ExecutorService reportPool = Executors.newFixedThreadPool(cores);

// Sending fee reminders: each task mostly waits on an email server.
ExecutorService reminderPool = Executors.newFixedThreadPool(cores * 8);
```

## What confuses people here

That a thread is "running" most of the time. It is not, and this is why an
application server can handle hundreds of simultaneous requests on eight cores:
nearly all of those threads are waiting for a database, and a waiting thread
costs no processor time and causes no involuntary switches.

A second one: a **mode switch** (your program entering the kernel for a system
call and returning) is not a context switch. No other process is loaded. It only
becomes one if the system call blocks and the scheduler picks somebody else.

## Interview questions

::accordion
  :::accordion-item{label="What is a context switch?" icon="i-lucide-message-circle"}
  Saving the state of the running process or thread (program counter,
  registers) into its PCB and loading another's, so the processor can run the
  other one. Triggered by a timer interrupt, a blocking system call, or a
  higher-priority process becoming ready. It is overhead: no useful work happens
  during it.
  :::

  :::accordion-item{label="Why is a thread switch cheaper than a process switch?" icon="i-lucide-message-circle"}
  Threads of one process share the same memory map, so the page table does not
  change and the memory caches stay useful. A process switch changes the page
  table, which invalidates the address-translation cache (the TLB) and leaves the
  new process with cold caches.
  :::

  :::accordion-item{label="What is the difference between concurrency and parallelism?" icon="i-lucide-message-circle"}
  Concurrency: several tasks in progress, possibly interleaved on one core by
  context switching. Parallelism: several tasks executing at the same instant on
  several cores. One core can be concurrent and never parallel.
  :::

  :::accordion-item{label="How many threads should a pool have?" icon="i-lucide-message-circle"}
  For processor-bound work, about the number of cores; more only adds context
  switches. For work that waits on I/O, many more, because waiting threads do not
  compete. A common estimate is cores × (1 + wait time ÷ compute time), and the
  honest follow-up is that you measure.
  :::

  :::accordion-item{label="What is the dispatcher?" icon="i-lucide-message-circle"}
  The part of the kernel that actually hands the processor to the process the
  scheduler chose: it performs the context switch, switches to user mode and
  jumps to the right instruction. The time it takes is the **dispatch latency**.
  The scheduler decides; the dispatcher does.
  :::
::
