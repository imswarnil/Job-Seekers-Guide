The other two hundred and ninety-two are waiting, and the kernel knows exactly
what each one is waiting for. Every process is always in one of five states, and
the kernel keeps a record on each one, the **process control block**, so that it
can take the processor away and hand it back later without the process noticing.

## Why this matters in a job

"Draw the process state diagram" is one of the most common operating systems
questions in a fresher technical round, and "what is a PCB" usually follows it.
Both are easy marks if you can draw five boxes and label six arrows with their
causes. At work, the same states are what you are reading when `top` says a
process is sleeping, or a thread dump says a thread is `BLOCKED` or `WAITING`.

## Five states

Think of the college library's reading room with one reference copy of a book.
You arrive and fill in the register (**new**). You join the queue for the book
(**ready**). You get the book and read (**running**). Halfway through you have to
go and fetch a notebook from your hostel, so you hand the book back and go
(**waiting**); when you return you join the queue again, not the front of it.
When you are finished you sign out (**terminated**). And if the librarian says
your fifteen minutes are up, you go back to the queue even though you were not
finished.

That is the whole diagram. The real version:

  :::feature{icon="i-lucide-clock" title="Ready"}

  :::
  :::feature{icon="i-lucide-play" title="Running"}
  Executing on a core. At most one process per core is in this state, so eight

  :::
  :::feature{icon="i-lucide-pause" title="Waiting (blocked)"}

  a key press, a lock. Giving it a processor would be useless.
  :::
  :::feature{icon="i-lucide-square" title="Terminated"}
  Finished. Its PCB stays until the parent reads its exit status, which is the
  zombie from the boot lesson.
  :::

::warning{icon="i-lucide-alert-triangle"}
The arrow interviewers check: **Waiting goes to Ready, never straight to
Running.** When the disk read finishes, the process has to queue for the
processor like everybody else. Drawing an arrow from Waiting to Running is the
most common mistake on this diagram.
::

Some textbooks add two more states, **suspended ready** and **suspended
waiting**, for processes whose memory has been swapped out to disk entirely.
Mention them if asked for "seven states"; draw five otherwise.

### The process control block

When the scheduler takes a process off the processor, everything needed to
restart it has to be written down somewhere. That somewhere is the **PCB**, one
per process, kept in kernel memory where the process cannot touch it.

| Field in the PCB | What it holds |
| --- | --- |
| Process id (pid), parent pid | Its number and who started it |
| Process state | New, ready, running, waiting or terminated |
| Program counter | The address of the next instruction to run |
| CPU registers | Every register's value at the moment it stopped |
| Scheduling information | Priority, time used so far, which queue it is in |
| Memory-management information | Where its page table is, its memory limits |
| Open files | Its file descriptor table |
| Accounting | CPU time used, when it started, the user who owns it |

The **process table** is the kernel's list of all the PCBs. In Linux the PCB is
a C structure called `task_struct`, and it is several kilobytes long.

## How it works

You can watch the states on your own machine. The `STAT` column in `ps` is the
state, in one letter.

```bash [Terminal]
ps -eo pid,stat,comm | head -8
```

```text [Output]
  PID STAT COMMAND
    1 Ss   /sbin/launchd
  312 S    /usr/sbin/syslogd
  388 S    /usr/libexec/UserEventAgent
 8421 Ss   -zsh
 9120 R+   ps
 9001 S+   java
 7710 Z    (python3)
```

`S` is sleeping (waiting), `R` is running or ready (Linux does not separate the
two in this column), `Z` is a zombie (terminated, not yet collected), and `D` is
waiting on a disk and cannot even be interrupted. Your own `ps` is `R` because it
is the one running while it looks.

Java names the same states for its threads, and you can see a thread move
through them:

```java [ThreadStates.java]
public class ThreadStates {
  public static void main(String[] args) throws Exception {
    Thread exporter = new Thread(() -> {
      try {
        Thread.sleep(200);            // waiting for a timer, like waiting for I/O
      } catch (InterruptedException e) { }
    });

    System.out.println("before start:  " + exporter.getState());
    exporter.start();
    System.out.println("after start:   " + exporter.getState());
    Thread.sleep(50);
    System.out.println("while sleeping: " + exporter.getState());
    exporter.join();
    System.out.println("after finish:  " + exporter.getState());
  }
}
```

```text [Output]
before start:  NEW
after start:   RUNNABLE
while sleeping: TIMED_WAITING
after finish:  TERMINATED
```

`RUNNABLE` in Java covers both ready and running, exactly like `R` in `ps`,
because the JVM cannot see which of its threads the kernel has on a core at this
instant.

## Real use case

The states are what you read in a thread dump when a service is slow. A dump of a
college results service under load, cut down:

```text [jstack output, trimmed]
"http-nio-8080-exec-7" #41 RUNNABLE
    at java.net.SocketInputStream.socketRead0(Native Method)
    at org.postgresql.core.PGStream.receive(...)

"http-nio-8080-exec-8" #42 BLOCKED (on object monitor)
    - waiting to lock <0x00000007c0a1b2c8> (a ResultCache)

"http-nio-8080-exec-9" #43 BLOCKED (on object monitor)
    - waiting to lock <0x00000007c0a1b2c8> (a ResultCache)
```

Forty threads, and thirty-eight of them `BLOCKED` on the same lock. The database
was fine and the processor was idle; one `synchronized` method on a shared cache
was letting one request through at a time. Reading the states told us that in a
minute. Without them it looks like "the site is slow".

## What confuses people here

That "waiting" means "waiting for the processor". It does not. A process waiting
for the processor is **ready**. **Waiting** means waiting for something else, and
that difference decides whether adding cores would help: more cores shorten the
ready queue and do nothing at all for processes waiting on a disk.

## Interview questions

::accordion
  :::accordion-item{label="Draw the process state diagram and explain each transition." icon="i-lucide-message-circle"}
  Five states: new, ready, running, waiting, terminated. New to ready when
  admitted; ready to running when the scheduler dispatches it; running to ready
  when its time slice ends or a higher-priority process pre-empts it; running to
  waiting when it requests I/O or waits for an event; waiting to ready when that
  completes; running to terminated on exit. Point out that waiting never goes
  straight to running.
  :::

  :::accordion-item{label="What is a PCB and what does it contain?" icon="i-lucide-message-circle"}
  The process control block: the kernel's record of one process, used to stop
  it and resume it later exactly where it was. It holds the pid, state, program
  counter, registers, scheduling information (priority, CPU time), memory
  information (page table location), the open-file table and accounting data.
  In Linux it is `task_struct`.
  :::

  :::accordion-item{label="What is the difference between the ready state and the waiting state?" icon="i-lucide-message-circle"}
  Ready: could run now, needs only a processor. Waiting: cannot run even if a
  processor is free, because it needs an I/O or an event to finish first.
  Consequence: extra cores help a long ready queue and do nothing for processes
  waiting on a slow disk.
  :::

  :::accordion-item{label="What are the ready queue and the device queue?" icon="i-lucide-message-circle"}
  The ready queue holds the PCBs of every process in the ready state; the
  scheduler picks from it. Each device (a disk, a network card) has its own queue
  of PCBs waiting on it. A process's PCB moves between these queues as it
  changes state; nothing is copied, only the PCB is relinked.
  :::
::
