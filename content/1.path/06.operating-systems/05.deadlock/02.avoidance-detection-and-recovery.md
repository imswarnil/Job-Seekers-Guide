Let processes ask for anything, but check each request before granting it: if
granting it could lead to a state from which some order of finishing no longer
exists, make the process wait. That check is **deadlock avoidance**, and the
algorithm that does it is Dijkstra's **banker's algorithm**. After it, the last
option: let deadlocks happen, detect them, and recover.

## Why this matters in a job

The banker's algorithm is asked as a numerical problem in written rounds and as
"explain it" in interviews: given Allocation, Max and Available, find the Need
matrix and a safe sequence, or say whether a request can be granted. It is five
minutes of arithmetic you can get entirely right. Detection and recovery are the
follow-up, and they are what databases actually do.

## Only lend what you can get back

Think of a college society treasurer with ₹10,000 in the account and three
clubs that have each been promised a budget ceiling. A club asks for money. The
treasurer does not only check whether the cash is there today; they check
whether, after lending it, there is still **some order** in which every club can
be given its full ceiling, finish its event and repay. If yes, lend. If no, the
club waits, even though the cash is sitting there. That is the banker's
algorithm; the clubs are processes and the money is resources.

Two words carry the whole idea:

- A **safe state** is one where there exists at least one order (a **safe
  sequence**) in which every process can get what it still needs, finish, and
  release everything it holds.
- An **unsafe state** has no such order. Unsafe is not yet deadlocked, but
  deadlock *can* happen from it, so the algorithm never enters one.

The data, for n processes and m resource types:

| Matrix | Meaning |
| --- | --- |
| **Available** | Free instances of each resource right now |
| **Max** | The most each process may ever request (declared in advance) |
| **Allocation** | What each process holds now |
| **Need** | What each process may still request: **Need = Max - Allocation** |

### The worked example

Five processes, three resource types A, B and C (10, 5 and 7 instances in total).
This is the classic textbook set, so it is also the one you are most likely to
be given.

| Process | Allocation (A B C) | Max (A B C) | Need = Max - Allocation |
| --- | --- | --- | --- |
| P0 | 0 1 0 | 7 5 3 | 7 4 3 |
| P1 | 2 0 0 | 3 2 2 | 1 2 2 |
| P2 | 3 0 2 | 9 0 2 | 6 0 0 |
| P3 | 2 1 1 | 2 2 2 | 0 1 1 |
| P4 | 0 0 2 | 4 3 3 | 4 3 1 |

Available = **3 3 2**.

**The safety algorithm:** find a process whose Need fits in Available. Pretend
it finishes: add its Allocation to Available. Repeat. If every process finishes,
the state is safe.

::steps
### Work = 3 3 2
P0 needs 7 4 3: no. **P1 needs 1 2 2: yes.** P1 finishes and returns 2 0 0.
Work = 3 3 2 + 2 0 0 = **5 3 2**.

### Work = 5 3 2
P2 needs 6 0 0: no (5 < 6). **P3 needs 0 1 1: yes.** Returns 2 1 1.
Work = **7 4 3**.

### Work = 7 4 3
**P4 needs 4 3 1: yes.** Returns 0 0 2. Work = **7 4 5**.

### Work = 7 4 5
**P0 needs 7 4 3: yes.** Returns 0 1 0. Work = **7 5 5**.

### Work = 7 5 5
**P2 needs 6 0 0: yes.** Returns 3 0 2. Work = **10 5 7**, which is every
resource in the system.
::

Safe sequence: **P1, P3, P4, P0, P2**. The state is safe. (Other safe sequences
exist, such as P3, P1, P4, P2, P0; any one is enough.)

### Should a request be granted?

**P1 requests 1 0 2.** Three checks:

1. Request ≤ Need(P1)? 1 0 2 ≤ 1 2 2. Yes (otherwise it has broken its promise).
2. Request ≤ Available? 1 0 2 ≤ 3 3 2. Yes (otherwise it waits).
3. Pretend to grant it and run the safety algorithm on the new state:
   Available 2 3 0, Allocation(P1) 3 0 2, Need(P1) 0 2 0. Running the steps
   above again gives P1, P3, P4, P0, P2. **Safe, so grant it.**

**Then P0 requests 0 2 0.** It passes checks 1 and 2 (Available is 2 3 0).
Pretend: Available becomes 2 1 0. Now P0 needs 7 2 3, P1 0 2 0, P2 6 0 0,
P3 0 1 1, P4 4 3 1. Nobody's Need fits in 2 1 0. **Unsafe, so P0 waits**, even
though the resources are free.

## How it works

The safety algorithm in Java, on the same data:

```java [Bankers.java]
import java.util.ArrayList;
import java.util.List;

public class Bankers {
  public static void main(String[] args) {
    int[] available = {3, 3, 2};
    int[][] max = {{7, 5, 3}, {3, 2, 2}, {9, 0, 2}, {2, 2, 2}, {4, 3, 3}};
    int[][] alloc = {{0, 1, 0}, {2, 0, 0}, {3, 0, 2}, {2, 1, 1}, {0, 0, 2}};
    System.out.println(safeSequence(available, max, alloc));
  }

  static String safeSequence(int[] available, int[][] max, int[][] alloc) {
    int n = max.length, m = available.length;
    int[] work = available.clone();
    boolean[] finished = new boolean[n];
    List<String> order = new ArrayList<>();

    boolean progress = true;
    while (progress) {
      progress = false;
      for (int i = 0; i < n; i++) {
        if (finished[i]) continue;
        boolean fits = true;
        for (int r = 0; r < m; r++) {
          if (max[i][r] - alloc[i][r] > work[r]) { fits = false; break; }   // Need > Work
        }
        if (fits) {
          for (int r = 0; r < m; r++) work[r] += alloc[i][r];               // it finishes, releases
          finished[i] = true;
          order.add("P" + i);
          progress = true;
        }
      }
    }
    for (boolean f : finished) if (!f) return "Unsafe: no safe sequence";
    return "Safe sequence: " + String.join(" ", order);
  }
}
```

```text [Output]
Safe sequence: P1 P3 P4 P0 P2
```

Change `available` to `{2, 1, 0}`, P0's allocation to `{0, 3, 0}` and P1's to
`{3, 0, 2}` (the state after both requests above), and it prints
`Unsafe: no safe sequence`.

### Detection and recovery

The third strategy: grant everything, and periodically check.

::flow{numbered direction="vertical" caption="Detect, then recover. What databases do every second."}
  :::flow-step{label="Build a wait-for graph" icon="i-lucide-git-fork"}
  With one instance per resource, collapse the resource allocation graph into
  "who waits for whom". With several instances, run an algorithm like the
  safety check above, using current requests instead of Need.
  :::
  :::flow-step{label="Look for a cycle" icon="i-lucide-search" highlight}
  A cycle in the wait-for graph is a deadlock. Detection runs every so often,
  or whenever a request has waited too long.
  :::
  :::flow-step{label="Recover" icon="i-lucide-life-buoy"}
  Kill every deadlocked process, or kill them one at a time until the cycle
  breaks (choosing the cheapest victim), or pre-empt a resource and roll its
  holder back to a safe point.
  :::
::

And the fourth, which most desktop operating systems choose: **ignore it**,
known as the **ostrich algorithm**. Deadlocks among ordinary programs are rare,
prevention and avoidance are expensive, so Windows and Linux leave it to the
programmer and the user's "force quit".

## Real use case

The banker's algorithm itself is rarely run in general-purpose systems: it needs
every process to declare its maximum in advance, and a fixed number of
processes. It survives where those are true, such as some embedded and
real-time systems.

Detection and recovery is everywhere. Every serious database runs a deadlock
detector: MySQL's InnoDB checks the wait-for graph on every lock wait, and
PostgreSQL checks after a transaction has waited `deadlock_timeout` (one second
by default). The victim gets an error, and application code is expected to
retry:

```java [RetryOnDeadlock.java]
for (int attempt = 1; attempt <= 3; attempt++) {
  try {
    feeService.applyLateFees(batch);        // one transaction
    break;
  } catch (CannotAcquireLockException e) {  // Spring's wrapper for "deadlock victim"
    if (attempt == 3) throw e;
    Thread.sleep(100L * attempt);           // back off, then try again
  }
}
```

## What confuses people here

That unsafe means deadlocked. It does not. An unsafe state is one where the
system can no longer **guarantee** avoiding deadlock; processes may still happen
to request less than their maximum and finish. The banker's algorithm refuses
unsafe states because it only accepts guarantees.

The other: **prevention and avoidance are different words.** Prevention makes one
of the four conditions impossible by design. Avoidance allows all four and checks
each request at run time.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between deadlock prevention, avoidance and detection?" icon="i-lucide-message-circle"}
  **Prevention**: design so one of the four conditions can never hold (lock
  ordering, request all at once). **Avoidance**: allow requests only if the
  resulting state is safe (banker's algorithm), which needs maximum demands in
  advance. **Detection and recovery**: allow deadlocks, find cycles in the
  wait-for graph, kill or roll back a victim. A fourth option is to ignore it
  (the ostrich algorithm).
  :::

  :::accordion-item{label="Explain the banker's algorithm." icon="i-lucide-message-circle"}
  Each process declares its Max. The system tracks Available, Allocation and
  Need = Max - Allocation. On a request, check Request ≤ Need and Request ≤
  Available, then pretend to grant it and run the safety algorithm: repeatedly
  find a process whose Need ≤ Work, add its Allocation to Work, mark it
  finished. If all finish, the state is safe and the request is granted;
  otherwise the process waits.
  :::

  :::accordion-item{label="What is a safe state?" icon="i-lucide-message-circle"}
  A state in which there exists at least one sequence of all processes such that
  each can obtain its remaining need from what is available plus what the
  earlier processes release. A safe state cannot deadlock. An unsafe state may.
  :::

  :::accordion-item{label="Why is the banker's algorithm not used in general-purpose operating systems?" icon="i-lucide-message-circle"}
  Processes rarely know their maximum resource needs in advance, the number of
  processes changes constantly, and running the safety check on every request
  costs O(m × n²). General-purpose systems prefer prevention in code and the
  ostrich approach at the operating system level.
  :::

  :::accordion-item{label="How does an operating system recover from a deadlock?" icon="i-lucide-message-circle"}
  Process termination (abort all deadlocked processes, or one at a time until
  the cycle is broken, choosing by priority, work done or resources held), or
  resource pre-emption (take a resource away, roll the victim back, and make
  sure the same process is not chosen every time, or it starves).
  :::
::
