Threads that wait for each other forever have a name. A **deadlock** is two threads each holding what the other
needs, and unlike a race condition it does not produce a wrong answer. It
produces nothing at all, which is sometimes worse, because a hung service has no
error message.

## Why this matters in a job

"What is a deadlock, what are the four necessary conditions, and how do you
prevent it?" is in the top five operating systems questions for freshers. At
work, when a service stops responding and the processor is idle, deadlock is the
first hypothesis, and being able to say that sentence puts you ahead of most
people in the room.

## Two threads, two locks, forever

Think of a narrow corridor in the old college block, one person wide. Two
lecturers enter from opposite ends carrying stacks of answer sheets, meet in the
middle, and neither can go forward until the other goes back. Neither will go
back, because each is halfway to where they are going. Nobody is doing anything
wrong, and nobody moves again.

In code: two staff members, two records. A transfer moves a student between
departments and needs both.

```java [Transfer.java]
static final Object computerScience = new Object();
static final Object electronics     = new Object();

// Staff member A: move a student from CSE to ECE
Thread a = new Thread(() -> {
  synchronized (computerScience) {
    sleep(50);                              // long enough to let B get going
    synchronized (electronics) {
      System.out.println("A moved the student");
    }
  }
});

// Staff member B: move a student from ECE to CSE
Thread b = new Thread(() -> {
  synchronized (electronics) {
    sleep(50);
    synchronized (computerScience) {        // A holds this, and wants what B holds
      System.out.println("B moved the student");
    }
  }
});
```

```text [Output]
(nothing, forever)
```

A holds computer science and wants electronics. B holds electronics and wants
computer science. Neither will let go, because neither is finished. The processor
is idle. The program will sit there until somebody kills it.

## The four conditions

A deadlock needs all four of these at once (they are called the **Coffman
conditions**), which is useful: break any one and it cannot happen.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-lock" title="Mutual exclusion"}
  The resource can only be held by one at a time. Usually not negotiable: it is
  what a lock is for.
  :::
  :::feature{icon="i-lucide-hand" title="Hold and wait"}
  A thread holds one thing while asking for another. Breakable: take everything
  you need at once, or nothing.
  :::
  :::feature{icon="i-lucide-shield-x" title="No pre-emption"}
  Nothing can take a lock away from a thread that holds it. Breakable with a
  timeout: `tryLock` gives up rather than waiting forever.
  :::
  :::feature{icon="i-lucide-refresh-cw" title="Circular wait"}
  A waits for B, B waits for A. **This is the one to break**, and the fix is
  almost embarrassingly simple.
  :::
::

The rule for reading one: **no cycle means no deadlock.** A cycle **guarantees**
deadlock when every resource has exactly one instance. If a resource has several
instances (three lab printers, say), a cycle means deadlock is *possible* but
not certain, because another instance may be freed.

### Prevention: break one condition

| Condition | How to break it | The cost |
| --- | --- | --- |
| Mutual exclusion | Make the resource shareable (read-only data needs no lock) | Impossible for most resources: a printer cannot print two documents at once |
| Hold and wait | Request everything at once before starting, or release everything before asking for more | Poor utilisation; you may not know in advance what you need |
| No pre-emption | Let the system take resources away (`tryLock` with a timeout, then release and retry) | Only works for resources whose state can be saved and restored |
| Circular wait | Number the resources and always request them in increasing order | Needs discipline across the whole codebase, and nothing else |

The last row is what real code does.

## How it works

The fix, in one line: **always take locks in the same order, everywhere in the
codebase.** The transfer program again, complete, with the order fixed:

```java [SafeTransfer.java]
public class SafeTransfer {
  record Department(int id, String name) {}

  static final Department cse = new Department(1, "CSE");
  static final Department ece = new Department(2, "ECE");

  static void transfer(String staff, Department from, Department to) {
    // Order by something stable and total: here, the department id.
    Department first  = from.id() < to.id() ? from : to;
    Department second = (first == from) ? to : from;

    synchronized (first) {
      nap(50);
      synchronized (second) {
        System.out.println(staff + " moved a student from " + from.name() + " to " + to.name());
      }
    }
  }

  public static void main(String[] args) throws Exception {
    Thread a = new Thread(() -> transfer("A", cse, ece));
    Thread b = new Thread(() -> transfer("B", ece, cse));
    a.start(); b.start();
    a.join();  b.join();
    System.out.println("Both transfers done");
  }

  static void nap(long ms) {
    try { Thread.sleep(ms); } catch (InterruptedException e) { }
  }
}
```

```text [Output, one run]
A moved a student from CSE to ECE
B moved a student from ECE to CSE
Both transfers done
```

Both threads now grab CSE (id 1) first. Whichever gets it second waits for it,
holding nothing, so a cycle cannot form: a cycle requires somebody to go
backwards. That is deadlock prevention in practice. The avoidance and detection
ideas in the next lesson are what operating systems and databases do internally;
ordinary application code almost always uses ordering.

## Real use case

Databases deadlock far more often than application threads. Two transactions
updating the same two rows in opposite orders:

```sql [fee-adjustments.sql]
-- Transaction 1 (a refund)           -- Transaction 2 (a late fee)
BEGIN;                                BEGIN;
UPDATE fee_payment SET amount = 0     UPDATE fee_payment SET amount = amount + 500
  WHERE id = 101;                       WHERE id = 202;
UPDATE fee_payment SET amount = 0     UPDATE fee_payment SET amount = amount + 500
  WHERE id = 202;  -- waits for T2      WHERE id = 101;  -- waits for T1
```

```text [Output, from PostgreSQL]
ERROR:  deadlock detected
DETAIL:  Process 4211 waits for ShareLock on transaction 9120; blocked by process 4212.
         Process 4212 waits for ShareLock on transaction 9119; blocked by process 4211.
```

The database runs a detector, finds the cycle, and kills one transaction (the
**deadlock victim**) so the other can finish; it is the error you met in the
DBMS track. The fix is the same as in Java: update rows in a consistent order,
by primary key, so both transactions touch 101 before 202.

## What confuses people here

Deadlock, starvation and livelock get mixed up. In a **deadlock**, nobody can
move. In **starvation**, the system moves but one thread is always passed over
(the priority lesson). In a **livelock**, threads are busy but make no progress,
like two people in a corridor who both step aside the same way, again and again:
two threads that both back off on `tryLock` and retry at the same moment can do
this. The fix for livelock is a random delay before retrying.

## Your turn

A college fee service has this code in two places. Find the deadlock and fix it
without removing either lock.

```java [FeeTransfer.java]
// In RefundService
synchronized (studentAccount) {
  synchronized (collegeAccount) { refund(); }
}

// In PaymentService
synchronized (collegeAccount) {
  synchronized (studentAccount) { charge(); }
}
```

::accordion
  :::accordion-item{label="The fix, and how to find this in real code" icon="i-lucide-check"}
  Circular wait: a refund and a payment happening at the same moment can each
  hold what the other wants. Fix by ordering both sites identically:

  ```java
  // Both services take the lower account number first, always.
  Object first  = studentAccount.getId() < collegeAccount.getId()
                ? studentAccount : collegeAccount;
  Object second = first == studentAccount ? collegeAccount : studentAccount;

  synchronized (first) {
    synchronized (second) { /* refund or charge */ }
  }
  ```

  **How you find it in real code:** you usually do not, by reading. You find it
  when the service hangs, and then you take a thread dump, `jstack <pid>` in
  Java, which prints every thread and what it is waiting on. The JVM detects
  cycles and prints "Found one Java-level deadlock" with both threads named. That
  command is worth remembering now: it is the difference between a two-minute
  diagnosis and an afternoon.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="What is a deadlock?" icon="i-lucide-message-circle"}
  A set of processes or threads each waiting for a resource held by another in
  the set, so none of them can ever proceed. No error, no output, and usually an
  idle processor.
  :::

  :::accordion-item{label="What are the four necessary conditions for deadlock?" icon="i-lucide-message-circle"}
  Mutual exclusion (a resource is held by one at a time), hold and wait (holding
  one while requesting another), no pre-emption (a resource cannot be taken
  away), circular wait (a cycle of processes, each waiting for the next). All
  four must hold together; break any one and deadlock is impossible.
  :::

  :::accordion-item{label="How do you prevent deadlock in practice?" icon="i-lucide-message-circle"}
  Break circular wait with a consistent lock order: always acquire locks in
  ascending order of some fixed key (id, name). Or break no-pre-emption with
  `tryLock(timeout)` and back off. Then name the diagnostic: `jstack <pid>`
  prints "Found one Java-level deadlock" with both threads. In a database the
  engine detects the cycle and kills one transaction as the deadlock victim.
  :::

  :::accordion-item{label="What is a resource allocation graph?" icon="i-lucide-message-circle"}
  A directed graph of processes (circles) and resources (squares). Request edges
  go process to resource; assignment edges go resource to process. No cycle means
  no deadlock. With single-instance resources, a cycle means deadlock; with
  multi-instance resources, a cycle means deadlock is possible.
  :::

  :::accordion-item{label="A service has stopped responding but the processor is at zero. What do you suspect?" icon="i-lucide-message-circle"}
  Deadlock first (threads blocked on each other), or every thread waiting on an
  external resource such as an exhausted connection pool. Take a thread dump:
  `jstack` names deadlocks outright, and shows what every other thread is
  waiting on.
  :::
::

## Next

::callout{icon="i-lucide-arrow-right"}
Prevention works by making a deadlock structurally impossible, and it costs
flexibility. There is a cleverer idea: let processes ask for anything, but have
the operating system check, before granting each request, whether granting it
could ever lead to a deadlock. That check has a name every interviewer knows:
the banker's algorithm.
::
