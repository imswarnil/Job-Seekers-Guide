One thread making things, another taking them, and a shelf between them that
can be full or empty. This is the **producer-consumer problem**, also called the
**bounded-buffer problem**, and it is the one synchronisation problem you should
be able to write out from memory with three semaphores.

## Why this matters in a job

"Explain the producer-consumer problem and solve it with semaphores" is asked in
interviews at every level, and the answer has a precise shape an interviewer
expects to see. At work, nearly every system that processes things in the
background is a producer and a consumer with a queue in between: uploads waiting
to be processed, emails waiting to be sent, logs waiting to be written.

## A shelf that can be full or empty

Think of the college canteen's counter with room for five plates. The cook
(producer) puts plates on it; students (consumers) take them. Three rules:

- The cook must stop when the counter is **full**.
- A student must wait when the counter is **empty**.
- Two people must not grab the same spot on the counter at the same instant.

Each rule is one semaphore:

| Semaphore | Starts at | Counts | Who waits on it |
| --- | --- | --- | --- |
| `empty` | N (buffer size) | Free slots | The producer, before adding |
| `full` | 0 | Filled slots | The consumer, before removing |
| `mutex` | 1 | Binary lock on the buffer itself | Both, around the actual add or remove |

The classic solution, as exam papers want it:

```text [Pseudocode]
semaphore empty = N;   // free slots
semaphore full  = 0;   // filled slots
semaphore mutex = 1;   // one at a time in the buffer

producer:                          consumer:
  while (true) {                     while (true) {
    item = produce();                  wait(full);     // wait for an item
    wait(empty);    // wait for space   wait(mutex);
    wait(mutex);                       item = remove();
    add(item);                         signal(mutex);
    signal(mutex);                     signal(empty);  // one more free slot
    signal(full);   // one more item   consume(item);
  }                                  }
```

::warning{icon="i-lucide-alert-triangle"}
**The order of the two waits matters.** If the producer does `wait(mutex)`
before `wait(empty)` and the buffer is full, it holds the buffer lock while
waiting for space, and the consumer can never get in to make space. Both wait
forever: a deadlock, which is the next chapter. Always wait on the counting
semaphore first, then the mutex.
::

## How it works

The pseudocode, line for line, in Java. Buffer of 3, one producer making 6
admission forms, one consumer processing them.

```java [AdmissionForms.java]
import java.util.ArrayDeque;
import java.util.concurrent.Semaphore;

public class AdmissionForms {
  static final int N = 3;
  static final ArrayDeque<Integer> buffer = new ArrayDeque<>();
  static final Semaphore empty = new Semaphore(N);
  static final Semaphore full  = new Semaphore(0);
  static final Semaphore mutex = new Semaphore(1);

  public static void main(String[] args) {
    Thread producer = new Thread(() -> {
      try {
        for (int form = 1; form <= 6; form++) {
          empty.acquire();                 // wait(empty)
          mutex.acquire();                 // wait(mutex)
          buffer.addLast(form);
          System.out.println("Received form " + form + "  buffer " + buffer);
          mutex.release();                 // signal(mutex)
          full.release();                  // signal(full)
        }
      } catch (InterruptedException e) { }
    });

    Thread consumer = new Thread(() -> {
      try {
        for (int i = 1; i <= 6; i++) {
          full.acquire();                  // wait(full)
          mutex.acquire();
          int form = buffer.removeFirst();
          System.out.println("  Processed form " + form + "  buffer " + buffer);
          mutex.release();
          empty.release();                 // signal(empty)
          Thread.sleep(100);               // processing is slower than receiving
        }
      } catch (InterruptedException e) { }
    });

    producer.start();
    consumer.start();
  }
}
```

```text [Output, one run; the interleaving varies]
Received form 1  buffer [1]
Received form 2  buffer [1, 2]
Received form 3  buffer [1, 2, 3]
  Processed form 1  buffer [2, 3]
Received form 4  buffer [2, 3, 4]
  Processed form 2  buffer [3, 4]
Received form 5  buffer [3, 4, 5]
  Processed form 3  buffer [4, 5]
Received form 6  buffer [4, 5, 6]
  Processed form 4  buffer [5, 6]
  Processed form 5  buffer [6]
  Processed form 6  buffer []
```

The buffer never holds more than three, and the consumer never takes from an
empty one. The producer is fast, fills the buffer, and then is held back by
`empty` to the consumer's pace.

## Real use case

In real Java code you do not write the three semaphores yourself. A
`BlockingQueue` is a bounded buffer with all of it built in: `put` blocks when
full, `take` blocks when empty.

```java [UploadPipeline.java]
BlockingQueue<AnswerSheet> uploads = new ArrayBlockingQueue<>(500);

// Producer: the web request that receives an uploaded answer sheet.
uploads.put(sheet);                       // blocks if 500 are already waiting

// Consumer: a background worker that grades them.
while (true) {
  AnswerSheet next = uploads.take();      // blocks if there is nothing to grade
  grade(next);
}
```

Message queues between services (Kafka, RabbitMQ, a cloud queue) are the same
pattern at the scale of whole machines. The bound matters there too: a queue
with no limit lets a fast producer fill memory until the process dies.

### Readers-writers, briefly

A shared notice board: **many readers may read at once**, but a **writer needs it
alone**, with no readers and no other writer. The standard solution keeps a
`readCount` protected by a mutex, and a `write` semaphore that the first reader
takes and the last reader releases. The catch: if readers keep arriving, the
writer can starve. Java's `ReentrantReadWriteLock` is this solution, ready-made.

### Dining philosophers, briefly

Five philosophers round a table, five chopsticks, one between each pair. Each
needs both neighbouring chopsticks to eat. If all five pick up their left
chopstick at the same moment, each waits forever for the right one. It is the
textbook illustration of **deadlock**, and the fixes are the deadlock fixes: let
at most four sit down at once, make one philosopher pick up right-then-left, or
pick up both chopsticks only if both are free.

::side-note{kind="go-deeper"}
A **monitor** is the higher-level alternative to semaphores: an object whose
methods run under one lock, plus **condition variables** a thread can wait on
inside it. Every Java object is a monitor: `synchronized` methods are the lock,
and `wait()` / `notifyAll()` are the condition variable. You can solve
producer-consumer with a monitor instead of three semaphores, and interviewers
sometimes ask for that version.
::

## What confuses people here

Why three semaphores and not one. The mutex only stops two threads touching the
buffer at the same instant. It knows nothing about full or empty: without
`empty` and `full`, a consumer holding the mutex would find the buffer empty and
have to give up or spin. `empty` and `full` are what let each side **sleep**
until the other has done something, and they are counting semaphores because
they count slots.

## Interview questions

::accordion
  :::accordion-item{label="Explain the producer-consumer problem and solve it with semaphores." icon="i-lucide-message-circle"}
  A producer adds to a bounded buffer, a consumer removes. The producer must
  not add when full, the consumer must not remove when empty, and they must not
  modify the buffer at the same time. Three semaphores: `empty = N`, `full = 0`,
  `mutex = 1`. Producer: `wait(empty)`, `wait(mutex)`, add, `signal(mutex)`,
  `signal(full)`. Consumer: `wait(full)`, `wait(mutex)`, remove,
  `signal(mutex)`, `signal(empty)`.
  :::

  :::accordion-item{label="What happens if the producer swaps wait(empty) and wait(mutex)?" icon="i-lucide-message-circle"}
  Deadlock when the buffer is full: the producer holds the mutex while waiting
  for an empty slot, and the consumer needs the mutex to create one.
  :::

  :::accordion-item{label="What is the readers-writers problem?" icon="i-lucide-message-circle"}
  Many readers may access shared data together, but a writer needs exclusive
  access. Solved with a reader count guarded by a mutex and a write lock taken
  by the first reader and released by the last. The simple version can starve
  writers; `ReentrantReadWriteLock` in Java handles it.
  :::

  :::accordion-item{label="What is the dining philosophers problem?" icon="i-lucide-message-circle"}
  Five philosophers, five chopsticks, each needs two. If all take the left one
  first, circular wait gives deadlock. Fixes: allow only four at the table,
  make one philosopher take the right chopstick first (breaks the cycle), or
  take both only when both are free.
  :::

  :::accordion-item{label="What is a monitor?" icon="i-lucide-message-circle"}
  A language-level construct where shared data and the procedures that use it
  are wrapped together, only one thread can be active inside at a time, and
  condition variables let threads wait for a state. In Java, every object with
  `synchronized` methods and `wait` / `notify` is a monitor.
  :::
::
