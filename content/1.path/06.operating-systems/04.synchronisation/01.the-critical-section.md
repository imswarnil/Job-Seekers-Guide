The scheduler cannot be told to wait. What you can do is mark a piece of code as
one that only one thread may be inside at a time, so that even if a thread is
stopped halfway through, nobody else can walk in and see the half-finished
state. That piece of code is a **critical section**, and the lock that guards it
is a **mutex**.

## Why this matters in a job

"What is a race condition?", "what is a critical section?" and "what are the
three requirements of a solution to the critical section problem?" are asked
together, often in that order, and the third is where most candidates stop.
At work, every `synchronized` block, every database row lock and every "only one
instance of this job may run" rule is the same idea.

## Only one inside at a time

Think of the single-occupancy washroom on a college floor. There is one key on a
hook. You take the key, go in, lock the door, come out and hang the key back.
Anyone who arrives while the key is gone waits. The washroom is the critical
section; the key is the mutex.

The real version. A **race condition** is when the result of a program depends
on the order in which threads happen to run, as with `received++` in the threads
lesson: read, add, write, with a switch possible between any two. The code that
touches the shared data is the **critical section**, and every thread's code
around it has four parts:

::flow{numbered direction="vertical" caption="The structure every solution fits into."}
  :::flow-step{label="Entry section" icon="i-lucide-log-in"}
  Ask permission: take the key, or wait for it.
  :::
  :::flow-step{label="Critical section" icon="i-lucide-lock" highlight}
  Touch the shared data. Only one thread may be here.
  :::
  :::flow-step{label="Exit section" icon="i-lucide-log-out"}
  Give permission back: hang the key up, wake a waiter.
  :::
  :::flow-step{label="Remainder section" icon="i-lucide-more-horizontal"}
  Everything else, which runs freely.
  :::
::

### The three requirements

Any correct solution to the critical section problem must guarantee all three:

::feature-list{columns="3"}
  :::feature{icon="i-lucide-user" title="Mutual exclusion"}
  If one thread is in its critical section, no other thread is in its own.
  :::
  :::feature{icon="i-lucide-fast-forward" title="Progress"}
  If nobody is inside and some threads want in, one of them must be allowed in
  soon. Threads in their remainder section cannot block the decision.
  :::
  :::feature{icon="i-lucide-timer" title="Bounded waiting"}
  There is a limit on how many times others can go in ahead of a waiting
  thread. Nobody waits forever.
  :::
::

A solution that locks everyone out forever meets mutual exclusion and fails
progress. A solution that lets one fast thread back in over and over fails
bounded waiting. Interviewers like asking which requirement a broken solution
violates.

### Peterson's solution, briefly

For two threads, there is a classic software-only answer: each thread sets a
`flag` saying it wants in, then politely sets `turn` to the **other** thread, and
waits only while the other wants in and it is the other's turn. It meets all
three requirements. It is asked about by name, and it does not work reliably on
modern processors, which reorder memory writes, so real systems use hardware
instructions (test-and-set, compare-and-swap) to build locks instead.

### The mutex

A **mutex** (mutual exclusion lock) has two operations: `acquire` (lock) and
`release` (unlock). Only the thread that acquired it may release it. In Java,
every object has one built in, used by `synchronized`, and
`java.util.concurrent.locks.ReentrantLock` is the explicit version.

## How it works

The lost-increment counter from the threads lesson, fixed with a mutex:

```java [SafeCounter.java]
import java.util.concurrent.locks.ReentrantLock;

public class SafeCounter {
  static int received = 0;
  static final ReentrantLock lock = new ReentrantLock();

  public static void main(String[] args) throws Exception {
    Runnable intake = () -> {
      for (int i = 0; i < 100_000; i++) {
        lock.lock();                // entry section
        try {
          received++;               // critical section
        } finally {
          lock.unlock();            // exit section, even if something throws
        }
      }
    };

    Thread a = new Thread(intake), b = new Thread(intake);
    a.start(); b.start();
    a.join();  b.join();
    System.out.println("Applications received: " + received);
  }
}
```

```text [Output, every run]
Applications received: 200000
```

Without the three lock lines the same program prints a different wrong number
every run. The `finally` matters: if the critical section throws and the unlock
is skipped, the lock is held forever and every other thread waits forever.

The shorter form, with Java's built-in lock:

```java [SafeCounter.java]
synchronized (SafeCounter.class) {
  received++;
}
```

### Spinning or sleeping

A thread that finds the lock taken can do one of two things. A **spinlock**
loops, checking again and again (**busy waiting**), which wastes processor time
but is fast when the wait is a few nanoseconds. A blocking mutex puts the thread
into the waiting state and lets the scheduler run somebody else, which costs a
context switch but wastes nothing. Java's locks spin briefly and then block.

## Real use case

The same critical section, one layer down, in a database. Two office staff
allocate the last hostel room at the same moment. Without a lock, both read
"1 room free", both allocate it, and two students hold one room.

```sql [allocate-room.sql]
BEGIN;
-- Entry section: lock this row until COMMIT. A second transaction running the
-- same statement waits here.
SELECT rooms_free FROM hostel WHERE block = 'B' FOR UPDATE;
UPDATE hostel SET rooms_free = rooms_free - 1 WHERE block = 'B' AND rooms_free > 0;
COMMIT;  -- exit section
```

`SELECT ... FOR UPDATE` is a mutex on one row. You met it in the DBMS track as
isolation; this is why it exists.

## What confuses people here

That locking makes code "slow", so it should be avoided. A lock that nobody else
wants costs a few nanoseconds. What is slow is **contention**: many threads
wanting the same lock, and a critical section that is longer than it needs to
be. Keep critical sections short (never do a network call or a disk read while
holding a lock) and the cost is negligible.

The other confusion: locking protects data only if **every** access goes through
the same lock. One method that reads `received` without the lock can still see
a half-updated value.

## Interview questions

::accordion
  :::accordion-item{label="What is a race condition?" icon="i-lucide-message-circle"}
  When the outcome depends on the unpredictable order in which threads run.
  Example: two threads doing `count++` (read, add, write) can both read the same
  value and one increment is lost. It shows up under load and rarely in testing.
  :::

  :::accordion-item{label="What is the critical section problem, and what are its three requirements?" icon="i-lucide-message-circle"}
  Designing entry and exit code so that threads sharing data can take turns in
  the code that touches it. Requirements: **mutual exclusion** (one at a time),
  **progress** (if nobody is inside, somebody waiting gets in; the decision is
  not postponed forever), **bounded waiting** (a limit on how often others can
  overtake a waiting thread).
  :::

  :::accordion-item{label="What is a mutex?" icon="i-lucide-message-circle"}
  A lock with acquire and release that allows one holder at a time, and only the
  holder may release it. `synchronized` and `ReentrantLock` in Java. Always
  release in a `finally` block.
  :::

  :::accordion-item{label="What is busy waiting, and what is a spinlock?" icon="i-lucide-message-circle"}
  Busy waiting is looping while checking a condition, using the processor the
  whole time. A spinlock is a lock implemented that way. Good for very short
  waits on multi-core machines (no context switch); wasteful for long ones,
  where a blocking lock is better.
  :::

  :::accordion-item{label="What is Peterson's solution?" icon="i-lucide-message-circle"}
  A software solution for two threads using a `flag[2]` array (who wants in) and
  a `turn` variable (whose turn it is to yield). Each sets its flag, gives the
  turn away, and waits while the other wants in and holds the turn. It satisfies
  all three requirements, but modern processors reorder memory operations, so
  real locks use hardware atomic instructions instead.
  :::
::
