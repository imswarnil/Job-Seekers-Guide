A lock that can count is a **semaphore**. Where a mutex lets one thread in, a
semaphore starts with a number, lets that many in, and makes the next one wait
until somebody leaves. It was invented by Edsger Dijkstra in the 1960s, and it is
still the word interviewers use for "controlling access to a limited resource".

## Why this matters in a job

"What is a semaphore?", "binary versus counting?" and "semaphore versus mutex?"
are three of the most common synchronisation questions in fresher interviews.
At work, semaphores are how you stop a service opening 500 connections to a
database that allows 50, or calling a partner's API faster than your contract
allows.

## A lock that counts

Think of the college computer lab with three machines and a lab assistant who
keeps a tally on the whiteboard: "machines free: 3". A student arrives, the
assistant rubs it down to 2 and lets them in. When it reaches 0, the next
student waits at the door. When somebody leaves, the tally goes up, and if
anyone is waiting, one of them goes in.

The real thing is an integer `S` with exactly two operations, both
**atomic** (nothing can interrupt them halfway):

| Operation | Other names | What it does |
| --- | --- | --- |
| `wait(S)` | `P(S)`, `down`, `acquire` | If `S > 0`, decrement it and continue. If `S == 0`, block until it is not. |
| `signal(S)` | `V(S)`, `up`, `release` | Increment `S`, and wake one blocked thread if any are waiting. |

The textbook definition, as it appears in exam papers:

```text [Pseudocode]
wait(S) {
    while (S <= 0)
        ;          // wait (a real implementation blocks instead of spinning)
    S--;
}

signal(S) {
    S++;
}
```

`P` and `V` come from the Dutch words Dijkstra used; knowing that is a nice
aside, not an answer.

### Binary and counting

::compare{caption="Same operations, different starting values."}
  :::compare-side{label="Binary semaphore" verdict="neutral"}
  Starts at 1 and only ever holds 0 or 1. One thread at a time: behaves like a
  lock for a critical section.
  :::
  :::compare-side{label="Counting semaphore" verdict="neutral"}
  Starts at N, the number of identical resources: three lab machines, fifty
  database connections. Up to N threads at once.
  :::
::

### Semaphore or mutex

A binary semaphore and a mutex look the same and are asked about precisely
because they are not:

| | Mutex | Semaphore |
| --- | --- | --- |
| Purpose | Locking: protect a critical section | Signalling and counting: limit access, or tell another thread something happened |
| Values | Locked or unlocked | Any non-negative integer (0 or 1 if binary) |
| Ownership | **Only the thread that locked it may unlock it** | **Any thread may signal**, including one that never waited |
| Typical use | Guarding shared data | N identical resources; one thread waking another |

That ownership row is the answer interviewers are looking for. Because anybody
can signal a semaphore, one thread can `wait` on it and a different thread can
`signal` it to say "your data is ready", which is how the producer-consumer
problem in the next lesson is solved.

## How it works

Three lab machines, six students. `java.util.concurrent.Semaphore` is exactly
the textbook semaphore.

```java [ComputerLab.java]
import java.util.concurrent.Semaphore;

public class ComputerLab {
  static final Semaphore machines = new Semaphore(3);   // counting semaphore, N = 3

  public static void main(String[] args) {
    String[] students = {"Asha", "Bilal", "Chitra", "Dev", "Esha", "Farhan"};
    for (String s : students) {
      new Thread(() -> useLab(s)).start();
    }
  }

  static void useLab(String student) {
    try {
      machines.acquire();                               // wait(S)
      try {
        System.out.println(student + " sits down. Free: " + machines.availablePermits());
        Thread.sleep(1000);                             // an hour of lab work, shortened
      } finally {
        System.out.println(student + " leaves.");
        machines.release();                             // signal(S)
      }
    } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
    }
  }
}
```

```text [Output, one run; the order varies]
Asha sits down. Free: 2
Chitra sits down. Free: 1
Bilal sits down. Free: 0
Asha leaves.
Dev sits down. Free: 0
Chitra leaves.
Esha sits down. Free: 0
Bilal leaves.
Farhan sits down. Free: 0
Dev leaves.
Esha leaves.
Farhan leaves.
```

Never more than three inside. Students four to six block inside `acquire` until
somebody `release`s. Change the 3 to a 1 and it becomes a binary semaphore: one
student at a time.

## Real use case

A college's results service calls a third-party SMS gateway to text students
their results. The contract allows 10 requests in flight at once; the 11th gets
rejected. A counting semaphore enforces that inside the service, however many
threads are sending:

```java [SmsSender.java]
public class SmsSender {
  private final Semaphore inFlight = new Semaphore(10);   // the contract's limit

  public void send(String phone, String message) throws InterruptedException {
    inFlight.acquire();
    try {
      gateway.post(phone, message);                       // at most 10 at once
    } finally {
      inFlight.release();
    }
  }
}
```

A database connection pool is the same idea: a counting semaphore with N
permits in front of N connections.

## What confuses people here

That `signal` "gives the lock back". It does not have to. With a semaphore, the
thread that signals and the thread that waited can be different, and a signal
can happen before anyone waits (the count goes up and the next `wait`
passes straight through). That flexibility is also its danger: a `release`
without a matching `acquire` silently raises the limit, and nothing stops you.
Put `release` in `finally`, exactly once per `acquire`.

## Interview questions

::accordion
  :::accordion-item{label="What is a semaphore?" icon="i-lucide-message-circle"}
  An integer variable accessed only through two atomic operations: `wait` (P),
  which decrements it or blocks if it is zero, and `signal` (V), which
  increments it and wakes a waiter. It controls access to a resource with N
  identical units, or lets one thread signal another.
  :::

  :::accordion-item{label="What is the difference between a binary and a counting semaphore?" icon="i-lucide-message-circle"}
  A binary semaphore takes only 0 and 1 and admits one thread at a time. A
  counting semaphore starts at N and admits up to N, for N identical resources
  such as connections or printers.
  :::

  :::accordion-item{label="What is the difference between a mutex and a semaphore?" icon="i-lucide-message-circle"}
  A mutex is a locking mechanism with ownership: only the thread that locked it
  can unlock it. A semaphore is a signalling mechanism with a count and no
  owner: any thread can signal it. Use a mutex to protect data; a semaphore to
  limit concurrent access or to signal between threads.
  :::

  :::accordion-item{label="What happens if you call signal without wait?" icon="i-lucide-message-circle"}
  The count goes up by one, so one more thread than intended can now enter. With
  a binary semaphore that breaks mutual exclusion. In Java, `Semaphore.release()`
  does not check, which is why it belongs in a `finally` paired with exactly one
  `acquire`.
  :::
::
