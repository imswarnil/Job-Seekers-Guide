Questions about deployment answered from a chair. These six are the situations,
and four of them happen on a Monday morning with somebody waiting.

## 1. The domain that went nowhere

You pointed `university.example` at the new host four hours ago. Your laptop
shows the new site. The registrar still sees the old one.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  DNS caching, at one of four layers: the browser, the operating system, their
  resolver, or an intermediate. Your machine has already picked up the new
  answer; theirs is holding the old one until its TTL expires.

  Diagnose rather than guess:

  ```bash
  dig university.example +noall +answer          # what your resolver says
  dig @8.8.8.8 university.example +noall +answer # what a public one says
  dig university.example +trace                  # what is authoritative
  ```

  If the authoritative answer is correct and theirs is not, it is a cache and
  the only fix is waiting out the TTL.

  **The lesson is for next time:** lower the TTL to 60 seconds a day *before* a
  migration, then raise it afterwards. A TTL of 86,400 means a full day of some
  people seeing the old site, and there is nothing you can do about it at the
  point you notice.
  :::
::

## 2. The secret in the history

You committed `.env` with the database password three weeks ago. It is in
fifteen commits and the repository is private.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Rotate the credential first.** Right now, before anything else. Change the
  database password, issue a new API key, and make the leaked one worthless.

  That is the whole answer and people get the order wrong: they spend an hour
  rewriting git history while the live credential is still valid.

  Then, and only then, the cleanup: `git filter-repo` or BFG to remove it from
  history, force-push, and everybody re-clones. This is disruptive and it is the
  second problem.

  Then prevention: `.env` in `.gitignore`, a committed `.env.example` with the
  key names and no values, and a pre-commit hook or a scanner in CI.

  If the repository were **public**, assume it was read within minutes.
  Automated scanners watch public commits continuously, and "it was only up for
  ten minutes" is not a defence.
  :::
::

## 3. The migration that stops the office

Your deploy adds a column to `Application`, which has four million rows. The
admissions office reports the system is frozen.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Adding a nullable column with no default is instant in modern Postgres. What
  locks the table is adding a `NOT NULL` column with a default that must be
  written to every row, or adding an index without `CONCURRENTLY`, or a
  `CHECK` that must validate four million rows.

  The safe sequence, in separate deploys:

  ```sql
  -- 1. Add it nullable. Instant.
  ALTER TABLE Application ADD COLUMN review_note TEXT;

  -- 2. Backfill in batches, so no single transaction is long.
  UPDATE Application SET review_note = '' WHERE review_note IS NULL
    AND application_id BETWEEN :lo AND :hi;

  -- 3. Only once everything is populated.
  ALTER TABLE Application ALTER COLUMN review_note SET NOT NULL;
  ```

  And indexes always:

  ```sql
  CREATE INDEX CONCURRENTLY ON Application (applied_on);
  ```

  The principle worth naming: **a migration must be safe to run while the old
  code is still serving traffic**, because during a deploy both versions are
  live for a few seconds. That rules out renaming or dropping a column in the
  same release that stops using it.
  :::
::

## 4. It works in preview and fails in production

The preview deployment is perfect. Production returns a 500 on every page.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Almost always an environment variable that exists in preview and not in
  production, or one pointing at the wrong thing.

  Check in this order:

  1. **Is the variable set in the production environment?** Preview and
     production are separate scopes and adding to one does not add to the other.
  2. **Is `DATABASE_URL` pointing at the production database**, or at the
     preview branch that just got deleted?
  3. **Is it set at build time or run time?** A variable read during the build
     is baked into the bundle; one read at run time is not. Setting a build-time
     variable after the build does nothing.
  4. **Read the actual logs.** Not the status page. The 500 has a stack trace
     behind it.

  Then the fix that prevents the class: fail loudly at startup.

  ```js
  const required = ["DATABASE_URL", "SESSION_SECRET", "GHOST_CONTENT_KEY"]
  for (const k of required) {
    if (!process.env[k]) throw new Error(`Missing required env var: ${k}`)
  }
  ```

  Now a missing variable is a refusal to start with a clear message, instead of
  a 500 on every request with a null pointer somewhere deep.
  :::
::

## 5. The deploy that has to go back

The new release is live and the admissions pipeline is broken. Twelve minutes
have passed.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Roll back first, investigate afterwards.** Every minute spent debugging in
  production is a minute the office cannot work, and you debug better when
  nothing is on fire.

  ```bash
  vercel rollback          # or the platform's equivalent, or redeploy the last good commit
  ```

  Then the question that decides whether rollback is even possible: **did this
  release include a migration?** If it dropped a column, the old code cannot
  run against the new database and rollback is not available. That is why
  migrations are expand-then-contract across separate releases, and this is the
  moment that discipline either saves you or does not.

  Afterwards: what would have caught it? Usually a test against a seeded
  database, or a preview deployment that somebody actually opened.
  :::
::

## 6. The preview that writes to production

Every pull request gets a preview URL. A colleague tested the delete flow on one
and deleted real applications.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  The previews are sharing `DATABASE_URL` with production. This is a
  configuration mistake and it is a common one, because it works perfectly until
  somebody clicks delete.

  The fix is a database branch per preview:

  ```bash
  neonctl branches create --name preview-$PR_NUMBER --parent main
  ```

  A copy-on-write branch, created in seconds, seeded from production structure
  with test data, destroyed when the PR merges. Every preview gets its own, and
  nothing a reviewer clicks can touch real data.

  Then the safety net regardless: production credentials should never be
  available to a preview environment at all, and the production database should
  refuse connections from anywhere but production. Configuration mistakes are
  inevitable; the question is whether one is survivable.

  And this is why the build track's `db/seed.sql` matters beyond development.
  A preview with realistic seeded data is testable; an empty one is not.
  :::
::

## The cheat-sheet

| Command | What it does |
| --- | --- |
| `dig <name> +noall +answer` | What your resolver returns, with the TTL |
| `dig @8.8.8.8 <name>` | What a public resolver returns |
| `dig <name> +trace` | Walk from the root to the authoritative answer |
| `curl -I <url>` | Headers only. Check the status and redirects |
| `vercel logs <url>` | The actual error behind a 500 |
| `vercel env ls` | Which variables exist, in which environment |
| `vercel rollback` | Back to the previous deployment |
| `neonctl branches create` | A database branch for a preview |
| `CREATE INDEX CONCURRENTLY` | An index without locking the table |

::pull-quote
Four of these six are configuration rather than code, which is the honest shape
of deployment work. The bug is almost never in the thing you changed; it is in
the difference between two environments you assumed were the same.
::
