You can program and you can ask a database anything. An API is the join: a URL
that runs your Java, which runs your SQL, and hands back something a browser can
use.

This is where the University Management App stops being a plan.

## Why this matters in a job

Because "built a REST API" is the single most common line on a backend job
advert, and because the difference between an endpoint that works and one that
is correct is four specific things this lesson is about.

## The four layers

Every request goes through the same four, and each exists because the one beside
it should not do its job.

::pull-quote
The controller knows about HTTP and nothing about the university. The repository
knows about SQL and nothing about who is asking. The rules live in exactly one
place, which is the only way they can be tested and the only way they cannot
drift.
::

## The endpoint

```java [ApplicationController.java]
@RestController
@RequestMapping("/api/applications")
public class ApplicationController {

  private final ShortlistService shortlist;

  public ApplicationController(ShortlistService shortlist) {   // handed in
    this.shortlist = shortlist;
  }

  @GetMapping
  public PageResponse<ApplicationSummary> list(
      @RequestParam(defaultValue = "2026") String intake,
      @RequestParam(required = false) String programme,
      @RequestParam(defaultValue = "0")  @Min(0)   int page,
      @RequestParam(defaultValue = "50") @Min(1) @Max(200) int size,
      @AuthenticationPrincipal Staff caller) {

    return shortlist.list(new ListCriteria(intake, programme, page, size), caller);
  }

  @PostMapping("/{id}/shortlist")
  @ResponseStatus(HttpStatus.OK)
  public ApplicationSummary shortlist(
      @PathVariable long id,
      @AuthenticationPrincipal Staff caller) {

    return shortlist.shortlist(id, caller);
  }
}
```

::code-trace{caption="Five decisions in a signature, and four of them are about not trusting the caller."}

  :::code-trace-step{lines="3" caption="`@Max(200)`. Without it somebody requests size=1000000 and your server loads 40,000 rows into memory to serialise them. A ceiling on every page size is not optional."}
  :::
  :::code-trace-step{lines="3" caption="A default, so a caller who omits it gets 50 rather than everything. Paginating by default is the single most useful habit in API design."}
  :::
  :::code-trace-step{lines="4" caption="The caller comes from the authenticated session, NEVER from a parameter. A `userId` query parameter is somebody else's account away from a breach."}
  :::
  :::code-trace-step{lines="5" caption="It returns a SUMMARY, not the entity. The table has an internal note field and an assessor's comments, and serialising the whole row publishes both."}
  :::
::

## The service, where the rules are

```java [ShortlistService.java]
@Service
public class ShortlistService {

  private final ApplicationRepository repository;
  private final AuditLog audit;

  @Transactional                                  // one bracket, the whole operation
  public ApplicationSummary shortlist(long applicationId, Staff caller) {

    Application application = repository.findById(applicationId)
        .orElseThrow(() -> new NotFoundException("No application " + applicationId));

    // ── The university's rules. One place. Testable without a database. ──
    if (!caller.canShortlistFor(application.getProgrammeId())) {
      throw new ForbiddenException("Not your programme");
    }
    if (application.getStatus() != Status.UNDER_REVIEW) {
      throw new ConflictException(
          "Only an application under review can be shortlisted, not "
              + application.getStatus());
    }
    if (application.getScore() == null) {
      throw new ConflictException("Cannot shortlist an unmarked application");
    }

    int updated = repository.shortlist(applicationId, caller.getId());
    if (updated == 0) {                           // somebody else got there first
      throw new ConflictException("Application was changed by somebody else");
    }

    audit.record(caller, "SHORTLIST", applicationId);
    return repository.summary(applicationId).orElseThrow();
  }
}
```

::warning{icon="i-lucide-alert-triangle"}
`if (updated == 0)` is the lost-update lesson from the DBMS track, in Java. The
repository's `UPDATE` carries `AND status = 'UNDER_REVIEW'`, so if two clerks
click at the same instant the second one affects zero rows and finds out. Code
that ignores the affected-row count has thrown away the answer.
::

## The repository, where the SQL is

```java [ApplicationRepository.java]
@Repository
public class ApplicationRepository {

  private final JdbcClient db;

  /** Conditional by design: the WHERE is the concurrency control. */
  public int shortlist(long applicationId, long staffId) {
    return db.sql("""
        UPDATE Application
           SET status         = 'SHORTLISTED',
               shortlisted_on = CURRENT_DATE,
               shortlisted_by = :staffId
         WHERE application_id = :id
           AND status         = 'UNDER_REVIEW'
           AND score IS NOT NULL
        """)
        .param("id", applicationId)               // parameterised, never joined
        .param("staffId", staffId)
        .update();
  }

  public PageResponse<ApplicationSummary> list(ListCriteria criteria, long departmentId) {
    List<ApplicationSummary> rows = db.sql("""
        SELECT a.application_id, ap.full_name, p.code AS programme,
               a.score, a.status, a.applied_on
          FROM Application a
          JOIN Applicant  ap USING (applicant_id)
          JOIN Programme  p  USING (programme_id)
         WHERE a.intake = :intake
           AND a.status <> 'WITHDRAWN'
           AND p.department_id = :departmentId
           AND (:programme IS NULL OR p.code = :programme)
         ORDER BY a.score DESC NULLS LAST, a.application_id
         LIMIT :size OFFSET :offset
        """)
        .param("intake", criteria.intake())
        .param("programme", criteria.programme())
        .param("departmentId", departmentId)
        .param("size", criteria.size())
        .param("offset", criteria.page() * criteria.size())
        .query(ApplicationSummary.class)
        .list();

    return new PageResponse<>(rows, criteria.page(), criteria.size());
  }
}
```

Every lesson from the SQL track is in that query: `<> 'WITHDRAWN'`, `NULLS LAST`,
a unique tie-break in the `ORDER BY` so paging is reproducible, and named
parameters rather than concatenation.

## Status codes, mapped once

```java [ApiExceptionHandler.java]
@RestControllerAdvice
public class ApiExceptionHandler {

  @ExceptionHandler(NotFoundException.class)
  @ResponseStatus(HttpStatus.NOT_FOUND)                    // 404
  ProblemDetail notFound(NotFoundException e) { return problem(e); }

  @ExceptionHandler(ForbiddenException.class)
  @ResponseStatus(HttpStatus.FORBIDDEN)                    // 403
  ProblemDetail forbidden(ForbiddenException e) { return problem(e); }

  @ExceptionHandler(ConflictException.class)
  @ResponseStatus(HttpStatus.CONFLICT)                     // 409
  ProblemDetail conflict(ConflictException e) { return problem(e); }

  @ExceptionHandler(MethodArgumentNotValidException.class)
  @ResponseStatus(HttpStatus.UNPROCESSABLE_ENTITY)         // 422
  ProblemDetail invalid(MethodArgumentNotValidException e) { ... }

  @ExceptionHandler(Exception.class)
  @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)        // 500
  ProblemDetail unexpected(Exception e) {
    log.error("Unhandled", e);                             // the trace, to the LOG
    return ProblemDetail.forStatusAndDetail(
        HttpStatus.INTERNAL_SERVER_ERROR,
        "Something went wrong. Reference: " + traceId());   // not to the caller
  }
}
```

::caution{icon="i-lucide-octagon-alert"}
The last one matters. Returning a stack trace to the caller publishes your file
paths, your library versions and sometimes a connection string. Log the detail,
return a reference the user can quote, and never the exception. This is
information disclosure and it is one of the most common findings in a first
security review.
::

## Testing it without a database

```java [ShortlistServiceTest.java]
@Test
void refusesToShortlistAnUnmarkedApplication() {
  var repository = new FakeApplicationRepository(
      application(9001, Status.UNDER_REVIEW, null));      // no score

  var e = assertThrows(ConflictException.class,
      () -> new ShortlistService(repository, audit).shortlist(9001, registrar));

  assertTrue(e.getMessage().contains("unmarked"));
}

@Test
void refusesWhenAnotherClerkGotThereFirst() {
  var repository = new FakeApplicationRepository(
      application(9001, Status.UNDER_REVIEW, 78));
  repository.shortlistReturns(0);                          // zero rows affected

  assertThrows(ConflictException.class,
      () -> new ShortlistService(repository, audit).shortlist(9001, registrar));
}
```

Milliseconds, no database, and the rules are what is being tested. That is the
pay-off from the interfaces lesson in the Java track: the service depends on
`ApplicationRepository` the interface, so a fake is four lines.

## The acceptance criteria

::feature-list{columns="2"}
  :::feature{icon="i-lucide-list" title="List, get, shortlist, reject"}
  With filtering, paging and a maximum page size.
  :::
  :::feature{icon="i-lucide-shield" title="The caller comes from the session"}
  Never from a parameter. Prove it: try to pass another staff id.
  :::
  :::feature{icon="i-lucide-hash" title="The right status code per failure"}
  404, 403, 409, 422, 500 — and a 409 when two clerks race.
  :::
  :::feature{icon="i-lucide-eye-off" title="No internal fields in a response"}
  A summary type, not the entity. Check what you are actually serialising.
  :::
  :::feature{icon="i-lucide-test-tube" title="The rules tested without a database"}
  Every branch of the service, with fakes.
  :::
  :::feature{icon="i-lucide-book-open" title="It documents itself"}
  Springdoc gives you OpenAPI and a browsable page from the annotations, free.
  :::

## Your turn

Build it, then attack it with `curl` rather than through the interface.

```bash [Terminal]
# 1. A page size nobody should get
curl -s "localhost:8080/api/applications?size=1000000" | head

# 2. Another department's programme
curl -s "localhost:8080/api/applications?programme=BTECH-ECE" -H "$CSE_TOKEN"

# 3. Shortlist the same application twice, fast
curl -sX POST localhost:8080/api/applications/9001/shortlist -H "$TOKEN" &
curl -sX POST localhost:8080/api/applications/9001/shortlist -H "$TOKEN" &

# 4. An application that does not exist
curl -si localhost:8080/api/applications/999999/shortlist -X POST -H "$TOKEN" | head -1
```

::accordion
  :::accordion-item{label="What should happen, and what usually does" icon="i-lucide-check"}
  **1.** `422`, because `@Max(200)` rejected it. If you get 40,000 rows, you have
  found the most common denial-of-service in a junior API: an unbounded page
  size. It is one annotation.

  **2.** An empty list or `403`, because the query is scoped by the caller's
  department. If you get another department's applicants, the scope check is
  missing, and this is the insecure-direct-object-reference class from the auth
  track.

  **3.** One `200` and one `409`. If both return `200`, the `UPDATE` has no
  `AND status = 'UNDER_REVIEW'` or the affected-row count is being ignored, and
  the audit log now has two shortlistings for one application.

  **4.** `404`, and the body must not say whether the application exists but
  belongs to somebody else — returning `403` there tells an attacker which ids
  are real. This is the same decision GitHub makes, from the HTTP lesson.

  **The habit worth taking:** test the API with `curl`, not through your own
  interface. The interface only ever sends the requests you designed it to send,
  which is precisely why it cannot find these.
  :::
::

## The interview question this answers

**"Describe the architecture of an API you have built."**

The four layers and the one reason each exists: the controller knows HTTP, the
service knows the university's rules and owns the transaction, the repository
knows SQL, and the database enforces what none of them should be trusted with.

Then the three details that make it sound built rather than read: the identity
comes from the session and never from a parameter, every list is paged with a
maximum, and the conditional `UPDATE` plus the affected-row check is what stops
two clerks shortlisting the same application.
