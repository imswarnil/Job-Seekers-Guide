Names in one table, scores in another. A join is how you ask a question that
needs both, and which join you choose decides what happens to the rows that have
no partner. That decision is where the wrong numbers come from.

## Why this matters in a job

Because joins are the most-tested SQL topic there is, and because the fan-out
bug in this lesson is responsible for more incorrect dashboards than any other
single mistake in this course.

## The data

```text [Applicant]
 applicant_id | full_name
--------------+--------------
         4182 | Anita Rao
         4183 | Vikram Shah
         4184 | Priya Nair      ← has never applied
```

```text [Application]
 application_id | applicant_id | programme_id | score
----------------+--------------+--------------+-------
           9001 |         4182 |            1 |    78
           9002 |         4182 |            2 |    74      ← Anita applied twice
           9003 |         4183 |            1 |    64
           9004 |         NULL |            1 |    55      ← orphan: no applicant
```

## INNER JOIN, only matching pairs

::runner{lang="sql"}
```sql
SELECT ap.full_name, a.programme_id, a.score
FROM   Applicant ap
JOIN   Application a ON a.applicant_id = ap.applicant_id;
```
::

```text [Output — 3 rows]
 full_name   | programme_id | score
-------------+--------------+-------
 Anita Rao   |            1 |    78
 Anita Rao   |            2 |    74
 Vikram Shah |            1 |    64
```

Priya is gone, because she has no application. The orphan row 9004 is gone,
because it has no applicant. **An inner join silently discards anything without
a partner on both sides**, and "silently" is the important word.

## LEFT JOIN, keep everything on the left

::runner{lang="sql"}
```sql
SELECT ap.full_name, a.programme_id, a.score
FROM   Applicant ap
LEFT JOIN Application a ON a.applicant_id = ap.applicant_id;
```
::

```text [Output — 4 rows]
 full_name   | programme_id | score
-------------+--------------+-------
 Anita Rao   |            1 |    78
 Anita Rao   |            2 |    74
 Vikram Shah |            1 |    64
 Priya Nair  |         NULL |  NULL     ← kept, with nulls where there was no match
```

Priya is back, with `NULL` in every column from the right-hand table. That is the
whole of what `LEFT JOIN` does: keep every left row, fill in nulls where there is
no partner.

## The LEFT JOIN that becomes an INNER JOIN

A genuine trap, and it looks like a small tidy-up.

::compare{caption="One condition, moved by two words, and the meaning changes completely."}
  :::compare-side{label="In the WHERE clause" verdict="wrong"}
  ```sql
  FROM Applicant ap
  LEFT JOIN Application a ON a.applicant_id = ap.applicant_id
  WHERE a.score >= 75;
  ```
  Priya's row has `score = NULL`, `NULL >= 75` is `UNKNOWN`, so `WHERE` removes
  her. The `LEFT JOIN` has been silently turned back into an inner join.
  :::
  :::compare-side{label="In the ON clause" verdict="right"}
  ```sql
  FROM Applicant ap
  LEFT JOIN Application a
         ON a.applicant_id = ap.applicant_id
        AND a.score >= 75;
  ```
  The condition is part of *what counts as a match*. Priya is kept with nulls,
  which is what "every applicant, with their high-scoring applications if any"
  actually means.
  :::
::

::pull-quote
On a LEFT JOIN, a condition on the right table belongs in `ON`. Put it in `WHERE`
and you have written an inner join with extra words.
::

## Finding what is missing

The `LEFT JOIN` idiom worth memorising.

::runner{lang="sql"}
```sql
-- Applicants who have never applied to anything.
SELECT ap.full_name
FROM   Applicant ap
LEFT JOIN Application a ON a.applicant_id = ap.applicant_id
WHERE  a.application_id IS NULL;
```
::

Join everything, then keep only the rows where the right side did not match. It
reads oddly the first time and it is the standard way to ask "which of these has
no corresponding that".

## The bug that doubles your numbers

Now the important one. This is the most common serious join mistake there is.

::runner{lang="sql"}
```sql
-- "Total fees collected per programme." Looks right. Is not.
SELECT p.code,
       SUM(f.amount_paise) AS collected,
       COUNT(*)            AS applications
FROM   Programme p
JOIN   Application a ON a.programme_id = p.programme_id
JOIN   FeePayment  f ON f.application_id = a.application_id
GROUP BY p.code;
```
::

If an application has **three** instalment payments, the join produces three rows
for that application. `COUNT(*)` now counts payments and calls them applications.
And if you add another join to a table with several rows per application, the fee
amounts are duplicated and `SUM` is multiplied.

::

::warning{icon="i-lucide-alert-triangle"}
The symptom is a dashboard number that is a suspiciously round multiple of the
truth, and the usual reaction is to add `DISTINCT` until it looks right. That
treats the symptom: `COUNT(DISTINCT application_id)` fixes the count and
`SUM(DISTINCT amount)` is actively wrong, because two genuine payments of ₹15,000
would be collapsed into one.
::

The fix is to aggregate **before** joining, so each side contributes one row.

```sql [Fixed.sql]
SELECT p.code,
       COALESCE(f.collected, 0) AS collected,
       a.applications
FROM   Programme p
LEFT JOIN (
        SELECT programme_id, COUNT(*) AS applications
        FROM   Application GROUP BY programme_id
      ) a ON a.programme_id = p.programme_id
LEFT JOIN (
        SELECT a.programme_id, SUM(f.amount_paise) AS collected
        FROM   FeePayment f
        JOIN   Application a ON a.application_id = f.application_id
        GROUP BY a.programme_id
      ) f ON f.programme_id = p.programme_id;
```

Each subquery produces exactly one row per programme, so there is nothing to
multiply.

## Aliases, and self-joins

```sql [Self.sql]
-- Applicants from the same city as Anita, excluding Anita.
SELECT other.full_name, other.city
FROM   Applicant anita
JOIN   Applicant other ON other.city = anita.city
                      AND other.applicant_id <> anita.applicant_id
WHERE  anita.full_name = 'Anita Rao';
```

A table joined to itself needs two aliases so each mention is distinguishable.
The `<>` is what stops Anita matching herself, and forgetting it is the classic
self-join bug.

## What you can do now

You can choose a join for what should happen to unmatched rows, spot the
`LEFT JOIN` that a `WHERE` clause has demoted, and recognise fan-out before it
reaches a dashboard.

## Your turn

::runner{lang="sql"}
```sql
-- 1. Every programme with the number of applications it received,
--    INCLUDING programmes that received none.

-- 2. Applicants who applied but have never made a fee payment.

-- 3. This is wrong. Say why, and fix it.
SELECT p.code, COUNT(*) AS applications, SUM(f.amount_paise) AS collected
FROM   Programme p
JOIN   Application a ON a.programme_id = p.programme_id
JOIN   FeePayment  f ON f.application_id = a.application_id
GROUP BY p.code;

-- 4. Why does this return no programmes with zero applications?
SELECT p.code, COUNT(a.application_id)
FROM   Programme p
LEFT JOIN Application a ON a.programme_id = p.programme_id
WHERE  a.intake = '2026'
GROUP BY p.code;
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  ```sql
  -- 1
  SELECT p.code, COUNT(a.application_id) AS applications
  FROM   Programme p
  LEFT JOIN Application a ON a.programme_id = p.programme_id
  GROUP BY p.code;
  ```
  **`COUNT(a.application_id)`, not `COUNT(*)`.** For a programme with no
  applications the joined row exists with nulls, so `COUNT(*)` counts it as 1 and
  reports "1 application" for a programme with none. Counting a column from the
  right-hand table skips nulls and gives 0. This is the most common mistake in
  this exact query.

  ```sql
  -- 2
  SELECT DISTINCT ap.full_name
  FROM   Applicant ap
  JOIN   Application a ON a.applicant_id = ap.applicant_id
  LEFT JOIN FeePayment f ON f.application_id = a.application_id
  WHERE  f.payment_id IS NULL;
  ```

  **3. Fan-out, twice.** An application with three payments produces three rows,
  so `COUNT(*)` counts payments. And the inner join to `FeePayment` drops every
  programme whose applicants have not paid, so a programme with applications and
  no payments disappears entirely. Fix by aggregating before joining, as above.

  **4.** The `WHERE a.intake = '2026'` is on the right-hand table, so for a
  programme with no applications `intake` is `NULL`, `NULL = '2026'` is
  `UNKNOWN`, and the row is removed. Move it into the `ON`:

  ```sql
  LEFT JOIN Application a
         ON a.programme_id = p.programme_id
        AND a.intake = '2026'
  ```
  :::
::

## Check yourself

1. What is the difference between putting a condition in `ON` and in `WHERE` on a
   `LEFT JOIN`?
2. **An interviewer asks: "explain the types of join."** Use the unmatched rows
   rather than the Venn diagram.

## The interview question this answers

**"What is the difference between an inner join and a left join?"**, asked in
essentially every SQL round.

Answer with what happens to unmatched rows, and give the concrete count: three
applicants, three applications, inner gives three rows and left gives four
because Priya is kept with nulls.

Then, unprompted, add the two things that separate you: a condition on the right
table in `WHERE` turns a left join back into an inner join; and joining to a
table with several matching rows multiplies your aggregates, which is why a
`SUM` can quietly report three times the truth. Most candidates can recite the
four joins. Almost none can name fan-out.
