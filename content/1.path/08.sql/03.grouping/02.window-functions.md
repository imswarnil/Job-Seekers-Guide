`GROUP BY` collapses. A window function does the same arithmetic and **keeps
every row**, which is what you need whenever the answer is about a row's position
among its peers.

## Why this matters in a job

Because "rank within programme", "running total" and "compare with last month"
are three of the most common real reporting requirements, and because a candidate
who can write a window function is immediately in a smaller group.

## The difference, in one pair

::runner{lang="sql"}
```sql
-- GROUP BY: three rows out, the individuals are gone.
SELECT   programme_id, AVG(score)
FROM     Application GROUP BY programme_id;

-- OVER: every row survives, and each carries its programme's average.
SELECT   applicant_id, programme_id, score,
         AVG(score) OVER (PARTITION BY programme_id) AS programme_average
FROM     Application;
```
::

```text [Output]
 applicant_id | programme_id | score | programme_average
--------------+--------------+-------+-------------------
         4182 |            1 |    78 |              74.2
         4183 |            1 |    64 |              74.2
         4184 |            2 |    81 |              71.8
```

Every applicant, with their own score **and** their programme's average beside
it. That single output cannot be produced by `GROUP BY` at all.

::pull-quote
`PARTITION BY` is `GROUP BY` that does not throw the rows away.
::

## Ranking

The most useful family, and the three are different in a way that gets asked.

::runner{lang="sql"}
```sql
SELECT ap.full_name, p.code, a.score,
       ROW_NUMBER() OVER (PARTITION BY p.code ORDER BY a.score DESC) AS row_num,
       RANK()       OVER (PARTITION BY p.code ORDER BY a.score DESC) AS rank,
       DENSE_RANK() OVER (PARTITION BY p.code ORDER BY a.score DESC) AS dense
FROM   Application a JOIN Programme p USING (programme_id)
                     JOIN Applicant ap USING (applicant_id)
WHERE  a.intake = '2026' AND a.score IS NOT NULL;
```
::

```text [Output — note the two applicants on 78]
 full_name    | code      | score | row_num | rank | dense
--------------+-----------+-------+---------+------+-------
 Priya Nair   | BTECH-CSE |    92 |       1 |    1 |     1
 Anita Rao    | BTECH-CSE |    78 |       2 |    2 |     2
 Rahul Verma  | BTECH-CSE |    78 |       3 |    2 |     2
 Vikram Shah  | BTECH-CSE |    64 |       4 |    4 |     3
```

| Function | On a tie | After a tie |
| --- | --- | --- |
| `ROW_NUMBER` | Different numbers, **arbitrarily** | Continues |
| `RANK` | Same number | **Skips** — 1, 2, 2, 4 |
| `DENSE_RANK` | Same number | No gap — 1, 2, 2, 3 |

::warning{icon="i-lucide-alert-triangle"}
`ROW_NUMBER` breaks ties arbitrarily, so two applicants on 78 get positions 2 and
3 in an order the database chose. If position decides who gets a seat, that is
not defensible. Add a deterministic tie-break —
`ORDER BY score DESC, applied_on ASC, application_id` — exactly as in the
stability lesson from the data structures track.
::

## The top n per group

The single most common real use, and it is awkward without window functions.

::runner{lang="sql"}
```sql
-- The top three scorers in each programme.
WITH ranked AS (
  SELECT ap.full_name, p.code, a.score,
         ROW_NUMBER() OVER (
           PARTITION BY p.code
           ORDER BY a.score DESC, a.applied_on ASC, a.application_id ASC
         ) AS position
  FROM   Application a JOIN Programme p USING (programme_id)
                       JOIN Applicant ap USING (applicant_id)
  WHERE  a.intake = '2026' AND a.score IS NOT NULL
)
SELECT code, position, full_name, score
FROM   ranked
WHERE  position <= 3
ORDER BY code, position;
```
::

A window function cannot go in `WHERE` — `WHERE` runs before `SELECT`, where the
window is computed — so the rank is calculated in a `WITH` and filtered outside
it. That two-step shape is the standard pattern and worth memorising.

## Running totals

::runner{lang="sql"}
```sql
-- Fees collected, cumulative, day by day.
SELECT paid_on,
       SUM(amount_paise) AS days_collection,
       SUM(SUM(amount_paise)) OVER (
         ORDER BY paid_on
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM   FeePayment
GROUP BY paid_on
ORDER BY paid_on;
```
::

```text [Output]
 paid_on    | days_collection | running_total
------------+-----------------+---------------
 2026-03-01 |         4500000 |       4500000
 2026-03-02 |         9000000 |      13500000
 2026-03-03 |         2250000 |      15750000
```

The nested `SUM(SUM(...))` is legal and looks wrong the first time: the inner one
is the `GROUP BY` aggregate, and the window runs over the already-grouped rows.

## Comparing with the previous row

::runner{lang="sql"}
```sql
-- Each intake's applications, and the change from the intake before.
SELECT intake,
       COUNT(*)                                    AS applications,
       LAG(COUNT(*)) OVER (ORDER BY intake)        AS previous_intake,
       COUNT(*) - LAG(COUNT(*)) OVER (ORDER BY intake) AS change
FROM   Application
GROUP BY intake
ORDER BY intake;
```
::

```text [Output]
 intake | applications | previous_intake | change
--------+--------------+-----------------+--------
 2024   |         1804 |            NULL |   NULL
 2025   |         1902 |            1804 |     98
 2026   |         2040 |            1902 |    138
```

`LAG` reaches back and `LEAD` reaches forward. The first row's `previous_intake`
is `NULL` because there is nothing before it, which is correct and which every
dashboard has to handle.

::tip
`LAG(x, 1, 0)` supplies a default instead of null, which is often what a chart
wants. Whether 0 or "no data" is the honest answer for the first row is a
decision, not a formatting preference.
::

## The full shape

```sql [Window.sql]
FUNCTION() OVER (
  PARTITION BY ...     -- optional: the groups. Omit it and the window is every row.
  ORDER BY ...         -- required for ranking; defines "before" for running totals
  ROWS BETWEEN ...     -- optional: which rows around the current one
)
```

::side-note{kind="go-deeper"}
`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` gives a three-row moving average,
which is how you smooth a noisy daily chart. And the default frame when you write
`ORDER BY` with no `ROWS` clause is `RANGE BETWEEN UNBOUNDED PRECEDING AND
CURRENT ROW`, which **includes all tied rows** and is a surprising source of
wrong running totals. Being explicit avoids it.
::

## What you can do now

You can rank within a group with a defensible tie-break, take the top n per
group, build a running total, and compare a row with the one before. That set
covers most real reporting requirements.

## Your turn

::runner{lang="sql"}
```sql
-- 1. Every applicant with their score, their programme's average,
--    and how far above or below it they are.

-- 2. The single highest scorer per programme, one row each,
--    with a tie-break that is reproducible.

-- 3. Each applicant's rank across the WHOLE university, not their programme.

-- 4. Why does this fail, and what is the fix?
SELECT full_name, ROW_NUMBER() OVER (ORDER BY score DESC) AS position
FROM   Application JOIN Applicant USING (applicant_id)
WHERE  ROW_NUMBER() OVER (ORDER BY score DESC) <= 10;
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  ```sql
  -- 1
  SELECT ap.full_name, a.score,
         ROUND(AVG(a.score) OVER (PARTITION BY a.programme_id), 1) AS prog_avg,
         ROUND(a.score - AVG(a.score) OVER (PARTITION BY a.programme_id), 1) AS diff
  FROM   Application a JOIN Applicant ap USING (applicant_id)
  WHERE  a.score IS NOT NULL;
  ```

  ```sql
  -- 2
  WITH ranked AS (
    SELECT ap.full_name, p.code, a.score,
           ROW_NUMBER() OVER (PARTITION BY p.code
                              ORDER BY a.score DESC, a.applied_on, a.application_id) AS rn
    FROM   Application a JOIN Programme p USING (programme_id)
                         JOIN Applicant ap USING (applicant_id)
    WHERE  a.score IS NOT NULL
  )
  SELECT code, full_name, score FROM ranked WHERE rn = 1;
  ```

  ```sql
  -- 3  Omit PARTITION BY and the window is the entire result set.
  SELECT ap.full_name, a.score,
         RANK() OVER (ORDER BY a.score DESC) AS university_rank
  FROM   Application a JOIN Applicant ap USING (applicant_id)
  WHERE  a.score IS NOT NULL;
  ```
  `RANK` rather than `ROW_NUMBER` here, because for a university-wide rank two
  people on the same score genuinely are in the same position, and giving one of
  them 47 and the other 48 arbitrarily would be indefensible.

  **4.** A window function cannot appear in `WHERE`, because `WHERE` runs before
  `SELECT` and the window has not been computed yet. This is the evaluation order
  from the first chapter doing real work. The fix is the two-step shape:

  ```sql
  WITH ranked AS (
    SELECT ap.full_name, a.score,
           ROW_NUMBER() OVER (ORDER BY a.score DESC, a.application_id) AS position
    FROM   Application a JOIN Applicant ap USING (applicant_id)
    WHERE  a.score IS NOT NULL
  )
  SELECT full_name, position FROM ranked WHERE position <= 10;
  ```
  :::
::

## Check yourself

1. What is the difference between `RANK` and `DENSE_RANK`, and when does it
   matter?
2. **An interviewer asks: "get the top three per category."** This is one of the
   most-asked SQL problems there is.

## The interview question this answers

**"Find the top N per group"** — asked constantly, because it is awkward without
window functions and elegant with them.

Give the two-step shape: `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` in a
`WITH`, then filter on it outside, and say *why* the filter has to be outside —
`WHERE` runs before the window is computed.

Then the detail that gets remembered: add a deterministic tie-break to the
`ORDER BY`, because if rank decides who gets a seat, "the database picked one"
is not an answer you can give to a parent.
