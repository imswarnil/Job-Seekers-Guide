Along with Java, this is the round most likely to decide a backend interview in
this market. It is also the most practical: you will often be given a keyboard
and a schema rather than asked to recite.

## The questions

::accordion
  :::accordion-item{label="1. WHERE or HAVING?" icon="i-lucide-message-circle"}
  `WHERE` removes rows before grouping; `HAVING` removes groups after. Then make
  it useful rather than memorised: that is *why* `WHERE` cannot reference an
  aggregate, and why a condition that could go in either belongs in `WHERE`,
  because it removes rows before the grouping work happens.
  :::

  :::accordion-item{label="2. Explain the joins" icon="i-lucide-message-circle"}
  Answer with what happens to **unmatched rows**, not with a Venn diagram. Three
  applicants and three applications: inner gives three rows, left gives four
  because the applicant who never applied is kept with nulls.

  Then add, unprompted, the two things that separate you: a right-table condition
  in `WHERE` turns a `LEFT JOIN` back into an inner join, and joining to a table
  with several matching rows multiplies your aggregates.
  :::

  :::accordion-item{label="3. What does NULL do?" icon="i-lucide-message-circle"}
  Not a value; three-valued logic; only `TRUE` returns a row. Prove it with the
  three that catch people: `= NULL` never matches, `NOT IN` containing a null
  returns nothing at all, and `AVG` divides by the non-null count.

  Close with the judgement: that last one is usually correct, and the bug is the
  label on the dashboard rather than the query.
  :::

  :::accordion-item{label="4. COUNT(*) versus COUNT(column) versus COUNT(DISTINCT)" icon="i-lucide-message-circle"}
  Rows; non-null values in that column; distinct non-null values.

  The example that makes it land: after a `LEFT JOIN`, a programme with no
  applications still produces one row with nulls, so `COUNT(*)` reports 1 and
  `COUNT(a.application_id)` reports 0. The second is what "how many
  applications" means.
  :::

  :::accordion-item{label="5. How does an index work, and when does it not help?" icon="i-lucide-message-circle"}
  A B-tree: sorted, wide and shallow, so ten million rows is four page reads.
  Then the cost, which most candidates omit: every write maintains it.

  The five cases where it is ignored: a function on the column, a leading
  wildcard, skipping the leading column of a composite index, a value that is not
  selective, and a type mismatch. Give the `YEAR(applied_on) = 2026` example and
  the range rewrite.
  :::

  :::accordion-item{label="6. A query is slow. What do you do?" icon="i-lucide-message-circle"}
  A sequence. Reproduce and time it. `EXPLAIN ANALYZE`, and look for `Seq Scan`
  and `Rows Removed by Filter` — ten million removed to return two thousand is
  the whole diagnosis. Check whether an index exists and whether the query is
  written so it can be used. Then ask whether the query is fetching more than it
  needs.

  Say what you would not do: add an index by guessing.
  :::

  :::accordion-item{label="7. Subquery, join or CTE?" icon="i-lucide-message-circle"}
  A join when you need columns from both. `EXISTS` when you only need to know
  whether a match exists, because it can stop at the first one. A CTE when the
  query has steps, because naming them is the difference between something a
  reviewer can follow and something nested four deep.

  Add: a correlated subquery in `SELECT` runs once per outer row, which is
  usually the thing to replace with a join.
  :::

  :::accordion-item{label="8. Get the top three per group" icon="i-lucide-message-circle"}
  `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` in a `WITH`, filtered
  outside it. Say *why* outside: `WHERE` runs before the window is computed.

  Then the detail: add a deterministic tie-break, because if rank decides who
  gets a seat, "the database picked one" is not an answer you can give a parent.
  :::

  :::accordion-item{label="9. RANK, DENSE_RANK or ROW_NUMBER?" icon="i-lucide-message-circle"}
  1-2-2-4, 1-2-2-3, and 1-2-3-4 with ties broken arbitrarily.

  When it matters: a university-wide merit rank should be `RANK`, because two
  people on the same marks genuinely share a position. A row number for
  pagination should be `ROW_NUMBER` with a unique tie-break, because you need
  every row to have a distinct position.
  :::

  :::accordion-item{label="10. DELETE, TRUNCATE or DROP?" icon="i-lucide-message-circle"}
  Rows with a `WHERE` and rollback and triggers; all rows instantly with none of
  those; the table itself.

  The detail that gets remembered: `TRUNCATE` **cannot be rolled back in MySQL**,
  so `BEGIN; TRUNCATE; ROLLBACK;` leaves the table empty.
  :::

  :::accordion-item{label="11. What is SQL injection and how do you prevent it?" icon="i-lucide-message-circle"}
  The `' OR '1'='1` example, then the fix with its mechanism: a prepared
  statement sends the query and the values on separate paths, so a value can
  never be parsed as part of the statement. Not escaping, not validation.

  Then the judgement: no exceptions, not for internal tools, not for values you
  believe are numeric.
  :::

  :::accordion-item{label="12. Normalisation, and when would you denormalise?" icon="i-lucide-message-circle"}
  The three anomalies rather than the three forms: a fact stored twice can be
  updated once and become inconsistent, some facts cannot be recorded without
  inventing others, deleting one thing destroys another.

  Denormalise for measured read performance, and name the case that is not
  denormalisation at all: a fee payment stores the amount **at the time of
  payment**, because the fee will change and the receipt must not.
  :::

  :::accordion-item{label="13. Two users book the same seat" icon="i-lucide-message-circle"}
  Name the bug — lost update — and that every major database's default isolation
  level still allows it. Then three fixes: a single conditional
  `UPDATE ... WHERE seats_left > 0` with the row count checked; `SELECT ... FOR
  UPDATE` when clashes are common; a version column when they are rare.

  Close with the `UNIQUE` constraint, because the real cause is usually a
  double-clicked button rather than two people.
  :::

  :::accordion-item{label="14. How would you model this?" icon="i-lucide-message-circle"}
  The open design question. It tests whether you ask before you draw.

  Nouns to entities. What identifies each, and could that value ever change.
  Cardinality, so many-to-many becomes a junction table. Which facts must be
  frozen at a moment in time. Then draw it and **name the constraints as you
  go** — this is unique, this cannot be deleted while children exist, this must
  be between 0 and 100. Naming constraints while drawing is the most senior-
  sounding thing available in this question.
  :::
::

## The three you will be given a keyboard for

These come up again and again, in this order of frequency.

::accordion
  :::accordion-item{label="Second highest salary — or here, second highest score" icon="i-lucide-keyboard"}
  The most-asked SQL problem in existence. Three answers, and being able to
  discuss the trade is the actual test.

  ```sql
  -- 1. Simple, and wrong if there are ties at the top.
  SELECT MAX(score) FROM Application
   WHERE score < (SELECT MAX(score) FROM Application);

  -- 2. DENSE_RANK: correct with ties, and says what it means.
  WITH ranked AS (
    SELECT score, DENSE_RANK() OVER (ORDER BY score DESC) AS r
    FROM Application WHERE score IS NOT NULL
  )
  SELECT DISTINCT score FROM ranked WHERE r = 2;

  -- 3. OFFSET: reads well, and quietly wrong with ties.
  SELECT DISTINCT score FROM Application
   WHERE score IS NOT NULL ORDER BY score DESC OFFSET 1 LIMIT 1;
  ```

  **Say the tie question out loud before writing anything.** "If three applicants
  tie on the highest score, is the second highest the same value or the next one
  down?" That question is what is being marked.
  :::

  :::accordion-item{label="Find the duplicates" icon="i-lucide-keyboard"}
  ```sql
  SELECT email, COUNT(*) AS occurrences
  FROM   Applicant
  GROUP BY email
  HAVING COUNT(*) > 1
  ORDER BY occurrences DESC;
  ```

  The follow-up is always "now delete all but the first", and the answer is a
  window function:

  ```sql
  DELETE FROM Applicant WHERE applicant_id IN (
    SELECT applicant_id FROM (
      SELECT applicant_id,
             ROW_NUMBER() OVER (PARTITION BY email ORDER BY created_at) AS rn
      FROM Applicant
    ) d WHERE rn > 1
  );
  ```

  And the answer that gets you the job: *"before I run that, I would check
  whether anything references those rows, and in a real system I would mark them
  as merged rather than deleting, so the ids in old emails and logs still
  resolve."*
  :::

  :::accordion-item{label="Rows in A with no match in B" icon="i-lucide-keyboard"}
  ```sql
  -- LEFT JOIN plus a null check
  SELECT ap.full_name
  FROM   Applicant ap
  LEFT JOIN Application a ON a.applicant_id = ap.applicant_id
  WHERE  a.application_id IS NULL;

  -- NOT EXISTS — usually clearer and immune to the NOT IN null trap
  SELECT ap.full_name
  FROM   Applicant ap
  WHERE  NOT EXISTS (
           SELECT 1 FROM Application a WHERE a.applicant_id = ap.applicant_id);
  ```

  If they ask which you would use: `NOT EXISTS`, because it says what it means
  and because `NOT IN` returns nothing at all if the subquery contains a null.
  :::
::

## What every answer above has in common

::feature-list{columns="2"}
  :::feature{icon="i-lucide-message-circle-question" title="It asks something first"}
  Are ties possible? Does "above the cutoff" include the cutoff? Should an
  applicant with no recorded city count as "not from Bangalore"? The question is
  frequently the point of the exercise.
  :::
  :::feature{icon="i-lucide-alert-triangle" title="It names the trap"}
  Fan-out, the null in `NOT IN`, `COUNT(*)` after a `LEFT JOIN`, `TRUNCATE` in
  MySQL. Naming a trap unprompted is the clearest signal of having done this for
  real.
  :::
::
