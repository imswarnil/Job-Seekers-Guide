No undo button anywhere. Reading a query wrongly gives you a wrong number on a
screen. Writing one wrongly changes forty thousand rows, and the database will do
it instantly and without asking.

::caution{icon="i-lucide-octagon-alert"}
**Read this lesson before you run a single `UPDATE` or `DELETE` against anything
you care about.** The habit in the "safety" section below takes four seconds and
prevents the worst mistake available to you in this subject. I know somebody who
ran an `UPDATE` with the `WHERE` on the next line, unselected, in a query tool.
::

## Why this matters in a job

Because at some point you will be given access to production data, and the
difference between a good day and a very bad one is a habit rather than a skill.

## INSERT

```sql [Insert.sql]
-- Name the columns. Always.
INSERT INTO Applicant (full_name, email, city)
VALUES ('Anita Rao', 'anita@university.edu', 'Bhopal');

-- Several at once: one statement, one round trip, far faster than three.
INSERT INTO Applicant (full_name, email, city) VALUES
  ('Vikram Shah', 'vikram@university.edu', 'Bhopal'),
  ('Priya Nair',  'priya@university.edu',  'Kochi');

-- And get back what the database generated.
INSERT INTO Application (applicant_id, programme_id, intake, status)
VALUES (4182, 1, '2026', 'RECEIVED')
RETURNING application_id, applied_on;
```

::warning{icon="i-lucide-alert-triangle"}
`INSERT INTO Applicant VALUES (...)` without column names depends on column
order. Somebody adds a column in the middle next year and every such statement
either fails or, worse, puts the city in the email field. Naming the columns
costs eight words and never breaks.
::

### When it might already exist

```sql [Upsert.sql]
-- Import that can be re-run safely after a half-finished load.
INSERT INTO Applicant (email, full_name, city)
VALUES ('anita@university.edu', 'Anita Rao', 'Bhopal')
ON CONFLICT (email) DO UPDATE
  SET full_name = EXCLUDED.full_name,
      city      = EXCLUDED.city;
```

That is an **upsert**, and it is what makes an import idempotent: running it twice
leaves the same state as running it once. From the networks track, that is the
property that makes a retry safe.

## UPDATE, and the clause you forgot

```sql [Update.sql]
UPDATE Application
   SET status = 'SHORTLISTED',
       shortlisted_on = CURRENT_DATE
 WHERE application_id = 9001;
```

```text [Output]
UPDATE 1
```

```sql [Disaster.sql]
UPDATE Application SET status = 'SHORTLISTED';
```

```text [Output]
UPDATE 2040
```

Every application in the university is now shortlisted. No error, no
confirmation, and the previous statuses are gone.

::pull-quote
`UPDATE 2040` when you expected `UPDATE 1` is the only warning you get, and it
arrives after the fact.
::

## The safety habit

Four steps, every time, and after a month it is automatic.

::flow{numbered direction="vertical" caption="Never type UPDATE first. Type SELECT first."}
  :::flow-step{label="Write it as a SELECT" icon="i-lucide-eye" highlight}
  ```sql
  SELECT * FROM Application WHERE application_id = 9001;
  ```
  Look at the rows. Is that the set you meant? Is it the number you expected?
  :::
  :::flow-step{label="Open a transaction" icon="i-lucide-shield"}
  ```sql
  BEGIN;
  ```
  Nothing you do now is permanent until you say so.
  :::
  :::flow-step{label="Run it, and READ THE COUNT" icon="i-lucide-hash"}
  ```sql
  UPDATE Application SET status = 'SHORTLISTED' WHERE application_id = 9001;
  -- UPDATE 1   ← the number is the check
  ```
  :::
  :::flow-step{label="COMMIT, or ROLLBACK" icon="i-lucide-check"}
  `UPDATE 1`, as expected → `COMMIT;`
  `UPDATE 2040` → **`ROLLBACK;`**, and nothing happened.
  :::
::

```sql [Safe.sql]
BEGIN;
UPDATE Application SET status = 'SHORTLISTED' WHERE score >= 75 AND intake = '2026';
-- UPDATE 1840. Expected roughly that. Good.
SELECT COUNT(*) FROM Application WHERE status = 'SHORTLISTED';   -- check inside
COMMIT;
```

You can query inside the transaction and see your own uncommitted changes, which
nobody else can see yet. That is the isolation lesson from the DBMS track being
directly useful.

::tip
Turn off autocommit in any tool you use against a real database. In `psql`,
`\set AUTOCOMMIT off`. It means every statement is inside a transaction by
default and a mistake needs a `ROLLBACK` rather than a restore from backup. This
single setting is the cheapest insurance in this subject.
::

## UPDATE from another table

```sql [UpdateFrom.sql]
-- Mark every application under review whose applicant has withdrawn.
UPDATE Application a
   SET status = 'WITHDRAWN'
  FROM Applicant ap
 WHERE ap.applicant_id = a.applicant_id
   AND ap.withdrawn = true
   AND a.status = 'UNDER_REVIEW';
```

::warning{icon="i-lucide-alert-triangle"}
Missing the join condition — `WHERE ap.applicant_id = a.applicant_id` — does not
fail. It matches every combination and updates every row. This is the fan-out
bug from the joining chapter, and here it writes instead of reporting.
::

## DELETE, and why you usually should not

```sql [Delete.sql]
DELETE FROM Application WHERE application_id = 9001;
```

Real systems rarely delete. They mark.

::compare{caption="Two ways to remove an application."}
  :::compare-side{label="DELETE" verdict="wrong"}
  The row is gone. So is the answer to "how many applications were withdrawn
  this intake", any foreign key pointing at it, and any chance of finding out
  what happened when somebody asks in November.
  :::
  :::compare-side{label="Soft delete" verdict="right"}
  ```sql
  UPDATE Application
     SET status = 'WITHDRAWN', withdrawn_on = CURRENT_DATE
   WHERE application_id = 9001;
  ```
  The history survives, reports can still count it, and it can be undone.
  :::
::

::side-note{kind="go-deeper"}
Soft deletion has a real cost that is worth naming: every query now needs
`AND status <> 'WITHDRAWN'`, and forgetting it once produces a report that
includes deleted rows. The usual mitigation is a view that filters them, which
application code reads instead of the table. Knowing the cost as well as the
benefit is what makes this an argument rather than a rule.
::

## TRUNCATE, and the difference that gets asked

| | `DELETE FROM t` | `TRUNCATE t` | `DROP TABLE t` |
| --- | --- | --- | --- |
| Removes | Rows, one at a time | All rows, instantly | Rows **and the table** |
| `WHERE` | Yes | No | No |
| Transactional | Yes, rollback works | In PostgreSQL yes; in MySQL **no** | Sometimes not |
| Fires triggers | Yes | No | No |
| Speed on a big table | Slow | Instant | Instant |

::caution{icon="i-lucide-octagon-alert"}
In MySQL, `TRUNCATE` cannot be rolled back. `BEGIN; TRUNCATE Application;
ROLLBACK;` leaves the table empty. This is a genuinely dangerous difference
between databases and a favourite interview question.
::

## SQL injection, from the writing side

The most exploited vulnerability in the world, and it is one line of code.

```java [Vulnerable.java]
// NEVER. Not once, not for an internal tool, not "just for now".
String sql = "SELECT * FROM Applicant WHERE email = '" + email + "'";
```

If `email` is `x' OR '1'='1`, the query becomes
`WHERE email = 'x' OR '1'='1'` and returns every applicant. If it is
`x'; DROP TABLE Application; --`, it does what it says.

```java [Safe.java]
// A placeholder. The value is sent separately and is NEVER parsed as SQL.
String sql = "SELECT * FROM Applicant WHERE email = ?";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
  ps.setString(1, email);
  ResultSet rs = ps.executeQuery();
}
```

::pull-quote
A prepared statement does not escape the value. It sends the query and the data
down separate paths, so the data can never become part of the statement. That is
why it is a fix rather than a mitigation.
::

::warning{icon="i-lucide-alert-triangle"}
Escaping by hand is not a fix. Every escaping scheme has been defeated by a
character encoding somebody did not think about. There is no situation in which
string concatenation into SQL is acceptable, including internal tools, including
a value you "know" is a number. Use the placeholder.
::

## What you can do now

You can insert, update and delete safely, you have the four-step habit that makes
a destructive mistake almost impossible, and you can explain why a prepared
statement is a fix rather than a precaution.

## Your turn

::runner{lang="sql"}
```sql
-- 1. Shortlist every 2026 application scoring 75 or more that is under review.
--    Write the SELECT first. Say what count you expect.

-- 2. A duplicate applicant was created with a typo'd email. Merge:
--    move their applications to the correct applicant_id, then mark
--    the duplicate as merged rather than deleting it.

-- 3. What is wrong with each of these?
UPDATE Application SET status = 'ACCEPTED' WHERE score > 90;
DELETE FROM Applicant WHERE city = 'Bhopal';
UPDATE FeePayment SET amount_paise = amount_paise * 1.1;
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  ```sql
  -- 1
  SELECT COUNT(*) FROM Application
   WHERE intake = '2026' AND score >= 75 AND status = 'UNDER_REVIEW';
  -- say the number out loud before continuing

  BEGIN;
  UPDATE Application
     SET status = 'SHORTLISTED', shortlisted_on = CURRENT_DATE
   WHERE intake = '2026' AND score >= 75 AND status = 'UNDER_REVIEW';
  -- does the count match? then:
  COMMIT;
  ```

  ```sql
  -- 2  Both statements, or neither.
  BEGIN;
  UPDATE Application SET applicant_id = 4182 WHERE applicant_id = 4999;
  UPDATE Applicant   SET status = 'MERGED', merged_into = 4182
   WHERE applicant_id = 4999;
  COMMIT;
  ```
  One transaction, because an application moved with the duplicate still active
  is worse than either change alone. And `MERGED` rather than `DELETE`, so that
  anybody who finds the old id in a log or an email can still trace it.

  **3.** All three:

  - `WHERE score > 90` has no `intake` filter, so it accepts high scorers from
    every intake including 2024. And `>` excludes exactly 90, which may or may
    not be the rule. Ask.
  - Deleting applicants by city will fail on a foreign key if they have
    applications, and if it succeeds it has destroyed people's records on the
    basis of where they live. There is no version of this that is right.
  - Multiplying money by `1.1` turns an exact `BIGINT` count of paise into a
    floating-point number and back, so 4,500,000 becomes 4,950,000.0000001 and
    is then truncated unpredictably. Fee changes are a new row with a new
    effective date, not arithmetic on the historical record. **A payment that
    already happened is a fact, and facts do not get a ten per cent increase.**
  :::
::

## Check yourself

1. What are the four steps before running an `UPDATE` on real data?
2. **An interviewer asks: "how do you prevent SQL injection?"** Answer with the
   mechanism, not the word "sanitise".

## The interview question this answers

**"What is SQL injection and how do you prevent it?"** — asked in almost every
backend interview, and one of the few where a wrong answer is disqualifying.

Say what it is with the `' OR '1'='1` example. Then the fix, with the mechanism:
a prepared statement sends the query and the values on separate paths, so a value
can never be parsed as part of the statement. It is not escaping and it is not
validation.

Then the sentence that shows judgement: there is no acceptable exception, not for
internal tools and not for values you believe are numeric, because "I know this
input" is the assumption every breach was built on.
