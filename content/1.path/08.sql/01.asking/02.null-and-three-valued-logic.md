Not a value. `NULL` means "we do not know", and once you accept that, everything
it does becomes predictable instead of infuriating.

## Why this matters in a job

Because `NULL` is behind a large share of reports that are quietly wrong, and
because "why does `NOT IN` return nothing" is a question that has ended
afternoons. It is also asked directly in interviews, and most candidates can
define it and cannot predict it.

## Three-valued logic

SQL has `TRUE`, `FALSE` and `UNKNOWN`, and only rows where the condition is
`TRUE` come back.

```sql [Logic.sql]
NULL = NULL      → UNKNOWN     -- not TRUE, and not FALSE
NULL <> 5        → UNKNOWN
NULL > 5         → UNKNOWN
NULL + 10        → NULL        -- unknown plus ten is unknown
'Anita' || NULL  → NULL        -- the whole string becomes unknown
```

::pull-quote
Is an unknown score equal to another unknown score? Nobody can say. That is
`UNKNOWN`, it is not `TRUE`, so the row is not returned.
::

```sql [Correct.sql]
WHERE score IS NULL           -- the only way to ask
WHERE score IS NOT NULL
WHERE COALESCE(score, 0) > 50 -- substitute a value, deliberately
```

## The one that costs an afternoon

```sql [NotIn.sql]
-- "Applicants who have NOT applied to any programme in the CSE department."
SELECT full_name
FROM   Applicant
WHERE  applicant_id NOT IN (
         SELECT applicant_id FROM Application WHERE department_id = 1
       );
```

```text [Output]
(0 rows)
```

Zero rows, and there are certainly applicants who have not. If **any** row in
that subquery has a `NULL` applicant_id, the whole `NOT IN` becomes `UNKNOWN`
for every outer row.

::code-trace{caption="Why. Expand what NOT IN actually means."}
```sql [NotIn.sql]
WHERE applicant_id NOT IN (4182, 9001, NULL)
```

  :::code-trace-step{lines="1" caption="NOT IN (a, b, c) expands to: id <> a AND id <> b AND id <> c."}
  :::
  :::code-trace-step{lines="1" caption="So: id <> 4182 AND id <> 9001 AND id <> NULL. The last one is UNKNOWN, always."}
  :::
  :::code-trace-step{lines="1" caption="TRUE AND TRUE AND UNKNOWN is UNKNOWN. Not TRUE. So the row is not returned — and this is true of EVERY row."}
  :::
::

Three fixes, and the third is the one to use:

```sql [Fixes.sql]
-- 1. Exclude the nulls from the subquery
WHERE applicant_id NOT IN (
        SELECT applicant_id FROM Application
        WHERE department_id = 1 AND applicant_id IS NOT NULL)

-- 2. NOT EXISTS: immune to this, and usually faster
WHERE NOT EXISTS (
        SELECT 1 FROM Application a
        WHERE a.applicant_id = Applicant.applicant_id AND a.department_id = 1)

-- 3. A LEFT JOIN with a null check. The joining chapter.
```

::tip
Prefer `NOT EXISTS` over `NOT IN` as a default. It handles nulls correctly
without you having to remember, and on most databases it plans better. This is a
small, specific preference that sounds experienced in an interview.
::

## Aggregates skip NULL, silently

This is the one that produces a wrong number on a dashboard with nothing
apparently broken.

::runner{lang="sql"}
```sql
-- 2,040 applications. 200 have not been marked yet.
SELECT COUNT(*)      AS rows_in_table,      -- 2040: counts rows
       COUNT(score)  AS marked,             -- 1840: counts NON-NULL scores
       AVG(score)    AS average,            -- over 1840, not 2040
       SUM(score)    AS total
FROM   Application
WHERE  intake = '2026';
```
::

```text [Output]
 rows_in_table | marked | average | total
---------------+--------+---------+--------
          2040 |   1840 |    72.4 | 133216
```

`AVG` divided by 1,840, not 2,040. That is almost certainly correct — an unmarked
applicant should not drag the average down — and **the screen must say so**,
because "average score: 72.4" invites the reader to assume it covers everybody.

::compare{caption="Same number. Two claims, and one of them is misleading."}
  :::compare-side{label="What gets put on the dashboard" verdict="wrong"}
  **Average score this intake: 72.4**

  The dean assumes 2,040 applicants. They do not know 200 are unmarked.
  :::
  :::compare-side{label="What the query actually computed" verdict="right"}
  **Average score: 72.4** — from 1,840 marked applications out of 2,040.
  200 not yet marked.

  Same query. The honest label is the deliverable.
  :::
::

`COUNT(*)` counts rows and `COUNT(column)` counts non-null values in that column.
That distinction is a standard interview question and it is exactly the mechanism
above.

## NULL in ORDER BY and GROUP BY

```sql [Sorting.sql]
-- Where do NULLs sort? It DIFFERS between databases.
ORDER BY score DESC                  -- PostgreSQL: nulls first. MySQL: nulls last.
ORDER BY score DESC NULLS LAST       -- say it explicitly
```

```sql [Grouping.sql]
-- GROUP BY treats all NULLs as ONE group, which is the opposite of
-- how comparison treats them. Inconsistent, and worth knowing.
SELECT status, COUNT(*) FROM Application GROUP BY status;
```

## The four tools

| Function | Does |
| --- | --- |
| `COALESCE(a, b, c)` | The first non-null. The standard way to substitute a default. |
| `NULLIF(a, b)` | `NULL` if the two are equal. Useful to turn a 0 divisor into a null and avoid an error. |
| `IS DISTINCT FROM` | Comparison that treats two nulls as equal. Rare and occasionally exactly right. |
| `CASE WHEN x IS NULL THEN ... END` | When you need different behaviour rather than a substitute value. |

```sql [Coalesce.sql]
SELECT full_name,
       COALESCE(score, 0)                       AS score_for_sorting,
       COALESCE(city, 'Not given')              AS city,
       ROUND(marks * 100.0 / NULLIF(held, 0), 1) AS attendance_pct
FROM   ...
```

That last line is the idiom worth stealing: `NULLIF(held, 0)` turns a zero
divisor into `NULL`, so instead of a division-by-zero error you get `NULL`,
meaning "cannot be calculated". Which is the truth.

::warning{icon="i-lucide-alert-triangle"}
`COALESCE(score, 0)` is a decision, not a formatting choice. It says an unmarked
applicant scored zero, which changes the average and can change who is
shortlisted. Use it when zero genuinely is the right default and never merely to
make a null go away.
::

## What you can do now

You can predict what `NULL` does in comparisons, arithmetic and aggregates,
avoid the `NOT IN` trap, and write the honest label that turns a correct number
into a true statement.

## Your turn

::runner{lang="sql"}
```sql
-- Application(application_id, applicant_id, score, status, city)
-- 2,040 rows. 200 have score NULL. 60 have city NULL.

-- Predict each, then run it.
SELECT COUNT(*)        FROM Application;                    -- 1
SELECT COUNT(score)    FROM Application;                    -- 2
SELECT COUNT(*)        FROM Application WHERE score > 50;   -- 3
SELECT COUNT(*)        FROM Application WHERE score <= 50;  -- 4
SELECT COUNT(*)        FROM Application WHERE score IS NULL;-- 5
-- Does 3 + 4 + 5 equal 1? Why, or why not?

-- 6. "Everyone not from Bangalore." This is wrong. Fix it.
SELECT full_name FROM Application WHERE city <> 'Bangalore';
```
::

::accordion
  :::accordion-item{label="Answers, and the one that matters" icon="i-lucide-check"}
  1. `2040`. 2. `1840`. 5. `200`.

  **3 + 4 + 5 does equal 2040**, and that is the point of the exercise: rows with
  a null score satisfy *neither* `> 50` nor `<= 50`, because both are `UNKNOWN`.
  They are only found by `IS NULL`. If you split a report into "passed" and
  "failed" with a single comparison, the unmarked ones vanish from both and the
  two numbers do not add up to the total. That is a real bug and it is invisible
  unless somebody adds the columns.

  **6.** `WHERE city <> 'Bangalore'` excludes the 60 rows with a null city,
  because `NULL <> 'Bangalore'` is `UNKNOWN`. "Everyone not from Bangalore"
  almost certainly includes people whose city is not recorded. The fix:

  ```sql
  WHERE city IS DISTINCT FROM 'Bangalore'            -- PostgreSQL
  WHERE city <> 'Bangalore' OR city IS NULL          -- portable
  ```

  And the real answer in an interview is to **ask**: should an applicant with no
  recorded city be in "not from Bangalore"? It is a question for the registrar,
  not for the developer, and noticing that it is a question is the skill.
  :::
::

1. Why does `NOT IN` return no rows when the subquery contains a null?
2. **An interviewer asks: "what is the difference between `COUNT(*)` and
   `COUNT(column)`?"**

## The interview question this answers

**"How does NULL behave in SQL?"**

Not a value; the absence of one; three-valued logic where only `TRUE` returns a
row. Then prove it with the three that catch people: `= NULL` never matches,
`NOT IN` with a null returns nothing at all, and aggregates skip nulls so `AVG`
divides by a smaller count than you expect.

Close with the judgement, which is what they are really listening for: the last
one is usually the *correct* behaviour, and the bug is the label on the
dashboard rather than the query.
