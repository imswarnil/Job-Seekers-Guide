The data belongs somewhere permanent, and you already know the theory from the
DBMS track. This is the language that puts it there and gets it back, and it is
the one that most often decides an interview.

## Why this matters in a job

Because almost every backend role tests SQL directly, because a data analyst role
is essentially SQL, and because it is the skill with the longest shelf life in
this course. Frameworks change every three years. The `SELECT` you write today
will still be valid in twenty.

::real-life{title="What I actually use, six years later" source="Salesforce, in Europe"}
I write far less Java than I did and I have not touched Spring in years. I think
in queries every week. How S. N. Dixit sir taught me to reason about a query:
what set of rows am I starting from, what am I removing, what am I grouping, is
the thing that transferred. The syntax is the smallest part of it.
::

## The tables

Everything in this track runs against these. They are the DBMS track's design.

```sql [schema.sql]
Applicant   (applicant_id, full_name, email, city, created_at)
Programme   (programme_id, code, name, department_id, seats, fee_paise)
Application (application_id, applicant_id, programme_id, intake,
             score, status, applied_on)
Department  (department_id, name, head_faculty_id)
FeePayment  (payment_id, application_id, receipt_number, amount_paise, paid_on)
```

`status` is the ladder: `RECEIVED`, `UNDER_REVIEW`, `SHORTLISTED`, `REJECTED`,
`ACCEPTED`, `WITHDRAWN`.

## SELECT

::runner{lang="sql"}
```sql
-- Every column, every row. Useful for looking, never for a real query.
SELECT * FROM Applicant;

-- The columns you actually want.
SELECT full_name, email, city FROM Applicant;

-- Renamed for the reader, and computed.
SELECT full_name          AS name,
       city               AS home_town,
       fee_paise / 100.0  AS fee_rupees
FROM   Programme;
```
::

::warning{icon="i-lucide-alert-triangle"}
`SELECT *` in application code is a habit worth not forming. It sends columns you
do not use over the network, it breaks silently when somebody adds a column, and
it stops the database answering from an index alone. Name the columns. In an
interview, using `SELECT *` in your answer is a small, noticed thing.
::

## WHERE

::runner{lang="sql"}
```sql
SELECT full_name, score
FROM   Application a
JOIN   Applicant  ap USING (applicant_id)
WHERE  a.intake = '2026'
  AND  a.score >= 75
  AND  a.status <> 'WITHDRAWN';
```
::

| Operator | Means | Note |
| --- | --- | --- |
| `=` `<>` | equals, not equals | `!=` also works; `<>` is the standard |
| `>` `>=` `<` `<=` | comparison | |
| `BETWEEN 70 AND 80` | inclusive at **both** ends | A boundary worth checking |
| `IN ('CSE', 'ECE')` | any of these | Cleaner than a chain of `OR` |
| `LIKE 'Anita%'` | pattern; `%` any run, `_` one character | A **leading** `%` cannot use an index |
| `IS NULL` / `IS NOT NULL` | absence | **Never `= NULL`.** Next lesson. |

## ORDER BY and LIMIT

::runner{lang="sql"}
```sql
SELECT full_name, score, applied_on
FROM   Application a JOIN Applicant USING (applicant_id)
WHERE  a.intake = '2026' AND a.score IS NOT NULL
ORDER BY a.score DESC,          -- highest first
         a.applied_on ASC       -- ties broken by who applied first
LIMIT 10;
```
::

That second sort column is the stability lesson from the data structures track,
in SQL. Without it, two applicants on 78 come back in whatever order the database
found convenient, which may differ between runs. **A shortlist with no tie-break
is not reproducible**, and that is a real problem rather than a tidiness one.

::tip
Always `ORDER BY` something unique last. `ORDER BY score DESC, application_id`
guarantees the same order every time. Without it, the same query can return
different rows for "page 2" on two consecutive requests, which is a genuinely
baffling bug to be handed.
::

## The order it is really evaluated in

You write the clauses in one order and the database evaluates them in another.
Three errors that otherwise look arbitrary fall straight out of this.

::flow{numbered direction="vertical" caption="Written: SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. Evaluated: this."}
  :::flow-step{label="FROM and JOIN" icon="i-lucide-table-2"}
  Build the working set of rows. Everything else operates on this.
  :::
  :::flow-step{label="WHERE" icon="i-lucide-filter" highlight}
  Throw rows away. **Before any grouping**, which is why `WHERE` cannot see an
  aggregate.
  :::
  :::flow-step{label="GROUP BY" icon="i-lucide-layers"}
  Collapse the survivors into groups.
  :::
  :::flow-step{label="HAVING" icon="i-lucide-funnel"}
  Throw whole groups away. This is where aggregate conditions go.
  :::
  :::flow-step{label="SELECT" icon="i-lucide-columns-3"}
  Work out the output columns, and only now do aliases exist.
  :::
  :::flow-step{label="ORDER BY" icon="i-lucide-arrow-down-up"}
  Sort. Aliases from `SELECT` **can** be used here, because it runs after.
  :::
  :::flow-step{label="LIMIT" icon="i-lucide-scissors"}
  Take the first n. Always last, which is why `LIMIT 10` still sorts everything
  first unless an index provides the order.
  :::
::

```sql [WhyItFails.sql]
-- Fails: the alias does not exist yet when WHERE runs.
SELECT score / 100.0 AS fraction FROM Application WHERE fraction > 0.75;

-- Works: ORDER BY runs after SELECT.
SELECT score / 100.0 AS fraction FROM Application ORDER BY fraction DESC;

-- Fails: WHERE runs before grouping, so there is no COUNT yet.
SELECT programme_id FROM Application WHERE COUNT(*) > 100 GROUP BY programme_id;

-- Works: HAVING runs after.
SELECT programme_id FROM Application GROUP BY programme_id HAVING COUNT(*) > 100;
```

::pull-quote
Nearly every "why does this not work" in SQL is this list. Learn the evaluation
order once and three categories of error stop being mysterious.
::

## DISTINCT, and the question it hides

::runner{lang="sql"}
```sql
-- How many applications? How many applicants? Different numbers.
SELECT COUNT(*)                        AS applications,
       COUNT(DISTINCT applicant_id)    AS applicants
FROM   Application
WHERE  intake = '2026';
```
::

```text [Output]
 applications | applicants
--------------+------------
         2040 |       1602
```

This is the dashboard bug from the English track, in its original form. Both
numbers are legitimate and they answer different questions, and the label on the
screen is what decides whether the dean is being told the truth.

::warning{icon="i-lucide-alert-triangle"}
`DISTINCT` appearing in a query is worth a second look. Sometimes it is what you
mean. More often it is covering up a join that is producing duplicate rows, and
you are treating a symptom. The joining chapter is about exactly that.
::

## What you can do now

You can select, filter, sort and limit, and you can explain three common errors
from the evaluation order rather than by trial.

## Your turn

::runner{lang="sql"}
```sql
-- Against Application(application_id, applicant_id, programme_id,
--                     intake, score, status, applied_on)

-- 1. The ten highest scores in the 2026 intake, excluding withdrawn,
--    with a tie-break that makes the result reproducible.

-- 2. Every application with a score between 60 and 75 inclusive.
--    Then: how would you exclude exactly 75?

-- 3. Applications from either CSE or ECE, received in March 2026.

-- 4. Why does this return nothing, and what is the fix?
SELECT * FROM Application WHERE score = NULL;
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  ```sql
  -- 1
  SELECT application_id, applicant_id, score
  FROM   Application
  WHERE  intake = '2026' AND status <> 'WITHDRAWN' AND score IS NOT NULL
  ORDER BY score DESC, applied_on ASC, application_id ASC
  LIMIT 10;
  ```
  Three sort keys, the last unique, so two runs cannot disagree.

  ```sql
  -- 2
  WHERE score BETWEEN 60 AND 75          -- inclusive at both ends
  WHERE score >= 60 AND score < 75       -- excluding exactly 75
  ```
  `BETWEEN` being inclusive at both ends is the kind of thing that produces a
  telephone call. When the rule matters, write the comparison out.

  ```sql
  -- 3
  SELECT a.*
  FROM   Application a
  JOIN   Programme p USING (programme_id)
  WHERE  p.code IN ('BTECH-CSE', 'BTECH-ECE')
    AND  a.applied_on >= DATE '2026-03-01'
    AND  a.applied_on <  DATE '2026-04-01';
  ```
  Note the date range rather than `MONTH(applied_on) = 3`. A function on the
  column means the index cannot be used, which is straight from the DBMS track.

  **4.** Nothing at all, and no error. `NULL` means "unknown", so `score = NULL`
  asks "is this unknown value equal to this unknown value", and the answer is
  itself unknown, which is not true, so no row is returned. The fix is
  `WHERE score IS NULL`, and the whole of the next lesson.
  :::
::

## Check yourself

1. Why can `WHERE` not use an alias defined in `SELECT`, when `ORDER BY` can?
2. **An interviewer asks: "what is the difference between `COUNT(*)` and
   `COUNT(DISTINCT applicant_id)`?"**

## The interview question this answers

**"Walk me through how a SQL query is executed."**

Give the evaluation order, `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`,
`ORDER BY`, `LIMIT`, and then immediately make it useful by naming what it
explains: why an alias fails in `WHERE` and works in `ORDER BY`, and why an
aggregate condition belongs in `HAVING`. Reciting the order is common; using it
to explain an error is not.

## Next

::callout{icon="i-lucide-arrow-right"}
That last question is the tip of something. `NULL` is not a value, it is the
absence of one, and it behaves differently from everything else in comparisons,
in arithmetic, in aggregates and in joins. It is the most common source of a
report that is quietly wrong.
::
