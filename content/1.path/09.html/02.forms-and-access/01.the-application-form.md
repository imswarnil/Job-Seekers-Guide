Eleven at night, on a phone, with a bad connection, getting it wrong. That is the
real condition of the form the entire university system depends on, and it is the
single highest-stakes page in the application.

## Why this matters in a job

Because forms are where users actually meet software, because a form that is
hard to complete costs a university applications, and because almost every form
on the internet has the same eight mistakes.

## The structure

```html [apply.html]
<form method="post" action="/applications">
  <h1>Application for admission, 2026</h1>

  <fieldset>
    <legend>Your details</legend>

    <p>
      <label for="full-name">Full name</label>
      <input id="full-name" name="fullName" type="text"
             autocomplete="name" required>
    </p>

    <p>
      <label for="email">Email address</label>
      <input id="email" name="email" type="email"
             autocomplete="email" required
             aria-describedby="email-help">
      <span id="email-help">We will send your application number here.</span>
    </p>

    <p>
      <label for="phone">Mobile number</label>
      <input id="phone" name="phone" type="tel"
             inputmode="numeric" autocomplete="tel" required>
    </p>
  </fieldset>

  <fieldset>
    <legend>Programme</legend>

    <p>
      <label for="programme">Programme applied for</label>
      <select id="programme" name="programmeId" required>
        <option value="">Choose a programme</option>
        <option value="1">B.Tech Computer Science</option>
        <option value="2">B.Tech Electronics</option>
      </select>
    </p>

    <p>
      <label for="marks">Class XII percentage</label>
      <input id="marks" name="marks" type="number"
             min="0" max="100" step="0.01" required
             aria-describedby="marks-help">
      <span id="marks-help">As printed on your marksheet, to two decimals.</span>
    </p>
  </fieldset>

  <button type="submit">Submit application</button>
</form>
```

## Why each part is there

::feature-list{columns="2"}
  :::feature{icon="i-lucide-tag" title="`label` with `for`"}
  Not a caption. It makes the **label clickable**, which is the whole target on
  a phone, and it is what a screen reader announces when the field is focused.
  Without it the user hears "edit text, blank".
  :::
  :::feature{icon="i-lucide-smartphone" title="`type` and `inputmode`"}
  `type="email"` gives a phone keyboard with `@` on it. `inputmode="numeric"`
  gives a number pad. On a phone this is the difference between eight taps and
  three.
  :::
  :::feature{icon="i-lucide-wand" title="`autocomplete`"}
  Lets the browser fill name, email and phone from what the user already has
  stored. Correctly spelled, instantly, every time. Omitting it is the most
  common unforced error in forms.
  :::
  :::feature{icon="i-lucide-info" title="`aria-describedby`"}
  Ties the hint text to the field so a screen reader reads it with the label. A
  hint sitting in a nearby `span` is invisible to a screen reader user, who then
  does not know the format.
  :::
  :::feature{icon="i-lucide-group" title="`fieldset` and `legend`"}
  Groups related fields and announces the group name. Essential for radio
  buttons, where the question itself is the legend.
  :::
  :::feature{icon="i-lucide-send" title="`type="submit"` and a real `form`"}
  Enter submits, the browser can restore the data, and it works before
  JavaScript loads. A `div` with a click handler does none of that.
  :::
::

## Validation that helps

::compare{caption="The same invalid email, two experiences."}
  :::compare-side{label="What most forms do" verdict="wrong"}
  Submit. Page reloads. Every field is empty again. A red bar at the top says
  "Invalid input". The user does not know which field, does not know why, and
  has to retype everything on a phone.
  :::
  :::compare-side{label="What to do" verdict="right"}
  The error appears next to the field, after the user has finished with it
  rather than while typing, says what is wrong **and what is expected**, the
  field is marked `aria-invalid`, focus moves to the first error on submit, and
  nothing the user typed is lost.
  :::
::

```html [error.html]
<p>
  <label for="marks">Class XII percentage</label>
  <input id="marks" name="marks" type="number" min="0" max="100"
         aria-invalid="true" aria-describedby="marks-error">
  <span id="marks-error" role="alert">
    Enter a percentage between 0 and 100. You entered 780, did you mean 78.0?
  </span>
</p>
```

That message does three things a generic one does not: it says the rule, it
repeats what they typed, and it guesses the likely mistake. Writing error
messages is a real skill and it is the English track showing up in the interface.

::warning{icon="i-lucide-alert-triangle"}
**Client-side validation is a kindness, never a rule.** Everything here can be
bypassed by anybody with developer tools open, so the server must check all of
it again. The front-end check exists so an honest user is told immediately; the
back-end check exists so the data is correct. This is the front-end/back-end
line from the orientation track and it is the most common serious mistake in
junior work.
::

## The eight mistakes

::feature-list{columns="2"}
  :::feature{icon="i-lucide-x" title="Placeholder instead of label"}
  The placeholder vanishes the moment they type, so anybody who loses their
  place no longer knows what the field was. It also fails contrast requirements
  in most designs.
  :::
  :::feature{icon="i-lucide-x" title="Validating while typing"}
  "Invalid email" appears after the first character. Validate on blur, or on
  submit, not on every keystroke.
  :::
  :::feature{icon="i-lucide-x" title="Clearing the form on error"}
  Unforgivable on a phone. Return what they typed.
  :::
  :::feature{icon="i-lucide-x" title="No autocomplete"}
  Forces manual typing of things the browser already knows, which is slower and
  produces more typos.
  :::
  :::feature{icon="i-lucide-x" title="A regular expression for emails"}
  Almost every one in circulation rejects valid addresses. Check there is an
  `@` with something either side, and confirm by sending mail. That is the only
  real validation.
  :::
  :::feature{icon="i-lucide-x" title="Disabling the submit button"}
  A disabled button that does not say why leaves the user stuck with no
  feedback. Let them submit and tell them what is wrong.
  :::
  :::feature{icon="i-lucide-x" title="No protection against a double submit"}
  They tap twice on a slow connection and apply twice. This is the idempotency
  lesson from the networks track, and the fix is a unique constraint plus
  disabling the button **after** submission starts.
  :::
  :::feature{icon="i-lucide-x" title="Losing everything on a dropped connection"}
  Eleven at night, bad signal. Save a draft to local storage as they go, and
  restore it.
  :::
::

## The acceptance criteria

Build it. Done means all of these, and test each one deliberately.

::flow{numbered direction="vertical" caption="Six tests. Four of them nobody runs."}
  :::flow-step{label="Complete it using only the keyboard" icon="i-lucide-keyboard" highlight}
  Tab through every field, choose a programme, submit, with the mouse
  untouched. If you cannot, neither can a real user.
  :::
  :::flow-step{label="Complete it on a phone" icon="i-lucide-smartphone"}
  A real one, not a resized browser window. Check the keyboard that appears for
  each field.
  :::
  :::flow-step{label="Submit it empty" icon="i-lucide-circle-slash"}
  Every error should be visible, specific, and focus should land on the first
  one.
  :::
  :::flow-step{label="Submit it invalid, and check nothing is lost" icon="i-lucide-undo"}
  Percentage 780, a malformed email. The valid fields must still be filled.
  :::
  :::flow-step{label="Submit it twice, fast" icon="i-lucide-copy"}
  One application, not two. Enforced in the database, not only in the interface.
  :::
  :::flow-step{label="Bypass the front end entirely" icon="i-lucide-shield"}
  `curl` the endpoint with a percentage of 780 and no email. The server must
  refuse. If it accepts, your validation is decoration.
  :::
::

## Your turn

Build the form, then run all six tests and write down what failed.

::accordion
  :::accordion-item{label="What usually fails, in order of frequency" icon="i-lucide-list-checks"}
  **Test six**, almost always, on a first attempt. The front end validates
  beautifully and the endpoint accepts anything. This is the single most common
  serious flaw in junior work and it is a five-minute fix once seen.

  **Test five.** The double submit. Nobody thinks of it until they watch an
  applicant do it on a slow connection, and the correct fix is in the schema
  (`UNIQUE (applicant_id, programme_id)`) rather than in the button.

  **Test one.** Usually one control is unreachable, and it is usually a custom
  dropdown or a `div` acting as a button.

  **And one that is not on the list:** try it with a 60-character name and a
  name containing an apostrophe. `O'Brien` breaks a surprising amount of
  software, and if it breaks yours, look very carefully at how that string is
  reaching your database, because you may have found an injection.
  :::
::

## Check yourself

1. Why is a `label` with `for` not the same as text next to an input?
2. **An interviewer asks: "you have client-side validation. Why does the server
   need to validate too?"**

## The interview question this answers

**"How do you make a form accessible?"**

Labels tied with `for`, correct input types so the right keyboard appears,
`autocomplete`, hints tied with `aria-describedby`, grouped fields with a
`legend`, errors next to the field and announced, and focus moved to the first
error.

Then the test that proves it, which is the part that sounds like somebody who has
actually done it: complete the whole form using only the keyboard. If you cannot,
it is not accessible, whatever the audit tool says.
