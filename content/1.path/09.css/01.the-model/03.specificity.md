The browser counts. Every selector gets a score of three numbers, and when two
rules set the same property on the same element, the higher score wins wherever
it sits in the file. In the last lesson's example, `.results td` and
`td[data-status="fail"]` score exactly the same, so the one written later wins.
By the end of this lesson you will be able to work that out in your head.

## Why this matters in a job

Because the specificity puzzle is the most common CSS question in fresher
interviews: three or four selectors on a whiteboard and "which colour is the
text?" It has a mechanical answer, and getting it right in ten seconds tells the
interviewer you understand the cascade rather than guessing at it.

At work, specificity is the reason a stylesheet either stays easy to change or
fills up with `!important`.

## The score, counted in three columns

Think of a cricket scoreboard read as wickets in hand, then runs, then extras.
You do not add them together. You compare the first column, and only if it is
level do you look at the second. Specificity works the same way, with three
columns:

- **Column A, ids:** each `#id` adds one.
- **Column B, classes:** each `.class`, each attribute selector `[type="email"]`
  and each pseudo-class `:hover` adds one.
- **Column C, types:** each tag name `p` and each pseudo-element `::before` adds
  one.
- **Adds nothing:** the universal selector `*` and the combinators `>`, `+`,
  `~` and the space.

An inline `style` attribute sits above all three columns, and `!important` sits
above that.

## How it works

Work through one selector slowly:

::code-trace{caption="Scoring #results tbody tr.topper td:first-child"}
```css [score.css]
#results tbody tr.topper td:first-child { color: green; }
```

  :::code-trace-step{lines="1" caption="#results is an id. A = 1."}
  :::
  :::code-trace-step{lines="1" caption=".topper is a class and :first-child is a pseudo-class. B = 2."}
  :::
  :::code-trace-step{lines="1" caption="tbody, tr and td are type selectors. C = 3. The score is (1, 2, 3)."}
  :::
::

Now a real puzzle. What colour is the note?

```html [panel.html]
<div id="panel" class="card featured">
  <p class="note">Fee due on 30 June.</p>
</div>
```

```css [panel.css]
p                     { color: black;  }
.note                 { color: blue;   }
.card p               { color: green;  }
.card .note           { color: orange; }
.featured.card .note  { color: purple; }
#panel p              { color: red;    }
```

```text [Output]
p                     → 0, 0, 1
.note                 → 0, 1, 0
.card p               → 0, 1, 1
.card .note           → 0, 2, 0
.featured.card .note  → 0, 3, 0
#panel p              → 1, 0, 1   ← wins: the note is red
```

The three-class selector loses to `#panel p`, because comparison stops at the
first column that differs, and the id column is first. Move `#panel p` to the
top of the file and it still wins. Order only matters on a tie.

::runner{lang="css"}
```css
#panel p              { color: red; }
p                     { color: black; }
.note                 { color: blue; }
.card .note           { color: orange; }
.featured.card .note  { color: purple; }

/* --- html --- */
<div id="panel" class="card featured">
  <p class="note">Fee due on 30 June.</p>
</div>
```
::

## Real use case

Real codebases keep specificity **flat and low**: almost every selector is one
class. Naming conventions such as BEM (Block, Element, Modifier) exist for this
reason:

```css [student-card.css]
.student-card           { border: 1px solid #ddd; }  /* 0,1,0 */
.student-card__name     { font-weight: 600; }        /* 0,1,0 */
.student-card--topper   { border-color: gold; }      /* 0,1,0 */
```

Every rule scores (0, 1, 0), so no rule wins by being clever. The one written
later wins, which is predictable. Compare that with a stylesheet where somebody
once wrote `#dashboard .card p`. To restyle that paragraph anywhere on the
dashboard you now need an id as well, and the next person reaches for
`!important`. That is why most teams have a lint rule that forbids ids in CSS.

## What confuses people here

**Scores are not added up as one number.** Eleven classes are not "more" than one
id. (0, 11, 0) loses to (1, 0, 0), because the first column decides.

**Specificity only applies when two rules target the same element.** Inherited
values have no specificity at all. A `p` rule of (0, 0, 1) beats a colour
inherited from `#panel` with (1, 0, 0), because the paragraph was never the
target of `#panel`.

**`:not()`, `:is()` and `:has()` count their argument**, not themselves.
`:not(#x)` adds one id. `:where()` is the exception and always scores zero,
which is why libraries use it for default styles you can override easily.

## Interview questions

::accordion
  :::accordion-item{label="How is specificity calculated?" icon="i-lucide-message-circle"}
  As three counts: ids; classes, attributes and pseudo-classes; type selectors
  and pseudo-elements. Compare them left to right. Inline styles beat all three,
  and `!important` beats inline. With equal scores, the later rule wins.
  :::
  :::accordion-item{label="Which wins: .a.b.c p or #x p?" icon="i-lucide-message-circle"}
  `#x p`, which scores (1, 0, 1) against (0, 3, 1). The id column is compared
  first and 1 beats 0, however many classes the other selector has.
  :::
  :::accordion-item{label="Why do teams avoid ids in CSS?" icon="i-lucide-message-circle"}
  An id rule can only be overridden by another rule with at least as many ids,
  or by `!important`. One id selector makes every future change to those
  elements harder, and the escalation ends in `!important` everywhere.
  :::
  :::accordion-item{label="What is the specificity of *, and of li > a?" icon="i-lucide-message-circle"}
  `*` is (0, 0, 0). `li > a` is (0, 0, 2): two type selectors, and the child
  combinator adds nothing.
  :::
  :::accordion-item{label="Two rules, same specificity, one in an external file and one in a style tag. Which wins?" icon="i-lucide-message-circle"}
  Whichever appears later in the document. If the `<link>` comes after the
  `<style>`, the external file wins. There is no built-in ranking between them.
  :::
::
