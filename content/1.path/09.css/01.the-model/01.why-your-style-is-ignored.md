The HTML track ended with a document that is structured, accessible and plain.
Every page of it looks like the browser's defaults, because nothing has told the
browser otherwise. CSS (Cascading Style Sheets) is the language that does, and
the first thing to learn about it is why it so often seems to refuse.

## Why this matters in a job

Because "why is my style not applying" is the question every beginner asks, and
it almost always has one of a handful of answers. Reaching for `!important`
instead of learning them is how a stylesheet becomes something nobody on the
team dares to edit.

It is also a real interview question, usually phrased as "what are the ways to
add CSS to a page, and which one wins?" The answer has three parts, and most
freshers give one.

## Three ways to attach style, and the cascade that decides

Think of a college notice board. The principal's circular, the department's
notice and a note a lecturer pinned for one class can all say something about
the same exam. Somebody has to decide which one you follow. In CSS that
somebody is the **cascade**: the set of rules the browser uses to choose between
two declarations that set the same property on the same element.

Style reaches an element in three ways:

::feature-list{columns="3"}
  :::feature{icon="i-lucide-file-code" title="External"}
  A separate `.css` file, attached with `<link rel="stylesheet">` in the
  `<head>`. One file styles every page, and the browser caches it. This is what
  real projects use.
  :::
  :::feature{icon="i-lucide-code" title="Internal"}
  A `<style>` block inside the page's `<head>`. Fine for one page or a demo.
  Every page carries its own copy.
  :::
  :::feature{icon="i-lucide-pen-line" title="Inline"}
  A `style="..."` attribute on one element. Beats every normal rule in any
  stylesheet, which is exactly why it causes trouble.
  :::
::

When two declarations conflict, the cascade compares them in this order and
stops at the first difference:

::flow{numbered direction="vertical" caption="The cascade, in the order the browser applies it."}
  :::flow-step{label="Importance" icon="i-lucide-alert-circle"}
  A declaration marked `!important` beats a normal one.
  :::
  :::flow-step{label="Inline or not" icon="i-lucide-pen-line"}
  A `style` attribute beats any selector in a stylesheet.
  :::
  :::flow-step{label="Specificity" icon="i-lucide-target" highlight}
  The more specific selector wins: an id beats a class, a class beats a tag
  name. This gets its own lesson.
  :::
  :::flow-step{label="Source order" icon="i-lucide-list-ordered"}
  If everything else is equal, the rule that appears **later** wins.
  :::
::

Internal and external stylesheets are not ranked against each other. Whichever
comes later in the document wins a tie, which is why the order of your `<link>`
and `<style>` tags matters.

## How it works

Here is a department notice page with all three kinds of style fighting over one
heading.

```html [notice.html]
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>CSE department notices</title>
  <link rel="stylesheet" href="college.css">
  <style>
    h1 { color: navy; }
  </style>
</head>
<body>
  <h1 style="color: green;">Semester exam timetable</h1>
  <p class="notice">Exams begin on 12 November.</p>
</body>
</html>
```

```css [college.css]
h1 { color: maroon; font-family: Georgia, serif; }
.notice { color: #444; }
body { color: #222; border: 1px solid #ccc; }
```

```text [Output]
The heading is green, in Georgia.
  colour: the inline style="color: green" beats both stylesheets
  font:   only college.css sets font-family, so there is no conflict
The paragraph is #444 grey.
  .notice sets it directly, so the body's #222 is not used
Only the <body> has a border. The heading and paragraph do not.
```

Delete the inline `style` and the heading turns navy, because the `<style>` block
comes after the `<link>` and ties are broken by source order. Swap the two tags
and it turns maroon.

Try it: change the order of the rules below and press Run.

::runner{lang="css"}
```css
h1 { color: maroon; }
h1 { color: navy; }
.notice { color: #444; }

/* --- html --- */
<h1>Semester exam timetable</h1>
<p class="notice">Exams begin on 12 November.</p>
```
::

### Inheritance: why the paragraph is not bordered

Some properties pass from a parent to its children, and most do not.

- **Inherits:** `color`, `font-family`, `font-size`, `line-height`,
  `text-align`, `visibility`.
- **Does not inherit:** everything about the box: `margin`, `padding`,
  `border`, `background`, `width`, `height`, `display`.

The rule of thumb is that text properties inherit and box properties do not.
That is why the body's `color` reached the paragraph and its `border` did not.
Form controls inherit almost nothing, which is why a `<button>` keeps the
browser's font until you write `font: inherit`.

### `link` against `@import`

A stylesheet can also pull in another with `@import url("forms.css");` at the
top. It works, and it is slower: the browser cannot discover the imported file
until it has downloaded and read the first one, so the two downloads happen one
after the other instead of side by side. Use several `<link>` tags instead.

## Real use case

Every real site loads one or two external stylesheets and almost never uses
inline styles. The typical head of a college admissions page looks like this:

```html [head.html]
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <link rel="stylesheet" href="/css/base.css">        <!-- reset, fonts, colours -->
  <link rel="stylesheet" href="/css/admissions.css">  <!-- this section only -->
</head>
```

The order is deliberate: the general file first, the specific one second, so
that a tie goes to the more specific file. Inline styles appear in real code
mostly when JavaScript sets them, such as a progress bar's width:
`bar.style.width = attendancePct + "%"`.

When a style is not applying at work, you check these four things, in order:

::flow{numbered direction="vertical" caption="Two minutes, in this order. Almost every CSS problem is in the first three."}
  :::flow-step{label="Is the rule reaching the element at all?" icon="i-lucide-crosshair" highlight}
  Open developer tools (right-click, Inspect), select the element and read the
  Styles panel. If your rule is not listed, the selector is wrong or the file is
  not loading. Check the Network tab for a 404 on the `.css` file.
  :::
  :::flow-step{label="Is it struck through?" icon="i-lucide-strikethrough"}
  Then something with higher priority won, and the panel shows you which.
  :::
  :::flow-step{label="Is the box the size you expect?" icon="i-lucide-box"}
  The box diagram in the tools shows content, padding, border and margin
  separately. The usual culprit is `box-sizing`.
  :::
  :::flow-step{label="Is the property even applicable?" icon="i-lucide-help-circle"}
  `width` on an inline element does nothing. `z-index` needs a `position`.
  These do not error. They are silently ignored.
  :::
::

## What confuses people here

That the last rule always wins. It wins only when everything above it in the
cascade is equal. A rule at the bottom of the file loses to a more specific rule
at the top, every time, and that is the next lesson.

::warning{icon="i-lucide-alert-triangle"}
`!important` is not a fix, it is a deferral. It wins now and can then only be
beaten by another `!important`, so the next person adds one, and within a year
the stylesheet has forty and none of them can be removed safely. If you feel you
need it, the real problem is specificity.
::

## Interview questions

::accordion
  :::accordion-item{label="What are the three ways to add CSS to a page?" icon="i-lucide-message-circle"}
  External (a `.css` file linked with `<link rel="stylesheet">`), internal (a
  `<style>` block in the head) and inline (a `style` attribute). External is
  preferred because one cached file styles every page and keeps content separate
  from presentation.
  :::
  :::accordion-item{label="If inline, internal and external all set the same property, which wins?" icon="i-lucide-message-circle"}
  Inline, unless a stylesheet rule uses `!important`. Between internal and
  external there is no fixed ranking: with equal specificity, whichever appears
  later in the document wins.
  :::
  :::accordion-item{label="What is the cascade?" icon="i-lucide-message-circle"}
  The order the browser uses to resolve conflicting declarations: importance,
  then inline versus stylesheet, then specificity, then source order. Name the
  four in order and you have answered it.
  :::
  :::accordion-item{label="Which properties inherit?" icon="i-lucide-message-circle"}
  Text properties such as `color`, `font-*` and `line-height`. Box properties
  such as `margin`, `padding`, `border` and `background` do not. You can force
  inheritance with the value `inherit`, as in `button { font: inherit; }`.
  :::
  :::accordion-item{label="Why avoid @import?" icon="i-lucide-message-circle"}
  The imported file is discovered only after the first file downloads, so the
  downloads happen in sequence and the page renders later. Several `<link>` tags
  download in parallel.
  :::
  :::accordion-item{label="Why is !important considered bad practice?" icon="i-lucide-message-circle"}
  It can only be overridden by another `!important`, so it escalates. Legitimate
  uses are rare: overriding a third-party library's inline styles, or a utility
  class such as `.hidden` that must always win.
  :::
::
