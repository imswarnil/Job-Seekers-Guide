Seven questions about layout. These six are the bugs, and all of them look
correct on the machine you built them on, which is the entire problem with
front-end work.

::tip
Open the browser's device toolbar and set the width to 360px before starting.
That is a real phone, and it is what four of these six break at.
::

## 1. The style that is ignored

```css
.applicant-card .status { color: red; }
#pipeline .status      { color: grey; }
```

The status is grey and you wanted red. Why?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Specificity. An id beats any number of classes.

  ```text
  .applicant-card .status   → 0, 2, 0
  #pipeline .status         → 1, 1, 0      ← wins on the first column
  ```

  The columns are ids, then classes and attributes, then elements. A higher
  number in an earlier column wins outright, however many are in the later ones.

  The fix is **not** `!important` and it is not adding another id. Lower the
  winning rule:

  ```css
  .pipeline .status { color: grey; }
  .applicant-card .status { color: red; }
  ```

  The habit worth building: avoid ids in stylesheets entirely. They start
  specificity wars that end in `!important`, and `!important` ends in a second
  `!important`.
  :::
::

## 2. The table that scrolls sideways

The applicant table has six columns and 360px of phone.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Horizontal page scroll is the failure. There are two acceptable answers and
  one bad one.

  **Bad:** shrink the font until it fits.

  **Acceptable:** scroll the table only, not the page.

  ```css
  .table-wrap { overflow-x: auto; }
  ```

  **Better:** restructure into cards, because a six-column table is not readable
  at that width however you scroll it.

  ```css
  @media (max-width: 48rem) {
    .table thead { display: none; }
    .table tr    { display: block; margin-bottom: 1rem; }
    .table td    { display: flex; justify-content: space-between; }
    .table td::before { content: attr(data-label); font-weight: 600; }
  }
  ```

  The `data-label` on each cell is the part people forget. In a table the column
  heading labelled the value; on a card, nothing does unless you add it, and
  "120" with no "Seats:" is meaningless.
  :::
::

## 3. The gap that is not there

```css
.section { margin-bottom: 2rem; }
.card    { margin-top: 3rem; }
```

You expected 5rem between them and got 3rem.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Margin collapse.** Adjacent vertical margins combine into the larger, not
  the sum. Horizontal margins never collapse, and this surprises people every
  time.

  Three things stop it: a flex or grid container, padding or a border between
  them, or `overflow` not `visible`.

  The modern answer is to stop fighting it. Use `gap` on the container and put
  no vertical margins on the children at all:

  ```css
  .stack { display: flex; flex-direction: column; gap: 2rem; }
  ```

  `gap` does not collapse, it is stated in one place, and a child moved
  elsewhere does not carry spacing with it. Most margin-collapse folklore
  stopped mattering the day `gap` arrived in flex layouts.
  :::
::

## 4. Flexbox or Grid

You need: the applicant filter bar (a row of controls, one pushed to the right),
and the dashboard (four cards in a 2×2 that becomes 1×4 on a phone).

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Filter bar: Flexbox.** One dimension, content-sized, and one item pushed
  away.

  ```css
  .filters { display: flex; gap: 1rem; align-items: center; }
  .filters .reset { margin-left: auto; }
  ```

  `margin-left: auto` absorbing the free space is the Flexbox idiom worth
  knowing; it beats `justify-content: space-between` because it still works when
  you add a third item.

  **Dashboard: Grid.** Two dimensions, and the responsive behaviour needs no
  media query at all:

  ```css
  .dashboard {
    display: grid;
    gap: 1.5rem;
    grid-template-columns: repeat(auto-fit, minmax(18rem, 1fr));
  }
  ```

  Four across on a wide screen, two on a tablet, one on a phone, and the
  breakpoints come from the content rather than from guessed device widths.

  The rule: **Flexbox for a row or a column of things. Grid when both directions
  matter.**
  :::
::

## 5. The element that will not centre

A 200px box inside a 600px-tall container, and it sits at the top.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  ```css
  .container { display: grid; place-items: center; }
  ```

  Two lines, both axes, any size of child, no magic numbers.

  The Flexbox version is equally fine:

  ```css
  .container {
    display: flex;
    align-items: center;
    justify-content: center;
  }
  ```

  The one that fails and that people still reach for is
  `position: absolute; top: 50%; transform: translateY(-50%)`. It works, it
  removes the element from the flow, and the container then has no height of its
  own, which produces a different bug two screens later.
  :::
::

## 6. The layout that breaks at one width

Everything is fine until exactly 768px, where the cards overlap the sidebar.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Almost always a fixed width meeting a percentage.

  ```css
  .sidebar { width: 260px; }
  .content { width: 70%; }           /* 70% of the parent, not of what is left */
  ```

  At some width `260px + 70%` exceeds 100%. The numbers were chosen at one
  screen size and tested at one screen size.

  ```css
  .layout {
    display: grid;
    grid-template-columns: 260px 1fr;   /* 1fr is "whatever is left" */
    gap: 2rem;
  }
  @media (max-width: 48rem) {
    .layout { grid-template-columns: 1fr; }
  }
  ```

  `1fr` means the remaining space, so the two can never add up to more than
  there is.

  The general lesson: **mixing fixed and percentage widths in one row always
  breaks at some width.** Let the layout system do the arithmetic.
  :::
::

## The habits

::feature-list{columns="3"}
  :::feature{icon="i-lucide-smartphone" title="Build at 360px first"}
  A narrow layout widening is easy. A wide layout narrowing is a rewrite, and
  you find out too late.
  :::
  :::feature{icon="i-lucide-ruler" title="Let content set breakpoints"}
  `auto-fit` with `minmax` beats device-width guesses, and it keeps working on
  devices that did not exist when you wrote it.
  :::
  :::feature{icon="i-lucide-ban" title="No ids, no !important"}
  Both are specificity escalations, and both are a sign the problem is further
  up the stylesheet.
  :::
::
