Two of these are near-certainties and the rest are common. All seven are
answerable from the mechanism rather than from memory.

::accordion
  :::accordion-item{label="1. Explain the event loop" icon="i-lucide-message-circle"}
  The near-certainty. One thread runs your code to completion. Slow operations
  are handed to the browser and their callbacks are **queued**; the queue is
  only drained once the current code has finished.

  Prove it with the output order: `console.log('a')`, `setTimeout(..., 0)`,
  `Promise.resolve().then(...)`, `console.log('d')` prints `a, d, c, b`.
  Synchronous first, then microtasks, then timers, even at zero milliseconds.

  Then the consequence: it is also why one long loop freezes the entire page
  including scrolling, and therefore why `async`/`await` exists at all.
  :::

  :::accordion-item{label="2. `==` versus `===`" icon="i-lucide-message-circle"}
  `==` converts types before comparing; `===` does not. Use `===`.

  Then the example that shows it matters rather than being pedantry: a value
  from a form is always a **string**, so `marks > 70` compares a string, and
  `'8' > '70'` is `true` because it compares character by character. Convert at
  the boundary and check the conversion worked.
  :::

  :::accordion-item{label="3. What is `this`?" icon="i-lucide-message-circle"}
  In a regular function it depends on **how it was called**, not where it was
  written, which is why a callback loses it. An arrow function has no `this` of
  its own and uses the surrounding one.

  The practical rule, which is the answer they want: arrow functions for
  callbacks, regular methods in objects and classes. That covers every ordinary
  case and is why modern code rarely thinks about `this` at all.
  :::

  :::accordion-item{label="4. null or undefined?" icon="i-lucide-message-circle"}
  `undefined` means never set — a missing property, a missing argument.
  `null` means deliberately empty.

  Then the trap worth volunteering: `0` is falsy, so `if (applicant.score)` is
  false for a genuine score of zero. `score != null` is the check that
  distinguishes "scored nothing" from "not marked", which is the same `NULL`
  versus zero distinction as SQL and Java.
  :::

  :::accordion-item{label="5. Why does `fetch` not throw on a 404?" icon="i-lucide-message-circle"}
  Because it only rejects on a **network** failure. A 404 or a 500 is a
  successful fetch of an error response, so `await fetch(...)` resolves and you
  carry on with an error page as your data.

  `if (!response.ok) throw` is therefore not optional, and forgetting it is the
  single most common `fetch` bug.
  :::

  :::accordion-item{label="6. What is event delegation?" icon="i-lucide-message-circle"}
  One listener on a container, working out what was clicked with
  `event.target.closest(...)`, instead of one listener per row.

  Two reasons rather than one: 412 listeners is 412 listeners, and — the one
  people miss — delegation keeps working for rows added to the table later,
  which per-row listeners do not.
  :::

  :::accordion-item{label="7. How do you handle an API call in the browser?" icon="i-lucide-message-circle"}
  The happy path is three lines and nobody is asking about it. The answer is the
  rest: disable the control **before** the request so a double tap cannot fire
  twice, show a pending state within a frame, check `response.ok`, render what
  the server returned rather than what you assumed, and re-enable on failure
  with an error a user can act on.

  Then close with the rule: any check that matters is repeated on the server,
  because everything in the browser is a convenience for honest users.
  :::
::
