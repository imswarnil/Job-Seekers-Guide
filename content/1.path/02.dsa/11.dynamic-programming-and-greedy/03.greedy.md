The shortcut is safe when taking the best choice now can never block a better
answer later. When that holds, a greedy algorithm (one that makes the locally
best choice at each step and never undoes it) is shorter and faster than any
table. When it does not hold, greedy gives an answer that looks right, runs
fast, and is wrong.

## Why this matters in a job

Greedy problems are popular in online assessments because the code is short and
the thinking is not: activity selection, meeting rooms, jump game, gas station,
minimum platforms, assigning cookies. The follow-up question is always the same,
"how do you know greedy is correct here?", and a candidate who can give a
counterexample for the wrong greedy rule stands out immediately.

At work, schedulers are greedy: a job queue that always runs the job with the
nearest deadline, a timetable generator that fills the earliest free slot, a
load balancer that sends a request to the least busy server.

## Best choice now, no regrets

Picture the exam cell with **one hall** and a list of requested exams, each with
a start and end time. The goal: fit the **most** exams into the hall with no
overlaps.

Three greedy rules suggest themselves:

| Rule | Why it sounds right | Does it work? |
| --- | --- | --- |
| Shortest exam first | Short exams leave room | **No.** A short exam straddling two long ones blocks both. |
| Earliest start first | Start the day early | **No.** An exam from 9 to 17 starts first and blocks everything. |
| **Earliest end first** | Frees the hall soonest | **Yes.** Proved below. |

Why earliest end works: whatever the best schedule picks first, swapping it for
the exam that ends earliest never makes things worse, because that exam frees the
hall at least as soon. Repeat the argument for each slot. This swap reasoning
(called an **exchange argument**) is how greedy algorithms are proved correct.

## How it works

```java [ExamHall.java]
import java.util.*;

public class ExamHall {
  record Exam(String subject, int start, int end) { }

  public static void main(String[] args) {
    List<Exam> requests = new ArrayList<>(List.of(
        new Exam("Maths", 9, 11),
        new Exam("Physics", 10, 12),
        new Exam("Chemistry", 11, 13),
        new Exam("DBMS", 12, 14),
        new Exam("Networks", 13, 15),
        new Exam("OS", 9, 17)));

    requests.sort(Comparator.comparingInt(Exam::end));   // earliest end first

    List<Exam> chosen = new ArrayList<>();
    int hallFreeAt = 0;
    for (Exam e : requests) {
      if (e.start() >= hallFreeAt) {                     // does not overlap
        chosen.add(e);
        hallFreeAt = e.end();
      }
    }

    for (Exam e : chosen) {
      System.out.println(e.subject() + " " + e.start() + ":00 to " + e.end() + ":00");
    }
    System.out.println(chosen.size() + " exams in one hall");
  }
}
```

```text [Output]
Maths 9:00 to 11:00
Chemistry 11:00 to 13:00
Networks 13:00 to 15:00
3 exams in one hall
```

::flow{numbered caption="Every greedy algorithm has this shape"}
  :::flow-step{label="Sort by the greedy key" icon="i-lucide-arrow-down-wide-narrow" highlight}
  Here, end time. Choosing the key is the whole problem.
  :::
  :::flow-step{label="Walk once" icon="i-lucide-footprints"}
  Look at each item in that order.
  :::

  :::

### Complexity

**O(n log n)** for the sort, then **O(n)** for the walk. Most greedy solutions
are "sort, then one pass", so most are O(n log n).

## Paying fees in the fewest notes

The fee counter has to return ₹2,888 in change using the fewest notes and coins.
With Indian denominations, take the largest that fits, repeatedly.

```java [FeeCounter.java]
import java.util.*;

public class FeeCounter {
  static Map<Integer, Integer> change(int amount, int[] denominations) {
    Map<Integer, Integer> used = new LinkedHashMap<>();
    for (int d : denominations) {                 // largest first
      if (amount >= d) {
        used.put(d, amount / d);
        amount %= d;
      }
    }
    return used;
  }

  public static void main(String[] args) {
    int[] rupees = {500, 200, 100, 50, 20, 10, 5, 2, 1};
    Map<Integer, Integer> result = change(2888, rupees);
    int pieces = 0;
    for (var entry : result.entrySet()) {
      System.out.println("₹" + entry.getKey() + " x " + entry.getValue());
      pieces += entry.getValue();
    }
    System.out.println("Total pieces: " + pieces);
  }
}
```

```text [Output]
₹500 x 5
₹200 x 1
₹100 x 1
₹50 x 1
₹20 x 1
₹10 x 1
₹5 x 1
₹2 x 1
₹1 x 1
Total pieces: 13
```

That is optimal for rupees, because each denomination is built so that the
larger ones never waste what the smaller ones could do. Now a made-up currency
with coins of 1, 3 and 4.

```java [OddCoins.java]
import java.util.*;

public class OddCoins {
  static int greedy(int amount, int[] coinsLargestFirst) {
    int count = 0;
    for (int c : coinsLargestFirst) {
      count += amount / c;
      amount %= c;
    }
    return count;
  }

  static int fewest(int amount, int[] coins) {        // the DP from last lesson's family
    int[] dp = new int[amount + 1];
    Arrays.fill(dp, Integer.MAX_VALUE);
    dp[0] = 0;
    for (int a = 1; a <= amount; a++)
      for (int c : coins)
        if (c <= a && dp[a - c] != Integer.MAX_VALUE)
          dp[a] = Math.min(dp[a], dp[a - c] + 1);
    return dp[amount];
  }

  public static void main(String[] args) {
    int[] coins = {4, 3, 1};
    System.out.println("Greedy for 6: " + greedy(6, coins) + " coins (4 + 1 + 1)");
    System.out.println("Best for 6:   " + fewest(6, coins) + " coins (3 + 3)");
  }
}
```

```text [Output]
Greedy for 6: 3 coins (4 + 1 + 1)
Best for 6:   2 coins (3 + 3)
```

::compare{caption="The same greedy code, two coin systems"}
  :::compare-side{label="Coins 4, 3, 1" verdict="wrong"}
  Taking 4 first leaves 2, which costs two 1s. Three coins. The greedy choice
  blocked the better answer, so this needs dynamic programming.
  :::
  :::compare-side{label="Rupees 500 down to 1" verdict="right"}
  Every larger denomination is worth at least as much as the best combination of
  smaller ones it replaces, so taking the largest never hurts.
  :::
::

## Fractional knapsack

In last lesson's knapsack, items were all or nothing and greedy failed. If items
can be **split**, greedy by value per unit is correct. A student has 6 hours
before the exam and several topics, each with marks available and hours needed.
She can study part of a topic for part of its marks.

```java [RevisionPlan.java]
import java.util.*;

public class RevisionPlan {
  record Topic(String name, double hours, double marks) {
    double marksPerHour() { return marks / hours; }
  }

  public static void main(String[] args) {
    List<Topic> topics = new ArrayList<>(List.of(
        new Topic("Joins", 2, 20),
        new Topic("Normalisation", 3, 18),
        new Topic("Indexing", 4, 16)));
    topics.sort(Comparator.comparingDouble(Topic::marksPerHour).reversed());

    double hoursLeft = 6, marks = 0;
    for (Topic t : topics) {
      double spend = Math.min(hoursLeft, t.hours());
      marks += spend * t.marksPerHour();
      hoursLeft -= spend;
      System.out.printf("%-14s %.1f of %.1f hours%n", t.name(), spend, t.hours());
    }
    System.out.printf("Expected marks: %.1f%n", marks);
  }
}
```

```text [Output]
Joins          2.0 of 2.0 hours
Normalisation  3.0 of 3.0 hours
Indexing       1.0 of 4.0 hours
Expected marks: 42.0
```

## Real use case

::real-life{title="The invigilator roster" source="An exam cell during semester exams"}
An exam cell has to cover every exam session with the fewest invigilators. Sort
sessions by start time; for each one, give it to any invigilator who is already
free (a `PriorityQueue` of end times tells you the earliest-free one in O(log n)),
otherwise bring in a new one. The size the queue reaches is the answer. That is
the "minimum meeting rooms" interview problem, and it is greedy plus a heap.
::

## What confuses people here

::warning{icon="i-lucide-alert-triangle"}
**Greedy always looks right on the example you were given.** The coin example
works for 7 (4 + 3) and fails for 6. Before committing to a greedy rule, spend
two minutes hunting for a counterexample with small numbers. If you cannot find
one and can explain the exchange argument, go ahead. If you find one, the problem
wants DP.
::

The other confusion is between greedy and DP themselves. Both build an answer
from choices. Greedy commits to one choice per step; DP keeps the best answer for
every possible state. If the current choice can change which future choices are
possible in a way that matters, greedy is not safe.

## Interview questions

::accordion
  :::accordion-item{label="How do you prove a greedy algorithm is correct?" icon="i-lucide-message-circle"}
  An exchange argument: take any optimal answer, swap its first choice for the
  greedy choice, and show it is no worse. Repeat. In interviews an informal
  version is enough, plus a counterexample for the rules that fail.
  :::
  :::accordion-item{label="Why sort by end time and not duration?" icon="i-lucide-message-circle"}
  Counterexample: exams 9–12, 11–13 and 12–15. The shortest (11–13) overlaps both
  others, so shortest-first fits one exam. Earliest-end fits 9–12 and 12–15, two.
  :::
  :::accordion-item{label="Minimum number of halls so no exams clash" icon="i-lucide-message-circle"}
  Sort by start, keep a min-heap of end times of halls in use:

  ```java
  static int halls(int[][] exams) {                 // {start, end}
    Arrays.sort(exams, Comparator.comparingInt(e -> e[0]));
    PriorityQueue<Integer> ends = new PriorityQueue<>();
    for (int[] e : exams) {
      if (!ends.isEmpty() && ends.peek() <= e[0]) ends.poll();  // reuse a hall
      ends.offer(e[1]);
    }
    return ends.size();
  }
  // halls(new int[][]{{9,11},{10,12},{11,13}}) → 2
  ```
  :::
  :::accordion-item{label="Greedy or DP for coin change?" icon="i-lucide-message-circle"}
  Greedy only for canonical coin systems like the rupee. For arbitrary coins,
  DP: `dp[a] = min(dp[a - c] + 1)` over every coin c, O(amount × coins).
  :::
::
