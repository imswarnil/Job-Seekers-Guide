The frightening name is **dynamic programming**, and the idea behind it is
smaller than the name: if you have already worked something out, write the answer
down and never work it out again. That is all it is.

I avoided this topic for a long time. When I was preparing for the switch from
Accenture, I skipped every problem tagged "DP" because the word sounded like a
subject for toppers. When I finally sat down with it, the first lesson took one
evening, and it is this one.

## Why this matters in a job

Product company interviews ask at least one DP question in almost every loop,
usually in the second or third round, because it separates people who memorised
solutions from people who can build one. Service company tests ask easier ones
(climbing stairs, the minimum cost to reach a step) in the coding section.

At work, the same idea hides behind every cache. A report that works out the
total fees paid per department once and keeps the answer, instead of adding up
40,000 rows each time somebody opens the page, is the idea of this lesson.

## Remembering answers

Think of a class teacher asked, "how many students in your section passed?" The
first time, she counts the register. The fifth time somebody asks, she does not
count again; she wrote the number on the cover of the register. Dynamic
programming is writing the number on the cover.

It only helps when the **same question gets asked more than once**. Those
repeated questions are called **overlapping subproblems** (small versions of the
problem that come up again and again). The other condition is **optimal
substructure**: the best answer to the big problem can be built from the best
answers to smaller ones.

The classic demonstration is the Fibonacci sequence: 0, 1, 1, 2, 3, 5, 8, 13…
where each number is the sum of the two before it.

## How it works

Three versions of the same method. First the naive one, with a counter so you
can see the waste.

```java [NaiveFib.java]
public class NaiveFib {
  static long calls = 0;

  static long fib(int n) {
    calls++;
    if (n <= 1) return n;              // base cases: fib(0) = 0, fib(1) = 1
    return fib(n - 1) + fib(n - 2);
  }

  public static void main(String[] args) {
    for (int n : new int[]{10, 20, 30, 40}) {
      calls = 0;
      long answer = fib(n);
      System.out.println("fib(" + n + ") = " + answer + " after " + calls + " calls");
    }
  }
}
```

```text [Output]
fib(10) = 55 after 177 calls
fib(20) = 6765 after 21891 calls
fib(30) = 832040 after 2692537 calls
fib(40) = 102334155 after 331160281 calls
```

Three hundred and thirty million calls to produce a nine-digit number. Each extra
step multiplies the calls by about 1.6, which is exponential growth.

### Top-down: memoisation

**Memoisation** means keeping a memo (a note) of every answer the recursion has
already found. The recursion stays the same shape; it checks the note first.

```java [MemoFib.java]
public class MemoFib {
  static long calls = 0;

  static long fib(int n, long[] memo) {
    calls++;
    if (n <= 1) return n;
    if (memo[n] != 0) return memo[n];            // already worked out
    memo[n] = fib(n - 1, memo) + fib(n - 2, memo);
    return memo[n];
  }

  public static void main(String[] args) {
    int n = 40;
    long answer = fib(n, new long[n + 1]);
    System.out.println("fib(" + n + ") = " + answer + " after " + calls + " calls");
    calls = 0;
    System.out.println("fib(90) = " + fib(90, new long[91]) + " after " + calls + " calls");
  }
}
```

```text [Output]
fib(40) = 102334155 after 79 calls
fib(90) = 2880067194370816120 after 179 calls
```

From 331 million calls to 79. Each value from 2 to 40 is worked out once, and
every other call is a lookup in the array.

### Bottom-up: tabulation

**Tabulation** throws the recursion away and fills a table from the smallest
case upwards. No call stack, so no `StackOverflowError` at large n.

```java [TabFib.java]
public class TabFib {
  static long fib(int n) {
    if (n <= 1) return n;
    long[] table = new long[n + 1];
    table[0] = 0;
    table[1] = 1;
    for (int i = 2; i <= n; i++) {
      table[i] = table[i - 1] + table[i - 2];
    }
    return table[n];
  }

  static long fibTwoVariables(int n) {
    if (n <= 1) return n;
    long before = 0, last = 1;
    for (int i = 2; i <= n; i++) {
      long next = before + last;
      before = last;
      last = next;
    }
    return last;
  }

  public static void main(String[] args) {
    System.out.println("table:     fib(50) = " + fib(50));
    System.out.println("variables: fib(50) = " + fibTwoVariables(50));
  }
}
```

```text [Output]
table:     fib(50) = 12586269025
variables: fib(50) = 12586269025
```

### Complexity

| Version | Time | Extra space |
| --- | --- | --- |
| Naive recursion | O(2ⁿ), roughly 1.6ⁿ | O(n) call stack |
| Memoisation (top-down) | **O(n)** | O(n) memo + O(n) stack |
| Tabulation (bottom-up) | **O(n)** | O(n) table |
| Two variables | **O(n)** | **O(1)** |

## Climbing stairs

The DP problem you are most likely to be given first. A student climbs to the
exam hall on the fourth floor, `n` steps, taking one or two steps at a time. In
how many different ways can she reach the top?

Think about the **last move**. To stand on step `n` she came either from step
`n - 1` (one step) or from `n - 2` (two steps). So
`ways(n) = ways(n - 1) + ways(n - 2)`. It is Fibonacci wearing a uniform.

```java [ClimbingStairs.java]
public class ClimbingStairs {
  static int ways(int n) {
    if (n <= 2) return n;             // 1 step: 1 way. 2 steps: 2 ways.
    int[] dp = new int[n + 1];
    dp[1] = 1;
    dp[2] = 2;
    for (int step = 3; step <= n; step++) {
      dp[step] = dp[step - 1] + dp[step - 2];
    }
    return dp[n];
  }

  public static void main(String[] args) {
    for (int n = 1; n <= 6; n++) {
      System.out.println(n + " steps: " + ways(n) + " ways");
    }
    System.out.println("45 steps: " + ways(45) + " ways");
  }
}
```

```text [Output]
1 steps: 1 ways
2 steps: 2 ways
3 steps: 3 ways
4 steps: 5 ways
5 steps: 8 ways
6 steps: 13 ways
45 steps: 1836311903 ways
```

## Real use case

::real-life{title="A fee instalment calculator" source="A college accounts office"}
A college lets students pay a semester fee of ₹60,000 in instalments of ₹10,000
or ₹20,000, and the accounts team wanted to show "how many payment plans are
possible". Written recursively it froze the page for large fees, because the
same remaining balance was being worked out thousands of times. Storing the count
for each remaining balance in a `HashMap<Integer, Long>` (memoisation) made it
instant. Same recurrence as the stairs: the last instalment was either ₹10,000
or ₹20,000.
::

## What confuses people here

::warning{icon="i-lucide-alert-triangle"}
**Using `0` to mean "not worked out yet".** It works for Fibonacci because only
`fib(0)` is zero, and that is a base case. In a problem where zero is a real
answer (the number of ways to pay an impossible amount, say), the memo never
remembers the zeros and you are back to exponential time. Fill the memo with
`-1` using `Arrays.fill(memo, -1)`, or use a `Long[]` and check for `null`.
::

The other confusion is thinking memoisation and tabulation are different
techniques. They are the same answers in a different order: top-down starts at
the question and recurses into what it needs; bottom-up starts at the base cases
and builds up. Interviewers accept either. Tabulation is usually safer in Java
because deep recursion can overflow the stack.

And overflow of a different kind: `int` holds up to about 2.1 billion. `fib(47)`
is past it, and Java does not warn you; the number wraps round to a negative.
Use `long` for counts that grow like this, and say so out loud.

## Interview questions

::accordion
  :::accordion-item{label="What is dynamic programming?" icon="i-lucide-message-circle"}
  Solving a problem by combining answers to smaller versions of it, and storing
  each smaller answer so it is computed once. It applies when there are
  overlapping subproblems and optimal substructure. Fibonacci goes from about
  1.6ⁿ calls to n.
  :::
  :::accordion-item{label="Memoisation or tabulation, which is better?" icon="i-lucide-message-circle"}
  Same time complexity. Memoisation is easier to write from a recursive idea and
  only computes the states it needs. Tabulation has no recursion, so no stack
  overflow, and often lets you drop the table to a few variables, as in
  `fibTwoVariables` above, which is O(1) space.
  :::
  :::accordion-item{label="How do you recognise a DP problem?" icon="i-lucide-message-circle"}
  The question asks for a count of ways, a minimum or maximum, or "is it
  possible", and a brute force would try choices whose results repeat. Draw the
  recursion tree for a small input: if boxes repeat, it is DP.
  :::
  :::accordion-item{label="Climbing stairs with 1, 2 or 3 steps allowed?" icon="i-lucide-message-circle"}
  One more term in the transition, three base cases:

  ```java
  static long ways(int n) {
    long[] dp = new long[Math.max(4, n + 1)];
    dp[0] = 1; dp[1] = 1; dp[2] = 2;
    for (int i = 3; i <= n; i++) dp[i] = dp[i - 1] + dp[i - 2] + dp[i - 3];
    return dp[n];
  }
  // ways(4) = 7
  ```
  :::
  :::accordion-item{label="What is the space complexity of memoised Fibonacci?" icon="i-lucide-message-circle"}
  O(n) for the memo array plus O(n) for the recursion depth, so O(n) overall.
  Candidates forget the call stack; mentioning it is the point of the question.
  :::
::
