A method that calls itself is called **recursive**. It works when each call
hands a smaller version of the same problem to the next, and one of those
versions is small enough to answer directly. Everything in this lesson is
those two parts, and the call stack that holds them together.

## Why this matters in a job

Because trees, graphs, backtracking, merge sort, quick sort and most of dynamic
programming are written recursively, so this chapter is the entry ticket to
half the track. Because "write factorial recursively" and "what happens if
there is no base case?" are standard questions in fresher interviews. And at
work, anything nested (folders, menus, a department with sub-departments, JSON
inside JSON) is walked with recursion.

## Passing the question down the row

Picture a lecture hall with students in one long row. The student at the far
end is asked, "how many people are sitting to your left, including you?". She
does not count. She asks the person on her left the same question and adds one
to whatever he answers. He does the same. Eventually the question reaches the
student at the wall, who has nobody to ask, and answers "1". The answers then
travel back up the row, each person adding one.

That is recursion in two rules:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-square" title="Base case"}
  The smallest version of the problem, answered directly with no further call.
  The student at the wall. Without it, the calls never stop.
  :::
  :::feature{icon="i-lucide-repeat" title="Recursive case"}
  Solve a smaller version by calling yourself, then do a little work with the
  answer. "Ask the next person, add one."
  :::
::

## How it works

Factorial: `5! = 5 × 4 × 3 × 2 × 1`. Written recursively, `n! = n × (n − 1)!`
and `0! = 1`.

```java [Factorial.java]
public class Factorial {
  static long factorial(int n) {
    if (n <= 1) return 1;              // base case
    return n * factorial(n - 1);       // recursive case: a smaller problem
  }

  public static void main(String[] args) {
    System.out.println("5! = " + factorial(5));
    System.out.println("10! = " + factorial(10));
    System.out.println("20! = " + factorial(20));
  }
}
```

```text [Output]
5! = 120
10! = 3628800
20! = 2432902008176640000
```

Each call waits for the one below it to return. Those waiting calls live on the
**call stack**: a pile of frames, one per unfinished call, holding that call's
parameters and local variables. The newest call is on top.

### Watching the calls

Printing on the way down and on the way back up shows the order. This program
prints the numbers 1 to n without a loop, and then n down to 1.

```java [UpAndDown.java]
public class UpAndDown {
  static void show(int n) {
    if (n == 0) return;                           // base case
    System.out.println("going down: " + n);
    show(n - 1);
    System.out.println("coming back: " + n);      // runs after the call returns
  }

  public static void main(String[] args) {
    show(3);
  }
}
```

```text [Output]
going down: 3
going down: 2
going down: 1
coming back: 1
coming back: 2
coming back: 3
```

Everything after the recursive call runs in reverse order. That one observation
explains how recursion reverses things, and later how tree traversals work.

### Three more classics

```java [RecursionClassics.java]
public class RecursionClassics {
  // Sum of digits of a roll number: 2026 -> 2 + 0 + 2 + 6
  static int digitSum(int n) {
    if (n < 10) return n;
    return n % 10 + digitSum(n / 10);
  }

  // Is a string a palindrome? Compare the ends, recurse on the middle.
  static boolean isPalindrome(String s, int left, int right) {
    if (left >= right) return true;
    if (s.charAt(left) != s.charAt(right)) return false;
    return isPalindrome(s, left + 1, right - 1);
  }

  // x to the power n in O(log n): halve n each call
  static long power(long x, int n) {
    if (n == 0) return 1;
    long half = power(x, n / 2);
    return (n % 2 == 0) ? half * half : half * half * x;
  }

  public static void main(String[] args) {
    System.out.println(digitSum(2026));
    System.out.println(isPalindrome("malayalam", 0, 8));
    System.out.println(power(2, 10));
    System.out.println(power(3, 13));
  }
}
```

```text [Output]
10
true
1024
1594323
```

`power` is the one to understand. Multiplying x by itself n times is O(n).
Computing `x^(n/2)` once and squaring it halves n on every call, so there are
about log₂ n calls. `power(2, 30)` makes 6 calls instead of 30 multiplications,
and a power of one million makes about 21.

### Complexity

A useful rule: **time = number of calls × work per call**, and **space = the
deepest the stack gets**.

| Method | Calls | Time | Stack space |
| --- | --- | --- | --- |
| `factorial(n)` | n | O(n) | O(n) |
| `digitSum(n)` | number of digits, about log₁₀ n | O(log n) | O(log n) |
| `isPalindrome` on length n | n / 2 | O(n) | O(n) |
| `power(x, n)` | about log₂ n | O(log n) | O(log n) |

## When the base case is missing

```java [NoBase.java]
public class NoBase {
  static int depth = 0;

  static void countDown(int n) {
    depth++;
    countDown(n - 1);                 // no base case: never stops
  }

  public static void main(String[] args) {
    try {
      countDown(5);
    } catch (StackOverflowError e) {
      System.out.println("StackOverflowError after thousands of calls");
    }
  }
}
```

```text [Output]
StackOverflowError after thousands of calls
```

Every call adds a frame and none of them ever returns, so the stack fills its
fixed memory (often around 512 KB to 1 MB per thread by default) and the JVM
throws `StackOverflowError`. The exact depth varies by machine and by how big
each frame is, which is why this program does not print it. Recursion on an
input of 10⁵ or 10⁶ elements can overflow even with a correct base case; in
that situation, a loop is the safer answer.

::compare{caption="The same sum, both correct. Pick by the shape of the problem."}
  :::compare-side{label="Recursion on a flat list" verdict="wrong"}
  Summing 1,000,000 marks recursively makes a million stack frames and may
  crash with `StackOverflowError`. A flat list has no nesting for recursion to
  follow.
  :::
  :::compare-side{label="Recursion on nested data" verdict="right"}
  Walking a department that contains sub-departments that contain courses:
  depth is small (five or six levels) and the code mirrors the data. This is
  where recursion earns its place.
  :::
::

## Real use case

::real-life{title="Total students across a faculty" source="A university structure"}
A university is a tree of units: the university has faculties, faculties have
departments, some departments have centres. Each unit knows its own students
and its children. "Total students in the Faculty of Engineering" is one
recursive method: my students plus the total of each child. It works whether
the tree is two levels deep or six, and nobody has to change it when a new
centre is added. The same shape walks folders on disk and nested comments on a
forum.
::

## What confuses people here

- **Trusting the recursion.** You do not trace every call in your head. Assume
  `factorial(n − 1)` returns the right answer, and check that your line turns
  it into the right answer for n. That leap is the skill.
- **A base case that is never reached.** `factorial(-3)` with `if (n == 0)`
  never hits zero. Use `n <= 1`, or reject negatives.
- **Overflow in the result.** `factorial(21)` overflows `long` silently and
  returns a negative number. Use `BigInteger` if you need bigger.
- **Thinking recursion is faster.** It is usually a little slower than the loop,
  because each call costs a frame. It is chosen for clarity on nested problems.

## Interview questions

::accordion
  :::accordion-item{label="What are the two parts of every recursive function?" icon="i-lucide-message-circle"}
  A base case, answered directly with no further call, and a recursive case
  that calls the function on a strictly smaller input and combines the result.
  Without a reachable base case, the calls never stop.
  :::

  :::accordion-item{label="What happens if there is no base case?" icon="i-lucide-message-circle"}
  Each call pushes a new frame on the call stack and none returns, so the stack
  runs out of memory and the JVM throws `StackOverflowError`. It is an `Error`,
  not an `Exception`, because the program cannot sensibly recover.
  :::

  :::accordion-item{label="What is the space complexity of a recursive factorial?" icon="i-lucide-message-circle"}
  O(n), because n frames are on the stack at the deepest point. The iterative
  version with one `long result` variable is O(1) space.
  :::

  :::accordion-item{label="Compute x to the power n in O(log n)." icon="i-lucide-message-circle"}
  Compute `half = power(x, n / 2)` once. If n is even return `half * half`,
  otherwise `half * half * x`. n halves on every call, so there are about
  log₂ n calls. Calling `power(x, n / 2)` twice instead of storing it makes it
  O(n) again, which is the trap.
  :::

  :::accordion-item{label="Recursion or iteration?" icon="i-lucide-message-circle"}
  Iteration for flat, possibly very long data, because it uses O(1) stack and
  cannot overflow. Recursion for nested or branching problems (trees, graphs,
  backtracking, divide and conquer), where the code mirrors the structure and
  the depth stays small.
  :::
::
