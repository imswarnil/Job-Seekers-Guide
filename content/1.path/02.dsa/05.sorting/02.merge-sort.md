Splitting the pile in half changes 800 million comparisons into about 640,000.
Merge sort does it by never sorting a big pile at all: it cuts the pile down to
single sheets, which are sorted by definition, and then only ever merges two
piles that are already in order.

## Why this matters in a job

Because merge sort is the cleanest example of **divide and conquer**, the idea
behind half the recursive problems you will meet. Because "merge two sorted
arrays" is asked on its own, as a warm-up, constantly. Because it is the sort
whose complexity you can derive on a whiteboard, and interviewers ask you to.
And because it is stable and predictable, which is why Java's sort for objects
is built on it.

## Two sorted piles are easy to combine

Two invigilators each hand you a pile of answer sheets already sorted by roll
number. To make one sorted pile, you do not need to think: look at the top sheet
of each pile, take the smaller, repeat. Every sheet is looked at once.

That is the whole trick. Merging two sorted piles is **O(n)**. So if you can get
two sorted halves, you are one cheap step from a sorted whole. And how do you
sort each half? The same way, by splitting it. Keep splitting until each pile has
one sheet.

## How it works

### Merging two sorted arrays

Write this on its own first. It is a complete interview question by itself.

```java [MergeTwo.java]
import java.util.Arrays;

public class MergeTwo {

  static int[] merge(int[] a, int[] b) {
    int[] result = new int[a.length + b.length];
    int i = 0, j = 0, k = 0;
    while (i < a.length && j < b.length) {
      if (a[i] <= b[j]) result[k++] = a[i++];   // <= keeps it stable
      else              result[k++] = b[j++];
    }
    while (i < a.length) result[k++] = a[i++];  // leftovers from a
    while (j < b.length) result[k++] = b[j++];  // leftovers from b
    return result;
  }

  public static void main(String[] args) {
    int[] hallA = {1003, 1019, 1042, 1068};
    int[] hallB = {1007, 1031, 1055};
    System.out.println(Arrays.toString(merge(hallA, hallB)));
  }
}
```

```text [Output]
[1003, 1007, 1019, 1031, 1042, 1055, 1068]
```

The two leftover loops are the part people forget. When one pile runs out, the
rest of the other pile is already sorted and goes on the end as it is.

### The full sort

```java [MergeSort.java]
import java.util.Arrays;

public class MergeSort {

  static void sort(int[] a, int low, int high) {      // sorts a[low..high]
    if (low >= high) return;                          // 0 or 1 element: sorted
    int mid = low + (high - low) / 2;
    sort(a, low, mid);
    sort(a, mid + 1, high);
    merge(a, low, mid, high);
  }

  static void merge(int[] a, int low, int mid, int high) {
    int[] temp = new int[high - low + 1];
    int i = low, j = mid + 1, k = 0;
    while (i <= mid && j <= high) {
      if (a[i] <= a[j]) temp[k++] = a[i++];
      else              temp[k++] = a[j++];
    }
    while (i <= mid)  temp[k++] = a[i++];
    while (j <= high) temp[k++] = a[j++];
    for (k = 0; k < temp.length; k++) {
      a[low + k] = temp[k];                           // copy back
    }
  }

  public static void main(String[] args) {
    int[] marks = {64, 35, 88, 12, 70, 41, 97, 23};
    sort(marks, 0, marks.length - 1);
    System.out.println(Arrays.toString(marks));
  }
}
```

```text [Output]
[12, 23, 35, 41, 64, 70, 88, 97]
```

### Complexity

| | Value | Why |
| --- | --- | --- |
| Time, every case | **O(n log n)** | log n levels of halving, n work of merging per level |
| Extra space | **O(n)** | the temporary array in `merge` |
| Stack space | O(log n) | the depth of the recursion |
| Stable | **Yes** | `<=` takes from the left half on ties |

"Every case" is the point. Merge sort does not care whether the input is
sorted, reversed or random: the splitting is always the same. For 40,000 marks,
log₂ 40,000 is about 15.3, so roughly 40,000 × 16 = 640,000 steps against
insertion sort's 800 million.

## Real use case

**Sorting data too big for memory.** A state board has the marks of 30 lakh
students in a file far larger than the server's RAM. It reads a chunk that fits,
sorts it, writes it to disk as a sorted run, and repeats. Then it merges the runs,
reading only the top few lines of each file at a time. This is called **external
merge sort**, and it is how databases sort a result that does not fit in memory
(you will see it in a query plan in the SQL track).

The in-memory version of that final step, merging several sorted lists, looks
like this:

```java [MergeHalls.java]
import java.util.ArrayList;
import java.util.List;

public class MergeHalls {

  static List<Integer> merge(List<Integer> a, List<Integer> b) {
    List<Integer> out = new ArrayList<>();
    int i = 0, j = 0;
    while (i < a.size() && j < b.size()) {
      out.add(a.get(i) <= b.get(j) ? a.get(i++) : b.get(j++));
    }
    while (i < a.size()) out.add(a.get(i++));
    while (j < b.size()) out.add(b.get(j++));
    return out;
  }

  public static void main(String[] args) {
    List<List<Integer>> halls = List.of(
        List.of(1003, 1042, 1090),
        List.of(1007, 1019),
        List.of(1011, 1031, 1055, 1068));
    List<Integer> all = new ArrayList<>();
    for (List<Integer> hall : halls) {
      all = merge(all, hall);
    }
    System.out.println("Seating list: " + all);
  }
}
```

```text [Output]
Seating list: [1003, 1007, 1011, 1019, 1031, 1042, 1055, 1068, 1090]
```

Merging k lists one after another like this is O(n × k). The heaps chapter shows
the O(n log k) way with a `PriorityQueue`, which is the version asked in product
company interviews.

## What confuses people here

**Where the time actually goes.** People think the splitting is the clever part.
Splitting is one line of arithmetic; merging is where every comparison happens.
If an interviewer asks "which step is O(n)?", the answer is the merge at each
level.

::warning{icon="i-lucide-alert-triangle"}
**`<` instead of `<=` in the merge silently breaks stability.** With `<`, on a
tie the element from the right half goes first, and two students with the same
mark swap order. The array is still sorted, every test on plain `int`s passes,
and the bug only shows when you sort objects by one field and expect an earlier
ordering to survive.
::

::side-note{kind="performance"}
Allocating a new `temp` array inside every `merge` call is fine for learning and
slow in practice. Production versions allocate one helper array of size n once
and pass it down. If an interviewer asks how you would optimise your merge sort,
that is the first answer, and switching to insertion sort for ranges under about
16 elements is the second.
::

## Interview questions

::accordion
  :::accordion-item{label="1. Derive the time complexity of merge sort" icon="i-lucide-message-circle"}
  The recurrence is T(n) = 2T(n/2) + n: two half-sized problems plus a linear
  merge. Drawn as a tree, there are log₂ n levels and each level merges n
  elements in total, so n log n. It is the same in the best, average and worst
  case.
  :::

  :::accordion-item{label="2. Why does merge sort need O(n) extra space?" icon="i-lucide-message-circle"}
  The merge cannot be done in place cheaply: it writes into a temporary array
  and copies back, and at the top level that array is size n. In-place merge
  variants exist but are complicated and slower, which is why quick sort, which
  is in place, is preferred for primitive arrays.
  :::

  :::accordion-item{label="3. Merge two sorted arrays into the first, which has space at the end" icon="i-lucide-message-circle"}
  Fill from the back so nothing is overwritten before it is read.

  ```java
  static void mergeInto(int[] a, int m, int[] b, int n) {
    int i = m - 1, j = n - 1, k = m + n - 1;
    while (j >= 0) {
      if (i >= 0 && a[i] > b[j]) a[k--] = a[i--];
      else                       a[k--] = b[j--];
    }
  }
  ```

  O(m + n) time, O(1) extra space. The loop only needs to run while `b` has
  elements; whatever is left in `a` is already in place.
  :::

  :::accordion-item{label="4. Is merge sort good for linked lists?" icon="i-lucide-message-circle"}
  It is the best general sort for them. Merging two linked lists needs no extra
  array (you relink nodes), so the space drops to O(log n) for the recursion, and
  it never needs random access. Quick sort, by contrast, needs to jump around.
  :::

  :::accordion-item{label="5. Count inversions in an array of ranks" icon="i-lucide-message-circle"}
  An inversion is a pair i < j with a[i] > a[j]. Brute force is O(n²). During
  merge sort, whenever an element from the right half is taken before the
  remaining `mid - i + 1` elements of the left half, those are all inversions:
  add that number. O(n log n). This is a favourite product-company follow-up
  precisely because it tests whether you understand the merge rather than having
  memorised it.
  :::
::

is a lot of memory to borrow. Quick sort sorts in place with no second array, and

it becomes as slow as bubble sort, and it is not the input you would guess.
