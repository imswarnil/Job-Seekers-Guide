For `int[]` Java calls a dual-pivot quick sort, and for a list of students it
calls Timsort, a stable merge sort. The split is deliberate, and explaining it is
a better interview answer than writing any sort from memory. From here on, you
call the library's sort and spend your effort on the comparator.

## Why this matters in a job

Because in real code you will write a comparator every week and a sort
algorithm never. Because "Comparable or Comparator?" is one of the most asked
Java questions in service company interviews. Because a comparator written as
`a - b` has an overflow bug that passes every test until it does not. And because
half of the array problems in this track start with "sort it first", and the
sorting line has to be right.

## Two sorts, for two reasons

::feature-list{columns="2"}
  :::feature{icon="i-lucide-zap" title="Primitives: dual-pivot quick sort"}
  `Arrays.sort(int[])`, `Arrays.sort(double[])` and friends. In place and very
  fast. Not stable, and it does not need to be: two equal `int`s are
  indistinguishable, so there is no order between them to keep.
  :::
  :::feature{icon="i-lucide-merge" title="Objects: Timsort"}
  `Arrays.sort(Object[])`, `Collections.sort`, `List.sort`. A merge sort that
  first finds runs already in order and uses insertion sort on short ones.
  **Stable**, guaranteed O(n log n), faster still on partly ordered data.
  :::
::

That split is the answer to "what sort does Java use?". Objects get a stable sort
because two students with the same mark are different people and you can tell
them apart; primitives do not need one because you cannot.

## How it works

### Sorting primitives and ranges

```java [ArraysSort.java]
import java.util.Arrays;
import java.util.Collections;

public class ArraysSort {
  public static void main(String[] args) {
    int[] marks = {72, 35, 91, 60, 48};
    Arrays.sort(marks);
    System.out.println("Ascending:  " + Arrays.toString(marks));

    int[] partial = {72, 35, 91, 60, 48};
    Arrays.sort(partial, 1, 4);                 // indexes 1, 2, 3 only
    System.out.println("Range 1-3:  " + Arrays.toString(partial));

    Integer[] boxed = {72, 35, 91, 60, 48};     // descending needs objects
    Arrays.sort(boxed, Collections.reverseOrder());
    System.out.println("Descending: " + Arrays.toString(boxed));
  }
}
```

```text [Output]
Ascending:  [35, 48, 60, 72, 91]
Range 1-3:  [72, 35, 60, 91, 48]
Descending: [91, 72, 60, 48, 35]
```

There is no `Arrays.sort(int[], comparator)`. To sort an `int[]` in descending
order, either sort ascending and read it backwards, or use `Integer[]`. In an
interview, sorting ascending and walking from the end is the better answer,
because boxing 40,000 ints into objects costs memory and time.

### Comparable: the natural order

A class that implements `Comparable` says "this is how I am normally ordered".
There can be only one natural order.

```java [NaturalOrder.java]
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class NaturalOrder {

  static class Student implements Comparable<Student> {
    final int roll;
    final String name;
    Student(int roll, String name) { this.roll = roll; this.name = name; }

    @Override
    public int compareTo(Student other) {
      return Integer.compare(this.roll, other.roll);   // by roll number
    }

    @Override
    public String toString() { return roll + " " + name; }
  }

  public static void main(String[] args) {
    List<Student> list = new ArrayList<>(List.of(
        new Student(1042, "Meera"), new Student(1007, "Kabir"), new Student(1019, "Riya")));
    Collections.sort(list);
    System.out.println(list);
  }
}
```

```text [Output]
[1007 Kabir, 1019 Riya, 1042 Meera]
```

### Comparator: any order you need

A `Comparator` is an ordering that lives outside the class. You can have as many
as you like, and Java 8 made them one-liners.

```java [ManyOrders.java]
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class ManyOrders {

  record Applicant(String name, int marks, int applied) {}   // applied = day of June

  public static void main(String[] args) {
    List<Applicant> list = new ArrayList<>(List.of(
        new Applicant("Arjun", 78, 9), new Applicant("Kabir", 64, 3),
        new Applicant("Riya", 78, 2), new Applicant("Meera", 91, 5),
        new Applicant("Sana", 64, 1)));

    list.sort(Comparator.comparing(Applicant::name));
    System.out.println("By name:   " + names(list));

    list.sort(Comparator.comparingInt(Applicant::marks).reversed()
        .thenComparingInt(Applicant::applied));
    System.out.println("Rank list: " + names(list));
  }

  static List<String> names(List<Applicant> list) {
    return list.stream().map(a -> a.name() + "(" + a.marks() + ")").toList();
  }
}
```

```text [Output]
By name:   [Arjun(78), Kabir(64), Meera(91), Riya(78), Sana(64)]
Rank list: [Meera(91), Riya(78), Arjun(78), Sana(64), Kabir(64)]
```

The rank list reads: highest marks first, and on a tie, whoever applied earlier.
`thenComparingInt` states the tie-break in the code, which is better than relying
on stability and an earlier sort, because the next person to read it can see the
rule.

::tip
If an interviewer asks how you would rank applicants, say the tie-break out loud
and ask what it should be. "Earlier application date? Higher marks in maths?"
That question is the senior answer. The code is one line either way.
::

### Sorting a 2D array by a column

Interval and scheduling problems hand you `int[][]` and need it sorted by the
first column. The comparator takes two rows.

```java [SortRows.java]
import java.util.Arrays;

public class SortRows {
  public static void main(String[] args) {
    // {start hour, end hour} of exam slots booked for Hall 3
    int[][] slots = {{14, 16}, {9, 12}, {11, 13}, {16, 18}};
    Arrays.sort(slots, (a, b) -> Integer.compare(a[0], b[0]));
    for (int[] s : slots) {
      System.out.println(s[0] + ":00 to " + s[1] + ":00");
    }
  }
}
```

```text [Output]
9:00 to 12:00
11:00 to 13:00
14:00 to 16:00
16:00 to 18:00
```

Once sorted by start, "do any slots overlap?" is one pass: compare each slot's
start with the previous slot's end. 11:00 is before 12:00, so the second slot
clashes. Sort first, then scan is a pattern you will see many times.

### Complexity

| Call | Algorithm | Time | Stable |
| --- | --- | --- | --- |
| `Arrays.sort(int[])` | dual-pivot quick sort | O(n log n) average | No (does not matter) |
| `Arrays.sort(Object[])` | Timsort | O(n log n) worst, O(n) if already sorted | **Yes** |
| `Collections.sort(list)`, `list.sort(c)` | Timsort | same | **Yes** |
| `PriorityQueue` top k | heap | O(n log k) | No |

## Real use case

**Top ten without sorting forty thousand.** The honest list of when to sort is
short, and the real mistake is sorting when you did not need to. Sorting 40,000
applications to find the top ten is O(n log n). Keeping a heap of ten is
O(n log 10).

```java [TopTen.java]
import java.util.ArrayList;
import java.util.List;
import java.util.PriorityQueue;
import java.util.Random;

public class TopTen {
  public static void main(String[] args) {
    Random random = new Random(42);
    PriorityQueue<Integer> top = new PriorityQueue<>();   // smallest on top
    for (int i = 0; i < 40_000; i++) {
      // entrance test out of 1000: most near 550, very few near the top
      int marks = (int) Math.max(0, Math.min(1000, 550 + random.nextGaussian() * 120));
      top.offer(marks);
      if (top.size() > 10) top.poll();                    // drop the lowest
    }
    List<Integer> result = new ArrayList<>(top);
    result.sort(null);
    System.out.println("Top ten marks: " + result);
  }
}
```

```text [Output]
Top ten marks: [958, 958, 963, 968, 976, 979, 979, 986, 1000, 1000]
```

Forty thousand marks, most of them near 550, and only ten numbers ever needed
remembering at the end. The heap never held more
than eleven values. The heaps chapter explains why `poll` removes the smallest,
and the SQL track shows the version that does not even load the rows: `ORDER BY
marks DESC LIMIT 10` on an indexed column.

## What confuses people here

**The subtraction comparator.** It looks clever and it overflows.

::compare{caption="Two comparators for marks that can be negative after moderation"}
  :::compare-side{label="Subtraction" verdict="wrong"}
  `(a, b) -> a - b`. When `a` is large and `b` is very negative, `a - b` overflows
  `int` and wraps to a negative number, so the comparator says `a < b`. The sort
  is silently wrong for a handful of values, which is the worst kind of wrong.
  :::
  :::compare-side{label="Integer.compare" verdict="right"}
  `(a, b) -> Integer.compare(a, b)`, or `Comparator.comparingInt(...)`. It cannot
  overflow, and it reads as what it means.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
**`compareTo` must agree with `equals`** for sorted collections. If two different
students compare as 0 (say you compare by marks only), a `TreeSet<Student>`
treats them as duplicates and silently keeps only one. The list sorts fine and
the set loses people. Always break ties down to something unique, like the roll
number, when the comparator is used as a key.
::

## Interview questions

::accordion
  :::accordion-item{label="1. Comparable versus Comparator" icon="i-lucide-message-circle"}
  `Comparable` lives inside the class, gives the one natural order through
  `compareTo`, and is used by `Collections.sort(list)` with no argument.
  `Comparator` lives outside, can be as many orders as you need, and is passed to
  the sort. Use `Comparable` for the obvious order (roll number) and comparators
  for every screen that sorts differently.
  :::

  :::accordion-item{label="2. Which algorithm does Arrays.sort use?" icon="i-lucide-message-circle"}
  For primitive arrays, dual-pivot quick sort, not stable, O(n log n) average.
  For object arrays and lists, Timsort, stable, O(n log n) worst case and O(n) on
  sorted input. Objects need stability because equal objects are still
  distinguishable; primitives do not.
  :::

  :::accordion-item{label="3. Sort students by marks descending, then by name" icon="i-lucide-message-circle"}
  ```java
  students.sort(Comparator.comparingInt(Student::marks).reversed()
      .thenComparing(Student::name));
  ```
  Watch where `.reversed()` goes: placed at the end of the chain, it would
  reverse the name order too.
  :::

  :::accordion-item{label="4. Why is return a - b a bad comparator?" icon="i-lucide-message-circle"}
  Integer overflow. `Integer.MAX_VALUE - (-1)` wraps to `Integer.MIN_VALUE`, a
  negative number, so a very large value is reported as smaller. Use
  `Integer.compare(a, b)`.
  :::

  :::accordion-item{label="5. How would you find the top 10 of 40,000 applicants?" icon="i-lucide-message-circle"}
  A min-heap of size 10: offer each, poll when size exceeds 10. O(n log 10),
  constant memory. Sorting everything is O(n log n) and wasteful. If the data is
  in a database, `ORDER BY ... LIMIT 10` with an index, so the rows never reach
  Java at all.
  :::
::
