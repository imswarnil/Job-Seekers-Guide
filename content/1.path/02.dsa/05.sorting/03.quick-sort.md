Quick sort needs no second array, and the input that makes it as slow as bubble
sort is a list that is **already sorted**. Both facts come from the same single
decision: which element you choose as the pivot.

## Why this matters in a job

Because "write quick sort" and "explain partition" are standard second-round
questions, and "why is quick sort O(n²) in the worst case?" is the follow-up
that separates people who memorised it from people who understand it. Because
`Arrays.sort(int[])` in Java is a quick sort. And because the partition step on
its own solves "kth largest element" in average O(n), which is asked at product
companies.

## Split around one value

A class teacher has a pile of answer sheets and one question: who passed? She
picks a sheet with 40 marks as the dividing line, puts every sheet below 40 on
the left of her desk and every sheet at 40 or above on the right. She has not
sorted anything, but she has made a promise: nothing on the left needs to move to
the right, ever. Now she does the same to the left pile and the right pile
separately.

That dividing sheet is the **pivot**, and the step of splitting around it is
**partition**. After one partition the pivot is in its **final sorted position**,
and it never moves again.

Merge sort does its work on the way **up** (the merge). Quick sort does its work
on the way **down** (the partition), and there is nothing to combine at the end.

## How it works

```java [QuickSort.java]
import java.util.Arrays;

public class QuickSort {

  static void sort(int[] a, int low, int high) {
    if (low >= high) return;
    int p = partition(a, low, high);   // a[p] is now in its final place
    sort(a, low, p - 1);
    sort(a, p + 1, high);
  }

  // Lomuto partition: last element is the pivot.
  static int partition(int[] a, int low, int high) {
    int pivot = a[high];
    int i = low - 1;                   // end of the "smaller than pivot" region
    for (int j = low; j < high; j++) {
      if (a[j] < pivot) {
        i++;
        swap(a, i, j);
      }
    }
    swap(a, i + 1, high);              // put the pivot after the smaller region
    return i + 1;
  }

  static void swap(int[] a, int x, int y) {
    int t = a[x]; a[x] = a[y]; a[y] = t;
  }

  public static void main(String[] args) {
    int[] marks = {64, 35, 88, 12, 70, 41};
    int p = partition(marks, 0, marks.length - 1);
    System.out.println("After one partition: " + Arrays.toString(marks) + ", pivot at " + p);

    int[] all = {64, 35, 88, 12, 70, 41, 97, 23};
    sort(all, 0, all.length - 1);
    System.out.println("Sorted: " + Arrays.toString(all));
  }
}
```

```text [Output]
After one partition: [35, 12, 41, 64, 70, 88], pivot at 2
Sorted: [12, 23, 35, 41, 64, 70, 88, 97]
```

The first line is worth staring at. The left side `[35, 12]` is not sorted and
the right side `[64, 70, 88]` happens to be, but neither matters yet. What
matters is that 41 is at index 2 and will stay there.

### Why sorted input is the worst case

With the last element as pivot, a sorted array always picks the **largest**
value. The partition puts everything on one side and nothing on the other, so
each call removes one element instead of half. That is n levels instead of log n,
and n + (n - 1) + ... + 1 comparisons: O(n²).

```java [WorstCase.java]
public class WorstCase {

  static long comparisons = 0;

  static void sort(int[] a, int low, int high) {
    if (low >= high) return;
    int pivot = a[high], i = low - 1;
    for (int j = low; j < high; j++) {
      comparisons++;
      if (a[j] < pivot) { i++; int t = a[i]; a[i] = a[j]; a[j] = t; }
    }
    int t = a[i + 1]; a[i + 1] = a[high]; a[high] = t;
    sort(a, low, i);
    sort(a, i + 2, high);
  }

  public static void main(String[] args) {
    int n = 2000;
    int[] sorted = new int[n];
    int[] shuffled = new int[n];
    java.util.Random random = new java.util.Random(7);
    for (int i = 0; i < n; i++) {
      sorted[i] = i;
      shuffled[i] = random.nextInt(100_000);
    }
    sort(sorted, 0, n - 1);
    System.out.println("Already sorted: " + comparisons + " comparisons");
    comparisons = 0;
    sort(shuffled, 0, n - 1);
    System.out.println("Random order:   " + comparisons + " comparisons");
  }
}
```

```text [Output]
Already sorted: 1999000 comparisons
Random order:   24494 comparisons
```

Same 2,000 roll numbers. The sorted list took about eighty times more work. On a
list of 2 lakh, the recursion is 2 lakh deep and the program dies with
`StackOverflowError`.

::tip
The fix is to stop choosing the pivot predictably. Pick a **random** index and
swap it to the end before partitioning, or take the median of the first, middle
and last elements. Either way, no fixed input can force the worst case. Say this
in the same breath as the O(n²) and the answer is complete.
::

### Complexity

| | Value | Why |
| --- | --- | --- |
| Time, average | **O(n log n)** | pivots split roughly in half, log n levels |
| Time, worst | **O(n²)** | pivot always the smallest or largest |
| Extra space | O(log n) average | recursion stack only; no second array |
| Stable | **No** | the long-distance swaps reorder equal values |

On random data quick sort usually beats merge sort in practice, because it works
in place and walks memory in order, which the processor cache rewards.

## Real use case

**The kth largest mark without sorting.** The placement cell wants the 10th
highest CGPA to set a shortlist cutoff. Sorting is O(n log n). **Quickselect**
partitions once, looks at where the pivot landed, and recurses into only the
side that contains position k. Average O(n).

```java [KthLargest.java]
public class KthLargest {

  static int kthLargest(int[] a, int k) {
    int target = a.length - k;           // kth largest = index n-k when sorted
    int low = 0, high = a.length - 1;
    while (true) {
      int p = partition(a, low, high);
      if (p == target) return a[p];
      if (p < target) low = p + 1;       // answer is on the right
      else high = p - 1;                 // answer is on the left
    }
  }

  static int partition(int[] a, int low, int high) {
    int pivot = a[high], i = low - 1;
    for (int j = low; j < high; j++) {
      if (a[j] < pivot) { i++; int t = a[i]; a[i] = a[j]; a[j] = t; }
    }
    int t = a[i + 1]; a[i + 1] = a[high]; a[high] = t;
    return i + 1;
  }

  public static void main(String[] args) {
    int[] marks = {72, 91, 45, 88, 60, 95, 38, 79, 84, 66};
    System.out.println("3rd highest: " + kthLargest(marks.clone(), 3));
    System.out.println("Highest:     " + kthLargest(marks.clone(), 1));
    System.out.println("Lowest:      " + kthLargest(marks.clone(), 10));
  }
}
```

```text [Output]
3rd highest: 88
Highest:     95
Lowest:      38
```

Each call throws away one side, so on average the work is n + n/2 + n/4 + ...,
which is 2n: O(n). The worst case is still O(n²) for the same pivot reason, and a
random pivot fixes it the same way. The heaps chapter gives you a second answer
to this question with a guaranteed O(n log k).

## What confuses people here

**Thinking the partition sorts the two sides.** It does not. It only promises
that everything left of the pivot is smaller and everything right is not. The
sides are sorted by the recursive calls.

::warning{icon="i-lucide-alert-triangle"}
**`sort(a, low, p)` instead of `sort(a, low, p - 1)`.** Including the pivot in a
recursive call means a range can hand itself back unchanged, and on some inputs
the recursion never shrinks. The pivot is finished; leave it out of both calls.
::

::compare{caption="Merge sort and quick sort, the comparison interviewers want"}
  :::compare-side{label="Merge sort"}
  O(n log n) **always**. O(n) extra memory. **Stable**. Works on linked lists and
  on data bigger than memory. Java uses its descendant, Timsort, for objects.
  :::
  :::compare-side{label="Quick sort"}
  O(n log n) **on average**, O(n²) worst. **In place**. Not stable. Usually faster
  on arrays of primitives in practice. Java uses a dual-pivot version for `int[]`.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="1. What is the worst case of quick sort and when does it happen?" icon="i-lucide-message-circle"}
  O(n²), when every pivot is the smallest or largest value in its range, so each
  partition removes only one element. With a first- or last-element pivot that
  happens on already sorted or reverse sorted input, and on an array where every
  value is equal. Randomised or median-of-three pivots make it vanishingly
  unlikely.
  :::

  :::accordion-item{label="2. Why is quick sort not stable?" icon="i-lucide-message-circle"}
  Partition swaps elements across long distances. Two students both on 70 can be
  swapped past each other depending on where the pivot is, so their original
  order is lost. Merge sort only ever moves elements between adjacent halves in
  order, which is why it can be stable.
  :::

  :::accordion-item{label="3. Quick sort or merge sort?" icon="i-lucide-message-circle"}
  Arrays of primitives in memory: quick sort, for in-place and cache-friendly
  speed, with a random pivot. Objects where equal keys must keep their order:
  merge sort, because it is stable. Linked lists or data larger than memory: merge
  sort. Needing a guaranteed bound (a real-time system): merge sort or heap sort.
  :::

  :::accordion-item{label="4. What is the space complexity of quick sort?" icon="i-lucide-message-circle"}
  O(log n) on average for the recursion stack, O(n) in the worst case when the
  recursion goes n deep. Recursing into the smaller side first and looping on the
  larger side caps the stack at O(log n) even in the worst case.
  :::

  :::accordion-item{label="5. Find the kth largest element" icon="i-lucide-message-circle"}
  Three answers, in the order to give them: sort and index, O(n log n); a min-heap
  of size k, O(n log k); quickselect, O(n) average and O(n²) worst. Naming all
  three with their trade-offs is the complete answer.
  :::
::
