Marks between 0 and 100 can be sorted without a single comparison: count how
many students got each mark, then write the marks back out in order. And the
moment you sort students rather than bare numbers, two students on the same mark
force a question every sort has to answer, which is who goes first.

## Why this matters in a job

Because "can you sort faster than O(n log n)?" is a real interview question, and
the answer is "yes, when the range of values is small", with counting sort as the
proof. Because **stability** is asked about every sort you name, and it is the
property that matters most in real code: it is what makes a rank list
reproducible. And because the counting idea (an array indexed by value) is the
same trick as the `int[26]` letter counts from the strings chapter.

## Count, then write back

The exam cell has 40,000 answer sheets marked out of 100. Instead of comparing
sheets, a clerk draws 101 boxes labelled 0 to 100 and drops a tally mark in the
right box for every sheet. Then she reads the boxes left to right: three students
on 12, one on 13, none on 14, and so on. The sorted list is those counts written
out. Every sheet was looked at once, and every box once.

## How it works

### Counting sort on plain marks

```java [CountingSort.java]
import java.util.Arrays;

public class CountingSort {

  static void sort(int[] marks, int maxMark) {
    int[] count = new int[maxMark + 1];
    for (int m : marks) {
      count[m]++;                          // tally
    }
    int k = 0;
    for (int m = 0; m <= maxMark; m++) {
      while (count[m]-- > 0) {
        marks[k++] = m;                    // write back
      }
    }
  }

  public static void main(String[] args) {
    int[] marks = {72, 35, 91, 35, 60, 72, 100, 0, 60, 72};
    sort(marks, 100);
    System.out.println(Arrays.toString(marks));
  }
}
```

```text [Output]
[0, 35, 35, 60, 60, 72, 72, 72, 91, 100]
```

This version is fine for bare numbers, because two 72s are indistinguishable.
It is useless for students, because it throws the students away and keeps only
their marks.

### Stability, defined

A sort is **stable** if two items that compare equal come out in the same order
they went in.

::compare{caption="Applications already in order of date received, now sorted by marks."}
  :::compare-side{label="Unstable sort" verdict="wrong"}
  Riya (applied 2 June) and Arjun (applied 9 June) both scored 78. After an
  unstable sort their order is arbitrary. Run it twice and a different one of the
  two may sit at position 40, and if 40 is the last seat, a different person gets
  admitted for no reason anybody can explain.
  :::
  :::compare-side{label="Stable sort" verdict="right"}
  Riya and Arjun stay in date order, so the earlier applicant ranks first every
  time. The result is reproducible and defensible to a parent on the telephone.
  :::
::

::pull-quote
Stability is what lets you sort by one thing and then by another, and have the
first sort still mean something.
::

### Stable counting sort for students

To keep students and their order, turn the counts into **positions**: a running
total (a prefix sum, from the arrays chapter) tells you where each mark's block
ends. Then place students by walking the input **from the back**, so that among
equal marks the last one in goes to the last slot.

```java [StableCountingSort.java]
public class StableCountingSort {

  record Student(String name, int marks) {}

  static Student[] sort(Student[] in, int maxMark) {
    int[] count = new int[maxMark + 1];
    for (Student s : in) count[s.marks()]++;
    for (int m = 1; m <= maxMark; m++) {
      count[m] += count[m - 1];            // count[m] = slots used up to mark m
    }
    Student[] out = new Student[in.length];
    for (int i = in.length - 1; i >= 0; i--) {   // back to front keeps it stable
      Student s = in[i];
      out[--count[s.marks()]] = s;
    }
    return out;
  }

  public static void main(String[] args) {
    Student[] byApplicationDate = {
        new Student("Riya", 78), new Student("Kabir", 64),
        new Student("Arjun", 78), new Student("Meera", 91),
        new Student("Sana", 64)
    };
    for (Student s : sort(byApplicationDate, 100)) {
      System.out.println(s.marks() + "  " + s.name());
    }
  }
}
```

```text [Output]
64  Kabir
64  Sana
78  Riya
78  Arjun
91  Meera
```

Kabir before Sana and Riya before Arjun, exactly as they applied. Walk the input
front to back in the last loop instead and each pair comes out reversed. The
array is still sorted by marks; only the tie order is wrong, which is the kind
of bug no test on plain numbers can catch.

### Which sorts are stable

| Sort | Stable? | Why |
| --- | --- | --- |
| Bubble | **Yes** | only swaps neighbours that are strictly out of order |
| Insertion | **Yes** | stops shifting at an equal element |
| Merge | **Yes** | takes from the left half on ties (`<=`) |
| Counting (with prefix sums) | **Yes** | places from the back |
| Selection | No | long-distance swap jumps over an equal element |
| Quick | No | partition swaps across the array |
| Heap | No | the heap reorders freely |

### Complexity

| | Value |
| --- | --- |
| Time | **O(n + k)**, n items, k = range of values (101 for marks out of 100) |
| Extra space | O(n + k) for the stable version, O(k) for bare numbers |
| Stable | Yes, in the prefix-sum version |
| When it wins | k is small compared with n: marks, ages, ratings, grades |
| When it loses | k is huge: sorting roll numbers up to 10⁹ needs a billion-slot array |

The famous "O(n log n) is the best possible" limit applies only to sorts that
**compare**. Counting sort never compares two items, so the limit does not apply
to it. That sentence is the interview answer.

## Real use case

Stability is used every day without anybody naming it: **sorting by two keys in
two passes**. Sort by the secondary key first, then stable-sort by the primary
key, and the secondary order survives inside each group. Java's `List.sort` is
stable, so this works:

```java [TwoKeySort.java]
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class TwoKeySort {

  record Student(String name, String department, int marks) {}

  public static void main(String[] args) {
    List<Student> list = new ArrayList<>(List.of(
        new Student("Meera", "ECE", 91), new Student("Kabir", "CSE", 64),
        new Student("Riya", "CSE", 78), new Student("Arjun", "ECE", 78),
        new Student("Sana", "CSE", 91)));

    list.sort(Comparator.comparingInt(Student::marks).reversed());  // secondary
    list.sort(Comparator.comparing(Student::department));           // primary, stable

    list.forEach(s -> System.out.println(s.department() + "  " + s.marks() + "  " + s.name()));
  }
}
```

```text [Output]
CSE  91  Sana
CSE  78  Riya
CSE  64  Kabir
ECE  91  Meera
ECE  78  Arjun
```

Each department is still in descending order of marks, because the second sort
did not disturb students within the same department. The next lesson shows the
clearer way to write this with `thenComparing`, but the two-pass version is what
you will find in older code, and it only works because the sort is stable.

## What confuses people here

**"Stable" has nothing to do with speed or with crashing.** It is only about the
order of equal items. An unstable sort still produces a correctly sorted array.

::warning{icon="i-lucide-alert-triangle"}
**Counting sort and negative values.** `count[m]` with a negative `m` throws
`ArrayIndexOutOfBoundsException`. For a range like -50 to 50 (a marks adjustment
column), shift every value by the minimum: use `count[m - min]` and add `min`
back when writing out.
::

::side-note{kind="go-deeper"}
**Radix sort** extends this to large numbers: sort ten-digit roll numbers by the
last digit with a stable counting sort, then by the second last, and so on. Ten
passes of O(n + 10) each. It only works because every pass is stable, which is a
neat way to show an interviewer you understand why stability exists.
::

## Interview questions

::accordion
  :::accordion-item{label="1. Can you sort in better than O(n log n)?" icon="i-lucide-message-circle"}
  Not with comparisons: any comparison sort needs about n log n comparisons in
  the worst case. Without comparisons, yes: counting sort is O(n + k) and radix
  sort O(d × (n + b)), when the values are integers in a limited range.
  :::

  :::accordion-item{label="2. What is a stable sort? Give an example where it matters." icon="i-lucide-message-circle"}
  Equal items keep their input order. Ranking applicants by marks when they are
  already in order of application date: a stable sort keeps the earlier applicant
  ahead on a tie, so the cutoff is reproducible.
  :::

  :::accordion-item{label="3. Is counting sort always better for integers?" icon="i-lucide-message-circle"}
  No. Its cost depends on k, the range. Sorting 1,000 roll numbers between 1 and
  10⁹ needs a count array of a billion ints, about 4 GB, to sort a thousand
  numbers. Use it when k is at most a small multiple of n.
  :::

  :::accordion-item{label="4. Make an unstable sort stable" icon="i-lucide-message-circle"}
  Add the original index as a tie-breaker: compare by marks, and if equal, by
  position in the input. Every comparison sort becomes stable, at the cost of
  storing one extra int per item.
  :::
::
