The question after every coding round is "what is the complexity?", and the
answer is not mathematics. It is counting: how many steps does this code take,
and what happens to that number when the input gets ten times bigger.

## Why this matters in a job

Because "this works on my 50 test rows but it will not work on the 4 lakh rows
in production" is a sentence you need to be able to say and defend. And because
every technical interview in this market, service or product, asks for the
complexity of whatever you have written. Online tests enforce it without asking:
a slow solution times out on the large hidden test cases.

## Big-O is a growth rate

Think of the exam cell checking whether a roll number is on the list of 40,000
students allowed to sit the exam. A clerk with an unsorted printout reads down
the list. With 40,000 names, the worst case is 40,000 looks. If the college
doubles in size, the worst case doubles too.

That relationship, "work grows in step with the input", is written **O(n)**,
read "order n". Big-O answers one question.

::pull-quote
If the input gets ten times bigger, what happens to the work?
::

| Notation | Name | Ten times more input means | Example |
| --- | --- | --- | --- |
| **O(1)** | Constant | The same work | Reading `marks[5]` |
| **O(log n)** | Logarithmic | One or two more steps | Binary search in a sorted list |
| **O(n)** | Linear | Ten times the work | Scanning every student once |
| **O(n log n)** | Linearithmic | About eleven times | Any good sort |
| **O(n²)** | Quadratic | **A hundred times** | Comparing every student with every other |
| **O(2ⁿ)** | Exponential | Unimaginably more | Trying every subset of courses |

**n** is the size of the input: the number of students, the length of the
string, the number of marks. Always say what n is.

## How it works

Count the steps a loop takes, as a function of n. Here is the exam cell's
check, with a counter added so you can see the count rather than trust it.

```java [LinearSearch.java]
public class LinearSearch {
  static int comparisons = 0;

  static boolean isAllowed(int[] rollNumbers, int target) {
    for (int roll : rollNumbers) {       // runs up to n times
      comparisons++;
      if (roll == target) return true;   // one comparison each time
    }
    return false;
  }

  public static void main(String[] args) {
    for (int n : new int[]{1_000, 10_000, 100_000}) {
      int[] rolls = new int[n];
      for (int i = 0; i < n; i++) rolls[i] = 1000 + i;

      comparisons = 0;
      isAllowed(rolls, -1);              // not on the list: the worst case
      System.out.println("n = " + n + "  comparisons = " + comparisons);
    }
  }
}
```

```text [Output]
n = 1000  comparisons = 1000
n = 10000  comparisons = 10000
n = 100000  comparisons = 100000
```

Ten times the input, ten times the work. That is O(n).

Now the most common accidental quadratic: checking whether any two students
share a roll number by comparing every pair.

```java [PairCount.java]
public class PairCount {
  public static void main(String[] args) {
    for (int n : new int[]{1_000, 10_000, 100_000}) {
      long comparisons = 0;
      for (int i = 0; i < n; i++) {
        for (int j = i + 1; j < n; j++) {
          comparisons++;                 // compare student i with student j
        }
      }
      System.out.println("n = " + n + "  comparisons = " + comparisons);
    }
  }
}
```

```text [Output]
n = 1000  comparisons = 499500
n = 10000  comparisons = 49995000
n = 100000  comparisons = 4999950000
```

Ten times the input, a hundred times the work. The exact count is
n(n − 1)/2, which is n²/2 minus a bit. Big-O keeps only the shape: **O(n²)**.

### Complexity rules you can apply by eye

| Code shape | Complexity |
| --- | --- |
| A fixed number of statements, no loop over the input | O(1) |
| One loop over n | O(n) |
| Two loops one after the other | O(n) + O(n) = O(n) |
| A loop inside a loop, both over n | O(n²) |
| A loop over n students inside a loop over m courses | O(n × m) |
| A loop that halves the range each time | O(log n) |
| A loop over n that does a halving search each time | O(n log n) |

## Why the constant is dropped

This is the part that feels like cheating, so here is the reason.

```java [TwoWays.java]
public class TwoWays {
  public static void main(String[] args) {
    int[] marks = {72, 91, 64, 85, 58};
    int steps = 0;

    // Version A: one pass, three jobs per student
    int total = 0, max = 0, passed = 0;
    for (int m : marks) {
      total += m; steps++;
      max = Math.max(max, m); steps++;
      if (m >= 60) passed++; steps++;
    }
    System.out.println("A: " + steps + " steps");

    // Version B: three passes, one job each
    steps = 0;
    for (int m : marks) { total += m; steps++; }
    for (int m : marks) { max = Math.max(max, m); steps++; }
    for (int m : marks) { if (m >= 60) passed++; steps++; }
    System.out.println("B: " + steps + " steps");
  }
}
```

```text [Output]
A: 15 steps
B: 15 steps
```

Both are 3n steps. Both are **O(n)**. Big-O ignores the 3 because the question
is about shape, not speed: an O(n) algorithm that is three times slower than
another O(n) algorithm still beats any O(n²) one once the input grows.

The same logic drops smaller terms: n² + n is O(n²), because at n = 100,000 the
extra n is 0.001% of the total.

::side-note{kind="go-deeper"}
The honest caveat, which good interviewers like to hear: the constant matters
at small n, and small n is a lot of real code. An O(n²) loop over five
departments is fine, and rewriting it with a `HashMap` can be slower because of
the hashing. Big-O is about how something scales, not about whether it is fast
today. Saying that shows judgement rather than recitation.
::

## The loop you cannot see

The nastiest quadratic is invisible, because the inner loop belongs to a
library method.

```java [HiddenLoop.java]
import java.util.*;

public class HiddenLoop {
  public static void main(String[] args) {
    List<Integer> rolls = List.of(101, 102, 101, 103, 102, 104);

    // Looks like one loop. contains() on a List scans, so it is two.
    List<Integer> unique = new ArrayList<>();
    for (int roll : rolls) {
      if (!unique.contains(roll)) unique.add(roll);   // O(n) inside O(n)
    }
    System.out.println("List version: " + unique);

    // A HashSet checks membership in O(1) on average. One real loop.
    Set<Integer> seen = new LinkedHashSet<>();
    for (int roll : rolls) seen.add(roll);
    System.out.println("Set version:  " + seen);
  }
}
```

```text [Output]
List version: [101, 102, 103, 104]
Set version:  [101, 102, 103, 104]
```

Same answer, and on six roll numbers nobody can tell the difference. On
4 lakh, the list version does around 80 billion comparisons in the worst case
and the set version does 4 lakh hash lookups.

::warning{icon="i-lucide-alert-triangle"}
The hidden costs to know by heart in Java: `List.contains`, `List.indexOf` and
`List.remove(Object)` scan, so they are O(n). `String +=` inside a loop copies
the whole string each time, so building a string of n pieces is O(n²). Use a
`HashSet` for membership and a `StringBuilder` for building text.
::

## Best, worst and average

Interviewers ask which case you mean, so say it before they ask.

For the exam cell's search: **best case** the roll number is first, O(1).
**Worst case** it is last or absent, O(n). **Average**, about half the list,
n/2, which is still O(n) once the constant is dropped.

By convention, an unqualified complexity means the **worst case**. That is the
one that matters, because the worst case is what happens on results day when
every student refreshes the page at once.

## Real use case

::real-life{title="The report that got slower every semester" source="A college attendance system"}
A nightly job flagged students below 75% attendance. For each student it looked
up their department in a `List<Department>` with a loop, and for each attendance
row it checked `flagged.contains(studentId)` on an `ArrayList`. With 2,000
students it ran in seconds. Five years later, with 18,000 students and a row per
lecture, it ran past morning. Nothing was broken. Two lookups were O(n) inside
an O(n) loop, and swapping both for a `HashMap` and a `HashSet` brought it back
to under a minute.
::

## What confuses people here

- **"Two loops means O(n²)."** Only if one is inside the other. Two loops one
  after the other are O(n) + O(n), which is O(n).
- **"O(n × m) is O(n²)."** Only if n and m are the same size. Students times
  courses each student takes is n × 6, which is O(n). Say the letters you mean.
- **"Big-O tells me the runtime."** It tells you the growth. Two O(n) programs
  can differ by a factor of fifty in seconds.
- **Forgetting the library.** `Collections.sort` is O(n log n), `contains` on a
  list is O(n), `HashMap.get` is O(1) on average. A single line can be a loop.

## Interview questions

::accordion
  :::accordion-item{label="What is the time complexity of this loop with list.contains inside it?" icon="i-lucide-message-circle"}
  O(n²). The outer loop runs n times and `ArrayList.contains` scans up to n
  elements each time. Replacing the list with a `HashSet` makes membership O(1)
  on average, so the whole thing becomes O(n). Naming the hidden loop inside the
  library call is the point of the question.
  :::

  :::accordion-item{label="Why do we drop constants in Big-O?" icon="i-lucide-message-circle"}
  Because Big-O describes how the work grows, not how long it takes. 3n and n
  both grow linearly, so both are O(n), and any linear algorithm beats any
  quadratic one for large enough input. The constant matters when n is small or
  when two algorithms have the same growth rate.
  :::

  :::accordion-item{label="What is the complexity of building a string with += in a loop?" icon="i-lucide-message-circle"}
  O(n²) in the total length, because `String` is immutable and each `+=`
  creates a new string and copies everything built so far. The fix:

  ```java
  StringBuilder report = new StringBuilder();
  for (int mark : marks) report.append(mark).append('\n');
  String result = report.toString();   // O(n) overall
  ```
  :::

  :::accordion-item{label="Two nested loops, the inner one from i to n. Is that still O(n²)?" icon="i-lucide-message-circle"}
  Yes. The inner loop runs n − 1, then n − 2, down to 0 times, which sums to
  n(n − 1)/2. That is half of n², and the half is a constant, so O(n²). The
  `PairCount` program above prints exactly this count.
  :::

  :::accordion-item{label="Best, worst and average case of linear search?" icon="i-lucide-message-circle"}
  Best O(1) when the target is first, worst O(n) when it is last or missing,
  average O(n) because on average you read half the array. An unqualified
  "complexity" means the worst case.
  :::
::
