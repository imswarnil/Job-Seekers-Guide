That opposite trade is a **linked list**. Each item sits wherever memory had
room, and carries one extra thing: the address of the item after it. Nothing
has to move when you insert, because nothing was ever next to anything.

## Why this matters in a job

In day-to-day Java you will almost never write a linked list, and I will argue
below that you should rarely even use Java's `LinkedList`. But in interviews it
is one of the three most-asked structures, because it tests the one thing an
array hides from you: whether you can hold a pointer in your head and move it
without losing the rest of the chain.

When I was preparing for the switch that took me to 15.5 LPA, linked list
questions came up in round after round, and they nearly always started the same
way: "write the node class".

## A chain of nodes

Think of a treasure hunt at a college fest. Each clue is hidden somewhere on
campus and tells you only where the next clue is. To reach clue 5 you must find
clues 1 to 4 first. Nobody can hand you clue 5 directly, because nobody knows
where it is except clue 4.

That is a linked list. Each clue is a **node**: a small object holding a value
and a reference (Java's word for a pointer) to the next node. The first node is
the **head**. The last node's `next` is `null`, which is how you know the chain
has ended.

::memory{kind="list" caption="Roll numbers in a linked list. Each node holds a value and the address of the next. The head is the only way in."}
---
cells:
  - { value: "101", label: "head", state: "active" }
  - { value: "102" }
  - { value: "103" }
  - { value: "104" }
  - { value: "null", state: "ghost" }
---
::

Compare that with an array. An array keeps its elements side by side, so the
machine finds element 4 by arithmetic: `start + 4 × size`. A linked list has no
arithmetic to do. The only way to element 4 is to start at the head and follow
four references.

## How it works

The whole structure is one tiny class nested in another.

```java
static class Node {
  int roll;
  Node next;      // the entire idea, in one field
}
```

Here is a complete singly linked list of roll numbers: add at the front, add at
the back, insert at a position, remove by value, search and print.

```java [RollList.java]
public class RollList {
  static class Node {
    int roll;
    Node next;
    Node(int roll) { this.roll = roll; }
  }

  private Node head;
  private int size;

  void addFirst(int roll) {
    Node node = new Node(roll);
    node.next = head;
    head = node;
    size++;
  }

  void addLast(int roll) {
    Node node = new Node(roll);
    if (head == null) { head = node; size++; return; }
    Node current = head;
    while (current.next != null) current = current.next;
    current.next = node;
    size++;
  }

  void insertAt(int index, int roll) {
    if (index < 0 || index > size) throw new IndexOutOfBoundsException("index " + index);
    if (index == 0) { addFirst(roll); return; }
    Node before = head;
    for (int i = 0; i < index - 1; i++) before = before.next;
    Node node = new Node(roll);
    node.next = before.next;
    before.next = node;
    size++;
  }

  boolean remove(int roll) {
    if (head == null) return false;
    if (head.roll == roll) { head = head.next; size--; return true; }
    Node current = head;
    while (current.next != null && current.next.roll != roll) current = current.next;
    if (current.next == null) return false;
    current.next = current.next.next;
    size--;
    return true;
  }

  boolean contains(int roll) {
    for (Node n = head; n != null; n = n.next) if (n.roll == roll) return true;
    return false;
  }

  void print() {
    StringBuilder sb = new StringBuilder();
    for (Node n = head; n != null; n = n.next) sb.append(n.roll).append(" -> ");
    System.out.println(sb.append("null").append("   (size ").append(size).append(")"));
  }

  public static void main(String[] args) {
    RollList list = new RollList();
    list.addLast(101);
    list.addLast(102);
    list.addLast(104);
    list.print();
    list.addFirst(100);
    list.insertAt(3, 103);
    list.print();
    System.out.println("contains 103? " + list.contains(103));
    list.remove(100);
    list.remove(104);
    list.print();
    System.out.println("remove 999? " + list.remove(999));
  }
}
```

```text [Output]
101 -> 102 -> 104 -> null   (size 3)
100 -> 101 -> 102 -> 103 -> 104 -> null   (size 5)
contains 103? true
101 -> 102 -> 103 -> null   (size 3)
remove 999? false
```

The two lines that matter most are in `insertAt`, and their order is the whole
trick.

::code-trace{caption="Inserting 103 after 102. Swap these two lines and you lose the rest of the list."}
```java [RollList.java]
Node node = new Node(roll);
node.next = before.next;
before.next = node;
```

  :::
  :::code-trace-step{lines="2" caption="First, the new node grabs the rest of the chain (104 onwards). Nothing in the list has changed yet, so nothing can be lost."}
  :::
  :::code-trace-step{lines="3" caption="Only then does 102 point at the new node. If you did this line first, 102 would forget 104, and the only reference to 104 and everything after it would be gone."}
  :::

Removal is the mirror image: to remove a node you stand on the node *before*
it and make its `next` skip over. That is why `remove` walks with
`current.next` rather than `current`. Once you are standing on the node you
want to delete, it is too late: in a singly linked list you cannot step back.

### Complexity

| Operation | Linked list | Why |
| --- | --- | --- |
| `addFirst` | **O(1)** | Two reference changes, however long the list |
| `addLast` (no tail reference) | O(n) | Walk to the end first |
| `addLast` (keep a `tail` field) | **O(1)** | Java's `LinkedList` does this |
| Get element `i` | O(n) | Follow `i` references |
| Insert or delete, **already standing there** | **O(1)** | Two reference changes |
| Insert or delete **by index or value** | O(n) | Getting there is the cost |
| Search | O(n) | No shortcut |
| Extra space | O(n) | One reference per node |

## Array or linked list: the table interviewers want

| Operation | Array / `ArrayList` | Linked list |
| --- | --- | --- |
| Get element `i` | **O(1)** | O(n) |
| Insert or remove at the end | O(1) amortised | O(1) with a tail |
| Insert or remove at the front | O(n) | **O(1)** |
| Insert or remove in the middle, **already there** | O(n) | **O(1)** |
| Insert or remove in the middle, **by index** | O(n) | O(n) |
| Search for a value | O(n) | O(n) |
| Memory per element | The value | Value **plus a reference and an object header**, often 3–4× |

The fifth row is the one that catches people. "Linked lists are fast at
insertion" is only true if you are already holding the node. Getting to
position 20,000 costs 20,000 steps, so `LinkedList.add(20000, x)` is O(n), the
same as an array.

::pull-quote
The complexity table says linked lists should often win. Real machines
disagree, and the reason is not in the table.
::

A modern processor reads memory in blocks of 64 bytes and keeps recent blocks
in a small, fast cache. Walking an array reads one block and gets the next
several elements for free. Walking a linked list jumps to an unrelated address
at every step, so nearly every step is a **cache miss** (the value was not in
the fast cache and has to come from main memory), which costs roughly a hundred
times more.

```text [Summing 10 million ints, one machine, illustrative]
int[]                    4 ms
ArrayList<Integer>      38 ms      ← boxing, but still contiguous
LinkedList<Integer>    412 ms      ← same O(n), about 100× slower
```

Those figures are from one run on one laptop and yours will differ, but the
shape will not: all three are O(n), and the gap is about what is next to what.

::side-note{kind="performance"}
For a list you mostly iterate and index, `ArrayList` is correct even where the
table suggests otherwise. For a stack or a queue, `ArrayDeque` beats
`LinkedList` too. Java's `LinkedList` is genuinely right in a narrow case:
you hold a `ListIterator` and insert or remove at that position many times.
::

## Real use case

You will not write `class Node` at work, but the idea is everywhere underneath
you. Java's `LinkedHashMap` threads a doubly linked list through its entries to
remember insertion order, and that is how a least-recently-used cache is built:
every time a student's profile is read, its entry is unlinked and relinked at
the end in O(1), and the oldest entry at the head is the one evicted.

```java [RecentProfiles.java]
import java.util.LinkedHashMap;
import java.util.Map;

public class RecentProfiles {
  public static void main(String[] args) {
    // accessOrder = true: every get moves the entry to the end of the internal linked list.
    Map<Integer, String> cache = new LinkedHashMap<>(16, 0.75f, true) {
      @Override
      protected boolean removeEldestEntry(Map.Entry<Integer, String> eldest) {
        return size() > 3;                 // keep only the three most recent
      }
    };
    cache.put(101, "Asha");
    cache.put(102, "Rahul");
    cache.put(103, "Meera");
    cache.get(101);                        // Asha was read, so she is recent again
    cache.put(104, "Imran");               // evicts the least recently used: Rahul
    System.out.println(cache.keySet());
  }
}
```

```text [Output]
[103, 101, 104]
```

## What confuses people here

- **Losing the list.** Writing `before.next = node` before `node.next =
  before.next` cuts the chain. Always attach the new node to the rest first.
- **Moving `head` while walking.** If you write `head = head.next` inside a
  loop to "walk" the list, you have deleted every node you walked past. Walk
  with a separate variable, `current`.
- **Forgetting the empty list and the one-node list.** Nearly every linked list
  bug is a `NullPointerException` on `head.next` when `head` is `null`. Test
  both before anything else.
- **Thinking `LinkedList` is the class to use for a list.** Almost never. Use
  `ArrayList` for lists and `ArrayDeque` for stacks and queues.

## Interview questions

::accordion
  :::accordion-item{label="Array versus linked list: when would you pick each?" icon="i-lucide-message-circle"}
  Give the table: O(1) indexed access against O(n); O(1) insertion at the front
  for a list against O(n) for an array; extra memory for references. Then the
  part that marks you out: in practice `ArrayList` wins even where the table
  favours a list, because arrays are contiguous and iterating a linked list is
  mostly cache misses. A linked list is right when you insert and delete in the
  middle at a position you are already holding.
  :::
  :::accordion-item{label="Insert a node at a given position. What is the order of the two assignments?" icon="i-lucide-message-circle"}
  Walk to the node before the position, then `node.next = before.next` first
  and `before.next = node` second. The reverse order drops every node after the
  insertion point. Handle index 0 separately, because there is no node before
  the head.
  :::
  :::accordion-item{label="Why is addLast O(n) in your list and O(1) in Java's LinkedList?" icon="i-lucide-message-circle"}
  Mine only keeps `head`, so reaching the end means walking the whole chain.
  Java's `LinkedList` also keeps a `tail` reference (and is doubly linked), so
  it goes straight to the end. Adding a `tail` field is a one-line fix, and you
  must then remember to update it in every method that can change the last node.
  :::
  :::accordion-item{label="Singly versus doubly linked list?" icon="i-lucide-message-circle"}
  A doubly linked node has `prev` as well as `next`. It costs one more reference
  per node and buys two things: you can walk backwards, and you can delete a
  node you are holding in O(1) without first finding the node before it. Java's
  `LinkedList` and the list inside `LinkedHashMap` are both doubly linked.
  :::
::
