The structure that turns any key into a position is a **hash table**, and in
Java you use it as `HashMap` and `HashSet`. It finds a student by roll number in
one step whether there are forty students or forty lakh, and the idea behind it
is simple once somebody draws it.

## Why this matters in a job

Because `HashMap` and `HashSet` are in essentially every Java program you will
ever read. Because "how does a HashMap work internally?" and "what is the
contract between equals and hashCode?" are two of the most asked Java questions
in Indian interviews, at service and product companies alike; I was asked one or
the other in almost every interview of my switch. And because getting the
contract wrong breaks your program in a way no compiler and few tests will catch.

## The trick

A college library keeps 16 shelves. Instead of searching every shelf for a book,
the librarian has a rule that turns the book's code into a shelf number. To shelve
a book, apply the rule and put it there. To find it, apply the same rule and look
on that one shelf. The rule is the **hash function**, and each shelf is a
**bucket**.

In Java: turn the key into an `int` with `hashCode()`, reduce that number to a
bucket index, and read that bucket directly.

## How it works

### From key to bucket

A `HashMap` starts with 16 buckets. To find a key's bucket it takes
`hashCode()`, mixes the high bits into the low bits (`h ^ (h >>> 16)`), and keeps
the last four bits (`& 15`), which is the same as the remainder after dividing by
16 but faster. You can watch it:

```java [BucketOf.java]
public class BucketOf {

  static int bucket(Object key, int buckets) {
    int h = key.hashCode();
    return (h ^ (h >>> 16)) & (buckets - 1);     // what HashMap does inside
  }

  public static void main(String[] args) {
    String[] rolls = {"2026CSE0184", "2026ECE0072", "2026CSE0185", "2026ME0031"};
    for (String roll : rolls) {
      System.out.println(roll + "  hashCode " + roll.hashCode() + "  bucket " + bucket(roll, 16));
    }
  }
}
```

```text [Output]
2026CSE0184  hashCode 722725072  bucket 3
2026ECE0072  hashCode 2039665024  bucket 2
2026CSE0185  hashCode 722725073  bucket 2
2026ME0031  hashCode 2097165688  bucket 8
```

`put(key, value)` computes the bucket and stores the pair there. `get(key)`
computes the same bucket and looks only there. No other bucket is ever touched.

### Collisions, and what actually happens

Look at the second and third lines: two different roll numbers, bucket 2. That is
a **collision**, and with 16 buckets and forty thousand students collisions are
certain, not possible. Java keeps a small linked list of entries in each bucket.
On a `get`, it goes to the bucket and then compares the keys in it one by one
with `equals`.

::pull-quote
A hash table is O(1) on average and O(n) in the worst case, and the worst case is
almost always your fault: it happens when your hash function puts everything in
one bucket.
::

Since Java 8, once a single bucket holds more than eight entries (and the table
has at least 64 buckets), that bucket turns into a balanced tree, so even the
degenerate case is O(log n) rather than O(n). Worth mentioning in an interview,
and worth not relying on.

### Resizing and the load factor

When the number of entries passes **capacity × load factor** (16 × 0.75 = 12 by
default), the map doubles to 32 buckets and **rehashes every entry**, because an
entry's bucket depends on the number of buckets. That one `put` is O(n). Spread
across all the puts it averages out to O(1), the same "amortised" argument as
`ArrayList` growing.

::tip
If you know you will store 40,000 students, say so up front:
`new HashMap<>(53_334)` (40,000 ÷ 0.75, rounded up). The map never resizes. On
Java 19 and later, `HashMap.newHashMap(40_000)` does that arithmetic for you.
::

### The contract that breaks it

This is the part that costs people real bugs, and it is asked constantly. Here is
a `Student` that overrides `equals` and forgets `hashCode`.

```java [BrokenKey.java]
import java.util.HashMap;
import java.util.Map;

public class BrokenKey {

  static class Student {
    final String roll;
    Student(String roll) { this.roll = roll; }

    @Override
    public boolean equals(Object o) {
      return o instanceof Student other && roll.equals(other.roll);
    }
    // hashCode NOT overridden
  }

  public static void main(String[] args) {
    Map<Student, Integer> marks = new HashMap<>();
    marks.put(new Student("2026CSE0184"), 78);

    Student sameStudent = new Student("2026CSE0184");
    System.out.println("equals: " + sameStudent.equals(new Student("2026CSE0184")));
    System.out.println("get:    " + marks.get(sameStudent));
    System.out.println("size:   " + marks.size());
  }
}
```

```text [Output]
equals: true
get:    null
size:   1
```

The two objects are equal. The map cannot find the second one, because the
default `hashCode` comes from the object's identity, so the two objects go to
different buckets and the lookup never even reaches `equals`. Write
`int m = marks.get(sameStudent);` instead and the `null` becomes a
`NullPointerException` when Java unboxes it.

**The contract, in one line:** if two objects are equal, their `hashCode` must
be the same. The reverse is not required: two unequal objects with the same hash
are a collision, which is normal.

```java [FixedKey.java]
import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

public class FixedKey {

  static class Student {
    final String roll;
    Student(String roll) { this.roll = roll; }

    @Override
    public boolean equals(Object o) {
      return o instanceof Student other && roll.equals(other.roll);
    }

    @Override
    public int hashCode() {
      return Objects.hash(roll);           // the same fields equals uses
    }
  }

  public static void main(String[] args) {
    Map<Student, Integer> marks = new HashMap<>();
    marks.put(new Student("2026CSE0184"), 78);
    System.out.println("get: " + marks.get(new Student("2026CSE0184")));
  }
}
```

```text [Output]
get: 78
```

A Java `record` writes both methods for you from its fields, which is why records
make good map keys.

### The mutable key

The nastier version. Put a student in a map, then change the field its hash is
computed from.

```java [MutableKey.java]
import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

public class MutableKey {

  static class Student {
    String roll;                              // not final: the mistake
    Student(String roll) { this.roll = roll; }
    @Override public boolean equals(Object o) {
      return o instanceof Student other && roll.equals(other.roll);
    }
    @Override public int hashCode() { return Objects.hash(roll); }
  }

  public static void main(String[] args) {
    Map<Student, String> hostel = new HashMap<>();
    Student s = new Student("2026CSE0184");
    hostel.put(s, "Block B, Room 12");

    s.roll = "2026CSE0999";                   // roll number corrected after admission

    System.out.println("containsKey: " + hostel.containsKey(s));
    System.out.println("size:        " + hostel.size());
    for (Student key : hostel.keySet()) {
      System.out.println("iterating finds: " + key.roll);
    }
  }
}
```

```text [Output]
containsKey: false
size:        1
iterating finds: 2026CSE0999
```

The entry is in the map, `containsKey` says no, and iterating finds it. It is
sitting in the bucket its **old** hash chose, and every lookup computes the
**new** hash and looks in a different bucket. Map keys should be immutable, and
that is why `String`, `Integer` and records are the keys you see everywhere.

### `HashMap`, `LinkedHashMap`, `TreeMap`

Three that get confused, and the difference is about order.

| | `HashMap` | `LinkedHashMap` | `TreeMap` |
| --- | --- | --- | --- |
| get / put | O(1) average | O(1) average | O(log n) |
| Iteration order | **None. Do not rely on it.** | Insertion order | Sorted by key |
| Needs | `equals` + `hashCode` | Same | `Comparable` or a `Comparator` |
| Use when | You only need lookup | Order of insertion matters, or an LRU cache | Sorted keys, ranges, floor and ceiling |

`HashSet` is a `HashMap` where every value is the same dummy object. That is not
an analogy; it is how Java implements it. Everything above applies to sets: same
contract, same buckets, same O(1).

### Complexity

| Operation | Average | Worst |
| --- | --- | --- |
| `put`, `get`, `remove`, `containsKey` | **O(1)** | O(log n) since Java 8, O(n) before |
| Resize | O(n), rare | |
| `containsValue` | O(n), it scans everything | O(n) |
| Iterate all entries | O(n + capacity) | |
| Space | O(n) | |

## Real use case

**A least-recently-used cache in a few lines.** The results portal keeps the 1,000
most recently viewed mark sheets in memory so repeat views do not hit the
database. `LinkedHashMap` with access order, plus one overridden method, is a
complete LRU cache.

```java [MarksheetCache.java]
import java.util.LinkedHashMap;
import java.util.Map;

public class MarksheetCache {

  static class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruCache(int capacity) {
      super(16, 0.75f, true);                  // true = order by access, not insertion
      this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
      return size() > capacity;                // evict the least recently used
    }
  }

  public static void main(String[] args) {
    LruCache<String, String> cache = new LruCache<>(3);
    cache.put("1003", "Kabir: 64");
    cache.put("1007", "Riya: 78");
    cache.put("1019", "Meera: 91");
    cache.get("1003");                          // Kabir viewed again
    cache.put("1031", "Arjun: 78");             // over capacity: evicts 1007
    System.out.println(cache.keySet());
  }
}
```

```text [Output]
[1019, 1003, 1031]
```

Riya's sheet (1007) was the least recently touched, so it went. "Design an LRU
cache" is a common product-company question, and this is the answer to give
before the interviewer asks you to build it by hand from a `HashMap` and a
doubly linked list.

## What confuses people here

**Thinking O(1) means instant.** It means the cost does not grow with the number
of entries. Hashing a long string key still reads every character of it, and a
`HashMap` of five entries can be slower than scanning an array of five.

::warning{icon="i-lucide-alert-triangle"}
**Relying on `HashMap` iteration order.** It often looks sorted for small integer
keys, because small `Integer` hash codes are the numbers themselves. Add a few
more entries, or change Java version, and the order changes. If you print a
`HashMap` and it happens to come out in order, that is a coincidence, not a
feature. Use `LinkedHashMap` or `TreeMap` when order matters.
::

## Interview questions

::accordion
  :::accordion-item{label="1. How does a HashMap work internally?" icon="i-lucide-message-circle"}
  An array of buckets. `put` computes `hashCode()`, spreads it, reduces it to a
  bucket index, and stores the entry there; `get` does the same and compares keys
  in that bucket with `equals`. Collisions are chained in a list, which becomes a
  red-black tree above eight entries. When size exceeds capacity × 0.75, the
  array doubles and every entry is rehashed. Average O(1), worst O(log n).
  :::

  :::accordion-item{label="2. What is the equals and hashCode contract?" icon="i-lucide-message-circle"}
  Equal objects must have equal hash codes. Unequal objects may share one. Break
  it and a map puts two equal keys in different buckets: `get` returns `null`
  for a key that is in the map, and a `HashSet` holds "duplicates". Always
  override both, on the same fields.
  :::

  :::accordion-item{label="3. Can a HashMap have a null key?" icon="i-lucide-message-circle"}
  Yes, one, stored in bucket 0 (its hash is treated as 0), and any number of null
  values. `Hashtable` and `ConcurrentHashMap` allow neither, because in a
  concurrent map `get` returning `null` would be ambiguous: absent, or present
  with null?
  :::

  :::accordion-item{label="4. Why should map keys be immutable?" icon="i-lucide-message-circle"}
  The bucket is chosen from the hash at insertion time. If a field used in
  `hashCode` changes later, lookups compute a new hash and search the wrong
  bucket, so the entry becomes unreachable by key while still taking up space.
  `String`, `Integer` and records are safe keys for that reason.
  :::

  :::accordion-item{label="5. HashMap or TreeMap?" icon="i-lucide-message-circle"}
  `HashMap` for pure lookup, O(1). `TreeMap` when you need sorted keys, ranges
  (`subMap(60, 80)`) or nearest matches (`floorKey`, `ceilingKey`), at O(log n).
  It is the same trade a database makes between a hash index and a B-tree index,
  which you will meet in the DBMS track.
  :::

  :::accordion-item{label="6. What changed in HashMap in Java 8?" icon="i-lucide-message-circle"}
  Buckets with more than eight entries (in a table of at least 64 buckets) turn
  into balanced trees, so a flood of colliding keys costs O(log n) per lookup
  instead of O(n). This was partly a security fix: attackers had sent crafted
  keys that all collided, to slow servers down.
  :::
::
