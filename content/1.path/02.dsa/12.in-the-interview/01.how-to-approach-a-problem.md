The first five minutes decide it. This page answers what to do in them, and in
the forty minutes after, so that a problem you half-know still ends in working
code and an interviewer who wants to hire you.

## Why it matters

In my early walk-ins I lost coding rounds I could have passed, and not because I
did not know the technique. I heard the question, panicked, started typing the
first idea, found it was wrong at minute twenty, and had nothing left. Years
later, preparing for the switch that ended at 15.5 LPA, I learned that the
interviewer is scoring four things, and the code is only one of them:

| What they score | What it looks like |
| --- | --- |
| **Problem solving** | You explored the problem before coding and found a better approach yourself |
| **Communication** | They always knew what you were thinking |
| **Coding** | Clean, correct Java, sensible names, no fighting the language |
| **Testing** | You found your own bugs before they did |

A candidate who talks through a brute force, improves it, and tests it often
beats a candidate who silently types the optimal answer. The first one shows the
interviewer how they will work on a team.

## What to do

::steps
### Clarify (2–3 minutes)

Repeat the problem in your own words. Then ask about the input:

- How big can n be? (This tells you the target complexity; see the constraints
  table in "Space and reading the constraints".)
- Can the array be empty? Contain negatives? Duplicates?
- Is it sorted? Can I modify it?
- What should I return if there is no answer: `-1`, `null`, an empty list?

### Work an example by hand (2 minutes)

Write a small input and the expected output. Then one awkward input: empty, one
element, all the same, all negative. Agree the answers with the interviewer
before coding.

### Say the brute force (2 minutes)

"The simplest thing that works is to try every pair, which is O(n²)." Say it even
if you already see something better. It proves you can solve it, gives you a
fallback, and gives you something to improve.

### Optimise (5–10 minutes)

Ask what the brute force repeats. Then walk the checklist below, out loud.

### Dry run the idea, then code (15 minutes)

Trace your approach on the example before writing Java. Then code with real
names (`marks`, `rollNumber`, `left`, `right`), not `a`, `b`, `x`.

### Test (5 minutes)

Run the example through your code line by line, reading variables aloud. Then the
edge cases. Then state the time and space complexity.
::

### The optimisation checklist

| Ask yourself | If yes, try |
| --- | --- |
| Am I searching for something I have seen before? | A `HashSet` or `HashMap` |
| Is the input sorted, or would sorting help? | Binary search, two pointers |
| Am I recomputing sums over ranges? | Prefix sums |
| Is it about a contiguous stretch? | Sliding window |
| Am I looking for the k largest or smallest? | A heap (`PriorityQueue`) |
| Does the answer repeat subproblems? | Dynamic programming |
| Can I take the best choice now safely? | Greedy, with a counterexample hunt |
| Is it about connections or dependencies? | A graph, BFS or DFS |

### What to say when you are stuck

- "Let me go back to the brute force and see what it repeats."
- "Let me try a smaller example." (Then do it on paper, in front of them.)
- "I am thinking about whether sorting helps here."
- "Can I have a hint on which direction to explore?" Asking once costs far less
  than ten minutes of silence.

## A worked example

**The question:** "Given the marks of students in a class and a number `target`,
return the roll numbers (indices) of two students whose marks add up to target."

**Clarify.** Me: "Can marks repeat? Is there always exactly one answer? Can I use
the same student twice?" Them: "Marks can repeat, exactly one answer, not the
same student."

**Example.** `marks = [45, 72, 31, 55]`, `target = 100` → `[0, 3]` (45 + 55).

**Brute force.** "Every pair: two loops, O(n²) time, O(1) space."

**Optimise.** "For each student I am searching for `target - marks[i]` among the
ones before. Searching for something seen before is a `HashMap` from mark to
index. One pass, O(n) time, O(n) space."

**Code.**

```java [PairOfMarks.java]
import java.util.*;

public class PairOfMarks {
  static int[] pairWithTotal(int[] marks, int target) {
    Map<Integer, Integer> seenAt = new HashMap<>();     // mark → roll number
    for (int roll = 0; roll < marks.length; roll++) {
      int needed = target - marks[roll];
      if (seenAt.containsKey(needed)) {
        return new int[]{seenAt.get(needed), roll};
      }
      seenAt.put(marks[roll], roll);
    }
    return new int[]{-1, -1};                           // agreed in clarify
  }

  public static void main(String[] args) {
    System.out.println(Arrays.toString(pairWithTotal(new int[]{45, 72, 31, 55}, 100)));
    System.out.println(Arrays.toString(pairWithTotal(new int[]{50, 50}, 100)));
    System.out.println(Arrays.toString(pairWithTotal(new int[]{70}, 100)));
    System.out.println(Arrays.toString(pairWithTotal(new int[]{}, 100)));
  }
}
```

```text [Output]
[0, 3]
[0, 1]
[-1, -1]
[-1, -1]
```

**Test.** I dry run `[45, 72, 31, 55]` aloud: roll 0 needs 55, not seen, store
45. Roll 1 needs 28, not seen, store 72. Roll 2 needs 69, not seen, store 31.
Roll 3 needs 45, **seen at 0**, return `[0, 3]`. Then the edge cases, each a line
of the output above: two equal marks (`[50, 50]` works because the check happens
before the `put`, so a student is never paired with themselves), one student, no
students.

Last, the complexity, said without being asked: O(n) time, one pass with O(1)
map operations on average; O(n) space for the map.

::tip
While dry running, I once found that my own example had two valid pairs (I had
written 28 where I meant 31), which broke the "exactly one answer" rule we had
agreed. Saying "my example is wrong, here is why" out loud is not a failure. It
is the testing skill the interviewer is scoring.
::

## Common mistakes

::compare{caption="Two candidates, same problem"}
  :::compare-side{label="Silent coder" verdict="wrong"}
  Reads the question, types for twenty minutes, says "done". The interviewer
  has no idea whether they understood, and when there is a bug they have no
  thinking to give partial credit for.
  :::
  :::compare-side{label="Narrator" verdict="right"}
  Clarifies, states the brute force, improves it with a reason, codes, dry runs,
  finds their own bug. Even an incomplete solution scores well.
  :::
::

- **Coding before agreeing the approach.** Ask "does this approach sound good
  before I code it?" It costs five seconds and saves twenty minutes.
- **Skipping edge cases.** Empty input, one element, duplicates, negatives,
  integer overflow (`int` tops out at about 2.1 billion).
- **Guessing the complexity.** Count it from the code, loop by loop.
- **Arguing with a hint.** A hint is the interviewer helping you. Take it.

## How to practise

- **Two problems a day**, one from a pattern you have done and one new, for 8 to
  10 weeks. That is roughly 120 to 140 problems, which covers the fifty on the
  must-do page with room for repeats.
- **Time-box**: 25 minutes for an easy, 40 for a medium. If you are stuck at the
  limit, read the approach (not the code), close it, and write it yourself.
- **Say it out loud** while practising, alone in your room if you must. When I
  was in a PG in BTM Layout this was embarrassing with roommates around. Do it
  anyway; talking while coding is a skill, and it only comes from practice.
- **Mock interviews** with a friend once a week: one of you asks, one solves,
  swap.
- **Revisit** any problem you needed help with after three days and again after
  a week.
