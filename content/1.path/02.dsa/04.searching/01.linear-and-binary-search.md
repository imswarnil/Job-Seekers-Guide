Looking up one roll number in a sorted list of 40,000 takes at most sixteen
checks, not 40,000, and the reason is that a sorted list lets you throw half of
it away with every look. Backtracking tried everything; this lesson is about
trying almost nothing.

## Why this matters in a job

Because "implement binary search" is a real interview question at service and
product companies alike, and it has a famous bug in it that most candidates
write. Because a whole family of medium problems (first occurrence, rotated
array, minimum capacity) are binary search wearing a disguise. And because the
same halving idea is how your database's index finds a row in a table of ten
million.

## Two ways to find a name

Think of the attendance register on the first day of term. If the names are in
the order students walked in, you read from the top until you find the one you
want. That is **linear search**: look at every entry, one after another.

Now think of a printed dictionary. You never read it from page one. You open the
middle, see that "marks" comes after "lecture", and ignore the whole first half.
That is **binary search**: only possible because the dictionary is sorted, and
fast because every look halves what is left.

| Sorted entries | Linear search, worst case | Binary search, worst case |
| --- | --- | --- |
| 1,000 | 1,000 | 10 |
| 40,000 | 40,000 | 16 |
| 1,000,000 | 1,000,000 | 20 |
| 1,000,000,000 | 1,000,000,000 | 30 |

A thousand times more data costs ten more steps. That is what **O(log n)**
buys: log₂ of a number is how many times you can halve it before one is left.

## How it works

### Linear search

Nothing clever. Walk the array, return the index when you find it, return `-1`
when you run out. `-1` is the convention for "not found" because it can never be
a real index.

```java [LinearSearch.java]
public class LinearSearch {

  static int indexOf(int[] rollNumbers, int target) {
    for (int i = 0; i < rollNumbers.length; i++) {
      if (rollNumbers[i] == target) {
        return i;
      }
    }
    return -1;
  }

  public static void main(String[] args) {
    int[] arrivals = {1042, 1007, 1019, 1003, 1031};   // order they walked in
    System.out.println("1019 is at index " + indexOf(arrivals, 1019));
    System.out.println("1050 is at index " + indexOf(arrivals, 1050));
  }
}
```

```text [Output]
1019 is at index 2
1050 is at index -1
```

It works on any array, sorted or not, and that is its only advantage. It is the
right choice for a list of thirty names you search once.

### Binary search

Keep two markers, `low` and `high`, around the part of the array that could
still contain the target. Look at the middle. If it is too small, the answer is
to the right; if too big, to the left. Repeat until found or until the markers
cross.

```java [BinarySearch.java]
public class BinarySearch {

  static int indexOf(int[] sortedRolls, int target) {
    int low = 0;
    int high = sortedRolls.length - 1;

    while (low <= high) {
      int mid = low + (high - low) / 2;

      if (sortedRolls[mid] == target) {
        return mid;
      } else if (sortedRolls[mid] < target) {
        low = mid + 1;          // the answer can only be to the right
      } else {
        high = mid - 1;         // the answer can only be to the left
      }
    }
    return -1;
  }

  public static void main(String[] args) {
    int[] rolls = {1003, 1007, 1019, 1031, 1042, 1055, 1068, 1071, 1090};
    System.out.println("1042 -> " + indexOf(rolls, 1042));
    System.out.println("1003 -> " + indexOf(rolls, 1003));
    System.out.println("1090 -> " + indexOf(rolls, 1090));
    System.out.println("1050 -> " + indexOf(rolls, 1050));
  }
}
```

```text [Output]
1042 -> 4
1003 -> 0
1090 -> 8
1050 -> -1
```

I test the first element, the last element and a missing one every time. Those
three are where binary search bugs live, and an interviewer will ask you to try
them if you do not.

### The three bugs, one line each

::code-trace{caption="Three lines that are each a bug in somebody's version."}
```java [BinarySearch.java]
while (low <= high) {
  int mid = low + (high - low) / 2;
  else if (sortedRolls[mid] < target)  low  = mid + 1;
```

  :::code-trace-step{lines="1" caption="`<=` not `<`. With `<`, a one-element range is never examined, so the search misses any target sitting at that final position. This is the most common binary search bug."}
  :::
  :::code-trace-step{lines="2" caption="`low + (high - low) / 2` not `(low + high) / 2`. On a very large array the sum overflows int and goes negative, producing a negative index. This bug sat in the JDK's own binary search for nine years."}
  :::
  :::code-trace-step{lines="3" caption="`mid + 1` and `mid - 1`, not `mid`. Setting a bound to `mid` can leave the range the same size when it is down to two elements, and the loop never ends."}
  :::
::

::warning{icon="i-lucide-alert-triangle"}
Joshua Bloch, who wrote much of the Java collections library, published a note in
2006 titled "Nearly All Binary Searches Are Broken", about the overflow bug. If
an interviewer asks you to write binary search, narrate the three boundary
decisions above out loud as you type them. That narration is the answer they are
listening for.
::

### The recursive version

Some interviewers ask for it to check that you understand recursion from the
previous chapter. Same logic, and the range shrinks through the parameters.

```java [RecursiveBinarySearch.java]
public class RecursiveBinarySearch {

  static int search(int[] a, int target, int low, int high) {
    if (low > high) {
      return -1;                          // base case: nothing left to search
    }
    int mid = low + (high - low) / 2;
    if (a[mid] == target) return mid;
    if (a[mid] < target) return search(a, target, mid + 1, high);
    return search(a, target, low, mid - 1);
  }

  public static void main(String[] args) {
    int[] marks = {35, 41, 48, 55, 62, 70, 78, 84, 91};
    System.out.println("78 found at " + search(marks, 78, 0, marks.length - 1));
    System.out.println("50 found at " + search(marks, 50, 0, marks.length - 1));
  }
}
```

```text [Output]
78 found at 6
50 found at -1
```

### Complexity

| | Time (worst) | Time (best) | Extra space |
| --- | --- | --- | --- |
| Linear search | O(n) | O(1) | O(1) |
| Binary search, iterative | O(log n) | O(1) | O(1) |
| Binary search, recursive | O(log n) | O(1) | O(log n), the call stack |

Say the space difference unprompted when you write the recursive one. The
iterative version is what you would ship.

## Real use case

Java has binary search built in, and in real code you call it rather than
writing it: `Arrays.binarySearch` for arrays and `Collections.binarySearch` for
sorted lists.

```java [ResultLookup.java]
import java.util.Arrays;

public class ResultLookup {
  public static void main(String[] args) {
    int[] passedRolls = {1003, 1007, 1019, 1031, 1042, 1055};

    int found = Arrays.binarySearch(passedRolls, 1031);
    int missing = Arrays.binarySearch(passedRolls, 1040);

    System.out.println("1031: " + found);
    System.out.println("1040: " + missing);
    System.out.println("1040 would be inserted at " + (-missing - 1));
  }
}
```

```text [Output]
1031: 3
1040: -5
1040 would be inserted at 4
```

Note the second line. `Arrays.binarySearch` does not return `-1` for a missing
value. It returns `-(insertionPoint) - 1`, which tells you where the value
*would* go. Checking `== -1` on its result is a real bug I have seen in code
review, because it only works when the missing value belongs at index 0.

::real-life{title="The results page on declaration day" source="A university exam cell"}
On result day the exam cell publishes a sorted file of every roll number that
passed. Forty thousand students each type their roll number and the portal checks
it against that list. A linear scan is 40,000 comparisons per student, which is
1.6 billion comparisons across the morning. Binary search is sixteen per student.
The same halving is what the database index under a real portal does, and it is
the reason the page loads in under a second while everybody in the state is
refreshing it.
::

## What confuses people here

**Binary search needs sorted data, and nothing checks that for you.** Run it on
an unsorted array and it returns a wrong answer confidently, with no exception.

```java [UnsortedTrap.java]
import java.util.Arrays;

public class UnsortedTrap {
  public static void main(String[] args) {
    int[] marks = {78, 12, 91, 45, 60};              // NOT sorted
    System.out.println(Arrays.binarySearch(marks, 45));
  }
}
```

```text [Output]
-1
```

45 is sitting at index 3 and binary search says it is not there. If you have to
sort first, that costs O(n log n), which is worse than a single linear scan. Sort
once and search many times, or do not sort at all.

::tip
The second confusion: thinking binary search is only for arrays. It works on
anything where you can ask "is the answer to the left or to the right of here?"
and get a yes or no. The next lesson uses exactly that to search for the smallest
answer that works, where there is no array at all.
::

## Interview questions

::accordion
  :::accordion-item{label="1. Why is binary search O(log n)?" icon="i-lucide-message-circle"}
  Each comparison halves the range that can still hold the answer. Starting from
  n, after k steps n / 2ᵏ remain, and the search ends when that is 1, so
  k = log₂ n. For 1,000,000 elements that is 20 comparisons.
  :::

  :::accordion-item{label="2. Why write low + (high - low) / 2?" icon="i-lucide-message-circle"}
  Because `low + high` can exceed `Integer.MAX_VALUE` (2,147,483,647) on a huge
  array and wrap to a negative number, giving a negative `mid` and an
  `ArrayIndexOutOfBoundsException`. `high - low` never overflows, so
  `low + (high - low) / 2` is always safe. `(low + high) >>> 1` also works, using
  an unsigned shift.
  :::

  :::accordion-item{label="3. When would you use linear search instead?" icon="i-lucide-message-circle"}
  When the data is unsorted and you search it once: sorting costs O(n log n), more
  than the O(n) scan. When the list is tiny (a department's ten courses). And when
  the data is a linked list, because binary search needs O(1) access to the
  middle, which a linked list cannot give.
  :::

  :::accordion-item{label="4. What does Arrays.binarySearch return for a missing key?" icon="i-lucide-message-circle"}
  `-(insertion point) - 1`, always negative. For `{10, 20, 30}` searching 25,
  the insertion point is 2, so it returns -3. Check `< 0`, never `== -1`.
  :::

  :::accordion-item{label="5. Can binary search work on a sorted linked list?" icon="i-lucide-message-circle"}
  It gives the right answer but loses the speed. Finding the middle of a linked
  list means walking to it, O(n), so the whole search becomes O(n) and is no
  better than linear search. This is why a sorted structure that must support
  fast search is a tree or an array, not a list.
  :::
::
