The first and last occurrence of a mark, and a sorted list that has been rotated,
both come from the same four lines of binary search with one decision changed.
The trick is to stop thinking "find the target" and start thinking "which half
can I safely throw away?".

## Why this matters in a job

Because exact-match binary search is almost never the question. The versions
that are asked, in online assessments and in the first DSA round at product
companies, are these: first and last position of an element, count of
occurrences, search in a rotated sorted array, minimum in a rotated array, and
"find the smallest capacity that works". In my own switch interviews, the rotated
array came up more often than plain binary search did.

## One question per half

Picture a sorted list of marks where 70 appears four times in a row. Plain
binary search stops at whichever 70 it lands on first, which could be any of the
four. To find the **first** 70, you do something that feels wrong: when you find
a 70, you write it down and **keep searching to the left**, because an earlier 70
might exist. For the **last** 70 you keep searching to the right.

## How it works

### First and last occurrence

One method with a flag keeps the two versions next to each other, so you can see
that exactly one line differs.

```java [FirstLast.java]
public class FirstLast {

  static int find(int[] marks, int target, boolean first) {
    int low = 0, high = marks.length - 1;
    int answer = -1;
    while (low <= high) {
      int mid = low + (high - low) / 2;
      if (marks[mid] == target) {
        answer = mid;                  // a candidate, not the end
        if (first) high = mid - 1;     // an earlier one may exist
        else       low = mid + 1;      // a later one may exist
      } else if (marks[mid] < target) {
        low = mid + 1;
      } else {
        high = mid - 1;
      }
    }
    return answer;
  }

  public static void main(String[] args) {
    int[] marks = {41, 55, 70, 70, 70, 70, 84, 92};
    int first = find(marks, 70, true);
    int last = find(marks, 70, false);
    System.out.println("First 70 at " + first);
    System.out.println("Last 70 at " + last);
    System.out.println("Students with 70: " + (last - first + 1));
    System.out.println("First 60 at " + find(marks, 60, true));
  }
}
```

```text [Output]
First 70 at 2
Last 70 at 5
Students with 70: 4
First 60 at -1
```

The third line is a free extra problem: **count occurrences** of a value in a
sorted array in O(log n) is `last - first + 1`. A linear count would be O(n),
and "can you do better than O(n)?" is the follow-up.

### Lower bound: the first mark at least the cutoff

"How many students scored below the cutoff of 60?" is the index of the first
mark that is at least 60. This version uses a half-open range, where `high` is
one past the last candidate. Three boundaries differ from the exact-match
version, and each one is deliberate.

```java [LowerBound.java]
public class LowerBound {

  static int firstAtLeast(int[] sorted, int cutoff) {
    int low = 0, high = sorted.length;        // length, not length - 1
    while (low < high) {                      // <, not <=
      int mid = low + (high - low) / 2;
      if (sorted[mid] < cutoff) low = mid + 1;
      else                      high = mid;   // mid itself may be the answer
    }
    return low;                               // may equal length: none qualify
  }

  public static void main(String[] args) {
    int[] marks = {28, 35, 41, 55, 60, 60, 72, 88};
    System.out.println("Below 60: " + firstAtLeast(marks, 60) + " students");
    System.out.println("Below 90: " + firstAtLeast(marks, 90) + " students");
    System.out.println("Below 10: " + firstAtLeast(marks, 10) + " students");
  }
}
```

```text [Output]
Below 60: 4 students
Below 90: 8 students
Below 10: 0 students
```

::tip
Hold one sentence in your head: **`low` is the first index that could still be
the answer and `high` is one past the last.** Every boundary in the code above
follows from that sentence. If you pick a convention and hold it, you stop
guessing between `<` and `<=`.
::

### Search in a rotated sorted array

A sorted list of roll numbers `{1003, 1007, 1019, 1031, 1042, 1055, 1068}` gets
rotated: somebody moved the first four to the end, giving
`{1042, 1055, 1068, 1003, 1007, 1019, 1031}`. It is no longer sorted, but at any
`mid`, **one of the two halves is still sorted**. Work out which, check whether
the target lies inside that sorted half, and throw away the other half.

::flow{numbered caption="The decision at every step"}
  :::flow-step{label="Is a[low..mid] sorted?" icon="i-lucide-scan"}
  It is if `a[low] <= a[mid]`. Otherwise the right half is the sorted one.
  :::
  :::flow-step{label="Is the target inside the sorted half?" icon="i-lucide-crosshair" highlight}
  Compare with both ends of that half. It is a plain range check.
  :::
  :::flow-step{label="Keep that half, or the other one" icon="i-lucide-scissors"}
  Inside means search there. Outside means it can only be in the other half.
  :::
::

```java [RotatedSearch.java]
public class RotatedSearch {

  static int search(int[] a, int target) {
    int low = 0, high = a.length - 1;
    while (low <= high) {
      int mid = low + (high - low) / 2;
      if (a[mid] == target) return mid;

      if (a[low] <= a[mid]) {                       // left half is sorted
        if (a[low] <= target && target < a[mid]) high = mid - 1;
        else low = mid + 1;
      } else {                                      // right half is sorted
        if (a[mid] < target && target <= a[high]) low = mid + 1;
        else high = mid - 1;
      }
    }
    return -1;
  }

  static int minimum(int[] a) {
    int low = 0, high = a.length - 1;
    while (low < high) {
      int mid = low + (high - low) / 2;
      if (a[mid] > a[high]) low = mid + 1;          // the drop is to the right
      else high = mid;                              // mid could be the minimum
    }
    return a[low];
  }

  public static void main(String[] args) {
    int[] rolls = {1042, 1055, 1068, 1003, 1007, 1019, 1031};
    System.out.println("1007 at " + search(rolls, 1007));
    System.out.println("1055 at " + search(rolls, 1055));
    System.out.println("1050 at " + search(rolls, 1050));
    System.out.println("Smallest roll: " + minimum(rolls));
  }
}
```

```text [Output]
1007 at 4
1055 at 1
1050 at -1
Smallest roll: 1003
```

The `minimum` method is the companion problem, "find the minimum in a rotated
sorted array". It compares with `a[high]` rather than `a[low]`, and that choice
is the whole problem: comparing with the right end tells you which side the
drop is on.

### Binary search on the answer

The version that surprises people: there is no array to search. Eight
departments have exam answer sheets to evaluate, `{120, 340, 200, 90, 410, 150,
260, 180}` sheets each, and three evaluators must each take a **consecutive**
group of departments. What is the smallest maximum load any evaluator carries?

The answer lies between 410 (someone must take the biggest department) and 1,750
(one person takes everything). For any guess, you can check in O(n) whether it is
possible. And if a load of 700 works, every load above 700 works too. That
yes/no switch is sorted, so you can binary search it.

```java [MinimumLoad.java]
public class MinimumLoad {

  static boolean possible(int[] sheets, int evaluators, int limit) {
    int used = 1, current = 0;
    for (int s : sheets) {
      if (current + s > limit) {      // start the next evaluator
        used++;
        current = 0;
      }
      current += s;
    }
    return used <= evaluators;
  }

  public static void main(String[] args) {
    int[] sheets = {120, 340, 200, 90, 410, 150, 260, 180};
    int low = 0, high = 0;
    for (int s : sheets) {
      low = Math.max(low, s);
      high += s;
    }
    while (low < high) {
      int mid = low + (high - low) / 2;
      if (possible(sheets, 3, mid)) high = mid;   // works, try smaller
      else low = mid + 1;                          // too small
    }
    System.out.println("Smallest possible maximum load: " + low);
  }
}
```

```text [Output]
Smallest possible maximum load: 660
```

The split behind it is 120 + 340 + 200 = 660 for the first evaluator, 90 + 410 =
500 for the second and 150 + 260 + 180 = 590 for the third. About eleven checks of
O(n) each found it, out of 1,341 possible answers.

This pattern is behind "allocate minimum pages", "ship packages within D days",
"Koko eating bananas" and "aggressive cows" on practice sites. Recognise the
shape: **a range of possible answers, and a check that flips from no to yes
exactly once.**

### Complexity

| Problem | Time | Space |
| --- | --- | --- |
| First / last occurrence | O(log n) | O(1) |
| Count of a value | O(log n), two searches | O(1) |
| Lower bound | O(log n) | O(1) |
| Search in rotated array | O(log n) | O(1) |
| Minimum in rotated array | O(log n) | O(1) |
| Binary search on the answer | O(n log S), S = sum of the range | O(1) |

## Real use case

`TreeMap` gives you lower bound and its relatives as methods, because it is a
sorted structure underneath. Grade boundaries are the classic use.

```java [GradeBands.java]
import java.util.TreeMap;

public class GradeBands {
  public static void main(String[] args) {
    TreeMap<Integer, String> bands = new TreeMap<>();
    bands.put(0, "F");
    bands.put(40, "D");
    bands.put(55, "C");
    bands.put(70, "B");
    bands.put(85, "A");

    for (int mark : new int[]{38, 55, 69, 91}) {
      System.out.println(mark + " -> " + bands.floorEntry(mark).getValue());
    }
  }
}
```

```text [Output]
38 -> F
55 -> C
69 -> C
91 -> A
```

`floorEntry(69)` is "the largest key at most 69", which is the mirror image of
the lower bound you wrote above. It is O(log n), and it replaces a chain of
five `if` statements that someone will one day get wrong when the boundaries
change.

## What confuses people here

**Mixing the two conventions.** Closed range (`high = length - 1`, `low <=
high`, `high = mid - 1`) and half-open range (`high = length`, `low < high`,
`high = mid`) are both correct. Taking the loop condition from one and the update
from the other gives an infinite loop or a missed element. Pick one per method
and do not mix.

::warning{icon="i-lucide-alert-triangle"}
**Duplicates break the rotated-array search.** With `{70, 70, 70, 10, 70}`,
`a[low]`, `a[mid]` and `a[high]` are all 70 and you cannot tell which half is
sorted. The usual fix is to shrink both ends by one (`low++`, `high--`) when all
three are equal, which makes the worst case O(n). If the interviewer's array
could contain duplicates, ask, and say this before they do.
::

## Interview questions

::accordion
  :::accordion-item{label="1. Find the first and last position of a value in a sorted array" icon="i-lucide-message-circle"}
  Two binary searches. When the middle equals the target, record it and keep
  going: left for the first, right for the last. O(log n) each. The brute force,
  finding any match and walking outwards, is O(n) when every element is equal,
  so say why you did not do that.
  :::

  :::accordion-item{label="2. Search in a rotated sorted array" icon="i-lucide-message-circle"}
  At every mid, one half is sorted (`a[low] <= a[mid]` means the left). If the
  target lies inside the sorted half's range, search there, otherwise search the
  other half. O(log n), O(1) space. Mention the duplicates case.
  :::

  :::accordion-item{label="3. How many times has a sorted array been rotated?" icon="i-lucide-message-circle"}
  The index of the minimum element. For `{1042, 1055, 1068, 1003, 1007}` the
  minimum 1003 is at index 3, so it was rotated 3 times. Use the
  minimum-in-rotated-array search: compare `a[mid]` with `a[high]`.
  :::

  :::accordion-item{label="4. Find the square root of n, rounded down, without Math.sqrt" icon="i-lucide-message-circle"}
  Binary search on the answer between 0 and n: the check "mid × mid <= n" is
  true up to the answer and false after it. Use `long` for `mid * mid` or it
  overflows past 46,340.

  ```java
  static int sqrt(int n) {
    long low = 0, high = n;
    while (low < high) {
      long mid = (low + high + 1) / 2;       // round up, or it loops forever
      if (mid * mid <= n) low = mid;
      else high = mid - 1;
    }
    return (int) low;
  }
  ```
  :::

  :::accordion-item{label="5. How do you recognise that a problem wants binary search?" icon="i-lucide-message-circle"}
  Three signals: the input is sorted (or rotated sorted); the constraint says
  n up to 10⁵ or more and asks for better than O(n); or the question asks for the
  "minimum maximum" or "smallest value that works" and checking one guess is
  easy. The last one is binary search on the answer.
  :::
::
