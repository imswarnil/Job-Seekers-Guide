Both clerks were inside a transaction, both transactions were correct, and the
seat was allotted twice. Isolation is a dial, not a switch, and where it is set
by default surprises people.

## Why this matters in a job

Because this is the single most common source of "it works but the numbers are
wrong" in systems that book, allot, reserve or count anything. It is also a
favourite interview topic precisely because it separates people who have read
about transactions from people who have been bitten.

## The four bugs, in order of nastiness

::feature-list{columns="2"}
  :::feature{icon="i-lucide-eye" title="Dirty read"}
  You read a change another transaction has made and not committed. It then rolls
  back, and you acted on a number that never existed.
  :::
  :::feature{icon="i-lucide-repeat" title="Non-repeatable read"}
  You read a row twice in one transaction and get different values, because
  somebody committed a change in between.
  :::
  :::feature{icon="i-lucide-ghost" title="Phantom read"}
  You run the same `WHERE` twice and get a different number of **rows**, because
  somebody inserted one that matches.
  :::
  :::feature{icon="i-lucide-pen-line" title="Lost update"}
  ⚠️ Two transactions read the same value, both compute from it, both write. One
  write silently overwrites the other. **This is the seat.**
  :::
::

## The four levels, and what each still allows

| Level | Dirty read | Non-repeatable | Phantom | Lost update |
| --- | --- | --- | --- | --- |
| Read uncommitted | possible | possible | possible | possible |
| **Read committed** ← PostgreSQL, Oracle, SQL Server default | no | possible | possible | **possible** |
| **Repeatable read** ← MySQL InnoDB default | no | no | mostly prevented | **possible** |
| Serializable | no | no | no | no |

Read the two default rows again. Whichever database you use, **the default level
still allows a lost update**, and that is not a flaw. Serializable is expensive,
and most transactions do not need it.

Nothing was dirty, nothing was rolled back, both transactions committed
successfully, and the university has sold a seat twice.

## Three fixes, and which one to use

### 1. Do the arithmetic in the database

The cheapest fix, and it removes the read entirely.

```sql [fix1.sql]
UPDATE Programme
   SET seats_left = seats_left - 1
 WHERE programme_id = 3
   AND seats_left > 0;
```

```text [Output]
UPDATE 0          -- ← zero rows. Somebody else got the last one.
```

The database locks the row for the duration of the `UPDATE`, so the two
statements are serialised by the engine. **Check the row count**: `UPDATE 0`
means you did not get it, and that check is the whole fix. Application code that
ignores the affected-row count throws away the answer.

### 2. Lock the row while you think

When you genuinely need to read, decide, and then write.

```sql [fix2.sql]
BEGIN;
  SELECT seats_left FROM Programme
   WHERE programme_id = 3
     FOR UPDATE;                 -- ← B blocks here until A commits

  -- now decide, in application code, safely
  UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 3;
  INSERT INTO SeatAllotment (...) VALUES (...);
COMMIT;
```

`FOR UPDATE` takes a write lock on the selected rows. Clerk B's `SELECT` waits
rather than returning a stale 1. This is **pessimistic locking**: assume a clash
and prevent it.

### 3. Detect the clash instead of preventing it

```sql [fix3.sql]
UPDATE Programme
   SET seats_left = seats_left - 1,
       version     = version + 1
 WHERE programme_id = 3
   AND version = 47;            -- the version I read a moment ago
```

If somebody else changed the row, `version` is no longer 47, zero rows update,
and you retry with fresh data. This is **optimistic locking**: assume no clash,
notice if you were wrong. It is what JPA's `@Version` does.

::pros-cons
---
title: Pessimistic or optimistic
pros:
  - Pessimistic (FOR UPDATE) is simple and correct, and right when clashes are common
  - Optimistic (version column) holds no locks, so it scales far better when clashes are rare
  - Both are vastly better than raising the isolation level everywhere
cons:
  - Pessimistic locks block other people, and a long transaction blocks them for a long time
  - Optimistic needs retry logic, and the retry must re-read rather than resubmit the old values
  - Neither helps if the check is in application code and the write does not carry it
---
::

## The fix that is not a fix

::warning{icon="i-lucide-alert-triangle"}
`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` does prevent this, and reaching
for it first is usually wrong. It makes every transaction more expensive, and
under PostgreSQL it does not block. It aborts one transaction with a
serialisation failure, so **you still need retry logic**, which is what
optimistic locking gives you with far less overhead. Use it where the
interleaving is genuinely too complex to reason about, not as a default.
::

## The real-world version

::real-life{title="Where I have actually seen this" source="A seat allotment, and everybody else's booking system"}
Counter-intuitively, the bug almost never appears as "two clerks clicked at once".
It appears when somebody double-clicks a submit button, or when a mobile client
retries after a timeout, or when an import runs twice. All three produce two
simultaneous identical requests, which is exactly the interleaving above, and all
three are far more common than two humans racing.

Which is why the best fix is usually a `UNIQUE` constraint as well: one allotment
per applicant per programme, enforced by the schema. The second insert fails with
a constraint violation rather than succeeding, and you have defence that does not
depend on anybody remembering the locking.
::

## What you can do now

You can name your database's default isolation level and the bug it allows, and
you can choose between three real fixes with a reason.

## Your turn

For each, say which fix you would use.

1. Allotting one of sixty seats, during a two-day admission window with heavy
   traffic.
2. A registrar editing an applicant's details on a form, where two staff rarely
   touch the same applicant.
3. Incrementing a counter of total applications received.
4. Generating the next receipt number, which must have no gaps.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1. Conditional update plus a `UNIQUE` constraint.** `WHERE seats_left > 0`,
  check the row count, and a unique index on (applicant, programme) as the
  backstop. Clashes are common here, so avoid holding locks across a user's
  thinking time.

  **2. Optimistic, with a version column.** Two staff rarely clash, so locking a
  row for the minutes somebody spends on a form would be terrible. When they do
  clash, the second save fails and you tell them the record changed, which is
  the correct behaviour anyway, rather than silently discarding somebody's edit.

  **3. Do the arithmetic in the database**: `SET total = total + 1`. Never read,
  add in Java, and write back. If the counter is very hot, the better answer is
  not to keep a counter at all and `COUNT(*)` with an index, or maintain it in a
  separate summary table updated in batches.

  **4. A database sequence, and accept that it will have gaps**: a rolled-back
  transaction consumes a value. If gaps are genuinely forbidden, which for legal
  receipts they sometimes are, you need a single row you lock and increment, and
  you have deliberately made that the bottleneck for every payment. Knowing that
  trade is the answer; pretending sequences are gapless is the trap.
  :::
::

## The interview question this answers

**"How do you handle concurrent updates to the same row?"**

Name the bug, lost update, and say that the default isolation level of every
major database still allows it, which immediately separates you from the
candidate who answers "use a transaction". Then the three fixes: arithmetic in a
single conditional `UPDATE` with the row count checked, pessimistic `FOR UPDATE`
when clashes are common, optimistic versioning when they are rare. Then the
closer that sounds like experience: a `UNIQUE` constraint as well, because the
real cause is usually a double-click or a retried request rather than two people.
