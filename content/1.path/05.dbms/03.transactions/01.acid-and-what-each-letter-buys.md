Two clerks, sixty seats, and a count that went down by one. The fix is a
**transaction**, and the four properties it gives you are the most quoted
acronym in this subject and the least understood.

So: four letters, each shown by the thing that happens without it.

## Why this matters in a job

Because the most damaging bugs in any system that handles money or records are
transaction bugs. They do not crash. They produce a database that is quietly
wrong, and nobody notices until an audit.

## A transaction is a bracket

```sql [payment.sql]
BEGIN;
  UPDATE FeeAccount
     SET balance_paise = balance_paise - 4500000
   WHERE applicant_id = 4182;

  INSERT INTO FeePayment (application_id, receipt_number, amount_paise, paid_on)
  VALUES (9001, 'RCP-2026-4182', 4500000, CURRENT_DATE);
COMMIT;
```

Everything between `BEGIN` and `COMMIT` happens as one indivisible thing. If the
server loses power between the two statements, neither happened.

## A — Atomicity: all of it, or none

::compare{caption="The fee payment, with and without the bracket."}
  :::compare-side{label="Two separate statements" verdict="wrong"}
  The balance is reduced. The process is killed before the `INSERT`. The
  applicant has paid ₹45,000 and there is no receipt, no record, and no way to
  prove it happened. Money has vanished into a gap between two statements.
  :::
  :::compare-side{label="One transaction" verdict="right"}
  The same crash rolls back the balance change. The applicant has not paid and
  there is no receipt. Consistent, recoverable, and obviously wrong to a human
  rather than silently wrong to everybody.
  :::
::

::pull-quote
Atomicity does not mean nothing goes wrong. It means the database never ends up
in a state that is half of something.
::

## C — Consistency: the rules hold at both ends

Every constraint you declared is true before the transaction and true after it. A
transaction that would leave a foreign key pointing at nothing, or a score of
150, is rejected in its entirety.

This is the letter people struggle to define, and the honest framing is that it
is not a separate mechanism: it is the promise that atomicity, isolation and your
constraints together never leave the database in a state your schema forbids.

## I — Isolation: other people do not see your half-finished work

The one that matters most in practice and has a whole lesson of its own next.

```sql [session-a.sql]
BEGIN;
  UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 3;
  -- Another clerk querying right now sees the OLD value, not this uncommitted one.
COMMIT;
```

Without isolation, clerk B reads a number that may never become true, because A
might roll back.

## D — Durability: committed means written

Once `COMMIT` returns, the change survives the machine losing power one
millisecond later. This is not achieved by writing the data to its final place —
that is too slow — but by writing a **log** record first and flushing it to disk.
On restart the database replays the log.

::side-note{kind="go-deeper"}
That is the write-ahead log, and it is why a database can be both fast and
durable: sequential appends to a log are enormously faster than scattered writes
to data pages, so the commit waits for a fast operation and the slow one happens
later. It is also what replication and point-in-time recovery are built on. If
somebody asks "how is durability achieved without writing everything
immediately", the write-ahead log is the answer.
::

## Watch atomicity work

```sql [transfer.sql]
BEGIN;
  UPDATE FeeAccount SET balance_paise = balance_paise - 4500000 WHERE applicant_id = 4182;
  UPDATE FeeAccount SET balance_paise = balance_paise + 4500000 WHERE applicant_id = 9999;
COMMIT;
```

```text [Output]
ERROR:  new row for relation "feeaccount" violates check constraint "balance_non_negative"
ROLLBACK
```

Applicant 4182 did not have the money. The first statement succeeded, the second
never ran, and the whole thing was undone. The balance is exactly what it was
before. Nobody had to write cleanup code.

## The part beginners get wrong

A transaction in application code is not the `BEGIN` you forgot to write. It is
usually a framework annotation, and the mistake is putting it in the wrong place.

```java [FeeService.java]
// WRONG: three separate transactions. A crash after the second leaves a payment
// recorded with no receipt and no audit entry.
public void payFee(long applicationId, long paise) {
  accounts.debit(applicationId, paise);      // transaction 1
  payments.record(applicationId, paise);     // transaction 2
  audit.record(applicationId, "FEE_PAID");   // transaction 3
}
```

```java [FeeService.java]
// RIGHT: one bracket around the whole business operation.
@Transactional
public void payFee(long applicationId, long paise) {
  accounts.debit(applicationId, paise);
  payments.record(applicationId, paise);
  audit.record(applicationId, "FEE_PAID");
}
```

::warning{icon="i-lucide-alert-triangle"}
Never call an external service inside a transaction. Sending the confirmation
email inside that bracket means the email can be sent and the transaction rolled
back afterwards, so the applicant has a receipt for a payment that did not
happen. It also holds database locks for as long as the mail server takes, which
on a bad day is thirty seconds. Commit first, then send.
::

## What confuses people here

That a transaction makes concurrency safe on its own. It does not. Atomicity is
about crashes; concurrency safety is the **I**, and the level of isolation you
get by default in most databases still allows several specific bugs. That is the
next lesson and it is the one that catches people out.

## What you can do now

You can say what each letter buys with a concrete failure, and you can spot the
most common transaction bug in application code — the bracket around the wrong
thing.

## Your turn

For each, say whether it needs one transaction, several, or none, and why.

1. Allotting a seat: decrement the programme's remaining seats and insert an
   allotment row.
2. Importing 40,000 attendance rows from another system overnight.
3. Publishing results: update 40,000 rows to `PUBLISHED` and send 40,000 emails.
4. Reading a dashboard: five `SELECT` statements for five widgets.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1. One.** They must both happen or neither; a seat decremented with no
  allotment row is a seat lost forever.

  **2. Several — one per batch of a few thousand.** One transaction around all
  40,000 holds locks for minutes and produces an enormous rollback segment. Batch
  it, and make the import idempotent so a half-finished run can simply be redone.

  **3. One transaction for the updates, and the emails outside it, afterwards.**
  This is the rule above at scale: 40,000 emails inside a transaction means
  minutes of held locks and emails that may describe a rollback. The usual
  pattern is to commit the status change and put the emails on a queue.

  **4. Usually none**, and here is the exception worth knowing: if the five
  widgets must agree with each other — a total and its breakdown — then reading
  them in one transaction is what stops the total being from 10:00:01 and the
  breakdown from 10:00:02. A dashboard whose numbers do not add up is often this,
  and it looks like a calculation bug.
  :::
::

## The interview question this answers

**"What is a transaction, and what does ACID mean?"**

Everybody can list the four words. Almost nobody attaches a failure to each, and
that is the whole difference. Atomicity: the balance went down and the receipt
was never written. Consistency: the constraints hold at both ends. Isolation:
another clerk reading a number that may never become true. Durability: committed
survives the power going. Then the sentence that shows judgement — atomicity is
about crashes, and concurrency safety is isolation, which by default is weaker
than most people assume.
