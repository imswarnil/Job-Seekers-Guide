Database theory is one of the two subjects most likely to decide a backend
interview, and the questions are remarkably consistent. Here are ten, with what
separates a memorised answer from a real one.

::accordion
  :::accordion-item{label="1. Primary key versus unique key" icon="i-lucide-message-circle"}
  One per table versus many. Never `NULL` versus usually nullable. And the one
  most candidates miss: a primary key is what foreign keys point at, so choosing
  it is a promise of permanence rather than just a uniqueness rule.

  Then pre-empt the follow-up with the permanence test: could this value ever
  change or need correcting? Roll numbers, emails and phone numbers all fail it,
  which is why production schemas use surrogate keys.
  :::

  :::accordion-item{label="2. What is normalisation and why?" icon="i-lucide-message-circle"}
  Do not recite the forms. Answer with the three anomalies: a fact stored twice
  can be updated once and become inconsistent; some facts cannot be recorded
  without inventing others; deleting one thing destroys another.

  Then the forms as method — one value per cell, no partial dependency on a
  composite key, no dependency on a non-key column. Then the honest closer: and
  you denormalise deliberately for reads, having measured, accepting that you
  now maintain both copies.
  :::

  :::accordion-item{label="3. When would you denormalise?" icon="i-lucide-message-circle"}
  A read-heavy dashboard where the joins are measurably the cost, or a nightly
  reporting table.

  And the case that is not really denormalisation at all, which is the answer
  worth giving: a fee payment must store the amount **at the time of payment**
  rather than pointing at the programme's current fee, because the fee will
  change and the receipt must not. Invoices, order lines and marks awarded are
  all like this. Getting that wrong is how a system rewrites its own history.
  :::

  :::accordion-item{label="4. What is ACID?" icon="i-lucide-message-circle"}
  Four words everybody can list. Attach a failure to each and you are
  immediately in a different group. Atomicity: the balance went down and the
  receipt was never written. Consistency: constraints hold at both ends.
  Isolation: another clerk reading a number that may never become true.
  Durability: committed survives the power going, via a write-ahead log.

  Close with the distinction people blur: atomicity is about crashes, isolation
  is about neighbours, and they are different problems.
  :::

  :::accordion-item{label="5. The isolation levels, and what each allows" icon="i-lucide-message-circle"}
  Read uncommitted, read committed, repeatable read, serializable, against dirty
  reads, non-repeatable reads and phantoms.

  The sentence that gets remembered: *"and every one of those defaults still
  allows a lost update. PostgreSQL defaults to read committed and MySQL to
  repeatable read, and neither stops two clerks reading the same seat count and
  both allotting."*
  :::

  :::accordion-item{label="6. Two users book the same seat. Stop it." icon="i-lucide-message-circle"}
  Three fixes, with when each is right. A single conditional `UPDATE ... WHERE
  seats_left > 0` and **check the affected row count**. `SELECT ... FOR UPDATE`
  when clashes are common. A version column when they are rare and you do not
  want to hold a lock across a user's thinking time.

  Then the closer that sounds like production: add a `UNIQUE` constraint too,
  because in practice the cause is a double-clicked button or a retried request
  rather than two humans racing.
  :::

  :::accordion-item{label="7. How does an index work?" icon="i-lucide-message-circle"}
  A B-tree: a sorted structure, wide and shallow, so ten million rows is about
  four page reads instead of a scan. Each node holds hundreds of keys, so depth
  grows logarithmically and doubling the table barely changes the cost.

  Then the half most candidates omit entirely: what it costs. Every insert,
  update and delete maintains it, and it is a real copy of that column on disk.
  :::

  :::accordion-item{label="8. When does an index NOT help?" icon="i-lucide-message-circle"}
  The differentiating question in this track. Five cases: a function applied to
  the column, a leading wildcard in `LIKE`, skipping the leading column of a
  composite index, a value that is not selective enough to beat a scan, and a
  type mismatch that forces an implicit cast.

  Give the `YEAR(applied_on) = 2026` example and the range rewrite that fixes it.
  It is concrete, it is common, and it shows you have actually looked at a plan.
  :::

  :::accordion-item{label="9. A query is slow. Walk me through it." icon="i-lucide-message-circle"}
  A sequence, not an answer. Reproduce it and time it. `EXPLAIN ANALYZE` and look
  for `Seq Scan` and for `Rows Removed by Filter` — ten million removed to return
  two thousand is the whole diagnosis. Check whether an index exists and whether
  the query is written in a way that can use it. Then consider whether the query
  is asking for more than it needs: `SELECT *` on a wide table, no `LIMIT`, or a
  join that could be a filter.

  Say what you would not do first: add an index by guessing, which is how tables
  end up with six of them and slow writes.
  :::

  :::accordion-item{label="10. How would you model this?" icon="i-lucide-message-circle"}
  The open design question, and the one people fear. It is not testing whether
  you produce the perfect schema; it is testing whether you ask before you draw.

  Say the nouns out loud and find the entities. Ask what identifies each one, and
  whether that identifier could change. Ask about the relationships and their
  cardinality — one applicant to many applications, many applications to many
  subjects, so a junction table. Ask which facts must be frozen as at a moment in
  time. Then draw it, and name the constraints as you go: this is unique, this
  cannot be deleted while children exist, this must be between 0 and 100.

  Naming constraints while you draw is the single most senior-sounding thing you
  can do in this question.
  :::
::

## What separates the answers

::feature-list{columns="2"}
  :::feature{icon="i-lucide-alert-triangle" title="Name a failure"}
  Every strong answer above contains something going wrong: money in a gap, a
  seat allotted twice, ten million rows removed by a filter. A definition and a
  failure sound completely different to a listener.
  :::
  :::feature{icon="i-lucide-scale" title="Name the cost"}
  Indexes slow writes. Serializable is expensive. Denormalising means maintaining
  two copies. Candidates who only know the benefit sound like they have read a
  tutorial.
  :::
::
