Nine milliseconds or nine seconds, and the difference is one line of DDL. An
index is the highest-leverage thing in this entire subject, and it is also the
thing people add by superstition.

## Why this matters in a job

Because "the page is slow" is the most common production complaint there is, and
the answer is a missing index far more often than anything else. It is also the
most practically useful database interview topic: "how does an index work" is
asked constantly and the answer is genuinely satisfying.

## What an index actually is

A second, sorted structure that says where things are. Nothing more mysterious
than the index at the back of a book, with one important difference: it is kept
correct automatically, on every write.

The structure is a **B-tree**, and the important property is that it is wide and
shallow. Each node holds hundreds of keys, so the tree stays about four levels
deep even at ten million rows. Four levels means four page reads to find
anything.

::side-note{kind="go-deeper"}
The arithmetic: if a node holds 200 keys, one level reaches 200 rows, two reach
40,000, three reach 8 million, four reach 1.6 billion. That is why adding rows
barely makes lookups slower: the depth grows logarithmically. Doubling the table
does not double the work; it occasionally adds one level.
::

## What it costs

This is the half that people leave out, and it is why "add an index to
everything" is wrong.

::pros-cons
---
title: Every index you add
pros:
  - Lookups, ranges and sorts on that column become logarithmic instead of linear
  - A query can sometimes be answered from the index alone, never touching the table
  - Uniqueness constraints are enforced by one, for free
cons:
  - Every INSERT, UPDATE and DELETE must update it too, writes get slower
  - It is a real copy of that column plus row pointers, so it takes disk and memory
  - An index nobody uses is pure cost, and most databases have several
---
::

::real-life{title="The import that took four hours and then forty minutes" source="An attendance migration"}
Importing 40,000 attendance rows took four hours. The table had six indexes, and
every insert updated all six. We dropped the five that were not needed during the
import, loaded the data, and rebuilt them afterwards: forty minutes total,
including the rebuild. Nothing about the data changed. The lesson is that indexes
are not free and the cost lands on writes, which is exactly where nobody is
looking.
::

## The five times your index does nothing

This is the part worth memorising, because every one of these produces a
perfectly reasonable-looking query that ignores the index you added.

**1. A function on the column.**

```sql [slow.sql]
-- The index on applied_on is useless: the database cannot un-apply YEAR().
SELECT * FROM Application WHERE YEAR(applied_on) = 2026;

-- This uses it, and returns the same rows.
SELECT * FROM Application
 WHERE applied_on >= '2026-01-01' AND applied_on < '2027-01-01';
```

**2. A leading wildcard.**

```sql [slow.sql]
SELECT * FROM Applicant WHERE full_name LIKE '%Rao';    -- cannot use the index
SELECT * FROM Applicant WHERE full_name LIKE 'Rao%';    -- can
```

An index is sorted by the start of the value. Searching by the end is like asking
a dictionary for every word ending in "ing".

**3. The wrong column of a composite index.**

```sql [composite.sql]
CREATE INDEX idx ON Application (programme_id, status, score);
```

That index can serve a query on `programme_id`, or on `programme_id + status`, or
on all three. It cannot serve a query on `status` alone. A composite index is
usable **left to right**, like a phone book sorted by surname then first name:
useless for finding everybody called Anita.

**4. The value is not selective enough.**

```sql [not-worth-it.sql]
-- 90% of applications are 'RECEIVED'. Using an index for those rows means
-- reading most of the table anyway, one scattered row at a time, which is
-- slower than reading it sequentially. The planner correctly ignores the index.
SELECT * FROM Application WHERE status = 'RECEIVED';
```

**5. A type mismatch.**

```sql [slow.sql]
-- roll_number is TEXT. Comparing to a number makes the database cast the
-- column, which is a function on the column, which is case 1 again.
SELECT * FROM Student WHERE roll_number = 2026184;
```

## Read the plan rather than guessing

Every database will tell you what it is actually going to do.

```sql [explain.sql]
EXPLAIN ANALYZE
SELECT * FROM Application WHERE programme_id = 3 AND score > 75;
```

```text [Before the index]
Seq Scan on application  (cost=0.00..184320.00 rows=1840 width=64)
                         (actual time=0.412..1284.933 rows=1840 loops=1)
  Filter: ((programme_id = 3) AND (score > 75))
  Rows Removed by Filter: 9998160
Execution Time: 1291.204 ms
```

```text [After CREATE INDEX ON Application (programme_id, score)]
Index Scan using idx_app_prog_score on application
                         (cost=0.43..142.18 rows=1840 width=64)
                         (actual time=0.031..2.104 rows=1840 loops=1)
  Index Cond: ((programme_id = 3) AND (score > 75))
Execution Time: 2.338 ms
```

1,291 ms to 2.3 ms. The three words that matter are **`Seq Scan`** versus
**`Index Scan`**, and `Rows Removed by Filter: 9998160` is the database telling
you it read ten million rows to return 1,840.

::pull-quote
Learn to read two words of a query plan, Seq Scan and Index Scan, and you can
diagnose most slow pages you will ever meet.
::

## Which indexes to actually create

::feature-list{columns="2"}
  :::feature{icon="i-lucide-key" title="Every foreign key"}
  Not automatic in PostgreSQL or MySQL InnoDB for the referring side. Joins and
  cascading deletes both scan without one, and this is the single most common
  missing index in real schemas.
  :::
  :::feature{icon="i-lucide-filter" title="Columns you filter on often"}
  The `WHERE` clauses that appear on your hot pages. Look at the actual queries,
  not at what seems important.
  :::
  :::feature{icon="i-lucide-arrow-down-up" title="Columns you sort by"}
  An index is already sorted, so `ORDER BY applied_on DESC LIMIT 20` can read
  twenty entries instead of sorting ten million rows.
  :::
  :::feature{icon="i-lucide-x" title="Not: low-cardinality columns alone"}
  An index on a boolean, or on a status where one value is 90% of rows, is
  usually ignored. It is worth having as part of a composite, with the selective
  column first.
  :::
::

## Your turn

For each query, say whether the index is used, and if not, rewrite it.

Index: `CREATE INDEX idx ON Application (programme_id, status, applied_on);`

1. `WHERE programme_id = 3`
2. `WHERE status = 'SHORTLISTED'`
3. `WHERE programme_id = 3 AND status = 'SHORTLISTED'`
4. `WHERE programme_id = 3 AND applied_on > '2026-01-01'`
5. `WHERE UPPER(status) = 'SHORTLISTED'`
6. `ORDER BY programme_id, status LIMIT 50`

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  1. **Used.** Leftmost column.
  2. **Not used.** Skips the leading column; left-to-right only. Needs its own
     index, and probably is not worth one on its own, see selectivity.
  3. **Used**, both columns.
  4. **Partly used.** It seeks on `programme_id`, then has to filter on
     `applied_on` because `status` in between was not specified. Far better than
     a scan, not as good as a matching index.
  5. **Not used.** A function on the column. Rewrite as
     `WHERE status = 'SHORTLISTED'` if the data is already uppercase, or create
     an index on the expression `UPPER(status)` if it genuinely varies.
  6. **Used.** The index is already sorted in exactly that order, so the database
     reads the first fifty entries and stops. No sort at all.
  :::
::

## The interview question this answers

**"How does a database index work, and when would you not use one?"**

The first half: a B-tree, sorted, wide and shallow, so a lookup is four page
reads rather than a scan. The second half is where the marks are, because most
candidates only prepare the first: every index slows writes and costs storage;
it is ignored when you apply a function to the column, use a leading wildcard,
skip the leading column of a composite, or the value is not selective. Then close
with `EXPLAIN`, that you would read the plan rather than guess, and that
`Seq Scan` against `Index Scan` is the line you look for.
