Three rules nobody can recite usefully. I was taught normal forms as definitions
and could repeat them and could not apply one, which is the normal outcome of
learning them that way.

So here they are backwards: three **problems** first, and the names afterwards.

## Why this matters in a job

Because the design question — "how would you model this?" — is asked in most
backend interviews, and it is really asking whether you can spot a duplicated
fact. Nobody will ask you to define third normal form. Several people will show
you a bad table.

## The table we are fixing

| app_id | applicant | email | programme | dept | dept_head | subjects_interested |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Anita Rao | anita@… | B.Tech CSE | Computer Science | Dr Iyer | DBMS, OS, Networks |
| 2 | Vikram Shah | vikram@… | B.Tech CSE | Computer Science | Dr Iyer | DBMS, AI |
| 3 | Anita Rao | anita@… | B.Tech ECE | Electronics | Dr Menon | Signals |

## Problem one: a cell holding a list

`subjects_interested` holds three values in one cell. Everything about that is
broken.

::compare{caption="Ask a simple question of that column."}
  :::compare-side{label="What you have to write" verdict="wrong"}
  ```sql
  SELECT * FROM Application
  WHERE subjects_interested LIKE '%OS%';
  ```
  This also matches an applicant interested in "ROS" or "OSINT". It cannot use
  an index. And adding a subject means reading the cell, appending text and
  writing it back, which two clerks can do at once and lose one.
  :::
  :::compare-side{label="What you want to write" verdict="right"}
  ```sql
  SELECT a.* FROM Application a
  JOIN ApplicationSubject s USING (application_id)
  WHERE s.subject_id = 12;
  ```
  Exact, indexable, and adding a subject is inserting one row, which two clerks
  can do simultaneously without interfering.
  :::
::

**The fix:** one value per cell. A repeating group becomes its own table.

```sql [fix.sql]
CREATE TABLE ApplicationSubject (
  application_id BIGINT REFERENCES Application(application_id),
  subject_id     BIGINT REFERENCES Subject(subject_id),
  PRIMARY KEY (application_id, subject_id)
);
```

That is **first normal form**, and notice that you did not need the name to see
the problem.

## Problem two: a fact that depends on part of the key

This one only appears when the primary key is composite, which is why it is the
one people find slippery.

Take a marks table keyed on student *and* subject:

| student_id | subject_id | student_name | marks |
| --- | --- | --- | --- |
| 184 | CS-201 | Anita Rao | 78 |
| 184 | CS-202 | Anita Rao | 81 |
| 185 | CS-201 | Vikram Shah | 64 |

`marks` depends on **both** parts of the key: a mark is for this student in this
subject. But `student_name` depends only on `student_id`. It does not care which
subject the row is about, and so it is repeated once per subject the student
takes.

::compare{caption="Anita takes six subjects."}
  :::compare-side{label="Stored six times" verdict="wrong"}
  Her name is in six rows. Correct a spelling and you must correct six, and if
  you miss one she is now two people in any report that groups by name.
  :::
  :::compare-side{label="Stored once" verdict="right"}
  `student_name` moves to the `Student` table, keyed on `student_id` alone. Six
  rows of marks, one row holding the name, one place to correct it.
  :::
::

**The fix:** if a column depends on only part of a composite key, it belongs in
a table keyed on that part. That is **second normal form**, and it can only ever
be violated when the key is composite.

## Problem three: a fact that depends on another fact

Back to the first table. `dept_head` depends on `dept`, which depends on
`programme`, which depends on the application. The department head has nothing to
do with the application at all; it arrived by association.

**The fix:** the head belongs in the `Department` table. That is **third normal
form**, and it is the one that fixes the Dr lyer typo forever, because there is
only one place the name can be written.

## The finished design

```sql [schema.sql]
CREATE TABLE Department (
  department_id  BIGSERIAL PRIMARY KEY,
  name           TEXT NOT NULL UNIQUE,
  head_faculty_id BIGINT REFERENCES Faculty(faculty_id)
);

CREATE TABLE Programme (
  programme_id   BIGSERIAL PRIMARY KEY,
  code           TEXT NOT NULL UNIQUE,              -- 'BTECH-CSE'
  name           TEXT NOT NULL,
  department_id  BIGINT NOT NULL REFERENCES Department(department_id)
);

CREATE TABLE Applicant (
  applicant_id   BIGSERIAL PRIMARY KEY,
  full_name      TEXT NOT NULL,
  email          TEXT NOT NULL UNIQUE
);

CREATE TABLE Application (
  application_id BIGSERIAL PRIMARY KEY,
  applicant_id   BIGINT NOT NULL REFERENCES Applicant(applicant_id),
  programme_id   BIGINT NOT NULL REFERENCES Programme(programme_id),
  score          NUMERIC(5,2) CHECK (score BETWEEN 0 AND 100),
  status         TEXT NOT NULL DEFAULT 'RECEIVED',
  UNIQUE (applicant_id, programme_id)
);
```

Every fact is in exactly one place. Dr Iyer's name appears once in the whole
database.

## The three anomalies, named

The reason any of this matters, in the vocabulary an exam will use.

| Anomaly | What it is | In the bad table |
| --- | --- | --- |
| **Update** | Changing a fact requires changing many rows, and missing one makes the data inconsistent | Dr Iyer retires; 40,000 rows to change; one typo and there are two department heads |
| **Insert** | You cannot record one fact without inventing another | A new department with no applicants yet cannot be stored at all |
| **Delete** | Removing one fact destroys an unrelated one | Delete the only applicant to a programme and the programme's existence vanishes |

Those three are what normalisation is *for*. The forms are the method; the
anomalies are the reason.

## When to break the rules on purpose

Normalising is not a virtue. It has a cost: more tables means more joins, and a
dashboard doing eight joins on every page load is slower than one reading a
single wide row.

::pros-cons
---
title: Denormalising on purpose
pros:
  - A read-heavy dashboard can avoid several joins per request
  - Some values must be frozen as they were — see below, and this one is not optional
  - Reporting tables built nightly are a normal and sensible pattern
cons:
  - Two copies of a fact will diverge; it is a question of when, not whether
  - You now own the job of keeping them in step, on every write path, forever
  - It is almost always premature — normalise first, measure, then denormalise the one thing that needed it
---
::

::note
The one case where "duplication" is actually correct: a `FeePayment` must store
the amount charged **at the time of payment**, not point at the programme's
current fee. The fee will change next year and the receipt must not. That is not
denormalisation, it is recognising that "the fee then" and "the fee now" are
different facts. Invoices, order lines and marks awarded are all like this, and
getting it wrong is how a system rewrites history.
::

## What you can do now

You can look at a table and find the duplicated fact, which is the actual skill.
The names are now labels for things you can already see.

## Your turn

Normalise this. It records which faculty member teaches which subject, and when.

| id | faculty | faculty_email | dept | subject_code | subject_name | room | day | time |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | Dr Iyer | iyer@… | CSE | CS-201 | DBMS | A-101 | Mon | 09:00 |
| 2 | Dr Iyer | iyer@… | CSE | CS-202 | OS | A-101 | Tue | 11:00 |
| 3 | Dr Menon | menon@… | ECE | EC-201 | Signals | B-204 | Mon | 09:00 |

Find the anomalies first, then draw the tables.

::accordion
  :::accordion-item{label="The anomalies, then the tables" icon="i-lucide-check"}
  **Update:** Dr Iyer's email is stored once per subject taught. Change it and
  you change several rows.

  **Insert:** you cannot record that a new subject exists until somebody is
  scheduled to teach it, and you cannot record a new room at all.

  **Delete:** remove the only row for EC-201 and the fact that the subject
  exists, and which department it belongs to, disappears with it.

  **The tables:**

  ```sql
  Department  (department_id PK, name)
  Faculty     (faculty_id PK, name, email UNIQUE, department_id FK)
  Subject     (subject_id PK, code UNIQUE, name, department_id FK)
  Room        (room_id PK, code UNIQUE)
  TimetableSlot (
    slot_id PK,
    subject_id FK, faculty_id FK, room_id FK,
    day_of_week, start_time,
    UNIQUE (room_id, day_of_week, start_time),      -- one class per room per slot
    UNIQUE (faculty_id, day_of_week, start_time)    -- nobody teaches two at once
  )
  ```

  **The part worth noticing** is the two `UNIQUE` constraints at the end. Once
  the data is normalised, two real-world rules that were previously impossible to
  express — a room cannot hold two classes at once, a lecturer cannot be in two
  places — become one line each, enforced by the database on every write. That is
  the pay-off, and it is not the one the textbook emphasises.
  :::
::

## The interview question this answers

**"What is normalisation, and why?"**

Do not recite the forms. Answer with the anomalies: storing a fact twice means
updates can make the data inconsistent, some facts cannot be recorded at all
without inventing others, and deleting one thing destroys another. Then name the
forms as the method — one value per cell, no partial dependency on a composite
key, no dependency on a non-key column. Then the honest closer: and you
denormalise deliberately for read performance, measuring first, accepting that
you now own keeping the copies in step.
