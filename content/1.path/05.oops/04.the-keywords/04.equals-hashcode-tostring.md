Every class extends `java.lang.Object`, and `Object` hands every class a set of
methods. Three of them matter every day: `toString`, `equals` and `hashCode`. The
Java track showed you how to write them; this lesson is the contract behind them,
which is what the interviewer is really asking about.

## Why this matters in a job

Because collections depend on them. `HashSet`, `HashMap`, `list.contains()`,
`list.remove(obj)` all call `equals` and `hashCode` behind your back. Get them
wrong and nothing crashes. You get duplicates in a set, a lookup that returns
`null` for a key you inserted a moment ago, and a report that counts one student twice.

In fresher interviews, "what is the contract between equals and hashCode?" is
asked so often that not knowing it is noticed more than knowing it.

## The methods Object gives you

::feature-list{columns="2"}
  :::feature{icon="i-lucide-text" title="toString()"}
  A text form of the object. Default: `ClassName@hexHash`. Override it for logs.
  :::
  :::feature{icon="i-lucide-equal" title="equals(Object)"}
  Are these two objects **meaningfully** equal? Default: same as `==`, same
  reference.
  :::
  :::feature{icon="i-lucide-hash" title="hashCode()"}
  An `int` used to pick a bucket in hash-based collections. Default: derived from
  the object's identity.
  :::
  :::feature{icon="i-lucide-list" title="The rest"}
  `getClass()`, `clone()`, `wait()`, `notify()`, `notifyAll()`, and the
  deprecated `finalize()`. Name them if asked "what methods does Object have?".
  :::
::

## == against equals

`==` asks "is this the **same object**?", comparing references. `equals` asks
"do these **mean the same thing**?", and you decide what that means. For a
student, two objects with the same roll number are the same student, even if
they were loaded from the database twice.

## How it works

Wrong first. No overrides.

```java [NoOverrides.java]
import java.util.HashSet;
import java.util.Set;

public class NoOverrides {
    static class Student {
        final int roll;
        final String name;
        Student(int roll, String name) { this.roll = roll; this.name = name; }
    }

    public static void main(String[] args) {
        Student a = new Student(2104, "Anita Rao");
        Student b = new Student(2104, "Anita Rao");    // same student, loaded again

        System.out.println(a);
        System.out.println(a == b);
        System.out.println(a.equals(b));

        Set<Student> present = new HashSet<>();
        present.add(a);
        present.add(b);
        System.out.println("Present today: " + present.size());
    }
}
```

```text [Output]
NoOverrides$Student@7a81197d
false
false
Present today: 2
```

The hex after `@` is the identity hash code, different on every run. And one
student has been marked present twice.

Now the fix, then a trap that is worse than no fix.

```java [Student.java]
import java.util.HashSet;
import java.util.Objects;
import java.util.Set;

public class Student {
    private final int roll;
    private final String name;

    public Student(int roll, String name) { this.roll = roll; this.name = name; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                          // same reference: equal
        if (!(o instanceof Student other)) return false;     // null or another type: not equal
        return roll == other.roll;                           // the identity of a student is the roll
    }

    @Override
    public int hashCode() {
        return Objects.hash(roll);                           // the SAME fields as equals
    }

    @Override
    public String toString() {
        return "Student{roll=" + roll + ", name=" + name + "}";
    }

    public static void main(String[] args) {
        Student a = new Student(2104, "Anita Rao");
        Student b = new Student(2104, "Anita Rao");

        System.out.println(a);
        System.out.println(a == b);
        System.out.println(a.equals(b));

        Set<Student> present = new HashSet<>();
        present.add(a);
        present.add(b);
        System.out.println("Present today: " + present.size());
    }
}
```

```text [Output]
Student{roll=2104, name=Anita Rao}
false
true
Present today: 1
```

`==` is still false (two objects), `equals` is true (one student), and the set
holds one.

## The contract

::steps
### If a.equals(b), then a.hashCode() == b.hashCode()
The one rule you must never break. Equal objects must land in the same bucket.

### Unequal objects may share a hash code
That is a **collision**, it is allowed, and `equals` sorts it out inside the
bucket. Too many collisions only make things slower.

### equals must be reflexive, symmetric, transitive and consistent
`a.equals(a)`; if `a.equals(b)` then `b.equals(a)`; if `a` equals `b` and `b`
equals `c` then `a` equals `c`; and the answer does not change unless the fields
do. `a.equals(null)` is always `false`.
::

What happens if you override `equals` and forget `hashCode`:

```java [HalfDone.java]
import java.util.HashSet;
import java.util.Set;

public class HalfDone {
    static class Student {
        final int roll;
        Student(int roll) { this.roll = roll; }

        @Override
        public boolean equals(Object o) {
            return o instanceof Student s && s.roll == roll;
        }
        // no hashCode
    }

    public static void main(String[] args) {
        Student a = new Student(2104);
        Student b = new Student(2104);
        Set<Student> set = new HashSet<>();
        set.add(a);
        System.out.println("equals says: " + a.equals(b));
        System.out.println("contains says: " + set.contains(b));
    }
}
```

```text [Output]
equals says: true
contains says: false
```

`equals` says yes, the set says no, because `b` was hashed to a different bucket
and `equals` was never even called. That is the bug the contract exists to stop.

## Real use case

At work you rarely hand-write these any more. A Java **record** generates all
three from its fields, and IDEs generate them for ordinary classes.

```java [Records.java]
public class Records {
    record ExamResult(int roll, String subject, int marks) { }

    public static void main(String[] args) {
        var a = new ExamResult(2104, "DBMS", 78);
        var b = new ExamResult(2104, "DBMS", 78);
        System.out.println(a);
        System.out.println(a.equals(b) + " " + (a.hashCode() == b.hashCode()));
    }
}
```

```text [Output]
ExamResult[roll=2104, subject=DBMS, marks=78]
true true
```

The skill is still knowing **which fields** define identity. A record uses all of
them, which is right for a value like an exam result and wrong for an entity like
a student, whose name can change while they stay the same person.

::side-note{kind="security"}
`toString` ends up in logs, and logs are read by more people than your database.
Leave passwords, Aadhaar numbers and bank details out of it.
::

## What confuses people here

- **Using mutable fields in `hashCode`.** Put a student in a `HashSet`, change a
  field that `hashCode` uses, and the set can no longer find it. Use fields that
  do not change.
- **`equals(Student other)` instead of `equals(Object o)`.** That overloads, it
  does not override. Collections call `equals(Object)` and never see yours.
  `@Override` catches it.
- **Comparing strings with `==`.** The same topic from the Java track: `==`
  compares references, and two equal strings are not always the same object.

## Interview questions

::accordion
  :::accordion-item{label="Difference between == and equals()?" icon="i-lucide-message-circle"}
  `==` compares references (same object?) for objects, and values for
  primitives. `equals` compares meaning, as defined by the class; by default it
  behaves like `==`. Two `Student` objects for roll 2104: `==` false, overridden
  `equals` true.
  :::
  :::accordion-item{label="What is the contract between equals and hashCode?" icon="i-lucide-message-circle"}
  If two objects are equal by `equals`, they must have the same `hashCode`. The
  reverse is not required. Break it and hash-based collections fail: the
  `HalfDone` example has `equals` true and `contains` false.
  :::
  :::accordion-item{label="What happens if you override equals but not hashCode?" icon="i-lucide-message-circle"}
  Equal objects get different identity-based hash codes, go into different
  buckets, and `HashSet`/`HashMap` treat them as different. Duplicates in sets,
  failed lookups in maps.
  :::
  :::accordion-item{label="What does the default toString print?" icon="i-lucide-message-circle"}
  `getClass().getName() + "@" + Integer.toHexString(hashCode())`, for example
  `NoOverrides$Student@7a81197d`. Override it for readable logs.
  :::
  :::accordion-item{label="Name the methods of the Object class." icon="i-lucide-message-circle"}
  `toString`, `equals`, `hashCode`, `getClass`, `clone`, `wait` (three
  overloads), `notify`, `notifyAll`, and the deprecated `finalize`.
  :::
::
