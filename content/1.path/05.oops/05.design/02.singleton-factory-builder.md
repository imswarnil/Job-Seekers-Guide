A **design pattern** is a named, reusable solution to a problem that keeps
coming up in object-oriented design. They were catalogued in 1994 in a book by
four authors, known ever since as the **Gang of Four** (GoF), which listed 23 of
them in three groups: creational, structural and behavioural. A fresher is
expected to know about five. This lesson is the three **creational** ones: patterns
about **how objects get created**.

## Why this matters in a job

You will use these long before you write them. `Calendar.getInstance()` is a
factory. `StringBuilder` and every HTTP client's `.newBuilder()` are builders.
Spring beans are singletons by default. Recognising the pattern tells you how the
library expects to be used.

In interviews: "write a Singleton" is the most commonly asked coding question in
the OOPs round, often on paper, and the follow-up is always "is it thread-safe?".

## Singleton: exactly one instance

**Singleton** ensures a class has only one instance and gives a global point of
access to it. Like the university's one registrar's office: every department goes
to the same one.

Three ingredients: a **private constructor** (nobody else can call `new`), a
**private static field** holding the one instance, and a **public static method**
that returns it.

```java [Registrar.java]
public class Registrar {
    private static Registrar instance;              // the one copy, not created yet
    private int nextRoll = 2101;

    private Registrar() {                           // nobody outside can call new
        System.out.println("Registrar created");
    }

    public static Registrar getInstance() {          // lazy: created on first use
        if (instance == null) {
            instance = new Registrar();
        }
        return instance;
    }

    public int issueRoll() { return nextRoll++; }

    public static void main(String[] args) {
        Registrar a = Registrar.getInstance();
        Registrar b = Registrar.getInstance();
        System.out.println(a.issueRoll() + " " + b.issueRoll());
        System.out.println("Same object? " + (a == b));
    }
}
```

```text [Output]
Registrar created
2101 2102
Same object? true
```

"Is it thread-safe?" No. Two threads can both see `instance == null` at the same
moment and both create one. Three fixes, in the order interviewers like to hear
them:

::tabs
  :::tabs-item{label="Eager"}
  ```java [EagerRegistrar.java]
  public class EagerRegistrar {
      private static final EagerRegistrar INSTANCE = new EagerRegistrar();
      private EagerRegistrar() { }
      public static EagerRegistrar getInstance() { return INSTANCE; }
  }
  ```
  Created when the class loads. Thread-safe because class loading is. Costs the
  object even if nobody uses it.
  :::
  :::tabs-item{label="Double-checked locking"}
  ```java [LockedRegistrar.java]
  public class LockedRegistrar {
      private static volatile LockedRegistrar instance;
      private LockedRegistrar() { }

      public static LockedRegistrar getInstance() {
          if (instance == null) {                          // fast path, no lock
              synchronized (LockedRegistrar.class) {
                  if (instance == null) {                  // check again inside the lock
                      instance = new LockedRegistrar();
                  }
              }
          }
          return instance;
      }
  }
  ```
  Lazy and thread-safe. `volatile` is essential: without it another thread can see
  a half-constructed object. This is the version interviewers ask you to write.
  :::
  :::tabs-item{label="Enum"}
  ```java [EnumRegistrar.java]
  public enum EnumRegistrar {
      INSTANCE;
      private int nextRoll = 2101;
      public int issueRoll() { return nextRoll++; }
  }
  ```
  The JVM guarantees one instance, and it survives serialisation and reflection
  attacks that break the other two. Recommended in *Effective Java*.
  :::
::

::pros-cons
---
title: Singleton, honestly
pros:
  - One shared resource (a config, a connection pool) with one point of access
  - Lazy creation when the object is expensive
cons:
  - It is global state in disguise, and global state makes testing hard
  - Hides dependencies; a class that calls getInstance() inside does not say it needs one
  - Many teams treat it as an anti-pattern and let a framework manage the single instance instead
---
::

## Factory: let one method decide the class

**Factory** (strictly, the **simple factory** or **factory method** idea) moves
the decision about **which class to instantiate** into one method. The caller
asks for "a fee calculator for this student" and gets the right one without
knowing the concrete classes exist.

```java [FeeFactory.java]
public class FeeFactory {
    interface FeeCalculator { int annualFee(); }

    static class DayScholarFee implements FeeCalculator { public int annualFee() { return 85000; } }
    static class HostellerFee  implements FeeCalculator { public int annualFee() { return 85000 + 78000; } }
    static class NriFee        implements FeeCalculator { public int annualFee() { return 85000 * 3; } }

    // The factory: the only place that knows the concrete classes.
    static FeeCalculator forCategory(String category) {
        return switch (category) {
            case "DAY"       -> new DayScholarFee();
            case "HOSTELLER" -> new HostellerFee();
            case "NRI"       -> new NriFee();
            default -> throw new IllegalArgumentException("Unknown category: " + category);
        };
    }

    public static void main(String[] args) {
        for (String c : new String[] { "DAY", "HOSTELLER", "NRI" }) {
            FeeCalculator calc = forCategory(c);        // caller sees only the interface
            System.out.println(c + ": " + calc.annualFee());
        }
    }
}
```

```text [Output]
DAY: 85000
HOSTELLER: 163000
NRI: 255000
```

The `switch` still exists, but it exists **once**. Without the factory it would
be copied into every screen that needs a fee.

## Builder: many optional fields, readably

**Builder** separates constructing a complex object from its representation, so
you set only the fields you need, by name, and get a finished object at the end.
It solves the **telescoping constructor** problem: constructors with so many
parameters that nobody can tell which `null` is which.

::compare{caption="Which argument is the hostel block?"}
  :::compare-side{label="Telescoping constructor" verdict="wrong"}
  ```java [Telescoping.java]
  new Applicant("Anita Rao", "CSE", null, 92.4,
                true, null, "C-Block", false);
  ```
  :::
  :::compare-side{label="Builder" verdict="right"}
  ```java [Readable.java]
  Applicant.builder("Anita Rao", "CSE")
      .percentage(92.4)
      .hosteller("C-Block")
      .build();
  ```
  :::
::

```java [Applicant.java]
public class Applicant {
    private final String name;          // required
    private final String branch;        // required
    private final double percentage;    // optional
    private final String hostelBlock;   // optional
    private final boolean scholarship;  // optional

    private Applicant(Builder b) {
        this.name = b.name;
        this.branch = b.branch;
        this.percentage = b.percentage;
        this.hostelBlock = b.hostelBlock;
        this.scholarship = b.scholarship;
    }

    public static Builder builder(String name, String branch) { return new Builder(name, branch); }

    public static class Builder {
        private final String name;
        private final String branch;
        private double percentage;
        private String hostelBlock;
        private boolean scholarship;

        private Builder(String name, String branch) { this.name = name; this.branch = branch; }

        public Builder percentage(double p)   { this.percentage = p; return this; }   // return this: chaining
        public Builder hosteller(String block) { this.hostelBlock = block; return this; }
        public Builder scholarship()          { this.scholarship = true; return this; }

        public Applicant build() {
            if (percentage < 0 || percentage > 100) throw new IllegalStateException("Bad percentage");
            return new Applicant(this);       // validated once, then immutable
        }
    }

    @Override
    public String toString() {
        return name + " (" + branch + ") " + percentage + "%"
            + (hostelBlock != null ? ", hostel " + hostelBlock : "")
            + (scholarship ? ", scholarship" : "");
    }

    public static void main(String[] args) {
        System.out.println(Applicant.builder("Anita Rao", "CSE").percentage(92.4).hosteller("C-Block").build());
        System.out.println(Applicant.builder("Rahul Menon", "ECE").scholarship().build());
    }
}
```

```text [Output]
Anita Rao (CSE) 92.4%, hostel C-Block
Rahul Menon (ECE) 0.0%, scholarship
```

This is the `return this` from the `this` lesson, doing real work.

## What confuses people here

- **"Singleton means static class."** A class with only static methods is a
  utility class. A singleton is a real object: it can implement an interface, be
  passed around, and hold state.
- **Factory method against abstract factory.** The GoF "Factory Method" is a
  method subclasses override to choose the product; "Abstract Factory" creates
  families of related objects. For a fresher, the simple factory above plus
  naming the other two is enough.
- **Builder against a setter-heavy object.** Setters leave the object half-built
  and mutable between calls. A builder produces a finished, validated,
  usually immutable object in one step.

## Interview questions

::accordion
  :::accordion-item{label="Write a thread-safe Singleton." icon="i-lucide-message-circle"}
  Double-checked locking with a `volatile` field (the tab above), or the enum
  version. Say why `volatile` is there: to stop another thread seeing a partly
  constructed instance. Mention that eager initialisation is also thread-safe.
  :::
  :::accordion-item{label="How can a Singleton be broken?" icon="i-lucide-message-circle"}
  Reflection (calling the private constructor with `setAccessible(true)`),
  serialisation (deserialising creates a new object unless you add
  `readResolve`), and cloning. An enum singleton is safe against all three.
  :::
  :::accordion-item{label="What is the Factory pattern, and what problem does it solve?" icon="i-lucide-message-circle"}
  A method that decides which concrete class to create and returns it as an
  interface. It keeps object-creation logic in one place, so callers depend only
  on the interface. `forCategory("NRI")` returns an `NriFee` the caller never names.
  :::
  :::accordion-item{label="When would you use the Builder pattern?" icon="i-lucide-message-circle"}
  When an object has many fields, several of them optional, and you want it
  immutable and validated. It replaces unreadable telescoping constructors with
  named, chained calls.
  :::
  :::accordion-item{label="What are the three categories of GoF patterns?" icon="i-lucide-message-circle"}
  Creational (how objects are made: Singleton, Factory, Builder, Prototype,
  Abstract Factory), structural (how they are composed: Adapter, Decorator,
  Facade, Proxy), behavioural (how they interact: Observer, Strategy, Command,
  Iterator, Template Method).
  :::
::
