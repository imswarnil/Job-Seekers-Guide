The five principles are called **SOLID**, one letter each, collected and named by
Robert C. Martin around 2000. They are not rules the compiler enforces. They are
the questions a reviewer asks when your class has grown too big, and the
vocabulary for asking them.

::warning{icon="i-lucide-alert-triangle"}
SOLID is where fresher answers go vague fastest. Everybody can expand the
acronym. Very few can give a violation and its fix for each letter. That is the
only thing that counts, so every principle below is exactly that: wrong, then
right, in a few lines.
::

## Why this matters in a job

Because code review is where you learn to design, and reviewers speak this
language. "This class has two reasons to change" is single responsibility. "Why
does adding a fee type mean editing this method?" is open/closed. You will hear
these in your first month.

In interviews, product companies ask SOLID from the second round onwards, and
service companies increasingly ask at least "what is the S".

## S: single responsibility

**A class should have one reason to change**: it should answer to one kind of
requirement.

::compare{caption="Three departments can each force a change to the left-hand class."}
  :::compare-side{label="Violation" verdict="wrong"}
  ```java [ResultService.java]
  class ResultService {
      int total(ExamResult r) { ... }        // exam cell's rules
      void save(ExamResult r) { ... }        // database schema
      String toPdf(ExamResult r) { ... }     // the format the dean wants
  }
  ```
  A change to the PDF layout means editing and re-testing the class that
  calculates marks.
  :::
  :::compare-side{label="Fix" verdict="right"}
  ```java [Split.java]
  class ResultCalculator { int total(ExamResult r) { ... } }
  class ResultRepository { void save(ExamResult r) { ... } }
  class ResultPdf        { String render(ExamResult r) { ... } }
  ```
  Each class changes for one reason, and a PDF change cannot break a mark.
  :::
::

## O: open/closed

**Open for extension, closed for modification.** Add new behaviour by adding code,
not by editing code that already works.

```java [Scholarships.java]
import java.util.List;

public class Scholarships {
    // Violation: every new scholarship means editing this method.
    static int discountBad(String type, int fee) {
        if (type.equals("MERIT")) return fee * 50 / 100;
        if (type.equals("SPORTS")) return fee * 25 / 100;
        return 0;
    }

    // Fix: each scholarship is its own class. New ones are new classes.
    interface Scholarship { int discount(int fee); }
    record Merit()  implements Scholarship { public int discount(int fee) { return fee * 50 / 100; } }
    record Sports() implements Scholarship { public int discount(int fee) { return fee * 25 / 100; } }
    record SingleGirlChild() implements Scholarship { public int discount(int fee) { return 10000; } }  // added later, nothing edited

    public static void main(String[] args) {
        int fee = 85000;
        System.out.println(discountBad("MERIT", fee));
        for (Scholarship s : List.of(new Merit(), new Sports(), new SingleGirlChild())) {
            System.out.println(s.getClass().getSimpleName() + ": " + s.discount(fee));
        }
    }
}
```

```text [Output]
42500
Merit: 42500
Sports: 21250
SingleGirlChild: 10000
```

This is polymorphism used on purpose.

## L: Liskov substitution

**A subclass must be usable anywhere its parent is, without surprising the
caller.** Named after Barbara Liskov, who stated it in 1987. If code that works
with a parent breaks when handed a child, the inheritance is wrong.

```java [Liskov.java]
public class Liskov {
    static class Course {
        int seats = 60;
        void enrol() { seats--; }
    }

    // Violation: an audit course "is a" course, but refuses the parent's promise.
    static class AuditCourse extends Course {
        @Override
        void enrol() { throw new UnsupportedOperationException("Audit courses have no enrolment"); }
    }

    static void admitFive(Course c) {       // written against Course, correctly
        for (int i = 0; i < 5; i++) c.enrol();
        System.out.println("Seats left: " + c.seats);
    }

    public static void main(String[] args) {
        admitFive(new Course());
        admitFive(new AuditCourse());
    }
}
```

```text [Output]
Seats left: 55
Exception in thread "main" java.lang.UnsupportedOperationException: Audit courses have no enrolment
	at Liskov$AuditCourse.enrol(Liskov.java:10)
	at Liskov.admitFive(Liskov.java:14)
	at Liskov.main(Liskov.java:20)
```

The fix is to stop pretending: an audit course is not an enrollable course. Make
`Enrollable` a separate interface that only real courses implement. The classic
textbook version of this is a `Square` extending `Rectangle`, where setting the
width also changes the height and breaks every caller that expected them to be
independent. Mention it; interviewers know it.

## I: interface segregation

**No class should be forced to implement methods it does not use.** Prefer several
small interfaces to one large one.

::compare{caption="A guest lecturer does not set exam papers."}
  :::compare-side{label="Violation" verdict="wrong"}
  ```java [Fat.java]
  interface FacultyDuties {
      void teach();
      void setPaper();
      void mentorStudents();
  }
  class GuestLecturer implements FacultyDuties {
      public void teach() { ... }
      public void setPaper() { throw new UnsupportedOperationException(); }
      public void mentorStudents() { throw new UnsupportedOperationException(); }
  }
  ```
  :::
  :::compare-side{label="Fix" verdict="right"}
  ```java [Thin.java]
  interface Teaches  { void teach(); }
  interface SetsPaper { void setPaper(); }
  interface Mentors  { void mentorStudents(); }

  class Professor implements Teaches, SetsPaper, Mentors { ... }
  class GuestLecturer implements Teaches { ... }
  ```
  :::
::

Notice the violation of I produced a violation of L: those
`UnsupportedOperationException`s are surprises. The principles overlap, and
saying so in an interview is a good sign.

## D: dependency inversion

**High-level code should depend on abstractions, not on concrete low-level
classes.** The class that decides *what* should not create the class that
decides *how*; it should be handed one.

```java [Inversion.java]
public class Inversion {
    interface ResultStore { void save(String roll, int marks); }

    static class MySqlStore implements ResultStore {
        public void save(String roll, int marks) { System.out.println("INSERT " + roll + " " + marks); }
    }
    static class InMemoryStore implements ResultStore {
        int saved;
        public void save(String roll, int marks) { saved++; }
    }

    // Violation would be: private final MySqlStore store = new MySqlStore();
    static class ResultPublisher {
        private final ResultStore store;                 // depends on the abstraction
        ResultPublisher(ResultStore store) { this.store = store; }   // handed in: dependency injection
        void publish(String roll, int marks) { store.save(roll, marks); }
    }

    public static void main(String[] args) {
        new ResultPublisher(new MySqlStore()).publish("2104", 78);

        InMemoryStore fake = new InMemoryStore();        // in a test: no database needed
        new ResultPublisher(fake).publish("2105", 91);
        System.out.println("Saved in test: " + fake.saved);
    }
}
```

```text [Output]
INSERT 2104 78
Saved in test: 1
```

Handing a class its dependencies through the constructor is called **dependency
injection**, and it is exactly what the Spring framework does for you at scale.

## Real use case

::real-life{title="Where SOLID shows up without its name" source="Salesforce work, Accenture onwards"}
Nobody at work says "that violates the open/closed principle" out loud very often.
They say "why is there a fourteen-branch `if` on the record type?" or "I cannot
test this without a live org". Both are SOLID questions. The trigger-handler
pattern every Salesforce team uses (one trigger, one handler class per object,
logic in service classes) is single responsibility applied to a platform that
makes it easy to put everything in one place.
::

## What confuses people here

- **"Single responsibility means one method."** It means one **reason to change**.
  A class with ten methods about calculating results is fine.
- **Dependency inversion against dependency injection.** Inversion is the
  principle (depend on abstractions). Injection is one technique for achieving it
  (pass dependencies in). Interviewers sometimes check you know they differ.
- **Following SOLID everywhere.** A 30-line script does not need five interfaces.
  The principles are for code that will change and be read by other people.

## Interview questions

::accordion
  :::accordion-item{label="What are the SOLID principles?" icon="i-lucide-message-circle"}
  Single responsibility (one reason to change), open/closed (extend without
  modifying), Liskov substitution (a subclass must work wherever its parent does),
  interface segregation (small focused interfaces), dependency inversion (depend
  on abstractions). Then offer one example, ideally the scholarship one for O.
  :::
  :::accordion-item{label="Give an example of violating the Liskov substitution principle." icon="i-lucide-message-circle"}
  `AuditCourse extends Course` but throws from `enrol()`, so `admitFive(Course)`
  works for a `Course` and crashes for an `AuditCourse`. Or the textbook one:
  `Square extends Rectangle`, where `setWidth` also changes the height.
  :::
  :::accordion-item{label="How does the open/closed principle relate to polymorphism?" icon="i-lucide-message-circle"}
  Polymorphism is how you achieve it. Code written against the `Scholarship`
  interface calls `discount()`; new scholarships are new classes, and that code is
  never edited.
  :::
  :::accordion-item{label="Difference between dependency inversion and dependency injection?" icon="i-lucide-message-circle"}
  Inversion is the principle: high-level classes depend on interfaces, not
  concrete classes. Injection is a technique: pass the dependency in (usually via
  the constructor) instead of creating it inside. Spring is a dependency
  injection framework.
  :::
  :::accordion-item{label="Which SOLID principle do you find most useful, and why?" icon="i-lucide-message-circle"}
  An opinion question; any is fine if you defend it. Single responsibility is a
  safe and honest pick: most messy code I have seen was one class doing four
  jobs, and splitting it is the first refactor that makes everything else
  possible.
  :::
::
