Here are the questions as they really arrive, in roughly the order an interviewer
climbs through them. Answer each one out loud before opening it. If your answer
has no example, it is not finished.

::tip
The shape that works for every answer: **one sentence of definition, one
university example, one line of code or one follow-up you pre-empt.** Thirty
seconds. Then stop and let them ask the next thing.
::

## The opening

::accordion
  :::accordion-item{label="1. What is OOP? Why do we need it?" icon="i-lucide-message-circle"}
  Organising a program around objects that hold their data and the methods
  allowed to change it. We need it so rules live next to the data they protect
  and a large codebase stays correct as people change it.

  ```java [Why.java]
  class FeeAccount {
      private int paid;
      void pay(int amount) {
          if (amount <= 0) throw new IllegalArgumentException("Payment must be positive");
          paid += amount;                 // the only way in
      }
  }
  ```
  :::
  :::accordion-item{label="2. What are the four pillars of OOP?" icon="i-lucide-message-circle"}
  Encapsulation, abstraction, inheritance, polymorphism. Name them, then offer:
  "shall I give an example of each?". That turns a list into a conversation you
  lead.
  :::
  :::accordion-item{label="3. Difference between a class and an object?" icon="i-lucide-message-circle"}
  A class is the blueprint; an object is one instance of it, created with `new`,
  on the heap, with its own fields.

  ```java [ClassObject.java]
  Student anita = new Student();   // Student: class. anita: reference to an object.
  Student rahul = new Student();   // a second, separate object
  ```
  :::
  :::accordion-item{label="4. Procedural against object-oriented programming?" icon="i-lucide-message-circle"}
  Procedural keeps data and functions apart, and any function can change any
  data (C). Object-oriented bundles them, and outside code asks the object (Java).
  :::
  :::accordion-item{label="5. Is Java 100% object-oriented?" icon="i-lucide-message-circle"}
  No. Eight primitives (`int`, `char`, `boolean` and the rest) are not objects,
  and `static` members belong to no object. Wrapper classes (`Integer`) exist to
  bridge the gap.
  :::
::

## The pillars

::accordion
  :::accordion-item{label="6. What is encapsulation? How is it achieved?" icon="i-lucide-message-circle"}
  Bundling data with the methods that guard it and restricting direct access.
  Private fields, public methods that validate, and never handing out mutable
  internals.

  ```java [Enc.java]
  public List<String> getSubjects() {
      return Collections.unmodifiableList(subjects);   // not the real list
  }
  ```
  :::
  :::accordion-item{label="7. What is abstraction? How is it different from encapsulation?" icon="i-lucide-message-circle"}
  Showing what, hiding how. Encapsulation hides data; abstraction hides
  complexity. Achieved with interfaces and abstract classes.

  ```java [Abs.java]
  interface Notifier { void send(String roll, String message); }
  // publish() calls send(); email or SMS is not its business
  ```
  :::
  :::accordion-item{label="8. What is inheritance? What are its types?" icon="i-lucide-message-circle"}
  A child acquiring a parent's members with `extends`, modelling is-a. Types:
  single, multilevel, hierarchical, multiple, hybrid. Java supports the first
  three with classes; multiple only through interfaces.
  :::
  :::accordion-item{label="9. Why does Java not support multiple inheritance?" icon="i-lucide-message-circle"}
  The diamond problem: two parents with the same method make the child
  ambiguous. With interfaces, Java forces the class to resolve it.

  ```java [Diamond.java]
  class TeachingAssistant implements Student, Faculty {
      public String idCardColour() { return Faculty.super.idCardColour(); }
  }
  ```
  :::
  :::accordion-item{label="10. What is polymorphism? Types?" icon="i-lucide-message-circle"}
  One call, different behaviour depending on the object or arguments.
  Compile-time (overloading) and runtime (overriding).

  ```java [Poly.java]
  Student s = new Hosteller("Anita");
  s.monthlyCharges();              // Hosteller's version: 6500, chosen at runtime
  ```
  :::
  :::accordion-item{label="11. Overloading against overriding?" icon="i-lucide-message-circle"}
  Overloading: same name, different parameters, compile time. Overriding: same
  signature in a subclass, runtime. Overriding cannot narrow access or throw
  broader checked exceptions; overloading cannot differ by return type alone.
  :::
  :::accordion-item{label="12. Can we override a static method? A private one? A final one?" icon="i-lucide-message-circle"}
  None of them. Static methods are hidden (bound by reference type), private ones
  are invisible to the child, final ones are forbidden.

  ```java [Hide.java]
  Student s = new Hosteller();
  s.office();     // static: Student's version, whatever the object
  ```
  :::
  :::accordion-item{label="13. Can we overload main?" icon="i-lucide-message-circle"}
  Yes, but the JVM only calls `public static void main(String[] args)`. Other
  overloads are ordinary methods.
  :::
  :::accordion-item{label="14. What is dynamic method dispatch?" icon="i-lucide-message-circle"}
  Resolving an overridden method call at runtime from the actual object, not the
  reference type. It is how runtime polymorphism works.
  :::
::

## Relationships and keywords

::accordion
  :::accordion-item{label="15. Abstract class against interface: when do you use which?" icon="i-lucide-message-circle"}
  Abstract class for an is-a family sharing state and code (extend one).
  Interface for a capability unrelated classes can have (implement many). Since
  Java 8 interfaces have default and static methods, so "interfaces have no
  bodies" is outdated.
  :::
  :::accordion-item{label="16. Can an abstract class have a constructor?" icon="i-lucide-message-circle"}
  Yes, called through `super(...)` when a child is created, to initialise the
  parent's fields.

  ```java [AbsCtor.java]
  abstract class Exam {
      protected final String subject;
      Exam(String subject) { this.subject = subject; }
  }
  class Theory extends Exam { Theory() { super("DBMS"); } }
  ```
  :::
  :::accordion-item{label="17. Association, aggregation and composition?" icon="i-lucide-message-circle"}
  All has-a. Association: they know each other (student and advisor).
  Aggregation: the part outlives the whole (department and professors).
  Composition: the part dies with it (student and ID card, created inside the
  constructor).
  :::
  :::accordion-item{label="18. What does composition over inheritance mean?" icon="i-lucide-message-circle"}
  Prefer holding an object and delegating to extending it. Extending
  `ArrayList` to cap a section at 60 fails, because `addAll` bypasses your `add`.
  Holding a private list and exposing `enrol()` cannot be bypassed.
  :::
  :::accordion-item{label="19. What are the access modifiers?" icon="i-lucide-message-circle"}
  `private` (class), default (package), `protected` (package plus subclasses),
  `public` (everywhere). Each level opens one more door.
  :::
  :::accordion-item{label="20. What is static? Why is main static?" icon="i-lucide-message-circle"}
  A static member belongs to the class, one shared copy. `main` is static so the
  JVM can call it before any object exists.

  ```java [Static.java]
  static int seatsFilled;          // one board for the whole university
  Admission(String name) { seatsFilled++; }
  ```
  :::
  :::accordion-item{label="21. final, finally and finalize?" icon="i-lucide-message-circle"}
  `final` restricts change (variable, method, class). `finally` always runs after
  `try`. `finalize()` was a garbage-collection hook, deprecated since Java 9.
  :::
  :::accordion-item{label="22. this against super?" icon="i-lucide-message-circle"}
  `this` refers to the current object; `super` to its parent part. `this(...)`
  and `super(...)` call constructors and must be the first statement, so a
  constructor can use only one of them.

  ```java [Super.java]
  @Override int monthlyCharges() { return super.monthlyCharges() + 6500; }
  ```
  :::
  :::accordion-item{label="23. == against equals?" icon="i-lucide-message-circle"}
  `==` compares references; `equals` compares meaning as the class defines it.

  ```java [Eq.java]
  new Student(2104).equals(new Student(2104));   // true, if equals uses roll
  new Student(2104) == new Student(2104);        // false: two objects
  ```
  :::
  :::accordion-item{label="24. What is the equals and hashCode contract? What breaks if you ignore it?" icon="i-lucide-message-circle"}
  Equal objects must have equal hash codes. Override `equals` without
  `hashCode` and a `HashSet` holds duplicates and `contains` returns `false` for an
  equal object, because it looks in the wrong bucket.
  :::
::

## Design

::accordion
  :::accordion-item{label="25. What are the SOLID principles? Give an example of one." icon="i-lucide-message-circle"}
  Single responsibility, open/closed, Liskov substitution, interface
  segregation, dependency inversion. Example for O: scholarships as classes
  behind an interface, so a new one is a new class and nothing is edited.

  ```java [Open.java]
  interface Scholarship { int discount(int fee); }
  record Merit() implements Scholarship { public int discount(int fee) { return fee / 2; } }
  ```
  :::
  :::accordion-item{label="26. What is the Liskov substitution principle? Give a violation." icon="i-lucide-message-circle"}
  A subclass must work anywhere its parent does. `AuditCourse extends Course`
  and throws from `enrol()`, so code written for `Course` crashes. Textbook
  version: `Square extends Rectangle`.
  :::
  :::accordion-item{label="27. Write a thread-safe Singleton." icon="i-lucide-message-circle"}
  ```java [Registrar.java]
  public class Registrar {
      private static volatile Registrar instance;
      private Registrar() { }
      public static Registrar getInstance() {
          if (instance == null) {
              synchronized (Registrar.class) {
                  if (instance == null) instance = new Registrar();
              }
          }
          return instance;
      }
  }
  ```
  `volatile` stops another thread seeing a half-built object. Mention that an
  `enum` singleton is the simplest safe version.
  :::
  :::accordion-item{label="28. Factory against Builder?" icon="i-lucide-message-circle"}
  Factory decides **which class** to create (`forCategory("NRI")` returns an
  `NriFee`). Builder decides **how to assemble** one object with many optional
  fields, readably and validated once in `build()`.
  :::
  :::accordion-item{label="29. Observer against Strategy?" icon="i-lucide-message-circle"}
  Observer notifies **all** registered listeners that something happened (the
  exam cell publishing a result). Strategy uses **one** chosen algorithm to do a
  job (ranking by entrance or by interview). `addEventListener` and `Comparator`
  are the everyday examples.
  :::
  :::accordion-item{label="30. What are coupling and cohesion? What do you aim for?" icon="i-lucide-message-circle"}
  Coupling: dependence between classes, aim low. Cohesion: relatedness inside a
  class, aim high. Every principle and pattern in this track is a way of getting
  one or both.
  :::
  :::accordion-item{label="31. Where have you used OOP in your own code?" icon="i-lucide-message-circle"}
  The question that ends many rounds, and the one you cannot memorise. Prepare
  one real example from something you built: which class you made, what it
  protected, what you would split if you wrote it again. Honest and small beats
  impressive and vague.
  :::
::

::real-life{title="The follow-up that decides it" source="Walk-in rounds, 2018"}
In the rounds I cleared, the interviewer never stopped at the definition. They
took my example and changed it: "and if a third kind of student arrives?", "and
if two threads call that?". Every answer in this bank has a follow-up waiting in
it. Practise by asking yourself the follow-up before they do.
::
