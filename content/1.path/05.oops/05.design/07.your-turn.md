## 1. The grace marks

This compiles and runs. Find the two ways a caller can put marks above 100.

```java [Marks.java]
import java.util.ArrayList;
import java.util.List;

public class Marks {
    private final List<Integer> scores = new ArrayList<>();

    public void add(int score) {
        if (score < 0 || score > 100) throw new IllegalArgumentException("0 to 100");
        scores.add(score);
    }

    public List<Integer> getScores() { return scores; }

    public static void main(String[] args) {
        Marks m = new Marks();
        m.add(78);
        m.getScores().add(140);
        m.getScores().set(0, 250);
        System.out.println(m.getScores());
    }
}
```

```text [Output]
[250, 140]
```

::accordion
  :::accordion-item{label="Solution" icon="i-lucide-check"}
  `getScores()` returns the real list, so `add` and `set` both go around the
  check. `private` protected the variable, not the list.

  ```java [MarksFixed.java]
  public List<Integer> getScores() {
      return List.copyOf(scores);           // an immutable copy; any change throws
  }
  ```
  The experienced version also asks whether callers need the list at all. Often
  what they want is `average()` or `highest()`, and exposing those methods keeps
  the list entirely inside.
  :::
::

## 2. Predict the output

Write down all four lines before running it.

```java [Predict.java]
public class Predict {
    static class Student {
        String type = "student";
        String describe() { return "I am a student"; }
        static String office() { return "Admissions"; }
    }
    static class Hosteller extends Student {
        String type = "hosteller";
        @Override String describe() { return "I am a hosteller"; }
        static String office() { return "Warden"; }
    }

    public static void main(String[] args) {
        Student s = new Hosteller();
        System.out.println(s.type);
        System.out.println(s.describe());
        System.out.println(s.office());
        System.out.println(((Hosteller) s).type);
    }
}
```

::accordion
  :::accordion-item{label="Solution" icon="i-lucide-check"}
  ```text [Output]
  student
  I am a hosteller
  Admissions
  hosteller
  ```
  Only the overridden instance method is chosen by the object. The field and the
  static method are chosen by the reference type. Casting changes the reference
  type, so the last line sees the child's field. If you got all four, you
  understand runtime polymorphism better than most people who can define it.
  :::
::

## 3. The set that counts twice

A register of students present today reports 3 when only two students came.
Find out why, and fix it without changing `main`.

```java [Register.java]
import java.util.HashSet;
import java.util.Set;

public class Register {
    static class Student {
        final int roll;
        Student(int roll) { this.roll = roll; }

        public boolean equals(Student other) {
            return other != null && other.roll == roll;
        }

        @Override public int hashCode() { return Integer.hashCode(roll); }
    }

    public static void main(String[] args) {
        Set<Student> present = new HashSet<>();
        present.add(new Student(2104));
        present.add(new Student(2105));
        present.add(new Student(2104));     // scanned twice at the gate
        System.out.println("Present: " + present.size());
    }
}
```

```text [Output]
Present: 3
```

::accordion
  :::accordion-item{label="Solution" icon="i-lucide-check"}
  `equals(Student other)` **overloads** `equals`, it does not override it.
  `HashSet` calls `equals(Object)`, which is still `Object`'s reference check.
  `hashCode` was right, so both 2104s land in the same bucket, and are then
  compared with the wrong `equals`.

  ```java [RegisterFixed.java]
  @Override
  public boolean equals(Object o) {
      return o instanceof Student s && s.roll == roll;
  }
  ```
  ```text [Output]
  Present: 2
  ```
  The lesson for a reviewer: `@Override` on the original would have made it a
  compile error. Put it on every override.
  :::
::

## 4. Split this class

Name every reason this class could change, then say which classes you would
split it into and which interfaces they would talk through. No code needed; this
is how the design round is really asked.

```java [HostelManager.java]
class HostelManager {
    void allotRoom(Student s) { ... }            // checks gender, year, vacancy
    int monthlyBill(Student s) { ... }           // mess + room + electricity
    void sendBillSms(Student s, int amount) { ... }
    void saveToMySql(Student s) { ... }
    String nightRollCallPdf(List<Student> all) { ... }
}
```

::accordion
  :::accordion-item{label="Solution" icon="i-lucide-check"}
  Five reasons to change: allotment rules, billing rules, SMS provider, database,
  report layout. That is low cohesion, and the concrete SMS and MySQL calls mean
  tight coupling.

  A good answer: `RoomAllotment`, `HostelBilling`, `RollCallReport`, each with
  one job, depending on `Notifier` and `StudentStore` interfaces handed in
  through their constructors. Name the principles as you go: single
  responsibility for the split, dependency inversion for the interfaces. Saying
  the principle's name only after the reasoning is what makes it sound earned.
  :::
::

## 5. Break the Singleton

This Singleton is correct for normal use. Write a few lines that create a
second `Registrar` anyway, then make it impossible.

```java [Registrar.java]
public class Registrar {
    private static final Registrar INSTANCE = new Registrar();
    private Registrar() { }
    public static Registrar getInstance() { return INSTANCE; }
}
```

::accordion
  :::accordion-item{label="Solution" icon="i-lucide-check"}
  Reflection can call the private constructor:

  ```java [Break.java]
  import java.lang.reflect.Constructor;

  public class Break {
      public static void main(String[] args) throws Exception {
          Constructor<Registrar> c = Registrar.class.getDeclaredConstructor();
          c.setAccessible(true);
          Registrar second = c.newInstance();
          System.out.println(second == Registrar.getInstance());
      }
  }
  ```
  ```text [Output]
  false
  ```
  A beginner fix: throw from the constructor if `INSTANCE` is already set. The fix
  an experienced developer writes: make it an `enum`, which the JVM refuses to
  instantiate reflectively and which also survives serialisation.

  ```java [EnumRegistrar.java]
  public enum EnumRegistrar { INSTANCE; }
  ```
  :::
::

## 6. Is-a or has-a?

For each pair, say inheritance, aggregation or composition, and the lifetime
reason in one line.

1. `Hosteller` and `Student`
2. `Department` and `Faculty`
3. `ExamResult` and `Student`
4. `Timetable` and the `Period`s it creates
5. `Library` and `Book`

::accordion
  :::accordion-item{label="Solution" icon="i-lucide-check"}
  1. Inheritance. A hosteller is a student.
  2. Aggregation. A department has faculty who exist before it and after it.
  3. Association (or composition if results are created by and owned by the
     student record). The honest answer names the ambiguity: it depends on
     whether a result can exist without the student. In most university systems
     it cannot, so composition.
  4. Composition. Periods are created by the timetable and mean nothing without
     it.
  5. Aggregation. Books exist before they are catalogued and after a library
     closes.

  An interviewer who hears you say "it depends, and here is on what" for number 3
  has learned more about you than from the other four.
  :::
::

## 7. Choose the pattern

Name the pattern and write the interface (not the implementation) for each.

1. Attendance below 75% must alert the student, the parent and the HOD, and next
   year the placement cell too.
2. Late fees are calculated differently for hostellers, day scholars and NRI
   students, and the rule is picked when the fee is computed.
3. A `Transcript` has a name and roll number (required) and up to twelve optional
   sections.

::accordion
  :::accordion-item{label="Solution" icon="i-lucide-check"}
  ```java [Choices.java]
  // 1. Observer: many listeners, one event.
  interface AttendanceListener { void onLowAttendance(int roll, double pct); }

  // 2. Strategy: one rule chosen at runtime. (A Factory can pick which strategy.)
  interface LateFeeRule { int lateFee(int daysLate); }

  // 3. Builder: required fields in the builder's constructor, optional ones as methods.
  // Transcript.builder("Anita Rao", 2104).cgpa(8.4).backlogs(0).build();
  ```
  Spotting that 2 is Strategy **and** Factory together is a good sign: patterns
  combine, and real code rarely uses one alone.
  :::
::

## 8. The interview in one minute

Set a timer for sixty seconds and answer out loud: "Explain polymorphism with an
example from a real system." Record it on your phone and listen back.

::accordion
  :::accordion-item{label="What a good answer contains" icon="i-lucide-check"}
  One sentence of definition, the two types with when each is decided, one
  university example (`Student s = new Hosteller(); s.monthlyCharges();`), and one
  real-world instance (`List` over `ArrayList`, or a `Comparator` in `sort`). No
  "many forms" and silence. If you ran over sixty seconds, cut the definition,
  not the example.
  :::
