The name is **coupling**: how much one class depends on the insides of another.
Its partner is **cohesion**: how closely the things inside one class belong
together. Good design is **low coupling and high cohesion**, and every principle
and pattern in this track is a way of getting one or both.

## Why this matters in a job

Because this is the question behind every "can you make this change by Friday?".
In a loosely coupled codebase, a change to the fee rules touches the fee classes.
In a tightly coupled one, it touches the fee classes, the report, the PDF, the
email template and a test nobody understands. The first takes a day; the second
takes a week and breaks something.

In interviews, "what is coupling and cohesion?" often closes the OOPs round,
because it checks whether the whole subject connected in your head.

## The idea

Think of a well-run college.

**High cohesion**: the exam cell does exam things. It does not also run the
canteen. Everything inside it is about exams, so when exam rules change, you know
exactly which office to go to.

**Low coupling**: the exam cell and the hostel talk through a notice (a result is
published), not by the exam cell walking into the hostel office and editing its
registers. Either office can reorganise itself without the other noticing.

::compare{caption="The two properties, and which direction you want each."}
  :::compare-side{label="Coupling: want it LOW" verdict="neutral"}
  How much a class knows about, and depends on, other classes. **Tight** coupling:
  it reaches into their fields, creates their concrete classes, relies on how
  they work inside. **Loose** coupling: it talks through small interfaces.
  :::
  :::compare-side{label="Cohesion: want it HIGH" verdict="neutral"}
  How closely related the responsibilities inside one class are. **High**
  cohesion: every method serves one purpose. **Low** cohesion: a grab-bag
  `Utils` or `StudentManager` that does twelve unrelated things.
  :::
::

## How it works

Tight coupling and low cohesion, in one class:

```java [StudentManager.java]
public class StudentManager {
    MySqlDatabase db = new MySqlDatabase();          // creates a concrete class: tight
    GmailSender mail = new GmailSender();             // tight again

    void admit(Student s) {
        if (s.percentage < 60) return;                // admission rules
        db.connection.execute("INSERT ...");          // reaches into db's fields: tight
        mail.smtpHost = "smtp.gmail.com";             // configures someone else's internals
        mail.send(s.email, "Welcome");
    }
    double hostelFee(Student s) { ... }               // hostel billing
    String attendancePdf(Student s) { ... }           // report formatting
    void resetPassword(Student s) { ... }             // login
}
```

Four unrelated jobs (low cohesion), and it cannot be tested without MySQL and
Gmail (tight coupling). Now split and loosened:

```java [Admissions.java]
public class Admissions {
    interface StudentStore { void save(String name); }
    interface Mailer { void send(String to, String body); }

    private final StudentStore store;       // abstractions, handed in
    private final Mailer mailer;

    Admissions(StudentStore store, Mailer mailer) {
        this.store = store;
        this.mailer = mailer;
    }

    boolean admit(String name, String email, double percentage) {   // one job: admission
        if (percentage < 60) return false;
        store.save(name);
        mailer.send(email, "Welcome to CSE, " + name);
        return true;
    }

    public static void main(String[] args) {
        Admissions a = new Admissions(
            name -> System.out.println("saved " + name),
            (to, body) -> System.out.println("mail to " + to + ": " + body));

        System.out.println(a.admit("Anita Rao", "anita@univ.edu", 92.4));
        System.out.println(a.admit("Kiran Das", "kiran@univ.edu", 54.0));
    }
}
```

```text [Output]
saved Anita Rao
mail to anita@univ.edu: Welcome to CSE, Anita Rao
true
false
```

`Admissions` knows two tiny interfaces and nothing else. Hostel fees, PDFs and
passwords went to their own classes, each cohesive.

## Real use case: how the whole track connects

Every idea you learned is a tool for one of these two properties.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-unlink" title="Tools for low coupling"}
  Encapsulation (nobody reaches into your fields), abstraction and interfaces
  (depend on a contract), dependency inversion, composition over inheritance,
  Factory, Observer, Strategy.
  :::
  :::feature{icon="i-lucide-target" title="Tools for high cohesion"}
  Single responsibility, interface segregation, and splitting classes by
  "reason to change".
  :::
::

::pull-quote
If you remember one sentence from this track for the interview, make it this one:
good object-oriented design is low coupling and high cohesion, and everything
else is how you get there.
::

## What confuses people here

- **"Zero coupling is the goal."** A system with no coupling does nothing; its
  parts never talk. The goal is coupling through small, stable interfaces.
- **Cohesion is not size.** A 500-line class can be highly cohesive (one hard
  job) and a 50-line class can have low cohesion (five small unrelated jobs).
- **Inheritance is the tightest coupling in Java.** A child depends on the
  parent's internals, which is why composition was preferred two chapters ago.

## Interview questions

::accordion
  :::accordion-item{label="What are coupling and cohesion?" icon="i-lucide-message-circle"}
  Coupling is how much one class depends on others; aim low. Cohesion is how
  related the responsibilities inside one class are; aim high. Loosely coupled,
  highly cohesive code can change one part without breaking the rest.
  :::
  :::accordion-item{label="How do you reduce coupling in Java?" icon="i-lucide-message-circle"}
  Depend on interfaces, not concrete classes; inject dependencies through the
  constructor; keep fields private; prefer composition to inheritance; use
  events (Observer) instead of direct calls between unrelated parts.
  :::
  :::accordion-item{label="Give an example of low cohesion." icon="i-lucide-message-circle"}
  A `StudentManager` that admits students, calculates hostel fees, formats PDFs
  and resets passwords. Four reasons to change. Split into `Admissions`,
  `HostelBilling`, `AttendanceReport` and `Accounts`.
  :::
  :::accordion-item{label="How are coupling and cohesion related to SOLID?" icon="i-lucide-message-circle"}
  Single responsibility and interface segregation raise cohesion. Open/closed,
  Liskov and dependency inversion lower coupling. SOLID is five concrete ways to
  get low coupling and high cohesion.
  :::
::
