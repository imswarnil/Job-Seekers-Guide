Both of the problems at the end of the last lesson are **behavioural**: about how
objects talk to each other after they exist. **Observer** handles "tell everyone
who cares". **Strategy** handles "do this job, but let me choose how".

## Why this matters in a job

You have already used Observer: every `addEventListener` in the JavaScript track
is one. Every button click handler, every webhook, every "notify me when" feature
is one. Strategy is the pattern behind every `Comparator` you pass to `sort`.
Knowing their names turns "some callback thing" into a design you can explain.

## Observer: one publishes, many listen

**Observer** defines a one-to-many relationship: when one object (the **subject**
or **publisher**) changes state, every registered **observer** (or **subscriber**)
is notified automatically. The subject knows only that its observers implement an
interface, nothing more.

Like the exam cell's result notice. The cell does not phone each student, the
hostel warden and the placement office. They have all asked to be told, and when
the result is published, each one is.

::flow{caption="The subject keeps a list and calls one method on each."}
  :::flow-step{label="Subscribe" icon="i-lucide-bell-plus"}
  Observers register with the subject.
  :::
  :::flow-step{label="State changes" icon="i-lucide-file-check" highlight}
  The result is published.
  :::
  :::flow-step{label="Notify" icon="i-lucide-megaphone"}
  The subject loops over its list and calls `onResult(...)` on each.
  :::
::

```java [ExamCell.java]
import java.util.ArrayList;
import java.util.List;

public class ExamCell {
    interface ResultListener {
        void onResult(int roll, int marks);
    }

    private final List<ResultListener> listeners = new ArrayList<>();

    void subscribe(ResultListener l)   { listeners.add(l); }
    void unsubscribe(ResultListener l) { listeners.remove(l); }

    void publish(int roll, int marks) {
        for (ResultListener l : listeners) {
            l.onResult(roll, marks);
        }
    }

    static class Student implements ResultListener {
        public void onResult(int roll, int marks) {
            System.out.println("Student " + roll + ": you scored " + marks);
        }
    }

    static class PlacementOffice implements ResultListener {
        public void onResult(int roll, int marks) {
            if (marks >= 60) System.out.println("Placement: " + roll + " is eligible for drives");
        }
    }

    public static void main(String[] args) {
        ExamCell cell = new ExamCell();
        cell.subscribe(new Student());
        cell.subscribe(new PlacementOffice());
        cell.subscribe((roll, marks) -> {                // a lambda is an observer too
            if (marks < 40) System.out.println("Mentor: call " + roll + " this week");
        });

        cell.publish(2104, 78);
        cell.publish(2107, 34);
    }
}
```

```text [Output]
Student 2104: you scored 78
Placement: 2104 is eligible for drives
Student 2107: you scored 34
Mentor: call 2107 this week
```

The `ExamCell` has no idea a placement office or a mentor exists. Adding a fourth
listener next term changes nothing in it. That is **loose coupling**, the subject
of the next lesson.

## Strategy: swap the algorithm

**Strategy** defines a family of algorithms, puts each in its own class behind a
common interface, and lets the caller choose one at runtime. The object using it
holds a strategy and delegates to it.

Like how the university ranks applicants. The engineering admission ranks by
entrance score, the management quota by interview marks, the sports quota by
certificates. The admission process is the same; the ranking rule is swapped in.

```java [Ranking.java]
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class Ranking {
    record Applicant(String name, int entrance, int interview) { }

    interface RankingStrategy {
        List<Applicant> rank(List<Applicant> all);
    }

    static class ByEntrance implements RankingStrategy {
        public List<Applicant> rank(List<Applicant> all) {
            List<Applicant> copy = new ArrayList<>(all);
            copy.sort(Comparator.comparingInt(Applicant::entrance).reversed());
            return copy;
        }
    }

    static class ByInterview implements RankingStrategy {
        public List<Applicant> rank(List<Applicant> all) {
            List<Applicant> copy = new ArrayList<>(all);
            copy.sort(Comparator.comparingInt(Applicant::interview).reversed());
            return copy;
        }
    }

    // The context: holds a strategy, does not care which.
    static class AdmissionRound {
        private RankingStrategy strategy;
        AdmissionRound(RankingStrategy s) { this.strategy = s; }
        void setStrategy(RankingStrategy s) { this.strategy = s; }   // swap at runtime

        String topOf(List<Applicant> all) {
            return strategy.rank(all).get(0).name();
        }
    }

    public static void main(String[] args) {
        List<Applicant> pool = List.of(
            new Applicant("Anita", 182, 71),
            new Applicant("Rahul", 169, 88),
            new Applicant("Farhan", 175, 80));

        AdmissionRound round = new AdmissionRound(new ByEntrance());
        System.out.println("Engineering topper: " + round.topOf(pool));

        round.setStrategy(new ByInterview());
        System.out.println("Management topper: " + round.topOf(pool));
    }
}
```

```text [Output]
Engineering topper: Anita
Management topper: Rahul
```

No `if (quota.equals("MANAGEMENT"))` anywhere. A new quota is a new class. That
is the open/closed principle from the SOLID lesson, built with composition: the
round **has a** strategy.

## What confuses people here

::compare{caption="They look alike (an interface, several implementations). They answer different questions."}
  :::compare-side{label="Observer" verdict="neutral"}
  **Many** objects, all notified, about **something that happened**. The subject
  does not choose between them; it tells all of them.
  :::
  :::compare-side{label="Strategy" verdict="neutral"}
  **One** object chosen from several, to **do a job**. The context uses exactly
  one at a time.
  :::
::

- **Strategy against State.** Structurally identical; the difference is who
  switches. In Strategy the **caller** picks. In the State pattern the object
  switches **itself** as its state changes (an application moving from
  `RECEIVED` to `SHORTLISTED`). Name-check it if asked.
- **Forgetting to unsubscribe.** An observer that is never removed is never
  garbage-collected, because the subject still holds it. That is a real memory
  leak, called the **lapsed listener** problem.

## Interview questions

::accordion
  :::accordion-item{label="Explain the Observer pattern with an example." icon="i-lucide-message-circle"}
  A subject keeps a list of observers behind an interface and notifies all of them
  when its state changes. The exam cell publishes a result; the student, the
  placement office and a mentor each react. The subject does not know the
  concrete observers.
  :::
  :::accordion-item{label="Explain the Strategy pattern with an example." icon="i-lucide-message-circle"}
  A family of interchangeable algorithms behind one interface; a context holds
  one and delegates to it, and it can be swapped at runtime. `AdmissionRound`
  ranks by entrance or by interview depending on the strategy it holds.
  `Comparator` in `sort` is the JDK's version.
  :::
  :::accordion-item{label="Difference between Strategy and Observer?" icon="i-lucide-message-circle"}
  Observer notifies **all** registered listeners that something happened.
  Strategy uses **one** chosen algorithm to perform a task. Observer is about
  broadcasting events; Strategy is about choosing behaviour.
  :::
  :::accordion-item{label="Where have you used Observer without calling it that?" icon="i-lucide-message-circle"}
  `addEventListener` in JavaScript: the button is the subject, the handler is the
  observer. Any honest answer from your own code is better than a textbook one.
  :::
::
