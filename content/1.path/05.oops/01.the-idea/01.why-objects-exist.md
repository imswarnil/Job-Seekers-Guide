The DBMS track ended with data sitting safely in tables, one fact in one place.
The moment Java reads a row out of those tables, it has to hold it somewhere in
memory, and the way it holds it is an **object**. That is the subject this whole
track is about, and it starts with why anybody bothered.

## Why this matters in a job

Every Java, C#, Python and Salesforce Apex codebase you will join is organised
around objects. At Accenture, the first Salesforce code I read was Apex: classes
called `AccountService` and `OpportunityTriggerHandler`, and I could not follow
any of it until I stopped reading it line by line and started asking "which
object owns this?".

In interviews, "what is OOP and why do we use it?" is usually the **first**
technical question after "tell me about yourself". It sets the tone for the next
twenty minutes.

## Two ways to organise the same program

Think of a college office before and after it was organised.

Before: one big register on one desk. Anybody can write in any column. The fee
clerk, the exam clerk and the hostel warden all edit the same pages. It works
with three people. With forty, somebody overwrites somebody else's figure and
nobody knows who.

After: each department keeps its own file, and you ask the department when you
need something. You do not edit the accounts ledger. You ask Accounts, and
Accounts decides whether your request is allowed.

That is the whole difference.

::compare{caption="Same data, two ways of deciding who may touch it."}
  :::compare-side{label="Procedural" verdict="neutral"}
  Data sits in plain variables or structures. **Functions** operate on it from
  outside. Any function can change any data. C is the classic example.
  :::
  :::compare-side{label="Object-oriented" verdict="neutral"}
  Data and the functions allowed to change it live **together**, in an object.
  Outside code asks the object to do things; it does not reach in. Java, C#,
  Apex.
  :::
::

**Object-oriented programming (OOP)** is a way of organising a program around
objects: bundles of data (called **state** or **fields**) and the behaviour that
works on that data (called **methods**), where each object is responsible for
keeping its own data correct.

## How it works

The problem: a student's fee. The tuition is ₹85,000, hostel students pay
₹40,000 more, and nobody should ever be able to record a negative payment.

First, procedurally. Everything is a loose variable and a static function.

```java [FeeProcedural.java]
public class FeeProcedural {

    static int totalFee(boolean isHosteller) {
        int fee = 85000;
        if (isHosteller) fee += 40000;
        return fee;
    }

    public static void main(String[] args) {
        String studentName = "Anita Rao";
        boolean isHosteller = true;
        int paid = 0;

        paid += 50000;
        paid += -20000;          // nothing stops this

        int due = totalFee(isHosteller) - paid;
        System.out.println(studentName + " owes " + due);
    }
}
```

```text [Output]
Anita Rao owes 95000
```

It runs, and it is wrong. The ₹20,000 refund-that-was-a-typo went straight in,
because `paid` is a plain `int` that anybody can change.

Now the same thing, object-oriented.

```java [FeeAccount.java]
public class FeeAccount {
    private final String studentName;
    private final boolean hosteller;
    private int paid;

    public FeeAccount(String studentName, boolean hosteller) {
        this.studentName = studentName;
        this.hosteller = hosteller;
    }

    public void pay(int amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Payment must be positive: " + amount);
        }
        paid += amount;
    }

    public int due() {
        int fee = hosteller ? 125000 : 85000;
        return fee - paid;
    }

    public static void main(String[] args) {
        FeeAccount anita = new FeeAccount("Anita Rao", true);
        anita.pay(50000);
        System.out.println(anita.studentName + " owes " + anita.due());
        anita.pay(-20000);
    }
}
```

```text [Output]
Anita Rao owes 75000
Exception in thread "main" java.lang.IllegalArgumentException: Payment must be positive: -20000
	at FeeAccount.pay(FeeAccount.java:13)
	at FeeAccount.main(FeeAccount.java:27)
```

The bad payment is refused **at the door**, loudly, with the line number. The
rule lives in one place, `pay`, and there is no other way to change `paid`.

::flow{caption="What changed between the two versions."}
  :::flow-step{label="Data" icon="i-lucide-database"}
  Moved inside the object and marked `private`.
  :::
  :::flow-step{label="Rules" icon="i-lucide-shield-check" highlight}
  Moved next to the data, into the only method that can change it.
  :::
  :::flow-step{label="Callers" icon="i-lucide-users"}
  Ask the object (`pay`, `due`) instead of editing numbers.
  :::
::

## Real use case

In a real Java backend, a student record comes out of the database and becomes
an object. The rules about that record (a roll number cannot change, attendance
cannot go above 100%, a fee cannot be negative) are methods on that object or on
a service that owns it. Hundreds of screens and reports then use it without
knowing how the rules work.

```java [Attendance.java]
public class Attendance {
    private int held;
    private int attended;

    public void markPresent() { held++; attended++; }
    public void markAbsent()  { held++; }

    public double percentage() {
        return held == 0 ? 0 : attended * 100.0 / held;
    }

    public boolean isDetained() {
        return percentage() < 75;
    }
}
```

Nobody outside can set `attended` higher than `held`, because nobody outside can
set it at all. That guarantee is the reason OOP won.

::pros-cons
---
title: OOP, honestly
pros:
  - Rules live beside the data they protect, in one place
  - Large teams can work on separate objects without stepping on each other
  - Real-world things (student, course, payment) map naturally to classes
cons:
  - More code for small scripts; a 20-line job does not need five classes
  - Deep class hierarchies become harder to follow than the procedural code they replaced
  - Not the only good answer; functional programming solves some problems more cleanly
---
::

## What confuses people here

- **"OOP means using classes."** Java forces every line into a class, so the
  procedural version above is also in a class. It is still procedural, because
  the data is loose and the rules are not attached to it. OOP is about **who owns
  the data**, not the `class` keyword.
- **"OOP is faster."** It is not. It is about organising code for people, not
  for the processor.
- **"Java is 100% object-oriented."** It is not, and interviewers like this one.
  Java has eight primitive types (`int`, `double`, `boolean` and the rest) that
  are not objects, and `static` methods that belong to no object.

## Interview questions

::accordion
  :::accordion-item{label="What is OOP, and why do we use it?" icon="i-lucide-message-circle"}
  A way of organising a program around objects, each holding its own data and
  the methods allowed to change it. We use it because it keeps rules next to the
  data they protect, so a large codebase stays correct as it grows. Then show
  `FeeAccount.pay` refusing a negative amount: one method, one rule, no other way
  in.
  :::
  :::accordion-item{label="What is the difference between procedural and object-oriented programming?" icon="i-lucide-message-circle"}
  Procedural: data and functions are separate, functions act on data from
  outside, and any function can change any data. Object-oriented: data and
  behaviour are bundled into objects, and outside code asks the object rather
  than editing its data. C is procedural; Java is object-oriented.
  :::
  :::accordion-item{label="Is Java a pure object-oriented language?" icon="i-lucide-message-circle"}
  No. It has eight primitive types that are not objects, and static members that
  belong to the class rather than to any object.

  ```java [NotPure.java]
  int seats = 60;              // a primitive, not an object
  // seats.toString();         // does not compile: int has no methods
  Integer boxed = seats;       // the wrapper class is an object
  System.out.println(boxed.toString());
  ```
  :::
  :::accordion-item{label="Name the four pillars of OOP." icon="i-lucide-message-circle"}
  Encapsulation, abstraction, inheritance and polymorphism. Each one gets its own
  lesson in the next chapter. Name them in that order, then offer an example for
  whichever the interviewer picks.
  :::
::
