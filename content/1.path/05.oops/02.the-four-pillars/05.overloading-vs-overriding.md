Every rule for overriding comes from one promise: **a child must be usable
anywhere the parent is expected**, without the caller getting a surprise.
Overloading has fewer rules, because it is not a promise at all. It is only a
convenience with a shared name.

## Why this matters in a job

In the first month at a new job, you will override `toString()`, `equals()`,
a framework's `handle()` or `execute()`, and a test's `setUp()`. Get the
signature slightly wrong and, without `@Override`, your method silently never
runs. It is one of the most common silent bugs a code reviewer catches in a
fresher's first pull requests.

In interviews: "difference between overloading and overriding" is asked in nearly
every fresher round I sat. The table in this lesson is the answer.

## The idea

**Overloading**: several methods in the **same class** with the **same name** and
**different parameter lists**. Like the college library's `issue` counter: issue
by roll number, issue by roll number and due date, issue by ID card. Same
counter, different inputs.

**Overriding**: a **subclass** provides its own version of a method it inherited,
with the **same signature**. Like each department setting its own attendance rule
while the university's rule book says "every department has an attendance rule".

A method's **signature** is its name plus its parameter types, in order. The
return type is not part of the signature.

| | Overloading | Overriding |
| --- | --- | --- |
| Where | Same class (or inherited into a child) | Parent and child |
| Method name | Same | Same |
| Parameters | **Must differ** (number, type or order) | **Must be the same** |
| Return type | Can be anything | Same, or a subtype (**covariant**) |
| Access modifier | Anything | Same or **wider**, never narrower |
| Checked exceptions | Anything | Same, narrower, or none. **Never new or broader** |
| `static` / `private` / `final` | Can be overloaded | **Cannot** be overridden |
| Resolved | Compile time | Runtime |
| Polymorphism | Compile-time | Runtime |

## How it works

```java [Library.java]
import java.time.LocalDate;

public class Library {
    // Overloading: same name, parameter lists differ.
    static String issue(int roll)                     { return issue(roll, LocalDate.of(2026, 10, 13)); }
    static String issue(int roll, LocalDate due)      { return "Roll " + roll + ", due " + due; }
    static String issue(String idCard)                { return "Card " + idCard + ", due 14 days"; }

    // Not allowed: differs only in return type.
    // static int issue(int roll) { return 0; }       // error: method issue(int) is already defined

    public static void main(String[] args) {
        System.out.println(issue(2104));
        System.out.println(issue(2104, LocalDate.of(2026, 10, 20)));
        System.out.println(issue("LNCT-2104"));
    }
}
```

```text [Output]
Roll 2104, due 2026-10-13
Roll 2104, due 2026-10-20
Card LNCT-2104, due 14 days
```

Now overriding, showing every rule in one place.

```java [Rules.java]
import java.io.IOException;
import java.io.FileNotFoundException;

public class Rules {
    static class Report {
        protected Object build() throws IOException { return "generic"; }
    }

    static class AttendanceReport extends Report {
        @Override
        public String build() throws FileNotFoundException {  // wider access, narrower return, narrower exception
            return "attendance for CSE-2";
        }
    }

    public static void main(String[] args) throws IOException {
        Report r = new AttendanceReport();
        System.out.println(r.build());
    }
}
```

```text [Output]
attendance for CSE-2
```

::feature-list{columns="3"}
  :::feature{icon="i-lucide-arrow-up-right" title="Wider access: allowed"}
  `protected` became `public`. A caller that could reach the parent's method can
  still reach the child's.
  :::
  :::feature{icon="i-lucide-arrow-down-right" title="Narrower return: allowed"}
  `Object` became `String`. A caller expecting an `Object` is happy with a
  `String`. This is a **covariant return type**.
  :::
  :::feature{icon="i-lucide-shield" title="Narrower exception: allowed"}
  `IOException` became `FileNotFoundException`, a subclass of it. The caller's
  `catch (IOException e)` still catches it.
  :::
::

Reverse any of the three and the caller could be surprised, so the compiler
refuses. That is the reason behind every row of the table.

## Real use case: what @Override is for

`@Override` is optional. It is also the cheapest bug catcher in Java.

::compare{caption="A one-letter difference. Only the annotation notices."}
  :::compare-side{label="No annotation" verdict="wrong"}
  ```java [Silent.java]
  class Student {
      @Override
      public String toString() { return "Student"; }
  }
  class Hosteller extends Student {
      public String tostring() {     // lower-case s
          return "Hosteller in C-Block";
      }
  }
  ```
  Compiles. `tostring` is a brand-new method. Printing a hosteller shows
  `Student`, and nothing tells you why.
  :::
  :::compare-side{label="With @Override" verdict="right"}
  ```java [Loud.java]
  class Hosteller extends Student {
      @Override
      public String tostring() {
          return "Hosteller in C-Block";
      }
  }
  ```
  `error: method does not override or implement a method from a supertype`.
  Caught before it ran.
  :::
::

Put `@Override` on every overriding method, every time.

## What confuses people here

- **"Overloading by return type."** Not possible. `int issue(int)` and
  `String issue(int)` clash, because at the call `issue(2104)` the compiler has
  nothing to choose by.
- **"Can `main` be overloaded?"** Yes. You can write `main(int x)`. The JVM
  only ever calls `public static void main(String[] args)` as the entry point.
  Can `main` be overridden? No, it is static.
- **Overloading with `null` or autoboxing can be ambiguous.** With `issue(String)`
  and `issue(Integer)` both present, `issue(null)` does not compile:
  `reference to issue is ambiguous`. Cast it: `issue((String) null)`.

```java [Widening.java]
public class Widening {
    static void mark(long x)    { System.out.println("long"); }
    static void mark(Integer x) { System.out.println("Integer"); }

    public static void main(String[] args) {
        mark(75);   // int: widening to long beats boxing to Integer
    }
}
```

```text [Output]
long
```

The compiler prefers, in order: exact match, **widening** a primitive, then
**autoboxing**, then varargs. It is a favourite trick question in written tests.

## Interview questions

::accordion
  :::accordion-item{label="Difference between method overloading and overriding?" icon="i-lucide-message-circle"}
  Overloading: same name, different parameters, usually same class, resolved at
  compile time. Overriding: same signature in a subclass, replaces the parent's
  behaviour, resolved at runtime. Then give one rule each: overloading cannot
  differ by return type alone; overriding cannot reduce access or throw broader
  checked exceptions.
  :::
  :::accordion-item{label="Can we change the return type when overriding?" icon="i-lucide-message-circle"}
  Only to a subtype: a covariant return type. `Object build()` can become
  `String build()`. For primitives it must be identical.
  :::
  :::accordion-item{label="Can an overriding method throw a checked exception the parent does not?" icon="i-lucide-message-circle"}
  No. It may throw the same, a subclass of it, or none. Unchecked exceptions
  (`RuntimeException` and subclasses) are not restricted.
  :::
  :::accordion-item{label="Can we override a private or final method?" icon="i-lucide-message-circle"}
  No. Private methods are not visible to the child, so a same-named method is a
  new one. Final methods are forbidden from being overridden:
  `error: build() in AttendanceReport cannot override build() in Report; overridden method is final`.
  :::
  :::accordion-item{label="Is @Override mandatory? Why use it?" icon="i-lucide-message-circle"}
  Not mandatory. Use it because it makes the compiler check that you really are
  overriding, so a typo like `tostring` fails at compile time instead of silently
  never running.
  :::
::
