A hosteller and a day scholar share a roll number, a name and marks. Write that
once, in a `Student` class, and let both of them **inherit** it. That is the
third pillar, and it is also the one most often used where it should not be.

## Why this matters in a job

You will meet inheritance in every framework you use. In Salesforce Apex, a
trigger handler extends a base handler class. In Spring, your exception classes
extend `RuntimeException`. In Java itself, every class you have ever written
extends `Object` whether you typed it or not. You need to read inheritance
comfortably from day one.

In interviews, the questions are predictable: the types of inheritance, why Java
has no multiple inheritance of classes, and the diamond problem. Learn all three.

## The idea: is-a

A hosteller **is a** student. A professor **is a** faculty member. If "X is a Y"
reads as true in plain English, X can inherit from Y.

**Inheritance** is a mechanism where one class (the **child**, **subclass** or
**derived class**) acquires the fields and methods of another (the **parent**,
**superclass** or **base class**), and can add its own or change inherited
behaviour. In Java you write it with `extends`. Its main purpose is **code reuse**,
and it also makes runtime polymorphism possible (next lesson).

## How it works

```java [Campus.java]
public class Campus {

    static class Student {
        protected final int roll;
        protected final String name;

        Student(int roll, String name) {
            this.roll = roll;
            this.name = name;
        }

        int monthlyCharges() { return 0; }

        String describe() {
            return roll + " " + name + ", charges " + monthlyCharges();
        }
    }

    static class Hosteller extends Student {
        private final String block;

        Hosteller(int roll, String name, String block) {
            super(roll, name);          // the parent builds its part first
            this.block = block;
        }

        @Override
        int monthlyCharges() { return 6500; }   // mess and room

        String block() { return block; }        // something only a Hosteller has
    }

    static class DayScholar extends Student {
        DayScholar(int roll, String name) { super(roll, name); }

        @Override
        int monthlyCharges() { return 900; }    // college bus
    }

    public static void main(String[] args) {
        Hosteller anita = new Hosteller(2104, "Anita Rao", "C-Block");
        DayScholar rahul = new DayScholar(2105, "Rahul Menon");

        System.out.println(anita.describe() + ", " + anita.block());
        System.out.println(rahul.describe());
    }
}
```

```text [Output]
2104 Anita Rao, charges 6500, C-Block
2105 Rahul Menon, charges 900
```

`describe()` was written once, in `Student`, and it called the right
`monthlyCharges()` for each child. That last part is polymorphism, and it is why
inheritance and polymorphism are always taught together.

## The five types

::tabs
  :::tabs-item{label="Single"}
  One child, one parent. `Hosteller extends Student`.
  :::
  :::tabs-item{label="Multilevel"}
  A chain. `Person` → `Faculty` → `Professor`. The professor inherits from both
  above it.
  :::
  :::tabs-item{label="Hierarchical"}
  Many children, one parent. `Hosteller` and `DayScholar` both extend `Student`.
  :::
  :::tabs-item{label="Multiple"}
  One child, two parents. `class TeachingAssistant extends Student, Faculty`.
  **Java does not allow this with classes.** It does allow a class to implement
  several interfaces.
  :::
  :::tabs-item{label="Hybrid"}
  A mix of two or more of the above. With classes alone Java cannot do the
  version that needs multiple inheritance; with interfaces it can.
  :::
::

```java [Multilevel.java]
public class Multilevel {
    static class Person   { String greet() { return "Person"; } }
    static class Faculty  extends Person  { String dept = "CSE"; }
    static class Professor extends Faculty { String chair = "Databases"; }

    public static void main(String[] args) {
        Professor p = new Professor();
        System.out.println(p.greet() + ", " + p.dept + ", " + p.chair);
    }
}
```

```text [Output]
Person, CSE, Databases
```

If `TeachingAssistant` inherited from both, `ta.idCardColour()` would be
ambiguous, and so would which copy of `Person`'s fields it holds. C++ allows it
and makes the programmer resolve it. Java's designers chose to forbid it for
classes.

Interfaces can still meet in a diamond, since Java 8 added `default` methods.
Java's answer: if two interfaces give the same default method, **the class must
override it** and choose, or it does not compile.

```java [Diamond.java]
public class Diamond {
    interface Student { default String idCardColour() { return "blue"; } }
    interface Faculty { default String idCardColour() { return "red"; } }

    static class TeachingAssistant implements Student, Faculty {
        @Override
        public String idCardColour() {
            return Faculty.super.idCardColour();   // the class decides, explicitly
        }
    }

    public static void main(String[] args) {
        System.out.println(new TeachingAssistant().idCardColour());
    }
}
```

```text [Output]
red
```

Remove that override and it does not compile:

```text [Compiler]
Diamond.java:5: error: types Student and Faculty are incompatible;
  class TeachingAssistant inherits unrelated defaults for idCardColour() from types Student and Faculty
```

## Real use case

The most common inheritance you will write at work is a custom exception.

```java [FeeNotPaidException.java]
public class FeeNotPaidException extends RuntimeException {
    private final int rollNumber;

    public FeeNotPaidException(int rollNumber, int due) {
        super("Roll " + rollNumber + " has Rs " + due + " due; hall ticket blocked");
        this.rollNumber = rollNumber;
    }

    public int getRollNumber() { return rollNumber; }

    public static void main(String[] args) {
        try {
            throw new FeeNotPaidException(2104, 42000);
        } catch (RuntimeException e) {           // caught as its parent type
            System.out.println(e.getMessage());
        }
    }
}
```

```text [Output]
Roll 2104 has Rs 42000 due; hall ticket blocked
```

It **is a** `RuntimeException`, so every piece of code that handles runtime
exceptions handles it too, and it adds the one field this situation needs.

## What confuses people here

- **"Private members are inherited."** The child object does contain the
  parent's private fields in memory, but the child's code **cannot access** them.
  For the interview, say: private members are not accessible in the subclass.
  Use `protected` or a getter.
- **"Constructors are inherited."** They are not; the child calls them with
  `super(...)`.
- **"Inheritance is always the right way to reuse code."** It is the tightest
  coupling there is between two classes. A change in the parent can break every
  child. The composition lesson in the next chapter is about when not to use it.

::warning{icon="i-lucide-alert-triangle"}
Test every `extends` with the is-a sentence out loud. "A `FeePayment` is a
`Student`" is false, so `FeePayment extends Student` is wrong even if it would
save you three fields. That mistake is how codebases end up with classes nobody
can change.
::

## Interview questions

::accordion
  :::accordion-item{label="What is inheritance? What is its main advantage?" icon="i-lucide-message-circle"}
  A child class acquiring the fields and methods of a parent with `extends`,
  modelling an is-a relationship. Advantages: code reuse, and it enables runtime
  polymorphism (`Student s = new Hosteller(...)`). Show `describe()` written once
  and working for both children.
  :::
  :::accordion-item{label="What are the types of inheritance? Which does Java support?" icon="i-lucide-message-circle"}
  Single, multilevel, hierarchical, multiple, hybrid. With classes, Java supports
  single, multilevel and hierarchical. Multiple (and hybrid that needs it) only
  through interfaces.
  :::
  :::accordion-item{label="Why does Java not support multiple inheritance of classes?" icon="i-lucide-message-circle"}
  The diamond problem: two parents with the same method (or the same inherited
  state) make the child ambiguous. Java avoids it for classes. For interfaces with
  conflicting `default` methods, the class must override and pick one with
  `Faculty.super.idCardColour()`.
  :::
  :::accordion-item{label="Which class is the parent of every class in Java?" icon="i-lucide-message-circle"}
  `java.lang.Object`. A class with no `extends` implicitly extends it, which is
  why every object has `toString()`, `equals()` and `hashCode()`.
  :::
  :::accordion-item{label="Can a subclass access the private members of its parent?" icon="i-lucide-message-circle"}
  No. They exist in the object but are not accessible from the subclass code.
  Mark them `protected` or expose a getter.
  :::
::
