At runtime, by looking at the **real object**, not at the type of the variable.
`describe()` asked for `monthlyCharges()`, and the JVM went to Anita's actual
object, found a `Hosteller`, and ran the `Hosteller` version. One call, two
behaviours: that is **polymorphism**.

::warning{icon="i-lucide-alert-triangle"}
This is the pillar where most freshers lose the interviewer. Not because it is
hard, but because "many forms" is the only sentence they have. Slow down here.
The difference between what the **compiler** decides and what the **JVM** decides
is the whole lesson.
::

## Why this matters in a job

Polymorphism is what lets you add a new kind of thing without editing the code
that uses it. A new fee type, a new notification channel, a new report format:
write one new class, and the loop that processes all of them keeps working. Every
design pattern in the last chapter of this track is built on it.

## The idea: one instruction, many responses

The principal announces over the tannoy: "Everyone, submit your attendance for
the day." Class teachers send a register, the lab in-charge sends a lab log, the
hostel warden sends a night roll-call. **One instruction, each receiver responds
in its own way.** The principal does not need to know who is listening.

**Polymorphism** ("many forms") is the ability of one method call, or one name, to
behave differently depending on the object or the arguments involved. Java has two
kinds, and the question is always **when** the decision is made.

::compare{caption="The two kinds. Learn this table."}
  :::compare-side{label="Compile-time (static)" verdict="neutral"}
  Achieved by **method overloading**: same name, different parameter lists. The
  **compiler** picks which one from the arguments. Also called **static binding**
  or **early binding**.
  :::
  :::compare-side{label="Runtime (dynamic)" verdict="neutral"}
  Achieved by **method overriding**: a child replaces a parent's method. The
  **JVM** picks which one from the actual object. Also called **dynamic binding**,
  **late binding** or **dynamic method dispatch**.
  :::
::

## How it works

Compile-time first. Three methods named `fee`, told apart by their parameters.

```java [FeeDesk.java]
public class FeeDesk {
    static int fee(int credits)                    { return credits * 4000; }
    static int fee(int credits, boolean hosteller) { return fee(credits) + (hosteller ? 40000 : 0); }
    static double fee(double lateDays)             { return lateDays * 50.0; }

    public static void main(String[] args) {
        System.out.println(fee(20));          // compiler picks fee(int)
        System.out.println(fee(20, true));    // fee(int, boolean)
        System.out.println(fee(3.0));         // fee(double)
    }
}
```

```text [Output]
80000
120000
150.0
```

The compiler looked at the arguments and wired each call to one method before the
program ever ran.

Now runtime. The variable is typed as the parent; the object is a child. Pointing
a parent-type reference at a child object is called **upcasting**, and it is
always allowed because a hosteller is a student.

```java [Dispatch.java]
import java.util.List;

public class Dispatch {
    static class Student {
        String name;
        Student(String name) { this.name = name; }
        int monthlyCharges() { return 0; }
    }
    static class Hosteller extends Student {
        Hosteller(String name) { super(name); }
        @Override int monthlyCharges() { return 6500; }
    }
    static class DayScholar extends Student {
        DayScholar(String name) { super(name); }
        @Override int monthlyCharges() { return 900; }
    }
    static class Scholarship extends Student {
        Scholarship(String name) { super(name); }
        @Override int monthlyCharges() { return 0; }
    }

    public static void main(String[] args) {
        List<Student> batch = List.of(          // every element typed as Student
            new Hosteller("Anita Rao"),
            new DayScholar("Rahul Menon"),
            new Scholarship("Farhan Ali")
        );

        int total = 0;
        for (Student s : batch) {
            int c = s.monthlyCharges();        // which version? decided per object, at runtime
            System.out.println(s.name + ": " + c);
            total += c;
        }
        System.out.println("Total: " + total);
    }
}
```

```text [Output]
Anita Rao: 6500
Rahul Menon: 900
Farhan Ali: 0
Total: 7400
```

The loop has no `if`, no `instanceof`, no type check. Add a `NightSchool` student
next year and this loop does not change.

::code-trace{caption="What the compiler checks, and what the JVM decides"}
```java [TwoSteps.java]
Student s = new Hosteller("Anita Rao");
int c = s.monthlyCharges();
```

  :::code-trace-step{lines="1" caption="The reference type is Student. The object type is Hosteller. Upcasting, always legal."}
  :::
  :::code-trace-step{lines="2" caption="Compile time: the compiler checks Student has a monthlyCharges() method. It does, so this compiles."}
  :::
  :::code-trace-step{lines="2" caption="Runtime: the JVM looks at the real object, finds a Hosteller, and runs the Hosteller override. 6500."}
  :::
::

::pull-quote
The reference type decides **what you may call**. The object type decides **what
actually runs**.
::

## Real use case

Downcasting is the reverse of upcasting: treating a parent reference as a child
type. It needs an explicit cast and can fail at runtime, so you check first.

```java [Downcast.java]
public class Downcast {
    static class Student { }
    static class Hosteller extends Student { String block() { return "C-Block"; } }
    static class DayScholar extends Student { }

    public static void main(String[] args) {
        Student s = new Hosteller();
        // s.block();                       // does not compile: Student has no block()

        if (s instanceof Hosteller h) {      // pattern matching, Java 16+
            System.out.println("Block: " + h.block());
        }

        Student d = new DayScholar();
        Hosteller wrong = (Hosteller) d;     // compiles, fails at runtime
    }
}
```

```text [Output]
Block: C-Block
Exception in thread "main" java.lang.ClassCastException: class Downcast$DayScholar cannot be cast to class Downcast$Hosteller (Downcast$DayScholar and Downcast$Hosteller are in unnamed module of loader com.sun.tools.javac.launcher.Main$MemoryClassLoader @6d4b1c02)
	at Downcast.main(Downcast.java:15)
```

In real code, a pile of `instanceof` checks is usually a sign that the method
should have been overridden instead. Reach for polymorphism first.

## What confuses people here

Two things look like they should be polymorphic and are not.

```java [NotPolymorphic.java]
public class NotPolymorphic {
    static class Student {
        String type = "student";
        static String office() { return "Admissions"; }
    }
    static class Hosteller extends Student {
        String type = "hosteller";                     // hides the field
        static String office() { return "Warden"; }    // hides the static method
    }

    public static void main(String[] args) {
        Student s = new Hosteller();
        System.out.println(s.type);
        System.out.println(s.office());
    }
}
```

```text [Output]
student
Admissions
```

- **Fields are not polymorphic.** `s.type` is resolved by the **reference** type,
  so it says `student`. Only methods are dispatched on the object.
- **Static methods are not overridden, they are hidden.** They belong to the class,
  not the object, so the compiler binds them by the reference type. This is the
  "can you override a static method?" question, and the answer is no.
- Also not overridable: `private` methods (the child cannot see them) and `final`
  methods (forbidden on purpose).

## Interview questions

::accordion
  :::accordion-item{label="What is polymorphism? What are its types?" icon="i-lucide-message-circle"}
  One call behaving differently depending on the object or arguments. Two types:
  compile-time (overloading, resolved by the compiler) and runtime (overriding,
  resolved by the JVM from the actual object). Show the `batch` loop: one call to
  `monthlyCharges()`, three results.
  :::
  :::accordion-item{label="What is dynamic method dispatch?" icon="i-lucide-message-circle"}
  The mechanism behind runtime polymorphism: a call on a parent-type reference is
  resolved at runtime to the overriding method of the actual object.
  `Student s = new Hosteller(); s.monthlyCharges();` runs `Hosteller`'s version.
  :::
  :::accordion-item{label="Can we override a static method?" icon="i-lucide-message-circle"}
  No. A static method with the same signature in a child **hides** the parent's.
  The call is bound by reference type at compile time, so
  `Student s = new Hosteller(); s.office()` returns the `Student` version.
  :::
  :::accordion-item{label="Are fields polymorphic in Java?" icon="i-lucide-message-circle"}
  No. A field with the same name in a child hides the parent's, and access is
  resolved by the reference type. That is one more reason to keep fields private
  and expose methods.
  :::
  :::accordion-item{label="What is upcasting and downcasting?" icon="i-lucide-message-circle"}
  Upcasting: a child object referred to by a parent type, implicit and always
  safe. Downcasting: a parent reference cast to a child type, explicit and can
  throw `ClassCastException`, so guard it with `instanceof`.
  :::
  :::accordion-item{label="Static binding against dynamic binding?" icon="i-lucide-message-circle"}
  Static binding happens at compile time, for overloaded, static, private and
  final methods. Dynamic binding happens at runtime, for overridden instance
  methods.
  :::
::
