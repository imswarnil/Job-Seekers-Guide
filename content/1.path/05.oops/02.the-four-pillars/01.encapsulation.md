Nothing stops it, unless the field is `private` and the only way to change it is
a method that checks. That arrangement is **encapsulation**, and it is the pillar
the other three lean on.

## Why this matters in a job

Every validation rule in a real system has to live somewhere. If it lives in the
screens, the API, the batch job and the report separately, one of the four will
forget it. Encapsulation puts it in the object, so it cannot be forgotten.

In interviews it is usually the first pillar asked, and the most common weak
answer is "making fields private and adding getters and setters". That is the
mechanism, not the idea, and a good interviewer will ask why.

## The idea: a capsule with one door

A medicine capsule keeps the powder inside and gives you one way to take it.
The college exam cell works the same way. You cannot walk into the strongroom and
change your marks. You submit a revaluation request at the counter, and the exam
cell decides whether the change is allowed.

**Encapsulation** is bundling an object's data with the methods that operate on
it, and **restricting direct access** to that data, so every change goes through
code that can enforce the rules. The rules that must always hold for an object
are called its **invariants**: marks between 0 and 100, attendance never above
classes held.

::flow{caption="Every change goes through one door."}
  :::flow-step{label="Caller" icon="i-lucide-user"}
  Wants to change the marks.
  :::
  :::flow-step{label="Public method" icon="i-lucide-door-open" highlight}
  `revalue(newMarks, approvedBy)` checks the range and the approval.
  :::
  :::flow-step{label="Private field" icon="i-lucide-lock"}
  `marks` changes only if the check passed.
  :::
::

## How it works

Wrong first. Public fields, and a caller that means well.

```java [ExamResultOpen.java]
public class ExamResultOpen {
    public String subject;
    public int marks;

    public static void main(String[] args) {
        ExamResultOpen r = new ExamResultOpen();
        r.subject = "Operating Systems";
        r.marks = 68;

        r.marks = r.marks + 40;   // a grace-marks script with a bug
        System.out.println(r.subject + ": " + r.marks);
    }
}
```

```text [Output]
Operating Systems: 108
```

A mark of 108 out of 100, stored and printed with no error. Now encapsulated.

```java [ExamResult.java]
public class ExamResult {
    private final String subject;
    private int marks;
    private boolean revalued;

    public ExamResult(String subject, int marks) {
        this.subject = subject;
        setMarks(marks);
    }

    public int getMarks() {
        return marks;
    }

    public void revalue(int newMarks, String approvedBy) {
        if (revalued) {
            throw new IllegalStateException("Already revalued once");
        }
        if (approvedBy == null) {
            throw new IllegalArgumentException("Revaluation needs an approver");
        }
        setMarks(newMarks);
        revalued = true;
    }

    private void setMarks(int marks) {
        if (marks < 0 || marks > 100) {
            throw new IllegalArgumentException("Marks must be 0 to 100, got " + marks);
        }
        this.marks = marks;
    }

    public static void main(String[] args) {
        ExamResult r = new ExamResult("Operating Systems", 68);
        r.revalue(72, "Dr. Iyer");
        System.out.println(r.subject + ": " + r.getMarks());

        try {
            r.revalue(80, "Dr. Iyer");
        } catch (IllegalStateException e) {
            System.out.println("Refused: " + e.getMessage());
        }
    }
}
```

```text [Output]
Operating Systems: 72
Refused: Already revalued once
```

Two rules (the range, and only one revaluation) that no caller can break,
because no caller can reach `marks`. Note there is **no public `setMarks`**. The
business does not "set marks"; it revalues them, with an approver. The method
names the real action.

## Real use case

The collection trap. A `private` field that holds a list is not protected if you
hand the list out.

```java [Timetable.java]
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Timetable {
    private final List<String> subjects = new ArrayList<>();

    public void add(String subject) {
        if (subjects.size() == 6) throw new IllegalStateException("Six subjects maximum");
        subjects.add(subject);
    }

    // Leaks: the caller gets the real list and can add a seventh.
    public List<String> leakySubjects() { return subjects; }

    // Safe: a read-only view.
    public List<String> getSubjects() { return Collections.unmodifiableList(subjects); }

    public static void main(String[] args) {
        Timetable t = new Timetable();
        for (int i = 1; i <= 6; i++) t.add("Subject " + i);

        t.leakySubjects().add("Subject 7");
        System.out.println("After the leak: " + t.getSubjects().size());

        try {
            t.getSubjects().add("Subject 8");
        } catch (UnsupportedOperationException e) {
            System.out.println("The safe view refused");
        }
    }
}
```

```text [Output]
After the leak: 7
The safe view refused
```

`private` protected the variable, not the list it pointed at. This is the
follow-up question that separates a real answer from a memorised one.

## What confuses people here

- **"Encapsulation means getters and setters."** A class with a private field
  and a public setter that accepts anything is not encapsulated. It is a public
  field with extra typing. Only add a setter if there is a real action to model,
  and make it check.
- **"Encapsulation and data hiding are the same."** Close, but interviewers
  separate them. **Data hiding** is the restriction (`private`).
  **Encapsulation** is the bundling of data with the behaviour that guards it.
  Hiding is how you achieve encapsulation.
- **"Encapsulation and abstraction are the same."** No, and that is the next
  lesson. Encapsulation hides the **data**. Abstraction hides the **complexity**.

::side-note{kind="security"}
If the only thing stopping a student editing their own marks is that the screen
has no edit button, anyone who calls the API directly edits them. Rules belong in
the object and on the server, never only in the interface.
::

## Interview questions

::accordion
  :::accordion-item{label="What is encapsulation?" icon="i-lucide-message-circle"}
  Bundling data with the methods that act on it, and restricting direct access to
  the data so every change passes through code that enforces the rules. Show
  `ExamResult`: `marks` is private, and the only way to change it is `revalue`,
  which checks the range and the approver.
  :::
  :::accordion-item{label="How do you achieve encapsulation in Java?" icon="i-lucide-message-circle"}
  Make fields `private`, expose behaviour through `public` methods that validate,
  and do not hand out references to mutable internals (return copies or
  unmodifiable views). Make fields `final` where they should never change.
  :::
  :::accordion-item{label="Difference between encapsulation and data hiding?" icon="i-lucide-message-circle"}
  Data hiding is restricting access, the `private` keyword. Encapsulation is the
  wider idea of keeping data and the behaviour that guards it together. You use
  data hiding to achieve encapsulation.
  :::
  :::accordion-item{label="A field is private. Can outside code still change it?" icon="i-lucide-message-circle"}
  Yes, if the field is a mutable object and a getter returns it. The caller gets
  the same list and can add to it. Return `Collections.unmodifiableList(...)` or
  `List.copyOf(...)` instead. (Reflection can also bypass `private`, but that is
  deliberate misuse, not a design flaw.)
  :::
  :::accordion-item{label="What are the benefits of encapsulation?" icon="i-lucide-message-circle"}
  Rules enforced in one place, the internal representation can change without
  breaking callers (store marks as a `double` tomorrow, `getMarks()` still
  returns an `int`), easier testing, and bugs that are traceable to one method.
  :::
::

The caller of `revalue` has no idea how the rules are checked, and does not need
one. That is a different kind of hiding from a private field. It is hiding **how**
something works, not **what** it holds, and it is the pillar freshers confuse
with this one most.
