Has-a comes in three strengths, and one question sorts them: **if the owner is
destroyed, does the part go with it?** A department closing does not delete its
professors. A student record being deleted does delete their ID card.

## Why this matters in a job

Because this is what real class design mostly is. When you read an entity model
at work (a `Student` with a list of `Enrolment`s, an `Enrolment` with a `Course`)
every arrow on that diagram is one of these three. It also decides real behaviour:
what gets deleted when a row is deleted, which is the `ON DELETE CASCADE` question
from the DBMS track in object form.

And "composition over inheritance" is the design principle interviewers use to
check whether you have written anything bigger than an exercise.

## The idea: three strengths of has-a

::flow{caption="From weakest to strongest link."}
  :::flow-step{label="Association" icon="i-lucide-link"}
  Two objects **use** or know each other. Neither owns the other. A student and a
  faculty advisor.
  :::
  :::flow-step{label="Aggregation" icon="i-lucide-folder-open"}
  A whole **has** parts, but the parts can exist on their own. A department has
  professors; close the department and the professors still exist.
  :::
  :::flow-step{label="Composition" icon="i-lucide-package" highlight}
  A whole **owns** parts that cannot exist without it. A student has an ID card;
  delete the student and the card goes too.
  :::
::

**Association** is the general term: any relationship where one object holds or
uses a reference to another. **Aggregation** and **composition** are special
kinds of association that describe ownership. Aggregation is sometimes called a
"weak has-a" and composition a "strong has-a".

In UML diagrams (the standard notation for drawing classes), aggregation is a
line with a hollow diamond at the owner and composition a filled diamond.

## How it works

```java [University.java]
import java.util.ArrayList;
import java.util.List;

public class University {

    // Association: a Student knows an advisor. Each lives independently.
    static class Faculty {
        final String name;
        Faculty(String name) { this.name = name; }
    }

    // Composition: the IdCard is created by, and only for, its Student.
    static class IdCard {
        final String number;
        private IdCard(String number) { this.number = number; }
    }

    static class Student {
        final String name;
        final IdCard card;               // composition: created inside, never shared
        Faculty advisor;                  // association: set from outside, can change

        Student(int roll, String name) {
            this.name = name;
            this.card = new IdCard("LNCT-" + roll);
        }
    }

    // Aggregation: a Department holds Faculty it did not create.
    static class Department {
        final String name;
        final List<Faculty> members = new ArrayList<>();
        Department(String name) { this.name = name; }
        void add(Faculty f) { members.add(f); }
    }

    public static void main(String[] args) {
        Faculty iyer = new Faculty("Dr. Iyer");        // exists before any department

        Department cse = new Department("CSE");
        cse.add(iyer);

        Student anita = new Student(2104, "Anita Rao");
        anita.advisor = iyer;

        System.out.println(anita.name + ", card " + anita.card.number + ", advisor " + anita.advisor.name);

        cse = null;       // the department is gone
        System.out.println("Advisor still here: " + iyer.name);

        anita = null;     // the student is gone; nothing else references the card, so it is collected with her
    }
}
```

```text [Output]
Anita Rao, card LNCT-2104, advisor Dr. Iyer
Advisor still here: Dr. Iyer
```

The code signs are worth memorising, because they are how you tell them apart
when reading someone else's class:

::feature-list{columns="3"}
  :::feature{icon="i-lucide-link" title="Association"}
  A reference set from outside, often changeable. `anita.advisor = iyer;`
  :::
  :::feature{icon="i-lucide-folder-open" title="Aggregation"}
  Parts **passed in** from outside, in a collection. `cse.add(iyer);`
  :::
  :::feature{icon="i-lucide-package" title="Composition"}
  Parts **created inside** the owner and not handed out. `new IdCard(...)` in the
  constructor.
  :::
::

## Composition over inheritance

The Java track taught `extends` early, and it is tempting to use it for every
reuse. Here is where that goes.

::compare{caption="Reusing a List's behaviour, two ways."}
  :::compare-side{label="Inheritance: Section is-a ArrayList" verdict="wrong"}
  ```java [SectionBad.java]
  class Section extends ArrayList<String> {
      @Override
      public boolean add(String name) {
          if (size() == 60) throw new IllegalStateException("Section full");
          return super.add(name);
      }
  }
  ```
  `section.addAll(seventyNames)` goes straight past the limit (ArrayList's
  `addAll` does not call `add`), and so does `section.add(0, name)`. The class
  also exposes `clear()`, `remove()` and forty other methods a section should not
  have. You inherited **all** of it.
  :::
  :::compare-side{label="Composition: Section has-a List" verdict="right"}
  ```java [Section.java]
  class Section {
      private final List<String> students = new ArrayList<>();

      void enrol(String name) {
          if (students.size() == 60) throw new IllegalStateException("Section full");
          students.add(name);
      }
      int size() { return students.size(); }
  }
  ```
  Exactly two operations, both checked. Swap `ArrayList` for anything tomorrow and
  no caller notices.
  :::
::

```java [OverLimit.java]
import java.util.ArrayList;
import java.util.Collections;

public class OverLimit {
    static class Section extends ArrayList<String> {
        @Override
        public boolean add(String name) {
            if (size() == 60) throw new IllegalStateException("Section full");
            return super.add(name);
        }
    }

    public static void main(String[] args) {
        Section s = new Section();
        s.addAll(Collections.nCopies(70, "student"));
        System.out.println("Seats in a 60-seat section: " + s.size());
    }
}
```

```text [Output]
Seats in a 60-seat section: 70
```

This is called the **fragile base class** problem: the child depends on how the
parent works internally, which the parent never promised. **Composition over
inheritance** is the principle: prefer holding an object and delegating to it
over extending it, unless there is a true, stable is-a relationship.

::pros-cons
---
title: Composition over inheritance
pros:
  - You expose only the operations you choose
  - The part can be swapped at runtime (a different fee calculator per student)
  - Changes inside the part do not break the owner
cons:
  - A few more lines, because you write the delegating methods
  - Where a real is-a exists (a custom exception), inheritance is simpler and correct
---
::

## What confuses people here

- **Aggregation against composition is about lifetime, not about lists.** A
  `Department` with one `Faculty` field is still aggregation; a `Student` with a
  list of `ExamResult`s it created is still composition.
- **Java has no keyword for any of these.** You show the relationship by who
  creates the part and whether it is shared. In an interview, draw it and say the
  lifetime rule.
- **"Composition over inheritance means never inherit."** It means prefer. It is
  a default, not a ban.

## Interview questions

::accordion
  :::accordion-item{label="Difference between association, aggregation and composition?" icon="i-lucide-message-circle"}
  All three are has-a. Association: objects know each other, no ownership
  (student and advisor). Aggregation: whole and parts, parts live independently
  (department and professors). Composition: whole owns parts, parts die with it
  (student and ID card). The test is lifetime.
  :::
  :::accordion-item{label="Difference between is-a and has-a?" icon="i-lucide-message-circle"}
  Is-a is inheritance: `Hosteller extends Student`. Has-a is composition or
  aggregation: `Student` has an `IdCard` field. Test with the sentence out loud.
  :::
  :::accordion-item{label="What does composition over inheritance mean? Why?" icon="i-lucide-message-circle"}
  Prefer holding an instance and delegating to it over extending a class.
  Inheritance exposes everything the parent has and couples you to its internals
  (the `addAll` bypass above). Composition exposes only what you choose and can be
  swapped.
  :::
  :::accordion-item{label="Give a real example of composition from the JDK." icon="i-lucide-message-circle"}
  `HashSet` is built on a `HashMap` it creates internally and never exposes. Every
  `add` on the set is a `put` on the private map. The set has-a map; it is not a
  map.
  :::
::
