Since Java 8, an interface can have `default` and `static` methods with real
bodies, and since Java 9, `private` ones too. So "interface is 100% abstract" is
an answer from before most of today's freshers were in school. The real
difference is somewhere else, and it is simpler.

## Why this matters in a job

Every framework you use hands you both. Spring gives you interfaces to implement
(`Repository`, `Filter`) and abstract classes to extend. Knowing which is which
tells you whether you are signing up to a contract or inheriting a half-built
machine. When you design your own code, this is the first real design decision
you will be asked to justify in a code review.

## The idea: a contract against a half-built house

An **interface** is a contract: "anything that is `Payable` can `pay(amount)`".
It says what, not how, and anything can sign it. A student, a vendor and a
canteen can all be `Payable` with nothing else in common.

An **abstract class** is a half-built house: some rooms finished (concrete
methods and fields), some left for the buyer (abstract methods). It is a parent
you extend, sharing both code and state with its children.

An **abstract class** is declared with `abstract`, cannot be instantiated, and
can have constructors, fields of any kind, concrete methods and `abstract`
methods (declared with no body). An **interface** declares a type through method
signatures; its fields are always `public static final` constants, and it has no
constructors.

| | Abstract class | Interface |
| --- | --- | --- |
| Keyword to use it | `extends` | `implements` |
| How many per class | **One** | **Many** |
| Constructors | Yes | No |
| Fields | Any: instance, private, mutable | Only `public static final` constants |
| Methods | Abstract and concrete, any access | Abstract, `default`, `static`, `private` (Java 9+) |
| Access of methods | Any | `public` by default |
| State per object | Yes | No |
| Models | **is-a** with shared code | **can-do**, a capability |

::pull-quote
If the classes share **state and code**, use an abstract class. If they share
only a **capability**, use an interface. When in doubt, start with the interface.
::

## How it works

```java [Exams.java]
import java.util.List;

public class Exams {

    // Capability: many unrelated things can be graded.
    interface Gradable {
        int MAX = 100;                           // implicitly public static final

        int marks();

        default char grade() {                   // Java 8: a body in an interface
            int m = marks();
            return m >= 90 ? 'A' : m >= 75 ? 'B' : m >= 50 ? 'C' : 'F';
        }
    }

    // Shared state and code: every exam has a subject and a duration.
    static abstract class Exam implements Gradable {
        private final String subject;
        protected final int obtained;

        Exam(String subject, int obtained) {    // abstract classes have constructors
            this.subject = subject;
            this.obtained = obtained;
        }

        abstract int durationMinutes();          // each child must decide

        String summary() {                       // shared, concrete
            return subject + " (" + durationMinutes() + " min): " + marks() + "/" + MAX + " " + grade();
        }
    }

    static class Theory extends Exam {
        Theory(String s, int m) { super(s, m); }
        int durationMinutes() { return 180; }
        public int marks() { return obtained; }
    }

    static class Practical extends Exam {
        private final int viva;
        Practical(String s, int m, int viva) { super(s, m); this.viva = viva; }
        int durationMinutes() { return 120; }
        public int marks() { return obtained + viva; }
    }

    // Not an Exam at all, and still Gradable.
    record Project(String title, int marks) implements Gradable { }

    public static void main(String[] args) {
        List<Exam> exams = List.of(new Theory("DBMS", 78), new Practical("DBMS Lab", 70, 22));
        exams.forEach(e -> System.out.println(e.summary()));

        Gradable p = new Project("Library system", 88);
        System.out.println("Project grade: " + p.grade());

        // new Exam("x", 1);   // error: Exam is abstract; cannot be instantiated
    }
}
```

```text [Output]
DBMS (180 min): 78/100 B
DBMS Lab (120 min): 92/100 A
Project grade: B
```

`Project` is not an exam, has no subject and no duration, and it can still be
graded, because `Gradable` is a capability, not a family.

## Real use case

The JDK is full of this pattern: an interface for the contract, and an abstract
class that implements most of it so you do not have to.

::flow{caption="Interface for the contract, abstract class for the shared code, concrete class for the rest."}
  :::flow-step{label="List" icon="i-lucide-file-signature"}
  Interface. What any list can do: `get`, `add`, `size`.
  :::
  :::flow-step{label="AbstractList" icon="i-lucide-hammer" highlight}
  Abstract class. Implements `iterator`, `indexOf`, `equals`, `hashCode` on top
  of `get` and `size`.
  :::
  :::flow-step{label="ArrayList" icon="i-lucide-box"}
  Concrete. Supplies the array and the few methods only it can.
  :::
::

A **functional interface** is an interface with exactly one abstract method, like
`Comparator` or `Runnable`. It is what makes lambdas possible:

```java [Rank.java]
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class Rank {
    record Result(String name, int marks) { }

    public static void main(String[] args) {
        List<Result> results = new ArrayList<>(List.of(
            new Result("Anita", 78), new Result("Rahul", 91), new Result("Farhan", 84)));

        Comparator<Result> byMarks = (a, b) -> b.marks() - a.marks();   // a lambda IS an interface implementation
        results.sort(byMarks);
        results.forEach(r -> System.out.println(r.name() + " " + r.marks()));
    }
}
```

```text [Output]
Rahul 91
Farhan 84
Anita 78
```

## What confuses people here

- **"An interface cannot have method bodies."** Out of date since Java 8.
  `default` and `static` methods have bodies. Say "Java 8 added default methods"
  in the interview and you look current.
- **"An abstract class must have an abstract method."** It does not. A class can
  be `abstract` purely to stop anybody instantiating it.
- **"If a class has an abstract method, it can be concrete."** It cannot. Any
  abstract method makes the class abstract, and a concrete child must implement
  every one, or be abstract itself.
- **"Interface fields can change."** They are always `public static final`,
  whether you write those words or not. `Gradable.MAX = 50;` does not compile.

## Interview questions

::accordion
  :::accordion-item{label="Difference between an abstract class and an interface?" icon="i-lucide-message-circle"}
  An abstract class can have state, constructors and methods of any access, and a
  class extends only one. An interface has only constants, no constructors, and
  a class can implement many. Since Java 8 interfaces can have default and static
  methods. Use an abstract class for shared state and code in an is-a family; an
  interface for a capability that unrelated classes can have.
  :::
  :::accordion-item{label="Can an abstract class have a constructor? Why, if it cannot be instantiated?" icon="i-lucide-message-circle"}
  Yes. It runs when a child is created, through `super(...)`, to initialise the
  parent's fields. `Exam(String subject, int obtained)` sets the subject for every
  `Theory` and `Practical`.
  :::
  :::accordion-item{label="Why were default methods added to interfaces?" icon="i-lucide-message-circle"}
  So that interfaces could grow without breaking every existing implementation.
  Java 8 added `forEach` and `stream()` to `Collection`; without default methods,
  every collection class ever written would have stopped compiling.
  :::
  :::accordion-item{label="Can an interface extend another interface? Can it extend a class?" icon="i-lucide-message-circle"}
  An interface can extend one or more interfaces (`interface Report extends Gradable, Printable`).
  It cannot extend a class.
  :::
  :::accordion-item{label="What is a marker interface?" icon="i-lucide-message-circle"}
  An interface with no methods at all, used to tag a class: `Serializable`,
  `Cloneable`. The JVM or a library checks `instanceof` to decide behaviour.
  Annotations mostly replaced the idea.
  :::
  :::accordion-item{label="What is a functional interface?" icon="i-lucide-message-circle"}
  An interface with exactly one abstract method, optionally marked
  `@FunctionalInterface`. A lambda can implement it: `Comparator<Result> byMarks = (a, b) -> b.marks() - a.marks();`.
  :::
::

Both tools in this lesson are about one class **being** another kind of thing.
But most relationships in a real system are not is-a at all. A department is not
a faculty member; it **has** faculty members. A student **has** an ID card. That
other kind of relationship comes in three strengths, and interviewers love the
difference between them.
