The same markup can be made to look like anything. It can also refuse to change
at all, for reasons that feel arbitrary until you know the three mechanisms
underneath.

## Why this matters in a job

Because "why is my style not applying" is the question every beginner asks and it
almost always has one of three answers, and because reaching for `!important`
instead of learning them is how a stylesheet becomes unmaintainable.

## Answer one: something more specific won

When two rules set the same property on the same element, the more **specific**
one wins, regardless of order.

```css [styles.css]
.card p       { color: grey; }      /* 0,1,1  — class + element */
p             { color: black; }     /* 0,0,1  — element */
#summary p    { color: red; }       /* 1,0,1  — id + element */
```

::tip
This is why almost no modern codebase styles by id. An id rule can only be
overridden by another id rule, so one `#summary p` quietly makes every future
change to that element harder. Use classes, keep specificity flat, and the
cascade stays predictable.
::

## Answer two: it was inherited, or it was not

Some properties inherit from the parent and most do not.

```css [inherit.css]
body { color: #333; font-family: Geist; }   /* inherited by everything */
body { border: 1px solid red; }             /* NOT inherited. Only the body. */
```

**Inherits:** `color`, `font-*`, `line-height`, `text-align`, `visibility`.
**Does not:** everything about the box — `margin`, `padding`, `border`,
`background`, `width`, `display`.

The rule of thumb: text properties inherit, box properties do not, and a form
control inherits almost nothing unless you ask it to. That last one is why a
`<button>` keeps the browser's font until you write `font: inherit`.

## Answer three: the box is not the size you think

```css [box.css]
.card {
  width: 300px;
  padding: 20px;
  border: 2px solid;
}
```

That element is **344 pixels** wide by default: 300 plus 20 padding on each side
plus 2 of border on each side. Which is why two 50% columns with any padding
overflow their row, and it is the most confusing default in the language.

```css [reset.css]
/* Put this at the top of every stylesheet you ever write. */
*, *::before, *::after { box-sizing: border-box; }
```

Now `width: 300px` means the element is 300 pixels including its padding and
border, which is what everybody expected in the first place.

::compare{caption="Two 50% columns with 20px of padding, in a 1000px row."}
  :::compare-side{label="content-box, the default" verdict="wrong"}
  Each column is 500 + 40 = 540px. Two of them is 1080. They overflow and the
  second one drops below.
  :::
  :::compare-side{label="border-box" verdict="right"}
  Each column is 500px total, padding included. Two fit exactly. Nothing
  overflows, and you never think about it again.
  :::
::

## Margin collapse, the fourth surprise

```html [collapse.html]
<p style="margin-bottom: 20px">First</p>
<p style="margin-top: 30px">Second</p>
```

The gap is **30 pixels**, not 50. Adjacent vertical margins collapse into the
larger one. Horizontal margins never do, and neither happens inside a flex or
grid container.

::side-note{kind="go-deeper"}
That last clause is the practical escape. Modern layout uses `gap` inside flex
and grid, which does not collapse, is not a property of the children, and is
simply the space between things. Most of the margin-collapse folklore stopped
mattering the day `gap` arrived.
::

## The debugging order

When something is not applying, check these in order and you will find it.

::flow{numbered direction="vertical" caption="Two minutes, in this order. Almost every CSS problem is in the first three."}
  :::flow-step{label="Is the rule reaching the element at all?" icon="i-lucide-crosshair" highlight}
  Open developer tools, select the element, and look at the styles panel. If
  your rule is not listed, the selector is wrong or the file is not loading.
  Stop guessing at this point.
  :::
  :::flow-step{label="Is it struck through?" icon="i-lucide-strikethrough"}
  Then something more specific won, and the tools show you which. This is the
  specificity answer, told to you directly.
  :::
  :::flow-step{label="Is the box the size you expect?" icon="i-lucide-box"}
  The box diagram in the tools shows content, padding, border and margin
  separately. Usually `box-sizing`.
  :::
  :::flow-step{label="Is the property even applicable?" icon="i-lucide-help-circle"}
  `width` on an inline element does nothing. `margin: auto` centres only with a
  width. `z-index` needs a `position`. These do not error; they are ignored.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
`!important` is not a fix, it is a deferral. It wins now and can then only be
beaten by another `!important`, so the next person adds one, and within a year
the stylesheet has forty and none of them can be removed safely. If you need it,
the real problem is specificity, and the real fix is deleting an id selector.
::

## What you can do now

You can explain why a style is ignored rather than guessing, and you know the one
line to put at the top of every stylesheet.

## Your turn

Predict which colour wins, for each.

```html [quiz.html]
<div id="panel" class="card featured">
  <p class="note">Which colour am I?</p>
</div>
```

```css [quiz.css]
p                     { color: black; }
.note                 { color: blue; }
.card p               { color: green; }
.card .note           { color: orange; }
#panel p              { color: red; }
.featured.card .note  { color: purple; }
```

::accordion
  :::accordion-item{label="Answer, with the counts" icon="i-lucide-check"}
  ```text
  p                     → 0,0,1
  .note                 → 0,1,0
  .card p               → 0,1,1
  .card .note           → 0,2,0
  .featured.card .note  → 0,3,0
  #panel p              → 1,0,1   ← wins
  ```

  **Red.** The id beats everything, even the three-class selector, because
  comparison is left to right: any number in the first column beats any number in
  the second.

  **And the practical point:** to override that red you must now write another id
  selector or reach for `!important`. One id in a stylesheet has made every
  future change to that element harder, which is exactly why modern CSS
  conventions avoid them entirely.
  :::
::

2. **An interviewer asks: "what does `box-sizing: border-box` do and why do

## The interview question this answers

**"Explain the CSS box model."**

Content, padding, border, margin, outward. Then the part that makes it useful:
by default `width` sets the **content** box, so padding and border are added on
top and a 300px element with 20px of padding is 344px wide. `border-box` makes
width mean the whole box, which is why almost every codebase sets it globally in
the first three lines.

If they follow up with specificity, count it as ids, classes, elements, compared
left to right, and add why ids are avoided: an id rule can only be beaten by
another id rule.
