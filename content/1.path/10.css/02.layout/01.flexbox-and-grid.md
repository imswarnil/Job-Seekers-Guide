Two answers, and for twenty years there were none. The decision between them is
one sentence, and almost everything else is detail.

## Why this matters in a job

Because layout is most of front-end work, because "Flexbox or Grid" is asked in
every front-end interview, and because a table that does not work on a phone is
the most common real layout failure in business software.

## The one-sentence decision

::pull-quote
Flexbox lays things out in **one** direction. Grid lays things out in **two**.
If you are arranging a row or a column, use flex. If you are arranging rows and
columns at once, use grid.
::

::compare{caption="The same page, two jobs."}
  :::compare-side{label="Flexbox" verdict="neutral"}
  A navigation bar. A row of buttons. A card with a title on the left and a
  status chip pushed to the right. Anything where the content decides the sizes
  and you want them distributed along a line.
  :::
  :::compare-side{label="Grid" verdict="neutral"}
  The page itself: header, sidebar, main, footer. A gallery of cards that must
  line up in both directions. A form where labels and fields align down a
  column. Anything where **you** decide the structure in advance.
  :::
::

## Flexbox, the five properties that matter

```css [flex.css]
.toolbar {
  display: flex;
  gap: 1rem;                      /* space between. Never margins. */
  align-items: center;            /* the CROSS axis: vertical, in a row */
  justify-content: space-between; /* the MAIN axis: horizontal, in a row */
  flex-wrap: wrap;                /* let items drop to a new line */
}

.toolbar__spacer { flex: 1; }     /* take all remaining space */
```

::code-trace{caption="The two that get confused, and the rule that fixes it."}
```css [flex.css]
.toolbar {
  display: flex;
  justify-content: space-between;
  align-items: center;
}
```

  :::code-trace-step{lines="2" caption="`flex-direction` defaults to `row`, so the MAIN axis is horizontal and the CROSS axis is vertical."}
  :::
  :::code-trace-step{lines="3" caption="`justify-content` always works on the MAIN axis. In a row that means horizontally."}
  :::
  :::code-trace-step{lines="4" caption="`align-items` always works on the CROSS axis. In a row that means vertically. Set `flex-direction: column` and both of these swap meaning, which is the entire source of the confusion."}
  :::
::

```css [centre.css]
/* Centring something, which used to be a famous problem. */
.hero {
  display: flex;
  align-items: center;
  justify-content: center;
  min-height: 60vh;
}
```

## Grid, the four that matter

```css [grid.css]
.page {
  display: grid;
  grid-template-columns: 16rem 1fr;    /* fixed sidebar, flexible main */
  grid-template-rows: auto 1fr auto;   /* header, content, footer */
  min-height: 100vh;
  gap: 1.5rem;
}
```

```css [cards.css]
/* A responsive gallery with NO media queries at all. */
.applicants {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(18rem, 1fr));
  gap: 1rem;
}
```

That second one is worth understanding because it is the most useful line in
modern CSS. It says: as many columns as fit, each at least 18rem, sharing the
remaining space equally. On a phone that is one column, on a laptop three, on a
projector five, and you wrote no breakpoints.

::tip
`minmax(18rem, 1fr)` with `auto-fill` replaces about thirty lines of media
queries in a typical card grid. If you learn one thing from this lesson, learn
that line.
::

## The hard one: a table on a phone

Six columns of applicant data, and a screen 375 pixels wide. This is genuinely
difficult, and there are three honest answers.

::pros-cons
---
title: Horizontal scroll
pros:
  - The table stays a table, so it stays accessible and comparable
  - Trivial to implement — one wrapper with overflow-x
  - Sorting, selecting and scanning down a column all still work
cons:
  - Scrolling sideways is unpleasant, and users frequently do not realise they can
  - The first column scrolls away unless it is pinned
---
::

::pros-cons
---
title: Cards on small screens
pros:
  - Genuinely readable on a phone; each applicant becomes one block
  - No horizontal scrolling at all
cons:
  - Comparing applicants becomes impossible, which is usually the point of the table
  - The markup must stay a table for accessibility, so the CSS is doing real work
---
::

::pros-cons
---
title: Show fewer columns, with a details view
pros:
  - Honest about the constraint: a phone cannot show six columns usefully
  - Forces a decision about which two columns actually matter, which is a good question to be forced to answer
cons:
  - An extra tap to see the rest
  - Somebody has to decide which columns are the important ones
---
::

```css [table.css]
/* The scroll version, done properly. */
.table-scroll {
  overflow-x: auto;
  -webkit-overflow-scrolling: touch;
}

/* Pin the applicant name so the reader never loses which row they are on. */
.table-scroll th[scope="row"] {
  position: sticky;
  left: 0;
  background: var(--surface);      /* required, or rows show through */
}
```

```css [cards.css]
/* The card version. The MARKUP stays a real table; only the display changes. */
@media (max-width: 40rem) {
  .applicants thead { display: none; }

  .applicants tr {
    display: block;
    border: 1px solid var(--line);
    border-radius: 0.5rem;
    padding: 0.75rem;
    margin-bottom: 0.75rem;
  }

  .applicants td {
    display: flex;
    justify-content: space-between;
    gap: 1rem;
    padding: 0.25rem 0;
  }

  /* The column heading, repeated per cell, from a data attribute. */
  .applicants td::before {
    content: attr(data-label);
    font-weight: 600;
    color: var(--muted);
  }
}
```

```html [table.html]
<td data-label="Score">78</td>
```

::warning{icon="i-lucide-alert-triangle"}
`display: block` on a `tr` removes its table semantics in some screen readers,
so the row and column relationships can be lost exactly where they were most
useful. If you use the card approach, test it with a screen reader, and consider
whether the scroll version with a pinned first column is the more honest answer.
"It looks better on a phone" is not worth "a blind user can no longer tell which
column a number is in".
::

## What you can do now

You can choose between the two layout systems for a reason, build a responsive
grid with no media queries, and make a data table usable on a phone knowing what
each approach costs.

## Your turn

Build the applications screen.

1. Page layout: header, a filter sidebar, the table, a footer. Grid.
2. The toolbar above the table: a heading on the left, filter controls on the
   right, one row, wrapping on small screens. Flex.
3. The table: readable at 375px wide.
4. Then resize from 1400px down to 320px slowly and find where it breaks.

::accordion
  :::accordion-item{label="Where it will break, and the three widths to check" icon="i-lucide-ruler"}
  **320px** is the narrowest phone still in real use, and it is where a fixed
  sidebar or a long unbroken string, such as an email address, overflows. Check
  `overflow-wrap: anywhere` on anything containing user data.

  **768px** is where a two-column layout usually has to become one, and where a
  sidebar that was 16rem is now half the screen.

  **1400px** is where a `max-width` needs to exist, because a line of text 1,400
  pixels wide is unreadable and looks unfinished.

  **The two that catch everybody:** a long applicant email with no spaces pushes
  the whole table wide, which is fixed with `overflow-wrap`. And a fixed-width
  sidebar in `grid-template-columns: 16rem 1fr` does not shrink, so below about
  500px the main column has nothing left. Use `minmax(0, 1fr)` for the flexible
  one and move the sidebar above the content in a media query.
  :::
::

## Check yourself

1. Which axis does `justify-content` work on, and what happens when
   `flex-direction` is `column`?
2. **An interviewer asks: "Flexbox or Grid?"**

## The interview question this answers

**"When would you use Flexbox and when Grid?"**

One dimension against two. Flex for a row or a column where the content decides
the sizes; grid when you are defining rows and columns at once.

Then the detail that shows real use: `repeat(auto-fill, minmax(18rem, 1fr))`
gives a responsive card grid with no media queries at all, and `gap` replaced the
margin arithmetic that layout used to be made of. And they are frequently used
together, grid for the page and flex inside each region, which is what most real
codebases actually do.
