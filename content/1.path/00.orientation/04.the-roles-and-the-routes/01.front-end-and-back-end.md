Eight jobs, then, and the first two are the ones most people mean. The split is
not decoration: it is a line drawn through every web application ever built, and
it lands in a specific place for a specific reason.

## Why this matters in a job

Because you will be asked which one you want, probably in your first interview,
and "either" is a weak answer while "back-end, because…" is a strong one. It also
decides what you learn after this course.

## Where the line is, and why

The line is the network. Front-end code runs on a machine you do not control.
Back-end code runs on a machine you do.

The highlighted box is the reason the line matters. Anything on the left can be
edited by whoever is sitting there. A front-end check is a convenience for honest
users; the real check is always on the right.

::side-note{kind="security"}
This is the most common serious mistake in junior work. If the "only the
registrar can shortlist" rule lives in the browser, then anybody who opens the
developer tools is a registrar. Front-end validation is for kindness. Back-end
validation is for correctness.
::

## Front-end, honestly

**What it actually is:** building an interface that works on a screen you have
never seen, at a size you did not anticipate, for somebody using a keyboard, on a
connection that drops.

::pros-cons
---
title: Front-end engineering
pros:
  - You see the result immediately, which is enormously motivating while learning
  - The most visible work in the company; people use it and say so
  - The largest amount of free, high-quality learning material
cons:
  - The tooling changes faster than anywhere else in this industry
  - "It looks easy" means your work is often undervalued by people who have not done it
  - Accessibility, performance and browser differences are genuinely hard and rarely taught
---
::

## Back-end, honestly

**What it actually is:** deciding what is true. Who is allowed to do what, what
the rules are, how data is stored so it stays correct, and what happens when two
people do the same thing at the same instant.

::pros-cons
---
title: Back-end engineering
pros:
  - The skills age slowly, SQL, data modelling and HTTP outlast every framework
  - Where most of the difficult, well-paid problems live
  - Easiest to demonstrate in an interview, because the reasoning is visible
cons:
  - Nothing to look at, which makes early progress feel slower
  - Mistakes are more expensive and less immediately visible
  - You will be woken up at night more often than a front-end engineer will
---
::

## Watch the same feature from both sides

Front-end, the filter the registrar types into:

```javascript [shortlist.js]
// Runs on her laptop. Convenience only — it must never be the real check.
async function shortlist(minimumScore) {
  const response = await fetch(`/api/applicants?minScore=${minimumScore}`);
  if (!response.ok) {
    showMessage('Could not load applicants. Retrying.');
    return;
  }
  render(await response.json());
}
```

Back-end, the thing it calls:

```java [ApplicantController.java]
// Runs on your server. This is where "allowed" and "correct" are decided.
@GetMapping("/api/applicants")
public List<Applicant> shortlist(@RequestParam int minScore, User user) {
  if (!user.hasRole(Role.REGISTRAR)) {
    throw new ForbiddenException("Only the registrar may shortlist.");
  }
  if (minScore < 0 || minScore > 100) {
    throw new BadRequestException("A score must be between 0 and 100.");
  }
  return applicants.above(minScore, user.getDepartment());
}
```

Both are short. The interesting question is what happens if you delete the
`hasRole` check: the page looks identical, works identically, and every student
in the university can now list every applicant's score.

## What confuses people here

That full-stack means both at once and is therefore better. In practice
"full-stack" usually means one side properly and the other side competently, and
every honest full-stack engineer can tell you which is which for them.

For a first job, having a side is an advantage. You can say a sentence about why.

## What you can do now

You can say which side you lean toward and defend it, and you know the one rule
that a surprising number of working developers get wrong.

## Your turn

For each of these, say whether it belongs on the front end, the back end, or
both, and why:

1. Checking that an email address contains an `@`
2. Checking that a student has paid their fees before showing their result
3. Making the applicant table still usable on a phone
4. Making sure two staff members cannot allot the same seat at the same moment

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1. Both.** Front end so she is told immediately and kindly. Back end because
  the front-end check can be bypassed. Neither is optional and they are for
  different purposes.

  **2. Back end only.** It is a rule about who may see what. If it is on the front
  end, it is not a rule, it is a suggestion.

  **3. Front end.** And it is harder than it sounds: a table is the single worst
  thing to fit on a phone, which is why this is a real design problem rather than
  a styling one.

  **4. Back end, and specifically the database.** This is a concurrency problem
  and it is solved with a transaction and a constraint, not with code that checks
  first and then writes. The DBMS track takes this apart; it is also one of the
  most common interview questions in existence.
  :::
::

## Check yourself

1. Why can a front-end check never be the real check?
2. **An interviewer asks: "front-end or back-end, and why?"** Answer in three
   sentences, with a reason that is about the work rather than about the salary.

## The interview question this answers

**"Which side do you prefer, and why?"**

Any of the three answers is fine and the reason is what is being marked. "Back
end, because I like deciding what is true and I find data modelling satisfying"
is a real answer. "Back end, because it pays more" is true and tells them nothing
about whether you will enjoy Tuesday.
