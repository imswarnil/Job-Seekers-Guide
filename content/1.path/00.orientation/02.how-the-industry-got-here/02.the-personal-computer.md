The queue disappeared. A machine on your desk meant you could run your program
whenever you liked, and the cost of being wrong fell from one day to one minute.

That single change did more to shape this industry than any language ever has.

## Why this matters in a job

Because it is the moment the expensive resource flipped from the machine to the
person, and it has never flipped back. Every practice you are about to learn,
from readable variable names to automated tests to code review, exists because
**a developer's time is the expensive thing** and the machine's time is nearly
free.

::real-life{title="Where this shows up in your first week" source="Any code review, anywhere"}
Somebody will ask you to rename a variable from `d` to `daysUntilDeadline`. The
machine does not care. It compiles to exactly the same thing. The request is
economic: the next person to read it is the expensive resource, and the name is
how you spend less of them.
::

## What actually changed

::feature-list{columns="2"}
  :::feature{icon="i-lucide-monitor" title="Interactive, not batched"}
  Write, run, see, fix, in a loop that takes seconds. The whole modern way of
  working is downstream of this.
  :::
  :::feature{icon="i-lucide-package" title="Software as a shipped product"}
  If a million people own the same machine, one program can be sold a million
  times. Copying costs nothing. This is the best business model ever invented
  and it is why this industry pays what it pays.
  :::
  :::feature{icon="i-lucide-users" title="Non-experts as users"}
  The person using it is no longer the person who wrote it. Interfaces, error
  messages and documentation start to matter, and "it works if you know what to
  type" stops being acceptable.
  :::
  :::feature{icon="i-lucide-box" title="Compatibility as a prison"}
  Sell a million copies and you cannot change anything. A great deal of what
  looks like bad design in old software is a promise somebody made in 1993.
  :::
::

## What confuses people here

That "product company good, service company bad". That is not the lesson.

A service company hired me when nobody else would, trained me, and gave me a
batch of people to learn beside. It was the right first job and possibly the only
available one. The point is to know which machine you are standing in, so that
you can decide when to move rather than discovering in year four that you have
been standing still.

::note
This is also why "why are you leaving your current company?" has a real answer
available to you: "I want to work somewhere the work compounds rather than being
billed by the hour." That is honest, specific, and not an insult to anybody.
::

## What you can do now

You can explain why readable code is an economic decision rather than a matter of
taste, which is an argument you will need in your first code review.

## Your turn

Take this line and rewrite it so the next reader needs no explanation. It is real
in spirit: a shortlisting rule from the university admissions system.

```java [Shortlist.java]
if (a.s() > 60 && a.c() == 1 && !a.w()) { r.add(a); }
```

::accordion
  :::accordion-item{label="One version, and what changed" icon="i-lucide-check"}
  ```java [Shortlist.java]
  boolean meetsCutoff = applicant.getScore() > PASS_MARK;
  boolean appliedToComputerScience = applicant.getProgrammeId() == CSE;
  boolean stillInTheRunning = !applicant.hasWithdrawn();

  if (meetsCutoff && appliedToComputerScience && stillInTheRunning) {
    shortlist.add(applicant);
  }
  ```

  Identical behaviour, identical speed. What changed is that `c() == 1` is now a
  sentence, and the magic number `1` has a name. In six months, when the
  programme ids change, the person who has to find this can find it.
  :::
::

## Check yourself

1. In one sentence, why did clear naming become important only after the personal
   computer?
2. **An interviewer asks: "why does readable code matter if the compiler does not
   care?"** Answer economically, not aesthetically.

## The interview question this answers

**"What makes code good?"**

Most candidates say "clean" or "efficient" and stop. A stronger answer: good code
is cheap to change, because most of the money in software is spent after it is
first written. Then give the example above. Efficiency matters where it matters
and is measured, not assumed.
