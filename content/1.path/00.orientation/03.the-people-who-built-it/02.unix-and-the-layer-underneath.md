Two people at Bell Labs, a machine nobody else wanted, and a set of ideas that
your laptop is still running. This one is not history: it is the operating manual
for the next track of this course.

## Why this matters in a job

Because you are about to spend three weeks in a terminal, and every command in it
was shaped by a design philosophy you can learn in five minutes. Knowing the
philosophy is the difference between memorising forty commands and understanding
one idea forty times.

## What they built

In 1969, Ken Thompson and Dennis Ritchie built Unix on a machine that had been
abandoned. Ritchie then created C to write it in, which was itself a radical
move: operating systems were written in assembly, because a high-level language
was assumed to be too slow and too far from the hardware.

Writing the system in C meant the system could be **moved to a different
machine**. That is the whole reason Unix spread and its competitors did not.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-scissors" title="Do one thing well"}
  `grep` searches. `sort` sorts. `wc` counts. None of them can do each other's
  job, and none of them need to.
  :::
  :::feature{icon="i-lucide-arrow-right-left" title="Text as the universal interface"}
  Programs speak lines of text, so any program's output can be any other's input,
  forever, without either knowing the other exists.
  :::
  :::feature{icon="i-lucide-file" title="Everything is a file"}
  A document, a disk, a keyboard, a network connection. One set of operations,
  applied to all of them.
  :::
  :::feature{icon="i-lucide-blocks" title="Composition over features"}
  You do not ask for a new feature. You combine the tools you have into something
  none of them could do alone.
  :::
::

## Watch it happen

This is the philosophy in one line, and it is a genuinely useful line. Say you
have a file of applications, one per line, and you want the three programmes with
the most applicants.

```bash [Terminal]
cut -d',' -f3 applications.csv | sort | uniq -c | sort -rn | head -3
```

```text [Output]
   412 Computer Science
   288 Electronics
   201 Mechanical
```

Five programs, none of which knows the others exist, solving a problem none of
them was written for.

::code-trace{caption="Each program does one thing, and hands its text to the next."}
```bash [Terminal]
cut -d',' -f3 applications.csv
sort
uniq -c
sort -rn
head -3
```

  :::code-trace-step{lines="1" caption="Take the third comma-separated column, the programme name, from every line. cut knows nothing about applications, only about columns."}
  :::
  :::code-trace-step{lines="2" caption="Put identical names next to each other, because the next program can only count runs of identical lines."}
  :::
  :::code-trace-step{lines="3" caption="Collapse each run into one line with a count in front. This is the only counting in the whole pipeline."}
  :::
  :::code-trace-step{lines="4" caption="Sort again, this time numerically and in reverse, so the biggest count is first."}
  :::
  :::code-trace-step{lines="5" caption="Take the first three lines and stop. The programs before this are still running and are told to stop too."}
  :::
::

::real-life{title="Why this is not a party trick" source="Any production server, at 2 a.m."}
When a service is misbehaving, you are on a machine with no editor you like, no
graphical tools, and a log file of four million lines. The ability to build a
one-line answer out of small tools is exactly the skill that gets you from "the
site is slow" to "it is these three customer accounts" in ninety seconds. I have
watched a senior engineer do this and it looked like magic. It is five commands.
::

## What confuses people here

That "everything is a file" is a metaphor. It is not, and it is why the next
track can teach you permissions once and have it apply to everything.

::side-note{kind="go-deeper"}
Your disk is a file. Your terminal is a file. A network connection is a file.
Random numbers come from a file. Because they are all files, one set of
operations, open, read, write, close, and one permission model covers all of
them. That is why `chmod` works on things that are obviously not documents, and
it is the single most elegant idea in this lesson.
::

## Your turn

Without running anything, predict what this does and in what order:

```bash [Terminal]
grep 'REJECTED' applications.csv | wc -l
```

Then say which of the two programs knows what "REJECTED" means.

::accordion
  :::accordion-item{label="The answer, and the point of the question" icon="i-lucide-check"}
  `grep` keeps only the lines containing `REJECTED` and passes them on; `wc -l`
  counts lines and has no idea what they contain. So you get the number of
  rejected applications.

  Only `grep` knows the word. `wc` counts anything. That separation is the entire
  philosophy: the tool that filters does not count, the tool that counts does not
  filter, and because neither is specialised to applications, both work on your
  next problem too.
  :::
::

## The interview question this answers

**"How do you approach a problem you have not seen before?"**

The Unix answer is a genuinely good one: break it into the smallest pieces that
each do one thing, solve those, and compose them. Give the pipeline above as the
example. It shows a way of thinking rather than a list of technologies, which is
what this question is actually for.
