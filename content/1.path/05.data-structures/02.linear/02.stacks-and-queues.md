Two structures defined by what they refuse to let you do. A stack only lets you
touch the top; a queue only the ends. Those restrictions are the point, because
they match how a great many real problems actually behave.

## Why this matters in a job

Because both appear constantly without being named: the call stack you met in the
operating systems track, the undo history in an editor, the job queue in every
background worker, the breadth-first traversal in chapter four.

## A stack, last in, first out

::memory{kind="stack" caption="The registrar's undo history. The last action is the first one undone."}
---
cells:
  - { value: "shortlist APP-0417", label: "top, undone first", state: "active" }
  - { value: "set score 78" }
  - { value: "open application" }
  - { value: "log in", label: "bottom" }
---
::

```java [Undo.java]
// ArrayDeque, not Stack. The reason is below.
Deque<Action> undo = new ArrayDeque<>();

undo.push(new Action("open application"));
undo.push(new Action("set score 78"));
undo.push(new Action("shortlist APP-0417"));

Action last = undo.pop();       // shortlist APP-0417
```

Three operations, all **O(1)**: `push`, `pop`, `peek`. That is the whole
structure.

::warning{icon="i-lucide-alert-triangle"}
Java has a class literally called `Stack`. Do not use it. It extends `Vector`,
so every method is synchronised. You pay for thread safety you almost never
need, and it exposes indexed access, which breaks the restriction that makes a
stack useful. `ArrayDeque` is the modern answer and saying so in an interview is
a small, real signal.
::

## Where you have already met one

::feature-list{columns="2"}
  :::feature{icon="i-lucide-layers" title="The call stack"}
  Every method call pushes a frame; every return pops one. Unbounded recursion
  pushes forever, which is `StackOverflowError`. You met this in the operating
  systems track and this is what it was.
  :::
  :::feature{icon="i-lucide-undo-2" title="Undo"}
  Every editor, every form. The most recent action is the first to be reversed,
  which is exactly last in, first out.
  :::
  :::feature{icon="i-lucide-braces" title="Matching brackets"}
  Push an opening bracket, pop on a closing one and check it matches. The classic
  interview problem, below.
  :::
  :::feature{icon="i-lucide-arrow-left" title="The back button"}
  Pages visited, in reverse. And "forward" is a second stack, which is a nice
  detail to notice.
  :::
::

## The classic problem

Validating a timetable expression, or any nested structure.

```java [Brackets.java]
static boolean isBalanced(String text) {
  Deque<Character> open = new ArrayDeque<>();
  Map<Character, Character> pairs = Map.of(')', '(', ']', '[', '}', '{');

  for (char c : text.toCharArray()) {
    if (c == '(' || c == '[' || c == '{') {
      open.push(c);
    } else if (pairs.containsKey(c)) {
      if (open.isEmpty() || open.pop() != pairs.get(c)) {
        return false;                       // wrong closer, or nothing open
      }
    }
  }
  return open.isEmpty();                    // anything left open is unbalanced
}
```

```text [Output]
isBalanced("{CSE[201](Mon)}")   → true
isBalanced("{CSE[201)(Mon]}")   → false
isBalanced("{CSE[201](Mon)")    → false
```

Note the last check. Returning `true` as soon as the loop ends is the bug in
this problem, and it is why the third case matters: everything matched and
something was never closed.

## A queue, first in, first out

::memory{kind="queue" caption="Applications waiting for review. First received, first reviewed."}
---
cells:
  - { value: "APP-0417", label: "front, next out", state: "active" }
  - { value: "APP-0418" }
  - { value: "APP-0419" }
  - { value: "APP-0420", label: "back, just added" }
---
::

```java [ReviewQueue.java]
Queue<Application> pending = new ArrayDeque<>();

pending.offer(app417);            // add at the back
pending.offer(app418);

Application next = pending.poll();   // take from the front → app417
```

::note
Use `offer` and `poll` rather than `add` and `remove`. The first pair returns
`false` and `null` when the queue is full or empty; the second pair throws. On a
bounded queue that difference is the whole of your error handling, and it is a
question interviewers sometimes use to check whether you have read the interface
or just used it.
::

## Where queues are the shape of the system

::real-life{title="Why background work is always a queue" source="Any system that sends email"}
Publishing results emails 40,000 students. Doing it in the request means the
registrar's browser waits four minutes and times out. So the request writes
40,000 rows into a queue and returns immediately, and a worker takes them one at
a time. Everything that follows, retries, rate limits, seeing how far along it
is, resuming after a crash, is possible because the work is a queue. This is the
single most common architectural pattern you will meet, and it is this structure.
::

A **priority queue** is the useful variant: not first in first out, but
highest priority out first.

```java [Priority.java]
// Review the highest-scoring applications first.
PriorityQueue<Application> review =
    new PriorityQueue<>(comparing(Application::getScore).reversed());
```

`offer` and `poll` are **O(log n)** here rather than O(1), because it maintains a
heap underneath. Worth knowing as a fact: a priority queue is a heap, and a heap
is a tree kept in an array.

## What confuses people here

That a stack and a queue are different data structures. They are both usually an
array or a deque underneath; what differs is which ends you are allowed to touch.
The restriction is the abstraction, and the restriction is what makes the code
using it easy to reason about.

## What you can do now

You can recognise a last-in-first-out or first-in-first-out problem, name the
right Java class, and write the bracket-matching solution from memory, which is
one of the most-asked warm-up problems there is.

## Your turn

1. Reverse the order of applications in a list, using a stack, without calling
   `Collections.reverse`.
2. A registrar can undo and redo. Design it. How many stacks, and what happens to
   the redo stack when a *new* action is performed?
3. Why is a priority queue O(log n) to insert when an ordinary queue is O(1)?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** Push every element, then pop them all into a new list. The stack does
  the reversing for free, which is a neat demonstration that the restriction is
  the feature.

  ```java
  Deque<Application> stack = new ArrayDeque<>();
  applications.forEach(stack::push);
  List<Application> reversed = new ArrayList<>();
  while (!stack.isEmpty()) reversed.add(stack.pop());
  ```

  **2.** Two stacks. Undo pushes onto the undo stack; undoing pops from it and
  pushes onto redo; redoing does the reverse. And the part that is the actual
  question: **a new action clears the redo stack**, because the future you could
  have redone into no longer exists. Every editor behaves this way and almost
  nobody notices until they are asked to build it.

  **3.** Because it must keep the highest-priority item reachable at the front.
  It maintains a heap: a tree where every parent outranks its children, and
  inserting means sifting the new element up to its correct level, which is the
  depth of the tree, which is log n. An ordinary queue does not care about order
  beyond arrival, so it just appends.
  :::
::

## Check yourself

1. Why should you use `ArrayDeque` rather than `Stack` in Java?
2. **An interviewer asks: "check whether a string of brackets is balanced."**
   Write it, then say what the final `return` must check and why.

## The interview question this answers

**"Validate balanced parentheses"**: one of the most common warm-up problems in
existence, and it is really testing whether you reach for a stack unprompted.

The two places candidates fail are both about the edges: popping from an empty
stack when a closer arrives first, and forgetting that anything left on the stack
at the end means something was never closed. Say both out loud as you write them
and the problem is finished in three minutes.
