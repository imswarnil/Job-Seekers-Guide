Creating a `Thread` per task, starting it, joining it and hoping nobody forgot
does not scale to four hundred students at 10:00. Real Java code hands tasks to
an **`ExecutorService`**, a managed pool of threads, and shares data through
collections built for several threads at once.

## Why this matters in a job

In a Spring Boot service you will see `ExecutorService`, `@Async`,
`CompletableFuture` and `ConcurrentHashMap` far more often than
`new Thread(...)`. Code review comments such as "don't create threads in a
loop, use the pool" and "this HashMap is shared across requests, it must be
concurrent" are standard.

Interviewers ask: "what is a thread pool and why use one?", "`submit` against
`execute`", "what is a `Future`?", "`shutdown` against `shutdownNow`", "how is
`ConcurrentHashMap` different from `Hashtable` and
`Collections.synchronizedMap`?", and "can `ConcurrentHashMap` hold a null
key?".

## A thread pool is a staffed counter

The last lesson hired a new clerk for every student who walked in and fired
them after one form. Hiring is slow (creating a thread costs memory, about
1 MB of stack by default, and operating system work), and if five thousand
students arrive you hire five thousand clerks and the office collapses.

A **thread pool** is a counter with a fixed number of clerks. Students join
one **queue**; whichever clerk is free takes the next form. Clerks are reused,
the number is capped, and the queue absorbs a rush. `ExecutorService` is Java's
interface for that counter; `Executors` is the class with factory methods that
set one up.

::flow{direction="horizontal" caption="Tasks go into a queue. A fixed set of worker threads takes them one by one."}
  :::flow-step{label="submit(task)" icon="i-lucide-inbox"}
  Returns a `Future` at once. The caller does not wait.
  :::
  :::flow-step{label="Work queue" icon="i-lucide-list" highlight}
  Tasks wait here until a worker is free.
  :::
  :::flow-step{label="Worker threads" icon="i-lucide-users"}
  `pool-1-thread-1`, `-2`, `-3`: created once, reused for every task.
  :::
  :::flow-step{label="Future.get()" icon="i-lucide-package-check"}
  Collect the result when you need it.
  :::
::

## Syntax

```java
ExecutorService pool = Executors.newFixedThreadPool(3);
Future<String> f = pool.submit(() -> generateMarksheet(roll));   // Callable or Runnable
String result = f.get();                  // blocks until the task finishes
List<Future<String>> all = pool.invokeAll(listOfCallables);
pool.shutdown();                          // stop accepting, finish what is queued
pool.awaitTermination(5, TimeUnit.SECONDS);
```

```java [ResultPool.java]
import java.util.*;
import java.util.concurrent.*;

public class ResultPool {
  static String generateMarksheet(String roll) throws InterruptedException {
    Thread.sleep(200);                                   // pretend: database + PDF
    return roll + " done by " + Thread.currentThread().getName();
  }

  public static void main(String[] args) throws Exception {
    ExecutorService pool = Executors.newFixedThreadPool(3);   // 3 workers, reused

    // submit a Callable, get a Future back immediately
    Future<String> first = pool.submit(() -> generateMarksheet("CSE1801"));
    System.out.println("submitted; isDone = " + first.isDone());
    System.out.println(first.get());                     // waits for the result

    // invokeAll: many tasks, wait for all of them
    List<Callable<String>> jobs = new ArrayList<>();
    for (int i = 2; i <= 7; i++) {
      String roll = "CSE180" + i;
      jobs.add(() -> generateMarksheet(roll));
    }
    long start = System.currentTimeMillis();
    for (Future<String> f : pool.invokeAll(jobs)) {
      System.out.println(f.get());
    }
    System.out.println("6 marksheets on 3 threads: " + (System.currentTimeMillis() - start) + " ms");

    pool.shutdown();                                     // no new tasks; finish queued ones
    System.out.println("terminated: " + pool.awaitTermination(5, TimeUnit.SECONDS));
  }
}
```

```bash [Terminal]
javac ResultPool.java && java ResultPool
```

```text [Output]
submitted; isDone = false
CSE1801 done by pool-1-thread-1
CSE1802 done by pool-1-thread-2
CSE1803 done by pool-1-thread-3
CSE1804 done by pool-1-thread-1
CSE1805 done by pool-1-thread-1
CSE1806 done by pool-1-thread-2
CSE1807 done by pool-1-thread-3
6 marksheets on 3 threads: 409 ms
terminated: true
```

Which thread gets which roll number will vary between runs; the rolls come
back in submission order because `invokeAll` returns futures in the order of the
list. Six tasks of 200 ms on three threads took about 400 ms: two rounds. Three
thread names, reused, and never more than three threads alive.

The last line matters more than it looks. **A pool's threads are not daemon
threads.** Forget `shutdown()` and the JVM never exits: `main` ends and the
program sits there with three idle workers.

### The factory methods

| Factory | What you get | When |
| --- | --- | --- |
| `newFixedThreadPool(n)` | n threads, unbounded queue | The default choice for a known workload |
| `newCachedThreadPool()` | Creates threads as needed, reuses idle ones | Many short tasks; dangerous under a flood |
| `newSingleThreadExecutor()` | One thread, tasks in order | When tasks must not overlap |
| `newScheduledThreadPool(n)` | Runs tasks after a delay or on a schedule | "Send fee reminders every morning at 9" |
| `newVirtualThreadPerTaskExecutor()` | A lightweight virtual thread per task (Java 21) | Very many tasks that mostly wait on I/O |

### Future: a receipt for work in progress

`submit` returns a `Future` straight away, like a receipt with a token number.
`get()` waits for the result; `get(timeout, unit)` waits at most that long;
`isDone()` checks without waiting; `cancel(true)` interrupts the task. If the
task threw, `get()` throws `ExecutionException` with the original exception as
its cause.

```java [FutureTimeout.java]
import java.util.concurrent.*;

public class FutureTimeout {
  public static void main(String[] args) throws Exception {
    ExecutorService pool = Executors.newSingleThreadExecutor();
    Future<Integer> slow = pool.submit(() -> {
      Thread.sleep(5000);                 // a university API that is having a bad day
      return 42;
    });
    try {
      System.out.println(slow.get(1, TimeUnit.SECONDS));
    } catch (TimeoutException e) {
      System.out.println("Gave up after 1 second: " + e);
      slow.cancel(true);                  // interrupt the worker
    }
    Future<Integer> failing = pool.submit(() -> Integer.parseInt("seventy"));
    try {
      failing.get();
    } catch (ExecutionException e) {
      System.out.println("Task failed: " + e.getCause());
    }
    pool.shutdown();
  }
}
```

```text [Output]
Gave up after 1 second: java.util.concurrent.TimeoutException
Task failed: java.lang.NumberFormatException: For input string: "seventy"
```

::warning{icon="i-lucide-alert-triangle"}
With `execute(runnable)` instead of `submit`, an exception in the task is
printed by the worker thread and then lost to your code. With `submit`, it is
stored in the `Future` and **only** appears if somebody calls `get()`. A
submitted task that fails and whose future nobody reads fails silently.
::

### CompletableFuture, briefly

`Future.get()` blocks. `CompletableFuture` (Java 8) lets you describe what to
do **when** a result arrives, and combine several, without blocking in between.

```java [Completable.java]
import java.util.concurrent.*;

public class Completable {
  static int fetchMarks(String roll) { sleep(300); return 78; }
  static int fetchAttendance(String roll) { sleep(300); return 91; }
  static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) { } }

  public static void main(String[] args) {
    long start = System.currentTimeMillis();
    CompletableFuture<Integer> marks = CompletableFuture.supplyAsync(() -> fetchMarks("CSE1801"));
    CompletableFuture<Integer> attendance = CompletableFuture.supplyAsync(() -> fetchAttendance("CSE1801"));

    String report = marks
        .thenCombine(attendance, (m, a) -> "marks " + m + ", attendance " + a + "%")
        .thenApply(s -> "CSE1801: " + s)
        .join();
    System.out.println(report);
    System.out.println("took about " + (System.currentTimeMillis() - start) / 100 * 100 + " ms, not 600");
  }
}
```

```text [Output]
CSE1801: marks 78, attendance 91%
took about 300 ms, not 600
```

The two fetches ran at the same time, on the shared common pool, and
`thenCombine` joined them. This is how a student dashboard calls three
services at once instead of one after another.

## Real use case

### ConcurrentHashMap

Shared maps are everywhere in services: a cache of student profiles, a count of
requests per college, votes per candidate in a student-council election. A
plain `HashMap` shared between threads does not only lose updates; while it
resizes, concurrent writes can corrupt its internal buckets.

```java [SharedMaps.java]
import java.util.*;
import java.util.concurrent.*;

public class SharedMaps {
  static void countVotes(Map<String, Integer> votes) throws InterruptedException {
    String[] candidates = {"Anita", "Farah", "Imran", "Meera"};
    Runnable booth = () -> {
      for (int i = 0; i < 25_000; i++) {
        votes.merge(candidates[i % 4], 1, Integer::sum);
      }
    };
    Thread[] booths = new Thread[4];
    for (int i = 0; i < 4; i++) { booths[i] = new Thread(booth); booths[i].start(); }
    for (Thread t : booths) t.join();
  }

  public static void main(String[] args) throws InterruptedException {
    Map<String, Integer> plain = new HashMap<>();
    Map<String, Integer> concurrent = new ConcurrentHashMap<>();
    countVotes(plain);
    countVotes(concurrent);
    int plainTotal = plain.values().stream().mapToInt(Integer::intValue).sum();
    int concTotal = concurrent.values().stream().mapToInt(Integer::intValue).sum();
    System.out.println("Expected 100000 votes");
    System.out.println("HashMap:           " + plainTotal + " " + new TreeMap<>(plain));
    System.out.println("ConcurrentHashMap: " + concTotal + " " + new TreeMap<>(concurrent));
  }
}
```

```text [Output]
Expected 100000 votes
HashMap:           59028 {Anita=14724, Farah=14800, Imran=14571, Meera=14933}
ConcurrentHashMap: 100000 {Anita=25000, Farah=25000, Imran=25000, Meera=25000}
```

Four booths, 100,000 votes, and the `HashMap` counted 59,028. A second run gave
56,082. `ConcurrentHashMap` counted every vote, both times. `merge` on a
`ConcurrentHashMap` is **atomic**: the read, the add and the write for one key
happen as one step.

::compare{caption="Three thread-safe maps. Only one of them is what you want."}
  :::compare-side{label="Hashtable, synchronizedMap" verdict="wrong"}
  One lock for the whole map. Every read and every write, from every thread,
  queues behind that one lock. `Hashtable` is a pre-Java 2 legacy class;
  `Collections.synchronizedMap(new HashMap<>())` wraps a map the same way.
  Correct, and slow under load.
  :::
  :::compare-side{label="ConcurrentHashMap" verdict="right"}
  Reads take no lock at all. Writes lock only the one bucket they touch (Java
  8 onwards; before that, one of 16 segments), so threads writing different
  keys do not wait for each other. It adds atomic `merge`, `compute`,
  `computeIfAbsent` and `putIfAbsent`.
  :::
::

::real-life{title="The cache that needs computeIfAbsent" source="Any Spring service"}
`profiles.computeIfAbsent(roll, r -> loadFromDatabase(r))` loads a student's
profile once and caches it, even if fifty requests for the same roll arrive
together. The check-then-put version (`if (!map.containsKey(r)) map.put(...)`)
is the check-then-act race from the last lesson, and loads it fifty times.
::

## What confuses people here

- **No null keys or values in `ConcurrentHashMap`.** `HashMap` allows one
  `null` key; `ConcurrentHashMap` throws `NullPointerException`. The reason:
  in a concurrent map, `get(key)` returning `null` must mean "absent", because
  between a `containsKey` and a `get` another thread could have changed things.

  ```java [NullKeys.java]
  import java.util.*;
  import java.util.concurrent.*;

  public class NullKeys {
    public static void main(String[] args) {
      Map<String, String> hm = new HashMap<>();
      hm.put(null, "no roll number");
      System.out.println("HashMap accepts a null key: " + hm);
      Map<String, String> chm = new ConcurrentHashMap<>();
      try {
        chm.put(null, "no roll number");
      } catch (NullPointerException e) {
        System.out.println("ConcurrentHashMap: " + e);
      }
    }
  }
  ```

  ```text [Output]
  HashMap accepts a null key: {null=no roll number}
  ConcurrentHashMap: java.lang.NullPointerException
  ```
- **Its iterators are fail-safe (weakly consistent).** They never throw
  `ConcurrentModificationException`, and may or may not show changes made
  during iteration. `CopyOnWriteArrayList` goes further: every write copies the
  whole array, so iterators see a snapshot. Good for a list read far more than
  it is written, such as notification subscribers:

  ```java [CowList.java]
  import java.util.*;
  import java.util.concurrent.*;

  public class CowList {
    public static void main(String[] args) {
      List<String> subscribers = new CopyOnWriteArrayList<>(List.of("Anita", "Farah"));
      for (String s : subscribers) {
        if (s.equals("Anita")) subscribers.add("Imran");   // no ConcurrentModificationException
      }
      System.out.println(subscribers);
    }
  }
  ```

  ```text [Output]
  [Anita, Farah, Imran]
  ```
- **Two atomic calls are not one atomic operation.** `if (!map.containsKey(k))
  map.put(k, v)` on a `ConcurrentHashMap` is still a race. Use `putIfAbsent`
  or `computeIfAbsent`.
- **Pool size.** For CPU-heavy work, about the number of cores
  (`Runtime.getRuntime().availableProcessors()`). For work that mostly waits on
  a database or network, more. An unbounded cached pool under a flood of
  requests can create thousands of threads and run out of memory.

## Interview questions

::accordion
  :::accordion-item{label="What is a thread pool and why use one?" icon="i-lucide-message-circle"}
  A fixed or managed set of worker threads that take tasks from a queue and are
  reused. It avoids the cost of creating a thread per task, caps how many
  threads exist so a flood of work cannot exhaust memory, and separates
  submitting work from running it. `ResultPool.java` ran seven marksheets on
  three reused threads.
  :::
  :::accordion-item{label="What is the difference between submit() and execute()?" icon="i-lucide-message-circle"}
  `execute(Runnable)` returns nothing; an exception in the task goes to the
  thread's uncaught-exception handler. `submit` takes a `Runnable` or
  `Callable` and returns a `Future`; an exception is captured and rethrown,
  wrapped in `ExecutionException`, when you call `get()`.
  :::
  :::accordion-item{label="shutdown() against shutdownNow()?" icon="i-lucide-message-circle"}
  `shutdown()` stops accepting new tasks and lets queued and running ones
  finish. `shutdownNow()` also interrupts running tasks and returns the list of
  tasks that never started. Neither waits; follow with `awaitTermination`.
  Without a shutdown, the non-daemon pool threads keep the JVM alive.
  :::
  :::accordion-item{label="How is ConcurrentHashMap different from Hashtable?" icon="i-lucide-message-circle"}
  `Hashtable` synchronises every method on one lock, so all threads queue. 
  `ConcurrentHashMap` has lock-free reads and locks only the bucket being
  written, so it scales with threads. It offers atomic compound operations
  (`merge`, `computeIfAbsent`), its iterators never throw
  `ConcurrentModificationException`, and neither map allows `null` keys or
  values.
  :::
  :::accordion-item{label="What does Future.get() do if the task threw an exception?" icon="i-lucide-message-circle"}
  It throws `ExecutionException`, and `getCause()` gives the original.
  `FutureTimeout.java` printed `Task failed: java.lang.NumberFormatException:
  For input string: "seventy"`. `get(1, TimeUnit.SECONDS)` throws
  `TimeoutException` if the result is not ready in time.
  :::
  :::accordion-item{label="Why does ConcurrentHashMap not allow null?" icon="i-lucide-message-circle"}
  So that `get` returning `null` can only mean "no mapping". In a single-thread
  `HashMap` you can call `containsKey` to tell "absent" from "mapped to null",
  but in a concurrent map another thread may change the entry between the two
  calls, so the ambiguity cannot be resolved safely.
  :::
::
