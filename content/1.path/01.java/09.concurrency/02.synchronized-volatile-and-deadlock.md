Four threads made four reports in one second because they never touched the
same data. The moment two threads share a variable, a line as innocent as
`count++` starts losing updates, and it loses a different number every run.
This lesson is how that happens and the three tools that stop it.

## Why this matters in a job

Concurrency bugs are the worst kind: they pass every test on your laptop and
appear under load in production, once a day, in a way nobody can reproduce.
Two students booked into the last seat. A fee counted twice. A report job that
hangs every few weeks until someone restarts the server.

In interviews, after "Thread or Runnable", the next questions are nearly
always: "what is a race condition?", "what does `synchronized` do?",
"`volatile` against `synchronized`?", "what is a deadlock and how do you avoid
it?". A candidate who can say "I ran it and `count++` lost 90,000 updates"
stands out.

## Two counselling desks, one register

During seat allotment there are two counselling desks and one register showing
seats allotted. To add one, a clerk (1) reads the number, (2) adds one in their
head, (3) writes it back. If both clerks read "57" at the same moment, both
write "58". Two seats were allotted; the register went up by one.

That is a **race condition**: the result depends on the timing of threads, and
some timings are wrong. The three steps (read, modify, write) are the problem.
An operation that cannot be interrupted halfway is **atomic**; `count++` is not.

## How it works

Watch it lose updates:

```java [SeatsSold.java]
public class SeatsSold {
  static int seatsAllotted = 0;

  public static void main(String[] args) throws InterruptedException {
    Runnable counsellingDesk = () -> {
      for (int i = 0; i < 100_000; i++) {
        seatsAllotted++;          // looks like one step. It is three.
      }
    };
    Thread deskA = new Thread(counsellingDesk);
    Thread deskB = new Thread(counsellingDesk);
    deskA.start();
    deskB.start();
    deskA.join();
    deskB.join();
    System.out.println("Expected 200000, got " + seatsAllotted);
  }
}
```

```bash [Terminal]
javac SeatsSold.java && java SeatsSold
```

```text [Output]
Expected 200000, got 123578
```

Three runs on my machine gave 123,578, then 108,535, then 106,565. Nearly half
the updates vanished, and a different number each time. Your numbers will
differ; on a machine with one core you might even see 200,000 and think the
code is fine, which is exactly why these bugs survive testing.

### synchronized

Every Java object has a built-in lock, called its **monitor** or **intrinsic
lock**. `synchronized` means "take this object's lock before running this code,
and release it after". Only one thread can hold a given lock at a time; any
other thread that wants it waits in the `BLOCKED` state.

```java
synchronized void allot() { ... }        // locks `this` for the whole method
static synchronized void reset() { ... } // locks the Class object (SeatsFixed.class)
synchronized (seatLock) { ... }          // locks one chosen object for one block
```

```java [SeatsFixed.java]
import java.util.concurrent.atomic.AtomicInteger;

public class SeatsFixed {
  private int allotted = 0;
  private final AtomicInteger atomicAllotted = new AtomicInteger();

  // Only one thread at a time may be inside a synchronized method of this object.
  synchronized void allot() {
    allotted++;
  }

  public static void main(String[] args) throws InterruptedException {
    SeatsFixed office = new SeatsFixed();
    Runnable desk = () -> {
      for (int i = 0; i < 100_000; i++) {
        office.allot();
        office.atomicAllotted.incrementAndGet();
      }
    };
    Thread a = new Thread(desk), b = new Thread(desk);
    a.start(); b.start();
    a.join(); b.join();
    System.out.println("synchronized:  " + office.allotted);
    System.out.println("AtomicInteger: " + office.atomicAllotted.get());
  }
}
```

```text [Output]
synchronized:  200000
AtomicInteger: 200000
```

`AtomicInteger` is the second fix. `incrementAndGet()` performs read, add and
write as one indivisible hardware operation (compare-and-swap), with no lock.
For a single counter it is simpler and usually faster than `synchronized`.

A **synchronized block** locks less than a whole method, which matters when
most of the method does not touch shared data:

```java [LastSeat.java]
public class LastSeat {
  private int seatsLeft = 1;
  private final Object seatLock = new Object();

  boolean book(String student) {
    System.out.println(student + " checking...");        // no lock needed here
    synchronized (seatLock) {                            // only the check-and-update
      if (seatsLeft > 0) {
        seatsLeft--;
        System.out.println(student + " got the last seat");
        return true;
      }
    }
    System.out.println(student + ": sorry, full");
    return false;
  }

  public static void main(String[] args) throws InterruptedException {
    LastSeat cse = new LastSeat();
    Thread t1 = new Thread(() -> cse.book("Anita"));
    Thread t2 = new Thread(() -> cse.book("Farah"));
    t1.start(); t2.start();
    t1.join(); t2.join();
    System.out.println("Seats left: " + cse.seatsLeft);
  }
}
```

```text [Output]
Anita checking...
Farah checking...
Anita got the last seat
Farah: sorry, full
Seats left: 0
```

Which student gets the seat varies between runs. What never varies is that
exactly one does. The check (`seatsLeft > 0`) and the update (`seatsLeft--`)
must be inside the **same** lock; checking outside and updating inside is the
"check-then-act" race, and two students both see one seat left.

### volatile: the other problem, visibility

There is a second, stranger failure. For speed, each CPU core keeps its own
cache, and the JIT compiler may keep a variable in a register. A thread can go
on reading a stale copy of a variable that another thread changed long ago.

```java [VolatileStop.java]
public class VolatileStop {
  static volatile boolean resultsPublished = false;   // try removing volatile

  public static void main(String[] args) throws InterruptedException {
    Thread poller = new Thread(() -> {
      long checks = 0;
      while (!resultsPublished) {
        checks++;                       // busy loop, no sleep, no lock
      }
      System.out.println("Poller saw the change after " + checks + " checks");
    });
    poller.start();
    Thread.sleep(500);
    resultsPublished = true;
    System.out.println("main: results published");
    poller.join(2000);
    System.out.println("poller still running? " + poller.isAlive());
    System.exit(0);
  }
}
```

```text [Output]
main: results published
Poller saw the change after 1562188560 checks
poller still running? false
```

Now the same program with `volatile` removed:

```text [Output]
main: results published
poller still running? true
```

Without `volatile`, the poller never saw the change. The JIT noticed nothing
inside the loop writes `resultsPublished` and effectively turned it into
`while (true)`. It would have spun for ever; `System.exit(0)` is only there to
end the demonstration. `volatile` tells the JVM: every read of this variable
goes to main memory, and every write is visible to other threads at once.

::compare{caption="volatile fixes visibility. It does not make count++ safe."}
  :::compare-side{label="volatile int counter; counter++" verdict="wrong"}
  Every thread now sees the latest value, and `counter++` is still read, add,
  write. Two threads can still read the same value and both write it plus one.
  Updates are still lost.
  :::
  :::compare-side{label="volatile boolean flag; flag = true" verdict="right"}
  One thread writes, others read, and a plain write is already atomic. This is
  what `volatile` is for: stop flags, "ready" flags, a published configuration
  reference.
  :::
::

### wait and notify, briefly

Sometimes a thread must wait until another thread has done something. Every
object has `wait()` (release the lock and sleep until notified) and
`notify()`/`notifyAll()` (wake threads waiting on this object). Both must be
called while holding that object's lock.

```java [ResultBoard.java]
public class ResultBoard {
  private String result;                     // null until published

  synchronized void publish(String r) {
    result = r;
    notifyAll();                             // wake everyone waiting on this object
  }

  synchronized String awaitResult() throws InterruptedException {
    while (result == null) {                 // a loop, not an if
      wait();                                // releases the lock while waiting
    }
    return result;
  }

  public static void main(String[] args) throws InterruptedException {
    ResultBoard board = new ResultBoard();
    Thread student = new Thread(() -> {
      try {
        System.out.println("student: waiting for results");
        System.out.println("student: got " + board.awaitResult());
      } catch (InterruptedException e) { }
    });
    student.start();
    Thread.sleep(300);
    System.out.println("exam cell: publishing");
    board.publish("CSE results: 86% pass");
    student.join();
  }
}
```

```text [Output]
student: waiting for results
exam cell: publishing
student: got CSE results: 86% pass
```

The `while` loop matters: a thread can wake without being notified (a
**spurious wakeup**), so it must re-check the condition. In modern code you
would usually reach for `CountDownLatch`, `CompletableFuture` or a
`BlockingQueue` from `java.util.concurrent` instead, but `wait`/`notify` is
still asked about.

## Real use case

### Deadlock

A **deadlock** is two threads each holding a lock the other needs, both
waiting for ever. The accounts office holds the fee ledger and wants the
hostel register; the warden holds the hostel register and wants the fee
ledger. Neither will put theirs down first.

```java [Deadlock.java]
public class Deadlock {
  static final Object feeLedger = new Object();
  static final Object hostelRegister = new Object();

  public static void main(String[] args) {
    Thread accounts = new Thread(() -> {
      synchronized (feeLedger) {
        System.out.println("accounts: has fee ledger, wants hostel register");
        pause();
        synchronized (hostelRegister) {
          System.out.println("accounts: has both");
        }
      }
    }, "accounts");

    Thread warden = new Thread(() -> {
      synchronized (hostelRegister) {
        System.out.println("warden: has hostel register, wants fee ledger");
        pause();
        synchronized (feeLedger) {
          System.out.println("warden: has both");
        }
      }
    }, "warden");

    accounts.start();
    warden.start();
  }

  static void pause() {
    try { Thread.sleep(100); } catch (InterruptedException e) { }
  }
}
```

```text [Output]
accounts: has fee ledger, wants hostel register
warden: has hostel register, wants fee ledger
```

And then nothing. No exception, no exit, no CPU use. The program hangs until
you kill it. This is what "the batch job hung overnight" looks like at work,
and the tool for diagnosing it ships with the JDK. In a second terminal:

```bash [Terminal]
jps                 # lists running Java processes and their ids
jstack 19046        # prints every thread's stack for process 19046
```


That is an excerpt of a real `jstack` run (the process id will be different on
yours). It names both threads, which lock each holds, which each wants, and the
exact line numbers. This is why naming your threads ("accounts", "warden")
pays off.

::real-life{title="How deadlocks are avoided in practice" source="Production Java services"}
The standard rule is **lock ordering**: every piece of code that needs both
locks takes them in the same order (always fee ledger, then hostel register).
If both threads above did that, the second would wait at the first lock instead
of grabbing the other one, and no cycle could form. The other tools: hold locks
for as short a time as possible, never call unknown code while holding a lock,
and use `ReentrantLock.tryLock(timeout)`, which gives up instead of waiting for
ever.
::

## What confuses people here

- **`synchronized` on different objects does not exclude each other.** Two
  threads calling a synchronized method on **two different** `SeatsFixed`
  objects run at the same time, because each locks its own `this`.
- **Static and instance synchronized methods use different locks.** A
  `static synchronized` method locks the `Class` object; an instance one locks
  `this`. They do not block each other.
- **`synchronized` is re-entrant.** A thread that already holds a lock can take
  it again (a synchronized method calling another on the same object) without
  deadlocking itself.
- **`sleep` keeps the lock; `wait` releases it.** A thread sleeping inside a
  synchronized block still blocks everyone else.
- **Local variables are always thread-safe,** because each thread has its own
  stack. Only shared objects on the heap need protecting.

## Interview questions

::accordion
  :::accordion-item{label="What is a race condition? Give an example." icon="i-lucide-message-circle"}
  When the result depends on the unpredictable timing of threads accessing
  shared data. `count++` from two threads is the classic: it is read, add,
  write, so two threads can read the same value and both write it plus one.
  `SeatsSold.java` expected 200,000 and got 123,578.
  :::
  :::accordion-item{label="What does the synchronized keyword do?" icon="i-lucide-message-circle"}
  Before running the method or block, the thread must acquire the object's
  intrinsic lock (monitor); only one thread can hold it at a time. It gives
  mutual exclusion and also visibility: changes made inside are seen by the next
  thread that takes the same lock. On an instance method the lock is `this`, on
  a static method the `Class` object, on a block whatever object you name.
  :::
  :::accordion-item{label="What is the difference between volatile and synchronized?" icon="i-lucide-message-circle"}
  `volatile` guarantees visibility only: every thread sees the latest write.
  It does not make compound actions such as `count++` atomic. `synchronized`
  guarantees both visibility and mutual exclusion, at the cost of blocking. Use
  `volatile` for a flag written by one thread and read by others; use
  `synchronized` or an atomic class for read-modify-write.
  :::
  :::accordion-item{label="What is a deadlock and how do you prevent it?" icon="i-lucide-message-circle"}
  Two or more threads each waiting for a lock held by another, so none can
  proceed. Prevent it by always acquiring locks in the same global order,
  holding them briefly, avoiding nested locks where possible, and using
  `tryLock` with a timeout. Detect it with `jstack`, which prints "Found one
  Java-level deadlock" with both threads and their locks.
  :::
  :::accordion-item{label="Why use AtomicInteger instead of synchronized?" icon="i-lucide-message-circle"}
  For a single variable, `AtomicInteger.incrementAndGet()` is atomic using a
  CPU compare-and-swap instruction, with no lock and no blocking. It is simpler
  to write and usually faster under contention. For keeping several variables
  consistent together you still need a lock.
  :::
  :::accordion-item{label="Difference between wait() and sleep()?" icon="i-lucide-message-circle"}
  `wait()` is an `Object` method, must be called while holding that object's
  lock, and releases the lock until notified. `sleep()` is a static `Thread`
  method, needs no lock, and keeps any locks it holds. Use `wait` in a `while`
  loop because of spurious wakeups.
  :::
::
