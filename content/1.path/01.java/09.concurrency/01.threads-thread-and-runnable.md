Every program so far has done one thing at a time, top to bottom. A results
server cannot: at 10:00 on result day, four hundred students press "check
result" at once. A **thread** is how one Java program does several things at
the same time.

## Why this matters in a job

You will rarely create a raw `Thread` at work; frameworks such as Spring and
Tomcat create them for you, one per incoming request. But your code runs on
those threads, and the bugs that come from several threads touching the same
data are the hardest bugs you will meet. The next lesson is about exactly
those.

In interviews, multithreading is the topic that separates a Java fresher who
has read ahead from one who has not. Almost every Java round asks at least
"Thread or Runnable?", "start() or run()?" and "what are the states of a
thread?". This lesson answers all three with code you can run.

## A process is a canteen, a thread is a cook

A **process** is a running program with its own memory, like the college
canteen with its own kitchen and store room. Two canteens do not share
ingredients. Your `java` command starts one process: the JVM.

A **thread** is one line of work inside that process, like one cook. A canteen
can have several cooks working at once, and they share the kitchen: the same
stove, the same store room. That sharing is what makes threads fast to create
and cheap to switch between, and it is also what makes them dangerous. Two
cooks reaching for the last packet of rice at once is the next lesson.

In JVM terms, from the pass-by-value lesson: **each thread has its own stack;
all threads share one heap.** Local variables are private to a thread. Objects
are shared.

## Syntax

There are two classic ways to give a thread work, and a third that is the
second written shorter:

```java
// 1. Extend Thread and override run()
class ResultMailer extends Thread { public void run() { ... } }
new ResultMailer().start();

// 2. Implement Runnable and pass it to a Thread
class HallTicketPrinter implements Runnable { public void run() { ... } }
new Thread(new HallTicketPrinter()).start();

// 3. Runnable is a functional interface, so a lambda works
new Thread(() -> System.out.println("SMS sent")).start();
```

```java [TwoWays.java]
public class TwoWays {
  // Way 1: extend Thread and override run()
  static class ResultMailer extends Thread {
    @Override
    public void run() {
      for (int i = 1; i <= 3; i++) {
        System.out.println(getName() + ": result email " + i);
      }
    }
  }

  // Way 2: implement Runnable and hand it to a Thread
  static class HallTicketPrinter implements Runnable {
    @Override
    public void run() {
      for (int i = 1; i <= 3; i++) {
        System.out.println(Thread.currentThread().getName() + ": hall ticket " + i);
      }
    }
  }

  public static void main(String[] args) throws InterruptedException {
    Thread mailer = new ResultMailer();
    mailer.setName("mailer");
    Thread printer = new Thread(new HallTicketPrinter(), "printer");
    Thread sms = new Thread(() -> System.out.println(Thread.currentThread().getName() + ": SMS sent"), "sms");

    mailer.start();
    printer.start();
    sms.start();

    mailer.join();       // wait for each to finish
    printer.join();
    sms.join();
    System.out.println("main: all done");
  }
}
```

```bash [Terminal]
javac TwoWays.java && java TwoWays
```

```text [Output]
sms: SMS sent
printer: hall ticket 1
mailer: result email 1
printer: hall ticket 2
mailer: result email 2
mailer: result email 3
printer: hall ticket 3
main: all done
```

::warning{icon="i-lucide-alert-triangle"}
**Your output will almost certainly be in a different order.** That is one
real run. Two more runs on the same machine gave all of the mailer's lines
before the printer's, and then the reverse. The operating system's **scheduler**
decides which thread runs when, and it does not promise any order. The only
guaranteed line is the last one, because `join()` makes `main` wait until each
thread has finished.
::

### Thread or Runnable?

::pros-cons
---
title: Implementing Runnable, rather than extending Thread
pros:
  - "Your class can still extend something else. Java allows only one parent class"
  - "It separates the job (Runnable) from the worker (Thread), so the same job can run on a thread pool later"
  - "It can be written as a lambda"
cons:
  - "run() cannot return a value or throw a checked exception. Callable, below, fixes both"
  - "You need Thread.currentThread() to reach the thread's name, instead of calling getName() directly"
---
::

The honest answer in an interview: prefer `Runnable` (or a lambda), because
extending `Thread` uses up your one `extends` and ties the task to one way of
running it. In real code you then hand that `Runnable` to an
`ExecutorService`, which is the lesson after next.

### start() against run()

```java [StartVsRun.java]
public class StartVsRun {
  public static void main(String[] args) throws InterruptedException {
    Runnable task = () -> System.out.println("running in: " + Thread.currentThread().getName());

    Thread t1 = new Thread(task, "worker-1");
    t1.run();                  // an ordinary method call, on main
    t1.start();                // a new thread
    t1.join();

    try {
      t1.start();              // a thread can only be started once
    } catch (IllegalThreadStateException e) {
      System.out.println("second start(): " + e);
    }
  }
}
```

```text [Output]
running in: main
running in: worker-1
second start(): java.lang.IllegalThreadStateException
```

`run()` is a normal method: calling it runs the code **on the current thread**,
with no new thread at all. `start()` asks the JVM to create a new thread, which
then calls `run()` for you. And a finished thread cannot be restarted; create a
new `Thread` object instead.

### The lifecycle

A thread moves through six states, available from `getState()`:

```java [Lifecycle.java]
public class Lifecycle {
  public static void main(String[] args) throws InterruptedException {
    Object lock = new Object();
    Thread t = new Thread(() -> {
      try {
        Thread.sleep(200);                       // TIMED_WAITING
        synchronized (lock) { }                  // BLOCKED if main holds the lock
      } catch (InterruptedException e) { }
    }, "report-generator");

    System.out.println("after new:    " + t.getState());
    synchronized (lock) {
      t.start();
      System.out.println("after start:  " + t.getState());
      Thread.sleep(50);
      System.out.println("while asleep: " + t.getState());
      Thread.sleep(300);
      System.out.println("wants lock:   " + t.getState());
    }
    t.join();
    System.out.println("after join:   " + t.getState());
  }
}
```

```text [Output]
after new:    NEW
after start:  RUNNABLE
while asleep: TIMED_WAITING
wants lock:   BLOCKED
after join:   TERMINATED
```

::flow{direction="horizontal" caption="The six states of Thread.State. WAITING comes from join() or wait() with no timeout."}
  :::flow-step{label="NEW" icon="i-lucide-circle"}
  Created, `start()` not called yet.
  :::
  :::flow-step{label="RUNNABLE" icon="i-lucide-play" highlight}
  Running, or ready and waiting for a CPU core.
  :::
  :::flow-step{label="BLOCKED / WAITING / TIMED_WAITING" icon="i-lucide-pause"}
  Waiting for a lock, for another thread, or for a timer (`sleep`).
  :::
  :::flow-step{label="TERMINATED" icon="i-lucide-square"}
  `run()` has finished. Cannot be started again.
  :::
::

`synchronized (lock)` is the subject of the next lesson. Here it shows the
BLOCKED state: `main` held the lock, so the worker had to wait for it.

## Real use case

The reason threads exist in business software is waiting. A report generator
spends most of its time waiting for a database or a file; while one thread
waits, another can work.

```java [Parallel.java]
public class Parallel {
  static void generateReport(String dept) {
    try {
      Thread.sleep(1000);      // pretend each report takes one second
    } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
    }
  }

  public static void main(String[] args) throws InterruptedException {
    String[] depts = {"CSE", "ECE", "MECH", "CIVIL"};

    long start = System.currentTimeMillis();
    for (String d : depts) generateReport(d);
    System.out.println("One after another: " + (System.currentTimeMillis() - start) + " ms");

    start = System.currentTimeMillis();
    Thread[] threads = new Thread[depts.length];
    for (int i = 0; i < depts.length; i++) {
      String d = depts[i];
      threads[i] = new Thread(() -> generateReport(d));
      threads[i].start();
    }
    for (Thread t : threads) t.join();
    System.out.println("Four threads:      " + (System.currentTimeMillis() - start) + " ms");
  }
}
```

```text [Output]
One after another: 4016 ms
Four threads:      1008 ms
```

Four seconds became one. Your exact milliseconds will differ. This is the
same idea as a web server giving each request its own thread: one student's
slow request does not hold up everyone behind them.

### Getting a result back: Callable

`Runnable.run()` returns `void`. When the thread must hand back an answer, use
`Callable<V>`, whose `call()` returns a value and may throw a checked
exception. You collect the answer through a **`Future`**, an object that will
hold the result once it is ready.

```java [CallableDemo.java]
import java.util.concurrent.*;

public class CallableDemo {
  public static void main(String[] args) throws Exception {
    Callable<Double> averageCgpa = () -> {
      Thread.sleep(300);
      return 7.84;
    };
    FutureTask<Double> task = new FutureTask<>(averageCgpa);
    new Thread(task, "cgpa-calculator").start();
    System.out.println("main carries on while it computes...");
    System.out.println("Average CGPA: " + task.get());   // waits for the result
  }
}
```

```text [Output]
main carries on while it computes...
Average CGPA: 7.84
```

In practice you almost never build a `FutureTask` by hand; an
`ExecutorService` gives you the `Future` directly. That is two lessons away.

## What confuses people here

- **`sleep` does not release locks,** and it is a static method: `t.sleep(100)`
  makes the **current** thread sleep, not `t`. Always write `Thread.sleep`.
- **`InterruptedException` is not an error to swallow.** It means another
  thread asked this one to stop. Either rethrow it or restore the flag with
  `Thread.currentThread().interrupt()`, as `Parallel.java` does.
- **The JVM waits for every non-daemon thread.** A **daemon** thread is a
  background helper that the JVM does not wait for: when the last normal
  thread ends, daemons are killed.

```java [Daemon.java]
public class Daemon {
  public static void main(String[] args) throws InterruptedException {
    Thread autosave = new Thread(() -> {
      while (true) {
        System.out.println("autosaving draft...");
        try { Thread.sleep(100); } catch (InterruptedException e) { return; }
      }
    });
    autosave.setDaemon(true);
    autosave.start();
    Thread.sleep(250);
    System.out.println("main ends; the daemon dies with it");
  }
}
```

```text [Output]
autosaving draft...
autosaving draft...
autosaving draft...
main ends; the daemon dies with it
```

Without `setDaemon(true)` that program would never exit. The garbage collector
runs on daemon threads.

- **More threads is not always faster.** For CPU-heavy work, more threads than
  cores only adds switching cost. Threads help most when work waits on I/O.
- **Priorities (`setPriority`) are hints,** and most operating systems largely
  ignore them. Never rely on them for correctness.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between a process and a thread?" icon="i-lucide-message-circle"}
  A process is a running program with its own memory space; processes do not
  share memory. A thread is a path of execution inside a process; threads in
  one process share the heap but each has its own stack. Threads are cheaper to
  create and switch, and sharing memory is both their speed and their danger.
  :::
  :::accordion-item{label="Extending Thread or implementing Runnable: which is better?" icon="i-lucide-message-circle"}
  Implementing `Runnable`. Java has single class inheritance, so extending
  `Thread` uses up your only parent. `Runnable` also separates the task from
  the thread, so the same task can be submitted to a thread pool, and it can be
  a lambda: `new Thread(() -> sendSms()).start()`.
  :::
  :::accordion-item{label="What happens if you call run() instead of start()?" icon="i-lucide-message-circle"}
  No new thread is created; `run()` executes on the calling thread like any
  method. `StartVsRun.java` printed `running in: main` for `run()` and
  `running in: worker-1` for `start()`. Calling `start()` twice throws
  `IllegalThreadStateException`.
  :::
  :::accordion-item{label="What are the states of a thread?" icon="i-lucide-message-circle"}
  `NEW`, `RUNNABLE`, `BLOCKED` (waiting for a monitor lock), `WAITING`
  (`join()` or `wait()` with no timeout), `TIMED_WAITING` (`sleep`, or a
  timed `join`/`wait`) and `TERMINATED`. `Lifecycle.java` shows five of them
  from one thread.
  :::
  :::accordion-item{label="What does join() do?" icon="i-lucide-message-circle"}
  `t.join()` makes the current thread wait until `t` has finished. In
  `TwoWays.java` it is why "main: all done" is always last, whatever order the
  other lines come in.
  :::
  :::accordion-item{label="Runnable against Callable?" icon="i-lucide-message-circle"}
  `Runnable.run()` returns nothing and cannot throw checked exceptions.
  `Callable<V>.call()` returns a `V` and can throw `Exception`. You get a
  `Callable`'s result through a `Future`, whose `get()` waits for it.
  :::
::
