`FeeReport` called `formatter.row(...)` without knowing which kind of formatter
it held, and got the right behaviour for each. That is **polymorphism**, from
the Greek for "many forms": one call, and the behaviour depends on the object
that is really there.

## Why this matters in a job

It is the mechanism behind nearly every framework you will use. Spring, JUnit
and the servlet containers that run Java web applications all hold your
objects through a parent type or an interface and call methods on them, having
never seen your class. And "what is the difference between overloading and
overriding?" is, in my experience, the single most-asked Java question in
fresher interviews. You will have the answer, with proof, by the end of this
page.

## One word, the right behaviour

At a college office, the clerk says "pay this month's fee" to every student in
the queue. The words are identical. A day scholar pays tuition plus the bus. A
hosteller pays tuition plus the room. The clerk does not ask "which kind are
you?" and then look up a rule; each student already knows what their own fee
is.

In Java:

- the clerk's words are a **method call on a parent type**: `s.monthlyFeePaise()`
  where `s` is declared as `Student`;
- each kind of student **overrides** the method with its own version;
- Java picks the version belonging to the **actual object** while the program
  runs. This is **dynamic dispatch** (also called dynamic method dispatch or
  late binding).

There are two kinds of polymorphism, and interviewers expect both names:

| | Compile-time polymorphism | Run-time polymorphism |
| --- | --- | --- |
| Achieved by | **Overloading**: same name, different parameters | **Overriding**: subclass replaces a parent method |
| Decided | When compiling, from the **declared** types | While running, from the **actual** object |
| Also called | Static binding, early binding | Dynamic binding, late binding |

## How it works

```java [FeeRun.java]
public class FeeRun {
  public static void main(String[] args) {
    Student[] students = {
      new DayScholar("Anita Rao"),
      new Hosteller("Vikram Shah", 2),
      new DayScholar("Farah Khan"),
      new Hosteller("Rohit Das", 1)
    };

    long totalPaise = 0;
    for (Student s : students) {
      long fee = s.monthlyFeePaise();           // which version runs?
      System.out.printf("%-12s %-11s Rs %,d%n", s.name, s.getClass().getSimpleName(), fee / 100);
      totalPaise += fee;
    }
    System.out.printf("Total this month: Rs %,d%n", totalPaise / 100);
  }
}

class Student {
  final String name;
  Student(String name) { this.name = name; }

  long monthlyFeePaise() {
    return 750_000;                             // tuition: Rs 7,500
  }
}

class DayScholar extends Student {
  DayScholar(String name) { super(name); }

  @Override
  long monthlyFeePaise() {
    return super.monthlyFeePaise() + 120_000;   // plus bus: Rs 1,200
  }
}

class Hosteller extends Student {
  final int sharing;                            // students per room
  Hosteller(String name, int sharing) { super(name); this.sharing = sharing; }

  @Override
  long monthlyFeePaise() {
    long room = sharing == 1 ? 900_000 : 600_000;
    return super.monthlyFeePaise() + room;
  }
}
```

```bash [Terminal]
javac FeeRun.java && java FeeRun
```

```text [Output]
Anita Rao    DayScholar  Rs 8,700
Vikram Shah  Hosteller   Rs 13,500
Farah Khan   DayScholar  Rs 8,700
Rohit Das    Hosteller   Rs 16,500
Total this month: Rs 47,400
```

The loop is written once against `Student`. There is no `if (s is a
Hosteller)` anywhere. Add a `ScholarshipStudent` next year and this loop does
not change at all; only the new class is written. That is the practical payoff:
**new behaviour by adding code, not by editing old code**.

::pull-quote
The declared type decides what you are allowed to call. The actual object
decides what happens when you call it.
::

### Overloading, overriding, fields and static methods, side by side

This is the program that answers the interview question. One variable, declared
`Member`, holding a `Student`, and four different kinds of call:

```java [CompileVsRun.java]
public class CompileVsRun {
  static void greet(Member m)  { System.out.println("overload chosen: greet(Member)"); }
  static void greet(Student s) { System.out.println("overload chosen: greet(Student)"); }

  public static void main(String[] args) {
    Member m = new Student();           // declared Member, actually a Student

    greet(m);                           // OVERLOADING: decided by the declared type
    System.out.println(m.role());       // OVERRIDING: decided by the actual object
    System.out.println(m.campus);       // FIELDS: decided by the declared type
    System.out.println(m.college());    // STATIC: decided by the declared type
  }
}

class Member {
  String campus = "Member campus";
  String role() { return "role(): member"; }
  static String college() { return "college(): Member's static method"; }
}

class Student extends Member {
  String campus = "Student campus";
  @Override String role() { return "role(): student"; }
  static String college() { return "college(): Student's static method"; }
}
```

```text [Output]
overload chosen: greet(Member)
role(): student
Member campus
college(): Member's static method
```

### The rules for overriding

For a child method to override a parent method:

- same name and **same parameter list**;
- the same return type, or a **subtype** of it (a **covariant return type**);
- access **the same or wider**, never narrower (a `public` method stays
  `public`);
- it cannot throw broader **checked exceptions** than the parent (the
  exceptions chapter explains checked exceptions);
- `private`, `static` and `final` methods cannot be overridden.

Break them and the compiler tells you, especially if you write `@Override`:

```java [BadOverride.java]
public class BadOverride { public static void main(String[] a) { } }

class Member {
  public String role() { return "member"; }
  long feePaise() { return 0; }
}

class Student extends Member {
  @Override
  String role() { return "student"; }          // narrower access
  @Override
  int feePaise() { return 0; }                  // different return type
  @Override
  String rolle() { return "typo"; }             // overrides nothing
}
```

```text [Output]

         ^
  attempting to assign weaker access privileges; was public
BadOverride.java:12: error: feePaise() in Student cannot override feePaise() in Member
  int feePaise() { return 0; }                  // different return type
      ^
  return type int is not compatible with long

```

The last one is why `@Override` matters. Without it, the typo `rolle()` would
compile as a brand-new method, `role()` would never be overridden, and you
would spend an afternoon wondering why your override "does nothing".

A covariant return type, which **is** allowed:

```java [Covariant.java]
public class Covariant {
  public static void main(String[] args) {
    Faculty f = new Faculty();
    Faculty copy = f.copy();            // no cast needed: the override returns Faculty
    System.out.println(copy.getClass().getSimpleName());
  }
}

class Member {
  Member copy() { return new Member(); }
}

class Faculty extends Member {
  @Override
  Faculty copy() { return new Faculty(); }      // a narrower return type is allowed
}
```

```text [Output]
Faculty
```

### Upcasting and downcasting

**Upcasting** is treating a child as its parent: `Student s = new
Hosteller(...)`. It is automatic and always safe, because every hosteller is a
student. **Downcasting** goes the other way and needs an explicit cast,
because not every student is a hosteller.

```java [Casting.java]
public class Casting {
  public static void main(String[] args) {
    Student s = new Hosteller("Vikram Shah", 2);   // upcast: automatic, always safe

    // s.roomSharing();   // does not compile: Student has no roomSharing()

    if (s instanceof Hosteller h) {                 // test and cast in one step
      System.out.println(h.name + " shares with " + (h.sharing - 1));
    }

    Student d = new DayScholar("Anita Rao");
    Hosteller wrong = (Hosteller) d;                // compiles; fails at run time
  }
}

class Student {
  final String name;
  Student(String name) { this.name = name; }
}
class DayScholar extends Student { DayScholar(String n) { super(n); } }
class Hosteller extends Student {
  final int sharing;
  Hosteller(String n, int sharing) { super(n); this.sharing = sharing; }
}
```

```text [Output]
Vikram Shah shares with 1
Exception in thread "main" java.lang.ClassCastException: class DayScholar cannot be cast to class Hosteller (DayScholar and Hosteller are in unnamed module of loader 'app')
	at Casting.main(Casting.java:12)
```

`s instanceof Hosteller h` (Java 16 onwards) checks the type and, if it
matches, gives you a variable `h` already cast. Use it instead of a bare cast
whenever you are not certain.

## Real use case

Frameworks are polymorphism at scale. A web framework keeps a list of
"filters" to run on every request (check the login, log the time, compress the
reply). It calls the same method on each, and each does its own thing:

```java
for (RequestFilter f : filters) {
  f.apply(request);          // LoginFilter, TimingFilter, your own filter...
}
```

The framework was compiled years before your filter existed. It works because
the call is dispatched on the actual object at run time. When you write
`@Override` on a method in a Spring or JUnit class at work, this is what you are
plugging into.

::side-note{kind="go-deeper"}
A chain of `if (x instanceof A) ... else if (x instanceof B) ...` is usually a
sign that the behaviour belongs in an overridden method on the classes
themselves. Pattern matching in `switch` (Java 21) makes type checks tidier,
and is the right tool for data that has no behaviour of its own; for objects
with behaviour, polymorphism is still the first answer.
::

## What confuses people here

::compare{caption="The two most common wrong answers in interviews."}
  :::compare-side{label="Can you override a static method?" verdict="wrong"}
  "Yes, write the same static method in the child." That compiles, but it is
  **hiding**: `m.college()` above ran `Member`'s version even though `m` held
  a `Student`. Nothing was overridden.
  :::
  :::compare-side{label="Are fields polymorphic?" verdict="right"}
  No. `m.campus` printed `Member campus`. A field with the same name in the
  child hides the parent's. Only instance methods are dispatched on the actual
  object, which is one more reason to keep fields `private`.
  :::
::

- **Overloading is chosen by declared type** even when the actual object would
  fit a better overload. `greet(m)` picked `greet(Member)`.
- **A private method is not overridden.** A child method with the same name is
  a new, unrelated method, and the parent's calls still go to the parent's
  private one.
- **`super.method()`** calls the parent's version from inside the override.
  Everything else goes through dynamic dispatch.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between overloading and overriding?" icon="i-lucide-message-circle"}
  Overloading: same method name, different parameter lists, usually in the same
  class, chosen at compile time from the declared argument types. Overriding: a
  subclass supplies its own version of an inherited method with the same
  signature, chosen at run time from the actual object. Prove it with
  `CompileVsRun.java`: `greet(m)` picked the `Member` overload while `m.role()`
  ran the `Student` override.
  :::
  :::accordion-item{label="What is runtime polymorphism, or dynamic method dispatch?" icon="i-lucide-message-circle"}
  Calling an overridden method through a parent-type reference, with the JVM
  choosing the version from the object's actual class at run time.
  `Student s = new Hosteller(...); s.monthlyFeePaise();` runs the hosteller's
  fee calculation.
  :::
  :::accordion-item{label="Can we override a static method? A private one? A final one?" icon="i-lucide-message-circle"}
  None of the three. A static method in the child with the same signature hides
  the parent's (the declared type decides which runs). A private method is
  invisible to the child, so a same-named method is new. A final method
  produces a compile error: `overridden method is final`.
  :::
  :::accordion-item{label="What is a covariant return type?" icon="i-lucide-message-circle"}
  An overriding method may return a subtype of the parent method's return type.
  `Member copy()` can be overridden as `Faculty copy()`, so callers holding a
  `Faculty` need no cast.
  :::
  :::accordion-item{label="Can an overriding method have narrower access?" icon="i-lucide-message-circle"}
  No. It can keep the same access or widen it. Narrowing `public role()` to
  package-private fails with `attempting to assign weaker access privileges;
  was public`. Otherwise code holding a parent reference could call a method
  the child had hidden.
  :::
  :::accordion-item{label="When do you get a ClassCastException, and how do you avoid it?" icon="i-lucide-message-circle"}
  When you downcast an object to a class it is not an instance of:
  `(Hosteller) new DayScholar(...)` compiles and throws at run time. Check
  first with `instanceof`, ideally the pattern form
  `if (s instanceof Hosteller h)`, or better, move the behaviour into an
  overridden method so no cast is needed.
  :::
::
