Two `Applicant` objects with identical details, and Java says they are
different. You already know why: `==` compares addresses, and these are two
objects. This lesson is how you tell Java what "the same" means for your class,
and the one rule about it that most people get wrong.

## Why this matters in a job

"What is the contract between `equals` and `hashCode`?" is, with "String
immutability" and "how does HashMap work", one of the three most-asked core
Java questions in Bangalore fresher interviews. At work, getting it wrong
produces the worst kind of bug: a `HashSet` that holds duplicates, or a
`HashMap` that cannot find an entry sitting inside it. Nothing crashes; the
numbers are wrong.

## Identity against equality

Two photocopies of the same marksheet are two pieces of paper (**identity**:
different objects, different addresses), and they say the same thing
(**equality**: the same meaning). `==` asks about identity. `equals()` is meant
to ask about equality, but only if you tell it what equality means for your
class.

Every class extends `Object` and inherits three methods you will override
constantly:

| Method | What the inherited version does | When to override |
| --- | --- | --- |
| `toString()` | `Applicant@13acb0d1`: class name and hash | Almost always. It is what logs and debuggers print. |
| `equals(Object)` | Compares addresses, the same as `==` | When two distinct objects can mean the same thing |
| `hashCode()` | A number derived from the object's identity | **Always, whenever you override `equals`** |

This lesson uses two collections from the collections chapter ahead of time. A
**`HashSet`** is a bag that refuses duplicates. A **`HashMap`** stores values
under keys and finds a value by its key. Both use `hashCode` and `equals` to
decide what "the same" is, which is why this lesson comes first.

## How it works

### Watch it break

```java [Equality.java]
import java.util.HashSet;
import java.util.Set;

public class Equality {
  public static void main(String[] args) {
    Applicant a = new Applicant("Anita Rao", "anita@lnct.edu");
    Applicant b = new Applicant("Anita Rao", "anita@lnct.edu");

    System.out.println(a == b);
    System.out.println(a.equals(b));
    System.out.println(a);

    Set<Applicant> unique = new HashSet<>();
    unique.add(a);
    unique.add(b);
    System.out.println("Set size: " + unique.size());
  }
}

class Applicant {
  private final String fullName;
  private final String email;
  Applicant(String fullName, String email) { this.fullName = fullName; this.email = email; }
}
```

```text [Output]
false
false
Applicant@13acb0d1
Set size: 2
```

A "set with no duplicates" holding the same applicant twice. (The hash after
the `@` differs on every run.)

### Override equals

The standard shape, which you should be able to write from memory:

```java
@Override
public boolean equals(Object o) {
  if (this == o) return true;                          // same object
  if (!(o instanceof Applicant other)) return false;   // also handles null
  return email.equals(other.email);                    // compare the identity
}
```

::feature-list{columns="2"}
  :::feature{icon="i-lucide-zap" title="this == o first"}
  Cheap, and it guarantees an object equals itself.
  :::
  :::feature{icon="i-lucide-shield" title="instanceof handles null"}
  `null instanceof Applicant` is `false`, so `equals(null)` returns `false`
  instead of throwing, which the contract requires.
  :::
  :::feature{icon="i-lucide-target" title="Decide what identity is"}
  Not necessarily every field. Two records with the same email are the same
  applicant even if one has a newer phone number.
  :::
  :::feature{icon="i-lucide-type" title="The parameter is Object"}
  `equals(Applicant other)` is an overload, not an override, and collections
  never call it. `@Override` catches this.
  :::
::

### And now the part that catches people

Override `equals` and forget `hashCode`:

```java [HalfDone.java]
import java.util.HashMap;
import java.util.Map;

public class HalfDone {
  public static void main(String[] args) {
    Applicant a = new Applicant("Anita Rao", "anita@lnct.edu");
    Applicant b = new Applicant("Anita Rao", "anita@lnct.edu");

    Map<Applicant, Integer> scores = new HashMap<>();
    scores.put(a, 78);

    System.out.println("equal? " + a.equals(b));
    System.out.println("hashes: " + a.hashCode() + " vs " + b.hashCode());
    System.out.println("score for b: " + scores.get(b));
  }
}

class Applicant {
  private final String fullName;
  private final String email;
  Applicant(String fullName, String email) { this.fullName = fullName; this.email = email; }

  @Override
  public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Applicant other)) return false;
    return email.equals(other.email);
  }
  // hashCode NOT overridden
}
```

```text [Output]
equal? true
hashes: 1989335500 vs 1978869058
score for b: null
```

The two objects are equal, and the map cannot find the entry. A `HashMap`
first uses `hashCode()` to pick a **bucket** (one of many small lists inside
the map), and only then calls `equals` on what is in that bucket. Different
hash codes, different buckets, and `equals` is never called at all. The
collections chapter draws the buckets.

::pull-quote
The contract: if two objects are equal, their hash codes must be equal. Break it
and a map looks in the wrong bucket for an entry that is sitting in it.
::

### Doing all three properly

```java [Done.java]
import java.util.HashMap;
import java.util.HashSet;
import java.util.Map;
import java.util.Objects;
import java.util.Set;

public class Done {
  public static void main(String[] args) {
    Applicant a = new Applicant("Anita Rao", "anita@lnct.edu");
    Applicant b = new Applicant("Anita R.", "anita@lnct.edu");     // same email

    Map<Applicant, Integer> scores = new HashMap<>();
    scores.put(a, 78);

    System.out.println("equal? " + a.equals(b));
    System.out.println("same hash? " + (a.hashCode() == b.hashCode()));
    System.out.println("score for b: " + scores.get(b));

    Set<Applicant> unique = new HashSet<>();
    unique.add(a);
    unique.add(b);
    System.out.println("Set size: " + unique.size());
    System.out.println(a);
    System.out.println(a.equals(null));
  }
}

class Applicant {
  private final String fullName;
  private final String email;          // the identity
  Applicant(String fullName, String email) { this.fullName = fullName; this.email = email; }

  @Override
  public boolean equals(Object o) {
    if (this == o) return true;                          // same object
    if (!(o instanceof Applicant other)) return false;   // also handles null
    return email.equals(other.email);                    // compare the identity
  }

  @Override
  public int hashCode() {
    return Objects.hash(email);                          // the SAME fields as equals
  }

  @Override
  public String toString() {
    return "Applicant[" + fullName + ", " + email + "]";
  }
}
```

```text [Output]
equal? true
same hash? true
score for b: 78
Set size: 1
Applicant[Anita Rao, anita@lnct.edu]
false
```

`Objects.hash(...)` combines the fields you pass it into one number. Pass it
exactly the fields `equals` compares, no more and no fewer.

### Records write all three

Since Java 16, a class whose job is to carry data can be one line. A **record**
declares its **components** in brackets and Java generates the rest:

- a `private final` field for each component, and a constructor taking all of
  them;
- an accessor for each, named after it with no `get` prefix: `marks()`;
- `equals` and `hashCode` over **all** components, consistent with each other;
- a readable `toString`.

```java [Records.java]
import java.util.HashSet;
import java.util.Set;

public class Records {
  public static void main(String[] args) {
    ExamResult r1 = new ExamResult("CSE1801", "CS-201", 78);
    ExamResult r2 = new ExamResult("  CSE1801 ", "CS-201", 78);

    System.out.println(r1);
    System.out.println(r1.marks());                 // accessor: no "get"
    System.out.println(r1.equals(r2));
    System.out.println(r1.hashCode() == r2.hashCode());

    Set<ExamResult> results = new HashSet<>();
    results.add(r1);
    results.add(r2);
    System.out.println("Set size: " + results.size());
    System.out.println(r1.grade());

    new ExamResult("CSE1802", "CS-201", 140);
  }
}

record ExamResult(String rollNumber, String subjectCode, int marks) {
  ExamResult {                                      // compact constructor
    if (marks < 0 || marks > 100) {
      throw new IllegalArgumentException("Marks must be 0 to 100, got " + marks);
    }
    rollNumber = rollNumber.strip();                // normalise before assignment
  }

  String grade() {                                  // records can have methods
    return marks >= 75 ? "A" : marks >= 60 ? "B" : marks >= 40 ? "C" : "F";
  }
}
```

```text [Output]
ExamResult[rollNumber=CSE1801, subjectCode=CS-201, marks=78]
78
true
true
Set size: 1
A
Exception in thread "main" java.lang.IllegalArgumentException: Marks must be 0 to 100, got 140
	at ExamResult.<init>(Records.java:27)
	at Records.main(Records.java:20)
```

The **compact constructor** (the record's name with no brackets) runs before
the fields are assigned, so it can validate and normalise: the spaces around
`"  CSE1801 "` were stripped, which is why `r1.equals(r2)` is `true`. The
fields are final: `r.marks = 90` fails with `marks has private access in
ExamResult`.

## Real use case

`toString` is the one you will be grateful for most often, in a log at the
worst possible moment:

```text [Two log lines]
Failed to shortlist: Applicant@13acb0d1
Failed to shortlist: Applicant[Anita Rao, anita@lnct.edu]
```

The first tells you nothing. And records are how modern Java code carries data
between layers: the result of a database query, the body of an API response, a
row read from a CSV. A Spring Boot service written today will have dozens of
small records like `ExamResult`.

::tip
Never put a password, a token or a full Aadhaar or PAN number in `toString`.
Logging libraries call it automatically, and logs are copied, shared and kept
for years. It is a real and common data-protection failure.
::

::pros-cons
---
title: record or class?
pros:
  - "Record: immutable by construction, so safe as a map key and across threads"
  - "Record: equals, hashCode and toString generated and consistent"
  - "Record: the intent is visible; this type carries data"
cons:
  - "Record: fields are always final, so it cannot model something that changes"
  - "Record: cannot extend a class (it may implement interfaces)"
  - "Record: equals uses every component, which is not always what identity means"
---
::

That last point decides it. An `Applicant` identified by email alone should not
be a record, because the record's `equals` would also compare the name.
**Records are for values; classes are for things with an identity and a
life cycle.**

## What confuses people here

### A mutable key goes missing

```java [MutableKey.java]
import java.util.HashSet;
import java.util.Objects;
import java.util.Set;

public class MutableKey {
  public static void main(String[] args) {
    Course c = new Course("CS-201");
    Set<Course> offered = new HashSet<>();
    offered.add(c);

    c.code = "CS-202";                       // change a field equals/hashCode use
    System.out.println(offered.contains(c)); // the same object...
    System.out.println(offered.size());
  }
}

class Course {
  String code;
  Course(String code) { this.code = code; }
  @Override public boolean equals(Object o) { return o instanceof Course k && code.equals(k.code); }
  @Override public int hashCode() { return Objects.hash(code); }
}
```

```text [Output]
false
1
```

The set holds the object and says it does not. It was filed in the bucket for
`CS-201`'s hash; now its hash is `CS-202`'s, so the set looks in the wrong
bucket. Fields used by `equals` and `hashCode` should be `final`, which is one
more reason records are good keys.

- **Equal objects must have equal hash codes; the reverse is not required.**
  Two unequal objects sharing a hash is a **collision**, which is normal.
  `hashCode() { return 1; }` is legal and turns every lookup into a search
  through one long list.
- **`equals(Applicant o)` is not an override.** Without `@Override` it compiles
  and collections ignore it.
- **`==` on records** still compares addresses. Use `equals`.

## Interview questions

::accordion
  :::accordion-item{label="What is the contract between equals and hashCode?" icon="i-lucide-message-circle"}
  If `a.equals(b)` is true, `a.hashCode() == b.hashCode()` must be true.
  Unequal objects may share a hash code. The consequence is what they are
  listening for: `HashMap` hashes first to pick a bucket, so with `equals`
  overridden and `hashCode` not, `HalfDone.java` printed `score for b: null`
  for an entry that was in the map.
  :::
  :::accordion-item{label="What is the difference between == and equals()?" icon="i-lucide-message-circle"}
  `==` compares references (are these the same object?) for objects, and
  values for primitives. `equals()` compares meaning, as defined by the class;
  the version inherited from `Object` behaves like `==`. `String`, `Integer`
  and records override it to compare contents.
  :::
  :::accordion-item{label="What are the properties of a correct equals?" icon="i-lucide-message-circle"}
  Reflexive (`a.equals(a)`), symmetric (if `a.equals(b)` then `b.equals(a)`),
  transitive, consistent (the same answer while nothing changes), and
  `a.equals(null)` is `false`. The `this == o` and `instanceof` lines in the
  standard shape cover the first and the last.
  :::
  :::accordion-item{label="What is a record and when would you not use one?" icon="i-lucide-message-circle"}
  A class declared as `record ExamResult(String rollNumber, int marks)`,
  immutable, with a constructor, accessors, `equals`, `hashCode` and
  `toString` generated. Not for anything that changes over time, anything that
  must extend a class, or anything whose identity is a subset of its fields
  (an `Applicant` identified by email).
  :::
  :::accordion-item{label="Why should HashMap keys be immutable?" icon="i-lucide-message-circle"}
  Because the map stores each entry in the bucket for the key's hash at the
  time it was added. Change a field that `hashCode` uses and the key's hash
  changes, so later lookups search the wrong bucket. `MutableKey.java` printed
  `false` for an object that was in the set.
  :::
::
