A student, a faculty member and an office clerk all need a name, an email and
the same validation. Copy it into three classes and you fix every bug three
times. **Inheritance** lets one class say "everything that class has, plus a
few extras of my own".

## Why this matters in a job

Every framework you will use at work is built on it: your class extends a
framework class, or the framework calls your code through a parent type. In
interviews, inheritance is the second of the four OOPs pillars, and it brings
fixed questions with it: types of inheritance, why Java has no multiple
inheritance of classes, what `super` does, the order constructors run in, and
"composition or inheritance?". Knowing when **not** to inherit is what
separates a design that lasts from a hierarchy nobody can change.

## An IS-A relationship

Inheritance models **IS-A**. A student **is a** member of the college. A
faculty member **is a** member of the college. Whatever is true of every member
(a name, an email) is written once in `Member`, and `Student` and `Faculty`
**inherit** it.

- The class being inherited from is the **parent**, **superclass** or **base
  class**.
- The class inheriting is the **child**, **subclass** or **derived class**.
- The keyword is `extends`.

## Syntax

```java
class Student extends Member {
  Student(String name, String email, String rollNumber) {
    super(name, email);          // call the parent's constructor, first line
    this.rollNumber = rollNumber;
  }
}
```

```java [Campus.java]
public class Campus {
  public static void main(String[] args) {
    Student s = new Student("Anita Rao", "anita@lnct.edu", "CSE1801");
    Faculty f = new Faculty("K. Menon", "menon@lnct.edu", "Computer Science");

    // Inherited from Member: written once, available on both.
    System.out.println(s.getName() + " <" + s.getEmail() + ">");
    System.out.println(f.getName() + " <" + f.getEmail() + ">");

    // Their own extras.
    System.out.println(s.getRollNumber());
    System.out.println(f.getDepartment());

    // Every class extends Object in the end.
    System.out.println(s instanceof Member);
    System.out.println(s instanceof Object);
  }
}

class Member {
  private final String name;
  private final String email;

  Member(String name, String email) {
    if (name == null || name.isBlank()) {
      throw new IllegalArgumentException("A member needs a name");
    }
    this.name = name;
    this.email = email;
  }

  String getName()  { return name; }
  String getEmail() { return email; }
}

class Student extends Member {
  private final String rollNumber;

  Student(String name, String email, String rollNumber) {
    super(name, email);                 // build the Member part first
    this.rollNumber = rollNumber;
  }

  String getRollNumber() { return rollNumber; }
}

class Faculty extends Member {
  private final String department;

  Faculty(String name, String email, String department) {
    super(name, email);
    this.department = department;
  }

  String getDepartment() { return department; }
}
```

```bash [Terminal]
javac Campus.java && java Campus
```

```text [Output]
Anita Rao <anita@lnct.edu>
K. Menon <menon@lnct.edu>
CSE1801
Computer Science
true
true
```

The name validation exists once, in `Member`, and both children get it. `Student`
cannot read `Member`'s `private` fields directly; it inherits them but reaches
them through `getName()`. `instanceof` checks "is this object a kind of that
type", and every object is an `Object`, the class at the top of every hierarchy
in Java.

### super, the other half of this

`super(...)` calls the parent's constructor. `super.method()` calls the
parent's version of a method, which is useful when the child wants to add to it
rather than replace it:

```java [SuperCall.java]
public class SuperCall {
  public static void main(String[] args) {
    Member m = new Member("Rohit Das");
    Student s = new Student("Anita Rao", "CSE1801");
    System.out.println(m.idCard());
    System.out.println(s.idCard());
  }
}

class Member {
  protected final String name;
  Member(String name) { this.name = name; }
  String idCard() { return "LNCT | " + name; }
}

class Student extends Member {
  private final String rollNumber;
  Student(String name, String rollNumber) {
    super(name);
    this.rollNumber = rollNumber;
  }

  @Override
  String idCard() {
    return super.idCard() + " | " + rollNumber;   // reuse the parent's, then add
  }
}
```

```text [Output]
LNCT | Rohit Das
LNCT | Anita Rao | CSE1801
```

A child writing its own version of a parent method is **overriding**, and
`@Override` asks the compiler to check that you really are overriding
something. The next lesson is entirely about what that makes possible.
`protected` means "visible to subclasses"; the access modifiers lesson has the
full table.

### Construction order

`new HostelStudent(...)` builds from the top of the hierarchy down. Watch it:

```java [BuildOrder.java]
public class BuildOrder {
  public static void main(String[] args) {
    new HostelStudent("Vikram Shah");
  }
}

class Member {
  Member(String name) {
    System.out.println("1. Member constructor: " + name);
  }
}

class Student extends Member {
  private String batch = initBatch();

  Student(String name) {
    super(name);
    System.out.println("3. Student constructor, batch " + batch);
  }

  private String initBatch() {
    System.out.println("2. Student field initialiser");
    return "2018";
  }
}

class HostelStudent extends Student {
  HostelStudent(String name) {
    super(name);
    System.out.println("4. HostelStudent constructor");
  }
}
```

```text [Output]
1. Member constructor: Vikram Shah
2. Student field initialiser
3. Student constructor, batch 2018
4. HostelStudent constructor
```

::flow{numbered direction="vertical" caption="new HostelStudent(...) builds from the parent down. Always."}
  :::flow-step{label="All fields get defaults" icon="i-lucide-circle-dot"}
  Everything in the whole chain: 0, `false`, `null`.
  :::
  :::flow-step{label="The parent is built first" icon="i-lucide-arrow-up" highlight}
  `super(...)` runs, explicitly or implicitly, all the way up to `Object`.
  :::
  :::flow-step{label="This class's field initialisers run" icon="i-lucide-equal"}
  `private String batch = initBatch();` happens here, after the parent is done.
  :::
  :::flow-step{label="This constructor's body runs" icon="i-lucide-hammer"}
  By now the parent part of the object is fully valid.
  :::
::

If you write no `super(...)`, Java inserts `super()` with no arguments. If the
parent has no no-argument constructor, that fails:

### Types of inheritance

::feature-list{columns="2"}
  :::feature{icon="i-lucide-arrow-down" title="Single"}
  `Student extends Member`. One parent, one child.
  :::
  :::feature{icon="i-lucide-layers" title="Multilevel"}
  `HostelStudent extends Student extends Member`. A chain.
  :::
  :::feature{icon="i-lucide-git-fork" title="Hierarchical"}
  `Student` and `Faculty` both extend `Member`. One parent, several children.
  :::
  :::feature{icon="i-lucide-x" title="Multiple (not with classes)"}
  One class with two parent classes. Java refuses it. Interfaces are the way
  round, in the abstraction lesson.
  :::
::

```java
class WorkingStudent extends Student, Employee { }
```

```text [Output]
TwoParents.java:3: error: '{' expected
class WorkingStudent extends Student, Employee { }
                                    ^
```

Why no multiple inheritance of classes? The **diamond problem**: if `Student`
and `Employee` both have an `idCard()` method and `WorkingStudent` extends both,
which one does `workingStudent.idCard()` run? C++ lets you tie that knot; Java's
designers decided one parent class was worth the simplicity.

## Real use case

The honest use case at work is often **composition** instead. A fee report
needs to format rows. It is tempting to write `class FeeReport extends
Formatter`, but a fee report is not a kind of formatter; it **has** one. That
is a **HAS-A** relationship, and it is a field.

```java [FeeReport.java]
public class FeeReport {
  private final Formatter formatter;          // HAS-A: a field, not a parent

  FeeReport(Formatter formatter) { this.formatter = formatter; }

  String render(String[] names, long[] duesPaise) {
    StringBuilder sb = new StringBuilder();
    for (int i = 0; i < names.length; i++) {
      sb.append(formatter.row(names[i], duesPaise[i])).append('\n');
    }
    return sb.toString();
  }

  public static void main(String[] args) {
    String[] names = {"Anita Rao", "Vikram Shah"};
    long[] dues = {0L, 1_250_000L};
    System.out.print(new FeeReport(new Formatter()).render(names, dues));
    System.out.print(new FeeReport(new CsvFormatter()).render(names, dues));
  }
}

class Formatter {
  String row(String name, long paise) {
    return String.format("%-12s Rs %,d.%02d", name, paise / 100, paise % 100);
  }
}

class CsvFormatter extends Formatter {        // a CSV formatter IS-A formatter
  @Override
  String row(String name, long paise) {
    return name + "," + (paise / 100) + "." + String.format("%02d", paise % 100);
  }
}
```

```text [Output]
Anita Rao    Rs 0.00
Vikram Shah  Rs 12,500.00
Anita Rao,0.00
Vikram Shah,12500.00
```

Both relationships in one program. `CsvFormatter extends Formatter` is true
IS-A. `FeeReport` holds a `Formatter` as a field, so the format can be swapped
without touching the report, and none of the formatter's methods leak onto it.

::pros-cons
---
title: extends, honestly
pros:
  - Models a real IS-A relationship, and shared code lives in one place
  - Lets code work through the parent type, which the next lesson is about
cons:
  - Only one parent, ever, and changing it later breaks every child
  - Children depend on the parent's internals, so a change in the parent can break them
  - Hierarchies deepen over time and become hard to reason about
  - Often used for code reuse where the IS-A is not true
---
::

::pull-quote
The test: can you say "every Y is an X", and will it stay true? If what you mean
is "a Y has an X" or "a Y uses an X", use a field. Prefer composition over
inheritance is one of the few design rules almost everyone agrees on.
::

## What confuses people here

### Calling an overridable method from a constructor

```java [ConstructorTrap.java]
public class ConstructorTrap {
  public static void main(String[] args) {
    new Student("Farah Khan", "cse1812");
  }
}

class Member {
  Member(String name) {
    System.out.println("Welcome, " + describe());   // runs the CHILD's version
  }
  String describe() { return "member"; }
}

class Student extends Member {
  private final String rollNumber;

  Student(String name, String rollNumber) {
    super(name);                        // Member's constructor runs first...
    this.rollNumber = rollNumber;       // ...so this line has not happened yet
  }

  @Override
  String describe() { return "student " + rollNumber.toUpperCase(); }
}
```

```text [Output]
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.toUpperCase()" because "this.rollNumber" is null
	at Student.describe(ConstructorTrap.java:23)
	at Member.<init>(ConstructorTrap.java:9)
	at Student.<init>(ConstructorTrap.java:18)
	at ConstructorTrap.main(ConstructorTrap.java:3)
```

A `final` field was read as `null`. The parent constructor called `describe()`,
Java ran the child's version (because the object really is a `Student`), and the
child's field had not been assigned yet. Rule: never call an overridable method
from a constructor.

- **Private members are not inherited in any usable way.** The child object
  contains the parent's private fields, but the child's code cannot name them.
- **Constructors are not inherited.** Each class writes its own and calls the
  parent's with `super(...)`.
- **`super` and `this` both have to be first** in a constructor, so a
  constructor can call one or the other, never both.

## Interview questions

::accordion
  :::accordion-item{label="What is inheritance and why use it?" icon="i-lucide-message-circle"}
  A class acquiring the fields and methods of another with `extends`, modelling
  an IS-A relationship. It removes duplication (validation written once in
  `Member`) and lets code work with the parent type. Then add the caveat that
  shows judgement: when the relationship is HAS-A, composition is better.
  :::
  :::accordion-item{label="Why does Java not support multiple inheritance of classes?" icon="i-lucide-message-circle"}
  To avoid the diamond problem: with two parents defining the same method, it
  is ambiguous which one the child inherits, and two parents' fields can
  conflict. `class WorkingStudent extends Student, Employee` does not compile.
  A class can implement several interfaces instead.
  :::
  :::accordion-item{label="In what order are constructors called?" icon="i-lucide-message-circle"}
  Parent first, all the way up to `Object`, then each child's field
  initialisers and constructor body on the way back down. `BuildOrder.java`
  prints Member, then Student's field initialiser, then Student, then
  HostelStudent.
  :::
  :::accordion-item{label="What is the difference between super and this?" icon="i-lucide-message-circle"}
  `this` refers to the current object; `this(...)` calls another constructor
  of the same class. `super` refers to the parent part of the current object;
  `super(...)` calls the parent's constructor and `super.method()` calls the
  parent's version of an overridden method. Both constructor calls must be the
  first statement.
  :::
  :::accordion-item{label="What is the difference between IS-A and HAS-A?" icon="i-lucide-message-circle"}
  IS-A is inheritance: a `CsvFormatter` is a `Formatter`. HAS-A is
  composition: a `FeeReport` has a `Formatter` as a field. Composition is more
  flexible: the part can be swapped at run time and tested on its own.
  :::
  :::accordion-item{label="Which class is the parent of every class in Java?" icon="i-lucide-message-circle"}
  `java.lang.Object`. A class with no `extends` extends `Object` implicitly,
  which is why every object has `toString()`, `equals()` and `hashCode()`.
  `s instanceof Object` printed `true` above.
  :::
::
