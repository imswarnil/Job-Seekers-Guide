`Map<Applicant, Integer>` stored a score as `Integer`, not `int`. Collections
only hold objects, and the eight primitives are not objects, so each has a
**wrapper class**: an object that holds one primitive value. This lesson is
about the wrappers, and the three traps they bring.

## Why this matters in a job

You use wrappers every day without typing their names: every `List<Integer>`,
every `Integer.parseInt` on a form field, every `Map<String, Double>` of fees.
The traps are real production bugs: an `==` that works in testing (small
numbers) and fails in production (large ones), and a `NullPointerException` on
a line with no dot in it. "What is the Integer cache?" and "what will
`Integer a = 128, b = 128; a == b` print?" are staple written-round and
interview questions.

## A primitive in a box

Picture a college locker that only takes parcels. Your marks are a number
written on a slip (a primitive). To put the slip in the locker, you seal it in
an envelope (the wrapper object). Taking it out, you open the envelope and get
the slip back.

| Primitive | Wrapper |
| --- | --- |
| `byte` | `Byte` |
| `short` | `Short` |
| `int` | **`Integer`** |
| `long` | `Long` |
| `float` | `Float` |
| `double` | `Double` |
| `char` | **`Character`** |
| `boolean` | `Boolean` |

Six are the primitive's name with a capital letter; `int` and `char` are the
two to remember. All eight live in `java.lang` and are immutable, like
`String`.

Since Java 5, the sealing and opening happen automatically:

- **Autoboxing**: Java turns an `int` into an `Integer` when an object is
  needed (`list.add(78)`).
- **Unboxing**: Java turns an `Integer` back into an `int` when a primitive is
  needed (`int first = list.get(0)`).

## How it works

```java [Wrappers.java]
import java.util.ArrayList;
import java.util.List;

public class Wrappers {
  public static void main(String[] args) {
    // A collection can only hold objects.
    List<Integer> marks = new ArrayList<>();
    marks.add(78);                   // autoboxing: int 78 -> Integer
    marks.add(64);
    int first = marks.get(0);        // unboxing: Integer -> int
    System.out.println(marks + ", first = " + first);

    // Parsing text: what you get from a form, a file or Scanner.nextLine()
    int score = Integer.parseInt("81");          // returns int
    Integer boxed = Integer.valueOf("81");       // returns Integer
    double cgpa = Double.parseDouble("8.45");
    boolean hosteller = Boolean.parseBoolean("TRUE");
    System.out.println(score + " " + boxed + " " + cgpa + " " + hosteller);

    // Useful constants and helpers
    System.out.println(Integer.MAX_VALUE + " " + Integer.MIN_VALUE);
    System.out.println(Integer.toBinaryString(10) + " " + Integer.toHexString(255));
    System.out.println(Character.isDigit('7') + " " + Character.isLetter('A') + " " + Character.toUpperCase('b'));
    System.out.println(Integer.compare(64, 78) + " " + Integer.max(64, 78));
  }
}
```

```bash [Terminal]
javac Wrappers.java && java Wrappers
```

```text [Output]
[78, 64], first = 78
81 81 8.45 true
2147483647 -2147483648
1010 ff
true true B
-1 78
```

`parseInt` returns a primitive `int`; `valueOf` returns an `Integer` object.
Use `parseInt` when you want a number to calculate with, which is most of the
time.

### The Integer cache

This is the famous one.

```java [Cache.java]
public class Cache {
  public static void main(String[] args) {
    Integer a = 127, b = 127;
    Integer c = 128, d = 128;

    System.out.println("127 == 127: " + (a == b));
    System.out.println("128 == 128: " + (c == d));
    System.out.println("128 equals 128: " + c.equals(d));

    Integer e = new Integer(127);            // deprecated: always a new object
    System.out.println("new Integer(127) == 127: " + (e == a));
    System.out.println("valueOf(127) == 127: " + (Integer.valueOf(127) == a));
  }
}
```

```text [Output]
Cache.java:10: warning: [removal] Integer(int) in Integer has been deprecated and marked for removal
    Integer e = new Integer(127);            // deprecated: always a new object
                ^
1 warning
127 == 127: true
128 == 128: false
128 equals 128: true
new Integer(127) == 127: false
valueOf(127) == 127: true
```

Autoboxing calls `Integer.valueOf(...)`, and `valueOf` keeps a ready-made
`Integer` object for every value from **-128 to 127**. Box 127 twice and you
get the same cached object, so `==` (which compares addresses) says `true`.
Box 128 twice and you get two new objects, so `==` says `false`. The same
caching applies to `Byte`, `Short`, `Long` and `Character` (0 to 127) and to
both `Boolean` values.

::memory{kind="array" caption="The cache is an array of ready-made Integer objects. Values outside it are created fresh each time."}
---
cells:
  - { value: "-128", label: "cached" }
  - { value: "…", label: "" }
  - { value: "0", label: "cached" }
  - { value: "…", label: "" }
  - { value: "127", label: "last cached", state: "active" }
  - { value: "128", label: "new object", state: "ghost" }
---
::

::warning{icon="i-lucide-alert-triangle"}
The rule that makes the cache irrelevant: **never compare wrapper objects with
`==`.** Use `equals`, or unbox first. A test with marks below 128 passes; the
same code comparing roll IDs or rupee amounts fails in production.
::

## Real use case

Every value that arrives as text (a form field, a CSV column, a line typed at a
`Scanner`) becomes a number through a wrapper's `parse` method, and some of
that text will be wrong. The robust version catches the failure:

```java [BadParse.java]
public class BadParse {
  public static void main(String[] args) {
    String[] typed = {"78", " 64", "eighty", ""};
    for (String t : typed) {
      try {
        System.out.println("parsed " + Integer.parseInt(t));
      } catch (NumberFormatException e) {
        System.out.println("rejected: " + e.getMessage());
      }
    }
    System.out.println(Integer.parseInt(" 64".strip()));
  }
}
```

```text [Output]
parsed 78
rejected: For input string: " 64"
rejected: For input string: "eighty"
rejected: For input string: ""
64
```

A single leading space is enough to reject `" 64"`. Strip input before parsing
it; that one habit prevents most of these in upload jobs.

::real-life{title="Where null wrappers come from at work" source="Databases and JSON"}
A database column that allows `NULL`, or a JSON field that is missing, is read
into Java as a `null` `Integer` or `Double`. That is a feature: `null` means "no
marks entered", which is different from 0. It becomes a bug the moment it is
unboxed into an `int`, and that is the trap below.
::

## What confuses people here

### Unboxing null

```java [UnboxNull.java]
import java.util.HashMap;
import java.util.Map;

public class UnboxNull {
  public static void main(String[] args) {
    Map<String, Integer> attendance = new HashMap<>();
    attendance.put("CSE1801", 36);

    int anita = attendance.get("CSE1801");
    System.out.println("Anita: " + anita);

    int vikram = attendance.get("CSE1802");      // no entry: get returns null
    System.out.println("Vikram: " + vikram);
  }
}
```

```text [Output]
Anita: 36
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.lang.Integer.intValue()" because the return value of "java.util.Map.get(Object)" is null
	at UnboxNull.main(UnboxNull.java:12)
```

Line 12 has no dot anywhere in `int vikram = attendance.get(...)` except the
`get` call, and the exception is about `intValue()`, a method you never wrote.
Java inserted it to unbox. When you read an `Integer` that might be absent,
keep it as `Integer` and check for `null`, or use
`attendance.getOrDefault("CSE1802", 0)`.

### remove(int) against remove(Object)

```java [RemoveTrap.java]
import java.util.ArrayList;
import java.util.List;

public class RemoveTrap {
  public static void main(String[] args) {
    List<Integer> rollNumbers = new ArrayList<>(List.of(10, 20, 30, 1));
    rollNumbers.remove(1);                          // remove(int index)
    System.out.println(rollNumbers);

    rollNumbers.remove(Integer.valueOf(1));         // remove(Object value)
    System.out.println(rollNumbers);
  }
}
```

```text [Output]
[10, 30, 1]
[10, 30]
```

`remove(1)` removed the element **at index 1** (20), not the value 1. Overload
resolution prefers the exact `int` match over boxing, the rule from the methods
lesson, and here it changes the meaning completely.

- **Boxing in a hot loop is slow.** Adding 50 million numbers into a `Long`
  took 117–167 ms on my machine against 13–14 ms with a `long`, because every
  `+=` unboxes, adds and boxes a new object. Use primitives for arithmetic.
- **`Integer.equals(Long)` is false** even for the same number:
  `Integer.valueOf(78).equals(78L)` is `false`, because the types differ.
- **`new Integer(127)` is deprecated** (marked for removal). Use
  `Integer.valueOf(127)` or plain autoboxing.

## Interview questions

::accordion
  :::accordion-item{label="What are wrapper classes and why do we need them?" icon="i-lucide-message-circle"}
  Classes that wrap one primitive value in an object: `Integer`, `Double`,
  `Character`, `Boolean` and four more. Needed because collections and generics
  work only with objects (`List<Integer>`, never `List<int>`), because they can
  be `null` (meaning "no value"), and for utility methods such as
  `Integer.parseInt`.
  :::
  :::accordion-item{label="What does Integer a = 128, b = 128; a == b print, and why?" icon="i-lucide-message-circle"}
  `false`. Autoboxing uses `Integer.valueOf`, which returns cached objects only
  for -128 to 127. 128 produces two distinct objects, and `==` compares
  references. With 127 it prints `true`. `a.equals(b)` is `true` in both cases,
  which is why wrappers are always compared with `equals`.
  :::
  :::accordion-item{label="What is the difference between parseInt and valueOf?" icon="i-lucide-message-circle"}
  `Integer.parseInt("81")` returns a primitive `int`. `Integer.valueOf("81")`
  returns an `Integer` object, from the cache if the value is between -128 and
  127. Both throw `NumberFormatException` for text that is not a number.
  :::
  :::accordion-item{label="What is autoboxing, and can it throw an exception?" icon="i-lucide-message-circle"}
  The automatic conversion between a primitive and its wrapper: boxing on the
  way into an object context, unboxing on the way out. Unboxing a `null` throws
  `NullPointerException`, as `int vikram = attendance.get("CSE1802")` did.
  :::
  :::accordion-item{label="Are wrapper classes mutable?" icon="i-lucide-message-circle"}
  No, all eight are immutable. `count++` on an `Integer count` unboxes, adds
  one, and boxes a new `Integer` into the variable. The old object is
  unchanged, which is also why an `Integer` passed to a method cannot be
  changed by it.
  :::
::
