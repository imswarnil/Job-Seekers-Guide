`Student.monthlyFeePaise()` was a guess nobody should call, and nothing stopped
anyone writing `new Student(...)`. **Abstraction** is how a parent says "every
child must define this" without pretending to know the answer, and how a class
can promise a capability without saying how it is done.

## Why this matters in a job

"Abstract class or interface?" is one of the five questions I would bet on in
any Java technical round, together with its follow-ups: can an abstract class
have a constructor, what are default methods for, what happens when two
interfaces have the same default method. At work, interfaces are everywhere:
you will code against `List`, not `ArrayList`, and against a
`PaymentGateway` interface, not a particular bank. The practical reason, which
tutorials rarely give, is that interfaces are what make code testable without
a database or a network.

## Abstraction: the college's rulebook

The university's rulebook says "every department must publish a timetable". It
does not say how the Computer Science department arranges its labs. That is
abstraction: **what** must happen is fixed; **how** is left to whoever does it.
The person reading the notice board only needs to know that a timetable
exists.

Java has two tools for it:

- An **abstract class** is a class that cannot be instantiated and may contain
  **abstract methods** (declared with no body). It can also have fields,
  constructors and ordinary methods. It says what something **is**.
- An **interface** is a pure contract: a list of methods a class promises to
  provide. It has no instance fields and no constructor. It says what
  something **can do**. A class **implements** as many interfaces as it likes.

## How it works

### Abstract classes

```java [AbstractFee.java]
public class AbstractFee {
  public static void main(String[] args) {
    Student[] students = { new DayScholar("Anita Rao"), new Hosteller("Vikram Shah", 2) };
    for (Student s : students) {
      System.out.println(s.feeSlip());
    }
  }
}

abstract class Student {
  private final String name;
  protected static final long TUITION_PAISE = 750_000;

  Student(String name) {                  // abstract classes CAN have constructors
    this.name = name;
  }

  abstract long monthlyFeePaise();        // no body: every child must supply one

  String feeSlip() {                      // a concrete method using the abstract one
    return String.format("%-12s Rs %,d", name, monthlyFeePaise() / 100);
  }
}

class DayScholar extends Student {
  DayScholar(String name) { super(name); }
  @Override long monthlyFeePaise() { return TUITION_PAISE + 120_000; }
}

class Hosteller extends Student {
  private final int sharing;
  Hosteller(String name, int sharing) { super(name); this.sharing = sharing; }
  @Override long monthlyFeePaise() { return TUITION_PAISE + (sharing == 1 ? 900_000 : 600_000); }
}
```

```bash [Terminal]
javac AbstractFee.java && java AbstractFee
```

```text [Output]
Anita Rao    Rs 8,700
Vikram Shah  Rs 13,500
```

`feeSlip()` is written once in the parent and calls `monthlyFeePaise()`,
which the parent never defines. At run time dynamic dispatch picks the child's
version. This shape (a fixed procedure in the parent with one or two steps left
for children) is the **template method** pattern, and it is all over framework
code.

The compiler now enforces both rules that were only conventions before:

```text [Output]
AbstractErrors.java:3: error: Student is abstract; cannot be instantiated
    Student s = new Student("Anita Rao");
                ^
AbstractErrors.java:12: error: ExchangeStudent is not abstract and does not override abstract method monthlyFeePaise() in Student
class ExchangeStudent extends Student {
^
2 errors
```

### Interfaces

```java [Notices.java]
public class Notices {
  public static void main(String[] args) {
    Notifiable[] recipients = {
      new Hosteller("Vikram Shah", "vikram@lnct.edu"),
      new Faculty("K. Menon", "menon@lnct.edu"),
      new Department("Computer Science", "cse-office@lnct.edu")
    };
    for (Notifiable n : recipients) {
      System.out.println(n.greeting() + " -> " + n.contact());
    }
    System.out.println(Notifiable.isValidEmail("menon@lnct.edu"));
    System.out.println(Notifiable.isValidEmail("menon.lnct.edu"));

    Payable p = new Hosteller("Farah Khan", "farah@lnct.edu");
    System.out.println("Payable: Rs " + p.amountDuePaise() / 100);
  }
}

interface Notifiable {
  String contact();                        // abstract: implicitly public abstract
  String displayName();

  default String greeting() {              // default: a body, shared by all
    return "Dear " + displayName() + ",";
  }

  static boolean isValidEmail(String e) {  // static: called on the interface
    return e != null && e.contains("@");
  }
}

interface Payable {
  long amountDuePaise();
}

class Member {
  protected final String name;
  protected final String email;
  Member(String name, String email) { this.name = name; this.email = email; }
}

// one parent class, any number of interfaces
class Hosteller extends Member implements Notifiable, Payable {
  Hosteller(String name, String email) { super(name, email); }
  public String contact()       { return email; }
  public String displayName()   { return name; }
  public long amountDuePaise()  { return 1_350_000; }
}

class Faculty extends Member implements Notifiable {
  Faculty(String name, String email) { super(name, email); }
  public String contact()     { return email; }
  public String displayName() { return "Dr. " + name; }
}

// not a Member at all, and still Notifiable
class Department implements Notifiable {
  private final String title, office;
  Department(String title, String office) { this.title = title; this.office = office; }
  public String contact()     { return office; }
  public String displayName() { return "Head of " + title; }
  @Override public String greeting() { return "To the " + displayName() + ","; }
}
```

```text [Output]
Dear Vikram Shah, -> vikram@lnct.edu
Dear Dr. K. Menon, -> menon@lnct.edu
To the Head of Computer Science, -> cse-office@lnct.edu
true
false
Payable: Rs 13500
```

A `Department` is not a `Member`, and it can still be sent a notice, because
the ability to be notified has nothing to do with being a person. That is what
an interface is for. Note that the implementing methods must be `public`:
interface methods are implicitly `public`, and an override cannot narrow access.

What an interface may contain, by Java version:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-square-dashed" title="Abstract methods"}
  Implicitly `public abstract`. The contract itself.
  :::
  :::feature{icon="i-lucide-hash" title="Constants"}
  Every field is implicitly `public static final`. No instance state.
  :::
  :::feature{icon="i-lucide-copy-plus" title="default methods (Java 8)"}
  A method with a body that implementers inherit and may override.
  :::
  :::feature{icon="i-lucide-function-square" title="static and private methods (Java 8, 9)"}
  `static` helpers called on the interface; `private` helpers shared by its
  default methods.
  :::
::

### Default methods and the diamond problem

Default methods were added in Java 8 so that interfaces such as `List` could
gain `forEach`, `sort` and `removeIf` without breaking every class that already
implemented them. They bring back a small version of the diamond problem: two
interfaces, the same default method.

```text [Output]
DiamondError.java:4: error: types StudentRole and StaffRole are incompatible;
class TeachingAssistant implements StudentRole, StaffRole { }
^
  class TeachingAssistant inherits unrelated defaults for badge() from types StudentRole and StaffRole
```

Java refuses to guess. You must override the method, and you can call either
parent's version with `InterfaceName.super.method()`:

```java [Diamond.java]
public class Diamond {
  public static void main(String[] args) {
    System.out.println(new TeachingAssistant().badge());
  }
}

interface StudentRole { default String badge() { return "STUDENT"; } }
interface StaffRole   { default String badge() { return "STAFF"; } }

class TeachingAssistant implements StudentRole, StaffRole {
  // Without this override the class does not compile.
  @Override
  public String badge() {
    return StudentRole.super.badge() + " + " + StaffRole.super.badge();
  }
}
```

```text [Output]
STUDENT + STAFF
```

### The decision, stated plainly

| | Abstract class | Interface |
| --- | --- | --- |
| Instance fields | Yes | **No** (constants only) |
| Constructor | Yes | **No** |
| Method bodies | Yes | `default`, `static`, `private` only |
| A class can have | **One** parent class | **Any number** of interfaces |
| Access of members | Anything | Methods are `public` (except `private` helpers) |
| Use when | Subtypes share **state and construction** | Types share a **capability** |

::pull-quote
An abstract class says what something is. An interface says what something can
do. A class has one identity and any number of capabilities, and that
asymmetry is the whole answer.
::

## Real use case

This is the reason interfaces are everywhere in real code, and the part that
makes an interviewer look up. A class that sends shortlist emails should not
create its own email sender. It should ask for **something that can send**:

```java [Notify.java]
public class Notify {
  public static void main(String[] args) {
    String[] shortlisted = {"anita@lnct.edu", "vikram@lnct.edu"};

    // In production: the real sender.
    new ShortlistNotifier(new ConsoleSender()).notifyEach(shortlisted);

    // In a test: a fake that records instead of sending.
    RecordingSender fake = new RecordingSender();
    new ShortlistNotifier(fake).notifyEach(shortlisted);
    System.out.println("Fake recorded " + fake.count + " message(s); last to " + fake.lastTo);
  }
}

interface MessageSender {
  void send(String to, String body);
}

class ConsoleSender implements MessageSender {
  public void send(String to, String body) {
    System.out.println("EMAIL to " + to + ": " + body);
  }
}

class RecordingSender implements MessageSender {
  int count;
  String lastTo;
  public void send(String to, String body) { count++; lastTo = to; }
}

class ShortlistNotifier {
  private final MessageSender sender;         // depends on the capability

  ShortlistNotifier(MessageSender sender) {   // handed in, not created here
    this.sender = sender;
  }

  void notifyEach(String[] emails) {
    for (String e : emails) {
      sender.send(e, "You have been shortlisted for B.Tech CSE.");
    }
  }
}
```

```text [Output]
EMAIL to anita@lnct.edu: You have been shortlisted for B.Tech CSE.
EMAIL to vikram@lnct.edu: You have been shortlisted for B.Tech CSE.
Fake recorded 2 message(s); last to vikram@lnct.edu
```

The same `ShortlistNotifier` ran twice: once sending, once recording, and it
could not tell the difference. That is how you test code that talks to email,
payment gateways or databases without any of them being there.

::real-life{title="Why every framework you meet is built this way" source="Spring, and everything like it"}
Handing a dependency in instead of creating it inside is called **dependency
injection**, and it is most of what the Spring framework does. `@Autowired
MessageSender sender` is Spring deciding, at start-up, which implementation to
hand you: the real one in production, a fake in a test. Most freshers learn the
annotation first and the reason years later. Explaining the reason in an
interview is rare, and it is noticed.
::

## What confuses people here

- **An abstract class can have a constructor.** You cannot call it with `new`,
  but children call it with `super(...)` to build the parent part, exactly as in
  `AbstractFee.java`.
- **An abstract class need not have any abstract methods.** Marking a class
  `abstract` only forbids `new`. And a class with even one abstract method must
  be declared `abstract`.
- **Interface fields are constants.** `int MIN_ATTENDANCE = 75;` in an
  interface is `public static final`, and assigning to it fails with `cannot
  assign a value to static final variable MIN_ATTENDANCE`.
- **`abstract` and `final` cannot go together.** An abstract method must be
  overridden and a final one cannot be; the compiler reports the combination as
  illegal. The same goes for `abstract` with `private` or `static` methods.
- **A marker interface** has no methods at all (`Serializable`, `Cloneable`). It
  tags a class so other code can check `instanceof`. Annotations mostly do this
  job now, but the term still comes up.

::side-note{kind="go-deeper"}
An interface with exactly one abstract method is a **functional interface**,
and it can be implemented with a lambda: `MessageSender fake = (to, body) ->
System.out.println(to);`. That one line replaces the whole `RecordingSender`
class, and it is where the Java 8 chapter starts.
::

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between an abstract class and an interface?" icon="i-lucide-message-circle"}
  An abstract class can have instance fields, constructors and any mix of
  abstract and concrete methods, and a class can extend only one. An interface
  has no instance state or constructor, its methods are public (abstract,
  default or static), and a class can implement many. Use an abstract class for
  shared state and construction (IS-A); use an interface for a shared
  capability (CAN-DO). Prefer interfaces by default.
  :::
  :::accordion-item{label="Can an abstract class have a constructor? Can we instantiate it?" icon="i-lucide-message-circle"}
  It can have a constructor, which subclasses call through `super(...)`. It
  cannot be instantiated: `new Student(...)` fails with `Student is abstract;
  cannot be instantiated`. You can, however, hold a child object in an
  abstract-typed variable: `Student s = new Hosteller(...)`.
  :::
  :::accordion-item{label="Why were default methods added to interfaces?" icon="i-lucide-message-circle"}
  To let an interface gain new methods without breaking every class that
  already implements it. Java 8 added `forEach`, `sort` and `removeIf` to
  `List` this way, and every existing list class got them for free.
  :::
  :::accordion-item{label="What if a class implements two interfaces with the same default method?" icon="i-lucide-message-circle"}
  It does not compile (`inherits unrelated defaults for badge()`) until the
  class overrides the method. Inside the override you can pick or combine them
  with `StudentRole.super.badge()` and `StaffRole.super.badge()`.
  :::
  :::accordion-item{label="How would you test a class that sends emails or reads a database?" icon="i-lucide-message-circle"}
  Make it depend on an interface (`MessageSender`, `StudentRepository`) handed
  in through its constructor, not on a concrete class it creates itself. In the
  test, hand in a fake implementation that records calls or returns fixed data.
  That is dependency injection, and it is what Spring automates.
  :::
  :::accordion-item{label="Can an interface extend another interface? Can it extend a class?" icon="i-lucide-message-circle"}
  An interface can extend one or more interfaces
  (`interface Resident extends Notifiable, Payable { }`). It cannot extend a
  class, because a class has state and constructors and an interface cannot.
  :::
::
