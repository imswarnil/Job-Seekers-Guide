Your constructor refuses a bad value, and then the next line can write
straight into the field and undo it. **Encapsulation** is the fix: the fields
are private, and the only way to change them is through methods that enforce
the rules.

## Why this matters in a job

"Why do we use getters and setters?" is asked constantly, and the usual answer,
"for encapsulation", is circular. The real answer is about **invariants**, and
it is the difference between a class that protects itself and one with
ceremony bolted on. It is also the first of the "four pillars of OOPs"
(encapsulation, inheritance, polymorphism, abstraction) that every fresher OOPs
round asks you to explain with an example.

## The problem

```java [OpenField.java]
public class OpenField {
  public static void main(String[] args) {
    Attendance a = new Attendance("Vikram Shah", 70);
    a.percentage = 140;          // nothing stops this
    System.out.println(a.studentName + ": " + a.percentage + "%");
  }
}

class Attendance {
  String studentName;
  int percentage;

  Attendance(String studentName, int percentage) {
    if (percentage < 0 || percentage > 100) {
      throw new IllegalArgumentException("0 to 100 only, got " + percentage);
    }
    this.studentName = studentName;
    this.percentage = percentage;
  }
}
```

```text [Output]
Vikram Shah: 140%
```

The validation lasted exactly as long as construction. And the worse damage is
not the wrong number: when a 140% turns up in a report, **any line in the
whole codebase could have written it**, so there is nowhere to start looking.

## Encapsulation: the exam cell counter

A college exam cell does not let students walk in and edit the marks register.
There is a counter. You hand in a request (re-evaluation, a correction), the
clerk checks it against the rules, and only the clerk writes in the register.

- The register is the **private field**: nobody outside the class can touch it.
- The counter is the **public method**: the one controlled way in.
- The rules the clerk checks are the **invariants**.

An **invariant** is a fact about an object that must be true from the moment it
is created until it is thrown away. For a fee account:

- the total fee never changes;
- the amount paid only goes up, never above the total;
- the payment history can be read, never rewritten.

::pull-quote
Encapsulation is not about hiding data. It is about there being exactly one
place that can break each rule, so that when a rule is broken you know where to
look.
::

## How it works

`private` on a field means only code inside the same class can read or write
it. Try from outside and the compiler refuses:

```text [Output]
Hidden.java:4: error: percentage has private access in Attendance
    a.percentage = 140;
     ^
1 error
```

Then you open exactly the doors you need, as methods, each guarding its rules.
The example below catches the refusals with `try` and `catch` so the program
can carry on and print them; the exceptions chapter covers that syntax.

```java [FeeDesk.java]
import java.util.Arrays;

public class FeeDesk {
  public static void main(String[] args) {
    FeeAccount acc = new FeeAccount("CSE1801", 4_500_000L);   // Rs 45,000 in paise
    acc.pay(1_500_000L);
    acc.pay(1_000_000L);
    System.out.println("Balance (paise): " + acc.getBalancePaise());
    System.out.println("Payments: " + Arrays.toString(acc.getPayments()));

    long[] copy = acc.getPayments();
    copy[0] = 0;                                  // only changes the copy
    System.out.println("Still: " + Arrays.toString(acc.getPayments()));

    try {
      acc.pay(-50_000L);
    } catch (IllegalArgumentException e) {
      System.out.println("Refused: " + e.getMessage());
    }
    try {
      acc.pay(9_000_000L);
    } catch (IllegalArgumentException e) {
      System.out.println("Refused: " + e.getMessage());
    }
  }
}

class FeeAccount {
  private final String rollNumber;
  private final long totalPaise;
  private long paidPaise;
  private long[] payments = new long[0];

  FeeAccount(String rollNumber, long totalPaise) {
    if (totalPaise <= 0) {
      throw new IllegalArgumentException("A fee must be positive");
    }
    this.rollNumber = rollNumber;
    this.totalPaise = totalPaise;
  }

  // The ONLY way money can come in, so the rules live here and nowhere else.
  void pay(long amountPaise) {
    if (amountPaise <= 0) {
      throw new IllegalArgumentException("A payment must be positive, got " + amountPaise);
    }
    if (amountPaise > getBalancePaise()) {
      throw new IllegalArgumentException("Payment " + amountPaise + " exceeds balance " + getBalancePaise());
    }
    paidPaise += amountPaise;
    payments = Arrays.copyOf(payments, payments.length + 1);
    payments[payments.length - 1] = amountPaise;
  }

  long getBalancePaise() { return totalPaise - paidPaise; }
  String getRollNumber() { return rollNumber; }

  long[] getPayments() {
    return payments.clone();     // a copy: the caller cannot rewrite history
  }
}
```

```bash [Terminal]
javac FeeDesk.java && java FeeDesk
```

```text [Output]
Balance (paise): 2000000
Payments: [1500000, 1000000]
Still: [1500000, 1000000]
Refused: A payment must be positive, got -50000
Refused: Payment 9000000 exceeds balance 2000000
```

Every invariant is now one guard in one place. There is no `setPaidPaise`
at all, because nothing outside should ever set it directly. `totalPaise` is
`final`, so not even the class itself can change it after construction.

::compare{caption="Two setters. Only one of them is doing anything."}
  :::compare-side{label="Ceremony" verdict="wrong"}
  ```java
  void setPercentage(int percentage) {
    this.percentage = percentage;
  }
  ```
  The same as a public field, with three extra lines. This is what people mean
  when they say getters and setters are pointless, and for this one they are
  right.
  :::
  :::compare-side{label="A guard" verdict="right"}
  ```java
  void setPercentage(int percentage) {
    if (percentage < 0 || percentage > 100) {
      throw new IllegalArgumentException("0 to 100 only");
    }
    this.percentage = percentage;
  }
  ```
  This one enforces something. It is the reason the field is private.
  :::
::

::tip
The naming convention is `getX()` for a getter, `setX(value)` for a setter and
`isX()` for a boolean getter (`isEligible()`). Frameworks such as Spring and
Hibernate find your fields through these names, so follow them exactly.
::

## Real use case

The strongest version is often not a setter at all. It is a method named after
what is happening in the business. An application moves along a status ladder
(`RECEIVED`, then `UNDER_REVIEW`, then `SHORTLISTED` or `REJECTED`), and a
generic `setStatus` would let any caller skip a step.

```java [StatusLadder.java]
public class StatusLadder {
  public static void main(String[] args) {
    Application app = new Application("Meera Iyer");
    app.startReview();
    app.shortlist("Registrar");
    System.out.println(app);

    Application other = new Application("Rohit Das");
    try {
      other.shortlist("Registrar");         // skipping UNDER_REVIEW
    } catch (IllegalStateException e) {
      System.out.println("Refused: " + e.getMessage());
    }
  }
}

class Application {
  enum Status { RECEIVED, UNDER_REVIEW, SHORTLISTED, REJECTED }

  private final String applicantName;
  private Status status = Status.RECEIVED;
  private String decidedBy;

  Application(String applicantName) { this.applicantName = applicantName; }

  void startReview() {
    if (status != Status.RECEIVED) {
      throw new IllegalStateException("Only a received application can go to review");
    }
    status = Status.UNDER_REVIEW;
  }

  void shortlist(String by) {
    if (status != Status.UNDER_REVIEW) {
      throw new IllegalStateException("Only an application under review can be shortlisted, not " + status);
    }
    status = Status.SHORTLISTED;
    decidedBy = by;
  }

  Status getStatus() { return status; }

  public String toString() {
    return applicantName + ": " + status + " by " + decidedBy;
  }
}
```

```text [Output]
Meera Iyer: SHORTLISTED by Registrar
Refused: Only an application under review can be shortlisted, not RECEIVED
```

The status and the person who decided can no longer drift apart, the ladder
cannot be skipped, and the rule lives with the data instead of being copied
into every caller.

::real-life{title="What this prevents, concretely" source="A status field set from six places"}
A public `status` string set from six different parts of a codebase will, over
a couple of years, collect `"Shortlisted"`, `"SHORTLISTED"` and
`"SHORT_LISTED"`, and somebody's dashboard will report four categories that
should have been three. Nothing breaks loudly enough to notice. One private
field, one enum and a method per transition makes it impossible.
::

## What confuses people here

### The leak through a getter

```java [Leak.java]
import java.util.Arrays;

public class Leak {
  public static void main(String[] args) {
    Results r = new Results(new int[] {78, 64, 81});
    int[] marks = r.getMarks();
    marks[0] = 100;                       // edits the object's private array
    System.out.println(Arrays.toString(r.getMarks()));
  }
}

class Results {
  private final int[] marks;
  Results(int[] marks) { this.marks = marks; }
  int[] getMarks() { return marks; }      // hands out the real array
}
```

```text [Output]
[100, 64, 81]
```

The field is `private` and `final`, and the marks were still rewritten from
outside. The getter handed out the **address** of the internal array (the
stack-and-heap lesson again). The constructor has the same hole in the other
direction: it keeps the caller's array, so the caller can change it later.

::compare{caption="Private is not enough when the field is a mutable object."}
  :::compare-side{label="Shares the array" verdict="wrong"}
  ```java
  Results(int[] marks) { this.marks = marks; }
  int[] getMarks() { return marks; }
  ```
  :::
  :::compare-side{label="Defensive copies" verdict="right"}
  ```java
  Results(int[] marks) { this.marks = marks.clone(); }
  int[] getMarks() { return marks.clone(); }
  ```
  Copy on the way in and on the way out. With lists it is `List.copyOf(...)`.
  :::
::

- **Encapsulation is not the same as data hiding.** Data hiding is the
  mechanism (`private`); encapsulation is the goal (the object guards its own
  rules). A class with private fields and a plain setter for each has hiding
  and no encapsulation.
- **Not every field needs a getter.** Generating a getter and setter for every
  field by habit (IDEs offer it in two clicks) undoes the point. Add them when
  something outside needs them.
- **The four access levels** (`private`, package-private, `protected`,
  `public`) get their own lesson later in this chapter. For now: start
  everything `private`.

## Interview questions

::accordion
  :::accordion-item{label="What is encapsulation?" icon="i-lucide-message-circle"}
  Bundling data with the methods that operate on it, and allowing changes only
  through those methods, so the object can enforce its own rules. The
  consequence to say out loud: each rule can be broken in exactly one place, so
  when it is broken there is one place to look. Then give `FeeAccount.pay` as
  the example.
  :::
  :::accordion-item{label="Why not make the fields public?" icon="i-lucide-message-circle"}
  Because then any code can put the object into an invalid state (140%
  attendance, a negative payment), and nothing can be changed about how the
  field is stored later without breaking every caller. A private field behind a
  method can add validation, logging or a different storage format without any
  caller noticing.
  :::
  :::accordion-item{label="Is a class with private fields and a getter and setter for each encapsulated?" icon="i-lucide-message-circle"}
  Only nominally. If `setPercentage` accepts any `int`, the field is as open as
  a public one. Encapsulation comes from the setter checking the rule, or from
  having no setter at all and a business method such as `pay` or `shortlist`.
  :::
  :::accordion-item{label="How can a private field still be modified from outside?" icon="i-lucide-message-circle"}
  When it holds a mutable object (an array, a list) and a getter returns the
  reference, as in `Leak.java`. Return a copy (`marks.clone()`,
  `List.copyOf(list)`) or an unmodifiable view, and copy what the constructor
  receives too.
  :::
  :::accordion-item{label="What is the difference between encapsulation and abstraction?" icon="i-lucide-message-circle"}
  Encapsulation is about protecting an object's state: keep it private, change
  it only through guarded methods. Abstraction is about hiding complexity
  behind a simple interface: the caller knows **what** `pay()` does, not how.
  They work together, and the abstraction lesson later in this chapter shows
  the second one with abstract classes and interfaces.
  :::
::
