Every value so far was written into the source code, so the program did the same
thing every time. A program becomes useful when it asks. In Java the first tool
for asking is `Scanner`, a class in the standard library that reads text and
turns it into the types you already know.

## Why this matters in a job

Honestly, you will rarely read from the keyboard at work. Real programs take
input from web forms, files and databases. But Scanner matters for two reasons
that are very real for a fresher.

First, **coding rounds**. HackerRank, HackerEarth and the machine tests that
Bangalore walk-ins run in a lab all feed your program through standard input
(`System.in`). If you cannot read five numbers from the input correctly, your
correct algorithm scores zero. The `nextLine` trap in this lesson is exactly
the kind of thing that fails a machine test whose logic was right.

Second, **the ideas carry over**: reading a stream of tokens, validating input
before trusting it, and what happens when the text is not the type you expected.
Those are the same problems a web form has.

## Scanner: a tokeniser on a stream

Imagine the exam cell clerk reading an answer sheet aloud to somebody entering
marks. The clerk reads one word at a time and stops at each space or new line.
Asked "give me the next number", he reads the next word and tries to treat it as
a number. Asked "give me the rest of this line", he reads everything up to the
end of the line, **even if that is nothing**.

That is Scanner. It reads from a **stream** (a source of characters that arrive
in order, here the keyboard) and splits it into **tokens**: pieces separated by
whitespace (spaces, tabs, new lines).

| Method | Reads | Stops at |
| --- | --- | --- |
| `next()` | one token as a `String` | the next whitespace |
| `nextInt()`, `nextLong()`, `nextDouble()`, `nextBoolean()` | one token, converted | the next whitespace, leaving the newline behind |
| `nextLine()` | the rest of the current line | the end of the line, and it consumes the newline |
| `hasNextInt()`, `hasNext()`, `hasNextLine()` | nothing; only looks ahead | returns `true` or `false` |

## Syntax

```java [MarksEntry.java]
import java.util.Scanner;

public class MarksEntry {
  public static void main(String[] args) {
    Scanner in = new Scanner(System.in);

    System.out.print("Student name: ");
    String name = in.nextLine();

    System.out.print("Marks in Java (out of 100): ");
    int javaMarks = in.nextInt();

    System.out.print("Marks in SQL (out of 100): ");
    int sqlMarks = in.nextInt();

    double average = (javaMarks + sqlMarks) / 2.0;
    System.out.printf("%s, average %.1f%n", name, average);
  }
}
```

```text [Terminal]
$ javac MarksEntry.java
$ java MarksEntry
Student name: Anita Rao
Marks in Java (out of 100): 78
Marks in SQL (out of 100): 85
Anita Rao, average 81.5
```

In a terminal session like this one, the text after each colon is what you
type; the rest is the program's output.

- `import java.util.Scanner;` tells the compiler which `Scanner` you mean.
  Classes in `java.lang` (`String`, `System`, `Math`) need no import; almost
  everything else does.
- `new Scanner(System.in)` creates one Scanner reading from standard input.
  Create **one** and reuse it.
- `print` does not add a new line, so the cursor waits after the prompt.
  `printf` formats: `%s` a string, `%.1f` a decimal to one place, `%n` a new line.

## Reading tokens from anywhere

Scanner can read a `String` as easily as the keyboard, which makes it easy to
try things out:

```java [Tokens.java]
import java.util.Scanner;

public class Tokens {
  public static void main(String[] args) {
    Scanner line = new Scanner("2026CSE0184 Anita 78.5 true");
    String roll = line.next();
    String first = line.next();
    double percentage = line.nextDouble();
    boolean feePaid = line.nextBoolean();
    System.out.println(roll + " | " + first + " | " + percentage + " | " + feePaid);
  }
}
```

```text [Output]
2026CSE0184 | Anita | 78.5 | true
```

## Real use case

The shape of nearly every coding-round input is "read numbers until there are no
more". `hasNextInt()` looks ahead without consuming anything, so it makes a
clean loop condition:

```java [ClassAverage.java]
import java.util.Scanner;

public class ClassAverage {
  public static void main(String[] args) {
    Scanner in = new Scanner(System.in);
    int count = 0;
    int total = 0;
    while (in.hasNextInt()) {
      total += in.nextInt();
      count++;
    }
    System.out.println(count + " marks read, average " + (count == 0 ? 0 : total * 1.0 / count));
  }
}
```

```text [Terminal]
$ printf '78 64 81\n55 92\n' | java ClassAverage
5 marks read, average 74.0
```

`printf '...' | java ClassAverage` sends that text into the program's standard
input, exactly the way an online judge does. Notice the marks were spread over
two lines and it did not matter: tokens ignore line breaks.

The other everyday use is **validation**: keep asking until the input is
acceptable, instead of crashing.

```java [SafeMarks.java]
import java.util.Scanner;

public class SafeMarks {
  public static void main(String[] args) {
    Scanner in = new Scanner(System.in);
    int marks = -1;

    while (marks < 0 || marks > 100) {
      System.out.print("Marks (0-100): ");
      if (in.hasNextInt()) {
        marks = in.nextInt();
        if (marks < 0 || marks > 100) System.out.println("Out of range, try again.");
      } else {
        System.out.println("'" + in.next() + "' is not a whole number, try again.");
      }
    }
    System.out.println("Recorded: " + marks);
  }
}
```

```text [Terminal]
$ java SafeMarks
Marks (0-100): eighty
'eighty' is not a whole number, try again.
Marks (0-100): 120
Out of range, try again.
Marks (0-100): 78
Recorded: 78
```

The `in.next()` in the `else` branch matters. It throws away the bad token.
Without it, `hasNextInt()` would look at `eighty` again, forever, and the loop
would never end.

## What confuses people here

### The nextInt then nextLine trap

```java [NextLineTrap.java]
import java.util.Scanner;

public class NextLineTrap {
  public static void main(String[] args) {
    Scanner in = new Scanner(System.in);

    System.out.print("Roll number: ");
    int roll = in.nextInt();

    System.out.print("Full name: ");
    String name = in.nextLine();

    System.out.println("Saved roll " + roll + " as [" + name + "]");
  }
}
```

```text [Terminal]
$ java NextLineTrap
Roll number: 184
Full name: Saved roll 184 as []
```

It never waited for the name. When you typed `184` and pressed Enter, the input
was `184\n` (`\n` is the newline character). `nextInt()` read `184` and **left
the `\n` behind**. `nextLine()` then read "the rest of the line", which was
empty, and returned at once.

::memory{kind="array" caption="What is left in the input after nextInt() reads 184. nextLine() sees the newline first."}
---
frames:
  - label: "You type 184 and press Enter"
    cells: [{ value: "1" }, { value: "8" }, { value: "4" }, { value: "\\n" }]
  - label: "After nextInt()"
    cells: [{ value: "1", state: "ghost" }, { value: "8", state: "ghost" }, { value: "4", state: "ghost" }, { value: "\\n", state: "active" }]
  - label: "nextLine() reads up to that newline: an empty String"
    cells: [{ value: "1", state: "ghost" }, { value: "8", state: "ghost" }, { value: "4", state: "ghost" }, { value: "\\n", state: "ghost" }]
---
::

::compare{caption="Two fixes. The second is what experienced people write."}
  :::compare-side{label="Swallow the leftover newline" verdict="neutral"}
  ```java
  int roll = in.nextInt();
  in.nextLine();              // throw away the rest of this line
  String name = in.nextLine();
  ```
  Works, and is easy to forget the next time.
  :::
  :::compare-side{label="Read every line as a line, then convert" verdict="right"}
  ```java
  int roll = Integer.parseInt(in.nextLine().strip());
  String name = in.nextLine();
  ```
  One rule for every input, so the trap cannot happen.
  :::
::

```java [NextLineFixed.java]
import java.util.Scanner;

public class NextLineFixed {
  public static void main(String[] args) {
    Scanner in = new Scanner(System.in);

    System.out.print("Roll number: ");
    int roll = Integer.parseInt(in.nextLine().strip());

    System.out.print("Full name: ");
    String name = in.nextLine();

    System.out.println("Saved roll " + roll + " as [" + name + "]");
  }
}
```

```text [Terminal]
$ java NextLineFixed
Roll number: 184
Full name: Anita Rao
Saved roll 184 as [Anita Rao]
```

`Integer.parseInt` converts a `String` to an `int`, and `strip()` removes stray
spaces around it.

### Typing text where a number was expected

Run `MarksEntry` and type `seventy` for the Java marks:

```text [Terminal]
$ java MarksEntry
Student name: Anita Rao
Marks in Java (out of 100): seventy
Exception in thread "main" java.util.InputMismatchException
	at java.base/java.util.Scanner.throwFor(Scanner.java:947)
	at java.base/java.util.Scanner.next(Scanner.java:1602)
	at java.base/java.util.Scanner.nextInt(Scanner.java:2267)
	at java.base/java.util.Scanner.nextInt(Scanner.java:2221)
	at MarksEntry.main(MarksEntry.java:11)
```

Read a stack trace from the top for **what** went wrong
(`InputMismatchException`) and find the first line that is **your** file for
**where** (`MarksEntry.java:11`). The lines in `java.base` are the library's
insides; you can skip them. Guard with `hasNextInt()` as `SafeMarks` does.

### Closing the Scanner

::warning{icon="i-lucide-alert-triangle"}
`in.close()` closes `System.in` as well, and it cannot be reopened. Any later
`new Scanner(System.in)` anywhere in the program then fails with
`NoSuchElementException`. For a Scanner on `System.in`, create one, share it, and
do not close it. For a Scanner on a file, always close it; the exceptions chapter
shows the tidy way (try-with-resources).
::

### Scanner is slow for very large inputs

For a few thousand numbers Scanner is fine. For a million, on a coding platform
with a one-second limit, it can be too slow, because it checks each token
against a pattern. Competitive programmers use `BufferedReader` and split the
lines themselves. You will not need it in a fresher test, but it is a good
answer if somebody asks "what if the input is huge?".

## Interview questions

::accordion
  :::accordion-item{label="Why does nextLine() return an empty string after nextInt()?"}
  `nextInt()` reads the number and leaves the newline in the input. `nextLine()`
  reads up to that newline and returns `""`. Fix it by calling `in.nextLine()` once
  to discard the rest of the line, or by reading every line with `nextLine()` and
  converting with `Integer.parseInt(in.nextLine().strip())`.
  :::

  :::accordion-item{label="What is the difference between next() and nextLine()?"}
  `next()` reads one token, stopping at whitespace, so for `Anita Rao` it returns
  `Anita`. `nextLine()` reads the whole rest of the line, `Anita Rao`, and consumes
  the newline.
  :::

  :::accordion-item{label="What happens if the user types text where nextInt() expects a number?"}
  It throws `java.util.InputMismatchException`, and the bad token stays in the
  input. Check with `hasNextInt()` first, and discard bad input with `next()`,
  or the same token fails again forever.
  :::

  :::accordion-item{label="Should you close a Scanner on System.in?"}
  No. Closing it closes `System.in` for the whole program, and later reads throw
  `NoSuchElementException`. Scanners on files should be closed, ideally with
  try-with-resources.
  :::

  :::accordion-item{label="Scanner or BufferedReader for large input?"}
  `BufferedReader` is much faster because it reads big chunks and does no
  pattern matching; you split and parse yourself with `line.split(" ")` and
  `Integer.parseInt`. Scanner is more convenient and fine for small inputs.
  :::
::
