You have a bed in a PG, a route to the institute and a timetable, or a laptop
and a plan to study alone. Either way, Java is the first subject on it, and
before you write a line of it you should know why, and what you are about to
install.

## Why this matters in a job

Almost every fresher interview I sat in Bangalore in 2018 opened the technical
round the same way: "What is Java? What is the difference between the JDK, the
JRE and the JVM? Is Java compiled or interpreted?" They are warm-up questions,
and a candidate who fumbles them rarely gets to the interesting ones.

There is a practical reason too. The day you join a company, somebody will hand
you a laptop and a project that "does not build". Knowing what `javac` does,
what `java` does and which of the two failed is the difference between fixing it
in ten minutes and asking for help for a day.

::pros-cons
---
title: Java as your first language
pros:
  - The largest share of fresher openings in Bangalore list Java, and most training institutes teach it first
  - Strictly typed and compiled, so a large class of mistakes is caught before the program ever runs
  - Wordy enough that what the machine is doing stays visible while you learn it
  - The standard library is enormous, and the official documentation is good
  - Banking, insurance, e-commerce back ends and Android all run on it
cons:
  - Slower to a first running program than Python
  - The ceremony (`public static void main`) feels pointless for the first fortnight
  - Build tools like Maven and Gradle take a while to feel normal
---
::

::note
If you already know Python or C++ well, the ideas here transfer directly. What I
would not do is learn three languages at once. It is the most common way I saw
people in my PG waste their first three months.
::

## Three boxes, one inside the other

Think of a kitchen. The **JVM** is the stove: it is what actually cooks. The
**JRE** is the stove plus the pantry of ingredients every recipe needs. The
**JDK** is the whole kitchen, including the knives and chopping boards you need
to *prepare* a new recipe. To eat, you need the stove and the pantry. To cook
something new, you need the whole kitchen.

Now the real thing:

- **JVM (Java Virtual Machine)**: a program that runs Java **bytecode**. Bytecode
  is a set of instructions for a machine that does not physically exist. The JVM
  also manages memory and runs the garbage collector, the part that throws away
  objects you no longer use.
- **JRE (Java Runtime Environment)**: the JVM plus the standard library
  (`String`, `ArrayList`, `HashMap` and everything else in `java.*`). Enough to
  **run** a Java program. Not enough to compile one.
- **JDK (Java Development Kit)**: the JRE plus the tools a developer needs:
  `javac` (the compiler), `jar`, `javadoc`, `jshell`, `javap`, `jstack`. This is
  what you install.

Since Java 11, Oracle and the other vendors no longer ship a separate JRE

matter, because interviewers still ask, and because a server that only runs
Java programs often has a cut-down runtime with no `javac` on it.

## How it works: from text to a running program

This sequence is the actual answer to "how does Java work", and to "what does
*write once, run anywhere* mean".

::flow{numbered direction="vertical" caption="Compiled once, run anywhere. That slogan is this diagram."}
  :::flow-step{label="You write a .java file" icon="i-lucide-file-code"}
  Plain text. Readable by you, meaningless to the processor.
  :::
  :::flow-step{label="javac compiles it to a .class file" icon="i-lucide-cog"}
  Not machine code. **Bytecode**, the instruction set of the JVM. The compiler
  also checks your types and refuses to produce anything if they are wrong.
  :::
  :::flow-step{label="java starts a JVM, which loads and runs the bytecode" icon="i-lucide-play" highlight}
  There is a different JVM for Windows, macOS, Linux and Android. Each one turns
  the same bytecode into that machine's instructions. The `.class` file is
  identical everywhere.
  :::
  :::flow-step{label="The JIT compiles the busy parts" icon="i-lucide-zap"}
  The **JIT (just-in-time) compiler** inside the JVM watches which methods run
  most often and compiles those to real machine code while the program runs.
  That is why a long-running Java service gets faster after a few minutes.
  :::
::

So is Java compiled or interpreted? **Both.** `javac` compiles ahead of time to
bytecode, the JVM interprets that bytecode, and the JIT compiles the hot parts
to native code at run time. Saying all three, in that order, is the answer.

## Install it

Install **JDK 21**. It is an LTS (long-term support) release, which means
vendors fix bugs and security issues in it for years, and it is what most
companies moving off Java 8 and 11 are moving to.

::tabs
  :::tabs-item{label="macOS" icon="i-lucide-command"}
  ```bash [Terminal]
  brew install openjdk@21
  # Homebrew does not link it by default. This makes java findable.
  sudo ln -sfn $(brew --prefix)/opt/openjdk@21/libexec/openjdk.jdk \
               /Library/Java/JavaVirtualMachines/openjdk-21.jdk
  ```
  :::

  :::tabs-item{label="Linux" icon="i-simple-icons-linux"}
  ```bash [Terminal]
  sudo apt update && sudo apt install openjdk-21-jdk
  ```
  :::

  :::tabs-item{label="Windows" icon="i-lucide-monitor"}
  Download the **Temurin 21 JDK** installer (`.msi`) from adoptium.net and run
  it. On the "Custom Setup" screen, turn on **Set JAVA_HOME variable** and
  **Add to PATH**. If you missed them: search for "Edit the system environment
  variables", add a variable `JAVA_HOME` pointing at the install folder (for
  example `C:\Program Files\Eclipse Adoptium\jdk-21...`), and add
  `%JAVA_HOME%\bin` to `Path`. Close every Command Prompt and open a new one,
  because an open window never sees a changed `PATH`.
  :::
::

`PATH` is the list of folders your terminal searches when you type a command.
`JAVA_HOME` is a variable that build tools such as Maven read to find your JDK.
Check both halves of the JDK are there:

```bash [Terminal]
java -version
javac -version
```

```text [Output]
openjdk version "21.0.12.1" 2026-08-18
OpenJDK Runtime Environment Homebrew (build 21.0.12.1)
OpenJDK 64-Bit Server VM Homebrew (build 21.0.12.1, mixed mode, sharing)
javac 21.0.12.1
```

Your version numbers will differ. What matters is that both commands answer.

::warning{icon="i-lucide-alert-triangle"}
If `java -version` works and `javac -version` says `command not found`, you
have a runtime and not a JDK, or the JDK's `bin` folder is not on your `PATH`.
It is the most common installation problem there is, and the error does not say
so. Install the JDK, then open a fresh terminal.
::

## Your first program, compiled by hand

Do it this way at least once. Every IDE (an editor such as IntelliJ IDEA or
Eclipse) hides these two steps, and people who have never seen them cannot
debug a build.

```java [Admissions.java]
public class Admissions {
  public static void main(String[] args) {
    System.out.println("University admissions, 2026 intake");
  }
}
```

```bash [Terminal]
javac Admissions.java     # compile: produces Admissions.class
ls
java Admissions           # run: the CLASS name, no .class, no .java
```

```text [Output]
Admissions.class
Admissions.java
University admissions, 2026 intake
```

::code-trace{caption="Five words on two lines, and every one of them is asked about."}
```java [Admissions.java]
public class Admissions {
  public static void main(String[] args) {
    System.out.println("University admissions, 2026 intake");
  }
}
```

  :::code-trace-step{lines="1" caption="`public class Admissions`: the file MUST be called Admissions.java. A public class and its file share a name, and the compiler enforces it."}
  :::
  :::code-trace-step{lines="2" caption="`public` so the JVM can call it from outside. `static` so it belongs to the class, not an object: the JVM calls it before any object exists."}
  :::
  :::code-trace-step{lines="2" caption="`void` returns nothing. `String[] args` receives anything typed after the class name on the command line."}
  :::
  :::code-trace-step{lines="3" caption="`System` is a class, `out` is a static field on it holding a PrintStream object, and `println` is a method on that object. Even printing is an object calling a method."}
  :::
::

You can look at the bytecode yourself with `javap -c Admissions`, one of the
tools the JDK ships:

```text [Output of javap -c Admissions]
public static void main(java.lang.String[]);
  Code:
     0: getstatic     #7    // Field java/lang/System.out:Ljava/io/PrintStream;
     3: ldc           #13   // String University admissions, 2026 intake
     5: invokevirtual #15   // Method java/io/PrintStream.println:(Ljava/lang/String;)V
     8: return
```

You will never write that by hand. Seeing it once makes "bytecode" a real
thing rather than a word.

::tip
Since Java 11 you can also run a single file without compiling it first:
`java Admissions.java`. The JVM compiles it in memory and runs it. It is handy
for trying things out. At work, and in interviews, the two-step version is the
one you are expected to explain.
::

## Real use case

At work nobody types `javac` for a real project. A build tool runs it for you,
across hundreds of files, and packs the `.class` files into a **JAR** (a zip
file of compiled classes). The JAR is what is deployed to a server, and on the
server the command is still `java`:

```bash [Terminal]
java -jar results-service.jar
```

That server has a JVM and no source code at all. The same JAR runs on the
developer's Windows laptop, on a Mac, and on the Linux server in the data
centre. That is "write once, run anywhere" doing a real job.

## What confuses people here

Every one of these will happen to you. Cause them now, on purpose, while
nothing is at stake.

**1. The file name does not match the class name.** Rename the file to
`Wrong.java` and compile it:

```text [Output]
Wrong.java:1: error: class Admissions is public, should be declared in a file named Admissions.java
public class Admissions {
       ^
1 error
```

**2. A missing semicolon.** Delete the `;` at the end of line 3:

```text [Output]
Admissions.java:3: error: ';' expected
    System.out.println("University admissions, 2026 intake")
                                                            ^
1 error
```

The caret `^` points at where the compiler noticed, which is not always where
the mistake is. Read the line above it too.

**3. `main` is misspelt.** Rename `main` to `start`. It compiles without a
murmur. Then run it:

```text [Output]
Error: Main method not found in class Admissions, please define the main method as:
   public static void main(String[] args)
or a JavaFX application class must extend javafx.application.Application
```

::compare{caption="Two steps, two kinds of failure. Knowing which step failed is half of debugging a build."}
  :::compare-side{label="javac errors" verdict="neutral"}
  About your **code**: a missing semicolon, a wrong type, a misnamed file. No
  `.class` file is produced.
  :::
  :::compare-side{label="java errors" verdict="neutral"}
  About **how you started it**, or about what happened while it ran: no `main`,
  the class is not found, an exception at run time. The code compiled fine.
  :::
::

**4. Reading `args` that were never given.**

```java [Args.java]
public class Args {
  public static void main(String[] args) {
    System.out.println("Arguments given: " + args.length);
    System.out.println("Course: " + args[0]);
  }
}
```

```bash [Terminal]
javac Args.java
java Args "B.Tech CSE"
java Args
```

```text [Output]
Arguments given: 1
Course: B.Tech CSE
Arguments given: 0
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0
	at Args.main(Args.java:4)
```

Read the exception as the English sentence it is: you asked for position 0 of
something with nothing in it. The last line tells you the file and line number.
Checking `args.length` before reading is the fix, and "check before you read" is
the shape of most defensive code you will ever write.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between the JDK, the JRE and the JVM?"}
  The JVM runs bytecode. The JRE is the JVM plus the standard library, enough to
  run a program. The JDK is the JRE plus development tools, most importantly the
  `javac` compiler. If `java -version` works and `javac -version` does not, you
  have a runtime without a JDK.
  :::

  :::accordion-item{label="Is Java compiled or interpreted?"}
  Both. `javac Admissions.java` compiles source to bytecode ahead of time. The
  JVM then interprets that bytecode, and the JIT compiler compiles frequently
  run methods to native machine code while the program runs.
  :::

  :::accordion-item{label="What does 'platform independent' mean, and is the JVM platform independent?"}
  The `.class` file is platform independent: the same `Admissions.class` runs on
  Windows, macOS and Linux. The JVM itself is **not**. There is a separate JVM
  build for each operating system, and that is precisely what makes the bytecode
  portable.
  :::

  :::accordion-item{label="Why is main public, static and void?"}
  `public` so the JVM can call it from outside the class. `static` so it can be
  called without creating an object first, because no object exists yet when the
  program starts. `void` because it returns nothing to the JVM; to report failure
  you call `System.exit(1)`. Misspell any part and it still compiles, then fails
  at run time with `Main method not found`.
  :::

  :::accordion-item{label="Can a .java file contain more than one class?"}
  Yes, but at most one of them may be `public`, and that one must share the file's
  name. `javac` produces one `.class` file per class, so a file with two classes
  produces two `.class` files.
  :::
::
