You can now build any text you like. Every program so far has run the same
lines in the same order, though, and a real one has to choose: pass or fail,
shortlist or reject, fine or no fine. This lesson is how Java decides.

## Why this matters in a job

Most of the business logic in a real codebase is decisions. Is this student
eligible, is this fee late, which message goes in this email. A condition that
cannot be read is a bug waiting to happen, because nobody can check it against
the rule it is meant to follow.

In interviews, this topic produces three reliable questions: the difference
between `&&` and `&`, what fall-through is in a `switch`, and "switch or
if-else?". All three are below.

## A decision is a fork in the road

Think of the admissions office at a college. A form arrives, and the clerk
looks at one thing (the score) and puts the form on one of two piles. That is
an `if`. When there are six piles, one per status, the clerk stops asking
yes-or-no questions and looks up the pile by name. That is a `switch`.

::flow{direction="horizontal" caption="An if asks yes or no. A switch looks up one of several named answers."}
  :::flow-step{label="Condition" icon="i-lucide-help-circle"}
  An expression that is `true` or `false`. In Java it must be a `boolean`,
  never a number.
  :::
  :::flow-step{label="if branch" icon="i-lucide-check" highlight}
  Runs when the condition is true.
  :::
  :::flow-step{label="else branch" icon="i-lucide-x"}
  Runs otherwise. Optional.
  :::
::

## Syntax

```java
if (condition) {
  // runs when condition is true
} else if (otherCondition) {
  // runs when the first was false and this one is true
} else {
  // runs when none of them were true
}
```

Java checks the conditions top to bottom and runs **the first** branch whose
condition is true. The rest are skipped, even if they would also be true.

Here is a real eligibility rule. The general cutoff is 60; applicants in a
reserved category have a relaxed cutoff of 55.

```java [Eligibility.java]
public class Eligibility {
  public static void main(String[] args) {
    String applicantName = "Meera Iyer";
    int score = 57;
    String category = "OBC";
    boolean withdrawn = false;

    boolean meetsGeneralCutoff = score >= 60;
    boolean meetsRelaxedCutoff = score >= 55 && !category.equals("GEN");
    boolean stillInTheRunning  = !withdrawn;

    if (stillInTheRunning && (meetsGeneralCutoff || meetsRelaxedCutoff)) {
      System.out.println(applicantName + ": shortlisted");
    } else if (withdrawn) {
      System.out.println(applicantName + ": withdrawn");
    } else {
      System.out.println(applicantName + ": below the cutoff");
    }
  }
}
```

```bash [Terminal]
javac Eligibility.java && java Eligibility
```

```text [Output]
Meera Iyer: shortlisted
```

::tip
Notice the three `boolean` variables with names. I could have written all of it
inside one `if`, and it would have worked. Naming each part costs a line and
buys the ability to check the rule against the admissions policy one sentence
at a time. A reviewer will thank you for it.
::

### Short-circuiting

`&&` (and) stops at the first `false`. `||` (or) stops at the first `true`.
Once the answer is known, the rest is not evaluated at all. This is called
**short-circuiting**, and it is why the null check always goes first.

```java [ShortCircuit.java]
public class ShortCircuit {
  public static void main(String[] args) {
    String rollNumber = null;

    // Safe: rollNumber != null is false, so the right side never runs.
    if (rollNumber != null && rollNumber.startsWith("CSE")) {
      System.out.println("Computer science student");
    } else {
      System.out.println("No roll number yet");
    }

    // Unsafe: & evaluates both sides, even when the left is false.
    if (rollNumber != null & rollNumber.startsWith("CSE")) {
      System.out.println("Never printed");
    }
  }
}
```

```text [Output]
No roll number yet
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.startsWith(String)" because "<local1>" is null
	at ShortCircuit.main(ShortCircuit.java:13)
```

The single `&` is a real operator (it also works on bits, which you met in the
operators lesson), and it does **not** short-circuit. On booleans, seeing one in
code is almost always a typo.

::side-note{kind="go-deeper"}
`<local1>` is the variable's slot number. `javac` leaves local variable names
out of the `.class` file unless you compile with `javac -g`, and then the
message says `"rollNumber" is null` instead. IDEs compile with `-g` for you.
::

### The ternary operator

`condition ? valueIfTrue : valueIfFalse` is a one-line `if` that produces a
value.

```java
String result = marks >= 40 ? "PASS" : "FAIL";
```

One ternary is a readable expression. Two nested ternaries are a puzzle that
nobody reads correctly under pressure. If you need a second one, write an
`if` or a small method.

### switch, the old form and the new form

A `switch` compares one value against a list of constants. The old form used
`case X:` with a colon, and every branch needed a `break` or it **fell through**
into the next branch. The new arrow form (`case X ->`), standard since Java 14,
never falls through and can produce a value.

An **enum** is a type with a fixed list of named constants, like the statuses
an application can be in. It gets a lesson of its own later; for now, read
`enum Status { ... }` as "a Status is one of these five words".

```java [StatusMessage.java]
public class StatusMessage {
  enum Status { RECEIVED, UNDER_REVIEW, SHORTLISTED, REJECTED, ACCEPTED }

  public static void main(String[] args) {
    // The old form, with a missing break.
    String code = "RECEIVED";
    String oldMessage = "";
    switch (code) {
      case "RECEIVED":
        oldMessage = "We have your application.";
        // break forgotten here
      case "SHORTLISTED":
        oldMessage = "You have been shortlisted.";
        break;
      default:
        oldMessage = "Status unknown.";
    }
    System.out.println("Old switch: " + oldMessage);

    // The arrow form over an enum: no break, no fall-through, and it returns a value.
    for (Status status : Status.values()) {
      String message = switch (status) {
        case RECEIVED     -> "We have your application.";
        case UNDER_REVIEW -> "Your application is being reviewed.";
        case SHORTLISTED  -> "You have been shortlisted.";
        case REJECTED     -> "Not successful this intake.";
        case ACCEPTED     -> "Congratulations. Pay the fee to confirm.";
      };
      System.out.println(status + " -> " + message);
    }
  }
}
```

```text [Output]
Old switch: You have been shortlisted.
RECEIVED -> We have your application.
UNDER_REVIEW -> Your application is being reviewed.
SHORTLISTED -> You have been shortlisted.
REJECTED -> Not successful this intake.
ACCEPTED -> Congratulations. Pay the fee to confirm.
```

Read the first line of output again. The applicant was `RECEIVED`, and the old
switch told them they had been shortlisted, because the missing `break` let
execution fall straight into the next case. That is the bug the arrow form
removes by construction.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-check" title="No fall-through"}
  Each arrow runs its own branch and stops. There is nothing to forget.
  :::
  :::feature{icon="i-lucide-equal" title="It is an expression"}
  It produces a value, so the variable can be assigned once and every branch
  must supply one.
  :::
  :::feature{icon="i-lucide-shield" title="Exhaustive over an enum"}
  With no `default`, the compiler checks that every constant is handled.
  :::
  :::feature{icon="i-lucide-list" title="Several labels per branch"}
  `case REJECTED, WITHDRAWN -> 1;` for cases that share an answer.
  :::
::

That exhaustiveness check is worth seeing fail. Remove the `ACCEPTED` case:

```java [MissingCase.java]
public class MissingCase {
  enum Status { RECEIVED, UNDER_REVIEW, SHORTLISTED, REJECTED, ACCEPTED }

  public static void main(String[] args) {
    Status status = Status.ACCEPTED;
    String message = switch (status) {
      case RECEIVED     -> "We have your application.";
      case UNDER_REVIEW -> "Your application is being reviewed.";
      case SHORTLISTED  -> "You have been shortlisted.";
      case REJECTED     -> "Not successful this intake.";
    };
    System.out.println(message);
  }
}
```

```text [Output]
MissingCase.java:6: error: the switch expression does not cover all possible input values
    String message = switch (status) {
                     ^
1 error
```

A missing case became a compile error instead of a wrong email to a student.
That is why you leave `default` out when switching over an enum: a `default`
silences exactly this check.

### When a branch needs more than one line

Use a block in braces, and `yield` the value:

```java [SeatRelease.java]
public class SeatRelease {
  enum Status { RECEIVED, UNDER_REVIEW, SHORTLISTED, REJECTED, WITHDRAWN, ACCEPTED }

  public static void main(String[] args) {
    Status[] decisions = {Status.REJECTED, Status.ACCEPTED, Status.WITHDRAWN, Status.UNDER_REVIEW};
    int seatsFree = 0;
    for (Status status : decisions) {
      int released = switch (status) {
        case REJECTED, WITHDRAWN -> 1;
        case ACCEPTED -> {
          System.out.println("Audit: seat confirmed");
          yield 0;               // yield gives the block its value
        }
        default -> 0;
      };
      seatsFree += released;
    }
    System.out.println("Seats released: " + seatsFree);
  }
}
```

```text [Output]
Audit: seat confirmed
Seats released: 2
```

`yield`, not `return`. A `return` there would try to leave the whole method.

## Real use case

The college charges a late fine on fees: nothing if paid on time, a flat ₹100
for the first week, ₹20 a day after that, capped at ₹1,000 after 30 days. This
is a range, not a list of exact values, so it is an `if` chain, not a `switch`.

```java [LateFine.java]
public class LateFine {
  public static void main(String[] args) {
    int[] daysLate = {0, 3, 10, 25, 45};
    for (int days : daysLate) {
      System.out.println(days + " days late -> fine Rs " + fine(days));
    }
  }

  static int fine(int daysLate) {
    if (daysLate <= 0) {
      return 0;
    } else if (daysLate <= 7) {
      return 100;
    } else if (daysLate <= 30) {
      return 100 + (daysLate - 7) * 20;
    } else {
      return 1000;            // capped; after 30 days the office calls you
    }
  }
}
```

```text [Output]
0 days late -> fine Rs 0
3 days late -> fine Rs 100
10 days late -> fine Rs 160
25 days late -> fine Rs 460
45 days late -> fine Rs 1000
```

The order of the branches matters. Because Java takes the **first** true
branch, each `else if` can assume every condition above it was false. Put
`daysLate <= 30` first and a student three days late is charged ₹0 + (3 − 7) × 20.
Negative fines are how a finance team finds out about your code.

::real-life{title="Where the if chain lives at work" source="Every fee, payroll and pricing module"}
Slab calculations like this one (tax slabs, fine slabs, discount tiers) are
some of the most common code in Indian enterprise software. When a slab is
changed, a test at each boundary (7, 8, 30, 31) is what tells you the order of
your branches is still right.
::

## What confuses people here

::compare{caption="Two classic mistakes that come from C and from maths."}
  :::compare-side{label="Assignment instead of comparison" verdict="wrong"}
  ```java
  int a = 10;
  if (a = 10) { ... }
  ```
  ```text
  error: incompatible types: int cannot be converted to boolean
  ```
  In C this compiles and is a famous bug. Java refuses, because a condition
  must be a `boolean` and `a = 10` is an `int`.
  :::
  :::compare-side{label="Comparison" verdict="right"}
  ```java
  int a = 10;
  if (a == 10) { ... }
  ```
  `==` compares; `=` assigns. For objects such as `String`, remember that `==`
  compares references and you want `.equals()`.
  :::
::

- **`switch` compares equality, not ranges.** You cannot write `case >= 90`.
  You can switch on `marks / 10`, which turns 95 into 9, but that is usually
  less readable than the `if` chain it replaced.
- **What a `switch` accepts:** `int` and the smaller integer types, `char`,
  `String`, enums and (since Java 21) any type with pattern cases. Not `long`,
  `float`, `double` or `boolean`.
- **An `if` without braces** controls exactly one statement. Add a second line
  under it later and that line runs every time. Always use braces.
- **A `switch` on a `null` String** throws a `NullPointerException` before
  checking any case.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between && and &?" icon="i-lucide-message-circle"}
  `&&` is the logical AND and short-circuits: if the left side is `false`, the
  right side is never evaluated. `&` evaluates both sides every time (and on
  integers it is bitwise AND). That is why `s != null && s.isEmpty()` is safe
  and `s != null & s.isEmpty()` throws a `NullPointerException` when `s` is
  null.
  :::
  :::accordion-item{label="What is fall-through in a switch?" icon="i-lucide-message-circle"}
  In the colon form, once a case matches, execution continues into every case
  below it until it reaches a `break`. A missing `break` after
  `case "RECEIVED":` in the example above told a received applicant they were
  shortlisted. The arrow form (`case X ->`) never falls through.
  :::
  :::accordion-item{label="When would you use switch instead of if-else?" icon="i-lucide-message-circle"}
  When comparing one value against a fixed set of exact values, such as a
  status or a menu choice. Use `if-else` for ranges and for conditions on
  several different variables. The modern switch expression adds two reasons:
  it produces a value, and over an enum with no `default` the compiler checks
  every constant is handled, so a new status breaks the build rather than
  failing silently.
  :::
  :::accordion-item{label="Can you switch on a String? On a long?" icon="i-lucide-message-circle"}
  A `String`, yes, since Java 7 (it uses `hashCode()` and then `equals()`
  internally). A `long`, `float`, `double` or `boolean`, no:

  ```java
  long id = 5L;
  switch (id) { case 5 -> System.out.println("five"); default -> {} }
  ```

  ```text
  error: selector type long is not allowed
  ```
  :::
  :::accordion-item{label="What is the difference between yield and return inside a switch expression?" icon="i-lucide-message-circle"}
  `yield` gives a value to the switch expression and carries on with the
  method. `return` would leave the whole method, so inside a switch
  expression the compiler refuses it with `error: attempt to return out of a
  switch expression`. `yield` is what you want.
  :::
::
