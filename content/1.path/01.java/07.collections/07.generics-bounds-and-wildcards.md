Every signature in this chapter had angle brackets: `List<Student>`,
`Map<String, Set<String>>`, and in the compiler error for `Collections.sort`,
the alarming `Comparable<? super T>`. This lesson is what those brackets are,
and by the end `? super T` reads as an ordinary sentence.

## Why this matters in a job

You use generics every time you declare a collection, and you will write
them whenever you build something reusable: a paged result, a cache, an API
response wrapper. More often, you will read them in library signatures and
compiler errors, and being able to read them is what turns a scary error into
a two-minute fix.

Interviewers ask a small, fixed set: why generics exist, what type erasure is,
the difference between `? extends` and `? super`, and why a `List<Integer>` is
not a `List<Number>`. Each has a compiled answer below.

## A generic is a form with a blank

The college office has one admission form template with a blank at the top:
"Programme: ______". The template is written once; each copy is filled in for
one programme. A **generic class** is the same: written once with a blank
called a **type parameter** (usually `T`, for type), and each use fills the
blank with a real type. `List<Student>` is "the List template, filled in with
Student".

## Why generics exist

Before Java 5, collections held `Object`, so anything could go in, and you cast
on the way out.

```java [RawList.java]
import java.util.*;

public class RawList {
  public static void main(String[] args) {
    List marks = new ArrayList();          // a raw type: no <...>
    marks.add(78);
    marks.add("absent");                   // compiles: anything goes in
    int total = 0;
    for (Object m : marks) {
      total += (Integer) m;                // the cast fails at run time
    }
  }
}
```

```text [Output]
Note: RawList.java uses unchecked or unsafe operations.
Note: Recompile with -Xlint:unchecked for details.
Exception in thread "main" java.lang.ClassCastException: class java.lang.String cannot be cast to class java.lang.Integer (java.lang.String and java.lang.Integer are in module java.base of loader 'bootstrap')
	at RawList.main(RawList.java:10)
```

With the type parameter, the same mistake cannot be compiled:

```java [TypedList.java]
import java.util.*;

public class TypedList {
  public static void main(String[] args) {
    List<Integer> marks = new ArrayList<>();
    marks.add(78);
    marks.add("absent");
  }
}
```

```text [Output]
TypedList.java:7: error: incompatible types: String cannot be converted to Integer
    marks.add("absent");
              ^
1 error
```

That is the whole reason for generics: **type errors move from run time, in
production, to compile time, on your machine**, and the casts disappear. A
`List` with no brackets is called a **raw type**; it still compiles (for old
code) with the "unchecked" warning above, and you should never write one.

## Syntax

```java
class Register<T> { ... }                          // generic class
static <T> T lastOf(List<T> items) { ... }         // generic method: <T> before the return type
static <T extends Comparable<T>> T highest(...)    // bounded: T must be Comparable
double total(List<? extends Number> marks)         // wildcard: any list of a Number type
```

```java [GenericsDemo.java]
import java.util.*;

public class GenericsDemo {
  // A generic class: T is chosen by whoever creates a Register
  static class Register<T> {
    private final List<T> entries = new ArrayList<>();
    void add(T entry) { entries.add(entry); }
    T get(int index)  { return entries.get(index); }
    int size()        { return entries.size(); }
  }

  record Student(String name, int marks) { }
  record Faculty(String name, String department) { }

  // A generic method: <T> before the return type declares it
  static <T> T lastOf(List<T> items) {
    return items.get(items.size() - 1);
  }

  // A bounded type: T must be comparable to itself
  static <T extends Comparable<T>> T highest(List<T> items) {
    T best = items.get(0);
    for (T item : items) {
      if (item.compareTo(best) > 0) best = item;
    }
    return best;
  }

  public static void main(String[] args) {
    Register<Student> students = new Register<>();
    students.add(new Student("Anita", 78));
    Student s = students.get(0);                      // no cast needed

    Register<Faculty> faculty = new Register<>();
    faculty.add(new Faculty("Dr. Rao", "CSE"));

    System.out.println(s.name() + ", " + faculty.get(0).department());
    System.out.println(lastOf(List.of("Java", "DBMS", "OS")));
    System.out.println(highest(List.of(78, 92, 64)));
    System.out.println(highest(List.of("Anita", "Vikram", "Farah")));
  }
}
```

```bash [Terminal]
javac GenericsDemo.java && java GenericsDemo
```

```text [Output]
Anita, CSE
OS
92
Vikram
```

One `Register` class serves students and faculty. One `highest` method serves
marks and names. Inside `highest`, the only thing Java knows about `T` is what
the **bound** promises: `T extends Comparable<T>` means "whatever T is, it has
a `compareTo`", so `item.compareTo(best)` compiles. Without the bound, `T`
could be anything and the call would be refused. (`extends` is used for
interfaces too, in a bound.)

Naming convention: `T` for type, `E` for element (collections), `K` and `V`
for key and value (maps), `R` for a return type.

## Wildcards, and why List<Integer> is not a List<Number>

`Integer` is a subclass of `Number`. So surely a `List<Integer>` can be passed
where a `List<Number>` is expected?

```java [NotCovariant.java]
import java.util.*;

public class NotCovariant {
  static double total(List<Number> marks) { return 0; }
  public static void main(String[] args) {
    List<Integer> internal = List.of(18, 20, 15);
    total(internal);
  }
}
```

```text [Output]
NotCovariant.java:7: error: incompatible types: List<Integer> cannot be converted to List<Number>
    total(internal);
          ^
1 error
```

It is refused, and for a good reason. If it were allowed, `total` could call
`marks.add(19.5)`, a `Double` is a `Number` so that would type-check, and your
`List<Integer>` would now contain a `Double`. Generics are deliberately
**invariant**: `List<Integer>` and `List<Number>` are unrelated types.

**Wildcards** (`?`, "some type") are how you say what you actually mean:

```java [Wildcards.java]
import java.util.*;

public class Wildcards {
  // ? extends Number: read from it as Numbers. A producer.
  static double total(List<? extends Number> marks) {
    double sum = 0;
    for (Number m : marks) sum += m.doubleValue();
    return sum;
  }

  // ? super Integer: write Integers into it. A consumer.
  static void addGraceMarks(List<? super Integer> target, int count) {
    for (int i = 0; i < count; i++) target.add(5);
  }

  public static void main(String[] args) {
    List<Integer> internal = List.of(18, 20, 15);
    List<Double> practical = List.of(22.5, 19.0);
    System.out.println("internal total:  " + total(internal));
    System.out.println("practical total: " + total(practical));

    List<Number> numbers = new ArrayList<>();
    List<Object> anything = new ArrayList<>();
    addGraceMarks(numbers, 2);
    addGraceMarks(anything, 1);
    System.out.println(numbers + " " + anything);
  }
}
```

```text [Output]
internal total:  53.0
practical total: 41.5
[5, 5] [5]
```

::compare{caption="The two wildcards. One reads, one writes."}
  :::compare-side{label="List<? extends Number>" verdict="neutral"}
  "A list of **some subtype** of Number." You can **read** each element as a
  `Number`. You cannot **add**, because Java does not know whether it is a
  list of Integers or Doubles:

  ```text
  error: incompatible types: int cannot be converted to CAP#1
  ```
  :::
  :::compare-side{label="List<? super Integer>" verdict="neutral"}
  "A list of Integer or **some supertype** of it" (Number, Object). You can
  **add** Integers, since every such list accepts them. Reading gives you only
  `Object`, because that is all Java can promise.
  :::
::

The rule that decides which to use is called **PECS**: **Producer Extends,
Consumer Super**. If the parameter **produces** values for your method to read,
use `? extends T`. If it **consumes** values your method writes, use `? super
T`. If it does both, use plain `T`. The library follows it exactly:

```java
// from java.util.Collections
public static <T> void copy(List<? super T> dest, List<? extends T> src)
```

`src` produces (extends), `dest` consumes (super). And `Comparable<? super T>`
in the sort error from the last lesson means "something that can compare Ts,
or compare any supertype of T": a comparator of `Number`s can sort `Integer`s.

## Type erasure

Generics exist only at compile time. After checking the types, the compiler
**erases** them: `List<String>` and `List<Integer>` both become plain `List` in
the bytecode, with casts inserted where you read. This was done so that
generic code in 2004 could run on older JVMs and mix with older libraries.

```java [Erasure.java]
import java.util.*;

public class Erasure {
  public static void main(String[] args) {
    List<String> names = new ArrayList<>();
    List<Integer> marks = new ArrayList<>();
    System.out.println(names.getClass() == marks.getClass());
    System.out.println(names.getClass().getName());
  }
}
```

```text [Output]
true
java.util.ArrayList
```

Erasure explains three restrictions that otherwise look arbitrary:

```java [ErasureClash.java]
import java.util.*;

public class ErasureClash {
  static void save(List<String> names) { }
  static void save(List<Integer> marks) { }
  static <T> T[] makeArray() { return new T[10]; }
  public static void main(String[] args) { }
}
```

```text [Output]
ErasureClash.java:5: error: name clash: save(List<Integer>) and save(List<String>) have the same erasure
  static void save(List<Integer> marks) { }
              ^
ErasureClash.java:6: error: generic array creation
  static <T> T[] makeArray() { return new T[10]; }
                                      ^
2 errors
```

- **No overloading on the type parameter**: after erasure both `save` methods
  are `save(List)`.
- **No `new T[]` and no `new T()`**: at run time there is no `T` to create.
- **No `instanceof List<String>`**: the run time cannot tell. Only
  `instanceof List<?>` compiles.
- **No primitives**: `List<int>` is impossible, because erasure turns `T` into
  `Object`, and an `int` is not an object. Hence `List<Integer>` and autoboxing.

## Real use case

Almost every backend returns long lists one page at a time: page 2 of the
student list, page 1 of fee payments. Without generics you would write
`StudentPage`, `FeePage`, `ResultPage`, each identical. With them, one class:

```java [Page.java]
import java.util.*;

// One class for a page of anything: students, results, fee payments.
public record Page<T>(List<T> items, int pageNumber, int totalPages) {

  static <T> Page<T> of(List<T> all, int pageNumber, int pageSize) {
    int from = Math.min((pageNumber - 1) * pageSize, all.size());
    int to = Math.min(from + pageSize, all.size());
    int totalPages = (all.size() + pageSize - 1) / pageSize;
    return new Page<>(List.copyOf(all.subList(from, to)), pageNumber, totalPages);
  }

  record Student(String rollNumber, String name) { }
  record FeePayment(String rollNumber, long amountPaise) { }

  public static void main(String[] args) {
    List<Student> students = new ArrayList<>();
    for (int i = 1; i <= 7; i++) students.add(new Student("CS180" + i, "Student " + i));

    Page<Student> page2 = Page.of(students, 2, 3);
    System.out.println("Page " + page2.pageNumber() + " of " + page2.totalPages());
    for (Student s : page2.items()) System.out.println("  " + s.rollNumber());

    Page<FeePayment> fees = Page.of(List.of(new FeePayment("CS1801", 4_500_000L)), 1, 3);
    long firstAmount = fees.items().get(0).amountPaise();     // typed, no cast
    System.out.println("Fees page " + fees.pageNumber() + " of " + fees.totalPages() + ", first: " + firstAmount);
  }
}
```

```text [Output]
Page 2 of 3
  CS1804
  CS1805
  CS1806
Fees page 1 of 1, first: 4500000
```

Records can be generic too. `(all.size() + pageSize - 1) / pageSize` is
integer division rounded up: 7 students at 3 per page is 3 pages, not 2.
`List.copyOf` hands back a frozen copy, so a caller cannot change the page or
reach back into the original list through `subList`.

::real-life{title="Where you will read generics every day" source="Spring, JPA, HTTP clients"}
Spring's `ResponseEntity<T>`, JPA's `JpaRepository<Student, Long>`,
`Optional<T>`, `CompletableFuture<T>`: most of the framework code a Java
developer touches in their first job is generic. You rarely write complex
generic code yourself; you read it all day.
::

## What confuses people here

- **`<T>` in two places means two things.** In `class Register<T>` it declares
  the type parameter for the whole class. In `static <T> T lastOf(...)` the
  first `<T>` declares it for that method only; the second `T` is the return
  type.
- **Static members cannot use the class's `T`.** Each `Register<Student>` and
  `Register<Faculty>` shares static fields, so a static field of type `T` could
  not be both. Static methods declare their own `<T>`, as `Page.of` does.
- **`<?>` is not the same as `<Object>`.** A `List<?>` is a list of some
  unknown type: you can read `Object`s from it but add nothing except `null`.
  A `List<Object>` accepts anything, and a `List<String>` cannot be passed as
  one.
- **The diamond `<>` needs something to infer from.** `new ArrayList<>()` works
  because the variable's type says what goes in the brackets. With `var list =
  new ArrayList<>();` there is nothing to infer, and you get an
  `ArrayList<Object>`.

## Interview questions

::accordion
  :::accordion-item{label="Why were generics introduced?" icon="i-lucide-message-circle"}
  For compile-time type safety and to remove casts. Without them, a raw `List`
  accepts a `String` among `Integer`s and fails with `ClassCastException` when
  read (`RawList.java`). With `List<Integer>`, the bad `add` is a compile error
  (`TypedList.java`).
  :::
  :::accordion-item{label="What is type erasure?" icon="i-lucide-message-circle"}
  The compiler checks generic types, then removes them from the bytecode,
  replacing `T` with its bound (usually `Object`) and inserting casts. So
  `new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()`
  is `true`. It is why you cannot write `new T[10]`, use primitives as type
  arguments, or overload `save(List<String>)` with `save(List<Integer>)`.
  :::
  :::accordion-item{label="What is the difference between ? extends T and ? super T?" icon="i-lucide-message-circle"}
  `? extends T` accepts T or any subtype; you can read elements as T but not
  add. `? super T` accepts T or any supertype; you can add T but only read
  `Object`. Rule of thumb, PECS: Producer Extends, Consumer Super.

  ```java
  static double total(List<? extends Number> marks)          // reads
  static void addGraceMarks(List<? super Integer> target, int n) // writes
  ```
  :::
  :::accordion-item{label="Is List<Integer> a subtype of List<Number>?" icon="i-lucide-message-circle"}
  No. Generics are invariant. If it were, a method taking `List<Number>` could
  add a `Double` to your list of Integers. `NotCovariant.java` shows the
  compile error. Use `List<? extends Number>` to accept both.
  :::
  :::accordion-item{label="What is a bounded type parameter?" icon="i-lucide-message-circle"}
  A type parameter restricted with `extends`, such as `<T extends
  Comparable<T>>` or `<T extends Number>`. It limits which types can be used
  and, in return, lets the method call the bound's methods on `T`: `highest`
  can call `compareTo` because of the bound.
  :::
  :::accordion-item{label="Can you use a primitive as a type argument?" icon="i-lucide-message-circle"}
  No. `List<int>` does not compile, because after erasure the element type is
  `Object`, and a primitive is not an object. Use the wrapper, `List<Integer>`,
  and autoboxing converts for you (at a small cost per element).
  :::
::
