You have looped over lists, sets and maps with the enhanced `for`. Now try
removing the withdrawn students from a batch inside that loop, and Java throws
an exception whose name is longer than the code that caused it. This lesson is
why, and the three ways to do it properly.

## Why this matters in a job

Removing items while looping is something you will want to do in your first
week: drop the absentees, clear the paid fees, remove the cancelled
applications. Done the obvious way, it throws a
`ConcurrentModificationException`. Done a slightly less obvious way (a
backwards index loop, a copy), it works but is easy to get wrong.

"What is a fail-fast iterator?", "fail-fast against fail-safe?" and "how do you
remove an element while iterating?" are standard collections questions in
fresher and two-year interviews.

## An iterator is a bookmark

An **iterator** is an object that walks through a collection one element at a
time and remembers where it is, like a bookmark in the attendance register. It
has three methods:

- `hasNext()`: is there another element?
- `next()`: give me the next one and move the bookmark forward;
- `remove()`: remove the element I was given last.

Every collection gives you one with `.iterator()`. And the enhanced `for` loop
is not a separate feature: the compiler **rewrites** it into an iterator loop.

::compare{caption="What you write, and what the compiler turns it into."}
  :::compare-side{label="You write" verdict="neutral"}
  ```java
  for (String s : batch) {
    System.out.println(s);
  }
  ```
  :::
  :::compare-side{label="The compiler generates" verdict="neutral"}
  ```java
  Iterator<String> it = batch.iterator();
  while (it.hasNext()) {
    String s = it.next();
    System.out.println(s);
  }
  ```
  :::
::

That is why the for-each loop works on anything that implements the
`Iterable` interface (which every `Collection` does), and why it does **not**
work on a `Map`, which is not `Iterable`.

## How it works

Here is the bug. Two students have withdrawn; remove them from the batch.

```java [RemoveInLoop.java]
import java.util.*;

public class RemoveInLoop {
  public static void main(String[] args) {
    List<String> batch = new ArrayList<>(List.of("Anita", "Vikram", "Farah", "Rohit", "Meera"));
    Set<String> withdrawn = Set.of("Vikram", "Rohit");

    for (String student : batch) {
      if (withdrawn.contains(student)) {
        batch.remove(student);
      }
    }
    System.out.println(batch);
  }
}
```

```bash [Terminal]
javac RemoveInLoop.java && java RemoveInLoop
```

```text [Output]
Exception in thread "main" java.util.ConcurrentModificationException
	at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1095)
	at java.base/java.util.ArrayList$Itr.next(ArrayList.java:1049)
	at RemoveInLoop.main(RemoveInLoop.java:8)
```

Read the stack trace from the bottom. Line 8 of our code is the `for` line,
not the `remove` line. The exception is thrown by `next()`, inside the
iterator (`ArrayList$Itr` is the list's iterator class), in a method called
`checkForComodification`. So the remove succeeded; it was the **next step of
the loop** that noticed.

::flow{numbered direction="vertical" caption="How a fail-fast iterator notices that the list changed under it."}
  :::flow-step{label="The list counts its changes" icon="i-lucide-hash"}
  Every `ArrayList` has a field `modCount`, increased on every add or remove.
  :::
  :::flow-step{label="The iterator remembers the count" icon="i-lucide-bookmark"}
  When created, it copies `modCount` into its own `expectedModCount`.
  :::
  :::flow-step{label="batch.remove() changes the list, not the iterator" icon="i-lucide-trash"}
  `modCount` goes up. `expectedModCount` does not.
  :::
  :::flow-step{label="next() compares the two" icon="i-lucide-triangle-alert" highlight}
  They differ, so it throws `ConcurrentModificationException` rather than carry
  on with a bookmark that may now point at the wrong element.
  :::
::

"Concurrent" in the name misleads people: there is only one thread here. It
means "the collection was modified while being iterated", by anyone, including
the loop itself. An iterator that fails immediately like this is called
**fail-fast**: it would rather crash than quietly skip or repeat elements.

### The three safe ways to remove while looping

```java [IteratorRemove.java]
import java.util.*;

public class IteratorRemove {
  public static void main(String[] args) {
    Set<String> withdrawn = Set.of("Vikram", "Rohit");

    // 1. The explicit iterator: remove through the iterator, not the list
    List<String> batch = new ArrayList<>(List.of("Anita", "Vikram", "Farah", "Rohit", "Meera"));
    Iterator<String> it = batch.iterator();
    while (it.hasNext()) {
      String student = it.next();
      if (withdrawn.contains(student)) {
        it.remove();                        // removes the element next() returned
      }
    }
    System.out.println("iterator.remove: " + batch);

    // 2. removeIf: the same thing in one line (Java 8+)
    List<String> batch2 = new ArrayList<>(List.of("Anita", "Vikram", "Farah", "Rohit", "Meera"));
    batch2.removeIf(withdrawn::contains);
    System.out.println("removeIf:        " + batch2);

    // 3. A map: remove through the entry set
    Map<String, Integer> feeDue = new HashMap<>(Map.of("Anita", 0, "Farah", 12000, "Meera", 0));
    feeDue.entrySet().removeIf(e -> e.getValue() == 0);
    System.out.println("still owe fees:  " + feeDue);
  }
}
```

```text [Output]
iterator.remove: [Anita, Farah, Meera]
removeIf:        [Anita, Farah, Meera]
still owe fees:  {Farah=12000}
```

`it.remove()` works because it removes **and** updates the iterator's
expected count, so the next `next()` sees nothing wrong. `removeIf` does the
same internally, and is what you should write in new code. For a map, removing
through `entrySet()`, `keySet()` or `values()` removes from the map itself.

The other safe way you will see in older code is an index loop that runs
**backwards**, `for (int i = list.size() - 1; i >= 0; i--)`, so removing
element `i` never shifts the ones you have still to visit.

### ListIterator: both directions, and edits

A `List` also offers `listIterator()`, which can move backwards, tell you the
index, replace the current element with `set`, and insert with `add`.

```java [ListIter.java]
import java.util.*;

public class ListIter {
  public static void main(String[] args) {
    List<String> names = new ArrayList<>(List.of("anita", "vikram", "farah"));
    ListIterator<String> it = names.listIterator();
    while (it.hasNext()) {
      int index = it.nextIndex();
      String name = it.next();
      it.set(name.substring(0, 1).toUpperCase() + name.substring(1));   // replace in place
      if (index == 0) {
        it.add("Meera");                                                  // insert after current
      }
    }
    System.out.println(names);

    System.out.print("Backwards:");
    while (it.hasPrevious()) {
      System.out.print(" " + it.previous());
    }
    System.out.println();
  }
}
```

```text [Output]
[Anita, Meera, Vikram, Farah]
Backwards: Farah Vikram Meera Anita
```

## Real use case

Sometimes the thing you want to loop over is your own class. A `Batch` that
holds students could expose its array, but then any caller could change it.
Instead, make `Batch` implement `Iterable<String>`, and callers can use the
for-each loop on it without ever seeing the array inside. That is
encapsulation from the objects chapter, applied to looping.

```java [Batch.java]
import java.util.*;

public class Batch implements Iterable<String> {
  private final String[] students;
  private final int size;

  Batch(String... students) {
    this.students = students;
    this.size = students.length;
  }

  @Override
  public Iterator<String> iterator() {
    return new Iterator<>() {
      private int next = 0;
      @Override public boolean hasNext() { return next < size; }
      @Override public String next() {
        if (!hasNext()) throw new NoSuchElementException();
        return students[next++];
      }
    };
  }

  public static void main(String[] args) {
    Batch morning = new Batch("Anita", "Vikram", "Farah");
    for (String s : morning) {                 // works because Batch is Iterable
      System.out.println("Present: " + s);
    }

    Iterator<String> it = morning.iterator();
    it.next(); it.next(); it.next();
    it.next();                                 // one too many
  }
}
```

```text [Output]
Present: Anita
Present: Vikram
Present: Farah
Exception in thread "main" java.util.NoSuchElementException
	at Batch$1.next(Batch.java:18)
	at Batch$1.next(Batch.java:14)
	at Batch.main(Batch.java:32)
```

`new Iterator<>() { ... }` is an **anonymous class**: a class with no name,
written and instantiated in one place, which is common for small one-off
implementations of an interface. `Batch$1` in the stack trace is the name the
compiler gave it. Calling `next()` when `hasNext()` is false must throw
`NoSuchElementException`; that is part of the `Iterator` contract, and the
library's iterators do the same.

::real-life{title="Where Iterable shows up" source="Library and framework code"}
Database result wrappers, file line readers and paginated API clients often
implement `Iterable`, so calling code can write a plain for-each over rows or
pages while the class fetches the next batch only when `hasNext()` asks for it.
::

## What confuses people here

### Sometimes it does not throw at all

```java [SecondLast.java]
import java.util.*;

public class SecondLast {
  public static void main(String[] args) {
    List<String> batch = new ArrayList<>(List.of("Anita", "Vikram", "Farah"));
    for (String s : batch) {
      if (s.equals("Vikram")) {
        batch.remove(s);          // the second-last element
      }
    }
    System.out.println("No exception, and: " + batch);
  }
}
```

```text [Output]
No exception, and: [Anita, Farah]
```

Removing the **second-last** element does not throw. After the removal the
list has two elements and the iterator's cursor is at 2, so `hasNext()` returns
false and `next()` (where the check lives) is never called. The loop also
silently never visits Farah. Fail-fast is "best effort", not a guarantee, and
this is a favourite trick question. Do not rely on the exception to catch the
bug.

### Fail-fast against fail-safe

The collections in `java.util.concurrent` have **fail-safe** (the official
word is weakly consistent) iterators: they never throw
`ConcurrentModificationException`.

```java [FailSafe.java]
import java.util.*;
import java.util.concurrent.*;

public class FailSafe {
  public static void main(String[] args) {
    List<String> notices = new CopyOnWriteArrayList<>(List.of("Exam on Monday", "Fees due Friday"));
    for (String n : notices) {
      notices.add("Reminder: " + n);          // allowed: the loop reads a snapshot
    }
    System.out.println(notices.size() + " notices: " + notices);

    Map<String, Integer> seats = new ConcurrentHashMap<>(Map.of("CSE", 0, "ECE", 12, "Civil", 0));
    for (String course : seats.keySet()) {
      if (seats.get(course) == 0) seats.remove(course);   // no exception
    }
    System.out.println("courses with seats: " + seats);
  }
}
```

```text [Output]
4 notices: [Exam on Monday, Fees due Friday, Reminder: Exam on Monday, Reminder: Fees due Friday]
courses with seats: {ECE=12}
```

::pros-cons
---
title: Fail-fast against fail-safe iterators
pros:
  - "Fail-fast (ArrayList, HashMap, HashSet): cheap, and a modification bug surfaces as an exception instead of wrong data"
  - "Fail-safe (CopyOnWriteArrayList, ConcurrentHashMap): safe to modify while iterating, including from other threads"
cons:
  - "Fail-fast: best effort only; SecondLast.java slips past it"
  - "CopyOnWriteArrayList copies the whole array on every write, so it suits lists read often and changed rarely"
  - "A fail-safe iterator may not show changes made after it started, as the snapshot loop shows"
---
::

## Interview questions

::accordion
  :::accordion-item{label="What is ConcurrentModificationException, and when is it thrown?" icon="i-lucide-message-circle"}
  It is thrown by a fail-fast iterator's `next()` when the collection's
  `modCount` no longer matches the count the iterator expected, meaning the
  collection was structurally changed (added to or removed from) other than
  through the iterator. It happens in a single thread too: `RemoveInLoop.java`
  removes inside a for-each.
  :::
  :::accordion-item{label="How do you remove elements while iterating?" icon="i-lucide-message-circle"}
  Use `iterator.remove()` inside an explicit iterator loop, or
  `collection.removeIf(condition)`, or loop backwards by index. For a map,
  `map.entrySet().removeIf(...)`.

  ```java
  batch.removeIf(withdrawn::contains);
  ```
  :::
  :::accordion-item{label="Fail-fast against fail-safe iterators?" icon="i-lucide-message-circle"}
  Fail-fast iterators (most of `java.util`) throw
  `ConcurrentModificationException` if the collection changes during
  iteration. Fail-safe iterators (`CopyOnWriteArrayList`, `ConcurrentHashMap`)
  do not throw; they iterate over a snapshot or a weakly consistent view, so
  they may not reflect changes made after they started.
  :::
  :::accordion-item{label="What is the difference between Iterator and ListIterator?" icon="i-lucide-message-circle"}
  `Iterator` works on any collection and goes forwards only, with `hasNext`,
  `next` and `remove`. `ListIterator` works on lists only and adds
  `hasPrevious`, `previous`, `nextIndex`, `previousIndex`, `set` and `add`.
  :::
  :::accordion-item{label="Why does removing the second-last element in a for-each not throw?" icon="i-lucide-message-circle"}
  After the removal, the size equals the iterator's cursor, so `hasNext()`
  returns false and the loop ends before `next()` runs its check. The last
  element is silently skipped. `SecondLast.java` prints `[Anita, Farah]` with
  no exception.
  :::
  :::accordion-item{label="What is the difference between Iterable and Iterator?" icon="i-lucide-message-circle"}
  `Iterable` is something that can be looped over; it has one method,
  `iterator()`, and implementing it enables the for-each loop. `Iterator` is
  the bookmark that does the walking. A `Batch` is `Iterable`; each call to
  `batch.iterator()` gives a fresh `Iterator`.
  :::
::
