You can now stop a program from falling over on a `null`. The next problem is
the one arrays left behind: they have a fixed size, and real data does not.
Forty students enrol today and three more tomorrow. The **Collections
framework** is Java's answer, and you will use it in almost every method you
ever write.

## Why this matters in a job

Open any Java codebase at any company in Bangalore and count the `List`,
`Map` and `Set` declarations. They are everywhere: a list of students from
the database, a map from roll number to result, a set of departments that
already have a timetable. Choosing the wrong one does not usually crash; it
makes the code slow, or lets duplicates in, or loses the order a report needed.

In interviews, collections are the single biggest block of core Java
questions after OOPs. "ArrayList or LinkedList", "how does HashMap work",
"difference between HashSet and TreeSet", "fail-fast iterator", "Comparable or
Comparator": each gets its own lesson in this chapter. This one is the map of
the territory.

## Two families, not one

The **Collections framework** is a set of interfaces (contracts) and classes
(implementations) in the package `java.util` for holding groups of objects.
Think of the college office. It keeps:

- **registers**, which are ordered and can repeat a name (the attendance
  register for each day): that is a **List**;
- **the list of departments**, where each appears exactly once: a **Set**;
- **the token queue at the fee counter**, first come first served: a **Queue**;
- **the roll-number book**, where you look up a roll number and get a name:
  a **Map**, which stores **key → value** pairs.

The first three are all a group of single things, and they share one parent
interface, `Collection`. The fourth stores pairs, so it is a separate family.

Two words to keep straight, because interviewers check:

- **`Collection`** (singular) is the root **interface** of the first family.
- **`Collections`** (plural) is a **utility class** full of static helper
  methods such as `Collections.sort`. It has its own lesson later in this
  chapter.

## How it works

The rule that runs through every real codebase: **declare the variable as the
interface, create it as a class.**

```java
List<String> attendance = new ArrayList<>();   // variable type: List
Map<String, Integer> marks = new HashMap<>();   // variable type: Map
```

The `<String>` in angle brackets says what the collection holds; it is a
**generic type parameter**, and the last lesson in this chapter explains it
properly. `<>` on the right, the **diamond**, tells the compiler to copy the
type from the left. Collections hold objects only, so a list of marks is
`List<Integer>`, not `List<int>`; autoboxing (from the wrapper classes lesson)
converts for you.

All four kinds in one program:

```java [CollectionsTour.java]
import java.util.*;

public class CollectionsTour {
  public static void main(String[] args) {
    // List: ordered, duplicates allowed, read by index
    List<String> attendance = new ArrayList<>();
    attendance.add("Anita");
    attendance.add("Vikram");
    attendance.add("Anita");               // marked twice by mistake: allowed
    System.out.println("List:  " + attendance + " size " + attendance.size());

    // Set: no duplicates
    Set<String> present = new HashSet<>(attendance);
    System.out.println("Set:   " + present + " size " + present.size());

    // Queue: first in, first out
    Queue<String> helpDesk = new ArrayDeque<>();
    helpDesk.offer("Farah: fee receipt");
    helpDesk.offer("Rohit: hall ticket");
    System.out.println("Queue: serving " + helpDesk.poll() + ", waiting " + helpDesk);

    // Map: key -> value. Not a Collection.
    Map<String, Integer> marks = new HashMap<>();
    marks.put("Anita", 78);
    marks.put("Vikram", 64);
    marks.put("Anita", 81);                // same key: replaces the value
    System.out.println("Map:   " + marks + " Anita has " + marks.get("Anita"));

    Collection<String> c = attendance;     // a List IS a Collection
    System.out.println("Collection contains Vikram? " + c.contains("Vikram"));
  }
}
```

```bash [Terminal]
javac CollectionsTour.java && java CollectionsTour
```

```text [Output]
List:  [Anita, Vikram, Anita] size 3
Set:   [Vikram, Anita] size 2
Queue: serving Farah: fee receipt, waiting [Rohit: hall ticket]
Map:   {Vikram=64, Anita=81} Anita has 81
Collection contains Vikram? true
```

Notice the `Set` printed Vikram before Anita. A `HashSet` does not promise any
order, and neither does a `HashMap`. If you need order, you choose a different
class, which is what the next table is for.

### Choosing, in one table

| What you need | Use |
| --- | --- |
| An ordered list, read by position | `ArrayList` |
| No duplicates, order does not matter | `HashSet` |
| No duplicates, keep insertion order | `LinkedHashSet` |
| No duplicates, sorted | `TreeSet` |
| Look up a value by a key | `HashMap` |
| Look up by key, iterate in insertion order | `LinkedHashMap` |
| Look up by key, sorted keys or ranges | `TreeMap` |
| A queue or a stack (add and remove at the ends) | `ArrayDeque` |
| Always take the highest-priority item next | `PriorityQueue` |

::tip
The answer to "which collection?" in an interview is the requirement first,
then the class, then the cost. "A `HashMap`, because I look students up by
roll number and constant-time lookup matters more here than order. I accept
that iteration order is undefined." Naming the cost is what makes the answer
sound like someone who has used it.
::

## Real use case

Enrolment requests arrive as pairs of (student, course), with duplicates,
because students click the button twice. The office wants each course's
students, once each, in the order they asked, with courses listed
alphabetically, and then who is taking both Java and DBMS.

```java [Enrolment.java]
import java.util.*;

public class Enrolment {
  public static void main(String[] args) {
    String[][] requests = {
      {"Anita", "Java"}, {"Vikram", "DBMS"}, {"Farah", "Java"},
      {"Anita", "DBMS"}, {"Rohit", "Java"}, {"Farah", "Java"}   // Farah twice
    };

    Map<String, Set<String>> byCourse = new TreeMap<>();   // sorted by course name
    for (String[] r : requests) {
      String student = r[0], course = r[1];
      byCourse.computeIfAbsent(course, k -> new LinkedHashSet<>()).add(student);
    }

    for (Map.Entry<String, Set<String>> e : byCourse.entrySet()) {
      System.out.println(e.getKey() + " (" + e.getValue().size() + "): " + e.getValue());
    }

    Set<String> both = new TreeSet<>(byCourse.get("Java"));
    both.retainAll(byCourse.get("DBMS"));                   // intersection
    System.out.println("Taking both: " + both);
  }
}
```

```text [Output]
DBMS (2): [Vikram, Anita]
Java (3): [Anita, Farah, Rohit]
Taking both: [Anita]
```

Three requirements, three class choices, no extra code: `TreeMap` for sorted
courses, `LinkedHashSet` for "once each, in the order they asked", and
`retainAll` for the intersection. `computeIfAbsent` means "get the set for this
course, creating an empty one first if there is none". The `k -> new
LinkedHashSet<>()` part is a **lambda**, a short inline function; chapter 8
explains it, and for now read it as "how to make a new one".

::real-life{title="Where this shape turns up" source="Every backend service"}
A map from an id to a list or set of things (course to students, department to
faculty, student to fee payments) is the most common data structure in
business code after the plain list. When a query returns flat rows from a
database, this loop is how they become something a page can display.
::

## What confuses people here

::warning{icon="i-lucide-alert-triangle"}
Three classes to avoid in new code. `Vector` and `Hashtable` are the original
1996 versions, with every method synchronised (locked for thread safety), so
you pay for locking you rarely need. `Stack` extends `Vector`. Their
replacements are `ArrayList`, `HashMap` and `ArrayDeque`. If you genuinely need
thread safety, the answer is `ConcurrentHashMap` (multithreading chapter), not
these. You will still meet them in interview questions and old code.
::

```java [Legacy.java]
import java.util.*;

public class Legacy {
  public static void main(String[] args) {
    Map<String, Integer> fees = new HashMap<>();
    fees.put(null, 0);                          // HashMap allows one null key
    System.out.println("HashMap with null key: " + fees);

    Map<String, Integer> old = new Hashtable<>();
    old.put(null, 0);                           // Hashtable does not
  }
}
```

```text [Output]
HashMap with null key: {null=0}
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "Object.hashCode()" because "key" is null
	at java.base/java.util.Hashtable.put(Hashtable.java:481)
	at Legacy.main(Legacy.java:10)
```

- **A Map is not a Collection.** `Map` does not extend `Collection` or
  `Iterable`, so `for (x : map)` does not compile. Loop over `map.entrySet()`.
- **Printing order is not a promise.** A `HashSet` or `HashMap` may print in a
  different order after more items are added. Code that relies on it will break
  later, silently.
- **`List.of(...)` cannot be changed.** It builds an **immutable** list;
  calling `add` on it throws `UnsupportedOperationException`. The next lesson
  shows it.
- **Streams are not collections.** A stream is a pipeline that reads from a
  collection. They get a whole chapter after this one.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between Collection and Collections?" icon="i-lucide-message-circle"}
  `Collection` is the root interface of List, Set and Queue. `Collections` is
  a utility class of static methods that work on collections:

  ```java
  List<Integer> marks = new ArrayList<>(List.of(78, 64, 92));
  Collections.sort(marks);                 // [64, 78, 92]
  System.out.println(Collections.max(marks)); // 92
  ```
  :::
  :::accordion-item{label="Why does Map not extend Collection?" icon="i-lucide-message-circle"}
  A `Collection` is a group of single elements with `add(E)`. A map stores
  pairs, so `add` makes no sense for it; it has `put(K, V)`. Instead, a map
  offers three collection views: `keySet()`, `values()` and `entrySet()`.
  :::
  :::accordion-item{label="List, Set or Map: how do you choose?" icon="i-lucide-message-circle"}
  List when order and duplicates matter (an attendance register). Set when each
  item must appear once (departments). Map when you look a value up by a key
  (roll number to result). Then pick the class by the extra need: order,
  sorting, or neither.
  :::
  :::accordion-item{label="What is the difference between HashMap and Hashtable?" icon="i-lucide-message-circle"}
  `Hashtable` is synchronised on every method and allows no null key or value;
  `HashMap` is not synchronised and allows one null key and any number of null
  values. `Legacy.java` shows `Hashtable.put(null, 0)` throwing a
  `NullPointerException`. For thread safety use `ConcurrentHashMap`, not
  `Hashtable`.
  :::
  :::accordion-item{label="Why declare List<String> x = new ArrayList<>() instead of ArrayList<String> x?" icon="i-lucide-message-circle"}
  Programming to the interface. Code that uses `x` depends only on what a
  `List` promises, so you can switch to a `LinkedList` or an immutable list by
  changing one line, and methods that accept `List` work with any
  implementation.
  :::
::
