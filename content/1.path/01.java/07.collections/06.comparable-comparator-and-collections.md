In the List lesson the results were sorted by marks with a `Comparator`, and
nothing explained it. Java can sort numbers and strings by itself, because it
knows what "less than" means for them. For a `Student` it has no idea: by roll
number, by name, by marks? This lesson is how you tell it.

## Why this matters in a job

Every list a user sees is sorted by something: a merit list by marks, a
register by roll number, a fee report by amount due. Sorting rules with
tie-breaks ("higher total first, then higher maths marks, then alphabetical")
are real admissions policy, and getting a tie-break wrong puts a student at the
wrong rank.

"Comparable against Comparator" is one of the most reliable core Java
interview questions. The follow-ups are usually "write a comparator for
this" and "sort by two fields".

## Two ways to answer "who comes first?"

Think of the college register. It has one **natural order**, fixed when the
register is printed: roll number. That order belongs to the register itself.
But the principal sometimes wants the same students by marks, and the
hostel warden wants them by name. Those orders come from **outside**, for one
job, and there can be as many as you like.

- **`Comparable`** is the natural order, written **inside** the class, once.
  The class implements `Comparable<Student>` and its one method
  `compareTo(Student other)`.
- **`Comparator`** is any other order, written **outside** the class, as a
  separate object with one method `compare(Student a, Student b)`. You can have
  many.

Both methods follow the same rule for the `int` they return:

| Return | Means |
| --- | --- |
| negative | the first comes **before** the second |
| zero | they are equal **for sorting** |
| positive | the first comes **after** the second |

The size of the number does not matter, only its sign.

## Syntax

```java [SortStudents.java]
import java.util.*;

public class SortStudents {
  // Natural order: by roll number. Written once, inside the class.
  record Student(String rollNumber, String name, int marks) implements Comparable<Student> {
    @Override
    public int compareTo(Student other) {
      return this.rollNumber.compareTo(other.rollNumber);
    }
  }

  public static void main(String[] args) {
    List<Student> batch = new ArrayList<>(List.of(
        new Student("CS1803", "Farah", 92),
        new Student("CS1801", "Anita", 78),
        new Student("CS1804", "Rohit", 78),
        new Student("CS1802", "Vikram", 64)));

    Collections.sort(batch);                        // uses compareTo
    System.out.println("By roll number:");
    batch.forEach(s -> System.out.println("  " + s));

    // Another order, from outside the class: an anonymous Comparator
    Comparator<Student> byMarksHighFirst = new Comparator<Student>() {
      @Override
      public int compare(Student a, Student b) {
        return Integer.compare(b.marks(), a.marks());
      }
    };
    batch.sort(byMarksHighFirst);
    System.out.println("By marks, highest first:");
    batch.forEach(s -> System.out.println("  " + s));
  }
}
```

`batch.forEach(s -> ...)` and `(a, b) -> ...` are **lambdas**, short inline
functions. The anonymous `Comparator` class above is eight lines to say "by
marks, descending". The next chapter shrinks it to one.

### Building comparators, the modern way

Since Java 8, `Comparator` has static and default methods that build a
comparator from the field you want to sort by, and chain tie-breaks:

| Method | Does |
| --- | --- |
| `Comparator.comparing(Student::name)` | sort by a field whose type is Comparable |
| `Comparator.comparingInt(Student::marks)` | the same for an `int` field, without boxing |
| `.reversed()` | flip the whole comparator built so far |
| `.thenComparing(...)` | tie-break when the previous comparison gave 0 |
| `Comparator.naturalOrder()` / `reverseOrder()` | the class's own `compareTo`, or its reverse |
| `Comparator.nullsFirst(...)` / `nullsLast(...)` | put `null` elements at one end instead of throwing |

`Student::name` is a **method reference**, meaning "call `name()` on each
student". That is also chapter 8.

## Real use case

The admissions office publishes the merit list with this rule: higher total
first; on a tie, higher maths marks; on a further tie, alphabetical by name.

```java [MeritList.java]
import java.util.*;

public class MeritList {
  record Applicant(String name, int total, int maths, String category) { }

  public static void main(String[] args) {
    List<Applicant> applicants = new ArrayList<>(List.of(
        new Applicant("Vikram Shah", 412, 88, "GEN"),
        new Applicant("Anita Rao",   438, 91, "OBC"),
        new Applicant("Farah Khan",  438, 95, "GEN"),
        new Applicant("Rohit Das",   412, 88, "SC"),
        new Applicant("Meera Iyer",  401, 97, "GEN")));

    // Rule from the admissions office: higher total first; on a tie, higher
    // maths marks; on a further tie, alphabetical by name.
    Comparator<Applicant> merit = Comparator
        .comparingInt(Applicant::total).reversed()
        .thenComparing(Comparator.comparingInt(Applicant::maths).reversed())
        .thenComparing(Applicant::name);

    applicants.sort(merit);
    int rank = 1;
    for (Applicant a : applicants) {
      System.out.printf("%d. %-12s %d  maths %d%n", rank++, a.name(), a.total(), a.maths());
    }
  }
}
```

```text [Output]
1. Farah Khan   438  maths 95
2. Anita Rao    438  maths 91
3. Rohit Das    412  maths 88
4. Vikram Shah  412  maths 88
5. Meera Iyer   401  maths 97
```

Each line of the comparator is one sentence of the policy, which is the whole
point: a reviewer can check it against the admissions document. Farah beats
Anita on maths; Rohit beats Vikram on name. Meera's 97 in maths does not
matter, because the tie-break is only consulted when totals are equal.

::warning{icon="i-lucide-alert-triangle"}
Where you put `.reversed()` matters. It reverses **everything built so far**.
`comparingInt(total).thenComparing(name).reversed()` would reverse the name
tie-break too, putting Vikram before Rohit. Reverse each key where you define
it, as above.
::

### The Collections utility class

`java.util.Collections` (plural) is a class of static helpers for collections,
the same idea as `Arrays` for arrays.

```java [CollectionsTools.java]
import java.util.*;

public class CollectionsTools {
  public static void main(String[] args) {
    List<Integer> marks = new ArrayList<>(List.of(78, 64, 92, 55, 78, 88));

    System.out.println("max / min:     " + Collections.max(marks) + " / " + Collections.min(marks));
    System.out.println("frequency 78:  " + Collections.frequency(marks, 78));
    Collections.sort(marks);
    System.out.println("sorted:        " + marks);
    System.out.println("binarySearch:  " + Collections.binarySearch(marks, 88));
    Collections.reverse(marks);
    System.out.println("reversed:      " + marks);
    Collections.swap(marks, 0, marks.size() - 1);
    System.out.println("swapped ends:  " + marks);
    Collections.shuffle(marks, new Random(2018));   // fixed seed: same order every run
    System.out.println("shuffled:      " + marks);
    System.out.println("nCopies:       " + Collections.nCopies(3, "absent"));
    System.out.println("disjoint:      " + Collections.disjoint(List.of("CSE", "ECE"), List.of("Civil")));
    System.out.println("max by length: " + Collections.max(List.of("OS", "DBMS", "Java"), Comparator.comparingInt(String::length)));

    List<String> subjects = new ArrayList<>(List.of("Java", "DBMS"));
    List<String> readOnly = Collections.unmodifiableList(subjects);
    subjects.add("OS");                              // the original can still change
    System.out.println("view sees:     " + readOnly);
    try {
      readOnly.add("Networks");
    } catch (UnsupportedOperationException e) {
      System.out.println("readOnly.add:  UnsupportedOperationException");
    }
  }
}
```

```text [Output]
max / min:     92 / 55
frequency 78:  2
sorted:        [55, 64, 78, 78, 88, 92]
binarySearch:  4
reversed:      [92, 88, 78, 78, 64, 55]
swapped ends:  [55, 88, 78, 78, 64, 92]
shuffled:      [64, 78, 55, 92, 78, 88]
nCopies:       [absent, absent, absent]
disjoint:      true
max by length: DBMS
view sees:     [Java, DBMS, OS]
readOnly.add:  UnsupportedOperationException
```

Two in there are interview material. `max by length` returned `DBMS`, not
`Java`: when several are equal, `max` keeps the first it found. And
`unmodifiableList` is a read-only **view**, not a copy: the caller cannot
change it, but whoever holds the original still can, and the view shows it.
For a true frozen copy, use `List.copyOf(subjects)`. The other wrapper worth
knowing, `Collections.synchronizedList(list)`, makes each method lock the
list; the multithreading chapter explains why that is less safe than it sounds.

## What confuses people here

### The comparator that loses a student

```java [LostInTree.java]
import java.util.*;

public class LostInTree {
  record Student(String name, int marks) { }

  public static void main(String[] args) {
    Set<Student> byMarks = new TreeSet<>(Comparator.comparingInt(Student::marks));
    byMarks.add(new Student("Anita", 78));
    byMarks.add(new Student("Rohit", 78));          // compares as 0 with Anita
    byMarks.add(new Student("Farah", 92));
    System.out.println(byMarks.size() + " " + byMarks);

    Set<Student> fixed = new TreeSet<>(
        Comparator.comparingInt(Student::marks).thenComparing(Student::name));
    fixed.add(new Student("Anita", 78));
    fixed.add(new Student("Rohit", 78));
    fixed.add(new Student("Farah", 92));
    System.out.println(fixed.size() + " " + fixed);
  }
}
```

```text [Output]
2 [Student[name=Anita, marks=78], Student[name=Farah, marks=92]]
3 [Student[name=Anita, marks=78], Student[name=Rohit, marks=78], Student[name=Farah, marks=92]]
```

A `TreeSet` (and `TreeMap`) decides duplicates **only** by the comparator.
Rohit compared as 0 with Anita, so he was treated as a duplicate and silently
dropped. A list sort would have kept him; a sorted set did not. The fix is a
tie-break that makes the comparator return 0 only for genuinely equal
students. The rule has a name: a comparator should be **consistent with
equals**.

### Subtraction as a comparator

::compare{caption="The shortcut from old tutorials, and why it fails."}
  :::compare-side{label="(a, b) -> a - b" verdict="wrong"}
  ```text
  [5000, 2147483647, -2147483648, -2000]
  ```
  `Integer.MAX_VALUE - (-2000)` overflows to a negative number, so the
  comparator gives the wrong sign and the list comes out unsorted. No error,
  no warning.
  :::
  :::compare-side{label="Integer.compare(a, b)" verdict="right"}
  ```text
  [-2147483648, -2000, 5000, 2147483647]
  ```
  No arithmetic, so nothing can overflow. Or use
  `Comparator.comparingInt(...)`, which calls it for you.
  :::
::

That output comes from sorting `[5000, Integer.MIN_VALUE, -2000,
Integer.MAX_VALUE]` both ways. Marks never get that large, which is exactly
why the shortcut survives in code until the day it sorts account balances.

- **Sorting a class that is not Comparable** with `Collections.sort(list)` is a
  compile error (`no suitable method found for sort(List<Course>)`) when the
  compiler can see the type. With a `TreeSet`, it compiles and throws
  `ClassCastException` at the first `add`, as the Set lesson showed.
- **`compareTo` on Strings is case-sensitive** and by character code: `"CSE"`
  sorts before `"Civil"`. Use `String.CASE_INSENSITIVE_ORDER` or
  `Comparator.comparing(String::toLowerCase)` for human order.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between Comparable and Comparator?" icon="i-lucide-message-circle"}
  `Comparable` (in `java.lang`) defines the class's single natural order,
  inside the class, with `compareTo(T other)`. `Comparator` (in `java.util`)
  defines any number of other orders, outside the class, with `compare(T a, T
  b)`. Use `Comparable` for the obvious order (a student by roll number) and
  `Comparator` for the rest, or for classes you cannot edit.
  :::
  :::accordion-item{label="Sort a list of students by marks descending, then by name." icon="i-lucide-message-circle"}
  ```java
  students.sort(Comparator.comparingInt(Student::marks).reversed()
                          .thenComparing(Student::name));
  ```

  `reversed()` flips only the marks comparison because it comes before
  `thenComparing`. `MeritList.java` does a three-key version.
  :::
  :::accordion-item{label="Why is return a - b a bad compare implementation?" icon="i-lucide-message-circle"}
  Subtraction can overflow for large values of opposite sign, producing the
  wrong sign. `Subtraction.java` sorts `Integer.MAX_VALUE` before
  `Integer.MIN_VALUE`. Use `Integer.compare(a, b)`.
  :::
  :::accordion-item{label="What does it mean for compareTo to be consistent with equals?" icon="i-lucide-message-circle"}
  `compareTo` returns 0 exactly when `equals` returns true. If not, sorted
  collections behave strangely: a `TreeSet` ordered only by marks treats two
  different students with 78 as the same element and drops one, as
  `LostInTree.java` shows.
  :::
  :::accordion-item{label="What is the difference between Collections.unmodifiableList and List.copyOf?" icon="i-lucide-message-circle"}
  `unmodifiableList` wraps the original: callers cannot change it, but changes
  to the original show through. `List.copyOf` makes an independent immutable
  copy. `CollectionsTools.java` adds `"OS"` to the original and the view shows
  it.
  :::
::
