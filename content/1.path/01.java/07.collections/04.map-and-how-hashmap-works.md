Every Set in the last lesson was a Map underneath. A **Map** stores **key →
value** pairs: give it a roll number, get back a result. `HashMap` is the one
you will use more than any other class in Java, and "how does HashMap work
internally?" is, in my experience of walk-ins, the most asked core Java
question after OOPs.

## Why this matters in a job

Look-ups are everywhere in business code: roll number to student, course code
to faculty, student id to fee balance. A `HashMap` answers them in constant
time however large the data gets, which is why it is also the answer to half
the coding-round problems (counting, grouping, "have I seen this before?").

The interview question has a known shape. The interviewer asks how `put` and
`get` work, then pushes: what is a collision, what happens when two keys have
the same hash code, what changed in Java 8, what is the load factor, why must
keys be immutable, what if you override `equals` but not `hashCode`? This
lesson answers every one of those, with code.

## A HashMap is a set of pigeonholes

The staff room has a wall of pigeonholes, numbered 0 to 15. When a letter
arrives for a lecturer, the clerk does not search the whole wall. He applies a
fixed rule to the name (say, a number worked out from its letters) and that
number says which pigeonhole it goes in. To collect, the lecturer applies the
same rule and goes straight to one pigeonhole. Sometimes two names give the
same number and share a pigeonhole; then he looks through the few letters in it
and checks the names.

In Java:

- the pigeonholes are **buckets**, slots in an internal array called `table`;
- the rule is **`hashCode()`**, a method every object has that returns an
  `int`;
- checking the name on the letter is **`equals()`**;
- two keys landing in the same bucket is a **collision**.

## Syntax

The methods you will use every day:

```java [MapBasics.java]
import java.util.*;

public class MapBasics {
  public static void main(String[] args) {
    Map<String, Integer> marks = new HashMap<>();
    marks.put("CS1801", 78);
    marks.put("CS1802", 64);
    marks.put("CS1803", 92);

    System.out.println("get CS1802:      " + marks.get("CS1802"));
    System.out.println("get CS1899:      " + marks.get("CS1899"));          // missing key: null
    System.out.println("getOrDefault:    " + marks.getOrDefault("CS1899", 0));
    System.out.println("containsKey:     " + marks.containsKey("CS1803"));
    System.out.println("put returns old: " + marks.put("CS1802", 70));      // replaces 64
    marks.putIfAbsent("CS1802", 10);                                        // already there: ignored
    marks.remove("CS1801");

    for (Map.Entry<String, Integer> e : marks.entrySet()) {
      System.out.println(e.getKey() + " -> " + e.getValue());
    }
    System.out.println("keys " + marks.keySet() + ", values " + marks.values());

    // Counting in one line: add 1, or start at 1 if missing
    Map<String, Integer> perDepartment = new TreeMap<>();
    for (String d : new String[] {"CSE", "ECE", "CSE", "Civil", "CSE", "ECE"}) {
      perDepartment.merge(d, 1, Integer::sum);
    }
    System.out.println(perDepartment);
  }
}
```

```bash [Terminal]
javac MapBasics.java && java MapBasics
```

```text [Output]
get CS1802:      64
get CS1899:      null
getOrDefault:    0
containsKey:     true
put returns old: 64
CS1802 -> 70
CS1803 -> 92
keys [CS1802, CS1803], values [70, 92]
{CSE=3, Civil=1, ECE=2}
```

Keys are unique; values are not. `put` with an existing key **replaces** the
value and returns the old one. `merge(d, 1, Integer::sum)` means "put 1 if the
key is missing, otherwise add 1 to what is there", which is a whole counting
loop in one line. (`Integer::sum` is a method reference, explained in chapter
8.)

## How it works

### put(key, value), step by step

::flow{numbered direction="vertical" caption="The same five steps run for get, except the last one returns the value instead of storing it."}
  :::flow-step{label="Call key.hashCode()" icon="i-lucide-hash"}
  Any `int`. For `"CS1801"` it is 1996320472.
  :::
  :::flow-step{label="Spread the bits" icon="i-lucide-shuffle"}
  `h ^ (h >>> 16)` mixes the high 16 bits into the low 16, so keys that differ
  only in their high bits do not all collide.
  :::
  :::flow-step{label="Pick the bucket" icon="i-lucide-grid-3x3" highlight}
  `hash & (n - 1)`, where `n` is the number of buckets. Because `n` is always a
  power of two, this equals `hash % n` and is faster.
  :::
  :::flow-step{label="Walk the bucket with equals()" icon="i-lucide-search"}
  Empty bucket: store a new node. Otherwise compare the hash, then `equals()`,
  against each node. A match means replace its value.
  :::
  :::flow-step{label="Grow if too full" icon="i-lucide-maximize"}
  If size now exceeds capacity × load factor (16 × 0.75 = 12), double the
  table and redistribute the entries.
  :::
::

You can run steps 1 to 3 yourself:

```java [Buckets.java]
public class Buckets {
  // What HashMap does with a key's hashCode (Java 8 onwards)
  static int bucket(Object key, int tableSize) {
    int h = key.hashCode();
    int spread = h ^ (h >>> 16);         // mix the high bits into the low bits
    return spread & (tableSize - 1);     // same as % tableSize, because size is a power of 2
  }

  public static void main(String[] args) {
    String[] keys = {"CS1801", "CS1802", "CS1803", "Aa", "BB"};
    for (String k : keys) {
      System.out.printf("%-7s hashCode %11d  bucket %2d of 16%n", k, k.hashCode(), bucket(k, 16));
    }
  }
}
```

```text [Output]
CS1801  hashCode  1996320472  bucket  5 of 16
CS1802  hashCode  1996320473  bucket  4 of 16
CS1803  hashCode  1996320474  bucket  7 of 16
Aa      hashCode        2112  bucket  0 of 16
BB      hashCode        2112  bucket  0 of 16
```

`"Aa"` and `"BB"` are different strings with the **same** hash code, 2112. That
is a collision, and it is legal: `hashCode` only has four billion possible
values, and there are far more possible strings. Both go into bucket 0, as a
short linked list, and `get("BB")` finds the right one because `equals()`
tells them apart.

### Collisions and Java 8's treeification

If many keys collide into one bucket, that bucket's chain gets long and `get`
slows from O(1) towards O(n). Java 8 added a defence: when one bucket holds
**8** or more entries (and the table has at least **64** buckets), the chain is
converted into a **red-black tree**, a self-balancing sorted tree, which makes
the worst case O(log n). If it shrinks to 6 or fewer, it turns back into a
list. Before 64 buckets, the map resizes instead of treeifying.

### Load factor and resizing

The **load factor** (default 0.75) is how full the table may get before it
grows. With 16 buckets, the 13th entry pushes it past 12 and the table doubles.
Watch it:

```java [Resize.java]
import java.lang.reflect.Field;
import java.util.*;

public class Resize {
  public static void main(String[] args) throws Exception {
    HashMap<Integer, String> students = new HashMap<>();
    Field table = HashMap.class.getDeclaredField("table");
    table.setAccessible(true);
    int last = -1;
    for (int i = 1; i <= 100; i++) {
      students.put(1800 + i, "student" + i);
      Object[] t = (Object[]) table.get(students);
      if (t.length != last) {
        System.out.println("size " + students.size() + " -> buckets " + t.length);
        last = t.length;
      }
    }
  }
}
```

```bash [Terminal]
java --add-opens java.base/java.util=ALL-UNNAMED Resize.java
```

```text [Output]
size 1 -> buckets 16
size 13 -> buckets 32
size 25 -> buckets 64
size 49 -> buckets 128
size 97 -> buckets 256
```

As with the `ArrayList` growth demo, the reflection is only for looking
inside. The table is created on the first `put`, not in the constructor. Each
resize rehashes every entry into a table twice the size, which is expensive,
so if you know you will store 40,000 students, pass an initial capacity.

## Real use case

The exam cell needs two things every term: how many students each department
has (counting, which is `merge`), and each student's grade from their marks
using grade bands. Bands are ranges, and ranges are what **TreeMap** is for.

A `TreeMap` keeps its keys **sorted** (it is a red-black tree, the same
structure a HashMap bucket turns into) and can find the nearest key below or
above a value. `floorEntry(m)` returns the entry with the greatest key less
than or equal to `m`.

```java [GradeBands.java]
import java.util.*;

public class GradeBands {
  public static void main(String[] args) {
    // lowest mark for each grade -> grade
    TreeMap<Integer, String> bands = new TreeMap<>();
    bands.put(0, "F");
    bands.put(40, "C");
    bands.put(60, "B");
    bands.put(75, "A");
    bands.put(90, "O");

    int[] marks = {92, 75, 74, 41, 39, 0, 100};
    for (int m : marks) {
      System.out.println(m + " -> " + bands.floorEntry(m).getValue());
    }
    System.out.println("first: " + bands.firstEntry() + ", last: " + bands.lastKey());
    System.out.println("pass bands: " + bands.tailMap(40));
    System.out.println("descending: " + bands.descendingMap());
  }
}
```

```text [Output]
92 -> O
75 -> A
74 -> B
41 -> C
39 -> F
0 -> F
100 -> O
first: 0=F, last: 90
pass bands: {40=C, 60=B, 75=A, 90=O}
descending: {90=O, 75=A, 60=B, 40=C, 0=F}
```

The boundaries (75 is A, 74 is B, 39 is F) are exactly right, and the grading
policy is now data rather than an `if` chain. When the university changes the
A cutoff to 80, one `put` changes. A negative mark would make `floorEntry`
return `null`; the band at 0 is there so every valid mark finds one.

### The three Map classes, side by side

```java [MapOrders.java]
import java.util.*;

public class MapOrders {
  public static void main(String[] args) {
    String[] rolls = {"EC1807", "CS1801", "ME1803", "CS1805"};
    Map<String, Integer> hash = new HashMap<>();
    Map<String, Integer> linked = new LinkedHashMap<>();
    Map<String, Integer> tree = new TreeMap<>();
    for (int i = 0; i < rolls.length; i++) {
      hash.put(rolls[i], i);
      linked.put(rolls[i], i);
      tree.put(rolls[i], i);
    }
    System.out.println("HashMap:       " + hash);
    System.out.println("LinkedHashMap: " + linked);
    System.out.println("TreeMap:       " + tree);

    Map<String, Integer> nulls = new HashMap<>();
    nulls.put(null, 1);
    nulls.put("CS1801", null);
    System.out.println("null key and value: " + nulls + ", get(CS1801) " + nulls.get("CS1801")
        + ", containsKey " + nulls.containsKey("CS1801"));
  }
}
```

```text [Output]
HashMap:       {CS1805=3, CS1801=1, EC1807=0, ME1803=2}
LinkedHashMap: {EC1807=0, CS1801=1, ME1803=2, CS1805=3}
TreeMap:       {CS1801=1, CS1805=3, EC1807=0, ME1803=2}
null key and value: {null=1, CS1801=null}, get(CS1801) null, containsKey true
```

| | HashMap | LinkedHashMap | TreeMap | Hashtable |
| --- | --- | --- | --- | --- |
| Order | none | insertion (or access) | sorted by key | none |
| get / put | O(1) average | O(1) average | O(log n) | O(1), synchronised |
| null key | one allowed | one allowed | no | no |
| null values | yes | yes | yes | no |

Notice the last line of output: `get("CS1801")` returned `null` even though the
key exists, because its **value** is `null`. `get` returning `null` cannot tell
"missing" from "stored null"; `containsKey` can.

::real-life{title="LinkedHashMap as a cache" source="Every service that remembers recent answers"}
`new LinkedHashMap<>(16, 0.75f, true)` orders entries by most recent **access**
instead of insertion. Override its `removeEldestEntry` method to return
`size() > 100` and you have a working LRU (least recently used) cache in about
five lines. "Design an LRU cache" is a common product-company question, and
this is the Java-library answer to give first.
::

## What confuses people here

### The key that goes missing

```java [BrokenKey.java]
import java.util.*;

public class BrokenKey {
  // A key class whose hashCode depends on a field that can change.
  static class RollNumber {
    String value;
    RollNumber(String value) { this.value = value; }
    @Override public boolean equals(Object o) {
      return o instanceof RollNumber r && r.value.equals(value);
    }
    @Override public int hashCode() { return value.hashCode(); }
    @Override public String toString() { return value; }
  }

  // A key class with equals but no hashCode.
  static class HalfKey {
    final String value;
    HalfKey(String value) { this.value = value; }
    @Override public boolean equals(Object o) {
      return o instanceof HalfKey k && k.value.equals(value);
    }
  }

  public static void main(String[] args) {
    Map<RollNumber, String> results = new HashMap<>();
    RollNumber anita = new RollNumber("CS1801");
    results.put(anita, "PASS");

    anita.value = "CS1899";                  // the key changes after it was stored
    System.out.println("map:             " + results);
    System.out.println("get(anita):      " + results.get(anita));
    System.out.println("get(new CS1801): " + results.get(new RollNumber("CS1801")));
    System.out.println("size:            " + results.size());

    Map<HalfKey, String> half = new HashMap<>();
    half.put(new HalfKey("CS1801"), "PASS");
    System.out.println("equals only, get: " + half.get(new HalfKey("CS1801")));
  }
}
```

```text [Output]
map:             {CS1899=PASS}
get(anita):      null
get(new CS1801): null
size:            1
equals only, get: null
```

::code-trace{caption="Why neither lookup finds an entry that is visibly in the map."}
```java [BrokenKey.java]
results.put(anita, "PASS");
anita.value = "CS1899";
results.get(anita);
results.get(new RollNumber("CS1801"));
```

  :::code-trace-step{lines="1" caption="Stored in the bucket for the hash of CS1801."}
  :::
  :::code-trace-step{lines="2" caption="The key object changes. The entry does not move: it is still in the CS1801 bucket, now holding a key that says CS1899."}
  :::
  :::code-trace-step{lines="3" caption="Hashes CS1899, looks in that bucket, finds nothing. null."}
  :::
  :::code-trace-step{lines="4" caption="Hashes CS1801, finds the right bucket, then equals() compares CS1801 with the stored key, now CS1899. No match. null. The entry is lost for good, but still counted in size."}
  :::
::

Two rules come out of this, and they are the answers the interviewer wants:

- **Keys must be immutable** (or at least, the fields used in `equals` and
  `hashCode` must never change). That is why `String`, `Integer` and records are
  the usual keys.
- **Override both or neither.** With `equals` but no `hashCode`, two equal keys
  get different identity hash codes, land in different buckets, and `equals` is
  never even called: `HalfKey` returns `null`.

::warning{icon="i-lucide-alert-triangle"}
A `HashMap` is not thread-safe. Two threads calling `put` at once can lose
entries or corrupt a bucket. Use `ConcurrentHashMap`, covered in the
multithreading chapter.
::

## Interview questions

::accordion
  :::accordion-item{label="How does HashMap work internally?" icon="i-lucide-message-circle"}
  It is an array of buckets (16 by default). `put` calls `key.hashCode()`,
  spreads the bits with `h ^ (h >>> 16)`, and picks bucket `hash & (n - 1)`.
  In that bucket it compares with `equals()`; a match replaces the value,
  otherwise a new node is added. `get` does the same lookup. Collisions form a
  linked list, which becomes a red-black tree at 8 entries once the table has
  64 buckets. When size exceeds capacity × 0.75, the table doubles and entries
  are redistributed.
  :::
  :::accordion-item{label="What happens when two keys have the same hashCode?" icon="i-lucide-message-circle"}
  They go into the same bucket (a collision) and are both kept, chained
  together; `equals()` tells them apart on `get`. `"Aa"` and `"BB"` both hash
  to 2112 and both land in bucket 0 in `Buckets.java`. Equal hash codes do not
  mean equal keys.
  :::
  :::accordion-item{label="What if you override equals but not hashCode?" icon="i-lucide-message-circle"}
  Two equal keys usually get different hash codes, land in different buckets,
  and `equals` is never called, so `get` returns `null` for a key you know you
  stored. `HalfKey` in `BrokenKey.java` shows it. The contract: equal objects
  must have equal hash codes.
  :::
  :::accordion-item{label="Why should HashMap keys be immutable?" icon="i-lucide-message-circle"}
  The bucket is chosen from the hash code at `put` time. If the key changes
  afterwards, its hash code changes but the entry stays in the old bucket, so
  neither the old nor the new value can find it. `BrokenKey.java` loses an entry
  that still counts in `size()`.
  :::
  :::accordion-item{label="What is the load factor, and why 0.75?" icon="i-lucide-message-circle"}
  The fraction of capacity the map may fill before doubling. 0.75 is a
  trade-off: lower wastes memory on empty buckets, higher means more collisions
  and slower look-ups. With the default, 16 buckets hold 12 entries; the 13th
  triggers the resize to 32.
  :::
  :::accordion-item{label="HashMap or TreeMap?" icon="i-lucide-message-circle"}
  `HashMap` for plain look-ups: O(1), no order. `TreeMap` when you need keys in
  sorted order or range questions (`floorEntry`, `headMap`, `tailMap`), at
  O(log n), with no null keys. `GradeBands.java` is a TreeMap job.
  :::
::
