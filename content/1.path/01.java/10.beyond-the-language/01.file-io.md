Your thread pool can now process four thousand results at once, safely, into a
`ConcurrentHashMap`. Then the program exits and every one of those results is
gone. The simplest place to keep data after the program stops is a file, and
that is this lesson.

## Why this matters in a job

Files are everywhere in back-office Java work: the CSV of results the exam cell
uploads, the report a batch job writes every night, the log file you read when
something breaks, the configuration file an application reads at start-up. A
fresher who can read a file line by line, skip the bad rows and write a clean
output is useful from the first week.

In interviews this topic produces a short, predictable list: `FileReader`
against `BufferedReader`, what try-with-resources does, what `transient` means,
and what serialisation is. All four are below.

## A file is a notebook the program keeps in the office

Everything so far lived in memory, which is like working on a whiteboard: fast,
and wiped when the lights go off. A file is the notebook in the drawer. Writing
to it is slower, but it is still there tomorrow, and anyone else (Excel, another
program, you) can open it.

Java has two generations of file code, and you will meet both:

- **`java.io`** (since Java 1.0): `File`, `FileReader`, `FileWriter`,
  `BufferedReader`, `BufferedWriter`, `ObjectOutputStream`. Most old code and
  most institute notes use these.
- **`java.nio.file`** (since Java 7): `Path` for a location and `Files` for
  the operations. Shorter, better error messages, and what new code uses.

A **stream** here means a flow of bytes or characters that you read from or
write to in order, one piece after another (not the Java 8 Streams from the
previous chapter, although `Files.lines` joins the two). A **buffer** is a block
of memory that collects many small reads or writes so the program talks to the
disk in large chunks instead of one character at a time.

## Syntax

```java
Path file = Path.of("students.csv");               // a location, not the file itself
Files.write(file, listOfLines);                     // create or overwrite
Files.writeString(file, text, StandardOpenOption.APPEND);
List<String> lines = Files.readAllLines(file);      // whole file into memory
BufferedReader reader = Files.newBufferedReader(file);   // one line at a time
```

Every one of these can fail (the file is missing, the disk is full, you have no
permission), so each throws `IOException`, a **checked** exception. You must
catch it or declare `throws IOException`.

```java [WriteAndRead.java]
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardOpenOption;
import java.util.List;

public class WriteAndRead {
  public static void main(String[] args) throws IOException {
    Path file = Path.of("students.csv");

    List<String> rows = List.of(
        "rollNumber,name,marks",
        "1801,Anita Rao,78",
        "1802,Vikram Shah,64",
        "1803,Farah Khan,92");
    Files.write(file, rows);                     // creates or overwrites

    System.out.println("Exists: " + Files.exists(file));
    System.out.println("Size:   " + Files.size(file) + " bytes");

    List<String> lines = Files.readAllLines(file);   // the whole file, in memory
    for (String line : lines) {
      System.out.println(line);
    }

    Files.writeString(file, "1804,Rohit Das,55\n",
        StandardOpenOption.APPEND);                  // add to the end
    System.out.println("Lines now: " + Files.readAllLines(file).size());
  }
}
```

```bash [Terminal]
javac WriteAndRead.java && java WriteAndRead
```

```text [Output]
Exists: true
Size:   79 bytes
rollNumber,name,marks
1801,Anita Rao,78
1802,Vikram Shah,64
1803,Farah Khan,92
Lines now: 5
```

The file appears in whatever folder you ran `java` from (the **working
directory**), not next to the `.java` file. A relative path is always relative
to where the program was started, which is the first thing to check when a
program "cannot find" a file that is plainly there.

Forget the `throws IOException` and the compiler stops you:

```text [Output]
NoThrows.java:6: error: unreported exception IOException; must be caught or declared to be thrown
    Files.readAllLines(Path.of("students.csv"));
                      ^
1 error
```

And a missing file, caught properly, names itself:

```text [Output]
Could not read: java.nio.file.NoSuchFileException: results-2026.csv
```

### Line by line, for files that do not fit in memory

`readAllLines` loads everything at once. A results file for one college is
fine; a year of attendance logs for a university might be gigabytes. For
those, read one line at a time with a `BufferedReader`: `readLine()` returns the
next line, or `null` at the end of the file.

::flow{direction="horizontal" caption="How a BufferedReader reads. The disk is visited in large blocks; your code sees one line at a time."}
  :::flow-step{label="Disk" icon="i-lucide-hard-drive"}
  Slow. Every visit costs time.
  :::
  :::flow-step{label="Buffer (8 KB)" icon="i-lucide-layers" highlight}
  Filled in one large read, then served from memory.
  :::
  :::flow-step{label="readLine()" icon="i-lucide-text"}
  Hands you the next line, or null at the end.
  :::
::

## Real use case

The exam cell hands you `students.csv`. Some rows are fine, one says `absent`
instead of a mark, and one is missing a column entirely. The job: write every
student at or above 75 to `toppers.csv`, skip the bad rows without crashing, and
report what happened.

```text [students.csv]
rollNumber,name,marks
1801,Anita Rao,78
1802,Vikram Shah,64
1803,Farah Khan,92
1804,Rohit Das,absent
1805,Meera Iyer,75
1806,broken row
```

```java [Toppers.java]
import java.io.BufferedReader;
import java.io.BufferedWriter;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class Toppers {
  public static void main(String[] args) throws IOException {
    Path input = Path.of("students.csv");
    Path output = Path.of("toppers.csv");
    int cutoff = 75;
    int read = 0, written = 0, skipped = 0;

    try (BufferedReader reader = Files.newBufferedReader(input);
         BufferedWriter writer = Files.newBufferedWriter(output)) {

      String header = reader.readLine();          // skip the header row
      writer.write(header);
      writer.newLine();

      String line;
      while ((line = reader.readLine()) != null) { // null means end of file
        read++;
        String[] parts = line.split(",");
        if (parts.length != 3) { skipped++; continue; }
        int marks;
        try {
          marks = Integer.parseInt(parts[2].trim());
        } catch (NumberFormatException e) {
          skipped++;
          continue;
        }
        if (marks >= cutoff) {
          writer.write(line);
          writer.newLine();
          written++;
        }
      }
    }                                               // both closed here, in reverse order

    System.out.println("Read " + read + ", wrote " + written + ", skipped " + skipped);
    Files.readAllLines(output).forEach(System.out::println);
  }
}
```

```text [Output]
Read 6, wrote 3, skipped 2
rollNumber,name,marks
1801,Anita Rao,78
1803,Farah Khan,92
1805,Meera Iyer,75
```

::real-life{title="What happens on real files" source="Every data import you will ever write"}
Real files are dirty: a trailing space, a blank last line, a name with a comma
in it ("Rao, Anita"), a mark typed as `7 8`. The shape above (count read,
written and skipped; never crash on one row; print a summary) is the shape every
import job takes. For quoted commas, real code uses a CSV library such as
OpenCSV or Apache Commons CSV rather than `split(",")`.
::

### The Java 8 version

`Files.lines` returns a lazy `Stream<String>`, reading lines only as the stream
asks for them. It must be closed, so it also goes in try-with-resources.

```java [Streamed.java]
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.stream.Stream;

public class Streamed {
  public static void main(String[] args) throws IOException {
    try (Stream<String> lines = Files.lines(Path.of("students.csv"))) {
      double average = lines.skip(1)
          .mapToInt(line -> Integer.parseInt(line.split(",")[2]))
          .average()
          .orElse(0);
      System.out.printf("Average marks: %.2f%n", average);
    }
  }
}
```

```text [Output]
Average marks: 77.25
```

(Run on a clean four-student file: 78, 64, 92 and 75.)

### Serialisation, and transient

**Serialisation** turns a whole object into bytes so it can be written to a file
or sent over a network; **deserialisation** turns the bytes back into an
object. The class must implement the `Serializable` marker interface. A field
marked **`transient`** is left out.

```java [SaveStudent.java]
import java.io.*;

public class SaveStudent {
  static class Student implements Serializable {
    private static final long serialVersionUID = 1L;
    String name;
    int marks;
    transient String password;               // never written to the file
    Student(String name, int marks, String password) {
      this.name = name; this.marks = marks; this.password = password;
    }
  }

  public static void main(String[] args) throws Exception {
    Student s = new Student("Anita Rao", 78, "secret123");
    try (ObjectOutputStream out = new ObjectOutputStream(new FileOutputStream("anita.ser"))) {
      out.writeObject(s);
    }
    try (ObjectInputStream in = new ObjectInputStream(new FileInputStream("anita.ser"))) {
      Student back = (Student) in.readObject();
      System.out.println(back.name + ", " + back.marks + ", password = " + back.password);
    }
  }
}
```

```text [Output]
Anita Rao, 78, password = null
```

`serialVersionUID` is a version number for the class. If the class changes and
the number does not match the one in the file, reading throws
`InvalidClassException`.

::side-note{kind="security"}
Java serialisation is asked about in interviews and avoided in new code.
Deserialising bytes from an untrusted source has been the cause of serious
security holes, because reading an object can run code. Modern systems save
data as JSON (with a library such as Jackson) or in a database.
::

## What confuses people here

::compare{caption="Closing a file: the version from old notes and the one to write."}
  :::compare-side{label="Manual close" verdict="wrong"}
  ```java
  BufferedWriter w = Files.newBufferedWriter(out);
  w.write("1801,Anita Rao,78");
  w.close();
  ```
  If `write` throws, `close` never runs. Worse, a `BufferedWriter` holds data in
  its buffer until it is flushed or closed, so a writer that is never closed can
  leave an **empty file**, with no error anywhere.
  :::
  :::compare-side{label="try-with-resources" verdict="right"}
  ```java
  try (BufferedWriter w = Files.newBufferedWriter(out)) {
    w.write("1801,Anita Rao,78");
  }
  ```
  Closed (and therefore flushed) when the block ends, however it ends.
  :::
::

- **`Files.write` overwrites.** Running it twice does not give two copies of the
  data; pass `StandardOpenOption.APPEND` to add to the end.
- **Relative paths are relative to where you ran `java`**, not to the source
  file and not to the project folder your IDE shows.
- **`FileReader` uses the platform's default character set** on older Java
  versions, so a file with ₹ or a Hindi name could be garbled on one machine
  and fine on another. `Files.newBufferedReader` uses UTF-8 by default; since
  Java 18 the default everywhere is UTF-8.
- **`readLine()` strips the line ending.** Writing back with `write(line)` and
  no `newLine()` joins every row into one.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between FileReader and BufferedReader?" icon="i-lucide-message-circle"}
  `FileReader` reads characters from a file, and each `read()` can go to the
  disk. `BufferedReader` wraps another reader, reads large blocks (8 KB by
  default) into memory and serves from there, and adds `readLine()`. You wrap
  one in the other: `new BufferedReader(new FileReader("students.csv"))`, or
  use `Files.newBufferedReader(path)`, which gives you the buffered one directly.
  :::
  :::accordion-item{label="What does try-with-resources do?" icon="i-lucide-message-circle"}
  It closes every resource declared in its brackets when the block ends,
  normally or through an exception, in the reverse order of declaration. The
  resource must implement `AutoCloseable`. In `Toppers.java` the writer is closed
  and flushed first, then the reader.
  :::
  :::accordion-item{label="What is serialisation, and what does transient do?" icon="i-lucide-message-circle"}
  Serialisation converts an object into a byte stream (`ObjectOutputStream.writeObject`)
  so it can be saved or sent; deserialisation rebuilds it. The class must
  implement `Serializable`. A `transient` field is skipped and comes back with
  its default value, which is why `password` printed `null`. `static` fields are
  not serialised either, because they belong to the class, not the object.
  :::
  :::accordion-item{label="Why does reading a file throw a checked exception?" icon="i-lucide-message-circle"}
  Because the failure is outside your code's control and the caller can do
  something about it: the file may be missing, locked or unreadable. The compiler
  forces you to decide, which is why `NoThrows.java` fails with `unreported
  exception IOException`.
  :::
  :::accordion-item{label="How would you read a 5 GB log file?" icon="i-lucide-message-circle"}
  Not with `readAllLines`, which would try to hold it all in memory and throw
  `OutOfMemoryError`. Read it line by line with a `BufferedReader`, or with
  `Files.lines(path)` inside try-with-resources, and process each line as it
  arrives, keeping only the totals you need.
  :::
::
