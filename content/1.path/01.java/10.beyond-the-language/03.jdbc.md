Files keep data for one program. The college has thousands of students, several
offices changing records at the same moment, and questions such as "every CSE
student at or above 60, highest first". That is a database's job, and **JDBC**
(Java Database Connectivity) is the standard way a Java program talks to one.

## Why this matters in a job

Almost every Java job is a Java program in front of a database. Most teams use
Spring and JPA/Hibernate on top, which write the JDBC calls for you, but
underneath every one of those frameworks is exactly the code in this lesson, and
when something goes wrong (a connection leak, a slow query, a transaction that
did not roll back) you debug it at this level.

At the institute, JDBC was the module that joined the Java half of the course to
the SQL half, and in walk-in technical rounds it is the bridge question: "how
do you connect Java to a database?", "Statement or PreparedStatement?", "what
is SQL injection?", "how do you handle a transaction in JDBC?". Every one is
answered below with code that ran.

## JDBC is a set of plugs, and the driver is the adapter

Think of the phone charger you carried from home to Bangalore. The phone expects
one kind of plug; the wall socket in the PG is a different shape. The adapter
in between makes them fit. JDBC is the phone's side: one set of interfaces
(`Connection`, `PreparedStatement`, `ResultSet`) that your code is written
against. Each database (MySQL, PostgreSQL, Oracle, H2) ships a **driver**, a jar
that implements those interfaces for its own wire protocol. Change the database
and you change the driver jar and the URL; your code barely moves.

::flow{numbered direction="horizontal" caption="Every JDBC program has these five steps."}
  :::flow-step{label="Driver on the classpath" icon="i-lucide-plug"}
  The database vendor's jar. Found automatically since JDBC 4.
  :::
  :::flow-step{label="Connection" icon="i-lucide-link"}
  `DriverManager.getConnection(url, user, password)`.
  :::
  :::flow-step{label="PreparedStatement" icon="i-lucide-file-code" highlight}
  SQL with `?` placeholders, values set separately.
  :::
  :::flow-step{label="Execute" icon="i-lucide-play"}
  `executeQuery` for SELECT, `executeUpdate` for INSERT, UPDATE, DELETE.
  :::
  :::flow-step{label="ResultSet, then close" icon="i-lucide-table"}
  Read rows with `next()`. Close everything, in reverse order.
  :::
::

The examples use **H2**, a small database written in Java that can run inside
your program, in memory, with nothing to install. The JDBC code is identical for
MySQL; only the URL and the driver jar change:

| Database | JDBC URL | Driver jar |
| --- | --- | --- |
| H2 (in memory) | `jdbc:h2:mem:college` | `h2-2.2.224.jar` |
| MySQL | `jdbc:mysql://localhost:3306/college` | `mysql-connector-j-8.x.jar` |
| PostgreSQL | `jdbc:postgresql://localhost:5432/college` | `postgresql-42.x.jar` |
| Oracle | `jdbc:oracle:thin:@localhost:1521:XE` | `ojdbc11.jar` |

## Syntax

```java
try (Connection conn = DriverManager.getConnection(url, user, password);
     PreparedStatement ps = conn.prepareStatement("SELECT name FROM students WHERE marks >= ?")) {
  ps.setInt(1, 60);                         // placeholders are numbered from 1
  try (ResultSet rs = ps.executeQuery()) {
    while (rs.next()) {                     // false when there are no more rows
      String name = rs.getString("name");
    }
  }
}
```

A complete program: create a table, insert four students, query them, update
one.

```java [StudentsDb.java]
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;

public class StudentsDb {
  static final String URL = "jdbc:h2:mem:college";   // an in-memory database

  public static void main(String[] args) throws SQLException {
    try (Connection conn = DriverManager.getConnection(URL, "sa", "")) {
      System.out.println("Connected to " + conn.getMetaData().getDatabaseProductName());

      try (Statement st = conn.createStatement()) {
        st.executeUpdate("""
            CREATE TABLE students (
              roll_number INT PRIMARY KEY,
              name        VARCHAR(100) NOT NULL,
              department  VARCHAR(10)  NOT NULL,
              marks       INT
            )""");
      }

      String insert = "INSERT INTO students (roll_number, name, department, marks) VALUES (?, ?, ?, ?)";
      try (PreparedStatement ps = conn.prepareStatement(insert)) {
        Object[][] rows = {
          {1801, "Anita Rao", "CSE", 78},
          {1802, "Vikram Shah", "ECE", 64},
          {1803, "Farah Khan", "CSE", 92},
          {1804, "Rohit Das", "CSE", 55}
        };
        for (Object[] r : rows) {
          ps.setInt(1, (Integer) r[0]);
          ps.setString(2, (String) r[1]);
          ps.setString(3, (String) r[2]);
          ps.setInt(4, (Integer) r[3]);
          ps.executeUpdate();
        }
        System.out.println("Inserted " + rows.length + " students");
      }

      String query = "SELECT roll_number, name, marks FROM students WHERE department = ? AND marks >= ? ORDER BY marks DESC";
      try (PreparedStatement ps = conn.prepareStatement(query)) {
        ps.setString(1, "CSE");
        ps.setInt(2, 60);
        try (ResultSet rs = ps.executeQuery()) {
          while (rs.next()) {                       // move to the next row; false when none left
            System.out.printf("%d  %-10s %d%n",
                rs.getInt("roll_number"), rs.getString("name"), rs.getInt("marks"));
          }
        }
      }

      try (PreparedStatement ps = conn.prepareStatement("UPDATE students SET marks = marks + ? WHERE roll_number = ?")) {
        ps.setInt(1, 5);
        ps.setInt(2, 1804);
        int changed = ps.executeUpdate();
        System.out.println("Rows updated: " + changed);
      }
    }
  }
}
```

The driver jar must be on the **classpath** (the list of places Java looks for
classes) at compile and run time:

```bash [Terminal]
javac -cp h2-2.2.224.jar StudentsDb.java
java -cp h2-2.2.224.jar:. StudentsDb        # on Windows, use ; instead of :
```

```text [Output]
Connected to H2
Inserted 4 students
1803  Farah Khan 92
1801  Anita Rao  78
Rows updated: 1
```

Forget the jar and the error does not say "jar missing":

```text [Output]
Exception in thread "main" java.sql.SQLException: No suitable driver found for jdbc:h2:mem:college
	at java.sql/java.sql.DriverManager.getConnection(DriverManager.java:708)
```

::side-note{kind="go-deeper"}
Older notes start with `Class.forName("com.mysql.jdbc.Driver");`. That line
loaded the driver class so it could register itself with `DriverManager`. Since
JDBC 4 (Java 6), drivers register automatically through a file inside their jar,
so the line is unnecessary. Interviewers still ask what it did.
::

The three `execute` methods:

- `executeQuery(sql)` for `SELECT`: returns a `ResultSet`.
- `executeUpdate(sql)` for `INSERT`, `UPDATE`, `DELETE` and `CREATE`: returns
  the number of rows changed (0 for `CREATE`).
- `execute(sql)` for anything: returns `true` if the result is a `ResultSet`.
  Rarely needed.

## Real use case

### SQL injection, shown working

The student portal has a search box. A developer builds the SQL by gluing the
typed text into a string and runs it with a plain `Statement`. Here is what an
attacker types, and what comes back.

```java [Injection.java]
import java.sql.*;

public class Injection {
  public static void main(String[] args) throws SQLException {
    try (Connection conn = DriverManager.getConnection("jdbc:h2:mem:college", "sa", "")) {
      try (Statement st = conn.createStatement()) {
        st.executeUpdate("CREATE TABLE students (roll_number INT PRIMARY KEY, name VARCHAR(100), marks INT)");
        st.executeUpdate("INSERT INTO students VALUES (1801, 'Anita Rao', 78), (1802, 'Vikram Shah', 64), (1803, 'Farah Khan', 92)");
      }

      String typedByUser = "Nobody' OR '1'='1";      // what an attacker types in the search box

      // WRONG: gluing user input into the SQL text
      String sql = "SELECT name, marks FROM students WHERE name = '" + typedByUser + "'";
      System.out.println("SQL sent: " + sql);
      try (Statement st = conn.createStatement(); ResultSet rs = st.executeQuery(sql)) {
        while (rs.next()) System.out.println("  leaked: " + rs.getString("name") + " " + rs.getInt("marks"));
      }

      // RIGHT: a placeholder; the input is sent as data, never as SQL
      try (PreparedStatement ps = conn.prepareStatement("SELECT name, marks FROM students WHERE name = ?")) {
        ps.setString(1, typedByUser);
        try (ResultSet rs = ps.executeQuery()) {
          int found = 0;
          while (rs.next()) found++;
          System.out.println("PreparedStatement found " + found + " rows");
        }
      }
    }
  }
}
```

```text [Output]
SQL sent: SELECT name, marks FROM students WHERE name = 'Nobody' OR '1'='1'
  leaked: Anita Rao 78
  leaked: Vikram Shah 64
  leaked: Farah Khan 92
PreparedStatement found 0 rows
```

The quote in the input closed the string early, and `OR '1'='1'` is true for
every row, so the search returned every student's marks. With a different input
it could have been `'; DROP TABLE students; --`. That is **SQL injection**.

::compare{caption="The single most important rule in this lesson."}
  :::compare-side{label="Statement with concatenation" verdict="wrong"}
  ```java
  "... WHERE name = '" + input + "'"
  ```
  The input becomes part of the SQL. Anything the user types can change what
  the query means.
  :::
  :::compare-side{label="PreparedStatement with ?" verdict="right"}
  ```java
  "... WHERE name = ?"
  ps.setString(1, input);
  ```
  The SQL is sent and compiled first; the value is sent separately as data. It
  can never become SQL, whatever it contains.
  :::
::

### A transaction: pay a fee, both steps or neither

Paying a fee is two writes: record the fee as received, and take the money from
the student's wallet. If the second fails, the first must be undone, or the
college has a receipt for money it never got. By default JDBC **auto-commits**:
every statement is permanent the moment it runs. For a group of statements that
must succeed or fail together (a **transaction**), turn auto-commit off, then
`commit()` or `rollback()`.

```java [FeeTransfer.java]
import java.sql.*;

public class FeeTransfer {
  public static void main(String[] args) throws SQLException {
    try (Connection conn = DriverManager.getConnection("jdbc:h2:mem:college", "sa", "")) {
      try (Statement st = conn.createStatement()) {
        st.executeUpdate("CREATE TABLE wallets (roll_number INT PRIMARY KEY, "
            + "balance_paise BIGINT, CONSTRAINT no_negative_balance CHECK (balance_paise >= 0))");
        st.executeUpdate("CREATE TABLE fees_received (roll_number INT, amount_paise BIGINT)");
        st.executeUpdate("INSERT INTO wallets VALUES (1801, 5000000), (1802, 100000)");
      }

      pay(conn, 1801, 4_500_000);   // Rs 50,000 in the wallet: works
      pay(conn, 1802, 4_500_000);   // Rs 1,000 in the wallet: must undo everything
      print(conn);
    }
  }

  static void pay(Connection conn, int roll, long amountPaise) throws SQLException {
    conn.setAutoCommit(false);                      // start a transaction
    try (PreparedStatement receive = conn.prepareStatement(
             "INSERT INTO fees_received VALUES (?, ?)");
         PreparedStatement debit = conn.prepareStatement(
             "UPDATE wallets SET balance_paise = balance_paise - ? WHERE roll_number = ?")) {
      receive.setInt(1, roll);
      receive.setLong(2, amountPaise);
      receive.executeUpdate();                      // step 1: record the fee as received

      debit.setLong(1, amountPaise);
      debit.setInt(2, roll);
      debit.executeUpdate();                        // step 2: take it from the wallet

      conn.commit();                                // both steps become permanent
      System.out.println(roll + ": paid, committed");
    } catch (SQLException e) {
      conn.rollback();                              // step 1 is undone too
      System.out.println(roll + ": failed, rolled back. " + e.getMessage().lines().findFirst().orElse(""));
    } finally {
      conn.setAutoCommit(true);
    }
  }

  static void print(Connection conn) throws SQLException {
    try (Statement st = conn.createStatement()) {
      try (ResultSet rs = st.executeQuery("SELECT * FROM wallets ORDER BY roll_number")) {
        while (rs.next()) System.out.println(rs.getInt(1) + " wallet Rs " + rs.getLong(2) / 100);
      }
      try (ResultSet rs = st.executeQuery("SELECT COUNT(*) FROM fees_received")) {
        rs.next();
        System.out.println("Fee receipts recorded: " + rs.getInt(1));
      }
    }
  }
}
```

```text [Output]
1801: paid, committed
1802: failed, rolled back. Check constraint violation: "NO_NEGATIVE_BALANCE: "; SQL statement:
1801 wallet Rs 5000
1802 wallet Rs 1000
Fee receipts recorded: 1
```

Student 1802's receipt was inserted (step 1) before the wallet update failed
(step 2). The rollback removed it: one receipt in the table, not two. Money is
stored in paise as a `long`, for the reason in the primitives lesson.

::real-life{title="Connection pools" source="Every Java web application"}
Opening a database connection takes tens of milliseconds (a network handshake
and a login). A web application serving hundreds of requests a second cannot
open one per request. It keeps a **connection pool**: a set of open connections
that requests borrow and give back. **HikariCP** is the default in Spring Boot.
Your code still calls `getConnection()` and `close()`; with a pool, `close()`
returns the connection to the pool instead of closing it. That is also why a
connection you forget to close is a **leak**: after the pool's ten connections
are all borrowed and never returned, every request waits and then times out.
::

## What confuses people here

- **Column indexes start at 1, not 0.** `ps.setInt(1, ...)` is the first `?`,
  and `rs.getInt(1)` is the first column. It is the one place in Java where
  counting starts at 1.
- **A `ResultSet` starts before the first row.** You must call `rs.next()`
  before reading anything, even when you expect exactly one row. Reading first
  throws `SQLException`.
- **`rs.getInt` on a SQL `NULL` returns 0**, not null. Call `rs.wasNull()` after
  it, or use `rs.getObject("marks", Integer.class)`, which returns `null`. A
  student with no marks yet is not a student who scored 0.
- **Close everything.** Connections, statements and result sets hold resources
  on the database server. try-with-resources closes them in reverse order even
  when an exception is thrown.
- **A `?` is for values only.** You cannot use a placeholder for a table or
  column name (`SELECT * FROM ?` fails). If a column name comes from the user,
  check it against a fixed list.
- **`SQLException` is checked**, so every JDBC method forces you to handle or
  declare it. Frameworks such as Spring wrap it in an unchecked exception.

## Interview questions

::accordion
  :::accordion-item{label="What are the steps to connect Java to a database?" icon="i-lucide-message-circle"}
  Put the driver jar on the classpath; get a `Connection` with
  `DriverManager.getConnection(url, user, password)`; create a
  `PreparedStatement`; set its parameters and execute it; read the `ResultSet`
  with `next()`; close all three, best with try-with-resources. `StudentsDb.java`
  does exactly this.
  :::
  :::accordion-item{label="Statement or PreparedStatement?" icon="i-lucide-message-circle"}
  `PreparedStatement`, nearly always. It prevents SQL injection because values
  are sent separately from the SQL (`Injection.java` leaked three rows with
  `Statement` and found zero with `PreparedStatement`). It is also compiled once
  by the database and can be reused with different values, and it handles
  quoting and dates for you. `Statement` is fine only for fixed SQL with no user
  input, such as `CREATE TABLE`.
  :::
  :::accordion-item{label="What is SQL injection and how do you prevent it?" icon="i-lucide-message-circle"}
  User input that changes the meaning of a SQL statement because it was
  concatenated into the SQL text. Typing `Nobody' OR '1'='1` turned a
  one-student search into an every-student search. Prevent it with
  `PreparedStatement` placeholders, never string concatenation, and a fixed
  list for anything that cannot be a placeholder (table and column names).
  :::
  :::accordion-item{label="How do you manage a transaction in JDBC?" icon="i-lucide-message-circle"}
  `conn.setAutoCommit(false)`, run the statements, `conn.commit()` if all
  succeed, `conn.rollback()` in the `catch` if any fail, and restore
  auto-commit in `finally`. In `FeeTransfer.java` the failed payment's receipt
  was rolled back, so only one receipt remained.
  :::
  :::accordion-item{label="What is the difference between executeQuery, executeUpdate and execute?" icon="i-lucide-message-circle"}
  `executeQuery` runs a `SELECT` and returns a `ResultSet`. `executeUpdate` runs
  `INSERT`, `UPDATE`, `DELETE` or DDL and returns the number of rows changed
  (`Rows updated: 1` above). `execute` runs anything and returns `true` if there
  is a `ResultSet` to read.
  :::
  :::accordion-item{label="What is a connection pool and why use one?" icon="i-lucide-message-circle"}
  A set of already-open connections that code borrows and returns, because
  opening a connection is slow. HikariCP is the common one. With a pool,
  `close()` returns the connection rather than closing it, which is why a
  forgotten `close()` exhausts the pool and freezes the application.
  :::
::
