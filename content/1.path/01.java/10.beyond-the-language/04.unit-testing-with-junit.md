Every program in this track was checked by running it and reading the output by
eye. That works once. It does not work next month, when you change the fee
code and need to know that the attendance rule, which you did not touch, still
works. A **unit test** is a small program that runs a piece of your program and
complains loudly if the answer is wrong.

## Why this matters in a job

Every real codebase has tests, and a pull request without them is usually sent
back. In many teams the build refuses to deploy if one test fails. You will be
expected to run the tests before pushing from your first week, and to write them
soon after.

In interviews, "how do you test your code?" comes up at every level, and
freshers who answer with anything more than "I run it and check" stand out. A
few JUnit tests in a GitHub project are a visible signal that almost no fresher
has.

## A test is the answer key the examiner keeps

When the exam cell marks papers, the examiner does not work out each answer
fresh for every script. There is an answer key, written once, and every script
is checked against it. A unit test is an answer key for one method: "given 18
out of 24 classes, the answer must be 75.0". Change the method, run the tests,
and every answer is checked again in milliseconds.

- A **unit** is the smallest piece worth testing on its own, usually one method.
- **JUnit** is the standard Java testing library. The current version, JUnit 5,
  is also called **JUnit Jupiter**.
- An **assertion** is a check: `assertEquals(expected, actual)`. If it is false,
  the test fails and says what it expected and what it got.

Every test has the same three parts, called **arrange, act, assert**:

::flow{numbered direction="horizontal" caption="Arrange, act, assert. A test with two act steps is two tests."}
  :::flow-step{label="Arrange" icon="i-lucide-settings"}
  Set up exactly the situation being tested: 18 attended, 24 held.
  :::
  :::flow-step{label="Act" icon="i-lucide-play" highlight}
  One call to the thing under test.
  :::
  :::flow-step{label="Assert" icon="i-lucide-check"}
  State what must be true about the result.
  :::
::

## Syntax

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class AttendanceTest {
  @Test                                   // marks a method as a test
  void calculatesAStraightforwardPercentage() {
    assertEquals(75.0, Attendance.percentage(18, 24), 0.001);
  }
}
```

The annotations and assertions you will use most:

| Annotation / method | What it does |
| --- | --- |
| `@Test` | This method is a test. |
| `@BeforeEach` / `@AfterEach` | Runs before / after every test, for setup and clean-up. |
| `@BeforeAll` / `@AfterAll` | Runs once for the class. The method must be `static`. |
| `@ParameterizedTest` + `@CsvSource` | One test, run once per row of inputs. |
| `@DisplayName("...")` | A readable name in the report. |
| `@Disabled` | Skip this test (say why). |
| `assertEquals(expected, actual)` | Equal, using `equals`. For doubles, pass a tolerance. |
| `assertTrue` / `assertFalse` | The condition holds / does not hold. |
| `assertNull` / `assertNotNull` | Checks for null. |
| `assertThrows(Type.class, () -> ...)` | The code must throw this exception; returns it. |

Here is the code under test. The rule: attendance is a percentage rounded to one
decimal place, and a student **below** 75% may not sit the exam.

```java [Attendance.java]
public class Attendance {
  /** Percentage of classes attended, rounded to one decimal place. */
  public static double percentage(int attended, int held) {
    if (held <= 0) {
      throw new IllegalArgumentException("No classes held yet: " + held);
    }
    if (attended < 0 || attended > held) {
      throw new IllegalArgumentException("Attended " + attended + " of " + held);
    }
    return Math.round(attended * 1000.0 / held) / 10.0;
  }

  /** Below 75% may not sit the exam. Exactly 75% may. */
  public static boolean isShort(int attended, int held) {
    return attended * 100 < 75 * held;
  }
}
```

And the tests:

```java [AttendanceTest.java]
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;

import static org.junit.jupiter.api.Assertions.*;

class AttendanceTest {

  @Test
  void calculatesAStraightforwardPercentage() {
    // Arrange
    int attended = 18, held = 24;
    // Act
    double result = Attendance.percentage(attended, held);
    // Assert
    assertEquals(75.0, result, 0.001);
  }

  @Test
  void roundsToOneDecimalPlace() {
    assertEquals(66.7, Attendance.percentage(2, 3), 0.001);
  }

  @Test
  void exactlySeventyFivePercentIsNotShort() {
    assertFalse(Attendance.isShort(18, 24), "the rule is BELOW 75%, so 75% may sit the exam");
  }

  @Test
  void oneClassUnderIsShort() {
    assertTrue(Attendance.isShort(17, 24));          // 70.8%
  }

  @Test
  void rejectsMoreAttendedThanHeld() {
    IllegalArgumentException e = assertThrows(IllegalArgumentException.class,
        () -> Attendance.percentage(25, 24));
    assertEquals("Attended 25 of 24", e.getMessage());
  }

  @Test
  void rejectsZeroClassesHeld() {
    assertThrows(IllegalArgumentException.class, () -> Attendance.percentage(0, 0));
  }

  @ParameterizedTest(name = "{0} of 40 classes -> short = {1}")
  @CsvSource({
      "40, false",
      "30, false",
      "29, true",
      "0,  true"
  })
  void shortageAtEachBoundary(int attended, boolean expectedShort) {
    assertEquals(expectedShort, Attendance.isShort(attended, 40));
  }
}
```

At work, Maven or Gradle downloads JUnit and runs `mvn test` for you. To see
what happens underneath, you can run it from the terminal with JUnit's
standalone jar (`junit-platform-console-standalone`, one download from Maven
Central):

```bash [Terminal]
javac -d out -cp junit-platform-console-standalone-1.10.2.jar Attendance.java AttendanceTest.java
java -jar junit-platform-console-standalone-1.10.2.jar execute --class-path out --scan-class-path --details=tree
```

::pull-quote
The name of a test is documentation that cannot go out of date. Not `test1`.
`exactlySeventyFivePercentIsNotShort` tells the next reader the rule, and when it
fails, the report names the broken rule.
::

## Real use case

### Watch a test fail before you trust it

This is the step everybody skips, and it is the most important one. Break the
code on purpose. A colleague "tidies" `isShort` and changes `<` to `<=`:

```java
return attended * 100 <= 75 * held;        // was <
```

Run the same tests:

```text [Output]
│     ├─ shortageAtEachBoundary(int, boolean) ✔
│     │  ├─ 40 of 40 classes -> short = false ✔
│     │  ├─ 30 of 40 classes -> short = false ✘ expected: <false> but was: <true>
│     │  ├─ 29 of 40 classes -> short = true ✔
│     │  └─ 0 of 40 classes -> short = true ✔
│     ├─ calculatesAStraightforwardPercentage() ✔
│     ├─ oneClassUnderIsShort() ✔
│     ├─ exactlySeventyFivePercentIsNotShort() ✘ the rule is BELOW 75%, so 75% may sit the exam ==> expected: <false> but was: <true>
...
    => org.opentest4j.AssertionFailedError: the rule is BELOW 75%, so 75% may sit the exam ==> expected: <false> but was: <true>
       AttendanceTest.exactlySeventyFivePercentIsNotShort(AttendanceTest.java:26)
...
[         8 tests successful      ]
[         2 tests failed          ]
```

Two tests caught it, and both are **boundary** tests: exactly 75%. The tests
with comfortable values (40 of 40, 0 of 40) passed happily with the bug in
place. Without the boundary tests, every student on exactly 75% would have been
barred from the exam, and the first you would hear of it is a parent on the
phone to the principal.

::warning{icon="i-lucide-alert-triangle"}
A test that has never failed proves nothing. It might assert something that is
always true, test the wrong method, or not run at all. Break the code, watch it
go red, put it back, watch it go green. Thirty seconds, and it is the only thing
that makes the test worth having.
::

### What to test: the boundaries

Do not test that 90% is above 75%. Test the places where the rule changes.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-move-horizontal" title="Exactly at the boundary"}
  30 of 40, 18 of 24. The value that produces a telephone call, and the one the
  first draft of the test never contains.
  :::
  :::feature{icon="i-lucide-circle-slash" title="Empty or zero"}
  No classes held. Should it return 0, 100 or throw? Writing the test forces the
  decision.
  :::
  :::feature{icon="i-lucide-circle-dot" title="One"}
  A surprising number of loops and averages are wrong at exactly one element.
  :::
  :::feature{icon="i-lucide-ban" title="Invalid"}
  25 attended of 24 held. `assertThrows` proves the method refuses it, and
  checking the message proves it refuses for the right reason.
  :::
::

::real-life{title="Where tests run at work" source="Every team with a build pipeline"}
Tests run in three places: in your IDE while you work, with `mvn test` before
you push, and on the build server (Jenkins, GitHub Actions, GitLab CI) for every
pull request. A red build blocks the merge. That is why the tests you write are
not for you; they are for the person who changes your code in six months.
::

## What confuses people here

::compare{caption="Two tests. One of them is worse than nothing."}
  :::compare-side{label="Testing the language" verdict="wrong"}
  ```java
  @Test void getterReturnsTheName() {
    Student s = new Student("Anita Rao");
    assertEquals("Anita Rao", s.getName());
  }
  ```
  This tests that assignment works. It will never fail for a real reason, and
  it has to be maintained for ever.
  :::
  :::compare-side{label="Testing a rule" verdict="right"}
  ```java
  @Test void exactlySeventyFivePercentIsNotShort() {
    assertFalse(Attendance.isShort(18, 24));
  }
  ```
  This encodes a decision someone at the college made. If it fails, something
  real is broken.
  :::
::

- **Comparing doubles needs a tolerance.** `assertEquals(75.0, result, 0.001)`,
  never `assertEquals(75.0, result)` on a calculated double, for the reason in
  the primitives lesson.
- **Expected comes first.** `assertEquals(expected, actual)`. Swap them and the
  failure message says "expected 70.8 but was 75.0" when the opposite is true,
  which wastes an afternoon.
- **The message is shown only on failure.** Use it to say why the rule is what
  it is: "the rule is BELOW 75%" is more useful than "expected false".
- **Unit tests do not touch the database or the network.** A test that needs
  MySQL running is an **integration test**. Those matter too, but they are
  slower and belong in a separate suite. Mocking libraries such as Mockito
  replace the database with a stand-in for unit tests.
- **Coverage** (the percentage of lines the tests execute) is a useful signal
  and a terrible target. It is easy to reach 90% by calling every method and
  asserting nothing.

## Interview questions

::accordion
  :::accordion-item{label="How do you test your code?" icon="i-lucide-message-circle"}
  With JUnit unit tests: arrange, act, assert, one behaviour per test, named for
  the rule. I test the boundaries, the empty case, one element and invalid input,
  not only a comfortable value, and I watch each test fail once by breaking the
  code. Changing `<` to `<=` in `isShort` failed exactly the two boundary tests.
  :::
  :::accordion-item{label="How do you test that a method throws an exception?" icon="i-lucide-message-circle"}
  `assertThrows`, which returns the exception so you can check the message too:

  ```java
  IllegalArgumentException e = assertThrows(IllegalArgumentException.class,
      () -> Attendance.percentage(25, 24));
  assertEquals("Attended 25 of 24", e.getMessage());
  ```
  :::
  :::accordion-item{label="What is the difference between @BeforeEach and @BeforeAll?" icon="i-lucide-message-circle"}
  `@BeforeEach` runs before every test, so each test gets a fresh setup.
  `@BeforeAll` runs once before all tests in the class and must be `static`
  (unless the class uses a per-class lifecycle); use it for expensive setup that
  tests only read. In JUnit 4 they were `@Before` and `@BeforeClass`.
  :::
  :::accordion-item{label="What is a parameterised test?" icon="i-lucide-message-circle"}
  One test method run once per set of inputs, with `@ParameterizedTest` and a
  source such as `@CsvSource`. `shortageAtEachBoundary` checks four values in
  one method, and each failure names its own value in the report.
  :::
  :::accordion-item{label="What is the difference between a unit test and an integration test?" icon="i-lucide-message-circle"}
  A unit test checks one piece in isolation, with no database, network or file
  system, and runs in milliseconds. An integration test checks that pieces work
  together, for example your JDBC code against a real database, and is slower.
  You want many unit tests and fewer integration tests.
  :::
::
