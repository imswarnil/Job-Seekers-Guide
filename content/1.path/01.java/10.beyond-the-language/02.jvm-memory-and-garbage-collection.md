Reading a 5 GB file with `readAllLines` ends in `OutOfMemoryError`, and a
recursion with no base case ends in `StackOverflowError`. Both are the JVM
running out of a particular area of memory. This lesson is the map of those
areas, and of the two jobs the JVM does that you never asked it to: collecting
garbage and loading classes.

## Why this matters in a job

When a Java service falls over in production, the first question is almost
always about memory: is the heap full, is something holding on to objects it
should have let go, are the garbage collection pauses too long. You will not
tune a garbage collector in your first year, but you will read an
`OutOfMemoryError` and you will be expected to know which memory ran out.

In interviews, "explain JVM memory", "how does garbage collection work", "when
is an object eligible for garbage collection", "difference between
`StackOverflowError` and `OutOfMemoryError`" and "what are class loaders" are
standard questions from the second year of experience down to fresher rounds
at product companies.

## The JVM is a building with separate rooms

Picture the college's admin building. Each clerk has a **desk** (small,
private, cleared when the clerk finishes a task). There is one shared **records
room** where every file lives, cleared out by a caretaker who throws away files
nobody has asked for in a while. And there is a **reference library** holding
the rule books themselves: how a Student record is laid out, what a FeePayment
contains.

- **Stack** (the clerk's desk): one per thread. Each method call pushes a
  **frame** with its parameters and local variables; the frame goes when the
  method returns. Primitives and references live here. Fixed size, set with
  `-Xss`.
- **Heap** (the records room): one, shared by all threads. Every object and
  array created with `new` lives here. Size set with `-Xms` (starting size) and
  `-Xmx` (maximum).
- **Metaspace** (the reference library): the class definitions themselves,
  their method bytecode and constant pools. Since Java 8 it is native memory
  outside the heap; before that it was called **PermGen** and lived inside the
  heap with a fixed size.
- There is also a **program counter** per thread (which instruction is next)
  and a **native method stack** for code written in C. You only need to name
  them.

## How it works

### Seeing the heap

`Runtime` gives the program a view of its own heap.

```java [MemoryNumbers.java]
public class MemoryNumbers {
  public static void main(String[] args) {
    Runtime rt = Runtime.getRuntime();
    long mb = 1024 * 1024;
    System.out.println("Processors:   " + rt.availableProcessors());
    System.out.println("Max heap:     " + rt.maxMemory() / mb + " MB");
    System.out.println("Heap now:     " + rt.totalMemory() / mb + " MB");
    System.out.println("Free in it:   " + rt.freeMemory() / mb + " MB");

    int[][] results = new int[1000][10_000];   // about 40 MB of ints
    System.out.println("After allocating results:");
    System.out.println("Heap now:     " + rt.totalMemory() / mb + " MB");
    System.out.println("Used:         " + (rt.totalMemory() - rt.freeMemory()) / mb + " MB");
    results = null;                            // nothing refers to it now
  }
}
```

```bash [Terminal]
javac MemoryNumbers.java && java MemoryNumbers
```

```text [Output]
Processors:   14
Max heap:     6144 MB
Heap now:     388 MB
Free in it:   385 MB
After allocating results:
Heap now:     388 MB
Used:         39 MB
```

Your numbers will differ. By default the JVM allows the heap to grow to a
quarter of the machine's RAM (this machine has 24 GB, so 6 GB). Ten million
`int`s at four bytes each is 40 MB, which is what the "Used" line shows.

### When is an object garbage?

**Garbage collection** (GC) is the JVM finding objects that can no longer be
used and reclaiming their memory, so you never call `free` or `delete`. The rule
is **reachability**: starting from a set of **GC roots**, the collector follows
every reference; anything it cannot reach is garbage.

GC roots are, mainly: local variables and parameters in every live stack frame,
static fields of loaded classes, and active threads.

```java [Eligible.java]
public class Eligible {
  static class Student {
    String name;
    Student(String name) { this.name = name; }
  }

  static Student topper;                        // a static field is a GC root

  public static void main(String[] args) {
    Student a = new Student("Anita");           // reachable from a local variable
    Student b = new Student("Vikram");
    b = null;                                   // Vikram's object: no references left, eligible
    Student c = new Student("Farah");
    c = a;                                      // Farah's object: eligible; c and a share Anita
    topper = new Student("Meera");              // reachable from a static field, not eligible
    process(new Student("Rohit"));              // eligible as soon as process returns
    System.out.println("Still reachable: " + a.name + ", " + c.name + ", " + topper.name);
  }

  static void process(Student s) { System.out.println("Processing " + s.name); }
}
```

```text [Output]
Processing Rohit
Still reachable: Anita, Anita, Meera
```

Three ways an object becomes eligible, all in that program: the only reference
is set to `null` (Vikram), the only reference is pointed elsewhere (Farah), and
the only reference was a local variable in a method that has returned (Rohit).
Two objects that refer only to each other, with nothing reaching them from a
root, are also garbage: Java's collector handles cycles.

::flow{numbered direction="horizontal" caption="Generational collection. Most objects die young, so the young generation is collected often and cheaply."}
  :::flow-step{label="Allocated in Eden" icon="i-lucide-sprout"}
  Every `new` lands here. Fast: bump a pointer.
  :::
  :::flow-step{label="Minor GC" icon="i-lucide-recycle" highlight}
  Eden fills; live objects are copied to a survivor space; everything else is
  dropped in one go.
  :::
  :::flow-step{label="Promoted to Old" icon="i-lucide-archive"}
  An object that survives several minor collections moves to the old generation.
  :::
  :::flow-step{label="Major GC" icon="i-lucide-trash-2"}
  The old generation fills; a slower, larger collection runs.
  :::
::

This works because of the **weak generational hypothesis**: most objects die
young. The `String` built inside a loop, the iterator of a for-each, the
temporary array: all garbage within milliseconds.

You can watch the collector with `-Xlog:gc`:

```bash [Terminal]
java -Xmx64m -Xlog:gc MemoryNumbers
```

```text [Output]
[0.004s][info][gc] Using G1
Processors:   14
Max heap:     64 MB
Heap now:     64 MB
Free in it:   61 MB
[0.030s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 24M->22M(64M) 3.563ms
[0.032s][info][gc] GC(1) Pause Young (Normal) (G1 Evacuation Pause) 33M->33M(64M) 1.230ms
After allocating results:
Heap now:     64 MB
Used:         39 MB
```

**G1** (Garbage First) is the default collector since Java 9. "Pause Young" is a
minor collection; "24M->22M(64M) 3.563ms" means the heap went from 24 MB used to
22 MB, out of 64 MB, and the program was paused for 3.5 milliseconds. Other
collectors exist (Serial, Parallel, ZGC, Shenandoah); naming G1 as the default
and ZGC as the low-pause option is enough for a fresher interview.

### The two errors

```java [Deep.java]
public class Deep {
  static int countDepartments(int level) {
    return 1 + countDepartments(level + 1);    // forgot the base case
  }
  public static void main(String[] args) {
    countDepartments(0);
  }
}
```

```text [Output]
Exception in thread "main" java.lang.StackOverflowError
	at Deep.countDepartments(Deep.java:3)
	at Deep.countDepartments(Deep.java:3)
	at Deep.countDepartments(Deep.java:3)
```

(The trace continues for about a thousand identical lines.)

```java [FillHeap.java]
import java.util.ArrayList;
import java.util.List;

public class FillHeap {
  public static void main(String[] args) {
    List<int[]> attendanceLogs = new ArrayList<>();
    int chunks = 0;
    while (true) {
      attendanceLogs.add(new int[1_000_000]);   // about 4 MB each, all kept reachable
      chunks++;
      System.out.println("Chunks held: " + chunks);
    }
  }
}
```

```bash [Terminal]
java -Xmx16m FillHeap
```

```text [Output]
Chunks held: 1
Chunks held: 2
Chunks held: 3
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
	at FillHeap.main(FillHeap.java:9)
```

With `-Xmx64m` the same program reaches 15 chunks before failing. The garbage
collector ran many times and could free nothing, because every array was still
reachable from the list.

::compare{caption="Two errors, two different rooms."}
  :::compare-side{label="StackOverflowError" verdict="neutral"}
  One thread's **stack** is full: too many nested calls, nearly always recursion
  with a missing or unreachable base case. The trace repeats the same method.
  Fix the recursion; `-Xss` only delays it.
  :::
  :::compare-side{label="OutOfMemoryError: Java heap space" verdict="neutral"}
  The shared **heap** is full of reachable objects. Either the program genuinely
  needs more (`-Xmx`), or something is holding references it should have let
  go: a **memory leak**. Other messages name other areas, such as
  `Metaspace`.
  :::
::

### Class loading

A class is not in memory until it is first used. **Class loaders** find the
`.class` bytes and turn them into a class in metaspace. There are three built
in, arranged as parent and child:

::flow{direction="vertical" caption="Parent delegation: a loader asks its parent first and loads the class itself only if the parent cannot."}
  :::flow-step{label="Bootstrap class loader" icon="i-lucide-shield"}
  Built into the JVM. Loads the core: `java.lang.String`, `java.util.ArrayList`.
  Shown as `null` in Java, because it is not a Java object.
  :::
  :::flow-step{label="Platform class loader" icon="i-lucide-layers"}
  Loads the rest of the JDK's modules, such as `java.sql`. Called the
  extension class loader before Java 9.
  :::
  :::flow-step{label="Application (system) class loader" icon="i-lucide-file-code" highlight}
  Loads your classes and your jars from the classpath.
  :::
::

```java [Loaders.java]
public class Loaders {
  public static void main(String[] args) throws Exception {
    System.out.println("String:   " + String.class.getClassLoader());
    System.out.println("Loaders:  " + Loaders.class.getClassLoader());
    System.out.println("Parent:   " + Loaders.class.getClassLoader().getParent());
    System.out.println("Its parent: " + Loaders.class.getClassLoader().getParent().getParent());
    System.out.println("java.sql.Date: " + Class.forName("java.sql.Date").getClassLoader());
  }
}
```

```text [Output]
String:   null
Loaders:  jdk.internal.loader.ClassLoaders$AppClassLoader@2c854dc5
Parent:   jdk.internal.loader.ClassLoaders$PlatformClassLoader@677327b6
Its parent: null
java.sql.Date: jdk.internal.loader.ClassLoaders$PlatformClassLoader@677327b6
```

Delegation is why you cannot replace `java.lang.String` by putting your own
`String.class` on the classpath: the application loader asks upwards first, and
the bootstrap loader already has the real one.

Loading has three phases: **loading** (find the bytes), **linking** (verify the
bytecode is safe, allocate static fields with defaults, resolve references) and
**initialisation** (run static field assignments and `static` blocks, top to
bottom). Initialisation happens once, the first time the class is actually used.

```java [InitOrder.java]
public class InitOrder {
  static class Department {
    static String university = log("static field");
    String name = log("instance field");

    static { log("static block"); }
    { log("instance block"); }

    Department() { log("constructor"); }

    static String log(String what) {
      System.out.println("  " + what);
      return what;
    }
  }

  public static void main(String[] args) {
    System.out.println("main starts");
    System.out.println("first new Department():");
    new Department();
    System.out.println("second new Department():");
    new Department();
  }
}
```

```text [Output]
main starts
first new Department():
  static field
  static block
  instance field
  instance block
  constructor
second new Department():
  instance field
  instance block
  constructor
```

Static parts run once, when the class is first used (not when the program
starts). Instance parts run for every object, in the order they are written,
and the constructor body runs last.

## Real use case

The classic memory leak in a Java service is a `static` collection used as a
cache that only ever grows:

```java
public class ResultCache {
  private static final Map<String, List<ExamResult>> CACHE = new HashMap<>();

  static List<ExamResult> resultsFor(String rollNumber) {
    return CACHE.computeIfAbsent(rollNumber, ResultCache::loadFromDatabase);
  }
}
```

The map is reachable from a static field, which is a GC root, so nothing in it
is ever garbage. Every roll number ever looked up stays in memory for the life
of the process. After results day, with lakhs of lookups, the service dies with
`OutOfMemoryError: Java heap space`. The fixes are a size limit and eviction (a
cache library such as Caffeine does both) or not caching at all.

::real-life{title="What the on-call engineer runs" source="Production Java support"}
When a service runs out of memory, the JVM can write a **heap dump** (a snapshot
of every object) if it was started with `-XX:+HeapDumpOnOutOfMemoryError`. The
engineer opens it in a tool such as Eclipse MAT or VisualVM and looks for the
biggest thing reachable from a GC root. It is nearly always a collection that
grew.
::

## What confuses people here

- **`System.gc()` is a request, not a command.** The JVM may ignore it. Code
  that relies on it to free memory is wrong.
- **`finalize()` is deprecated** (since Java 9, marked for removal). It was never
  guaranteed to run. Use try-with-resources to release resources.
- **Setting a variable to `null` is rarely needed.** A local variable stops
  being a root when its method returns. Nulling helps only for long-lived
  references, such as a slot in an array you keep.
- **Java can leak memory.** GC frees unreachable objects. An object you forgot
  about but still reach (from a static map, a listener list, a thread-local) is
  not garbage.
- **The String pool** moved from PermGen into the heap in Java 7, so pooled
  strings are garbage collected like anything else.
- **More heap is not always better.** A larger heap means fewer collections but
  longer pauses when they happen.

## Interview questions

::accordion
  :::accordion-item{label="Explain the JVM memory areas." icon="i-lucide-message-circle"}
  Per thread: the stack (frames with locals and references), the program counter
  and the native method stack. Shared: the heap (every object, split into young
  and old generations) and metaspace (class metadata, native memory since Java
  8, replacing PermGen). A `StackOverflowError` means one stack is full; an
  `OutOfMemoryError` usually means the heap is.
  :::
  :::accordion-item{label="When is an object eligible for garbage collection?" icon="i-lucide-message-circle"}
  When it cannot be reached from any GC root (live local variables, static
  fields, active threads). In `Eligible.java`: Vikram after `b = null`, Farah
  after `c = a`, Rohit after `process` returned. Meera is reachable from a static
  field and never becomes eligible while the class is loaded.
  :::
  :::accordion-item{label="Can you force garbage collection?" icon="i-lucide-message-circle"}
  No. `System.gc()` and `Runtime.getRuntime().gc()` only suggest it. The JVM
  decides, and some configurations ignore the call completely
  (`-XX:+DisableExplicitGC`).
  :::
  :::accordion-item{label="What is the difference between StackOverflowError and OutOfMemoryError?" icon="i-lucide-message-circle"}
  Different memory. `StackOverflowError` is one thread's stack running out,
  usually from runaway recursion (`Deep.java`). `OutOfMemoryError: Java heap
  space` is the shared heap full of reachable objects (`java -Xmx16m FillHeap`
  after three 4 MB chunks). Both are `Error`s, not `Exception`s, and you should
  not catch them.
  :::
  :::accordion-item{label="What are class loaders, and what is parent delegation?" icon="i-lucide-message-circle"}
  They load `.class` bytes into the JVM. Bootstrap loads the core (`String`
  reports `null`), Platform loads the rest of the JDK, Application loads your
  classpath. Each asks its parent first, so core classes cannot be replaced by a
  class of the same name on your classpath.
  :::
  :::accordion-item{label="In what order do static blocks, instance blocks and constructors run?" icon="i-lucide-message-circle"}
  Static fields and static blocks, top to bottom, once, when the class is first
  used. Then, for each new object: instance fields and instance blocks, top to
  bottom, then the constructor body. `InitOrder.java` shows the static lines
  only before the first object.
  :::
::
