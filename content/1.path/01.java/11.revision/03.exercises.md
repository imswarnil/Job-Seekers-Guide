The question bank was answered from a chair. These fourteen programs are the
same ideas with a keyboard in front of you, and every one of them compiles. Most
run to the end and print a plausible wrong answer, which is exactly how bugs
look at work: nothing crashes, and a student gets the wrong result.

::note
Type each program, run it, and find the bug **before** you open the answer.
Reading a bug and finding one are different skills, and the technical round
tests the second. Each answer shows two fixes: the one a beginner writes
(correct, a little clumsy) and the one an experienced developer writes, with the
reason it is better.
::

## 1. Attendance of zero percent

Vikram attended 18 of 24 classes. The report says he attended none.

```java [AttendanceBug.java]
public class AttendanceBug {
  public static void main(String[] args) {
    int attended = 18, held = 24;
    double pct = attended / held * 100;
    System.out.println("Attendance: " + pct + "%");
  }
}
```

```text [Output]
Attendance: 0.0%
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `18 / 24` is division between two `int`s, so it is `0`, and `0 * 100` is `0`.
  The `double` on the left only receives the already-broken answer. The types
  of the operands decide the arithmetic.

  ```java [AttendanceFix.java]
  public class AttendanceFix {
    public static void main(String[] args) {
      int attended = 18, held = 24;
      double beginner = (double) attended / held * 100;
      double better = attended * 100.0 / held;
      System.out.println(beginner + " " + better);
    }
  }
  ```

  ```text [Output]
  75.0 75.0
  ```

  The experienced version multiplies first by a `double` literal, so it never
  divides two ints at all, and the intent ("percentage") reads left to right.
  :::
::

## 2. The department that is not recognised

The student typed `cse` and the portal does not recognise it.

```java [DeptBug.java]
public class DeptBug {
  public static void main(String[] args) {
    String typed = "cse";                       // what the student typed
    String dept = typed.toUpperCase();
    if (dept == "CSE") {
      System.out.println("Computer Science block");
    } else {
      System.out.println("Unknown department: " + dept);
    }
  }
}
```

```text [Output]
Unknown department: CSE
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `toUpperCase()` returns a **new** String object, not the pooled literal
  `"CSE"`, so `==` (which compares references) is false. The message even
  prints `CSE`, which is what makes this bug so confusing the first time.

  ```java [DeptFix.java]
  public class DeptFix {
    public static void main(String[] args) {
      String typed = "cse";
      System.out.println(typed.toUpperCase().equals("CSE"));
      System.out.println("CSE".equalsIgnoreCase(typed));
      String missing = null;
      System.out.println("CSE".equalsIgnoreCase(missing));
    }
  }
  ```

  ```text [Output]
  true
  true
  false
  ```

  Beginner: `.equals`. Experienced: `"CSE".equalsIgnoreCase(typed)`, with the
  literal first, which handles case and is safe when the input is `null`
  (the third line) instead of throwing.
  :::
::

## 3. The fine that is out by a fraction of a paisa

A library fine of ₹0.10 a day for 30 days.

```java [FeeBug.java]
public class FeeBug {
  public static void main(String[] args) {
    double finePerDay = 0.10;
    double total = 0;
    for (int day = 0; day < 30; day++) total += finePerDay;
    System.out.println("Total fine: " + total);
    System.out.println("Equals 3.0? " + (total == 3.0));
  }
}
```

```text [Output]
Total fine: 3.0000000000000013
Equals 3.0? false
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `0.10` has no exact binary representation, so each addition is very
  slightly off and the error builds up. Never use `double` for money.

  ```java [FeeFix.java]
  import java.math.BigDecimal;

  public class FeeFix {
    public static void main(String[] args) {
      long finePaisePerDay = 10;
      long totalPaise = 0;
      for (int day = 0; day < 30; day++) totalPaise += finePaisePerDay;
      System.out.printf("Total fine: Rs %d.%02d%n", totalPaise / 100, totalPaise % 100);

      BigDecimal total = BigDecimal.ZERO;
      for (int day = 0; day < 30; day++) total = total.add(new BigDecimal("0.10"));
      System.out.println("BigDecimal: " + total);
      System.out.println(new BigDecimal(0.1));
    }
  }
  ```

  ```text [Output]
  Total fine: Rs 3.00
  BigDecimal: 3.00
  0.1000000000000000055511151231257827021181583404541015625
  ```

  Beginner: count paise in a `long`. Experienced: the same, or `BigDecimal`
  built **from a String**. The last line shows why not from a `double`: the
  error is already inside `0.1` before `BigDecimal` sees it.
  :::
::

## 4. The second topper who is also the first

```java [SecondBug.java]
public class SecondBug {
  public static void main(String[] args) {
    int[] marks = {92, 64, 78, 92};
    int highest = marks[0], second = marks[0];
    for (int i = 1; i < marks.length - 1; i++) {
      if (marks[i] > highest) { second = highest; highest = marks[i]; }
      else if (marks[i] > second) second = marks[i];
    }
    System.out.println("Highest " + highest + ", second " + second);
  }
}
```

```text [Output]
Highest 92, second 92
```

There are two bugs. Find both.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  One: `second` starts at `marks[0]`, which is the highest mark, so nothing
  smaller can ever replace it. Two: `i < marks.length - 1` skips the last
  element, an off-by-one that happened to be invisible with this data. A third
  trap waits once those are fixed: a repeated 92 must not count as second.

  ```java [SecondFix.java]
  import java.util.Arrays;

  public class SecondFix {
    public static void main(String[] args) {
      int[] marks = {92, 64, 78, 92};
      int highest = Integer.MIN_VALUE, second = Integer.MIN_VALUE;
      for (int m : marks) {
        if (m > highest) { second = highest; highest = m; }
        else if (m > second && m != highest) second = m;
      }
      System.out.println("Highest " + highest + ", second " + second);

      int secondByStream = Arrays.stream(marks).boxed().distinct()
          .sorted((a, b) -> b - a).skip(1).findFirst().orElseThrow();
      System.out.println("Stream: " + secondByStream);
    }
  }
  ```

  ```text [Output]
  Highest 92, second 78
  Stream: 78
  ```

  The loop is the experienced answer here, because it is one pass and O(n);
  the stream sorts, which is O(n log n). Say both in an interview and say why
  you picked the loop. The enhanced `for` also removes the off-by-one by
  construction.
  :::
::

## 5. The reset that does not reset

```java [ResetBug.java]
import java.util.Arrays;

public class ResetBug {
  static void resetMarks(int[] marks) {
    marks = new int[marks.length];     // "start again with zeros"
  }
  public static void main(String[] args) {
    int[] marks = {78, 64, 92};
    resetMarks(marks);
    System.out.println(Arrays.toString(marks));
  }
}
```

```text [Output]
[78, 64, 92]
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Java is pass by value. The method received a copy of the address, then
  pointed its own copy at a new array. The caller's variable never moved.

  ```java [ResetFix.java]
  import java.util.Arrays;

  public class ResetFix {
    static void resetMarks(int[] marks) {
      Arrays.fill(marks, 0);             // change the caller's array itself
    }
    static int[] freshMarks(int[] marks) {
      return new int[marks.length];      // or return a new one and say so
    }
    public static void main(String[] args) {
      int[] marks = {78, 64, 92};
      resetMarks(marks);
      System.out.println(Arrays.toString(marks));
      int[] other = {55, 61};
      other = freshMarks(other);
      System.out.println(Arrays.toString(other));
    }
  }
  ```

  ```text [Output]
  [0, 0, 0]
  [0, 0]
  ```

  Beginner: mutate the array that was passed in. Experienced: prefer returning
  a new value, because a method that changes its arguments surprises the next
  reader. If it must mutate, its name should say so.
  :::
::

## 6. The student registered twice

```java [DupBug.java]
import java.util.*;

public class DupBug {
  static class Student {
    final String rollNumber;
    Student(String rollNumber) { this.rollNumber = rollNumber; }
    @Override public boolean equals(Object o) {
      return o instanceof Student s && s.rollNumber.equals(rollNumber);
    }
  }
  public static void main(String[] args) {
    Set<Student> registered = new HashSet<>();
    registered.add(new Student("2026CSE0184"));
    registered.add(new Student("2026CSE0184"));
    System.out.println("Registered: " + registered.size());
  }
}
```

```text [Output]
Registered: 2
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `equals` is overridden and `hashCode` is not. `HashSet` picks a bucket by
  hash code first; two objects with different default hash codes land in
  different buckets and `equals` is never called.

  ```java [DupFix.java]
  import java.util.*;

  public class DupFix {
    static class Student {
      final String rollNumber;
      Student(String rollNumber) { this.rollNumber = rollNumber; }
      @Override public boolean equals(Object o) {
        return o instanceof Student s && s.rollNumber.equals(rollNumber);
      }
      @Override public int hashCode() { return Objects.hash(rollNumber); }
    }
    record StudentRecord(String rollNumber) { }

    public static void main(String[] args) {
      Set<Student> registered = new HashSet<>();
      registered.add(new Student("2026CSE0184"));
      registered.add(new Student("2026CSE0184"));
      System.out.println("Class with hashCode: " + registered.size());
      Set<StudentRecord> records = new HashSet<>(List.of(new StudentRecord("2026CSE0184")));
      records.add(new StudentRecord("2026CSE0184"));
      System.out.println("Record: " + records.size());
    }
  }
  ```

  ```text [Output]
  Class with hashCode: 1
  Record: 1
  ```

  Beginner: add `hashCode` on the same fields as `equals`. Experienced: a
  `record`, which generates both and cannot let them drift apart when someone
  adds a field later.
  :::
::

## 7. The list that throws while you clean it

Remove every mark below 40.

```java [RemoveBug.java]
import java.util.*;

public class RemoveBug {
  public static void main(String[] args) {
    List<Integer> marks = new ArrayList<>(List.of(78, 35, 92, 20, 64));
    for (Integer m : marks) {
      if (m < 40) marks.remove(m);
    }
    System.out.println(marks);
  }
}
```

```text [Output]
Exception in thread "main" java.util.ConcurrentModificationException
	at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1095)
	at java.base/java.util.ArrayList$Itr.next(ArrayList.java:1049)
	at RemoveBug.main(RemoveBug.java:6)
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  The enhanced `for` walks the list with a fail-fast iterator. Removing through
  the list, not the iterator, changes the list behind its back, and the next
  `next()` throws.

  ```java [RemoveFix.java]
  import java.util.*;

  public class RemoveFix {
    public static void main(String[] args) {
      List<Integer> marks = new ArrayList<>(List.of(78, 35, 92, 20, 64));
      Iterator<Integer> it = marks.iterator();
      while (it.hasNext()) {
        if (it.next() < 40) it.remove();
      }
      System.out.println(marks);

      List<Integer> again = new ArrayList<>(List.of(78, 35, 92, 20, 64));
      again.removeIf(m -> m < 40);
      System.out.println(again);
    }
  }
  ```

  ```text [Output]
  [78, 92, 64]
  [78, 92, 64]
  ```

  Beginner: an explicit `Iterator` and `it.remove()`. Experienced:
  `removeIf`, one line that says what it means and has no iterator to get
  wrong.
  :::
::

## 8. The tie that is only a tie for small ranks

```java [RankBug.java]
public class RankBug {
  public static void main(String[] args) {
    Integer anitaRank = 150, farahRank = 150;
    Integer vikramRank = 12, rohitRank = 12;
    System.out.println("Vikram and Rohit tied: " + (vikramRank == rohitRank));
    System.out.println("Anita and Farah tied: " + (anitaRank == farahRank));
  }
}
```

```text [Output]
Vikram and Rohit tied: true
Anita and Farah tied: false
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `==` on `Integer` compares references. Autoboxing reuses cached objects from
  -128 to 127, so 12 and 12 are the same object and 150 and 150 are not. The
  code worked in every test with small ranks.

  ```java [RankFix.java]
  import java.util.Objects;

  public class RankFix {
    public static void main(String[] args) {
      Integer anitaRank = 150, farahRank = 150;
      Integer unknown = null;
      System.out.println(anitaRank.equals(farahRank));
      System.out.println(Objects.equals(anitaRank, farahRank));
      System.out.println(Objects.equals(unknown, farahRank));
      System.out.println(anitaRank.intValue() == farahRank.intValue());
    }
  }
  ```

  ```text [Output]
  true
  true
  false
  true
  ```

  Beginner: `.equals`. Experienced: `Objects.equals`, which is also safe when
  either side is `null`, or keep ranks as `int` in the first place if they can
  never be missing.
  :::
::

## 9. The total that crashes on a student with no marks

```java [TotalBug.java]
import java.util.*;

public class TotalBug {
  public static void main(String[] args) {
    Map<String, Integer> marks = new HashMap<>();
    marks.put("1801", 78);
    marks.put("1802", 64);
    String[] rolls = {"1801", "1802", "1803"};
    int total = 0;
    for (String roll : rolls) {
      total += marks.get(roll);
    }
    System.out.println("Total: " + total);
  }
}
```

```text [Output]
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.lang.Integer.intValue()" because the return value of "java.util.Map.get(Object)" is null
	at TotalBug.main(TotalBug.java:11)
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `get` returns `null` for roll 1803, and `total += null` unboxes it by calling
  `intValue()`. A line with no visible method call threw a
  `NullPointerException`.

  The quick fix is `marks.getOrDefault(roll, 0)`. Stop before using it: a
  student who has not been marked is not a student who scored zero, and
  counting them as 0 drags the average down. The experienced fix keeps the
  difference visible:

  ```java [TotalFix.java]
  import java.util.*;

  public class TotalFix {
    public static void main(String[] args) {
      Map<String, Integer> marks = new HashMap<>();
      marks.put("1801", 78);
      marks.put("1802", 64);
      String[] rolls = {"1801", "1802", "1803"};

      int total = 0, missing = 0;
      for (String roll : rolls) {
        Integer m = marks.get(roll);
        if (m == null) { missing++; continue; }
        total += m;
      }
      System.out.println("Total: " + total + ", not yet marked: " + missing);
    }
  }
  ```

  ```text [Output]
  Total: 142, not yet marked: 1
  ```
  :::

## 10. The report with a comma too many

```java [ReportBug.java]
import java.util.List;

public class ReportBug {
  public static void main(String[] args) {
    List<String> names = List.of("Anita", "Vikram", "Farah");
    String report = "";
    for (String n : names) {
      report += n + ", ";
    }
    System.out.println("[" + report + "]");
  }
}
```

```text [Output]
[Anita, Vikram, Farah, ]
```

Two problems: the trailing comma, and what happens with 40,000 names.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  The trailing separator is the visible bug. The invisible one is `+=` on a
  `String` in a loop: Strings are immutable, so each pass copies everything so
  far, which is quadratic. With three names it does not matter; with a whole
  university it takes seconds instead of milliseconds.

  ```java [ReportFix.java]
  import java.util.List;
  import java.util.stream.Collectors;

  public class ReportFix {
    public static void main(String[] args) {
      List<String> names = List.of("Anita", "Vikram", "Farah");
      StringBuilder sb = new StringBuilder();
      for (int i = 0; i < names.size(); i++) {
        if (i > 0) sb.append(", ");
        sb.append(names.get(i));
      }
      System.out.println("[" + sb + "]");
      System.out.println("[" + String.join(", ", names) + "]");
      System.out.println(names.stream().collect(Collectors.joining(", ", "[", "]")));
    }
  }
  ```

  ```text [Output]
  [Anita, Vikram, Farah]
  [Anita, Vikram, Farah]
  [Anita, Vikram, Farah]
  ```

  Beginner: `StringBuilder` with a separator before every element but the
  first. Experienced: `String.join`, or `Collectors.joining` with a prefix and
  suffix, which handles the separator for you.
  :::
::

## 11. The subclass that cannot do what its parent does

```java [StateBug.java]
public class StateBug {
  static class Application {
    void submit() { System.out.println("Submitted"); }
  }
  static class RejectedApplication extends Application {
    @Override void submit() { throw new UnsupportedOperationException("Rejected applications cannot be submitted"); }
  }
  static void submitAll(Application[] apps) {
    for (Application a : apps) a.submit();
  }
  public static void main(String[] args) {
    submitAll(new Application[] { new Application(), new RejectedApplication() });
  }
}
```

```text [Output]
Submitted
Exception in thread "main" java.lang.UnsupportedOperationException: Rejected applications cannot be submitted
	at StateBug$RejectedApplication.submit(StateBug.java:6)
	at StateBug.submitAll(StateBug.java:9)
	at StateBug.main(StateBug.java:12)
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  This is a design bug, not a syntax one. Code holding an `Application`
  expects `submit` to work; a subclass that removes the behaviour breaks that
  promise. "Rejected" is not a kind of application. It is a **state** an
  application is in, and state belongs in a field.

  ```java [StateFix.java]
  public class StateFix {
    enum Status { DRAFT, SUBMITTED, REJECTED }

    static class Application {
      private final String applicantName;
      private Status status = Status.DRAFT;
      Application(String applicantName) { this.applicantName = applicantName; }

      void submit() {
        if (status != Status.DRAFT) {
          System.out.println(applicantName + ": cannot submit, already " + status);
          return;
        }
        status = Status.SUBMITTED;
        System.out.println(applicantName + ": submitted");
      }
      void reject() { status = Status.REJECTED; }
    }

    public static void main(String[] args) {
      Application anita = new Application("Anita");
      Application vikram = new Application("Vikram");
      vikram.reject();
      for (Application a : new Application[] { anita, vikram }) a.submit();
    }
  }
  ```

  ```text [Output]
  Anita: submitted
  Vikram: cannot submit, already REJECTED
  ```

  A beginner catches the exception in `submitAll`. The experienced answer
  removes the subclass: use inheritance only when every subclass can be used
  wherever its parent can (the Liskov substitution principle), and prefer a
  field or composition otherwise.
  :::
::

## 12. The stream that fails on the second CSE student

Build a map from department to student name.

```java [ToMapBug.java]
import java.util.*;
import java.util.stream.*;

public class ToMapBug {
  record Student(String name, String dept) { }
  public static void main(String[] args) {
    List<Student> students = List.of(
        new Student("Anita", "CSE"), new Student("Vikram", "ECE"), new Student("Farah", "CSE"));
    Map<String, String> byDept = students.stream()
        .collect(Collectors.toMap(Student::dept, Student::name));
    System.out.println(byDept);
  }
}
```

```text [Output]
Exception in thread "main" java.lang.IllegalStateException: Duplicate key CSE (attempted merging values Anita and Farah)
	at java.base/java.util.stream.Collectors.duplicateKeyException(Collectors.java:135)
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `toMap` with two arguments throws on a duplicate key, and two students share
  a department. The message says exactly that, which is the lesson about
  reading the first line of an exception.

  ```java [ToMapFix.java]
  import java.util.*;
  import java.util.stream.*;

  public class ToMapFix {
    record Student(String name, String dept) { }
    public static void main(String[] args) {
      List<Student> students = List.of(
          new Student("Anita", "CSE"), new Student("Vikram", "ECE"), new Student("Farah", "CSE"));

      Map<String, String> joined = students.stream()
          .collect(Collectors.toMap(Student::dept, Student::name, (a, b) -> a + ", " + b, TreeMap::new));
      System.out.println(joined);

      Map<String, List<String>> grouped = students.stream()
          .collect(Collectors.groupingBy(Student::dept, TreeMap::new,
              Collectors.mapping(Student::name, Collectors.toList())));
      System.out.println(grouped);
    }
  }
  ```

  ```text [Output]
  {CSE=Anita, Farah, ECE=Vikram}
  {CSE=[Anita, Farah], ECE=[Vikram]}
  ```

  Beginner: a merge function as the third argument. Experienced: recognise that
  "department to students" is one-to-many and use `groupingBy`, which gives a
  real list instead of a joined string.
  :::
::

## 13. The papers that were marked and not counted

Four examiners, 25,000 papers each.

```java [CountBug.java]
import java.util.concurrent.*;

public class CountBug {
  static int papersMarked = 0;
  public static void main(String[] args) throws Exception {
    ExecutorService pool = Executors.newFixedThreadPool(4);
    for (int examiner = 0; examiner < 4; examiner++) {
      pool.submit(() -> {
        for (int i = 0; i < 25_000; i++) papersMarked++;
      });
    }
    pool.shutdown();
    pool.awaitTermination(10, TimeUnit.SECONDS);
    System.out.println("Papers marked: " + papersMarked + " (expected 100000)");
  }
}
```

```text [Output]
Papers marked: 29264 (expected 100000)
```

(Your number will be different, and different on every run.)

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `papersMarked++` is three steps: read, add one, write. Two threads read the
  same value, both add one, both write, and one update is lost. That is a race
  condition, and the wrong answer changing on every run is its signature.

  ```java [CountFix.java]
  import java.util.concurrent.*;
  import java.util.concurrent.atomic.AtomicInteger;

  public class CountFix {
    static final AtomicInteger papersMarked = new AtomicInteger();
    public static void main(String[] args) throws Exception {
      ExecutorService pool = Executors.newFixedThreadPool(4);
      for (int examiner = 0; examiner < 4; examiner++) {
        pool.submit(() -> {
          for (int i = 0; i < 25_000; i++) papersMarked.incrementAndGet();
        });
      }
      pool.shutdown();
      pool.awaitTermination(10, TimeUnit.SECONDS);
      System.out.println("Papers marked: " + papersMarked.get());
    }
  }
  ```

  ```text [Output]
  Papers marked: 100000
  ```

  Beginner: a `synchronized` method around the increment. Experienced:
  `AtomicInteger`, which is lock-free and says "this is a shared counter" in its
  type. `volatile` would **not** fix it: it makes the write visible, not the
  read-add-write atomic.
  :::
::

## 14. The test that passes with the bug in it

The rule: 90 and above is an A, 75 to 89 is a B, 40 to 74 is a C, below 40 is
an F.

```java [Grade.java]
public class Grade {
  public static String of(int marks) {
    if (marks >= 90) return "A";
    if (marks > 75) return "B";       // the rule says 75 and above is a B
    if (marks >= 40) return "C";
    return "F";
  }
}
```

```java [GradeTest.java]
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class GradeTest {
  @Test
  void gradesWork() {
    assertEquals("A", Grade.of(95));
    assertEquals("B", Grade.of(82));
    assertEquals("F", Grade.of(12));
  }
}
```

The test passes. Write the test that would have caught the bug.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `gradesWork` only checks comfortable values in the middle of each band, so
  it passes whether the comparison is `>` or `>=`. A test that would still pass
  if the code were wrong is not a test. Test the boundaries:

  ```java [GradeBoundaryTest.java]
  import org.junit.jupiter.params.ParameterizedTest;
  import org.junit.jupiter.params.provider.CsvSource;
  import static org.junit.jupiter.api.Assertions.assertEquals;

  class GradeBoundaryTest {
    @ParameterizedTest(name = "{0} marks -> {1}")
    @CsvSource({ "90, A", "89, B", "75, B", "74, C", "40, C", "39, F" })
    void gradeAtEachBoundary(int marks, String expected) {
      assertEquals(expected, Grade.of(marks));
    }
  }
  ```

  ```text [Output]
  ├─ JUnit Jupiter ✔
  │  ├─ GradeTest ✔
  │  │  └─ gradesWork() ✔
  │  └─ GradeBoundaryTest ✔
  │     └─ gradeAtEachBoundary(int, String) ✔
  │        ├─ 90 marks -> A ✔
  │        ├─ 89 marks -> B ✔
  │        ├─ 75 marks -> B ✘ expected: <B> but was: <C>
  │        ├─ 74 marks -> C ✔
  │        ├─ 40 marks -> C ✔
  │        └─ 39 marks -> F ✔
  ```

  Beginner: add a test for 75. Experienced: one parameterised test with both
  sides of **every** boundary, so each failure names the exact mark. Then fix
  `>` to `>=` and watch it go green.
  :::
