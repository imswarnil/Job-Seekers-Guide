## Basics and the JVM

::accordion
  :::accordion-item{label="1. Is Java compiled or interpreted?" icon="i-lucide-message-circle"}
  Both. `javac` compiles source code to bytecode ahead of time; the JVM then
  interprets that bytecode, and the JIT compiler turns the frequently run parts
  into native machine code while the program runs. You can see the bytecode
  with `javap -c`:

  ```java [Hello.java]
  public class Hello {
    public static void main(String[] args) {
      int marks = 78;
      System.out.println(marks + 5);
    }
  }
  ```

  ```text [javap -c Hello]
    public static void main(java.lang.String[]);
      Code:
         0: bipush        78
         2: istore_1
         3: getstatic     #7                  // Field java/lang/System.out:Ljava/io/PrintStream;
         6: iload_1
         7: iconst_5
         8: iadd
         9: invokevirtual #13                 // Method java/io/PrintStream.println:(I)V
        12: return
  ```

  That is not machine code for any real CPU. It is instructions for the JVM,
  which is why the same `.class` file runs on Windows, macOS and Linux.
  :::
  :::accordion-item{label="2. What is the difference between the JDK, JRE and JVM?" icon="i-lucide-message-circle"}
  The JDK contains the JRE, which contains the JVM. The JDK adds the compiler
  and tools; the JRE is enough to run a program; the JVM executes bytecode,
  manages memory and runs the garbage collector. The practical test: if
  `java -version` works and `javac -version` says "command not found", you have
  a runtime and not a JDK.
  :::
  :::accordion-item{label="3. Why is main static? Can it be overloaded?" icon="i-lucide-message-circle"}
  Static because the JVM calls it before any object exists, so it must belong to
  the class. It can be overloaded; the JVM only ever calls the
  `main(String[] args)` version.

  ```java [MainOverload.java]
  public class MainOverload {
    public static void main(String[] args) {
      System.out.println("The JVM calls this one");
      main(42);
    }
    public static void main(int batch) {
      System.out.println("Overloaded main, batch " + batch);
    }
  }
  ```

  ```text [Output]
  The JVM calls this one
  Overloaded main, batch 42
  ```
  :::
  :::accordion-item{label="4. What do these print: 7 / 2, (double) 7 / 2, (int) 81.99, i = i++?" icon="i-lucide-message-circle"}
  Integer division truncates; a cast truncates rather than rounds; and `i = i++`
  assigns the old value back, so `i` does not change. `b += 5` compiles on a
  `byte` because compound assignment hides a cast.

  ```java [Arith.java]
  public class Arith {
    public static void main(String[] args) {
      System.out.println(7 / 2);
      System.out.println((double) 7 / 2);
      System.out.println((int) 81.99);
      System.out.println(0.1 + 0.2);
      int i = 5;
      i = i++;
      System.out.println(i);
      byte b = 10;
      b += 5;                 // compiles: hidden cast
      System.out.println(b);
    }
  }
  ```

  ```text [Output]
  3
  3.5
  81
  0.30000000000000004
  5
  15
  ```

  And `b = b + 5;` on a `byte` does not compile: `error: incompatible types:
  possible lossy conversion from int to byte`, because `b + 5` is an `int`.
  :::
  :::accordion-item{label="5. Why should you not use double for money?" icon="i-lucide-message-circle"}
  Binary floating point cannot store most decimal fractions exactly, so
  `0.1 + 0.2` prints `0.30000000000000004` (above), and the errors add up over
  many operations. Store money as a `long` count of paise
  (`long feePaise = 4_500_000L;` for ₹45,000) or as `new BigDecimal("45000.00")`,
  built from a String, never from a double.
  :::

## Strings

::accordion
  :::accordion-item{label="6. What is the difference between == and equals for Strings?" icon="i-lucide-message-circle"}
  `==` compares references; `equals` compares characters. String literals are
  pooled, so two identical literals are one object and `==` happens to be true.
  `new String` forces a separate object. `intern()` returns the pooled copy.

  ```java [Pool.java]
  public class Pool {
    public static void main(String[] args) {
      String a = "Anita";
      String b = "Anita";
      String c = new String("Anita");
      System.out.println(a == b);
      System.out.println(a == c);
      System.out.println(a.equals(c));
      System.out.println(a == c.intern());
    }
  }
  ```

  ```text [Output]
  true
  false
  true
  true
  ```

  The danger: `==` works in a test with literals and fails in production when
  the String came from a form or a database. Always use `equals`.
  :::
  :::accordion-item{label="7. Why is String immutable?" icon="i-lucide-message-circle"}
  So the pool is safe (a shared literal cannot be changed under someone else),
  so its hash code never goes stale as a map key, and so it can be shared
  between threads without locks. Every method that "changes" a String returns
  a new one:

  ```java [Immutable.java]
  public class Immutable {
    public static void main(String[] args) {
      String name = "anita";
      name.toUpperCase();                 // result thrown away
      System.out.println(name);
      name = name.toUpperCase();          // keep the new String
      System.out.println(name);
      StringBuilder sb = new StringBuilder("anita");
      sb.append(" rao").reverse();
      System.out.println(sb);
    }
  }
  ```

  ```text [Output]
  anita
  ANITA
  oar atina
  ```
  :::
  :::accordion-item{label="8. String, StringBuilder or StringBuffer?" icon="i-lucide-message-circle"}
  `String` is immutable, so `+=` in a loop copies everything each time.
  `StringBuilder` is mutable and not synchronised: use it to build text.
  `StringBuffer` is the older synchronised version; it is almost never the
  right choice now, because one builder shared across threads is a design
  problem that locking `append` does not fix. The last line of `Immutable.java`
  shows `StringBuilder` changing in place.
  :::
  :::accordion-item{label="9. How many objects does new String with a literal inside create?" icon="i-lucide-message-circle"}
  Up to two. The literal `"Anita"` goes into the pool (if it is not already
  there, which it usually is once the class is loaded), and `new` always
  creates a second, separate object on the heap. That is why `a == c` printed
  `false` in `Pool.java`, and why you should never write `new String("...")`.
  :::
::

## OOPs

::accordion
  :::accordion-item{label="10. What are the four pillars of OOPs?" icon="i-lucide-message-circle"}
  Encapsulation (private fields, controlled methods), inheritance (`extends`),
  polymorphism (one call, behaviour chosen by the actual object) and
  abstraction (abstract classes and interfaces that say what, not how). Give
  one line of code for each, from the college: a private `marks` field with a
  validating setter; `ScholarshipStudent extends Student`; `fee()` returning a
  different amount for each; a `Payable` interface.
  :::
  :::accordion-item{label="11. What is the difference between overloading and overriding?" icon="i-lucide-message-circle"}
  Overloading: same name, different parameters, in one class, chosen at compile
  time. Overriding: same signature in a subclass, chosen at run time from the
  object. Static methods are not overridden; they are hidden, chosen by the
  declared type:

  ```java [Hiding.java]
  public class Hiding {
    static class Student {
      static String type() { return "Student"; }
      String fee() { return "Rs 90,000"; }
    }
    static class ScholarshipStudent extends Student {
      static String type() { return "ScholarshipStudent"; }
      @Override String fee() { return "Rs 0"; }
    }
    public static void main(String[] args) {
      Student s = new ScholarshipStudent();
      System.out.println(s.fee());    // overriding: the object decides
      System.out.println(s.type());   // hiding: the declared type decides
    }
  }
  ```

  ```text [Output]
  Rs 0
  Student
  ```
  :::
  :::accordion-item{label="12. Can we override a static or a private method?" icon="i-lucide-message-circle"}
  No. A static method with the same signature in a subclass hides the parent's
  (`s.type()` printed `Student` above). A private method is not visible to the
  subclass at all, so a method with the same name there is a new, unrelated
  method. `@Override` on either is a compile error, which is the quickest way
  to prove it.
  :::
  :::accordion-item{label="13. Abstract class or interface?" icon="i-lucide-message-circle"}
  An abstract class can have fields, constructors and state, and a class can
  extend only one. An interface is a contract with no instance state, and a
  class can implement many. Since Java 8 interfaces may have `default` and
  `static` methods; since Java 9, `private` ones. Use an abstract class for
  shared state, an interface for a shared capability, and prefer the interface.
  :::
  :::accordion-item{label="14. Why does Java not allow multiple inheritance of classes? What about two default methods with the same name?" icon="i-lucide-message-circle"}
  To avoid the diamond problem: if two parents had the same method with
  different bodies, which one runs? With interfaces the compiler makes you
  decide:

  ```java [Diamond.java]
  public class Diamond {
    interface Attendable { default String report() { return "attendance"; } }
    interface Gradable   { default String report() { return "grades"; } }

    static class Student implements Attendable, Gradable {
      @Override public String report() {            // must resolve the clash
        return Attendable.super.report() + " + " + Gradable.super.report();
      }
    }
    public static void main(String[] args) {
      System.out.println(new Student().report());
    }
  }
  ```

  ```text [Output]
  attendance + grades
  ```

  Remove the override and the class does not compile: `error: types Attendable
  and Gradable are incompatible`.
  :::
  :::accordion-item{label="15. In what order do constructors run in an inheritance chain?" icon="i-lucide-message-circle"}
  Parent first. Every constructor starts with `super(...)`, written or not, so
  the chain runs from the top down:

  ```java [CtorOrder.java]
  public class CtorOrder {
    static class Member {
      Member() { System.out.println("Member constructor"); }
    }
    static class Student extends Member {
      Student() { System.out.println("Student constructor"); }
    }
    static class HostelStudent extends Student {
      HostelStudent() { System.out.println("HostelStudent constructor"); }
    }
    public static void main(String[] args) {
      new HostelStudent();
    }
  }
  ```

  ```text [Output]
  Member constructor
  Student constructor
  HostelStudent constructor
  ```
  :::
  :::accordion-item{label="16. Composition or inheritance?" icon="i-lucide-message-circle"}
  Inheritance for a true IS-A that holds for every subclass forever; composition
  (a field) for HAS-A. A `Student` HAS-A `Address`; it is not a kind of address.
  Prefer composition: it can change at run time, it does not expose the parent's
  methods, and it does not break when the parent class changes.

  ```java
  class Student {
    private final Address address;      // composition
    Student(Address address) { this.address = address; }
  }
  ```
  :::
  :::accordion-item{label="17. What does protected mean?" icon="i-lucide-message-circle"}
  Visible in the same package, and in subclasses in other packages (through
  inheritance). From most to least open: `public`, `protected`, default (no
  keyword, same package only), `private` (same class only).

  ```java
  package college.core;
  public class Student { protected int marks; }

  package college.hostel;
  public class HostelStudent extends college.core.Student {
    void bonus() { marks += 5; }        // allowed: subclass
  }
  ```
  :::
::

## static and final

::accordion
  :::accordion-item{label="18. What is the difference between final, finally and finalize?" icon="i-lucide-message-circle"}
  `final` stops change: a variable assigned once, a method that cannot be
  overridden, a class that cannot be extended. `finally` is the block after
  `try` that always runs. `finalize()` was a method the garbage collector might
  call before reclaiming an object; it is deprecated since Java 9 and should not
  be used. Three unrelated things with similar names.
  :::
  :::accordion-item{label="19. Can you add to a final List?" icon="i-lucide-message-circle"}
  Yes. `final` fixes the reference, not the object. To make the contents
  unchangeable, use an unmodifiable list:

  ```java [FinalList.java]
  import java.util.ArrayList;
  import java.util.List;

  public class FinalList {
    public static void main(String[] args) {
      final List<String> toppers = new ArrayList<>();
      toppers.add("Farah");                 // allowed: the object changes
      System.out.println(toppers);
      List<String> fixed = List.of("Farah");
      fixed.add("Anita");                   // the object itself refuses
    }
  }
  ```

  ```text [Output]
  [Farah]
  Exception in thread "main" java.lang.UnsupportedOperationException
  	at java.base/java.util.ImmutableCollections.uoe(ImmutableCollections.java:142)
  	at java.base/java.util.ImmutableCollections$AbstractImmutableCollection.add(ImmutableCollections.java:147)
  	at FinalList.main(FinalList.java:10)
  ```
  :::
  :::accordion-item{label="20. When does a static block run?" icon="i-lucide-message-circle"}
  Once, when the class is first used (not when the program starts), before any
  object of it is created. Then, for every object, instance fields and instance
  blocks run in order, then the constructor. The JVM lesson's `InitOrder.java`
  prints `static field`, `static block` only before the first object, and
  `instance field`, `instance block`, `constructor` for each object.
  :::
::

## equals, hashCode and wrappers

::accordion
  :::accordion-item{label="21. What is the equals and hashCode contract?" icon="i-lucide-message-circle"}
  If two objects are equal, they must have the same hash code. Override
  `equals` without `hashCode` and hash-based collections break, because they
  look in the bucket chosen by the hash before calling `equals`:

  ```java [EqHash.java]
  import java.util.HashSet;
  import java.util.Set;

  public class EqHash {
    static class Student {
      final int roll;
      Student(int roll) { this.roll = roll; }
      @Override public boolean equals(Object o) {
        return o instanceof Student s && s.roll == roll;
      }
      // hashCode NOT overridden
    }
    record StudentRecord(int roll) { }

    public static void main(String[] args) {
      Set<Student> set = new HashSet<>();
      set.add(new Student(1801));
      set.add(new Student(1801));
      System.out.println("class, no hashCode: " + set.size());

      Set<StudentRecord> set2 = new HashSet<>();
      set2.add(new StudentRecord(1801));
      set2.add(new StudentRecord(1801));
      System.out.println("record:             " + set2.size());
    }
  }
  ```

  ```text [Output]
  class, no hashCode: 2
  record:             1
  ```

  A record generates both correctly.
  :::
  :::accordion-item{label="22. Why is Integer 127 == 127 true but 128 == 128 false?" icon="i-lucide-message-circle"}
  Autoboxing uses `Integer.valueOf`, which returns cached objects for -128 to
  127. Outside that range each boxing makes a new object, and `==` compares
  references.

  ```java [Cache.java]
  public class Cache {
    public static void main(String[] args) {
      Integer a = 127, b = 127;
      Integer c = 128, d = 128;
      System.out.println(a == b);
      System.out.println(c == d);
      System.out.println(c.equals(d));
    }
  }
  ```

  ```text [Output]
  true
  false
  true
  ```

  Never compare wrappers with `==`: it works in testing with small numbers and
  fails with real ones.
  :::
  :::accordion-item{label="23. How can a line with no method call throw a NullPointerException?" icon="i-lucide-message-circle"}
  Unboxing. Assigning a `null` `Integer` to an `int` calls `intValue()` on it,
  invisibly.

  ```java [Unbox.java]
  import java.util.HashMap;
  import java.util.Map;

  public class Unbox {
    public static void main(String[] args) {
      Map<String, Integer> marks = new HashMap<>();
      marks.put("1801", 78);
      int m = marks.get("1802");
    }
  }
  ```

  ```text [Output]
  Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.lang.Integer.intValue()" because the return value of "java.util.Map.get(Object)" is null
  	at Unbox.main(Unbox.java:8)
  ```
  :::

## Exceptions

::accordion
  :::accordion-item{label="24. What is the difference between checked and unchecked exceptions?" icon="i-lucide-message-circle"}
  Checked exceptions (`IOException`, `SQLException`, anything extending
  `Exception` but not `RuntimeException`) must be caught or declared; the
  compiler enforces it. Unchecked ones (`RuntimeException` and subclasses such
  as `NullPointerException`, `IllegalArgumentException`) are not enforced and
  usually mean a bug. Proof: `Files.readAllLines(path)` without a `try` or
  `throws` fails to compile with `unreported exception IOException; must be
  caught or declared to be thrown`.
  :::
  :::accordion-item{label="25. Does finally always run? What if try returns?" icon="i-lucide-message-circle"}
  Yes, even after a `return`, unless the JVM stops (`System.exit`, a crash). A
  `return` inside `finally` overrides the one in `try`, which is why you should
  never write one.

  ```java [FinallyRuns.java]
  public class FinallyRuns {
    static int attempt() {
      try {
        return 1;
      } finally {
        System.out.println("finally runs before the method returns");
      }
    }
    static int override() {
      try {
        return 1;
      } finally {
        return 2;          // swallows the first return: never do this
      }
    }
    public static void main(String[] args) {
      System.out.println(attempt());
      System.out.println(override());
    }
  }
  ```

  ```text [Output]
  finally runs before the method returns
  1
  2
  ```
  :::
  :::accordion-item{label="26. What is the difference between throw and throws? Write a custom exception." icon="i-lucide-message-circle"}
  `throw` throws one exception object now; `throws` in a signature declares
  what a method may throw. A custom exception extends `Exception` (checked) or
  `RuntimeException` (unchecked) and is named for the problem:

  ```java [Custom.java]
  public class Custom {
    static class InsufficientAttendanceException extends Exception {
      InsufficientAttendanceException(String message) { super(message); }
    }

    static void allowExam(String name, double pct) throws InsufficientAttendanceException {
      if (pct < 75) {
        throw new InsufficientAttendanceException(name + " has " + pct + "%, needs 75%");
      }
      System.out.println(name + " may sit the exam");
    }

    public static void main(String[] args) {
      try {
        allowExam("Anita", 90.0);
        allowExam("Vikram", 70.0);
      } catch (InsufficientAttendanceException e) {
        System.out.println("Refused: " + e.getMessage());
      }
    }
  }
  ```

  ```text [Output]
  Anita may sit the exam
  Refused: Vikram has 70.0%, needs 75%
  ```
  :::
  :::accordion-item{label="27. How does try-with-resources close things, and in what order?" icon="i-lucide-message-circle"}
  Anything `AutoCloseable` declared in the brackets is closed when the block
  ends, even on an exception, in reverse order of opening, and before the
  `catch` runs.

  ```java [CloseOrder.java]
  public class CloseOrder {
    static class Resource implements AutoCloseable {
      final String name;
      Resource(String name) { this.name = name; System.out.println("open " + name); }
      @Override public void close() { System.out.println("close " + name); }
    }
    public static void main(String[] args) {
      try (Resource db = new Resource("database"); Resource file = new Resource("report file")) {
        System.out.println("working");
        throw new IllegalStateException("marks missing");
      } catch (IllegalStateException e) {
        System.out.println("caught: " + e.getMessage());
      }
    }
  }
  ```

  ```text [Output]
  open database
  open report file
  working
  close report file
  close database
  caught: marks missing
  ```
  :::
::

## Collections

::accordion
  :::accordion-item{label="28. ArrayList or LinkedList?" icon="i-lucide-message-circle"}
  `ArrayList` in almost every case. It is a growable array: O(1) access by
  index and fast iteration, because the elements are side by side in memory.
  `LinkedList` is a chain of nodes: O(1) insert at either end, but O(n) to reach
  an index, and slower to iterate in practice. For a queue or stack, use
  `ArrayDeque` rather than either.
  :::
  :::accordion-item{label="29. HashSet, LinkedHashSet or TreeSet?" icon="i-lucide-message-circle"}
  All three drop duplicates. `HashSet` has no guaranteed order, `LinkedHashSet`
  keeps insertion order, `TreeSet` keeps sorted order (O(log n)).

  ```java [Sets.java]
  import java.util.*;

  public class Sets {
    public static void main(String[] args) {
      List<String> depts = List.of("MECH", "CSE", "IT", "ECE", "CSE", "AIML", "CIVIL");
      System.out.println(new HashSet<>(depts));
      System.out.println(new LinkedHashSet<>(depts));
      System.out.println(new TreeSet<>(depts));
    }
  }
  ```

  ```text [Output]
  [CIVIL, CSE, ECE, MECH, AIML, IT]
  [MECH, CSE, IT, ECE, AIML, CIVIL]
  [AIML, CIVIL, CSE, ECE, IT, MECH]
  ```
  :::
  :::accordion-item{label="30. Comparable or Comparator?" icon="i-lucide-message-circle"}
  `Comparable` is a class's one natural order, written inside it
  (`compareTo`). `Comparator` is any number of separate orders, written outside
  (`compare`), and chains nicely since Java 8.

  ```java [Sorting.java]
  import java.util.*;

  public class Sorting {
    record Student(String name, int marks) implements Comparable<Student> {
      @Override public int compareTo(Student other) {
        return name.compareTo(other.name);            // natural order: by name
      }
    }
    public static void main(String[] args) {
      List<Student> list = new ArrayList<>(List.of(
          new Student("Vikram", 64), new Student("Anita", 78), new Student("Farah", 92)));
      Collections.sort(list);
      System.out.println(list);
      list.sort(Comparator.comparingInt(Student::marks).reversed());
      System.out.println(list);
    }
  }
  ```

  ```text [Output]
  [Student[name=Anita, marks=78], Student[name=Farah, marks=92], Student[name=Vikram, marks=64]]
  [Student[name=Farah, marks=92], Student[name=Anita, marks=78], Student[name=Vikram, marks=64]]
  ```
  :::
  :::accordion-item{label="31. What is a ConcurrentModificationException, and how do you remove while iterating?" icon="i-lucide-message-circle"}
  The enhanced for loop uses an iterator that is fail-fast: if the list changes
  behind it (other than through the iterator), the next `next()` throws. Use
  `removeIf` or `iterator.remove()`.

  ```java [Cme.java]
  import java.util.*;

  public class Cme {
    public static void main(String[] args) {
      List<Integer> marks = new ArrayList<>(List.of(78, 35, 92, 20, 64));
      marks.removeIf(m -> m < 40);
      System.out.println(marks);
      for (Integer m : marks) {
        if (m == 78) marks.remove(m);
      }
    }
  }
  ```

  ```text [Output]
  [78, 92, 64]
  Exception in thread "main" java.util.ConcurrentModificationException
  	at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1095)
  	at java.base/java.util.ArrayList$Itr.next(ArrayList.java:1049)
  	at Cme.main(Cme.java:8)
  ```
  :::
  :::accordion-item{label="32. What does list.remove(2) do on a List of Integer?" icon="i-lucide-message-circle"}
  It removes the element at index 2, because `remove(int)` is an exact match and
  beats boxing to `remove(Object)`. To remove the value, pass an `Integer`.

  ```java [RemoveTrap.java]
  import java.util.*;

  public class RemoveTrap {
    public static void main(String[] args) {
      List<Integer> marks = new ArrayList<>(List.of(10, 20, 2, 30));
      marks.remove(2);                       // index 2
      System.out.println(marks);
      marks.remove(Integer.valueOf(20));     // the value 20
      System.out.println(marks);
    }
  }
  ```

  ```text [Output]
  [10, 20, 30]
  [10, 30]
  ```

## HashMap

::accordion
  :::accordion-item{label="33. How does a HashMap work internally?" icon="i-lucide-message-circle"}
  An array of buckets (16 by default). `put` computes the key's `hashCode`,
  spreads it, and picks a bucket by `hash & (capacity - 1)`. Keys that land in
  the same bucket (a collision) are kept in a linked list, which becomes a
  red-black tree once it holds more than 8 entries (and the table has at least
  64 buckets). `get` finds the bucket by hash, then compares with `equals`. When
  the map is 75% full (the load factor) it doubles and rehashes. Collisions are
  normal and handled:

  ```java [Collide.java]
  import java.util.*;

  public class Collide {
    public static void main(String[] args) {
      System.out.println("Aa".hashCode() + " " + "BB".hashCode());
      Map<String, String> m = new HashMap<>();
      m.put("Aa", "CSE");
      m.put("BB", "ECE");
      System.out.println(m.get("Aa") + " " + m.get("BB") + " size " + m.size());
      m.put(null, "unknown");
      System.out.println(m.get(null));
    }
  }
  ```

  ```text [Output]
  2112 2112
  CSE ECE size 2
  unknown
  ```

  Same hash, same bucket, and `equals` still tells them apart. A `null` key is
  allowed and always goes to bucket 0.
  :::
  :::accordion-item{label="34. Why should HashMap keys be immutable?" icon="i-lucide-message-circle"}
  If a key changes after it is inserted, its hash changes, and `get` looks in a
  different bucket. The entry is still in the map and can no longer be found.

  ```java [MutableKey.java]
  import java.util.*;

  public class MutableKey {
    public static void main(String[] args) {
      List<String> key = new ArrayList<>(List.of("CSE", "2026"));
      Map<List<String>, Integer> seats = new HashMap<>();
      seats.put(key, 120);
      key.add("A");                           // the key changes after insertion
      System.out.println(seats.get(key));
      System.out.println(seats.containsKey(key) + " but size is " + seats.size());
    }
  }
  ```

  ```text [Output]
  null
  false but size is 1
  ```

  That is why `String`, `Integer` and records make good keys.
  :::
  :::accordion-item{label="35. HashMap, Hashtable or ConcurrentHashMap?" icon="i-lucide-message-circle"}
  `HashMap`: not thread-safe, allows one `null` key and `null` values.
  `Hashtable`: legacy, every method synchronised on one lock, no nulls.
  `ConcurrentHashMap`: thread-safe with fine-grained locking so threads rarely
  wait for each other, no nulls. Use `HashMap` in one thread and
  `ConcurrentHashMap` across threads; never `Hashtable` in new code.

  ```java [NullKeys.java]
  import java.util.*;
  import java.util.concurrent.ConcurrentHashMap;

  public class NullKeys {
    public static void main(String[] args) {
      new HashMap<String, Integer>().put(null, 1);
      System.out.println("HashMap accepted a null key");
      try {
        new ConcurrentHashMap<String, Integer>().put(null, 1);
      } catch (NullPointerException e) {
        System.out.println("ConcurrentHashMap: NullPointerException");
      }
      try {
        new Hashtable<String, Integer>().put(null, 1);
      } catch (NullPointerException e) {
        System.out.println("Hashtable: NullPointerException");
      }
    }
  }
  ```

  ```text [Output]
  HashMap accepted a null key
  ConcurrentHashMap: NullPointerException
  Hashtable: NullPointerException
  ```
  :::

## Java 8

::accordion
  :::accordion-item{label="36. What is a functional interface? Name the common ones." icon="i-lucide-message-circle"}
  An interface with exactly one abstract method, so a lambda can implement it.
  `@FunctionalInterface` makes the compiler check it. The common ones:
  `Predicate<T>` (test, returns boolean), `Function<T,R>` (transform),
  `Consumer<T>` (use, returns nothing), `Supplier<T>` (produce from nothing).

  ```java [Lambdas.java]
  import java.util.function.*;

  public class Lambdas {
    @FunctionalInterface
    interface Grader { String grade(int marks); }

    public static void main(String[] args) {
      Grader g = marks -> marks >= 40 ? "PASS" : "FAIL";
      Predicate<Integer> distinction = m -> m >= 75;
      Function<String, Integer> length = String::length;
      Supplier<String> college = () -> "LNCT";
      System.out.println(g.grade(38) + " " + distinction.test(78) + " " + length.apply("Anita") + " " + college.get());
    }
  }
  ```

  ```text [Output]
  FAIL true 5 LNCT
  ```
  :::
  :::accordion-item{label="37. What is the difference between map and flatMap?" icon="i-lucide-message-circle"}
  `map` turns each element into exactly one element. `flatMap` turns each
  element into a stream and joins those streams into one.

  ```java [FlatMap.java]
  import java.util.*;

  public class FlatMap {
    public static void main(String[] args) {
      List<List<String>> electivesByDept = List.of(
          List.of("Cloud", "ML"), List.of("VLSI"), List.of("ML", "IoT"));
      System.out.println(electivesByDept.stream().map(List::size).toList());
      System.out.println(electivesByDept.stream().flatMap(List::stream).distinct().toList());
    }
  }
  ```

  ```text [Output]
  [2, 1, 2]
  [Cloud, ML, VLSI, IoT]
  ```
  :::
  :::accordion-item{label="38. Average marks per department, and pass or fail lists, with streams." icon="i-lucide-message-circle"}
  `groupingBy` builds a map from a key to a downstream result;
  `partitioningBy` splits into `true` and `false`.

  ```java [Group.java]
  import java.util.*;
  import java.util.stream.*;

  public class Group {
    record Student(String name, String dept, int marks) { }
    public static void main(String[] args) {
      List<Student> students = List.of(
          new Student("Anita", "CSE", 78), new Student("Vikram", "ECE", 64),
          new Student("Farah", "CSE", 92), new Student("Rohit", "ECE", 35));
      Map<String, Double> avg = students.stream().collect(
          Collectors.groupingBy(Student::dept, TreeMap::new, Collectors.averagingInt(Student::marks)));
      System.out.println(avg);
      Map<Boolean, List<String>> passed = students.stream().collect(
          Collectors.partitioningBy(s -> s.marks() >= 40,
              Collectors.mapping(Student::name, Collectors.toList())));
      System.out.println(passed);
    }
  }
  ```

  ```text [Output]
  {CSE=85.0, ECE=49.5}
  {false=[Rohit], true=[Anita, Vikram, Farah]}
  ```
  :::
  :::accordion-item{label="39. What is the difference between orElse and orElseGet on Optional?" icon="i-lucide-message-circle"}
  `orElse(x)` always evaluates `x`, even when the value is present.
  `orElseGet(supplier)` only calls the supplier when the Optional is empty.
  With an expensive default, the difference is real:

  ```java [Opt.java]
  import java.util.Optional;

  public class Opt {
    static String loadDefault() {
      System.out.println("  loadDefault() ran");
      return "Not allotted";
    }
    public static void main(String[] args) {
      Optional<String> hostel = Optional.of("Block C");
      System.out.println("orElse:");
      System.out.println(hostel.orElse(loadDefault()));
      System.out.println("orElseGet:");
      System.out.println(hostel.orElseGet(Opt::loadDefault));
    }
  }
  ```

  ```text [Output]
  orElse:
    loadDefault() ran
  Block C
  orElseGet:
  Block C
  ```
  :::
  :::accordion-item{label="40. Can a stream be reused?" icon="i-lucide-message-circle"}
  No. A stream is a one-time pipeline; after a terminal operation it is
  consumed. Create a new one from the source each time.

  ```java [Reuse.java]
  import java.util.stream.*;

  public class Reuse {
    public static void main(String[] args) {
      Stream<Integer> marks = Stream.of(78, 64, 92);
      System.out.println(marks.count());
      System.out.println(marks.count());
    }
  }
  ```

  ```text [Output]
  3
  Exception in thread "main" java.lang.IllegalStateException: stream has already been operated upon or closed
  	at java.base/java.util.stream.AbstractPipeline.evaluate(AbstractPipeline.java:229)
  	at java.base/java.util.stream.ReferencePipeline.count(ReferencePipeline.java:709)
  	at Reuse.main(Reuse.java:7)
  ```

## Multithreading

::accordion
  :::accordion-item{label="41. What is the difference between start() and run()?" icon="i-lucide-message-circle"}
  `start()` creates a new thread, which then calls `run()`. Calling `run()`
  yourself is an ordinary method call on the current thread.

  ```java [StartRun.java]
  public class StartRun {
    public static void main(String[] args) throws InterruptedException {
      Runnable task = () -> System.out.println("running on " + Thread.currentThread().getName());
      Thread t = new Thread(task, "results-worker");
      t.run();      // a plain method call
      t.start();    // a new thread
      t.join();
    }
  }
  ```

  ```text [Output]
  running on main
  running on results-worker
  ```

  Calling `start()` twice on the same thread throws `IllegalThreadStateException`.
  :::
  :::accordion-item{label="42. What is a race condition? Fix it two ways." icon="i-lucide-message-circle"}
  Two threads doing read, add, write on shared data at the same time, so some
  updates are lost. `count++` is three steps, not one. Fix it with
  `synchronized` or an atomic class:

  ```java [Race.java]
  import java.util.concurrent.atomic.AtomicInteger;

  public class Race {
    static int unsafeCount = 0;
    static int safeCount = 0;
    static AtomicInteger atomicCount = new AtomicInteger();

    static synchronized void safeIncrement() { safeCount++; }

    public static void main(String[] args) throws InterruptedException {
      Runnable markPapers = () -> {
        for (int i = 0; i < 100_000; i++) {
          unsafeCount++;
          safeIncrement();
          atomicCount.incrementAndGet();
        }
      };
      Thread t1 = new Thread(markPapers), t2 = new Thread(markPapers);
      t1.start(); t2.start();
      t1.join(); t2.join();
      System.out.println("unsafe:       " + unsafeCount);
      System.out.println("synchronized: " + safeCount);
      System.out.println("atomic:       " + atomicCount.get());
    }
  }
  ```

  ```text [Output]
  unsafe:       199947
  synchronized: 200000
  atomic:       200000
  ```

  The unsafe number is different on every run, and occasionally correct, which
  is what makes race conditions so hard to find.
  :::
  :::accordion-item{label="43. volatile or synchronized?" icon="i-lucide-message-circle"}
  `volatile` guarantees visibility: every read sees the latest write, so a
  `volatile boolean running` flag stops a worker thread reliably. It does not
  make `count++` atomic, because that is a read and a write. `synchronized`
  gives both mutual exclusion and visibility. For counters, `AtomicInteger` is
  the usual answer (above).

  ```java
  private volatile boolean resultsPublished = false;   // a flag: volatile is enough
  ```
  :::
  :::accordion-item{label="44. What is a deadlock and how do you avoid it?" icon="i-lucide-message-circle"}
  Two threads each hold one lock and wait for the lock the other holds, so both
  wait for ever. The standard fix is lock ordering: every thread takes the locks
  in the same order, so the cycle cannot form. A timed `tryLock` on a
  `ReentrantLock` is the other. `jstack <pid>` on a hung program prints
  `Found one Java-level deadlock` and the two threads.

  ```java
  // Both threads lock the lower roll number first, whatever the direction.
  Object first  = a.roll() < b.roll() ? a : b;
  Object second = a.roll() < b.roll() ? b : a;
  synchronized (first) { synchronized (second) { /* transfer */ } }
  ```
  :::
  :::accordion-item{label="45. Why use an ExecutorService instead of new Thread?" icon="i-lucide-message-circle"}
  Creating a thread is expensive and unbounded creation can exhaust the
  machine. A pool reuses a fixed number of threads, queues the rest, and gives
  back results through `Future`:

  ```java [Pool2.java]
  import java.util.concurrent.*;

  public class Pool2 {
    public static void main(String[] args) throws Exception {
      ExecutorService pool = Executors.newFixedThreadPool(2);
      Future<Integer> total = pool.submit(() -> 78 + 64 + 92);   // a Callable
      System.out.println("Total: " + total.get());               // waits for the result
      pool.shutdown();
      System.out.println("Terminated: " + pool.awaitTermination(1, TimeUnit.SECONDS));
    }
  }
  ```

  ```text [Output]
  Total: 234
  Terminated: true
  ```

  Forget `shutdown()` and the program never exits, because the pool's threads
  keep the JVM alive.
  :::
::

## JVM memory

::accordion
  :::accordion-item{label="46. What goes on the stack and what goes on the heap?" icon="i-lucide-message-circle"}
  The stack (one per thread) holds method frames: parameters, local variables,
  primitive values and references. The heap (shared) holds every object and
  array. So in `int[] marks = {78, 64};` inside a method, the variable `marks`
  (an address) is on the stack and the array is on the heap. Exhausting a stack
  gives `StackOverflowError`; exhausting the heap gives `OutOfMemoryError: Java
  heap space` (the JVM lesson showed both, the second after three 4 MB arrays
  with `-Xmx16m`).
  :::
  :::accordion-item{label="47. When is an object eligible for garbage collection?" icon="i-lucide-message-circle"}
  When no chain of references leads to it from a GC root (live local variables,
  static fields, active threads). Setting the only reference to `null`, pointing
  it elsewhere, or returning from the method that held it all qualify. You
  cannot force collection: `System.gc()` is only a request.

  ```java
  Student s = new Student("Vikram");
  s = null;                  // the Vikram object is now eligible
  ```
  :::

## JDBC and testing

::accordion
  :::accordion-item{label="48. Statement or PreparedStatement?" icon="i-lucide-message-circle"}
  `PreparedStatement`. Values go in separately from the SQL, so user input can
  never change the query. In the JDBC lesson, the search text
  `Nobody' OR '1'='1` concatenated into a `Statement` returned every student;
  the same text through a `PreparedStatement` found zero rows.

  ```java
  PreparedStatement ps = conn.prepareStatement("SELECT name FROM students WHERE name = ?");
  ps.setString(1, typedByUser);
  ```
  :::
  :::accordion-item{label="49. How do you do a transaction in JDBC?" icon="i-lucide-message-circle"}
  Turn off auto-commit, run the statements, commit if all succeed, roll back if
  any fail, and restore auto-commit in `finally`.

  ```java
  conn.setAutoCommit(false);
  try {
    recordFee.executeUpdate();
    debitWallet.executeUpdate();
    conn.commit();
  } catch (SQLException e) {
    conn.rollback();
  } finally {
    conn.setAutoCommit(true);
  }
  ```
  :::
  :::accordion-item{label="50. How do you test that a method throws?" icon="i-lucide-message-circle"}
  JUnit 5's `assertThrows`, which returns the exception so you can check its
  message:

  ```java
  IllegalArgumentException e = assertThrows(IllegalArgumentException.class,
      () -> Attendance.percentage(25, 24));
  assertEquals("Attended 25 of 24", e.getMessage());
  ```

  And say the habit: break the code once and watch the test fail, because a
  test that has never failed proves nothing.
