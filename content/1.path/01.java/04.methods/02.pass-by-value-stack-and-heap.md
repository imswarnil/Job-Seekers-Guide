`addBonus(total)` could not change the caller's `total`, and yet a method that
changes `marks[0]` changes the caller's array. Same syntax, opposite result.
This lesson draws the single most important picture in the track, and
`equals`, `NullPointerException` and "why did my list change" all rest on it.

## Why this matters in a job

"Is Java pass by value or pass by reference?" is one of the most asked Java
questions in fresher interviews, and most candidates get it half right. The bug
it explains (a method quietly changing data its caller still uses) is one of
the most common in real code. And you cannot reason about `null` until you know
what a reference is.

## Two kinds of variable

Think of a PG notice board. Some notices have the information written on them:
"Rent due on the 5th". Others say "Rules: see the sheet in the warden's
office". Photocopy the first kind and you have your own copy of the
information. Photocopy the second and you have a second note pointing at the
**same** sheet; if the warden changes the sheet, both notes lead to the change.

Java variables are the same:

- A **primitive** variable (`int`, `double`, `boolean` and the other five)
  holds the value itself.
- A **reference** variable (any array, `String`, `StringBuilder`, and every
  object you will create) holds an **address**: where the object lives in
  memory. The object itself is somewhere else.

Where is "somewhere else"? Java splits memory into two areas:

- The **stack** holds local variables and parameters. Each method call gets a
  block of it, called a **stack frame**, which disappears when the method
  returns.
- The **heap** holds objects. Everything created with `new` (and every array)
  lives here, and stays until nothing refers to it any more.

::pull-quote
A reference variable never holds an object. It holds the address of one.
Copying the variable copies the address, not the thing at the end of it.
::

## How it works

Watch the two kinds behave differently with identical-looking code:

```java [Copying.java]
import java.util.Arrays;

public class Copying {
  public static void main(String[] args) {
    // A primitive: the variable holds the value itself.
    int scoreA = 78;
    int scoreB = scoreA;          // copy the VALUE
    scoreB = 92;
    System.out.println("scoreA = " + scoreA);

    // An array is an object: the variable holds its address.
    int[] marksA = {78, 64, 81};
    int[] marksB = marksA;        // copy the ADDRESS
    marksB[0] = 92;
    System.out.println("marksA = " + Arrays.toString(marksA));
  }
}
```

```bash [Terminal]
javac Copying.java && java Copying
```

```text [Output]
scoreA = 78
marksA = [92, 64, 81]
```

### Pass by value, always

When you call a method, Java **copies the value of each argument** into the
parameter. That is **pass by value**, and Java does nothing else. The
confusion comes from what gets copied: for a primitive, the value; for an
array or object, the address.

```java [Passing.java]
import java.util.Arrays;

public class Passing {
  static void raise(int score) {
    score = 92;                        // changes the local copy only
  }

  static void raise(int[] marks) {
    marks[0] = 92;                     // follows the address, changes the array
  }

  static void replace(int[] marks) {
    marks = new int[] {0, 0, 0};       // points the LOCAL copy somewhere else
    marks[0] = 50;
  }

  public static void main(String[] args) {
    int score = 78;
    raise(score);
    System.out.println("after raise(int):   " + score);

    int[] marks = {78, 64, 81};
    raise(marks);
    System.out.println("after raise(int[]): " + Arrays.toString(marks));

    replace(marks);
    System.out.println("after replace:      " + Arrays.toString(marks));
  }
}
```

```text [Output]
after raise(int):   78
after raise(int[]): [92, 64, 81]
after replace:      [92, 64, 81]
```

### Stack frames

Each method call pushes a frame onto the stack holding its parameters and
local variables. When the method returns, the frame is popped and those
variables are gone. The heap objects they pointed to survive as long as
something else still points at them.

## Real use case

This is how the bug looks in real code. A method is written to compute the
median mark. To find a median you sort, and `Arrays.sort` sorts **in place**:
it changes the array it is given.

```java [Median.java]
import java.util.Arrays;

public class Median {
  // WRONG: sorts the caller's array as a side effect.
  static double medianWrong(int[] marks) {
    Arrays.sort(marks);
    int mid = marks.length / 2;
    return marks.length % 2 == 1 ? marks[mid] : (marks[mid - 1] + marks[mid]) / 2.0;
  }

  // RIGHT: sorts a copy; the caller's array is untouched.
  static double median(int[] marks) {
    int[] sorted = marks.clone();
    Arrays.sort(sorted);
    int mid = sorted.length / 2;
    return sorted.length % 2 == 1 ? sorted[mid] : (sorted[mid - 1] + sorted[mid]) / 2.0;
  }

  public static void main(String[] args) {
    String[] names = {"Anita", "Vikram", "Farah", "Rohit"};
    int[] marks    = {78, 55, 92, 64};     // matched to names by position

    System.out.println("Median: " + medianWrong(marks));
    for (int i = 0; i < names.length; i++) {
      System.out.println(names[i] + " " + marks[i]);
    }
  }
}
```

```text [Output]
Median: 71.0
Anita 55
Vikram 64
Farah 78
Rohit 92
```

The median is right. Every student now has somebody else's marks. Anita scored
78 and the report says 55. Nothing crashed, nothing warned, and the method was
called `median`, which does not sound like something that rearranges your data.
Swap `medianWrong` for `median` and the names and marks stay matched.

::real-life{title="How this reaches production" source="A results-processing job"}
One person writes the helper, another calls it six months later. The caller
assumes a method called `median` reads the data; the helper changes it. The
rule that prevents the whole category: **a method should not change its
arguments unless its name says so** (`sortMarks`, `fillDefaults`). When in
doubt, work on a copy.
::

## What confuses people here

### What `null` is

`null` is not zero and not empty. It is a reference that points at nothing.

```java [NullRef.java]
public class NullRef {
  public static void main(String[] args) {
    int[] marks = null;                // a variable that points at nothing
    System.out.println(marks.length);
  }
}
```

```text [Output]
Exception in thread "main" java.lang.NullPointerException: Cannot read the array length because "<local1>" is null
	at NullRef.main(NullRef.java:4)
```

Read the message literally and it is complete: you tried to follow an address
that is not an address. (Compile with `javac -g` and it names the variable,
`"marks"`, instead of `<local1>`.) A primitive can never be `null`, because it
holds a value, not an address: `int score = null;` does not compile.

### Strings look like primitives and are not

Predict each line before reading the output.

```java [Predict.java]
public class Predict {
  public static void main(String[] args) {
    String s = "Anita";
    change(s);
    System.out.println(s);

    StringBuilder sb = new StringBuilder("Anita");
    change(sb);
    System.out.println(sb);

    int a = 1, b = 2;
    swap(a, b);
    System.out.println(a + " " + b);
  }

  static void change(String s) { s = s + " Rao"; }
  static void change(StringBuilder sb) { sb.append(" Rao"); }
  static void swap(int x, int y) { int t = x; x = y; y = t; }
}
```

```text [Output]
Anita
Anita Rao
1 2
```

::compare{caption="What matters is not whether you passed an object. It is whether the method changed the object or reassigned its own variable."}
  :::compare-side{label="Reassigns the parameter" verdict="wrong"}
  `s = s + " Rao"` builds a **new** String (Strings are immutable) and points
  the local copy at it. The caller never sees it. Same for `swap(int, int)`:
  it swaps two copies.
  :::
  :::compare-side{label="Mutates the object" verdict="right"}
  `sb.append(" Rao")` follows the address and changes the object that the
  caller's variable also points at. The caller sees it.
  :::
::

::tip
That is why a `swap(int a, int b)` method cannot be written in Java. To swap two
values from a method, pass the array that holds them and swap the elements:
`swap(int[] arr, int i, int j)`.
::

## Interview questions

::accordion
  :::accordion-item{label="Is Java pass by value or pass by reference?" icon="i-lucide-message-circle"}
  Always pass by value. For an object, the value copied is the reference, so the
  method can follow it and change the object. The proof: assign a new object
  to the parameter inside the method and the caller sees nothing.
  `replace(marks)` above assigns a new array and the caller's `marks` is still
  `[92, 64, 81]`. Under pass by reference it would have been replaced.
  :::
  :::accordion-item{label="What is stored on the stack and what on the heap?" icon="i-lucide-message-circle"}
  The stack holds method frames: parameters and local variables, including
  primitive values and references. The heap holds objects and arrays. Each
  thread has its own stack; all threads share one heap. A stack frame is freed
  the moment its method returns; a heap object is freed by the garbage
  collector once nothing refers to it.
  :::
  :::accordion-item{label="Why can you not write a swap(int, int) method in Java?" icon="i-lucide-message-circle"}
  The method receives copies of the two values. Swapping the copies does not
  touch the caller's variables, as `swap(a, b)` printing `1 2` shows. Swap
  inside an array instead, or return the swapped pair.
  :::
  :::accordion-item{label="Why did change(String) not change the caller's string when change(StringBuilder) did?" icon="i-lucide-message-circle"}
  `String` is immutable, so `s + " Rao"` creates a new String and reassigns
  the local parameter. `StringBuilder` is mutable, so `append` changes the
  shared object in place.
  :::
  :::accordion-item{label="Can a primitive be null?" icon="i-lucide-message-circle"}
  No. `int score = null;` is a compile error, because a primitive holds a
  value, not a reference. Its wrapper `Integer` can be `null`, which causes a
  sneaky `NullPointerException` when it is unboxed; the wrapper classes lesson
  shows it.
  :::
::
