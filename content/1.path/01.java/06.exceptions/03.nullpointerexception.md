One exception is more common than every other put together. A
**`NullPointerException`** (NPE) is thrown when you use a reference that points
at nothing: call a method on it, read a field, take its length. Every Java
programmer meets it in the first week, and many never get past scattering
`if (x != null)` everywhere until it stops.

## Why this matters in a job

It is the most frequent exception in production Java logs, so reading one
quickly is a daily skill. Modern Java tells you far more about an NPE than most
people realise. And the good fixes are about **never having the null** rather
than checking for it, which is exactly what a senior reviewer will push you
towards. In interviews: "what is a NullPointerException, how do you avoid it?",
"what is `Objects.requireNonNull` for?", and "why is `"CSE".equals(dept)` safer
than `dept.equals("CSE")`?"

## An address with no house

A reference variable holds an address (the stack-and-heap lesson). `null` is an
address that leads nowhere: a letter addressed to a plot of land with no house
on it. Nothing goes wrong while the letter sits in your hand. It goes wrong
when you try to **deliver** it: knock on the door, read the nameplate, count
the rooms. In Java, "delivering" is using the dot (`.`), taking `.length` of an
array, indexing into it, or unboxing a wrapper.

## How it works

Since Java 14, the message names the exact expression that was null. This
matters most in a chain:

```java [Chain.java]
public class Chain {
  public static void main(String[] args) {
    Department cse = new Department("Computer Science", new Faculty("K. Menon"));
    Department mech = new Department("Mechanical", null);     // HOD not yet appointed

    Student anita = new Student("Anita Rao", cse);
    Student rohit = new Student("Rohit Das", mech);

    System.out.println(anita.getDepartment().getHod().getName().toUpperCase());
    System.out.println(rohit.getDepartment().getHod().getName().toUpperCase());
  }
}

class Faculty {
  private final String name;
  Faculty(String name) { this.name = name; }
  String getName() { return name; }
}

class Department {
  private final String title;
  private final Faculty hod;
  Department(String title, Faculty hod) { this.title = title; this.hod = hod; }
  Faculty getHod() { return hod; }
}

class Student {
  private final String name;
  private final Department department;
  Student(String name, Department department) { this.name = name; this.department = department; }
  Department getDepartment() { return department; }
}
```

```bash [Terminal]
javac Chain.java && java Chain
```

```text [Output]
K. MENON
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "Faculty.getName()" because the return value of "Department.getHod()" is null
	at Chain.main(Chain.java:10)
```

Four things on line 10 could have been null: the student, the department, the
HOD, the name. The message says exactly which: the return value of
`getHod()`. Before Java 14 you got only the line number, and finding which of
the four took a debugger.

::pull-quote
"Cannot invoke X because Y is null" is a complete diagnosis. Read the whole
sentence and you will rarely need a debugger for an NPE again.
::

::side-note{kind="go-deeper"}
For local variables the message shows `"<local1>"` unless the class was
compiled with `javac -g`, which keeps variable names. Method return values and
fields (`"Department.getHod()"`, `"this.rollNumber"`) are always named. IDEs and
build tools such as Maven compile with names by default.
::

### Where nulls hide

::feature-list{columns="2"}
  :::feature{icon="i-lucide-box" title="Fields never assigned"}
  An object field starts as `null` until something sets it.
  :::
  :::feature{icon="i-lucide-grid-3x3" title="Arrays of objects"}
  `new String[3]` is three nulls, not three empty strings.
  :::
  :::feature{icon="i-lucide-search-x" title="Lookups that find nothing"}
  `map.get(key)` for a missing key returns `null`.
  :::
  :::feature{icon="i-lucide-database" title="Outside data"}
  A database column that allows NULL, a missing JSON field, an empty form box.
  :::
::

The sneakiest one has no dot on the line at all: **unboxing**.

```java [HiddenNulls.java]
public class HiddenNulls {
  public static void main(String[] args) {
    String[] names = new String[3];         // three nulls, not three empty strings
    names[0] = "Anita";
    for (String n : names) {
      System.out.print((n == null ? "null" : n.length()) + " ");
    }
    System.out.println();

    Integer scholarshipPct = null;          // no scholarship recorded
    boolean topper = false;
    int pct = topper ? 50 : scholarshipPct; // unboxing inside a ternary
    System.out.println(pct);
  }
}
```

```text [Output]
5 null null 
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.lang.Integer.intValue()" because "<local2>" is null
	at HiddenNulls.main(HiddenNulls.java:12)
```

`intValue()` appears nowhere in the code. Java inserted it to turn the
`Integer` into an `int`, the unboxing trap from the wrapper classes lesson.

## Real use case

The instinct is to add a check at the line that crashed. That hides the
symptom and leaves the invalid data in circulation. The better fixes, in the
order I would reach for them:

### 1. Do not allow the null in the first place

```java [RequireNonNull.java]
import java.util.Objects;

public class RequireNonNull {
  public static void main(String[] args) {
    Student ok = new Student("Anita Rao", "CSE1801");
    System.out.println(ok.name + " " + ok.rollNumber);

    Student bad = new Student(null, "CSE1802");    // fails HERE, at the cause
  }
}

class Student {
  final String name;
  final String rollNumber;

  Student(String name, String rollNumber) {
    this.name = Objects.requireNonNull(name, "name must not be null");
    this.rollNumber = Objects.requireNonNull(rollNumber, "rollNumber must not be null");
  }
}
```

```text [Output]
Anita Rao CSE1801
Exception in thread "main" java.lang.NullPointerException: name must not be null
	at java.base/java.util.Objects.requireNonNull(Objects.java:259)
	at Student.<init>(RequireNonNull.java:17)
	at RequireNonNull.main(RequireNonNull.java:8)
```

It still throws an NPE, and that is the point: it throws at **construction**,
with a message, at the line that caused the problem. Without it, the null would
sit inside the object until some report, weeks later and far away, tried to
print the name. This is **fail fast**, and it is the highest-value fix.

### 2. Return an empty array or list, never null

```java [EmptyNotNull.java]
public class EmptyNotNull {
  public static void main(String[] args) {
    for (String s : electivesEmpty("MECH")) System.out.println(s);
    System.out.println("empty array: loop ran zero times, no crash");

    for (String s : electivesNull("MECH")) System.out.println(s);
  }

  static String[] electivesEmpty(String dept) {
    if (dept.equals("CSE")) return new String[] {"Cloud", "ML"};
    return new String[0];                   // nothing to offer: an empty array
  }

  static String[] electivesNull(String dept) {
    if (dept.equals("CSE")) return new String[] {"Cloud", "ML"};
    return null;                            // every caller must now remember to check
  }
}
```

```text [Output]
empty array: loop ran zero times, no crash
Exception in thread "main" java.lang.NullPointerException: Cannot read the array length because "<local1>" is null
	at EmptyNotNull.main(EmptyNotNull.java:6)
```

An empty collection loops zero times, which is the correct behaviour. "Return
an empty collection, never null" removes a null check from every caller,
forever.

### 3. Compare with the known value first, or use Objects

```java [SafeEquals.java]
import java.util.Objects;

public class SafeEquals {
  public static void main(String[] args) {
    String dept = null;                     // not chosen yet

    System.out.println("CSE".equals(dept));           // literal first: safe
    System.out.println(Objects.equals(dept, "CSE"));  // both may be null: safe
    System.out.println(Objects.requireNonNullElse(dept, "UNDECIDED"));
    System.out.println(dept.equals("CSE"));           // variable first: NPE
  }
}
```

```text [Output]
false
false
UNDECIDED
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.equals(Object)" because "<local1>" is null
	at SafeEquals.main(SafeEquals.java:10)
```

### 4. Say "might be absent" in the type

When a value can legitimately be missing (a search that may find nothing), Java
8 added **`Optional`**, a box that is either empty or holds one value, which
forces the caller to deal with both. It has its own lesson in the Java 8
chapter.

::flow{numbered direction="vertical" caption="Working backwards from an NPE. The crash site is rarely the cause."}
  :::flow-step{label="Read the message for which value is null" icon="i-lucide-text"}
  It names the exact expression. No guessing.
  :::
  :::flow-step{label="Find where that value was set" icon="i-lucide-search" highlight}
  Loaded from a column that was NULL? Built by a constructor that did not
  require it? A setter that was never called?
  :::
  :::flow-step{label="Decide whether absence is legitimate" icon="i-lucide-scale"}
  If every department must have an HOD, the bug is upstream, and the fix is a
  `requireNonNull` in the constructor, not a check on line 10.
  :::
  :::flow-step{label="Fix it there, not at the crash" icon="i-lucide-wrench"}
  A check at the crash makes the symptom disappear and leaves the bad object
  for the next twelve places to trip over.
  :::
::

::real-life{title="The NPE you will meet at work" source="A service reading from a database"}
A report crashes on `student.getDepartment().getTitle()`. The code is fine; one
row in the `students` table has `department_id` set to NULL because it was
inserted by a one-off script. The fix is a `NOT NULL` constraint in the
database (the DBMS track) and a `requireNonNull` in the constructor, so a bad
row fails loudly on load rather than quietly on display.
::

## What confuses people here

::compare{caption="The instinct, and the problem with it."}
  :::compare-side{label="Check and carry on" verdict="wrong"}
  ```java
  if (s != null && s.getDepartment() != null
      && s.getDepartment().getHod() != null) {
    print(s.getDepartment().getHod().getName());
  }
  ```
  Three checks to read one name, repeated at every call site, and it silently
  prints nothing when data is missing. The next reader cannot tell whether a
  null is expected or a bug.
  :::
  :::compare-side{label="Decide what null means" verdict="right"}
  For each value ask: can this legitimately be absent? If not, make it
  impossible (`requireNonNull`, a `final` field set in the constructor). If
  yes, say so in the type (`Optional`) and handle it once.
  :::
::

- **`null` is not an empty string.** `""` is a real `String` of length 0;
  `null` is no `String` at all. `"".length()` is 0; `null.length()` throws.
- **`instanceof` never throws on null**; `null instanceof Student` is `false`.
  `switch` on a null `String` does throw.
- **Catching `NullPointerException`** is almost always wrong. It is a bug to
  fix, not a condition to handle.
- **`String.valueOf(null object)`** returns the text `"null"`, and
  `"Name: " + null` gives `"Name: null"`. Neither throws, which is how the word
  "null" ends up printed on a certificate.

## Interview questions

::accordion
  :::accordion-item{label="What is a NullPointerException and when is it thrown?" icon="i-lucide-message-circle"}
  An unchecked exception thrown when code uses a `null` reference as if it
  pointed at an object: calling a method or reading a field on it, reading an
  array's length or element, unboxing a null wrapper, or throwing `null`.
  Since Java 14 the message names the exact null expression.
  :::
  :::accordion-item{label="How do you avoid NullPointerExceptions?" icon="i-lucide-message-circle"}
  Fail fast with `Objects.requireNonNull` in constructors so invalid objects
  cannot exist; return empty collections instead of null; compare with the
  constant first (`"CSE".equals(dept)`) or `Objects.equals`; use `Optional` as
  the return type when absence is legitimate; and keep fields `final` and set
  in the constructor.
  :::
  :::accordion-item{label="What does Objects.requireNonNull do, if it throws an NPE anyway?" icon="i-lucide-message-circle"}
  It moves the failure to the moment the null enters the object, with your
  message ("name must not be null"), instead of weeks later wherever the value
  is first used. The stack trace then points at the cause, not the victim.
  :::
  :::accordion-item{label="Why is 'CSE'.equals(dept) safer than dept.equals('CSE')?" icon="i-lucide-message-circle"}
  The string literal is never null, so calling `equals` on it cannot throw; it
  returns `false` for a null argument. Calling `equals` on `dept` throws when
  `dept` is null, as `SafeEquals.java` showed.
  :::
  :::accordion-item{label="Can unboxing cause a NullPointerException?" icon="i-lucide-message-circle"}
  Yes. Assigning a null `Integer` to an `int`, comparing it with `>`, or using
  it in a ternary alongside an `int` calls `intValue()` on null.
  `int pct = topper ? 50 : scholarshipPct;` threw with no dot in the
  expression.
  :::
::
