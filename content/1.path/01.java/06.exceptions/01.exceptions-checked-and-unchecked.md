The last lesson threw a `NumberFormatException` for the word "eighty" and a
`NullPointerException` from a missing map entry. An **exception** is an object
Java throws when something goes wrong, and it stops the normal flow of the
program until something **catches** it. This chapter is how to read them, catch
them and throw your own.

## Why this matters in a job

Your first weeks on a real project are largely spent reading stack traces:
from the logs, from a failed build, from a tester's bug report. Exception
handling is also where junior code does the most damage, with one line:
`catch (Exception e) { }`. In interviews: "checked versus unchecked?", "throw
versus throws?", "does finally always run?" and "can we have try without
catch?" come up at almost every level.

## An exception is a complaint that travels upwards

At a college, a clerk finds a problem with your form (a missing signature).
She cannot fix it, so she passes the complaint up to the section officer. If he
cannot deal with it, it goes to the registrar. If nobody deals with it, the
admission stops.

In Java, a method that hits a problem **throws** an exception. It travels back
up the chain of method calls (the **call stack**) until a method **catches**
it. If nothing catches it, the program stops and prints a **stack trace**: the
exception, its message, and the chain of calls it travelled through.

```java [Uncaught.java]
public class Uncaught {
  public static void main(String[] args) {
    int[] attended = {36, 28, 30};
    int[] held = {40, 40, 0};                 // a new section: no classes yet
    for (int i = 0; i < attended.length; i++) {
      System.out.println("Section " + i + ": " + percentage(attended[i], held[i]) + "%");
    }
    System.out.println("Report done");
  }

  static int percentage(int attended, int held) {
    return attended * 100 / held;
  }
}
```

```text [Output]
Section 0: 90%
Section 1: 70%
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at Uncaught.percentage(Uncaught.java:12)
	at Uncaught.main(Uncaught.java:6)
```

::code-trace{caption="How to read any stack trace, top to bottom."}
```text [Output]
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at Uncaught.percentage(Uncaught.java:12)
```

report.

## Syntax

```java
try {
  // code that might throw
} catch (SomeException e) {
  // runs only if SomeException (or a subclass) was thrown in the try
} finally {
  // runs whatever happens: after try, or after catch
}
```

```java [TryCatch.java]
public class TryCatch {
  public static void main(String[] args) {
    String[] typed = {"78", "eighty", "92"};
    int total = 0;
    for (String t : typed) {
      try {
        System.out.println("try: parsing " + t);
        total += Integer.parseInt(t);
        System.out.println("try: added");
      } catch (NumberFormatException e) {
        System.out.println("catch: " + e.getMessage());
      } finally {
        System.out.println("finally: runs either way");
      }
    }
    System.out.println("Total of valid marks: " + total);
  }
}
```

```bash [Terminal]
javac TryCatch.java && java TryCatch
```

```text [Output]
try: parsing 78
try: added
finally: runs either way
try: parsing eighty
catch: For input string: "eighty"
finally: runs either way
try: parsing 92
try: added
finally: runs either way
Total of valid marks: 170
```

When "eighty" failed, the rest of the `try` block ("try: added") was skipped,
the `catch` ran, `finally` ran, and the loop carried on to 92.

| | Checked | Unchecked (`RuntimeException` and its children) |
| --- | --- | --- |
| Compiler forces you to handle it | **Yes** | No |
| Usually means | Something outside your program failed | A bug in the code |
| Examples | `IOException`, `FileNotFoundException`, `SQLException` | `NullPointerException`, `ArithmeticException`, `ArrayIndexOutOfBoundsException`, `NumberFormatException`, `IllegalArgumentException` |
| What to do | Catch it, or declare it with `throws` | Fix the code so it cannot happen |

An **`Error`** (such as `OutOfMemoryError` or `StackOverflowError`) is a
problem with the JVM itself. It is technically unchecked, and you should not
catch it: there is nothing sensible to do.

### Checked: the compiler insists

Reading a file can fail for reasons your code cannot prevent (the file is
missing, the disk is full). Java makes you decide what to do:

```java [Unreported.java]
import java.nio.file.Files;
import java.nio.file.Path;

public class Unreported {
  public static void main(String[] args) {
    String results = Files.readString(Path.of("results.csv"));
    System.out.println(results);
  }
}
```

```text [Output]
Unreported.java:6: error: unreported exception IOException; must be caught or declared to be thrown
    String results = Files.readString(Path.of("results.csv"));
                                     ^
1 error
```

"Caught or declared" are your two choices: wrap it in `try`/`catch`, or add
`throws IOException` to your method so your caller has to decide.

```java [ReadResults.java]
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.NoSuchFileException;
import java.nio.file.Path;

public class ReadResults {
  public static void main(String[] args) {
    try {
      System.out.println(load("results-2018.csv"));
    } catch (NoSuchFileException e) {
      System.out.println("No such file: " + e.getMessage() + ". Ask the exam cell to upload it.");
    } catch (IOException e) {
      System.out.println("Could not read the file: " + e);
    }
  }

  // "throws" declares it: the caller must deal with it
  static String load(String name) throws IOException {
    return Files.readString(Path.of(name));
  }
}
```

```text [Output]
No such file: results-2018.csv. Ask the exam cell to upload it.
```

Catch blocks are checked **top to bottom**, and the first match wins. So the
most specific exception goes first. `NoSuchFileException` is a child of
`IOException`; put `IOException` first and the compiler refuses:
`exception NoSuchFileException has already been caught`.

### throw against throws

::compare{caption="One letter apart, completely different jobs."}
  :::compare-side{label="throw" verdict="right"}
  A **statement** that throws one exception object now:
  `throw new IllegalArgumentException("Marks must be 0 to 100, got " + marks);`
  :::
  :::compare-side{label="throws" verdict="right"}
  Part of a **method signature** that warns callers which checked exceptions
  may come out: `static String load(String name) throws IOException`.
  :::
::

```java [ThrowDemo.java]
public class ThrowDemo {
  public static void main(String[] args) {
    System.out.println(grade(78));
    System.out.println(grade(140));
  }

  static String grade(int marks) {
    if (marks < 0 || marks > 100) {
      throw new IllegalArgumentException("Marks must be 0 to 100, got " + marks);  // throw: do it now
    }
    return marks >= 40 ? "PASS" : "FAIL";
  }
}
```

```text [Output]
PASS
Exception in thread "main" java.lang.IllegalArgumentException: Marks must be 0 to 100, got 140
	at ThrowDemo.grade(ThrowDemo.java:9)
	at ThrowDemo.main(ThrowDemo.java:4)
```

### Multi-catch

When two exceptions need the same handling, catch them together with `|`:

```java [MultiCatch.java]
public class MultiCatch {
  public static void main(String[] args) {
    String[] rows = {"CSE1801,78", "CSE1802", "CSE1803,abc"};
    for (String row : rows) {
      try {
        String[] parts = row.split(",");
        int marks = Integer.parseInt(parts[1]);
        System.out.println(parts[0] + " -> " + marks);
      } catch (ArrayIndexOutOfBoundsException | NumberFormatException e) {
        System.out.println("Bad row '" + row + "': " + e.getClass().getSimpleName());
      }
    }
  }
}
```

```text [Output]
CSE1801 -> 78
Bad row 'CSE1802': ArrayIndexOutOfBoundsException
Bad row 'CSE1803,abc': NumberFormatException
```

## Real use case

An exam cell uploads a CSV of marks every semester, and some rows are always
wrong. The version that dies on the first bad row is useless; the version that
imports the good rows and reports the bad ones with line numbers is the one
that ships.

```java [ImportMarks.java]
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class ImportMarks {
  public static void main(String[] args) {
    Path file = Path.of("data/marks.csv");

    String[] lines;
    try {
      lines = Files.readString(file).split("\n");   // checked: IOException
    } catch (IOException e) {
      System.out.println("Cannot read " + file + ": " + e);
      return;
    }

    int imported = 0;
    StringBuilder rejected = new StringBuilder();
    for (int i = 0; i < lines.length; i++) {
      String line = lines[i];
      try {
        String[] parts = line.split(",");
        if (parts.length != 2) {
          throw new IllegalArgumentException("expected 2 columns, got " + parts.length);
        }
        int marks = Integer.parseInt(parts[1].strip());
        if (marks < 0 || marks > 100) {
          throw new IllegalArgumentException("marks out of range: " + marks);
        }
        imported++;
      } catch (IllegalArgumentException e) {        // NumberFormatException is one of these
        rejected.append("  rejected line ").append(i + 1)
                .append(" (").append(line).append("): ").append(e.getMessage()).append('\n');
      }
    }

    System.out.println("Imported " + imported + " of " + lines.length);
    System.out.print(rejected);
  }
}
```

```text [data/marks.csv]
CSE1801,78
CSE1802,sixty
CSE1803
CSE1804,92
CSE1805,140
```

```text [Output]
Imported 2 of 5
  rejected line 2 (CSE1802,sixty): For input string: "sixty"
  rejected line 3 (CSE1803): expected 2 columns, got 1
  rejected line 5 (CSE1805,140): marks out of range: 140
```

Two different levels of failure, handled at two different places. A missing
file stops the whole job (nothing to import). A bad row is recorded and the job
carries on. `NumberFormatException` extends `IllegalArgumentException`, so one
`catch` handles both kinds of bad row.

::warning{icon="i-lucide-alert-triangle"}
**The line that does the damage:**

```java
try {
  importMarks(file);
} catch (Exception e) {
  // ignore
}
```

It catches everything, including bugs, throws away the reason, and carries on
as if the work succeeded. The results page is empty and there is no trace
anywhere of why. If you must catch broadly, log the exception object itself
(`log.error("Import failed for {}", file, e)`, not `e.getMessage()`, which loses
the stack trace) and say in a comment why carrying on is correct.
::

## What confuses people here

### Does finally always run?

The trick question, and the honest answer is "almost".

```java [FinallyEdges.java]
public class FinallyEdges {
  public static void main(String[] args) {
    System.out.println("tricky() returned " + tricky());
    System.out.println("swallow() returned " + swallow());
    try {
      System.out.println("about to exit");
      System.exit(0);
    } finally {
      System.out.println("finally after exit");   // never printed
    }
  }

  @SuppressWarnings("finally")
  static int tricky() {
    try {
      return 1;
    } finally {
      return 2;                   // replaces the 1
    }
  }

  @SuppressWarnings("finally")
  static int swallow() {
    try {
      throw new IllegalStateException("real problem");
    } finally {
      return 0;                   // the exception vanishes
    }
  }
}
```

```text [Output]
tricky() returned 2
swallow() returned 0
about to exit
```

- `finally` runs after the `return` value is worked out, and a `return` inside
  `finally` **replaces** it. Worse, in `swallow()` it made a thrown exception
  disappear completely. Never `return` from `finally`; the compiler warns about
  it for this reason.
- `finally` does **not** run after `System.exit()`, or if the JVM process is
  killed or crashes.
- **`try` without `catch` is legal** if it has a `finally` (or is a
  try-with-resources, next lesson). `try` with neither is a compile error.
- **Catching `Exception` also catches every `RuntimeException`**, so a
  `NullPointerException` from your own bug gets handled as if it were a network
  failure.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between checked and unchecked exceptions?" icon="i-lucide-message-circle"}
  Checked exceptions extend `Exception` but not `RuntimeException`, and the
  compiler forces you to catch or declare them: `unreported exception
  IOException; must be caught or declared to be thrown`. They represent
  failures outside the program's control. Unchecked exceptions extend
  `RuntimeException`, need no handling, and usually mean a bug: `/ by zero`,
  a null reference, an index out of range.
  :::
  :::accordion-item{label="What is the difference between throw and throws?" icon="i-lucide-message-circle"}
  `throw` is a statement that throws one exception object right now:
  `throw new IllegalArgumentException(...)`. `throws` is a clause in a method
  signature listing the checked exceptions the method may pass to its caller:
  `String load(String name) throws IOException`.
  :::
  :::accordion-item{label="Does finally always execute?" icon="i-lucide-message-circle"}
  Almost always: after a normal `try`, after a `catch`, and even after a
  `return` in the `try`. It does not run if `System.exit()` is called or the
  JVM dies. A `return` in `finally` overrides the `try`'s return value and can
  swallow an exception, as `tricky()` returning 2 and `swallow()` returning 0
  show.
  :::
  :::accordion-item{label="Can we have try without catch? Multiple catch blocks?" icon="i-lucide-message-circle"}
  `try` with only `finally` is legal, and so is try-with-resources with no
  `catch`. A `try` must have at least one `catch` or a `finally`. Multiple
  `catch` blocks are allowed and are checked in order, so the most specific
  goes first; the reverse order is a compile error (`has already been caught`).
  :::
  :::accordion-item{label="What is wrong with catch (Exception e) {}?" icon="i-lucide-message-circle"}
  It catches bugs (every `RuntimeException`) as well as genuine failures,
  discards the stack trace, and lets the program carry on as if the work
  succeeded. Catch the specific type you can handle, log the exception object
  (not only its message), and let anything else propagate.
  :::
  :::accordion-item{label="What is the difference between an Error and an Exception?" icon="i-lucide-message-circle"}
  Both extend `Throwable`. An `Error` is a serious problem with the JVM
  (`OutOfMemoryError`, `StackOverflowError`) that an application should not try
  to recover from. An `Exception` is a condition a program might reasonably
  catch and handle.
  :::
::
