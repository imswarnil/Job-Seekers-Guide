A file or database connection opened in a `try` has to be closed even when an
exception is thrown, and Java's built-in exceptions do not know what a
duplicate application is. This lesson fixes both: **try-with-resources**
closes things for you, and **custom exceptions** let you name your own
failures.

## Why this matters in a job

A resource leak (a file, socket or database connection that is opened and
never closed) does not fail at once. It fails after four hours of real traffic
with "too many open files" or "connection pool exhausted", and the stack trace
points at whatever was unlucky enough to be next. Every code reviewer checks
for try-with-resources. And in any real service, the errors a user can see
("already applied", "fee already paid") are custom exceptions. Interviewers
ask how you would create one, whether it should be checked, and what
"exception chaining" means.

## A register that signs itself back in

At a college library, every register you borrow has to be returned, even if
you are called away halfway through. Imagine a register that walks itself back
to the desk the moment you leave the room, whatever the reason you left. That
is try-with-resources: anything opened in its brackets is **closed
automatically** when the block ends, normally or by an exception.

A **resource** is any object that must be closed after use: files, network
connections, database connections, scanners. To work with try-with-resources,
its class must implement the interface **`AutoCloseable`**, which has one
method: `close()`.

## Syntax

```java
try (Type resource = new Type(...);
     Type another  = new Type(...)) {
  // use them
} catch (SomeException e) {
  // optional
}
// both are closed here, in reverse order, whatever happened
```

```java [Register.java]
public class Register {
  public static void main(String[] args) {
    try (AttendanceRegister cse = new AttendanceRegister("CSE-A");
         AttendanceRegister ece = new AttendanceRegister("ECE-B")) {
      cse.mark("CSE1801");
      ece.mark("ECE1804");
      throw new IllegalStateException("power cut in the lab");
    } catch (IllegalStateException e) {
      System.out.println("caught: " + e.getMessage());
    }
    System.out.println("both registers were closed before the catch ran");
  }
}

class AttendanceRegister implements AutoCloseable {
  private final String section;

  AttendanceRegister(String section) {
    this.section = section;
    System.out.println("open " + section);
  }

  void mark(String roll) { System.out.println("  " + section + ": " + roll + " present"); }

  @Override
  public void close() {
    System.out.println("close " + section);
  }
}
```

```bash [Terminal]
javac Register.java && java Register
```

```text [Output]
open CSE-A
open ECE-B
  CSE-A: CSE1801 present
  ECE-B: ECE1804 present
close ECE-B
close CSE-A
caught: power cut in the lab
both registers were closed before the catch ran
```

Three things to see: the resources closed in **reverse** order of opening (the
last one opened depends on nothing opened after it); they closed **before**
the `catch` ran; and there is no `finally` anywhere.

::compare{caption="The same file read, before and after Java 7."}
  :::compare-side{label="finally, by hand" verdict="wrong"}
  ```java
  BufferedReader reader = null;
  try {
    reader = Files.newBufferedReader(file);
    // read
  } finally {
    if (reader != null) {
      reader.close();   // can itself throw
    }
  }
  ```
  Nine lines of plumbing, a null check, and if both the body and `close()`
  throw, the `close()` exception replaces the real one.
  :::
  :::compare-side{label="try-with-resources" verdict="right"}
  ```java
  try (BufferedReader reader = Files.newBufferedReader(file)) {
    // read
  }
  ```
  Closed on every path. If both throw, the real exception is kept and the
  `close()` one is attached to it as **suppressed**.
  :::
::

### Suppressed exceptions

```java [Suppressed.java]
public class Suppressed {
  public static void main(String[] args) {
    try (FaultyRegister r = new FaultyRegister()) {
      throw new IllegalStateException("marking failed");
    } catch (IllegalStateException e) {
      System.out.println("main exception: " + e.getMessage());
      for (Throwable s : e.getSuppressed()) {
        System.out.println("suppressed:     " + s.getMessage());
      }
    }
  }
}

class FaultyRegister implements AutoCloseable {
  @Override
  public void close() {
    throw new IllegalStateException("could not save register on close");
  }
}
```

```text [Output]
main exception: marking failed
suppressed:     could not save register on close
```

The exception that explains what went wrong is the one you catch; the cleanup
failure is not lost, it is attached.

### Reading a real file

```java [ReadStudents.java]
import java.io.BufferedReader;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class ReadStudents {
  public static void main(String[] args) {
    Path file = Path.of("data/students.csv");
    try (BufferedReader reader = Files.newBufferedReader(file)) {   // closed automatically
      String line;
      int count = 0;
      while ((line = reader.readLine()) != null) {
        String[] parts = line.split(",");
        System.out.println(parts[0] + " -> " + parts[1]);
        count++;
      }
      System.out.println(count + " students read");
    } catch (IOException e) {
      System.out.println("Could not read " + file + ": " + e);
    }
  }
}
```

```text [Output]
CSE1801 -> Anita Rao
CSE1802 -> Vikram Shah
CSE1803 -> Priya Nair
3 students read
```

The file-handling lesson later in the track goes further; this is the shape
every one of those examples follows.

## Real use case: exceptions of your own

Java's exceptions describe Java's problems. "This roll number has already
applied to this programme" and "attendance below 75%" are yours. A **custom
exception** is a class that extends `RuntimeException` (unchecked) or
`Exception` (checked).

```java [Admissions.java]
public class Admissions {
  private static final String[] applied = {"CSE1801:BTECH-CSE", "CSE1802:BTECH-ECE"};

  public static void main(String[] args) {
    try {
      apply("CSE1803", "BTECH-CSE");
      apply("CSE1801", "BTECH-CSE");
    } catch (DuplicateApplicationException e) {
      System.out.println("Refused: " + e.getMessage());
      System.out.println("Roll number on the exception: " + e.getRollNumber());
    }

    try {
      checkHallTicket("CSE1802", 68);
    } catch (AttendanceShortException e) {
      System.out.println("No hall ticket: " + e.getMessage() + " (short by " + e.getShortBy() + "%)");
    }
  }

  static void apply(String roll, String programme) {
    for (String a : applied) {
      if (a.equals(roll + ":" + programme)) {
        throw new DuplicateApplicationException(roll, programme);
      }
    }
    System.out.println("Accepted " + roll + " for " + programme);
  }

  static void checkHallTicket(String roll, int attendancePct) throws AttendanceShortException {
    if (attendancePct < 75) {
      throw new AttendanceShortException(roll, attendancePct);
    }
    System.out.println("Hall ticket issued to " + roll);
  }
}

// Unchecked: the caller made a mistake it should have avoided.
class DuplicateApplicationException extends RuntimeException {
  private final String rollNumber;
  private final String programme;

  DuplicateApplicationException(String rollNumber, String programme) {
    super(rollNumber + " has already applied to " + programme);
    this.rollNumber = rollNumber;
    this.programme = programme;
  }

  String getRollNumber() { return rollNumber; }
  String getProgramme()  { return programme; }
}

// Checked: a normal business outcome the caller must decide how to handle.
class AttendanceShortException extends Exception {
  private final int shortBy;

  AttendanceShortException(String rollNumber, int attendancePct) {
    super(rollNumber + " has " + attendancePct + "% attendance; 75% is required");
    this.shortBy = 75 - attendancePct;
  }

  int getShortBy() { return shortBy; }
}
```

```text [Output]
Accepted CSE1803 for BTECH-CSE
Refused: CSE1801 has already applied to BTECH-CSE
Roll number on the exception: CSE1801
No hall ticket: CSE1802 has 68% attendance; 75% is required (short by 7%)
```

::feature-list{columns="2"}
  :::feature{icon="i-lucide-tag" title="Named for the situation"}
  A caller can catch exactly this and nothing else. With a plain
  `RuntimeException` that is impossible.
  :::
  :::feature{icon="i-lucide-database" title="Carries the data"}
  `getRollNumber()` and `getShortBy()` let the handler build a useful reply
  without parsing the message text.
  :::
  :::feature{icon="i-lucide-message-square" title="The message is a sentence"}
  With the real values in it. Somebody reading a log late at night can act on
  "CSE1801 has already applied to BTECH-CSE"; not on "Invalid request".
  :::
  :::feature{icon="i-lucide-git-branch" title="super(message)"}
  Passing the message to the parent constructor is what makes `getMessage()`
  and the stack trace show it.
  :::
::

### Checked or unchecked: the decision

::compare{caption="Ask one question: can the caller sensibly do something about it?"}
  :::compare-side{label="Checked (extends Exception)" verdict="right"}
  The caller has a real alternative, and forcing it to decide is useful.
  Attendance is short: show the student the shortfall. A file is missing: ask
  for another.
  :::
  :::compare-side{label="Unchecked (extends RuntimeException)" verdict="right"}
  The caller should not have caused it and cannot fix it here: a duplicate
  application, a negative fee, an invalid status change. Let it travel to one
  place (in a web app, an error handler) that turns it into a response.
  :::
::

::side-note{kind="go-deeper"}
Most modern Java leans unchecked. Checked exceptions were a good idea that in
practice produced `throws Exception` on every signature and empty `catch`
blocks at the bottom. Spring wraps the checked `SQLException` into an unchecked
`DataAccessException` for exactly this reason. Being able to say this is a
genuine design debate, not a settled rule, is a good sign in an interview.
::

### Exception chaining: keep the cause

When you catch a low-level exception and throw a more meaningful one, pass the
original in as the **cause**. Otherwise the real reason disappears.

```java [Chained.java]
public class Chained {
  public static void main(String[] args) {
    importLine(3, "CSE1803,seventy");
  }

  static void importLine(int lineNumber, String line) {
    try {
      Integer.parseInt(line.split(",")[1]);
    } catch (NumberFormatException e) {
      throw new MarksImportException("line " + lineNumber + " of marks.csv: '" + line + "'", e);
    }
  }
}

class MarksImportException extends RuntimeException {
  MarksImportException(String message, Throwable cause) {
    super(message, cause);          // keep the original as the cause
  }
}
```

```text [Output]
Exception in thread "main" MarksImportException: line 3 of marks.csv: 'CSE1803,seventy'
	at Chained.importLine(Chained.java:10)
	at Chained.main(Chained.java:3)
Caused by: java.lang.NumberFormatException: For input string: "seventy"
	at java.base/java.lang.NumberFormatException.forInputString(NumberFormatException.java:67)
	at java.base/java.lang.Integer.parseInt(Integer.java:662)
	at java.base/java.lang.Integer.parseInt(Integer.java:778)
	at Chained.importLine(Chained.java:8)
	... 1 more
```

The top says what the business was doing (line 3 of the marks file). The
`Caused by:` says why (the word "seventy"). Both halves are needed to fix it,
and dropping `e` from the constructor call loses the second half.

## What confuses people here

- **Only `AutoCloseable` objects can go in the brackets.** `String` or your own
  class without `implements AutoCloseable` is a compile error.
- **A resource variable is effectively final** inside the block; you cannot
  reassign it.
- **Since Java 9**, a resource declared before the `try` can be used directly:
  `try (reader) { ... }`, as long as it is final or effectively final.
- **`extends Exception` makes it checked.** People write `extends Exception`
  out of habit and then force every caller to write a `try`. Decide on
  purpose.
- **Do not create an exception for normal control flow.** Throwing is slower
  than a `return` and hides what is going on. An empty search result is a
  return value, not an exception.

## Interview questions

::accordion
  :::accordion-item{label="What is try-with-resources and why use it?" icon="i-lucide-message-circle"}
  A `try` whose brackets declare resources that implement `AutoCloseable`.
  They are closed automatically when the block ends, in reverse order of
  opening, even if an exception is thrown. It replaces `finally` blocks that
  close resources by hand, and it keeps the original exception if `close()`
  also fails.
  :::
  :::accordion-item{label="What is a suppressed exception?" icon="i-lucide-message-circle"}
  When the body of a try-with-resources throws and then `close()` also throws,
  the body's exception is the one propagated and the `close()` exception is
  attached to it. `e.getSuppressed()` returns it: `Suppressed.java` printed
  "could not save register on close" as suppressed.
  :::
  :::accordion-item{label="How do you create a custom exception?" icon="i-lucide-message-circle"}
  Extend `RuntimeException` for unchecked or `Exception` for checked, pass a
  clear message to `super(message)` (and a cause to `super(message, cause)`
  when wrapping), and add fields for any data a handler will need, like
  `getRollNumber()` above.
  :::
  :::accordion-item{label="Should a custom exception be checked or unchecked?" icon="i-lucide-message-circle"}
  Checked if the caller can reasonably recover and should be forced to decide
  (short attendance, a missing file). Unchecked if it signals a programming or
  validation error the caller should have prevented (a duplicate application,
  a negative amount). Modern frameworks lean unchecked.
  :::
  :::accordion-item{label="What is exception chaining?" icon="i-lucide-message-circle"}
  Wrapping a caught exception inside a new, more meaningful one, passing the
  original as the cause: `new MarksImportException("line 3 ...", e)`. The stack
  trace then shows both, joined by `Caused by:`. Without the cause, the root
  reason is lost.
  :::
::
