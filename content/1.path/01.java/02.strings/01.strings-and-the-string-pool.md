The name you read with `nextLine()` is a `String`, and it is not one of the eight
primitives. It is an **object**, and that single fact explains why two names
that look identical on the screen can be "different" to Java.

## Why this matters in a job

Comparing strings is in every program you will ever write: a login checks a
username, a search matches a course code, a report groups by department. Get
the comparison wrong and the program misbehaves only sometimes, which is the
worst way for a bug to behave.

In interviews, "`==` against `equals`", "what is the String pool", "why is
String immutable" and "how many objects does `new String("Anita")` create" are
asked at nearly every fresher round. At JSpiders the trainers drilled these
three until everyone in the batch could answer them half asleep, because they
knew the walk-ins would ask.

## A String is an object, and a variable holds its address

A primitive variable holds its value in the box. A `String` variable holds an
**address**: the location of a String object somewhere else in memory (the
**heap**, the area where Java keeps objects). Think of two students' ID cards
that both say "Anita Rao". Same text; two separate cards.

- `==` asks: **are these the same object?** It compares the two addresses.
- `equals` asks: **do these contain the same characters?**

The addresses in the picture are made up for illustration. Java never shows you
real ones.

```java [Names.java]
import java.util.Scanner;

public class Names {
  public static void main(String[] args) {
    Scanner in = new Scanner(System.in);
    System.out.print("Applicant name: ");
    String typed = in.nextLine();
    String stored = "Anita Rao";

    System.out.println("typed == stored      : " + (typed == stored));
    System.out.println("typed.equals(stored) : " + typed.equals(stored));
  }
}
```

```text [Terminal]
$ java Names
Applicant name: Anita Rao
typed == stored      : false
typed.equals(stored) : true
```

**The rule, without exception: compare strings with `equals`.** `==` on objects
asks "is this literally the same object", which you almost never want.

## How it works: the String pool

Here is why the bug is so nasty: sometimes `==` appears to work.

Java keeps a **String pool** (also called the string constant pool): a table of
string **literals** (text written in double quotes in your source code). When the
same literal appears twice, both variables are given the **same** pooled object.
Since Java 7 the pool lives inside the heap.

```java [Pool.java]
public class Pool {
  public static void main(String[] args) {
    String a = "2026CSE0184";
    String b = "2026CSE0184";
    String c = new String("2026CSE0184");
    String d = "2026CSE" + "0184";
    String part = "0184";
    String e = "2026CSE" + part;
    final String finalPart = "0184";
    String f = "2026CSE" + finalPart;

    System.out.println("1. a == b          " + (a == b));
    System.out.println("2. a == c          " + (a == c));
    System.out.println("3. a == d          " + (a == d));
    System.out.println("4. a == e          " + (a == e));
    System.out.println("5. a == f          " + (a == f));
    System.out.println("6. a == c.intern() " + (a == c.intern()));
    System.out.println("7. a.equals(e)     " + a.equals(e));
  }
}
```

```text [Output]
1. a == b          true
2. a == c          false
3. a == d          true
4. a == e          false
5. a == f          true
6. a == c.intern() true
7. a.equals(e)     true
```

::warning{icon="i-lucide-alert-triangle"}
This is why the bug survives testing. A test compares two literals and passes.
In production the string came from a Scanner, a database or a web form, so it is
a new object and `==` is false. The code was always wrong; the literals were
hiding it.
::

## Immutable: a String can never change

A `String` object can never be modified after it is created. Every method that
appears to change one returns a **new** String.

```java [Immutable.java]
public class Immutable {
  public static void main(String[] args) {
    String name = "anita rao";
    name.toUpperCase();
    System.out.println(name);

    name = name.toUpperCase();
    System.out.println(name);

    String department = "CSE";
    String alias = department;
    department = department + " (Evening)";
    System.out.println("department: " + department);
    System.out.println("alias:      " + alias);
  }
}
```

```text [Output]
anita rao
ANITA RAO
department: CSE (Evening)
alias:      CSE
```

The first line is the second most common String mistake: calling `toUpperCase()`
and throwing the result away. The method did exactly what it promised: it
**returned** an uppercase string. It never claimed to change yours.

The second half shows immutability protecting you. `alias` and `department`
pointed at the same `"CSE"` object. Changing `department` made a new object and
pointed `department` at it; `alias` still sees `"CSE"`, because nobody can change
that object.

Why Java's designers made String immutable, which is the interview answer:

::feature-list
  :::feature{title="Safe pooling" icon="i-lucide-copy"}
  Sharing one object between many variables is only safe if nobody can change
  it. Without immutability, changing `a` would change `b`.
  :::
  :::feature{title="Safe as a HashMap key" icon="i-lucide-key-round"}
  A String's hash code is computed once and cached. It can never go stale, so a
  String key is always found again.
  :::
  :::feature{title="Security" icon="i-lucide-shield"}
  File paths, database URLs and class names are Strings. If they could be
  changed after a security check, the check would be meaningless.
  :::
  :::feature{title="Thread safety for free" icon="i-lucide-cpu"}
  Many threads can read the same String with no locking, because none of them
  can modify it.
  :::
::

## Real use case

At work the string you compare against usually comes from outside and may be
missing entirely (`null`, meaning no object at all). Calling a method on `null`
crashes, so the order of the comparison matters.

```java [SafeCompare.java]
import java.util.Objects;

public class SafeCompare {
  public static void main(String[] args) {
    String typed = null;   // the form field was left empty

    System.out.println("\"Anita Rao\".equals(typed): " + "Anita Rao".equals(typed));
    System.out.println("Objects.equals(typed, ...): " + Objects.equals(typed, "Anita Rao"));
    System.out.println("typed.equals(...):          " + typed.equals("Anita Rao"));
  }
}
```

```text [Output]
"Anita Rao".equals(typed): false
Objects.equals(typed, ...): false
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.equals(Object)" because "<local1>" is null
	at SafeCompare.main(SafeCompare.java:9)
```

Putting the literal first (sometimes called a Yoda comparison) is safe because a
literal is never null. `Objects.equals(a, b)` is safe on both sides and reads
better; it is what most codebases use.

Immutability is also why a roll number is a safe `HashMap` key. Its hash code is
the same however the String was made:

```java [HashKey.java]
public class HashKey {
  public static void main(String[] args) {
    String roll = "2026CSE0184";
    System.out.println(roll.hashCode());
    System.out.println("2026CSE0184".hashCode());
    System.out.println(new String("2026CSE0184").hashCode());
  }
}
```

```text [Output]
722725072
722725072
722725072
```

## What confuses people here

- **`==` working in a test proves nothing.** Two literals are pooled; input from
  anywhere else is not.
- **Calling a String method without assigning the result.** `name.trim();` on its
  own line does nothing useful.
- **`new String("...")` is almost never needed.** It exists, it appears in
  interview questions, and it wastes an object in real code.
- **`equals` is case-sensitive.** `"cse".equals("CSE")` is false. Use
  `equalsIgnoreCase` when case should not matter, such as a department code
  typed by a person.

::compare{caption="The same check, written twice."}
  :::compare-side{label="Intermittently wrong" verdict="wrong"}
  ```java
  if (department == "CSE") { ... }
  ```
  True for a literal, false for the same text from a file or form.
  :::
  :::compare-side{label="Always right" verdict="right"}
  ```java
  if ("CSE".equals(department)) { ... }
  ```
  Compares characters, and cannot throw even if `department` is null.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between == and equals() for Strings?"}
  `==` compares references (is it the same object); `equals` compares characters.
  `"2026CSE0184" == new String("2026CSE0184")` is `false`, and `.equals` is
  `true`. Two literals happen to be `==` because of the pool, which is why the bug
  passes tests and fails on real input.
  :::

  :::accordion-item{label="What is the String pool, and where does it live?"}
  A table of unique string literals that Java reuses, so `"CSE"` written twice is
  one object. Since Java 7 it is part of the heap (before that it was in PermGen).
  `intern()` returns the pooled copy of any string, adding it if missing:
  `new String("CSE").intern() == "CSE"` is `true`.
  :::

  :::accordion-item{label="How many objects does new String with a literal argument create?"}
  Up to two. The literal `"Anita"` goes into the pool (if it is not already
  there, from class loading), and `new` creates a second object on the heap. So
  `new String("Anita") == new String("Anita")` is `false`, while their
  `intern()` results are `==`.
  :::

  :::accordion-item{label="Why is String immutable in Java?"}
  So literals can be pooled and shared safely, so its cached hash code is
  always valid for use as a `HashMap` key, so a path or URL cannot be changed
  after it is checked, and so threads can share Strings without locks. Proof of
  the behaviour: `name.toUpperCase();` leaves `name` unchanged.
  :::

  :::accordion-item{label="Are two joined literals == to the whole literal?"}
  Yes. Joining two literals is a compile-time constant, so the compiler produces
  the pooled literal. With a non-final variable on either side,
  `"2026CSE" + part`, the joining happens at run time and the result is a new
  object, so `==` is false.
  :::
::
