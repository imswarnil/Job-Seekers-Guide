`Optional` was Java 8 fixing `null`. The `java.time` package was Java 8 fixing
dates, which had been broken in Java since 1996. Every real system has dates in
it: an admission deadline, a fee due in thirty days, an exam at 9:30, a
student's age on the 1st of July.

## Why this matters in a job

Date bugs are some of the most embarrassing in production because users notice
them at once: a fee reminder on the wrong day, an exam slot an hour out for a
student in another time zone, an age calculated a year wrong. In a code review,
any new use of `java.util.Date` or `Calendar` in modern code gets questioned.

Interview questions here are short and common: "why was the new Date-Time API
introduced?", "LocalDate against LocalDateTime against ZonedDateTime",
"Period against Duration", and "is LocalDate immutable?".

## What was wrong with Date and Calendar

```java [OldDate.java]
import java.util.*;

public class OldDate {
  public static void main(String[] args) {
    @SuppressWarnings("deprecation")
    Date d = new Date(2026, 7, 31);
    System.out.println(d);
    Calendar c = Calendar.getInstance();
    c.set(2026, 7, 31);
    System.out.println(c.get(Calendar.MONTH));
  }
}
```

```text [Output]
Tue Aug 31 00:00:00 CEST 3926
7
```

I asked for 31 July 2026 and got 31 **August** **3926**. The old `Date`
constructor adds 1900 to the year and counts months from 0, so 7 means August.
`Calendar` also counts months from 0. The time zone in the output (`CEST` on my
machine) comes from wherever the program runs, whether you wanted one or not.
And both classes are **mutable**: pass a `Date` to a method and that method can
change your date under you, the exact bug from the pass-by-value lesson. They
are not thread-safe either.

`java.time` (Java 8) fixed all of it: months from 1, years as written,
immutable objects, and separate types for separate ideas.

## One type per idea

Think of the admissions notice board. "Last date: 31 July" is a date with no
time. "Counselling at 10:00" is a time with no date. "Exam: 20 November, 9:30"
is both. "Online exam, 9:30 India time" needs a time zone too, because a
student in London sees it at 04:00. Java has a type for each:

| Type | Holds | Example |
| --- | --- | --- |
| `LocalDate` | Date, no time, no zone | Admission deadline `2026-07-31` |
| `LocalTime` | Time, no date | Counselling slot `10:00` |
| `LocalDateTime` | Date and time, no zone | Exam `2026-11-20T09:30` |
| `ZonedDateTime` | Date, time and zone | Online exam in `Asia/Kolkata` |
| `Instant` | A point on the global timeline (UTC) | When a payment was recorded |
| `Period` | An amount in years, months, days | Age: 17 years 10 months |
| `Duration` | An amount in hours, minutes, seconds | Exam length `PT3H` |

"Local" means "no time zone attached", not "my time zone".

## Syntax

```java
LocalDate.of(2026, 7, 31)                 // build one
LocalDate.parse("2026-07-18")             // from ISO text, yyyy-MM-dd
LocalDate.now()                           // today, from the system clock
date.plusDays(30) / minusMonths(1)        // returns a NEW date
date.isBefore(other) / isAfter / isEqual
Period.between(start, end)                // years, months, days
ChronoUnit.DAYS.between(start, end)       // a single number of days
date.format(DateTimeFormatter.ofPattern("dd/MM/yyyy"))
```

```java [Admissions.java]
import java.time.*;
import java.time.format.DateTimeFormatter;
import java.time.temporal.ChronoUnit;

public class Admissions {
  public static void main(String[] args) {
    LocalDate deadline = LocalDate.of(2026, 7, 31);
    LocalDate applied  = LocalDate.parse("2026-07-18");

    System.out.println("Deadline:            " + deadline);
    System.out.println("Day of week:         " + deadline.getDayOfWeek());
    System.out.println("Applied in time?     " + !applied.isAfter(deadline));
    System.out.println("Days to spare:       " + ChronoUnit.DAYS.between(applied, deadline));

    LocalDate feeDue = applied.plusDays(30);
    System.out.println("Fee due:             " + feeDue);
    System.out.println("Month end + 1 month: " + LocalDate.of(2026, 1, 31).plusMonths(1));

    LocalDate dob = LocalDate.of(2008, 8, 15);
    Period age = Period.between(dob, LocalDate.of(2026, 7, 1));
    System.out.println("Age on 1 July:       " + age.getYears() + " years " + age.getMonths() + " months");

    LocalDateTime examStart = LocalDateTime.of(2026, 11, 20, 9, 30);
    LocalDateTime examEnd = examStart.plusHours(3);
    Duration length = Duration.between(examStart, examEnd);
    System.out.println("Exam:                " + examStart + " to " + examEnd.toLocalTime() + " (" + length + ")");

    DateTimeFormatter indian = DateTimeFormatter.ofPattern("dd/MM/yyyy");
    DateTimeFormatter slip = DateTimeFormatter.ofPattern("EEEE, d MMMM yyyy 'at' h:mm a");
    System.out.println("Indian format:       " + deadline.format(indian));
    System.out.println("Hall ticket:         " + examStart.format(slip));
    System.out.println("Parsed:              " + LocalDate.parse("05/08/2026", indian));

    ZonedDateTime bangalore = ZonedDateTime.of(examStart, ZoneId.of("Asia/Kolkata"));
    ZonedDateTime london = bangalore.withZoneSameInstant(ZoneId.of("Europe/London"));
    System.out.println("Online exam, London: " + london.toLocalDateTime());
    System.out.println("Leap year 2028?      " + Year.isLeap(2028));
  }
}
```

```bash [Terminal]
javac Admissions.java && java Admissions
```

```text [Output]
Deadline:            2026-07-31
Day of week:         FRIDAY
Applied in time?     true
Days to spare:       13
Fee due:             2026-08-17
Month end + 1 month: 2026-02-28
Age on 1 July:       17 years 10 months
Exam:                2026-11-20T09:30 to 12:30 (PT3H)
Indian format:       31/07/2026
Hall ticket:         Friday, 20 November 2026 at 9:30 am
Parsed:              2026-08-05
Online exam, London: 2026-11-20T04:00
Leap year 2028?      true
```

Things worth noticing in that output:

- **31 January plus one month is 28 February**, not 3 March. `java.time`
  clamps to the last valid day. Know this before you write a monthly fee
  schedule.
- **`PT3H`** is the ISO-8601 way of writing "a period of time, 3 hours".
  `Duration` and `Period` both print in that format.
- **The formatter's words** (Friday, November, "am") come from the machine's
  **locale** (language and region settings). On another machine you may see
  "AM". Pass `Locale.ENGLISH` to `ofPattern` when the output must be fixed.
- **In pattern letters, case matters.** `MM` is month, `mm` is minutes. `yyyy`
  is the year; `DD` is day of the **year**. `dd/mm/yyyy` compiles, runs, and
  prints the minutes where the month should be.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-calendar" title="Period"}
  Calendar amounts: years, months, days. `Period.between(dob, today)` for age.
  Used with `LocalDate`.
  :::
  :::feature{icon="i-lucide-timer" title="Duration"}
  Clock amounts: hours, minutes, seconds, nanoseconds. `Duration.between` two
  times for an exam length. Used with times and `Instant`.
  :::
::

## Real use case

Every Indian college ERP has a fee module with a due date, a grace period and
a late fine. With `java.time` the rules read like the circular that announced
them:

```java
LocalDate dueDate = semesterStart.plusDays(30);
LocalDate graceEnds = dueDate.plusDays(7);

long daysLate = paidOn.isAfter(graceEnds)
    ? ChronoUnit.DAYS.between(graceEnds, paidOn)
    : 0;

long finePaise = Math.min(daysLate * 2_000, 100_000);   // Rs 20 a day, capped at Rs 1,000
```

At work, you store **`Instant`** (or a UTC timestamp column) for "when did this
happen", and convert to a `ZonedDateTime` in the user's zone only for display.
Storing a `LocalDateTime` for a payment from a server in Mumbai and another in
Frankfurt gives you two times that cannot be compared.

::real-life{title="The time zone bug" source="Any system with users in two countries"}
An exam portal stores "9:30" with no zone. The server moves from a data centre
in Mumbai to one in Europe, the JVM's default zone changes, and every slot
shifts by hours. The fix is always the same: `Instant` or `ZonedDateTime` with
an explicit `ZoneId.of("Asia/Kolkata")`, never the server's default.
::

## What confuses people here

### They are immutable, so the result must be kept

```java [Immutable.java]
import java.time.LocalDate;

public class Immutable {
  public static void main(String[] args) {
    LocalDate deadline = LocalDate.of(2026, 7, 31);
    deadline.plusDays(7);                    // result thrown away
    System.out.println(deadline);
    deadline = deadline.plusDays(7);         // keep the new object
    System.out.println(deadline);
  }
}
```

```text [Output]
2026-07-31
2026-08-07
```

::compare{caption="The same mistake people make with String.toUpperCase()."}
  :::compare-side{label="Ignoring the return value" verdict="wrong"}
  ```java
  deadline.plusDays(7);
  ```
  Returns a new date and throws it away. The deadline is unchanged, silently.
  :::
  :::compare-side{label="Keeping it" verdict="right"}
  ```java
  deadline = deadline.plusDays(7);
  ```
  Immutability is also why these objects are thread-safe and safe to pass to
  any method.
  :::
::

- **Invalid dates throw, which is good.** `LocalDate.of(2026, 2, 30)` throws
  `DateTimeException: Invalid date 'FEBRUARY 30'` instead of quietly rolling
  over to March, as `Calendar` did.
- **`now()` makes code hard to test**, because the answer changes every day.
  Real code passes in a `Clock` or the date itself, so a test can fix "today".
- **Converting old to new:** `date.toInstant()` turns a legacy `Date` into an
  `Instant`; you will need it when an old library hands you a `Date`.

## Interview questions

::accordion
  :::accordion-item{label="Why was the java.time API introduced in Java 8?" icon="i-lucide-message-circle"}
  `Date` and `Calendar` were mutable (so not thread-safe and easy to change by
  accident), counted months from 0, stored years offset from 1900, mixed dates
  with times and zones in one class, and rolled invalid dates over silently.
  `new Date(2026, 7, 31)` printed a date in August 3926. `java.time` is
  immutable, thread-safe, 1-based for months, and has a separate type for each
  concept.
  :::
  :::accordion-item{label="LocalDate, LocalDateTime and ZonedDateTime: when do you use each?" icon="i-lucide-message-circle"}
  `LocalDate` for a date with no time (a deadline, a birthday). `LocalDateTime`
  for a date and time that do not need a zone (a timetable slot inside one
  college). `ZonedDateTime` when the zone matters (an online exam taken from
  several countries). For timestamps in storage, `Instant`.
  :::
  :::accordion-item{label="What is the difference between Period and Duration?" icon="i-lucide-message-circle"}
  `Period` is date-based: years, months and days, as in an age of "17 years 10
  months". `Duration` is time-based: hours, minutes, seconds, as in an exam of
  `PT3H`. A month has no fixed number of seconds, which is why they are two
  different types.
  :::
  :::accordion-item{label="Is LocalDate immutable? What does that mean in practice?" icon="i-lucide-message-circle"}
  Yes. Methods such as `plusDays` return a new object and leave the original
  unchanged, so you must assign the result: `deadline = deadline.plusDays(7)`.
  It also means a `LocalDate` can be shared between threads and passed to any
  method safely.
  :::
  :::accordion-item{label="How do you calculate someone's age from a date of birth?" icon="i-lucide-message-circle"}
  ```java
  int years = Period.between(dob, LocalDate.now()).getYears();
  ```
  With a date of birth of 15 August 2008 and a reference date of 1 July 2026,
  `Period.between` gives 17 years 10 months. Subtracting years alone would say
  18, which is wrong until the birthday.
  :::
::
