`findFirst`, `max` and `maxBy` all handed back an `Optional` instead of the
value itself. That was deliberate. There might be no first element, no maximum,
no topper, and Java 8 added a type whose whole job is to say so out loud.

## Why this matters in a job

The `NullPointerException` lesson showed the most common crash in Java: a
method returned `null`, and the caller never imagined it could. `Optional` is
the fix for the **return value** half of that problem. You will see it on
repository methods such as `findById` in Spring Data, on stream results, and in
code review comments like "return Optional here, not null".

Interviewers ask what it is for, `orElse` against `orElseGet`, and "should a
field or parameter be Optional?". The last one separates people who have used
it from people who have read about it.

## Optional is a box that may be empty

Imagine asking the college office for a student's hall ticket by roll number.
One clerk hands you the ticket, or hands you nothing and says nothing; you only
discover the nothing when you try to read it. That is `null`. A better clerk
always hands you an **envelope**. Sometimes the ticket is inside, sometimes the
envelope is empty, but you always know you have to open it and check.

`Optional<Student>` is that envelope. It holds exactly zero or one `Student`.
The method's signature now tells the caller "this can be missing", and the
compiler will not let them use the envelope as if it were a student.

## Syntax

```java
Optional.of(value)            // a full box. value must not be null
Optional.ofNullable(value)    // full if value is non-null, empty if null
Optional.empty()              // an empty box

opt.isPresent() / opt.isEmpty()
opt.orElse(fallback)          // the value, or the fallback
opt.orElseGet(() -> ...)      // the value, or compute a fallback only if needed
opt.orElseThrow(() -> ...)    // the value, or throw your exception
opt.map(f)                    // transform the value if present
opt.filter(p)                 // keep it only if it passes the test
opt.ifPresent(consumer)       // do something only if present
```

```java [OptionalBasics.java]
import java.util.*;

public class OptionalBasics {
  record Student(String roll, String name, String email) {}

  static final List<Student> STUDENTS = List.of(
      new Student("1801", "Anita", "anita@college.edu"),
      new Student("1802", "Vikram", null));

  // The return type says: there may be no such student.
  static Optional<Student> findByRoll(String roll) {
    return STUDENTS.stream().filter(s -> s.roll().equals(roll)).findFirst();
  }

  public static void main(String[] args) {
    Optional<Student> found = findByRoll("1801");
    Optional<Student> missing = findByRoll("1899");

    System.out.println(found);
    System.out.println(missing);
    System.out.println(found.isPresent() + " " + missing.isEmpty());

    // Get a value out, with a fallback
    System.out.println(missing.map(Student::name).orElse("Unknown student"));

    // Transform, then fall back: map returns empty if the email is null
    String email = findByRoll("1802").map(Student::email).orElse("no email on file");
    System.out.println(email);

    // Run something only if present
    found.ifPresent(s -> System.out.println("Hall ticket issued to " + s.name()));
    missing.ifPresentOrElse(
        s -> System.out.println("Issued"),
        () -> System.out.println("Roll 1899 not found, ticket not issued"));

    // filter on an Optional
    System.out.println(found.filter(s -> s.name().startsWith("A")).isPresent());

    // Fail loudly with your own exception
    try {
      missing.orElseThrow(() -> new IllegalArgumentException("No student with roll 1899"));
    } catch (IllegalArgumentException e) {
      System.out.println("Caught: " + e.getMessage());
    }

    // The mistake: get() on an empty Optional
    try {
      missing.get();
    } catch (NoSuchElementException e) {
      System.out.println("get() on empty: " + e);
    }
  }
}
```

```bash [Terminal]
javac OptionalBasics.java && java OptionalBasics
```

The line to study is the Vikram one. `findByRoll("1802")` found him, but his
`email` is `null`. `map(Student::email)` noticed the `null` result and turned
the box empty, so `orElse` supplied the fallback. The same chain with plain
references would have been `student.getEmail().toLowerCase()` and a crash.

### orElse against orElseGet

They look identical. They are not.

```java [OrElseGet.java]
import java.util.*;

public class OrElseGet {
  static String loadDefaultFromDatabase() {
    System.out.println("  (expensive database call ran)");
    return "Guest";
  }

  public static void main(String[] args) {
    Optional<String> name = Optional.of("Anita");

    System.out.println("orElse:");
    System.out.println(name.orElse(loadDefaultFromDatabase()));

    System.out.println("orElseGet:");
    System.out.println(name.orElseGet(() -> loadDefaultFromDatabase()));
  }
}
```

```text [Output]
orElse:
  (expensive database call ran)
Anita
orElseGet:
Anita
```

`orElse(x)` is an ordinary method call, so Java evaluates `x` **before** calling
it, whether or not the box is empty. The database was queried for a fallback
nobody used. `orElseGet` takes a `Supplier` (a lambda) and calls it only when
the box is empty. Use `orElse` for constants, `orElseGet` for anything that
costs something.

## Real use case

Repository methods are where you will meet `Optional` first at work. In a
Spring Boot project, `studentRepository.findById(roll)` returns
`Optional<Student>`, and a service method typically does one of two things
with it:

```java
// An API that must return a student or a clear 404
Student student = studentRepository.findById(roll)
    .orElseThrow(() -> new StudentNotFoundException(roll));

// A screen that can show a placeholder
String mentor = studentRepository.findById(roll)
    .map(Student::mentor)
    .map(Faculty::name)
    .orElse("Not assigned");
```

The second chain walks three levels (student, mentor, mentor's name), any of
which could be missing, without one `if (x != null)`.

::real-life{title="Where Optional stops" source="Code review"}
The Java designers intended `Optional` as a **return type** for methods that
may have no result. It is not serialisable, it adds an object per value, and
as a field or parameter it only moves the null check somewhere else. Reviewers
will flag `private Optional<String> email;` and `void notify(Optional<Student> s)`.
Use a plain nullable field, or overload the method.
::

## What confuses people here

::compare{caption="Calling get() is a null check with extra steps."}
  :::compare-side{label="isPresent then get" verdict="wrong"}
  ```java
  Optional<Student> s = findByRoll(roll);
  if (s.isPresent()) {
    return s.get().name();
  }
  return "Unknown";
  ```
  This is `if (s != null)` wearing a costume, and a missed `isPresent` gives
  `NoSuchElementException: No value present` instead of an NPE.
  :::
  :::compare-side{label="Say what you want" verdict="right"}
  ```java
  return findByRoll(roll)
      .map(Student::name)
      .orElse("Unknown");
  ```
  One expression, and there is no path that reads an empty box.
  :::
::

- **`Optional.of(null)` throws** a `NullPointerException` immediately. If the
  value might be `null`, use `ofNullable`:

  ```java [OfNull.java]
  import java.util.*;

  public class OfNull {
    public static void main(String[] args) {
      String email = null;
      System.out.println(Optional.ofNullable(email));
      System.out.println(Optional.of(email));
    }
  }
  ```

  ```text [Output]
  Optional.empty
  Exception in thread "main" java.lang.NullPointerException
  	at java.base/java.util.Objects.requireNonNull(Objects.java:233)
  	at java.base/java.util.Optional.of(Optional.java:113)
  	at OfNull.main(OfNull.java:7)
  ```
- **Never return `null` from a method whose return type is `Optional`.** The
  caller trusts the envelope and calls `.map` on `null`.
- **Do not wrap collections.** An empty list already means "nothing". Return
  `List.of()`, not `Optional<List<Student>>`.
- **`OptionalInt`, `OptionalDouble`** exist for primitive streams:
  `IntStream.average()` returns `OptionalDouble`, read with `getAsDouble()` or
  `orElse(0)`.
- **`map` against `flatMap` on Optional:** if your function already returns an
  `Optional`, `map` gives `Optional<Optional<T>>`. Use `flatMap` to keep one
  layer.

## Interview questions

::accordion
  :::accordion-item{label="What is Optional and why was it introduced?" icon="i-lucide-message-circle"}
  A container that holds zero or one value, added in Java 8. It makes "this
  method might not have a result" part of the return type, so the caller has
  to deal with the empty case, instead of discovering a `null` through a
  `NullPointerException`. `findByRoll("1899")` returned `Optional.empty`, and
  `orElse("Unknown student")` handled it.
  :::
  :::accordion-item{label="What is the difference between orElse and orElseGet?" icon="i-lucide-message-circle"}
  `orElse(value)` always evaluates its argument, even when the Optional is
  full. `orElseGet(supplier)` only calls the supplier when it is empty. In
  `OrElseGet.java` the expensive call ran for `orElse` and not for `orElseGet`,
  although both printed Anita.
  :::
  :::accordion-item{label="Optional.of against Optional.ofNullable?" icon="i-lucide-message-circle"}
  `of` requires a non-null value and throws `NullPointerException` for `null`.
  `ofNullable` returns `Optional.empty()` for `null`. Use `of` when a `null`
  would be a bug you want to catch at once, and `ofNullable` when wrapping a
  value that may legitimately be missing.
  :::
  :::accordion-item{label="Should you use Optional for fields or method parameters?" icon="i-lucide-message-circle"}
  Generally no. It was designed as a return type. It is not `Serializable`,
  adds an allocation per value, and as a parameter forces every caller to wrap
  arguments. Keep fields nullable (or give them a default) and overload methods
  instead of taking `Optional` parameters.
  :::
  :::accordion-item{label="What does get() do on an empty Optional?" icon="i-lucide-message-circle"}
  Throws `NoSuchElementException: No value present`. That is why `get()` is
  discouraged; `orElseThrow()` with no arguments does the same thing and says
  what it does in its name.
  :::
::
