A student in Bhopal types `results.university.ac.in`, presses Enter, and the
marks appear in under a second. At least eight things happened in that second,
and naming them in order is the answer to "what happens when you type a URL into
a browser?"

## Why this matters in a job

Because it is asked in almost every fresher interview, at every level, in
developer, tester and support roles alike. It is also how you debug: a page that
does not load could have failed at DNS, at the connection, at the server or at
the database, and knowing the order tells you where to look. The
[Computer Networks](/computer-networks) track goes deep on each layer; this
lesson is the whole journey on one page.

## The journey, analogy first

Posting a letter to the university's exam office. You know the office's name but
not its address, so you look it up in a directory (**DNS**). You check the post
office is open and agree how you will talk (**TCP**), and seal the envelope so
nobody on the way can read it (**TLS**). You send the request (**HTTP**). A
clerk reads it, pulls your file from the records room (**server and database**),
writes a reply and sends it back. You open it and read it (**the browser
renders**).

## How it works

::flow{numbered direction="vertical" caption="Eight steps, each one a place a request can fail."}
  :::flow-step{label="1. The URL is parsed" icon="i-lucide-link"}
  `https://results.university.ac.in/sem5?roll=22CS041`: protocol `https`, host
  `results.university.ac.in`, path `/sem5`, query `roll=22CS041`.
  :::
  :::flow-step{label="2. DNS lookup" icon="i-lucide-book-open" highlight}
  The browser needs an IP address. It checks its cache, then the operating
  system's, then asks a DNS resolver (usually your internet provider's), which
  asks root, `.in` and `ac.in` servers in turn. Answer: `13.235.18.42`.
  :::
  :::flow-step{label="3. TCP connection" icon="i-lucide-handshake"}
  A three-way handshake with the server on port 443: SYN, SYN-ACK, ACK. Now
  there is a reliable connection.
  :::
  :::flow-step{label="4. TLS handshake" icon="i-lucide-lock"}
  Browser and server agree encryption keys, and the browser checks the server's
  certificate proves it really is `results.university.ac.in`.
  :::
  :::flow-step{label="5. HTTP request" icon="i-lucide-send"}
  `GET /sem5?roll=22CS041` with headers: host, browser, cookies.
  :::
  :::flow-step{label="6. Server and database" icon="i-lucide-database"}
  A load balancer passes it to an application server, which runs code, queries
  the database for the student's marks, and builds a response.
  :::
  :::flow-step{label="7. HTTP response" icon="i-lucide-inbox"}
  Status `200 OK`, headers, and the HTML body.
  :::
  :::flow-step{label="8. The browser renders" icon="i-lucide-monitor"}
  Parse HTML into the DOM, fetch CSS, JavaScript and images (each one more
  request), lay out and paint. The JavaScript track's DOM lives here.
  :::
::

You can watch steps 2, 5 and 7 from the terminal:

```bash [Terminal]
nslookup results.university.ac.in
curl -I https://results.university.ac.in/sem5
```

```text [Output]
Name:    results.university.ac.in
Address: 13.235.18.42

HTTP/2 200
content-type: text/html; charset=utf-8
cache-control: max-age=60
server: nginx
```

(The host name is an example; try it with any real site.) `curl -I` sends the
request and prints only the response headers.

### Status codes worth knowing

| Code | Means | Example |
| --- | --- | --- |
| `200 OK` | Worked | Marks returned |
| `301` / `302` | Moved, go here instead | `http://` redirected to `https://` |
| `400 Bad Request` | The request was malformed | Roll number missing |
| `401 Unauthorized` | Not logged in | Session expired |
| `403 Forbidden` | Logged in, not allowed | A student opening the admin page |
| `404 Not Found` | No such page | Mistyped path |
| `500 Internal Server Error` | The server's code failed | An unhandled exception |
| `503 Service Unavailable` | Server overloaded or down | Results day at 10:00 |

**4xx means the client's side is wrong; 5xx means the server's side is.**

## Real use case

::real-life{title="Where to look, by symptom" source="Any production support rota"}
"This site can't be reached" before anything loads: DNS or the network, steps
2–3. A certificate warning: step 4. A page that loads but says 500: the server's
code or database, step 6, and the application log is where you go next (the
`tail -f` from the Linux chapter). A page that loads slowly with 200: usually the
database query or large files in step 8. Four symptoms, four different teams.
::

## What confuses people here

- **DNS gives an IP address, not the page.** It is a lookup, like a phone
  directory.
- **HTTP versus HTTPS.** HTTPS is HTTP inside a TLS-encrypted connection, on port
  443 instead of 80.
- **401 versus 403.** 401: who are you? 403: I know who you are, and no.
- **One page, many requests.** A single page often makes 50 to 100 requests for
  its CSS, scripts and images.

## Interview questions

::accordion
  :::accordion-item{label="What happens when you type a URL in the browser and press Enter?"}
  The browser parses the URL; resolves the domain to an IP through DNS (browser
  cache, OS cache, resolver, root, TLD, authoritative server); opens a TCP
  connection (three-way handshake) and a TLS handshake for HTTPS; sends an HTTP
  request; the server (often behind a load balancer) runs application code,
  queries the database, and returns an HTTP response; the browser parses HTML,
  builds the DOM, fetches CSS, JS and images, and renders the page.
  :::
  :::accordion-item{label="What is DNS?"}
  The Domain Name System translates human-readable domain names into IP addresses.
  It is hierarchical (root, top-level domain, authoritative servers) and heavily
  cached, which is why a DNS change can take time to reach everyone.
  :::
  :::accordion-item{label="Difference between HTTP and HTTPS?"}
  HTTPS is HTTP over TLS: the data is encrypted and the server's identity is
  verified by a certificate. HTTP is plain text on port 80; HTTPS uses port 443.
  :::
  :::accordion-item{label="GET versus POST?"}
  GET asks for data, sends parameters in the URL, and should not change anything
  on the server. POST sends data in the request body, usually to create or
  change something (submit a fee payment). GET is safe to repeat and to
  bookmark; POST is not.
  :::
  :::accordion-item{label="What is the difference between a 4xx and a 5xx error?"}
  4xx: the client made an error (bad request, not logged in, forbidden, not
  found). 5xx: the server failed to handle a valid request (a bug, an overload,
  a dependency down).
  :::
::
