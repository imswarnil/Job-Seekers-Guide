A processor understands only **machine code**: binary instructions for that
particular chip. Everything else must be translated, and there are two ways to
do it: all at once before running (a **compiler**) or piece by piece while
running (an **interpreter**).

## Why this matters in a job

It explains everyday things: why a Java typo stops the build but a JavaScript
typo breaks only when that line runs, why Java runs on any machine with a JVM,
and why the first request to a Java service is slow. In interviews, "compiler
versus interpreter" is a stock question, and "is Java compiled or interpreted?"
is the follow-up that catches people.

## Translation, analogy first

A guest lecturer from Germany is giving a talk to students in Bhopal. A
**translator** can take the whole speech a week early and produce a Hindi
version, printed and ready (compiler): slow to prepare, fast to read, and any
mistakes found before the day. Or an **interpreter** can stand beside the
lecturer and translate sentence by sentence as it is spoken: starts
immediately, slower overall, and a mistake in sentence 40 is only noticed when
sentence 40 arrives.

## How it works

::compare{caption="The two strategies."}
  :::compare-side{label="Compiler" verdict="neutral"}
  Translates the **whole program** into machine code before it runs. Reports
  all syntax errors up front. Produces an executable file. Runs fast. Examples:
  C, C++, Go, Rust.
  :::
  :::compare-side{label="Interpreter" verdict="neutral"}
  Reads and runs the program **one statement at a time**. Stops at the first
  error it reaches. No separate executable. Slower, but quick to start and
  change. Examples: Python, classic JavaScript, shell scripts.
  :::
::

### Java does both

::flow{caption="Java: compiled once to bytecode, then run anywhere a JVM is installed."}
  :::flow-step{label="Result.java" icon="i-lucide-file-code"}
  Source code you write.
  :::
  :::flow-step{label="javac" icon="i-lucide-hammer"}
  The compiler checks and translates it.
  :::
  :::flow-step{label="Result.class" icon="i-lucide-file-box" highlight}
  **Bytecode**: instructions for a virtual machine, not for any real chip.
  :::
  :::flow-step{label="JVM" icon="i-lucide-cpu"}
  Interprets the bytecode, and its **JIT** (just-in-time) compiler turns the
  frequently run parts into machine code while the program runs.
  :::
::

```java [Result.java]
public class Result {
    public static void main(String[] args) {
        int marks = 78;
        String grade = marks >= 75 ? "Distinction" : "First class";
        System.out.println("22CS041: " + grade);
    }
}
```

```bash [Terminal]
javac Result.java
ls
java Result
```

```text [Output]
Result.class  Result.java
22CS041: Distinction
```

Remove a semicolon and `javac` refuses to produce `Result.class` at all:

```text [Output]
Result.java:3: error: ';' expected
        int marks = 78
                      ^
1 error
```

The same mistake in JavaScript is only reported when that part of the file is
reached. And a JavaScript function that calls a misspelt method throws only
when that function runs, which might be the day a user clicks that button.

This is what "write once, run anywhere" means: the same `.class` file runs on
Windows, macOS and Linux, because each has its own JVM. A C program must be
compiled separately for each.

## Real use case

The first few requests to a freshly started Java service are slower than the
thousandth, because the JIT has not yet compiled the busy code paths to machine
code. Teams "warm up" a service by sending it test traffic before real users
arrive. Modern JavaScript engines (Chrome's V8) also use JIT compilation, which
is why "JavaScript is interpreted" is only half true today.

## What confuses people here

- **"Java is interpreted."** Java is compiled to bytecode, then that bytecode is
  interpreted and JIT-compiled by the JVM. Say both.
- **JDK, JRE, JVM.** The **JVM** runs bytecode. The **JRE** is the JVM plus the
  standard libraries needed to run programs. The **JDK** is the JRE plus
  development tools such as `javac`. You need the JDK to write Java.
- **Assembler.** Translates assembly language (human-readable machine
  instructions) into machine code. A third translator, asked occasionally.
- **Syntax errors versus runtime errors.** A compiler catches syntax and type
  errors; nothing catches a division by zero until it happens.

## Interview questions

::accordion
  :::accordion-item{label="Compiler versus interpreter?"}
  A compiler translates the whole program to machine code before execution,
  reports all errors up front, and produces a fast executable. An interpreter
  translates and executes one statement at a time, stops at the first error,
  and is slower but needs no separate build step.
  :::
  :::accordion-item{label="Is Java compiled or interpreted?"}
  Both. `javac` compiles source to platform-independent bytecode (`.class`).
  The JVM then interprets that bytecode and uses a JIT compiler to turn hot
  code into native machine code at runtime.
  :::
  :::accordion-item{label="What is bytecode, and why is Java platform independent?"}
  Bytecode is the instruction set of the Java Virtual Machine rather than of a
  real processor. Any platform with a JVM can run the same `.class` files, so
  the program does not need recompiling per operating system.
  :::
  :::accordion-item{label="JDK versus JRE versus JVM?"}
  JVM executes bytecode. JRE is JVM plus core libraries, enough to run Java
  programs. JDK is JRE plus development tools (`javac`, `jar`, debugger),
  needed to write and compile them.
  :::
  :::accordion-item{label="What is JIT compilation?"}
  Just-in-time compilation: while the program runs, the JVM identifies frequently
  executed code and compiles it to native machine code, so later calls run at
  close to compiled speed.
  :::
::
