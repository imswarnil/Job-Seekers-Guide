These are the questions this track produces, in the form they arrive: often
casually, often as a follow-up to something on your résumé. Try each one aloud
before opening it. An answer you can only recognise is not an answer you can
give.

::tip
The pattern for every answer here: one sentence of definition, one concrete
example, and, where it fits, the command or the number. Thirty to forty-five
seconds each. The example is what an interviewer remembers.

## How software gets made

::accordion
  :::accordion-item{label="1. Which SDLC model would you choose for a university's exam portal whose rules are fixed by regulation, and why?"}
  Waterfall or the V-model. The requirements are stable and set by law, the
  scope can be fixed and priced up front, and the V-model adds a test level
  planned against each phase, which suits a system where every rule must be
  proved correct. For a start-up's student app, I would choose Agile instead.
  :::
  :::accordion-item{label="2. What are the four values of the Agile Manifesto?"}
  Individuals and interactions over processes and tools; working software over
  comprehensive documentation; customer collaboration over contract negotiation;
  responding to change over following a plan. "Over", not "instead of".
  :::
  :::accordion-item{label="3. What happens in sprint planning?"}
  The team and Product Owner agree a sprint goal, pick items from the top of the
  product backlog that fit the team's capacity (using velocity), and break them
  into tasks. Output: the sprint backlog.
  :::
  :::accordion-item{label="4. Your team's velocity is 18, 22 and 20 over three sprints. The backlog is 120 points. When will it be done?"}
  Average velocity = (18 + 22 + 20) / 3 = 20. 120 / 20 = 6 sprints, about 12
  weeks with two-week sprints. Add that velocity is a forecast, not a promise,
  and new work usually arrives.
  :::
  :::accordion-item{label="5. Who is responsible for the product backlog, and who for the sprint backlog?"}
  The Product Owner owns and orders the product backlog. The development team
  owns the sprint backlog and how the work gets done.
  :::
  :::accordion-item{label="6. Scrum versus Kanban?"}
  Scrum works in fixed sprints with defined roles and events. Kanban has
  continuous flow on a board, no sprints, and limits the number of items in
  progress at once. Feature teams often use Scrum; support teams often use
  Kanban.
  :::
::

## Testing

::accordion
  :::accordion-item{label="7. A fix went into the fee module. Which tests do you run, in what order?"}
  Smoke test on the new build (does it start, do the main pages open). Retest
  the original bug. Sanity check the fee module around the fix. Then regression
  across related features (receipts, reports, late fees), ideally automated.
  :::
  :::accordion-item{label="8. Give an example of high severity, low priority."}
  The annual archive report crashes, but it runs once a year in March and it is
  September. Serious impact, not urgent.
  :::
  :::accordion-item{label="9. Pass marks are 40 to 100. Which values do you test with boundary value analysis?"}
  39, 40, 41 at the lower edge; 99, 100, 101 at the upper edge. Plus one from
  inside (70) and invalid inputs such as -1 and a letter.
  :::
  :::accordion-item{label="10. Write three test cases for a fee payment page."}

  | ID | Data | Expected |
  | --- | --- | --- |
  | TC_FEE_01 | Valid UPI, Rs 48,000 due | Payment succeeds, receipt with receipt number shown |
  | TC_FEE_02 | UPI app declines | Clear failure message, fee not marked paid |
  | TC_FEE_03 | Paid 5 days late | Amount includes late fee Rs 250 |
  :::
  :::accordion-item{label="11. What is the bug life cycle?"}
  New, assigned, open, fixed, retest, closed (or reopened if the retest fails).
  Side states: rejected, duplicate, deferred.
  :::
  :::accordion-item{label="12. Manual or automation for a login page?"}
  Both. Manual first, to explore and find usability problems on a new page.
  Automate once it is stable, because login is in every regression run. Tools:
  Selenium for the browser, JUnit or TestNG to run the tests.
  :::
  :::accordion-item{label="13. What is the difference between a unit test and an integration test? Show a unit test."}
  A unit test checks one piece in isolation; an integration test checks pieces
  working together (service and database).

  ```java [GradeTest.java]
  @Test
  void seventyFiveIsDistinction() {
      assertEquals("Distinction", Grades.forMarks(75));
  }
  ```
  :::

## Git and GitHub

::accordion
  :::accordion-item{label="14. Walk me through how you would fix a bug and get it into main."}
  ```bash [Terminal]
  git switch main && git pull
  git switch -c bugfix/BUG-1182-late-fee
  # fix, test
  git add src/FeeService.java
  git commit -m "Add late fee after due date (BUG-1182)"
  git push -u origin bugfix/BUG-1182-late-fee
  ```
  Then open a pull request, get a review, address comments, merge once approved
  and checks pass, delete the branch.
  :::
  :::accordion-item{label="15. You committed to main by mistake and have not pushed. How do you move the commit to a branch?"}
  ```bash [Terminal]
  git switch -c feature/attendance-card   # new branch keeps the commit
  git switch main
  git reset --hard origin/main            # main back to the remote
  ```
  Safe here because the commit is not pushed and is still on the new branch.
  Run `git status` first so no uncommitted work is lost.
  :::
  :::accordion-item{label="16. A bad commit is already on the remote main. How do you undo it?"}
  `git revert <hash>` then `git push`. It adds a commit that reverses the
  change, so nobody's history is rewritten. Never reset and force-push a shared
  branch.
  :::
  :::accordion-item{label="17. How do you see what changed in the last three commits?"}
  `git log --oneline -3` for the list, `git log -p -3` for the diffs,
  `git show <hash>` for one commit.
  :::
  :::accordion-item{label="18. What is the difference between git merge and git rebase?"}
  Merge joins two histories with a merge commit and keeps what happened. Rebase
  replays your commits on the tip of the other branch, giving a straight line
  but new commit IDs. Rebase only local, unshared work.
  :::
  :::accordion-item{label="19. You pushed a file with a database password. What do you do?"}
  Change the password first: it is leaked the moment it reached the remote.
  Then remove the file from tracking (`git rm --cached .env`), add it to
  `.gitignore`, commit, and if needed clean the history with a tool such as
  `git filter-repo`. Rotating the secret is the step that matters.
  :::
::

## Linux

::accordion
  :::accordion-item{label="20. How do you find which of today's log lines contain ERROR, and count them?"}
  ```bash [Terminal]
  grep "2026-09-29" app.log | grep -c ERROR
  ```
  ```text [Output]
  44
  ```
  :::
  :::accordion-item{label="21. A script says Permission denied. What do you check?"}
  `ls -l script.sh` to see its permissions. If there is no `x` for my user, add
  it: `chmod u+x script.sh` (or `chmod 755`). If the problem is a file it
  writes to, check that file's and its directory's permissions. Not `chmod 777`.
  :::
  :::accordion-item{label="22. Port 8080 is already in use. How do you find out why?"}
  ```bash [Terminal]
  lsof -i :8080
  ```
  Shows the process and PID holding the port. Then decide: it is an old copy of
  my service (`kill <PID>`), or somebody else's, and I use a different port.
  :::
  :::accordion-item{label="23. Find all .log files over 100 MB under /var/log."}
  `find /var/log -type f -name "*.log" -size +100M`
  :::
  :::accordion-item{label="24. What does chmod 640 give?"}
  Owner read and write (6 = 4+2), group read (4), others nothing (0):
  `rw-r-----`.
  :::
::

## Cloud, the web and the machine

::accordion
  :::accordion-item{label="25. Is Gmail IaaS, PaaS or SaaS? And AWS EC2? And Heroku?"}
  Gmail is SaaS (finished software you use). EC2 is IaaS (virtual machines, you
  manage the OS). Heroku is PaaS (deploy code, the platform runs it).
  :::
  :::accordion-item{label="26. What happens when you type a URL and press Enter? Keep it under a minute."}
  URL parsed; DNS turns the domain into an IP; TCP handshake, then TLS for
  HTTPS; the browser sends an HTTP GET; a load balancer routes it to an
  application server, which runs code and queries the database; an HTTP
  response comes back with a status code and HTML; the browser builds the DOM,
  fetches CSS, JS and images, and paints.
  :::
  :::accordion-item{label="27. A page returns 503 on results day. What does that tell you?"}
  A server-side problem: the service is unavailable, usually overloaded or down.
  Not the user's fault (that would be 4xx). The fix is capacity (scale out,
  cache the results page) rather than anything in the browser.
  :::
  :::accordion-item{label="28. Is Java compiled or interpreted?"}
  Both. `javac Result.java` produces bytecode in `Result.class`; `java Result`
  starts the JVM, which interprets bytecode and JIT-compiles hot methods into
  machine code.
  :::
  :::accordion-item{label="29. Convert 213 to binary and hex."}
  ```text [Working]
  213 = 128 + 64 + 16 + 4 + 1
      = 1101 0101 (binary)
      = D    5    (hex)  →  0xD5
  Check: 13 × 16 + 5 = 213
  ```
  :::
  :::accordion-item{label="30. What is the value of binary 1111 1111 as a signed 8-bit number?"}
  -1. In two's complement, invert (0000 0000) and add one (0000 0001): the
  magnitude is 1, and the sign bit was set. Unsigned it would be 255.
  :::
  :::accordion-item{label="31. Why is reading from RAM faster than reading from an SSD, and why does it matter to a developer?"}
  RAM is electronic memory next to the CPU, about 100 ns per access; an SSD is
  storage behind a controller and bus, about 100 µs, a thousand times slower.
  It is why frequently read data (a list of departments, a logged-in session)
  is cached in memory rather than read from disk or a database each time.
  :::
::
