The machine code has to sit somewhere while the processor works through it, and
so do the marks it is working on. There is not one "memory" but a ladder of
them, each level bigger, cheaper and far slower than the one above.

## Why this matters in a job

Every performance problem you meet at work is some version of "the data was on
the slow rung of this ladder": a database read from disk, a network call
instead of a cache hit. Caching, one of the most used ideas in software, only
makes sense once you see the gap. And written rounds at service companies still
ask computer organisation questions: "which memory is fastest?", "what is
cache?", "RAM versus ROM?".

## The CPU, analogy first

Think of an exam hall. The **invigilator's desk** (registers) holds the one or
two things in hand right now. The **table beside them** (cache) holds the papers
likely to be needed next. The **cupboard in the hall** (RAM) holds today's
papers. The **records room downstairs** (SSD or hard disk) holds every paper
from every year. Fetching from the desk takes a second; from the records room,
a long walk.

The **CPU** (Central Processing Unit) has three main parts:

::feature-list{columns="3"}
  :::feature{icon="i-lucide-calculator" title="ALU"}
  The Arithmetic Logic Unit. Adds, subtracts, compares, does AND and OR.
  :::
  :::feature{icon="i-lucide-route" title="Control unit"}
  Fetches instructions, decodes them, and tells the other parts what to do.
  :::
  :::feature{icon="i-lucide-square-stack" title="Registers"}
  A handful of tiny, extremely fast storage slots inside the CPU itself.
  :::
::

## How it works

### The fetch-decode-execute cycle

::flow{numbered caption="Repeated billions of times a second. A 3 GHz processor ticks 3 billion times a second."}
  :::flow-step{label="Fetch" icon="i-lucide-download"}
  Read the next instruction from memory, at the address in the **program
  counter**.
  :::
  :::flow-step{label="Decode" icon="i-lucide-scan"}
  The control unit works out what it means: "add these two registers".
  :::
  :::flow-step{label="Execute" icon="i-lucide-zap" highlight}
  The ALU does it; the result goes into a register or memory.
  :::
::

### The memory hierarchy

Put those into human terms by pretending one register access takes one second:

```text [If a register read took 1 second]
Register            1 second
L1 cache            about 1 second
RAM                 about 2 minutes
SSD                 about 1 day
Hard disk           about 4 months
Network, India to Europe and back   about 5 years
```

That is why software caches everything: the difference between memory and disk
is the difference between two minutes and a day.

**Volatile** memory (registers, cache, RAM) loses its contents when power goes.
**Non-volatile** storage (SSD, hard disk, ROM) keeps them.

### RAM and ROM

**RAM** (Random Access Memory) is the read-write working memory where running
programs and their data live. **ROM** (Read-Only Memory) holds firmware that
must survive power-off, such as the code that starts the machine (the BIOS or
UEFI). The operating systems track covers what happens after that.

## Real use case

A university portal shows the list of 40 departments on every page. Reading it
from the database (disk, then network) each time takes around 20 ms; keeping it
in the application's memory takes well under a millisecond. At 5,000 page views
a minute, that single cache saves the database 5,000 queries a minute. Tools
like Redis exist to do exactly this, and the reason they work is the ladder
above.

::side-note{kind="performance"}
**Locality** is why caches work. Programs tend to reuse data they used recently
(temporal locality) and data stored next to it (spatial locality). A loop over an
array of marks is fast because the array sits in consecutive memory and arrives
in the cache a block at a time.
::

## What confuses people here

- **Memory versus storage.** "Memory" usually means RAM; "storage" means the SSD
  or disk. An "8 GB laptop" is talking about RAM.
- **Cache is not one thing.** CPU caches (L1, L2, L3), the browser cache and a
  Redis cache are different, but all rely on the same idea.
- **Clock speed is not the whole story.** A processor waiting for RAM does
  nothing useful however many gigahertz it has.
- **32-bit versus 64-bit** refers to register width and how much memory can be
  addressed: 32 bits addresses at most 4 GB.

## Interview questions

::accordion
  :::accordion-item{label="Arrange in order of speed: RAM, cache, registers, hard disk, SSD."}
  Registers, cache, RAM, SSD, hard disk. Speed falls and size rises as you go
  down; cost per byte falls too.
  :::
  :::accordion-item{label="What is cache memory and why is it needed?"}
  Small, very fast memory between the CPU and RAM that keeps recently and
  frequently used data. The CPU is far faster than RAM, so without cache it
  would spend most of its time waiting.
  :::
  :::accordion-item{label="RAM versus ROM?"}
  RAM is volatile, read-write, and holds running programs and data. ROM is
  non-volatile, mostly read-only, and holds firmware such as the boot code.
  :::
  :::accordion-item{label="What are the main parts of a CPU?"}
  The ALU for arithmetic and logic, the control unit which fetches and decodes
  instructions and coordinates the rest, and registers for the values being
  worked on right now, including the program counter.
  :::
  :::accordion-item{label="Volatile versus non-volatile memory?"}
  Volatile memory loses its contents without power (RAM, cache). Non-volatile
  keeps them (ROM, SSD, hard disk, flash).
  :::
::
