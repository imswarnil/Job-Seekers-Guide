Testing starts long before there is anything to run. The **Software Testing
Life Cycle** (STLC) is the testing team's own set of phases, running alongside
the SDLC. And a bug, once found, has a life of its own, with states and owners
you will see on a Jira ticket every day.

## Why this matters in a job

As a developer, bugs will be assigned to you, and you will need to know what
"Rejected", "Deferred" and "Reopened" mean before you move one. As a tester, the
bug report is your product. In interviews, "explain the bug life cycle" and
"severity versus priority, with an example" are among the most asked testing
questions in India.

## The STLC

Think of an invigilation team for a university exam. Before exam day they read
the rules (requirements), decide which halls and how many invigilators
(planning), write the checklist for each hall (test cases), set up the halls
(environment), run the exam (execution) and file a report (closure). Testing a
system is the same shape.

::flow{numbered direction="vertical" caption="Each phase has an entry condition and produces something the next phase needs."}
  :::flow-step{label="Requirement analysis" icon="i-lucide-file-search"}
  Read the requirements and ask what is testable. Produces a list of questions
  and a **requirement traceability matrix** (RTM) linking each requirement to
  its tests.
  :::
  :::flow-step{label="Test planning" icon="i-lucide-map"}
  Scope, approach, tools, effort, schedule, risks. Produces the **test plan**.
  :::
  :::flow-step{label="Test case design" icon="i-lucide-list-checks" highlight}
  Write test cases and test data. The next lesson is about this phase.
  :::
  :::flow-step{label="Environment set-up" icon="i-lucide-server"}
  A test server with the right build and realistic data. Starts with a smoke
  test.
  :::
  :::flow-step{label="Test execution" icon="i-lucide-play"}
  Run the cases, record pass or fail, log defects.
  :::
  :::flow-step{label="Test closure" icon="i-lucide-flag"}
  Test summary report: what was run, what passed, open defects, lessons.
  :::
::

## How a bug moves

::flow{direction="vertical" caption="The common path. Tools such as Jira let each team rename or add states."}
  :::flow-step{label="New" icon="i-lucide-circle-plus"}
  A tester logs the defect.
  :::
  :::flow-step{label="Assigned" icon="i-lucide-user"}
  A lead reviews it and assigns it to a developer.
  :::
  :::flow-step{label="Open" icon="i-lucide-folder-open"}
  The developer starts working on it.
  :::
  :::flow-step{label="Fixed" icon="i-lucide-wrench"}
  The developer changes the code and sends it back to testing.
  :::
  :::flow-step{label="Retest" icon="i-lucide-refresh-cw" highlight}
  The tester runs the failed case again on the new build.
  :::
  :::flow-step{label="Closed, or Reopened" icon="i-lucide-check-check"}
  Passes: closed. Fails again: reopened and back to the developer.
  :::
::

Three side exits, each an interview favourite:

- **Rejected**: the developer says it is not a bug (working as designed).
- **Duplicate**: the same defect is already logged.
- **Deferred**: a real bug, but it will be fixed in a later release.

### Severity and priority

**Severity** is how badly the bug hurts the system. **Priority** is how soon it
must be fixed. A tester usually sets severity; the product owner or lead sets
priority. They are independent, which is why the four combinations are asked:

| | High priority | Low priority |
| --- | --- | --- |
| **High severity** | Fee payment crashes for every student on the last date | The yearly archive report crashes, and it runs once in March |
| **Low severity** | The university's name is misspelt on the home page | A tooltip on an admin page has a typo |

### A bug report that will not bounce

```text [BUG-1182]
Title       : Late fee not added when payment is made after the due date
Environment : QA server, build 4.3.1, Chrome 128, Windows 11
Severity    : High          Priority : High
Steps to reproduce:
  1. Log in as student 22CS041 (fee due 15-08-2026, not paid)
  2. Set system date to 20-08-2026
  3. Open Fees > Pay semester fee
Expected    : Amount shown = Rs 48,000 + late fee Rs 250 = Rs 48,250
Actual      : Amount shown = Rs 48,000
Attachments : screenshot.png, console-log.txt
```

## Real use case

::compare{caption="The developer can act on only one of these."}
  :::compare-side{label="Bounced back as 'cannot reproduce'" verdict="wrong"}
  "Late fee not working. Please check urgently."
  :::
  :::compare-side{label="Fixed the same day" verdict="right"}
  Exact steps, the student ID used, the build number, expected against actual
  with numbers, and a screenshot.
  :::
::

::real-life{title="Rejected is not an insult" source="Every project"}
A developer marking a bug "Rejected: working as designed" is often right, and
sometimes the requirement itself was unclear. The fix then is not an argument in
Jira comments but a two-minute call with the product owner. Learning to tell
those apart early saves more time than any tool.
::

## What confuses people here

- **STLC is not separate from SDLC.** It runs inside it, in parallel with
  development, and starts at requirements, not after coding.
- **Severity and priority are not the same scale.** A typo in the university's
  name is low severity and top priority.
- **Fixed is not Closed.** Only the tester closes a bug, after retesting.
- **Defect, bug, error, failure.** A developer's **error** (mistake) causes a
  **defect** (bug) in the code, which may cause a **failure** when it runs.

## Interview questions

::accordion
  :::accordion-item{label="What are the phases of STLC?"}
  Requirement analysis, test planning, test case design, environment set-up,
  test execution, test closure. Each has entry and exit criteria and a
  deliverable: RTM, test plan, test cases, a ready environment, execution
  results and defects, the summary report.
  :::
  :::accordion-item{label="Explain the bug life cycle."}
  New, assigned, open, fixed, retest, then closed if it passes or reopened if it
  fails. Side exits: rejected (not a bug), duplicate, deferred (fix later).
  :::
  :::accordion-item{label="Severity versus priority, with an example of high priority and low severity."}
  Severity is impact on the system; priority is urgency of the fix. High
  priority, low severity: the university's name misspelt on the home page. It
  breaks nothing, but everyone sees it, so it is fixed first.
  :::
  :::accordion-item{label="What goes into a good bug report?"}
  A specific title, environment and build, severity and priority, numbered steps
  to reproduce with the exact data used, expected result, actual result, and
  evidence such as a screenshot or log.
  :::
  :::accordion-item{label="What is a requirement traceability matrix?"}
  A table mapping each requirement to the test cases that cover it (and later to
  their results and defects). It proves every requirement is tested and shows
  what is affected when a requirement changes.
  :::
::
