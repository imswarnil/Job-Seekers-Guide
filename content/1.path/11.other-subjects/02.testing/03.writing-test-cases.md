A **test case** is a written instruction precise enough that a stranger could
run it and reach the same verdict you would. That is the standard, and most
first attempts miss it by being vague about the data.

## Why this matters in a job

In a testing role you will write dozens a week, and a review lead will send back
any that say "enter valid details". In a developer role your unit tests are test
cases in code. And in interviews, especially for QA roles, "write test cases for
a login page" (or a pen, or a lift, or an ATM) is asked constantly. It is testing
whether you think about the unhappy paths.

## A test case, analogy first

A recipe that says "add some salt, cook till done" works for the person who
wrote it. A recipe that says "5 g salt, 12 minutes at medium heat, the rice
should be soft with no hard centre" works for anybody. A test case is the second
kind of recipe, and its "should be" line is the **expected result**.

The standard fields:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-hash" title="ID and title"}
  `TC_LOGIN_03`, and what it checks in one line.
  :::
  :::feature{icon="i-lucide-list-start" title="Preconditions"}
  What must be true first: the account exists, the browser is open.
  :::
  :::feature{icon="i-lucide-footprints" title="Steps"}
  Numbered, one action each.
  :::
  :::feature{icon="i-lucide-database" title="Test data"}
  The exact values. Never "a valid ID".
  :::
  :::feature{icon="i-lucide-target" title="Expected result"}
  What should happen, observable and specific.
  :::
  :::feature{icon="i-lucide-clipboard-check" title="Actual result and status"}
  Filled in at execution. Pass, fail or blocked.
  :::
::

## How it works

Requirement: *A student logs in to the portal with a roll number and password.
Roll numbers look like 22CS041. Five wrong passwords lock the account for 30
minutes.*

| ID | Title | Test data | Expected result | Type |
| --- | --- | --- | --- | --- |
| TC_LOGIN_01 | Valid roll number and password | 22CS041 / `Exam@2026` | Dashboard opens, shows "Welcome, Priya" | Positive |
| TC_LOGIN_02 | Valid roll number, wrong password | 22CS041 / `exam@2026` | "Invalid roll number or password", stays on login | Negative |
| TC_LOGIN_03 | Roll number that does not exist | 22CS999 / `Exam@2026` | Same message as TC_LOGIN_02 (does not reveal which field was wrong) | Negative, security |
| TC_LOGIN_04 | Both fields empty | blank / blank | Login button disabled, or "Roll number is required" | Negative |
| TC_LOGIN_05 | Roll number in lower case | 22cs041 / `Exam@2026` | Logs in (roll numbers are case-insensitive, confirm with the PO) | Edge |
| TC_LOGIN_06 | Fifth wrong password | 22CS041, wrong five times | Account locked for 30 minutes, message says so | Boundary |
| TC_LOGIN_07 | Fourth wrong password | 22CS041, wrong four times | Not locked, fifth attempt still allowed | Boundary |
| TC_LOGIN_08 | Password field masks input | type `Exam@2026` | Shows dots, not characters | UI |
| TC_LOGIN_09 | SQL injection in roll number | `' OR '1'='1` / anything | Rejected with the normal error, no login | Security |

Notice the proportions: one positive case and eight that try to break it. That
ratio is normal. Users find the unhappy paths for you if you do not.

A single case written out in full:

```text [TC_LOGIN_06.txt]
ID            : TC_LOGIN_06
Title         : Account locks after the fifth consecutive wrong password
Precondition  : Account 22CS041 exists and is not locked
Steps         : 1. Open https://portal.test/login
                2. Enter roll number 22CS041, password wrong1, click Login
                3. Repeat step 2 with wrong2, wrong3, wrong4, wrong5
                4. Enter the correct password Exam@2026, click Login
Expected      : After step 3: "Account locked for 30 minutes"
                After step 4: still locked, dashboard does not open
Actual        : (filled at execution)
Status        : (Pass / Fail / Blocked)
```

## Real use case

Cases 06 and 07 come from **boundary value analysis**: the limit is five, so
test four and five (and six, if you have time). Cases 02, 03 and 04 come from
**equivalence partitioning**: all wrong passwords behave the same, so one
represents the group. Those two techniques are how a tester chooses nine cases
instead of nine hundred, and saying their names while you answer is what
separates a prepared candidate.

::tip
When an interviewer says "write test cases for a pen", they want categories, not
fifty lines. Say: functional (does it write, does the cap fit), boundary (writes
at a 45° angle, at the last drop of ink), negative (on wet paper, dropped from a
desk), non-functional (how many metres of line, comfort after an hour). Then
give two or three in each.
::

## What confuses people here

- **Test case versus test scenario.** A scenario is *what* to test, one line:
  "check student login". A test case is *how*, with steps and data. One
  scenario has many cases.
- **Test case versus test script.** A script is automated code that performs a
  test case.
- **Expected results must be observable.** "Works correctly" is not an expected
  result. "Dashboard opens and shows Welcome, Priya" is.
- **Do not reveal which field was wrong.** TC_LOGIN_03 is a security case that
  most freshers miss.

## Interview questions

::accordion
  :::accordion-item{label="Write test cases for a login page."}
  Group them. Positive: valid credentials. Negative: wrong password, unknown user,
  empty fields, spaces. Boundary: maximum length, the lock-out limit and one
  below it. Security: SQL injection, password masked, same error for both wrong
  fields, session expiry. UI: tab order, Enter key submits, error message
  placement.
  :::
  :::accordion-item{label="Test case versus test scenario?"}
  A scenario is a one-line statement of what to test ("verify fee payment by
  UPI"). A test case is a detailed, executable instruction with preconditions,
  steps, data and expected result. One scenario usually has several cases.
  :::
  :::accordion-item{label="What makes a good test case?"}
  Independent of other cases, one thing checked, exact test data, numbered
  steps, an observable expected result, and traceable to a requirement.
  :::
  :::accordion-item{label="Positive versus negative testing?"}
  Positive testing uses valid input to confirm the system does what it should.
  Negative testing uses invalid or unexpected input to confirm it fails
  gracefully: a clear message, no crash, no data corrupted.
  :::
::
