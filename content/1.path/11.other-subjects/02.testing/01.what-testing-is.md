QA is the column where somebody other than the author tries to prove the code
wrong. That is the whole job, stated plainly, and it is split into levels and
types so that nothing is checked twice and nothing is missed.

## Why this matters in a job

Every developer tests: you will write unit tests from your first sprint. And a
large share of fresher openings in Bangalore are testing roles (manual QA,
automation with Selenium), which are a perfectly good way in. At the walk-ins I
went to, "smoke versus sanity" and "regression versus retesting" came up more
often than any Java question except OOPs.

## Testing, analogy first

Think of an exam being prepared for 600 students. The paper-setter checks each
question has one correct answer (**unit**). The coordinator checks the questions
fit together, numbered right, marks adding to 100 (**integration**). The
controller of examinations checks the whole printed paper, timing and
instructions (**system**). Finally a teacher who never saw it sits it as a
student would (**acceptance**). Four people, four levels, each catching what the
one before could not.

**Software testing** is running software to find differences between what it
does and what it should do. A **defect** (bug) is such a difference.

## How it works

### Manual and automated

::compare{caption="Most teams use both. Automation does not replace a human, it replaces repetition."}
  :::compare-side{label="Manual testing" verdict="neutral"}
  A person follows test cases by hand and judges the result. Best for new
  features, exploratory testing, and anything about how a screen *feels*. Slow
  to repeat.
  :::
  :::compare-side{label="Automation testing" verdict="neutral"}
  A script performs the steps and checks the result (Selenium for browsers,
  JUnit for Java, Postman for APIs). Costly to write, cheap to rerun a thousand
  times. Best for regression.
  :::
::

### The four levels

::flow{numbered direction="vertical" caption="Bottom to top. Each level assumes the one below has passed."}
  :::flow-step{label="Unit testing" icon="i-lucide-box"}
  One method or class in isolation. Written by the **developer**. Example: does
  `calculateLateFee(10)` return 500?
  :::
  :::flow-step{label="Integration testing" icon="i-lucide-link"}
  Two or more units together. Does the fee service save a payment the report
  service can then read?
  :::
  :::flow-step{label="System testing" icon="i-lucide-monitor" highlight}
  The complete application against the requirements, on an environment like
  production. Done by the **testing team**.
  :::
  :::flow-step{label="User acceptance testing (UAT)" icon="i-lucide-user-check"}
  Real users or the client check it does what they need. **Alpha** is done at
  the vendor's site, **beta** by real users in their own world.
  :::
::

A unit test in Java, with JUnit 5:

```java [LateFeeTest.java]
import static org.junit.jupiter.api.Assertions.assertEquals;
import org.junit.jupiter.api.Test;

class LateFeeTest {

    // Rule: Rs 50 a day late, capped at Rs 1,000.
    static int calculateLateFee(int daysLate) {
        if (daysLate <= 0) return 0;
        return Math.min(daysLate * 50, 1000);
    }

    @Test void onTimeCostsNothing()    { assertEquals(0,    calculateLateFee(0)); }
    @Test void tenDaysLate()           { assertEquals(500,  calculateLateFee(10)); }
    @Test void capIsApplied()          { assertEquals(1000, calculateLateFee(45)); }
}
```

```text [Output]
LateFeeTest > onTimeCostsNothing() PASSED
LateFeeTest > tenDaysLate() PASSED
LateFeeTest > capIsApplied() PASSED

3 tests completed, 0 failed
```

### The types

**Functional testing** checks *what* the system does (can a student pay a
fee?). **Non-functional testing** checks *how well* it does it: performance
(does it survive 5,000 students paying on the last day?), security, usability,
compatibility across browsers.

The pairs interviewers ask about:

| Pair | First one | Second one |
| --- | --- | --- |
| **Smoke vs sanity** | Smoke: a quick, broad check that a **new build** is stable enough to test at all. Login works, main pages open. Often scripted. | Sanity: a quick, narrow check that a **specific fix or change** works, before deeper testing. Usually unscripted. |
| **Regression vs retesting** | Regression: rerun existing tests to check a change **did not break what used to work**. | Retesting: rerun the **failed test** to confirm the reported bug is now fixed. |
| **Black box vs white box** | Black box: test from outside, knowing only inputs and expected outputs. Testers. | White box: test with knowledge of the code, its paths and branches. Developers. |
| **Verification vs validation** | Reviews without running code. | Running the code against needs. |

::tip
A memory hook for smoke and sanity: **smoke** comes from hardware, where you
switched a new board on and checked it did not catch fire. Broad and shallow.
**Sanity** is "is this one thing sane now?" Narrow and focused.
::

## Real use case

The day before semester registration opens, a university's portal gets a fix
to the course-selection page. The testing team runs a **smoke test** on the new
build (login, dashboard, payment page all open), a **sanity test** on course
selection (the fix works), **retests** the original bug, then kicks off the
automated **regression suite** overnight to be sure fee payment, hall tickets
and results still work. Four kinds of testing in one evening, each answering a
different question.

::side-note{kind="go-deeper"}
Two techniques for choosing test inputs come up in testing interviews.
**Equivalence partitioning**: if marks 0–39 fail and 40–100 pass, test one value
from each group (25 and 70) instead of all 101. **Boundary value analysis**:
bugs cluster at the edges, so test 39, 40, 41, 0, 100, -1 and 101.
::

## What confuses people here

- **Smoke and sanity get swapped.** Smoke is broad and on a new build; sanity is
  narrow and on a change.
- **Regression is not retesting.** Retesting checks the bug is fixed; regression
  checks nothing else broke.
- **"Testing proves there are no bugs."** It cannot. Testing shows the presence of
  defects, never their absence. It is one of the seven testing principles.
- **UAT is not the testing team's job.** It is the users' or client's.

## Interview questions

::accordion
  :::accordion-item{label="What are the levels of testing?"}
  Unit (one component, by developers), integration (components together),
  system (the whole application against requirements, by testers), and user
  acceptance (by the client or end users). Each assumes the level below passed.
  :::
  :::accordion-item{label="Smoke testing versus sanity testing?"}
  Smoke: broad, shallow check that a new build is stable enough to test further.
  Sanity: narrow check that a particular fix or feature works after a change.
  Smoke is often scripted and done first; sanity is usually unscripted.
  :::
  :::accordion-item{label="Regression testing versus retesting?"}
  Retesting runs the specific failed test again to confirm a bug is fixed.
  Regression reruns the wider suite to confirm the change did not break working
  features. Regression is the prime candidate for automation.
  :::
  :::accordion-item{label="What is boundary value analysis? Give an example."}
  Testing at and around the edges of valid ranges, where defects cluster. For
  pass marks 40–100: test 39, 40, 41, 99, 100 and 101.
  :::
  :::accordion-item{label="Functional versus non-functional testing?"}
  Functional checks behaviour against requirements (paying a fee generates a
  receipt). Non-functional checks qualities: performance, load, security,
  usability, compatibility.
  :::
  :::accordion-item{label="Alpha versus beta testing?"}
  Both are forms of acceptance testing. Alpha is done by internal users or the
  client at the developer's site before release. Beta is done by real users in
  their own environment, and their feedback shapes the final release.
  :::
::
