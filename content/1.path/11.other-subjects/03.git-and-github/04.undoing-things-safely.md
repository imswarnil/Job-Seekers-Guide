Almost every mistake in Git can be undone, and the right command depends on one
question: **has anybody else already got this commit?** If not, you can rewrite
history. If they have, you add a new commit that undoes the old one.

## Why this matters in a job

Because you will commit to the wrong branch, commit a half-finished file, or
push a bug to `main`, and the team will watch how you recover. "How do you undo
a commit that is already pushed?" and "reset versus revert?" are among the most
asked Git questions, precisely because the wrong answer loses other people's
work.

## Undo, analogy first

A university results register kept in ink. If you spot a wrong mark before the
page is sent to the exam controller, you can tear out the page and rewrite it
(rewriting history). Once copies have been sent to every department, tearing
out your page does not help and confuses everyone: you write a correction entry
instead (reverting). Git works the same way.

## How it works

::flow{direction="vertical" caption="Pick the command by where the mistake is."}
  :::flow-step{label="Edited a file, not staged" icon="i-lucide-file-x"}
  `git restore attendance.csv` puts the file back to the last commit.
  :::
  :::flow-step{label="Staged, not committed" icon="i-lucide-inbox"}
  `git restore --staged attendance.csv` unstages it, keeps your edit.
  :::
  :::flow-step{label="Committed, not pushed" icon="i-lucide-git-commit-horizontal"}
  `git commit --amend` to fix the last commit, or `git reset` to move back.
  :::
  :::flow-step{label="Committed and pushed" icon="i-lucide-cloud" highlight}
  `git revert <commit>` creates a new commit that undoes it. History stays
  intact for everyone.
  :::
::

### Fixing the last commit

```bash [Terminal]
git add forgotten-file.csv
git commit --amend -m "Add semester 5 attendance, both sections"
```

`--amend` replaces the last commit with a new one. Only for commits you have not
pushed.

### Revert: the safe undo for shared history

```bash [Terminal]
git log --oneline -3
git revert c41d7e2
```

```text [Output]
5e8a2f0 (HEAD -> main, origin/main) Merge fix-header
c41d7e2 Add percentage column
9b2e4d1 Add DBMS attendance for 22CS041
[main 7a19b03] Revert "Add percentage column"
 1 file changed, 1 insertion(+), 1 deletion(-)
```

The bad commit is still in history, and a new commit cancels it. Push that
normally. Nobody's copy breaks.

### Reset, three strengths

`git reset` moves the branch label back to an earlier commit. What happens to
the changes from the commits you stepped over depends on the flag:

| Command | Branch moves back | Staging area | Your files |
| --- | --- | --- | --- |
| `git reset --soft HEAD~1` | yes | changes kept, staged | untouched |
| `git reset HEAD~1` (mixed, the default) | yes | cleared | changes kept, unstaged |
| `git reset --hard HEAD~1` | yes | cleared | **changes deleted** |

`HEAD~1` means "one commit before where I am".

::warning{icon="i-lucide-alert-triangle"}
**`git reset --hard` deletes uncommitted work with no confirmation and no
recycle bin.** Anything you changed and did not commit is gone. Before you run
it, run `git status` and `git stash` anything you might want. Never paste it
from a forum answer without reading what it will throw away.
::

::warning{icon="i-lucide-alert-triangle"}
**`git push --force` overwrites the remote branch with yours.** If a colleague
pushed commits you do not have, they disappear from the remote, and they find
out when their next pull goes wrong. Never force-push to `main` or any shared
branch. If you must force-push your own feature branch after a rebase, use
`git push --force-with-lease`, which refuses if the remote has commits you have
not seen.
::

### Stash: put work aside

```bash [Terminal]
git stash
git switch main
# fix the urgent bug, commit, switch back
git switch add-percentage
git stash pop
```

```text [Output]
Saved working directory and index state WIP on add-percentage: c41d7e2 Add percentage column
Switched to branch 'main'
Switched to branch 'add-percentage'
On branch add-percentage
Changes not staged for commit:
	modified:   attendance.csv
Dropped refs/stash@{0} (4b7e1d9...)
```

### Reflog: the safety net

Git records every place `HEAD` has been for about 90 days. If a reset went
wrong, the "lost" commit is usually still there:

```bash [Terminal]
git reflog -3
git reset --hard c41d7e2
```

```text [Output]
9b2e4d1 HEAD@{0}: reset: moving to HEAD~1
c41d7e2 HEAD@{1}: commit: Add percentage column
9b2e4d1 HEAD@{2}: commit: Add DBMS attendance for 22CS041
HEAD is now at c41d7e2 Add percentage column
```

Reflog saves commits. It cannot save changes that were never committed, which is
why the warning above says stash first.

## Real use case

::compare{caption="A bug reached main and the team has already pulled it."}
  :::compare-side{label="Rewrites shared history" verdict="wrong"}
  `git reset --hard HEAD~1` then `git push --force`. Every colleague's `main` now
  disagrees with the remote, and any commit pushed in between is gone.
  :::
  :::compare-side{label="Adds a correction" verdict="right"}
  `git revert <bad-commit>` then `git push`. One new commit, nothing lost, and
  the history shows exactly what happened.
  :::
::

## What confuses people here

- **Reset versus revert.** Reset moves the branch back (rewrites history).
  Revert adds a new commit that undoes one (keeps history).
- **`--amend` changes the commit's ID.** It is a new commit, so the same rule
  applies: not after pushing.
- **`restore` versus `reset`.** `restore` works on files; `reset` moves the
  branch.
- **Committed to the wrong branch?** Note the commit ID, switch to the right
  branch, `git cherry-pick <id>`, then remove it from the wrong one with a
  reset (if unpushed).

## Interview questions

::accordion
  :::accordion-item{label="git reset versus git revert?"}
  Reset moves the branch pointer to an earlier commit, discarding the later ones
  from the branch; safe only for commits nobody else has. Revert creates a new
  commit that applies the inverse of a given commit; safe for shared history.
  :::
  :::accordion-item{label="How do you undo a commit that has already been pushed?"}
  `git revert <commit>` and push the new commit. Do not reset and force-push a
  shared branch: it rewrites history under your colleagues.
  :::
  :::accordion-item{label="Soft, mixed and hard reset?"}
  All move the branch back. `--soft` keeps the changes staged, mixed (default)
  keeps them in the working directory unstaged, `--hard` discards them
  completely.
  :::
  :::accordion-item{label="What is git stash?"}
  It saves uncommitted changes on a stack and cleans the working directory, so
  you can switch branches. `git stash pop` reapplies the latest and removes it
  from the stack; `git stash list` shows them.
  :::
  :::accordion-item{label="You ran reset --hard by mistake. Can you recover?"}
  Committed work, usually yes: `git reflog` shows where HEAD was, then
  `git reset --hard <that id>`. Uncommitted changes that were never staged or
  stashed, no.
  :::
  :::accordion-item{label="What does git cherry-pick do?"}
  Applies the changes of one specific commit from another branch onto the
  current branch as a new commit. Useful to move a commit made on the wrong
  branch, or to bring one fix into a release branch.
  :::
::
