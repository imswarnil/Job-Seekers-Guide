A **branch** is a separate line of commits growing out of the main one, so you
can fix a bug on one line while a colleague builds a feature on another, and
`main` keeps working for everybody until each is ready.

## Why this matters in a job

Nobody at a company commits directly to `main`. You create a branch per ticket
(`feature/STU-214-attendance-card`, `bugfix/BUG-1182-late-fee`), work there,
and merge through a pull request. And one week in, you will hit your first merge
conflict. Interviewers ask "what is a branch?", "merge versus rebase?" and "how
do you resolve a conflict?" because the answers show whether you have worked
with other people's code.

## What a branch actually is

Not a copy of the folder. Git keeps one set of commits, and a branch is a small
label pointing at one of them. Creating a branch writes about 41 bytes, which is
why it is instant even on a huge project. Think of bookmarks in the same
textbook: two bookmarks, one book.

::flow{numbered direction="vertical" caption="Two lines of work from the same starting point."}
  :::flow-step{label="main, two commits in" icon="i-lucide-git-commit-horizontal"}
  The attendance sheet works. This is what everyone relies on.
  :::
  :::flow-step{label="A branch off the second commit" icon="i-lucide-git-branch" highlight}
  `add-percentage`. Same history behind it; from here the lines diverge.
  :::
  :::flow-step{label="Commits on the branch" icon="i-lucide-file-pen"}
  You add a percentage column. `main` has not moved.
  :::
  :::flow-step{label="Merge back" icon="i-lucide-git-merge"}
  When it works, its commits join `main`. If it never works, delete the branch
  and nothing was lost.
  :::
::

## How it works

```bash [Terminal]
git switch -c add-percentage
git branch
```

```text [Output]
Switched to a new branch 'add-percentage'
  main
* add-percentage
```

`switch -c` creates a branch and moves to it. The older `git checkout -b` does
the same. The asterisk is where you are. Work normally; commits land on this
branch.

```bash [Terminal]
sed -i 's/Total$/Total,Percent/' attendance.csv
git commit -am "Add percentage column"
git switch main
```

`-a` stages every already-tracked file that changed. Back on `main`, the file has
its old contents: Git swapped the working directory for `main`'s snapshot.

### Merging

Go to the branch you want to merge *into*, then merge the other one in:

```bash [Terminal]
git merge add-percentage
```

```text [Output]
Updating 9b2e4d1..c41d7e2
Fast-forward
 attendance.csv | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

::compare{caption="The two kinds of merge."}
  :::compare-side{label="Fast-forward" verdict="neutral"}
  `main` had not moved since the branch started, so Git slides the `main` label
  forward. No new commit.
  :::
  :::compare-side{label="Three-way merge" verdict="neutral"}
  Both lines have new commits. Git combines them using their common ancestor and
  creates a **merge commit** with two parents.
  :::
::

### The conflict

It happens when two branches change **the same lines of the same file**, and
Git will not guess which you meant.

```bash [Terminal]
git merge fix-header
```

```text [Output]
Auto-merging attendance.csv
CONFLICT (content): Merge conflict in attendance.csv
Automatic merge failed; fix conflicts and then commit the result.
```

Nothing is broken and nothing is lost. Git has paused and written both versions
into the file:

```text [attendance.csv]
<<<<<<< HEAD
Student,Course,Attended,Total,Percent
=======
RollNo,Course,Attended,Total
>>>>>>> fix-header
22CS041,DBMS,38,42,90.5
```

::feature-list{columns="3"}
  :::feature{icon="i-lucide-arrow-up" title="HEAD to ======="}
  The version on the branch you are standing on.
  :::
  :::feature{icon="i-lucide-arrow-down" title="======= to >>>>>>>"}
  The version from the branch you are merging in.
  :::
  :::feature{icon="i-lucide-pencil" title="Your job"}
  Edit the file to what it should be, delete all three markers.
  :::
::

```bash [Terminal]
# after editing the line to: RollNo,Course,Attended,Total,Percent
git add attendance.csv
git commit -m "Merge fix-header, keep both the rename and the percent column"
```

```text [Output]
[main 5e8a2f0] Merge fix-header, keep both the rename and the percent column
```

::tip
Often the right answer is neither side but both, as here: one branch renamed a
column, the other added one. Read both before choosing. If you are lost,
`git merge --abort` puts everything back to before the merge.
::

## Real use case

Teams name branches after tickets and keep them short-lived: a branch that lives
two days merges easily; a branch that lives two months is a week of conflicts.
Pull `main` into your branch every morning and the conflicts stay small.

::real-life{title="My first conflict" source="Accenture, 2019"}
I saw `CONFLICT` in red on a shared project and assumed I had broken something
for everybody. I had not. The file had two versions in it and I had to pick. It
took four minutes once somebody showed me the markers. The fear cost more time
than the fix.
::

## What confuses people here

- **A branch is not a copy.** It is a pointer to a commit.
- **Merge direction.** You stand on the branch that *receives* the changes.
- **Conflicts are per line, not per file.** Two people editing different parts
  of the same file merge cleanly.
- **Merge versus rebase.** Rebase replays your commits on top of the other
  branch, giving a straight history with no merge commit. Never rebase commits
  others already have: it rewrites their IDs.

## Interview questions

::accordion
  :::accordion-item{label="What is a branch in Git?"}
  A lightweight, movable pointer to a commit. New commits on a branch move its
  pointer forward. It lets several lines of work proceed in parallel without
  affecting `main`.
  :::
  :::accordion-item{label="What is a merge conflict and how do you resolve it?"}
  When two branches change the same lines differently, Git cannot decide and
  marks the file with `<<<<<<<`, `=======` and `>>>>>>>`. Open the file, decide
  the correct content, remove the markers, `git add` the file, then `git commit`.
  `git merge --abort` cancels the merge.
  :::
  :::accordion-item{label="Fast-forward versus three-way merge?"}
  Fast-forward: the target branch has no new commits, so its pointer moves
  forward, no merge commit. Three-way: both have diverged, so Git combines them
  using the common ancestor and creates a merge commit with two parents.
  :::
  :::accordion-item{label="git merge versus git rebase?"}
  Merge keeps history as it happened and adds a merge commit. Rebase moves your
  commits onto the tip of another branch, rewriting them, for a linear history.
  Rule: do not rebase shared, already-pushed commits.
  :::
  :::accordion-item{label="git checkout versus git switch?"}
  `checkout` is the older command that does several jobs (switch branches and
  restore files). `switch` changes branches and `restore` restores files; they
  were added in Git 2.23 to split those jobs.
  :::
::
