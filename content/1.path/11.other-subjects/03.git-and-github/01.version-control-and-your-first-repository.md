Two people editing the same code on the same day, and a need to know who
changed what, when, and how to get yesterday's version back. The tool that
solves all three is **Git**, and you will use it every working day of your
career.

## Why this matters in a job

On your first day you will be given a repository link and asked to "clone it and
raise a PR". There is no job in software, developer or tester, where Git is
optional. In interviews: "What is Git?", "Git versus GitHub?", "What does
`git add` do?", "What is a commit?". They are easy marks, and missing them
suggests you have never worked in a team.

## Version control, analogy first

You have seen folders like this. I had one at JSpiders:

```text [My folder, 2018]
StudentReport.java
StudentReport_v2.java
StudentReport_v2_final.java
StudentReport_v2_final_WORKING.java
StudentReport_v3_dont_use.java
```

That is version control done badly by hand: no record of what changed between
them or why, and no way for two people to work on it at once.

**Version control** is a system that records every change to a set of files, so
you can see who changed what and why, and go back to any earlier state. Think of
it as the register a college office keeps for every change to a student's
record: date, clerk, what changed, why. Nothing is overwritten; everything is
appended.

**Git** is the version control system nearly everyone uses, created in 2005 by
Linus Torvalds for the Linux kernel. It is **distributed**: every developer has
the full history on their own machine. **GitHub** is a website that hosts Git
repositories online and adds pull requests, reviews and issues. Git is the tool;
GitHub is one place to keep what it produces (GitLab and Bitbucket are others).

## How it works

A **repository** (repo) is a folder whose history Git is tracking. A **commit**
is a saved snapshot of the files, with a message, an author and a unique ID.

Files move between three areas:

::flow{caption="git add moves changes right one step; git commit moves them right again."}
  :::flow-step{label="Working directory" icon="i-lucide-folder"}
  The files as you are editing them now.
  :::
  :::flow-step{label="Staging area" icon="i-lucide-inbox" highlight}
  Changes you have chosen for the next commit. Also called the **index**.
  :::
  :::flow-step{label="Repository" icon="i-lucide-archive"}
  Committed snapshots, permanent history.
  :::
::

### Once per machine

```bash [Terminal]
git --version
git config --global user.name "Priya Sharma"
git config --global user.email "priya@example.com"
```

```text [Output]
git version 2.46.0
```

Every commit is stamped with this name and email. Set it before your first
commit, or your history at work will say "unknown".

### A first session

```bash [Terminal]
mkdir attendance-report && cd attendance-report
git init
```

```text [Output]
Initialized empty Git repository in /home/priya/attendance-report/.git/
```

`git init` creates a hidden `.git` folder. That folder *is* the repository; delete
it and the history is gone. Now create a file and ask Git what it sees:

```bash [Terminal]
echo "Student,Course,Attended,Total" > attendance.csv
git status
```

```text [Output]
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	attendance.csv

nothing added to commit but untracked files present (use "git add" to track)
```

**Untracked** means Git sees the file but is not recording it. Stage it, then
commit:

```bash [Terminal]
git add attendance.csv
git commit -m "Add attendance sheet with header row"
```

```text [Output]
[main (root-commit) 3f7a1c9] Add attendance sheet with header row
 1 file changed, 1 insertion(+)
 create mode 100644 attendance.csv
```

`3f7a1c9` is the start of the commit's ID, a **hash** computed from its contents.
Now change the file and look at the difference before committing:

```bash [Terminal]
echo "22CS041,DBMS,38,42" >> attendance.csv
git diff
```

```text [Output]
diff --git a/attendance.csv b/attendance.csv
index 2b1e5c3..8d4f0a2 100644
--- a/attendance.csv
+++ b/attendance.csv
@@ -1 +1,2 @@
 Student,Course,Attended,Total
+22CS041,DBMS,38,42
```

Lines starting `+` were added, `-` removed. Commit it and read the history:

```bash [Terminal]
git add attendance.csv
git commit -m "Add DBMS attendance for 22CS041"
git log --oneline
```

```text [Output]
9b2e4d1 (HEAD -> main) Add DBMS attendance for 22CS041
3f7a1c9 Add attendance sheet with header row
```

Newest first. **HEAD** is Git's name for "where you are now".

::tip
Run `git status` constantly: before you add, after you add, before you commit.
It costs nothing and it answers the question you are about to get wrong.
::

## Real use case

A commit message is written for the colleague who reads the history in six
months, often you.

::compare{caption="The log is only useful if the messages are."}
  :::compare-side{label="Useless in six months" verdict="wrong"}
  `fixed`, `changes`, `asdf`, `final commit`, `updated file`
  :::
  :::compare-side{label="Readable history" verdict="right"}
  `Fix late fee not added after due date (BUG-1182)`, one change per commit,
  present tense, the ticket number where there is one.
  :::
::

## What confuses people here

- **Git versus GitHub.** Git runs on your machine and needs no internet. GitHub
  is a hosting service built around it.
- **`git add` does not save anything permanently.** It stages. Only `commit`
  records history.
- **Why the staging area exists.** So you can commit some changes and not
  others: fix a bug and tidy formatting, then commit them as two clear commits.
- **`main` or `master`.** Both are only the default branch's name. Newer
  repositories use `main`.

## Interview questions

::accordion
  :::accordion-item{label="What is Git? How is it different from GitHub?"}
  Git is a distributed version control system that records snapshots of a
  project so you can track and undo changes and work in parallel. GitHub is a
  website that hosts Git repositories and adds collaboration features: pull
  requests, code review, issues, Actions.
  :::
  :::accordion-item{label="What is the staging area?"}
  An intermediate area between the working directory and the repository.
  `git add` puts changes there; `git commit` turns everything staged into one
  snapshot. It lets you choose exactly what goes into each commit.
  :::
  :::accordion-item{label="What is a commit?"}
  A snapshot of the tracked files at a moment, with an author, a timestamp, a
  message, a pointer to its parent commit, and a SHA-1 hash that identifies it,
  such as `9b2e4d1`.
  :::
  :::accordion-item{label="What does distributed version control mean?"}
  Every clone has the complete history, not only the latest files. You can
  commit, branch and read history offline; a central server is a convention for
  sharing, not a requirement. The older, centralised model (SVN) needed the
  server for almost everything.
  :::
  :::accordion-item{label="What does git diff show, and git diff --staged?"}
  `git diff` shows changes in the working directory not yet staged.
  `git diff --staged` shows what is staged and will go into the next commit.
  :::
::
