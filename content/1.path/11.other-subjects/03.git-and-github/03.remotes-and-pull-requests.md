The second home is a **remote**: a copy of the repository on another machine,
usually GitHub, that everybody on the team pushes to and pulls from. Your laptop
can burn; the history survives.

## Why this matters in a job

Your first task at a new company is nearly always "clone the repo, make a small
change on a branch, raise a PR". A **pull request** is how every change reaches
`main` at work, and reviewing other people's PRs is part of your job from week
one. For a fresher, a GitHub profile with real commits is also the easiest
evidence you can code.

## Remotes, analogy first

Think of the university's central records office and your department's copy of
the register. You work on your copy, then send changes to the office (**push**),
and collect changes others sent (**pull**). The office keeps the official copy,
but every department has the whole register.

| Command | What it does |
| --- | --- |
| `git clone <url>` | Copy a remote repository, with its full history, to your machine |
| `git remote -v` | List the remotes this repository knows. `origin` is the default name |
| `git push` | Send your commits to the remote |
| `git fetch` | Download new commits from the remote, change nothing locally |
| `git pull` | `fetch`, then merge them into your current branch |

## How it works

### Connecting a local repository to GitHub

Create an empty repository on github.com (no README), then:

```bash [Terminal]
git remote add origin https://github.com/priya-sharma/attendance-report.git
git push -u origin main
```

```text [Output]
Enumerating objects: 9, done.
Counting objects: 100% (9/9), done.
Writing objects: 100% (9/9), 812 bytes | 812.00 KiB/s, done.
Total 9 (delta 1), reused 0 (delta 0)
To https://github.com/priya-sharma/attendance-report.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

`-u` links your local `main` to `origin/main`, so from now on `git push` and
`git pull` need no arguments. GitHub no longer accepts your account password on
the command line: use a **personal access token** or an SSH key.

### The rejected push

Everyone meets this in their first week:

```bash [Terminal]
git push
```

```text [Output]
To https://github.com/priya-sharma/attendance-report.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/priya-sharma/attendance-report.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref.
```

A colleague pushed first. Git refuses to overwrite their work. The fix is to
bring their commits in, then push:

```bash [Terminal]
git pull
git push
```

If the pull produces a conflict, resolve it exactly as in the last lesson. The
wrong fix, `git push --force`, is in the next lesson, with the warning it needs.

### A pull request

::steps
### Branch and push
`git switch -c bugfix/BUG-1182-late-fee`, commit the fix, then
`git push -u origin bugfix/BUG-1182-late-fee`.

### Open the PR on GitHub
Base `main`, compare your branch. Title with the ticket, a description of what
changed and how to test it.

### Review
A colleague reads the diff, leaves comments, approves or requests changes.
Automated checks (tests, a linter) run on the branch.

### Fix and push again
New commits on the same branch update the PR automatically.

### Merge
Once approved and green, it is merged into `main` and the branch is deleted.
::

### .gitignore

Some files must never be committed: compiled output, editor settings, and above
all secrets. A `.gitignore` file in the repository root lists them:

```text [.gitignore]
# Build output
target/
*.class

# Editor and OS
.idea/
.vscode/
.DS_Store

# Secrets: never in history
.env
application-local.properties
```

```bash [Terminal]
echo "DB_PASSWORD=Exam@2026" > .env
git status --short
```

```text [Output]
?? .gitignore
```

`.env` does not appear at all: Git is ignoring it.

::caution
`.gitignore` only affects files Git is not already tracking. If a password was
committed once, adding it to `.gitignore` does not remove it from history.
Treat the password as leaked: change it first, then clean the history.
::

## Real use case

::real-life{title="What a good PR description contains" source="Twilio, the GTM team"}
What changed, why (the ticket), how to test it, and anything the reviewer should
look at closely. A reviewer who has to guess what your PR does will approve it
slowly or not at all. Small PRs, under about 300 lines, get reviewed the same
day; a 2,000-line PR waits a week.
::

## What confuses people here

- **`fetch` versus `pull`.** Fetch downloads and changes nothing you are working
  on. Pull fetches *and merges*. When unsure, fetch and look first.
- **`origin` is only a name.** It is the conventional name for the remote you
  cloned from.
- **Pull request versus merge request.** Same idea; GitHub says pull request,
  GitLab says merge request.
- **Fork versus clone.** A fork is your own copy of someone else's repository
  *on GitHub*. A clone is a copy on your machine.

## Interview questions

::accordion
  :::accordion-item{label="git fetch versus git pull?"}
  `fetch` downloads new commits from the remote into remote-tracking branches
  (`origin/main`) without touching your working branch. `pull` is `fetch`
  followed by a merge (or rebase) into your current branch.
  :::
  :::accordion-item{label="What is a pull request?"}
  A request to merge one branch into another on a hosting platform, with a
  place for code review, discussion and automated checks before the merge
  happens. It is how changes reach `main` on almost every team.
  :::
  :::accordion-item{label="Your push was rejected. Why, and what do you do?"}
  The remote has commits you do not have locally, usually a colleague's. Run
  `git pull` to bring them in, resolve any conflict, then `git push`. Do not
  force-push to a shared branch.
  :::
  :::accordion-item{label="What is .gitignore? Can it remove a file already committed?"}
  A file listing patterns Git should not track: build output, IDE files,
  secrets. It does not affect already-tracked files; for those, run
  `git rm --cached <file>` and commit, and if it was a secret, rotate it.
  :::
  :::accordion-item{label="Fork versus clone?"}
  A fork is a server-side copy of a repository under your GitHub account, used
  to contribute to projects you cannot push to. A clone is a local copy on your
  machine. You usually fork, then clone your fork.
  :::
::
