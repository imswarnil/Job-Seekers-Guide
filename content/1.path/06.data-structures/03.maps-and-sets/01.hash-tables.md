One step, whether there are forty applicants or forty million. A hash table is
the single most useful data structure there is, and the idea behind it is
genuinely simple once somebody draws it.

## Why this matters in a job

Because `HashMap` and `HashSet` are in essentially every Java program you will
ever read, because "how does a HashMap work" is one of the two most-asked Java
interview questions, and because getting the contract wrong silently breaks
your program in a way no compiler will catch.

## The trick

Turn the key into a number, and use that number as an array index.

## Collisions, and what actually happens

Sixteen buckets and forty thousand applicants means collisions are certain, not
possible. Two different keys will land in the same bucket, and the structure has
to cope.

Java keeps a small list in each bucket. On a `get`, it goes to the bucket and
then compares keys within it.

::memory{kind="table" caption="Bucket 5 holds two entries. A get for 2026CSE0184 compares with each until equals returns true."}

::pull-quote
A hash table is O(1) on average and O(n) in the worst case, and the worst case is
entirely your fault: it happens when your hash function puts everything in one
bucket.
::

Java improves the worst case: once a bucket holds more than eight entries and
the table is large enough, that bucket becomes a balanced tree instead of a list,
so the degenerate case is O(log n) rather than O(n). Worth mentioning in an
interview and worth not relying on.

## The contract that breaks it

This is the part that costs people real bugs, and it is asked constantly.

```java [Applicant.java]
public class Applicant {
  private final long id;
  private final String rollNumber;

  @Override
  public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Applicant other)) return false;
    return rollNumber.equals(other.rollNumber);
  }

  // hashCode NOT overridden. This class is now broken as a map key.
}
```

```java [Broken.java]
Map<Applicant, Integer> scores = new HashMap<>();
scores.put(new Applicant(1, "2026CSE0184"), 78);

int score = scores.get(new Applicant(1, "2026CSE0184"));
```

```text [Output]
Exception in thread "main" java.lang.NullPointerException
```

The two objects are `equals`. The map cannot find the second one, because the
default `hashCode` is derived from the object's identity, so the two go to
different buckets and the second bucket is empty. It never gets as far as calling
`equals`.

**The contract, in one line:** if two objects are equal, their `hashCode` must be
the same. The reverse is not required, because two unequal objects landing in the
same bucket is just a collision.

```java [Applicant.java]
  @Override
  public int hashCode() {
    return Objects.hash(rollNumber);      // the same fields equals uses
  }
```

::warning{icon="i-lucide-alert-triangle"}
The nastier version: a **mutable** key. Put an applicant in a map, then change
the field its hash is computed from. The object is now sitting in the bucket its
old hash chose, and every lookup computes the new hash and looks in the wrong
bucket. The entry is in the map, `containsKey` says no, and iterating finds it.
That is why map keys should be immutable, and why `String` and `Integer` are the
keys you see everywhere.
::

## `HashMap`, `TreeMap`, `LinkedHashMap`

Three that get confused, and the difference is entirely about order.

| | `HashMap` | `LinkedHashMap` | `TreeMap` |
| --- | --- | --- | --- |
| get / put | O(1) average | O(1) average | O(log n) |
| Iteration order | **None. Do not rely on it.** | Insertion order | Sorted by key |
| Needs | `equals` + `hashCode` | Same | `Comparable` or a `Comparator` |
| Use when | You just need lookup | Order of insertion matters, or LRU caching | You need sorted keys or ranges |

::side-note{kind="go-deeper"}
`LinkedHashMap` has a constructor flag for access order rather than insertion
order, and an overridable `removeEldestEntry`. Those two together are a
least-recently-used cache in about five lines, which is the fix for the memory
leak in the operating systems track and a common interview problem in its own
right.
::

## Sets are maps with no values

`HashSet` is a `HashMap` where every value is the same dummy object. That is not
an analogy, it is literally how Java implements it. Everything above applies:
same contract, same collisions, same O(1).

```java [Duplicates.java]
// The accidental-quadratic fix from chapter one, and now you know why it works.
Set<Long> seen = new HashSet<>();
for (Application a : applications) {
  if (!seen.add(a.getApplicantId())) {
    duplicates.add(a.getApplicantId());
  }
}
```

`add` returns `false` if the element was already present. One hash, one bucket,
one comparison. That is how twenty-four minutes became eighty milliseconds.

## Your turn

1. Why does a `HashSet` of `Applicant` objects sometimes contain two applicants
   with the same roll number?
2. What happens to a `HashMap` when it gets full? What is the "load factor"?
3. Write a method that finds the first non-repeating character in an applicant's
   name, in one pass over the name plus one over the counts.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** Because `equals` and `hashCode` were not overridden, or were overridden
  on different fields. The set compares by hash first, so two objects with
  different hashes are never compared for equality at all. This is the single
  most common cause of "my set has duplicates in it".

  **2.** It resizes. When the number of entries exceeds `capacity × loadFactor`
  (0.75 by default, so twelve entries in a sixteen-bucket table) it allocates
  a table twice as large and **rehashes every entry**, because the bucket index
  depends on the table size. That is an O(n) operation, which is why passing an
  expected size to the constructor is a free win when you know it.

  **3.**

  ```java
  static Character firstNonRepeating(String name) {
    Map<Character, Integer> counts = new LinkedHashMap<>();   // keeps order
    for (char c : name.toCharArray()) {
      counts.merge(c, 1, Integer::sum);
    }
    for (var entry : counts.entrySet()) {
      if (entry.getValue() == 1) return entry.getKey();
    }
    return null;
  }
  ```

  `LinkedHashMap` is the whole trick: a `HashMap` would find *a* non-repeating
  character rather than the *first* one, because its iteration order is
  undefined. Saying that out loud is what turns a correct answer into a good one.
  :::
::

## The interview question this answers

**"How does HashMap work?"** and **"What is the contract between equals and
hashCode?"**: two of the three most-asked Java questions in this market.

Answer the first with the picture: the key is hashed, the hash is reduced to a
bucket index, the bucket holds entries, and within a bucket keys are compared
with `equals`. Then the parts that show depth: collisions are normal, Java turns
a long bucket into a tree, resizing at 0.75 load factor rehashes everything, and
the worst case is O(n) when the hash is bad. Answer the second with the
consequence rather than the rule: equal objects must hash the same, or the map
looks in the wrong bucket and cannot find an entry that is sitting in it.
