A shape that keeps things sorted. Hashing destroys order to get its speed; a tree
keeps order and gets a different kind of speed, and it is the shape your
database's index turned out to be.

## Why this matters in a job

Because binary search is the clearest example of a logarithmic algorithm there
is, because "implement binary search" is a real interview question with a famous
bug in it, and because trees are how ranges and sorted iteration are done
everywhere.

A thousand times more data costs ten more steps. That is what **O(log n)** buys,
and it is the same arithmetic as the four-level B-tree from the DBMS track.

## Write it, including the famous bug

```java [BinarySearch.java]
static int indexOf(int[] sortedScores, int target) {
  int low = 0;
  int high = sortedScores.length - 1;

  while (low <= high) {                        // <=, not <. See below.
    int mid = low + (high - low) / 2;          // not (low + high) / 2. See below.

    if (sortedScores[mid] == target)      return mid;
    else if (sortedScores[mid] < target)  low  = mid + 1;
    else                                  high = mid - 1;
  }
  return -1;
}
```

  :::code-trace-step{lines="1" caption="`<=` not `<`. With `<`, a one-element range is never examined, so the search misses any target sitting at that final position. This is the most common binary search bug."}
  :::
  :::code-trace-step{lines="2" caption="`low + (high - low) / 2` not `(low + high) / 2`. On a large array the sum overflows int and goes negative, producing a negative index. This bug was in the JDK's own binary search for nine years."}
  :::
  :::code-trace-step{lines="3" caption="`mid + 1` and `mid - 1`, not `mid`. Setting the bound to `mid` leaves the range the same size when it is down to two elements, and the loop never terminates."}
  :::

::warning{icon="i-lucide-alert-triangle"}
Binary search is four lines and famously hard to write correctly. Joshua Bloch,
who wrote much of the Java collections library, published a note in 2006 titled
"Nearly All Binary Searches Are Broken", about the overflow bug that had been in
the JDK since 1997. If an interviewer asks you to write it, narrate the three
boundary decisions above out loud. That is the answer they want.
::

And the precondition that makes it all work: **the data must already be sorted.**
Binary search over an unsorted array returns nonsense confidently.

## A binary search tree

The same idea as a structure rather than as an algorithm: every node has a value,
everything smaller is on the left, everything larger on the right.

## The catch, and the fix

A binary search tree is only fast if it is **balanced**. Insert already-sorted
data and every node goes to the right, and the tree is a linked list wearing a
costume.

::compare{caption="The same seven values, two insertion orders."}
  :::compare-side{label="Inserted 55, 41, 92, 25, 48, 78, 99" verdict="right"}
  Three levels. Any value found in at most three comparisons. **O(log n)**.
  :::
  :::compare-side{label="Inserted 25, 41, 48, 55, 78, 92, 99" verdict="wrong"}
  Seven levels, each node hanging off the previous one's right. Finding 99 takes
  seven comparisons. **O(n)**, and it is a list.
  :::
::

Which is why nobody uses a plain binary search tree in production. **Self-balancing**
trees — red-black trees, AVL trees, B-trees — rebalance on insert to keep the
depth logarithmic whatever order the data arrives in.

::side-note{kind="go-deeper"}
Java's `TreeMap` is a red-black tree. Your database's index is a B-tree, which is
the same idea widened so each node fills a disk page. You do not need to be able
to implement the rebalancing. You do need to be able to say *why* it exists,
which is this comparison, and that is what gets asked.
::

## Reading a tree in order

Three traversals, and one of them is the useful one.

```java [Traversal.java]
// In-order: left, self, right. On a binary search tree this yields
// the values in SORTED order, which is the whole reason it is useful.
static void inOrder(Node node, List<Integer> out) {
  if (node == null) return;
  inOrder(node.left, out);
  out.add(node.value);
  inOrder(node.right, out);
}
```

```text [Output]
[25, 41, 48, 55, 78, 92, 99]
```

| Traversal | Order | What it is for |
| --- | --- | --- |
| **In-order** | left, self, right | Sorted output from a search tree |
| Pre-order | self, left, right | Copying a tree, or serialising its shape |
| Post-order | left, right, self | Deleting a tree; evaluating an expression |
| **Level-order** | row by row, using a **queue** | Shortest path in an unweighted graph |

That last one is worth noticing: level-order needs a queue, and you built one two
chapters ago. Depth-first traversal needs a stack, which recursion gives you for
free by using the call stack.

## Your turn

1. An array of 40,000 sorted scores. How many comparisons to find one, worst
   case? Now 80,000?
2. Write binary search for the **first** index where a score is at least 75,
   rather than an exact match.
3. Why would you use a `TreeMap` over a `HashMap` for storing applicants by
   score?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** Sixteen, and seventeen. Doubling the data adds one comparison, which is
  the sentence that makes logarithmic growth land.

  **2.** The lower-bound variant, and it is asked more often than exact-match
  binary search because it is the one used in practice:

  ```java
  static int firstAtLeast(int[] sorted, int target) {
    int low = 0, high = sorted.length;        // note: length, not length - 1
    while (low < high) {                      // note: <, not <=
      int mid = low + (high - low) / 2;
      if (sorted[mid] < target) low = mid + 1;
      else                      high = mid;   // note: mid, not mid - 1
    }
    return low;                               // may be length, meaning none
  }
  ```

  Three of the boundaries are the opposite of the exact-match version, which is
  exactly why binary search is hard. The invariant to hold in your head: `low` is
  the first candidate and `high` is one past the last candidate, throughout.

  **3.** Because a `HashMap` cannot answer "every applicant scoring between 70
  and 80" or "the top ten", and a `TreeMap` can: `subMap(70, 80)` and
  `descendingMap`. You pay O(log n) instead of O(1) for a single lookup and you
  buy ordered access and ranges. That is exactly the trade your database makes
  when it chooses a B-tree index over a hash index.
  :::
::

## The interview question this answers

**"Implement binary search"** and **"What is the difference between a HashMap and
a TreeMap?"**

For the first, narrate the boundaries: `<=` versus `<`, the overflow-safe
midpoint, and `mid + 1` rather than `mid`. Mentioning that the JDK had the
overflow bug for nine years is memorable and true.

For the second, do not stop at "one is sorted". Say what sorting buys — ranges,
ordered iteration, floor and ceiling lookups — and what it costs, O(log n)
instead of O(1). Then connect it to the database index, which shows you see one
idea in two places rather than two facts.
