You will never write one. That is the honest ending, and it makes the subject
more interesting rather than less: you are learning sorting to be able to reason
about cost and stability, not to implement it.

## Why this matters in a job

Because "what sorting algorithms do you know" is asked constantly, and because
the *useful* knowledge is narrower than the syllabus: which complexity, whether
it is stable, and what `Collections.sort` actually does.

## The three you will be asked about

::feature-list{columns="2"}
  :::feature{icon="i-lucide-arrow-down-up" title="Bubble sort — O(n²)"}
  Repeatedly swap adjacent elements that are in the wrong order. Never used for
  anything. Asked about because it is the easiest to reason about, and because
  recognising it in somebody's code is a real skill.
  :::
  :::feature{icon="i-lucide-list-ordered" title="Insertion sort — O(n²), and fast when nearly sorted"}
  Take each element and slide it back into place. Genuinely used, inside better
  sorts, for small runs. On nearly-sorted data it is close to O(n), which is why
  it survives.
  :::
  :::feature{icon="i-lucide-split" title="Merge sort — O(n log n), stable"}
  Split in half, sort each half, merge. Predictable, stable, and needs O(n) extra
  memory. This is what Java uses for objects.
  :::
  :::feature{icon="i-lucide-zap" title="Quick sort — O(n log n) average, O(n²) worst"}
  Pick a pivot, put smaller on one side and larger on the other, recurse. Sorts
  in place with no extra array. This is what Java uses for primitives.
  :::
::

## Merge sort, because it explains the n log n

```java [MergeSort.java]
static void sort(int[] a, int low, int high) {
  if (high - low < 2) return;                      // one element is sorted
  int mid = low + (high - low) / 2;
  sort(a, low, mid);                               // sort the left half
  sort(a, mid, high);                              // sort the right half
  merge(a, low, mid, high);                        // walk both, take the smaller
}
```

The complexity falls out of the shape. Halving repeatedly gives **log n** levels,
and merging at each level touches every element once, so **n** per level.
n × log n.

## Stability, which is the part that matters in a job

A **stable** sort keeps equal elements in their original relative order. This
sounds academic and is the single most practically important property of a sort.

::compare{caption="Applications already sorted by date received, now sorted by score."}
  :::compare-side{label="Unstable sort" verdict="wrong"}
  Two applicants both score 78. Their relative order is now arbitrary, so the
  shortlist is not reproducible: run it twice and a different one of the two is
  at position 40. If position 40 is the cutoff, the university has just admitted
  a different person for no reason.
  :::
  :::compare-side{label="Stable sort" verdict="right"}
  The two applicants on 78 stay in date-received order, so the earlier applicant
  is ranked first. The result is reproducible, explainable and defensible to a
  parent on the telephone.
  :::
::

::pull-quote
Stability is what lets you sort by one thing and then another, and have the first
sort still mean something.
::

| Sort | Stable? |
| --- | --- |
| Merge sort | **Yes** |
| Insertion sort | **Yes** |
| Bubble sort | Yes |
| Quick sort | **No** |
| Heap sort | No |

## What Java actually does

```java [Sorting.java]
// Objects: a stable merge sort (Timsort). Guaranteed O(n log n), guaranteed stable.
applications.sort(comparing(Application::getScore).reversed());

// Primitives: a dual-pivot quicksort. Not stable, and it does not matter —
// two equal ints are indistinguishable, so there is nothing to keep in order.
int[] scores = ...;
Arrays.sort(scores);
```

That split is deliberate and it is a good interview answer: objects get a stable
sort because you can tell two equal-by-comparator objects apart, primitives do
not need one because you cannot.

**Timsort** is the one to name. It is merge sort that first looks for runs that
are already sorted and uses insertion sort on short ones. On real data, which is
usually partly ordered, it beats a plain merge sort substantially.

```java [Chained.java]
// Stability in practice: sort by score, and ties broken by date received.
applications.sort(
    comparing(Application::getScore).reversed()
        .thenComparing(Application::getReceivedAt));
```

::tip
`thenComparing` is the better answer than relying on stability, because it states
the tie-break rather than depending on the previous ordering. If an interviewer
asks how you would rank applicants, saying the tie-break out loud — and asking
the registrar what it should be — is the senior answer.
::

## When writing your own is right

Almost never, and the honest list is short: a coding interview that asks for it,
a constraint the library cannot express, or data so large it does not fit in
memory and must be sorted in chunks on disk.

::warning{icon="i-lucide-alert-triangle"}
The real mistake is not writing a bad sort. It is **sorting when you did not need
to**. Sorting 40,000 applications to find the top ten is O(n log n) for something
a priority queue does in O(n log k), and a `LIMIT` in SQL does without loading
them at all. The best sort is the one you talked yourself out of.
::

## What you can do now

You can name four sorts with their complexity and stability, say what Java
actually calls, and explain why stability decides whether a shortlist is
reproducible.

## Your turn

1. Sort 40,000 applications by score descending, ties broken by earliest received.
   Write it.
2. You need only the top ten. What should you do instead of sorting?
3. Why is quicksort O(n²) in the worst case, and what causes that case?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.**
  ```java
  applications.sort(
      comparing(Application::getScore).reversed()
          .thenComparing(Application::getReceivedAt));
  ```

  **2.** A bounded priority queue, or in SQL an `ORDER BY ... LIMIT 10` with an
  index, which does not sort the table at all.

  ```java
  // Keep only ten. O(n log 10) instead of O(n log n), and constant memory.
  PriorityQueue<Application> top = new PriorityQueue<>(comparing(Application::getScore));
  for (Application a : applications) {
    top.offer(a);
    if (top.size() > 10) top.poll();       // drop the lowest
  }
  ```

  **3.** Because quicksort's speed depends on the pivot splitting the data
  roughly in half. If the pivot is always the smallest or largest element, each
  step removes one element instead of half, giving n levels instead of log n.
  The classic trigger is already-sorted data with a naive first-element pivot,
  which is an unpleasant surprise: the sort is slowest on the input that looks
  easiest. Real implementations pick the pivot from a sample or use two pivots,
  which is what Java's dual-pivot quicksort is doing.
  :::
::

## The interview question this answers

**"Which sorting algorithm would you use?"**

The answer that works is not naming a sort. It is: I would call the library's,
because it is Timsort for objects — stable, guaranteed O(n log n), and faster on
partly-ordered real data — and a dual-pivot quicksort for primitives. Then the
question behind the question: whether I need to sort at all, because the top ten
is a priority queue and a page of results is a `LIMIT`.
