This is the most-tested subject in entry-level technical interviews, and the
questions are remarkably repetitive. Twelve, with what separates a memorised
answer from a real one.

::accordion
  :::accordion-item{label="1. Array versus linked list" icon="i-lucide-message-circle"}
  The table: O(1) indexed access against O(n); O(1) insertion at the front for a
  list against O(n) for an array; ~2× memory for the pointers.

  Then the part almost nobody says: in practice `ArrayList` wins even where the
  table favours a list, because arrays are contiguous and processors read memory
  in blocks, so iterating a linked list is mostly cache misses. Same O(n), a
  hundredfold measured difference. And `LinkedList` is almost never the right
  Java class: `ArrayDeque` is.
  :::

  :::accordion-item{label="2. How does a HashMap work?" icon="i-lucide-message-circle"}
  Key → `hashCode` → reduced to a bucket index → the bucket holds entries → keys
  within a bucket are compared with `equals`.

  Then the depth: collisions are normal; Java converts a bucket with more than
  eight entries into a tree so the worst case is O(log n) rather than O(n);
  it resizes at a load factor of 0.75 and rehashes everything, which is why
  passing an expected size is a free win.
  :::

  :::accordion-item{label="3. equals and hashCode" icon="i-lucide-message-circle"}
  Answer with the consequence, not the rule. If two objects are equal their hash
  codes must match, because otherwise the map computes a different bucket and
  never even reaches the `equals` comparison. The entry is in the map and
  `containsKey` says no.

  Then the nastier one, which marks you out: a **mutable** key. Change the field
  the hash is computed from after inserting, and the object is stranded in the
  bucket its old hash chose. Which is why map keys should be immutable.
  :::

  :::accordion-item{label="4. HashMap or TreeMap?" icon="i-lucide-message-circle"}
  O(1) and unordered against O(log n) and sorted. What the O(log n) buys:
  ranges (`subMap`), ordered iteration, and floor and ceiling lookups.

  Close by connecting it outward: this is exactly the trade a database makes
  between a hash index and a B-tree index. B-trees are the default because most
  queries want ranges and ordering, not just equality.
  :::

  :::accordion-item{label="5. What is the complexity of your solution?" icon="i-lucide-message-circle"}
  Asked after every coding question. Walk the code aloud: this loop is n, this
  call inside it is n because `contains` on a list scans, so O(n²) overall, and a
  `HashSet` makes it O(n).

  Naming a hidden cost inside a library call (`List.contains`,
  `List.remove(Object)`, string concatenation in a loop) is exactly what the
  question is for.
  :::

  :::accordion-item{label="6. Implement binary search" icon="i-lucide-message-circle"}
  Narrate the three boundaries as you write: `low <= high` not `<`, or a
  one-element range is never examined; `low + (high - low) / 2` not
  `(low + high) / 2`, or a large array overflows into a negative index; and
  `mid + 1` / `mid - 1` not `mid`, or a two-element range never shrinks and the
  loop hangs.

  Mentioning that the overflow bug sat in the JDK from 1997 to 2006 is true,
  short and memorable.
  :::

  :::accordion-item{label="7. Why is a BST sometimes O(n)?" icon="i-lucide-message-circle"}
  Because it is only O(log n) when balanced. Insert already-sorted data into a
  plain BST and every node goes right, so it is a linked list with extra steps.

  Which is why production structures self-balance: red-black in `TreeMap`,
  B-trees in a database. You are not expected to implement the rebalancing; you
  are expected to know why it exists.
  :::

  :::accordion-item{label="8. Which sorting algorithm would you use?" icon="i-lucide-message-circle"}
  Not a sort name. "The library's": Timsort for objects, stable and guaranteed
  O(n log n) and faster on partly-ordered real data; dual-pivot quicksort for
  primitives, where stability is meaningless because two equal ints are
  indistinguishable.

  Then the better question: do I need to sort at all? Top ten is a bounded
  priority queue at O(n log k); a page of results is a `LIMIT` with an index.
  :::

  :::accordion-item{label="9. What does stable mean, and why care?" icon="i-lucide-message-circle"}
  Equal elements keep their original relative order. Give the shortlist example:
  two applicants on 78, an unstable sort puts an arbitrary one at position 40,
  and if 40 is the cutoff the university admits a different person each time it
  runs. Reproducibility, not tidiness.

  Then the practical closer: rather than relying on stability, state the
  tie-break with `thenComparing`, and ask the registrar what it should be.
  :::

  :::accordion-item{label="10. Stack or queue, for this problem?" icon="i-lucide-message-circle"}
  Undo, bracket matching, depth-first traversal and the call stack are all
  last-in-first-out. Background jobs, breadth-first traversal and anything
  fair-ordered are first-in-first-out.

  And the Java detail: `ArrayDeque`, not `Stack`. `Stack` extends `Vector`, so
  every method is synchronised and it exposes indexed access that breaks the
  abstraction.
  :::

  :::accordion-item{label="11. Find duplicates in a list" icon="i-lucide-message-circle"}
  The warm-up that tests whether you reach for a set unprompted. The nested-loop
  answer is O(n²); one pass with a `HashSet` is O(n).

  Quote the measurement if you have run it: 400,000 items took twenty-four
  minutes nested and eighty milliseconds with a set. A number is unfakeable.
  :::

  :::accordion-item{label="12. What data structure would you use for X?" icon="i-lucide-message-circle"}
  The open question, and it is testing whether you ask before answering. Ask what
  the operations are and their relative frequency: mostly reads or mostly writes,
  lookup by key or by range, does order matter, how many items.

  Then choose and **name the cost you are accepting**. "A `TreeMap`, because the
  registrar needs score ranges, and I am accepting O(log n) lookups instead of
  O(1) to get them." Naming the cost is the senior move in every one of these
  twelve.
  :::
::
