A running program has to keep data somewhere while it thinks, and which shape it
uses decides whether the answer takes a millisecond or a fortnight. Before any
shape, a way of saying how expensive something is.

Big-O has a reputation for being mathematics. It is counting.

## Why this matters in a job

Because the sentence "this works but it will not work at ten thousand" is one you
need to be able to say and defend, and because every technical interview in this
market asks for the complexity of whatever you just wrote.

## Count the steps

The registrar wants to know whether an applicant with a given roll number
applied. Here is the obvious way.

```java [Search.java]
static boolean hasApplied(String[] rollNumbers, String target) {
  for (int i = 0; i < rollNumbers.length; i++) {   // n times
    if (rollNumbers[i].equals(target)) {           // one comparison each
      return true;
    }
  }
  return false;
}
```

With 40,000 applicants, the worst case is 40,000 comparisons. With 400,000, it is
400,000. The work grows in step with the input, and that is all **O(n)** means.

::pull-quote
Big-O answers one question: if the input gets ten times bigger, what happens to
the work?
::

| Notation | Ten times more input means | Example |
| --- | --- | --- |
| **O(1)** | Exactly the same work | Reading `marks[5]` |
| **O(log n)** | One or two more steps | Binary search, a B-tree lookup |
| **O(n)** | Ten times the work | Scanning every applicant |
| **O(n log n)** | About eleven times | Any good sort |
| **O(n²)** | **A hundred times** | Comparing every applicant with every other |

## Why the constant is dropped

This is the part that feels like cheating, and the reason is worth understanding
rather than accepting.

```java [Two.java]
// Version A: one pass, three operations per applicant
for (Applicant a : applicants) { check(a); score(a); log(a); }

// Version B: three separate passes, one operation each
for (Applicant a : applicants) check(a);
for (Applicant a : applicants) score(a);
for (Applicant a : applicants) log(a);
```

Both are 3n operations. Both are **O(n)**. Big-O deliberately ignores the 3,
because the question it answers is about *shape*, not speed: an O(n) algorithm
that is three times slower than another O(n) algorithm still beats an O(n²) one
the moment the input grows.

::side-note{kind="go-deeper"}
The honest caveat, which good interviewers like to hear: the constant matters at
small n, and small n is a lot of real code. An O(n²) loop over five departments
is fine, and rewriting it as an O(n) version with a `HashMap` can genuinely be
slower because of the hashing. Big-O is about how something scales, not about
whether it is fast today. Saying that out loud shows judgement rather than
recitation.
::

## Watch O(n²) happen

The single most common accidental quadratic in real code, and it never looks like
a nested loop.

```java [Duplicates.java]
// Find applicants who applied to more than one programme.
List<String> duplicates = new ArrayList<>();
for (Application a : applications) {              // n
  for (Application b : applications) {            // × n
    if (a != b && a.getApplicantId() == b.getApplicantId()) {
      duplicates.add(a.getApplicantId());
    }
  }
}
```

```text [Measured, same machine]
   1,000 applications →      0.01 s
  10,000 applications →      0.9 s
  40,000 applications →     14.2 s
 400,000 applications →  ~24 minutes
```

Ten times the input, a hundred times the work. Now the same answer in one pass.

```java [Duplicates.java]
// A set remembers what it has seen. One pass, O(n).
Set<Long> seen = new HashSet<>();
Set<Long> duplicates = new HashSet<>();
for (Application a : applications) {
  if (!seen.add(a.getApplicantId())) {   // add returns false if already present
    duplicates.add(a.getApplicantId());
  }
}
```

```text [Measured, same machine]
 400,000 applications →  0.08 s
```

Twenty-four minutes to eighty milliseconds, and the second version is shorter.
That is what this subject is for.

## The one that hides inside a loop

The nastiest version of this is invisible, because the nested loop is somebody
else's.

```java [Hidden.java]
// Looks like one loop. Is not.
List<Applicant> shortlist = new ArrayList<>();
for (Application a : applications) {           // n
  if (shortlist.contains(a.getApplicant())) {  // ← contains on a List is O(n)
    continue;
  }
  shortlist.add(a.getApplicant());
}
```

`List.contains` scans. One visible loop, one hidden one, and it is O(n²). Swap
`ArrayList` for `HashSet` and the same code is O(n).

::warning{icon="i-lucide-alert-triangle"}
The two most common hidden costs in Java: `List.contains` and `List.remove(Object)`
are both O(n), and string concatenation inside a loop is O(n²) because each `+`
copies the whole string so far. Both look like single operations and both are the
reason a job that took two minutes last year takes an hour this year.
::

## Best, worst and average

Interviewers ask which one you mean, so say it unprompted.

For the linear search at the top: best case the applicant is first, **O(1)**;
worst case they are last or absent, **O(n)**; average, half the list, which is
still **O(n)** because constants are dropped.

By convention, an unqualified complexity means the **worst case**. That is the
one that matters, because the worst case is what happens on results day.

## What you can do now

You can count the work in a loop, spot an accidental quadratic including the
hidden ones, and say a complexity out loud with the case you mean.

## Your turn

Give the complexity of each, and say which of them has a hidden cost.

```java
// 1
for (Subject s : subjects) total += s.getCredits();

// 2
for (Student s : students)
  for (Subject sub : s.getSubjects())
    print(s, sub);

// 3
String report = "";
for (ExamResult r : results) report += r.toString() + "\n";

// 4
Collections.sort(applicants, comparing(Applicant::getScore));

// 5
Applicant a = applicantsById.get(4182L);    // applicantsById is a HashMap

// 6
for (Application app : applications)
  if (shortlistedIds.contains(app.getId()))   // shortlistedIds is an ArrayList
    notify(app);
```

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  1. **O(n)**. One pass.
  2. **O(n × m)**, students times subjects each. Often written O(n²) loosely, and
     saying "n students times m subjects" is the better answer because it is
     more precise.
  3. **O(n²)**, and this is the hidden one. Strings are immutable, so each `+`
     copies everything built so far. Use `StringBuilder` and it becomes O(n).
     This has its own lesson in the Java track.
  4. **O(n log n)**. Every good general-purpose sort is, and this is worth
     knowing as a fact you can quote.
  5. **O(1)** on average. The whole reason hash maps exist, and chapter three.
  6. **O(n × m)**, hidden. `ArrayList.contains` scans. Make `shortlistedIds` a
     `HashSet` and it is O(n). This is the most common accidental quadratic in
     real application code, by a distance.
  :::
::

## Check yourself

1. Why does big-O drop the constant, and when does that make it misleading?
2. **An interviewer asks: "what is the complexity of your solution?"** after you
   write a loop containing `list.contains(...)`.

## The interview question this answers

**"What is the time complexity of this?"**

Asked after essentially every coding question. Say the case you mean, then walk
the code: this loop is n, this call inside it is n because `contains` on a list
scans, so it is O(n²) overall, and swapping to a set makes it O(n). Naming the
hidden cost inside a library call is exactly what the question is looking for,
and it is where most candidates lose the point.
