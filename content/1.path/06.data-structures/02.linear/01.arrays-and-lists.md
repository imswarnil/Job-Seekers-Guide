What is physically next to what. An array and a linked list both hold things in
order, and they are opposites in every single operation, because one of them
stores its elements next to each other and the other does not.

## Why this matters in a job

Because "array or linked list" is asked in essentially every data structures
round, and because the real answer, "an `ArrayList` in almost every case, and
here is why", is one very few candidates give confidently.

## An array is contiguous

::memory{kind="array" caption="Forty thousand scores, in one continuous block. The address of any element is arithmetic."}
---
cells:
  - { value: 78, label: "0" }
  - { value: 64, label: "1" }
  - { value: 81, label: "2" }
  - { value: 55, label: "3" }
  - { value: 92, label: "4", state: "active" }
  - { value: 70, label: "5" }
---
::

Because every element is the same size and they are adjacent, the machine finds
element 4 with one multiplication and one addition: `start + 4 × size`. It does
not look at elements 0 to 3. That is why array access is **O(1)** and why it does
not get slower as the array grows.

The cost is the other side of the same fact.

```java [Arrays.java]
int[] scores = new int[40_000];
scores[4] = 92;                    // O(1) — arithmetic, no searching

// Inserting in the middle: everything after it must physically move.
// There is no gap to put it in, because the whole point is that there are no gaps.
```

## A linked list is scattered

Each element holds its value and the address of the next one. They can be
anywhere in memory.

::memory{kind="list" caption="Each node points at the next. Nothing is adjacent, so there is no arithmetic to do."}
---
cells:
  - { value: "78 →" }
  - { value: "64 →" }
  - { value: "81 →" }
  - { value: "55 →" }
  - { value: "null" }
---
::

To reach element 4 you must start at the head and follow four pointers. There is
no way to jump, because nothing knows where anything else is except its immediate
neighbour. That is **O(n)** access, and it is the price of the thing it is good
at.

```java [Node.java]
class Node {
  Applicant value;
  Node next;              // the whole idea, in one field
}
```

Inserting in the middle, once you are already there, is three assignments and
nothing moves.

## The table that answers the interview question

| Operation | Array / `ArrayList` | Linked list |
| --- | --- | --- |
| Get element `i` | **O(1)** | O(n) |
| Insert or remove at the end | O(1) amortised | O(1) |
| Insert or remove at the front | O(n) | **O(1)** |
| Insert or remove in the middle, **already there** | O(n) | **O(1)** |
| Insert or remove in the middle, **by index** | O(n) | O(n) |
| Search for a value | O(n) | O(n) |
| Memory per element | Just the value | Value **plus a pointer**, so ~2–3× |

The fifth row is the one that catches people. "Linked lists are fast at
insertion" is only true if you are already holding the node. Getting to position
20,000 costs 20,000 steps, so `LinkedList.add(20000, x)` is O(n), the same as an
array.

## Why `ArrayList` wins in practice

::pull-quote
The complexity table says linked lists should often win. Real machines disagree,
and the reason is not in the table.
::

A modern processor reads memory in blocks of 64 bytes and keeps recent blocks in
a small fast cache. Walking an array reads one block and gets the next sixteen
elements for free. Walking a linked list jumps to an unrelated address each time,
so nearly every step is a cache miss and costs a hundred times more.

```text [Summing 10 million ints, same machine]
int[]                    4 ms
ArrayList<Integer>      38 ms      ← boxing, but still contiguous
LinkedList<Integer>    412 ms      ← same O(n), 100× slower
```

All three are O(n). The measured difference is a hundredfold, and it is entirely
about what is next to what.

::side-note{kind="performance"}
This is why "use the right data structure" is not always the same advice as "use
the one with the better big-O". For a list you mostly iterate and index,
`ArrayList` is correct even where the table suggests otherwise. `LinkedList` in
Java is genuinely right in a narrow case: a queue or deque where you add and
remove at both ends, and even there `ArrayDeque` is usually faster.
::

## How `ArrayList` grows

Worth knowing, because "amortised O(1)" appears in the table above and sounds
like hand-waving.

```java [Growth.java]
List<Applicant> applicants = new ArrayList<>();   // capacity 10
// ...adding. When it fills, it allocates a NEW array 1.5× bigger and copies.
```

Most `add` calls are O(1). Occasionally one is O(n) because everything is copied.
Because the capacity grows by a *factor* rather than a fixed amount, those
expensive copies get rarer as the list grows, and the average across all adds
works out to O(1). That average is what "amortised" means.

::tip
If you know roughly how many elements you will have, say so:
`new ArrayList<>(40_000)`. It avoids every one of those copies. The same applies
to `StringBuilder` and `HashMap`, and it is a free performance win that costs one
argument.
::

## What confuses people here

That `LinkedList` is the Java class you should use when you want a linked list.
Almost never. `ArrayList` for lists, `ArrayDeque` for stacks and queues. In
fifteen years of production Java I have used `LinkedList` deliberately perhaps
twice, and both times `ArrayDeque` would have been better.

## What you can do now

You can answer "array or linked list" with the table and the cache reason, which
is the answer that sounds like somebody who has measured something.

## Your turn

For each, say which structure and why.

1. Forty thousand applicant scores, read constantly by index, never inserted into
   the middle.
2. A queue of applications waiting for review: add at the back, take from the
   front.
3. A browser's back button.
4. Storing a list where you frequently remove items from the middle while
   iterating.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1. An array, or `ArrayList`.** Indexed access is the whole workload and
  contiguity makes it fast twice over, O(1) and cache-friendly.

  **2. `ArrayDeque`.** Both ends are O(1) and it is contiguous, so it beats
  `LinkedList` despite the identical complexity. This is the standard answer for
  a queue in Java and is worth knowing by name.

  **3. A stack**, `ArrayDeque` again. Last in, first out is exactly the back
  button's behaviour, and it is the classic example for the next lesson.

  **4. A trick question worth thinking about.** Removing from the middle of an
  `ArrayList` while iterating throws `ConcurrentModificationException`, and
  `LinkedList` is O(n) to reach the position anyway. The real answers are
  `Iterator.remove()`, or `removeIf(...)`, or building a new list of what you
  want to keep, which is usually clearest. "Change the algorithm rather than the
  structure" is a legitimate and good answer here.
  :::
::

## The interview question this answers

**"Array versus linked list."**

Give the table, indexed access, insertion at each end, memory overhead, and
then the part that distinguishes you: in practice `ArrayList` wins even in cases
where the table favours a linked list, because arrays are contiguous and
processors read memory in blocks, so iterating a linked list is mostly cache
misses. If you have the number, use it: same O(n), a hundredfold difference
measured. And name `ArrayDeque` as the actual answer for stacks and queues.
