The last kind of reading, and the one you will do most. Nobody was trying to help
you. There is no introduction, the comments are wrong where they exist, and the
person who wrote it left two years ago.

## Why this matters in a job

Because this is literally the first thing that happens to you. Day one is a
repository URL and "have a look around". Nobody will teach you how, because
everybody who can do it has forgotten that they learned.

::real-life{title="My first day at a real codebase" source="Accenture, 2019"}
Forty thousand lines. I opened files at random for two days, understood nothing,
and did not say so, because I thought being lost was evidence I should not be
there. What I needed was a method and thirty minutes. The method is below and it
is not difficult; it is just never written down.
::

## The method

::flow{numbered direction="vertical" caption="An hour, in this order. Do not open a random file."}
  :::flow-step{label="Run it first" icon="i-lucide-play"}
  Before reading anything. Get it working locally and click through it as a user.
  You cannot map a system you have never seen behave.
  :::
  :::flow-step{label="Read the folder names, not the files" icon="i-lucide-folder-tree"}
  The directory tree is the architecture, stated by somebody who knew it. Five
  minutes here is worth two hours of file-opening.
  :::
  :::flow-step{label="Find the entry point" icon="i-lucide-door-open"}
  `main`, the router, the controller list. Where does a request first meet this
  team's own code? Everything hangs off that.
  :::
  :::flow-step{label="Follow ONE path all the way down" icon="i-lucide-route" highlight}
  Pick the simplest real thing the system does and trace it from the click to the
  database and back. One path understood completely beats forty files skimmed.
  :::
  :::flow-step{label="Read the tests" icon="i-lucide-check-check"}
  The most under-used trick in this lesson. Tests are executable documentation of
  what the authors believed the code should do, including the edge cases they had
  been burned by.
  :::
  :::flow-step{label="Read the git history of one file" icon="i-lucide-git-commit"}
  `git log -p` on the file that confuses you. The commit messages tell you *why*
  the strange part is strange, which the code never will.
  :::
::

## Watch it happen

Here is the folder tree of the university system as it will exist by the end of
this course. Read it and say what the system does, without opening anything.

```text [Terminal]
src/main/java/com/university/
├── admissions/          Applicant, Application, Shortlister, EmailService
├── academics/           Programme, Subject, Faculty, Timetable
├── attendance/          AttendanceRecord, AttendanceCalculator
├── examinations/        ExamResult, GradeCalculator, ResultSheet
├── finance/             FeePayment, FeeSchedule, ReceiptGenerator
├── placement/           Placement, Alumni, Recruiter
└── platform/            Auth, Audit, Database, Config
```

That tells you almost everything: six business areas and one shared layer. You
now know that a question about fees lives in `finance/`, and you have not read a
line.

Compare with what you get from opening a file at random.

::compare{caption="Two people, same codebase, first hour."}
  :::compare-side{label="Opens files" verdict="wrong"}
  Starts in `GradeCalculator.java` because it sounded interesting. Two hours
  later, understands grade calculation and has no idea where it is called from,
  what a grade is for, or what else exists.
  :::
  :::compare-side{label="Follows one path" verdict="right"}
  Runs it, marks one applicant, and traces that single action from the screen
  through the controller, the service, the calculator and into the database. Two
  hours later, understands one thing completely and has a map that every
  subsequent question hangs on.
  :::
::

## Reading a method you did not write

Three questions, in this order, and you do not need to understand the body.

```java [Shortlister.java]
public List<Applicant> shortlist(int minimumScore, Programme programme, User staff) {
  if (!staff.canShortlistFor(programme)) {
    throw new ForbiddenException("Not your programme.");
  }

  List<Applicant> eligible = applications
      .forIntake(currentIntake())
      .forProgramme(programme)
      .withScoreAtLeast(minimumScore)
      .excludingWithdrawn()
      .distinctApplicants();

  audit.record(staff, "SHORTLIST", programme, eligible.size());
  return eligible;
}
```

::code-trace{caption="Signature, then guards, then the shape. The body is last and often unnecessary."}
```java [Shortlister.java]
public List<Applicant> shortlist(int minimumScore, Programme programme, User staff) {
  if (!staff.canShortlistFor(programme)) {
    throw new ForbiddenException("Not your programme.");
  }
  List<Applicant> eligible = applications
      .forIntake(currentIntake())
      .withScoreAtLeast(minimumScore)
      .excludingWithdrawn()
      .distinctApplicants();
  audit.record(staff, "SHORTLIST", programme, eligible.size());
  return eligible;
}
```

  :::code-trace-step{lines="1" caption="WHAT GOES IN AND WHAT COMES OUT. A score, a programme, a user; a list of applicants. You now know what this is for without reading any of it."}
  :::
  :::code-trace-step{lines="2-4" caption="WHAT IT REFUSES TO DO. Guard clauses at the top of a method are the business rules, stated plainly. This one tells you permissions are per-programme, which is a fact about the whole system."}
  :::
  :::code-trace-step{lines="5-10" caption="THE SHAPE. Read the method names down the chain and it is a sentence: this intake, this score or above, not withdrawn, one row per person. You have read the logic without reading any logic."}
  :::

## What confuses people here

That being lost means you are not good enough. Everybody is lost in a new
codebase, including the senior engineer who looks like they are not. The
difference is that they know it takes a week and you think it should take an
hour.

::tip
The most useful sentence available to you in week one: *"I have traced the
shortlisting path from the controller down to the query. Can I walk you through
what I think happens, so you can tell me what I have wrong?"* It is not admitting
ignorance. It is showing a map and asking for corrections, and the person you ask
will remember it.
::

## What you can do now

You can get oriented in an unfamiliar codebase deliberately instead of by
wandering, and you can read a method for its contract rather than its
implementation.

## Your turn

Find any open-source Java or SQL project on GitHub. Do not read it. Instead,
in twenty minutes, answer:

1. What does the folder tree say this system is made of?
2. Where is the entry point?
3. Pick one feature. What files does it touch, in order?

Write those three answers down. That is the artefact, and it is exactly what your
first week at a job should produce.

::accordion
  :::accordion-item{label="If you cannot find the entry point" icon="i-lucide-compass"}
  Search the repository for `public static void main` in Java, or for the
  router/controller registration in a web project. Failing that, read the run
  command in `README.md` and work backwards from the file it names. There is
  always a first line of your team's own code; the trick is that it is usually
  buried under a framework, which is why searching beats browsing.
  :::
::

## Check yourself

1. Why do you read the tests before reading the implementation?
2. **An interviewer asks: "you join a team with a large existing codebase. What
   do you do in your first week?"**

## The interview question this answers

**"How do you get up to speed on an unfamiliar codebase?"**

This is asked of every experienced hire and increasingly of freshers, because it
separates people who have worked on something real from people who have only ever
written from scratch. Give the method: run it, read the tree, find the entry
point, trace one path end to end, read the tests, and check the git history of
anything that looks strange. Then say what you would produce at the end of the
week — a diagram of one path and a list of questions. That last part is what
makes it sound like something you have actually done.
