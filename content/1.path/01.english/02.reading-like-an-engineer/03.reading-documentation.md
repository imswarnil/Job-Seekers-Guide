Documentation was written by somebody who already knew the answer, for somebody
who already knows the answer, and you are reading it precisely because you do
not. That is not incompetence on their part. It is a structural problem, and
there is a way around it.

## Why this matters in a job

Because for the rest of your career the answer to most of your questions will be
in a documentation page you found and could not use. I lost weeks to this before
I understood that there are four different kinds of page and that I kept opening
the wrong one.

## The four kinds

Almost every documentation site is made of these four, and they answer different
questions. Opening the wrong kind is why documentation feels useless.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-footprints" title="Tutorial: 'take me through it'"}
  A guided sequence with a known end. Good when you know nothing. Useless when
  you have a specific question, because it will not let you skip.
  :::
  :::feature{icon="i-lucide-target" title="How-to guide: 'I need to do X'"}
  A recipe for one task. This is the one you want ninety per cent of the time
  and the one that is hardest to find, because it is usually titled something
  like "Advanced usage".
  :::
  :::feature{icon="i-lucide-list" title="Reference: 'what are the options'"}
  Exhaustive, alphabetical, unreadable front to back, and correct. You search
  this, you never read it.
  :::
  :::feature{icon="i-lucide-lightbulb" title="Explanation: 'why is it like this'"}
  Background and design decisions. Feels like a luxury and is the thing that
  makes everything else make sense. Read it once, on a quiet afternoon, for any
  tool you will use for a year.
  :::
::

::tip
When documentation feels useless, ask which of the four you have open and which
one your question needs. Nine times out of ten you are in a tutorial with a
how-to question, or in a reference with a why question.
::

## The reading order that works

::flow{numbered direction="vertical" caption="Never start at the top of the page. The page is not written in the order you need it."}
  :::flow-step{label="Find the example first" icon="i-lucide-code"}
  Scroll past the prose to the first code block. Documentation prose is written
  to be precise; the example is written to be understood. Read the example, then
  go back up only for the parts of it you did not follow.
  :::
  :::flow-step{label="Read the signature, not the paragraph" icon="i-lucide-braces" highlight}
  In a reference page, the one line that names the parameters and the return type
  tells you more than the description under it. What goes in, what comes out.
  :::
  :::flow-step{label="Check the version" icon="i-lucide-tag"}
  Top of the page or in the URL. Half of all documentation frustration is
  reading the page for a version you are not running.
  :::
  :::flow-step{label="Then search within the page" icon="i-lucide-search"}
  Ctrl+F for the noun in your question. Faster than reading and it finds the
  section the navigation hid.
  :::
::

## Watch it happen

You need to round an applicant's composite score to one decimal place in Java.
Here is the reference entry you land on.

```java [Reference]
public static double round(double a)
public static long round(double a)
```

```text [Description]
Returns the closest long to the argument, with ties rounding to positive infinity.
```

Read the signature, not the description. `Math.round` returns a **whole number**.
It cannot round to one decimal place, and no amount of reading the paragraph will
change that. You have your answer in four seconds: wrong method.

So you search the page for "decimal" and find the right tool.

```java [ScoreFormatter.java]
// Right for money and marks: exact decimal arithmetic, and you choose
// what happens at the halfway point rather than discovering it.
BigDecimal score = new BigDecimal("72.45");
BigDecimal rounded = score.setScale(1, RoundingMode.HALF_UP);
System.out.println(rounded);
```

```text [Output]
72.5
```

::warning{icon="i-lucide-alert-triangle"}
`new BigDecimal(72.45)` with a `double` instead of a `String` gives you
`72.4500000000000028421709430404007434844970703125`, because the `double` was
never exactly 72.45 in the first place. The documentation says this, in the
constructor's note, in a sentence most people skip. This exact trap is in the
Java track's lesson on floating point, and it is worth meeting twice.
::

## What confuses people here

That you are supposed to understand a page fully before using it. You are not.
The working relationship with documentation is: land, find the example, take the
one thing you need, leave. You will read the same page eleven times over a year
and understand a bit more each time, and that is the normal way this works.

::real-life{title="What 'reads the docs' actually means on a CV" source="Any team"}
It never means having read them. It means: when something is unclear, this person
goes to the source rather than to a five-year-old answer on a forum that was
written for version 2. The habit is worth saying out loud in an interview,
because the alternative habit is extremely common and everybody senior has been
burned by it.
::

## What you can do now

You can tell which kind of page you have open, read a signature instead of a
paragraph, and check a version before losing an afternoon to it.

## Your turn

Pick any method you have used and never read about. `String.split` is a good one.
Find its official reference page and answer three questions from the signature
alone, before reading any prose:

1. What does it return?
2. What happens to a trailing empty string?
3. What is the second parameter in the two-argument version for?

::accordion
  :::accordion-item{label="What you will find, and why question two matters" icon="i-lucide-check"}
  It returns a `String[]`. The two-argument version takes a limit, which controls
  how many pieces you get and, crucially, whether trailing empty strings survive.

  `"CSE,ECE,,".split(",")` gives you three elements, not four: the trailing empty
  one is discarded. `"CSE,ECE,,".split(",", -1)` gives you four.

  That is a genuine bug generator when you are parsing a CSV of applications
  where the last column is often blank, and it is one line in the documentation
  that nobody reads until it costs them an afternoon.
  :::
::

## Check yourself

1. Name the four kinds of documentation page, and say which one you need when you
   have a specific task to do.
2. **An interviewer asks: "how do you learn a library you have never used?"**

## The interview question this answers

**"How do you approach a technology you do not know?"**

The answer that works is a process, not enthusiasm. Find the official
documentation, read the explanation page once to get the model, then work from
examples and the reference for the specific task, and check the version against
what I am running. Mentioning the version check is a small detail that signals
you have actually been burned, which is what they are listening for.
