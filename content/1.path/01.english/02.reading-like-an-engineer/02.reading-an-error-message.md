The machine is telling you exactly what is wrong. It is doing so in the least
helpful possible order, addressed to nobody, and most beginners respond by
copying the whole thing into a search box.

There is a method, and it takes about a minute to learn.

## Why this matters in a job

Because the gap between a developer who reads errors and one who searches them is
enormous and visible. I spent my first year searching. The people around me were
reading, and they looked like geniuses, and they were doing something I could
have done on day one.

## The anatomy

Here is a real-shaped Java error from the university system.

```text [Terminal]
Exception in thread "main" java.lang.NullPointerException: Cannot invoke
"String.trim()" because the return value of "Applicant.getEmail()" is null
	at com.university.admissions.EmailService.send(EmailService.java:42)
	at com.university.admissions.Shortlister.notifyApplicant(Shortlister.java:88)
	at com.university.admissions.Shortlister.shortlistAll(Shortlister.java:61)
	at com.university.admissions.AdmissionsApp.main(AdmissionsApp.java:23)
```

Four parts, and only three of them matter.

::code-trace{caption="Read it in this order. Not top to bottom."}
```text [Terminal]
java.lang.NullPointerException: Cannot invoke "String.trim()" because the return value of "Applicant.getEmail()" is null
	at com.university.admissions.EmailService.send(EmailService.java:42)
	at com.university.admissions.Shortlister.notifyApplicant(Shortlister.java:88)
	at com.university.admissions.Shortlister.shortlistAll(Shortlister.java:61)
	at com.university.admissions.AdmissionsApp.main(AdmissionsApp.java:23)
```

  :::code-trace-step{lines="1" caption="FIRST. The kind of failure and, in modern Java, exactly which thing was null. This one line tells you that an applicant has no email address. You have not opened a file yet and you already know the bug."}
  :::
  :::code-trace-step{lines="2" caption="SECOND. Where it happened: EmailService line 42. This is where the program noticed, which is not necessarily where the mistake is."}
  :::
  :::code-trace-step{lines="3-5" caption="THIRD. How it got there, most recent first. Read downwards and you get the story: main called shortlistAll, which called notifyApplicant, which called send, which blew up."}
  :::
::

## The rule that changes everything

**The top line is where it noticed. The bug is usually further down.**

In this trace, `EmailService.send` is blameless: it was handed an applicant with
no email and did the reasonable thing. The real question is why `notifyApplicant`
on line 88 passed it one. The fix is almost never on the line the error names.

::flow{numbered direction="vertical" caption="Four steps, ninety seconds, before you search for anything."}
  :::flow-step{label="Read the first line properly" icon="i-lucide-text"}
  All of it, slowly. Modern error messages are far more helpful than their
  reputation, and most people never actually read them.
  :::
  :::flow-step{label="Find the topmost line that is YOUR code" icon="i-lucide-crosshair" highlight}
  A trace is usually mostly framework and library. Scan for your own package
  name, which here is `com.university`. That is where your investigation starts.
  :::
  :::flow-step{label="Read downwards for the story" icon="i-lucide-list-ordered"}
  Who called whom. This tells you what the program was trying to do, which is
  usually the thing you had forgotten it was doing.
  :::
  :::flow-step{label="Find 'Caused by', if present" icon="i-lucide-search"}
  A wrapped exception hides the original underneath. The last "Caused by" in the
  output is almost always the real one.
  :::
::

## Watch a wrapped one

This is the shape that defeats people, because the useful information is at the
bottom.

```text [Terminal]
Exception in thread "main" org.springframework.dao.DataIntegrityViolationException:
could not execute statement
	at com.university.admissions.ApplicationRepository.save(ApplicationRepository.java:31)
	... 24 more
Caused by: java.sql.SQLIntegrityConstraintViolationException:
Duplicate entry 'APP-2026-00417' for key 'application.application_number'
	at com.mysql.cj.jdbc.ClientPreparedStatement.executeInternal(...)
```

The first line says "could not execute statement", which is almost useless. The
`Caused by` says a duplicate application number, which is the entire bug: somebody
submitted twice, or your number generator is not unique.

::warning{icon="i-lucide-alert-triangle"}
Scroll down. The habit of reading the first line and stopping is the single most
common reason a beginner spends an afternoon on a five-minute bug. In a wrapped
trace the first line is the outermost layer complaining, and the truth is at the
bottom.
::

## What confuses people here

That a long error means a big problem. Trace length is about how deep the call
stack was, not how bad the bug is. A forty-line trace from a web framework is
usually a two-character fix.

::real-life{title="What senior engineers are actually doing" source="Watching someone debug, 2019"}
I watched a senior engineer glance at a screen of red text for about four seconds
and say "your config file is not where you think it is". It looked like
experience and intuition. It was: read the first line, find our package, read the
message. He was doing the four steps above, fast, and I could have been doing
them in my first week if anybody had written them down.
::

## What you can do now

You can turn forty lines of red text into a sentence about what is wrong, before
opening a browser. This is worth more hours than almost anything else in this
track.

## Your turn

Read this trace and answer three questions without looking anything up: what
failed, in whose code, and what would you look at first?

```text [Terminal]
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException:
Index 5 out of bounds for length 5
	at com.university.results.GradeCalculator.average(GradeCalculator.java:17)
	at com.university.results.ResultSheet.build(ResultSheet.java:54)
	at com.university.results.ResultsApp.main(ResultsApp.java:12)
```

::accordion
  :::accordion-item{label="The answer, and the bug" icon="i-lucide-check"}
  **What failed:** something tried to read position 5 of a thing that has five
  positions. Java counts from zero, so a five-element array has positions 0 to 4,
  and 5 is one past the end.

  **Whose code:** all of it is `com.university`, so there is nowhere to hide. The
  topmost is `GradeCalculator.average`, line 17.

  **What to look at first:** the loop condition on or near line 17. This error
  has essentially one cause, and it is `<=` where it should be `<`:

  ```java
  for (int i = 0; i <= marks.length; i++) {   // wrong: reaches length
  for (int i = 0; i < marks.length; i++) {    // right: stops one before
  ```

  The off-by-one is the most common bug in programming and it lives at the
  boundary, every time. There is a whole lesson on it in the Java track.
  :::
::

## Check yourself

1. Why is the line named in the first frame usually not where the bug is?
2. **An interviewer asks: "you get an exception you have never seen before. Walk
   me through what you do."**

## The interview question this answers

**"How do you debug something?"**

This is asked constantly and most freshers answer "I search the error on Google",
which is honest and weak. The strong answer is a method: read the message
properly, find the topmost frame in my own code, read the call chain to
understand what it was doing, check for a `Caused by`, then reproduce it in the
smallest possible case. Searching comes after all of that, and by then you are
searching for something specific rather than pasting forty lines.
