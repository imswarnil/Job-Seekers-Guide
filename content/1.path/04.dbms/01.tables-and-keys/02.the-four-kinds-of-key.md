That id is doing an enormous amount of work. Keys are how a database knows one
row from another and how one row points at another, and getting them wrong is
the single most expensive design mistake available, because everything else is
built on top.

## Why this matters in a job

Because "what is the difference between a primary key and a unique key" is asked
in essentially every database round, and because the choice of primary key is one
of the few decisions that is genuinely hard to change later.

## The four

::feature-list{columns="2"}
  :::feature{icon="i-lucide-key" title="Candidate key"}
  Any column, or set of columns, that could uniquely identify a row. A table can
  have several. For an applicant: the roll number, the email address, and the
  Aadhaar number are all candidates.
  :::
  :::feature{icon="i-lucide-key-round" title="Primary key"}
  The candidate you chose. Exactly one per table, never `NULL`, and it is what
  every other table will refer to. This is a decision, not a discovery.
  :::
  :::feature{icon="i-lucide-key-square" title="Composite key"}
  A key made of more than one column, because no single column is unique. An
  attendance row is identified by student *and* subject *and* date.
  :::
  :::feature{icon="i-lucide-link" title="Foreign key"}
  A column holding another table's primary key. It is a *constraint*: the
  database will refuse a value that does not exist over there.
  :::
::

## Primary key or unique constraint

The distinction people fumble. Both enforce uniqueness. The differences are
narrow and exact.

| | Primary key | Unique constraint |
| --- | --- | --- |
| How many per table | Exactly one | As many as you like |
| `NULL` allowed | Never | Usually yes, and often several times |
| What refers to it | Foreign keys point here | Rarely pointed at |
| What it means | "This is how this row is identified" | "No two rows may share this" |

```sql [schema.sql]
CREATE TABLE Applicant (
  applicant_id  BIGSERIAL PRIMARY KEY,          -- identity, never changes
  email         TEXT NOT NULL UNIQUE,           -- no two applicants share one
  aadhaar       TEXT UNIQUE,                    -- unique, and may be NULL
  full_name     TEXT NOT NULL
);
```

Three columns with uniqueness, one primary key. `aadhaar` shows why the
distinction matters: it must be unique where present and applicants without one
must still be storable, which a primary key could never allow.

## Natural or surrogate: the argument, settled

The real decision, and it comes up on every schema you will ever design.

::compare{caption="Should the applicant's roll number be the primary key?"}
  :::compare-side{label="Natural key: the roll number" verdict="wrong"}
  It is meaningful, it is already unique, and it saves a column. Then in 2027 the
  university changes the roll-number format to include the intake year, and that
  value is repeated in eleven other tables as a foreign key. Every one of them
  has to change, in one transaction, and anything that cached it is now wrong.
  :::
  :::compare-side{label="Surrogate key: a generated id" verdict="right"}
  `applicant_id BIGSERIAL`. Meaningless, so nothing outside the database has an
  opinion about it, so it never has to change. The roll number is still a column,
  still `UNIQUE`, and still searchable. It is not what other tables point
  at.
  :::
::

::pull-quote
The question that settles it: could this value ever change, or be entered wrong
and need correcting? If yes, it must not be the primary key, because a primary
key is a promise of permanence to every table that points at it.
::

Every natural candidate fails that test eventually. Email addresses change.
Phone numbers are reassigned. Names are corrected. National identifiers are
reissued. Roll-number formats change when a new registrar arrives.

::side-note{kind="go-deeper"}
There is one honest counter-argument, and it is worth knowing so you are not
caught out: a surrogate key needs an extra index and an extra join to get from
"the roll number the registrar typed" to the row. In practice that cost is tiny
and the flexibility is enormous, which is why essentially every production schema
you will meet uses surrogate keys. But an interviewer asking "when would you use
a natural key?" wants to hear that you know it is a trade rather than a rule:
a junction table joining two ids is the usual case where the natural composite
key is right.
::

## What a foreign key actually prevents

```sql [try-it.sql]
INSERT INTO Application (applicant_id, programme_id, score)
VALUES (999999, 3, 78);
```

```text [Output]
ERROR:  insert or update on table "application" violates foreign key constraint
DETAIL: Key (applicant_id)=(999999) is not present in table "applicant".
```

An application for an applicant who does not exist is now impossible. Not
discouraged, not checked by convention. Impossible, from every program, forever.

And the other direction:

```sql [try-it.sql]
DELETE FROM Applicant WHERE applicant_id = 4182;
```

```text [Output]
ERROR:  update or delete on table "applicant" violates foreign key constraint
DETAIL: Key (applicant_id)=(4182) is still referenced from table "application".
```

You cannot delete an applicant who still has applications, which is the database
refusing to create orphan rows. What should happen instead is a decision you make
explicitly:

| Option | What happens on delete | When it is right |
| --- | --- | --- |
| `ON DELETE RESTRICT` | Refuses. The default, and usually correct. | Anything financial or academic |
| `ON DELETE CASCADE` | Deletes the applications too | A junction table, or a child that is meaningless alone |
| `ON DELETE SET NULL` | Keeps the row, empties the reference | A reviewer who has left; the review still happened |

::warning{icon="i-lucide-alert-triangle"}
`ON DELETE CASCADE` is a loaded weapon. Deleting one programme can silently
remove ten thousand applications and every fee payment attached to them, in one
statement, with no warning. Use it where the child genuinely cannot exist
without the parent, and nowhere else. The default of refusing is the safe one and
it is the default for a reason.
::

## The composite key, done properly

Attendance has no single unique column. Student 2026CSE0184 appears hundreds of
times, so does subject CS-201, and so does 12 March.

```sql [schema.sql]
CREATE TABLE Attendance (
  student_id  BIGINT NOT NULL REFERENCES Student(student_id),
  subject_id  BIGINT NOT NULL REFERENCES Subject(subject_id),
  class_date  DATE   NOT NULL,
  present     BOOLEAN NOT NULL,
  PRIMARY KEY (student_id, subject_id, class_date)
);
```

That primary key is also the business rule: one attendance record per student per
subject per day. A double-marking is not a bug to be handled in code, it is an
error the database returns.

## Your turn

Design the keys for `FeePayment`. It records that an applicant paid an amount on
a date with a receipt number, against a particular application.

1. What are the candidate keys?
2. What is the primary key, and why?
3. What foreign keys, and what `ON DELETE` behaviour for each?

::accordion
  :::accordion-item{label="One answer, and the reasoning" icon="i-lucide-check"}
  ```sql
  CREATE TABLE FeePayment (
    payment_id      BIGSERIAL PRIMARY KEY,
    application_id  BIGINT NOT NULL
                      REFERENCES Application(application_id) ON DELETE RESTRICT,
    receipt_number  TEXT   NOT NULL UNIQUE,
    amount_paise    BIGINT NOT NULL CHECK (amount_paise > 0),
    paid_on         DATE   NOT NULL
  );
  ```

  **Candidates:** the receipt number is genuinely unique. So, arguably, is
  application plus date plus amount, though that is fragile, somebody could pay
  the same amount twice in a day.

  **Primary key:** a surrogate. The receipt number is a natural candidate and it
  fails the permanence test: receipts get reissued and formats change when the
  finance system is replaced. It stays as a `UNIQUE` column.

  **Foreign key:** `RESTRICT`, emphatically. Cascading a delete here would erase
  the record that money changed hands, which is the one thing an institution must
  never lose. If an application must go, the payments have to be dealt with
  deliberately first.

  **The detail worth noticing:** `amount_paise BIGINT`, not `NUMERIC` and
  certainly not a floating-point type. Money is stored as an integer count of the
  smallest unit, because 0.1 + 0.2 is not 0.3 in binary floating point. That trap
  has its own lesson in the Java track and it starts here, in the schema.
  :::
::

## The interview question this answers

**"What is the difference between a primary key and a unique key?"**

One per table versus many; never `NULL` versus usually nullable; and the one
most candidates miss: a primary key is what foreign keys point at, so it is a
promise of permanence rather than merely a uniqueness rule. Then the follow-up
they will ask: natural or surrogate, and the answer is the permanence test with
the roll-number example.
