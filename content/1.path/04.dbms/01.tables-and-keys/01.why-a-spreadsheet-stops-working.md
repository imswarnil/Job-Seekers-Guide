A file works until it does not, and it is worth seeing exactly where it stops,
because each failure is one of the four things a database exists to provide.

Here is the university's admissions spreadsheet. It is completely reasonable and
thousands of real institutions run on one.

## Why this matters in a job

Because "why not just use a spreadsheet" is a real question asked by real
clients, and because each answer below is a database feature you are about to
spend two weeks on. Knowing which problem each feature solves is the difference
between memorising and understanding.

## The spreadsheet

| Applicant | Email | Programme | Dept | Dept head | Score | Fee paid |
| --- | --- | --- | --- | --- | --- | --- |
| Anita Rao | anita@… | B.Tech CSE | Computer Science | Dr Iyer | 78 | 45000 |
| Vikram Shah | vikram@… | B.Tech CSE | Computer Science | Dr Iyer | 64 | 45000 |
| Anita Rao | anita@… | B.Tech ECE | Electronics | Dr Menon | 78 | 45000 |
| Priya Nair | priya@… | B.Tech CSE | Computer Science | Dr lyer | 81 | 0 |

Look at the last row's department head. `Dr lyer`, with a lowercase L instead of
a capital I. Nobody will ever notice, and any count grouped by department head
now reports two people.

## Failure one: the same fact, stored many times

"The head of Computer Science is Dr Iyer" is written three times. Change it once
and you must change it everywhere, and you will miss one.

::compare{caption="The same change, two designs."}
  :::compare-side{label="The spreadsheet" verdict="wrong"}
  Dr Iyer retires. Find and replace across 40,000 rows, hope nobody has a typo,
  hope nobody is editing at the same time, hope you catch `Dr lyer`.
  :::
  :::compare-side{label="Tables" verdict="right"}
  The fact lives in one row of a `Department` table. One update. Every applicant
  row referred to it by id, so every one of them is now correct, including the
  ones with typos, because there are no typos to have.
  :::
::

That is **normalisation**, and it is chapter two.

## Failure two: nothing stops nonsense

A spreadsheet will accept anything. `Score: 780`. `Score: "absent"`. An empty
email. A programme that does not exist. Two applicants with the same application
number.

A database refuses.

```sql [schema.sql]
CREATE TABLE Application (
  application_id   BIGSERIAL PRIMARY KEY,
  applicant_id     BIGINT      NOT NULL REFERENCES Applicant(applicant_id),
  programme_id     BIGINT      NOT NULL REFERENCES Programme(programme_id),
  score            NUMERIC(5,2) CHECK (score >= 0 AND score <= 100),
  status           TEXT        NOT NULL DEFAULT 'RECEIVED',
  UNIQUE (applicant_id, programme_id)     -- one application per programme
);
```

Six rules in six lines, and the database enforces every one of them on every
write, from every program, forever. Nobody can bypass them by opening the file in
a different tool.

::side-note{kind="security"}
That last point matters more than it sounds. A rule in your Java code protects
you from your Java code. A rule in the database protects you from the import
script somebody wrote in a hurry, the intern with a query tool, and the next
application written against the same data in three years.
::

## Failure three: two people at once

::memory{kind="table" caption="Sixty seats. Both clerks read 59 remaining. Both allot. Sixty-one students, sixty seats."}

  - label: "3. A allots a seat and saves"
    cells: [{ value: "writes 58", state: "active" }, { value: "" }, { value: "58" }]
  - label: "4. B allots and saves, from the 59 it read"
    cells: [{ value: "" }, { value: "writes 58", state: "active" }, { value: "58", state: "active" }]
---
::

Two seats were allotted. The count went down by one. This is the identical shape
to the lost increment in the operating systems track, and a database solves it
with **transactions and locking**, which is chapter three.

## Failure four: finding things

Forty thousand rows is fine. Ten million is not, and a spreadsheet has exactly
one strategy: look at every row.

A database has **indexes**, which turn ten million rows into about eleven reads.
That is chapter four, and it is the single most valuable practical topic in this
track.

## What a database actually is

::feature-list{columns="2"}
  :::feature{icon="i-lucide-copy-minus" title="A place for each fact"}
  Stored once, referred to by id. Change it in one place and everything that
  points at it is correct.
  :::
  :::feature{icon="i-lucide-shield" title="Rules it will not let you break"}
  Types, required fields, ranges, uniqueness, and references that must point at
  something real.
  :::
  :::feature{icon="i-lucide-users" title="Safety when several people write"}
  Transactions: all of a change happens or none of it does, even with four
  hundred people writing at once.
  :::
  :::feature{icon="i-lucide-search" title="Finding without reading everything"}
  Indexes, and a planner that decides how to answer your question.
  :::
::

## What confuses people here

That a database is "where you put the data". It is a program that enforces rules
and arbitrates between users. The storing is the least interesting thing it does,
which is why this track comes before SQL rather than after.

::real-life{title="What actually happens in a small institution" source="Common, everywhere"}
A college runs admissions on a shared spreadsheet for years and it works,
because three people use it and they talk to each other. It fails in one specific
week: the intake doubles, six people are editing, and two of them allot the same
seat on the same afternoon. The reason to know this is that you will be asked to
replace one, and the answer to "why can we not keep using the sheet" should be
the four failures above rather than "because databases are better".
::

## What you can do now

You can name the four things a database provides and say which failure each one
prevents, which is a complete answer to a very common client question.

## Your turn

Look at the spreadsheet at the top again and find three more problems I did not
name.

::accordion
  :::accordion-item{label="Three more" icon="i-lucide-search"}
  **The fee is attached to the wrong thing.** ₹45,000 appears on every row for
  Anita, who has two rows. Has she paid ₹45,000 or ₹90,000? The sheet cannot
  express the difference, because a payment is a fact about an applicant and
  the row is about an application.

  **Deleting loses more than you meant.** If Priya is the only applicant to a
  programme and her row is deleted, the fact that the programme exists and which
  department it belongs to disappears with her. This is called a deletion
  anomaly and it is chapter two.

  **`Fee paid: 0` is ambiguous.** Not paid, or paid nothing because they are
  exempt? A spreadsheet has one empty and one zero and no way to say "we do not
  know yet". A database has `NULL`, which means exactly that and behaves
  differently in every calculation, which is a lesson of its own in the SQL
  track.
  :::
::

## Check yourself

1. Name the four failures and the database feature that answers each.
2. **An interviewer asks: "we have an Excel sheet that works. Why would we move
   to a database?"** Answer without saying "it is more professional".

## The interview question this answers

**"Why use a database instead of files?"**

Answer with the four failures, in order, and give the seat-allotment example for
the concurrency one. That example does real work: it is concrete, it is visibly
expensive, and it is the one failure a client has usually already experienced.
Candidates who answer "databases are faster and more secure" are describing
properties rather than problems.
