Two weeks of theory, in one page of words.

## Tables and keys

| Term | In one line |
| --- | --- |
| **Relation / table** | A set of rows with the same named, typed columns. |
| **Tuple / row** | One record. One applicant, one application, one payment. |
| **Attribute / column** | One named, typed field. |
| **Domain** | The set of values a column may hold. Enforced by the type plus `CHECK`. |
| **Candidate key** | Any column set that could uniquely identify a row. A table may have several. |
| **Primary key** | The candidate you chose. One per table, never `NULL`, and what foreign keys point at. |
| **Surrogate key** | A generated, meaningless id. Preferred, because it can never need to change. |
| **Natural key** | A real-world value used as a key. Usually a trap: real-world values change. |
| **Composite key** | A key made of several columns, because no single one is unique. |
| **Foreign key** | A column holding another table's primary key, enforced by the database. |
| **Referential integrity** | The guarantee that a foreign key always points at a row that exists. |
| **ON DELETE RESTRICT / CASCADE / SET NULL** | What happens to children when a parent is deleted. `RESTRICT` is the safe default. |
| **NULL** | "We do not know." Not zero, not empty string, and it behaves differently in every calculation. |

## Normalisation

| Term | In one line |
| --- | --- |
| **Functional dependency** | B depends on A if knowing A fixes B. `department_id → head`. |
| **Partial dependency** | A column depending on only part of a composite key. Only possible when the key is composite. |
| **Transitive dependency** | A column depending on a non-key column, which depends on the key. |
| **1NF** | One value per cell. No lists in a column. |
| **2NF** | 1NF, and no partial dependency on a composite key. |
| **3NF** | 2NF, and no transitive dependency. This is where you stop, in practice. |
| **BCNF** | A stricter 3NF for tables with overlapping candidate keys. Examined more often than it is needed. |
| **Update anomaly** | A fact stored twice, changed once. The data is now inconsistent. |
| **Insert anomaly** | Cannot record one fact without inventing another. |
| **Delete anomaly** | Removing one fact destroys an unrelated one. |
| **Denormalisation** | Storing a duplicate on purpose, for read speed, accepting that you now maintain both. |

## Transactions

| Term | In one line |
| --- | --- |
| **Transaction** | A set of statements that all happen or none do. |
| **Atomicity** | All or nothing, even across a crash. |
| **Consistency** | Every declared constraint holds before and after. |
| **Isolation** | Other transactions do not see your half-finished work. |
| **Durability** | Once committed, it survives the power going. Achieved with a write-ahead log. |
| **Write-ahead log** | Changes appended to a log and flushed before the data pages. Why commits are fast *and* durable. |
| **COMMIT / ROLLBACK** | Make it permanent, or undo all of it. |
| **Dirty read** | Reading uncommitted data that may be rolled back. |
| **Non-repeatable read** | The same row read twice in one transaction, with different values. |
| **Phantom read** | The same `WHERE` read twice, returning a different number of rows. |
| **Lost update** | ⚠️ Two reads, two writes, one silently overwritten. Allowed at every default isolation level. |
| **Read committed** | PostgreSQL, Oracle and SQL Server default. Prevents dirty reads only. |
| **Repeatable read** | MySQL InnoDB default. Also prevents non-repeatable reads. |
| **Serializable** | As if transactions ran one at a time. Correct and expensive, and may abort rather than block. |
| **Pessimistic locking** | `SELECT ... FOR UPDATE`. Assume a clash and block. |
| **Optimistic locking** | A version column checked in the `WHERE`. Assume no clash and detect one. |
| **Deadlock** | Two transactions each holding what the other wants. The engine kills one as the victim. |

## Indexes

| Term | In one line |
| --- | --- |
| **Index** | A sorted structure that says where rows are. Faster reads, slower writes. |
| **B-tree** | The usual index shape. Wide and shallow, so ten million rows is about four page reads. |
| **Clustered index** | One per table, where the table itself is stored in that order. MySQL InnoDB does this with the primary key. |
| **Composite index** | On several columns, usable **left to right** only. |
| **Covering index** | Contains every column a query needs, so the table is never touched. |
| **Selectivity** | How well a value narrows the rows. Low selectivity means the index is ignored. |
| **Cardinality** | How many distinct values a column has. A boolean has two. |
| **Seq Scan / Full table scan** | Reading every row. Fine on a small table, fatal on a large one. |
| **Index Scan / Index Seek** | Using the index to jump to matching rows. |
| **EXPLAIN / EXPLAIN ANALYZE** | Ask the database what it plans to do, or what it actually did. |
| **Query planner** | The component that chooses between the available strategies using table statistics. |

## The five sentences to keep

::pull-quote
A primary key is a promise of permanence. A fact belongs in exactly one place.
Atomicity is about crashes and isolation is about neighbours. Every default
isolation level allows a lost update. And an index is a sorted copy you pay for
on every write.
::
