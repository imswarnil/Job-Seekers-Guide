Two weeks of theory. Now a paragraph and a blank page, which is exactly the shape
of the design question in an interview.

::note
Do this with pen and paper first. Drawing boxes and arrows by hand is faster than
typing DDL, and it is what you will be asked to do on a whiteboard.
::

## The brief

::callout{icon="i-lucide-file-text" color="neutral"}
The university runs a placement cell. Companies register and visit campus in a
drive. A drive is for one or more programmes and has a date and a minimum
required percentage. Students apply to a drive; a student may apply to several
drives and a drive receives many applications. Each application moves through
rounds, aptitude, technical, HR, and each round has a result and a date.
A student who receives an offer has a package and a joining date, and a student
may hold more than one offer. The placement officer needs to know, for any
programme and year: how many students were placed, the highest and average
package, and which companies made the most offers.
::

## Work through it in this order

::flow{numbered direction="vertical" caption="The same order you should say out loud in an interview."}
  :::flow-step{label="Underline the nouns" icon="i-lucide-spell-check"}
  Company, drive, programme, student, application, round, offer. Seven, and each
  is probably a table.
  :::
  :::flow-step{label="Find the relationships and their cardinality" icon="i-lucide-git-fork"}
  A drive is for many programmes and a programme has many drives, many to many,
  so a junction table. A student has many applications; an application has many
  rounds; a student may have many offers.
  :::
  :::flow-step{label="Choose a key for each, and test it" icon="i-lucide-key"}
  Surrogate everywhere, unless a natural composite is genuinely the identity.
  Apply the permanence test out loud to at least one of them.
  :::
  :::flow-step{label="Find the facts that must be frozen" icon="i-lucide-snowflake" highlight}
  The package on an offer. The minimum percentage at the time of the drive. Not
  pointers to current values, because those change and the record must not.
  :::
  :::flow-step{label="Name the constraints as you draw" icon="i-lucide-shield"}
  One application per student per drive. A round result from a fixed set. A
  package greater than zero. This is the step that sounds senior.
  :::
  :::flow-step{label="Then the indexes the questions need" icon="i-lucide-list-tree"}
  The officer's three questions tell you exactly which columns get filtered and
  grouped.
  :::
::

::accordion
  :::accordion-item{label="One answer, with the reasoning for each decision" icon="i-lucide-check"}
  ```sql
  CREATE TABLE Company (
    company_id   BIGSERIAL PRIMARY KEY,
    name         TEXT NOT NULL UNIQUE,
    sector       TEXT
  );

  CREATE TABLE Drive (
    drive_id       BIGSERIAL PRIMARY KEY,
    company_id     BIGINT NOT NULL REFERENCES Company(company_id) ON DELETE RESTRICT,
    drive_date     DATE   NOT NULL,
    -- FROZEN: the rule as it was for this drive, not the company's current policy
    min_percentage NUMERIC(5,2) NOT NULL CHECK (min_percentage BETWEEN 0 AND 100)
  );

  -- Many to many: a drive covers several programmes, a programme sees many drives
  CREATE TABLE DriveProgramme (
    drive_id     BIGINT NOT NULL REFERENCES Drive(drive_id) ON DELETE CASCADE,
    programme_id BIGINT NOT NULL REFERENCES Programme(programme_id) ON DELETE RESTRICT,
    PRIMARY KEY (drive_id, programme_id)
  );

  CREATE TABLE PlacementApplication (
    application_id BIGSERIAL PRIMARY KEY,
    drive_id       BIGINT NOT NULL REFERENCES Drive(drive_id) ON DELETE RESTRICT,
    student_id     BIGINT NOT NULL REFERENCES Student(student_id) ON DELETE RESTRICT,
    applied_on     TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (drive_id, student_id)          -- one application per student per drive
  );

  CREATE TABLE DriveRound (
    round_id       BIGSERIAL PRIMARY KEY,
    application_id BIGINT NOT NULL REFERENCES PlacementApplication(application_id)
                     ON DELETE CASCADE,     -- a round is meaningless without its application
    round_type     TEXT NOT NULL CHECK (round_type IN ('APTITUDE','TECHNICAL','HR')),
    held_on        DATE NOT NULL,
    result         TEXT NOT NULL CHECK (result IN ('CLEARED','REJECTED','PENDING')),
    UNIQUE (application_id, round_type)     -- one of each round per application
  );

  CREATE TABLE Offer (
    offer_id       BIGSERIAL PRIMARY KEY,
    application_id BIGINT NOT NULL UNIQUE
                     REFERENCES PlacementApplication(application_id) ON DELETE RESTRICT,
    -- FROZEN, and in paise as an integer: never a float for money
    package_paise  BIGINT NOT NULL CHECK (package_paise > 0),
    offered_on     DATE NOT NULL,
    joining_date   DATE,
    accepted       BOOLEAN NOT NULL DEFAULT FALSE
  );

  -- The officer's three questions, indexed
  CREATE INDEX ON Drive (drive_date);
  CREATE INDEX ON PlacementApplication (student_id);
  CREATE INDEX ON PlacementApplication (drive_id);
  CREATE INDEX ON Offer (offered_on);
  ```

  **The decisions worth defending out loud:**

  `min_percentage` lives on the **drive**, not on the company. A company's
  requirement changes between years and the record of what the rule was in 2026
  must not move with it.

  `package_paise BIGINT`, not `NUMERIC` and never a float. Money is an integer
  count of the smallest unit. This one detail marks out somebody who has handled
  money before.

  `Offer.application_id` is `UNIQUE`, which encodes a real rule: one offer per
  application. A student holding several offers is several applications, which is
  what the brief actually describes.

  `DriveRound` cascades and `Offer` restricts. A round cannot exist without its
  application; an offer is a record that must never be deleted by accident.

  **What is deliberately absent:** a `placed` flag on `Student`. That is
  derivable: a student is placed if they have an accepted offer, and a derived
  column
  that can be edited independently will eventually disagree with the offers. If
  the query turns out to be too slow, *then* it becomes a measured
  denormalisation with a job that maintains it.
  :::
::

## Four shorter problems

### 1. Find the anomalies

| enrol_id | student | student_email | subject | teacher | teacher_phone | marks |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Anita Rao | anita@… | DBMS | Dr Iyer | 98xxx | 78 |
| 2 | Anita Rao | anita@… | OS | Dr Iyer | 98xxx | 81 |
| 3 | Vikram Shah | vikram@… | DBMS | Dr Iyer | 98xxx | 64 |

Name all three anomalies with a specific example of each, then draw the tables.

### 2. Make this safe

```java [SeatService.java]
public void allot(long programmeId, long studentId) {
  int left = programmeRepo.seatsLeft(programmeId);
  if (left > 0) {
    programmeRepo.setSeatsLeft(programmeId, left - 1);
    allotmentRepo.insert(programmeId, studentId);
  }
}
```

Two clerks call it at the same instant. Say what happens, then fix it two
different ways.

### 3. Why is this slow?

```sql
SELECT * FROM Application
 WHERE LOWER(status) = 'shortlisted'
   AND YEAR(applied_on) = 2026
 ORDER BY score DESC;
```

There is an index on `(status, applied_on)`. Name three separate reasons it will
not be used and rewrite the query.

### 4. What breaks

```sql
DELETE FROM Programme WHERE programme_id = 3;
```

`Application.programme_id` is `ON DELETE CASCADE`, and `FeePayment` references
`Application` with `ON DELETE CASCADE` too. Say exactly what happens and why this
schema is dangerous.

::accordion
  :::accordion-item{label="Answers to all four" icon="i-lucide-check"}
  **1.** Update: Dr Iyer's phone is in three rows; change it once and the data
  disagrees. Insert: a new subject with no enrolments cannot be recorded, nor can
  a teacher who is not yet teaching. Delete: remove row 3 and, if it were the only
  DBMS row, the subject's existence goes with it. Tables: `Student`, `Teacher`,
  `Subject`, and `Enrolment(student_id, subject_id, marks)` with a composite
  primary key, note that `teacher` belongs to `Subject`, not to the enrolment.

  **2.** Both read `left = 1`, both pass the check, both write 0, both insert.
  Two students, one seat. **Fix A:** `UPDATE Programme SET seats_left =
  seats_left - 1 WHERE programme_id = ? AND seats_left > 0` and only insert the
  allotment if one row was affected. **Fix B:** `SELECT ... FOR UPDATE` inside a
  transaction so the second clerk blocks. And in both cases add `UNIQUE
  (programme_id, student_id)` on the allotment table, because the real cause will
  be a double-clicked button.

  **3.** `LOWER(status)` is a function on the column. `YEAR(applied_on)` is
  another. And `SELECT *` with `ORDER BY score DESC` needs a sort the index
  cannot provide, so even a partial index use ends in a sort of everything.
  Rewrite:

  ```sql
  SELECT application_id, applicant_id, score, applied_on
    FROM Application
   WHERE status = 'SHORTLISTED'
     AND applied_on >= DATE '2026-01-01'
     AND applied_on <  DATE '2027-01-01'
   ORDER BY score DESC
   LIMIT 100;
  ```

  With an index on `(status, applied_on, score)` this becomes a range scan and a
  small read, and the `LIMIT` means the sort is over a bounded set.

  **4.** Deleting one programme deletes every application to it, and deleting
  those deletes every fee payment attached to them. One statement, no warning,
  and the record that money changed hands is gone. **Cascades chain**, and that
  is the danger: each individual `ON DELETE CASCADE` looked reasonable to whoever
  added it. `FeePayment` must be `ON DELETE RESTRICT`, which forces anybody
  removing a programme to deal with the money deliberately.
  :::
::

## Next

::callout{icon="i-lucide-arrow-right"}
Everything in this track was about data at rest: rows in a table, on a disk,
being arranged so they can be found. None of it says anything about the ten
seconds while your program is actually thinking. An algorithm holds data in
memory, and which shape it holds it in decides whether the answer takes a
millisecond or a fortnight.
::
