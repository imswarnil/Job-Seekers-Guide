The leaves of a B+ tree point at the rows. But where do the rows themselves
live, and in what order? In one kind of index the leaves **are** the rows; in the
other they are signposts to rows stored somewhere else. That difference decides
how many reads a lookup costs, and it is one of the most asked index questions.

## Why this matters in a job

"What is the difference between a clustered and a non-clustered index?" is asked
in most DBMS rounds, and "how many clustered indexes can a table have?" is the
quick check that follows. At work it explains real behaviour: why MySQL tables
with random UUID primary keys insert slowly, why a query that selects one extra
column suddenly gets slower, and why adding a column to an index can make a query
several times faster.

## A dictionary and a textbook index

::compare{caption="Two ways a book can help you find a word."}
  :::compare-side{label="Clustered: a dictionary" verdict="right"}
  The entries **themselves** are in alphabetical order. Find the word and you
  have found the definition: there is nowhere else to go. A book can only be
  sorted one way, so there is only one such order.
  :::
  :::compare-side{label="Non-clustered: a textbook's index" verdict="right"}
  A separate sorted list at the back, with page numbers. Find the word, then turn
  to the page: **two** steps. A book can have several such lists (a topic index,
  an author index).
  :::
::

- A **clustered index** determines the **physical order** of the table's rows:
  the table is stored inside the index, in key order. **One per table**, because
  rows can only be physically sorted one way.
- A **non-clustered (secondary) index** is a separate structure holding the
  indexed column(s) and a pointer back to each row. **Many per table.**

## How it works

### In MySQL InnoDB and SQL Server

InnoDB **always** clusters on the primary key: the table is a B+ tree whose
leaves hold the full rows, in primary-key order. A secondary index's leaves hold
the indexed value **plus the primary key**, so a secondary lookup is two tree
walks:

::flow{numbered direction="vertical" caption="SELECT * FROM Student WHERE email = 'anita@college.edu', in InnoDB."}
  :::flow-step{label="Walk the secondary index on email" icon="i-lucide-search"}
  Three or four reads to find 'anita@college.edu', whose leaf says: primary key 1.
  :::
  :::flow-step{label="Walk the clustered index on student_id" icon="i-lucide-search" highlight}
  Three or four more reads to reach row 1 and the rest of its columns. This extra
  trip is the **key lookup** (or bookmark lookup).
  :::
  :::flow-step{label="Return the row" icon="i-lucide-check"}
  Two tree walks instead of one.
  :::
::

SQL Server clusters on the primary key by default too, and lets you choose a
different clustering key (`CREATE CLUSTERED INDEX`). PostgreSQL does not
maintain clustered tables at all: the table is an unordered **heap**, every index
is secondary, and `CLUSTER` reorders it once without keeping it ordered.

```sql [sql-server-indexes.sql]
-- SQL Server
CREATE TABLE ExamResult (result_id INT PRIMARY KEY CLUSTERED, student_id INT, marks INT);
CREATE NONCLUSTERED INDEX ix_result_student ON ExamResult (student_id);
CREATE CLUSTERED INDEX ix_other ON ExamResult (marks);   -- a second clustered index
```

```text [Output (SQL Server, illustrative)]
Msg 1902: Cannot create more than one clustered index on table 'ExamResult'.
Drop the existing clustered index 'PK__ExamResult' before creating another.
```

### In SQLite, where you can see it

SQLite stores every ordinary table clustered on its hidden `rowid` (an `INTEGER
PRIMARY KEY` **is** the rowid). A secondary index stores the value and the rowid.
When an index contains **every column a query needs**, the database never visits
the table at all: a **covering index**.

::runner{lang="sql"}
```sql [covering-index.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, email TEXT, full_name TEXT, city TEXT);
INSERT INTO Student VALUES (1, 'anita@college.edu', 'Anita Rao', 'Bhopal'),
                           (2, 'rahul@college.edu', 'Rahul Verma', 'Patna');

-- Clustered: the table itself is ordered by student_id (the rowid).
EXPLAIN QUERY PLAN SELECT * FROM Student WHERE student_id = 2;

CREATE INDEX idx_email ON Student (email);

-- Secondary index, then a lookup into the table for full_name and city.
EXPLAIN QUERY PLAN SELECT full_name, city FROM Student WHERE email = 'anita@college.edu';

-- Only columns the index already holds (email, and the rowid): no table visit.
EXPLAIN QUERY PLAN SELECT student_id FROM Student WHERE email = 'anita@college.edu';

-- Widen the index to cover the query.
CREATE INDEX idx_email_name ON Student (email, full_name);
EXPLAIN QUERY PLAN SELECT full_name FROM Student WHERE email = 'anita@college.edu';
```
::

```text [Output]
QUERY PLAN
`--SEARCH Student USING INTEGER PRIMARY KEY (rowid=?)
QUERY PLAN
`--SEARCH Student USING INDEX idx_email (email=?)
QUERY PLAN
`--SEARCH Student USING COVERING INDEX idx_email (email=?)
QUERY PLAN
`--SEARCH Student USING COVERING INDEX idx_email_name (email=?)
```

`USING INTEGER PRIMARY KEY` is the clustered lookup. `USING INDEX idx_email` means
index then table. `USING COVERING INDEX` means the index alone answered it: one
tree walk, no key lookup.

## The textbook terms

University syllabuses and written tests use an older vocabulary for index types
on ordered files. Match them to what you now know:

| Term | Meaning | Today's equivalent |
| --- | --- | --- |
| **Dense index** | An index entry for **every** record | Every secondary index |
| **Sparse index** | An entry for only **some** records (one per data block); works only when the file is sorted on that key | The internal levels of a clustered index |
| **Primary index** | A sparse index on the ordering **key** field of a sorted file | Clustered index on the primary key |
| **Clustering index** | An index on the ordering field when it is **not** a key (many records per value) | Clustered index on a non-unique column |
| **Secondary index** | An index on a non-ordering field; must be dense | Non-clustered index |
| **Multilevel index** | An index on the index, repeated until it fits in one block | A B+ tree |

A file can have at most **one** primary or clustering index (it can only be
sorted one way) and **many** secondary indexes.

## Real use case

The consequence of "the table is stored in primary-key order" shows up the day
someone chooses a random UUID as the primary key of a large InnoDB table. Every
new row belongs at a random place in the clustered B+ tree, so inserts land in
random pages, pages split constantly, and the table fragments. An auto-increment
`student_id` always appends at the right-hand edge of the tree, which is why it
is the usual choice for a clustered key.

The other everyday use is the covering index. The college portal's "my results"
page runs `SELECT course_code, marks FROM ExamResult WHERE student_id = ?`
thousands of times a day in results week. An index on `(student_id,
course_code, marks)` answers it from the index alone, and removes the key lookup
from every one of those requests. The cost: a wider index, updated on every
write. That trade is worth it for a query this hot, and not for one that runs
once a month.

## What confuses people here

- **Primary key is not automatically clustered everywhere.** It is in InnoDB and
  by default in SQL Server; it is not in PostgreSQL (no clustered tables) or
  Oracle (heap tables unless you use an index-organised table).
- **Clustered is not "faster" in general.** It is faster for range scans and
  lookups on the clustering key, and it makes the choice of that key matter.
- **Non-clustered indexes in InnoDB store the primary key**, not a physical
  address. A wide primary key therefore makes every secondary index wider.
- **Covering does not mean clustered.** A covering index is any index that
  contains all the columns a query needs.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between a clustered and a non-clustered index?" icon="i-lucide-message-circle"}
  A clustered index stores the table's rows in the index's key order, so the leaf
  level is the data itself; there can be one per table. A non-clustered index is
  a separate structure of keys and pointers back to the rows; there can be many,
  and a lookup through one may need an extra trip to the table.
  :::
  :::accordion-item{label="How many clustered indexes can a table have? Why?" icon="i-lucide-message-circle"}
  One, because rows can be physically stored in only one order. A table can have
  many non-clustered indexes.
  :::
  :::accordion-item{label="Is the primary key always the clustered index?" icon="i-lucide-message-circle"}
  In MySQL InnoDB, yes. In SQL Server, by default, but you can cluster on
  another column. PostgreSQL has no maintained clustered tables, and Oracle uses
  heap tables unless you choose an index-organised table.
  :::
  :::accordion-item{label="What is a covering index?" icon="i-lucide-message-circle"}
  An index that contains every column a query needs, so the database answers from
  the index without reading the table. SQLite's plan shows `USING COVERING
  INDEX`. Built by adding the selected columns to the index.
  :::
  :::accordion-item{label="Dense vs sparse index?" icon="i-lucide-message-circle"}
  A dense index has an entry for every record; a sparse index has entries for
  only some (typically one per block) and works only on a file sorted by that
  key. Secondary indexes must be dense; a primary index can be sparse.
  :::
::
