Correctness is done: the right design and safe concurrent writes. The last thing
a DBMS promises is speed. The SQL track showed that an index turns a `SCAN` into
a `SEARCH`. This lesson is what is inside that index: a tree that finds one
student's marks among crores of rows in three or four disk reads.

## Why this matters in a job

"How does an index work internally?" is one of the most common DBMS interview
questions, and "B-tree vs B+ tree" is its standard follow-up. The honest answer
is also genuinely useful at work: once you can picture the tree, you can predict
which queries an index will help (equality, ranges, prefixes, sorting) and which
it cannot, instead of adding indexes by superstition.

## Why a tree, and why a wide one

The DSA track covered binary search trees: each node has two children, and a
balanced one finds a key in about log₂(n) steps. For 1 crore (10 million) rows
that is about 24 steps. In memory, 24 steps is nothing. On disk, each step can be
a separate **disk page read**, and a disk read is thousands of times slower than
a memory access. 24 disk reads per lookup is far too many.

The fix is to make each node **wide**. A database stores the tree in pages (often
8 KB or 16 KB), and one page can hold **hundreds** of keys. A node with 200
children instead of 2 cuts the height dramatically:

| Fan-out (children per node) | Height for 1 crore rows | Disk reads per lookup |
| --- | --- | --- |
| 2 (binary tree) | about 24 | about 24 |
| 100 | 4 (100⁴ = 10 crore) | 4 |
| 200 | 4 (200³ = 80 lakh, so one more level) | 4 |
| 500 | 3 (500³ = 12.5 crore) | 3 |

And the top one or two levels are read so often that they stay in memory, so a
lookup usually costs **one or two real disk reads**. That is why indexed lookups
barely slow down as a table grows: doubling the rows occasionally adds a level,
never doubles the work.

## How it works: the B-tree

A **B-tree of order m** is a balanced search tree where:

- every node holds up to m − 1 keys, in sorted order, and up to m child pointers;
- every node except the root is at least half full;
- **all leaves are at the same depth** (always perfectly balanced).

To search, start at the root, find which pair of keys your value falls between,
follow that pointer, and repeat until you reach a leaf.

### Inserting: nodes split, the tree grows at the top

When a new key arrives, it is placed in the right leaf. If the leaf is full, it
**splits** into two half-full leaves and the middle key moves **up** into the
parent. If the parent is full it splits too, and so on. When the root splits, a
new root is created above it: that is the only way the tree gets taller, which is
why it stays perfectly balanced. Deletes do the reverse (borrow from a sibling,
or merge).

## B-tree against B+ tree

Almost every database (MySQL InnoDB, PostgreSQL, Oracle, SQL Server, SQLite) uses
the **B+ tree** variant. The difference is where the data pointers live:

::compare{caption="Same idea, one important change."}
  :::compare-side{label="B-tree" verdict="right"}
  Keys **and** their record pointers are stored in every node, internal and
  leaf. A lookup can stop early at an internal node. Each key appears once. A
  range query must walk up and down the tree.
  :::
  :::compare-side{label="B+ tree" verdict="right"}
  Internal nodes hold **only keys** (signposts); **all** record pointers live in
  the leaves. The leaves are **linked** in order. Internal nodes fit more keys, so
  the tree is shallower, and a range query finds the first leaf and walks
  sideways.
  :::
::

| | B-tree | B+ tree |
| --- | --- | --- |
| Data pointers | In all nodes | Only in leaves |
| Keys repeated? | No | Yes, internal keys are copies of leaf keys |
| Leaves linked | No | Yes, a sorted linked list |
| Range query (`BETWEEN 60 AND 80`) | Tree traversal | Find 60, then walk the leaf list |
| Search always reaches a leaf | No | Yes, so every search costs the same |
| Used by | Some file systems, older systems | Almost every relational database |

The linked leaves are why an index helps `BETWEEN`, `>`, `<`, `ORDER BY` and
`LIKE 'Ra%'` (a prefix is a range), and not `LIKE '%Rao'` (no starting point in a
sorted list). And they are why the SQL track's "my results, newest first" query
needed no separate sort: the database read the leaves in order.

::runner{lang="sql"}
```sql [range-uses-index.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, marks INTEGER);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 20000)
INSERT INTO ExamResult (student_id, marks) SELECT i, (i * 37) % 101 FROM n;
CREATE INDEX idx_marks ON ExamResult (marks);

EXPLAIN QUERY PLAN SELECT student_id FROM ExamResult WHERE marks BETWEEN 90 AND 100;
EXPLAIN QUERY PLAN SELECT student_id FROM ExamResult ORDER BY marks DESC LIMIT 10;

SELECT COUNT(*) AS in_range FROM ExamResult WHERE marks BETWEEN 90 AND 100;
```
::

```text [Output]
QUERY PLAN
`--SEARCH ExamResult USING INDEX idx_marks (marks>? AND marks<?)
QUERY PLAN
`--SCAN ExamResult USING INDEX idx_marks

in_range
--------
2178
```

A range search and a sort, both served by walking the index's ordered leaves
(`SCAN ... USING INDEX` for the `ORDER BY` means reading the index in order, not
scanning the table), with no separate sort step.

## Why not a hash index everywhere?

A **hash index** puts each key into a bucket by a hash function, so an equality
lookup (`WHERE student_id = 48213`) is one step. But hashing scatters keys: there
is no order, so a hash index cannot do ranges, sorting or prefix `LIKE`. B+ trees
do equality in three or four steps **and** everything else. That generality is
why they are the default; PostgreSQL and MySQL's MEMORY engine offer hash indexes
for the equality-only case.

## Real use case

The cost side is where real problems come from. Every `INSERT`, `UPDATE` and
`DELETE` must also update every index on the table: find the right leaf, insert,
maybe split. A typical attendance table (one row per student per class) is
written to constantly, so every extra index slows every write.

The standard practice for a large one-time load (importing a year of attendance
from an old system) follows directly: **drop the non-essential indexes, load the
rows, rebuild the indexes once.** Building an index from sorted data in one pass
is much cheaper than updating it lakhs of times one row at a time. And an index
that no query uses is pure cost: most databases can list index usage (in
PostgreSQL, `pg_stat_user_indexes`), and removing unused ones is one of the
cheapest performance wins there is.

## What confuses people here

- **"B" does not stand for binary.** A B-tree has many children per node; a
  binary tree has two. (Nobody is sure what the B stands for: balanced, broad,
  and Bayer, one of its inventors, are all suggested.)
- **Balanced means all leaves at the same depth**, not "roughly even". Splitting
  at the top is what guarantees it.
- **The index is not the table.** It is a separate structure pointing at rows
  (except in a clustered index, where the leaves **are** the rows; that is the
  next lesson).
- **An index helps reads and costs writes.** Both halves belong in any answer.

## Interview questions

::accordion
  :::accordion-item{label="How does an index work internally?" icon="i-lucide-message-circle"}
  Usually as a B+ tree: a balanced tree of wide nodes, each a disk page holding
  hundreds of sorted keys. A lookup goes root to leaf, three or four page reads
  even for crores of rows, instead of scanning every row. Leaves hold pointers to
  rows and are linked in order for range scans.
  :::
  :::accordion-item{label="What is the difference between a B-tree and a B+ tree?" icon="i-lucide-message-circle"}
  In a B-tree, every node stores keys with data pointers. In a B+ tree, internal
  nodes store only keys and all data pointers are in the leaves, which are linked
  in order. B+ trees are shallower (more keys per internal node) and much better
  at range queries, which is why databases use them.
  :::
  :::accordion-item{label="Why are B+ trees preferred over binary search trees for databases?" icon="i-lucide-message-circle"}
  Data lives on disk, and each tree level can cost a disk read. A binary tree of
  1 crore keys is about 24 levels deep; a B+ tree with fan-out of a few hundred is
  3 or 4. Fewer levels means fewer disk reads.
  :::
  :::accordion-item{label="Why not use a hash index for everything?" icon="i-lucide-message-circle"}
  Hash indexes are excellent for equality but keep no order, so they cannot serve
  ranges, `ORDER BY` or prefix searches. A B+ tree handles equality almost as
  fast and all of those too.
  :::
  :::accordion-item{label="What happens when a B+ tree node is full and a key is inserted?" icon="i-lucide-message-circle"}
  The node splits into two half-full nodes and the middle key is pushed up into
  the parent, which may split in turn. If the root splits, a new root is created,
  so the tree grows at the top and stays balanced.
  :::
  :::accordion-item{label="What is the disadvantage of an index?" icon="i-lucide-message-circle"}
  Every write must also update the index, which slows inserts, updates and
  deletes, and each index takes disk and memory. Unused indexes are pure cost.
  :::
::
