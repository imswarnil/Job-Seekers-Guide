A precedence graph can tell you, afterwards, that a schedule was unsafe. A
database needs a mechanism that only ever **produces** safe schedules while
transactions are running. The standard one is **locking**, and locking brings a
problem of its own: two transactions each waiting for the other, forever.

## Why this matters in a job

"What is a deadlock?" is asked in both the DBMS and the operating systems rounds,
and "what is two-phase locking?" is a DBMS favourite. At work, a deadlock is an
error message you will actually see (`Deadlock found when trying to get lock` in
MySQL, `deadlock detected` in PostgreSQL), usually from two pieces of code that
update the same two tables in opposite orders. Knowing why it happened is what
lets you fix it instead of adding retries until it goes away.

## A register that one person holds at a time

Picture the exam cell's marks register. Several teachers may **read** it at once
without harm. But while one teacher is **writing** a correction, nobody else
should read it (they might see half a correction) or write it (two corrections
would clash). A lock is the rule "you must hold the register before you use
it":

| Lock | Also called | Allows | Many at once? |
| --- | --- | --- | --- |
| **Shared (S)** | Read lock | Reading | Yes, many readers together |
| **Exclusive (X)** | Write lock | Reading and writing | No, one holder, and no readers |

**Compatibility matrix**, asked by name:

| Requested ↓ / Held → | S | X |
| --- | --- | --- |
| **S** | Granted | Wait |
| **X** | Wait | Wait |

## How it works: two-phase locking

Locks alone do not guarantee serialisability: a transaction could lock A, unlock
it, then lock B, and in the gap another transaction can slip in and create a
cycle. **Two-phase locking (2PL)** adds one rule:

::flow{numbered direction="vertical" caption="2PL: all locks are acquired before any is released."}
  :::flow-step{label="Growing phase" icon="i-lucide-trending-up"}
  The transaction may acquire locks. It may not release any.
  :::
  :::flow-step{label="Lock point" icon="i-lucide-circle-dot" highlight}
  The moment it holds every lock it will ever need.
  :::
  :::flow-step{label="Shrinking phase" icon="i-lucide-trending-down"}
  It may release locks. It may not acquire any new one.
  :::
::

**Every schedule produced by 2PL is conflict serialisable**, and the equivalent
serial order is the order of the transactions' lock points. That is the theorem,
and it is why every major database uses a form of it.

The lost seat, with 2PL. Both clerks want to read then write `seats`:

::memory{kind="table" caption="T1 takes X on seats first. T2 must wait, and reads the committed 0."}
---

    cells: [{ value: "1" }, { value: "X-lock(seats), R = 1", state: "active" }, { value: "" }, { value: "1" }]

T2 waited, then saw 0 and refused the admission. The lost update is gone.

### Variants

- **Basic 2PL:** as above. Serialisable, but a transaction may release a lock
  before committing, so others can read its uncommitted data (cascading
  rollbacks possible).
- **Strict 2PL:** hold all **exclusive** locks until commit or abort. No dirty
  reads, cascadeless and strict schedules. This is what real databases do.
- **Rigorous 2PL:** hold **all** locks until commit.
- **Conservative (static) 2PL:** acquire every lock before starting. No
  deadlocks, but you must know every item in advance, which is rarely possible.

In SQL, the explicit form is `SELECT ... FOR UPDATE` (take an exclusive row lock
while reading), which the isolation levels lesson uses:

```sql [for-update.sql]
-- MySQL 8 / PostgreSQL
BEGIN;
SELECT seats_left FROM Programme WHERE programme_id = 1 FOR UPDATE;   -- X-lock the row
UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 1;
COMMIT;                                                              -- lock released
```

```text [Output (PostgreSQL 16, second session while the first is open, illustrative)]
-- the second session's SELECT ... FOR UPDATE waits here until the first COMMITs,
-- then returns seats_left = 0
```

## Deadlock

2PL makes transactions wait, and waiting can go in a circle.

T1 transfers a fee credit from Anita's account to Rahul's: it locks Anita's row,
then wants Rahul's. At the same moment T2 transfers from Rahul to Anita: it locks
Rahul's row, then wants Anita's. Each holds what the other needs.

**The four (Coffman) conditions.** A deadlock needs all four at once, so breaking
any one prevents it:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-lock" title="Mutual exclusion"}
  A resource (an X-locked row) can be held by one transaction only.
  :::
  :::feature{icon="i-lucide-hand" title="Hold and wait"}
  A transaction holds some locks while waiting for others.
  :::
  :::feature{icon="i-lucide-ban" title="No pre-emption"}
  A lock cannot be taken away; only its holder releases it.
  :::
  :::feature{icon="i-lucide-refresh-cw" title="Circular wait"}
  A cycle of transactions, each waiting for the next.
  :::
::

### Handling deadlock

| Approach | How | Cost |
| --- | --- | --- |
| **Prevention: lock ordering** | Always lock rows in the same order (lower `student_id` first) | Breaks circular wait. Free, if every code path follows it |
| **Prevention: wait-die** | Older transaction may **wait** for a younger one; a younger one requesting from an older one **dies** (aborts, restarts later with its original timestamp) | Non-pre-emptive. Young ones may die repeatedly |
| **Prevention: wound-wait** | Older transaction **wounds** (aborts) a younger holder; a younger one requesting from an older one **waits** | Pre-emptive. Fewer restarts than wait-die in practice |
| **Detection** | Build the wait-for graph periodically; on a cycle, abort one **victim** (usually the youngest or cheapest) | What MySQL InnoDB, PostgreSQL, Oracle and SQL Server actually do |
| **Timeout** | Abort any transaction waiting longer than N seconds | Simple; may abort transactions that were not deadlocked |

In both wait-die and wound-wait, "older" means the smaller timestamp (started
earlier), and the **older transaction never gets aborted**, which prevents
starvation. A way to remember: in both schemes, only the young die.

**Starvation** is a different failure: a transaction that is chosen as the victim
again and again, or keeps waiting while others get the lock. Keeping the
original timestamp on restart is how wait-die and wound-wait avoid it.

## Optimistic concurrency, and timestamp ordering

Locking is **pessimistic**: it assumes conflicts are likely and blocks early.
Two alternatives are worth knowing by name:

- **Optimistic concurrency control (validation-based):** let transactions run
  without locks, and check at commit time whether anything they read has changed
  since. If so, abort and retry. Good when conflicts are rare. Application code
  does the same with a **version column**: `UPDATE ... SET marks = 78, version =
  version + 1 WHERE result_id = 9 AND version = 4`; zero rows updated means
  someone else changed it first.
- **Timestamp ordering:** give each transaction a timestamp and allow a read or
  write only if it does not violate timestamp order; otherwise abort. No locks,
  so no deadlocks, at the cost of more aborts.
- **MVCC** (multi-version concurrency control): keep several versions of each
  row so readers see a consistent snapshot without blocking writers. PostgreSQL,
  Oracle and MySQL InnoDB all use it. The next lesson shows what it means for
  isolation levels.

## Real use case

The version-column pattern is how most web applications avoid lost updates
without holding locks while a person is looking at a form. A teacher opens
Anita's marks, a second teacher opens them too, both save:

::runner{lang="sql"}
```sql [optimistic-version.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, marks INTEGER, version INTEGER);
INSERT INTO ExamResult VALUES (9, 1, 72, 4);

-- Both teachers loaded the form when version was 4.
UPDATE ExamResult SET marks = 78, version = version + 1 WHERE result_id = 9 AND version = 4;  -- teacher 1
SELECT changes() AS teacher1_rows;

UPDATE ExamResult SET marks = 75, version = version + 1 WHERE result_id = 9 AND version = 4;  -- teacher 2
SELECT changes() AS teacher2_rows;   -- 0: someone changed it first

SELECT marks, version FROM ExamResult;
```
::

```text [Output]
teacher1_rows
-------------
1

teacher2_rows
-------------
0

marks  version
-----  -------
78     5
```

Teacher 2's save updated nothing, so the application shows "these marks were
changed by someone else, please reload" instead of silently overwriting 78 with
75. That is optimistic concurrency, in two lines of SQL.

## What confuses people here

- **2PL does not prevent deadlock.** It guarantees serialisability and can
  **cause** deadlock. Conservative 2PL is the variant that avoids it.
- **Wait-die vs wound-wait.** In both, older means smaller timestamp and only
  younger transactions are aborted. Wait-die: old waits, young dies. Wound-wait:
  old wounds young, young waits.
- **Deadlock vs starvation.** Deadlock: a cycle, nobody proceeds. Starvation:
  others proceed, one transaction never does.
- **Deadlock vs livelock.** Livelock: transactions keep aborting and retrying in
  step, all busy, none finishing.
- **Databases usually detect, not prevent.** Real systems let deadlocks happen,
  detect the cycle within about a second, and abort one transaction with an
  error your code should retry.

## Interview questions

::accordion
  :::accordion-item{label="What are shared and exclusive locks?" icon="i-lucide-message-circle"}
  A shared (read) lock lets several transactions read an item at once. An
  exclusive (write) lock lets one transaction read and write it, and blocks all
  others. S is compatible with S; X is compatible with nothing.
  :::
  :::accordion-item{label="What is two-phase locking? Why does it work?" icon="i-lucide-message-circle"}
  A transaction acquires all its locks (growing phase) before releasing any
  (shrinking phase). Every 2PL schedule is conflict serialisable, equivalent to
  the order of the transactions' lock points. Strict 2PL also holds exclusive
  locks until commit, which prevents cascading rollbacks.
  :::
  :::accordion-item{label="What is a deadlock? What are the necessary conditions?" icon="i-lucide-message-circle"}
  Two or more transactions each waiting for a lock the next one holds, in a
  cycle, so none can proceed. It needs mutual exclusion, hold and wait, no
  pre-emption and circular wait, all four.
  :::
  :::accordion-item{label="How can deadlocks be prevented or handled?" icon="i-lucide-message-circle"}
  Prevent by always locking in the same order, or with timestamp schemes
  (wait-die, wound-wait), or conservative 2PL. Or detect with a wait-for graph
  and abort a victim, which is what most databases do, or use timeouts.
  :::
  :::accordion-item{label="Wait-die vs wound-wait?" icon="i-lucide-message-circle"}
  Both use start timestamps, and only the younger transaction is ever aborted.
  Wait-die: an older requester waits; a younger requester dies. Wound-wait: an
  older requester wounds (aborts) the younger holder; a younger requester waits.
  :::
  :::accordion-item{label="Optimistic vs pessimistic concurrency control?" icon="i-lucide-message-circle"}
  Pessimistic locks before access and blocks on conflict; good when conflicts
  are frequent. Optimistic runs without locks and validates at commit (or uses a
  version column), aborting on conflict; good when conflicts are rare, such as
  two teachers rarely editing the same result.
  :::
::
