Isolation promised that concurrent transactions behave as if they ran one after
another. But a database runs hundreds at once, their operations interleaved
statement by statement. This lesson is how you tell whether a particular
interleaving is safe, and it is the part of DBMS that written tests love most.

## Why this matters in a job

Concurrency bugs are the hardest bugs to reproduce: the fee report is right a
thousand times and wrong once, when two clerks happened to click within the same
second. In interviews, "what is a lost update?", "what is a dirty read?" and
"what is serialisability?" are standard, and written tests give you a schedule
and ask "is it conflict serialisable?". The precedence graph answers that in two
minutes once you have done it three times.

::warning{icon="i-lucide-alert-triangle"}
This is one of the two places in DBMS where people memorise instead of
understand. Draw every schedule in this lesson on paper, with time going down
the page, before reading the answer.
::

## A schedule is an interleaving

A **schedule** is the order in which the operations of several transactions
actually run. Write `R1(A)` for "transaction T1 reads item A" and `W2(A)` for "T2
writes A".

- A **serial schedule** runs one transaction completely, then the next. Always
  correct, and slow: nobody else can do anything while a long transaction runs.
- A **concurrent (non-serial) schedule** interleaves them. Fast, and possibly
  wrong.
- A schedule is **serialisable** if its effect equals that of **some** serial
  schedule. That is the definition of "safe".

## How it works: three ways an interleaving goes wrong

### 1. Lost update (write, write)

One seat left in CSE. T1 and T2 are two clerks each allotting it.

  - label: "t2"
    cells: [{ value: "2" }, { value: "" }, { value: "R2(seats) = 1", state: "active" }, { value: "1" }]
  - label: "t3"
    cells: [{ value: "3" }, { value: "W1(seats) = 0" }, { value: "" }, { value: "0" }]
  - label: "t4"
    cells: [{ value: "4" }, { value: "" }, { value: "W2(seats) = 0", state: "active" }, { value: "0" }]
---
::

The runner cannot run two transactions at once, but it can replay this exact
interleaving step by step, keeping what each clerk read in its own table:

::runner{lang="sql"}
```sql [lost-update-replay.sql]
CREATE TABLE Programme (programme_id INTEGER PRIMARY KEY, seats_left INTEGER);
CREATE TABLE Admission (student_id INTEGER, programme_id INTEGER);
CREATE TABLE ClerkRead (clerk TEXT, seats_seen INTEGER);
INSERT INTO Programme VALUES (1, 1);

INSERT INTO ClerkRead SELECT 'A', seats_left FROM Programme;   -- t1: R1(seats) = 1
INSERT INTO ClerkRead SELECT 'B', seats_left FROM Programme;   -- t2: R2(seats) = 1

UPDATE Programme SET seats_left = (SELECT seats_seen FROM ClerkRead WHERE clerk = 'A') - 1;  -- t3: W1
INSERT INTO Admission VALUES (7, 1);
UPDATE Programme SET seats_left = (SELECT seats_seen FROM ClerkRead WHERE clerk = 'B') - 1;  -- t4: W2
INSERT INTO Admission VALUES (8, 1);

SELECT (SELECT seats_left FROM Programme) AS seats_left,
       (SELECT COUNT(*) FROM Admission)   AS students_admitted;
```
::

```text [Output]
seats_left  students_admitted
----------  -----------------
0           2
```

T1's write was overwritten by T2's, which was computed from a stale read. One
update is lost.

### 2. Dirty read (write, read, before commit)

T1 records a fee payment and reduces `amount_due` from ₹42,500 to 0, but has not
committed. T2, the hall-ticket job, reads 0 and issues a hall ticket. Then T1
**fails and rolls back**. T2 acted on a value that never officially existed.
Reading uncommitted data is a **dirty read**.

### 3. Unrepeatable read (read, write, read)

T1 reads Anita's marks (72) to compute a grade. T2 updates them to 78 after a
revaluation and commits. T1 reads them again for the certificate and gets 78.
The same read, twice, in one transaction, gave two answers.

A close relative, the **phantom read**, happens when a transaction runs the same
**query** twice ("students with marks above 75") and a new **row** has appeared
in between. The isolation levels lesson maps each of these to the level that
prevents it.

## Conflict serialisability

Two operations **conflict** if they are from different transactions, touch the
same item, and **at least one is a write**:

| Pair | Conflict? | Why |
| --- | --- | --- |
| R1(A), R2(A) | No | Two reads never interfere |
| R1(A), W2(A) | Yes | Read-write |
| W1(A), R2(A) | Yes | Write-read |
| W1(A), W2(A) | Yes | Write-write |
| W1(A), W2(B) | No | Different items |

A schedule is **conflict serialisable** if you can reach a serial schedule by
swapping adjacent **non-conflicting** operations. The practical test is the
precedence graph.

### The precedence graph test

::flow{numbered direction="vertical" caption="Testing a schedule for conflict serialisability."}
  :::flow-step{label="One node per transaction" icon="i-lucide-circle"}
  T1, T2, T3...
  :::
  :::flow-step{label="An edge Ti → Tj for each conflicting pair" icon="i-lucide-arrow-right"}
  Where Ti's operation comes first in the schedule.
  :::
  :::flow-step{label="Look for a cycle" icon="i-lucide-refresh-cw" highlight}
  No cycle: conflict serialisable, and a topological order of the graph is an
  equivalent serial schedule. A cycle: not conflict serialisable.
  :::
::

### Worked example 1: the lost update

S1: `R1(A), R2(A), W1(A), W2(A)`

- R1(A) before W2(A): edge **T1 → T2**
- R2(A) before W1(A): edge **T2 → T1**
- W1(A) before W2(A): edge T1 → T2

T1 → T2 and T2 → T1 is a **cycle**. Not conflict serialisable, which matches
what the replay showed: no serial order produces "two students, count fell by
one".

### Worked example 2: a safe interleaving

S2: `R1(A), W1(A), R2(A), W2(A), R1(B), W1(B), R2(B), W2(B)`

- On A: R1(A), W1(A) both come before R2(A), W2(A): edges T1 → T2.
- On B: R1(B), W1(B) both come before R2(B), W2(B): edges T1 → T2.

Only T1 → T2: **no cycle**. Conflict serialisable, equivalent to the serial
schedule **T1 then T2**, even though T2 started working on A before T1 touched B.

### Worked example 3: three transactions

S3: `R1(A), R2(B), W3(A), R2(A), W1(B)`

::code-trace{caption="Every conflicting pair, left to right."}
```text [S3.txt]
R1(A) ... W3(A)   read-write on A   T1 → T3
W3(A) ... R2(A)   write-read on A   T3 → T2
R2(B) ... W1(B)   read-write on B   T2 → T1
R1(A) ... R2(A)   both reads        no edge
```

  :::

## View serialisability, briefly

**View serialisable** is a weaker (more permissive) condition: the schedule reads
the same values and produces the same final writes as some serial schedule.
Every conflict-serialisable schedule is view serialisable; the reverse is not
true. The difference only shows up with **blind writes** (a write with no
preceding read of that item). Testing view serialisability is NP-complete, which
is why real databases enforce conflict serialisability. At fresher level, know
the definition and that relationship.

## Recoverable and cascadeless schedules

Serialisability is about the result if everything commits. These two are about
what happens when something **aborts**:

| Property | Rule | Why |
| --- | --- | --- |
| **Recoverable** | If T2 reads a value T1 wrote, T1 commits **before** T2 commits | Otherwise T2 commits a decision based on data that T1's abort erases, and it cannot be undone |
| **Cascadeless** | Transactions read only **committed** values | Otherwise one abort forces every reader to abort too: a **cascading rollback** |
| **Strict** | No read **or write** of an item until the last writer of it has committed or aborted | Makes undo a matter of restoring old values; what strict two-phase locking gives you |

Each row is stricter than the one above: strict ⊂ cascadeless ⊂ recoverable.
The dirty-read hall-ticket example is a schedule that is not even recoverable if
T2 commits first.

## Real use case

At work nobody draws precedence graphs; the database's concurrency control does
it for you. What you do is recognise the **shape** of a lost update in code:
"read a value, compute in the application, write it back". Written like that, two
requests at once lose one update. Written as a single statement, the database
does the read and write together:

::compare{caption="The same fee adjustment, two ways."}
  :::compare-side{label="Read, compute, write" verdict="wrong"}
  `SELECT amount_due` into Java, subtract the payment in Java, `UPDATE ... SET
  amount_due = ?`. Two payments at the same moment: one is lost.
  :::
  :::compare-side{label="One statement" verdict="right"}
  `UPDATE FeeAccount SET amount_due = amount_due - ? WHERE student_id = ?`. The
  read and the write happen under one lock, inside the database.
  :::
::

## What confuses people here

- **Serial is not the same as serialisable.** Serial means actually one after
  another. Serialisable means interleaved, with the same effect as some serial
  order.
- **Any serial order counts.** A schedule equivalent to T2 then T1 is every bit as
  serialisable as one equivalent to T1 then T2.
- **Reads never conflict with reads.** Only pairs with at least one write on the
  same item create edges.
- **Edge direction follows time.** The edge goes from the transaction whose
  operation came **first**.

## Interview questions

::accordion
  :::accordion-item{label="What is a schedule? Serial vs non-serial?" icon="i-lucide-message-circle"}
  The order in which operations of concurrent transactions execute. Serial: each
  transaction runs completely before the next starts. Non-serial: operations are
  interleaved. Serial is always correct and slow; non-serial is fast and must be
  checked for serialisability.
  :::
  :::accordion-item{label="What is serialisability? Why does it matter?" icon="i-lucide-message-circle"}
  A schedule is serialisable if its effect equals some serial schedule. It is
  the correctness criterion for concurrency: interleave as much as you like, as
  long as the result could have come from running them one at a time.
  :::
  :::accordion-item{label="How do you test for conflict serialisability?" icon="i-lucide-message-circle"}
  Build a precedence graph: a node per transaction, an edge Ti → Tj for every
  conflicting pair (same item, different transactions, at least one write) where
  Ti's operation is first. Acyclic means conflict serialisable, and a topological
  sort gives the equivalent serial order.
  :::
  :::accordion-item{label="Is R1(A), R2(A), W1(A), W2(A) serialisable?" icon="i-lucide-message-circle"}
  No. R1(A) before W2(A) gives T1 → T2; R2(A) before W1(A) gives T2 → T1. Cycle.
  It is the lost update.
  :::
  :::accordion-item{label="Explain lost update, dirty read and unrepeatable read." icon="i-lucide-message-circle"}
  Lost update: two transactions read the same value and both write, so one write
  is lost. Dirty read: reading another transaction's uncommitted write, which may
  be rolled back. Unrepeatable read: reading the same item twice in one
  transaction and getting different values because another transaction committed
  a change in between.
  :::
  :::accordion-item{label="What is a cascading rollback? How do you avoid it?" icon="i-lucide-message-circle"}
  When one transaction aborts and every transaction that read its uncommitted
  data must abort too. Avoided by cascadeless schedules: read only committed
  data. Strict two-phase locking guarantees this.
  :::
::
