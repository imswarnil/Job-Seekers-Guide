The design is right: every fact in one place. All of it assumed one person
writing at a time, and a server that never loses power. A **transaction** is
what makes a database safe when neither is true, and the four properties it
guarantees (ACID) are the most quoted acronym in this subject and among the least
understood.

## Why this matters in a job

The most damaging bugs in any system that handles money or records are
transaction bugs. They do not crash anything. They leave a database that is
quietly wrong (a fee taken with no receipt, a seat allotted twice) and nobody
notices until an audit. In interviews, "explain ACID" is asked in nearly every
DBMS round, followed by "give an example of each" and "draw the transaction
states". The SQL track showed the syntax (`BEGIN`, `COMMIT`, `ROLLBACK`); this
lesson is what the database promises in return.

## A transaction is a bracket

A **transaction** is a sequence of reads and writes that the database treats as
one logical unit of work. A fee payment is the classic one: reduce what the
student owes, and record the payment. Two statements, one meaning.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-atom" title="A: Atomicity"}
  All of it happens, or none of it. Never half.
  :::
  :::feature{icon="i-lucide-scale" title="C: Consistency"}
  The database moves from one valid state to another. Every rule holds before
  and after.
  :::
  :::feature{icon="i-lucide-box" title="I: Isolation"}
  Concurrent transactions do not see each other's half-finished work. The
  result is as if they ran one after another.
  :::
  :::feature{icon="i-lucide-hard-drive" title="D: Durability"}
  Once committed, it survives a crash, a power cut, a restart.
  :::
::

## How it works: each letter, by what breaks without it

### Atomicity

::runner{lang="sql"}
```sql [atomicity.sql]
CREATE TABLE FeeAccount (student_id INTEGER PRIMARY KEY, amount_due INTEGER CHECK (amount_due >= 0));
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER);
INSERT INTO FeeAccount VALUES (1, 42500);

-- The clerk types 52500 instead of 42500. The second statement will fail.
BEGIN;
INSERT INTO FeePayment (student_id, amount) VALUES (1, 52500);
UPDATE FeeAccount SET amount_due = amount_due - 52500 WHERE student_id = 1;
```
::

```text [Output]
Error: CHECK constraint failed: amount_due >= 0
```

The `UPDATE` broke the `CHECK`. Because both statements were inside one
transaction, the application issues `ROLLBACK` and the payment row disappears
with it:

::runner{lang="sql"}
```sql [atomicity-rollback.sql]
CREATE TABLE FeeAccount (student_id INTEGER PRIMARY KEY, amount_due INTEGER CHECK (amount_due >= 0));
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER);
INSERT INTO FeeAccount VALUES (1, 42500);

BEGIN;
INSERT INTO FeePayment (student_id, amount) VALUES (1, 52500);
-- the UPDATE failed here, so the application rolls back:
ROLLBACK;

SELECT (SELECT COUNT(*) FROM FeePayment) AS payments_recorded,
       (SELECT amount_due FROM FeeAccount) AS amount_due;
```
::

```text [Output]
payments_recorded  amount_due
-----------------  ----------
0                  42500
```

No payment and nothing changed: consistent, and plainly wrong to a human (the
clerk re-enters it) rather than silently wrong to everyone. Without atomicity
there would be a ₹52,500 payment on record against a student who still owes
₹42,500.

::pull-quote
Atomicity does not mean nothing goes wrong. It means the database never ends up
holding half of something.
::

### Consistency

Every constraint you declared (keys, foreign keys, `CHECK`, `NOT NULL`) is true
before the transaction and true after it. A transaction that would leave a
result pointing at a deleted student, or `amount_due` below zero, is rejected.
Consistency is partly the database's job (enforcing declared rules) and partly
yours (a transfer that debits ₹8,000 must credit ₹8,000; the database cannot know
that rule unless you write it down).

### Isolation

Two clerks run transactions at the same time. Isolation means each behaves as if
it were alone: neither sees the other's uncommitted changes, and the final
result equals **some** one-after-the-other order. Without it you get the lost
seat from the first lesson of this track. How the database achieves this
(schedules, locks) is the next two lessons; how much of it you actually get by
default (isolation levels) is the one after.

### Durability

When `COMMIT` returns, the change is on disk (or in a log on disk) and will
survive a crash one millisecond later. The database achieves this with a
**write-ahead log** (WAL): before changing the data files, it writes a record of
the change to an append-only log and forces that log to disk. After a crash, it
replays the log: committed transactions are **redone**, uncommitted ones
**undone**.

## Transaction states

A transaction moves through five states, and drawing them is a standard
question:

::flow{numbered direction="vertical" caption="The life of a transaction."}
  :::flow-step{label="Active" icon="i-lucide-play"}
  Executing its reads and writes.
  :::
  :::flow-step{label="Partially committed" icon="i-lucide-hourglass"}
  The last statement has run; changes may still be only in memory.
  :::
  :::flow-step{label="Committed" icon="i-lucide-check" highlight}
  The log record of the commit is safely on disk. Now durable.
  :::
  :::flow-step{label="Failed" icon="i-lucide-x"}
  An error, a constraint violation, or a crash stopped it (from Active or
  Partially committed).
  :::
  :::flow-step{label="Aborted" icon="i-lucide-undo-2"}
  Rolled back: every change undone. The transaction may then be restarted, or
  killed.
  :::
::

Two paths: **Active → Partially committed → Committed**, or **Active (or
Partially committed) → Failed → Aborted**. A transaction ends in exactly one of
Committed or Aborted; both are called **terminated**.

## Real use case

Seat allotment in a college counselling round is the textbook case, because it
needs all four letters at once:

::runner{lang="sql"}
```sql [seat-allotment.sql]
CREATE TABLE Programme (programme_id INTEGER PRIMARY KEY, name TEXT, seats_left INTEGER CHECK (seats_left >= 0));
CREATE TABLE Admission (student_id INTEGER PRIMARY KEY, programme_id INTEGER);
INSERT INTO Programme VALUES (1, 'B.Tech CSE', 1);

-- Student 7 accepts the last seat: two writes, one transaction.
BEGIN;
UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 1 AND seats_left > 0;
INSERT INTO Admission SELECT 7, 1 WHERE changes() = 1;   -- only if a seat was actually taken
COMMIT;

-- Student 8 tries a moment later.
BEGIN;
UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 1 AND seats_left > 0;
INSERT INTO Admission SELECT 8, 1 WHERE changes() = 1;
COMMIT;

SELECT (SELECT seats_left FROM Programme) AS seats_left,
       (SELECT GROUP_CONCAT(student_id) FROM Admission) AS admitted;
```
::

```text [Output]
seats_left  admitted
----------  --------
0           7
```

Atomicity: the seat and the admission row go together. Consistency: the `CHECK`
forbids negative seats. Isolation: the conditional `UPDATE ... WHERE seats_left >
0` means two clerks cannot both see the last seat as free (why, precisely, is the
locking lesson). Durability: once student 7's `COMMIT` returns, a power cut
cannot take the seat back.

## What confuses people here

- **Consistency in ACID is not consistency in CAP.** In ACID it means "rules
  hold". In the CAP theorem (the NoSQL lesson) it means "every reader sees the
  latest write". Same word, different idea.
- **Atomicity is not isolation.** Atomicity is about failure (all or nothing).
  Isolation is about concurrency (not seeing others' half-done work). A single
  user with no concurrency still needs atomicity.
- **Durability does not mean "written to the data file".** It means written to
  the log. The data files catch up later; the log is what recovery replays.
- **Autocommit hides all this.** In autocommit mode every statement is its own
  transaction, which is atomic, and a two-statement payment is two transactions,
  which is not.

## Interview questions

::accordion
  :::accordion-item{label="What is a transaction? Explain ACID with an example." icon="i-lucide-message-circle"}
  A logical unit of work of one or more operations. Using a fee payment (record
  the payment, reduce the amount due): Atomicity, both or neither; Consistency,
  constraints such as amount_due ≥ 0 hold after; Isolation, a clerk viewing the
  account mid-payment sees before or after, never half; Durability, once
  committed, a crash cannot undo it.
  :::
  :::accordion-item{label="Draw the transaction state diagram." icon="i-lucide-message-circle"}
  Active → Partially committed → Committed; Active or Partially committed →
  Failed → Aborted. Committed and Aborted are terminal. After abort, the
  transaction is restarted or killed.
  :::
  :::accordion-item{label="How does a DBMS ensure atomicity and durability?" icon="i-lucide-message-circle"}
  With a log (write-ahead logging). Every change is logged before it is applied;
  commit forces the log to disk. On recovery, committed transactions are redone
  from the log and uncommitted ones undone. Shadow paging is an older
  alternative.
  :::
  :::accordion-item{label="Which ACID property is the programmer's responsibility?" icon="i-lucide-message-circle"}
  Largely consistency. The DBMS enforces the constraints you declare, but only
  you know the business rules (a transfer must debit and credit the same amount),
  and your transaction must preserve them. The others are provided by the DBMS
  (atomicity and durability by recovery, isolation by concurrency control).
  :::
  :::accordion-item{label="What is the difference between commit and rollback?" icon="i-lucide-message-circle"}
  Commit makes all the transaction's changes permanent and visible; rollback
  undoes all of them. Above, after `ROLLBACK` there were no payments and the
  amount due was unchanged.
  :::
::
