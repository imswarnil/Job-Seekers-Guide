Full serialisability, with every read locked, is correct and slow. So databases
let you choose how much isolation to pay for, per transaction. Isolation is a
dial, not a switch, and where it is set by default surprises people: in no major
database is the default fully serialisable.

## Why this matters in a job

This is the most common source of "it works, but the numbers are wrong" in
anything that books, allots, reserves or counts. It is also a favourite interview
topic because it separates people who have read about transactions from people
who have been bitten. The standard question is the table below; the follow-up is
"two users book the same seat, how do you stop it?"

## Four anomalies, four levels

The anomalies from the schedules lesson, in order of nastiness:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-eye" title="Dirty read"}
  Reading another transaction's uncommitted change, which may be rolled back.
  :::
  :::feature{icon="i-lucide-repeat" title="Non-repeatable read"}
  Reading the same row twice in one transaction and getting different values,
  because someone committed a change in between.
  :::
  :::feature{icon="i-lucide-ghost" title="Phantom read"}
  Running the same `WHERE` twice and getting a different set of **rows**,
  because someone inserted or deleted a matching row.
  :::
  :::feature{icon="i-lucide-pen-line" title="Lost update"}
  Two transactions read a value, both compute from it, both write; one write is
  silently overwritten. The seat.
  :::
::

The SQL standard defines four isolation levels by which of the first three they
allow:

| Level | Dirty read | Non-repeatable read | Phantom read |
| --- | --- | --- | --- |
| **Read uncommitted** | possible | possible | possible |
| **Read committed** | prevented | possible | possible |
| **Repeatable read** | prevented | prevented | possible (by the standard) |
| **Serialisable** | prevented | prevented | prevented |

And the defaults you will actually meet:

| Database | Default level | Notes |
| --- | --- | --- |
| **MySQL (InnoDB)** | Repeatable read | Consistent snapshot per transaction; locking reads also block phantoms with gap locks |
| **PostgreSQL** | Read committed | Its repeatable read is a snapshot that also refuses concurrent updates to the same row |
| **Oracle** | Read committed | Offers only read committed and serialisable |
| **SQL Server** | Read committed | Snapshot isolation available as an option |
| **SQLite** | Serialisable | One writer at a time for the whole database |

::warning{icon="i-lucide-alert-triangle"}
Read the defaults again. At MySQL's repeatable read, and at read committed
everywhere, **a lost update is still possible** if your code reads a value,
computes in the application, and writes it back. That is not a flaw: serialisable
is expensive and most transactions do not need it. It means the protection has to
come from how you write the update.
::

## How it works: the seat, at read committed

Both clerks do exactly the right thing, inside a transaction, and it still
breaks:

::memory{kind="table" caption="One seat left. Both clerks are inside a correct transaction, and both allot it."}
---
columns: ["Clerk A", "Clerk B", "seats_left (committed)"]
frames:
  - label: "1. A begins and reads"
    cells: [{ value: "BEGIN; SELECT → 1", state: "active" }, { value: "" }, { value: "1" }]
  - label: "2. B begins and reads the same"
    cells: [{ value: "" }, { value: "BEGIN; SELECT → 1", state: "active" }, { value: "1" }]
  - label: "3. Both check in Java: 1 > 0, so both proceed"
    cells: [{ value: "if (1 > 0) allot" }, { value: "if (1 > 0) allot" }, { value: "1" }]
  - label: "4. A writes 0 and commits"
    cells: [{ value: "UPDATE = 0; COMMIT", state: "active" }, { value: "" }, { value: "0" }]
  - label: "5. B writes its own computed 0 and commits"
    cells: [{ value: "" }, { value: "UPDATE = 0; COMMIT", state: "active" }, { value: "0", state: "active" }]
---
::

Nothing was dirty, nothing rolled back, both committed successfully, and the
college has given one seat to two students.

Setting the level is one statement, which the runner's SQLite does not have (it
is always serialisable):

```sql [set-isolation.sql]
-- MySQL 8 (for the next transaction)
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- PostgreSQL (inside the transaction)
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Check the current level, MySQL 8
SELECT @@transaction_isolation;
```

```text [Output (MySQL 8, illustrative)]
+-------------------------+
| @@transaction_isolation |
+-------------------------+
| READ-COMMITTED          |
+-------------------------+
```

## Three fixes, and which one to use

### 1. Do the arithmetic in the database

The cheapest fix: remove the separate read entirely.

::runner{lang="sql"}
```sql [conditional-update.sql]
CREATE TABLE Programme (programme_id INTEGER PRIMARY KEY, seats_left INTEGER);
INSERT INTO Programme VALUES (3, 1);

-- Clerk A
UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 3 AND seats_left > 0;
SELECT 'A' AS clerk, changes() AS got_seat;

-- Clerk B, a moment later
UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 3 AND seats_left > 0;
SELECT 'B' AS clerk, changes() AS got_seat;

SELECT seats_left FROM Programme;
```
::

```text [Output]
clerk  got_seat
-----  --------
A      1

clerk  got_seat
-----  --------
B      0

seats_left
----------
0
```

The database locks the row for the duration of each `UPDATE`, so the two are
serialised by the engine. **Check the affected-row count**: 0 means you did not
get the seat, and that check is the whole fix. Code that ignores the count
throws the answer away.

### 2. Lock the row while you decide (pessimistic)

When you genuinely need to read, decide in code, and then write:

```sql [select-for-update.sql]
-- MySQL 8 / PostgreSQL
BEGIN;
SELECT seats_left FROM Programme WHERE programme_id = 3 FOR UPDATE;   -- B blocks here
-- decide in application code, safely
UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 3;
INSERT INTO Admission (student_id, programme_id) VALUES (7, 3);
COMMIT;
```

```text [Output (clerk B's session, illustrative)]
-- waits until clerk A commits, then:
 seats_left
------------
          0
```

`FOR UPDATE` takes an exclusive lock on the row as it reads. Clerk B's `SELECT`
waits instead of returning a stale 1: strict two-phase locking, requested
explicitly.

### 3. Detect the clash instead (optimistic)

A version column, checked in the `UPDATE`'s `WHERE`, as in the locking lesson.
Zero rows updated means someone changed the row since you read it; re-read and
retry. It holds no locks while a person is looking at a form.

::pros-cons
---
title: Pessimistic or optimistic
pros:
  - Pessimistic (FOR UPDATE) is simple and correct, and right when clashes are common
  - Optimistic (version column) holds no locks, so it scales far better when clashes are rare
  - Both are far better than raising the isolation level everywhere
cons:
  - Pessimistic locks block others, and a long transaction blocks them for a long time
  - Optimistic needs retry logic, and the retry must re-read rather than resend old values
  - Neither helps if the check lives only in application code and the write does not carry it
---
::

::note
`SERIALIZABLE` also prevents the lost seat, and reaching for it first is usually
wrong. It makes every transaction more expensive, and in PostgreSQL it does not
block: it aborts one transaction with a serialisation failure, so you still need
retry logic. Use it where the interleaving is too complex to reason about, not as
a default.
::

## Real use case

The bug almost never appears as "two clerks clicked at once". It appears when
someone **double-clicks** the submit button, when a phone **retries** after a
timeout, or when an import runs **twice**. All three produce two simultaneous,
identical requests, and all three are far more common than two people racing.

That is why the strongest fix is a constraint as well: one admission per student
per programme, enforced by the schema. The second insert fails loudly, whatever
the isolation level, and nothing depends on someone remembering to lock:

::runner{lang="sql"}
```sql [unique-backstop.sql]
CREATE TABLE Admission (student_id INTEGER, programme_id INTEGER, UNIQUE (student_id, programme_id));
INSERT INTO Admission VALUES (7, 3);
INSERT INTO Admission VALUES (7, 3);   -- the double-click
```
::

```text [Output]
Error: UNIQUE constraint failed: Admission.student_id, Admission.programme_id
```

## What confuses people here

- **Higher isolation is not free.** Serialisable costs throughput (more locking
  or more aborts). The default is a deliberate trade.
- **Phantoms are about rows, non-repeatable reads about values.** A new student
  appearing in "marks above 75" is a phantom; Anita's 72 becoming 78 is a
  non-repeatable read.
- **Databases differ from the standard.** The standard says repeatable read may
  allow phantoms; MySQL InnoDB largely prevents them, and PostgreSQL's
  repeatable read is snapshot isolation. Say "by the standard" and then name your
  database.
- **Lost update is not in the standard's table.** It is prevented by
  serialisable, and in practice by PostgreSQL's repeatable read, but not by MySQL's
  repeatable read with a plain read-then-write. That detail is worth knowing.

## Interview questions

::accordion
  :::accordion-item{label="What are the isolation levels in SQL?" icon="i-lucide-message-circle"}
  Read uncommitted (allows dirty reads), read committed (prevents dirty reads),
  repeatable read (also prevents non-repeatable reads), serialisable (also
  prevents phantoms; equivalent to running one at a time). Higher levels are
  safer and slower.
  :::
  :::accordion-item{label="What is the default isolation level in MySQL and PostgreSQL?" icon="i-lucide-message-circle"}
  MySQL InnoDB: repeatable read. PostgreSQL, Oracle and SQL Server: read
  committed. Neither default prevents a lost update from a read-compute-write in
  application code.
  :::
  :::accordion-item{label="What is a phantom read?" icon="i-lucide-message-circle"}
  A transaction runs the same query twice and gets a different set of rows,
  because another transaction inserted or deleted a matching row and committed in
  between. Prevented by serialisable.
  :::
  :::accordion-item{label="Two users book the last seat at the same time. How do you stop it?" icon="i-lucide-message-circle"}
  Name the bug (lost update) and that default isolation allows it. Then: a single
  conditional `UPDATE ... WHERE seats_left > 0` with the affected-row count
  checked; or `SELECT ... FOR UPDATE` when clashes are common; or a version
  column when they are rare. Add a `UNIQUE` constraint on (student, programme)
  as the backstop, because the usual cause is a double-click.
  :::
  :::accordion-item{label="Dirty read vs non-repeatable read?" icon="i-lucide-message-circle"}
  A dirty read sees another transaction's **uncommitted** change. A
  non-repeatable read sees another transaction's **committed** change between two
  reads of the same row. Read committed prevents the first, not the second.
  :::
::
