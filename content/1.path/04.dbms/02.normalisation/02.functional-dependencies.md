Every fix in the last lesson came from noticing, by eye, that one column belongs
to another: the head belongs to the department. On a table of thirty columns
that stops working. A **functional dependency** is the precise way to say "this
depends on that", and every normal form is defined in terms of them.

## Why this matters in a job

In interviews and written tests, normalisation questions are FD questions in
disguise: "given R(A, B, C, D) and these dependencies, find the candidate keys",
"which normal form is this in?", "decompose it into 3NF". Without FDs you can
only guess; with attribute closure you can answer mechanically and be right. At
work, the same thinking ("if I know the student id, do I know the department?")
is how you decide which table a new column belongs in.

## If you know this, you know that

Know a student's id, and you know their name and department: there is exactly
one of each per id. Know the department, and you know its head. But know the
department, and you do **not** know a student's name: many students share a
department. That one-way "knowing" is a functional dependency.

**X → Y** (read "X determines Y", or "Y is functionally dependent on X") means:
any two rows that agree on X must agree on Y.

| Dependency | True? | Why |
| --- | --- | --- |
| `student_id → student_name` | Yes | One name per student id |
| `student_id → department` | Yes | One department per student |
| `department → dept_head` | Yes | One head per department |
| `course_code → course_title` | Yes | One title per code |
| `{student_id, course_code} → marks` | Yes | One mark per student per course |
| `department → student_name` | **No** | CSE has many students |
| `student_id → marks` | **No** | A student has marks in many courses |

::warning{icon="i-lucide-alert-triangle"}
A functional dependency is a **rule of the domain**, not a pattern in today's
data. If today every CSE student happens to be from Bhopal, `department → city`
holds in the data and is still not a dependency. You find FDs by asking what the
college's rules are, and you can use data only to **disprove** one.
::

## Syntax: checking an FD against data

An FD `X → Y` is violated if some X value appears with more than one Y value.
That is a `GROUP BY` question:

::runner{lang="sql"}
```sql [check-fd.sql]
CREATE TABLE ResultSheet (student_id INTEGER, student_name TEXT, department TEXT, dept_head TEXT,
                          course_code TEXT, course_title TEXT, marks INTEGER);
INSERT INTO ResultSheet VALUES
  (1, 'Anita Rao',   'CSE', 'Dr. Meera Joshi', 'CS201', 'Data Structures', 87),
  (1, 'Anita Rao',   'CSE', 'Dr. Meera Joshi', 'CS202', 'DBMS',            72),
  (2, 'Rahul Verma', 'ECE', 'Dr. Suresh Rao',  'CS201', 'Data Structures', 64),
  (3, 'Priya Nair',  'CSE', 'Dr. Meera Joshi', 'CS202', 'DBMS',            91);

-- Does department -> dept_head hold? (No rows back = no violation in this data.)
SELECT department, COUNT(DISTINCT dept_head) AS heads
FROM   ResultSheet GROUP BY department HAVING COUNT(DISTINCT dept_head) > 1;

-- Does department -> student_name hold? (Rows back = violated.)
SELECT department, COUNT(DISTINCT student_name) AS names
FROM   ResultSheet GROUP BY department HAVING COUNT(DISTINCT student_name) > 1;
```
::

```text [Output]
department  names
----------  -----
CSE         2
```

The first query returned nothing, so the data does not contradict
`department → dept_head`. The second found CSE with two names, which proves
`department → student_name` false.

## Trivial, non-trivial, and Armstrong's axioms

- **Trivial FD:** Y is part of X. `{student_id, course_code} → student_id` is
  always true and tells you nothing.
- **Non-trivial:** Y is not part of X. These are the interesting ones.

From a few known FDs, others follow. **Armstrong's axioms** are the three rules
that derive every implied FD, and they are asked by name:

::feature-list{columns="3"}
  :::feature{icon="i-lucide-repeat" title="Reflexivity"}
  If Y ⊆ X, then X → Y. (The trivial ones.)
  :::
  :::feature{icon="i-lucide-plus" title="Augmentation"}
  If X → Y, then XZ → YZ. Add the same attributes to both sides.
  :::
  :::feature{icon="i-lucide-arrow-right" title="Transitivity"}
  If X → Y and Y → Z, then X → Z. `student_id → department → dept_head`.
  :::
::

Three useful rules follow from those: **union** (X → Y and X → Z give X → YZ),
**decomposition** (X → YZ gives X → Y and X → Z) and **pseudo-transitivity**
(X → Y and WY → Z give WX → Z).

## How it works: attribute closure

The **closure** of a set of attributes X, written **X⁺**, is every attribute X
determines, directly or through a chain. It is the one algorithm you need:

::flow{numbered direction="vertical" caption="Computing X⁺."}
  :::flow-step{label="Start with X itself" icon="i-lucide-play"}
  X⁺ = X.
  :::
  :::flow-step{label="Scan the FDs" icon="i-lucide-search" highlight}
  For each FD L → R, if every attribute of L is already in X⁺, add R to X⁺.
  :::
  :::flow-step{label="Repeat until nothing changes" icon="i-lucide-repeat"}
  One pass can unlock another FD, so loop until a full pass adds nothing.
  :::
::

**If X⁺ contains every attribute of R, X is a super key.** If, in addition, no
proper subset of X is a super key, X is a **candidate key**.

### Worked example 1: the result sheet

`R(student_id, student_name, department, dept_head, course_code, course_title, marks)`

FDs:
1. `student_id → student_name, department`
2. `department → dept_head`
3. `course_code → course_title`
4. `{student_id, course_code} → marks`

Compute `{student_id}⁺`: start {student_id}; FD 1 adds student_name, department;
FD 2 adds dept_head; FD 3 needs course_code (no); FD 4 needs course_code (no).
So `{student_id}⁺ = {student_id, student_name, department, dept_head}`. Not
everything: not a key.

Compute `{student_id, course_code}⁺`: FD 1 adds student_name, department; FD 2
adds dept_head; FD 3 adds course_title; FD 4 adds marks. That is **all seven**,
so it is a super key. Neither `{student_id}⁺` nor `{course_code}⁺` (=
{course_code, course_title}) is all seven, so it is minimal: **the candidate key
is {student_id, course_code}**.

### Worked example 2: letters, as a written test asks it

`R(A, B, C, D)` with `F = { A → B, B → C, C → A }`. Find every candidate key.

::code-trace{caption="Finding the candidate keys with closure."}
```text [trace.txt]
Attributes never on a right-hand side: D  →  D is in EVERY key.
{D}+    = {D}                         not a key
{A,D}+  = {A,D} → B → C = {A,B,C,D}  key, and minimal ({A}+ and {D}+ are not all)
{B,D}+  = {B,D} → C → A = {A,B,C,D}  key, minimal
{C,D}+  = {C,D} → A → B = {A,B,C,D}  key, minimal
```

  :::code-trace-step{lines="1" caption="Any attribute that no FD produces can only come from the key itself, so it must be in every candidate key. This shortcut prunes most of the search."}
  :::
  :::code-trace-step{lines="2" caption="D alone determines nothing else."}
  :::
  :::code-trace-step{lines="3-5" caption="Each of A, B, C reaches the other two through the cycle. So AD, BD and CD are all candidate keys."}
  :::
::

Candidate keys: **{A, D}, {B, D}, {C, D}**. Every attribute appears in some
candidate key.

## Prime, partial and transitive

Three words the normal forms are written in:

| Term | Meaning | In the result sheet |
| --- | --- | --- |
| **Prime attribute** | Part of **some** candidate key | `student_id`, `course_code` |
| **Non-prime attribute** | Part of **no** candidate key | `student_name`, `department`, `dept_head`, `course_title`, `marks` |
| **Partial dependency** | A non-prime attribute depends on a **proper part** of a candidate key | `student_id → student_name` (only half of the key) |
| **Transitive dependency** | A non-prime attribute depends on another non-prime attribute | `department → dept_head` (so `student_id → department → dept_head`) |

In worked example 2, every attribute is prime, which matters in the BCNF lesson.

## Real use case

When someone asks to add a column to an existing table, the FD question decides
where it goes. The placement cell asks to add `company_hr_email` to the
`Placement(placement_id, student_id, company, package_lpa)` table. Ask: what
determines an HR email? Not the placement: the **company**. `company →
company_hr_email` would be a transitive dependency (placement_id → company →
hr_email), so the column belongs in a `Company` table, and `Placement` should
hold a `company_id`. Asking "what does this column depend on?" before adding it
is the everyday form of this whole lesson.

::runner{lang="sql"}
```sql [where-does-it-go.sql]
CREATE TABLE Company   (company_id INTEGER PRIMARY KEY, name TEXT UNIQUE, hr_email TEXT);
CREATE TABLE Placement (placement_id INTEGER PRIMARY KEY, student_id INTEGER,
                        company_id INTEGER REFERENCES Company, package_lpa REAL);
INSERT INTO Company VALUES (1, 'Infosys', 'campus@infosys.example'), (2, 'Accenture', 'hiring@accenture.example');
INSERT INTO Placement VALUES (1, 1, 1, 3.6), (2, 3, 2, 4.5), (3, 5, 1, 3.6);

-- The HR email changes once, in one row, for every placement.
UPDATE Company SET hr_email = 'freshers@infosys.example' WHERE name = 'Infosys';

SELECT p.student_id, c.name, c.hr_email
FROM   Placement p JOIN Company c ON c.company_id = p.company_id
ORDER BY p.student_id;
```
::

```text [Output]
student_id  name       hr_email
----------  ---------  ------------------------
1           Infosys    freshers@infosys.example
3           Accenture  hiring@accenture.example
5           Infosys    freshers@infosys.example
```

## What confuses people here

- **Direction matters.** `student_id → department` is true;
  `department → student_id` is false. An FD is not symmetric.
- **FDs come from rules, not from rows.** Data can disprove an FD, never prove
  one.
- **A candidate key is minimal, not smallest.** {A, D} and a hypothetical
  {B, C, E} can both be candidate keys; minimal means no attribute can be
  removed, not "fewest attributes overall".
- **Closure is of attributes, not of FDs.** There is also a closure of an FD set
  (F⁺, every implied FD), which is huge; exams almost always want attribute
  closure (X⁺).

## Interview questions

::accordion
  :::accordion-item{label="What is a functional dependency?" icon="i-lucide-message-circle"}
  X → Y means any two tuples that agree on X must agree on Y: X determines Y.
  `student_id → department` holds because each student is in one department.
  It is a rule of the domain; data can only disprove it.
  :::
  :::accordion-item{label="What are Armstrong's axioms?" icon="i-lucide-message-circle"}
  Reflexivity (if Y ⊆ X then X → Y), augmentation (X → Y gives XZ → YZ) and
  transitivity (X → Y and Y → Z give X → Z). They are sound and complete: they
  derive exactly the FDs that are implied. Union, decomposition and
  pseudo-transitivity follow from them.
  :::
  :::accordion-item{label="What is the closure of an attribute set? How do you use it to find keys?" icon="i-lucide-message-circle"}
  X⁺ is every attribute determined by X. Start with X and keep adding the
  right-hand side of any FD whose left-hand side is inside X⁺. If X⁺ is all
  attributes, X is a super key; if no proper subset is, it is a candidate key.
  :::
  :::accordion-item{label="R(A, B, C, D, E) with A → B, B → C and CD → E. Find the candidate key." icon="i-lucide-message-circle"}
  A and D never appear on a right-hand side, so both are in every key.
  {A, D}⁺: A gives B, B gives C, CD gives E, so {A, B, C, D, E}: all. Neither
  {A}⁺ = {A, B, C} nor {D}⁺ = {D} is all, so **AD** is the only candidate key.
  :::
  :::accordion-item{label="What is the difference between a partial and a transitive dependency?" icon="i-lucide-message-circle"}
  Partial: a non-prime attribute depends on part of a composite candidate key
  (`student_id → student_name` when the key is {student_id, course_code}). It
  breaks 2NF. Transitive: a non-prime attribute depends on another non-prime
  attribute (`department → dept_head`). It breaks 3NF.
  :::
  :::accordion-item{label="What is a prime attribute?" icon="i-lucide-message-circle"}
  An attribute that belongs to at least one candidate key. In R(A, B, C, D) with
  A → B, B → C, C → A, the candidate keys are AD, BD and CD, so all four are
  prime.
  :::
::
