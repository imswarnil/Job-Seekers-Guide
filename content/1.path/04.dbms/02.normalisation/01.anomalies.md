Keys pin every row down. But a table with perfect keys can still store the same
fact many times, and when that fact changes, the copies disagree. The problems
that follow have names (update, insertion and deletion anomalies), and removing
them is the whole purpose of **normalisation**.

## Why this matters in a job

The design question in interviews ("how would you model this?", or "what is
wrong with this table?") is really asking whether you can spot a duplicated fact.
In DBMS vivas, "what is normalisation and why do we need it?" is asked almost as
often as ACID, and the answer interviewers want is the anomalies, not the list of
normal forms. I learned the forms as definitions first and could recite them
without being able to apply one. Starting from the problems is what made them
make sense.

## One wide table

Here is how an exam cell might keep results if nobody had designed anything: one
row per student per course, with everything about both copied in.

::runner{lang="sql"}
```sql [wide-table.sql]
CREATE TABLE ResultSheet (
  student_id INTEGER, student_name TEXT, department TEXT, dept_head TEXT,
  course_code TEXT, course_title TEXT, marks INTEGER,
  PRIMARY KEY (student_id, course_code)
);
INSERT INTO ResultSheet VALUES
  (1, 'Anita Rao',   'CSE', 'Dr. Meera Joshi', 'CS201', 'Data Structures', 87),
  (1, 'Anita Rao',   'CSE', 'Dr. Meera Joshi', 'CS202', 'DBMS',            72),
  (2, 'Rahul Verma', 'ECE', 'Dr. Suresh Rao',  'CS201', 'Data Structures', 64),
  (3, 'Priya Nair',  'CSE', 'Dr. Meera Joshi', 'CS202', 'DBMS',            91);

SELECT * FROM ResultSheet;
```
::

```text [Output]
student_id  student_name  department  dept_head        course_code  course_title     marks
----------  ------------  ----------  ---------------  -----------  ---------------  -----
1           Anita Rao     CSE         Dr. Meera Joshi  CS201        Data Structures  87
1           Anita Rao     CSE         Dr. Meera Joshi  CS202        DBMS             72
2           Rahul Verma   ECE         Dr. Suresh Rao   CS201        Data Structures  64
3           Priya Nair    CSE         Dr. Meera Joshi  CS202        DBMS             91
```

The key is `(student_id, course_code)` and it works: no two rows share it. And
yet "the head of CSE is Dr. Meera Joshi" is stored three times, "CS201 is Data
Structures" twice, and "Anita is in CSE" twice. Each copy is a future
disagreement.

## The three anomalies

::feature-list{columns="3"}
  :::feature{icon="i-lucide-pencil" title="Update anomaly"}
  Changing one fact means changing many rows. Miss one and the data contradicts
  itself.
  :::
  :::feature{icon="i-lucide-plus" title="Insertion anomaly"}
  You cannot record one fact without inventing another.
  :::
  :::feature{icon="i-lucide-trash-2" title="Deletion anomaly"}
  Deleting one fact destroys an unrelated one.
  :::
::

## How it works: each anomaly, shown

### Update anomaly

Dr. Meera Joshi retires and Dr. Vikram Singh becomes head of CSE. The clerk
updates the rows for the CS201 exam and forgets the rest:

::runner{lang="sql"}
```sql [update-anomaly.sql]
CREATE TABLE ResultSheet (student_id INTEGER, student_name TEXT, department TEXT, dept_head TEXT,
  course_code TEXT, course_title TEXT, marks INTEGER, PRIMARY KEY (student_id, course_code));
INSERT INTO ResultSheet VALUES
  (1, 'Anita Rao', 'CSE', 'Dr. Meera Joshi', 'CS201', 'Data Structures', 87),
  (1, 'Anita Rao', 'CSE', 'Dr. Meera Joshi', 'CS202', 'DBMS', 72),
  (2, 'Rahul Verma', 'ECE', 'Dr. Suresh Rao', 'CS201', 'Data Structures', 64),
  (3, 'Priya Nair', 'CSE', 'Dr. Meera Joshi', 'CS202', 'DBMS', 91);

UPDATE ResultSheet SET dept_head = 'Dr. Vikram Singh'
WHERE  department = 'CSE' AND course_code = 'CS201';

-- Who is the head of CSE?
SELECT DISTINCT dept_head FROM ResultSheet WHERE department = 'CSE';
```
::

```text [Output]
dept_head
----------------
Dr. Vikram Singh
Dr. Meera Joshi
```

Two answers to a question that has one. Nothing failed; the data is
inconsistent now.

### Insertion anomaly

The college starts a Civil department with a new head. No student has taken an
exam in it yet. Where does the fact "the head of Civil is Dr. Nitin Gupta" go?

::runner{lang="sql"}
```sql [insertion-anomaly.sql]
CREATE TABLE ResultSheet (student_id INTEGER NOT NULL, student_name TEXT, department TEXT, dept_head TEXT,
  course_code TEXT NOT NULL, course_title TEXT, marks INTEGER, PRIMARY KEY (student_id, course_code));

-- There is no student and no course to put in the key.
INSERT INTO ResultSheet (department, dept_head) VALUES ('Civil', 'Dr. Nitin Gupta');
```
::

```text [Output]
Error: NOT NULL constraint failed: ResultSheet.student_id
```

The key is `(student_id, course_code)` and neither can be `NULL`. You cannot
store a department until a student in it sits an exam, so you would have to
invent a fake student. That is the insertion anomaly.

### Deletion anomaly

Rahul, the only ECE student in the sheet, leaves. His row is deleted:

::runner{lang="sql"}
```sql [deletion-anomaly.sql]
CREATE TABLE ResultSheet (student_id INTEGER, student_name TEXT, department TEXT, dept_head TEXT,
  course_code TEXT, course_title TEXT, marks INTEGER, PRIMARY KEY (student_id, course_code));
INSERT INTO ResultSheet VALUES
  (1, 'Anita Rao', 'CSE', 'Dr. Meera Joshi', 'CS201', 'Data Structures', 87),
  (1, 'Anita Rao', 'CSE', 'Dr. Meera Joshi', 'CS202', 'DBMS', 72),
  (2, 'Rahul Verma', 'ECE', 'Dr. Suresh Rao', 'CS201', 'Data Structures', 64),
  (3, 'Priya Nair', 'CSE', 'Dr. Meera Joshi', 'CS202', 'DBMS', 91);

DELETE FROM ResultSheet WHERE student_id = 2;

-- Who heads ECE now?
SELECT COUNT(*) AS rows_about_ece FROM ResultSheet WHERE department = 'ECE';
```
::

```text [Output]
rows_about_ece
--------------
0
```

Deleting a student deleted the only record that ECE exists and who runs it. Two
unrelated facts shared a row, so they died together.

## What normalisation does

**Normalisation** is splitting a table into smaller tables so that each fact is
stored exactly once, which removes all three anomalies. The same data, split:

::runner{lang="sql"}
```sql [normalised.sql]
CREATE TABLE Department (department TEXT PRIMARY KEY, dept_head TEXT);
CREATE TABLE Student    (student_id INTEGER PRIMARY KEY, student_name TEXT, department TEXT REFERENCES Department);
CREATE TABLE Course     (course_code TEXT PRIMARY KEY, course_title TEXT);
CREATE TABLE Result     (student_id INTEGER, course_code TEXT, marks INTEGER, PRIMARY KEY (student_id, course_code));

INSERT INTO Department VALUES ('CSE', 'Dr. Meera Joshi'), ('ECE', 'Dr. Suresh Rao'), ('Civil', 'Dr. Nitin Gupta');
INSERT INTO Student VALUES (1, 'Anita Rao', 'CSE'), (2, 'Rahul Verma', 'ECE'), (3, 'Priya Nair', 'CSE');
INSERT INTO Course VALUES ('CS201', 'Data Structures'), ('CS202', 'DBMS');
INSERT INTO Result VALUES (1, 'CS201', 87), (1, 'CS202', 72), (2, 'CS201', 64), (3, 'CS202', 91);

UPDATE Department SET dept_head = 'Dr. Vikram Singh' WHERE department = 'CSE';   -- one row
DELETE FROM Result WHERE student_id = 2;                                          -- ECE survives

-- The original sheet, rebuilt with joins.
SELECT s.student_id, s.student_name, d.department, d.dept_head, c.course_code, c.course_title, r.marks
FROM   Result r
JOIN   Student s    ON s.student_id  = r.student_id
JOIN   Department d ON d.department  = s.department
JOIN   Course c     ON c.course_code = r.course_code;

SELECT * FROM Department;
```
::

```text [Output]
student_id  student_name  department  dept_head         course_code  course_title     marks
----------  ------------  ----------  ----------------  -----------  ---------------  -----
1           Anita Rao     CSE         Dr. Vikram Singh  CS201        Data Structures  87
1           Anita Rao     CSE         Dr. Vikram Singh  CS202        DBMS             72
3           Priya Nair    CSE         Dr. Vikram Singh  CS202        DBMS             91

department  dept_head
----------  ----------------
CSE         Dr. Vikram Singh
ECE         Dr. Suresh Rao
Civil       Dr. Nitin Gupta
```

The head changed in one row and every result shows it. Civil exists with no
students. Rahul's result is gone and ECE is still there. The next three lessons
turn this intuition into rules: functional dependencies, then 1NF, 2NF, 3NF and
BCNF.

## The rule every split must obey: lossless join

Splitting is only safe if joining the pieces gives back **exactly** the original
rows: no rows lost, and none invented. That is a **lossless-join**
decomposition. Split on the wrong column and the join invents rows that were
never there, called **spurious tuples**:

::runner{lang="sql"}
```sql [lossy-split.sql]
CREATE TABLE ResultSheet (student_id INTEGER, department TEXT, course_code TEXT, marks INTEGER);
INSERT INTO ResultSheet VALUES (1, 'CSE', 'CS201', 87), (3, 'CSE', 'CS202', 91);

-- A bad split: the only shared column is department, which identifies nothing.
CREATE TABLE PartA AS SELECT student_id, department FROM ResultSheet;
CREATE TABLE PartB AS SELECT department, course_code, marks FROM ResultSheet;

SELECT a.student_id, a.department, b.course_code, b.marks
FROM   PartA a JOIN PartB b ON b.department = a.department
ORDER BY a.student_id, b.course_code;
```
::

```text [Output]
student_id  department  course_code  marks
----------  ----------  -----------  -----
1           CSE         CS201        87
1           CSE         CS202        91
3           CSE         CS201        87
3           CSE         CS202        91
```

Two rows went in and four came back: student 1 now appears to have scored 91 in
CS202 and student 3 87 in CS201, and neither happened. The rule that prevents this: **the shared columns
must be a key of at least one of the pieces.** In the good split above, `Result`
and `Student` share `student_id`, which is `Student`'s key, so nothing can be
invented. The BCNF lesson states this formally.

## Real use case

In most real systems you meet this in reverse: someone has built a wide table
(often an export turned into a table, or a spreadsheet imported "for now") and
reports start disagreeing with each other. The fix is always the same sequence:
find the fact stored more than once, give it a table of its own keyed on what it
depends on, and replace the copies with a foreign key. The dependency analysis in
the next lesson is how you find those facts systematically instead of by eye.

## What confuses people here

- **Duplication is not the same as redundancy.** The student id appearing in
  many result rows is not a problem: it is a reference, and changing it is not a
  normal operation. The student's **name** appearing many times is the problem,
  because it is a fact that can change.
- **Normalisation is not "more tables is better".** It removes anomalies at the
  cost of joins. The last lesson of this chapter covers when to deliberately
  denormalise.
- **Not every split is safe.** A split must be lossless, and ideally
  dependency-preserving; "split until every table has two columns" loses
  information.

## Interview questions

::accordion
  :::accordion-item{label="What is normalisation? Why is it needed?" icon="i-lucide-message-circle"}
  Organising tables so each fact is stored once, by decomposing a table along its
  dependencies. It removes the update, insertion and deletion anomalies and
  reduces redundancy. Give one example of each anomaly on a real table.
  :::
  :::accordion-item{label="What are the update, insertion and deletion anomalies?" icon="i-lucide-message-circle"}
  Update: changing a fact means changing many rows, and missing one makes the
  data inconsistent (two heads of CSE). Insertion: you cannot store a fact
  without another (a department with no students). Deletion: deleting one fact
  removes another (the last ECE student takes ECE with him).
  :::
  :::accordion-item{label="What is a lossless-join decomposition?" icon="i-lucide-message-circle"}
  A split of a table into two whose natural join gives back exactly the original
  rows. It is lossless if the common attributes are a key (super key) of at least
  one of the two pieces. Otherwise the join can produce spurious tuples.
  :::
  :::accordion-item{label="What is a spurious tuple?" icon="i-lucide-message-circle"}
  A row produced by joining the pieces of a lossy decomposition that was never in
  the original table. Above, splitting on `department` made Anita appear to have
  scored 91 in CS202.
  :::
  :::accordion-item{label="Does normalisation have disadvantages?" icon="i-lucide-message-circle"}
  More tables means more joins for reads, which can be slower for read-heavy
  reports. That is why reporting tables are sometimes denormalised deliberately,
  with the cost of keeping copies consistent.
  :::
::
