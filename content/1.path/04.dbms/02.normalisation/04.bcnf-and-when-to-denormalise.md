3NF allows one exception: a dependency whose right-hand side is a prime
attribute. It sounds harmless, and it still lets a fact be stored twice.
**BCNF** (Boyce-Codd normal form) closes that gap, at a price you should be able
to name.

## Why this matters in a job

"What is the difference between 3NF and BCNF?" is the follow-up that separates
candidates who understood normalisation from those who memorised three
definitions. Written tests ask "is this relation in BCNF?" with a set of FDs. At
work, the more useful half of this lesson is the second: knowing when a design
should deliberately **not** be fully normalised, and saying why.

## The one rule: every determinant is a key

**BCNF:** for every non-trivial functional dependency X → Y, **X is a super
key**. No exceptions.

Compare with 3NF: "for every non-trivial X → A, X is a super key **or A is
prime**". BCNF drops the "or A is prime". So every BCNF table is in 3NF, and a
3NF table fails BCNF only when some non-key determines a **prime** attribute.
That only happens when a table has **overlapping composite candidate keys**,
which is why it is rare and why interviewers love it.

## How it works: a table in 3NF and not in BCNF

The college runs popular courses in several sections, each taught by a
different faculty member. The rules:

- A student takes a course in exactly one section, so `{student_id, course} →
  faculty`.
- Each faculty member teaches exactly one course, so `faculty → course`.

`Teaching(student_id, course, faculty)`:

::runner{lang="sql"}
```sql [teaching.sql]
CREATE TABLE Teaching (student_id INTEGER, course TEXT, faculty TEXT,
                       PRIMARY KEY (student_id, course));
INSERT INTO Teaching VALUES
  (1, 'DBMS', 'Vikram Singh'),
  (2, 'DBMS', 'Kavita Sharma'),
  (3, 'DBMS', 'Vikram Singh'),
  (1, 'Data Structures', 'Rohit Kumar'),
  (2, 'Data Structures', 'Rohit Kumar');

-- "Vikram Singh teaches DBMS" is stored once per student he teaches.
SELECT faculty, course, COUNT(*) AS times_stored
FROM   Teaching GROUP BY faculty, course ORDER BY times_stored DESC;
```
::

```text [Output]
faculty        course           times_stored
-------------  ---------------  ------------
Rohit Kumar    Data Structures  2
Vikram Singh   DBMS             2
Kavita Sharma  DBMS             1
```

### Find the keys

Using closure:

- `{student_id, course}⁺` = {student_id, course, faculty}: all. Candidate key.
- `{student_id, faculty}⁺`: faculty → course, so {student_id, faculty, course}:
  all. Also a candidate key.
- `{student_id}⁺` = {student_id}; `{faculty}⁺` = {faculty, course}. Neither is a
  key alone.

Candidate keys: **{student_id, course}** and **{student_id, faculty}**. They
overlap on `student_id`. Every attribute is in some candidate key, so **every
attribute is prime**.

### Check each normal form

- **2NF, 3NF:** there are no non-prime attributes at all, so there can be no
  partial or transitive dependency of a non-prime attribute. **In 3NF.**
- **BCNF:** `faculty → course`, and `faculty` is **not** a super key. **Not in
  BCNF.** The fact "Vikram teaches DBMS" is stored twice, and if he switches to
  another course, two rows must change: the update anomaly, back again.

### Decompose

Split on the violating FD, `faculty → course`: put `faculty` and what it
determines in one table, and `faculty` with the rest in the other:

- `FacultyCourse(faculty, course)`: key `faculty`
- `StudentFaculty(student_id, faculty)`: key `{student_id, faculty}`

Both are in BCNF (the only FD in each has a key on the left). The split is
**lossless**: the shared attribute `faculty` is the key of `FacultyCourse`.

::runner{lang="sql"}
```sql [bcnf-split.sql]
CREATE TABLE FacultyCourse  (faculty TEXT PRIMARY KEY, course TEXT NOT NULL);
CREATE TABLE StudentFaculty (student_id INTEGER, faculty TEXT REFERENCES FacultyCourse,
                             PRIMARY KEY (student_id, faculty));
INSERT INTO FacultyCourse VALUES ('Vikram Singh', 'DBMS'), ('Kavita Sharma', 'DBMS'), ('Rohit Kumar', 'Data Structures');
INSERT INTO StudentFaculty VALUES (1, 'Vikram Singh'), (2, 'Kavita Sharma'), (3, 'Vikram Singh'),
                                  (1, 'Rohit Kumar'), (2, 'Rohit Kumar');

-- Lossless: the join gives back exactly the original five rows.
SELECT sf.student_id, fc.course, sf.faculty
FROM   StudentFaculty sf JOIN FacultyCourse fc ON fc.faculty = sf.faculty
ORDER BY fc.course, sf.student_id;

-- The cost: nothing now stops student 1 being given a second DBMS faculty.
INSERT INTO StudentFaculty VALUES (1, 'Kavita Sharma');
SELECT sf.student_id, fc.course, COUNT(*) AS sections
FROM   StudentFaculty sf JOIN FacultyCourse fc ON fc.faculty = sf.faculty
GROUP BY sf.student_id, fc.course HAVING COUNT(*) > 1;
```
::

```text [Output]
student_id  course           faculty
----------  ---------------  -------------
1           DBMS             Vikram Singh
2           DBMS             Kavita Sharma
3           DBMS             Vikram Singh
1           Data Structures  Rohit Kumar
2           Data Structures  Rohit Kumar

student_id  course  sections
----------  ------  --------
1           DBMS    2
```

## The trade-off: lossless against dependency-preserving

A good decomposition has two properties:

| Property | Means | Test |
| --- | --- | --- |
| **Lossless join** | Joining the pieces gives back exactly the original, no spurious rows | The shared attributes are a super key of at least one piece |
| **Dependency preserving** | Every original FD can be checked inside a single piece, without a join | Each FD's attributes all sit in one of the new tables |

The BCNF split above is lossless and **not** dependency-preserving:
`{student_id, course} → faculty` spans both tables, so no single table's key
enforces "one section per course per student". The last query shows the result:
student 1 now has two DBMS sections, and nothing refused it.

::compare{caption="What each normal form can always guarantee."}
  :::compare-side{label="3NF" verdict="right"}
  A decomposition that is **both** lossless and dependency-preserving always
  exists. Some redundancy may remain.
  :::
  :::compare-side{label="BCNF" verdict="right"}
  A **lossless** decomposition always exists; dependency preservation is **not**
  guaranteed. No redundancy from FDs remains.
  :::
::

That is why many designers stop at 3NF when BCNF would lose a dependency, and
enforce the lost rule another way (a trigger, or application code). Saying this
in an interview is what "understood, not memorised" sounds like.

## Beyond BCNF, in one line each

- **4NF** removes **multi-valued dependencies**: a student's hobbies and a
  student's phone numbers stored in one table produce every combination of the
  two. Split them into two tables.
- **5NF** (project-join normal form) removes **join dependencies**: a table that
  can only be rebuilt losslessly from three or more pieces.

At fresher level, knowing they exist and what 4NF is about is enough. Almost
every real design stops at 3NF or BCNF.

## Real use case: denormalising on purpose

Normalising is not a virtue in itself. More tables means more joins, and a
dashboard doing six joins on every page load is slower than one reading a
single wide row. So real systems sometimes store a fact twice **on purpose**:

::pros-cons
---
title: Denormalising deliberately
pros:
  - A read-heavy dashboard avoids several joins per request
  - Reporting tables rebuilt every night are a normal, sensible pattern
  - Some values must be frozen as they were at a moment in time
cons:
  - Two copies of a fact will diverge; the only question is when
  - You now own keeping them in step, on every write path, forever
  - It is usually premature. Normalise first, measure, then denormalise the one thing that needs it
---
::

The case that is **not** denormalisation at all, and the one most often got wrong
more than any other: a fee receipt must store the amount charged **at the time
of payment**, not point at the course's current fee. The fee will change next
year and the receipt must not.

::runner{lang="sql"}
```sql [frozen-fee.sql]
CREATE TABLE Programme (programme_id INTEGER PRIMARY KEY, name TEXT, annual_fee INTEGER);
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, programme_id INTEGER,
                         amount_charged INTEGER, paid_on TEXT);   -- the fee THEN, stored on purpose
INSERT INTO Programme VALUES (1, 'B.Tech CSE', 85000);
INSERT INTO FeePayment VALUES (1, 1, 1, 85000, '2024-07-10');

UPDATE Programme SET annual_fee = 92000 WHERE programme_id = 1;   -- next year's fee

SELECT f.payment_id, f.amount_charged AS on_receipt, p.annual_fee AS current_fee
FROM   FeePayment f JOIN Programme p ON p.programme_id = f.programme_id;
```
::

```text [Output]
payment_id  on_receipt  current_fee
----------  ----------  -----------
1           85000       92000
```

"The fee then" and "the fee now" are different facts, so storing both is
correct normalisation, not a violation of it. Invoices, marks awarded and salary
history all work the same way.

## What confuses people here

- **BCNF is not "3NF but stricter everywhere".** The two differ only when a
  table has overlapping composite candidate keys. Most 3NF tables you design are
  already in BCNF.
- **"Every determinant is a candidate key"** is the common phrasing; strictly it
  is "a super key", which includes candidate keys.
- **Lossless is compulsory; dependency preservation is desirable.** Never give up
  losslessness. Dependency preservation you may trade for BCNF, knowingly.

## Interview questions

::accordion
  :::accordion-item{label="What is BCNF? How is it different from 3NF?" icon="i-lucide-message-circle"}
  A relation is in BCNF if for every non-trivial FD X → Y, X is a super key. 3NF
  also allows X → Y when Y is a prime attribute. So BCNF is stricter, and the two
  differ only when there are overlapping composite candidate keys.
  :::
  :::accordion-item{label="Give an example of a table in 3NF but not in BCNF." icon="i-lucide-message-circle"}
  Teaching(student_id, course, faculty) with {student_id, course} → faculty and
  faculty → course. Candidate keys {student_id, course} and {student_id,
  faculty}; all attributes prime, so 3NF. faculty → course has a non-key
  determinant, so not BCNF. Decompose into (faculty, course) and (student_id,
  faculty).
  :::
  :::accordion-item{label="What is a lossless decomposition? How do you test it?" icon="i-lucide-message-circle"}
  One whose natural join reproduces the original exactly. For a split into R1 and
  R2, it is lossless if R1 ∩ R2 → R1 or R1 ∩ R2 → R2 (the common attributes are a
  super key of one side).
  :::
  :::accordion-item{label="What is dependency preservation? Is it always possible with BCNF?" icon="i-lucide-message-circle"}
  Every original FD can be enforced within one of the decomposed tables. BCNF
  cannot always preserve dependencies (the Teaching example loses
  {student_id, course} → faculty); 3NF always can. That is the reason to stop at
  3NF sometimes.
  :::
  :::accordion-item{label="What is denormalisation? When would you do it?" icon="i-lucide-message-circle"}
  Deliberately storing redundant data to speed up reads, for example a
  pre-joined reporting table rebuilt nightly. Do it after measuring a real
  performance problem, and accept that you must keep the copies consistent.
  :::
  :::accordion-item{label="What are 4NF and 5NF?" icon="i-lucide-message-circle"}
  4NF removes multi-valued dependencies (independent multi-valued facts about the
  same key, like hobbies and phone numbers, in one table). 5NF removes join
  dependencies. Both are rare in practice.
  :::
::
