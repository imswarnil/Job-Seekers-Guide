The interview bank was questions. The design round is different: a paragraph and
a blank page. This page starts with exactly that, then eight shorter problems,
one per chapter. Do each with pen and paper first; drawing boxes and arrows by
hand is faster than typing, and it is what you will be asked to do on a
whiteboard.

## The brief

::callout{icon="i-lucide-file-text" color="neutral"}
The college runs a placement cell. Companies register and visit campus for a
drive. A drive is open to one or more departments, and has a date and a minimum
CGPA. Students apply to drives; a student may apply to many drives, and a drive
receives many applications. Each application goes through rounds (aptitude,
technical, HR), and each round has a result and a date. A student who gets an
offer has a package and a joining date, and a student may hold more than one
offer. The placement officer needs, for any department and year: how many
students were placed, the highest and average package, and which companies made
the most offers.
::

::flow{numbered direction="vertical" caption="The order to work in, and to say out loud in an interview."}
  :::flow-step{label="Underline the nouns" icon="i-lucide-spell-check"}
  Company, drive, department, student, application, round, offer. Each is
  probably an entity.
  :::
  :::flow-step{label="Relationships and cardinality" icon="i-lucide-git-fork"}
  Drive to department is M:N (junction table). Student to drive is M:N through
  Application. Application to round is 1:N. Application to offer is 1:1 or 1:0.
  :::
  :::flow-step{label="A key for each, and test it" icon="i-lucide-key"}
  Surrogate keys, with the permanence test said out loud for at least one.
  :::
  :::flow-step{label="Facts that must be frozen" icon="i-lucide-snowflake" highlight}
  The package on an offer. The minimum CGPA of the drive as it was. Not
  pointers to current values.
  :::
  :::flow-step{label="Name the constraints as you draw" icon="i-lucide-shield"}
  One application per student per drive; round results from a fixed set; a
  package above zero.
  :::
  :::flow-step{label="Then the indexes the questions need" icon="i-lucide-list-tree"}
  The officer's three questions say which columns get filtered and grouped.
  :::
::

::accordion
  :::accordion-item{label="One answer, built and queried" icon="i-lucide-check"}
  ::::runner{lang="sql"}
  ```sql [placement-design.sql]
  PRAGMA foreign_keys = ON;
  CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE);
  CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT NOT NULL,
                        department_id INTEGER NOT NULL REFERENCES Department, batch_year INTEGER NOT NULL);
  CREATE TABLE Company (company_id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE);
  CREATE TABLE Drive (drive_id INTEGER PRIMARY KEY,
                      company_id INTEGER NOT NULL REFERENCES Company ON DELETE RESTRICT,
                      drive_date TEXT NOT NULL,
                      min_cgpa REAL NOT NULL CHECK (min_cgpa BETWEEN 0 AND 10));   -- frozen for this drive
  CREATE TABLE DriveDepartment (drive_id INTEGER REFERENCES Drive ON DELETE CASCADE,
                                department_id INTEGER REFERENCES Department,
                                PRIMARY KEY (drive_id, department_id));             -- M:N
  CREATE TABLE Application (application_id INTEGER PRIMARY KEY,
                            drive_id INTEGER NOT NULL REFERENCES Drive ON DELETE RESTRICT,
                            student_id INTEGER NOT NULL REFERENCES Student ON DELETE RESTRICT,
                            UNIQUE (drive_id, student_id));                          -- once per drive
  CREATE TABLE Round (application_id INTEGER REFERENCES Application ON DELETE CASCADE,
                      round_type TEXT CHECK (round_type IN ('APTITUDE', 'TECHNICAL', 'HR')),
                      held_on TEXT NOT NULL,
                      result TEXT NOT NULL CHECK (result IN ('CLEARED', 'REJECTED', 'PENDING')),
                      PRIMARY KEY (application_id, round_type));                    -- weak entity
  CREATE TABLE Offer (offer_id INTEGER PRIMARY KEY,
                      application_id INTEGER NOT NULL UNIQUE REFERENCES Application ON DELETE RESTRICT,
                      package_lpa REAL NOT NULL CHECK (package_lpa > 0),             -- frozen
                      joining_date TEXT);
  CREATE INDEX idx_application_student ON Application (student_id);

  INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE');
  INSERT INTO Student VALUES (1, 'Anita Rao', 1, 2025), (2, 'Rahul Verma', 2, 2025),
                             (3, 'Priya Nair', 1, 2025), (4, 'Sneha Iyer', 1, 2025);
  INSERT INTO Company VALUES (1, 'Infosys'), (2, 'Accenture');
  INSERT INTO Drive VALUES (1, 1, '2025-09-10', 6.5), (2, 2, '2025-10-02', 7.0);
  INSERT INTO DriveDepartment VALUES (1, 1), (1, 2), (2, 1);
  INSERT INTO Application VALUES (1, 1, 1), (2, 1, 2), (3, 2, 1), (4, 2, 3), (5, 1, 4);
  INSERT INTO Offer VALUES (1, 1, 3.6, '2026-07-01'), (2, 3, 4.5, '2026-07-15'),
                           (3, 4, 4.5, '2026-07-15'), (4, 2, 3.6, '2026-07-01');

  -- The officer's first two questions, for the 2025 batch, per department.
  SELECT d.name,
         COUNT(DISTINCT s.student_id)  AS placed_students,
         MAX(o.package_lpa)            AS highest_lpa,
         ROUND(AVG(o.package_lpa), 2)  AS average_offer_lpa
  FROM   Offer o
  JOIN   Application a ON a.application_id = o.application_id
  JOIN   Student s     ON s.student_id     = a.student_id
  JOIN   Department d  ON d.department_id  = s.department_id
  WHERE  s.batch_year = 2025
  GROUP BY d.name;

  -- The third: companies by number of offers.
  SELECT c.name, COUNT(*) AS offers
  FROM   Offer o JOIN Application a ON a.application_id = o.application_id
               JOIN Drive dr ON dr.drive_id = a.drive_id
               JOIN Company c ON c.company_id = dr.company_id
  GROUP BY c.name ORDER BY offers DESC, c.name;
  ```
  ::::

  ```text [Output]
  name  placed_students  highest_lpa  average_offer_lpa
  ----  ---------------  -----------  -----------------
  CSE   2                4.5          4.2
  ECE   1                3.6          3.6

  name       offers
  ---------  ------
  Accenture  2
  Infosys    2
  ```

  **The decisions worth defending out loud.** `min_cgpa` lives on the **drive**,
  not the company: a company's bar changes between years and the record of what
  it was in 2025 must not move. `Offer.application_id` is `UNIQUE`: one offer per
  application, and a student with two offers has two applications, which is what
  the brief says. `Round` cascades from `Application` (a round means nothing
  without it) while `Offer` restricts (an offer is a record that must never
  vanish by accident). And there is deliberately **no** `placed` flag on
  `Student`: it is derivable from offers, and a stored copy would eventually
  disagree. Anita has two offers, which is why "placed students" counts distinct
  students, not offers.
  :::
::

## 1. Find the anomalies

| enrol_id | student | student_email | course | faculty | faculty_phone | marks |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Anita Rao | anita@… | DBMS | Vikram Singh | 98xxx | 87 |
| 2 | Anita Rao | anita@… | OS | Vikram Singh | 98xxx | 72 |
| 3 | Rahul Verma | rahul@… | DBMS | Vikram Singh | 98xxx | 64 |

Name all three anomalies with a specific example of each, then list the tables.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Update:** Vikram's phone is in three rows; change it in one and the data
  disagrees. **Insertion:** a new course with no enrolments cannot be recorded,
  nor a faculty member who is not yet teaching. **Deletion:** delete the only
  enrolment in a course and the course, and who teaches it, disappears.

  Tables: `Student(student_id, name, email)`, `Faculty(faculty_id, name,
  phone)`, `Course(course_id, name, faculty_id)`, and
  `Enrolment(student_id, course_id, marks)` with a composite primary key.
  Faculty belongs to the course, not to the enrolment.
  :::
::

## 2. Keys and closure

`R(A, B, C, D, E, F)` with `F = { A → B, C → D, AC → E, E → F }`.

1. Find every candidate key.
2. How many super keys does R have?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  A and C appear on no right-hand side, so both are in every key.
  `{A, C}⁺`: A gives B, C gives D, AC gives E, E gives F. That is all six, and
  neither `{A}⁺ = {A, B}` nor `{C}⁺ = {C, D}` is, so **AC** is the only
  candidate key.

  Super keys: every superset of {A, C}. The other four attributes can each be in
  or out: 2⁴ = **16**.
  :::
::

## 3. Which normal form?

`Result(student_id, course_code, student_name, course_title, marks)` with
`student_id → student_name`, `course_code → course_title`,
`{student_id, course_code} → marks`. What is its highest normal form?
Decompose it to BCNF and check the decomposition is lossless.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Candidate key: {student_id, course_code}. `student_name` and `course_title`
  each depend on **part** of it: partial dependencies, so it is in **1NF only**.

  Decompose: `Student(student_id, student_name)`, `Course(course_code,
  course_title)`, `Marks(student_id, course_code, marks)`. Each has one FD whose
  left side is its key, so each is in BCNF.

  Lossless: `Marks` shares `student_id` with `Student` (Student's key) and
  `course_code` with `Course` (Course's key), so no join can invent rows. All
  three original FDs sit inside one table each, so it is dependency preserving
  too.
  :::
::

## 4. Serialisable or not?

Draw the precedence graph for each and say whether it is conflict serialisable.
If it is, give the equivalent serial order.

- S1: `R1(A), R2(A), W2(A), R1(B), W1(A), W2(B)`
- S2: `R1(A), W1(A), R2(A), R3(B), W2(A), W3(B), R1(B)`

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **S1.** On A: R1(A) before W2(A) gives T1 → T2; R2(A) before W1(A) gives
  T2 → T1; W2(A) before W1(A) gives T2 → T1. Cycle T1 ⇄ T2: **not** conflict
  serialisable. (On B: R1(B) before W2(B) adds another T1 → T2.)

  **S2.** On A: R1(A), W1(A) before R2(A), W2(A) give T1 → T2. On B: R3(B) and
  W3(B) come before R1(B); W3(B) before R1(B) gives T3 → T1 (R3(B) before R1(B)
  is two reads, no edge). Edges: T3 → T1 → T2. **No cycle**, so conflict
  serialisable, equivalent to the serial order **T3, T1, T2**.
  :::
::

## 5. Deadlock

T1 locks Student row 1 and then requests row 2. T2 locks row 2 and then requests
row 1. Timestamps: T1 = 10 (older), T2 = 20.

1. Draw the wait-for graph.
2. Under **wait-die**, what happens when T2 requests row 1?
3. Under **wound-wait**, what happens when T1 requests row 2?
4. What single coding rule would have prevented it?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  1. T1 → T2 (T1 waits for row 2, held by T2) and T2 → T1: a cycle, so a
     deadlock.
  2. Wait-die: T2 is younger and requests from an older holder, so T2 **dies**
     (aborts, restarts later keeping timestamp 20). T1 proceeds.
  3. Wound-wait: T1 is older and requests from a younger holder, so T1
     **wounds** T2 (T2 aborts). T1 proceeds. In both schemes only the younger
     transaction is aborted.
  4. Always lock rows in the same order, such as ascending `student_id`. Then T2
     would request row 1 first, wait for T1, and no cycle can form.
  :::
::

## 6. Make this safe

```java [SeatService.java]
public void allot(long programmeId, long studentId) {
  int left = programmeRepo.seatsLeft(programmeId);
  if (left > 0) {
    programmeRepo.setSeatsLeft(programmeId, left - 1);
    admissionRepo.insert(programmeId, studentId);
  }
}
```

Two clerks call it at the same instant for the last seat. Say what happens, name
the anomaly, and fix it two ways.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Both read `left = 1`, both pass the check, both write 0, both insert: two
  students, one seat. A **lost update**, and default isolation in MySQL and
  PostgreSQL allows it.

  **Fix A:** one conditional statement, and insert only if it changed a row:

  ```sql [fix-a.sql]
  CREATE TABLE Programme (programme_id INTEGER PRIMARY KEY, seats_left INTEGER);
  CREATE TABLE Admission (programme_id INTEGER, student_id INTEGER, UNIQUE (programme_id, student_id));
  INSERT INTO Programme VALUES (3, 1);

  UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 3 AND seats_left > 0;
  INSERT INTO Admission SELECT 3, 7 WHERE changes() = 1;
  UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 3 AND seats_left > 0;
  INSERT INTO Admission SELECT 3, 8 WHERE changes() = 1;

  SELECT (SELECT seats_left FROM Programme) AS seats_left,
         (SELECT COUNT(*) FROM Admission)   AS admitted;
  ```

  ```text [Output]
  seats_left  admitted
  ----------  --------
  0           1
  ```

  **Fix B:** `SELECT seats_left ... FOR UPDATE` inside a transaction, so the
  second clerk blocks until the first commits and then reads 0. In both cases,
  keep `UNIQUE (programme_id, student_id)` on admissions, because the usual real
  cause is a double-click.
  :::
::

## 7. Why will this not use the index?

```sql [slow-query.sql]
SELECT * FROM ExamResult
WHERE  LOWER(status) = 'published'
  AND  substr(exam_date, 1, 4) = '2025'
ORDER BY marks DESC;
```

There is an index on `(status, exam_date)`. Give three reasons it will not
help, rewrite the query, and say which index would serve it best.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `LOWER(status)` and `substr(exam_date, 1, 4)` are functions on indexed columns,
  so the sorted values cannot be searched. And `ORDER BY marks` needs a sort the
  index does not provide. Rewrite, then check the plan:

  ```sql [fast-query.sql]
  CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, status TEXT, exam_date TEXT, marks INTEGER);
  CREATE INDEX idx_status_date ON ExamResult (status, exam_date);

  EXPLAIN QUERY PLAN
  SELECT result_id, student_id, marks FROM ExamResult
  WHERE  LOWER(status) = 'published' AND substr(exam_date, 1, 4) = '2025';

  EXPLAIN QUERY PLAN
  SELECT result_id, student_id, marks FROM ExamResult
  WHERE  status = 'PUBLISHED' AND exam_date >= '2025-01-01' AND exam_date < '2026-01-01';
  ```

  ```text [Output]
  QUERY PLAN
  `--SCAN ExamResult
  QUERY PLAN
  `--SEARCH ExamResult USING INDEX idx_status_date (status=? AND exam_date>? AND exam_date<?)
  ```
  Store `status` in one case so no `LOWER()` is needed, use a half-open date
  range, and name the columns. For the sort as well, an index on
  `(status, marks)` with the date filter applied afterwards, or a covering index
  that includes `marks`, depending on which filter is more selective.
  :::
::

## 8. What breaks?

```sql [delete-department.sql]
DELETE FROM Department WHERE department_id = 3;
```

`Student.department_id` is `ON DELETE CASCADE`, and `FeePayment.student_id` is
`ON DELETE CASCADE` too. Say exactly what happens and why this schema is
dangerous.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  ```sql [cascade-chain.sql]
  PRAGMA foreign_keys = ON;
  CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT);
  CREATE TABLE Student (student_id INTEGER PRIMARY KEY, department_id INTEGER REFERENCES Department ON DELETE CASCADE);
  CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER REFERENCES Student ON DELETE CASCADE, amount INTEGER);
  INSERT INTO Department VALUES (3, 'Mechanical');
  INSERT INTO Student VALUES (4, 3), (8, 3);
  INSERT INTO FeePayment VALUES (1, 4, 42500), (2, 8, 42500), (3, 8, 42500);

  DELETE FROM Department WHERE department_id = 3;

  SELECT (SELECT COUNT(*) FROM Student)    AS students_left,
         (SELECT COUNT(*) FROM FeePayment) AS payments_left;
  ```

  ```text [Output]
  students_left  payments_left
  -------------  -------------
  0              0
  ```
  One statement deleted the department, every student in it, and every fee
  payment those students made: ₹1,27,500 of payment records, gone, with no
  warning. **Cascades chain**, and each one looked reasonable to whoever added
  it. Money must be `ON DELETE RESTRICT`, which forces anyone removing a
  department to deal with the students and their payments deliberately.
  :::
