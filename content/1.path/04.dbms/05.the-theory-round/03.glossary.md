That was the whole DBMS track. This is every term in it on one page, one plain
line each, grouped the way the chapters were. Read it the night before a walk-in,
and read the last section twice: it is where the follow-up questions come from.

## Foundations

| Term | In one line |
| --- | --- |
| **Database** | An organised collection of related data. |
| **DBMS** | The software that stores a database and controls every access to it. |
| **File system (as a store)** | Data in files; no rules, no safe concurrency, no query language. |
| **Redundancy** | The same fact stored more than once; the source of inconsistency. |
| **Three-schema architecture** | External (views), conceptual (logical schema), internal (physical storage). |
| **Physical data independence** | Change storage (add an index) without changing the schema or queries. |
| **Logical data independence** | Change the schema without changing views and applications. Harder. |
| **ER model** | Entities, attributes and relationships, drawn before tables exist. |
| **Entity / entity set** | One thing (Anita) / all things of that kind (Student). Rectangle. |
| **Attribute** | A fact about an entity. Simple or composite, single- or multi-valued, stored or derived. |
| **Relationship** | An association between entities. Diamond. |
| **Cardinality (ER)** | 1:1, 1:N or M:N: how many of one relate to how many of the other. |
| **Participation** | Total (every entity must take part; double line) or partial. |
| **Weak entity** | Identified only with its owner's key plus a partial key. Double rectangle. |
| **Junction table** | The table an M:N relationship becomes, keyed on both sides. |
| **Relational model** | Data as relations (sets of tuples), proposed by E. F. Codd in 1970. |
| **Relation, tuple, attribute** | Table, row, column. |
| **Domain** | The set of values an attribute may take. |
| **Degree / cardinality (relation)** | Number of attributes / number of tuples. |
| **Schema / instance** | The design / the data at a moment. |
| **Entity integrity** | Primary key values are unique and never `NULL`. |
| **Referential integrity** | A foreign key matches an existing key or is `NULL`. |

## Keys

| Term | In one line |
| --- | --- |
| **Super key** | Any attribute set that uniquely identifies a tuple. |
| **Candidate key** | A minimal super key. |
| **Primary key** | The candidate key chosen as the identity. One per table, never `NULL`. |
| **Alternate key** | A candidate key not chosen as primary. Enforced with `UNIQUE`. |
| **Composite key** | A key of two or more attributes. |
| **Foreign key** | An attribute that references another relation's key. |
| **Surrogate key** | A generated, meaningless id. Never needs to change. |
| **Natural key** | A real-world value used as a key. Usually a trap: real values change. |

## Normalisation

| Term | In one line |
| --- | --- |
| **Update anomaly** | Changing one fact means changing many rows; miss one and data contradicts itself. |
| **Insertion anomaly** | Cannot record one fact without inventing another. |
| **Deletion anomaly** | Deleting one fact destroys another. |
| **Normalisation** | Decomposing tables so each fact is stored once. |
| **Functional dependency (X → Y)** | Rows equal on X must be equal on Y. A rule of the domain. |
| **Trivial FD** | Y is a subset of X. Always true, says nothing. |
| **Armstrong's axioms** | Reflexivity, augmentation, transitivity. Derive every implied FD. |
| **Attribute closure (X⁺)** | Every attribute X determines. All of R means X is a super key. |
| **Prime attribute** | Part of some candidate key. |
| **Partial dependency** | A non-prime attribute depends on part of a candidate key. Breaks 2NF. |
| **Transitive dependency** | A non-prime attribute depends on another non-prime attribute. Breaks 3NF. |
| **1NF** | Atomic values; no lists in a cell. |
| **2NF** | 1NF and no partial dependencies. |
| **3NF** | 2NF and no transitive dependencies (X → A needs X super key or A prime). |
| **BCNF** | Every determinant of a non-trivial FD is a super key. |
| **4NF / 5NF** | No multi-valued dependencies / no join dependencies. Rare in practice. |
| **Lossless-join decomposition** | Joining the pieces gives back exactly the original; common attributes are a key of one piece. |
| **Spurious tuple** | A row invented by joining a lossy decomposition. |
| **Dependency preservation** | Every FD can be checked within one piece. Always possible for 3NF, not BCNF. |
| **Denormalisation** | Storing redundant data on purpose for read speed, owning the cost of keeping it consistent. |

## Transactions and concurrency

| Term | In one line |
| --- | --- |
| **Transaction** | A logical unit of work that succeeds or fails as a whole. |
| **Atomicity** | All or nothing. |
| **Consistency** | Rules hold before and after. |
| **Isolation** | Concurrent transactions do not see each other's half-done work. |
| **Durability** | Committed changes survive a crash. |
| **Transaction states** | Active, partially committed, committed; or failed, aborted. |
| **Write-ahead log (WAL)** | Changes logged to disk before data files; replayed (redo/undo) after a crash. |
| **Schedule** | The order in which operations of concurrent transactions run. |
| **Serial / serialisable** | One after another / interleaved with the same effect as some serial order. |
| **Conflicting operations** | Same item, different transactions, at least one a write. |
| **Conflict serialisable** | Reachable from a serial schedule by swapping non-conflicting operations. |
| **Precedence graph** | Node per transaction, edge per conflict; acyclic means conflict serialisable. |
| **View serialisable** | Same reads and final writes as some serial schedule. Weaker; NP-complete to test. |
| **Recoverable / cascadeless / strict** | Commit after the writers you read from / read only committed data / touch only committed data. |
| **Lost update** | Two transactions read, compute and write; one write is lost. |
| **Dirty read** | Reading another transaction's uncommitted write. |
| **Non-repeatable read** | Same row read twice, different values, in one transaction. |
| **Phantom read** | Same query run twice, different set of rows. |
| **Shared / exclusive lock** | Read lock (many holders) / write lock (one holder). |
| **Two-phase locking (2PL)** | Acquire all locks before releasing any. Guarantees conflict serialisability. |
| **Strict 2PL** | Hold exclusive locks until commit. No cascading rollbacks. |
| **Deadlock** | A cycle of transactions each waiting for the next. |
| **Coffman conditions** | Mutual exclusion, hold and wait, no pre-emption, circular wait. |
| **Wait-for graph** | Edge Ti → Tj if Ti waits for Tj. A cycle is a deadlock. |
| **Wait-die / wound-wait** | Timestamp schemes; only the younger transaction is ever aborted. |
| **Starvation** | One transaction never gets to run while others do. |
| **Optimistic concurrency** | No locks; validate at commit (or a version column). |
| **MVCC** | Several versions of each row, so readers never block writers. |
| **Isolation levels** | Read uncommitted, read committed, repeatable read, serialisable. |

## Indexes and the theory round

| Term | In one line |
| --- | --- |
| **Index** | A separate sorted structure that finds rows without scanning the table. |
| **B-tree** | Balanced, wide, shallow tree; keys and data pointers in every node. |
| **B+ tree** | Data pointers only in leaves; leaves linked in order. What databases use. |
| **Fan-out** | Children per node. Hundreds, so height is three or four. |
| **Node split** | A full node splits and pushes its middle key up; the tree grows at the root. |
| **Hash index** | Equality in one step; no ranges or ordering. |
| **Clustered index** | The table stored in index order; leaves are the rows. One per table. |
| **Non-clustered (secondary) index** | Keys plus pointers to rows. Many per table. |
| **Key lookup** | The extra trip from a secondary index to the table for other columns. |
| **Covering index** | Contains every column a query needs; no table visit. |
| **Dense / sparse index** | An entry per record / per block (needs a sorted file). |
| **Relational algebra** | Operators on relations: σ, π, ∪, −, ×, ρ, ⋈, ∩, ÷. |
| **Selection σ / projection π** | Choose rows (`WHERE`) / choose columns (`SELECT DISTINCT`). |
| **Natural join ⋈** | Join on all same-named attributes, one copy each. |
| **Division ÷** | "Related to all": students who took every core course. |
| **NoSQL** | Non-relational stores: document, key-value, column-family, graph. |
| **CAP theorem** | During a network partition, choose consistency or availability. |
| **BASE** | Basically available, soft state, eventually consistent. |

## The pairs people confuse

::accordion
  :::accordion-item{label="Super key against candidate key" icon="i-lucide-git-compare"}
  Any unique set, against a minimal unique set.
  :::
  :::accordion-item{label="Primary key against unique key" icon="i-lucide-git-compare"}
  One per table and never `NULL`, against many per table and `NULL` allowed.
  :::
  :::accordion-item{label="2NF against 3NF against BCNF" icon="i-lucide-git-compare"}
  No partial dependency; also no transitive dependency; every determinant a
  super key (3NF's "or A is prime" exception removed).
  :::
  :::accordion-item{label="Lossless against dependency preserving" icon="i-lucide-git-compare"}
  No rows invented by the join (compulsory), against every FD checkable in one
  table (desirable; BCNF may lose it).
  :::
  :::accordion-item{label="Cardinality in ER against cardinality of a relation" icon="i-lucide-git-compare"}
  1:N as a relationship ratio, against the number of rows.
  :::
  :::accordion-item{label="Consistency in ACID against consistency in CAP" icon="i-lucide-git-compare"}
  Rules hold, against every reader sees the latest write.
  :::
  :::accordion-item{label="Dirty read against non-repeatable read against phantom" icon="i-lucide-git-compare"}
  Uncommitted value, against a committed change to a row read twice, against new
  or vanished rows in a repeated query.
  :::
  :::accordion-item{label="Deadlock against starvation" icon="i-lucide-git-compare"}
  Nobody proceeds (a cycle), against one transaction never proceeding while
  others do.
  :::
  :::accordion-item{label="Clustered against non-clustered index" icon="i-lucide-git-compare"}
  The table in index order, one per table, against a separate pointer structure,
  many per table.
  :::
  :::accordion-item{label="B-tree against B+ tree" icon="i-lucide-git-compare"}
  Data pointers in every node, against only in linked leaves.
  :::
::
