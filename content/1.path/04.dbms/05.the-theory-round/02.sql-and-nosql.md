Everything in this track assumed data lives in tables with a fixed schema,
joined by keys. Some of the most used databases in the world do not work that
way, and "SQL or NoSQL, and why?" is now a standard interview question. This
lesson is the awareness level a fresher needs: what the options are, and how to
choose honestly.

## Why this matters in a job

You will hear "we use MongoDB" or "the cache is Redis" in your first month at
many companies, and the interview question comes in two forms: "what is the
difference between SQL and NoSQL?" and "which would you use for X?". The weak
answer is "NoSQL is faster and more scalable". The strong answer names what
each kind is good at and what it gives up.

## Not only SQL

**NoSQL** ("not only SQL") is an umbrella for databases that do not use the
relational model of fixed tables joined by keys. They appeared because some
workloads (huge scale across many machines, very flexible data, extremely fast
simple lookups) fit tables badly. They are not one thing; they are four quite
different kinds:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-file-json" title="Document"}
  Each record is a JSON-like document, and documents in one collection can have
  different fields. **MongoDB**, Couchbase. Good for data that is read as a
  whole and varies in shape: a student profile with optional sections.
  :::
  :::feature{icon="i-lucide-key-round" title="Key-value"}
  A giant dictionary: give a key, get a value. Extremely fast, no queries on the
  value. **Redis**, DynamoDB. Good for sessions, caches, counters.
  :::
  :::feature{icon="i-lucide-columns-3" title="Column-family (wide-column)"}
  Rows with huge numbers of columns grouped into families, spread across many
  machines. **Cassandra**, HBase. Good for enormous write-heavy data such as
  logs and sensor readings.
  :::
  :::feature{icon="i-lucide-share-2" title="Graph"}
  Nodes and relationships as first-class data. **Neo4j**. Good for questions
  about connections: "which alumni are two hops from this recruiter?"
  :::
::

## How it works: the same student, two ways

In the relational design from this track, a student is spread across tables
(Student, Enrolment, ExamResult) and assembled with joins. In a document
database, the same student might be stored as one document:

```text [student-document.json]
{
  "_id": 1,
  "full_name": "Anita Rao",
  "department": { "name": "CSE", "head": "Dr. Meera Joshi" },
  "enrolments": [
    { "course": "CS201", "title": "Data Structures", "marks": 87 },
    { "course": "CS202", "title": "DBMS", "marks": 72 }
  ],
  "phones": ["9876543210"]
}
```

One read returns everything about Anita, with no joins, and a new optional field
can be added to one document without changing any schema. Now look again with
the normalisation chapter in mind: the department head is copied into every CSE
student's document. When the head changes, every one of those documents must be
updated: the **update anomaly**, by design. Document databases accept that
trade in exchange for fast whole-record reads.

SQLite can store and query JSON too, which makes the shape easy to see:

::runner{lang="sql"}
```sql [json-in-sql.sql]
CREATE TABLE StudentDoc (id INTEGER PRIMARY KEY, doc TEXT);
INSERT INTO StudentDoc VALUES
  (1, '{"full_name":"Anita Rao","department":{"name":"CSE","head":"Dr. Meera Joshi"},
        "enrolments":[{"course":"CS201","marks":87},{"course":"CS202","marks":72}]}'),
  (2, '{"full_name":"Rahul Verma","department":{"name":"ECE","head":"Dr. Suresh Rao"},
        "enrolments":[{"course":"CS201","marks":64}]}');

-- Reach inside the documents.
SELECT json_extract(doc, '$.full_name')       AS name,
       json_extract(doc, '$.department.head') AS head,
       json_array_length(doc, '$.enrolments') AS courses
FROM   StudentDoc;
```
::

```text [Output]
name         head             courses
-----------  ---------------  -------
Anita Rao    Dr. Meera Joshi  2
Rahul Verma  Dr. Suresh Rao   1
```

## CAP, BASE and ACID in three sentences

- **CAP theorem:** a database spread across machines, when the network between
  them fails (a **partition**), must choose between **consistency** (every read
  sees the latest write, or gets an error) and **availability** (every request
  gets an answer, possibly stale). It cannot guarantee both during a partition.
- **ACID** (this track) is the relational choice: correctness first, including
  when that means waiting or refusing.
- **BASE** (basically available, soft state, eventually consistent) is the
  common NoSQL choice: stay up and answer, and let copies agree **eventually**,
  usually within milliseconds.

::note
The C in CAP is not the C in ACID. ACID's consistency means "the rules hold";
CAP's means "every reader sees the latest write". The same word, two ideas, and a
favourite trick question.
::

## SQL against NoSQL

| | Relational (SQL) | NoSQL |
| --- | --- | --- |
| Data model | Tables, rows, fixed schema | Documents, key-value, wide-column, graph; flexible schema |
| Relationships | Joins across normalised tables | Usually embedded or duplicated; joins limited or absent |
| Consistency | ACID transactions | Often eventual (BASE); many now offer transactions within limits |
| Scaling | Mostly vertical (a bigger server), replicas for reads | Built to scale horizontally across many machines |
| Query language | SQL, standard and powerful | Varies by product |
| Best for | Structured data with rules and relationships; money; reports | Huge scale, flexible or nested data, simple access patterns |

## Real use case

Where does a college's data belong?

::compare{caption="Choosing by the data, not by fashion."}
  :::compare-side{label="Relational" verdict="right"}
  Students, courses, enrolments, marks, fees, placements. Highly related,
  rule-heavy (a result must belong to a real student; a fee cannot be negative),
  reported on in every combination, and money must never be eventually
  consistent. Every reason in this track points here.
  :::
  :::compare-side{label="NoSQL, alongside it" verdict="right"}
  A Redis cache of the results page during results week (key: student id,
  value: the rendered marks), a document store for free-form alumni profiles, a
  log store for lakhs of portal clicks. Each is a narrow job next to the
  relational database, not a replacement for it.
  :::
::

Most real systems are like this: a relational database as the source of truth,
with a NoSQL store or two for a specific job. "Both, for different parts" is
usually the honest answer in an interview, provided you can say which part goes
where and why.

## What confuses people here

- **"NoSQL means no schema."** The schema moves into the application code. The
  data still has a shape; the database does not enforce it.
- **"NoSQL is faster."** It is faster at the access patterns it was designed
  for (fetch this whole document by key) and often worse at others (ad-hoc
  reports across many records).
- **"NoSQL has no transactions."** MongoDB has had multi-document transactions
  since version 4.0. The trade-offs are real but less absolute than older
  articles suggest.
- **SQL databases do scale.** Read replicas, partitioning and managed services
  run very large relational systems. Choosing NoSQL "for scale" at a college's
  size is choosing complexity you do not need.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between SQL and NoSQL databases?" icon="i-lucide-message-circle"}
  SQL databases store data in tables with a fixed schema, relate them with keys
  and joins, and provide ACID transactions. NoSQL databases use other models
  (document, key-value, wide-column, graph), have flexible schemas, usually
  scale horizontally, and often trade strict consistency for availability.
  :::
  :::accordion-item{label="What are the types of NoSQL databases?" icon="i-lucide-message-circle"}
  Document (MongoDB), key-value (Redis, DynamoDB), column-family (Cassandra,
  HBase) and graph (Neo4j). Give one use for each.
  :::
  :::accordion-item{label="What is the CAP theorem?" icon="i-lucide-message-circle"}
  In a distributed database, when a network partition happens, you must choose
  between consistency (every read sees the latest write) and availability (every
  request gets a response). Partition tolerance is not optional across machines,
  so the real choice is C or A during a partition.
  :::
  :::accordion-item{label="What is BASE?" icon="i-lucide-message-circle"}
  Basically available, soft state, eventually consistent: the system stays
  available, data may be temporarily inconsistent across copies, and converges
  given time. The usual NoSQL counterpart to ACID.
  :::
  :::accordion-item{label="When would you choose NoSQL over SQL?" icon="i-lucide-message-circle"}
  When the data is naturally nested or varies in shape, access is by key or
  whole document, scale needs many machines, and eventual consistency is
  acceptable: caches, sessions, logs, activity feeds, catalogues. Keep money,
  records with rules, and anything reported on in many ways in a relational
  database.
  :::
::
