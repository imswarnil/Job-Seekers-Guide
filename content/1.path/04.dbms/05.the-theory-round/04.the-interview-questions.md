Every term, one line each, was the glossary. This is the round: the DBMS
questions as interviewers phrase them, in the order they tend to come. The
questions are remarkably consistent from company to company. What changes is
whether the answer sounds understood or recited, and the difference is almost
always an example.

Answer each out loud before opening it.

## Foundations

::accordion
  :::accordion-item{label="1. What is a DBMS? Why not use a file system?" icon="i-lucide-message-circle"}
  Software that stores data and controls all access to it. Over files it gives:
  controlled redundancy (a head's name stored once, not on every student row),
  integrity constraints, safe concurrent access (two clerks cannot both take the
  last seat), a query language with indexes, and security with backup and
  recovery. Name the failures, not adjectives.
  :::
  :::accordion-item{label="2. Explain the three-schema architecture and data independence." icon="i-lucide-message-circle"}
  External level (each user's views), conceptual level (the logical schema),
  internal level (physical storage). Physical data independence: add an index
  without changing any query. Logical data independence: change the schema
  without changing views and applications, which is harder.
  :::
  :::accordion-item{label="3. What is an ER diagram? Draw one for a college." icon="i-lucide-message-circle"}
  A picture of entities, attributes and relationships with cardinalities. For a
  college: Department 1:N Student; Student M:N Course through Enrolment (with
  grade as a relationship attribute); Faculty 1:N Course; Faculty 1:1 Department
  as head; FeeInstalment as a weak entity of Student. Ask first whether history
  is needed, because it turns N:1 relationships into M:N ones.
  :::
  :::accordion-item{label="4. What is a weak entity?" icon="i-lucide-message-circle"}
  An entity with no key of its own, identified by its owner's key plus a partial
  key: a fee instalment is (student_id, instalment_no). Always totally
  participates in its identifying relationship; double rectangle and double
  diamond.
  :::
  :::accordion-item{label="5. How is an M:N relationship stored?" icon="i-lucide-message-circle"}
  As a junction table holding both primary keys as foreign keys, with the pair as
  its primary key:

  ```sql [q5.sql]
  CREATE TABLE Enrolment (student_id INTEGER, course_id INTEGER, grade TEXT,
                          PRIMARY KEY (student_id, course_id));
  INSERT INTO Enrolment VALUES (1, 101, 'A'), (1, 102, 'B'), (2, 101, 'C');
  SELECT course_id, COUNT(*) AS students FROM Enrolment GROUP BY course_id;
  ```

  ```text [Output]
  course_id  students
  ---------  --------
  101        2
  102        1
  ```
  :::
  :::accordion-item{label="6. What are degree and cardinality of a relation? Schema vs instance?" icon="i-lucide-message-circle"}
  Degree: number of attributes. Cardinality: number of tuples. The schema is the
  structure and rarely changes; the instance is the data at a moment and changes
  constantly.
  :::
  :::accordion-item{label="7. What are entity integrity and referential integrity?" icon="i-lucide-message-circle"}
  Entity integrity: primary key values are unique and never `NULL`. Referential
  integrity: every foreign key value matches an existing key or is `NULL`:

  ```sql [q7.sql]
  PRAGMA foreign_keys = ON;
  CREATE TABLE Student (student_id INTEGER PRIMARY KEY);
  CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER REFERENCES Student);
  INSERT INTO Student VALUES (1);
  INSERT INTO ExamResult VALUES (1, 99);   -- no student 99
  ```

  ```text [Output]
  Error: FOREIGN KEY constraint failed
  ```
  :::
::

## Keys

::accordion
  :::accordion-item{label="8. Super key vs candidate key vs primary key vs alternate key?" icon="i-lucide-message-circle"}
  Super key: any set that uniquely identifies a tuple. Candidate key: a minimal
  super key. Primary key: the candidate chosen as the identity. Alternate keys:
  the other candidates. In Student(student_id, email, roll_number, name), each of
  the first three is a candidate key; {student_id, name} is a super key but not a
  candidate.
  :::
  :::accordion-item{label="9. Primary key vs unique key?" icon="i-lucide-message-circle"}
  Both prevent duplicates. Primary: one per table, never `NULL`, referenced by
  foreign keys, clustered by default in InnoDB. Unique: many per table, `NULL`
  allowed (usually several). Then the permanence test: could the value ever
  change? If yes, it should not be the primary key.
  :::
  :::accordion-item{label="10. R(A, B, C, D) has candidate keys A and B. How many super keys?" icon="i-lucide-message-circle"}
  Supersets of {A}: 2³ = 8. Of {B}: 8. Of both {A, B}: 2² = 4. Total 8 + 8 − 4 =
  **12**.
  :::
  :::accordion-item{label="11. What is a composite key? A foreign key?" icon="i-lucide-message-circle"}
  Composite: a key of several attributes where only the combination is unique,
  such as (student_id, course_id). Foreign: an attribute referencing another
  table's key; many rows may share the same foreign key value.
  :::
::

## Normalisation

::accordion
  :::accordion-item{label="12. What is normalisation? Why is it needed?" icon="i-lucide-message-circle"}
  Decomposing tables so each fact is stored once, to remove the update,
  insertion and deletion anomalies. Give one of each: the CSE head's name on every
  CSE row (update); a new department with no students cannot be stored
  (insertion); deleting the last ECE student deletes ECE (deletion).
  :::
  :::accordion-item{label="13. Explain 1NF, 2NF and 3NF with an example." icon="i-lucide-message-circle"}
  1NF: atomic values (split "CS201, CS202" into rows). 2NF: no non-prime
  attribute depends on part of a composite key (student_name depends only on
  student_id in (student_id, course_code), so move it to Student). 3NF: no
  non-prime attribute depends on another non-prime (dept_head depends on
  department, so move it to Department). Show the four resulting tables.
  :::
  :::accordion-item{label="14. What is BCNF? How is it different from 3NF?" icon="i-lucide-message-circle"}
  For every non-trivial FD X → Y, X is a super key. 3NF also allows X → Y when Y
  is prime. Example in 3NF but not BCNF: Teaching(student_id, course, faculty)
  with {student_id, course} → faculty and faculty → course. faculty is not a
  super key. Decompose into (faculty, course) and (student_id, faculty).
  :::
  :::accordion-item{label="15. What is a functional dependency? Armstrong's axioms?" icon="i-lucide-message-circle"}
  X → Y: rows equal on X are equal on Y. It is a rule of the domain, and data can
  only disprove it:

  ```sql [q15.sql]
  CREATE TABLE S (student_id INTEGER, department TEXT, dept_head TEXT);
  INSERT INTO S VALUES (1, 'CSE', 'Dr. Meera Joshi'), (2, 'CSE', 'Dr. Meera Joshi'), (3, 'ECE', 'Dr. Suresh Rao');
  -- Violations of department -> dept_head (none expected):
  SELECT department FROM S GROUP BY department HAVING COUNT(DISTINCT dept_head) > 1;
  SELECT 'no violations' AS result
  WHERE NOT EXISTS (SELECT department FROM S GROUP BY department HAVING COUNT(DISTINCT dept_head) > 1);
  ```

  ```text [Output]
  result
  -------------
  no violations
  ```
  Armstrong's axioms: reflexivity, augmentation, transitivity.
  :::
  :::accordion-item{label="16. R(A, B, C, D, E) with A → B, B → C and CD → E. Find the candidate key." icon="i-lucide-message-circle"}
  A and D appear on no right-hand side, so both are in every key. {A, D}⁺ = A, D,
  then B (A → B), C (B → C), E (CD → E): all five. {A}⁺ = {A, B, C} and {D}⁺ =
  {D} are not. The only candidate key is **AD**. Since B depends on A alone (part
  of the key), R is not in 2NF.
  :::
  :::accordion-item{label="17. What is a lossless decomposition? Dependency preservation?" icon="i-lucide-message-circle"}
  Lossless: joining the pieces returns exactly the original; guaranteed when the
  common attributes are a super key of one piece. Dependency preserving: every
  FD can be checked in one piece. 3NF can always have both; BCNF guarantees only
  losslessness.
  :::
  :::accordion-item{label="18. What is denormalisation? When would you do it?" icon="i-lucide-message-circle"}
  Storing redundant data deliberately to make reads faster, such as a nightly
  reporting table. Only after measuring a real problem, and owning the job of
  keeping copies in step. Add the case that is not denormalisation: a fee receipt
  stores the fee **then**, because the fee **now** will change.
  :::
::

## Transactions and concurrency

::accordion
  :::accordion-item{label="19. What is a transaction? Explain ACID." icon="i-lucide-message-circle"}
  A unit of work that succeeds or fails as a whole. With a fee payment (record
  the payment, reduce the amount due): atomicity, both or neither; consistency,
  amount_due never goes negative; isolation, nobody sees it half done;
  durability, committed survives a crash.
  :::
  :::accordion-item{label="20. What are the states of a transaction?" icon="i-lucide-message-circle"}
  Active → partially committed → committed; or active / partially committed →
  failed → aborted (then restart or kill). Committed and aborted are terminal.
  :::
  :::accordion-item{label="21. How does a DBMS guarantee atomicity and durability?" icon="i-lucide-message-circle"}
  Write-ahead logging: every change is written to a log on disk before the data
  pages, and commit forces the log. After a crash, committed transactions are
  redone and uncommitted ones undone from the log.
  :::
  :::accordion-item{label="22. What is a schedule? What is serialisability?" icon="i-lucide-message-circle"}
  A schedule is the interleaved order of operations of concurrent transactions.
  It is serialisable if its effect equals some serial (one-after-another)
  schedule. Serialisability is the correctness criterion for concurrency.
  :::
  :::accordion-item{label="23. Is R1(A), R2(B), W3(A), R2(A), W1(B) conflict serialisable?" icon="i-lucide-message-circle"}
  Edges: R1(A)…W3(A) gives T1 → T3; W3(A)…R2(A) gives T3 → T2; R2(B)…W1(B) gives
  T2 → T1. T1 → T3 → T2 → T1 is a cycle, so **no**.
  :::
  :::accordion-item{label="24. Explain lost update, dirty read, non-repeatable read and phantom read." icon="i-lucide-message-circle"}
  Lost update: two transactions read and write the same value, one write is
  lost. Dirty read: reading uncommitted data that may be rolled back.
  Non-repeatable read: the same row read twice gives different values.
  Phantom: the same query returns a different set of rows.
  :::
  :::accordion-item{label="25. What are the isolation levels? Which is the default?" icon="i-lucide-message-circle"}
  Read uncommitted, read committed, repeatable read, serialisable, each
  preventing one more anomaly. Default: repeatable read in MySQL InnoDB, read
  committed in PostgreSQL, Oracle and SQL Server. Neither default stops a lost
  update from read-compute-write code.
  :::
  :::accordion-item{label="26. What is two-phase locking?" icon="i-lucide-message-circle"}
  A transaction acquires all its locks before releasing any (growing then
  shrinking phase). It guarantees conflict serialisability. Strict 2PL holds
  exclusive locks until commit, preventing dirty reads and cascading rollbacks.
  It does not prevent deadlock.
  :::
  :::accordion-item{label="27. What is a deadlock? How is it handled?" icon="i-lucide-message-circle"}
  Transactions waiting for each other in a cycle. Needs mutual exclusion, hold
  and wait, no pre-emption and circular wait. Prevent with consistent lock
  ordering, wait-die or wound-wait; or detect a cycle in the wait-for graph and
  abort a victim (what real databases do); or time out.
  :::
  :::accordion-item{label="28. Two users book the last seat at once. How do you stop it?" icon="i-lucide-message-circle"}
  A conditional update with the row count checked, backed by a unique
  constraint:

  ```sql [q28.sql]
  CREATE TABLE Programme (programme_id INTEGER PRIMARY KEY, seats_left INTEGER);
  INSERT INTO Programme VALUES (3, 1);
  UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 3 AND seats_left > 0;
  SELECT changes() AS first_clerk_got_it;
  UPDATE Programme SET seats_left = seats_left - 1 WHERE programme_id = 3 AND seats_left > 0;
  SELECT changes() AS second_clerk_got_it;
  ```

  ```text [Output]
  first_clerk_got_it
  ------------------
  1

  second_clerk_got_it
  -------------------
  0
  ```
  Or `SELECT ... FOR UPDATE` when clashes are common, or a version column when
  they are rare.
  :::
::

## Indexes and the rest

::accordion
  :::accordion-item{label="29. How does an index work? B-tree vs B+ tree?" icon="i-lucide-message-circle"}
  A B+ tree: balanced, with hundreds of keys per node, so three or four page
  reads find a row among crores. B-tree nodes hold keys and data pointers; B+ tree
  internal nodes hold only keys, all data pointers are in leaves, and leaves are
  linked for range scans. Databases use B+ trees.
  :::
  :::accordion-item{label="30. Clustered vs non-clustered index?" icon="i-lucide-message-circle"}
  Clustered: the table is stored in the index's order, leaves are the rows, one
  per table (the primary key in InnoDB). Non-clustered: a separate structure of
  keys and row pointers, many per table, possibly needing a key lookup. A
  covering index avoids that lookup:

  ```sql [q30.sql]
  CREATE TABLE Student (student_id INTEGER PRIMARY KEY, email TEXT, full_name TEXT);
  CREATE INDEX idx_email ON Student (email);
  EXPLAIN QUERY PLAN SELECT full_name FROM Student WHERE email = 'a@college.edu';
  EXPLAIN QUERY PLAN SELECT student_id FROM Student WHERE email = 'a@college.edu';
  ```

  ```text [Output]
  QUERY PLAN
  `--SEARCH Student USING INDEX idx_email (email=?)
  QUERY PLAN
  `--SEARCH Student USING COVERING INDEX idx_email (email=?)
  ```
  :::
  :::accordion-item{label="31. Selection vs projection in relational algebra? What is a natural join?" icon="i-lucide-message-circle"}
  Selection σ chooses rows (`WHERE`); projection π chooses columns and removes
  duplicates (`SELECT DISTINCT`). A natural join ⋈ joins on all same-named
  attributes and keeps one copy of each.
  :::
  :::accordion-item{label="32. SQL vs NoSQL? What is the CAP theorem?" icon="i-lucide-message-circle"}
  SQL: tables, fixed schema, joins, ACID. NoSQL: document, key-value,
  column-family or graph, flexible schema, horizontal scale, often eventual
  consistency. CAP: during a network partition a distributed store must choose
  consistency or availability. A college's fees and marks belong in SQL; a
  results-page cache can be Redis.
  :::
::

## What every good answer above has in common

A definition, then an example on real-looking data, then the trap or the
trade-off. "Normalisation removes redundancy" is a definition. "Here is the CSE
head's name on every CSE row, and here is what happens when it changes" is an
answer, and it is the one an interviewer remembers.
