That completes how a DBMS stores, protects and finds data. The theory round has
one more favourite: the algebra underneath every SQL query. It is written in
Greek letters that look harder than they are, and every operator is something you
already did in the SQL track.

## Why this matters in a job

Relational algebra is how a database thinks about your query: the optimiser
turns SQL into a tree of these operators and rearranges it to run faster (for
example, filtering before joining). In interviews and university exams, the
questions are "what is the difference between selection and projection?", "what
is a natural join?", and "write this query in relational algebra". Once you map
each symbol to its SQL, they are easy marks.

## Operators that take relations and return relations

Relational algebra is a set of **operators**. Each takes one or two relations
(tables) as input and returns a relation, so they can be chained, like
arithmetic. That closure is the whole idea: the output of any query can be the
input to another.

| Symbol | Name | Does | SQL |
| --- | --- | --- | --- |
| **σ** (sigma) | Selection | Keeps rows that satisfy a condition | `WHERE` |
| **π** (pi) | Projection | Keeps chosen columns, removes duplicate rows | `SELECT DISTINCT cols` |
| **∪** | Union | Rows in either relation | `UNION` |
| **−** | Set difference | Rows in the first, not the second | `EXCEPT` |
| **×** | Cartesian product | Every row with every row | `CROSS JOIN` |
| **ρ** (rho) | Rename | Renames a relation or its attributes | `AS` |
| **⋈** | Join | Product followed by selection | `JOIN ... ON` |
| **∩** | Intersection | Rows in both | `INTERSECT` |
| **÷** | Division | Rows related to **all** rows of another relation | `NOT EXISTS ... NOT EXISTS` |

The first six are the **fundamental** operators; join, intersection and division
can be written using them (∩ as R − (R − S), ⋈ as σ applied to ×).

## How it works: every operator, run

Every example uses these two relations:

```sql [algebra-setup.sql]
CREATE TABLE Student (student_id INTEGER, full_name TEXT, department TEXT, city TEXT);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'CSE', 'Bhopal'), (2, 'Rahul Verma', 'ECE', 'Patna'),
  (3, 'Priya Nair', 'CSE', 'Bangalore'), (4, 'Arjun Mehta', 'Mechanical', 'Bhopal');
CREATE TABLE Enrolment (student_id INTEGER, course_code TEXT);
INSERT INTO Enrolment VALUES (1, 'CS201'), (1, 'CS202'), (2, 'CS201'), (3, 'CS202'), (3, 'CS201');
```

### Selection σ and projection π

**σ** _department = 'CSE'_ (Student): rows.
**π** _city_ (Student): columns, duplicates removed.

```sql [selection-projection.sql]
SELECT * FROM Student WHERE department = 'CSE';      -- σ department='CSE' (Student)
SELECT DISTINCT city FROM Student;                    -- π city (Student)
```

```text [Output]
student_id  full_name   department  city
----------  ----------  ----------  ---------
1           Anita Rao   CSE         Bhopal
3           Priya Nair  CSE         Bangalore

city
---------
Bhopal
Patna
Bangalore
```

Selection cuts rows (horizontal), projection cuts columns (vertical). Projection
removes duplicates because a relation is a **set**: Bhopal appears once. SQL
keeps duplicates unless you write `DISTINCT`, which is the one place SQL and the
algebra differ.

### Composition: σ and π together

π _full_name_ ( σ _city = 'Bhopal'_ (Student) ): names of students from Bhopal.
Read it inside out: select first, then project.

```sql [composition.sql]
SELECT DISTINCT full_name FROM Student WHERE city = 'Bhopal';
```

```text [Output]
full_name
-----------
Anita Rao
Arjun Mehta
```

### Union ∪, difference −, intersection ∩

These need **union-compatible** relations: same number of attributes, with
compatible domains, the same rule as SQL's `UNION`.

```sql [set-operators.sql]
-- π student_id (σ course_code='CS201' (Enrolment))  ∪  π student_id (σ course_code='CS202' (Enrolment))
SELECT student_id FROM Enrolment WHERE course_code = 'CS201'
UNION
SELECT student_id FROM Enrolment WHERE course_code = 'CS202';

-- ... ∩ ...  : took both
SELECT student_id FROM Enrolment WHERE course_code = 'CS201'
INTERSECT
SELECT student_id FROM Enrolment WHERE course_code = 'CS202';

-- ... − ...  : took CS201 but not CS202
SELECT student_id FROM Enrolment WHERE course_code = 'CS201'
EXCEPT
SELECT student_id FROM Enrolment WHERE course_code = 'CS202';
```

```text [Output]
student_id
----------
1
2
3

student_id
----------
1
3

student_id
----------
2
```

### Cartesian product × and rename ρ

Student × Enrolment pairs every student with every enrolment: 4 × 5 = 20 rows,
mostly meaningless. Both relations have `student_id`, so one must be renamed
(ρ) to tell them apart, which is SQL's table alias.

```sql [product.sql]
SELECT COUNT(*) AS rows_in_product
FROM   Student AS s CROSS JOIN Enrolment AS e;      -- ρ s(Student) × ρ e(Enrolment)
```

```text [Output]
rows_in_product
---------------
20
```

### Join ⋈

A join is a product followed by a selection: keep only the pairs that match.

- **Theta join** R ⋈θ S: any condition θ. σ _s.student_id = e.student_id_ (s × e).
- **Equi-join**: a theta join whose condition is only equalities.
- **Natural join** R ⋈ S: an equi-join on **all** attributes with the same name,
  keeping one copy of each.

```sql [natural-join.sql]
-- Student ⋈ Enrolment  (natural join on student_id)
SELECT student_id, full_name, course_code
FROM   Student NATURAL JOIN Enrolment
ORDER BY student_id, course_code;
```

```text [Output]
student_id  full_name    course_code
----------  -----------  -----------
1           Anita Rao    CS201
1           Anita Rao    CS202
2           Rahul Verma  CS201
3           Priya Nair   CS201
3           Priya Nair   CS202
```

Arjun is missing: a natural join is an inner join. The **outer joins** (⟕ left,
⟖ right, ⟗ full) are extended operators that keep unmatched rows with `NULL`s,
exactly as in SQL.

### Division ÷

**R ÷ S** returns the values in R that are paired with **every** row of S. It
answers "for all" questions: students who took **all** the core courses.

Core = {CS201, CS202}. Enrolment(student_id, course_code) ÷ Core(course_code) =
students enrolled in both. SQL has no division operator; the standard way is a
double `NOT EXISTS` ("there is no core course that this student did not take"):

```sql [division.sql]
CREATE TABLE Core (course_code TEXT);
INSERT INTO Core VALUES ('CS201'), ('CS202');

SELECT DISTINCT e.student_id
FROM   Enrolment e
WHERE  NOT EXISTS (
         SELECT 1 FROM Core c
         WHERE  NOT EXISTS (SELECT 1 FROM Enrolment x
                            WHERE x.student_id = e.student_id AND x.course_code = c.course_code));
```

```text [Output]
student_id
----------
1
3
```

Students 1 and 3 took both core courses; student 2 took only CS201.

## Real use case

One query, written both ways: "names of CSE students enrolled in CS202".

::code-trace{caption="Relational algebra, read inside out, and the SQL it becomes."}
```text [query.txt]
π full_name ( σ department='CSE' ∧ course_code='CS202' ( Student ⋈ Enrolment ) )

SELECT DISTINCT s.full_name
FROM   Student s JOIN Enrolment e ON e.student_id = s.student_id
WHERE  s.department = 'CSE' AND e.course_code = 'CS202';
```

  :::code-trace-step{lines="1" caption="Innermost: join Student and Enrolment on student_id."}
  :::
  :::code-trace-step{lines="1" caption="Then σ keeps rows where department is CSE and the course is CS202 (∧ means AND)."}
  :::
  :::code-trace-step{lines="1" caption="Then π keeps only full_name, removing duplicates."}
  :::
  :::code-trace-step{lines="3-5" caption="The same three steps as SQL: JOIN, WHERE, SELECT DISTINCT."}
  :::
::

```sql [both-ways.sql]
SELECT DISTINCT s.full_name
FROM   Student s JOIN Enrolment e ON e.student_id = s.student_id
WHERE  s.department = 'CSE' AND e.course_code = 'CS202';
```

```text [Output]
full_name
----------
Anita Rao
Priya Nair
```

This is also how an optimiser improves your query. The expression above joins
first and filters second. An equivalent, cheaper tree **pushes the selection
down**: π _full_name_ ( σ _department='CSE'_ (Student) ⋈ σ _course_code='CS202'_
(Enrolment) ). Filtering each table before the join means joining fewer rows.
Same answer, less work. The planner does this for you, which is why the order of
conditions in your `WHERE` rarely matters.

## What confuses people here

- **Selection is not SQL's SELECT.** σ (selection) is SQL's `WHERE`. SQL's
  `SELECT` list is π (projection). The names clash; the table at the top is the
  fix.
- **Projection removes duplicates; SQL does not** unless you write `DISTINCT`.
- **Natural join joins on every common column name.** If both tables also had a
  `created_on` column, the natural join would silently require it to match too.
- **Relational algebra is procedural; SQL is declarative.** An algebra expression
  says in what order to apply operators. SQL says what you want; the database
  picks the order. (Relational **calculus**, tuple and domain, is the declarative
  formal language, and knowing that it exists is enough.)

## Interview questions

::accordion
  :::accordion-item{label="What is relational algebra?" icon="i-lucide-message-circle"}
  A procedural query language of operators that take relations and return
  relations: selection, projection, union, set difference, Cartesian product and
  rename as the fundamental ones, plus join, intersection and division. It is the
  internal form the query optimiser works on.
  :::
  :::accordion-item{label="Selection vs projection?" icon="i-lucide-message-circle"}
  Selection (σ) chooses rows that satisfy a condition, like `WHERE`. Projection
  (π) chooses columns and removes duplicate rows, like `SELECT DISTINCT` with a
  column list.
  :::
  :::accordion-item{label="What is a natural join? How is it different from an equi-join?" icon="i-lucide-message-circle"}
  A natural join joins on all attributes with the same name and keeps one copy
  of each. An equi-join joins on equality conditions you specify and keeps both
  copies of the join columns. A natural join is an equi-join on all common
  attributes, followed by a projection.
  :::
  :::accordion-item{label="What is the division operator used for?" icon="i-lucide-message-circle"}
  "For all" queries: find the entities related to every row of another relation,
  such as students who took all core courses. SQL expresses it with a double
  `NOT EXISTS`, or with `GROUP BY student_id HAVING COUNT(DISTINCT course_code) =
  (SELECT COUNT(*) FROM Core)` restricted to core courses.
  :::
  :::accordion-item{label="What are the fundamental operators of relational algebra?" icon="i-lucide-message-circle"}
  Selection, projection, union, set difference, Cartesian product and rename.
  Intersection, join and division can be expressed using them.
  :::
::
