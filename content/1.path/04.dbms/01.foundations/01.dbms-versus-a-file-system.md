The SQL track ended with you able to ask a database anything and defend the
answer. The next round of an interview asks something different: **why** it
works that way. It nearly always starts here: "What is a DBMS, and why not keep
the data in files?"

## Why this matters in a job

"We have an Excel sheet that works. Why would we move to a database?" is a real
question real clients ask, and every answer below is a feature this track covers
in depth. In the walk-ins I went to, "DBMS versus file system" was the most
common opening DBMS question, and a list of adjectives ("faster, more secure")
was the most common weak answer. The strong answer names the failures.

## Five ways a spreadsheet fails

Here is a college's admissions spreadsheet. It is reasonable, and plenty of real
colleges have run on one.

| Student | Email | Course | Department | Head of department | Marks | Fee paid |
| --- | --- | --- | --- | --- | --- | --- |
| Anita Rao | anita@… | CS201 | Computer Science | Dr. Meera Joshi | 87 | 42500 |
| Rahul Verma | rahul@… | CS201 | Computer Science | Dr. Meera Joshi | 64 | 42500 |
| Anita Rao | anita@… | EC201 | Electronics | Dr. Suresh Rao | 78 | 42500 |
| Priya Nair | priya@… | CS201 | Computer Science | Dr. Meera Jooshi | 91 | 0 |

Look at the last row's head of department: `Dr. Meera Jooshi`. Nobody will notice,
and any count grouped by head of department now reports two people.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-copy" title="1. Redundancy and inconsistency"}
  "The head of CSE is Dr. Meera Joshi" is written on every CSE row. Change it
  once and you must change it everywhere, and you will miss one. The copies
  disagree, and nothing tells you which is right.
  :::
  :::feature{icon="i-lucide-shield-off" title="2. No integrity"}
  A spreadsheet accepts marks of 780, a blank email, a course that does not
  exist. Nothing enforces a rule.
  :::
  :::feature{icon="i-lucide-users" title="3. No safe concurrency"}
  Two clerks editing at once overwrite each other's work, and neither knows.
  :::
  :::feature{icon="i-lucide-search-x" title="4. Hard to query"}
  "Which department has the most students with a backlog?" needs somebody to
  build the answer by hand, and a program to be written for every new question.
  :::
  :::feature{icon="i-lucide-lock-open" title="5. No security or recovery"}
  Whoever opens the file sees every column, fees included. A half-saved file
  after a power cut can be corrupt, with no log to recover from.
  :::
::

## What a DBMS gives you instead

A **DBMS** (database management system) is the software that stores the data and
sits between it and every program and person that uses it. Each failure above has
a feature that answers it, and each feature is a chapter of this track:

| Failure in files | What the DBMS provides | Where in this track |
| --- | --- | --- |
| Same fact stored many times | Each fact in one place, referred to by a key | Keys, normalisation |
| Nothing stops nonsense | Constraints: types, `NOT NULL`, `CHECK`, foreign keys | Keys, relational model |
| Two people at once | Transactions, locking, isolation | Transactions and concurrency |
| Hard to query, slow at scale | A query language (SQL), indexes, a query optimiser | Indexes, relational algebra |
| No security, no recovery | Users and permissions; logs, backup and crash recovery | ACID |

### The concurrency failure, drawn

Sixty seats, one left. Two clerks allot at the same moment:

::memory{kind="table" caption="Both clerks read 1 seat left. Both allot. Sixty-one students for sixty seats."}
---
columns: ["Clerk A", "Clerk B", "Seats left"]
frames:
  - label: "1. A opens the sheet"
    cells: [{ value: "reads 1", state: "active" }, { value: "" }, { value: "1" }]
  - label: "2. B opens it too, before A saves"
    cells: [{ value: "" }, { value: "reads 1", state: "active" }, { value: "1" }]
  - label: "3. A allots a seat and saves"
    cells: [{ value: "writes 0", state: "active" }, { value: "" }, { value: "0" }]
  - label: "4. B allots and saves, from the 1 it read"
    cells: [{ value: "" }, { value: "writes 0", state: "active" }, { value: "0", state: "active" }]
---
::

Two seats were allotted and the count went down by one. This is called a **lost
update**, and it is the reason the transactions chapter exists.

## How it works: the three-schema architecture

A DBMS separates **how data is seen** from **how it is stored**, in three levels.
This is asked by name in DBMS vivas and written rounds.

::flow{numbered direction="vertical" caption="The ANSI/SPARC three-schema architecture."}
  :::flow-step{label="External level (views)" icon="i-lucide-eye"}
  What each user sees. The placement cell sees names and CGPA; accounts sees
  fees. Many external schemas, one per kind of user. In SQL: views and grants.
  :::
  :::flow-step{label="Conceptual level (logical schema)" icon="i-lucide-table-2" highlight}
  The whole database's structure: every table, column, type, key and
  relationship. One per database. In SQL: the `CREATE TABLE` statements.
  :::
  :::flow-step{label="Internal level (physical schema)" icon="i-lucide-hard-drive"}
  How it is stored on disk: files, pages, indexes, compression. One per
  database. You rarely see it.
  :::
::

The point of the levels is **data independence**:

- **Physical data independence**: change the internal level (add an index, move
  the files to a faster disk) without changing the conceptual schema or any
  query. Easy, and every DBMS gives it to you.
- **Logical data independence**: change the conceptual level (split a table,
  add a column) without changing the external views and the programs using them.
  Harder; views are the tool.

With files there is no such separation: the program that reads the file knows
exactly how it is laid out, and changing the layout means changing the program.

::runner{lang="sql"}
```sql [external-view.sql]
-- Conceptual level: the real table.
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department TEXT,
                      cgpa REAL, phone TEXT, fee_due INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'CSE', 8.7, '9876543210', 0),
  (2, 'Rahul Verma', 'ECE', 6.4, '9123456780', 21250);

-- External level: what the placement cell sees.
CREATE VIEW placement_view AS SELECT full_name, department, cgpa FROM Student;

-- Internal level changes (a new index); nothing above it notices.
CREATE INDEX idx_student_cgpa ON Student (cgpa);

SELECT * FROM placement_view ORDER BY cgpa DESC;
```
::

```text [Output]
full_name    department  cgpa
-----------  ----------  ----
Anita Rao    CSE         8.7
Rahul Verma  ECE         6.4
```

The index changed how the data is stored and found. The view, and anyone querying
it, did not change at all. That is physical data independence in one line.

## Real use case

A typical college moves from a shared admissions spreadsheet to a database for
one reason: the week the intake doubles, six people are editing, and two allot
the same seat on the same afternoon. The replacement is not "a better
spreadsheet". It is a set of tables with rules the database enforces on every
write, from every program:

::runner{lang="sql"}
```sql [rules-not-cells.sql]
PRAGMA foreign_keys = ON;
CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE,
                         head TEXT NOT NULL);
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT NOT NULL,
                      email TEXT NOT NULL UNIQUE,
                      department_id INTEGER NOT NULL REFERENCES Department (department_id));
INSERT INTO Department VALUES (1, 'Computer Science', 'Dr. Meera Jooshi');   -- typed wrong, once
INSERT INTO Student VALUES (1, 'Anita Rao', 'anita@college.edu', 1), (2, 'Priya Nair', 'priya@college.edu', 1);

-- The head's name is stored once. Fix it once, and every student row is right.
UPDATE Department SET head = 'Dr. Meera Joshi' WHERE department_id = 1;

SELECT s.full_name, d.name, d.head
FROM   Student s JOIN Department d ON d.department_id = s.department_id;
```
::

```text [Output]
full_name   name              head
----------  ----------------  ---------------
Anita Rao   Computer Science  Dr. Meera Joshi
Priya Nair  Computer Science  Dr. Meera Joshi
```

The typo was made once and fixed once, and every student row is right, because
there is only one place the name is written. And a second student with Anita's email, or a student in a department
that does not exist, is refused by the database itself.

## What confuses people here

- **"A database is where you put data."** It is a program that enforces rules and
  arbitrates between users. Storing is the least interesting thing it does.
- **DBMS is not the database.** The database is the data; the DBMS is the
  software (MySQL, Oracle). "The college's database runs on MySQL."
- **Files are not always wrong.** A log file, a configuration file, a CSV export
  for one person: files are fine when there is one writer, no rules and no
  questions to ask. A DBMS earns its cost when there are many users, rules and
  questions.
- **Disadvantages exist.** A DBMS costs money or expertise to run, needs backups
  and upgrades, and is overkill for tiny data. Saying so shows judgement.

## Interview questions

::accordion
  :::accordion-item{label="What is a DBMS? What are its advantages over a file system?" icon="i-lucide-message-circle"}
  Software that stores data and controls every access to it. Over files it
  gives: controlled redundancy and consistency, integrity constraints, safe
  concurrent access through transactions, a query language with indexes, and
  security plus backup and recovery. Give the lost-seat example for concurrency.
  :::
  :::accordion-item{label="What are the disadvantages of a DBMS?" icon="i-lucide-message-circle"}
  Cost (licences, hardware, skilled people), complexity, a single point of
  failure unless replicated, and overhead that is wasted on small, single-user
  data. Files are fine for a log or a one-off export.
  :::
  :::accordion-item{label="Explain the three-schema architecture." icon="i-lucide-message-circle"}
  External (the views each user sees), conceptual (the logical structure of the
  whole database) and internal (physical storage). It separates how data is seen
  from how it is stored, which gives data independence.
  :::
  :::accordion-item{label="What is data independence? Physical vs logical?" icon="i-lucide-message-circle"}
  Changing one level without changing the level above. Physical: change storage
  (add an index) without changing the schema or queries. Logical: change the
  schema (split a table) without changing views and applications. Physical is
  easier to achieve.
  :::
  :::accordion-item{label="What is the difference between a database, a DBMS and a database system?" icon="i-lucide-message-circle"}
  The database is the organised data. The DBMS is the software managing it. The
  database system is both together, plus the applications that use them.
  :::
::
