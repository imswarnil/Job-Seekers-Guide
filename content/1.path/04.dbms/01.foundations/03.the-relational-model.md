An ER diagram is a picture. The tables it turns into obey a small, precise piece
of mathematics, the **relational model**, and interviewers use its vocabulary
without warning: "what is the degree of this relation?", "what is a tuple?",
"what is referential integrity?"

## Why this matters in a job

The words matter because they are exact. "Cardinality" means one thing in an ER
diagram (1:N) and another for a relation (the number of rows), and confusing the
two in a viva sounds like memorising. The rules matter more: entity integrity and
referential integrity are the reason primary and foreign keys exist, and they are
what the database is enforcing every time it refuses one of your inserts.

## A table is a relation

In 1970 E. F. Codd, a researcher at IBM, proposed storing data as
**relations**: sets of rows with the same columns, manipulated with a small set
of mathematical operations. Every RDBMS since, from Oracle to SQLite, is built on
that idea. A table is the everyday name for a relation.

  - label: "Tuple 2"

  - label: "Tuple 3"

| Relational term | Everyday term | In the example |
| --- | --- | --- |
| **Relation** | Table | `Student` |
| **Tuple** | Row, record | (2, Rahul Verma, Patna, 2024) |
| **Attribute** | Column, field | `city` |
| **Domain** | The set of allowed values for an attribute | `admission_year`: whole numbers 2000 to 2100 |
| **Degree (arity)** | Number of attributes | 4 |
| **Cardinality** | Number of tuples | 3 |
| **Relation schema** | The table's definition | Student(student_id, full_name, city, admission_year) |
| **Relation instance** | The rows in it right now | The three rows above |

**Schema against instance** is asked often. The schema is the design and changes
rarely (a new column once a year). The instance is the data and changes every
second. Like a form template against the filled-in forms.

## How it works: the properties of a relation

Because a relation is a mathematical **set** of tuples, it has properties a
spreadsheet does not:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-copy-x" title="No duplicate tuples"}
  A set cannot contain the same element twice. This is why every relation needs
  a key.
  :::
  :::feature{icon="i-lucide-shuffle" title="Row order does not matter"}
  There is no "first row". This is why `ORDER BY` is needed and `LIMIT` without it
  is meaningless.
  :::
  :::feature{icon="i-lucide-columns-3" title="Column order does not matter"}
  Attributes are identified by name, not position. Why `SELECT *` into a fixed
  column order is fragile.
  :::
  :::feature{icon="i-lucide-atom" title="Every value is atomic"}
  One value per cell, from the attribute's domain. No lists in a cell. This is
  the first normal form, in the next chapter.
  :::
::

::note
SQL tables bend the first rule: a table without a primary key can hold two
identical rows, and `SELECT` without `DISTINCT` can return duplicates. That is a
practical compromise in SQL, and one reason every table you design should have a
key.
::

## The two integrity rules

These are the rules keys exist to enforce, and "what is referential integrity?"
is one of the most asked DBMS questions.

::compare{caption="Two rules, two kinds of key."}
  :::compare-side{label="Entity integrity" verdict="right"}
  The **primary key** of every tuple must be unique and **never NULL**. A row with
  no identity cannot be referred to, updated or deleted reliably.
  :::
  :::compare-side{label="Referential integrity" verdict="right"}
  Every **foreign key** value must either match an existing primary key in the
  referenced relation, or be `NULL` (if allowed). No result for a student who does
  not exist.
  :::
::

::runner{lang="sql"}
```sql [integrity-rules.sql]
PRAGMA foreign_keys = ON;
CREATE TABLE Student (student_id INTEGER PRIMARY KEY NOT NULL, full_name TEXT NOT NULL);
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY,
                         student_id INTEGER NOT NULL REFERENCES Student (student_id),
                         marks INTEGER CHECK (marks BETWEEN 0 AND 100));   -- domain constraint
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma');
INSERT INTO ExamResult VALUES (1, 1, 87), (2, 2, 64);

-- Degree and cardinality of the instance, asked of the database itself.
SELECT COUNT(*) AS cardinality FROM ExamResult;
SELECT COUNT(*) AS degree FROM pragma_table_info('ExamResult');
```
::

```text [Output]
cardinality
-----------
2

degree
------
3
```

Now break each rule:

```sql [integrity-setup.sql]
PRAGMA foreign_keys = ON;
CREATE TABLE Student (student_id INTEGER PRIMARY KEY NOT NULL, full_name TEXT NOT NULL);
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY,
                         student_id INTEGER NOT NULL REFERENCES Student (student_id),
                         marks INTEGER CHECK (marks BETWEEN 0 AND 100));
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma');
```

::tabs
  :::tabs-item{label="Entity integrity"}
  ```sql [duplicate-key.sql]
  INSERT INTO Student VALUES (1, 'Another Anita');
  ```

  ```text [Output]
  Error: UNIQUE constraint failed: Student.student_id
  ```
  :::
  :::tabs-item{label="Referential integrity"}
  ```sql [orphan.sql]
  INSERT INTO ExamResult VALUES (3, 99, 70);
  ```

  ```text [Output]
  Error: FOREIGN KEY constraint failed
  ```
  :::
  :::tabs-item{label="Domain constraint"}
  ```sql [out-of-domain.sql]
  INSERT INTO ExamResult VALUES (3, 1, 140);
  ```

  ```text [Output]
  Error: CHECK constraint failed: marks BETWEEN 0 AND 100
  ```
  :::
::

## Real use case

A college migrates student records from an old system into a new database. The
migration script is a practical test of every rule above: rows without an id
(entity integrity), results pointing at students who were deleted years ago
(referential integrity), marks typed as "AB" for absent (domain). A good
migration does not switch the constraints off to make the errors go away; it
counts each kind of violation first:

::runner{lang="sql"}
```sql [migration-check.sql]
CREATE TABLE OldStudent (student_id INTEGER, full_name TEXT);
INSERT INTO OldStudent VALUES (1, 'Anita Rao'), (2, 'Rahul Verma'), (NULL, 'Unknown'), (2, 'Rahul V.');
CREATE TABLE OldResult (student_id INTEGER, marks TEXT);
INSERT INTO OldResult VALUES (1, '87'), (2, '64'), (7, '55'), (1, 'AB');

SELECT 'missing id (entity integrity)'       AS problem, COUNT(*) AS n_rows FROM OldStudent WHERE student_id IS NULL
UNION ALL
SELECT 'duplicate id (entity integrity)',    COUNT(*) - COUNT(DISTINCT student_id) FROM OldStudent WHERE student_id IS NOT NULL
UNION ALL
SELECT 'orphan result (referential)',        COUNT(*) FROM OldResult r
       WHERE NOT EXISTS (SELECT 1 FROM OldStudent s WHERE s.student_id = r.student_id)
UNION ALL
SELECT 'marks not a number (domain)',        COUNT(*) FROM OldResult WHERE marks GLOB '*[^0-9]*';
```
::

```text [Output]
problem                          n_rows
-------------------------------  ------
missing id (entity integrity)    1
duplicate id (entity integrity)  1
orphan result (referential)      1
marks not a number (domain)      1
```

Four kinds of problem, each with a count and a name from this lesson. Each goes to
whoever owns the data with a decision to make: is "AB" absent (`NULL`) or zero?
Is student 7 real?

## What confuses people here

- **Two meanings of cardinality.** In an ER diagram it is the ratio of a
  relationship (1:N). For a relation it is the number of tuples. Say which you
  mean.
- **Degree is columns, cardinality is rows.** Easy to swap under pressure.
  Degree is fixed by the schema; cardinality changes with every insert.
- **Relation is not relationship.** A relation is a table. A relationship is an
  association between entities in an ER diagram. An M:N relationship becomes a
  relation of its own.
- **A foreign key may be NULL** (unless you add `NOT NULL`), and that does not
  break referential integrity: it means "not linked to anything yet".

## Interview questions

::accordion
  :::accordion-item{label="What is a relation, tuple, attribute and domain?" icon="i-lucide-message-circle"}
  A relation is a table: a set of tuples with the same attributes. A tuple is a
  row. An attribute is a named column. A domain is the set of values an attribute
  may take (marks: whole numbers 0 to 100).
  :::
  :::accordion-item{label="What are the degree and cardinality of a relation?" icon="i-lucide-message-circle"}
  Degree is the number of attributes (columns); cardinality is the number of
  tuples (rows). `ExamResult` above has degree 3 and cardinality 2.
  :::
  :::accordion-item{label="What is the difference between a schema and an instance?" icon="i-lucide-message-circle"}
  The schema is the structure (relation names, attributes, types, keys) and
  changes rarely. The instance is the data at a moment and changes constantly.
  :::
  :::accordion-item{label="What is referential integrity?" icon="i-lucide-message-circle"}
  The rule that a foreign key value must match an existing primary key in the
  referenced table, or be `NULL`. It is enforced by a `FOREIGN KEY` constraint:
  inserting a result for student 99, who does not exist, fails.
  :::
  :::accordion-item{label="What is entity integrity?" icon="i-lucide-message-circle"}
  The rule that a primary key is unique and never `NULL`, so every tuple can be
  identified. Enforced by the `PRIMARY KEY` constraint.
  :::
  :::accordion-item{label="Who proposed the relational model?" icon="i-lucide-message-circle"}
  E. F. Codd at IBM, in 1970. His later "12 rules" describe what a system must do
  to be fully relational; knowing that they exist is enough at fresher level.
  :::
::
