Entity integrity needs a key, and a table usually has several columns that could
be one: the student id, the email, the university roll number. Which one is the
primary key, and what are the others called? Keys are how a database tells one
row from another and how one row points at another, and getting them wrong is
the most expensive design mistake there is, because everything else is built on
top.

## Why this matters in a job

"What is the difference between a primary key and a unique key?" and "what is a
super key?" are asked in essentially every DBMS round. Written tests (and GATE,
if you ever sit it) ask you to count the super keys of a relation. At work, the
choice of primary key is one of the few decisions that is genuinely hard to
change later.

## The family of keys

Take one relation:
`Student(student_id, email, roll_number, full_name, city)`. `student_id`, `email`
and `roll_number` are each unique for every student and never empty. `full_name`
and `city` are not unique.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-layers" title="Super key"}
  **Any** set of attributes that uniquely identifies a tuple, even with extra
  attributes along for the ride. {student_id}, {student_id, city} and
  {email, full_name} are all super keys.
  :::
  :::feature{icon="i-lucide-key" title="Candidate key"}
  A **minimal** super key: remove any attribute and it stops being unique.
  {student_id}, {email}, {roll_number}. {student_id, city} is not minimal.
  :::
  :::feature{icon="i-lucide-key-round" title="Primary key"}
  The candidate key you **choose** as the table's identity. One per table, never
  `NULL`. Usually {student_id}.
  :::
  :::feature{icon="i-lucide-key-square" title="Alternate key"}
  The candidate keys you did not choose: {email}, {roll_number}. Enforced with
  `UNIQUE`.
  :::
  :::feature{icon="i-lucide-combine" title="Composite key"}
  A key with more than one attribute: {student_id, course_id} in Enrolment.
  :::
  :::feature{icon="i-lucide-link" title="Foreign key"}
  An attribute that refers to another relation's primary (or candidate) key.
  `ExamResult.student_id`.
  :::
::

## How it works: finding and counting keys

### Worked example 1: every super key of a small relation

`Student(student_id, email, full_name, city)` with candidate keys {student_id}
and {email}. A set is a super key if it **contains at least one candidate key**.

- Supersets of {student_id}: the other 3 attributes can each be in or out, so
  2³ = **8**.
- Supersets of {email}: likewise **8**.
- Counted twice, supersets of **both** {student_id, email}: the other 2 can be in
  or out, 2² = **4**.
- Super keys = 8 + 8 − 4 = **12**.

This inclusion-exclusion count is a standard written-test question. With one
candidate key of k attributes in a relation of n attributes, the answer is
2^(n−k).

### Worked example 2: a composite candidate key

`Enrolment(student_id, course_id, semester, grade)`. A student appears many
times, and so does a course, so neither alone is unique. The pair is:

::runner{lang="sql"}
```sql [composite-key.sql]
CREATE TABLE Enrolment (student_id INTEGER, course_id INTEGER, semester TEXT, grade TEXT,
                        PRIMARY KEY (student_id, course_id));
INSERT INTO Enrolment VALUES
  (1, 101, '2025-ODD', 'A'), (1, 102, '2025-ODD', 'B'), (2, 101, '2025-ODD', 'C');

-- Is student_id alone unique? Is course_id? Is the pair?
SELECT COUNT(*) AS n_rows,
       COUNT(DISTINCT student_id)                  AS distinct_students,
       COUNT(DISTINCT course_id)                   AS distinct_courses,
       COUNT(DISTINCT student_id || '-' || course_id) AS distinct_pairs
FROM   Enrolment;
```
::

```text [Output]
n_rows  distinct_students  distinct_courses  distinct_pairs
------  -----------------  ----------------  --------------
3       2                  2                 3
```

Three rows, three distinct pairs: the pair identifies each row, and neither half
does. And it is minimal: drop either column and uniqueness is lost. So
{student_id, course_id} is a candidate key, and a composite one.

::warning{icon="i-lucide-alert-triangle"}
Uniqueness in today's data is evidence, not proof. A candidate key is decided by
**the rules of the domain** ("a student can enrol in a course only once"), not by
what the current rows happen to contain. Three rows where `full_name` is unique
do not make `full_name` a key.
::

## Primary key or unique key

| | Primary key | Unique key |
| --- | --- | --- |
| How many per table | Exactly one | As many as you like |
| `NULL` allowed | Never | Usually yes (several `NULL`s in most databases) |
| What refers to it | Foreign keys | Rarely |
| Default index | Clustered in MySQL InnoDB and SQL Server | Non-clustered |
| Meaning | "This is how the row is identified" | "No two rows may share this" |

::runner{lang="sql"}
```sql [primary-vs-unique.sql]
CREATE TABLE Student (
  student_id   INTEGER PRIMARY KEY,
  email        TEXT NOT NULL UNIQUE,    -- alternate key
  roll_number  TEXT UNIQUE,             -- alternate key, may be NULL until allotted
  full_name    TEXT NOT NULL
);
INSERT INTO Student VALUES (1, 'anita@college.edu', 'CS24-001', 'Anita Rao');
INSERT INTO Student VALUES (2, 'rahul@college.edu', NULL, 'Rahul Verma');
INSERT INTO Student VALUES (3, 'priya@college.edu', NULL, 'Priya Nair');   -- two NULLs: allowed

SELECT * FROM Student;
```
::

```text [Output]
student_id  email              roll_number  full_name
----------  -----------------  -----------  -----------
1           anita@college.edu  CS24-001     Anita Rao
2           rahul@college.edu  NULL         Rahul Verma
3           priya@college.edu  NULL         Priya Nair
```

`roll_number` shows why the distinction matters: it must be unique where present,
and students not yet allotted one must still be storable, which a primary key
could never allow.

## Real use case

The argument you will have on every schema: should the primary key be a
meaningful value from the real world (a **natural key**) or a generated number
with no meaning (a **surrogate key**)?

::compare{caption="Should the university roll number be the primary key?"}
  :::compare-side{label="Natural key: roll number" verdict="wrong"}
  Meaningful, already unique, saves a column. Then the university changes the
  roll-number format to include the campus code, and that value is copied as a
  foreign key into results, attendance, fees and placements. Every one must
  change, together, and anything outside the database that stored the old value
  is now wrong.
  :::
  :::compare-side{label="Surrogate key: student_id" verdict="right"}
  `student_id INTEGER PRIMARY KEY`, generated by the database. Meaningless, so
  nothing outside has an opinion about it, so it never has to change. The roll
  number is still a column, still `UNIQUE`, still searchable. It is not what
  other tables point at.
  :::
::

The question that settles it: **could this value ever need to change?** Emails
change, names change, roll-number formats change, even Aadhaar numbers are
occasionally reissued. If the answer is "possibly", it is not the primary key.

## What confuses people here

- **Super key vs candidate key.** Every candidate key is a super key; not every
  super key is a candidate key. Candidate means minimal.
- **Composite key vs candidate key.** Different axes. "Composite" is about size
  (more than one attribute); "candidate" is about minimality. {student_id,
  course_id} is both.
- **A foreign key does not have to be unique.** Many results point at the same
  student; that is the point of a 1:N relationship.
- **A foreign key can reference a unique key**, not only a primary key, in most
  databases. It is rare, and legal.
- **Primary key does not mean "first column" or "auto-increment".** It is a
  constraint on values. Auto-increment is one way to generate a surrogate.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between a super key, a candidate key and a primary key?" icon="i-lucide-message-circle"}
  A super key is any set of attributes that uniquely identifies a tuple. A
  candidate key is a minimal super key. The primary key is the candidate key
  chosen as the table's identity. Every primary key is a candidate key; every
  candidate key is a super key.
  :::
  :::accordion-item{label="Primary key vs unique key?" icon="i-lucide-message-circle"}
  Both prevent duplicates. A primary key allows no `NULL`, there is one per
  table, and foreign keys point at it. A unique key allows `NULL`, a table can
  have several, and it marks an alternate key.
  :::
  :::accordion-item{label="What is an alternate key?" icon="i-lucide-message-circle"}
  A candidate key that was not chosen as the primary key. `email` and
  `roll_number` in `Student`. Enforce it with `UNIQUE` (and `NOT NULL` if it must
  always be present).
  :::
  :::accordion-item{label="R(A, B, C, D) has candidate keys A and B. How many super keys?" icon="i-lucide-message-circle"}
  Supersets of {A}: 2³ = 8. Of {B}: 8. Of both: 2² = 4. Total 8 + 8 − 4 = 12.
  :::
  :::accordion-item{label="What is a composite key? Give an example." icon="i-lucide-message-circle"}
  A key of two or more attributes where only the combination is unique.
  Enrolment(student_id, course_id): a student has many enrolments and a course has
  many, but each pair occurs once.
  :::
  :::accordion-item{label="Natural key or surrogate key?" icon="i-lucide-message-circle"}
  Usually surrogate as the primary key, with the natural key kept as a `UNIQUE`
  alternate key. Natural keys can change, and a primary key is copied into every
  table that refers to it. Ask "could this ever change?"; if yes, it is not the
  primary key.
  :::
::
