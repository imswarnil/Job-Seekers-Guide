Six questions answered. These six are the code, and two of them are the ways
people turn TypeScript off without noticing they have.

## 1. The `any` that spreads

```ts
async function loadApplications(): Promise<any> {
  const res = await fetch("/api/applications");
  return res.json();
}

const apps = await loadApplications();
apps.forEach(a => console.log(a.applicantName));   // no error, ever
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `any` disables checking for everything it touches, and it spreads: `apps` is
  `any`, so `a` is `any`, so `a.applicantName` is unchecked, and so is
  `a.aplicantName` with the typo.

  ```ts
  type Application = {
    applicationId: number
    applicantName: string
    status: "RECEIVED" | "UNDER_REVIEW" | "SHORTLISTED" | "REJECTED" | "ACCEPTED"
    score: number | null
  }

  async function loadApplications(): Promise<Application[]> {
    const res = await fetch("/api/applications")
    if (!res.ok) throw new Error(`${res.status}`)
    return res.json() as Promise<Application[]>
  }
  ```

  Note `score: number | null`. An unmarked application has no score, and the
  type says so, which forces every caller to handle it.

  And set `"noImplicitAny": true` in `tsconfig.json`. Without it, TypeScript
  silently inserts `any` in the places you forgot, which is the default you
  least want.
  :::
::

## 2. The type that is a lie

```ts
const res = await fetch("/api/applications")
const apps = await res.json() as Application[]
```

`as` compiles. What is wrong with it?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `as` is an assertion, not a check. You are telling the compiler "trust me",
  and nothing verifies it at runtime. If the API changes `score` to a string,
  or returns `{ error: "..." }`, TypeScript still believes you and the failure
  appears three functions later as `undefined is not a function`.

  **Types are erased at compile time.** They cannot check data that arrives
  while the program is running, which is exactly where wrong data comes from.

  Validate at the boundary:

  ```ts
  import { z } from "zod"

  const Application = z.object({
    applicationId: z.number(),
    applicantName: z.string(),
    status: z.enum(["RECEIVED","UNDER_REVIEW","SHORTLISTED","REJECTED","ACCEPTED"]),
    score: z.number().nullable(),
  })

  const apps = z.array(Application).parse(await res.json())
  ```

  Now a wrong shape fails loudly at the point it arrives, with a message naming
  the field, and `apps` is correctly typed from the schema.

  The rule: **`as` for things you know and the compiler cannot; a validator for
  anything crossing a boundary.**
  :::
::

## 3. The optional that is not

```ts
type Applicant = {
  fullName: string
  phone?: string
}

function ring(a: Applicant) {
  console.log(a.phone.trim())    // error, good
}
```

Fix it three ways and say which is right.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  ```ts
  a.phone!.trim()            // 1. assertion: "trust me". Same lie as `as`.
  a.phone?.trim()            // 2. optional chaining: undefined if absent
  if (a.phone) a.phone.trim()  // 3. narrowing: the compiler now knows
  ```

  **1 is wrong.** `!` silences the compiler and the crash still happens.

  **2 and 3 are both right**, and which one depends on what should happen. If
  "no phone number" is a normal state, `?.` and handle the `undefined`. If it
  means something is wrong, narrow and say so:

  ```ts
  if (!a.phone) throw new Error(`No phone for applicant ${a.fullName}`)
  a.phone.trim()
  ```

  The habit: when the compiler objects, ask what it knows that you do not,
  rather than looking for the shortest way to make it stop.
  :::
::

## 4. The status that accepts anything

```ts
function setStatus(id: number, status: string) { ... }
setStatus(9001, "SHORTLSTED")     // typo, compiles fine
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `string` accepts every string. A union accepts five.

  ```ts
  type Status = "RECEIVED" | "UNDER_REVIEW" | "SHORTLISTED" | "REJECTED" | "ACCEPTED"
  function setStatus(id: number, status: Status) { ... }
  ```

  Now the typo is an error at the point it was typed, with the five valid values
  listed.

  Then the thing that makes it genuinely valuable: **exhaustiveness**.

  ```ts
  function label(s: Status): string {
    switch (s) {
      case "RECEIVED":     return "Received"
      case "UNDER_REVIEW": return "Under review"
      case "SHORTLISTED":  return "Shortlisted"
      case "REJECTED":     return "Rejected"
      case "ACCEPTED":     return "Accepted"
      default: { const _never: never = s; return _never }
    }
  }
  ```

  Add a sixth status to the union and this function stops compiling, pointing
  at the missing case. That is a compiler finding every place a new value needs
  handling, which is the single most useful thing TypeScript does.
  :::
::

## 5. The two ids that are the same type

```ts
function enrol(studentId: number, programId: number) { ... }
enrol(programId, studentId)    // compiles. Wrong students, wrong programmes.
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  Both are `number`, so the compiler cannot tell them apart.

  ```ts
  type StudentId = number & { readonly __brand: "StudentId" }
  type ProgramId = number & { readonly __brand: "ProgramId" }

  function enrol(studentId: StudentId, programId: ProgramId) { ... }
  ```

  Now swapping them is an error. This is called a **branded** or **nominal**
  type, it costs nothing at runtime because the brand is erased, and it is worth
  it exactly where two values of the same primitive type must never be
  confused: ids, currencies, and anything measured in different units.

  Worth knowing about rather than using everywhere. Mentioning it in an
  interview when asked "what do you like about TypeScript" is a good answer
  because almost nobody does.
  :::
::

## 6. The interface nobody can extend

```ts
type Props = {
  applications: Application[]
  onSelect: (id: number) => void
}
```

The same component now needs to render students as well.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  ```ts
  type ListProps<T> = {
    items: T[]
    keyOf: (item: T) => number
    renderRow: (item: T) => ReactNode
    onSelect: (id: number) => void
  }
  ```

  A generic parameter, so the same component works for applications, students
  and faculty, and the compiler still checks each usage properly: `renderRow`
  for an `Application` list receives an `Application`, not an `any`.

  What to avoid: `items: Application[] | Student[]`, which forces a type check
  inside the component and grows every time a new kind is added.

  The principle, and it is the same one from the Java generics lesson: **a
  generic says "whatever you put in, you get back", and that is what preserves
  the type through the component.**
  :::
::

## The two ways people switch it off

::feature-list{columns="2"}
  :::feature{icon="i-lucide-circle-slash" title="any"}
  Disables checking for everything it touches, and it spreads outward silently.
  If you need an escape hatch, use `unknown`: it forces you to narrow before
  doing anything, which is the whole point.
  :::
  :::feature{icon="i-lucide-triangle-alert" title="as and !"}
  Both are assertions, neither is a check. They tell the compiler to stop
  arguing, and the runtime does not care what you told the compiler.
  :::
::

::pull-quote
TypeScript checks the code you wrote, not the data you receive. Everything
crossing a boundary, an API, a form, a query string, `localStorage`, needs a
runtime validator, and a type is not one.
::
