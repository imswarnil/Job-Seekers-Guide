A typo in a property name found by a user rather than by a compiler, after
sixteen weeks in a language that would not have allowed it. TypeScript is that
compiler, added on top.

## Why this matters in a job

Because most professional JavaScript is now TypeScript, and because the one thing
people get wrong about it is genuinely dangerous: they believe a type is a
guarantee at run time, and it is not.

## What it is

TypeScript is JavaScript with type annotations, checked before it runs and then
**removed**. The browser never sees a type.

```typescript [applicant.ts]
interface Applicant {
  id: number;
  fullName: string;
  email: string;
  score: number | null;          // explicitly: might not be marked
  withdrawn: boolean;
}

function shortlist(applications: Application[], cutoff: number): Applicant[] {
  return applications
    .filter(a => !a.withdrawn)
    .filter(a => a.score !== null && a.score >= cutoff)
    .map(a => a.applicant);
}
```

```typescript [errors.ts]
applicant.fullname          // Property 'fullname' does not exist. Did you mean 'fullName'?
applicant.score + 1         // 'applicant.score' is possibly 'null'.
shortlist(applications)     // Expected 2 arguments, but got 1.
```

Three bugs at nine in the morning rather than three weeks later in a support
email. That is the entire value proposition.

::pull-quote
`score: number | null` is not documentation. The compiler will refuse to let you
do arithmetic on it until you have handled the null, which is the zero-versus-
missing problem finally being enforced instead of remembered.
::

## The types that earn their place

```typescript [types.ts]
// Union: one of a fixed set. This is the status ladder, enforced.
type Status = 'RECEIVED' | 'UNDER_REVIEW' | 'SHORTLISTED'
            | 'REJECTED' | 'ACCEPTED' | 'WITHDRAWN';

// A typo is now a compile error, and your editor autocompletes the six.
application.status = 'Shortlisted';   // Type '"Shortlisted"' is not assignable

// Generics: the same idea as Java's.
interface Page<T> {
  items: T[];
  total: number;
  page: number;
}
const applicants: Page<Applicant> = await fetchPage('/api/applicants');

// Utility types, which have no Java equivalent and are genuinely useful.
type NewApplicant = Omit<Applicant, 'id'>;         // everything except id
type ApplicantPatch = Partial<Applicant>;          // every field optional
type ApplicantSummary = Pick<Applicant, 'id' | 'fullName'>;
```

::tip
The union of string literals is the feature to reach for first. It turns a
`String` status into a closed set the compiler checks, autocompletes, and, with
a `switch` and no `default`, will tell you about when somebody adds a seventh
status. That is exactly the exhaustiveness argument from the Java track.
::

## The boundary, which is the whole lesson

::caution{icon="i-lucide-octagon-alert"}
**Types do not exist at run time.** They are checked and then deleted. So a type
on data arriving from outside your program is not a guarantee. It is a claim you
are making about somebody else's data, and nothing checks it.
::

```typescript [lying.ts]
// This compiles. It is also a lie waiting to happen.
const applicant: Applicant = await fetch('/api/applicants/4182')
  .then(r => r.json());        // json() returns `any`. You asserted the rest.
```

If the API returns `{ "name": "Anita" }` instead of `fullName`, TypeScript
reports nothing, because it believed you. The failure surfaces later, somewhere
unrelated, as `undefined is not a function`.

```typescript [checked.ts]
// Validate at the boundary. The type is then DERIVED from the check.
import { z } from 'zod';

const ApplicantSchema = z.object({
  id: z.number(),
  fullName: z.string().min(1),
  email: z.string().email(),
  score: z.number().min(0).max(100).nullable(),
  withdrawn: z.boolean()
});

type Applicant = z.infer<typeof ApplicantSchema>;   // one source of truth

const response = await fetch('/api/applicants/4182');
const applicant = ApplicantSchema.parse(await response.json());
// ← throws here, with a clear message, if the shape is wrong
```

Now the type and the run-time check cannot drift apart, and a change at the API
fails immediately at the boundary with a message naming the field, rather than
three layers away.

::pull-quote
Inside your program a type is a guarantee. At the edge, HTTP, a form, a file,
`localStorage`. It is a claim, and a claim needs checking.
::

## `any`, and what to use instead

```typescript [any.ts]
function process(data: any) {          // every check is now off, silently
  return data.applicants.map(a => a.fullNmae);   // no error. None.
}

function process(data: unknown) {      // safe: you must narrow it first
  if (typeof data === 'object' && data !== null && 'applicants' in data) {
    ...
  }
}
```

`any` switches off type checking for everything it touches and spreads outward
through return values. `unknown` says the same thing honestly and makes you
prove what it is.

::warning{icon="i-lucide-alert-triangle"}
`as` is an assertion, not a conversion. `const a = data as Applicant` tells the
compiler to stop checking, exactly like `any` but narrower. It is occasionally
right and it is usually somebody silencing an error they did not understand. If
you find yourself writing `as` more than rarely, the type is wrong somewhere
upstream.
::

## Configure it strictly, from day one

```json [tsconfig.json]
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noUnusedLocals": true
  }
}
```

`strict` is what makes `null` checking real. Without it, `string` silently
includes `null` and the main benefit of the language is switched off.
`noUncheckedIndexedAccess` makes `array[0]` have type `T | undefined`, which is
true and which nobody enables, and it catches the empty-array bug the Java track
found by splitting a method.

::side-note{kind="go-deeper"}
Turning `strict` on in an existing untyped codebase produces several hundred
errors and is a genuine project. Turning it on in a new one costs nothing.
Which is why the advice is always "from day one": the same setting is free now
and a fortnight later.
::

## What you can do now

You can add types that catch real mistakes, and you know the boundary where a
type stops being a guarantee, which is the thing most people using TypeScript
have not internalised.

## Your turn

::runner{lang="javascript"}
```javascript
// Type this properly. There are four decisions to make.
// (Written as JavaScript here so it runs; add the types on paper.)

function feeBalance(application) {
  const paid = application.payments.reduce((t, p) => t + p.amount, 0);
  return application.programme.fee - paid;
}

console.log(feeBalance({
  programme: { fee: 4500000 },
  payments: [{ amount: 1500000 }, { amount: 1000000 }]
}));
```
::

The four: what is an amount, what if there are no payments, what if the
programme is missing, and what does the function return.

::accordion
  :::accordion-item{label="One answer" icon="i-lucide-check"}
  ```typescript
  /** Paise. Never rupees, never a float. */
  type Paise = number;

  interface Payment { readonly amountPaise: Paise; readonly paidOn: string }

  interface Application {
    readonly programme: Programme;          // required: an application must have one
    readonly payments: readonly Payment[];  // possibly empty, never null
  }

  function feeBalance(application: Application): Paise {
    const paid = application.payments
      .reduce((total, p) => total + p.amountPaise, 0);   // [] reduces to 0
    return application.programme.feePaise - paid;
  }
  ```

  **The four decisions:**

  `Paise` as a named type rather than `number` documents the unit in the
  signature. Passing rupees is now visible in review even though the compiler
  cannot catch it, and a mixed-unit bug is the most expensive kind in fee code.

  **No payments** needs no special case: `reduce` with an initial value of 0
  handles an empty array. Writing the initial value is what makes that true, and
  omitting it throws on an empty array.

  **A missing programme** is not `Programme | undefined`. An application without
  one should not exist, so the type says it is required and the check belongs at
  the boundary where applications are loaded: the same "make it impossible
  rather than checking everywhere" argument as the Java constructor lesson.

  **`readonly`** everywhere, because a function called `feeBalance` has no
  business modifying anything, and the compiler can enforce that.
  :::
::

## The interview question this answers

**"Why TypeScript?"**

Errors at compile time rather than from a user, plus autocomplete and safe
renaming across a codebase. Then the answer that shows you have used it in anger:
types are erased, so at the boundary, HTTP, forms, storage: a type is a claim
rather than a check, and you validate there with something like Zod so the type
and the run-time check cannot drift apart.

Follow-ups to have ready: `any` disables checking and spreads, `unknown` forces
you to narrow; and `strict` from day one, because it is free in a new project and
a fortnight of work later.
