Pie charts handed you the shares. A caselet hands you a paragraph: the numbers
are all in it, but scattered across sentences, some given directly and some
given relative to others. The whole skill is building the table yourself.

## Why it matters

Caselets appear in Infosys, Capgemini, Cognizant, AMCAT-style papers and the
harder tracks of TCS, typically as three to five questions on one paragraph.
Check the current pattern. They are the slowest DI type to set up (about 90
seconds before the first question) and the fastest to answer once the table
exists, so they reward the habit of drawing before reading questions.

## What to study

| # | Type | Priority |
| --- | --- | --- |
| 1 | One-way breakdown (a total split into parts) | High |
| 2 | Two-way breakdown (courses × men/women) | High |
| 3 | Relative clues ("60 fewer than", "twice as many as") | High |
| 4 | Venn-style overlaps (students in both of two groups) | Medium |

## The method

::steps
### Draw the empty table
Rows and columns from the categories the paragraph names, plus a total row and
column.

### Fill the direct numbers
Anything stated as a plain number goes in first.

### Fill the relative numbers
"45% of", "60 fewer than", "half of". Each one fills a cell from a cell you
already have.

### Fill the rest by subtraction
Totals minus known parts. Check that rows and columns add up.
::

::tip
Do not read the questions until the table is complete and adds up. Answering
from a half-built table means rereading the paragraph for every question, and
that is where the time goes.
::

## A worked example

> A training institute has 400 students across three courses: Java, Testing
> and Web. 45% of them study Java. Testing has 60 fewer students than Java, and
> the rest study Web. 40% of the Java students are women. Testing has 50 women.
> Half of the Web students are women.

Build the table:

```text
Java     = 45% of 400        = 180
Testing  = 180 − 60          = 120
Web      = 400 − 180 − 120   = 100

Women: Java 40% of 180 = 72, Testing 50, Web 100 ÷ 2 = 50
Men:   subtract from each course
```

| Course | Women | Men | Total |
| --- | ---: | ---: | ---: |
| Java | 72 | 108 | 180 |
| Testing | 50 | 70 | 120 |
| Web | 50 | 50 | 100 |
| **Total** | **172** | **228** | **400** |

Now the questions take seconds each:

::accordion
  :::accordion-item{label="1. How many women in total?"}
  **172.**
  :::
  :::accordion-item{label="2. What percentage of Testing students are men?"}
  `70 ÷ 120 = 58.3%`.
  :::
  :::accordion-item{label="3. Ratio of men in Java to men in Web?"}
  `108 : 50 = 54 : 25`.
  :::
  :::accordion-item{label="4. Women as a percentage of all students?"}
  `172 ÷ 400 = 43%`.
  :::
::

## Common mistakes

- **Answering before the table is built.**
- **Percent of the wrong base.** "40% of the Java students" is 40% of 180, not
  of 400.
- **Not checking totals.** If the row totals do not add to 400, a cell is wrong,
  and every answer from it will be too.
- **Missing a relative clue** hidden in a subordinate clause. Underline every
  number and every "more", "fewer", "twice", "half" as you read.

## How to practise

- **Daily for a week:** one caselet from IndiaBix "Data Interpretation" or
  PrepInsta's Infosys and Capgemini pages. Time the table-building separately:
  target **90 seconds**, then **45 seconds** a question.
- **After that:** one DI set of any type every day until the mocks.
