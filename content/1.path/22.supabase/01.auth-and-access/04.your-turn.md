Questions about the managed backend, answered. These six are the checks, and
every one is a default that is convenient in a tutorial and wrong in production.

::warning{icon="i-lucide-alert-triangle"}
A managed backend makes your database reachable from the internet by design.
That is the feature. It also means a mistake that would have been invisible on
`localhost` is now a public endpoint, which is why this list exists.
::

## 1. The table with no policy

You create `ExamResult` through the dashboard and the app can read it
immediately.

::accordion
  :::accordion-item{label="What is wrong" icon="i-lucide-check"}
  If row-level security is not enabled, **the table is readable by anyone with
  the anon key**, and the anon key is in your JavaScript bundle by design. Any
  student can open the network tab, copy it, and query the whole table.

  ```sql
  ALTER TABLE ExamResult ENABLE ROW LEVEL SECURITY;
  ```

  With RLS on and no policies, the table returns nothing to everybody, which is
  the correct starting point: **deny by default, then add access.**

  ```sql
  CREATE POLICY student_reads_own ON ExamResult FOR SELECT
    USING (student_id = current_student_id());
  ```

  The check to run on every table before launch:

  ```sql
  SELECT tablename, rowsecurity FROM pg_tables
  WHERE schemaname = 'public' AND NOT rowsecurity;
  ```

  Anything this returns is public. There should be nothing in the list.
  :::
::

## 2. The key in the bundle

Your app has two keys. One is in the client code.

::accordion
  :::accordion-item{label="Which is which, and what happens if you confuse them" icon="i-lucide-check"}
  The **anon** key is public by design. It identifies the project and it is
  meant to be in the browser. It is safe **only because** RLS is enforcing
  everything, which is the point of check 1.

  The **service role** key bypasses RLS entirely. It is a superuser. It belongs
  in server-side code and nowhere else, never in an environment variable that
  is exposed to the client, and never in a repository.

  The mistake is putting the service key in a `NEXT_PUBLIC_` variable because
  something was returning no rows. It fixes the symptom by removing every
  security control at once, and it ships to every visitor.

  If a service key has ever been in client code or a commit: **rotate it
  immediately**, then fix the policy that was actually wrong.
  :::
::

## 3. The policy that lets anyone write

```sql
CREATE POLICY students_update ON Student FOR UPDATE
  USING (auth.uid() = user_id);
```

A student changes their own `program_id` to the most competitive programme.

::accordion
  :::accordion-item{label="What is wrong" icon="i-lucide-check"}
  The policy controls **which rows**, not **which columns**. The student owns
  the row, so they may update all of it, including fields that are not theirs to
  change.

  Two fixes, and use both:

  ```sql
  -- Only the columns a student may touch.
  REVOKE UPDATE ON Student FROM authenticated;
  GRANT  UPDATE (phone, address) ON Student TO authenticated;
  ```

  And a `WITH CHECK` clause, which validates the **new** row rather than the old
  one:

  ```sql
  CREATE POLICY students_update ON Student FOR UPDATE
    USING      (auth.uid() = user_id)
    WITH CHECK (auth.uid() = user_id AND program_id = (SELECT program_id FROM Student WHERE ...));
  ```

  `USING` decides which rows you may act on. `WITH CHECK` decides what the
  result is allowed to look like. Without the second, a user can update a row
  they own into a row they should not own.
  :::
::

## 4. The storage bucket that is public

Applicants upload documents. The bucket was created with the default settings.

::accordion
  :::accordion-item{label="What is wrong" icon="i-lucide-check"}
  A public bucket means every file has a permanent URL that needs no
  authentication. These are mark sheets and identity documents.

  Worse: the URLs are predictable if you named files sensibly, so somebody who
  has their own URL can guess others.

  Make it private and serve through **signed URLs** that expire:

  ```js
  const { data } = await supabase.storage
    .from("documents")
    .createSignedUrl(path, 60)      // valid for 60 seconds
  ```

  And put policies on the bucket, keyed by path:

  ```sql
  CREATE POLICY own_documents ON storage.objects FOR SELECT
    USING (bucket_id = 'documents' AND (storage.foldername(name))[1] = auth.uid()::text);
  ```

  Also cap the file size and restrict the types at the bucket level. An upload
  endpoint with neither is an invitation, and "the form only accepts PDFs" is a
  client-side claim.
  :::
::

## 5. The email confirmation that is switched off

Sign-up works instantly. Convenient in development.

::accordion
  :::accordion-item{label="What is wrong" icon="i-lucide-check"}
  Anyone can create an account claiming any email address, including a real
  student's. If any part of the system treats the email as an identity, and it
  will, that is account takeover by sign-up.

  Turn on email confirmation before launch, and add rate limiting on sign-up so
  the endpoint is not a way to send mail to arbitrary addresses on your domain's
  reputation.

  Then the wider question this raises for a university: **should students sign
  up at all?** They already exist in your `Student` table. A better model is
  accounts created by the admin and an invitation flow, so an account can only
  exist for a person who is actually enrolled.

  That answer is better than fixing the setting, and it is the sort of thing
  worth saying out loud.
  :::
::

## 6. The realtime subscription that leaks

```js
supabase.channel("applications")
  .on("postgres_changes", { event: "*", table: "Application" }, handleChange)
  .subscribe()
```

::accordion
  :::accordion-item{label="What is wrong" icon="i-lucide-check"}
  Realtime is a second way into your data and it needs the same scrutiny as
  queries. If RLS is not enabled on `Application`, this streams every change on
  the table to every subscribed client, including applications belonging to
  other people.

  RLS does apply to realtime, but only if it is enabled on the table and the
  publication is configured for it. This is the check people miss, because the
  subscription is written in the front end where the security question does not
  feel present.

  Verify it the only way that counts: sign in as a student, subscribe, and have
  an admin change a **different** student's record. If your handler fires, it is
  leaking.

  The general rule for this whole list: **every path to the data needs the same
  policy.** Queries, realtime, storage, and any edge function. A single
  unprotected path makes the other three irrelevant.
  :::
::

## The pre-launch checklist

::feature-list{columns="2"}
  :::feature{icon="i-lucide-shield-check" title="Every table has RLS on"}
  Run the `pg_tables` query. An empty result is the only acceptable answer.
  :::
  :::feature{icon="i-lucide-key" title="The service key is server-side only"}
  Search the built bundle for it. If it appears, rotate before anything else.
  :::
  :::feature{icon="i-lucide-folder-lock" title="Buckets are private, URLs signed"}
  With a size cap and a type restriction set at the bucket, not in the form.
  :::
  :::feature{icon="i-lucide-user-check" title="Sign-up is confirmed and rate limited"}
  Or removed entirely in favour of invitations, which is usually better here.
  :::
::

::pull-quote
Every item on this list is a default that is convenient while you are building
and wrong the moment a stranger can reach it. The platform is not doing anything
wrong; it is optimising for the first ten minutes, and you are responsible for
the rest.
::
