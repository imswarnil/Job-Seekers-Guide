Java has the most predictable interview round of any subject in this course. The
same sixteen questions, in roughly this order, in a large majority of entry-level
technical rounds in this market.

Every answer below is short on definition and long on consequence, because that
is what is actually being marked.

## The platform

::accordion
  :::accordion-item{label="1. Is Java compiled or interpreted?" icon="i-lucide-message-circle"}
  **Both**, and saying only one is the trap. `javac` compiles source to bytecode
  ahead of time; the JVM interprets the bytecode; the JIT then compiles the
  frequently-run parts to native machine code while the program runs.

  The consequence: the same `.class` file runs anywhere there is a JVM, and a
  long-running service gets faster after it warms up, which is why your first
  timing measurement is always misleading.
  :::

  :::accordion-item{label="2. JDK, JRE, JVM" icon="i-lucide-message-circle"}
  Nested, outermost first. The JDK is what you install and contains the compiler
  and tools; the JRE is enough to run and contains the standard library; the JVM
  executes bytecode, manages the heap and runs the garbage collector.

  The practical detail: if `java` works and `javac` does not, you have a JRE.
  :::

  :::accordion-item{label="3. What does static mean?" icon="i-lucide-message-circle"}
  Belongs to the class rather than to any object, which is why `main` is static:
  the JVM calls it before an object exists.

  Then the sentence almost nobody adds: one per class **per process**. A static
  cache is shared between requests on one server and not between servers, which
  is why an in-memory cache silently goes stale the day you run a second
  instance behind a load balancer.
  :::
::

## Memory and types

::accordion
  :::accordion-item{label="4. Stack or heap?" icon="i-lucide-message-circle"}
  The stack is per thread and holds method frames with their parameters and local
  variables, freed on return, about a megabyte. The heap is shared and holds
  every object made with `new`, reclaimed by garbage collection.

  Connect it: a local variable is inherently thread-safe because it is on the
  thread's own stack; a field on a shared object is not, because it is on the
  heap.
  :::

  :::accordion-item{label="5. Is Java pass by value or pass by reference?" icon="i-lucide-message-circle"}
  **Always pass by value.** For an object the value copied is a reference, so the
  method can follow it and mutate the object.

  Give the proof: assign a brand new object to the parameter inside the method.
  The caller sees nothing. If Java were pass by reference, the caller's variable
  would have been replaced.
  :::

  :::accordion-item{label="6. Why not use double for money?" icon="i-lucide-message-circle"}
  Binary floating point cannot represent most decimal fractions, so
  `0.1 + 0.2` is `0.30000000000000004` and the error accumulates. A thousand
  instalments of a ₹45,000 fee came to ₹44,999.99999999967.

  Two correct answers: an integer count of the smallest unit (`long` paise), or
  `BigDecimal` constructed **from a String**. Adding why the String matters:
  `new BigDecimal(0.1)` is already wrong before BigDecimal sees it, is the
  detail that gets remembered.
  :::

  :::accordion-item{label="7. Can a line with no dot throw a NullPointerException?" icon="i-lucide-message-circle"}
  Yes. `int score = map.get(key)` where the key is absent: `get` returns null and
  assigning to an `int` calls `intValue()` on it. Unboxing is an invisible method
  call.

  Same trap in `if (integerValue > 5)` and in a ternary that mixes a boxed type
  with a primitive.
  :::
::

## Strings and objects

::accordion
  :::accordion-item{label="8. == versus equals" icon="i-lucide-message-circle"}
  `==` compares references, `equals` compares contents.

  The part that shows understanding: the **string pool** means identical literals
  share one object, so `==` is often true in a test written with literals and
  false in production where the string came from a user. The code was always
  wrong; the literals were hiding it.
  :::

  :::accordion-item{label="9. Why is String immutable?" icon="i-lucide-message-circle"}
  Three reasons, and any two is a good answer. Pooling is only safe if nobody can
  change a shared instance. Its hash can never go stale, so it is a reliable map
  key. And it is thread-safe with no synchronisation.

  Consequence: building a string in a loop with `+` copies everything each time
  and is O(n²). Quote the measurement, 14 seconds against 9 milliseconds at
  40,000 lines.
  :::

  :::accordion-item{label="10. The equals and hashCode contract" icon="i-lucide-message-circle"}
  Equal objects must have equal hash codes. The reverse is not required; that is
  a collision and it is normal.

  The consequence is the answer: a `HashMap` hashes first to choose a bucket, so
  unequal hashes send it to the wrong bucket and `equals` is never called. The
  entry is in the map and `get` returns null.

  Follow-up to pre-empt: this is why map keys should be immutable. Change a field
  the hash uses after inserting and the object is stranded.
  :::

  :::accordion-item{label="11. Overloading versus overriding" icon="i-lucide-message-circle"}
  Same name with different parameters, resolved at **compile** time from the
  declared types; against a subclass replacing a parent method, resolved at
  **run** time from the actual object.

  Two follow-ups to have ready. A `static` method cannot be overridden. It is
  hidden, because dispatch needs an object. And `@Override` exists so a mistyped
  signature fails the build rather than silently becoming an unused overload.
  :::

  :::accordion-item{label="12. Interface or abstract class?" icon="i-lucide-message-circle"}
  Abstract class when subtypes share state and construction; interface when they
  share only a capability. A class has one identity and any number of
  capabilities, so prefer the interface.

  Then the practical reason, which very few freshers give: depending on an
  interface means the dependency can be handed in, so the class is testable with
  a one-line fake instead of a database. That is dependency injection, and it is
  what every Spring application is doing.
  :::
::

## Failure and collections

::accordion
  :::accordion-item{label="13. Checked versus unchecked exceptions" icon="i-lucide-message-circle"}
  Checked is enforced by the compiler and means an environmental failure the
  caller can act on. Unchecked means a bug in the code.

  Choose by asking whether the caller can sensibly do something about it. Add
  that modern Java leans unchecked, and that Spring wraps `SQLException` into an
  unchecked `DataAccessException` for exactly that reason.
  :::

  :::accordion-item{label="14. What is wrong with catch (Exception e) { }" icon="i-lucide-message-circle"}
  It catches bugs as well as failures, so a `NullPointerException` is treated as
  a network problem, and the empty block destroys the evidence. The work silently
  did not happen and nothing anywhere says why.

  What you do instead: catch the specific type, log the **exception object**
  rather than `e.getMessage()` so the stack trace survives, and let anything you
  cannot handle propagate.
  :::

  :::accordion-item{label="15. Which collection, and why?" icon="i-lucide-message-circle"}
  Requirement, then class, then the cost you are accepting. "A `HashMap`, because
  I look up by applicant id and O(1) matters more than ordering, and I accept
  that iteration order is undefined."

  Have three comparisons ready: `ArrayList` over `LinkedList` because contiguity
  beats the complexity table on real hardware; `HashMap` over `TreeMap` unless
  you need ranges; `ArrayDeque` over `Stack` because `Stack` extends `Vector`.
  :::

  :::accordion-item{label="16. How do you test your code?" icon="i-lucide-message-circle"}
  Arrange, act, assert. One behaviour per test, named for the rule it encodes.
  Test the boundaries, the empty case, the single element and the invalid input,
  not the happy path with a comfortable value.

  Then the line that lands: you watch each test fail once, because a test that
  has never been red proves nothing. And if coverage comes up, it is a useful
  signal and a terrible target.
  :::
::

## What the sixteen have in common

::feature-list{columns="2"}
  :::feature{icon="i-lucide-arrow-right" title="Definition, then consequence"}
  Every strong answer above is one sentence of definition and two of what it
  causes. The consequence is what cannot be memorised from a list.
  :::
  :::feature{icon="i-lucide-hash" title="A number where you have one"}
  47 seconds against 0.38. 14 seconds against 9 milliseconds. Numbers you
  measured yourself are unfakeable and are remembered.
  :::
  :::feature{icon="i-lucide-link" title="Connect two subjects"}
  Static fields to the concurrency lesson. hashCode to the data structures
  track. Interfaces to testing. Seeing one idea in two places is what senior
  sounds like.
  :::
  :::feature{icon="i-lucide-code" title="Prove it with code"}
  Every one of these can be demonstrated in five lines. "Shall I show you?" is a
  strong thing to be able to say.
  :::
::

## Your turn

Pick the five you are least confident about. Answer each out loud, ninety
seconds, recorded. Play back one.

Then for three of them, write the five-line program that proves the answer, and
run it. Those three programs are worth more than a week of reading.
