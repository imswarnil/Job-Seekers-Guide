Sixteen weeks of Java answered in a room. These eight are the same material with
a keyboard instead, and every one of them is code that compiles, runs, and is
wrong.

::note
Type them. Reading a bug and finding a bug are different skills, and only one of
them is tested.
::

## 1. The set with duplicates in it

```java [Duplicates.java]
Set<Applicant> unique = new HashSet<>();
unique.add(new Applicant(1, "2026CSE0184"));
unique.add(new Applicant(1, "2026CSE0184"));
System.out.println(unique.size());      // 2
```

Why, and what is the minimum fix?

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `Applicant` overrides `equals` but not `hashCode`, or neither. `HashSet`
  computes the bucket from `hashCode` first, so two objects with different hashes
  are never compared for equality at all.

  Minimum fix: override both, on the same fields.

  ```java
  @Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Applicant other)) return false;
    return rollNumber.equals(other.rollNumber);
  }
  @Override public int hashCode() { return Objects.hash(rollNumber); }
  ```

  The experienced answer: make it a `record`. `record Applicant(long id, String
  rollNumber) {}` generates both correctly and cannot drift apart when somebody
  adds a field.
  :::
::

## 2. The fee that is out by paise

```java [Fees.java]
double fee = 45000.0;
double paid = 0.0;
for (int i = 0; i < 3; i++) paid += fee / 3;
System.out.println(paid == fee);        // false
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `45000.0 / 3` is representable, but the general case is not: binary floating
  point cannot hold most decimal fractions exactly, so accumulated arithmetic
  drifts.

  Never use `double` or `float` for money. Two correct answers:

  ```java
  long feePaise = 4_500_000L;             // integer count of the smallest unit
  BigDecimal fee = new BigDecimal("45000.00");   // from a String, never a double
  ```

  `new BigDecimal(45000.0)` takes the double's imprecision with it, which is why
  the String constructor is the only safe one.
  :::
::

## 3. The list that throws while you read it

```java [Shortlist.java]
List<Application> apps = new ArrayList<>(all);
for (Application a : apps) {
  if (a.getScore() < cutoff) apps.remove(a);
}
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `ConcurrentModificationException`. The enhanced for loop uses an iterator, and
  modifying the list behind it invalidates that iterator.

  Beginner fix: iterate a copy, or use an explicit `Iterator` with
  `it.remove()`.

  The version an experienced developer writes:

  ```java
  apps.removeIf(a -> a.getScore() < cutoff);
  ```

  One line, no iterator to get wrong, and it says what it means.

  The nastier variant worth knowing: removing the second-to-last element
  sometimes does **not** throw, because of how `ArrayList`'s check happens to
  work. A bug that throws most of the time is easier than one that throws
  occasionally.
  :::
::

## 4. The string built in a loop

```java [Report.java]
String report = "";
for (Application a : applications) {        // 40,000 of them
  report += a.getApplicantName() + ",";
}
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `String` is immutable, so `+=` creates a new one each time and copies
  everything so far. That is O(n²): 40,000 iterations do roughly 800 million
  character copies.

  ```java
  var report = new StringBuilder();
  for (Application a : applications) report.append(a.getApplicantName()).append(',');
  ```

  Or `applications.stream().map(Application::getApplicantName)
  .collect(joining(","))`, which is the better answer here because it also
  handles the trailing comma you were about to have to strip.

  The detail that gets noticed: the compiler **does** optimise `+` into a
  `StringBuilder` for a single expression. It cannot do so across loop
  iterations, which is exactly the case that matters.
  :::
::

## 5. The comparison that is true and should not be

```java [Compare.java]
String a = "2026CSE0184";
String b = new String("2026CSE0184");
System.out.println(a == b);             // false
System.out.println(a.equals(b));        // true

Integer x = 127, y = 127;
Integer p = 128, q = 128;
System.out.println(x == y);             // true
System.out.println(p == q);             // false
```

Explain all four.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `==` on objects compares **references**, not contents. `a` comes from the
  string pool; `new String` forces a fresh object, so different references.
  `equals` compares contents, so true.

  The `Integer` pair is the famous one. Java caches boxed integers from −128 to
  127, so `x` and `y` are literally the same object. 128 is outside the cache,
  so two objects.

  The lesson, and the thing to say in an interview: **`==` on any boxed type or
  object is a bug waiting for the value to grow.** It works in testing with small
  numbers and fails in production with real ones.
  :::
::

## 6. The null that is not a null

```java [Score.java]
Map<String, Integer> scores = new HashMap<>();
scores.put("2026CSE0184", 78);
int score = scores.get("2026ECE0072");    // NullPointerException
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  `get` returns `null` for a missing key, and assigning `null` to an `int`
  requires unboxing, which throws.

  ```java
  int score = scores.getOrDefault("2026ECE0072", 0);
  ```

  But stop and ask whether 0 is right. An applicant who has not been marked is
  not an applicant who scored zero, and that distinction has decided
  admissions. If the difference matters, keep the `Integer` and handle absence
  explicitly, because **null means "we do not know" and 0 means "we know, and it
  is zero"**.

  This is the same idea as SQL's `NULL`, and saying so connects two tracks in
  one sentence.
  :::
::

## 7. The inheritance that should not be

```java [Bad.java]
class Application { void submit() { /* ... */ } }
class RejectedApplication extends Application {
  @Override void submit() { throw new UnsupportedOperationException(); }
}
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  A subclass that removes behaviour breaks the contract: anything holding an
  `Application` expects `submit` to work, and now it throws.

  The "is a" is false. A rejected application is not a kind of application you
  can submit; it is an application in a particular **state**.

  ```java
  class Application {
    private Status status;
    void submit() {
      if (status != Status.DRAFT)
        throw new IllegalStateException("Already " + status);
      // ...
    }
  }
  ```

  State belongs in a field, not in a class hierarchy. The general rule to say
  out loud: **prefer composition, and use inheritance only when every subclass
  can honestly be used wherever the parent can.**
  :::
::

## 8. The test that passes and proves nothing

```java [EligibilityTest.java]
@Test void eligibilityWorks() {
  assertTrue(rules.isEligible(score(90), program(cutoff(78.5))));
}
```

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  It tests the case that could not plausibly be wrong. 90 against 78.5 passes
  under `>`, `>=`, and almost any bug you could write.

  The cases that matter are the boundary and the absence:

  ```java
  @Test void scoreExactlyAtCutoffIsEligible() {
    assertTrue(rules.isEligible(score(78.5), program(cutoff(78.5))));
  }
  @Test void unmarkedApplicationIsNotEligible() {
    assertFalse(rules.isEligible(score(null), program(cutoff(78.5))));
  }
  ```

  The habit: **a test that would still pass if the code were wrong is not a
  test.** Before writing one, ask which bug it would catch. If you cannot name
  one, write a different test.
  :::
::

## The pattern in all eight

::pull-quote
Every one of these compiles and runs. Not one produces an error at the point
where the mistake was made, and six of them produce a plausible wrong answer
rather than a crash. That is what "correct, not just runnable" means, and it is
most of what separates a second-year developer from a fresher.
::
