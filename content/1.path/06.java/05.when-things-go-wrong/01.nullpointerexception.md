You called a method on something that turned out to be null. Every Java
programmer meets this in their first week and a large number never move past
scattering null checks around until it stops.

## Why this matters in a job

Because it is the single most common exception in production Java, because modern
Java tells you far more than people realise, and because the good fixes are about
never having a null rather than about checking for one.

## Read the message properly

```java [Shortlist.java]
Application application = repository.findById(9001);
String email = application.getApplicant().getEmail().toLowerCase();
```

```text [Output]
Exception in thread "main" java.lang.NullPointerException: Cannot invoke
"String.toLowerCase()" because the return value of "Applicant.getEmail()" is null
	at com.university.admissions.Shortlist.notify(Shortlist.java:42)
```

Three nulls were possible on that line and the message names exactly which one it
was: the **email**, not the application and not the applicant. Before Java 14 you
got a line number and nothing else, and finding which of the three took a
debugger.

::pull-quote
"Cannot invoke X because Y is null" is a complete diagnosis. Read the whole
sentence and you will almost never need a debugger for an NPE again.
::

## The four bad fixes and the four good ones

::compare{caption="The instinct, and the problem with it."}
  :::compare-side{label="Check and carry on" verdict="wrong"}
  ```java
  if (application != null
      && application.getApplicant() != null
      && application.getApplicant().getEmail() != null) {
    ...
  }
  ```
  Three checks to read one field, repeated at every call site, and it silently
  does nothing when the data is missing. The next reader cannot tell whether a
  null is expected or a bug.
  :::
  :::compare-side{label="Decide what null means" verdict="right"}
  Ask, for each one: *can this legitimately be absent?* If no, stop it being
  possible. If yes, say so in the type and handle it once.
  :::
::

### 1. Do not allow it in the first place

```java [Applicant.java]
public Applicant(String fullName, String email) {
  this.fullName = Objects.requireNonNull(fullName, "fullName");
  this.email    = Objects.requireNonNull(email, "email");
}
```

The object now cannot exist with a null name, so no caller anywhere ever needs to
check. **This is the highest-value fix and it is the one people skip**, because
it means fixing the class rather than the line that crashed.

### 2. Never return null from a method that returns a collection

```java [Repository.java]
// Every caller must now remember to check. One will not.
List<Application> findByIntake(String intake) {
  if (none) return null;
}

// Nothing to check. An empty list loops zero times, which is correct.
List<Application> findByIntake(String intake) {
  if (none) return List.of();
}
```

::tip
"Return an empty collection, never null" is one of the few pieces of advice in
this course that has no exceptions. It removes an entire category of null check
from every caller, forever.
::

### 3. `Optional` for "might genuinely not be there"

```java [Repository.java]
Optional<Application> findById(long id);
```

```java [Caller.java]
repository.findById(9001)
    .map(Application::getApplicant)
    .map(Applicant::getEmail)
    .map(String::toLowerCase)
    .ifPresentOrElse(
        this::sendShortlistEmail,
        () -> log.warn("No application 9001, or no email on it"));
```

The type now says "this may be absent" and the compiler makes you deal with it.

::warning{icon="i-lucide-alert-triangle"}
`Optional` is for **return types**, not for fields or parameters. An
`Optional` field costs an extra object per instance and is not serialisable;
an `Optional` parameter means the caller has to wrap a value it already has. And
`optional.get()` without checking is just an NPE with extra steps, use
`orElse`, `orElseThrow` or `ifPresent`.
::

### 4. A default, where one makes sense

```java [Applicant.java]
public String getPreferredName() {
  return preferredName != null ? preferredName : fullName;
}
```

## The null that has no dot in it

The sneakiest NPE in the language, and it catches experienced people.

```java [Unboxing.java]
Map<String, Integer> marks = new HashMap<>();
int score = marks.get("2026CSE0184");     // no such key
```

```text [Output]
Exception in thread "main" java.lang.NullPointerException: Cannot invoke
"java.lang.Integer.intValue()" because the return value of "Map.get(Object)" is null
```

`marks.get` returns `null`, and assigning an `Integer` to an `int` calls
`intValue()` on it. There is no dot on that line, and there is still a method
call.

```java [Unboxing.java]
int score = marks.getOrDefault("2026CSE0184", 0);      // fixed
```

::side-note{kind="go-deeper"}
The same trap appears in arithmetic: `Integer a = null; if (a > 5)` throws,
because comparing an `Integer` to an `int` unboxes. And in a ternary:
`int x = flag ? null : 5;` compiles and throws. Any time a boxed type meets a
primitive, unboxing happens and null is fatal.
::

## Finding the real cause

```text [Output]
java.lang.NullPointerException: Cannot invoke "Programme.getSeats()"
because the return value of "Application.getProgramme()" is null
	at com.university.admissions.SeatAllotter.allot(SeatAllotter.java:31)
	at com.university.admissions.AdmissionsService.run(AdmissionsService.java:88)
```

The line that throws is line 31, and the **bug** is wherever an `Application` was
created or loaded without a programme. Line 31 is the victim.

::flow{numbered direction="vertical" caption="Working backwards from an NPE. The crash site is rarely the cause."}
  :::flow-step{label="Read the message for which value is null" icon="i-lucide-text"}
  It names the exact expression. No guessing.
  :::
  :::flow-step{label="Find where that value was set" icon="i-lucide-search" highlight}
  Loaded from the database with a column that was null? Built by a constructor
  that did not require it? Set later and the setter was never called?
  :::
  :::flow-step{label="Decide whether absence is legitimate" icon="i-lucide-scale"}
  If an application must always have a programme, the bug is upstream and the
  fix is a `requireNonNull` in the constructor, not a check at line 31.
  :::
  :::flow-step{label="Fix it there, not at the crash" icon="i-lucide-wrench"}
  A null check at line 31 makes the symptom disappear and leaves the invalid
  object in circulation for the next twelve places to trip over.
  :::
::

## What you can do now

You can read an NPE to the exact value, and you know four fixes that are better
than another null check, starting with making the null impossible.

## Your turn

::runner{lang="java"}
```java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    Map<String, Integer> attendance = new HashMap<>();
    attendance.put("2026CSE0184", 18);

    // Each of these throws or misbehaves. Say which, why, and fix it.
    int a = attendance.get("2026CSE0999");                      // 1
    String name = findName("2026CSE0999").toUpperCase();        // 2
    List<String> subjects = subjectsFor("2026CSE0999");
    for (String s : subjects) System.out.println(s);            // 3
  }

  static String findName(String roll) {
    return roll.equals("2026CSE0184") ? "Anita Rao" : null;
  }

  static List<String> subjectsFor(String roll) {
    return roll.equals("2026CSE0184") ? List.of("CS-201") : null;
  }
}
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1. NPE on unboxing**, with no dot on the line. `get` returns `null` and
  assigning it to an `int` calls `intValue()`. Fix:
  `int a = attendance.getOrDefault("2026CSE0999", 0);`, and pause on whether 0
  is honest here. "No record" and "attended zero classes" are different facts,
  which is the `NULL`-versus-zero distinction again. If they differ, the return
  type should be `Optional<Integer>` or the method should throw.

  **2. NPE on `toUpperCase`.** `findName` returns null to signal "not found",
  which pushes the problem onto every caller. Fix the **method**:
  `static Optional<String> findName(String roll)`, then
  `findName(roll).map(String::toUpperCase).orElse("UNKNOWN")`.

  **3. NPE on the enhanced for**, before the loop body ever runs: the loop calls
  `iterator()` on null. Fix: `return List.of();`. An empty list loops zero times,
  which is exactly the behaviour wanted, with no check at the call site.

  **The pattern across all three:** every fix is in the method that produced the
  null, not at the line that crashed. That is the habit worth taking from this
  lesson.
  :::
::

## Check yourself

1. Why can a line with no `.` on it throw a NullPointerException?
2. **An interviewer asks: "how do you avoid NullPointerExceptions?"** Answer with
   four techniques, not with "null checks".

## The interview question this answers

**"How do you handle nulls in Java?"**

Weak: "I check for null." Strong, and in this order: prevent it at construction
with `Objects.requireNonNull` so callers never have to check; return empty
collections rather than null, always; use `Optional` as a return type where
absence is a legitimate outcome; and read the modern NPE message, which names the
exact expression that was null.

Then the sentence that makes it sound like experience: the crash site is usually
the victim rather than the cause, so the fix belongs where the null was created.
