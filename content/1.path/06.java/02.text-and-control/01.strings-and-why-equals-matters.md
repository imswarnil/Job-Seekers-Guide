Two applicant names that look identical on the screen, and Java says they are
different. This is the most common bug in a beginner's Java program and it takes
one lesson to never make again.

## Why this matters in a job

Because comparing strings is in every program you will ever write, because
`==` versus `equals` is asked in almost every Java interview, and because the
string pool makes the bug appear intermittently, which is the worst possible way
for a bug to behave.

## Watch it happen

```java [Names.java]
String typed = new Scanner(System.in).nextLine();   // the registrar types: Anita Rao
String stored = "Anita Rao";

System.out.println(typed == stored);          // false
System.out.println(typed.equals(stored));     // true
```

Same characters. `==` says no.

Because a `String` is an object, and from the previous lesson you know what an
object variable holds: an address. `==` compares the two addresses. `equals`
compares the characters.

**The rule, without exception: compare strings with `equals`.** `==` on objects
is for asking "is this literally the same object", which you almost never want.

## Why it sometimes appears to work

Here is why this bug is so nasty.

```java [Pool.java]
String a = "Anita Rao";
String b = "Anita Rao";
System.out.println(a == b);       // true  ← !!

String c = new String("Anita Rao");
System.out.println(a == c);       // false
```

Java keeps a **string pool**: identical string *literals* written in source code
are stored once and shared. So `a` and `b` genuinely are the same object, and
`==` happens to be true.

::warning{icon="i-lucide-alert-triangle"}
This is why the bug survives testing. Your test compares two literals and passes.
In production the string came from a `Scanner`, a database or an HTTP request, so
it is a new object, and `==` is false. The code was always wrong and only the
literals were hiding it.
::

## Immutable, which explains everything else

A `String` can never be changed. Every method that appears to modify one returns
a new one.

```java [Immutable.java]
String name = "anita rao";
name.toUpperCase();
System.out.println(name);          // anita rao — unchanged

name = name.toUpperCase();
System.out.println(name);          // ANITA RAO
```

Forgetting the reassignment is the second most common String mistake. The method
did exactly what it promised: it *returned* an uppercase string. It never claimed
to change yours.

::side-note{kind="go-deeper"}
Immutability is why strings can be pooled safely, sharing one object between
many variables is only safe if nobody can change it. It is also why `String`
makes a good `HashMap` key: its hash can never go stale, which is exactly the
mutable-key trap from the data structures track.
::

## The methods you will actually use

```java [StringMethods.java]
String roll = "  2026CSE0184  ";

roll.trim()                    // "2026CSE0184" — removes surrounding spaces
roll.strip()                   // the same, and Unicode-aware. Prefer this.
roll.isBlank()                 // true if empty or only whitespace
roll.strip().length()          // 11
roll.strip().substring(0, 4)   // "2026"
roll.strip().charAt(4)         // 'C'
roll.contains("CSE")           // true
roll.strip().startsWith("2026")// true
roll.strip().indexOf("CSE")    // 4, or -1 if absent
"a,b,c".split(",")             // ["a", "b", "c"]
String.join("-", "2026", "CSE")// "2026-CSE"
"Anita".equalsIgnoreCase("ANITA")  // true
"%s scored %d".formatted("Anita", 78)   // "Anita scored 78"
```

::tip
`strip()` over `trim()`, in new code. `trim()` only removes characters below
U+0020 and will leave a non-breaking space behind, which is exactly what gets
pasted in from a spreadsheet and produces a name that looks clean and does not
match anything.
::

## Comparing safely when one side might be null

```java [SafeCompare.java]
String typed = form.get("name");      // might be null

typed.equals("Anita Rao")             // NullPointerException if typed is null
"Anita Rao".equals(typed)             // false. Safe, because the literal is never null
Objects.equals(typed, "Anita Rao")    // false. Safe, and reads better.
```

The middle line is a real technique called a Yoda comparison, and it is worth
knowing because you will see it. `Objects.equals` is clearer and handles both
sides being null.

## What you can do now

You can compare strings correctly, explain the string pool well enough to say why
the bug is intermittent, and use the methods that cover ninety per cent of text
handling.

## Your turn

::runner{lang="java"}
```java
public class Names {
  public static void main(String[] args) {
    String a = "2026CSE0184";
    String b = "2026CSE0184";
    String c = new String("2026CSE0184");
    String d = "2026CSE" + "0184";
    String part = "0184";
    String e = "2026CSE" + part;

    System.out.println(a == b);        // 1
    System.out.println(a == c);        // 2
    System.out.println(a == d);        // 3
    System.out.println(a == e);        // 4
    System.out.println(a.equals(e));   // 5
  }
}
```
::

::accordion
  :::accordion-item{label="Answers, and why 3 and 4 differ" icon="i-lucide-check"}
  **1. `true`**: two literals, pooled, one object.
  **2. `false`**: `new String` forces a new object every time.
  **3. `true`**. This is the interesting one. `"2026CSE" + "0184"` is two
  *constants*, so the compiler joins them at compile time and the result is a
  pooled literal.
  **4. `false`**: `part` is a variable, so the joining happens at run time and
  produces a new object on the heap.
  **5. `true`**, which is the only one you should ever have been relying on.

  Three and four are the same expression to a human and different to the
  compiler. That is precisely why `==` on strings is unreliable and why the rule
  is absolute rather than conditional.
  :::
::

## The interview question this answers

**"What is the difference between == and equals?"**, asked in a large majority
of entry-level Java interviews.

`==` compares references, `equals` compares contents. Then the part that shows
understanding rather than recall: explain the string pool and say that this is
why the bug is intermittent, passing in tests that use literals and failing on
input from a user. If they follow up with "why is String immutable", give safe
pooling, safe use as a hash key, and thread safety without synchronisation.
