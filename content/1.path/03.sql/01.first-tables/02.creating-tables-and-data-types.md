A table needs a shape before it can hold anything: which columns, and what kind
of value each one accepts. That shape is written with `CREATE TABLE`, and the
type you give each column is the first rule the database enforces for you.

## Why this matters in a job

Choosing a type is a decision that lives for years. A column created as
`VARCHAR(20)` for phone numbers, or `FLOAT` for fees, or text for dates, is the
kind of thing a whole team works around long after the person who chose it has
left. In interviews it comes up as "what is the difference between CHAR and
VARCHAR?", "which type would you use for money?", and "design a table for
students", where the types you pick are half of what is being marked.

## A type is a promise about a column

Think of the admission form. The date-of-birth box has little squares for
DD/MM/YYYY; the fee box has a ₹ sign in front of it; the name box is a long line.
The shape of each box stops people writing a name where a date should be. A
column's data type is that box. It says what the column holds, how much space it
takes, and what the database will refuse.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-hash" title="Whole numbers"}
  `INT` / `INTEGER`, `SMALLINT`, `BIGINT`. Ids, counts, marks, credits,
  admission year.
  :::
  :::feature{icon="i-lucide-indian-rupee" title="Exact decimals"}
  `DECIMAL(p, s)` / `NUMERIC(p, s)`. Money and anything that must add up
  exactly. `DECIMAL(10, 2)` holds up to 99,999,999.99.
  :::
  :::feature{icon="i-lucide-type" title="Text"}
  `CHAR(n)` fixed length, `VARCHAR(n)` up to n characters, `TEXT` for long
  text. Names, emails, codes.
  :::
  :::feature{icon="i-lucide-calendar" title="Dates and times"}
  `DATE` (2026-07-01), `TIME`, `DATETIME` / `TIMESTAMP` (date and time). Exam
  dates, payment times.
  :::
  :::feature{icon="i-lucide-toggle-left" title="True or false"}
  `BOOLEAN`. In MySQL it is stored as `TINYINT(1)`, 1 or 0. Present or absent.
  :::
  :::feature{icon="i-lucide-waves" title="Approximate decimals"}
  `FLOAT`, `DOUBLE`, `REAL`. Measurements where a tiny error is fine. **Never
  money.**
  :::
::

## Syntax

```sql [create-table-syntax.sql]
CREATE TABLE table_name (
  column_name  DATA_TYPE  [constraints],
  column_name  DATA_TYPE  [constraints],
  ...
);
```

The constraints (`PRIMARY KEY`, `NOT NULL`, `UNIQUE` and the rest) get their own
lesson later in this track. For now, a primary key and the right types are
enough. Here is the college's `Student` and `FeePayment` tables, created and
checked:

::runner{lang="sql"}
```sql [create-student.sql]
CREATE TABLE Student (
  student_id      INTEGER PRIMARY KEY,
  full_name       VARCHAR(100),
  email           VARCHAR(120),
  city            VARCHAR(50),
  department_id   INTEGER,
  admission_year  INTEGER
);

CREATE TABLE FeePayment (
  payment_id  INTEGER PRIMARY KEY,
  student_id  INTEGER,
  amount      DECIMAL(10, 2),
  paid_on     DATE
);

INSERT INTO Student VALUES (1, 'Anita Rao', 'anita@college.edu', 'Bhopal', 1, 2024);
INSERT INTO FeePayment VALUES (1, 1, 42500.00, '2024-07-15');

SELECT s.full_name, f.amount, f.paid_on
FROM   Student s, FeePayment f
WHERE  s.student_id = f.student_id;
```
::

```text [Output]
full_name  amount  paid_on
---------  ------  ----------
Anita Rao  42500   2024-07-15
```

## CHAR against VARCHAR

`CHAR(10)` always takes ten characters of space; a shorter value is padded with
spaces. `VARCHAR(10)` takes only as much as the value needs, up to ten.

| Value | `CHAR(10)` stores | `VARCHAR(10)` stores |
| --- | --- | --- |
| `'CSE'` | `'CSE       '` (10 characters) | `'CSE'` (3 characters) |
| `'MECH'` | `'MECH      '` (10 characters) | `'MECH'` (4 characters) |

Use `CHAR` only when every value is genuinely the same length: a two-letter
state code, a fixed six-character course code. Use `VARCHAR` for everything
else. In Oracle, the type is `VARCHAR2`; it behaves the same way.

## Why money is never a FLOAT

A `FLOAT` stores numbers in binary, and most decimal fractions (0.1, 0.2) have no
exact binary form, so they are stored as the nearest thing. The error is tiny,
and it adds up.

::runner{lang="sql"}
```sql [float-money.sql]
SELECT 0.1 + 0.2              AS float_sum,
       0.1 + 0.2 = 0.3        AS is_equal,
       ROUND(0.1 + 0.2, 2)    AS rounded;
```
::

```text [Output]
float_sum  is_equal  rounded
---------  --------  -------
0.3        0         0.3
```

`is_equal` is `0`, which means false: 0.1 + 0.2 is not 0.3 in floating point.
Now picture a fee table where lakhs of such additions are summed at the end of
the year and the accounts office's total does not match the bank's by a few
paise. That is why money goes in `DECIMAL`, which stores exact decimal digits,
or as a whole number of paise in an `INTEGER`.

::warning{icon="i-lucide-alert-triangle"}
"Which data type would you use for a salary or a fee?" is a common interview
question, and `FLOAT` is the wrong answer. Say `DECIMAL(10, 2)`, and say why:
floating point cannot represent most decimal fractions exactly.
::

## Changing a table after it exists

Tables change. The college decides to record each student's phone number:

::runner{lang="sql"}
```sql [alter-table.sql]
CREATE TABLE Student (
  student_id  INTEGER PRIMARY KEY,
  full_name   VARCHAR(100)
);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma');

ALTER TABLE Student ADD COLUMN phone VARCHAR(15);
ALTER TABLE Student RENAME COLUMN full_name TO name;

UPDATE Student SET phone = '9876543210' WHERE student_id = 1;

SELECT * FROM Student;
```
::

```text [Output]
student_id  name         phone
----------  -----------  ----------
1           Anita Rao    9876543210
2           Rahul Verma  NULL
```

Existing rows get `NULL` in the new column: the value is unknown, not empty.
`NULL` has a lesson of its own in the next chapter. Other forms you will see:
`ALTER TABLE ... DROP COLUMN`, and in MySQL `ALTER TABLE ... MODIFY COLUMN` to
change a type. `DROP TABLE Student;` removes the table and every row in it; the
difference between that, `DELETE` and `TRUNCATE` is one of the most asked
questions in the SQL round, and it gets its own lesson at the end of this track.

## Real use case

An exam cell stores results. A careful table for it looks like this, and every
type is a decision someone can defend:

::runner{lang="sql"}
```sql [exam-result.sql]
CREATE TABLE ExamResult (
  result_id   INTEGER PRIMARY KEY,
  student_id  INTEGER,          -- whole number, joins to Student
  course_id   INTEGER,          -- whole number, joins to Course
  marks       INTEGER,          -- 0 to 100, no fractions in this college
  exam_date   DATE              -- a real date, so it sorts and compares as one
);

INSERT INTO ExamResult VALUES
  (1, 1, 101, 87, '2025-11-20'),
  (2, 2, 101, 64, '2025-11-20'),
  (3, 1, 102, 91, '2025-12-02');

SELECT student_id, marks, exam_date
FROM   ExamResult
WHERE  exam_date >= '2025-12-01';
```
::

```text [Output]
student_id  marks  exam_date
----------  -----  ----------
1           91     2025-12-02
```

The date comparison works because dates are stored as `YYYY-MM-DD`, which sorts
correctly as text as well. Store them as `'20/11/2025'` and `'02/12/2025'` sorts
before `'20/11/2025'`, and every date filter in the college quietly returns the
wrong rows.

## What confuses people here

- **SQLite, which this site's runner uses, is relaxed about types.** It accepts
  `VARCHAR(100)` but does not enforce the 100, and it will store text in an
  `INTEGER` column if you insist. MySQL and PostgreSQL are stricter. SQLite has
  a `STRICT` option that makes it behave:

::runner{lang="sql"}
```sql [strict.sql]
CREATE TABLE ExamResult (
  result_id  INTEGER PRIMARY KEY,
  marks      INTEGER
) STRICT;

INSERT INTO ExamResult VALUES (1, 'eighty');
```
::

```text [Output]
Error: cannot store TEXT value in INTEGER column ExamResult.marks
```

- **`VARCHAR(n)` counts characters, not bytes**, in MySQL and PostgreSQL. A
  name in Hindi takes more bytes than one in English, but the same number of
  characters.
- **Phone numbers and PIN codes are text, not numbers.** You never add two phone
  numbers, and a number type drops the leading zero of `011` numbers.
- **`INT` has a ceiling**: about 2.1 billion in MySQL. Enough for student ids.
  Not always enough for a table that logs every click, which is what `BIGINT`
  is for.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between CHAR and VARCHAR?" icon="i-lucide-message-circle"}
  `CHAR(n)` is fixed length: it always uses n characters and pads shorter values
  with spaces. `VARCHAR(n)` is variable length: it uses only what the value
  needs, up to n. Use `CHAR` for values that are always the same length (a
  two-letter code), `VARCHAR` for names, emails and everything else.
  :::
  :::accordion-item{label="Which data type would you use to store money?" icon="i-lucide-message-circle"}
  `DECIMAL(10, 2)` (or `NUMERIC`), because it stores exact decimal digits.
  `FLOAT` stores an approximation: `SELECT 0.1 + 0.2 = 0.3` returns false in
  floating point. Storing paise as a whole-number `INTEGER` is also correct.
  :::
  :::accordion-item{label="Write a CREATE TABLE for a Course table." icon="i-lucide-message-circle"}
  ```sql [course.sql]
  CREATE TABLE Course (
    course_id      INTEGER PRIMARY KEY,
    code           VARCHAR(10),
    title          VARCHAR(100),
    department_id  INTEGER,
    credits        INTEGER
  );
  ```
  Then say what you would add next: `NOT NULL` on `code` and `title`, `UNIQUE`
  on `code`, a `CHECK` that credits are between 1 and 6, and a foreign key to
  `Department`. Mentioning them shows you know a table is more than its types.
  :::
  :::accordion-item{label="How do you add a column to an existing table?" icon="i-lucide-message-circle"}
  `ALTER TABLE Student ADD COLUMN phone VARCHAR(15);` Existing rows get `NULL`
  in the new column unless you give it a `DEFAULT`.
  :::
  :::accordion-item{label="What is the difference between DATE, DATETIME and TIMESTAMP?" icon="i-lucide-message-circle"}
  `DATE` is a day with no time. `DATETIME` is a date and a time exactly as
  written. In MySQL, `TIMESTAMP` is also a date and time but is stored in UTC and
  converted to the session's time zone when read, and it has a smaller range
  (up to 2038). Use `DATE` for an exam date, `DATETIME` or `TIMESTAMP` for the
  moment a fee payment was made.
  :::
::
