The table exists, it has the right types, and it is empty. Three statements
change what is inside it: `INSERT` adds rows, `UPDATE` changes them, `DELETE`
removes them. There is no undo button for any of them.

## Why this matters in a job

Reading a query wrongly gives you a wrong number on a screen. Writing one
wrongly changes forty thousand rows, and the database does it instantly and
without asking. At some point in your first year you will be given access to
real data, and the difference between a good day and a very bad one is a habit,
not a skill. In interviews these three are asked as syntax ("write an UPDATE
that raises every CSE faculty member's salary by 10%") and as judgement ("what
happens if you forget the WHERE?").

## Three verbs, one rule

Think of the college register. `INSERT` is writing a new student on a new line.
`UPDATE` is crossing out a value and writing a new one. `DELETE` is tearing a
line out. The register cannot tell whether you meant to do it to one line or to
all of them; it does what the statement says. The rule that follows from that:
**`UPDATE` and `DELETE` change every row the `WHERE` matches, and with no
`WHERE`, that is every row in the table.**

## INSERT

```sql [insert-syntax.sql]
INSERT INTO table_name (column1, column2, ...)
VALUES (value1, value2, ...);
```

::runner{lang="sql"}
```sql [insert.sql]
CREATE TABLE Student (
  student_id      INTEGER PRIMARY KEY,
  full_name       TEXT,
  email           TEXT UNIQUE,
  city            TEXT,
  admission_year  INTEGER
);

-- Name the columns. Always.
INSERT INTO Student (student_id, full_name, email, city, admission_year)
VALUES (1, 'Anita Rao', 'anita@college.edu', 'Bhopal', 2024);

-- Several rows in one statement: one round trip, far faster than three.
INSERT INTO Student (student_id, full_name, email, city, admission_year) VALUES
  (2, 'Rahul Verma', 'rahul@college.edu', 'Patna',     2024),
  (3, 'Priya Nair',  'priya@college.edu', 'Bangalore', 2025);

-- Leave a column out and it gets NULL (or its DEFAULT).
INSERT INTO Student (student_id, full_name, email)
VALUES (4, 'Arjun Mehta', 'arjun@college.edu');

SELECT * FROM Student;
```
::

```text [Output]
student_id  full_name    email              city       admission_year
----------  -----------  -----------------  ---------  --------------
1           Anita Rao    anita@college.edu  Bhopal     2024
2           Rahul Verma  rahul@college.edu  Patna      2024
3           Priya Nair   priya@college.edu  Bangalore  2025
4           Arjun Mehta  arjun@college.edu  NULL       NULL
```

::warning{icon="i-lucide-alert-triangle"}
`INSERT INTO Student VALUES (...)` without column names depends on the order the
columns were created in. Somebody adds a column in the middle next year and
every such statement either fails or, worse, puts the city in the email column.
Naming the columns costs a few words and never breaks.
::

### INSERT from a SELECT

You can insert the result of a query. The placement cell copies every 2024
student into a new `PlacementDrive` table in one statement:

::runner{lang="sql"}
```sql [insert-select.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, admission_year INTEGER);
INSERT INTO Student VALUES (1, 'Anita Rao', 2024), (2, 'Rahul Verma', 2024), (3, 'Priya Nair', 2025);

CREATE TABLE PlacementDrive (student_id INTEGER, full_name TEXT, status TEXT);

INSERT INTO PlacementDrive (student_id, full_name, status)
SELECT student_id, full_name, 'REGISTERED'
FROM   Student
WHERE  admission_year = 2024;

SELECT * FROM PlacementDrive;
```
::

```text [Output]
student_id  full_name    status
----------  -----------  ----------
1           Anita Rao    REGISTERED
2           Rahul Verma  REGISTERED
```

## UPDATE

Before you read the syntax, read this.

::warning{icon="i-lucide-alert-triangle"}
**An `UPDATE` with no `WHERE` changes every row in the table.** There is no
error, no confirmation, and the old values are gone. Always write the `WHERE`
first, and always run it as a `SELECT` before you run it as an `UPDATE`.
::

```sql [update-syntax.sql]
UPDATE table_name
SET    column1 = value1, column2 = value2
WHERE  condition;
```

::runner{lang="sql"}
```sql [update.sql]
CREATE TABLE Faculty (
  faculty_id     INTEGER PRIMARY KEY,
  full_name      TEXT,
  department_id  INTEGER,
  salary         INTEGER
);
INSERT INTO Faculty VALUES
  (1, 'Dr. Meera Joshi',  1, 120000),
  (2, 'Vikram Singh',     1,  85000),
  (3, 'Divya Menon',      2,  80000),
  (4, 'Rohit Kumar',      1,  78000);

-- A 10% raise for everyone in department 1 (CSE).
UPDATE Faculty
SET    salary = salary * 110 / 100
WHERE  department_id = 1;

SELECT changes() AS rows_changed;
SELECT * FROM Faculty;
```
::

```text [Output]
rows_changed
------------
3

faculty_id  full_name        department_id  salary
----------  ---------------  -------------  ------
1           Dr. Meera Joshi  1              132000
2           Vikram Singh     1              93500
3           Divya Menon      2              80000
4           Rohit Kumar      1              85800
```

`changes()` is SQLite's way of reporting how many rows the last statement
touched; MySQL prints `3 rows affected` and PostgreSQL prints `UPDATE 3`. **That
number is your only check**, and it arrives after the fact. Now the same
statement with the `WHERE` forgotten:

::runner{lang="sql"}
```sql [update-disaster.sql]
CREATE TABLE Faculty (faculty_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER, salary INTEGER);
INSERT INTO Faculty VALUES
  (1, 'Dr. Meera Joshi', 1, 120000), (2, 'Vikram Singh', 1, 85000),
  (3, 'Divya Menon',     2,  80000), (4, 'Rohit Kumar',  1, 78000);

UPDATE Faculty SET salary = 90000;

SELECT changes() AS rows_changed;
SELECT * FROM Faculty;
```
::

```text [Output]
rows_changed
------------
4

faculty_id  full_name        department_id  salary
----------  ---------------  -------------  ------
1           Dr. Meera Joshi  1              90000
2           Vikram Singh     1              90000
3           Divya Menon      2              90000
4           Rohit Kumar      1              90000
```

The head of department now earns the same as everyone else, and nobody knows
what she earned before.

## The safety habit

Four steps, every time. After a month it is automatic, and it is the single
most valuable habit in this track.

::flow{numbered direction="vertical" caption="Never type UPDATE first. Type SELECT first."}
  :::flow-step{label="Write it as a SELECT" icon="i-lucide-eye" highlight}
  `SELECT * FROM Faculty WHERE department_id = 1;` Look at the rows. Are they
  the ones you meant? Is it the number you expected?
  :::
  :::flow-step{label="Open a transaction" icon="i-lucide-shield"}
  `BEGIN;` Nothing you do now is permanent until you say so.
  :::
  :::flow-step{label="Run it, and read the count" icon="i-lucide-hash"}
  Change `SELECT *` to `UPDATE ... SET`, keep the same `WHERE`, run it, and
  compare the row count with step 1.
  :::
  :::flow-step{label="COMMIT or ROLLBACK" icon="i-lucide-check"}
  Count as expected: `COMMIT;`. Anything else: `ROLLBACK;`, and nothing
  happened.
  :::
::

::runner{lang="sql"}
```sql [rollback.sql]
CREATE TABLE Faculty (faculty_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER, salary INTEGER);
INSERT INTO Faculty VALUES
  (1, 'Dr. Meera Joshi', 1, 120000), (2, 'Vikram Singh', 1, 85000),
  (3, 'Divya Menon',     2,  80000), (4, 'Rohit Kumar',  1, 78000);

BEGIN;
UPDATE Faculty SET salary = 90000;        -- forgot the WHERE
SELECT changes() AS rows_changed;         -- 4, expected 1: stop
ROLLBACK;

SELECT * FROM Faculty;                    -- untouched
```
::

```text [Output]
rows_changed
------------
4

faculty_id  full_name        department_id  salary
----------  ---------------  -------------  ------
1           Dr. Meera Joshi  1              120000
2           Vikram Singh     1              85000
3           Divya Menon      2              80000
4           Rohit Kumar      1              78000
```

Transactions get a full lesson later in this track. For now, `BEGIN` before a
risky write and `ROLLBACK` when the count is wrong is enough to save you.

## DELETE

::warning{icon="i-lucide-alert-triangle"}
**`DELETE FROM Student;` with no `WHERE` removes every student.** Same rule, same
habit: `SELECT` first with the exact `WHERE`, then change `SELECT *` to
`DELETE`, inside a transaction.
::

```sql [delete-syntax.sql]
DELETE FROM table_name
WHERE  condition;
```

::runner{lang="sql"}
```sql [delete.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, city TEXT, admission_year INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao',   'Bhopal', 2024), (2, 'Rahul Verma', 'Patna',  2024),
  (3, 'Priya Nair',  'Bangalore', 2025), (4, 'Test Student', NULL, NULL);

-- Step 1: look first.
SELECT * FROM Student WHERE full_name = 'Test Student';

-- Step 2: the same WHERE, now as a DELETE.
DELETE FROM Student WHERE full_name = 'Test Student';
SELECT changes() AS rows_deleted;

SELECT * FROM Student;
```
::

```text [Output]
student_id  full_name     city  admission_year
----------  ------------  ----  --------------
4           Test Student  NULL  NULL

rows_deleted
------------
1

student_id  full_name    city       admission_year
----------  -----------  ---------  --------------
1           Anita Rao    Bhopal     2024
2           Rahul Verma  Patna      2024
3           Priya Nair   Bangalore  2025
```

## Real use case

Real systems rarely delete. They **mark**, which is called a soft delete. A
student who leaves mid-course still has fee payments, marks and attendance that
the accounts office and the university will ask about later.

::compare{caption="Two ways to remove a student who has left."}
  :::compare-side{label="DELETE" verdict="wrong"}
  The row is gone. So is the answer to "how many students left in the first
  year", every fee receipt that pointed at them, and any chance of finding out
  what happened when somebody asks in November.
  :::
  :::compare-side{label="Soft delete" verdict="right"}
  `UPDATE Student SET status = 'LEFT', left_on = '2025-02-10' WHERE student_id = 2;`
  The history survives, reports can still count it, and it can be undone.
  :::
::

::runner{lang="sql"}
```sql [soft-delete.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, status TEXT DEFAULT 'ACTIVE', left_on TEXT);
INSERT INTO Student (student_id, full_name) VALUES (1, 'Anita Rao'), (2, 'Rahul Verma'), (3, 'Priya Nair');

UPDATE Student SET status = 'LEFT', left_on = '2025-02-10' WHERE student_id = 2;

-- Current students: every report now filters on status.
SELECT student_id, full_name FROM Student WHERE status = 'ACTIVE';

-- The history is still there.
SELECT status, COUNT(*) AS students FROM Student GROUP BY status;
```
::

```text [Output]
student_id  full_name
----------  ----------
1           Anita Rao
3           Priya Nair

status  students
------  --------
ACTIVE  2
LEFT    1
```

The cost of soft delete is real, and worth naming in an interview: every query
now needs `WHERE status = 'ACTIVE'`, and forgetting it once produces a report
that includes students who left. The usual fix is a view that filters them out,
which the views lesson later in this track shows.

A second pattern you will meet is the **upsert**: insert a row, or update it if
it already exists. It is how an import can be re-run safely after it failed
halfway.

::runner{lang="sql"}
```sql [upsert.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, email TEXT UNIQUE, city TEXT);
INSERT INTO Student VALUES (1, 'Anita Rao', 'anita@college.edu', 'Bhopal');

-- The admission office re-sends Anita with a new city. Insert, or update if the email exists.
INSERT INTO Student (student_id, full_name, email, city)
VALUES (7, 'Anita Rao', 'anita@college.edu', 'Indore')
ON CONFLICT (email) DO UPDATE SET city = excluded.city;

SELECT * FROM Student;
```
::

```text [Output]
student_id  full_name  email              city
----------  ---------  -----------------  ------
1           Anita Rao  anita@college.edu  Indore
```

This syntax works in SQLite and PostgreSQL. MySQL writes it as
`INSERT ... ON DUPLICATE KEY UPDATE city = VALUES(city)`.

## What confuses people here

- **`UPDATE ... SET a = 1, b = 2`, not `SET a = 1 AND b = 2`.** The second one is
  valid SQL in MySQL and sets `a` to the result of the comparison `1 AND b = 2`,
  which is 0 or 1. No error. Wrong data.
- **`WHERE city = NULL` matches nothing.** An `UPDATE` or `DELETE` using it
  changes zero rows and looks like it worked. Use `IS NULL`; the NULL lesson
  explains why.
- **Deleting a row that other rows point at.** Deleting a student who has exam
  results either fails (with a foreign key) or leaves orphan results pointing at
  nobody (without one). The constraints lesson covers this.
- **DELETE is not the only way to empty a table.** `TRUNCATE` and `DROP` exist,
  behave differently, and the difference is one of the most asked SQL
  questions. It has its own lesson at the end of this track.
- **SQL injection.** When Java builds a query by gluing strings,
  `"... WHERE email = '" + email + "'"`, a user can type SQL into the email box.
  The fix is a `PreparedStatement` with `?` placeholders, which the Java track
  covers under JDBC. Never glue user input into SQL.

## Interview questions

::accordion
  :::accordion-item{label="What happens if you run UPDATE or DELETE without a WHERE clause?" icon="i-lucide-message-circle"}
  It applies to every row in the table, with no error and no confirmation.
  `UPDATE Faculty SET salary = 90000;` gives all four faculty the same salary.
  The protection is a habit: run the `WHERE` as a `SELECT` first, then run the
  write inside `BEGIN`, check the affected-row count, and `COMMIT` or
  `ROLLBACK`.
  :::
  :::accordion-item{label="Write a query to give every CSE faculty member a 10% raise." icon="i-lucide-message-circle"}
  ```sql [raise.sql]
  UPDATE Faculty
  SET    salary = salary * 1.10
  WHERE  department_id = (SELECT department_id FROM Department WHERE name = 'CSE');
  ```

  ```text [Output (PostgreSQL, on the four faculty above)]
  UPDATE 3
  ```
  Mention that you would run the `SELECT` with the same `WHERE` first.
  :::
  :::accordion-item{label="How do you insert several rows in one statement?" icon="i-lucide-message-circle"}
  One `VALUES` clause with several tuples:
  `INSERT INTO Student (student_id, full_name) VALUES (2, 'Rahul Verma'), (3, 'Priya Nair');`
  Or `INSERT INTO ... SELECT ...` to insert the result of a query.
  :::
  :::accordion-item{label="What is a soft delete, and why would you use one?" icon="i-lucide-message-circle"}
  Marking a row as removed (`status = 'LEFT'`, or a `deleted_at` date) instead
  of deleting it. History, audit and reports survive, and it can be undone. The
  cost is that every query must filter out the marked rows, usually through a
  view.
  :::
  :::accordion-item{label="What is an upsert?" icon="i-lucide-message-circle"}
  Insert a row, or update it if a row with the same key already exists, in one
  statement. `INSERT ... ON CONFLICT (email) DO UPDATE ...` in PostgreSQL and
  SQLite, `INSERT ... ON DUPLICATE KEY UPDATE ...` in MySQL, `MERGE` in Oracle
  and SQL Server.
  :::
::
