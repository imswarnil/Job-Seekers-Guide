questions as interviewers actually phrase them, and answers short enough to say
out loud. Along with Java, this was the round most likely to decide a technical
interview in the walk-ins I sat, and it is the most practical one: often a
schema on paper and "write me a query".

Read each question, answer it aloud or on paper, and only then open it.

## Theory

::accordion
  :::accordion-item{label="1. What is the difference between a DBMS and an RDBMS?" icon="i-lucide-message-circle"}
  A DBMS stores and manages data and controls access to it. An RDBMS is a DBMS
  that stores data as related tables and enforces those relationships with keys.
  MySQL, PostgreSQL, Oracle and SQL Server are RDBMSs; MongoDB is a DBMS that is
  not relational.
  :::
  :::accordion-item{label="2. What are DDL, DML, DCL and TCL?" icon="i-lucide-message-circle"}
  DDL defines structure (`CREATE`, `ALTER`, `DROP`, `TRUNCATE`). DML changes rows
  (`INSERT`, `UPDATE`, `DELETE`). DCL controls access (`GRANT`, `REVOKE`). TCL
  controls transactions (`COMMIT`, `ROLLBACK`, `SAVEPOINT`). `SELECT` is DQL, or
  DML in some books. Add that DDL commits implicitly in MySQL and Oracle.
  :::
  :::accordion-item{label="3. DELETE vs TRUNCATE vs DROP?" icon="i-lucide-message-circle"}
  `DELETE`: DML, rows matching `WHERE`, logged per row, fires triggers, can be
  rolled back. `TRUNCATE`: DDL, all rows at once, no `WHERE`, resets identity,
  no rollback in MySQL or Oracle. `DROP`: DDL, removes the table itself with its
  structure, indexes and constraints.
  :::
  :::accordion-item{label="4. Primary key vs unique key vs foreign key?" icon="i-lucide-message-circle"}
  Primary: unique, never `NULL`, one per table, the row's identity. Unique:
  no duplicates, `NULL` allowed, many per table. Foreign: a value that must exist
  in another table's key, which is referential integrity.
  :::
  :::accordion-item{label="5. What constraints does SQL have?" icon="i-lucide-message-circle"}
  `NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, `CHECK`, `DEFAULT`. The
  bank's `ExamResult` has a `CHECK`, which refuses marks of 140:

  ```sql [q5.sql]
  INSERT INTO ExamResult VALUES (10, 1, 'CS203', 140);
  ```

  ```text [Output]
  Error: CHECK constraint failed: marks BETWEEN 0 AND 100
  ```
  :::
  :::accordion-item{label="6. What is a view? Does it store data?" icon="i-lucide-message-circle"}
  A stored query used like a table. It stores no rows: every read runs the query
  against the current data. Used for reuse, simplicity and restricting access. A
  materialised view does store its result and must be refreshed.
  :::
  :::accordion-item{label="7. What is an index? Why not index every column?" icon="i-lucide-message-circle"}
  A sorted structure (usually a B+ tree) over columns, so the database can find
  rows without scanning the table. Every index slows every insert, update and
  delete and takes space, so index only the columns used in frequent `WHERE`,
  `JOIN` and `ORDER BY`.
  :::
  :::accordion-item{label="8. Clustered vs non-clustered index?" icon="i-lucide-message-circle"}
  A clustered index is the table's physical order, so there is one per table (the
  primary key in MySQL's InnoDB). A non-clustered index is a separate structure
  pointing back to the rows; a table can have many.
  :::
  :::accordion-item{label="9. What is a transaction? What is ACID?" icon="i-lucide-message-circle"}
  A group of statements that succeed or fail as one. ACID: Atomicity (all or
  nothing), Consistency (rules hold before and after), Isolation (concurrent
  transactions do not see each other's half-done work), Durability (committed
  means it survives a crash).
  :::
  :::accordion-item{label="10. What is NULL? Why does = NULL not work?" icon="i-lucide-message-circle"}
  The absence of a value. Comparisons with `NULL` are `UNKNOWN`, not `TRUE`, and
  only `TRUE` rows are returned, so `WHERE city = NULL` matches nothing. Use
  `IS NULL`:

  ```sql [q10.sql]
  SELECT (SELECT COUNT(*) FROM Student WHERE city = NULL)  AS equals_null,
         (SELECT COUNT(*) FROM Student WHERE city IS NULL) AS is_null;
  ```

  ```text [Output]
  equals_null  is_null
  -----------  -------
  0            1
  ```
  :::
::

## Querying and filtering

::accordion
  :::accordion-item{label="11. What is the order of execution of a SQL query?" icon="i-lucide-message-circle"}
  `FROM`/`JOIN`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `ORDER BY`, `LIMIT`.
  Then use it: that is why a `SELECT` alias fails in `WHERE` but works in
  `ORDER BY`, and why aggregate conditions go in `HAVING`.
  :::
  :::accordion-item{label="12. WHERE vs HAVING?" icon="i-lucide-message-circle"}
  `WHERE` filters rows before grouping; `HAVING` filters groups after, and can use
  aggregates. Departments with more than one student admitted in 2025:

  ```sql [q12.sql]
  SELECT department_id, COUNT(*) AS students
  FROM   Student
  WHERE  admission_year = 2025
  GROUP BY department_id
  HAVING COUNT(*) > 1;
  ```

  ```text [Output]
  department_id  students
  -------------  --------
  1              2
  ```
  The `WHERE` kept only 2025 admissions; the `HAVING` kept only departments
  with more than one of them.
  :::
  :::accordion-item{label="13. COUNT(*) vs COUNT(column) vs COUNT(DISTINCT column)?" icon="i-lucide-message-circle"}
  ```sql [q13.sql]
  SELECT COUNT(*) AS rows_, COUNT(marks) AS marked, COUNT(DISTINCT marks) AS distinct_marks
  FROM   ExamResult;
  ```

  ```text [Output]
  rows_  marked  distinct_marks
  -----  ------  --------------
  9      8       6
  ```
  Nine rows, eight with marks (one is `NULL`), six different mark values.
  :::
  :::accordion-item{label="14. Find students whose name starts with 'A'." icon="i-lucide-message-circle"}
  ```sql [q14.sql]
  SELECT full_name FROM Student WHERE full_name LIKE 'A%';
  ```

  ```text [Output]
  full_name
  -----------
  Anita Rao
  Arjun Mehta
  ```
  `%` is any run of characters, `_` exactly one.
  :::
  :::accordion-item{label="15. Is BETWEEN inclusive?" icon="i-lucide-message-circle"}
  Yes, at both ends:

  ```sql [q15.sql]
  SELECT student_id, marks FROM ExamResult WHERE marks BETWEEN 72 AND 87 ORDER BY marks;
  ```

  ```text [Output]
  student_id  marks
  ----------  -----
  1           72
  3           72
  5           78
  1           87
  4           87
  ```
  For dates with times, prefer `>= start AND < next_start`.
  :::
  :::accordion-item{label="16. Why does NOT IN return no rows here?" icon="i-lucide-message-circle"}
  "Departments with no students" with `NOT IN` fails because Karan's
  `department_id` is `NULL`, and `x NOT IN (..., NULL)` is never `TRUE`:

  ```sql [q16.sql]
  SELECT name FROM Department WHERE department_id NOT IN (SELECT department_id FROM Student);
  SELECT name FROM Department d
  WHERE  NOT EXISTS (SELECT 1 FROM Student s WHERE s.department_id = d.department_id);
  ```

  ```text [Output]
  name
  -----
  Civil
  ```
  The first query printed nothing; `NOT EXISTS` found Civil.
  :::
::

## Joins

::accordion
  :::accordion-item{label="17. Explain the types of joins." icon="i-lucide-message-circle"}
  By what happens to unmatched rows: `INNER` keeps only matches, `LEFT` keeps
  every left row, `RIGHT` every right row, `FULL` everything; `CROSS` pairs every
  row with every row; a self join is a table joined to itself.

  ```sql [q17.sql]
  SELECT 'inner' AS join_type, COUNT(*) AS n_rows FROM Student s JOIN Department d ON d.department_id = s.department_id
  UNION ALL
  SELECT 'left',  COUNT(*) FROM Student s LEFT JOIN Department d ON d.department_id = s.department_id
  UNION ALL
  SELECT 'right', COUNT(*) FROM Student s RIGHT JOIN Department d ON d.department_id = s.department_id
  UNION ALL
  SELECT 'full',  COUNT(*) FROM Student s FULL JOIN Department d ON d.department_id = s.department_id
  UNION ALL
  SELECT 'cross', COUNT(*) FROM Student s CROSS JOIN Department d;
  ```

  ```text [Output]
  join_type  n_rows
  ---------  ------
  inner      5
  left       6
  right      6
  full       7
  cross      24
  ```
  Karan has no department (left and full keep him); Civil has no students (right
  and full keep it); 6 × 4 = 24 for cross.
  :::
  :::accordion-item{label="18. Find faculty who earn more than their head." icon="i-lucide-message-circle"}
  ```sql [q18.sql]
  SELECT f.full_name, f.salary, h.full_name AS head, h.salary AS head_salary
  FROM   Faculty f JOIN Faculty h ON h.faculty_id = f.reports_to
  WHERE  f.salary > h.salary;
  ```

  ```text [Output]
  full_name     salary  head             head_salary
  ------------  ------  ---------------  -----------
  Anjali Desai  155000  Dr. Meera Joshi  150000
  Divya Menon   145000  Dr. Suresh Rao   140000
  ```
  :::
  :::accordion-item{label="19. Number of students in every department, including empty ones." icon="i-lucide-message-circle"}
  ```sql [q19.sql]
  SELECT d.name, COUNT(s.student_id) AS students
  FROM   Department d LEFT JOIN Student s ON s.department_id = d.department_id
  GROUP BY d.name
  ORDER BY students DESC, d.name;
  ```

  ```text [Output]
  name        students
  ----------  --------
  CSE         3
  ECE         1
  Mechanical  1
  Civil       0
  ```
  `COUNT(s.student_id)`, not `COUNT(*)`, or Civil shows 1.
  :::
  :::accordion-item{label="20. What is fan-out, and why does it matter?" icon="i-lucide-message-circle"}
  Joining a table to several matching rows multiplies the rows, and every `SUM`
  and `COUNT` over them. A student with two payments and three enrolments
  appears six times, so their fees are tripled. Fix by aggregating each table
  in a subquery before joining.
  :::
::

## Subqueries and set operations

::accordion
  :::accordion-item{label="21. Find students who scored above the average in CS201." icon="i-lucide-message-circle"}
  ```sql [q21.sql]
  SELECT student_id, marks FROM ExamResult
  WHERE  course_code = 'CS201'
    AND  marks > (SELECT AVG(marks) FROM ExamResult WHERE course_code = 'CS201')
  ORDER BY marks DESC;
  ```

  ```text [Output]
  student_id  marks
  ----------  -----
  3           91
  1           87
  4           87
  ```
  The CS201 average is 81.4.
  :::
  :::accordion-item{label="22. What is a correlated subquery? Give an example." icon="i-lucide-message-circle"}
  A subquery that refers to the outer row, so it is evaluated per row. Each
  student's results above that student's own average:

  ```sql [q22.sql]
  SELECT e.student_id, e.course_code, e.marks
  FROM   ExamResult e
  WHERE  e.marks > (SELECT AVG(x.marks) FROM ExamResult x WHERE x.student_id = e.student_id);
  ```

  ```text [Output]
  student_id  course_code  marks
  ----------  -----------  -----
  1           CS201        87
  3           CS201        91
  5           CS201        78
  ```
  :::
  :::accordion-item{label="23. EXISTS vs IN?" icon="i-lucide-message-circle"}
  `IN` compares against a returned list; `EXISTS` asks whether any matching row
  exists and stops at the first. The practical difference is negation: `NOT IN`
  breaks on `NULL`, `NOT EXISTS` does not (question 16).
  :::
  :::accordion-item{label="24. UNION vs UNION ALL?" icon="i-lucide-message-circle"}
  ```sql [q24.sql]
  SELECT COUNT(*) AS union_rows     FROM (SELECT city FROM Student UNION     SELECT 'Bhopal');
  SELECT COUNT(*) AS union_all_rows FROM (SELECT city FROM Student UNION ALL SELECT 'Bhopal');
  ```

  ```text [Output]
  union_rows
  ----------
  5

  union_all_rows
  --------------
  7
  ```
  `UNION` removed the repeated cities (and kept one `NULL`); `UNION ALL` kept all
  seven rows. `UNION ALL` is faster; use it when duplicates are impossible or
  meaningful.
  :::
::

## The classic queries

::accordion
  :::accordion-item{label="25. Find the second highest marks." icon="i-lucide-message-circle"}
  ```sql [q25.sql]
  SELECT MAX(marks) AS second_highest FROM ExamResult
  WHERE  marks < (SELECT MAX(marks) FROM ExamResult);
  ```

  ```text [Output]
  second_highest
  --------------
  87
  ```
  Say you are treating it as the second highest **distinct** value.
  :::
  :::accordion-item{label="26. Find the Nth highest marks (N = 3)." icon="i-lucide-message-circle"}
  ```sql [q26.sql]
  WITH r AS (SELECT marks, DENSE_RANK() OVER (ORDER BY marks DESC) AS rnk
             FROM ExamResult WHERE marks IS NOT NULL)
  SELECT DISTINCT marks AS third_highest FROM r WHERE rnk = 3;
  ```

  ```text [Output]
  third_highest
  -------------
  78
  ```
  Distinct marks are 91, 87, 78, 72, 64, 58, so the third is 78.
  :::
  :::accordion-item{label="27. Find duplicate emails." icon="i-lucide-message-circle"}
  ```sql [q27.sql]
  SELECT email, COUNT(*) AS copies FROM Student GROUP BY email HAVING COUNT(*) > 1;
  ```

  ```text [Output]
  email              copies
  -----------------  ------
  anita@college.edu  2
  ```
  To delete all but one: `DELETE FROM Student WHERE student_id NOT IN (SELECT
  MIN(student_id) FROM Student GROUP BY email);` inside a transaction, after
  running it as a `SELECT`.
  :::
  :::accordion-item{label="28. Find the top student in each course." icon="i-lucide-message-circle"}
  ```sql [q28.sql]
  WITH r AS (
    SELECT course_code, student_id, marks,
           DENSE_RANK() OVER (PARTITION BY course_code ORDER BY marks DESC) AS rnk
    FROM   ExamResult WHERE marks IS NOT NULL
  )
  SELECT course_code, student_id, marks FROM r WHERE rnk = 1 ORDER BY course_code, student_id;
  ```

  ```text [Output]
  course_code  student_id  marks
  -----------  ----------  -----
  CS201        3           91
  CS202        1           72
  CS202        3           72
  ```
  CS202 has two toppers on 72. `ROW_NUMBER` would have picked one of them.
  :::
  :::accordion-item{label="29. Department with the highest average marks." icon="i-lucide-message-circle"}
  ```sql [q29.sql]
  WITH d AS (
    SELECT s.department_id, ROUND(AVG(e.marks), 2) AS average
    FROM   ExamResult e JOIN Student s ON s.student_id = e.student_id
    GROUP BY s.department_id
  )
  SELECT department_id, average FROM d WHERE average = (SELECT MAX(average) FROM d);
  ```

  ```text [Output]
  department_id  average
  -------------  -------
  3              87.0
  ```
  :::
::

## Windows, CASE and transactions

::accordion
  :::accordion-item{label="30. RANK vs DENSE_RANK vs ROW_NUMBER?" icon="i-lucide-message-circle"}
  ```sql [q30.sql]
  SELECT student_id, marks,
         ROW_NUMBER() OVER (ORDER BY marks DESC, student_id) AS row_num,
         RANK()       OVER (ORDER BY marks DESC)             AS rnk,
         DENSE_RANK() OVER (ORDER BY marks DESC)             AS dense_rnk
  FROM   ExamResult WHERE course_code = 'CS201';
  ```

  ```text [Output]
  student_id  marks  row_num  rnk  dense_rnk
  ----------  -----  -------  ---  ---------
  3           91     1        1    1
  1           87     2        2    2
  4           87     3        2    2
  5           78     4        4    3
  2           64     5        5    4
  ```
  :::
  :::accordion-item{label="31. Show each result with the student's previous result." icon="i-lucide-message-circle"}
  ```sql [q31.sql]
  SELECT student_id, course_code, marks,
         LAG(marks) OVER (PARTITION BY student_id ORDER BY result_id) AS previous
  FROM   ExamResult WHERE student_id IN (1, 3, 5)
  ORDER BY student_id, result_id;
  ```

  ```text [Output]
  student_id  course_code  marks  previous
  ----------  -----------  -----  --------
  1           CS201        87     NULL
  1           CS202        72     87
  3           CS201        91     NULL
  3           CS202        72     91
  5           CS201        78     NULL
  5           CS202        58     78
  ```
  :::
  :::accordion-item{label="32. Convert marks into grades." icon="i-lucide-message-circle"}
  ```sql [q32.sql]
  SELECT student_id, marks,
         CASE WHEN marks >= 90 THEN 'O' WHEN marks >= 75 THEN 'A'
              WHEN marks >= 60 THEN 'B' WHEN marks >= 40 THEN 'C'
              WHEN marks IS NULL THEN 'Absent' ELSE 'F' END AS grade
  FROM   ExamResult WHERE course_code = 'CS202';
  ```

  ```text [Output]
  student_id  marks  grade
  ----------  -----  ------
  1           72     B
  3           72     B
  5           58     C
  2           NULL   Absent
  ```
  :::
  :::accordion-item{label="33. Count passes and fails per course in one query." icon="i-lucide-message-circle"}
  ```sql [q33.sql]
  SELECT course_code,
         SUM(CASE WHEN marks >= 60 THEN 1 ELSE 0 END) AS passed,
         SUM(CASE WHEN marks <  60 THEN 1 ELSE 0 END) AS failed,
         SUM(CASE WHEN marks IS NULL THEN 1 ELSE 0 END) AS absent
  FROM   ExamResult GROUP BY course_code;
  ```

  ```text [Output]
  course_code  passed  failed  absent
  -----------  ------  ------  ------
  CS201        5       0       0
  CS202        2       1       1
  ```
  (Pass mark 60 here, to make the fails visible.)
  :::
  :::accordion-item{label="34. What happens to your changes if you ROLLBACK?" icon="i-lucide-message-circle"}
  Every change since `BEGIN` is discarded:

  ```sql [q34.sql]
  BEGIN;
  UPDATE Faculty SET salary = 0;
  ROLLBACK;
  SELECT SUM(salary) AS total_salary FROM Faculty;
  ```

  ```text [Output]
  total_salary
  ------------
  763000
  ```
  The salaries are untouched. In MySQL the same is not true if a DDL statement
  (which commits implicitly) ran in between.
  :::
::

## What every good answer above has in common

Each one says the rule, then **proves it** with a small query and its result,
then names the trap. Reciting the definition of `LEFT JOIN` is common. Adding
"and if you filter the right table in `WHERE`, it becomes an inner join" is
what an interviewer remembers.
