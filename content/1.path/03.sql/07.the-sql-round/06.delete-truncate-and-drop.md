`TRUNCATE` turned out to be DDL while `DELETE` is DML, and that is only one of
seven differences between them and `DROP`. "What is the difference between
DELETE, TRUNCATE and DROP?" is, in my experience, the most asked SQL theory
question for freshers, and a complete answer takes about forty seconds.

::warning{icon="i-lucide-alert-triangle"}
All three destroy data, and two of them cannot be undone in MySQL and Oracle.
Practise on a copy, never on a table you care about, and never on a live
database without a backup you have checked. Read the whole lesson before you
type any of them anywhere real.
::

## Why this matters in a job

Beyond the interview, choosing the wrong one is a real incident. `TRUNCATE` on
the wrong table in MySQL is gone the moment you press Enter. `DROP` takes the
table's structure, indexes, constraints and permissions with it, so even
restoring the rows from a backup is not enough to put things back. Knowing
exactly what each removes is how you choose the least destructive tool that does
the job.

## Three ways to clear a notice board

Picture the college notice board. **DELETE** is taking notices down one at a
time; you can choose which ones (`WHERE`), and the office register records each
removal, so it can be undone. **TRUNCATE** is pulling every notice off in one
sweep: much faster, no choosing, and in some colleges no record of what was on
it. **DROP** is unscrewing the notice board from the wall and taking it away:
the notices, the board, the frame and the label saying what it was for.

::flow{direction="horizontal" caption="From least to most destructive."}
  :::flow-step{label="DELETE" icon="i-lucide-eraser"}
  Some or all rows. Table stays.
  :::
  :::flow-step{label="TRUNCATE" icon="i-lucide-scissors"}
  All rows. Table stays, empty.
  :::
  :::flow-step{label="DROP" icon="i-lucide-trash-2" highlight}
  Rows, structure, indexes, constraints. Table gone.
  :::
::

## How it works

| | `DELETE` | `TRUNCATE` | `DROP` |
| --- | --- | --- | --- |
| Removes | Rows matching `WHERE` (all if none) | All rows | The whole table: rows, structure, indexes, constraints, grants |
| `WHERE` allowed | Yes | No | No |
| Family | DML | DDL | DDL |
| Rollback | Yes, inside a transaction | MySQL, Oracle: **no**. PostgreSQL, SQL Server: yes | MySQL, Oracle: **no**. PostgreSQL, SQL Server: yes |
| Row triggers fire | Yes | No | No |
| Auto-increment / identity | Keeps counting | Reset to the start | Gone with the table |
| Speed on a big table | Slow: logs every row | Fast: deallocates pages | Fast |
| Blocked by foreign keys? | Only the referenced rows | Yes, if any table references it | Yes, unless `CASCADE` |

SQLite, the runner's database, has `DELETE` and `DROP` but **no `TRUNCATE`**. A
`DELETE FROM table` with no `WHERE` is SQLite's equivalent, and it is optimised
to clear the table quickly.

::runner{lang="sql"}
```sql [delete-vs-drop.sql]
CREATE TABLE Attendance (attendance_id INTEGER PRIMARY KEY AUTOINCREMENT,
                         student_id INTEGER, class_date TEXT, present INTEGER);
INSERT INTO Attendance (student_id, class_date, present) VALUES
  (1, '2025-08-04', 1), (2, '2025-08-04', 0), (1, '2025-08-05', 1), (2, '2025-08-05', 1);

-- DELETE with a WHERE: some rows.
DELETE FROM Attendance WHERE class_date = '2025-08-04';
SELECT COUNT(*) AS after_delete_where FROM Attendance;

-- DELETE with no WHERE: every row, table kept, id counter kept.
DELETE FROM Attendance;
INSERT INTO Attendance (student_id, class_date, present) VALUES (3, '2025-08-06', 1);
SELECT attendance_id, student_id FROM Attendance;   -- id continues at 5, not 1

-- DROP: the table itself is gone.
DROP TABLE Attendance;
SELECT name FROM sqlite_master WHERE type = 'table' AND name = 'Attendance';
```
::

```text [Output]
after_delete_where
------------------
2

attendance_id  student_id
-------------  ----------
5              3
```

The new row got id 5, not 1: `DELETE` removed the rows but kept the counter.
`TRUNCATE` in MySQL would have reset it to 1. The last query returns nothing,
because after `DROP` the table does not exist at all, and any query on it
fails:

::runner{lang="sql"}
```sql [after-drop.sql]
CREATE TABLE Attendance (attendance_id INTEGER PRIMARY KEY, student_id INTEGER);
DROP TABLE Attendance;
SELECT * FROM Attendance;
```
::

```text [Output]
Error: no such table: Attendance
```

### Rollback, side by side

::runner{lang="sql"}
```sql [delete-rollback.sql]
CREATE TABLE Attendance (attendance_id INTEGER PRIMARY KEY, student_id INTEGER, present INTEGER);
INSERT INTO Attendance VALUES (1, 1, 1), (2, 2, 0), (3, 3, 1);

BEGIN;
DELETE FROM Attendance;
SELECT COUNT(*) AS inside_transaction FROM Attendance;
ROLLBACK;

SELECT COUNT(*) AS after_rollback FROM Attendance;
```
::

```text [Output]
inside_transaction
------------------
0

after_rollback
--------------
3
```

The same with `TRUNCATE` in MySQL:

```sql [truncate-mysql.sql]
-- MySQL 8
START TRANSACTION;
TRUNCATE TABLE Attendance;
ROLLBACK;
SELECT COUNT(*) FROM Attendance;
```

```text [Output (MySQL 8, illustrative)]
+----------+
| COUNT(*) |
+----------+
|        0 |
+----------+
```

The `ROLLBACK` had nothing to undo: `TRUNCATE` committed on its own. In
PostgreSQL the same script leaves all three rows in place.

## Real use case

At the end of each semester a college clears its `AttendanceStaging` table, the
scratch table where the day's biometric punches are loaded before being checked
and copied into the real `Attendance` table. Which command, and why?

::compare{caption="Three candidates for clearing a staging table."}
  :::compare-side{label="DELETE FROM AttendanceStaging" verdict="right"}
  Correct, and the safe default when you are unsure: can take a `WHERE`, can be
  rolled back, fires triggers. Slow if the table holds crores of rows.
  :::
  :::compare-side{label="TRUNCATE TABLE AttendanceStaging" verdict="right"}
  The usual choice for a staging table: instant, resets the id counter, and
  nothing in it needs keeping. Safe here because it is only ever scratch data.
  :::
::

And `DROP` is wrong for this job: the loader would fail the next morning with
"table not found", and whoever recreates the table has to remember every index
and constraint it had.

The inverse mistake, `TRUNCATE` on the real `Attendance` table because someone
meant to type `AttendanceStaging`, is the reason to check which database and
which table you are connected to before running any of the three.

## What confuses people here

- **"DELETE without WHERE is the same as TRUNCATE."** Same rows gone; different
  logging, triggers, rollback (in MySQL and Oracle), speed and identity counter.
- **"TRUNCATE can never be rolled back."** True in MySQL and Oracle, false in
  PostgreSQL and SQL Server. Name the database when you answer.
- **Foreign keys block `TRUNCATE`.** In MySQL you cannot `TRUNCATE Student` while
  `ExamResult` references it, even if `ExamResult` is empty. `DELETE` works if no
  rows reference the ones being deleted.
- **`DELETE` does not always shrink the file.** The space is marked free and
  reused, but the file on disk may stay the same size until the table is
  rebuilt (`VACUUM` in SQLite and PostgreSQL, `OPTIMIZE TABLE` in MySQL).
- **`DROP TABLE IF EXISTS`** avoids an error when the table is missing, which is
  why it appears at the top of setup scripts. It is still a `DROP`.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between DELETE, TRUNCATE and DROP?" icon="i-lucide-message-circle"}
  `DELETE` is DML: removes rows, optionally with `WHERE`, logs each row, fires
  triggers, can be rolled back. `TRUNCATE` is DDL: removes all rows at once, no
  `WHERE`, no row triggers, resets identity, and in MySQL and Oracle cannot be
  rolled back. `DROP` is DDL: removes the table itself, with its structure,
  indexes and constraints. Then give the rule: `DELETE` for some rows, `TRUNCATE`
  to empty a scratch table, `DROP` only when the table should no longer exist.
  :::
  :::accordion-item{label="Which is faster, DELETE or TRUNCATE? Why?" icon="i-lucide-message-circle"}
  `TRUNCATE`, because it deallocates the table's data pages in one operation
  instead of removing and logging each row. On a table with crores of rows,
  `DELETE` can take minutes and fill the transaction log; `TRUNCATE` is near
  instant.
  :::
  :::accordion-item{label="Can you use WHERE with TRUNCATE?" icon="i-lucide-message-circle"}
  No. `TRUNCATE` always removes every row. To remove some rows, use `DELETE ...
  WHERE`.
  :::
  :::accordion-item{label="Can you roll back a DELETE? A TRUNCATE?" icon="i-lucide-message-circle"}
  `DELETE`, yes, inside a transaction: the runner above went from 0 rows inside
  the transaction back to 3 after `ROLLBACK`. `TRUNCATE`: not in MySQL or Oracle
  (implicit commit), yes in PostgreSQL and SQL Server.
  :::
  :::accordion-item{label="After TRUNCATE, does the auto-increment reset?" icon="i-lucide-message-circle"}
  Yes, in MySQL and SQL Server the next row starts from 1 again. After `DELETE`
  the counter continues; above, the next id after deleting four rows was 5.
  :::
::
