The last lesson ended with aggregates skipping `NULL` silently, and you have
been using `COUNT` and `AVG` without a proper introduction. Here it is: the five
functions that turn a thousand rows into one number.

## Why this matters in a job

"How many students", "total fees collected this month", "average marks in Data
Structures", "highest package this year": every one of them is an aggregate, and
they are most of what a manager actually asks a database. In interviews they
appear inside nearly every query question, and on their own as "difference
between `COUNT(*)`, `COUNT(1)` and `COUNT(column)`".

## Many rows in, one value out

A normal function such as `ROUND(marks)` or `UPPER(full_name)` works on one row
at a time: one row in, one value out, for every row. An **aggregate function**
works on a whole set of rows: many rows in, **one** value out.

::compare{caption="The difference is how many rows come back."}
  :::compare-side{label="Row function" verdict="right"}
  `SELECT UPPER(full_name) FROM Student` returns one row per student.
  :::
  :::compare-side{label="Aggregate function" verdict="right"}
  `SELECT COUNT(*) FROM Student` returns exactly one row, whatever the size of
  the table.
  :::
::

| Function | Returns | Ignores `NULL`? |
| --- | --- | --- |
| `COUNT(*)` | Number of rows | Counts every row |
| `COUNT(col)` | Number of non-`NULL` values in `col` | Yes |
| `COUNT(DISTINCT col)` | Number of different non-`NULL` values | Yes |
| `SUM(col)` | Total | Yes |
| `AVG(col)` | Mean: sum divided by the **non-`NULL`** count | Yes |
| `MIN(col)` / `MAX(col)` | Smallest / largest (numbers, dates and text) | Yes |

## Syntax

```sql [aggregate-syntax.sql]
SELECT COUNT(*), SUM(col), AVG(col), MIN(col), MAX(col)
FROM   table_name
WHERE  condition;       -- filters rows BEFORE they are aggregated
```

::runner{lang="sql"}
```sql [exam-summary.sql]
CREATE TABLE ExamResult (
  result_id   INTEGER PRIMARY KEY,
  student_id  INTEGER,
  course_id   INTEGER,
  marks       INTEGER,
  exam_date   TEXT
);
INSERT INTO ExamResult VALUES
  (1, 1, 101, 87, '2025-11-20'),
  (2, 2, 101, 64, '2025-11-20'),
  (3, 3, 101, 91, '2025-11-20'),
  (4, 4, 101, NULL, '2025-11-20'),
  (5, 1, 102, 72, '2025-12-02'),
  (6, 2, 102, 38, '2025-12-02'),
  (7, 3, 102, 91, '2025-12-02');

SELECT COUNT(*)                   AS results,
       COUNT(marks)               AS marked,
       COUNT(DISTINCT student_id) AS students,
       SUM(marks)                 AS total_marks,
       ROUND(AVG(marks), 2)       AS average,
       MIN(marks)                 AS lowest,
       MAX(marks)                 AS highest
FROM   ExamResult;
```
::

```text [Output]
results  marked  students  total_marks  average  lowest  highest
-------  ------  --------  -----------  -------  ------  -------
7        6       4         443          73.83    38      91
```

Seven rows, six of them marked, four different students. `AVG` is 443 divided
by 6, not by 7. `ROUND(x, 2)` keeps two decimal places.

### With a WHERE

`WHERE` runs first, so the aggregate only sees the rows that survive:

::runner{lang="sql"}
```sql [course-101.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, course_id INTEGER, marks INTEGER, exam_date TEXT);
INSERT INTO ExamResult VALUES
  (1, 1, 101, 87, '2025-11-20'), (2, 2, 101, 64, '2025-11-20'), (3, 3, 101, 91, '2025-11-20'),
  (4, 4, 101, NULL, '2025-11-20'), (5, 1, 102, 72, '2025-12-02'), (6, 2, 102, 38, '2025-12-02'),
  (7, 3, 102, 91, '2025-12-02');

-- Course 101 only, and how many passed (40 or more).
SELECT COUNT(marks)          AS sat_and_marked,
       ROUND(AVG(marks), 1)  AS average
FROM   ExamResult
WHERE  course_id = 101;

SELECT COUNT(*) AS passed
FROM   ExamResult
WHERE  course_id = 102 AND marks >= 40;
```
::

```text [Output]
sat_and_marked  average
--------------  -------
3               80.7

passed
------
2
```

### MIN and MAX on dates and text

They are not only for numbers. On dates, `MIN` is the earliest; on text, it is
alphabetical order.

::runner{lang="sql"}
```sql [min-max-other.sql]
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeePayment VALUES
  (1, 1, 42500, '2025-07-14'), (2, 2, 42500, '2025-07-02'),
  (3, 3, 21250, '2025-08-30'), (4, 3, 21250, '2025-09-29');

SELECT MIN(paid_on)  AS first_payment,
       MAX(paid_on)  AS last_payment,
       SUM(amount)   AS collected,
       COUNT(*)      AS payments
FROM   FeePayment;
```
::

```text [Output]
first_payment  last_payment  collected  payments
-------------  ------------  ---------  --------
2025-07-02     2025-09-29    127500     4
```

## Real use case

The accounts office sends the principal a one-line summary of fee collection for
July: how many payments, how many different students paid, the total, and the
average payment. This is the query behind that line, and the kind of thing I
wrote every week as an analytics engineer, on sales data rather than fees:

::runner{lang="sql"}
```sql [july-summary.sql]
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeePayment VALUES
  (1, 1, 42500, '2025-07-14'), (2, 2, 20000, '2025-07-02'),
  (3, 2, 22500, '2025-07-28'), (4, 3, 42500, '2025-07-30'),
  (5, 4, 42500, '2025-08-03');

SELECT COUNT(*)                    AS payments,
       COUNT(DISTINCT student_id)  AS students_paid,
       SUM(amount)                 AS total_collected,
       ROUND(AVG(amount), 0)       AS average_payment
FROM   FeePayment
WHERE  paid_on >= '2025-07-01' AND paid_on < '2025-08-01';
```
::

```text [Output]
payments  students_paid  total_collected  average_payment
--------  -------------  ---------------  ---------------
4         3              127500           31875.0
```

Four payments but three students, because student 2 paid in two instalments. If the
line said "4 students paid", it would be wrong, and the principal would notice
at the next meeting. `COUNT(*)` against `COUNT(DISTINCT student_id)` is the
difference between counting events and counting people.

## What confuses people here

- **You cannot put a plain column next to an aggregate** without `GROUP BY`.
  `SELECT full_name, MAX(marks) FROM ExamResult` asks for "the name" alongside
  one maximum, and there are seven names. PostgreSQL, Oracle and SQL Server
  reject it. SQLite and old MySQL accept it and return the name from some row,
  which is how wrong reports are born. The next lesson is about doing this
  properly.
- **`WHERE` cannot contain an aggregate.** `WHERE AVG(marks) > 60` fails,
  because `WHERE` runs before any aggregate exists. That is what `HAVING` is
  for, next lesson.
- **`COUNT(1)` is the same as `COUNT(*)`.** Both count rows. There is no
  performance difference in any modern database, whatever you may be told.
- **`SUM` of no rows is `NULL`, not 0.** `SELECT SUM(amount) FROM FeePayment
  WHERE paid_on > '2030-01-01'` returns `NULL`. Wrap it: `COALESCE(SUM(amount), 0)`.
- **Integer averages.** In some databases `AVG` of whole numbers returns a whole
  number, and `SUM(marks) / COUNT(marks)` in integer arithmetic throws away the
  decimals. Multiply by `1.0` first if you divide yourself.

::runner{lang="sql"}
```sql [integer-division.sql]
SELECT 443 / 6        AS integer_division,
       443 * 1.0 / 6  AS real_division;
```
::

```text [Output]
integer_division  real_division
----------------  ----------------
73                73.8333333333333
```

## Interview questions

::accordion
  :::accordion-item{label="What are aggregate functions? Name them." icon="i-lucide-message-circle"}
  Functions that take many rows and return one value: `COUNT`, `SUM`, `AVG`,
  `MIN`, `MAX`. All except `COUNT(*)` ignore `NULL`. Used with `GROUP BY`, they
  return one value per group.
  :::
  :::accordion-item{label="COUNT(*) vs COUNT(1) vs COUNT(column)?" icon="i-lucide-message-circle"}
  `COUNT(*)` and `COUNT(1)` both count rows, identically. `COUNT(marks)` counts
  rows where `marks` is not `NULL`. On the seven results above: 7, 7 and 6.
  :::
  :::accordion-item{label="What does SUM return when there are no rows?" icon="i-lucide-message-circle"}
  `NULL`, not zero. `COUNT` of no rows is 0. Use `COALESCE(SUM(amount), 0)` when
  a report needs a zero.
  :::
  :::accordion-item{label="Can you use an aggregate in a WHERE clause?" icon="i-lucide-message-circle"}
  No. `WHERE` filters rows before aggregation, so there is no aggregate yet.
  Filter on aggregates with `HAVING`, or compute the aggregate in a subquery:
  `WHERE marks > (SELECT AVG(marks) FROM ExamResult)`.
  :::
  :::accordion-item{label="Find the highest and lowest marks, and the difference between them." icon="i-lucide-message-circle"}
  `SELECT MAX(marks), MIN(marks), MAX(marks) - MIN(marks) AS spread FROM ExamResult;`
  On the data above: 91, 38 and 53. Aggregates can be used inside expressions
  like any other value.
  :::
::
