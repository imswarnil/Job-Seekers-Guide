Ranking compares each row with its whole group. "How did this student do
compared with their **previous** exam?" compares a row with the one immediately before
it. `LAG` looks back and `LEAD` looks ahead, without a self join.

## Why this matters in a job

"Change since last month", "gap between two payments", "did attendance drop
compared with last week", "next exam date": any question about change over time
compares a row with its neighbour. Before window functions, that took a
self join on "the row with the largest date smaller than mine", which is hard to
write and slow. In interviews, `LAG` and `LEAD` appear as "find students whose
marks dropped in every exam" or "month-over-month growth", and knowing them
marks you out from candidates who only know `GROUP BY`.

## Looking over your shoulder in the queue

Picture students standing in a queue in order of roll number. `LAG` is turning
round to read the number of the person **behind** you; `LEAD` is reading the
number of the person **in front**. The first person in the queue has nobody
behind them, so `LAG` gives `NULL` there unless you say what to use instead.
With `PARTITION BY`, each course has its own queue.

## Syntax

```sql [lag-lead-syntax.sql]
LAG(column, offset, default)  OVER (PARTITION BY ... ORDER BY ...)
LEAD(column, offset, default) OVER (PARTITION BY ... ORDER BY ...)
-- offset defaults to 1; default (used when there is no such row) defaults to NULL
```

::runner{lang="sql"}
```sql [marks-over-time.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, full_name TEXT, exam_date TEXT, marks INTEGER);
INSERT INTO ExamResult VALUES
  (1, 1, 'Anita Rao',   '2025-01-15', 62), (2, 1, 'Anita Rao',   '2025-05-10', 71),
  (3, 1, 'Anita Rao',   '2025-11-20', 68), (4, 2, 'Rahul Verma', '2025-01-15', 80),
  (5, 2, 'Rahul Verma', '2025-05-10', 74), (6, 2, 'Rahul Verma', '2025-11-20', 69);

SELECT full_name, exam_date, marks,
       LAG(marks)  OVER (PARTITION BY student_id ORDER BY exam_date)          AS previous,
       marks - LAG(marks) OVER (PARTITION BY student_id ORDER BY exam_date)   AS change,
       LEAD(exam_date) OVER (PARTITION BY student_id ORDER BY exam_date)      AS next_exam
FROM   ExamResult
ORDER BY student_id, exam_date;
```
::

```text [Output]
full_name    exam_date   marks  previous  change  next_exam
-----------  ----------  -----  --------  ------  ----------
Anita Rao    2025-01-15  62     NULL      NULL    2025-05-10
Anita Rao    2025-05-10  71     62        9       2025-11-20
Anita Rao    2025-11-20  68     71        -3      NULL
Rahul Verma  2025-01-15  80     NULL      NULL    2025-05-10
Rahul Verma  2025-05-10  74     80        -6      2025-11-20
Rahul Verma  2025-11-20  69     74        -5      NULL
```

Each student's first exam has no previous one (`NULL`), and each last exam has
no next one. `PARTITION BY student_id` stops Rahul's first exam from looking
back at Anita's last.

### Offset and default

::runner{lang="sql"}
```sql [offset-default.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, exam_date TEXT, marks INTEGER);
INSERT INTO ExamResult VALUES
  (1, 1, '2025-01-15', 62), (2, 1, '2025-05-10', 71), (3, 1, '2025-11-20', 68), (4, 1, '2026-05-08', 77);

SELECT exam_date, marks,
       LAG(marks, 1, 0) OVER (ORDER BY exam_date) AS previous_or_zero,
       LAG(marks, 2)    OVER (ORDER BY exam_date) AS two_exams_ago
FROM   ExamResult;
```
::

```text [Output]
exam_date   marks  previous_or_zero  two_exams_ago
----------  -----  ----------------  -------------
2025-01-15  62     0                 NULL
2025-05-10  71     62                NULL
2025-11-20  68     71                62
2026-05-08  77     68                71
```

::warning{icon="i-lucide-alert-triangle"}
`LAG(marks, 1, 0)` makes the first exam look like a jump from zero, which is a
lie on a chart. A default is a decision, exactly like `COALESCE(marks, 0)` in the
NULL lesson. Leave it `NULL` unless zero is genuinely true.
::

## FIRST_VALUE, LAST_VALUE and NTILE

Three more window functions you should recognise when you see them:

::runner{lang="sql"}
```sql [first-value-ntile.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, full_name TEXT, course_id INTEGER, marks INTEGER);
INSERT INTO ExamResult VALUES
  (1, 'Anita Rao', 101, 87), (2, 'Rahul Verma', 101, 64), (3, 'Priya Nair', 101, 91),
  (4, 'Arjun Mehta', 101, 45), (5, 'Sneha Iyer', 101, 78), (6, 'Karan Patel', 101, 55);

SELECT full_name, marks,
       FIRST_VALUE(full_name) OVER (ORDER BY marks DESC)  AS topper,
       marks - FIRST_VALUE(marks) OVER (ORDER BY marks DESC) AS behind_topper,
       NTILE(3) OVER (ORDER BY marks DESC)                AS band
FROM   ExamResult
ORDER BY marks DESC;
```
::

```text [Output]
full_name    marks  topper      behind_topper  band
-----------  -----  ----------  -------------  ----
Priya Nair   91     Priya Nair  0              1
Anita Rao    87     Priya Nair  -4             1
Sneha Iyer   78     Priya Nair  -13            2
Rahul Verma  64     Priya Nair  -27            2
Karan Patel  55     Priya Nair  -36            3
Arjun Mehta  45     Priya Nair  -46            3
```

- `FIRST_VALUE(x)` is the first row's `x` in the window: the topper.
- `LAST_VALUE(x)` is the last row's `x`, with a trap: by default the window
  only runs from the start **up to the current row**, so `LAST_VALUE` returns
  the current row. Add `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED
  FOLLOWING` to make it see the whole partition.
- `NTILE(3)` splits the ordered rows into 3 roughly equal bands: top third,
  middle, bottom.

### The frame clause, briefly

That `ROWS BETWEEN ...` is a **frame**: which rows around the current one the
function looks at. The one you will actually use is a moving average:

::runner{lang="sql"}
```sql [moving-average.sql]
CREATE TABLE Attendance (class_date TEXT, present_pct REAL);
INSERT INTO Attendance VALUES
  ('2025-08-04', 92), ('2025-08-05', 88), ('2025-08-06', 71),
  ('2025-08-07', 85), ('2025-08-08', 64), ('2025-08-11', 90);

SELECT class_date, present_pct,
       ROUND(AVG(present_pct) OVER (ORDER BY class_date
             ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 1) AS three_day_avg
FROM   Attendance;
```
::

```text [Output]
class_date  present_pct  three_day_avg
----------  -----------  -------------
2025-08-04  92.0         92.0
2025-08-05  88.0         90.0
2025-08-06  71.0         83.7
2025-08-07  85.0         81.3
2025-08-08  64.0         73.3
2025-08-11  90.0         79.7
```

## Real use case

The accounts office wants month-on-month fee collection: each month's total and
the change from the month before. It is a `GROUP BY` to get monthly totals, then
`LAG` over the result. This two-step shape (aggregate, then compare
neighbours) is the standard "growth" query in every reporting job:

::runner{lang="sql"}
```sql [month-on-month.sql]
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeePayment VALUES
  (1, 1, 42500, '2025-07-02'), (2, 2, 20000, '2025-07-15'), (3, 3, 42500, '2025-07-29'),
  (4, 2, 22500, '2025-08-10'), (5, 4, 42500, '2025-08-21'),
  (6, 5, 42500, '2025-09-05'), (7, 6, 42500, '2025-09-12'), (8, 7, 21250, '2025-09-30');

WITH monthly AS (
  SELECT substr(paid_on, 1, 7) AS month, SUM(amount) AS collected
  FROM   FeePayment
  GROUP BY substr(paid_on, 1, 7)
)
SELECT month, collected,
       LAG(collected) OVER (ORDER BY month)              AS previous_month,
       collected - LAG(collected) OVER (ORDER BY month)  AS change,
       ROUND(100.0 * (collected - LAG(collected) OVER (ORDER BY month))
             / LAG(collected) OVER (ORDER BY month), 1)  AS change_pct
FROM   monthly
ORDER BY month;
```
::

```text [Output]
month    collected  previous_month  change  change_pct
-------  ---------  --------------  ------  ----------
2025-07  105000     NULL            NULL    NULL
2025-08  65000      105000          -40000  -38.1
2025-09  106250     65000           41250   63.5
```

`substr(paid_on, 1, 7)` takes `'2025-07'` from the date in SQLite; MySQL would
use `DATE_FORMAT(paid_on, '%Y-%m')` and PostgreSQL `to_char(paid_on,
'YYYY-MM')`.

## What confuses people here

- **`LAG` follows the window's `ORDER BY`, not the table's order.** Without an
  `ORDER BY` inside `OVER`, "previous" means nothing.
- **A missing month is not a zero month.** If no fees were paid in August,
  there is no August row, and `LAG` in September looks back at July. For a true
  month-by-month comparison, generate every month first and `LEFT JOIN` the
  totals onto it.
- **`LAST_VALUE` returns the current row** unless you widen the frame, as shown
  above. It is the most common window-function surprise.
- **You still cannot filter on `LAG` in `WHERE`.** "Students whose marks
  dropped" means computing `LAG` in a CTE and filtering `WHERE marks < previous`
  outside it.

## Interview questions

::accordion
  :::accordion-item{label="What do LAG and LEAD do?" icon="i-lucide-message-circle"}
  `LAG(col)` returns `col` from the previous row in the window's order; `LEAD`
  from the next row. Both take an optional offset and a default for when there
  is no such row. They replace self joins for comparing a row with its
  neighbour.
  :::
  :::accordion-item{label="Find exams where a student's marks dropped compared with their previous exam." icon="i-lucide-message-circle"}
  ```sql [dropped.sql]
  WITH m AS (
    SELECT full_name, exam_date, marks,
           LAG(marks) OVER (PARTITION BY student_id ORDER BY exam_date) AS previous
    FROM   ExamResult
  )
  SELECT full_name, exam_date, previous, marks
  FROM   m
  WHERE  marks < previous;
  ```

  ```text [Output (on the six results above)]
  full_name    exam_date   previous  marks
  -----------  ----------  --------  -----
  Anita Rao    2025-11-20  71        68
  Rahul Verma  2025-05-10  80        74
  Rahul Verma  2025-11-20  74        69
  ```
  :::
  :::accordion-item{label="How would you calculate month-over-month growth?" icon="i-lucide-message-circle"}
  Aggregate to one row per month, then `collected - LAG(collected) OVER (ORDER
  BY month)`, divided by the `LAG` for a percentage. Mention that months with no
  rows need filling in first.
  :::
  :::accordion-item{label="Why does LAST_VALUE sometimes return the current row?" icon="i-lucide-message-circle"}
  With an `ORDER BY` in `OVER`, the default frame ends at the current row, so
  the "last" row of the frame is the current one. Use `ROWS BETWEEN UNBOUNDED
  PRECEDING AND UNBOUNDED FOLLOWING`, or `FIRST_VALUE` with the order reversed.
  :::
  :::accordion-item{label="What is NTILE?" icon="i-lucide-message-circle"}
  `NTILE(n)` divides the ordered rows of a window into n groups of nearly equal
  size and numbers them 1 to n. `NTILE(4)` gives quartiles: which quarter of
  the class each student is in.
  :::
::
