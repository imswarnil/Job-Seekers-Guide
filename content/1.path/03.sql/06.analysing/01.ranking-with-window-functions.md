The data is correct, fast and safe. Now the harder questions. "Rank students
within each course" needs a per-course calculation **and** every individual row,
and `GROUP BY` collapses exactly the rows you still need. Window functions give
you both at once.

## Why this matters in a job

Rankings, top N per category, running totals, "compared with the previous
month": these are the questions managers actually ask, and window functions
answer them in a few lines where older SQL needed a page of self joins. In
interviews they are the modern answer to "Nth highest marks" and "top 3 per
department", and "what is the difference between `RANK` and `DENSE_RANK`?" is
asked constantly. They are also the topic that separates people who write
reports from people who write queries.

::warning{icon="i-lucide-alert-triangle"}
Window functions are a new way of thinking, not new syntax. Most people need to
see the same example three times before it clicks. Run each one and compare it
with the `GROUP BY` version before moving on.
::

## GROUP BY collapses; a window looks

`GROUP BY` is the exam cell sorting sheets into piles and writing **one line per
pile**. A window function is a teacher walking down the full list with a ruler,
and for **each** student, looking at the other students in the same course (the
window) to write something next to that student's name: "3rd in this course",
"12 marks above this course's average". Nobody is removed. Every row stays, and
gains a column.

::compare{caption="The same average, two shapes of result."}
  :::compare-side{label="GROUP BY" verdict="right"}
  `SELECT course_id, AVG(marks) FROM ExamResult GROUP BY course_id`

  One row per course. The students are gone.
  :::
  :::compare-side{label="Window function" verdict="right"}
  `SELECT student_id, course_id, marks, AVG(marks) OVER (PARTITION BY course_id) FROM ExamResult`

  One row per student, each carrying their course's average.
  :::
::

## Syntax

```sql [window-syntax.sql]
function() OVER (
  PARTITION BY column     -- which rows form this row's window (optional)
  ORDER BY column         -- the order inside the window (needed for ranking)
)
```

- `OVER (...)` is what makes a function a window function.
- `PARTITION BY` splits the rows into groups, like `GROUP BY`, **without
  collapsing them**. Leave it out and the whole result is one window.
- `ORDER BY` inside `OVER` orders rows within each window.

::runner{lang="sql"}
```sql [avg-over.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, full_name TEXT, course_id INTEGER, marks INTEGER);
INSERT INTO ExamResult VALUES
  (1, 1, 'Anita Rao',   101, 87), (2, 2, 'Rahul Verma', 101, 64),
  (3, 3, 'Priya Nair',  101, 91), (4, 4, 'Arjun Mehta', 101, 87),
  (5, 1, 'Anita Rao',   102, 72), (6, 2, 'Rahul Verma', 102, 58),
  (7, 3, 'Priya Nair',  102, 72), (8, 5, 'Sneha Iyer',  102, 80);

SELECT full_name, course_id, marks,
       ROUND(AVG(marks) OVER (PARTITION BY course_id), 1)            AS course_avg,
       marks - ROUND(AVG(marks) OVER (PARTITION BY course_id), 1)    AS vs_avg
FROM   ExamResult
ORDER BY course_id, marks DESC;
```
::

```text [Output]
full_name    course_id  marks  course_avg  vs_avg
-----------  ---------  -----  ----------  ------
Priya Nair   101        91     82.3        8.7
Anita Rao    101        87     82.3        4.7
Arjun Mehta  101        87     82.3        4.7
Rahul Verma  101        64     82.3        -18.3
Sneha Iyer   102        80     70.5        9.5
Anita Rao    102        72     70.5        1.5
Priya Nair   102        72     70.5        1.5
Rahul Verma  102        58     70.5        -12.5
```

Eight rows in, eight rows out, each with its course's average beside it.

## ROW_NUMBER, RANK and DENSE_RANK

The three ranking functions differ only in how they treat **ties**, and that
difference is the interview question. In course 101, Anita and Arjun both have
87:

::runner{lang="sql"}
```sql [three-ranks.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, full_name TEXT, course_id INTEGER, marks INTEGER);
INSERT INTO ExamResult VALUES
  (1, 1, 'Anita Rao',   101, 87), (2, 2, 'Rahul Verma', 101, 64),
  (3, 3, 'Priya Nair',  101, 91), (4, 4, 'Arjun Mehta', 101, 87),
  (9, 5, 'Sneha Iyer',  101, 78);

SELECT full_name, marks,
       ROW_NUMBER() OVER (ORDER BY marks DESC, student_id) AS row_number,
       RANK()       OVER (ORDER BY marks DESC)             AS rank,
       DENSE_RANK() OVER (ORDER BY marks DESC)             AS dense_rank
FROM   ExamResult
ORDER BY marks DESC, student_id;
```
::

```text [Output]
full_name    marks  row_number  rank  dense_rank
-----------  -----  ----------  ----  ----------
Priya Nair   91     1           1     1
Anita Rao    87     2           2     2
Arjun Mehta  87     3           2     2
Sneha Iyer   78     4           4     3
Rahul Verma  64     5           5     4
```

::feature-list{columns="3"}
  :::feature{icon="i-lucide-list-ordered" title="ROW_NUMBER"}
  1, 2, 3, 4, 5. Always unique, even for ties; the tie is broken by the rest of
  the `ORDER BY`, or arbitrarily if there is none.
  :::
  :::feature{icon="i-lucide-medal" title="RANK"}
  1, 2, 2, 4, 5. Ties share a rank, then the next rank **skips** (no 3rd). Like
  a race: two silver medals, no bronze.
  :::
  :::feature{icon="i-lucide-layers" title="DENSE_RANK"}
  1, 2, 2, 3, 4. Ties share a rank and the next rank does **not** skip. The one
  for "Nth highest distinct marks".
  :::
::

## Top N per group

Rank within each course with `PARTITION BY`, then keep rank 1 (or 1 to 3). A
window function cannot go in `WHERE` (it is computed after `WHERE`, in
`SELECT`), so rank in a CTE and filter outside it:

::runner{lang="sql"}
```sql [topper-per-course.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, full_name TEXT, course_id INTEGER, marks INTEGER);
INSERT INTO ExamResult VALUES
  (1, 1, 'Anita Rao',   101, 87), (2, 2, 'Rahul Verma', 101, 64),
  (3, 3, 'Priya Nair',  101, 91), (4, 4, 'Arjun Mehta', 101, 87),
  (5, 1, 'Anita Rao',   102, 72), (6, 2, 'Rahul Verma', 102, 58),
  (7, 3, 'Priya Nair',  102, 72), (8, 5, 'Sneha Iyer',  102, 80);

WITH ranked AS (
  SELECT full_name, course_id, marks,
         DENSE_RANK() OVER (PARTITION BY course_id ORDER BY marks DESC) AS rnk
  FROM   ExamResult
)
SELECT course_id, rnk, full_name, marks
FROM   ranked
WHERE  rnk <= 2
ORDER BY course_id, rnk, full_name;
```
::

```text [Output]
course_id  rnk  full_name    marks
---------  ---  -----------  -----
101        1    Priya Nair   91
101        2    Anita Rao    87
101        2    Arjun Mehta  87
102        1    Sneha Iyer   80
102        2    Anita Rao    72
102        2    Priya Nair   72
```

With `DENSE_RANK`, both students on 87 in course 101 are "2nd", and both on 72
in course 102 are "2nd". If only one student may be listed per position, use
`ROW_NUMBER` with a tie-break instead. Which one is right is a question for
whoever asked for the report, and asking it is part of the answer. The SQL round
chapter has a full lesson on this query.

## Running totals

With `ORDER BY` inside `OVER`, `SUM` becomes a running total: each row adds
everything up to and including itself.

::runner{lang="sql"}
```sql [running-total.sql]
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeePayment VALUES
  (1, 1, 42500, '2025-07-02'), (2, 2, 20000, '2025-07-05'),
  (3, 3, 42500, '2025-07-09'), (4, 2, 22500, '2025-07-21'),
  (5, 4, 42500, '2025-07-28');

SELECT paid_on, student_id, amount,
       SUM(amount) OVER (ORDER BY paid_on)                           AS collected_so_far,
       SUM(amount) OVER (PARTITION BY student_id ORDER BY paid_on)   AS student_paid_so_far
FROM   FeePayment
ORDER BY paid_on;
```
::

```text [Output]
paid_on     student_id  amount  collected_so_far  student_paid_so_far
----------  ----------  ------  ----------------  -------------------
2025-07-02  1           42500   42500             42500
2025-07-05  2           20000   62500             20000
2025-07-09  3           42500   105000            42500
2025-07-21  2           22500   127500            42500
2025-07-28  4           42500   170000            42500
```

## Real use case

The college publishes a merit list per department for scholarships: each
student's CGPA, their rank within the department, and the department's size. At
Twilio, the same pattern (rank within a group, then filter) was behind most of
the "top accounts per region" reports I wrote for the sales teams:

::runner{lang="sql"}
```sql [merit-list.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department TEXT, cgpa REAL);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'CSE', 8.7), (2, 'Priya Nair', 'CSE', 9.1), (3, 'Sneha Iyer', 'CSE', 8.7),
  (4, 'Divya Menon', 'CSE', 7.2), (5, 'Rahul Verma', 'ECE', 7.9), (6, 'Karan Patel', 'ECE', 8.4),
  (7, 'Rohit Kumar', 'ECE', 6.8);

SELECT department, full_name, cgpa,
       RANK() OVER (PARTITION BY department ORDER BY cgpa DESC) AS dept_rank,
       COUNT(*) OVER (PARTITION BY department)                  AS in_dept
FROM   Student
ORDER BY department, dept_rank, full_name;
```
::

```text [Output]
department  full_name    cgpa  dept_rank  in_dept
----------  -----------  ----  ---------  -------
CSE         Priya Nair   9.1   1          4
CSE         Anita Rao    8.7   2          4
CSE         Sneha Iyer   8.7   2          4
CSE         Divya Menon  7.2   4          4
ECE         Karan Patel  8.4   1          3
ECE         Rahul Verma  7.9   2          3
ECE         Rohit Kumar  6.8   3          3
```

`RANK` here, because a scholarship rule usually says "ranks 1 to 3", and two
students on the same CGPA should share a rank and push the next one down.

## What confuses people here

- **You cannot use a window function in `WHERE`, `GROUP BY` or `HAVING`.** They
  are evaluated in `SELECT`, after all of those. Put the ranking in a subquery
  or CTE and filter outside it, as in "top N per group" above.
- **`ORDER BY` inside `OVER` is not the query's `ORDER BY`.** One orders rows
  inside each window for the calculation; the other orders the final output.
  You usually want both.
- **`PARTITION BY` does not reduce rows.** If you expected one row per course,
  you wanted `GROUP BY`.
- **Support.** MySQL 8+, PostgreSQL, Oracle, SQL Server and SQLite 3.25+ all
  have window functions. MySQL 5.7 does not, which is why older interview
  answers use self joins and variables.

## Interview questions

::accordion
  :::accordion-item{label="What is a window function? How is it different from GROUP BY?" icon="i-lucide-message-circle"}
  A function computed over a set of rows related to the current row (its window,
  defined by `OVER`), which returns a value for **every** row. `GROUP BY`
  collapses each group into one row; `PARTITION BY` keeps every row and adds the
  group's value to it.
  :::
  :::accordion-item{label="ROW_NUMBER vs RANK vs DENSE_RANK?" icon="i-lucide-message-circle"}
  For marks 91, 87, 87, 78: `ROW_NUMBER` gives 1, 2, 3, 4 (always unique);
  `RANK` gives 1, 2, 2, 4 (ties share, then a gap); `DENSE_RANK` gives 1, 2, 2,
  3 (ties share, no gap). Use `DENSE_RANK` for "Nth highest distinct value",
  `ROW_NUMBER` when exactly one row per position is needed.
  :::
  :::accordion-item{label="Find the top 2 students in each course." icon="i-lucide-message-circle"}
  `DENSE_RANK() OVER (PARTITION BY course_id ORDER BY marks DESC)` in a CTE,
  then `WHERE rnk <= 2` outside it. The query and its output are in "Top N per
  group" above. Say which ranking function you chose and why ties matter.
  :::
  :::accordion-item{label="What does PARTITION BY do?" icon="i-lucide-message-circle"}
  Divides the rows into independent windows for the window function, like
  `GROUP BY` but without collapsing them. Ranking restarts at 1 in each
  partition; a running total restarts at 0.
  :::
  :::accordion-item{label="How do you calculate a running total in SQL?" icon="i-lucide-message-circle"}
  `SUM(amount) OVER (ORDER BY paid_on)`. Add `PARTITION BY student_id` for a
  running total per student. Before window functions this needed a correlated
  subquery summing every earlier row, which is slow on large tables.
  :::
::
