`NOT IN (2024, 2025)` worked in the last lesson. Put a `NULL` inside that list
and it returns nothing at all, with no error. The reason is that `NULL` is not a
value. It means "we do not know", and once you accept that, everything it does
becomes predictable instead of infuriating.

## Why this matters in a job

`NULL` is behind a large share of reports that are quietly wrong: a pass
percentage that ignores absentees, a list of "students not from Bangalore" that
drops everyone whose city was never recorded. "Why does `NOT IN` return
nothing?" has ended many afternoons. In interviews it is asked directly ("what
is NULL?", "what is the difference between `COUNT(*)` and `COUNT(column)`?"),
and most candidates can define it and cannot predict it.

## Unknown, not zero, not empty

Think of the exam cell's marks register the day after an exam. Anita's marks are
87. Rahul's are 0 because he wrote nothing. Priya's box is blank because her
paper has not been marked yet. Rahul's 0 is a fact. Priya's blank is **not
zero**: it is "we do not know yet". That blank is `NULL`.

So SQL has three answers to a condition, not two: `TRUE`, `FALSE` and
`UNKNOWN`. **Only rows where the `WHERE` condition is `TRUE` come back.**

| Expression | Result | Why |
| --- | --- | --- |
| `NULL = NULL` | `UNKNOWN` | Is one unknown mark equal to another? Nobody can say. |
| `NULL <> 50` | `UNKNOWN` | |
| `NULL > 50` | `UNKNOWN` | |
| `NULL + 10` | `NULL` | Unknown plus ten is unknown. |
| `'Anita' \|\| NULL` | `NULL` | The whole string becomes unknown. |
| `NULL IS NULL` | `TRUE` | The only way to ask. |

::pull-quote
`= NULL` never matches, not even another NULL. `IS NULL` is the only way to ask
whether something is unknown.
::

## Syntax

```sql [null-syntax.sql]
WHERE marks IS NULL
WHERE marks IS NOT NULL
COALESCE(marks, 0)          -- the first non-NULL of its arguments
NULLIF(classes_held, 0)     -- NULL if the two are equal
```

::runner{lang="sql"}
```sql [is-null.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, full_name TEXT, marks INTEGER);
INSERT INTO ExamResult VALUES
  (1, 1, 'Anita Rao',   87),
  (2, 2, 'Rahul Verma',  0),
  (3, 3, 'Priya Nair',  NULL),
  (4, 4, 'Arjun Mehta', 42),
  (5, 5, 'Sneha Iyer',  NULL);

-- Wrong: returns nothing, and no error.
SELECT full_name FROM ExamResult WHERE marks = NULL;

-- Right.
SELECT full_name FROM ExamResult WHERE marks IS NULL;
```
::

```text [Output]
full_name
----------
Priya Nair
Sneha Iyer
```

The first query printed nothing: not an error, not a warning, zero rows. That
silence is what makes `= NULL` dangerous.

### The pass-and-fail split that does not add up

::runner{lang="sql"}
```sql [three-way-split.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, full_name TEXT, marks INTEGER);
INSERT INTO ExamResult VALUES
  (1, 1, 'Anita Rao', 87), (2, 2, 'Rahul Verma', 0), (3, 3, 'Priya Nair', NULL),
  (4, 4, 'Arjun Mehta', 42), (5, 5, 'Sneha Iyer', NULL);

SELECT
  (SELECT COUNT(*) FROM ExamResult)                    AS total,
  (SELECT COUNT(*) FROM ExamResult WHERE marks >= 40)  AS passed,
  (SELECT COUNT(*) FROM ExamResult WHERE marks < 40)   AS failed,
  (SELECT COUNT(*) FROM ExamResult WHERE marks IS NULL) AS not_marked;
```
::

```text [Output]
total  passed  failed  not_marked
-----  ------  ------  ----------
5      2       1       2
```

Passed plus failed is 3, not 5. The two unmarked papers satisfy neither
`>= 40` nor `< 40`, because both comparisons are `UNKNOWN`. Split a report on a
single comparison and the `NULL` rows vanish from both halves.

## The NOT IN trap

"Students who have not been placed" sounds like `NOT IN`:

::runner{lang="sql"}
```sql [not-in-trap.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma'), (3, 'Priya Nair'), (4, 'Arjun Mehta');

-- One placement row was entered without a student_id.
CREATE TABLE Placement (placement_id INTEGER PRIMARY KEY, student_id INTEGER, company TEXT);
INSERT INTO Placement VALUES (1, 1, 'Infosys'), (2, 3, 'TCS'), (3, NULL, 'Wipro');

SELECT full_name FROM Student
WHERE  student_id NOT IN (SELECT student_id FROM Placement);
```
::

```text [Output]
(no rows)
```

Zero rows, and Rahul and Arjun are certainly not placed. Expand what `NOT IN`
means and the reason appears:

::code-trace{caption="Why NOT IN returns nothing when the list holds a NULL."}
```sql [expanded.sql]
WHERE student_id NOT IN (1, 3, NULL)
```

  :::code-trace-step{lines="1" caption="NOT IN (a, b, c) means: id <> a AND id <> b AND id <> c."}
  :::
  :::code-trace-step{lines="1" caption="For Rahul: 2 <> 1 is TRUE, 2 <> 3 is TRUE, 2 <> NULL is UNKNOWN."}
  :::
  :::code-trace-step{lines="1" caption="TRUE AND TRUE AND UNKNOWN is UNKNOWN, which is not TRUE, so Rahul is not returned. The same happens to every row."}
  :::
::

Two fixes. The second is the one to reach for by default:

::runner{lang="sql"}
```sql [not-in-fixes.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma'), (3, 'Priya Nair'), (4, 'Arjun Mehta');
CREATE TABLE Placement (placement_id INTEGER PRIMARY KEY, student_id INTEGER, company TEXT);
INSERT INTO Placement VALUES (1, 1, 'Infosys'), (2, 3, 'TCS'), (3, NULL, 'Wipro');

-- 1. Keep the NULLs out of the list.
SELECT full_name FROM Student
WHERE  student_id NOT IN (SELECT student_id FROM Placement WHERE student_id IS NOT NULL);

-- 2. NOT EXISTS: immune to NULLs.
SELECT full_name FROM Student s
WHERE  NOT EXISTS (SELECT 1 FROM Placement p WHERE p.student_id = s.student_id);
```
::

```text [Output]
full_name
-----------
Rahul Verma
Arjun Mehta

full_name
-----------
Rahul Verma
Arjun Mehta
```

`NOT EXISTS` gets its own lesson in the joining chapter. For now: prefer it over
`NOT IN` whenever the list comes from a query.

## Aggregates skip NULL, silently

::runner{lang="sql"}
```sql [aggregates-and-null.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, marks INTEGER);
INSERT INTO ExamResult VALUES (1, 1, 87), (2, 2, 0), (3, 3, NULL), (4, 4, 42), (5, 5, NULL);

SELECT COUNT(*)      AS rows_in_table,
       COUNT(marks)  AS marked,
       SUM(marks)    AS total,
       AVG(marks)    AS average
FROM   ExamResult;
```
::

```text [Output]
rows_in_table  marked  total  average
-------------  ------  -----  -------
5              3       129    43.0
```

`COUNT(*)` counts rows (5). `COUNT(marks)` counts non-`NULL` marks (3). `AVG`
divided 129 by 3, not by 5. That is usually correct (an unmarked paper should not
drag the average down), and **the report must say so**: "average 43 from 3 marked
papers out of 5". The number is right; a label that implies all five is what
makes it misleading.

## NULL in ORDER BY and GROUP BY

- **Sorting:** where `NULL`s go differs by database. SQLite and MySQL put them
  first in ascending order; PostgreSQL and Oracle put them last. Say what you
  want: `ORDER BY marks DESC NULLS LAST` (PostgreSQL, Oracle, SQLite).
- **Grouping:** `GROUP BY` puts every `NULL` into **one** group, which is the
  opposite of how `=` treats them. Inconsistent, and worth knowing.

::runner{lang="sql"}
```sql [null-sort-group.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, city TEXT);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'Bhopal'), (2, 'Rahul Verma', NULL),
  (3, 'Priya Nair', 'Patna'), (4, 'Arjun Mehta', NULL);

SELECT full_name, city FROM Student ORDER BY city NULLS LAST;

SELECT city, COUNT(*) AS students FROM Student GROUP BY city;
```
::

```text [Output]
full_name    city
-----------  ------
Anita Rao    Bhopal
Priya Nair   Patna
Rahul Verma  NULL
Arjun Mehta  NULL

city    students
------  --------
NULL    2
Bhopal  1
Patna   1
```

## Real use case

The college computes attendance percentage per student. Some courses have not
held a class yet, so `classes_held` is 0, and dividing by zero either errors or
returns nonsense. The idiom used in real reporting code is `COALESCE` for a
display default and `NULLIF` to turn a zero divisor into `NULL`:

::runner{lang="sql"}
```sql [attendance-pct.sql]
CREATE TABLE AttendanceSummary (student_id INTEGER, full_name TEXT, city TEXT, classes_held INTEGER, classes_attended INTEGER);
INSERT INTO AttendanceSummary VALUES
  (1, 'Anita Rao',   'Bhopal', 40, 36),
  (2, 'Rahul Verma', NULL,     40, 27),
  (3, 'Priya Nair',  'Patna',   0,  0);

SELECT full_name,
       COALESCE(city, 'Not given')                                  AS city,
       ROUND(classes_attended * 100.0 / NULLIF(classes_held, 0), 1) AS attendance_pct
FROM   AttendanceSummary;
```
::

```text [Output]
full_name    city       attendance_pct
-----------  ---------  --------------
Anita Rao    Bhopal     90.0
Rahul Verma  Not given  67.5
Priya Nair   Patna      NULL
```

Priya's percentage is `NULL`, meaning "cannot be calculated yet", which is the
truth. A 0% would have put her on the detention list.

::warning{icon="i-lucide-alert-triangle"}
`COALESCE(marks, 0)` is a decision, not a formatting choice. It says an unmarked
student scored zero, which changes the average and can change who passes. Use it
when zero genuinely is the right value, never merely to make a `NULL` go away.
::

## What confuses people here

- **`NULL` is not zero and not an empty string.** `''` is a known, empty value.
  (Oracle is the exception: it treats `''` as `NULL`, which surprises everyone
  who moves to it.)
- **`WHERE city <> 'Bangalore'` drops students with no city.** If "not from
  Bangalore" should include them, write `city <> 'Bangalore' OR city IS NULL`.
  Better still, ask whoever wants the report; it is a business question.
- **`COUNT(column)` is not the number of rows.** `COUNT(*)` is.
- **MySQL has `IFNULL(a, b)`, Oracle has `NVL(a, b)`, SQL Server has
  `ISNULL(a, b)`.** All are two-argument versions of `COALESCE`, which is
  standard and works everywhere.

## Interview questions

::accordion
  :::accordion-item{label="What is NULL in SQL?" icon="i-lucide-message-circle"}
  The absence of a value: unknown or not applicable. It is not zero and not an
  empty string. Comparisons with `NULL` give `UNKNOWN`, and only `TRUE` rows are
  returned, so `WHERE marks = NULL` matches nothing. Test with `IS NULL`.
  :::
  :::accordion-item{label="What is the difference between COUNT(*) and COUNT(column)?" icon="i-lucide-message-circle"}
  `COUNT(*)` counts rows. `COUNT(marks)` counts rows where `marks` is not
  `NULL`. On the five results above, 5 and 3. `COUNT(DISTINCT marks)` counts
  distinct non-`NULL` values.
  :::
  :::accordion-item{label="Why does NOT IN return no rows when the subquery has a NULL?" icon="i-lucide-message-circle"}
  `x NOT IN (1, 3, NULL)` means `x <> 1 AND x <> 3 AND x <> NULL`. The last
  part is `UNKNOWN` for every `x`, so the whole condition is never `TRUE`. Use
  `NOT EXISTS`, or filter `NULL`s out of the subquery.
  :::
  :::accordion-item{label="What does COALESCE do? And NULLIF?" icon="i-lucide-message-circle"}
  `COALESCE(a, b, c)` returns the first non-`NULL` argument:
  `COALESCE(city, 'Not given')`. `NULLIF(a, b)` returns `NULL` if `a = b`,
  otherwise `a`; `x / NULLIF(y, 0)` avoids division by zero.
  :::
  :::accordion-item{label="Does AVG include NULL values?" icon="i-lucide-message-circle"}
  No. All aggregates except `COUNT(*)` ignore `NULL`. `AVG` of 87, 0, `NULL`,
  42, `NULL` is 129 / 3 = 43, not 129 / 5. If `NULL` should count as zero,
  write `AVG(COALESCE(marks, 0))`, and be sure that is the rule.
  :::
::
