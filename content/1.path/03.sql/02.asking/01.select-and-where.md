The data is in, and it can be changed safely. Now the part you will do a
hundred times more often than writing: asking for exactly the rows and columns
you want back.

## Why this matters in a job

Almost every backend and support role tests `SELECT` directly, a data analyst
role is essentially `SELECT`, and it is the skill with the longest shelf life in
this guide. I have not written a line of Spring in years. I still think in
queries every week, and the habit that transferred was not the syntax. It was
reasoning about a query in order: which rows am I starting from, which am I
throwing away, what am I showing.

## Two questions: which columns, which rows

Think of the exam cell's big register. `SELECT` decides which **columns** you
copy out (name and marks, not the address). `WHERE` decides which **rows** you
copy (only CSE, only marks above 60). Every query you write answers those two
questions, and nearly every other clause is a refinement of one of them.

::compare{caption="Columns across, rows down."}
  :::compare-side{label="SELECT picks columns" verdict="right"}
  `SELECT full_name, city` keeps two of the six columns, for every row.
  :::
  :::compare-side{label="WHERE picks rows" verdict="right"}
  `WHERE city = 'Bhopal'` keeps every column, for some rows. Together they cut
  the table down to the rectangle you asked for.
  :::
::

## Syntax

```sql [select-syntax.sql]
SELECT column1, column2, expression AS alias
FROM   table_name
WHERE  condition;
```

Every example below uses these students:

::runner{lang="sql"}
```sql [students.sql]
CREATE TABLE Student (
  student_id      INTEGER PRIMARY KEY,
  full_name       TEXT,
  city            TEXT,
  department_id   INTEGER,    -- 1 CSE, 2 ECE, 3 Mechanical
  admission_year  INTEGER
);
INSERT INTO Student VALUES
  (1, 'Anita Rao',    'Bhopal',    1, 2024),
  (2, 'Rahul Verma',  'Patna',     2, 2024),
  (3, 'Priya Nair',   'Bangalore', 1, 2025),
  (4, 'Arjun Mehta',  'Bhopal',    3, 2023),
  (5, 'Sneha Iyer',   'Indore',    1, 2024),
  (6, 'Karan Patel',  'Bhopal',    2, 2025);

-- Every column, every row. Useful for looking, never for a real query.
SELECT * FROM Student;
```
::

```text [Output]
student_id  full_name    city       department_id  admission_year
----------  -----------  ---------  -------------  --------------
1           Anita Rao    Bhopal     1              2024
2           Rahul Verma  Patna      2              2024
3           Priya Nair   Bangalore  1              2025
4           Arjun Mehta  Bhopal     3              2023
5           Sneha Iyer   Indore     1              2024
6           Karan Patel  Bhopal     2              2025
```

### Choosing, renaming and computing columns

::runner{lang="sql"}
```sql [columns.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, city TEXT, department_id INTEGER, admission_year INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'Bhopal', 1, 2024), (2, 'Rahul Verma', 'Patna', 2, 2024),
  (3, 'Priya Nair', 'Bangalore', 1, 2025), (4, 'Arjun Mehta', 'Bhopal', 3, 2023);

SELECT full_name              AS name,
       city                   AS home_town,
       admission_year + 4     AS expected_graduation,
       'B.Tech'               AS programme
FROM   Student;
```
::

```text [Output]
name         home_town  expected_graduation  programme
-----------  ---------  -------------------  ---------
Anita Rao    Bhopal     2028                 B.Tech
Rahul Verma  Patna      2028                 B.Tech
Priya Nair   Bangalore  2029                 B.Tech
Arjun Mehta  Bhopal     2027                 B.Tech
```

`AS` gives a column a new name in the result; it does not change the table. A
computed column (`admission_year + 4`) and a constant (`'B.Tech'`) are worked
out for each row.

::warning{icon="i-lucide-alert-triangle"}
`SELECT *` in real code is a habit worth not forming. It sends columns nobody
uses, it changes silently when someone adds a column, and it stops the database
answering from an index alone. Name the columns. In an interview, writing
`SELECT *` in an answer is a small thing that gets noticed.
::

### WHERE, AND, OR, NOT

| Operator | Means |
| --- | --- |
| `=` | equals |
| `<>` or `!=` | not equal (`<>` is the standard) |
| `>` `>=` `<` `<=` | comparison |
| `AND` | both conditions true |
| `OR` | at least one true |
| `NOT` | reverses a condition |

::runner{lang="sql"}
```sql [where.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, city TEXT, department_id INTEGER, admission_year INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'Bhopal', 1, 2024), (2, 'Rahul Verma', 'Patna', 2, 2024),
  (3, 'Priya Nair', 'Bangalore', 1, 2025), (4, 'Arjun Mehta', 'Bhopal', 3, 2023),
  (5, 'Sneha Iyer', 'Indore', 1, 2024), (6, 'Karan Patel', 'Bhopal', 2, 2025);

-- CSE students admitted in 2024.
SELECT full_name FROM Student
WHERE  department_id = 1 AND admission_year = 2024;

-- Students from Bhopal who are NOT in CSE.
SELECT full_name, department_id FROM Student
WHERE  city = 'Bhopal' AND NOT department_id = 1;
```
::

```text [Output]
full_name
----------
Anita Rao
Sneha Iyer

full_name    department_id
-----------  -------------
Arjun Mehta  3
Karan Patel  2
```

### AND before OR: the precedence trap

`AND` binds tighter than `OR`, the way multiplication binds tighter than
addition. The dean asks for "2025 students from Bhopal or Bangalore":

::runner{lang="sql"}
```sql [precedence.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, city TEXT, department_id INTEGER, admission_year INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'Bhopal', 1, 2024), (2, 'Rahul Verma', 'Patna', 2, 2024),
  (3, 'Priya Nair', 'Bangalore', 1, 2025), (4, 'Arjun Mehta', 'Bhopal', 3, 2023),
  (5, 'Sneha Iyer', 'Indore', 1, 2024), (6, 'Karan Patel', 'Bhopal', 2, 2025),
  (7, 'Meera Joshi', 'Bangalore', 1, 2023);

-- Wrong: read as  admission_year = 2025 AND city = 'Bhopal'   OR   city = 'Bangalore'
SELECT full_name, city, admission_year FROM Student
WHERE  admission_year = 2025 AND city = 'Bhopal' OR city = 'Bangalore';

-- Right: brackets say what you mean.
SELECT full_name, city, admission_year FROM Student
WHERE  admission_year = 2025 AND (city = 'Bhopal' OR city = 'Bangalore');
```
::

```text [Output]
full_name    city       admission_year
-----------  ---------  --------------
Priya Nair   Bangalore  2025
Karan Patel  Bhopal     2025
Meera Joshi  Bangalore  2023

full_name    city       admission_year
-----------  ---------  --------------
Priya Nair   Bangalore  2025
Karan Patel  Bhopal     2025
```

Meera Joshi was admitted in 2023 and still appears in the first result, because
`OR city = 'Bangalore'` stands on its own. Take her row out and the two queries
return the same thing, which is exactly how this bug survives testing. **Whenever `AND` and
`OR` meet, write the brackets**, even when you think you do not need them.

## The order a query is really evaluated in

You write the clauses in one order and the database evaluates them in another.
Three errors that otherwise look arbitrary fall straight out of this list, so
learn it once.

::flow{numbered direction="vertical" caption="Written: SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. Evaluated: this."}
  :::flow-step{label="FROM and JOIN" icon="i-lucide-table-2"}
  Build the working set of rows. Everything else operates on this.
  :::
  :::flow-step{label="WHERE" icon="i-lucide-filter" highlight}
  Throw rows away, **before any grouping**, which is why `WHERE` cannot see an
  aggregate or a `SELECT` alias.
  :::
  :::flow-step{label="GROUP BY" icon="i-lucide-layers"}
  Collapse the survivors into groups.
  :::
  :::flow-step{label="HAVING" icon="i-lucide-funnel"}
  Throw whole groups away. Conditions on `COUNT` and `AVG` go here.
  :::
  :::flow-step{label="SELECT" icon="i-lucide-columns-3"}
  Work out the output columns. Only now do aliases exist.
  :::
  :::flow-step{label="ORDER BY" icon="i-lucide-arrow-down-up"}
  Sort. Aliases **can** be used here, because it runs after `SELECT`.
  :::
  :::flow-step{label="LIMIT" icon="i-lucide-scissors"}
  Keep the first n rows. Always last.
  :::
::

::runner{lang="sql"}
```sql [alias-in-where.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, admission_year INTEGER);
INSERT INTO Student VALUES (1, 'Anita Rao', 2024), (2, 'Rahul Verma', 2023), (3, 'Priya Nair', 2025);

-- Fails in MySQL, PostgreSQL, Oracle and SQL Server: the alias does not exist yet when WHERE runs.
-- (SQLite is lenient and allows it, which is why the error is shown from PostgreSQL below.)
SELECT full_name, admission_year + 4 AS graduates_in
FROM   Student
WHERE  admission_year + 4 = 2028;     -- repeat the expression instead
```
::

```text [Output]
full_name  graduates_in
---------  ------------
Anita Rao  2028
```

```sql [alias-error.sql]
-- PostgreSQL
SELECT full_name, admission_year + 4 AS graduates_in
FROM   Student
WHERE  graduates_in = 2028;
```

```text [Output (PostgreSQL 16)]
ERROR:  column "graduates_in" does not exist
LINE 3: WHERE  graduates_in = 2028;
```

::pull-quote
Nearly every "why does this not work" in SQL is this list. Learn the evaluation
order once and three categories of error stop being mysterious.
::

## Real use case

The training-and-placement office needs every student eligible for a campus
drive: 2024 or 2025 admission, from CSE or ECE, and not from the college's own
city, because the company is paying relocation. One `WHERE`, brackets written:

::runner{lang="sql"}
```sql [drive-eligibility.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, city TEXT, department_id INTEGER, admission_year INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'Bhopal', 1, 2024), (2, 'Rahul Verma', 'Patna', 2, 2024),
  (3, 'Priya Nair', 'Bangalore', 1, 2025), (4, 'Arjun Mehta', 'Bhopal', 3, 2023),
  (5, 'Sneha Iyer', 'Indore', 1, 2024), (6, 'Karan Patel', 'Bhopal', 2, 2025);

SELECT student_id, full_name, city
FROM   Student
WHERE  (admission_year = 2024 OR admission_year = 2025)
  AND  (department_id = 1 OR department_id = 2)
  AND  city <> 'Bhopal';
```
::

```text [Output]
student_id  full_name    city
----------  -----------  ---------
2           Rahul Verma  Patna
3           Priya Nair   Bangalore
5           Sneha Iyer   Indore
```

The next two lessons make this shorter (`IN (2024, 2025)`), but the logic is
exactly this.

## What confuses people here

- **Single quotes for text, nothing around numbers.** `city = 'Bhopal'`,
  `admission_year = 2024`. Writing `city = Bhopal` makes SQL look for a column
  called Bhopal.
- **`=` compares; it does not assign** inside a `WHERE`. There is no `==`.
- **`WHERE city = NULL` returns nothing, ever.** It is not a syntax error, which
  makes it worse. The NULL lesson in this chapter explains why and what to
  write instead.
- **Rows come back in no guaranteed order** unless you ask for one. The same
  query can return the same rows in a different order tomorrow. The next lesson
  fixes that.

## Interview questions

::accordion
  :::accordion-item{label="Walk me through how a SQL query is executed." icon="i-lucide-message-circle"}
  Logically: `FROM` (and joins), `WHERE`, `GROUP BY`, `HAVING`, `SELECT`,
  `ORDER BY`, `LIMIT`. Then make it useful: that order is why an alias from
  `SELECT` fails in `WHERE` but works in `ORDER BY`, and why a condition on
  `COUNT(*)` belongs in `HAVING`, not `WHERE`. Reciting the order is common;
  using it to explain an error is not.
  :::
  :::accordion-item{label="Why should you avoid SELECT * ?" icon="i-lucide-message-circle"}
  It fetches columns nobody uses, it changes meaning when a column is added, and
  it can stop the database answering from an index alone. Naming columns makes
  the query cheaper and its intent readable.
  :::
  :::accordion-item{label="What is the precedence of AND and OR?" icon="i-lucide-message-circle"}
  `NOT` first, then `AND`, then `OR`. So `a AND b OR c` means `(a AND b) OR c`.
  Always add brackets when they meet: without them the "2025 students from
  Bhopal or Bangalore" query above also returned a 2023 student.
  :::
  :::accordion-item{label="What is an alias?" icon="i-lucide-message-circle"}
  A temporary name for a column or table in one query, written with `AS`:
  `SELECT admission_year + 4 AS graduates_in FROM Student s`. It exists only in
  that query's result and cannot be used in `WHERE` in standard SQL.
  :::
::
