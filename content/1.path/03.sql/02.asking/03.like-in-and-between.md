`=` and `>` cannot say "names starting with A", "any of these four cities" or
"marks from 60 to 75". Three operators can, and each has one trap worth knowing
before an interviewer asks about it.

## Why this matters in a job

Search boxes are `LIKE`. Filters with checkboxes ("CSE, ECE, Civil") are `IN`.
Date pickers ("from 1 July to 31 July") are `BETWEEN` or its safer cousin. You
will write all three in your first month. In interviews they appear as "find
students whose name starts with 'S'", "what is the difference between `%` and
`_`", and the trick question "is `BETWEEN` inclusive?"

## Three shortcuts for longer conditions

Each of these is a shorter way to write something you could already say with
`AND` and `OR`. That is the easiest way to remember what they do:

| Shortcut | Means the same as |
| --- | --- |
| `city IN ('Bhopal', 'Patna', 'Indore')` | `city = 'Bhopal' OR city = 'Patna' OR city = 'Indore'` |
| `marks BETWEEN 60 AND 75` | `marks >= 60 AND marks <= 75` (**both ends included**) |
| `full_name LIKE 'S%'` | "starts with S", which `=` cannot express at all |

`LIKE` is the one that adds something new: a **pattern**. Two wildcard
characters make the pattern:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-asterisk" title="% any run of characters"}
  Zero, one or many. `'S%'` starts with S. `'%Rao'` ends with Rao. `'%an%'`
  contains "an" anywhere.
  :::
  :::feature{icon="i-lucide-minus" title="_ exactly one character"}
  `'CS_101'` matches CSE101 and CSM101. `'____'` (four underscores) matches any
  four-character value.
  :::
::

## Syntax

```sql [like-in-between-syntax.sql]
WHERE column LIKE 'pattern'          -- NOT LIKE to exclude
WHERE column IN (value1, value2)     -- NOT IN to exclude
WHERE column BETWEEN low AND high    -- NOT BETWEEN to exclude
```

::runner{lang="sql"}
```sql [like.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, email TEXT, city TEXT);
INSERT INTO Student VALUES
  (1, 'Anita Rao',    'anita@college.edu',   'Bhopal'),
  (2, 'Rahul Verma',  'rahul.v@gmail.com',   'Patna'),
  (3, 'Priya Nair',   'priya@college.edu',   'Bangalore'),
  (4, 'Sneha Iyer',   'sneha_iyer@yahoo.com','Indore'),
  (5, 'Sanjay Rao',   'sanjay@college.edu',  'Bhopal'),
  (6, 'Karan Patel',  'karan@gmail.com',     'Jaipur');

-- Names starting with S.
SELECT full_name FROM Student WHERE full_name LIKE 'S%';

-- Surname Rao.
SELECT full_name FROM Student WHERE full_name LIKE '% Rao';

-- Students not using the college email.
SELECT full_name, email FROM Student WHERE email NOT LIKE '%@college.edu';

-- Names whose second letter is 'a'.
SELECT full_name FROM Student WHERE full_name LIKE '_a%';
```

### IN

::runner{lang="sql"}
```sql [in.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, city TEXT, admission_year INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'Bhopal', 2024), (2, 'Rahul Verma', 'Patna', 2024),
  (3, 'Priya Nair', 'Bangalore', 2025), (4, 'Sneha Iyer', 'Indore', 2023),
  (5, 'Sanjay Rao', 'Bhopal', 2025), (6, 'Karan Patel', 'Jaipur', 2024);

SELECT full_name, city FROM Student
WHERE  city IN ('Bhopal', 'Indore');

SELECT full_name, admission_year FROM Student
WHERE  admission_year NOT IN (2024, 2025);
```
::

```text [Output]
full_name   city
----------  ------
Anita Rao   Bhopal
Sneha Iyer  Indore
Sanjay Rao  Bhopal

full_name   admission_year
----------  --------------
Sneha Iyer  2023
```

`IN` also takes a query instead of a list, `WHERE student_id IN (SELECT ...)`,
which is the subqueries lesson in the joining chapter.

### BETWEEN

::runner{lang="sql"}
```sql [between.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, marks INTEGER, exam_date TEXT);
INSERT INTO ExamResult VALUES
  (1, 1, 60, '2025-11-20'), (2, 2, 75, '2025-11-30'),
  (3, 3, 59, '2025-12-01'), (4, 4, 76, '2025-11-01'),
  (5, 5, 68, '2025-10-31');

-- Inclusive at BOTH ends: 60 and 75 are both in.
SELECT student_id, marks FROM ExamResult
WHERE  marks BETWEEN 60 AND 75;

-- Exams in November 2025.
SELECT student_id, exam_date FROM ExamResult
WHERE  exam_date BETWEEN '2025-11-01' AND '2025-11-30';
```
::

```text [Output]
student_id  marks
----------  -----
1           60
2           75
5           68

student_id  exam_date
----------  ----------
1           2025-11-20
2           2025-11-30
4           2025-11-01
```

## Real use case

A college's fee office records every payment with the date **and time** it was
made. The accountant asks for every payment received in November. The obvious
query loses a whole day of money:

::runner{lang="sql"}
```sql [november-fees.sql]
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeePayment VALUES
  (1, 1, 42500, '2025-11-01 09:15:00'),
  (2, 2, 42500, '2025-11-18 14:02:00'),
  (3, 3, 21250, '2025-11-30 16:45:00'),
  (4, 4, 42500, '2025-12-01 10:00:00');

-- Looks right. Misses payment 3: '2025-11-30 16:45' is AFTER '2025-11-30'.
SELECT payment_id, amount, paid_on FROM FeePayment
WHERE  paid_on BETWEEN '2025-11-01' AND '2025-11-30';

-- Right: from the start of the month, up to but not including the next.
SELECT payment_id, amount, paid_on FROM FeePayment
WHERE  paid_on >= '2025-11-01' AND paid_on < '2025-12-01';
```
::

```text [Output]
payment_id  amount  paid_on
----------  ------  -------------------
1           42500   2025-11-01 09:15:00
2           42500   2025-11-18 14:02:00

payment_id  amount  paid_on
----------  ------  -------------------
1           42500   2025-11-01 09:15:00
2           42500   2025-11-18 14:02:00
3           21250   2025-11-30 16:45:00
```

::compare{caption="Two November reports. One is ₹21,250 short."}
  :::compare-side{label="BETWEEN with a date" verdict="wrong"}
  `BETWEEN '2025-11-01' AND '2025-11-30'` stops at midnight at the start of the
  30th. Every payment made later that day is missing, with no error.
  :::
  :::compare-side{label="A half-open range" verdict="right"}
  `>= '2025-11-01' AND < '2025-12-01'` includes every moment of November and
  nothing of December, whatever precision the times have.
  :::
::

This is one of those bugs that nobody notices until the monthly totals do not
match the bank statement. The half-open range, `>=` the start and `<` the next
start, is the habit worth forming for every date filter.

## What confuses people here

- **Case sensitivity of `LIKE` depends on the database.** MySQL (with its usual
  settings) and SQLite treat `'s%'` and `'S%'` the same for English letters.
  PostgreSQL does not: `LIKE` is case-sensitive, and `ILIKE` is the
  case-insensitive version. `LOWER(full_name) LIKE 's%'` works everywhere.
- **Searching for a literal `%` or `_`.** In `sneha_iyer@yahoo.com`, the `_` is a
  real character. `LIKE '%_%'` matches every non-empty value, because `_` is a
  wildcard. Escape it:

::runner{lang="sql"}
```sql [escape.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, email TEXT);
INSERT INTO Student VALUES (1, 'anita@college.edu'), (2, 'sneha_iyer@yahoo.com');

SELECT email FROM Student WHERE email LIKE '%\_%' ESCAPE '\';
```
::

```text [Output]
email
--------------------
sneha_iyer@yahoo.com
```

- **A leading `%` cannot use an index.** `LIKE 'S%'` can jump to the S's in a
  sorted index; `LIKE '%Rao'` has to read every row. On a table of a few lakh
  students, that is the difference between instant and noticeably slow.
- **`BETWEEN 75 AND 60` returns nothing.** The smaller value must come first.
- **`NOT IN` with a `NULL` in the list returns no rows at all.** That is the
  next lesson, and it is one of the most famous traps in SQL.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between % and _ in LIKE?" icon="i-lucide-message-circle"}
  `%` matches any number of characters, including none. `_` matches exactly one.
  `'S%'` is anything starting with S; `'S_'` is S followed by exactly one
  character.
  :::
  :::accordion-item{label="Is BETWEEN inclusive?" icon="i-lucide-message-circle"}
  Yes, at both ends. `marks BETWEEN 60 AND 75` includes 60 and 75. For dates
  with times, prefer `>= start AND < next_start`, because `BETWEEN` with a
  date-only upper bound excludes everything after midnight on the last day.
  :::
  :::accordion-item{label="Find students whose name starts with 'A' and ends with 'a'." icon="i-lucide-message-circle"}
  ```sql [a-to-a.sql]
  SELECT full_name FROM Student WHERE full_name LIKE 'A%a';
  ```

  ```text [Output]
  (no rows)
  ```
  On the students above this returns nobody, because 'Anita Rao' ends in 'o'.
  Saying "let me check it against the data" before declaring it done is a good
  habit to show.
  :::
  :::accordion-item{label="What is the difference between IN and a chain of ORs?" icon="i-lucide-message-circle"}
  They return the same rows; `IN` is shorter and easier to read. `IN` also
  accepts a subquery, which a chain of `OR` cannot.
  :::
  :::accordion-item{label="How would you search for a name case-insensitively?" icon="i-lucide-message-circle"}
  `WHERE LOWER(full_name) LIKE LOWER('%rao%')` works in every database.
  PostgreSQL also has `ILIKE`. Add that wrapping a column in `LOWER()` stops a
  normal index being used, which is a sign you know what it costs.
  :::
::
