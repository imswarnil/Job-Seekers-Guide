Every result so far came back in whatever order the database found convenient,
and some came back with the same value twice. Three clauses fix both: `ORDER BY`
sorts, `LIMIT` keeps the first n rows, and `DISTINCT` removes duplicates.

## Why this matters in a job

A merit list, a top-ten, a page of search results and a dropdown of cities are
all these three clauses. In interviews they are the building blocks of the most
asked query of all, the second highest salary (in this guide, the second highest
marks), and the follow-up is nearly always "what if two students have the same
marks?" That follow-up is a question about tie-breaks, and this lesson is where
you learn to answer it.

## A merit list, a cut-off, a register of cities

Think of how a college publishes a merit list. The marks are **sorted** highest
first (`ORDER BY marks DESC`). Two students on the same marks are separated by
a rule, perhaps the earlier application date (a second sort column). Only the
first fifty get a seat (`LIMIT 50`). And the list of cities students came from
lists each city **once**, not once per student (`DISTINCT`).

::flow{direction="horizontal" caption="Where these clauses sit in the evaluation order."}
  :::flow-step{label="FROM, WHERE" icon="i-lucide-filter"}
  Pick the rows.
  :::
  :::flow-step{label="SELECT, DISTINCT" icon="i-lucide-columns-3"}
  Work out columns, drop duplicate rows.
  :::
  :::flow-step{label="ORDER BY" icon="i-lucide-arrow-down-up" highlight}
  Sort what is left.
  :::
  :::flow-step{label="LIMIT, OFFSET" icon="i-lucide-scissors"}
  Keep a slice of the sorted rows.
  :::
::

## Syntax

```sql [order-limit-syntax.sql]
SELECT DISTINCT column1, column2
FROM   table_name
WHERE  condition
ORDER BY column1 DESC, column2 ASC
LIMIT  n OFFSET m;
```

`ASC` (ascending, smallest first) is the default. `DESC` is descending.

::runner{lang="sql"}
```sql [merit-list.sql]
CREATE TABLE ExamResult (
  result_id   INTEGER PRIMARY KEY,
  student_id  INTEGER,
  full_name   TEXT,
  marks       INTEGER,
  exam_date   TEXT
);
INSERT INTO ExamResult VALUES
  (1, 1, 'Anita Rao',   87, '2025-11-20'),
  (2, 2, 'Rahul Verma', 64, '2025-11-20'),
  (3, 3, 'Priya Nair',  91, '2025-11-21'),
  (4, 4, 'Arjun Mehta', 87, '2025-11-19'),
  (5, 5, 'Sneha Iyer',  78, '2025-11-20'),
  (6, 6, 'Karan Patel', 55, '2025-11-21');

-- Highest marks first; ties broken by who sat the exam first.
SELECT full_name, marks, exam_date
FROM   ExamResult
ORDER BY marks DESC, exam_date ASC;
```
::

```text [Output]
full_name    marks  exam_date
-----------  -----  ----------
Priya Nair   91     2025-11-21
Arjun Mehta  87     2025-11-19
Anita Rao    87     2025-11-20
Sneha Iyer   78     2025-11-20
Rahul Verma  64     2025-11-20
Karan Patel  55     2025-11-21
```

Anita and Arjun both have 87. The second sort column decides: Arjun sat the
exam on the 19th, so he comes first.

## LIMIT and OFFSET

::runner{lang="sql"}
```sql [top-three.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, full_name TEXT, marks INTEGER, exam_date TEXT);
INSERT INTO ExamResult VALUES
  (1, 1, 'Anita Rao', 87, '2025-11-20'), (2, 2, 'Rahul Verma', 64, '2025-11-20'),
  (3, 3, 'Priya Nair', 91, '2025-11-21'), (4, 4, 'Arjun Mehta', 87, '2025-11-19'),
  (5, 5, 'Sneha Iyer', 78, '2025-11-20'), (6, 6, 'Karan Patel', 55, '2025-11-21');

-- The top three.
SELECT full_name, marks FROM ExamResult
ORDER BY marks DESC, result_id
LIMIT 3;

-- "Page 2" with two rows per page: skip 2, take 2.
SELECT full_name, marks FROM ExamResult
ORDER BY marks DESC, result_id
LIMIT 2 OFFSET 2;
```
::

```text [Output]
full_name    marks
-----------  -----
Priya Nair   91
Anita Rao    87
Arjun Mehta  87

full_name    marks
-----------  -----
Arjun Mehta  87
Sneha Iyer   78
```

`LIMIT` is how MySQL, PostgreSQL and SQLite say it. The other databases you
will meet say the same thing differently, and an interviewer may ask:

| Database | The top three |
| --- | --- |
| MySQL, PostgreSQL, SQLite | `... ORDER BY marks DESC LIMIT 3` |
| SQL Server | `SELECT TOP 3 ... ORDER BY marks DESC` |
| Oracle 12c+, PostgreSQL, standard SQL | `... ORDER BY marks DESC FETCH FIRST 3 ROWS ONLY` |
| Oracle, older | `... WHERE ROWNUM <= 3` (applied **before** `ORDER BY`, a classic trap) |

## DISTINCT

::runner{lang="sql"}
```sql [distinct.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, city TEXT, department_id INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'Bhopal', 1), (2, 'Rahul Verma', 'Patna', 2),
  (3, 'Priya Nair', 'Bangalore', 1), (4, 'Arjun Mehta', 'Bhopal', 3),
  (5, 'Sneha Iyer', 'Bhopal', 1), (6, 'Karan Patel', 'Patna', 2);

-- Every city students came from, once each.
SELECT DISTINCT city FROM Student ORDER BY city;

-- DISTINCT applies to the whole row: each (city, department) pair once.
SELECT DISTINCT city, department_id FROM Student ORDER BY city, department_id;

-- How many students, and how many different cities?
SELECT COUNT(*) AS students, COUNT(DISTINCT city) AS cities FROM Student;
```
::

```text [Output]
city
---------
Bangalore
Bhopal
Patna

city       department_id
---------  -------------
Bangalore  1
Bhopal     1
Bhopal     3
Patna      2

students  cities
--------  ------
6         3
```

::note
`DISTINCT` is not a function, and it does not apply to "the first column". In
`SELECT DISTINCT city, department_id`, it removes rows where **both** values
repeat. Bhopal appears twice in the second result because it pairs with two
different departments.
::

## Real use case

The placement cell wants the three highest-scoring students in the final exam
to recommend for a company's interview slots, with a rule that is fair and
repeatable. The query below is what that rule looks like when it is written
down. Note the last sort column, which is unique:

::runner{lang="sql"}
```sql [recommendations.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, full_name TEXT, marks INTEGER, exam_date TEXT);
INSERT INTO ExamResult VALUES
  (1, 1, 'Anita Rao', 87, '2025-11-20'), (2, 2, 'Rahul Verma', 64, '2025-11-20'),
  (3, 3, 'Priya Nair', 91, '2025-11-21'), (4, 4, 'Arjun Mehta', 87, '2025-11-19'),
  (5, 5, 'Sneha Iyer', 87, '2025-11-19'), (6, 6, 'Karan Patel', 55, '2025-11-21');

SELECT student_id, full_name, marks, exam_date
FROM   ExamResult
WHERE  marks IS NOT NULL
ORDER BY marks DESC, exam_date ASC, student_id ASC
LIMIT 3;
```
::

```text [Output]
student_id  full_name    marks  exam_date
----------  -----------  -----  ----------
3           Priya Nair   91     2025-11-21
4           Arjun Mehta  87     2025-11-19
5           Sneha Iyer   87     2025-11-19
```

Three students are on 87. Without `exam_date` and `student_id` in the
`ORDER BY`, which two of them get a slot would depend on how the rows happened
to be stored, and could change between two runs of the same query. **A shortlist
with no tie-break is not reproducible**, and in a real placement cell that is a
complaint waiting to be filed.

## What confuses people here

::compare{caption="The same intention, two queries."}
  :::compare-side{label="No tie-break" verdict="wrong"}
  `ORDER BY marks DESC LIMIT 3` returns Priya and two of the three students on
  87, but not necessarily the same two every time. Pages of results can repeat or skip
  rows between requests.
  :::
  :::compare-side{label="Unique last column" verdict="right"}
  `ORDER BY marks DESC, student_id LIMIT 3` is the same every time, because no
  two rows can tie on every column.
  :::
::

- **`LIMIT` without `ORDER BY` means "any n rows".** It is not "the first n
  inserted". There is no such thing as the natural order of a table.
- **`ORDER BY` can use an alias** (`ORDER BY graduates_in`), because it runs
  after `SELECT`. It can also use a column position (`ORDER BY 2 DESC`), which is
  legal and fragile: reorder the columns and the sort silently changes.
- **`DISTINCT` hiding a bug.** When a query returns duplicates you did not expect,
  adding `DISTINCT` makes them disappear and leaves the cause (usually a join
  that matched too many rows) in place. Ask why the duplicates are there first.
- **`OFFSET` gets slow on big tables.** `OFFSET 100000` still reads and throws
  away a hundred thousand rows. Real systems page with `WHERE student_id > last
  seen id` instead; mentioning that in an interview is a good sign.

## Interview questions

::accordion
  :::accordion-item{label="How do you get the top 3 students by marks?" icon="i-lucide-message-circle"}
  `SELECT full_name, marks FROM ExamResult ORDER BY marks DESC, student_id LIMIT 3;`
  In SQL Server, `SELECT TOP 3`; in Oracle 12c+, `FETCH FIRST 3 ROWS ONLY`.
  Then add, unprompted, that ties need a rule: either a tie-break column, or
  `DENSE_RANK()` (the window functions chapter) if everyone on the same marks
  should be included.
  :::
  :::accordion-item{label="What is the difference between DISTINCT and GROUP BY?" icon="i-lucide-message-circle"}
  `SELECT DISTINCT city FROM Student` and `SELECT city FROM Student GROUP BY city`
  return the same rows. `DISTINCT` only removes duplicates; `GROUP BY` forms
  groups so you can compute an aggregate per group (`COUNT(*)` per city). Use
  `DISTINCT` for a unique list, `GROUP BY` when you need a number per group.
  :::
  :::accordion-item{label="Does DISTINCT apply to one column or the whole row?" icon="i-lucide-message-circle"}
  The whole row of selected columns. `SELECT DISTINCT city, department_id`
  returns each distinct pair, so the same city can appear more than once.
  :::
  :::accordion-item{label="Why is ORDER BY needed with LIMIT?" icon="i-lucide-message-circle"}
  Without it, "the first 3" has no meaning: a table has no guaranteed order,
  and the database can return any three rows. And the sort must end on a unique
  column, or the rows at the boundary can change between runs.
  :::
  :::accordion-item{label="How do you implement pagination in SQL?" icon="i-lucide-message-circle"}
  `ORDER BY student_id LIMIT 20 OFFSET 40` for page 3 of 20. For large tables,
  keyset pagination (`WHERE student_id > 40 ORDER BY student_id LIMIT 20`) is
  faster, because `OFFSET` still reads every skipped row.
  :::
::
