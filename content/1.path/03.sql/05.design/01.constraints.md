Every query in this track so far trusted its data. Nothing stopped marks of 140,
a student with no name, two students with the same email, or a result for a
student who does not exist. **Constraints** are rules you attach to a table, and
the database refuses any write that breaks them.

## Why this matters in a job

Application code has bugs, imports have bad rows, and people type things into
tools directly. A rule written only in Java is one bug away from being broken; a
rule written as a constraint is enforced for every program and every person, on
every write, forever. In interviews: "what constraints are there in SQL?", "what
is the difference between a primary key and a unique key?", and "what does
`ON DELETE CASCADE` do?" are all standard.

## The form that refuses to be submitted

Think of an online admission form. The name field is marked with a red asterisk
(you cannot leave it empty). The email field says "already registered" if you
reuse one. The marks field will not accept 140. The department is a dropdown, so
you cannot pick one that does not exist. Constraints are those same rules, but
enforced by the database itself, so they hold even when the data arrives by some
route other than the form.

| Constraint | Refuses | Example |
| --- | --- | --- |
| `NOT NULL` | An empty (`NULL`) value | Every student must have a name |
| `UNIQUE` | A value already used in that column | No two students share an email |
| `PRIMARY KEY` | A duplicate **or** a `NULL`; one per table | `student_id` |
| `FOREIGN KEY` | A value with no matching row in the parent table | A result's `student_id` must exist in `Student` |
| `CHECK` | A value that fails a condition | `marks BETWEEN 0 AND 100` |
| `DEFAULT` | Nothing; fills in a value when none is given | `status` defaults to `'ACTIVE'` |

## Syntax

```sql [constraints-syntax.sql]
CREATE TABLE child (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,
  email       TEXT UNIQUE,
  score       INTEGER CHECK (score BETWEEN 0 AND 100),
  status      TEXT DEFAULT 'ACTIVE',
  parent_id   INTEGER REFERENCES parent (id)
);

-- Or named, at the table level (needed for composite keys):
CONSTRAINT pk_enrolment PRIMARY KEY (student_id, course_id),
CONSTRAINT fk_result_student FOREIGN KEY (student_id) REFERENCES Student (student_id)
```

::note
SQLite, which the runner uses, only enforces foreign keys after
`PRAGMA foreign_keys = ON;`, so the examples below start with it. MySQL (InnoDB),
PostgreSQL, Oracle and SQL Server enforce them always.
::

The college's tables with every rule written in:

::runner{lang="sql"}
```sql [college-with-constraints.sql]
PRAGMA foreign_keys = ON;

CREATE TABLE Department (
  department_id  INTEGER PRIMARY KEY,
  name           TEXT NOT NULL UNIQUE
);

CREATE TABLE Student (
  student_id      INTEGER PRIMARY KEY,
  full_name       TEXT NOT NULL,
  email           TEXT NOT NULL UNIQUE,
  department_id   INTEGER NOT NULL REFERENCES Department (department_id),
  status          TEXT NOT NULL DEFAULT 'ACTIVE'
                  CHECK (status IN ('ACTIVE', 'LEFT', 'GRADUATED')),
  admission_year  INTEGER CHECK (admission_year >= 2000)
);

CREATE TABLE ExamResult (
  result_id   INTEGER PRIMARY KEY,
  student_id  INTEGER NOT NULL REFERENCES Student (student_id),
  course_id   INTEGER NOT NULL,
  marks       INTEGER CHECK (marks BETWEEN 0 AND 100),
  UNIQUE (student_id, course_id)          -- one result per student per course
);

INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE');
INSERT INTO Student (student_id, full_name, email, department_id, admission_year)
VALUES (1, 'Anita Rao', 'anita@college.edu', 1, 2024);
INSERT INTO ExamResult VALUES (1, 1, 101, 87);

SELECT s.full_name, s.status, r.marks
FROM   Student s JOIN ExamResult r ON r.student_id = s.student_id;
```
::

```text [Output]
full_name  status  marks
---------  ------  -----
Anita Rao  ACTIVE  87
```

`status` was not given, so `DEFAULT 'ACTIVE'` filled it in. Now try to break each
rule. Each runner below is the same setup plus one bad write; the output is the
real error message.

```sql [setup.sql]
PRAGMA foreign_keys = ON;
CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE);
CREATE TABLE Student (
  student_id INTEGER PRIMARY KEY, full_name TEXT NOT NULL, email TEXT NOT NULL UNIQUE,
  department_id INTEGER NOT NULL REFERENCES Department (department_id),
  status TEXT NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('ACTIVE', 'LEFT', 'GRADUATED')));
CREATE TABLE ExamResult (
  result_id INTEGER PRIMARY KEY, student_id INTEGER NOT NULL REFERENCES Student (student_id),
  course_id INTEGER NOT NULL, marks INTEGER CHECK (marks BETWEEN 0 AND 100), UNIQUE (student_id, course_id));
INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE');
INSERT INTO Student (student_id, full_name, email, department_id) VALUES (1, 'Anita Rao', 'anita@college.edu', 1);
INSERT INTO ExamResult VALUES (1, 1, 101, 87);
```

## Primary key against unique key

::compare{caption="Both guarantee no duplicates. They differ in two ways."}
  :::compare-side{label="PRIMARY KEY" verdict="right"}
  Never `NULL`. Exactly **one** per table. The identity of the row, and what
  foreign keys point at. In MySQL's InnoDB, it also decides how the table is
  physically stored.
  :::
  :::compare-side{label="UNIQUE" verdict="right"}
  Allows `NULL` (and, in most databases, several `NULL`s, since `NULL` is not
  equal to `NULL`). **Many** per table: `email`, `phone`, `roll_number`.
  :::
::

## Foreign keys and ON DELETE

A foreign key says "this value must exist in that table". The interesting
question is what happens when the parent row is deleted while children still
point at it. You choose, when you declare the key:

| Option | When the student is deleted, their exam results... |
| --- | --- |
| `RESTRICT` / `NO ACTION` (default) | block the delete: you get an error |
| `CASCADE` | are deleted too |
| `SET NULL` | stay, with `student_id` set to `NULL` |
| `SET DEFAULT` | stay, with `student_id` set to its default |

::runner{lang="sql"}
```sql [on-delete.sql]
PRAGMA foreign_keys = ON;
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT NOT NULL);
CREATE TABLE ExamResult (
  result_id   INTEGER PRIMARY KEY,
  student_id  INTEGER REFERENCES Student (student_id) ON DELETE CASCADE,
  marks       INTEGER
);
CREATE TABLE FeePayment (
  payment_id  INTEGER PRIMARY KEY,
  student_id  INTEGER REFERENCES Student (student_id) ON DELETE SET NULL,
  amount      INTEGER
);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma');
INSERT INTO ExamResult VALUES (1, 1, 87), (2, 1, 72), (3, 2, 64);
INSERT INTO FeePayment VALUES (1, 1, 42500), (2, 2, 42500);

DELETE FROM Student WHERE student_id = 1;

SELECT 'results' AS tbl, COUNT(*) AS n_rows FROM ExamResult;
SELECT * FROM FeePayment;
```
::

```text [Output]
tbl      n_rows
-------  ------
results  1

payment_id  student_id  amount
----------  ----------  ------
1           NULL        42500
2           2           42500
```

Anita's two results were deleted with her (`CASCADE`); her fee payment survived
with no student (`SET NULL`).

::warning{icon="i-lucide-alert-triangle"}
`ON DELETE CASCADE` turns one `DELETE` into many, silently. Deleting one
department with cascades all the way down could remove every student, result
and payment under it. Use it for rows that genuinely cannot exist without their
parent, and keep the default (`RESTRICT`) for anything with history worth
keeping, such as money.
::

## Real use case

An `Enrolment` table records which student takes which course. A student cannot
enrol in the same course twice, so the key is the **pair** `(student_id,
course_id)`: a **composite primary key**. Each half is also a foreign key:

::runner{lang="sql"}
```sql [enrolment.sql]
PRAGMA foreign_keys = ON;
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT NOT NULL);
CREATE TABLE Course  (course_id  INTEGER PRIMARY KEY, code TEXT NOT NULL UNIQUE,
                      credits INTEGER NOT NULL CHECK (credits BETWEEN 1 AND 6));
CREATE TABLE Enrolment (
  student_id  INTEGER NOT NULL REFERENCES Student (student_id),
  course_id   INTEGER NOT NULL REFERENCES Course (course_id),
  semester    TEXT    NOT NULL,
  PRIMARY KEY (student_id, course_id)
);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma');
INSERT INTO Course VALUES (101, 'CS201', 4), (102, 'CS202', 3);
INSERT INTO Enrolment VALUES (1, 101, '2025-ODD'), (1, 102, '2025-ODD'), (2, 101, '2025-ODD');

SELECT s.full_name, c.code, e.semester
FROM   Enrolment e
JOIN   Student s ON s.student_id = e.student_id
JOIN   Course  c ON c.course_id  = e.course_id;
```
::

```text [Output]
full_name    code   semester
-----------  -----  --------
Anita Rao    CS201  2025-ODD
Anita Rao    CS202  2025-ODD
Rahul Verma  CS201  2025-ODD
```

Now Anita tries to enrol in CS201 a second time:

```sql [duplicate-enrolment.sql]
INSERT INTO Enrolment VALUES (1, 101, '2025-EVEN');
```

```text [Output]
Error: UNIQUE constraint failed: Enrolment.student_id, Enrolment.course_id
```

The composite key refused it. Anita can take many courses and CS201 can have
many students, but the pair can only appear once.

## What confuses people here

- **A foreign key does not create an index** in PostgreSQL or SQLite (MySQL
  does create one). Joining on an unindexed foreign key is slow on big tables;
  the indexes lesson covers this.
- **`CHECK` passes on `NULL`.** `CHECK (marks BETWEEN 0 AND 100)` accepts
  `NULL`, because the check is `UNKNOWN`, not `FALSE`, and only `FALSE` is
  rejected. Add `NOT NULL` if the value is required.
- **Old MySQL ignored `CHECK`.** Before MySQL 8.0.16, `CHECK` was parsed and
  silently not enforced. If you meet an older system, do not trust it.
- **Adding a constraint to a table with bad data fails.** `ALTER TABLE ... ADD
  CONSTRAINT` checks existing rows first. Clean the data, then add the rule.
- **Constraints in code are not enough.** Validate in Java for a friendly error
  message, and constrain in the database so no other path can break the rule.
  Both, not either.

## Interview questions

::accordion
  :::accordion-item{label="What constraints are available in SQL?" icon="i-lucide-message-circle"}
  `NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, `CHECK` and `DEFAULT`
  (strictly a default value rather than a restriction). Give one example of each
  from a real table: `email UNIQUE`, `marks CHECK (marks BETWEEN 0 AND 100)`.
  :::
  :::accordion-item{label="Primary key vs unique key?" icon="i-lucide-message-circle"}
  Both prevent duplicates. A primary key cannot be `NULL` and there is only one
  per table; a unique key allows `NULL` and a table can have several. The
  primary key is the row's identity and what foreign keys reference.
  :::
  :::accordion-item{label="What is a foreign key? What does ON DELETE CASCADE do?" icon="i-lucide-message-circle"}
  A column whose value must match a primary (or unique) key in another table,
  which enforces referential integrity: no result for a student who does not
  exist. `ON DELETE CASCADE` deletes the child rows when the parent is deleted;
  the default blocks the delete instead; `SET NULL` keeps the children with the
  reference cleared.
  :::
  :::accordion-item{label="What is a composite key?" icon="i-lucide-message-circle"}
  A key made of more than one column, where only the combination must be unique.
  `PRIMARY KEY (student_id, course_id)` on `Enrolment`: a student appears many
  times and a course appears many times, but each pair only once.
  :::
  :::accordion-item{label="Can a table have more than one primary key? Can a primary key be NULL?" icon="i-lucide-message-circle"}
  One primary key per table, though it may span several columns. It can never be
  `NULL`. (SQLite has a historical quirk that allows `NULL` in some non-integer
  primary keys; every other database refuses, and the standard does too.)
  :::
::
