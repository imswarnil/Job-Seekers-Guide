A view saves typing, not time. On a table with lakhs of results, finding one
student's marks still reads every row, one after another. An **index** is the
structure that lets the database jump straight to the rows it needs.

## Why this matters in a job

The first performance problem most freshers are handed is "this page is slow",
and very often the answer is a missing index on a column in a `WHERE` or a
`JOIN`. It is also the most common way to make things slower by accident, by
adding indexes nobody uses. In interviews: "what is an index?", "why not index
every column?", "what is a composite index?", and "why is my query not using the
index?"

## The index at the back of a textbook

Your DBMS textbook has 600 pages. To find "normalisation", you could read from
page 1 until you found it: that is a **full table scan**. Or you turn to the
index at the back, where topics are listed **alphabetically** with page numbers,
find "normalisation" in a few seconds because the list is sorted, and jump to
page 212.

A database index is the same idea. It is a separate, **sorted** copy of one or
more columns, each entry pointing to where the full row lives. Because it is
sorted, the database can find a value without reading everything, the way you
found a word without reading every page. The DBMS track, next, shows the tree
structure (the B+ tree) that makes this take three or four steps even for crores
of rows.

::compare{caption="Two ways to find student 48213's results."}
  :::compare-side{label="No index: full scan" verdict="wrong"}
  Read every one of 5,00,000 rows and keep the ones where `student_id =
  48213`. The work grows with the table.
  :::
  :::compare-side{label="Index on student_id" verdict="right"}
  Look up 48213 in the sorted index, follow the pointers to its handful of rows.
  Three or four page reads, however big the table gets.
  :::
::

## Syntax

```sql [index-syntax.sql]
CREATE INDEX index_name ON table_name (column);
CREATE INDEX index_name ON table_name (column1, column2);   -- composite
CREATE UNIQUE INDEX index_name ON table_name (column);      -- also enforces uniqueness
DROP INDEX index_name;         -- MySQL: DROP INDEX index_name ON table_name;
```

A `PRIMARY KEY` and a `UNIQUE` constraint create an index automatically. Anything
else you index yourself.

### Reading the plan

You do not have to guess whether an index is used. `EXPLAIN QUERY PLAN` (SQLite),
`EXPLAIN` (MySQL) or `EXPLAIN ANALYZE` (PostgreSQL) shows what the database
intends to do. The runner below builds 50,000 results, then asks for the plan
before and after adding an index:

::runner{lang="sql"}
```sql [explain-before-after.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, course_id INTEGER, marks INTEGER);

-- 50,000 generated rows: 10,000 students, 5 courses each.
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 50000)
INSERT INTO ExamResult (student_id, course_id, marks)
SELECT (i - 1) / 5 + 1, 100 + (i % 5), 35 + (i * 37) % 65 FROM n;

EXPLAIN QUERY PLAN
SELECT course_id, marks FROM ExamResult WHERE student_id = 4821;

CREATE INDEX idx_result_student ON ExamResult (student_id);

EXPLAIN QUERY PLAN
SELECT course_id, marks FROM ExamResult WHERE student_id = 4821;

SELECT course_id, marks FROM ExamResult WHERE student_id = 4821;
```
::

```text [Output]
QUERY PLAN
`--SCAN ExamResult
QUERY PLAN
`--SEARCH ExamResult USING INDEX idx_result_student (student_id=?)

course_id  marks
---------  -----
101        37
102        74
103        46
104        83
100        55
```

`SCAN ExamResult` means every row is read. `SEARCH ExamResult USING INDEX
idx_result_student (student_id=?)` means the index is used to jump to the
matching rows. (In the browser runner the plan appears as a small table; the
`detail` column holds the same words.) Learn to read those two words, SCAN and
SEARCH, and you can diagnose most slow queries you will meet in your first year.

## Composite indexes and the leftmost prefix

An index on `(course_id, marks)` is sorted by `course_id` first, and by `marks`
within each course, like a phone book sorted by surname and then first name.

::runner{lang="sql"}
```sql [composite-index.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, course_id INTEGER, marks INTEGER);
CREATE INDEX idx_course_marks ON ExamResult (course_id, marks);

-- Uses the index: the leftmost column is in the WHERE.
EXPLAIN QUERY PLAN SELECT student_id FROM ExamResult WHERE course_id = 101;

-- Uses both columns of the index.
EXPLAIN QUERY PLAN SELECT student_id FROM ExamResult WHERE course_id = 101 AND marks >= 75;

-- Cannot seek: marks alone is not the leftmost column.
EXPLAIN QUERY PLAN SELECT student_id FROM ExamResult WHERE marks >= 75;
```
::

```text [Output]
QUERY PLAN
`--SEARCH ExamResult USING INDEX idx_course_marks (course_id=?)
QUERY PLAN
`--SEARCH ExamResult USING INDEX idx_course_marks (course_id=? AND marks>?)
QUERY PLAN
`--SCAN ExamResult
```

A phone book sorted by surname helps you find every "Rao", and every "Rao,
Anita". It does not help you find every "Anita". That is the **leftmost-prefix
rule**: a composite index helps a query that filters on its first column, or its
first and second, and so on, but not one that skips the first.

## What an index costs

::pros-cons
---
pros:
  - Lookups, joins and sorts on the indexed columns become dramatically faster
  - A unique index also enforces a rule (no duplicate emails)
  - An index that contains every column a query needs can answer it without touching the table
cons:
  - Every INSERT, UPDATE and DELETE must also update every index on the table
  - Each index takes disk space, sometimes as much as the table
  - An unused index is pure cost, and it is easy to forget it exists
---
::

That is why you do not index every column. A table written to constantly (an
attendance table with a row per student per class) pays for every index on
every write. Index the columns that appear in `WHERE`, `JOIN ... ON` and
`ORDER BY` of the queries that actually run often, and nothing else.

## Real use case

A college portal's "my results" page runs one query, thousands of times a day
during results week: a student's marks for a semester, newest first. The index
is designed for that query, column by column:

::runner{lang="sql"}
```sql [portal-index.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, course_id INTEGER, marks INTEGER, exam_date TEXT);
INSERT INTO ExamResult (student_id, course_id, marks, exam_date) VALUES
  (1, 101, 87, '2025-11-20'), (1, 102, 72, '2025-12-02'), (2, 101, 64, '2025-11-20'),
  (1, 103, 79, '2025-12-05'), (2, 102, 58, '2025-12-02');

-- Equality column first, then the sort column.
CREATE INDEX idx_result_student_date ON ExamResult (student_id, exam_date);

EXPLAIN QUERY PLAN
SELECT course_id, marks, exam_date
FROM   ExamResult
WHERE  student_id = 1
ORDER BY exam_date DESC;

SELECT course_id, marks, exam_date
FROM   ExamResult
WHERE  student_id = 1
ORDER BY exam_date DESC;
```
::

```text [Output]
QUERY PLAN
`--SEARCH ExamResult USING INDEX idx_result_student_date (student_id=?)

course_id  marks  exam_date
---------  -----  ----------
103        79     2025-12-05
102        72     2025-12-02
101        87     2025-11-20
```

No separate sort step appears in the plan, because the index already holds each
student's rows in date order; the database reads them backwards. Equality
columns first, then the column you sort or range on, is the rule of thumb for
designing a composite index.

## What confuses people here

The index you added does nothing in these cases, and each is a common interview
follow-up:

::runner{lang="sql"}
```sql [index-not-used.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, email TEXT, admission_year INTEGER);
CREATE INDEX idx_student_name ON Student (full_name);
CREATE INDEX idx_student_year ON Student (admission_year);

-- 1. A function wrapped around the indexed column.
EXPLAIN QUERY PLAN SELECT * FROM Student WHERE LOWER(full_name) = 'anita rao';

-- 2. A leading wildcard.
EXPLAIN QUERY PLAN SELECT * FROM Student WHERE full_name LIKE '%Rao';

-- 3. Arithmetic on the column instead of the value.
EXPLAIN QUERY PLAN SELECT * FROM Student WHERE admission_year + 4 = 2028;

-- The same question, written so the index can be used.
EXPLAIN QUERY PLAN SELECT * FROM Student WHERE admission_year = 2028 - 4;
```
::

```text [Output]
QUERY PLAN
`--SCAN Student
QUERY PLAN
`--SCAN Student
QUERY PLAN
`--SCAN Student
QUERY PLAN
`--SEARCH Student USING INDEX idx_student_year (admission_year=?)
```

- **A function on the column** (`LOWER(full_name)`, `YEAR(paid_on)`) hides the
  sorted values from the index. Rewrite the condition, or create an index on the
  expression (`CREATE INDEX ... ON Student (LOWER(full_name))`, supported by
  PostgreSQL, SQLite and MySQL 8).
- **A leading `%`** has no starting point in a sorted list.
- **Arithmetic on the column**: move it to the other side of the `=`.
- **Low selectivity**: an index on `status` where 95% of rows are `'ACTIVE'`
  rarely helps; reading the table is cheaper than following 95% of it through an
  index, and the optimiser knows it.
- **Small tables**: for a few hundred rows, a scan is fast and the index may be
  ignored. That is correct behaviour, not a bug.

## Interview questions

::accordion
  :::accordion-item{label="What is an index? How does it make queries faster?" icon="i-lucide-message-circle"}
  A separate sorted structure (usually a B+ tree) over one or more columns, with
  pointers to the rows. Because it is sorted, the database can find a value in a
  few steps instead of scanning the whole table. Show it: the plan changes from
  `SCAN ExamResult` to `SEARCH ExamResult USING INDEX`.
  :::
  :::accordion-item{label="Why not create an index on every column?" icon="i-lucide-message-circle"}
  Every index must be updated on every insert, update and delete, and takes
  space. Indexes that no query uses are pure cost. Index the columns used in
  frequent `WHERE`, `JOIN` and `ORDER BY` clauses.
  :::
  :::accordion-item{label="What is a composite index? Does column order matter?" icon="i-lucide-message-circle"}
  An index on several columns, sorted by the first, then the second within it.
  Order matters: an index on `(course_id, marks)` helps `WHERE course_id = 101`
  and `WHERE course_id = 101 AND marks > 75`, but not `WHERE marks > 75`
  alone. That is the leftmost-prefix rule.
  :::
  :::accordion-item{label="Why might a query not use an index?" icon="i-lucide-message-circle"}
  A function or arithmetic on the column, a leading `%` in `LIKE`, filtering on
  a non-leading column of a composite index, low selectivity, or a small table.
  Check with `EXPLAIN` rather than guessing.
  :::
  :::accordion-item{label="What is the difference between a clustered and a non-clustered index?" icon="i-lucide-message-circle"}
  A clustered index decides the physical order of the table's rows, so there can
  be only one (in MySQL InnoDB it is the primary key). A non-clustered index is a
  separate structure pointing back to the rows; there can be many. The DBMS
  track has a lesson on exactly this.
  :::
::
