The same four-table join, showing each student's name, department, course and
marks, is being copy-pasted into every report, and one copy already has a bug in
it. A **view** saves that query once, under a name, so everyone uses the same
one.

## Why this matters in a job

In any team that reports on data, the same few joins are needed everywhere: the
"current students" filter, the "results with names" join, the "fees outstanding"
calculation. Writing them once as views means one definition, one place to fix a
bug, and a simpler table for people who do not know the schema. Views are also a
way to show someone some columns and not others. In interviews: "what is a
view?", "does a view store data?", "can you update through a view?", and "view
against materialised view".

## A saved question, not a saved answer

Think of a shortcut on your phone's home screen that opens a particular page of
a website. The shortcut does not contain the page; tapping it fetches the page
fresh each time. A view is a shortcut to a query. It stores the **query**, not
the rows. Every time you select from it, the database runs the query underneath
against whatever the tables contain right now.

::flow{direction="horizontal" caption="What happens when you SELECT from a view."}
  :::flow-step{label="SELECT * FROM student_results" icon="i-lucide-search"}
  You query the view as if it were a table.
  :::
  :::flow-step{label="The view's query is expanded" icon="i-lucide-expand" highlight}
  The database substitutes the saved join.
  :::
  :::flow-step{label="Run against live tables" icon="i-lucide-table"}
  Current data, every time.
  :::
::

## Syntax

```sql [view-syntax.sql]
CREATE VIEW view_name AS
SELECT ...;

SELECT * FROM view_name WHERE ...;   -- use it like a table

DROP VIEW view_name;                 -- removes the view, not the data
```

::runner{lang="sql"}
```sql [student-results-view.sql]
CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER, status TEXT);
CREATE TABLE Course (course_id INTEGER PRIMARY KEY, code TEXT, title TEXT);
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, course_id INTEGER, marks INTEGER);

INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE');
INSERT INTO Student VALUES (1, 'Anita Rao', 1, 'ACTIVE'), (2, 'Rahul Verma', 2, 'ACTIVE'), (3, 'Priya Nair', 1, 'LEFT');
INSERT INTO Course VALUES (101, 'CS201', 'Data Structures'), (102, 'CS202', 'DBMS');
INSERT INTO ExamResult VALUES (1, 1, 101, 87), (2, 2, 101, 64), (3, 1, 102, 72), (4, 3, 102, 91);

CREATE VIEW student_results AS
SELECT s.student_id, s.full_name, d.name AS department,
       c.code, c.title, r.marks
FROM   ExamResult r
JOIN   Student    s ON s.student_id    = r.student_id
JOIN   Department d ON d.department_id = s.department_id
JOIN   Course     c ON c.course_id     = r.course_id
WHERE  s.status = 'ACTIVE';

-- Now every report is a one-liner.
SELECT full_name, code, marks FROM student_results WHERE department = 'CSE';

SELECT code, ROUND(AVG(marks), 1) AS average FROM student_results GROUP BY code;
```
::

```text [Output]
full_name  code   marks
---------  -----  -----
Anita Rao  CS201  87
Anita Rao  CS202  72

code   average
-----  -------
CS201  75.5
CS202  72.0
```

Priya left the college, so she is filtered out by the view's `WHERE`. Nobody
writing a report has to remember that rule any more; it lives in one place.

### A view always shows current data

::runner{lang="sql"}
```sql [view-is-live.sql]
CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, marks INTEGER);
INSERT INTO ExamResult VALUES (1, 1, 87), (2, 2, 35);

CREATE VIEW failed AS SELECT student_id, marks FROM ExamResult WHERE marks < 40;

SELECT 'before' AS moment, * FROM failed;

UPDATE ExamResult SET marks = 42 WHERE student_id = 2;   -- revaluation
INSERT INTO ExamResult VALUES (3, 3, 28);

SELECT 'after' AS moment, * FROM failed;
```
::

```text [Output]
moment  student_id  marks
------  ----------  -----
before  2           35

moment  student_id  marks
------  ----------  -----
after   3           28
```

The view was never changed. The table was, and the view reflects it
immediately, because it holds no rows of its own.

## Real use case

A college gives an outside placement agency read access so it can see which
students are eligible for drives. The agency must see names, departments and
CGPA, and must **not** see phone numbers, home addresses or fee details. You
create a view with exactly those columns and grant access to the view, not the
table:

::runner{lang="sql"}
```sql [placement-view.sql]
CREATE TABLE Student (
  student_id INTEGER PRIMARY KEY, full_name TEXT, department TEXT,
  cgpa REAL, phone TEXT, home_address TEXT, fee_due INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao',   'CSE', 8.7, '9876543210', 'MP Nagar, Bhopal', 0),
  (2, 'Rahul Verma', 'ECE', 6.4, '9123456780', 'Boring Road, Patna', 21250),
  (3, 'Sneha Iyer',  'CSE', 7.8, '9988776655', 'Vijay Nagar, Indore', 0);

CREATE VIEW placement_eligible AS
SELECT student_id, full_name, department, cgpa
FROM   Student
WHERE  cgpa >= 7.0;

SELECT * FROM placement_eligible ORDER BY cgpa DESC;
```
::

```text [Output]
student_id  full_name   department  cgpa
----------  ----------  ----------  ----
1           Anita Rao   CSE         8.7
3           Sneha Iyer  CSE         7.8
```

In MySQL or PostgreSQL the last step is
`GRANT SELECT ON placement_eligible TO placement_agency;` and the agency's login
can read the view and nothing else. (SQLite has no users or `GRANT`, so the
runner cannot show that line; the DDL, DML, DCL and TCL lesson covers it.)

## Updatable views

You can sometimes `INSERT`, `UPDATE` or `DELETE` through a view, and the change
goes to the underlying table. It only works for simple views: one table, no
`GROUP BY`, no `DISTINCT`, no aggregates, no `UNION`. MySQL, PostgreSQL, Oracle
and SQL Server all allow it for such views.

```sql [updatable-view.sql]
-- PostgreSQL
CREATE VIEW cse_students AS
SELECT student_id, full_name, department_id FROM Student WHERE department_id = 1
WITH CHECK OPTION;

UPDATE cse_students SET full_name = 'Anita R. Rao' WHERE student_id = 1;  -- works
UPDATE cse_students SET department_id = 2 WHERE student_id = 1;           -- refused
```

```text [Output (PostgreSQL 16, illustrative)]
UPDATE 1
ERROR:  new row violates check option for view "cse_students"
```

`WITH CHECK OPTION` refuses changes that would make the row disappear from the
view. SQLite views are read-only unless you write triggers, which is one reason
most teams treat views as read-only everywhere.

## Materialised views

A **materialised view** does store its rows: the query runs once and the result
is saved, like a snapshot. Reading it is as fast as reading a table, and it is
out of date until you refresh it.

::compare{caption="Two kinds of view."}
  :::compare-side{label="View" verdict="right"}
  Stores the query. Always current. As slow as the query underneath. Supported
  everywhere.
  :::
  :::compare-side{label="Materialised view" verdict="right"}
  Stores the result. Fast to read. Stale until
  `REFRESH MATERIALIZED VIEW` (PostgreSQL) or a scheduled refresh (Oracle).
  MySQL and SQLite do not have them.
  :::
::

A college's year-end dashboard that summarises lakhs of results does not need
to be current to the second. A materialised view refreshed every night is the
usual answer.

## What confuses people here

- **A view does not make a query faster.** It is the same query with a name.
  If the join underneath is slow, the view is slow. (A materialised view is the
  exception, and an index is the real fix; that is the next lesson.)
- **Views on views.** You can build a view on another view, and it is tempting.
  Five layers deep, nobody can tell what a simple-looking `SELECT` actually does,
  or why it is slow. Keep it shallow.
- **`SELECT *` in a view definition** captures the columns that existed when the
  view was created in some databases. Add a column to the table and the view
  does not show it. Name the columns.
- **Dropping the table breaks the view.** In most databases the view stays but
  errors when used; in PostgreSQL you cannot drop the table without
  `CASCADE`, which drops the view too.

## Interview questions

::accordion
  :::accordion-item{label="What is a view? Why would you use one?" icon="i-lucide-message-circle"}
  A named, stored query that can be selected from like a table. It simplifies
  complex joins into one name, keeps a business rule (only active students) in
  one place, and restricts what a user can see by granting access to the view
  rather than the table.
  :::
  :::accordion-item{label="Does a view store data?" icon="i-lucide-message-circle"}
  No. It stores the query, which runs each time the view is used, so the result
  is always current. A materialised view is the exception: it stores the result
  and must be refreshed.
  :::
  :::accordion-item{label="Can you update data through a view?" icon="i-lucide-message-circle"}
  Yes, if the view is simple enough that each view row maps to exactly one table
  row: a single table, no aggregates, no `GROUP BY`, no `DISTINCT`, no `UNION`.
  `WITH CHECK OPTION` stops updates that would move a row out of the view.
  :::
  :::accordion-item{label="What is the difference between a view and a table?" icon="i-lucide-message-circle"}
  A table stores rows on disk. A view stores only a query and produces rows when
  read. You can index a table; you generally cannot index an ordinary view
  (SQL Server's indexed views and materialised views are the exceptions).
  :::
  :::accordion-item{label="View vs materialised view?" icon="i-lucide-message-circle"}
  A view runs its query every time: always current, as slow as the query. A
  materialised view saves the result: fast to read, stale until refreshed. Use a
  materialised view for expensive summaries that can be a few hours old.
  :::
::
