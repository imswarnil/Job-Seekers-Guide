Every write so far was one statement. A fee payment is two: record the payment,
and reduce what the student still owes. If the power goes, or the second
statement fails, between them, the college has taken money and recorded nothing
against the student. A **transaction** makes several statements one: all of
them happen, or none do.

## Why this matters in a job

Anything involving money, seats or stock is several writes that must stay
consistent: a payment and a balance, an admission and a seat count, a transfer
out and a transfer in. Get this wrong and the numbers drift apart in ways nobody
can explain months later. In interviews, "what is a transaction?", "what do
`COMMIT` and `ROLLBACK` do?" and "what is ACID?" are standard, and the DBMS
track goes deep on the last one.

## All or nothing

Think of a bank transfer from your father's account to yours for the PG rent.
Two things happen: ₹8,000 leaves his account, and ₹8,000 arrives in yours. If
only the first happens, the money has vanished. The bank treats the pair as one
unit: either both are recorded, or neither is. That unit is a transaction.

::flow{numbered direction="vertical" caption="The life of a transaction."}
  :::flow-step{label="BEGIN" icon="i-lucide-play"}
  Start the unit. Changes from here on are provisional.
  :::
  :::flow-step{label="Statements" icon="i-lucide-list"}
  Insert the payment, update the balance. You can see your own changes; nobody
  else can yet.
  :::
  :::flow-step{label="COMMIT" icon="i-lucide-check" highlight}
  Make every change permanent and visible, together.
  :::
  :::flow-step{label="or ROLLBACK" icon="i-lucide-undo-2"}
  Throw every change away, as if none had happened.
  :::
::

## Syntax

```sql [transaction-syntax.sql]
BEGIN;              -- MySQL also: START TRANSACTION;  SQL Server: BEGIN TRANSACTION;
  statement 1;
  statement 2;
COMMIT;             -- or ROLLBACK;

SAVEPOINT name;           -- a marker inside a transaction
ROLLBACK TO name;         -- undo back to the marker, keep what came before
```

::runner{lang="sql"}
```sql [fee-payment.sql]
CREATE TABLE FeeAccount (student_id INTEGER PRIMARY KEY, total_fee INTEGER, amount_due INTEGER);
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeeAccount VALUES (1, 85000, 85000);

BEGIN;
INSERT INTO FeePayment (student_id, amount, paid_on) VALUES (1, 42500, '2025-07-14');
UPDATE FeeAccount SET amount_due = amount_due - 42500 WHERE student_id = 1;
COMMIT;

SELECT * FROM FeePayment;
SELECT * FROM FeeAccount;
```
::

```text [Output]
payment_id  student_id  amount  paid_on
----------  ----------  ------  ----------
1           1           42500   2025-07-14

student_id  total_fee  amount_due
----------  ---------  ----------
1           85000      42500
```

### ROLLBACK undoes everything since BEGIN

::runner{lang="sql"}
```sql [rollback.sql]
CREATE TABLE FeeAccount (student_id INTEGER PRIMARY KEY, total_fee INTEGER, amount_due INTEGER);
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeeAccount VALUES (1, 85000, 85000);

BEGIN;
INSERT INTO FeePayment (student_id, amount, paid_on) VALUES (1, 42500, '2025-07-14');
UPDATE FeeAccount SET amount_due = amount_due - 42500 WHERE student_id = 1;
SELECT 'inside' AS moment, amount_due FROM FeeAccount;   -- you see your own change
ROLLBACK;                                                -- the clerk entered the wrong student

SELECT 'after' AS moment, amount_due FROM FeeAccount;
SELECT COUNT(*) AS payments FROM FeePayment;
```
::

```text [Output]
moment  amount_due
------  ----------
inside  42500

moment  amount_due
------  ----------
after   85000

payments
--------
0
```

Both changes are gone, the payment row and the balance update, together.

## What a failure halfway looks like

Here is the same payment without a transaction, where the second statement fails
because of a constraint (a balance cannot go below zero, and the clerk typed
₹92,500 instead of ₹42,500):

::runner{lang="sql"}
```sql [no-transaction.sql]
CREATE TABLE FeeAccount (student_id INTEGER PRIMARY KEY, total_fee INTEGER,
                         amount_due INTEGER CHECK (amount_due >= 0));
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeeAccount VALUES (1, 85000, 85000);

-- No BEGIN: each statement commits on its own (autocommit).
INSERT INTO FeePayment (student_id, amount, paid_on) VALUES (1, 92500, '2025-07-14');
UPDATE FeeAccount SET amount_due = amount_due - 92500 WHERE student_id = 1;   -- fails
```
::

```text [Output]
Error: CHECK constraint failed: amount_due >= 0
```

The error is on the `UPDATE`. But the `INSERT` before it had already committed
on its own. The runner stops at the first error, so here is the state of the two
tables right after it:

::runner{lang="sql"}
```sql [the-mismatch.sql]
CREATE TABLE FeeAccount (student_id INTEGER PRIMARY KEY, total_fee INTEGER,
                         amount_due INTEGER CHECK (amount_due >= 0));
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeeAccount VALUES (1, 85000, 85000);

INSERT INTO FeePayment (student_id, amount, paid_on) VALUES (1, 92500, '2025-07-14');
-- (the UPDATE failed here)

SELECT (SELECT SUM(amount) FROM FeePayment) AS recorded_paid,
       (SELECT amount_due  FROM FeeAccount)  AS still_due;
```
::

```text [Output]
recorded_paid  still_due
-------------  ---------
92500          85000
```

With `BEGIN` in front, the application sees the error and issues `ROLLBACK`, and
the payment row disappears with it. That is **atomicity**, the A in ACID: a
transaction is atomic, indivisible, like the bank transfer.

## Autocommit

Most tools start in **autocommit** mode: every statement is its own transaction
and commits the moment it succeeds. That is why `UPDATE Faculty SET salary =
90000` without a `WHERE` could not be undone in the first chapter's example
unless it was inside `BEGIN`. `BEGIN` switches autocommit off until the next
`COMMIT` or `ROLLBACK`.

::tip
In any tool connected to real data, turn autocommit off, or type `BEGIN` before
every manual write. Then a mistake costs a `ROLLBACK` instead of a restore from
last night's backup. It is the cheapest insurance in this subject.
::

## SAVEPOINT: a partial undo

A savepoint is a marker inside a transaction. `ROLLBACK TO` undoes the work
after the marker and keeps the work before it.

::runner{lang="sql"}
```sql [savepoint.sql]
CREATE TABLE Enrolment (student_id INTEGER, course_id INTEGER, PRIMARY KEY (student_id, course_id));

BEGIN;
INSERT INTO Enrolment VALUES (1, 101), (1, 102);     -- core courses
SAVEPOINT electives;
INSERT INTO Enrolment VALUES (1, 205);               -- an elective, wrong choice
ROLLBACK TO electives;                               -- undo only the elective
INSERT INTO Enrolment VALUES (1, 207);               -- the right elective
COMMIT;

SELECT * FROM Enrolment;
```
::

```text [Output]
student_id  course_id
----------  ---------
1           101
1           102
1           207
```

## Real use case

Seat allotment in counselling: when a student accepts a seat, the college
inserts an admission row **and** reduces the programme's vacant seats. The two
must never disagree, and two students must not take the last seat. In real
application code (Java with JDBC, which the Java track covers), it looks like
this:

```java [AllotSeat.java]
connection.setAutoCommit(false);                 // BEGIN
try {
  insertAdmission(connection, studentId, programmeId);
  int updated = decrementSeat(connection, programmeId);   // UPDATE ... WHERE vacant > 0
  if (updated == 0) {
    throw new IllegalStateException("No seats left");
  }
  connection.commit();                           // COMMIT: both, together
} catch (Exception e) {
  connection.rollback();                         // ROLLBACK: neither
  throw e;
}
```

```text [Output (illustrative, two students racing for the last seat)]
Student 1 admitted to CSE; vacant seats 1 -> 0 (committed)
Student 2: No seats left (rolled back, no admission row written)
```

The `WHERE vacant > 0` inside the update is what stops two clerks taking the
last seat at the same moment, and why that works is the DBMS track's chapter on
concurrency and isolation levels.

## What confuses people here

- **DDL often commits by itself.** In MySQL and Oracle, `CREATE TABLE`,
  `ALTER TABLE`, `DROP TABLE` and `TRUNCATE` commit the current transaction
  implicitly and cannot be rolled back. PostgreSQL and SQLite can roll back most
  DDL. This is a favourite interview trap.
- **A transaction is not a backup.** Once you `COMMIT`, `ROLLBACK` cannot help.
- **Long transactions hurt everyone.** A transaction left open (a tool window
  with `BEGIN` and no `COMMIT`, left overnight) can hold locks that block other
  users. Keep them short.
- **Errors do not always roll back automatically.** In many databases a failed
  statement inside a transaction leaves the transaction open; your code must
  call `ROLLBACK`. PostgreSQL goes further and refuses every statement after an
  error until you do.

## Interview questions

::accordion
  :::accordion-item{label="What is a transaction?" icon="i-lucide-message-circle"}
  A group of SQL statements that succeed or fail as one unit. Example: inserting
  a fee payment and reducing the amount due. Either both are committed or, on
  any failure, both are rolled back.
  :::
  :::accordion-item{label="What do COMMIT and ROLLBACK do?" icon="i-lucide-message-circle"}
  `COMMIT` makes every change since `BEGIN` permanent and visible to others.
  `ROLLBACK` discards every change since `BEGIN`. In the example above, after
  `ROLLBACK` the amount due was back to ₹85,000 and there were no payment rows.
  :::
  :::accordion-item{label="What is a savepoint?" icon="i-lucide-message-circle"}
  A named marker inside a transaction. `ROLLBACK TO name` undoes only the work
  after the marker, and the transaction continues. Useful when one step of a
  larger unit can be retried without redoing everything.
  :::
  :::accordion-item{label="What is autocommit?" icon="i-lucide-message-circle"}
  A mode where every statement is its own transaction and commits immediately.
  It is the default in MySQL, PostgreSQL and SQLite clients. `BEGIN` suspends it
  until the transaction ends.
  :::
  :::accordion-item{label="What does ACID stand for?" icon="i-lucide-message-circle"}
  Atomicity (all or nothing), Consistency (rules hold before and after),
  Isolation (concurrent transactions do not see each other's half-done work),
  Durability (committed changes survive a crash). The DBMS track takes each
  letter in turn, with what breaks without it.
  :::
  :::accordion-item{label="Can you roll back a TRUNCATE or a DROP?" icon="i-lucide-message-circle"}
  In MySQL and Oracle, no: they are DDL and commit implicitly. In PostgreSQL and
  SQL Server, yes, inside a transaction. The lesson on `DELETE`, `TRUNCATE` and
  `DROP` at the end of this track covers the full comparison.
  :::
::
