The report said "course 102" and "department 2", and nobody reading it knew what
those were. The names live in one table and the numbers in another. A join is
how you ask a question that needs both, and which join you choose decides what
happens to the rows that have no partner.

## Why this matters in a job

Joins are the most tested SQL topic there is. "Explain the types of joins" is
asked in almost every SQL round, usually followed by a query to write on paper.
At work, nearly every real query touches two or more tables, and the fan-out bug
at the end of this lesson is responsible for more wrong numbers on dashboards
than any other single mistake.

::warning{icon="i-lucide-alert-triangle"}
Joins are where SQL stops being "a list of clauses" and becomes a way of
thinking. If this lesson takes two sittings, that is normal. Run every example
and count the rows yourself before reading the output.
::

## Lining up two registers

Imagine two registers on a desk. One lists students with the id of their
department. The other lists departments with their names. To write "Anita Rao,
CSE", you run your finger down the students, and for each one find the
department with the same id. That matching is a join, and the matching rule
(`Student.department_id = Department.department_id`) is the **join condition**.

The only real question is what to do with the rows that have **no** partner: a
student not yet allotted a department, or a department with no students yet.
The four joins are four answers to that question.

## The data

::runner{lang="sql"}
```sql [join-data.sql]
CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE'), (3, 'Mechanical'), (4, 'Civil');

CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao',   1),
  (2, 'Rahul Verma', 2),
  (3, 'Priya Nair',  1),
  (4, 'Arjun Mehta', NULL);   -- not yet allotted a department

SELECT * FROM Department;
SELECT * FROM Student;
```
::

```text [Output]
department_id  name
-------------  ----------
1              CSE
2              ECE
3              Mechanical
4              Civil

student_id  full_name    department_id
----------  -----------  -------------
1           Anita Rao    1
2           Rahul Verma  2
3           Priya Nair   1
4           Arjun Mehta  NULL
```

Two things to notice before joining: Arjun has no department, and Mechanical and
Civil have no students.

## Syntax

```sql [join-syntax.sql]
SELECT columns
FROM   left_table  l
[INNER | LEFT | RIGHT | FULL OUTER] JOIN right_table r
       ON r.key = l.key;
```

`l` and `r` are **table aliases**: short names so you can say which table a
column comes from. With two tables that both have a `department_id`, you must.

### INNER JOIN: only matching pairs

::runner{lang="sql"}
```sql [inner-join.sql]
CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE'), (3, 'Mechanical'), (4, 'Civil');
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER);
INSERT INTO Student VALUES (1, 'Anita Rao', 1), (2, 'Rahul Verma', 2), (3, 'Priya Nair', 1), (4, 'Arjun Mehta', NULL);

SELECT s.full_name, d.name AS department
FROM   Student s
INNER JOIN Department d ON d.department_id = s.department_id;
```
::

```text [Output]
full_name    department
-----------  ----------
Anita Rao    CSE
Rahul Verma  ECE
Priya Nair   CSE
```

Three rows. Arjun is gone because he has no department. Mechanical and Civil are
gone because they have no students. **An inner join silently discards anything
without a partner on both sides.** `JOIN` on its own means `INNER JOIN`.

### LEFT JOIN: every row from the left

::runner{lang="sql"}
```sql [left-join.sql]
CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE'), (3, 'Mechanical'), (4, 'Civil');
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER);
INSERT INTO Student VALUES (1, 'Anita Rao', 1), (2, 'Rahul Verma', 2), (3, 'Priya Nair', 1), (4, 'Arjun Mehta', NULL);

SELECT s.full_name, d.name AS department
FROM   Student s
LEFT JOIN Department d ON d.department_id = s.department_id;
```
::

```text [Output]
full_name    department
-----------  ----------
Anita Rao    CSE
Rahul Verma  ECE
Priya Nair   CSE
Arjun Mehta  NULL
```

Four rows. Arjun is back, with `NULL` in every column from the right-hand table.
That is the whole of what `LEFT JOIN` (also written `LEFT OUTER JOIN`) does: keep
every left row, and fill in `NULL` where there is no partner.

### RIGHT JOIN: every row from the right

::runner{lang="sql"}
```sql [right-join.sql]
CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE'), (3, 'Mechanical'), (4, 'Civil');
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER);
INSERT INTO Student VALUES (1, 'Anita Rao', 1), (2, 'Rahul Verma', 2), (3, 'Priya Nair', 1), (4, 'Arjun Mehta', NULL);

SELECT s.full_name, d.name AS department
FROM   Student s
RIGHT JOIN Department d ON d.department_id = s.department_id;
```
::

```text [Output]
full_name    department
-----------  ----------
Anita Rao    CSE
Rahul Verma  ECE
Priya Nair   CSE
NULL         Mechanical
NULL         Civil
```

Five rows: every department, including the two with nobody in them. A
`RIGHT JOIN` is a `LEFT JOIN` with the tables written the other way round, and
real code almost always uses `LEFT JOIN` for readability. MySQL, PostgreSQL,
Oracle, SQL Server and SQLite 3.39 onwards all support it.

### FULL OUTER JOIN: everything from both

::runner{lang="sql"}
```sql [full-join.sql]
CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE'), (3, 'Mechanical'), (4, 'Civil');
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER);
INSERT INTO Student VALUES (1, 'Anita Rao', 1), (2, 'Rahul Verma', 2), (3, 'Priya Nair', 1), (4, 'Arjun Mehta', NULL);

SELECT s.full_name, d.name AS department
FROM   Student s
FULL OUTER JOIN Department d ON d.department_id = s.department_id;
```
::

```text [Output]
full_name    department
-----------  ----------
Anita Rao    CSE
Rahul Verma  ECE
Priya Nair   CSE
Arjun Mehta  NULL
NULL         Mechanical
NULL         Civil
```

Six rows: the three matches, Arjun with no department, and the two departments
with no students. **MySQL has no `FULL OUTER JOIN`**; there you write a `LEFT
JOIN` and a `RIGHT JOIN` and combine them with `UNION`, which is a lesson later
in this chapter.

## Finding what is missing

The `LEFT JOIN` idiom worth memorising, often called an **anti-join**: join
everything, then keep only the rows where the right side did not match.

::runner{lang="sql"}
```sql [anti-join.sql]
CREATE TABLE Department (department_id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO Department VALUES (1, 'CSE'), (2, 'ECE'), (3, 'Mechanical'), (4, 'Civil');
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER);
INSERT INTO Student VALUES (1, 'Anita Rao', 1), (2, 'Rahul Verma', 2), (3, 'Priya Nair', 1), (4, 'Arjun Mehta', NULL);

-- Departments with no students.
SELECT d.name
FROM   Department d
LEFT JOIN Student s ON s.department_id = d.department_id
WHERE  s.student_id IS NULL;

-- Students per department, INCLUDING departments with none.
SELECT d.name, COUNT(s.student_id) AS students
FROM   Department d
LEFT JOIN Student s ON s.department_id = d.department_id
GROUP BY d.name
ORDER BY students DESC, d.name;
```
::

```text [Output]
name
----------
Mechanical
Civil

name        students
----------  --------
CSE         2
ECE         1
Civil       0
Mechanical  0
```

Note `COUNT(s.student_id)`, not `COUNT(*)`. For Mechanical the joined row
exists with `NULL`s, so `COUNT(*)` would count it as 1 and report one student in
an empty department. Counting a column from the right-hand table skips the
`NULL` and gives 0.

## The WHERE that turns a LEFT JOIN into an INNER JOIN

A genuine trap, and it looks like a small tidy-up.

::compare{caption="One condition, moved from ON to WHERE, and the meaning changes."}
  :::compare-side{label="In the WHERE clause" verdict="wrong"}
  `FROM Department d LEFT JOIN Student s ON s.department_id = d.department_id WHERE s.admission_year = 2024`

  For Mechanical, `s.admission_year` is `NULL`, `NULL = 2024` is `UNKNOWN`,
  and `WHERE` removes the row. The `LEFT JOIN` has quietly become an inner one.
  :::
  :::compare-side{label="In the ON clause" verdict="right"}
  `FROM Department d LEFT JOIN Student s ON s.department_id = d.department_id AND s.admission_year = 2024`

  The year is now part of what counts as a match. Mechanical is kept with
  `NULL`s, which is what "every department, with its 2024 students if any"
  means.
  :::
::

::pull-quote
On a LEFT JOIN, a condition on the right-hand table belongs in `ON`. Put it in
`WHERE` and you have written an inner join with extra words.
::

## Real use case

The accounts office wants, per student, the total fees paid and the number of
courses they are enrolled in. This is the bug that doubles every number, and it
has been shipped in more reports than any other:

::runner{lang="sql"}
```sql [fan-out.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma');

CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER);
INSERT INTO FeePayment VALUES (1, 1, 30000), (2, 1, 12500), (3, 2, 42500);   -- Anita paid in two instalments

CREATE TABLE Enrolment (student_id INTEGER, course_id INTEGER);
INSERT INTO Enrolment VALUES (1, 101), (1, 102), (1, 103), (2, 101), (2, 102);

-- Looks right. Is not.
SELECT s.full_name,
       SUM(f.amount)       AS fees_paid,
       COUNT(e.course_id)  AS courses
FROM   Student s
JOIN   FeePayment f ON f.student_id = s.student_id
JOIN   Enrolment  e ON e.student_id = s.student_id
GROUP BY s.full_name;
```
::

```text [Output]
full_name    fees_paid  courses
-----------  ---------  -------
Anita Rao    127500     6
Rahul Verma  85000      2
```

Anita paid ₹42,500 and takes three courses. The report says ₹1,27,500 and six
courses. Two payments joined to three enrolments makes 2 × 3 = 6 rows for her,
and `SUM` and `COUNT` faithfully add up all six. This is called **fan-out**:
joining to a table with several matches per row multiplies the rows, and with
them every aggregate.

::warning{icon="i-lucide-alert-triangle"}
The usual reaction is to add `DISTINCT` until the number looks right.
`COUNT(DISTINCT e.course_id)` does fix the count, but `SUM(DISTINCT f.amount)`
is actively wrong: two genuine payments of the same amount would collapse into
one. Treat the cause, not the symptom.
::

The fix is to **aggregate before joining**, so each side contributes one row per
student:

::runner{lang="sql"}
```sql [fan-out-fixed.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma');
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER);
INSERT INTO FeePayment VALUES (1, 1, 30000), (2, 1, 12500), (3, 2, 42500);
CREATE TABLE Enrolment (student_id INTEGER, course_id INTEGER);
INSERT INTO Enrolment VALUES (1, 101), (1, 102), (1, 103), (2, 101), (2, 102);

SELECT s.full_name, f.fees_paid, e.courses
FROM   Student s
LEFT JOIN (SELECT student_id, SUM(amount) AS fees_paid
           FROM FeePayment GROUP BY student_id) f ON f.student_id = s.student_id
LEFT JOIN (SELECT student_id, COUNT(*) AS courses
           FROM Enrolment GROUP BY student_id) e ON e.student_id = s.student_id;
```
::

```text [Output]
full_name    fees_paid  courses
-----------  ---------  -------
Anita Rao    42500      3
Rahul Verma  42500      2
```

Each inner query produces exactly one row per student, so there is nothing to
multiply. Queries inside queries get their own lesson two lessons from now.

## What confuses people here

- **`ON` against `WHERE` for an inner join.** For `INNER JOIN` they give the same
  result; for outer joins they do not (see above). Keep join conditions in `ON`
  and filters in `WHERE` and you will not have to remember which case you are in.
- **The Venn diagram is a simplification.** Joins match rows, not sets of
  values, which is exactly why one student with three enrolments appears three
  times. Circles cannot show fan-out.
- **The old comma syntax.** `FROM Student s, Department d WHERE s.department_id =
  d.department_id` is an inner join written the 1980s way. Forget the `WHERE`
  and it becomes a cross join (every student with every department). Use `JOIN
  ... ON`.
- **`NULL` never matches `NULL`** in a join condition. Two rows with a `NULL`
  department are not "in the same department".

## Interview questions

::accordion
  :::accordion-item{label="Explain the types of joins." icon="i-lucide-message-circle"}
  Answer with the unmatched rows, and give counts. With four students (one with
  no department) and four departments (two with no students): `INNER` keeps only
  matches, 3 rows; `LEFT` keeps every student, 4; `RIGHT` keeps every
  department, 5; `FULL OUTER` keeps everything, 6. Mention `CROSS JOIN` and
  self join, which are the next lesson.
  :::
  :::accordion-item{label="What is the difference between INNER JOIN and LEFT JOIN?" icon="i-lucide-message-circle"}
  `INNER JOIN` returns only rows with a match on both sides. `LEFT JOIN` returns
  every row from the left table, with `NULL`s for the right table's columns
  where there is no match. Then add the trap: a condition on the right table in
  `WHERE` turns a `LEFT JOIN` back into an inner one.
  :::
  :::accordion-item{label="Find students who are not in any department (or: departments with no students)." icon="i-lucide-message-circle"}
  `LEFT JOIN` and keep the unmatched rows:
  `SELECT d.name FROM Department d LEFT JOIN Student s ON s.department_id = d.department_id WHERE s.student_id IS NULL;`
  returns Mechanical and Civil. `NOT EXISTS` is the other correct answer.
  :::
  :::accordion-item{label="Why might a SUM be wrong after adding a join?" icon="i-lucide-message-circle"}
  Fan-out. Joining to a table with several rows per key multiplies the rows, so
  every aggregate over them is multiplied too: two payments times three
  enrolments counted Anita's fees three times. Fix by aggregating each table in a
  subquery before joining. Most candidates can recite the four joins; almost
  none can name fan-out.
  :::
  :::accordion-item{label="How do you do a FULL OUTER JOIN in MySQL?" icon="i-lucide-message-circle"}
  MySQL does not support it. Combine a `LEFT JOIN` and a `RIGHT JOIN` with
  `UNION`, which removes the duplicated matched rows.
  :::
::
