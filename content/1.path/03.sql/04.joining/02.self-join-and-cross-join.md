Every join so far connected two different tables. "Which faculty member does
each faculty member report to?" needs a table joined to **itself**, because the
answer is another row of the same table.

## Why this matters in a job

Any table that points at itself needs a self join: a faculty member and their
head, a course and its prerequisite course, a category and its parent category.
In interviews, the self join is the most famous single SQL question after
"second highest salary": "find employees who earn more than their manager". In
this guide it is "faculty who earn more than their head", and it has a whole
lesson in the SQL round chapter. This lesson is the mechanism it needs.

## One register, two fingers

The `Faculty` table has a column `reports_to`, which holds the `faculty_id` of
that person's head. To write "Vikram Singh reports to Dr. Meera Joshi", you put
one finger on Vikram's row, read `reports_to = 1`, and put a second finger on
row 1 of **the same register**. A self join is exactly that: the same table,
read twice, with a different alias for each finger.

::memory{caption="Two aliases over one table. f is the faculty member, h is their head."}
---
cells:
  - { label: "f: Vikram Singh", value: "reports_to = 1" }
  - { label: "h: faculty_id = 1", value: "Dr. Meera Joshi", state: "active" }
---
::

## Syntax

```sql [self-join-syntax.sql]
SELECT a.column, b.column
FROM   Faculty a
JOIN   Faculty b ON b.faculty_id = a.reports_to;
```

The aliases are not optional here. Without them, `faculty_id` would be
ambiguous: which copy of the table do you mean?

::runner{lang="sql"}
```sql [who-reports-to-whom.sql]
CREATE TABLE Faculty (
  faculty_id     INTEGER PRIMARY KEY,
  full_name      TEXT,
  department_id  INTEGER,
  salary         INTEGER,
  reports_to     INTEGER      -- faculty_id of their head; NULL for a head
);
INSERT INTO Faculty VALUES
  (1, 'Dr. Meera Joshi',  1, 150000, NULL),
  (2, 'Vikram Singh',     1,  95000, 1),
  (3, 'Rohit Kumar',      1,  82000, 1),
  (4, 'Dr. Suresh Rao',   2, 140000, NULL),
  (5, 'Divya Menon',      2, 145000, 4),
  (6, 'Kavita Sharma',    2,  78000, 4);

SELECT f.full_name AS faculty,
       h.full_name AS reports_to
FROM   Faculty f
JOIN   Faculty h ON h.faculty_id = f.reports_to;
```
::

```text [Output]
faculty        reports_to
-------------  ---------------
Vikram Singh   Dr. Meera Joshi
Rohit Kumar    Dr. Meera Joshi
Divya Menon    Dr. Suresh Rao
Kavita Sharma  Dr. Suresh Rao
```

Four rows. The two heads are missing, because an inner join drops rows with no
partner and their `reports_to` is `NULL`. The previous lesson's rule applies
unchanged: to keep them, use a `LEFT JOIN`.

::runner{lang="sql"}
```sql [self-left-join.sql]
CREATE TABLE Faculty (faculty_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER, salary INTEGER, reports_to INTEGER);
INSERT INTO Faculty VALUES
  (1, 'Dr. Meera Joshi', 1, 150000, NULL), (2, 'Vikram Singh', 1, 95000, 1),
  (3, 'Rohit Kumar', 1, 82000, 1), (4, 'Dr. Suresh Rao', 2, 140000, NULL),
  (5, 'Divya Menon', 2, 145000, 4), (6, 'Kavita Sharma', 2, 78000, 4);

SELECT f.full_name                       AS faculty,
       COALESCE(h.full_name, '(head)')   AS reports_to
FROM   Faculty f
LEFT JOIN Faculty h ON h.faculty_id = f.reports_to
ORDER BY f.faculty_id;
```
::

```text [Output]
faculty          reports_to
---------------  ---------------
Dr. Meera Joshi  (head)
Vikram Singh     Dr. Meera Joshi
Rohit Kumar      Dr. Meera Joshi
Dr. Suresh Rao   (head)
Divya Menon      Dr. Suresh Rao
Kavita Sharma    Dr. Suresh Rao
```

### Comparing a row with its partner

Once both rows are side by side, you can compare them like any two columns. The
famous interview question falls out in one line:

::runner{lang="sql"}
```sql [earns-more-than-head.sql]
CREATE TABLE Faculty (faculty_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER, salary INTEGER, reports_to INTEGER);
INSERT INTO Faculty VALUES
  (1, 'Dr. Meera Joshi', 1, 150000, NULL), (2, 'Vikram Singh', 1, 95000, 1),
  (3, 'Rohit Kumar', 1, 82000, 1), (4, 'Dr. Suresh Rao', 2, 140000, NULL),
  (5, 'Divya Menon', 2, 145000, 4), (6, 'Kavita Sharma', 2, 78000, 4);

SELECT f.full_name, f.salary, h.full_name AS head, h.salary AS head_salary
FROM   Faculty f
JOIN   Faculty h ON h.faculty_id = f.reports_to
WHERE  f.salary > h.salary;
```
::

```text [Output]
full_name    salary  head            head_salary
-----------  ------  --------------  -----------
Divya Menon  145000  Dr. Suresh Rao  140000
```

### Pairs within the same table

A self join does not have to follow a `reports_to` column. "Pairs of students
from the same city" joins `Student` to itself on `city`:

::runner{lang="sql"}
```sql [same-city-pairs.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, city TEXT);
INSERT INTO Student VALUES
  (1, 'Anita Rao', 'Bhopal'), (2, 'Rahul Verma', 'Patna'),
  (3, 'Arjun Mehta', 'Bhopal'), (4, 'Sneha Iyer', 'Bhopal');

SELECT a.full_name AS student, b.full_name AS same_city_as, a.city
FROM   Student a
JOIN   Student b ON b.city = a.city
               AND b.student_id > a.student_id;   -- not yourself, and each pair once
```
::

```text [Output]
student      same_city_as  city
-----------  ------------  ------
Anita Rao    Arjun Mehta   Bhopal
Anita Rao    Sneha Iyer    Bhopal
Arjun Mehta  Sneha Iyer    Bhopal
```

`b.student_id > a.student_id` does two jobs. It stops Anita being paired with
herself, and it stops the same pair appearing twice (Anita with Arjun, then
Arjun with Anita). With `<>` instead of `>`, you would get six rows, each pair
twice. Forgetting this condition entirely is the classic self-join bug.

## CROSS JOIN: every row with every row

A `CROSS JOIN` has no join condition. It pairs every row of one table with every
row of the other, so 3 rows and 4 rows give 12. This is called the **Cartesian
product**.

It is usually an accident (a forgotten `ON`), and occasionally exactly what you
want. The exam cell building a blank timetable needs every course in every slot:

::runner{lang="sql"}
```sql [timetable-grid.sql]
CREATE TABLE Course (course_id INTEGER PRIMARY KEY, code TEXT);
INSERT INTO Course VALUES (101, 'CS201'), (102, 'CS202'), (103, 'MA201');

CREATE TABLE Slot (slot_id INTEGER PRIMARY KEY, label TEXT);
INSERT INTO Slot VALUES (1, 'Mon 10:00'), (2, 'Mon 14:00');

SELECT c.code, s.label
FROM   Course c
CROSS JOIN Slot s
ORDER BY c.code, s.slot_id;

SELECT COUNT(*) AS combinations FROM Course CROSS JOIN Slot;
```
::

```text [Output]
code   label
-----  ---------
CS201  Mon 10:00
CS201  Mon 14:00
CS202  Mon 10:00
CS202  Mon 14:00
MA201  Mon 10:00
MA201  Mon 14:00

combinations
------------
6
```

::warning{icon="i-lucide-alert-triangle"}
A cross join of two tables with a lakh rows each is ten thousand million rows.
If a query that should return hundreds returns millions, or never finishes,
look for a join with a missing or wrong `ON`.
::

## Real use case

Joining three tables is the same operation twice. The head of department wants
each student's marks with the student's name and the course title, which live in
three different tables. Each `JOIN` adds one table and one condition:

::runner{lang="sql"}
```sql [three-tables.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma'), (3, 'Priya Nair');

CREATE TABLE Course (course_id INTEGER PRIMARY KEY, code TEXT, title TEXT);
INSERT INTO Course VALUES (101, 'CS201', 'Data Structures'), (102, 'CS202', 'DBMS');

CREATE TABLE ExamResult (result_id INTEGER PRIMARY KEY, student_id INTEGER, course_id INTEGER, marks INTEGER);
INSERT INTO ExamResult VALUES (1, 1, 101, 87), (2, 2, 101, 64), (3, 1, 102, 72), (4, 3, 102, 91);

SELECT s.full_name, c.title, r.marks
FROM   ExamResult r
JOIN   Student s ON s.student_id = r.student_id
JOIN   Course  c ON c.course_id  = r.course_id
ORDER BY c.title, r.marks DESC;
```
::

```text [Output]
full_name    title            marks
-----------  ---------------  -----
Priya Nair   DBMS             91
Anita Rao    DBMS             72
Anita Rao    Data Structures  87
Rahul Verma  Data Structures  64
```

Start from the table whose rows you are reporting on (one row per result, here),
then join outwards to the tables that describe it. Each extra table is one more
`JOIN ... ON`.

## What confuses people here

- **A self join is not a special kind of join.** It is an ordinary inner or
  left join where both sides happen to be the same table. The only new thing is
  that aliases become compulsory.
- **`NATURAL JOIN` and `USING`.** `JOIN Course USING (course_id)` joins on a
  column with the same name in both tables and is fine. `NATURAL JOIN` joins on
  **every** column with the same name, automatically. Add a `created_on` column
  to both tables next year and every `NATURAL JOIN` silently gains a condition.
  Avoid it.
- **Cross join by accident.** `FROM Student, Course` with no `WHERE` is a cross
  join. The comma syntax makes this very easy to do.

## Interview questions

::accordion
  :::accordion-item{label="What is a self join? Give an example." icon="i-lucide-message-circle"}
  A table joined to itself, with two aliases so each copy can be referred to
  separately. Example: each faculty member with the name of their head, using
  `Faculty f JOIN Faculty h ON h.faculty_id = f.reports_to`. Any table that
  refers to itself (reporting lines, prerequisites, parent categories) needs one.
  :::
  :::accordion-item{label="Find faculty who earn more than their head." icon="i-lucide-message-circle"}
  `SELECT f.full_name FROM Faculty f JOIN Faculty h ON h.faculty_id = f.reports_to WHERE f.salary > h.salary;`
  On the data above, Divya Menon (₹1,45,000, against her head's ₹1,40,000). The
  full lesson on this question, with its variants, is in the SQL round chapter.
  :::
  :::accordion-item{label="What is a CROSS JOIN? When would you use one?" icon="i-lucide-message-circle"}
  Every row of one table paired with every row of another, with no condition:
  the Cartesian product, m × n rows. Useful for generating combinations (every
  course in every exam slot, every department in every month for a report with
  no gaps). Usually, though, it is an accident caused by a missing join
  condition.
  :::
  :::accordion-item{label="If table A has 5 rows and B has 4, how many rows does each join return?" icon="i-lucide-message-circle"}
  `CROSS JOIN`: exactly 20. `INNER JOIN`: anywhere from 0 to 20, depending on
  matches. `LEFT JOIN`: at least 5 (every A row, some possibly repeated). `FULL
  OUTER JOIN`: at least 5. This question checks whether you think in rows rather
  than Venn diagrams.
  :::
  :::accordion-item{label="Find pairs of students from the same city." icon="i-lucide-message-circle"}
  Self join on `city` with `b.student_id > a.student_id`, which excludes pairing
  a student with themselves and lists each pair once. The query and its output
  are above.
  :::
::
