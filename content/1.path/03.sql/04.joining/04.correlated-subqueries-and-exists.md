Every inner query so far ran once and handed its answer out. "Students who
scored above their own department's average" needs a **different** average for
every student. A correlated subquery is an inner query that looks at the outer
row it is being asked about.

## Why this matters in a job

"Above their own group's average", "the latest payment for each student",
"courses with at least one failure", "students with no fee payment at all": each
compares a row with other rows related to it. In interviews, correlated
subqueries are one of the standard ways to solve "Nth highest marks" and "top N
per group", and `EXISTS` against `IN` is a favourite follow-up.

## The inner query asks about this row

A normal subquery is like the exam cell working out the college average once and
pinning it on the notice board; everybody compares themselves with the same
number. A correlated subquery is like a teacher going down the list and, for
each student, working out the average **of that student's own department**
before comparing. The inner calculation depends on who is being looked at, so
it is repeated for each one.

::flow{numbered direction="vertical" caption="How a correlated subquery runs, logically."}
  :::flow-step{label="Take one outer row" icon="i-lucide-user"}
  Anita, department 1, marks 87.
  :::
  :::flow-step{label="Run the inner query for that row" icon="i-lucide-repeat" highlight}
  Average of department 1 is 85.33.
  :::
  :::flow-step{label="Test the condition" icon="i-lucide-check"}
  87 > 85.33, so Anita is kept.
  :::
  :::flow-step{label="Next outer row" icon="i-lucide-arrow-down"}
  Repeat for Rahul, then Priya, and so on.
  :::
::

## Syntax

The inner query mentions a column of the outer query, through its alias:

```sql [correlated-syntax.sql]
SELECT ...
FROM   Outer o
WHERE  o.col > (SELECT AGG(i.col) FROM Inner i WHERE i.key = o.key);
--                                                          └── the correlation
```

::runner{lang="sql"}
```sql [above-own-department.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT, department_id INTEGER, marks INTEGER);
INSERT INTO Student VALUES
  (1, 'Anita Rao',   1, 87), (2, 'Rahul Verma', 2, 64), (3, 'Priya Nair',  1, 91),
  (4, 'Arjun Mehta', 3, 45), (5, 'Sneha Iyer',  1, 78), (6, 'Karan Patel', 2, 55);

SELECT s.full_name, s.department_id, s.marks
FROM   Student s
WHERE  s.marks > (SELECT AVG(x.marks)
                  FROM   Student x
                  WHERE  x.department_id = s.department_id)
ORDER BY s.department_id;
```
::

```text [Output]
full_name    department_id  marks
-----------  -------------  -----
Anita Rao    1              87
Priya Nair   1              91
Rahul Verma  2              64
```

Department 1 averages 85.33, so Anita (87) and Priya (91) are above it.
Department 2 averages 59.5, so Rahul (64) is above it. Arjun is alone in
department 3; he is equal to his own average, not above it.

Compare this with the college-wide version from the last lesson (average 70):
that one returned Priya, Anita and Sneha. Different question, different answer,
and Rahul only appears in this one.

## EXISTS and NOT EXISTS

`EXISTS (subquery)` is true if the subquery returns **at least one row**. It
does not care what the row contains, which is why you will see `SELECT 1`
inside it. It is almost always correlated.

::runner{lang="sql"}
```sql [exists.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma'), (3, 'Priya Nair'), (4, 'Arjun Mehta');

CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER);
INSERT INTO FeePayment VALUES (1, 1, 30000), (2, 1, 12500), (3, 3, 42500), (4, NULL, 5000);

-- Students who have made at least one payment.
SELECT full_name FROM Student s
WHERE  EXISTS (SELECT 1 FROM FeePayment f WHERE f.student_id = s.student_id);

-- Students who have made no payment at all.
SELECT full_name FROM Student s
WHERE  NOT EXISTS (SELECT 1 FROM FeePayment f WHERE f.student_id = s.student_id);
```
::

```text [Output]
full_name
----------
Anita Rao
Priya Nair

full_name
-----------
Rahul Verma
Arjun Mehta
```

Anita appears once, even though she has two payments: `EXISTS` stops at the
first match. A join would have listed her twice.

### NOT EXISTS against NOT IN

Payment 4 was entered without a `student_id`. Watch what that does to `NOT IN`:

::runner{lang="sql"}
```sql [not-in-vs-not-exists.sql]
CREATE TABLE Student (student_id INTEGER PRIMARY KEY, full_name TEXT);
INSERT INTO Student VALUES (1, 'Anita Rao'), (2, 'Rahul Verma'), (3, 'Priya Nair'), (4, 'Arjun Mehta');
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER);
INSERT INTO FeePayment VALUES (1, 1, 30000), (2, 1, 12500), (3, 3, 42500), (4, NULL, 5000);

SELECT 'NOT IN' AS method, COUNT(*) AS unpaid FROM Student
WHERE  student_id NOT IN (SELECT student_id FROM FeePayment);

SELECT 'NOT EXISTS' AS method, COUNT(*) AS unpaid FROM Student s
WHERE  NOT EXISTS (SELECT 1 FROM FeePayment f WHERE f.student_id = s.student_id);
```
::

```text [Output]
method  unpaid
------  ------
NOT IN  0

method      unpaid
----------  ------
NOT EXISTS  2
```

::compare{caption="Same question, one NULL in the payments table."}
  :::compare-side{label="NOT IN" verdict="wrong"}
  0 unpaid students. One `NULL` in the list makes `NOT IN` unknown for every
  row, as the NULL lesson showed. The fee office concludes everyone has paid.
  :::
  :::compare-side{label="NOT EXISTS" verdict="right"}
  2 unpaid students, Rahul and Arjun. `NOT EXISTS` asks "is there a matching
  row?", and a `NULL` matches nothing, so it is ignored.
  :::
::

::tip
Make `NOT EXISTS` your default for "which of these has no matching that". It is
correct with `NULL`s, and on most databases it is planned as an efficient
anti-join. Saying this in an interview sounds like experience, because it is.
::

## Real use case

The fee office wants each student's **latest** payment: the date and the
amount. It is a correlated subquery that, for each payment, asks "is there a
later payment for the same student?"

::runner{lang="sql"}
```sql [latest-payment.sql]
CREATE TABLE FeePayment (payment_id INTEGER PRIMARY KEY, student_id INTEGER, amount INTEGER, paid_on TEXT);
INSERT INTO FeePayment VALUES
  (1, 1, 30000, '2025-07-10'), (2, 1, 12500, '2025-09-02'),
  (3, 2, 20000, '2025-07-15'), (4, 2, 22500, '2025-08-20'),
  (5, 3, 42500, '2025-07-01');

SELECT f.student_id, f.amount, f.paid_on
FROM   FeePayment f
WHERE  f.paid_on = (SELECT MAX(x.paid_on)
                    FROM   FeePayment x
                    WHERE  x.student_id = f.student_id)
ORDER BY f.student_id;
```
::

```text [Output]
student_id  amount  paid_on
----------  ------  ----------
1           12500   2025-09-02
2           22500   2025-08-20
3           42500   2025-07-01
```

"The latest row per group" is one of the most common queries in any job. You
will see it written this way, with `NOT EXISTS (a later row)`, and with window
functions (`ROW_NUMBER`), which a later chapter covers. The window-function
version is usually faster on large tables; this one is easier to read on paper.

## What confuses people here

- **"Runs once per row" is the logical model, not always what happens.**
  Databases often rewrite a correlated subquery into a join. But on a large
  table without an index on the correlated column, it really can run once per
  row, and that is slow. An index on `FeePayment(student_id)` is what makes the
  queries above fast on lakhs of rows.
- **`EXISTS` ignores the select list.** `SELECT 1`, `SELECT *` and
  `SELECT student_id` inside `EXISTS` all behave identically.
- **Forgetting the correlation.** Leave out `WHERE f.student_id = s.student_id`
  and `EXISTS` asks "is there any payment at all?", which is true for every
  student. No error, wrong answer.
- **Ambiguous names.** Inside the subquery, a bare `student_id` refers to the
  inner table if it has one. Always qualify with aliases in correlated
  subqueries.

## Interview questions

::accordion
  :::accordion-item{label="What is a correlated subquery?" icon="i-lucide-message-circle"}
  A subquery that refers to a column of the outer query, so it is evaluated for
  each outer row. Example: students above their own department's average, where
  the inner `AVG` is filtered by `x.department_id = s.department_id`. A
  non-correlated subquery runs once and does not depend on the outer row.
  :::
  :::accordion-item{label="What is the difference between EXISTS and IN?" icon="i-lucide-message-circle"}
  `IN` compares a value against a list the subquery returns. `EXISTS` checks
  whether the (usually correlated) subquery returns any row at all, and stops at
  the first. The important difference is with negation: `NOT IN` returns nothing
  if the list contains a `NULL`; `NOT EXISTS` is unaffected. On the data above,
  `NOT IN` found 0 unpaid students and `NOT EXISTS` found 2.
  :::
  :::accordion-item{label="Find courses that have at least one failing result." icon="i-lucide-message-circle"}
  ```sql [courses-with-failures.sql]
  SELECT c.code
  FROM   Course c
  WHERE  EXISTS (SELECT 1 FROM ExamResult r
                 WHERE r.course_id = c.course_id AND r.marks < 40);
  ```
  Each course is listed once however many students failed it, which a join
  would not give you without `DISTINCT`.
  :::
  :::accordion-item{label="Is a correlated subquery slow?" icon="i-lucide-message-circle"}
  It can be, because logically it runs once per outer row. In practice the
  optimiser often turns it into a join, and an index on the correlated column
  makes each run cheap. If it is slow, rewrite it as a join to a grouped derived
  table, or with a window function, and compare the plans.
  :::
::
