title: Interview questions
description: Five TypeScript questions, including the one that separates somebody who has used it from somebody who has read about it.
minutes: 7
kind: quiz
---

::accordion
  :::accordion-item{label="1. Why TypeScript?" icon="i-lucide-message-circle"}
  Errors at nine in the morning rather than in a support email three weeks
  later, plus autocomplete and safe renaming across a codebase that no editor
  can offer for untyped JavaScript.

  Then the one that shows use rather than reading: types are **erased**, so at
  the boundary, HTTP, a form, `localStorage`: a type is a claim you made about
  somebody else's data, not a check. You validate there with a schema and derive
  the type from it, so the two cannot drift apart.
  :::

  :::accordion-item{label="2. `any` or `unknown`?" icon="i-lucide-message-circle"}
  `any` switches off checking for everything it touches and spreads outward
  through return values, so one `any` in a utility disables checking in every
  caller. `unknown` says the same thing honestly and forces you to narrow before
  using it.

  And `as` belongs in the same answer: it is an assertion rather than a
  conversion, so it tells the compiler to stop checking. Occasionally right,
  usually somebody silencing an error they did not understand.
  :::

  :::accordion-item{label="3. `interface` or `type`?" icon="i-lucide-message-circle"}
  Both describe a shape. `interface` can be reopened and extended, which matters
  for augmenting a library's types; `type` can be a union, which `interface`
  cannot. Everything else is preference, and the real answer is to be consistent
  within a codebase.

  If they push, the useful detail is that TypeScript is **structurally** typed:
  two types are compatible when their members match, not when their names do,
  which is the opposite of Java and surprises people coming from it.
  :::

  :::accordion-item{label="4. What does `strict` turn on, and would you use it?" icon="i-lucide-message-circle"}
  Yes, from day one. `strict` is what makes null checking real: without it,
  `string` silently includes `null` and the main benefit of the language is
  switched off.

  Then the observation that makes it a judgement rather than a rule: turning it
  on in an existing untyped codebase produces several hundred errors and is a
  genuine project, and turning it on in a new one costs nothing. Which is why
  the advice is always "day one": the same setting is free now and a fortnight
  later.
  :::

  :::accordion-item{label="5. How do you type data coming from an API?" icon="i-lucide-message-circle"}
  The question that separates the two groups. `await response.json()` returns
  `any`, so writing `const a: Applicant = await response.json()` compiles and is
  a lie: if the API renames a field, TypeScript reports nothing and you get
  `undefined is not a function` three layers away.

  Parse at the boundary with Zod or similar, and use `z.infer` so the type is
  **derived from the check** rather than written beside it. Then a change at the
  API fails immediately, with a message naming the field.
  :::
::
