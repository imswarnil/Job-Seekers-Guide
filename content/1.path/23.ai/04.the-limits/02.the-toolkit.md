This subject changes about every four months, so a long list of tools would be
wrong by the time you read it. What follows is short on purpose: the categories
you need, one or two names in each, and the reason rather than the ranking.

::note
Everything here has a free tier big enough for the University Management App.
None of it needs a card to start, and where one does, that is stated.
::

## Models

| For | Reach for | Why |
| --- | --- | --- |
| Most product features | A mid-tier hosted model | The default. Good enough, priced sanely. |
| Classification, extraction, routing | The smallest hosted model | Ten times cheaper and nobody can tell |
| Hard reasoning, difficult code | A frontier model | Route only the tail here; see the cost lesson |
| Privacy-constrained, or offline | **Ollama**, locally | Runs an open model on your own machine. Free, private, slower. |
| Embeddings | A hosted embedding model | Cents per million tokens; almost never the cost problem |

```bash [Terminal]
# A model on your own laptop, in two commands. No account, no key, no bill.
brew install ollama
ollama run llama3.2
```

::tip
Do the Ollama one early. Having a model running locally makes the whole subject
concrete, it costs nothing to experiment against, and it is the right answer any
time the data genuinely cannot leave your machine, which for student records is
a real constraint rather than a hypothetical one.
::

## Storing and searching vectors

| For | Reach for | Why |
| --- | --- | --- |
| **Start here, always** | **PostgreSQL + `pgvector`** | You already run Postgres. One extension, one index, and your documents sit beside your data with the same backups and the same permissions. |
| Serverless Postgres | **Neon** | Postgres with `pgvector`, a real free tier, branching per pull request, and it scales to zero so a portfolio project costs nothing. |
| Very large scale | A dedicated vector database | Real above roughly ten million vectors. Below that it is a second system to run for no gain. |

::warning{icon="i-lucide-alert-triangle"}
The most common overbuild in this subject is reaching for a dedicated vector
database on day one. A prospectus is about four hundred chunks. Four hundred
rows in a table you already have, with an index, answers in single-digit
milliseconds. Adding a second datastore for that is a decision you will have to
justify and cannot.
::

## Running it

| For | Reach for | Why |
| --- | --- | --- |
| The web application | **Vercel** | Push a branch, get a URL. Preview per pull request, certificates handled, free tier ample. Built by the people who make Next.js, so that path is the smooth one. |
| A Java backend or a worker | **Railway** or **Render** | Long-running processes and background jobs, which a serverless platform is awkward about. |
| Anything you want to learn from | **A ₹400 droplet** | nginx, systemd, certbot, a firewall. Do this once for the knowledge, as the hosting track says. |
| The database | **Neon** or **Supabase** | Managed Postgres with backups you did not have to configure. |

::flow{numbered direction="vertical" caption="The stack this course's project actually runs on, and why each piece."}
  :::flow-step{label="Neon for Postgres" icon="i-lucide-database" highlight}
  Free tier, scales to zero, `pgvector` included, and a **branch per pull
  request** so a migration can be tested against a copy of real data without
  touching it.
  :::
  :::flow-step{label="Vercel for the Next.js front end" icon="i-lucide-cloud"}
  Git push deploys. Preview URLs per branch, which is the single most useful
  thing on a team.
  :::
  :::flow-step{label="Railway for the Java API" icon="i-lucide-server"}
  A long-running Spring process with a real port, which is what serverless is
  bad at.
  :::
  :::flow-step{label="A model API, and Ollama locally" icon="i-lucide-sparkles"}
  Hosted in production for quality; local while developing, so experimenting
  costs nothing and no student data leaves the machine.
  :::
::

## Libraries, and one warning

| For | Reach for |
| --- | --- |
| Calling a model | The provider's own SDK. Small, current, and it does not hide the request. |
| Validating a model's output | **Zod** or **Pydantic**. Parse it; never trust the shape. |
| Tool access to your systems | The **MCP SDK**, per the previous lesson |
| Chunking and retrieval | Write it. It is fifty lines and you will want to control it. |
| Evaluating changes | **Promptfoo** or a spreadsheet. See below. |

::warning{icon="i-lucide-alert-triangle"}
The orchestration frameworks: the ones that promise chains, agents and memory in
four lines, are worth being careful with while learning. They hide the request,
which is exactly the thing you need to see, and they move fast enough that
tutorials go stale in months. Write the HTTP call yourself first. When you
genuinely need orchestration you will know which part you want, rather than
adopting all of it.
::

## Evaluating, which is the part everybody skips

You cannot improve what you do not measure, and a model is non-deterministic, so
"it looked better" is not evidence.

```text [evals/prospectus.csv]
question,expected_contains,must_decline
"What documents do I need?","transfer certificate",false
"What is the last date to apply?","31 March",false
"What is the hostel fee?","",true          ← not in the documents
"Who won the cricket match?","",true        ← not the system's job
```

::pull-quote
Twenty questions in a spreadsheet, with the three you know it cannot answer, run
before and after every prompt change. That is an evaluation suite, it takes an
afternoon, and almost nobody building these features has one.
::

## Where to look when this changes

It will, about every four months. These are the sources worth having rather than
a list of links that rot.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-file-text" title="The provider's own documentation"}
  Anthropic, OpenAI and Google all publish genuinely good guides on prompting,
  tool use and evaluation. Read the source rather than a summary of it.
  :::
  :::feature{icon="i-lucide-book" title="The MCP specification and SDK"}
  `modelcontextprotocol.io`. Short, readable, and the servers list is the
  fastest way to see what people are actually building.
  :::
  :::feature{icon="i-lucide-graduation-cap" title="Karpathy's videos and nanoGPT"}
  The best available explanation of what is inside one of these, by a distance,
  and free. This is the "build a tiny one" route from the training lesson.
  :::
  :::feature{icon="i-lucide-users" title="Hugging Face"}
  Open models, datasets and leaderboards. Where you go when you want to run
  something yourself rather than call an API.
  :::
  :::feature{icon="i-lucide-search" title="'awesome-mcp-servers' and friends"}
  The `awesome-*` lists on GitHub are community-maintained indexes, and they are
  the correct shape for a fast-moving field: a list somebody updates, rather
  than a blog post from March.
  :::
  :::feature{icon="i-lucide-x" title="Not: the model's own claims about itself"}
  It does not know its own version, its cut-off, or its pricing reliably. Ask
  the documentation, which is one of the better demonstrations of this whole
  track's argument.
  :::
::

## Your turn

Pick the stack for the University Management App and write down, for each piece,
what it costs at the scale you expect and what you would use instead if it were
ten times bigger.

::accordion
  :::accordion-item{label="One answer, and the number that decides it" icon="i-lucide-check"}
  **Postgres on Neon** for everything, including the prospectus vectors with
  `pgvector`. At 400 chunks and 40,000 applications this is comfortably inside a
  free tier. At ten times bigger it is still Postgres; at a hundred times, the
  vectors might justify their own store, and only then.

  **Vercel** for the Next.js front end, free at this scale. At ten times bigger
  it is still Vercel and it is now a real invoice worth comparing against a
  container host.

  **Railway** for the Java API. At ten times bigger, a container platform with
  autoscaling.

  **A small hosted model** for classification and SQL generation, a mid-tier one
  for the assistant. About ₹2,500 an intake from the cost lesson. At ten times
  bigger, the first thing to change is not the provider: it is adding a cache,
  because the same eleven questions are being asked repeatedly.

  **The number that decides all of it** is calls per day, and you can estimate it
  before writing anything. Doing that estimate, and being wrong by an order of
  magnitude in the safe direction, is the whole of capacity planning at this
  scale.
  :::
