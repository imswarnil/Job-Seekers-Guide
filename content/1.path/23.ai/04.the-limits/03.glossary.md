Four chapters on models, and about forty-five terms arrived with them. Most are
now used loosely enough in job adverts that knowing the actual meaning is itself
a distinguishing thing.

## What a model is

::field-group
  :::field{name="Token" type="mechanics"}
  A chunk of text, roughly three-quarters of a word in English. Models read and
  write tokens, not characters, which is why they miscount letters.
  :::
  :::field{name="Tokenisation" type="mechanics"}
  Turning text into tokens. Different models split differently, and non-English
  text usually costs more tokens for the same meaning.
  :::
  :::field{name="Parameters" type="mechanics"}
  The numbers learned during training. "70 billion parameters" is a size, not a
  quality, and a smaller well-trained model routinely beats a larger one.
  :::
  :::field{name="Context window" type="mechanics"}
  How many tokens the model can consider at once, input and output together.
  The hard limit on how much of your codebase it can see.
  :::
  :::field{name="Inference" type="mechanics"}
  Running the model to produce output, as opposed to training it. What you pay
  for per token.
  :::
  :::field{name="Temperature" type="mechanics"}
  How much randomness in choosing the next token. Zero is repeatable and flat;
  higher is varied and less reliable. For anything you will check against a
  schema, keep it low.
  :::
  :::field{name="Autoregressive" type="mechanics"}
  Producing one token at a time, each conditioned on everything before it. Why
  the first wrong token derails a whole answer, and why output costs more than
  input.
  :::
::

## How one is made

::field-group
  :::field{name="Pre-training" type="training"}
  The expensive part. Learning to predict the next token across an enormous
  amount of text. Months and millions of pounds.
  :::
  :::field{name="Fine-tuning" type="training"}
  Further training on a smaller, specific set, to change behaviour or style.
  Thousands rather than millions.
  :::
  :::field{name="LoRA" type="training"}
  Low-Rank Adaptation. Fine-tuning by training a small number of extra
  parameters rather than all of them. What makes fine-tuning affordable.
  :::
  :::field{name="RLHF" type="training"}
  Reinforcement Learning from Human Feedback. Humans rank outputs, and the model
  is trained toward the preferred ones. Why a model is helpful rather than
  merely fluent.
  :::
  :::field{name="Distillation" type="training"}
  Training a smaller model on a larger one's outputs. How the cheap fast models
  exist.
  :::
  :::field{name="Quantisation" type="training"}
  Storing parameters at lower precision so the model fits in less memory and
  runs faster, with some quality loss. What lets a model run on your laptop.
  :::
::

## Building with one

::field-group
  :::field{name="Prompt" type="building"}
  Everything you send. System instructions, context and the question.
  :::
  :::field{name="System prompt" type="building"}
  Instructions that frame the whole conversation. Not a security boundary, and
  treating it as one is a common and serious mistake.
  :::
  :::field{name="Few-shot" type="building"}
  Including examples of the input and output you want. The single most effective
  thing you can do to a prompt, and it costs only tokens.
  :::
  :::field{name="RAG" type="building"}
  Retrieval-Augmented Generation. Find relevant documents, put them in the
  prompt, ask the question against them. How a model answers about data it was
  never trained on.
  :::
  :::field{name="Embedding" type="building"}
  Text turned into a list of numbers, where similar meanings land near each
  other. What makes retrieval work on meaning rather than keywords.
  :::
  :::field{name="Vector database" type="building"}
  A store that finds the nearest embeddings quickly. Postgres with `pgvector`
  is usually enough, and a separate service usually is not needed.
  :::
  :::field{name="Chunking" type="building"}
  Splitting documents before embedding them. Chunk boundaries decide what can
  ever be retrieved together, which makes it the highest-impact decision in a
  RAG system and the one people spend least time on.
  :::
  :::field{name="Tool use" type="building"}
  Letting a model call a function you defined. The model chooses and supplies
  arguments; **your code decides whether to run it**.
  :::
  :::field{name="MCP" type="building"}
  Model Context Protocol. A standard way to expose tools and data to a model, so
  one server works with any client that speaks it.
  :::
  :::field{name="Agent" type="building"}
  A model in a loop with tools, deciding its own next step. Powerful, hard to
  bound, and the place where cost and blast radius both escape.
  :::
::

## Where it fails

::field-group
  :::field{name="Hallucination" type="limits"}
  Confident, fluent output that is false. Not a bug being fixed; a consequence
  of predicting plausible text. The mitigation is verification, never trust.
  :::
  :::field{name="Prompt injection" type="limits"}
  Instructions hidden in data the model reads, which it then follows. The
  unsolved security problem of this field, and the reason a model must never
  hold permissions a user does not.
  :::
  :::field{name="Knowledge cutoff" type="limits"}
  The date after which the model knows nothing. It will still answer confidently
  about later events.
  :::
  :::field{name="Non-determinism" type="limits"}
  The same prompt can give different answers. Which is why anything important
  gets validated against a schema rather than parsed hopefully.
  :::
::

## The three pairs confused in interviews

::compare{caption="Said interchangeably, and they are different operations with different costs."}
  :::compare-side{label="RAG" verdict="neutral"}
  Put the relevant documents in the prompt at question time. Cheap, immediate,
  and the answer can cite its source. Correct for facts that change.
  :::
  :::compare-side{label="Fine-tuning" verdict="neutral"}
  Change the model's weights. Expensive, slow, and it teaches **behaviour and
  format** rather than facts. Choosing it to add knowledge is the most common
  architectural mistake in this area.
  :::
::

**Tokens against words.** Pricing, limits and speed are all per token. Roughly
0.75 words per token in English, and considerably worse in most other languages,
which matters if your users are not writing in English.

**Tool use against agency.** A model choosing to call a function is tool use.
A model looping until it decides it is finished is an agent. The first has a
bounded cost and the second does not, and conflating them is how an overnight
job spends a month's budget.
