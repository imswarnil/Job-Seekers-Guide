The number that decides whether a feature ships. Every call costs money, the
cost is per token in and per token out, and a feature that is free at ten users
is a monthly invoice at ten thousand.

## Why this matters in a job

Because you will propose a feature and somebody will ask what it costs to run,
and "I am not sure" is the answer that stops it. Doing the arithmetic on the back
of an envelope takes two minutes and is one of the more visible ways a junior
engineer sounds senior.

## How it is priced

Per million tokens, **input and output priced separately**, output usually
several times more expensive. A token is roughly three to four characters of
English.

| Rough tier | Input, per 1M tokens | Output, per 1M tokens | Use it for |
| --- | --- | --- | --- |
| Small / fast | $0.10 – $0.50 | $0.30 – $2 | Classification, extraction, routing |
| Mid | $1 – $5 | $5 – $15 | Most product features |
| Frontier | $5 – $20 | $20 – $80 | Hard reasoning, code, the difficult tail |

::note
Those are bands rather than prices, because the actual numbers move every few
months and always downward. The **ratios** are what to remember: output costs
several times input, and the gap between tiers is roughly ten times per step.
Both of those have held for years and both drive the design decisions below.
::

## The arithmetic, done once

The dean's dashboard assistant from the building chapter.

```text [One call]
System prompt with the schema and the rules      1,200 tokens
The dean's question                                  20 tokens
                                              ──────────────
Input                                             1,220 tokens
Output: one SQL statement                           120 tokens
```

```text [At a mid-tier price of $3 in / $15 out per million]
Input    1,220 / 1,000,000 × $3   = $0.0037
Output     120 / 1,000,000 × $15  = $0.0018
                                    ───────
Per call                            $0.0055   ≈ ₹0.46
```

Now multiply, which is the step people skip.

| Usage | Calls per month | Cost |
| --- | --- | --- |
| Twelve staff, ten questions a day | 2,400 | **₹1,100** |
| The whole university, once each per day | 40,000 | **₹18,400** |
| Every applicant, five questions each | 200,000 | **₹92,000** |
| The same, with a frontier model | 200,000 | **₹6,10,000** |

::pull-quote
The same feature is ₹1,100 a month or ₹6,10,000 a month depending on two
decisions: who is allowed to use it, and which model you chose. Neither
decision is technical and both are yours to raise.
::

## The four levers

In order of how much they save.

::flow{numbered direction="vertical" caption="Apply them in this order. The first two usually cut the bill by ten between them."}
  :::flow-step{label="1. Do not call it at all" icon="i-lucide-circle-slash" highlight}
  Cache the answer. The dean asks "how many applicants this intake?" eleven
  times a day and the answer changes hourly. One call an hour instead of eleven
  a day, and the eleventh user gets a faster answer as well as a free one.
  :::
  :::flow-step{label="2. Use a smaller model" icon="i-lucide-minimize-2"}
  Most calls are not hard. Classification, extraction, routing and simple SQL
  are all well within a small model, at a tenth of the price. Route the hard
  tail to a bigger one and measure whether anybody notices.
  :::
  :::flow-step{label="3. Shorten the input" icon="i-lucide-scissors"}
  That 1,200-token system prompt is sent on **every** call and is most of the
  input bill. Trim it. Send five retrieved passages rather than twenty, and
  the schema for three tables rather than thirty.
  :::
  :::flow-step{label="4. Shorten the output" icon="i-lucide-align-left"}
  Output costs several times input. "Reply with only the SQL, no explanation"
  is a cost decision as much as a correctness one, and asking for JSON rather
  than prose typically halves it.
  :::
::

::tip
Prompt caching is worth knowing by name: most providers will charge a fraction
for a long prefix that has been sent before. A 1,200-token system prompt sent
on every call is exactly that shape, so putting the fixed part **first** and the
variable part last can cut the input cost substantially for one line of
reordering.
::

## The mistake everybody makes once

::compare{caption="The same feature, written two ways."}
  :::compare-side{label="A call inside a loop" verdict="wrong"}
  ```java
  for (Application a : applications) {      // 2,040 of them
    String summary = ai.summarise(a);       // one call each
  }
  ```
  2,040 calls, several minutes, and about ₹950 every time the page loads. This
  is the N+1 query problem from the SQL track, with a bill attached.
  :::
  :::compare-side{label="Batched, and only when asked" verdict="right"}
  Summarise on demand for the one application being viewed, store the result,
  and regenerate only when the application changes. Two calls a day rather than
  2,040 a page load.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
Set a spending limit on the account before you write a line of code, and an
alert at half of it. A retry loop with no ceiling, pointed at a paid API, is a
bill rather than an outage, and you will not find out until the invoice. This is
the retry lesson from the networks track with money attached.
::

## The other costs

Money is the visible one. Three more decide whether a feature is usable.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-clock" title="Latency"}
  One to five seconds per call. A screen making three sequentially is a slow
  screen. Batch them, run them in parallel, or stream the output so something
  appears immediately.
  :::
  :::feature{icon="i-lucide-plug" title="Availability"}
  Your feature now depends on somebody else's service. Design for it being
  down: degrade to the ordinary interface rather than breaking the page.
  :::
  :::feature{icon="i-lucide-shield" title="Data"}
  Everything you send leaves your infrastructure. Applicant names, marks and
  contact details going to a third party is a legal question before it is a
  technical one. Ask before you build.
  :::
  :::feature{icon="i-lucide-gauge" title="Rate limits"}
  Measured in tokens per minute as well as requests. A batch job can exhaust
  the minute's budget and stall every interactive user behind it, which is a
  queueing problem rather than a pricing one.
  :::
::

## What you can do now

You can estimate the monthly cost of a feature before building it, name the four
levers, and raise the two decisions that change the bill by a factor of five
hundred.

## Your turn

Estimate these. Use $3 in and $15 out per million, and show the arithmetic.

1. Summarising each of 2,040 applications once: 800 tokens in, 150 out.
2. The prospectus assistant: 3,000 in (five retrieved passages), 200 out,
   used by 500 applicants five times each in an intake.
3. Classifying 40,000 enquiries into nine categories: 200 in, 5 out, on a small
   model at $0.15 in / $0.60 out.

::accordion
  :::accordion-item{label="Answers, and the one that changes the design" icon="i-lucide-calculator"}
  **1.** In: 2,040 × 800 = 1.63M → $4.90. Out: 2,040 × 150 = 306K → $4.59.
  **About $9.50, or ₹800, once.** Cheap, because it is once. It becomes
  expensive the moment somebody puts it in a page-load loop.

  **2.** 2,500 calls. In: 7.5M → $22.50. Out: 500K → $7.50. **About $30, or
  ₹2,500, per intake.** Entirely reasonable, and note the input is three
  quarters of it, which points straight at lever three: retrieve three passages
  instead of five and you save a third.

  **3.** In: 8M → $1.20. Out: 200K → $0.12. **About $1.30, or ₹110, for forty
  thousand classifications.** Which is the lesson: the small model is not a
  compromise here, it is the correct engineering choice, and using a frontier
  model for this would cost roughly forty times more for a task where nobody
  could tell the difference.

  **And the design change all three point at:** cost per call is small and cost
  per *feature* is decided by how many calls you make. Almost every expensive AI
  feature is expensive because of a loop, not because of a price.
  :::
::

## Check yourself

1. Why is output usually more expensive than input, and what does that change
   about how you write a prompt?
2. **An interviewer asks: "roughly what would this feature cost to run?"**

## The interview question this answers

**"How do you control the cost of an AI feature?"**

The four levers in order: cache so you do not call at all, use the smallest model
that passes, shorten the input because the system prompt is sent every time, and
constrain the output because it is priced higher.

Then the answer that shows judgement rather than knowledge: the cost is decided
by the number of calls, not the price per call, so the first thing to look for is
a loop. And a spending limit and an alert before any code is written, because a
retry with no ceiling against a paid API is an invoice rather than an outage.
