Plain readable text, including the session cookie. Anybody on the same wifi, any
router along the path and your internet provider could read it and copy it.
**TLS** (Transport Layer Security) is the layer that fixes that, and HTTPS is
ordinary HTTP sent inside it. It is worth being precise about what it fixes.

## Why this matters in a job

"HTTP against HTTPS" and "how does HTTPS work?" are both common fresher
questions, and "is a site with a padlock safe?" is a favourite trick. At work,
TLS is the layer that most often breaks in a deployment, with an error message
nobody can read, and each of the three common certificate errors has a
different fix.

## HTTP against HTTPS

| | HTTP | HTTPS |
| --- | --- | --- |
| Default port | 80 | 443 |
| Encryption | None: plain text on the wire | Everything after the handshake is encrypted |
| Server identity | Not checked | Proved with a certificate |
| Tampering | Undetected | Detected, the connection fails |
| Extra cost | None | One more round trip for the TLS handshake (TLS 1.3) |
| Browser shows | "Not secure" | A padlock |

## A sealed envelope and a stamped ID card

TLS gives three guarantees, and it helps to know how each is achieved.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-eye-off" title="Confidentiality"}
  Nobody in between can read it. Your password, the student's marks, the fee
  amount.
  :::
  :::feature{icon="i-lucide-badge-check" title="Identity"}
  You are talking to the machine that holds the private key for this name. Not
  "this site is honest": "this site is who the name says".
  :::
  :::feature{icon="i-lucide-shield-check" title="Integrity"}
  Nobody changed anything in transit. A modified byte is detected and the
  connection fails rather than delivering altered data.
  :::
  :::feature{icon="i-lucide-x" title="NOT: that the site is trustworthy"}
  A phishing site can have a perfectly valid certificate for its own name. The
  padlock says "encrypted to whoever this is", not "this is safe".
  :::
::

Two kinds of encryption do the work, and interviewers like to hear both named:

- **Asymmetric encryption** uses a pair of keys: a **public key** anyone may
  have, and a **private key** only the server has. Something locked with one can
  be opened only with the other. It is slow, so TLS uses it only at the start,
  to prove identity and agree a secret.
- **Symmetric encryption** uses one shared key for both locking and unlocking.
  It is fast, so everything after the handshake uses it.

A **certificate** is the server's ID card: its public key, the names it is valid
for, an expiry date, and a signature from a **certificate authority** (CA), an
organisation your operating system and browser already trust.

## How it works

::flow{numbered direction="vertical" caption="The TLS 1.3 handshake, one round trip on top of TCP's. TLS 1.2 took two."}
  :::flow-step{label="Client hello" icon="i-lucide-hand"}
  The client lists the ciphers it supports, sends its half of the key exchange
  and, crucially, the hostname it wants. That name is how one IP address can
  serve certificates for many sites.
  :::
  :::flow-step{label="Server hello and certificate" icon="i-lucide-file-badge"}
  The server picks a cipher, sends its half of the key exchange and its
  certificate, and signs the exchange with its private key.
  :::
  :::flow-step{label="The client checks the certificate" icon="i-lucide-search-check" highlight}
  Three checks, and all must pass. Is the name in the certificate the name I
  asked for? Has it expired? Is it signed by an authority I trust, following the
  chain up to a root my system ships with?
  :::
  :::flow-step{label="Both derive the same symmetric key" icon="i-lucide-key"}
  From the two halves of the key exchange, both sides compute a shared key that
  an eavesdropper who recorded everything still cannot. From here on the
  conversation is fast symmetric encryption.
  :::
::

Look at a real certificate:

```bash [Terminal]
openssl s_client -connect github.com:443 -servername github.com < /dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text [Output]
subject=CN=github.com
issuer=C=US, O=DigiCert Inc, CN=DigiCert TLS Hybrid ECC SHA384 2020 CA1
notBefore=Feb 5 00:00:00 2026 GMT
notAfter=Mar 6 23:59:59 2027 GMT
```

Who it is for, who vouches for it, and the window it is valid in. Everything TLS
decides comes from those. (Dates change when the certificate is renewed.)

## Real use case

### The three errors, and what each one means

::compare{caption="All three say 'certificate problem'. They are different problems."}
  :::compare-side{label="Expired" verdict="wrong"}
  `certificate has expired`. The most common production TLS incident there is,
  and a calendar failure rather than a technical one. The fix is renewal and,
  more importantly, automated renewal plus an alert at thirty days.
  :::
  :::compare-side{label="Name mismatch" verdict="wrong"}
  `Hostname mismatch`. You asked for `api.college.edu` and the certificate is
  for `college.edu`. A wildcard covers one level only: `*.college.edu` covers
  `api.` and not `api.exams.college.edu`.
  :::
::

The third, **unable to verify / PKIX path building failed**, means the chain
could not be followed to a trusted root. Either the certificate is self-signed,
or, far more often, the server is not sending its **intermediate** certificate.
A browser may hide this by fetching the missing link; Java will not, which is why
a site that works in Chrome fails from your application.

A monitoring job that warns before expiry is one line:

```bash [check-cert.sh]
echo | openssl s_client -connect results.college.edu:443 2>/dev/null \
  | openssl x509 -noout -checkend 2592000 \
  || echo "ALERT: certificate expires within 30 days"
```

`-checkend` takes seconds (30 days is 2,592,000) and fails if the certificate
expires within that window.

::warning{icon="i-lucide-alert-triangle"}
Never "fix" a certificate error by turning verification off. `curl -k`,
`verify=False`, or a Java `TrustManager` that accepts everything all turn HTTPS
back into HTTP with a padlock drawn on it. It is a common suggestion in forum
answers, it removes the whole identity guarantee, and it has shipped to
production more times than anyone would like.
::

::real-life{title="What actually happens when a certificate expires" source="A Sunday morning"}
It does not degrade. At one second past midnight every client stops connecting
at once: browsers show a full-page warning, mobile apps fail, internal services
throw handshake exceptions. This is why certificate expiry is monitored like
disk space rather than remembered like a birthday.
::

## What confuses people here

- **"SSL" and "TLS".** SSL is the old name; every version of SSL is broken and
  retired. What runs today is TLS 1.2 or 1.3, and people still say "SSL
  certificate".
- **HTTPS does not hide which site you visited.** The name is visible during the
  handshake and in the DNS lookup before it. Your provider knows you went to
  `college.edu`, not which page you read.
- **The padlock is not a safety rating.** Certificates are free now, and most
  phishing sites have one.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between HTTP and HTTPS?" icon="i-lucide-message-circle"}
  HTTPS is HTTP sent inside a TLS connection, on port 443 instead of 80. TLS
  encrypts the traffic, proves the server's identity with a certificate, and
  detects tampering. Plain HTTP does none of the three.
  :::
  :::accordion-item{label="How does HTTPS work?" icon="i-lucide-message-circle"}
  After the TCP handshake, the client and server do a TLS handshake. The server
  presents a certificate signed by a trusted authority; the client checks the
  name, the expiry and the chain. Both use asymmetric key exchange to agree a
  shared secret, and everything after that is encrypted with fast symmetric
  encryption.
  :::
  :::accordion-item{label="Symmetric against asymmetric encryption?" icon="i-lucide-message-circle"}
  Symmetric uses one shared key to encrypt and decrypt; it is fast but both
  sides need the key. Asymmetric uses a public and a private key pair; it solves
  the key-sharing problem but is slow. TLS uses asymmetric to set up and
  symmetric for the data.
  :::
  :::accordion-item{label="What is a digital certificate and a certificate authority?" icon="i-lucide-message-circle"}
  A certificate binds a public key to a domain name, with an expiry date, and is
  signed by a certificate authority. A CA is an organisation whose root
  certificates ship with operating systems and browsers, so anything it signs
  can be trusted by following the chain.
  :::
  :::accordion-item{label="Does the padlock mean the site is safe?" icon="i-lucide-message-circle"}
  No. It means the connection is encrypted and the server controls that domain
  name. A phishing site can hold a valid certificate for its own look-alike name.
  :::
::
