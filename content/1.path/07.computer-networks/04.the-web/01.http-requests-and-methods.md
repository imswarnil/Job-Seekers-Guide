Bytes with no meaning, until both ends agree what they mean. **HTTP**
(HyperText Transfer Protocol) is that agreement, and it is plain text. Once you
have seen one raw request there is nothing mysterious left in it.

## Why this matters in a job

Every web and backend role is HTTP all day: the browser calls a server, the
server calls other services. In interviews, "difference between GET and POST",
"PUT against PATCH" and "what is idempotent?" come up constantly and have exact
answers. In my JSpiders web module in 2018 we learnt GET and POST as "one puts
data in the URL, one hides it". That is true and it is not the answer an
interviewer wants.

## A letter with a fixed format

A request is a letter with a subject line, some labelled details, a blank line,
and then the body. A response is the reply, same shape, with a result code at
the top.

```http [Request]
GET /api/students?department=CSE&year=2018 HTTP/1.1
Host: results.college.edu
Authorization: Bearer eyJhbGciOiJIUzI1...
Accept: application/json
User-Agent: Mozilla/5.0

```

::code-trace{caption="Four parts, and the blank line is load-bearing."}
```http [Request]
GET /api/students?department=CSE&year=2018 HTTP/1.1
Host: results.college.edu
Authorization: Bearer eyJhbGciOiJIUzI1...
Accept: application/json

(body would go here)
```

  :::code-trace-step{lines="1" caption="The request line: the method (what to do), the path (what to do it to), and the protocol version. The part after ? is the query string."}
  :::
  :::code-trace-step{lines="2" caption="Host. Mandatory since HTTP/1.1, and the reason one IP address can serve a thousand websites: the server reads it to know which site you meant."}
  :::
  :::code-trace-step{lines="3-4" caption="Headers. Who you are, what formats you can handle. Any number of them, one per line, as Name: value."}
  :::
  :::code-trace-step{lines="5-6" caption="A blank line, then the body. The blank line is how the server knows the headers ended. A GET has nothing after it."}
  :::
::

```http [Response]
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 1842
Cache-Control: max-age=60

[{"rollNo":"CS2018041","name":"Anita Rao","cgpa":7.8}, ...]
```

The headers you will meet most:

| Header | Direction | Says |
| --- | --- | --- |
| `Host` | Request | Which site on this server |
| `Content-Type` | Both | The format of the body: `application/json`, `text/html` |
| `Accept` | Request | Which formats the client can read |
| `Authorization` | Request | Proof of who you are, often `Bearer <token>` |
| `Cookie` / `Set-Cookie` | Request / Response | Small values the browser stores and sends back |
| `Cache-Control` | Response | Whether and how long a copy may be kept |
| `Location` | Response | Where a new resource is, or where to go instead |
| `User-Agent` | Request | Which browser or program is asking |

## How it works

Send one by hand, with no browser and no library. It makes the protocol concrete
forever.

```bash [Terminal]
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80 | head -5
```

```text [Output]
HTTP/1.1 200 OK
Content-Type: text/html
ETag: "84238dfc8092e5d9c0dac8ef93371a07:1736799080.121134"
Last-Modified: Mon, 13 Jan 2025 20:11:20 GMT
Cache-Control: max-age=3326
```

`\r\n` is a line ending, and the empty `\r\n\r\n` is the blank line. You have
spoken HTTP. (Illustrative output: the headers after the first line, and their
values, will differ when you run it.)

### The five methods

| Method | Meaning | Safe? | Idempotent? | Has a body? |
| --- | --- | --- | --- | --- |
| `GET` | Read something | Yes | Yes | No |
| `POST` | Create something new, or trigger an action | No | **No** | Yes |
| `PUT` | Replace the whole resource at a known address | No | Yes | Yes |
| `PATCH` | Change some fields of a resource | No | Not guaranteed | Yes |
| `DELETE` | Remove it | No | Yes | Usually no |

Two words decide most arguments, and they are not opinions:

- **Safe**: changes nothing on the server. `GET` (and `HEAD`, `OPTIONS`).
- **Idempotent**: doing it twice has the same effect as doing it once. `GET`,
  `PUT`, `DELETE`. Deleting a student twice leaves one deleted student.

```bash [Terminal]
curl -s https://jsonplaceholder.typicode.com/users/1 | head -4
curl -s -X POST https://jsonplaceholder.typicode.com/users \
     -H "Content-Type: application/json" -d '{"name":"Anita Rao"}'
```

```text [Output]
{
  "id": 1,
  "name": "Leanne Graham",
  "username": "Bret",
{
  "name": "Anita Rao",
  "id": 11
}
```

The `GET` read a record. The `POST` created one and got a new id back. (That
service is a free test API that pretends to save; the output is what it returns
today.)

## Real use case

A college API written the way a reviewer expects:

```text [routes.txt]
GET    /api/students                 list students (filter with ?department=CSE)
GET    /api/students/CS2018041       one student
POST   /api/students                 admit a new student; server assigns the roll number
PUT    /api/students/CS2018041       replace the whole record
PATCH  /api/students/CS2018041       change only the phone number
DELETE /api/students/CS2018041       remove the record
```

::compare{caption="Why idempotency is not academic."}
  :::compare-side{label="POST /fee-payments" verdict="wrong"}
  The network drops the response. The client retries. The student has now paid
  twice. POST is not idempotent, so a retry is a second action.
  :::
  :::compare-side{label="PUT /fee-payments/FEE-2018-00417" verdict="right"}
  The same retry replaces the same resource with the same content. Doing it five
  times leaves exactly one payment. The client chose the id, which is what makes
  it repeatable.
  :::
::

::side-note{kind="go-deeper"}
Real payment APIs make you send an **idempotency key** with a POST: a unique
string you generate, which the server remembers, so a retry with the same key
returns the original result instead of charging again. It is POST made
idempotent by hand, and it exists because "the request succeeded and the
response was lost" is a real and common event.
::

## What confuses people here

- **"GET is for reading, POST is for security."** POST data is not in the URL,
  so it does not show up in browser history or server logs by default, but it
  is still plain text without HTTPS. POST is not encryption.
- **"PUT updates, POST creates."** A rule of thumb that breaks quickly. The real
  difference is idempotency and who picks the address.
- **A GET that changes data** is a real and dangerous bug. Browsers prefetch
  links and crawlers follow them, so `GET /students/42/delete` will eventually
  be called by something that did not mean to.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between GET and POST?" icon="i-lucide-message-circle"}
  GET reads data, sends parameters in the URL, is safe and idempotent, and can
  be cached and bookmarked. POST sends data in the body, usually creates
  something or triggers an action, is neither safe nor idempotent, and is not
  cached. Neither is encrypted without HTTPS.
  :::
  :::accordion-item{label="PUT against PATCH?" icon="i-lucide-message-circle"}
  PUT replaces the whole resource with what you send, so fields you leave out
  are removed, and repeating it gives the same result. PATCH changes only the
  fields you send.
  :::
  :::accordion-item{label="What does idempotent mean? Which methods are idempotent?" icon="i-lucide-message-circle"}
  Making the same request several times has the same effect as making it once.
  GET, PUT, DELETE, HEAD and OPTIONS are idempotent. POST is not, and PATCH is
  not guaranteed to be.
  :::
  :::accordion-item{label="What is a safe method?" icon="i-lucide-message-circle"}
  One that does not change anything on the server: GET, HEAD and OPTIONS. Every
  safe method is idempotent, but not every idempotent method is safe (DELETE).
  :::
  :::accordion-item{label="What is the Host header for?" icon="i-lucide-message-circle"}
  It names the website being requested. Many sites can share one IP address, and
  the server reads Host to decide which one to serve. It has been mandatory since
  HTTP/1.1.
  :::
::
