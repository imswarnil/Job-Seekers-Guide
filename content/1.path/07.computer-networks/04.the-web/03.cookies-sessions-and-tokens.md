Every request arrives as a stranger. HTTP is **stateless**: the server keeps no
memory of the previous request, even from the same browser a second ago. Logging
in would be impossible without something extra, and that something is a cookie.

## Why this matters in a job

"HTTP is stateless, so how does login work?", "cookie against session" and
"session against token (JWT)" are standard web interview questions. At work,
every login bug, every "it logs me out randomly", and half of web security
(stolen sessions, cross-site attacks) lives here.

## The PG gate pass

The PG security guard does not remember faces. On your first day, the owner gives
you a gate pass with a number on it (the **cookie**). The owner's register maps
that number to your name, room and rent status (the **session**, kept on the
server). Every time you come back, you show the pass, and the guard looks the
number up.

A **token** is a different idea: instead of a number to look up, the pass itself
says "Swarnil, room 12, valid until March", with the owner's signature so it
cannot be forged. The guard checks the signature and needs no register.

::compare{caption="Two ways to remember a logged-in student."}
  :::compare-side{label="Session (state on the server)" verdict="neutral"}
  The cookie holds only a random id, `SESSIONID=7f3a...`. The server stores
  "7f3a belongs to CS2018041, logged in at 10:02". Logging out deletes the entry,
  which ends the session immediately. Needs shared storage when there are
  several servers.
  :::
  :::compare-side{label="Token (state on the client)" verdict="neutral"}
  The client holds a signed token (often a **JWT**, JSON Web Token) containing
  the roll number and an expiry. Any server can verify the signature without a
  lookup. Hard to revoke before it expires, so expiries are kept short.
  :::
::

## How it works

A **cookie** is a small name and value the server asks the browser to store
with the `Set-Cookie` header. The browser sends it back automatically, in a
`Cookie` header, on every later request to that site.

```http [First response, after login]
HTTP/1.1 302 Found
Location: /dashboard
Set-Cookie: SESSIONID=7f3a9c21e4; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

```http [Every request after that]
GET /dashboard HTTP/1.1
Host: portal.college.edu
Cookie: SESSIONID=7f3a9c21e4
```

Watch it with `curl`, which keeps cookies in a file (a "cookie jar") when asked:

```bash [Terminal]
curl -s https://httpbin.org/cookies
curl -s -i "https://httpbin.org/cookies/set?session=abc123" -c jar.txt | grep -i -E "^HTTP|set-cookie|location"
curl -s -b jar.txt https://httpbin.org/cookies
```

```text [Output]
{
  "cookies": {}
}
HTTP/2 302
location: /cookies
set-cookie: session=abc123; Path=/
{
  "cookies": {
    "session": "abc123"
  }
}
```

First request: no cookies, the server sees a stranger. Second: the server sets
one. Third: `curl` sends it back and the server recognises you. That is all a
browser does, automatically.

The flags on `Set-Cookie` matter:

| Flag | Does |
| --- | --- |
| `HttpOnly` | JavaScript on the page cannot read it, so an injected script cannot steal it |
| `Secure` | Sent only over HTTPS |
| `SameSite=Lax` or `Strict` | Not sent on most requests started by other sites, which blocks cross-site request forgery (CSRF) |
| `Max-Age` / `Expires` | When it expires. Without either it is a **session cookie**, gone when the browser closes |
| `Domain` / `Path` | Which addresses it is sent to |

## Real use case

In Java web applications (servlets, Spring), the session is built in. The
server creates the cookie for you (named `JSESSIONID`) the first time you touch
the session.

```java [LoginServlet.java]
protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
    Student student = auth.check(req.getParameter("rollNo"), req.getParameter("password"));
    if (student == null) {
        resp.sendError(401);
        return;
    }
    HttpSession session = req.getSession(true);   // creates JSESSIONID cookie
    session.setAttribute("rollNo", student.getRollNo());
    session.setMaxInactiveInterval(30 * 60);      // 30 minutes idle, then gone
    resp.sendRedirect("/dashboard");
}
```

```java [DashboardServlet.java]
protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
    HttpSession session = req.getSession(false);  // do not create one
    if (session == null) {
        resp.sendRedirect("/login");              // a stranger
        return;
    }
    String rollNo = (String) session.getAttribute("rollNo");
    resp.getWriter().println("Attendance for " + rollNo + ": 82%");
}
```

::real-life{title="Logged out at random, only in production" source="A college portal behind a load balancer"}
The portal worked on one server. In production there were three behind a load
balancer, and students were logged out every few clicks. Sessions lived in each
server's memory, so a request that landed on server B did not know about the
session created on server A. The fixes: keep sessions in a shared store such as
Redis, or make the load balancer send each user to the same server ("sticky
sessions"), or move to tokens. Knowing that HTTP is stateless is what makes the
cause obvious.
::

## What confuses people here

- **A cookie is not a session.** The cookie is the pass in your pocket; the
  session is the register entry on the server. A session usually uses a cookie
  to carry its id.
- **Cookies are not only for login.** Language preference, a cart, analytics.
  The browser sends them all, on every request to that site.
- **`localStorage` is not a cookie.** It stays in the browser and is never sent
  automatically; your JavaScript has to read it and put it in a header.
- **A JWT is signed, not encrypted.** Anyone holding it can decode and read the
  contents. Never put a password or a secret in one.

## Interview questions

::accordion
  :::accordion-item{label="HTTP is stateless. How does login work, then?" icon="i-lucide-message-circle"}
  After a successful login, the server gives the browser something to send back
  on every later request: a session id in a cookie (the server looks it up) or a
  signed token (the server verifies it). Each request proves who it is on its
  own.
  :::
  :::accordion-item{label="What is the difference between a cookie and a session?" icon="i-lucide-message-circle"}
  A cookie is data stored in the browser and sent with every request to its
  site. A session is data stored on the server about one user. They usually work
  together: the cookie carries the session id, the server holds the details.
  :::
  :::accordion-item{label="Session-based against token-based authentication?" icon="i-lucide-message-circle"}
  Sessions keep state on the server: easy to revoke, but every server must reach
  the same store. Tokens (JWTs) carry signed claims on the client: any server can
  verify them without a lookup, which scales easily, but they are hard to revoke
  before expiry, so they are kept short-lived.
  :::
  :::accordion-item{label="What do HttpOnly, Secure and SameSite do?" icon="i-lucide-message-circle"}
  HttpOnly stops JavaScript reading the cookie, which limits damage from
  cross-site scripting. Secure sends it only over HTTPS. SameSite stops it being
  sent on requests started by other sites, which blocks most cross-site request
  forgery.
  :::
  :::accordion-item{label="Session cookie against persistent cookie?" icon="i-lucide-message-circle"}
  A session cookie has no expiry and is deleted when the browser closes. A
  persistent cookie has Max-Age or Expires and survives restarts until then.
  "Remember me" on a login form sets a persistent one.
  :::
::
