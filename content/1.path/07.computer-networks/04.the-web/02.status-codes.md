Three digits at the top of every response, and the first digit alone answers
most of the question. The rest is knowing a dozen specific codes and, more
importantly, which of them get confused with each other.

## Why this matters in a job

"What does a 404 mean, a 500, a 403?" is a quick-fire fresher question, and the
401 against 403 pair is asked constantly because most people get it backwards.
At work, the status code is the first line of every incident: a wall of 502s
and a wall of 504s are two different emergencies.

## The five families

A hospital reception desk. **1xx**: "hold on, still processing". **2xx**: "here
you are". **3xx**: "not here, go to that counter". **4xx**: "your form is wrong,
fix it and come back". **5xx**: "our fault, the doctor is not available".

| Family | Means | Whose fault |
| --- | --- | --- |
| 1xx | Informational, keep going | Nobody's |
| 2xx | Success | |
| 3xx | Redirect, look elsewhere | |
| 4xx | Client error | **The request** |
| 5xx | Server error | **The server** |

The codes worth knowing by number:

| Code | Name | Means |
| --- | --- | --- |
| `200` | OK | Here it is |
| `201` | Created | Made it; the `Location` header says where. The right reply to a successful POST |
| `204` | No Content | Worked, nothing to send back. The usual reply to a DELETE |
| `301` | Moved Permanently | Use the new address from now on. Browsers cache this, sometimes for good |
| `302` | Found (temporary redirect) | Go there this time, keep using the old address |
| `304` | Not Modified | Your cached copy is still good. No body sent |
| `400` | Bad Request | Malformed, cannot be parsed |
| `401` | Unauthorized | **I do not know who you are.** Log in |
| `403` | Forbidden | **I know who you are, and you may not** |
| `404` | Not Found | No such thing |
| `405` | Method Not Allowed | That path exists, not with that method |
| `409` | Conflict | Clashes with the current state (a duplicate roll number) |
| `422` | Unprocessable Content | Parsed fine, failed validation (marks of 150 out of 100) |
| `429` | Too Many Requests | Slow down; `Retry-After` says for how long |
| `500` | Internal Server Error | An unhandled exception on the server |
| `502` | Bad Gateway | A proxy could not get a valid reply from the server behind it |
| `503` | Service Unavailable | Up, and refusing right now: overloaded or in maintenance |
| `504` | Gateway Timeout | A proxy waited for the server behind it and gave up |

## How it works

`curl -i` shows the status line and headers. `-o /dev/null -w "%{http_code}"`
prints only the code.

```bash [Terminal]
curl -s -o /dev/null -w "%{http_code}\n" https://api.github.com/users/imswarnil
curl -s -o /dev/null -w "%{http_code}\n" https://api.github.com/users/no-such-user-91723
curl -s -o /dev/null -w "%{http_code}\n" -X DELETE https://api.github.com/users/imswarnil
curl -sI http://github.com | head -3
```

```text [Output]
200
404
404
HTTP/1.1 301 Moved Permanently
Content-Length: 0
Location: https://github.com/
```

The third is interesting: deleting a user without logging in returns 404, not
401 or 403. GitHub hides whether something exists from people who are not
allowed to see it, which is a real security decision. The last one is the
`http://` address permanently redirecting to `https://`, with `Location` saying
where to go.

## Real use case

Returning the right code from a server is one of the visible signs of someone
who knows what they are doing. Here is a Java controller for admissions, with a
reason for every code.

```java [AdmissionController.java]
@PostMapping("/api/applications")
public ResponseEntity<?> apply(@RequestBody Application app, Principal user) {
    if (user == null)                                   // not logged in
        return ResponseEntity.status(401).build();
    if (app.getMarks() < 0 || app.getMarks() > 100)     // parsed, but invalid
        return ResponseEntity.status(422).body("marks must be 0-100");
    if (repo.existsByRollNo(app.getRollNo()))           // already applied
        return ResponseEntity.status(409).body("application exists");
    Application saved = repo.save(app);
    return ResponseEntity
        .created(URI.create("/api/applications/" + saved.getId()))  // 201 + Location
        .build();
}
```

::real-life{title="Why 502 and 504 are the two you will actually see" source="Every production incident"}
You almost never see your application's 500 directly, because there is a load
balancer or reverse proxy in front of it. When your app crashes, the proxy
cannot connect and you get **502**. When your app is alive but a query is taking
ninety seconds, the proxy gives up and you get **504**. Those two codes tell you
which it is before you open a single log.
::

## What confuses people here

- **401 is badly named.** "Unauthorized" actually means **unauthenticated**: we
  do not know who you are. 403 is the real "not authorised".
- **301 against 302.** 301 is permanent and cached by browsers; a wrong 301 can
  stick in users' browsers long after you fix it. Use 302 until you are sure.
- **A 404 is not a network failure.** The whole chain worked.
- **Returning 200 with an error message in the body** ("status": "failed") is
  common in older codebases and breaks every tool that reads status codes.

## Interview questions

::accordion
  :::accordion-item{label="What do the five status code families mean?" icon="i-lucide-message-circle"}
  1xx informational, 2xx success, 3xx redirection, 4xx client error (the request
  was wrong), 5xx server error (the server failed on a valid request).
  :::
  :::accordion-item{label="401 against 403?" icon="i-lucide-message-circle"}
  401 means the server does not know who you are: authenticate and try again.
  403 means it knows who you are and you are not allowed. A student opening the
  marks-entry page without logging in gets 401; logged in as a student, 403.
  :::
  :::accordion-item{label="301 against 302?" icon="i-lucide-message-circle"}
  301 is a permanent redirect: clients and search engines should use the new
  address, and browsers cache it. 302 is temporary: go there this time, keep the
  old address.
  :::
  :::accordion-item{label="500, 502, 503 and 504?" icon="i-lucide-message-circle"}
  500: the server itself hit an unhandled error. 502: a proxy got no valid reply
  from the server behind it (it is down or crashed). 503: the server is up but
  refusing, overloaded or in maintenance. 504: a proxy waited for the server
  behind it and timed out (it is alive but slow).
  :::
  :::accordion-item{label="Which status code should a successful POST return?" icon="i-lucide-message-circle"}
  201 Created, with a Location header pointing at the new resource. 200 is
  acceptable when the POST performs an action rather than creating something.
  :::
  :::accordion-item{label="What is 304 Not Modified?" icon="i-lucide-message-circle"}
  The client sent a conditional request ("I have the version with this ETag")
  and the server replies that it has not changed, with no body. The browser uses
  its cached copy. It saves bandwidth on every repeat visit.
  :::
::
