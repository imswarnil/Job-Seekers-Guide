Seven layers, then, with two of them you will never see in an error message.
The OSI model is a reference drawing made by a standards committee; the TCP/IP
model is what got built. You need both, because the written round asks for the
first and the technical round thinks in the second.

## Why this matters in a job

In a fresher written round, OSI questions are nearly free marks: "which layer
does a router work at", "which layer is responsible for encryption", "what is
the data unit at the transport layer". In the technical round, "explain the OSI
model" is often the first networking question, and the follow-up is almost
always "how does it map to TCP/IP?". At work nobody says "layer 5", but everybody
says "layer 4 load balancer" and "layer 7 load balancer", and you should know
what those mean.

## Two drawings of the same stack

Think of OSI as the full syllabus of a subject and TCP/IP as the chapters the
examiner actually sets questions from. Both describe the same journey. OSI
splits it into seven steps; TCP/IP merges some of those into four.

Remember the OSI layers bottom-up with a sentence: **P**lease **D**o **N**ot
**T**hrow **S**ausage **P**izza **A**way. Physical, Data link, Network,
Transport, Session, Presentation, Application.

| # | OSI layer | What it does | Data unit | Examples | TCP/IP layer |
| --- | --- | --- | --- | --- | --- |
| 7 | Application | What the user's program wants | Data | HTTP, DNS, SMTP, FTP | Application |
| 6 | Presentation | Format, encoding, encryption, compression | Data | TLS encryption, JPEG, UTF-8 | Application |
| 5 | Session | Opening, keeping and closing a conversation | Data | Session setup, RPC | Application |
| 4 | Transport | Which program, reliable or not, in order | **Segment** (TCP) / datagram (UDP) | TCP, UDP | Transport |
| 3 | Network | Which machine, and the route to it | **Packet** | IP, ICMP, routers | Internet |
| 2 | Data link | One hop to the next device on the same network | **Frame** | Ethernet, wifi, MAC addresses, switches | Network access (link) |
| 1 | Physical | Signals on the wire or in the air | **Bits** | Cables, radio, hubs, repeaters | Network access (link) |

  :::

Some books draw TCP/IP with five layers, splitting network access back into
data link and physical. Both are accepted in interviews. Say which one you mean.

## How it works

Follow one request for a student's marks down the sender's stack and up the
receiver's. Each layer adds its header on the way down (encapsulation) and
removes it on the way up.

::flow{numbered direction="vertical" caption="Down the sender, across the wire, up the receiver."}
  :::flow-step{label="Application (7)" icon="i-lucide-file-text"}
  The browser writes `GET /marks?roll=CS2018041 HTTP/1.1`.
  :::
  :::flow-step{label="Presentation (6)" icon="i-lucide-lock"}
  The text is encoded as UTF-8 bytes and, on HTTPS, encrypted by TLS.
  :::
  :::flow-step{label="Session (5)" icon="i-lucide-link"}
  The conversation is kept open so the next request can reuse it.
  :::
  :::flow-step{label="Transport (4)" icon="i-lucide-arrow-down-up" highlight}
  TCP cuts the bytes into **segments**, numbers them and adds source and
  destination ports.
  :::
  :::flow-step{label="Network (3)" icon="i-lucide-globe"}
  IP puts each segment in a **packet** with source and destination IP
  addresses.
  :::
  :::flow-step{label="Data link (2)" icon="i-lucide-network"}
  Each packet goes in a **frame** addressed to the next device's MAC address.
  :::
  :::flow-step{label="Physical (1)" icon="i-lucide-cable"}
  The frame becomes **bits**: voltages on copper, light in fibre, or radio.
  :::
::

Here is the same journey as a small program, so you can change the values and
watch the table change. It prints what each layer adds and what the result is
called, in the order the headers are added. (Layers 5 and 6 are left out because
on the internet they live inside the application.)

::runner{lang="javascript"}
```javascript
const request = "GET /marks?roll=CS2018041 HTTP/1.1";
const layers = [
  { osi: 7, name: "Application", adds: "the HTTP request itself", unit: "data" },
  { osi: 4, name: "Transport", adds: "ports 51514 -> 443, sequence number", unit: "segment" },
  { osi: 3, name: "Network", adds: "IP 192.168.1.23 -> 142.250.183.4", unit: "packet" },
  { osi: 2, name: "Data link", adds: "MAC 3c:22:fb:.. -> router's MAC", unit: "frame" },
  { osi: 1, name: "Physical", adds: "nothing, it becomes signals", unit: "bits" },
];
console.log("Payload:", request);
for (const l of layers) {
  console.log(`L${l.osi} ${l.name.padEnd(12)} adds ${l.adds.padEnd(40)} -> ${l.unit}`);
}
```
::

```text [Output]
Payload: GET /marks?roll=CS2018041 HTTP/1.1
L7 Application  adds the HTTP request itself                  -> data
L4 Transport    adds ports 51514 -> 443, sequence number      -> segment
L3 Network      adds IP 192.168.1.23 -> 142.250.183.4         -> packet
L2 Data link    adds MAC 3c:22:fb:.. -> router's MAC          -> frame
L1 Physical     adds nothing, it becomes signals              -> bits
```

## Real use case

"Layer 4" and "layer 7" are everyday words when you configure a load balancer,
the machine that spreads traffic over several servers.

```yaml [load-balancer.yaml]
# Layer 4: sees only IP addresses and ports. Fast, cannot read the request.
- name: results-db-proxy
  type: tcp
  listen: 5432
  targets: [10.0.4.12:5432, 10.0.4.13:5432]

# Layer 7: reads the HTTP request, so it can route by path.
- name: college-portal
  type: http
  listen: 443
  routes:
    - path: /admissions/*
      targets: [10.0.5.10:8080]
    - path: /results/*
      targets: [10.0.5.20:8080]
```

The layer 4 one cannot send `/results` somewhere different from `/admissions`,
because the path is inside the HTTP request and it never looks that far up. That
single fact is the whole difference, and it is exactly the OSI model in use.

## What confuses people here

That the session and presentation layers are separate pieces of software. On the
internet they are not. TLS does presentation-layer work (encryption) and HTTP
libraries do session-layer work (keeping connections open), but both live inside
the TCP/IP application layer. OSI is the vocabulary; TCP/IP is the
implementation.

The other trap is the data unit names. Segment belongs to transport, packet to
network, frame to data link, bits to physical. "Packet" gets used loosely for
everything in conversation, but not in an exam answer.

## Interview questions

::accordion
  :::accordion-item{label="Name the seven OSI layers and what each does." icon="i-lucide-message-circle"}
  Bottom-up: physical (bits on a medium), data link (one hop, frames, MAC
  addresses), network (routing packets between networks, IP), transport
  (end-to-end delivery and ports, TCP and UDP), session (managing
  conversations), presentation (encoding, encryption, compression), application
  (the protocols programs use: HTTP, DNS, SMTP).
  :::
  :::accordion-item{label="How does OSI map to TCP/IP?" icon="i-lucide-message-circle"}
  OSI 5, 6 and 7 become the TCP/IP application layer. OSI 4 is transport in
  both. OSI 3 is the internet layer. OSI 1 and 2 become network access (or
  link). OSI is a reference model; TCP/IP is what the internet is built on.
  :::
  :::accordion-item{label="What is the data unit at each layer?" icon="i-lucide-message-circle"}
  Bits at physical, frames at data link, packets at network, segments at
  transport for TCP (datagrams for UDP), and data or messages above that.
  :::
  :::accordion-item{label="At which layer do TLS, a router, a switch and HTTP work?" icon="i-lucide-message-circle"}
  TLS: presentation in OSI terms (application in TCP/IP). Router: network,
  layer 3. Switch: data link, layer 2. HTTP: application, layer 7.
  :::
  :::accordion-item{label="What is the difference between a layer 4 and a layer 7 load balancer?" icon="i-lucide-message-circle"}
  A layer 4 balancer sees only IP addresses and ports and forwards connections
  without reading them. A layer 7 balancer reads the HTTP request, so it can
  route by path, header or cookie, at the cost of more work per request.
  :::
::
