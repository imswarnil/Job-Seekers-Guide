One machine, understood completely. Now add a second one and a problem appears
that never existed inside a single computer: the thing in between is
unreliable, and it does not care about you. Layers are how that is made
survivable.

## Why this matters in a job

Because every network error you will ever read is a layer complaining. Once you
can place the error in a layer, you have eliminated three quarters of the
possible causes before opening anything. And in the interview, "explain the OSI
model" is the opening networking question at almost every service company.

::compare{caption="Four errors. Read them as layers and each one names its own suspect."}
  :::compare-side{label="What a beginner sees" verdict="wrong"}
  `Connection refused`, `Name or service not known`, `Connection timed out`,
  `404 Not Found`. Four ways of saying "the network is broken", all equally
  mysterious, all leading to the same reflex of restarting things.
  :::
  :::compare-side{label="What they actually say" verdict="right"}
  `Name or service not known` → **DNS**: the name never became a number.
  `Connection refused` → **the machine was reached** and nothing is listening on
  that port. `Connection timed out` → the packets went out and nothing came
  back; a firewall or a dead machine. `404` → everything worked perfectly and
  the *application* says there is no such thing.
  :::
::

That last one matters most. A 404 means the network succeeded. People restart
servers over 404s constantly.

## A stack of fixes

Think of posting a letter from Bangalore to your college in Bhopal. You write
the letter (what you want to say). You put it in an envelope with the
department's name on it (who inside the college should get it). The post office
adds a PIN code (which city, which office). A van carries the bag to the next
sorting centre (one hop). Nobody in that chain needs to understand the others'
jobs. The van driver never reads your letter.

A network is built the same way. The model used in practice has four layers.
The seven-layer OSI model, which your syllabus examines, comes in the next
lesson.

Read it bottom-up and each layer is a fix for the one beneath it.

::flow{numbered direction="vertical" caption="Bottom to top. Every layer is a complaint about the one beneath it."}
  :::flow-step{label="Link: I can reach the next device" icon="i-lucide-cable"}
  Wifi or a cable gets bits to your router. That is all it can do. **Problem it
  leaves:** the machine you want is nine hops away and the link layer has never
  heard of it.
  :::
  :::flow-step{label="Internet: I can reach any machine" icon="i-lucide-globe"}
  IP gives every machine an address and every router a rule for which way to
  pass a packet. **Problems it leaves:** packets can be lost, duplicated,
  reordered, and there is no way to say which program on that machine.
  :::
  :::flow-step{label="Transport: every byte, in order, to the right program" icon="i-lucide-arrow-down-up" highlight}
  TCP numbers the bytes, acknowledges them, resends the lost ones and puts them
  back in order; ports say which program. **Problem it leaves:** you now have a
  reliable stream of bytes and no agreement about what they mean.
  :::
  :::flow-step{label="Application: we both know what the bytes mean" icon="i-lucide-message-square"}
  HTTP says the first line is a method and a path, then headers, then a blank
  line, then a body. Both ends agree, so the bytes become a request.
  :::
::

## How it works

Your request does not travel alone. Each layer adds a header in front of it,
like envelopes inside envelopes. This is called **encapsulation**: wrapping the
data from the layer above in your own header. The receiving machine unwraps
them in reverse.

You can watch three of the four layers announce themselves with one command.
`curl -v` makes a request and narrates each step.

```bash [Terminal]
curl -v http://example.com/ -o /dev/null
```

```text [Output]
*   Trying 93.184.215.14:80...
* Connected to example.com (93.184.215.14) port 80
> GET / HTTP/1.1
> Host: example.com
> User-Agent: curl/8.7.1
> Accept: */*
>
< HTTP/1.1 200 OK
< Content-Type: text/html; charset=UTF-8
< Content-Length: 1256
```

The address `93.184.215.14` is the internet layer (which machine). `port 80`
and "Connected" are the transport layer (which program, and a connection made).
The lines starting `>` and `<` are the application layer (the request and the
reply). The link layer is your wifi, and it stays silent unless it breaks. The
exact address and version numbers will differ on your machine.

## Real use case

At work the layers are a debugging order. Here is what a Java service prints
when it cannot reach a database, and how the layer tells you where to look.

```java [ResultsRepository.java]
try (Connection c = DriverManager.getConnection(
        "jdbc:postgresql://db.college.internal:5432/results", user, password)) {
    // ...
} catch (SQLException e) {
    // The cause tells you the layer:
    // UnknownHostException   -> DNS (application layer): check the name
    // ConnectException       -> transport: machine reached, nothing on 5432
    // SocketTimeoutException -> transport: packets leave, nothing comes back
    log.error("Could not reach the results database", e);
}
```

::real-life{title="Why this saves you an afternoon" source="A service that could not reach a database"}
Our application could not connect to the database. The error was
`Connection timed out`. Because that is a *transport* error rather than a DNS
one, we knew the name had resolved, so it was not DNS; and because it timed out
rather than being refused, we knew the packets were leaving and nothing was
coming back, which means something is silently dropping them rather than the
database being down. It was a firewall rule. Ten minutes, because the error
named its own layer.
::

## What confuses people here

That layers are a diagram in a textbook. They are the actual implementation: TCP
is code in your operating system's kernel, IP is code in your kernel and in
every router between here and there, and HTTP is a library in your program.
When people say "somewhere in the network", they usually mean they have not
decided which of these is the suspect.

## Your turn

For each error, name the layer and say what you would check first.

1. `java.net.UnknownHostException: db.college.internal`
2. `java.net.ConnectException: Connection refused`
3. `java.net.SocketTimeoutException: Read timed out`
4. `HTTP 503 Service Unavailable`
5. `javax.net.ssl.SSLHandshakeException: PKIX path building failed`

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  1. **Application layer, DNS.** The name never became an address. Check the
     spelling, then whether this machine can resolve it at all with `nslookup`.
     Nothing has been sent to any database.
  2. **Transport.** The machine was reached and actively said no, which means
     nothing is listening on that port. A refusal is good news: everything below
     worked.
  3. **Transport.** The connection was established and then the other end went
     quiet. Usually a slow query or an overloaded server.
  4. **Application.** The whole network worked. The server is up and telling
     you it cannot serve right now.
  5. **TLS, between transport and application.** The connection was made and
     the certificate could not be trusted. The web chapter covers it.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="Why is the network divided into layers?" icon="i-lucide-message-circle"}
  So each layer solves one problem and can change without the others knowing.
  Wifi can replace Ethernet without HTTP changing, because HTTP never talks to
  the link layer. The answer that impresses explains each layer as a fix for the
  one below: link reaches the next device, IP reaches any machine, TCP makes
  delivery reliable and picks the program, HTTP gives the bytes meaning.
  :::
  :::accordion-item{label="What is encapsulation in networking?" icon="i-lucide-message-circle"}
  Each layer wraps the data from the layer above in its own header before
  passing it down. An HTTP request goes inside a TCP segment, inside an IP
  packet, inside an Ethernet frame. The receiver removes the headers in reverse
  order, which is called decapsulation.
  :::
  :::accordion-item{label="Connection refused against connection timed out: what is the difference?" icon="i-lucide-message-circle"}
  Refused means the machine was reached and replied that nothing is listening on
  that port. Timed out means no reply came back at all, usually a firewall
  silently dropping packets or a machine that is down. Refused is better news,
  because everything up to the transport layer worked.
  :::
  :::accordion-item{label="A page returns 404. Is the network broken?" icon="i-lucide-message-circle"}
  No. A 404 is an application-layer answer, which means DNS, TCP and HTTP all
  worked and the server replied that the path does not exist. Restarting the
  network cannot fix it.
  :::
::
