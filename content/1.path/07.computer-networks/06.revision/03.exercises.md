Thirty-four answers you could give. This is the part nobody does, and it is the
difference between saying "I would check DNS first" as a thing you read and as a
thing you have done. Attempt each set before opening the answers.

## Why this matters in a job

The written round gives you about a minute per question and no calculator.
Subnetting and "which layer" questions are free marks only if your hands already
know the method. The commands matter for the technical round: an interviewer can
hear the difference between a candidate who has run `dig` and one who has read
about it.

## Set 1: subnetting by hand

No runner, no calculator. Paper and the block-size table.

1. A lab machine has `10.1.1.200/26`. Give the mask, network address, broadcast
   address, first and last usable host, and the number of usable hosts.
2. The college has `192.168.20.0/24` and needs four department subnets with at
   least 50 machines each. What prefix do you use, and what are the four
   subnets?
3. Are `172.16.4.10/22` and `172.16.7.200/22` on the same subnet?
4. How many usable hosts does a /30 have, and what is it typically used for?
5. Which of these are private: `172.20.1.5`, `172.32.1.5`, `192.169.1.1`,
   `10.255.0.1`?

::accordion
  :::accordion-item{label="Answers, set 1" icon="i-lucide-check"}
  1. /26: 6 host bits, block 64, mask **255.255.255.192**. Blocks start at 0, 64,
     128, 192; 200 is in the 192 block. Network **10.1.1.192**, broadcast
     **10.1.1.255**, hosts **.193 to .254**, **62** usable.
  2. 50 machines need 6 host bits (62 usable; 5 bits gives only 30). 32 − 6 =
     **/26**. Subnets: **192.168.20.0/26, .64/26, .128/26, .192/26**. Exactly
     four, with nothing left over.
  3. /22 leaves 2 host bits in the third octet, so the third octet moves in
     blocks of 4: 0, 4, 8. Both 4 and 7 are in the 4 to 7 block. **Yes**: network
     172.16.4.0, broadcast 172.16.7.255.
  4. 4 addresses, **2** usable. Used for a link between two routers, where only
     two addresses are needed.
  5. `172.20.1.5` (inside 172.16 to 172.31) and `10.255.0.1` are private.
     `172.32.1.5` and `192.169.1.1` are public: both sit a step outside the ranges,
     which is exactly why they appear in exam options.
  :::
::

## Set 2: which status code?

A college admissions API. Pick the code for each, and say why in one line.

1. A student fetches their application and it is returned.
2. A new application is created.
3. A student who is not logged in opens `/api/marks`.
4. A logged-in student tries to open the marks-entry page meant for faculty.
5. The application form is submitted with marks of 150 out of 100.
6. The same roll number applies a second time.
7. The request body is not valid JSON at all.
8. An old URL `/admission-form` has moved to `/apply` for good.
9. The application server has crashed and the load balancer cannot reach it.
10. The server is alive, but a report query takes 90 seconds and the load
    balancer gives up.
11. A student refreshes the page and their cached copy is still current.
12. A script hits the results API 500 times in a minute.

::accordion
  :::accordion-item{label="Answers, set 2" icon="i-lucide-check"}
  1. **200 OK**.
  2. **201 Created**, with a `Location` header.
  3. **401 Unauthorized**: we do not know who they are.
  4. **403 Forbidden**: we know who they are, and they may not.
  5. **422 Unprocessable Content**: it parsed, it failed a rule. (400 is also
     commonly accepted; say why you chose one.)
  6. **409 Conflict**: it clashes with an existing application.
  7. **400 Bad Request**: it cannot even be parsed.
  8. **301 Moved Permanently**.
  9. **502 Bad Gateway**.
  10. **504 Gateway Timeout**.
  11. **304 Not Modified**.
  12. **429 Too Many Requests**, with `Retry-After`.
  :::
::

## Set 3: name the layer

For each, name the OSI layer and one thing you would check.

1. `java.net.UnknownHostException: results.college.edu`
2. The wifi icon shows no connection at all.
3. Two laptops on the same switch can talk; neither reaches the internet.
4. `SSLHandshakeException: certificate expired`
5. `Connection refused` on port 5432.

::accordion
  :::accordion-item{label="Answers, set 3" icon="i-lucide-check"}
  1. **Application (DNS).** Check the name with `nslookup`.
  2. **Physical / data link.** Check the radio, the password, the access point.
  3. **Network.** The default gateway is missing or wrong, or the router is
     down. Check `netstat -rn` (or `ip route`) for a default route.
  4. **Presentation in OSI terms (TLS).** Check the certificate dates with
     `openssl`.
  5. **Transport.** The machine is reachable and nothing listens on 5432. Is the
     database running, and on that port?
  :::
::

## Set 4: run it yourself

Every one of these is real and takes under a minute.

```bash [Terminal]
# 1. DNS: the answer and its TTL, then the whole chain from the root
dig github.com +noall +answer
dig github.com +trace | tail -20

# 2. Split a request into phases
curl -o /dev/null -s -w "dns %{time_namelookup}s  connect %{time_connect}s  tls %{time_appconnect}s  first byte %{time_starttransfer}s  total %{time_total}s\n" https://github.com

# 3. HTTP is text: > is what you sent, < is what came back
curl -v https://example.com -o /dev/null 2>&1 | grep -E "^[<>]"

# 4. Read a certificate
openssl s_client -connect github.com:443 -servername github.com < /dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# 5. Your addresses: private IP, MAC, gateway, and what the world sees
ifconfig en0 | grep -E "ether|inet "        # Linux: ip addr   Windows: ipconfig /all
netstat -rn -f inet | grep default          # Linux: ip route
curl -s https://api.ipify.org; echo

# 6. Who is holding a port
lsof -i :8080                               # Windows: netstat -ano | findstr :8080

# 7. Every router on the way
traceroute github.com                       # Windows: tracert github.com
```

::accordion
  :::accordion-item{label="What to look for in each" icon="i-lucide-check"}
  1. The number after the name is the TTL in seconds. Run it twice and watch it
     count down: proof the answer is cached. `+trace` shows root, then `.com`,
     then GitHub's own servers.
  2. Run it twice. `dns` drops to almost zero the second time. `connect` minus
     `dns` is the TCP handshake; `tls` minus `connect` is TLS.
  3. The request is a handful of lines of text. That is the whole protocol.
  4. Subject, issuer, validity dates. Every TLS decision comes from these.
  5. The `inet` address is private; the `ipify` one is public. The difference is
     NAT.
  6. "Port already in use" is the most common first-week error. Finding the PID
     and stopping it beats restarting the laptop.
  7. The first hop is your router, the second your provider. Rows of `* * *` are
     routers that do not answer this probe, which is normal.
  :::
::

## Real use case

At work these exercises come back as one question in a chat message: "the
results portal is down, can you check?". The order you check in is this track in
reverse: does the name resolve (`dig`), is the port open (`nc -zv host 443`), does
TLS complete (`openssl s_client`), what status comes back (`curl -I`).

```bash [check-portal.sh]
host=results.college.edu
dig +short "$host"                                   || echo "DNS failed"
nc -zv -w 3 "$host" 443                              || echo "port 443 not reachable"
curl -s -o /dev/null -w "HTTP %{http_code}\n" "https://$host/"
```

Four lines, and whichever one fails names the layer.

## The cheat-sheet

| Command | What it does |
| --- | --- |
| `ping <host>` | Is it reachable, and the round-trip time |
| `traceroute <host>` / `tracert` | Every router along the path |
| `nslookup <name>` | Resolve a name (works on every system) |
| `dig <name>` | Resolve a name, with the TTL |
| `dig <name> +trace` | Walk DNS from the root |
| `ifconfig` / `ip addr` / `ipconfig` | Your IP and MAC addresses |
| `netstat -rn` / `ip route` | Your routing table and default gateway |
| `arp -a` | Your ARP cache: IP to MAC |
| `curl -v <url>` | A request with every phase narrated |
| `curl -I <url>` | Only the status line and headers |
| `curl -w "%{time_total}"` | Time the phases of a request |
| `openssl s_client -connect host:443` | Inspect a TLS certificate |
| `nc -zv <host> <port>` | Is that port open |
| `lsof -i :<port>` | Which process holds a port |

## Interview questions

::accordion
  :::accordion-item{label="How would you check whether a server is reachable and a service is running on it?" icon="i-lucide-message-circle"}
  `ping` for reachability (though some servers block it), then `nc -zv host
  port` or `telnet host port` to see whether the service is listening. A machine
  that answers ping and refuses the port is running; the program is not.
  :::
  :::accordion-item{label="How would you find your machine's IP address and default gateway?" icon="i-lucide-message-circle"}
  `ipconfig` on Windows, `ifconfig` or `ip addr` on macOS and Linux for the
  address, and `ip route` or `netstat -rn` for the default gateway.
  :::
  :::accordion-item{label="What does traceroute show, and how does it work?" icon="i-lucide-message-circle"}
  Every router on the path, with the round-trip time to each. It sends packets
  with a time-to-live of 1, 2, 3 and so on; each router that decrements it to
  zero sends back an error, which reveals that router's address.
  :::
::
