Your request succeeded perfectly and the reply never came back. This is the
failure that separates code that works from code that works in production, and
almost nobody meets it until it has already cost them something.

## Why this matters in a job

Every client you write calls something that can be slow, and the default
behaviour of most libraries, wait forever, is the worst available choice. In
interviews, "how do you handle a call to another service failing?" is a common
second-round question for anyone with even a year of experience, and a fresher
who answers it well stands out.

## Three things a timeout could mean

You send a fee payment by courier and the receipt never arrives. Did the courier
lose the envelope? Did the college receive it, bank the money, and the receipt
got lost? Is it still sitting in a queue? From your side, all three look
identical.

So the rule is narrow and it follows from the methods lesson:

::pull-quote
Retry anything idempotent, freely. Never blindly retry anything that is not.
::

`GET`, `PUT` and `DELETE` are safe to repeat. `POST` is not, unless you have made
it safe with an idempotency key the server remembers.

There are also **two** timeouts, and most people set neither.

::compare{caption="Two settings, two completely different failures."}
  :::compare-side{label="Connect timeout" verdict="neutral"}
  How long to wait for the TCP handshake. Should be **short**: a second or two.
  If a machine has not answered a SYN in two seconds it is not going to; it is
  down, or a firewall is dropping packets silently.
  :::
  :::compare-side{label="Read timeout" verdict="neutral"}
  How long to wait for a response after connecting. Depends on what you are
  calling: a fast API, two or three seconds; a report that legitimately takes
  thirty, thirty.
  :::
::

## How it works

Both timeouts set, and a retry with exponential backoff, jitter and a ceiling.
This one calls a public test endpoint that always answers 503, so you can watch
the waits grow.

```java [AttendanceClient.java]
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import java.util.concurrent.ThreadLocalRandom;

public class AttendanceClient {
    public static void main(String[] args) throws Exception {
        HttpClient client = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(2))       // it answers fast or it is down
            .build();
        HttpRequest request = HttpRequest.newBuilder()
            .uri(URI.create("https://httpbin.org/status/503"))
            .timeout(Duration.ofSeconds(5))              // read timeout for this call
            .GET()                                       // GET: safe to retry
            .build();

        for (int attempt = 1; attempt <= 3; attempt++) {             // a ceiling, always
            int status = client.send(request, HttpResponse.BodyHandlers.discarding()).statusCode();
            System.out.println("attempt " + attempt + ": " + status);
            if (status < 500) return;                                // done, or not retryable
            if (attempt == 3) break;
            long base = 200L * (1L << (attempt - 1));                // 200, 400 ms
            long wait = base + ThreadLocalRandom.current().nextLong(base / 2);  // jitter
            System.out.println("  waiting " + wait + " ms");
            Thread.sleep(wait);
        }
        System.out.println("giving up: show the user an error, do not show an empty list");
    }
}
```

```text [Output]
attempt 1: 503
  waiting 243 ms
attempt 2: 503
  waiting 517 ms
attempt 3: 503
giving up: show the user an error, do not show an empty list
```

The waits are random within a range, so yours will differ.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-trending-up" title="Backoff: wait longer each time"}
  If the server is overloaded, retrying immediately makes it worse. Doubling the
  wait gives it room to recover.
  :::
  :::feature{icon="i-lucide-shuffle" title="Jitter: randomise the wait"}
  Without it, a thousand clients that failed together retry together, in a
  synchronised wave. A real and famous failure mode.
  :::
  :::feature{icon="i-lucide-octagon-x" title="A ceiling: give up"}
  Three attempts, not "until it works". Retrying forever converts a brief outage
  into a permanent one by keeping the load on.
  :::
  :::feature{icon="i-lucide-shield" title="A circuit breaker, eventually"}
  After enough consecutive failures, stop calling for a while and fail fast.
  Better to answer "unavailable" in one millisecond than wait five seconds to
  learn the same thing.
  :::
::

## Real use case

::real-life{title="How one slow database took down a website that did not use it" source="A results portal"}
A reporting query started taking ninety seconds. The report page had no timeout,
so its threads waited. The thread pool filled with threads waiting on that one
query. New requests for *every other page* queued behind them, and the whole
site went down, including the student login that never touched that database.
The root cause was one slow query; the outage was caused by an absent timeout.
::

::warning{icon="i-lucide-alert-triangle"}
A timeout you have not set is not "no timeout". It is the operating system's,
which on Linux can be over two minutes for a connect. Two minutes is long enough
for your whole thread pool to fill.
::

For a payment, the safe design is to make the retry idempotent:

```http [Request]
POST /api/fee-payments HTTP/1.1
Host: fees.college.edu
Idempotency-Key: 6c1e7a0e-7b1d-4b4e-9a53-CS2018041-sem6
Content-Type: application/json

{"rollNo":"CS2018041","amount":42500}
```

The server stores the key with the result. A retry with the same key gets the
first result back instead of a second charge.

## What confuses people here

That retrying is always the right answer. A **retry storm** is a genuine cause of
outages: the dependency has a brief problem, every client retries three times,
the dependency now has four times the load, and it stays down. Backoff, jitter
and a ceiling are what make a retry helpful rather than an attack.

## Your turn

For each, say which timeouts you would set, whether it is safe to retry, and
what you do after the last attempt fails.

1. `GET /api/students?department=CSE`: a list for a screen, normally 200 ms.
2. `POST /api/fee-payments`: takes a payment.
3. `POST /api/reports/results`: generates a PDF, legitimately takes 45 seconds.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** Connect 2 s, read 3 s. Safe to retry, it is a GET. After three
  failures, show an error with a retry button: an empty list and a failed call
  must never look the same.

  **2.** Connect 2 s, read 10 s. **Not safe to retry** as written. Send an
  idempotency key the server records, or on timeout do not retry: look the
  payment up by that key and act on what you find. Charging twice is far worse
  than asking somebody to check.

  **3.** This is the wrong shape. A 45-second request holds a connection and a
  thread the whole time and dies to any proxy timeout in between. Better: the
  POST returns `202 Accepted` with a job id at once, and the client checks back.
  :::
::

## Interview questions

::accordion
  :::accordion-item{label="What happens if your payment API call times out?" icon="i-lucide-message-circle"}
  You do not know whether the payment went through, so you must not blindly
  retry. Either the request carries an idempotency key so a retry is safe, or you
  query the payment's status by a known reference before deciding.
  :::
  :::accordion-item{label="Connect timeout against read timeout?" icon="i-lucide-message-circle"}
  Connect timeout limits the wait for the TCP handshake; keep it short, a second
  or two. Read timeout limits the wait for the response after connecting; set it
  from how long that endpoint normally takes.
  :::
  :::accordion-item{label="What is exponential backoff, and why add jitter?" icon="i-lucide-message-circle"}
  Waiting longer after each failure (200 ms, 400 ms, 800 ms) so a struggling
  server gets room to recover. Jitter randomises each wait so that many clients
  that failed together do not all retry at the same instant.
  :::
  :::accordion-item{label="What is a circuit breaker?" icon="i-lucide-message-circle"}
  A wrapper that counts failures to a dependency and, past a threshold, stops
  calling it for a while and fails immediately. After a pause it lets a trial
  request through to see whether the dependency has recovered.
  :::
::
