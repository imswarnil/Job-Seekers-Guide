Every piece is on the table now. This lesson puts them in order. The question is
asked constantly because it has no bottom: you can answer it in thirty seconds
or in forty minutes, and how far you go shows exactly how deep you are.

## Why this matters in a job

"What happens when you type google.com in the browser and press Enter?" is the
networking question in fresher technical rounds, at service companies and
product companies alike. It is really five questions at once (DNS, TCP, TLS,
HTTP, rendering), so one good preparation answers all five. At work, the same
sequence is your debugging checklist when a page does not load.

## One trip, ten stops

A courier from a Bangalore PG to your college office in Bhopal. Find the address
(DNS). Confirm the office is open and accepting parcels (TCP). Seal it so nobody
on the way can open it, and check the office's ID at the door (TLS). Hand over
the request form (HTTP). The clerk fetches the file (the application and its
database). The reply comes back, and you open it and read it (rendering).

### The thirty-second version

For when it is an opening question and they want to move on.

> The browser resolves the domain name to an IP address through DNS, opens a TCP
> connection to that address on port 443, and negotiates TLS so the connection is
> encrypted and the server's identity is verified. Then it sends an HTTP GET
> request. The server runs its application code, probably queries a database, and
> returns HTML. The browser parses that, requests the stylesheets, scripts and
> images it refers to, and renders the page.

Six sentences, correct, complete in outline. If they want more they will ask,
and now the conversation is on ground you chose.

## How it works

The four-minute version, step by step.

::flow{numbered direction="vertical" caption="Ten steps. Each one is a lesson in this track."}
  :::flow-step{label="The browser parses the URL" icon="i-lucide-link"}
  Scheme, host, port, path, query. `https://results.college.edu/marks?roll=CS2018041`
  means port 443 by default. If what you typed is not a URL, it becomes a search.
  :::
  :::flow-step{label="DNS resolution" icon="i-lucide-search"}
  Browser cache, then the operating system, then the hosts file, then the
  recursive resolver, then root → `.edu` → the authoritative server. Answers are
  cached for their TTL.
  :::
  :::flow-step{label="ARP and the first hop" icon="i-lucide-network"}
  The server is not on your network, so the laptop sends to its default gateway,
  using ARP to find the router's MAC. NAT at the router swaps in the public
  address.
  :::
  :::flow-step{label="TCP handshake" icon="i-lucide-handshake"}
  SYN, SYN-ACK, ACK. One full round trip before any data.
  :::
  :::flow-step{label="TLS handshake" icon="i-lucide-lock"}
  The server presents a certificate; the client checks the name, the expiry and
  the chain, and both derive a shared key. One more round trip in TLS 1.3.
  :::
  :::flow-step{label="The HTTP request" icon="i-lucide-send"}
  `GET /marks?roll=CS2018041`, with `Host`, cookies (your session) and `Accept`.
  :::
  :::flow-step{label="A proxy or load balancer first" icon="i-lucide-shuffle"}
  Almost never straight to the application. A load balancer often ends TLS and
  picks one of several application servers. This is why you see 502 and 504.
  :::
  :::flow-step{label="The application runs" icon="i-lucide-server" highlight}
  Routing, checking the session, checking permission, then the work: usually a
  database query. The DBMS and SQL you have already studied live in this step.
  :::
  :::flow-step{label="The response comes back" icon="i-lucide-download"}
  Status line, headers, body. `Cache-Control` decides whether the browser even
  asks next time.
  :::
  :::flow-step{label="The browser parses, fetches more, renders" icon="i-lucide-monitor"}
  HTML becomes a tree of elements (the DOM), CSS becomes style rules, and every
  stylesheet, script, font and image is another request. Then layout, paint, and
  JavaScript runs.
  :::
::

Watch most of it happen in one command. `curl -v` narrates DNS, TCP, TLS and
HTTP in order.

```bash [Terminal]
curl -v https://github.com -o /dev/null 2>&1 | grep -E "^\*   Trying|Connected|SSL connection|subject:|^> GET|^< HTTP"
```

```text [Output]
*   Trying 140.82.121.4:443...
* Connected to github.com (140.82.121.4) port 443
* SSL connection using TLSv1.3 / AEAD-AES128-GCM-SHA256 / [blank] / UNDEF
*  subject: CN=github.com
> GET / HTTP/2
< HTTP/2 200
```

Trying is DNS done, Connected is the TCP handshake, the SSL line and subject
are TLS, and the last two are HTTP. (Illustrative; the address and cipher will
differ on your machine.)

## Real use case

What separates candidates once they are past four minutes is **naming what can
go wrong at each step**, because the question is really asking: have you ever
debugged this? The same table is what you walk through at work when "the site is
down".

| Step | What breaks | What you see |
| --- | --- | --- |
| DNS | Record missing, stale cache, resolver down | `UnknownHostException`, or the old server keeps answering |
| TCP | Nothing listening | `Connection refused`: the machine was reached |
| TCP | Firewall dropping silently | `Connection timed out`: packets leave, nothing returns |
| TLS | Expired, wrong name, missing intermediate | Handshake failure; the intermediate case works in a browser and fails from Java |
| Proxy → app | The application is down | `502 Bad Gateway` |
| Proxy → app | The application is slow | `504 Gateway Timeout` |
| Application | Unhandled exception | `500`, and a stack trace in a log |
| Application | Not logged in, or not allowed | `401` against `403` |
| Response | Wrong `Cache-Control` | A change is deployed and users still see the old page |

::real-life{title="What an interviewer is actually listening for" source="Interviews I have sat on"}
Not the number of steps. The moment somebody says "and if that step fails you see
this specific error" is the moment their answer stops sounding like a blog post
they read. One well-chosen failure is worth four extra steps of detail.
::

## What confuses people here

- **Starting at "the browser makes a request".** That skips DNS and the
  handshakes, the two most interesting parts.
- **Forgetting that one URL is dozens of requests.** The HTML is only the first;
  every image, stylesheet and script is another.
- **Wandering.** Jumping back to DNS caching after you reached rendering reads
  as reconstruction. Go in order, then stop, and let them choose where to dig.

## Interview questions

::accordion
  :::accordion-item{label="What happens when you type a URL and press Enter?" icon="i-lucide-message-circle"}
  Give the thirty-second version: DNS, TCP, TLS, HTTP request, server work,
  response, rendering. Then offer depth instead of taking it: "I can go deeper
  on any of those; DNS caching and the handshake cost are the interesting parts."
  That hands them the steering wheel.
  :::
  :::accordion-item{label="Which protocols are involved, at which layers?" icon="i-lucide-message-circle"}
  DNS (application, usually over UDP), ARP (link), IP (network), TCP
  (transport), TLS (presentation in OSI terms), HTTP (application).
  :::
  :::accordion-item{label="Where can caching happen along the way?" icon="i-lucide-message-circle"}
  DNS answers in the browser, operating system and resolver; TCP and TLS
  connections reused with keep-alive; HTTP responses in the browser cache (304
  Not Modified); and content delivery networks close to the user.
  :::
  :::accordion-item{label="The page loads slowly. Where do you start?" icon="i-lucide-message-circle"}
  Split the time into phases: DNS, connect, TLS, time to first byte, download.
  `curl -w` or the browser's network tab shows them. A large time to first byte
  points at the server or database; large connect and TLS times point at
  distance and missing connection reuse.
  :::
::
