The network has no idea what names are. It moves packets between numbers. So
before anything else can happen, `lnct.ac.in` has to become an IP address, and
the system that does it is the **Domain Name System**: a distributed phone book
older than the web.

## Why this matters in a job

"How does DNS work?" is one of the most common networking interview questions,
and it is also step one of "what happens when you type a URL". At work, DNS is
the first thing to fail and the last thing people check. "Have you tried it by IP
address?" is the question that splits a network problem from a naming problem in
ten seconds.

## A phone book with branches

You want the number of the exam cell at a college you have never called. You ask
a friend who knows everything (the **recursive resolver**). He does not know it,
but he knows the national directory office (a **root server**), which sends him
to the directory for all `.in` numbers (the **TLD server**, top-level domain),
which sends him to the college's own switchboard (the **authoritative server**),
which gives the number. Your friend writes it down, so next time he answers
without asking anyone.

DNS is read right to left: `.` (root), then `in`, then `ac.in`, then
`lnct.ac.in`.

::flow{numbered direction="vertical" caption="The first time. Every later lookup usually stops at step one or two."}
  :::flow-step{label="Your own machine" icon="i-lucide-laptop"}
  The browser's cache, then the operating system's cache, then the `hosts` file
  (`/etc/hosts`, or `C:\Windows\System32\drivers\etc\hosts`): a plain text file
  that overrides everything.
  :::
  :::flow-step{label="The recursive resolver" icon="i-lucide-server"}
  Your router or your provider, or a public one such as 1.1.1.1 or 8.8.8.8. If it
  has the answer cached, you get it here, in a millisecond. Otherwise it does
  the next three steps on your behalf.
  :::
  :::flow-step{label="A root server" icon="i-lucide-globe"}
  Thirteen named root server addresses, known to every resolver. It does not
  know `lnct.ac.in`. It knows who is responsible for `.in`.
  :::
  :::flow-step{label="The TLD server" icon="i-lucide-signpost"}
  The `.in` servers do not know the answer either. They know who is responsible
  for `lnct.ac.in`.
  :::
  :::flow-step{label="The authoritative server" icon="i-lucide-check" highlight}
  The one that actually holds the record. It answers with the address and a
  **TTL** (time to live): how many seconds the answer may be cached.
  :::
::

Your machine asks the resolver **one** question and waits for the final answer.
That is a **recursive** query. The resolver asks root, TLD and authoritative
servers in turn, each of which answers "ask them instead". Those are
**iterative** queries.

## How it works

```bash [Terminal]
nslookup github.com
```

```text [Output]
Server:		192.168.1.1
Address:	192.168.1.1#53

Non-authoritative answer:
Name:	github.com
Address: 140.82.121.4
```

`Server` is your resolver, the router, on port 53. "Non-authoritative" means the
answer came from a cache, not from GitHub's own DNS server. `dig` shows more:

```bash [Terminal]
dig github.com +noall +answer
dig www.github.com +noall +answer
```

```text [Output]
github.com.		42	IN	A	140.82.121.4
www.github.com.		3600	IN	CNAME	github.com.
github.com.		42	IN	A	140.82.121.4
```

The `42` is seconds remaining before this cached answer expires. The second
lookup shows a `CNAME`: `www.github.com` is an alias for `github.com`, which is
then looked up. Your addresses and TTLs will differ. `dig +trace github.com`
walks the whole chain from the root, one step at a time.

The record types you will meet:

| Type | Means | Example |
| --- | --- | --- |
| `A` | This name is this IPv4 address | `results.college.edu → 10.0.1.20` |
| `AAAA` | The same, for IPv6 | |
| `CNAME` | This name is an alias for another name | `www.college.edu → college.edu` |
| `MX` | Send mail for this domain to this server | `college.edu → mail.college.edu` |
| `NS` | These servers are authoritative for this domain | |
| `TXT` | Free text, used for domain verification and mail policy | |
| `PTR` | Reverse lookup: address to name | |

## Real use case

The TTL is why a DNS change is not instant, and it bites every team that moves a
site to a new server.

::real-life{title="Why you lower the TTL before you move anything" source="A domain migration"}
We moved a site to a new server on a Saturday, changed the DNS record, and half
the traffic kept arriving at the old machine until Monday. The record's TTL was
86,400: one day. The correct sequence, learned the hard way: lower the TTL to
60 seconds a day *before* the move, make the change, watch the traffic shift in
a minute, then put the TTL back up. Everybody learns this once.
::

And the `hosts` file is a real everyday tool: point a production name at a
test server on your machine only, and check the new site before anybody else
sees it.

```text [/etc/hosts]
127.0.0.1       localhost
10.0.9.15       results.college.edu    # test server, my laptop only
```

## What confuses people here

That DNS is part of the connection. It is not. DNS is a separate conversation,
usually over **UDP on port 53**, that finishes before any connection to the real
server is attempted. (It falls back to TCP for large answers.) So an
`UnknownHostException` means nothing was ever sent to the server, and a DNS
failure and a server failure are entirely different investigations.

## Interview questions

::accordion
  :::accordion-item{label="What is DNS and how does it resolve a name?" icon="i-lucide-message-circle"}
  The Domain Name System turns names into IP addresses. The client checks its
  own caches and hosts file, then asks a recursive resolver. On a cache miss the
  resolver asks a root server (which points to the TLD servers), the TLD server
  (which points to the authoritative server), and the authoritative server
  (which answers). Every answer is cached for its TTL.
  :::
  :::accordion-item{label="Recursive query against iterative query?" icon="i-lucide-message-circle"}
  In a recursive query the client asks once and expects the final answer; the
  resolver does the work. In an iterative query each server answers with the
  best referral it has ("ask this server next"), and the asker follows it. The
  client-to-resolver query is recursive; resolver-to-root, TLD and
  authoritative are iterative.
  :::
  :::accordion-item{label="What are A, AAAA, CNAME and MX records?" icon="i-lucide-message-circle"}
  A maps a name to an IPv4 address; AAAA to an IPv6 address. CNAME makes one
  name an alias of another. MX names the mail server for a domain.
  :::
  :::accordion-item{label="Does DNS use TCP or UDP?" icon="i-lucide-message-circle"}
  Mostly UDP on port 53, because a query and a reply each fit in one packet and
  a handshake would double the time. It uses TCP for large responses and for
  zone transfers between DNS servers.
  :::
  :::accordion-item{label="You changed a DNS record an hour ago and some users still reach the old server. Why?" icon="i-lucide-message-circle"}
  Caching. Resolvers and browsers keep the old answer until its TTL expires.
  The fix for next time is to lower the TTL well before a planned change, then
  raise it again afterwards.
  :::
::
