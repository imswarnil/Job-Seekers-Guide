Guarantee everything, or guarantee nothing and go fast. Those are the two
answers, and the internet uses both. **TCP** (Transmission Control Protocol)
takes the first; **UDP** (User Datagram Protocol) takes the second.

## Why this matters in a job

"Difference between TCP and UDP" is asked in nearly every fresher networking
round, and so is "give an example of where each is used". Listing features gets
you half marks. The rule that decides between them gets you the rest.

## Registered post against a shout across the corridor

Registered post (TCP): the post office confirms it has the letter, numbers every
page, tells you if a page went missing and sends it again, and delivers the pages
in order. Slower, and it needs a signature at the start.

Shouting a roll number across the hostel corridor (UDP): instant, no setup. If
nobody heard, nobody knows. If you shout three things, they may be heard in any
order, or not at all.

| | TCP | UDP |
| --- | --- | --- |
| Connection | Connection-oriented: a handshake first | Connectionless: send immediately |
| Delivery | Guaranteed, lost data is resent | Not guaranteed |
| Order | Bytes arrive in order | Datagrams may arrive in any order |
| Duplicates | Removed | Possible |
| Flow and congestion control | Yes, slows down for a slow receiver or a busy network | No |
| Header size | 20 bytes minimum | 8 bytes |
| Unit of data | Segment, part of a byte stream | Datagram, each one separate |
| Speed | Slower to start, steady after | Fast, no waiting |
| Used by | HTTP/1.1 and HTTP/2, HTTPS, SSH, email, file transfer, databases | DNS, video calls, live streaming, online games, DHCP, VoIP |

::pull-quote
TCP when every byte must arrive. UDP when arriving late is worse than not
arriving at all.
::

A dropped frame in a video call is invisible. A frame delivered 400 ms late is
a stutter. That is why a call uses UDP and the recording you download later uses
TCP.

## How it works

`nc` (netcat) can speak both. Try sending to a port where nothing is listening,
once each way.

```bash [Terminal]
echo "roll CS2018041 present" | nc -v localhost 9000; echo "tcp exit: $?"
echo "roll CS2018041 present" | nc -u -w1 localhost 9000; echo "udp exit: $?"
```

```text [Output]
nc: connectx to localhost port 9000 (tcp) failed: Connection refused
tcp exit: 1
udp exit: 0
```

TCP tried to set up a connection, the operating system replied "nothing is
listening", and `nc` failed with exit code 1. UDP sent the datagram into nothing
and exited with 0, success, because UDP never asks. (This is macOS; the exact
error wording differs between versions of `nc`.)

Now start a UDP listener in one terminal and send to it from another:

```bash [Terminal]
nc -u -l 9000                                            # terminal 1
echo "roll CS2018041 present" | nc -u -w1 localhost 9000 # terminal 2
```

```text [Terminal 1 output]
roll CS2018041 present
```

No handshake happened. One datagram went, and it arrived because the network
between a machine and itself does not lose anything. Across a real network, some
fraction would not, and the sender would never know.

## Real use case

DNS is the classic UDP case, and it is worth being able to explain why: the
question fits in one packet and so does the answer. A TCP handshake would double
the time of every lookup for no benefit, and if the reply is lost the resolver
asks again.

```java [ResultsClient.java]
// Anything where every byte matters goes over TCP. JDBC to a database,
// and HTTP to an API, both open TCP connections underneath.
Connection db = DriverManager.getConnection(
    "jdbc:postgresql://10.0.2.10:5432/results", user, password);

HttpResponse<String> marks = http.send(
    HttpRequest.newBuilder(URI.create("https://results.college.edu/api/marks/CS2018041")).build(),
    HttpResponse.BodyHandlers.ofString());
```

Nobody wants half a mark sheet or a fee payment where one byte of the amount
went missing. That is TCP's job, and you get it without writing any code for it.

::side-note{kind="go-deeper"}
HTTP/3 runs over **QUIC**, which is built on UDP. It rebuilds reliability itself,
per stream, so one lost packet stalls only its own stream rather than everything
on the connection. That is the fix for TCP's head-of-line blocking, which the
next lesson explains. Mention it and you have shown you know where things are
going, not only where they have been.
::

## What confuses people here

- **"UDP is unreliable, so it is bad."** It is a choice, not a flaw. UDP leaves
  reliability to the application, which is exactly right when resending late
  data would be useless.
- **"TCP is slow."** After the handshake it is fast. What costs is the setup and
  the waiting for lost data, which matters over long distances.
- **Ports.** Both have ports, and they are separate: TCP port 53 and UDP port 53
  are different doors.

## Interview questions

::accordion
  :::accordion-item{label="What is the difference between TCP and UDP?" icon="i-lucide-message-circle"}
  TCP is connection-oriented: a handshake, guaranteed in-order delivery,
  retransmission of lost data, flow and congestion control, a 20-byte header.
  UDP is connectionless: no handshake, no guarantee of delivery or order, an
  8-byte header, and much less overhead.
  :::
  :::accordion-item{label="When would you use UDP over TCP?" icon="i-lucide-message-circle"}
  When late data is worse than missing data, or when one small request and
  reply do not justify a handshake. Video and voice calls, live streaming, online
  games, DNS lookups and DHCP.
  :::
  :::accordion-item{label="Why does DNS use UDP?" icon="i-lucide-message-circle"}
  A query and its answer each fit in one packet, so a handshake would double the
  time for no gain, and if a reply is lost the client asks again. DNS uses TCP for
  large answers and zone transfers.
  :::
  :::accordion-item{label="Which applications use TCP?" icon="i-lucide-message-circle"}
  Anything where every byte must arrive correctly: web pages over HTTP/1.1 and
  HTTP/2, HTTPS, email (SMTP, IMAP), file transfer (FTP), SSH, and database
  connections.
  :::
::
