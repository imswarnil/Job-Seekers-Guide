Three messages before a single byte of your request. That is the price of TCP's
guarantees, paid at the start of every new connection, and it is measured in
round trips.

## Why this matters in a job

"Explain the TCP three-way handshake" is one of the most asked networking
questions for freshers, often followed by "and how is a connection closed?". At
work the handshake explains performance: "the API is slow" is usually not about
bandwidth, it is about how many times something had to cross an ocean and back.

## Agreeing before talking

A phone call. You dial and say "hello, can you hear me?" (SYN). They say "yes, I
can hear you, can you hear me?" (SYN-ACK). You say "yes" (ACK). Only then does
either of you say anything useful. Both sides now know the line works in **both
directions**, which is the point of three messages rather than two.

1. **SYN** (synchronise): the client picks a random starting **sequence number**
   (the number of its first byte) and sends it.
2. **SYN-ACK**: the server acknowledges it (ACK = client's number + 1) and sends
   its own starting sequence number.
3. **ACK**: the client acknowledges the server's number. The connection is
   **ESTABLISHED**.

From then on every byte has a number, which is how "in order" and "did it
arrive" are both solved.

### Closing: four messages

Closing takes four, because each direction is closed separately. Either side
may still have data to send when the other is finished.

::flow{numbered direction="horizontal" caption="The four-way close."}
  :::flow-step{label="FIN" icon="i-lucide-log-out"}
  Client: "I have nothing more to send."
  :::
  :::flow-step{label="ACK" icon="i-lucide-check"}
  Server: "Noted." It may keep sending.
  :::
  :::flow-step{label="FIN" icon="i-lucide-log-out"}
  Server: "I am finished too."
  :::
  :::flow-step{label="ACK" icon="i-lucide-check" highlight}
  Client: "Noted." It then waits a little (TIME_WAIT) in case the last ACK was lost.
  :::
::

A connection can also be killed at once with an **RST** (reset). That is what
the server sends back when nothing is listening on the port, and it is what
`Connection refused` means.

## How it works

### Watch the round trips

`curl` can time each phase of a request separately.

```bash [Terminal]
curl -o /dev/null -s -w "dns %{time_namelookup}s | connect %{time_connect}s | tls %{time_appconnect}s | first byte %{time_starttransfer}s | total %{time_total}s\n" https://github.com
```

```text [Output]
dns 0.004s | connect 0.162s | tls 0.331s | first byte 0.498s | total 0.502s
```

Each number is the time since the start. `connect` minus `dns` is the TCP
handshake (about 158 ms here, one round trip to a server in Europe). `tls` minus
`connect` is the TLS handshake on top of it. Run it twice and `dns` drops to
almost nothing, because the answer is now cached. (Illustrative; your times
depend on where you are.)

### How a lost packet is noticed

```text [What the sender sees]
sent bytes 1000-1499  → ACK 1500 received      ✓
sent bytes 1500-1999  → (nothing)
sent bytes 2000-2499  → ACK 1500 received      ← "still waiting for 1500"
sent bytes 2500-2999  → ACK 1500 received      ← again
sent bytes 3000-3499  → ACK 1500 received      ← three duplicates: resend now
```

The receiver keeps saying "I am still expecting 1500". Three duplicate
acknowledgements and the sender retransmits without waiting for a timeout. This
is why a lossy connection is *slow* rather than broken. It also shows TCP's
weakness, **head-of-line blocking**: bytes 2000 to 3499 have arrived but cannot
be handed to your program until 1500 fills the gap.

TCP also controls speed. **Flow control** stops a fast sender drowning a slow
receiver (the receiver advertises how much room it has, the "window").
**Congestion control** slows down when loss suggests the network is busy: a new
connection starts cautiously ("slow start") and speeds up each round trip. So a
brand new connection is slower than a warmed-up one.

## Real use case

### Latency is not bandwidth

::compare{caption="Bangalore to Frankfurt, a 1 MB response."}
  :::compare-side{label="Bandwidth" verdict="neutral"}
  How much fits through per second. A 1 MB response on a 100 Mbps link takes
  about 80 ms of actual transfer. Buying a faster connection improves this.
  :::
  :::compare-side{label="Latency" verdict="right"}
  How long one trip takes: about 140 ms each way, limited by the speed of light
  in fibre and the routers along the way. **Nothing you buy makes this shorter.**
  :::
::

Count what a first page load costs on a fresh connection:

| Step | Round trips |
| --- | --- |
| DNS lookup (uncached) | 1 |
| TCP handshake | 1 |
| TLS handshake (1.3) | 1 |
| HTTP request and response | 1 |
| **Total before any content** | **4** |

At 140 ms each, that is 560 ms of waiting for a page that transfers in 80 ms.
This is why performance work is largely about removing round trips: reusing
connections (HTTP **keep-alive**), caching, servers nearer the user, and not
calling an API in a loop.

::real-life{title="The dashboard that took nine seconds and transferred 40 KB" source="A report screen"}
The principal's dashboard made 34 separate API calls, one per widget, one after
another. On the office network that was fine. Opened from home it was nine
seconds, and the total data was 40 kilobytes. Nothing was slow. Thirty-four
sequential round trips were slow. Fetching them in parallel took it to 1.1
seconds, and combining them into one call took it to 300 milliseconds.
::

```javascript [dashboard.js]
// Slow: each call waits for the previous one. 34 round trips in a row.
for (const widget of widgets) {
  data[widget] = await fetch(`/api/widgets/${widget}`).then(r => r.json());
}

// Faster: all 34 in flight at once. Roughly one round trip of waiting.
const results = await Promise.all(
  widgets.map(w => fetch(`/api/widgets/${w}`).then(r => r.json()))
);
```

## What confuses people here

- **Why three and not two?** With two, the server would never learn that the
  client received its sequence number. Three messages confirm both directions.
- **Why four to close?** Because each side closes its own direction
  independently. The server's ACK and FIN can be sent together, which is why you
  sometimes see three.
- **"Connection refused" is not a timeout.** Refused is an RST coming back
  immediately. A timeout is the SYN going out and nothing ever coming back.

## Interview questions

::accordion
  :::accordion-item{label="Explain the TCP three-way handshake." icon="i-lucide-message-circle"}
  The client sends SYN with its initial sequence number. The server replies
  SYN-ACK, acknowledging the client's number and sending its own. The client
  sends ACK, acknowledging the server's number. Both sides now know the other can
  send and receive, and have agreed where each byte stream starts.
  :::
  :::accordion-item{label="How is a TCP connection closed?" icon="i-lucide-message-circle"}
  With a four-way close: one side sends FIN, the other ACKs, then sends its own
  FIN when it is done, and the first side ACKs. The side that closed first waits
  in TIME_WAIT for a while in case its last ACK was lost. A connection can also
  be aborted immediately with RST.
  :::
  :::accordion-item{label="Why is the handshake three messages and not two?" icon="i-lucide-message-circle"}
  Each side has to send its own sequence number and have it acknowledged. The
  server's SYN and its ACK of the client ride in one message, so three messages
  cover four jobs. With only two, the server would not know its sequence number
  had reached the client.
  :::
  :::accordion-item{label="How does TCP guarantee reliable delivery?" icon="i-lucide-message-circle"}
  Sequence numbers on every byte, acknowledgements from the receiver,
  retransmission on timeout or three duplicate ACKs, checksums to detect
  corruption, and reordering at the receiver. Flow control and congestion
  control stop it overwhelming the receiver or the network.
  :::
  :::accordion-item{label="Our API is slow for users in another country, but the payload is tiny. Why?" icon="i-lucide-message-circle"}
  Latency, not bandwidth. A new connection costs a DNS lookup, a TCP handshake
  and a TLS handshake, each a round trip, before the request itself. Reuse
  connections, reduce the number of calls, cache, or serve from closer to the
  user.
  :::
::
