Questions about the trade, answered. These five are the decisions, and the point
of the exercise is that four of them come out relational, which is the honest
proportion.

::note
For each: say which store and why, before opening the answer. A wrong choice
argued well is worth more here than a right choice guessed.
::

## 1. The application, with arbitrary extra fields

Each programme asks for different documents and extra details. B.Tech wants
JEE rank; MBA wants work experience; the fine arts course wants a portfolio
link. New programmes appear every year.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Relational, with a `JSONB` column.** Not a document database.

  ```sql
  ALTER TABLE Application ADD COLUMN extra JSONB NOT NULL DEFAULT '{}';
  CREATE INDEX ON Application USING GIN (extra);
  ```

  Why: everything **structural** about an application is still relational. It
  belongs to an applicant and a programme, it has a status ladder, it needs
  foreign keys and a transaction when the status changes. Only the per-programme
  extras are variable.

  Postgres will index inside the JSON and query it:

  ```sql
  SELECT * FROM Application WHERE extra->>'jee_rank' < '5000';
  ```

  The mistake this exercise is testing for: moving the whole application to a
  document store because one field varies. You would lose the constraints and
  the transactions to gain flexibility you already had.

  The sentence worth saying: **"relational with a JSON column" is the answer to
  most schema-flexibility questions, and it is under-used because it is not
  exciting.**
  :::
::

## 2. The session store

Thousands of logged-in students, each with a session that must be read on every
request and expires after an hour.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Redis**, and this is the one that genuinely is not relational.

  Why: read on literally every request, a pure key-value lookup with no
  relationships, no queries across it, and it has a natural expiry. Redis does
  expiry natively with `EX`, which in Postgres would be a cleanup job you have
  to write and monitor.

  It is also acceptable to lose it. If Redis restarts, everybody signs in again,
  which is an annoyance rather than a data loss, and that tolerance is what
  makes an in-memory store the right choice.

  The honest caveat to add: at a few thousand users, a sessions table in
  Postgres is completely fine and one fewer thing to run. I would start there
  and move when the read volume justified it.
  :::
::

## 3. The audit log

Every status change, every admin read of a fee record, every login. Append-only,
never updated, queried occasionally, kept for seven years.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Relational**, with partitioning by month.

  It looks like a document-store case: high write volume, never updated,
  semi-structured. It is not, and the reason is what the log is *for*.

  An audit log is read when something has gone wrong, by somebody who needs to
  join it to the application, the user and the programme, and to be able to
  swear the record is complete. That means foreign keys and transactional
  writes: the audit row and the status change must commit together or neither.

  ```sql
  CREATE TABLE ApplicationEvent (...) PARTITION BY RANGE (changed_at);
  ```

  Partitioning keeps each month's index small and makes dropping the
  seven-year-old data a partition drop rather than a `DELETE` over millions of
  rows.

  The principle: **an eventually-consistent audit log is not an audit log.** If
  it can be missing a row, it cannot answer the question it exists for.
  :::
::

## 4. Full-text search over the prospectus

Applicants search course descriptions, fee structures and admission rules.
Thousands of documents, and results should be ranked by relevance.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Postgres full-text search first.** Elasticsearch only if it is not enough.

  ```sql
  ALTER TABLE Program ADD COLUMN search tsvector
    GENERATED ALWAYS AS (to_tsvector('english', name || ' ' || description)) STORED;
  CREATE INDEX ON Program USING GIN (search);

  SELECT name, ts_rank(search, query) AS rank
  FROM   Program, to_tsquery('english', 'computer & science') query
  WHERE  search @@ query ORDER BY rank DESC;
  ```

  Stemming, ranking, and no second system to run, back up, secure and keep in
  sync.

  When Elasticsearch genuinely wins: millions of documents, fuzzy matching and
  typo tolerance, faceted search, or aggregations over the results. At the scale
  of a university prospectus, none of those apply.

  The trap: **adding a search cluster is the most common premature
  infrastructure decision there is**, and it brings a synchronisation problem
  that never goes away.
  :::
::

## 5. The AI assistant's document chunks

Prospectus text split into chunks, each with an embedding, searched by semantic
similarity when a question is asked.

::accordion
  :::accordion-item{label="Answer" icon="i-lucide-check"}
  **Postgres with `pgvector`.** Not a dedicated vector database.

  ```sql
  CREATE EXTENSION vector;
  CREATE TABLE Chunk (
    chunk_id   BIGSERIAL PRIMARY KEY,
    program_id BIGINT REFERENCES Program,
    content    TEXT NOT NULL,
    embedding  vector(1536)
  );
  CREATE INDEX ON Chunk USING hnsw (embedding vector_cosine_ops);
  ```

  Why it matters that it is in the same database: you can filter by programme
  **and** search by similarity in one query, with the foreign key guaranteeing
  the chunk still belongs to a real programme.

  ```sql
  SELECT content FROM Chunk
  WHERE  program_id = :id
  ORDER BY embedding <=> :query_embedding LIMIT 5;
  ```

  In a separate vector store, that filter is either a second round trip or a
  duplicated copy of your metadata that can drift.

  A dedicated vector database starts winning in the hundreds of millions of
  vectors. A prospectus is thousands.
  :::
::

## The sentence that makes either answer sound like judgement

::pull-quote
"The data is relational, so I would stay relational until something specific
forces me out, and the thing that would force me is X." Then name X, and mean
it.
::

Four of these five came out relational, which is the honest proportion for a
system like this. Being able to say that, rather than reaching for the newer
option to sound current, is what an interviewer is listening for.

## The scorecard

| What you have | What it suggests |
| --- | --- |
| Relationships, transactions, joins in the questions | Relational |
| Genuinely variable per-row fields | Relational with `JSONB` |
| Key-value, per-request, expiring, losable | Redis |
| Millions of documents, fuzzy and faceted search | A search engine |
| Vectors at very large scale | A vector database |
| Anything else | Relational, and say why you considered otherwise |
