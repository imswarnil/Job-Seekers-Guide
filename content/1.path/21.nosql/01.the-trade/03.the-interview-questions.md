title: Interview questions
description: Four questions about non-relational stores, answered with the trade rather than with a side.
minutes: 6
kind: quiz

::accordion
  :::accordion-item{label="1. SQL or NoSQL?" icon="i-lucide-message-circle"}
  A weak answer picks a side. A strong one names the trade: a document store
  gives up joins, cross-document transactions and enforced constraints, in
  exchange for reading a whole nested thing in one operation and sharding more
  easily.

  Then the answer that is right most of the time and that almost nobody gives:
  relational, with a `JSONB` column for the part that genuinely varies. You get
  flexibility exactly where it is needed and constraints everywhere else,
  instead of trading all of one for all of the other.
  :::

  :::accordion-item{label="2. What does 'schema-less' actually mean?" icon="i-lucide-message-circle"}
  That the schema moved. It still exists, every query and every report assumes
  a shape. It just lives in application code where nothing enforces it and the
  next application written against the same data will not know about it.

  Give the consequence: one collection, four developers, three years, and you
  have `name`, `fullName` and `full_name` in the same collection with `score` as
  both a number and a string. Nothing rejected any of it.
  :::

  :::accordion-item{label="3. When is a document store the right choice?" icon="i-lucide-message-circle"}
  When each record is naturally a whole nested thing that is read and written
  together and rarely joined, when the shape genuinely varies, or when you are
  sharding at a scale a single relational node cannot serve.

  Then the honest qualifier: most projects that choose it for scale never reach
  a scale where it mattered, and they do reach the day a fee changed in forty
  thousand documents.
  :::

  :::accordion-item{label="4. What would you use Redis for?" icon="i-lucide-message-circle"}
  Caching an expensive query, sessions shared across servers, rate limiting, and
  a simple queue. Not as the only copy of anything, because it is in memory and
  can vanish.

  The session example is the one worth giving, because it connects to something
  else you know: a `static` cache is per process, so it goes stale the moment
  you run a second server. Redis is that problem solved properly.
  :::
::
