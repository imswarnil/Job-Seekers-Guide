Every answer so far has appeared in a black terminal window, and the registrar is
not going to learn `psql`. This track is about the thing that turns their question
into your query. Before building anything with it, what it actually is.

## Why this matters in a job

Because you are going to be reviewing this system's output for the rest of your
career, and you cannot supervise what you do not understand. Every failure mode
in this track falls directly out of the mechanism in this lesson.

## The mechanism, honestly

A large language model does one thing: given some text, it predicts what comes
next. Then it appends that and predicts again.

::flow{numbered direction="vertical" caption="Generating four words. The same step, repeated."}
  :::flow-step{label="Input: 'The registrar shortlisted the'" icon="i-lucide-type"}
  Every word is turned into a number. The model has never seen a letter.
  :::
  :::flow-step{label="Predict a distribution over what comes next" icon="i-lucide-chart-column" highlight}
  Not one answer. A probability for every possible token: `applicant` 31%,
  `students` 12%, `top` 9%, `candidates` 7%, and so on for fifty thousand more.
  :::
  :::flow-step{label="Pick one" icon="i-lucide-dices"}
  Usually not the highest. Sampling with some randomness is what makes the output
  read naturally rather than mechanically, and it is why the same question gives
  a different answer twice.
  :::
  :::flow-step{label="Append it and repeat" icon="i-lucide-repeat"}
  'The registrar shortlisted the applicant' → predict again. Every word you see
  was produced by this loop.
  :::
::

::pull-quote
There is no plan. The model has not decided what it is going to say before it
starts saying it. It produces one token, then reconsiders everything including
what it just wrote.
::

That single fact is worth sitting with, because almost everything else follows
from it.

## What follows from it

::feature-list{columns="2"}
  :::feature{icon="i-lucide-circle-alert" title="It cannot know it is wrong"}
  A confident sentence and a fabricated one are produced by the identical
  process. There is no separate step where it checks. This is why hallucination
  is not a bug to be fixed but a property to be designed around.
  :::
  :::feature{icon="i-lucide-shuffle" title="The same question gives different answers"}
  Because of the sampling. Which means "it worked when I tried it" is weak
  evidence, and a feature built on a model needs to handle the version that
  comes out differently.
  :::
  :::feature{icon="i-lucide-clock" title="It has no memory between conversations"}
  Each request is the whole context, sent again. A chat that "remembers" is
  resending the previous messages every time.
  :::
  :::feature{icon="i-lucide-calculator" title="It is bad at arithmetic for a reason"}
  It is predicting the characters of a number, not calculating one. Which is why
  serious systems make it *write the query* and let the database do the sums.
  :::
::

## Tokens, and why they are not words

A token is roughly three to four characters of English. `university` might be
one token; `2026CSE0184` might be six.

```text [Tokenised]
"The registrar shortlisted 1,602 applicants"
→ ["The", " registrar", " short", "listed", " 1", ",", "602", " applicants"]
   8 tokens
```

Three consequences you will actually meet:

- **You are billed per token**, input and output. A long prompt sent on every
  request is a recurring cost.
- **Numbers are split arbitrarily**, which is part of why arithmetic is
  unreliable.
- **Non-English text uses more tokens per word**, so the same paragraph in Hindi
  can cost several times as much as in English.

::warning{icon="i-lucide-alert-triangle"}
"Just put the whole database in the context window" is the first idea everybody
has and it fails three ways: it costs money on every single request, it is
slower, and models attend less reliably to material in the middle of a long
context. That is why retrieval exists, and it is chapter three.
::

## Embeddings, which is the other useful idea

A model can also turn a piece of text into a list of numbers — typically several
hundred to a few thousand — positioned so that **texts about similar things end
up near each other**.

```text [Roughly]
"application deadline"     → [0.21, -0.55, 0.13, ...]
"last date to apply"       → [0.19, -0.51, 0.15, ...]   ← close
"hostel fee structure"     → [-0.62, 0.30, -0.44, ...]  ← far
```

Nearness is measured with arithmetic, usually cosine similarity. The consequence
is what matters: you can search by **meaning** rather than by keyword.

::compare{caption="A student asks 'when do I have to apply by?'"}
  :::compare-side{label="Keyword search" verdict="wrong"}
  `LIKE '%apply by%'` finds nothing. The document says "the application
  deadline". Not a single word overlaps.
  :::
  :::compare-side{label="Embedding search" verdict="right"}
  The question's vector is close to the deadline paragraph's vector, so it comes
  back first. Nobody had to anticipate the phrasing.
  :::
::

This is how every "ask a question about our documents" feature works, and you
will build one in chapter three.

## Temperature, in one line

The dial controlling how much randomness there is in the picking step.

| Setting | Behaviour | Use for |
| --- | --- | --- |
| 0 | Almost always the most likely token. Repeatable. | Extracting data, generating SQL, classification |
| 0.7 | The default. Natural, varied. | Writing, explanation, conversation |
| 1.5 | Adventurous, and increasingly incoherent | Almost nothing |

::tip
Any feature where the same input must give the same output — extraction,
classification, generating a query — should run at temperature 0. It is the
single most common configuration mistake in a first AI feature, and it produces
a system that is mysteriously inconsistent.
::

## What you can do now

You can say what a model is doing in one sentence, and derive from it why it
hallucinates, why it is bad at arithmetic, and why the same question gives two
answers. That derivation is the whole point of the lesson.

## Your turn

Answer these from the mechanism, without looking anything up.

1. Why can a model produce a confident citation for a paper that does not exist?
2. Why does asking it to "think step by step" often improve an answer?
3. Why would you not ask it to calculate the average of 1,840 scores?
4. Why does a longer conversation get more expensive per message?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** A plausible citation is exactly what next-token prediction is good at
  producing: author names, a year and a title that all *look* like a real paper,
  because they have the statistical shape of one. There is no step where the
  model checks whether the thing exists. Fluency and truth are produced by the
  same process, which is precisely why fluency is not evidence.

  **2.** Because the model has no hidden scratchpad: its only working memory is
  the text it has already produced. Asking for intermediate steps makes it
  generate those steps as tokens, and each subsequent prediction is conditioned
  on them. It is not "thinking harder", it is giving itself more relevant context
  to predict from.

  **3.** Because it would be predicting the characters of a plausible-looking
  number, not adding anything. The right design is to have it write
  `SELECT AVG(score) ...` and let the database compute. That is the central
  architectural idea of chapter three.

  **4.** Because there is no memory between requests. The entire conversation is
  re-sent every time, so message twenty carries messages one to nineteen with it
  and is billed for all of them.
  :::
::

## The interview question this answers

**"How does a large language model work?"**

Next-token prediction over a distribution, sampled with some randomness, repeated.
Then immediately make it useful by deriving three consequences: hallucination is
the same process as correct output so the model cannot flag it; the same input
gives different outputs, so tests must account for that; and arithmetic is
unreliable because it is predicting digits rather than calculating.

Naming the *design response* — temperature 0 for anything deterministic, and
letting the database do the arithmetic — is what turns a textbook answer into an
engineering one.
