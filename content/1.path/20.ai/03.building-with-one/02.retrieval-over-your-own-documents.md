No `SELECT` answers "what documents do I need for admission?". The answer is in a
prospectus, a circular and three notice-board PDFs, and the pattern for that has
a name: **retrieval-augmented generation**, which is a long name for a simple
idea.

## Why this matters in a job

Because this is the second-most-requested AI feature after the one in the
previous lesson, and because the naive version — paste everything into the
prompt — fails for reasons you already know from chapter one.

## The idea

Find the few paragraphs that are relevant, put only those in the context, and
ask the model to answer **from them only**.

::flow{numbered direction="vertical" caption="Two phases. The first happens once; the second happens per question."}
  :::flow-step{label="Once: split the documents into chunks" icon="i-lucide-scissors"}
  The prospectus becomes perhaps four hundred passages of a few hundred words
  each.
  :::
  :::flow-step{label="Once: embed each chunk and store the vector" icon="i-lucide-database"}
  Each passage becomes a list of numbers positioned by meaning. Store them
  beside the text.
  :::
  :::flow-step{label="Per question: embed the question" icon="i-lucide-search"}
  The same model, so the question's vector lives in the same space.
  :::
  :::flow-step{label="Per question: find the nearest chunks" icon="i-lucide-target" highlight}
  Usually five. This is arithmetic over vectors, and a database can do it.
  :::
  :::flow-step{label="Per question: answer from those five only" icon="i-lucide-message-square"}
  The model is given the passages and instructed to answer from them, cite them,
  and say so when they do not contain the answer.
  :::
::

## Chunking, which decides everything

The least glamorous step and the one that most often makes the feature bad.

::compare{caption="The same prospectus, two chunking strategies."}
  :::compare-side{label="Fixed 500 characters" verdict="wrong"}
  Cuts mid-sentence and mid-table. A chunk ends with "documents required for
  admission are:" and the list is in the next chunk. Retrieval finds the
  question's wording and returns the half with no answer in it.
  :::
  :::compare-side{label="By section, with overlap" verdict="right"}
  Split on headings, then on paragraphs if a section is too long, with about
  fifty words of overlap between neighbours so a sentence spanning a boundary
  appears in both. Each chunk carries its section heading as a prefix.
  :::
::

```text [A good chunk]
[Prospectus 2026 → Section 4: Admission → 4.2 Documents required]

Applicants must submit the following at the time of admission: the class XII
marksheet, a transfer certificate from the previous institution, a migration
certificate where applicable, four passport-size photographs, and proof of
category where a reserved seat is claimed. Originals are verified and returned.
```

The heading is inside the text of the chunk, not only in metadata, which means it
is part of what gets embedded. A chunk that says "originals are returned" with no
indication of what it is about will never be retrieved by anybody.

## Storing and searching

```sql [schema.sql]
-- PostgreSQL with the pgvector extension. Your database can do this;
-- a separate vector database is a scaling decision, not a starting point.
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE DocumentChunk (
  chunk_id     BIGSERIAL PRIMARY KEY,
  document     TEXT   NOT NULL,       -- 'Prospectus 2026'
  section      TEXT   NOT NULL,       -- '4.2 Documents required'
  page         INT,
  content      TEXT   NOT NULL,
  embedding    VECTOR(1536) NOT NULL,
  indexed_on   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX ON DocumentChunk USING hnsw (embedding vector_cosine_ops);
```

```sql [search.sql]
-- The five nearest chunks. <=> is cosine distance: smaller is closer.
SELECT document, section, page, content,
       1 - (embedding <=> :question_embedding) AS similarity
FROM   DocumentChunk
ORDER  BY embedding <=> :question_embedding
LIMIT  5;
```

That is the whole search. It is an `ORDER BY` with an unusual operator, and the
index is the same idea as every other index: a structure that avoids comparing
against every row.

::side-note{kind="go-deeper"}
Pure vector search misses exact terms. A student searching for course code
"CS-201" may get chunks about similar-sounding courses, because the embedding
captures meaning and "CS-201" means very little on its own. The standard fix is
**hybrid search**: run a keyword search and a vector search, and combine the
rankings. Knowing that pure vector search has this specific weakness is a good
thing to be able to say.
::

## The prompt, and the citation requirement

```text [answer-prompt.txt]
Answer the student's question using ONLY the passages below.

Rules:
  - If the passages do not contain the answer, say: "I could not find that in
    the prospectus. Please contact the admissions office." Do not use anything
    you know from elsewhere.
  - Cite the section for every fact, like [4.2].
  - If the passages disagree with each other, say so rather than choosing.
  - Quote fees, dates and document names exactly as written.

PASSAGES
[4.2 Documents required, page 17] Applicants must submit the following...
[3.1 Eligibility, page 11] Candidates must have passed class XII with...
...

QUESTION
What documents do I need for admission?
```

::pull-quote
"Answer only from these passages, cite the section, and say when you cannot" is
the difference between a feature that is checkable and one that is a confident
stranger with your letterhead.
::

## What it should look like

```text [Good]
You need to submit these at the time of admission [4.2]:

  · class XII marksheet
  · transfer certificate from your previous institution
  · migration certificate, where applicable
  · four passport-size photographs
  · proof of category, if you are claiming a reserved seat

Originals are verified and returned [4.2].

  Source: Prospectus 2026, section 4.2, page 17.  [ Open ]
```

```text [Also good, and more important]
I could not find that in the prospectus. Please contact the admissions office
on admissions@university.edu.

  Searched: Prospectus 2026, Admission Circular 12/2026.
```

The second one is the feature working correctly. A system that always produces an
answer is a system that invents one when it has to.

## The acceptance criteria

::feature-list{columns="2"}
  :::feature{icon="i-lucide-quote" title="Every fact is cited"}
  With a section and a page, and the citation opens the source. Uncited output
  is unverifiable and should not ship.
  :::
  :::feature{icon="i-lucide-x" title="It refuses when it should"}
  Ask something genuinely not in the documents. It must decline. Test this
  first, because it is the behaviour that decides whether the feature is
  trustworthy.
  :::
  :::feature{icon="i-lucide-scale" title="It surfaces contradictions"}
  Put an old fee in the prospectus and a revised one in a circular. It must say
  the sources disagree, not silently pick.
  :::
  :::feature{icon="i-lucide-refresh-cw" title="Re-indexing is one command"}
  A prospectus is revised. Stale chunks must not survive, or the system will
  confidently quote last year's fee.
  :::
  :::feature{icon="i-lucide-shield" title="Only public documents are indexed"}
  The prospectus, yes. Internal deliberations about individual applicants,
  emphatically not. What goes in the index is a governance decision.
  :::
  :::feature{icon="i-lucide-user-check" title="A human is in the loop where it matters"}
  Answering "what documents do I need" is low stakes. Answering "am I eligible
  for a scholarship" is not, and should route to a person.
  :::
::

## The failure to design for

::warning{icon="i-lucide-alert-triangle"}
The dangerous failure is not "it could not find the answer". It is **retrieving
the wrong but plausible chunk**, which the model then answers from faithfully and
cites correctly. A student asks about the postgraduate fee, the search returns
the undergraduate one because the wording is nearly identical, and the answer is
fluent, sourced and wrong.

Two mitigations, and both are worth stating in an interview: put the document and
section in the *visible* answer so a reader can notice the mismatch, and record a
similarity threshold below which the system declines rather than answering from a
weak match.
::

## Your turn

Build it over three real documents. The university prospectus, a fee circular and
an examination timetable are the right shape.

Then write ten questions you know the answers to, including **three you know are
not in the documents**, and score it honestly.

::accordion
  :::accordion-item{label="How to score it, and what the numbers mean" icon="i-lucide-clipboard-check"}
  For each of the ten, record one of four outcomes:

  **Correct and cited** — the answer is right and the citation points at the
  passage it came from.

  **Correct, wrong citation** — right answer, citation points somewhere else.
  More serious than it looks: the citation is the thing that makes it checkable,
  so a wrong one is worse than none.

  **Wrong** — count it as a failure even if it is close. A fee that is out by a
  year is wrong.

  **Correctly declined** — for your three unanswerable questions, this is the
  *success* outcome.

  **What the numbers mean.** Seven or eight correct out of ten is typical for a
  first build and is not good enough to put in front of students unsupervised.
  But the one that decides whether you ship is the three you planted: if it
  invented an answer for any of them, the feature is not ready at any accuracy,
  because you have built something that cannot be trusted specifically when it is
  out of its depth.
  :::
::

## Check yourself

1. Why not simply put the entire prospectus in the context window?
2. **An interviewer asks: "how do you stop it making things up?"**

## The interview question this answers

**"What is RAG and when would you use it?"**

Retrieval-augmented generation: embed your documents once, embed the question,
retrieve the nearest few passages, and instruct the model to answer only from
them with citations. Use it when the answer lives in documents rather than in
rows.

Then the three things that separate a real answer: chunking strategy decides
quality more than the model does; the system must be able to say it does not
know, and that is the first thing you test; and the dangerous failure is a
plausible wrong retrieval answered faithfully, which is why the source is shown
and why a similarity threshold below which you decline is worth having.
