A plausible answer, with no signal attached about whether it is a true one. That
is the situation, and the working practice that follows from it is narrow and
teachable.

## Why this matters in a job

Because this is now most of what a junior engineer is paid for, and because "how
do you use AI in your work" is asked in nearly every interview in 2026 with two
easy answers that both fail.

## The boundary

::compare{caption="The rule, and it has one sentence."}
  :::compare-side{label="Delegate" verdict="right"}
  Boilerplate. A first draft. Syntax in a language you know but do not write
  daily. An explanation of somebody else's code. Test cases you would have
  written anyway. Anything where **you could verify the output in less time than
  writing it**.
  :::
  :::compare-side{label="Never delegate" verdict="wrong"}
  Anything you could not have written yourself. Anything encoding a business
  rule. Anything touching data where being wrong is expensive. Anything in a
  language you cannot read.
  :::
::

::pull-quote
Never accept output you could not have written yourself. The moment you do, you
have stopped being able to tell right from wrong, which is the only thing you
are for.
::

## Watch a review that matters

The registrar asks for the shortlisting rule. Here is a completely typical
generated answer.

```java [Generated.java]
public List<Applicant> shortlist(List<Application> applications, int cutoff) {
    return applications.stream()
        .filter(a -> a.getScore() >= cutoff)
        .map(Application::getApplicant)
        .collect(Collectors.toList());
}
```

It compiles. It is idiomatic. It is what most people would have written. And
there are four problems, every one of which is a thing the model could not have
known.

::code-trace{caption="Four questions the model cannot answer, because the answers live in a registrar's office."}
```java [Generated.java]

    return applications.stream()
        .filter(a -> a.getScore() >= cutoff)
        .map(Application::getApplicant)
        .collect(Collectors.toList());
}
```

  :::code-trace-step{lines="3" caption="getScore() returns Integer, and 200 applications are unmarked. Comparing null with >= throws a NullPointerException on unboxing. The model had no way to know some are unmarked."}
  :::
  :::code-trace-step{lines="3" caption=">= or >? 'Above the cutoff' in English is ambiguous, and eleven applicants on exactly 60 will find out which you chose. This is a question for the registrar."}
  :::
  :::code-trace-step{lines="4" caption="One applicant applying to three programmes appears three times in the result. Whether the shortlist is of applications or applicants is the dashboard bug again, and it is a policy question."}
  :::
  :::code-trace-step{lines="3" caption="Nothing excludes WITHDRAWN. A withdrawn applicant would be shortlisted and emailed, which is a real and embarrassing outcome."}
  :::
::

```java [Reviewed.java]
/**
 * Applicants shortlisted for a programme.
 *
 * "At or above" the cutoff, confirmed with the registrar's office on 12 March:
 * an applicant scoring exactly the cutoff IS shortlisted.
 * Unmarked applications are excluded rather than treated as zero.
 * One entry per applicant, even if they applied to several programmes.
 */
public List<Applicant> shortlist(List<Application> applications, int cutoff) {
    if (cutoff < 0 || cutoff > 100) {
        throw new IllegalArgumentException("Cutoff must be 0–100, got " + cutoff);
    }
    return applications.stream()
        .filter(a -> a.getStatus() != Status.WITHDRAWN)
        .filter(a -> a.getScore() != null)
        .filter(a -> a.getScore() >= cutoff)
        .map(Application::getApplicant)
        .distinct()
        .toList();
}
```

The generated version was a perfectly good draft. The review is where the
university's rules entered the system, and it is the only place they could have.

::real-life{title="Why the failures cluster" source="Any team using these tools daily"}
The generated code is usually fine. The problem is that "usually" is not a
standard anybody runs a university on, and the failures are not randomly
distributed: they cluster exactly where the business rules live, because that is
the part that was never in the training data. The review is not proofreading. It
is the only point at which the domain enters the system.
::

## The four questions to ask of any generated code

::flow{numbered direction="vertical" caption="Every time. It takes ninety seconds and it is the job."}
  :::flow-step{label="What did it assume?" icon="i-lucide-help-circle" highlight}
  It filled every gap in your request, silently and fluently. List what you did
  not specify and check each one against reality.
  :::
  :::flow-step{label="What happens at the edges?" icon="i-lucide-move-horizontal"}
  Null, empty, zero, exactly at the boundary, duplicate, very large. Generated
  code is written for the middle of the distribution.
  :::
  :::flow-step{label="Does it invent anything?" icon="i-lucide-search"}
  A method that does not exist, a parameter in the wrong order, a library
  version that never shipped. Check the API rather than assuming.
  :::
  :::flow-step{label="Could I explain every line?" icon="i-lucide-message-square"}
  If not, you cannot maintain it and you cannot defend it in review. Delete it
  and write the version you understand.
  :::
::

## Prompting, as a skill rather than a trick

Three things account for most of the difference, and none of them is a magic
phrase.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-file-text" title="Give it the actual context"}
  The schema, the real method signature, the constraint. "Write a shortlisting
  method" against "here is my `Application` class, `getScore()` returns a
  nullable `Integer`, and the rule is at-or-above" produce completely different
  output.
  :::
  :::feature{icon="i-lucide-target" title="State the constraints"}
  Java 21, no new dependencies, must handle unmarked applications, must be
  testable without a database. Unstated constraints get violated, every time.
  :::
  :::feature{icon="i-lucide-list-checks" title="Ask for the edge cases"}
  "Now list every case where this would be wrong" is the single highest-return
  follow-up available, and models are considerably better at critique than at
  first drafts.
  :::
  :::feature{icon="i-lucide-x" title="Do not ask for 'best practice'"}
  It produces confident generic advice detached from your situation. Ask about
  *your* code and *your* constraint.
  :::
::

## The loop that is worth more than the code

This is the one I would have paid for in 2018, alone in Bangalore with nobody to
ask.

::ai-prompt{title="The understanding check" model="Any"}
I am learning [topic] for entry-level interviews. Here is my explanation in my
own words: [your explanation].

Do not rewrite it. Tell me which parts are wrong, which parts are vague, and then
ask me the three follow-up questions an interviewer would ask after hearing this.

  #why
  It asks for a critique, not an answer. A critique tells you what your
  understanding was missing; an answer gives you somebody else's words to repeat,
  which is exactly what an interviewer is testing for and will find. The
  follow-up questions are the real output: if you cannot answer them, your
  explanation opened doors you cannot walk through.
::

::ai-prompt{title="The code review you do not have" model="Any"}
Here is a method I wrote. [code]

Review it the way a senior engineer would in a pull request. Specifically: what
breaks at the boundaries, what happens with null or empty input, what I have
assumed that is not stated, and what you would ask me before approving it.

Do not rewrite it. Ask me questions.

  #why
  A junior learning alone has no reviewer, and the reviewer is where most of the
  learning in a first job actually happens. This is not a replacement for one. It
  is considerably better than nothing, and the instruction not to rewrite is what
  stops it becoming a way to avoid thinking.
::

## What confuses people here

That using it well means using it more. The engineers I have watched get the most
out of these tools use them for a narrower set of things than beginners do, and
review the output harder.

::warning{icon="i-lucide-alert-triangle"}
The honest risk for somebody learning this way: you can reach month six feeling
productive and be unable to explain why your own code works. Interviews find this
immediately, because they ask you to explain rather than to produce. If you
cannot answer "why did you write it this way", the answer is that you did not.
::

## What you can do now

You can state the boundary between what you delegate and what you never do, run
the four-question review, and use the two prompts above, which together are the
closest thing to a mentor available to somebody learning alone.

## Your turn

Ask any model to write a Java method deciding whether an applicant is eligible
for a scholarship. Give it no rules at all.

Then write down every assumption it invented, and for each one, who at a real
university would have to decide it.

::accordion
  :::accordion-item{label="What you will find, and the point" icon="i-lucide-list-checks"}
  It will invent a merit cutoff, usually 75 or 80. Probably an attendance
  threshold. Possibly an income limit, and a rule that higher score wins. It may
  assume scholarship is a boolean rather than an amount, and that eligibility is
  computed rather than approved by somebody.

  **Every one of those is policy**, set by a scholarship committee, written in a
  document, approved by a governing body, and different at every institution in
  the country.

  The point is not that the model did badly. It did what was asked. The point is
  that **the thing you did not specify is precisely the thing you are paid to
  know**, and it will be filled in fluently and silently either way. That is the
  whole argument for the fourteen tracks before this one.
  :::
::

## The interview question this answers

**"How do you use AI in your work?"** — asked in nearly every interview now, and
both easy answers fail. "I do not" reads as dishonest or inefficient. "For
everything" reads as somebody who cannot be trusted with a review.

The answer that works describes a boundary and then proves it with one example.
Boilerplate, first drafts, unfamiliar syntax, explaining somebody else's code;
never anything you could not have written yourself, anything encoding a business
rule, or anything in a language you cannot read. Then the shortlisting example:
the generated code was fine and the four things wrong with it were all domain
rules the model had no way to know. That example is the answer.
