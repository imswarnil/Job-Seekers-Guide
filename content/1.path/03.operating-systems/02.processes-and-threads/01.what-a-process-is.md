Three hundred of them on an idle laptop. A process is not "a running program",
which is the answer everybody gives and which explains nothing. A process is a
**bundle of things the kernel gives your program so it can pretend it owns the
machine.**

## Why this matters in a job

Because the single most-asked operating systems question in an interview is
"process versus thread", and it is unanswerable until you know exactly what a
process contains. It is also the frame for every deployment question later in
this course: why restarting a service loses its in-memory state, why two copies
of your application cannot share a cache in memory, why a crash in one request
handler can take down every request in flight.

## Watch the isolation

Two copies of the same program, started a second apart, with an obvious shared
variable.

```java [Counter.java]
public class Counter {
  static int applicantsProcessed = 0;

  public static void main(String[] args) throws Exception {
    for (int i = 0; i < 5; i++) {
      applicantsProcessed++;
      System.out.println(ProcessHandle.current().pid()
          + " has processed " + applicantsProcessed);
      Thread.sleep(500);
    }
  }
}
```

```bash [Terminal]
java Counter & java Counter &
```

```text [Output]
41822 has processed 1
41823 has processed 1
41822 has processed 2
41823 has processed 2
41822 has processed 3
41823 has processed 3
```

Two processes, same class, same `static` field, two completely separate values.
`static` in Java means "one per class, per process" and the second half of that
sentence is the one nobody says.

::real-life{title="Why the in-memory cache stopped working in production" source="A scale-out, year three"}
An application kept a `static Map` of programme fee schedules so it would not hit
the database every request. It worked perfectly on one server. When we ran four
copies behind a load balancer, a fee updated by an administrator took effect on
whichever server happened to serve them and stayed stale on the other three for
an hour. Nothing was broken; the cache was per process, and there were now four
processes. This is the most common surprise in a first deployment, and it is this
diagram.
::

## The three states

A process is not always running. There are three states and the middle one is
where most processes spend most of their lives.

::flow{numbered direction="vertical" caption="On a normal laptop, nearly every process is blocked nearly all the time."}
  :::flow-step{label="Running" icon="i-lucide-play"}
  Actually executing on a processor, right now. At most one per processor core,
  which is why eight cores means at most eight running processes.
  :::
  :::flow-step{label="Ready" icon="i-lucide-clock"}
  Able to run, waiting for its turn. The scheduler's queue.
  :::
  :::flow-step{label="Blocked" icon="i-lucide-pause" highlight}
  Waiting for something that is not the processor: a disk read, a network
  response, a keypress. It cannot use a processor even if one is free, and this
  is where the overwhelming majority of processes sit.
  :::
::

That third state is why three hundred processes on eight cores is not a problem.
Almost none of them want a processor at any given instant.

::side-note{kind="go-deeper"}
Run `ps aux` and look at the `STAT` column. `S` means sleeping: blocked and
interruptible. `R` means running or ready. Count them. On my laptop right now:
412 processes, 3 in state `R`. That ratio is the answer to "how does my machine
run all this at once", and most people have never looked.
::

## How a process is made

On Unix, a process is created by **copying an existing one** and then replacing
its program. That is a strange design and it explains several things you will
meet later.

```bash [Terminal]
# What happens when you type `java Counter` at a prompt:
# 1. The shell calls fork()  → an identical copy of the shell now exists
# 2. The copy calls exec()   → its program is replaced by the JVM
# 3. The shell calls wait()  → it sleeps until the copy exits
```

::compare{caption="Two system calls that are always described together and do opposite things."}
  :::compare-side{label="fork()" verdict="neutral"}
  Makes a copy of the calling process. Same code, same open files, a copy of the
  memory, a new pid. It returns twice: `0` in the child, the child's pid in the
  parent, which is how each copy knows which one it is.
  :::
  :::compare-side{label="exec()" verdict="neutral"}
  Keeps the process but throws away its program and loads a different one.
  Same pid, same file descriptors, completely different code. It does not return
  at all on success, because there is nothing left to return to.
  :::
::

::side-note{kind="go-deeper"}
This is why a shell can set things up for a program before running it. Between
`fork` and `exec`, the child is still the shell and can open files, change the
working directory or redirect output, and all of that survives into the new
program, because file descriptors are kept across `exec`. Every `>` and `|` you
typed in the terminal track works because of that gap.
::

## What confuses people here

That "process" and "program" are the same word. A program is a file on disk. A
process is one running instance of it with its own memory. Open your browser
twice and there is one program and two processes, and they cannot see each
other's variables.

## What you can do now

You can say exactly what is private to a process, which is the entire basis of
the thread lesson next, and you can predict which of your application's state
survives a restart and which does not.

## Your turn

Look at your own machine and answer three questions:

```bash [Terminal]
ps aux | wc -l
ps aux | awk '$8 ~ /^R/' | wc -l
ls -l /proc/self/fd     # Linux only; on macOS use: lsof -p $$
```

1. How many processes are there, and how many are actually running?
2. What are file descriptors 0, 1 and 2 of your shell pointing at?
3. If you start the same Java program twice, how many copies of its `static`
   fields exist?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  1. Usually hundreds of processes and a single-figure number running. Everything
     else is blocked waiting for something.
  2. All three point at your terminal. That is why output appears on your screen
     and why `2>&1` works: it is making descriptor 2 point at whatever 1 points
     at.
  3. **Two.** One per process. This is the answer to the interview question "is
     `static` shared between users of my web application?" It is shared
     between requests in the same process, not between processes, and therefore not
     between servers.
  :::
::

1. Name the five things a process owns, and say which one `static` fields live

2. **An interviewer asks: "what is the difference between a program and a

## The interview question this answers

**"What is a process?"**

Do not say "a program in execution" and stop; that is the definition from the
textbook everybody read. Say what it contains: its own memory divided into code,
static data, heap and stack; its own file descriptors; its own registers; its own
identity and pid. Then the consequence that shows you have used this: two
processes running the same program share nothing, which is why an in-memory cache
stops working the moment you run a second copy behind a load balancer.

## Next

::callout{icon="i-lucide-arrow-right"}
Every one of those five things is private, and that is expensive. Making a new
process means copying all of it. So what if you wanted two things happening at
once inside *one* process, sharing the same heap? You would get something much
cheaper, and a category of bug that has ruined careers.
::
