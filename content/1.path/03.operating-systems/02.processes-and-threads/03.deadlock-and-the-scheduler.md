Both wait forever. A **deadlock** is two threads each holding what the other
needs, and unlike a race condition it does not produce a wrong answer. It
produces nothing at all, which is sometimes worse, because a hung service has no
error message.

## Why this matters in a job

Because when a service stops responding and the processor is idle, deadlock is
the first hypothesis, and being able to say that sentence puts you ahead of most
people in the room.

## Watch it happen

Two staff members, two records. A transfer moves a student between departments
and needs both.

```java [Transfer.java]
static final Object computerScience = new Object();
static final Object electronics     = new Object();

// Staff member A: move a student from CSE to ECE
Thread a = new Thread(() -> {
  synchronized (computerScience) {
    sleep(50);                              // just enough to let B get going
    synchronized (electronics) {
      System.out.println("A moved the student");
    }
  }
});

// Staff member B: move a student from ECE to CSE
Thread b = new Thread(() -> {
  synchronized (electronics) {
    sleep(50);
    synchronized (computerScience) {        // ← A holds this, and wants what B holds
      System.out.println("B moved the student");
    }
  }
});
```

```text [Output]
(nothing, forever)
```

A holds computer science and wants electronics. B holds electronics and wants
computer science. Neither will let go, because neither is finished. The processor
is idle. The program will sit there until somebody kills it.

## The four conditions

A deadlock needs all four of these at once, which is useful: break any one and it
cannot happen.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-lock" title="Mutual exclusion"}
  The resource can only be held by one at a time. Usually not negotiable — that
  is what a lock is for.
  :::
  :::feature{icon="i-lucide-hand" title="Hold and wait"}
  A thread holds one thing while asking for another. Breakable: take everything
  you need at once, or nothing.
  :::
  :::feature{icon="i-lucide-shield-x" title="No pre-emption"}
  Nothing can take a lock away from a thread that holds it. Breakable with a
  timeout: `tryLock` gives up rather than waiting forever.
  :::
  :::feature{icon="i-lucide-refresh-cw" title="Circular wait"}
  A waits for B, B waits for A. **This is the one to break**, and the fix is
  almost embarrassingly simple.
  :::
::

## The fix, in one line

**Always take locks in the same order, everywhere in the codebase.**

```java [Transfer.java]
// Order by something stable and total — here, the department id.
Object first  = from.getId() < to.getId() ? from : to;
Object second = from.getId() < to.getId() ? to   : from;

synchronized (first) {
  synchronized (second) {
    // Both threads now grab the lower id first, so a cycle is impossible.
  }
}
```

If every thread acquires locks in ascending order of some fixed key, a cycle
cannot form, because a cycle requires somebody to go backwards. That is the whole
of deadlock prevention in practice, and it is worth knowing that the textbook
alternatives — detection, the banker's algorithm — are almost never used in
ordinary application code.

::side-note{kind="go-deeper"}
The same rule applies in databases, where deadlocks are far more common than in
application threads. Two transactions updating the same two rows in opposite
orders will deadlock, and the database will detect it and kill one of them with a
"deadlock victim" error. Updating rows in a consistent order — by primary key — is
the same fix. You will meet this again in the DBMS track.
::

## The scheduler

Now the other half of the chapter. Eight cores, four hundred processes, and every
one of them believes it is running continuously.

::flow{numbered direction="vertical" caption="A context switch. Between any two of your instructions, all of this can happen."}
  :::flow-step{label="A timer interrupt fires" icon="i-lucide-timer"}
  Every few milliseconds, the hardware interrupts whatever is running. Your
  program has no say in this and cannot detect it.
  :::
  :::flow-step{label="The kernel saves everything" icon="i-lucide-save"}
  All registers, including which instruction was next, into that process's
  record.
  :::
  :::flow-step{label="The scheduler chooses" icon="i-lucide-list-checks" highlight}
  Who runs next, from the ready queue. Modern Linux uses a scheme that picks
  whoever has had least processor time relative to their weight, so that nothing
  starves.
  :::
  :::flow-step{label="Load the new one" icon="i-lucide-upload"}
  Its registers back, its memory mapping switched in.
  :::
  :::flow-step{label="Resume" icon="i-lucide-play"}
  The chosen process continues on the exact instruction it was interrupted at,
  with no knowledge that four milliseconds and forty other programs passed.
  :::
::

::compare{caption="Two words that get used interchangeably and are not the same."}
  :::compare-side{label="Concurrency" verdict="neutral"}
  Several things **in progress** at once. Achievable on a single core by
  switching fast. Your laptop in 2005 was concurrent.
  :::
  :::compare-side{label="Parallelism" verdict="neutral"}
  Several things **executing** at the same instant. Needs more than one core.
  Eight cores means at most eight-way parallelism, however many threads you
  start.
  :::
::

This distinction has a practical edge: starting four hundred threads on an
eight-core machine does not make anything four hundred times faster. It makes it
slower, because each context switch costs a few microseconds and you have just
bought a great many of them.

::real-life{title="The service that got slower when we gave it more threads" source="A load test"}
Response times were poor, so somebody raised the thread pool from 50 to 500. It
got worse. The work was processor-bound on an eight-core machine, so 500 threads
meant the same total work plus enormous context-switching overhead and far more
memory for stacks. Going down to 16 was faster than either. The rule of thumb:
for processor-bound work, about the number of cores; for work that spends its
time waiting on a database or a network, many more, because those threads are
blocked and not competing.
::

## What confuses people here

That a thread is "running" most of the time. It is not, and this is why an
application server can handle hundreds of simultaneous requests on eight cores:
nearly all of those threads are blocked waiting for a database.

## What you can do now

You can recognise a deadlock, prevent one with lock ordering, and explain why
adding threads sometimes makes a program slower.

## Your turn

The university system has this code in two places. Find the deadlock and fix it
without removing either lock.

```java [FeeTransfer.java]
// In RefundService
synchronized (studentAccount) {
  synchronized (universityAccount) { refund(); }
}

// In PaymentService
synchronized (universityAccount) {
  synchronized (studentAccount) { charge(); }
}
```

::accordion
  :::accordion-item{label="The fix, and how to find this in real code" icon="i-lucide-check"}
  Circular wait: a refund and a payment happening at the same moment can each
  hold what the other wants. Fix by ordering both sites identically:

  ```java
  // Both services take the lower account number first, always.
  Object first  = studentAccount.getId() < universityAccount.getId()
                ? studentAccount : universityAccount;
  Object second = first == studentAccount ? universityAccount : studentAccount;

  synchronized (first) {
    synchronized (second) { /* refund or charge */ }
  }
  ```

  **How you find it in real code:** you usually do not, by reading. You find it
  when the service hangs, and then you take a thread dump — `jstack <pid>` in
  Java — which prints every thread and what it is waiting on. The JVM detects
  cycles and prints "Found one Java-level deadlock" with both threads named. That
  command is worth remembering now: it is the difference between a two-minute
  diagnosis and an afternoon.
  :::
::

## The interview question this answers

**"What is a deadlock and how do you prevent it?"**

Give the four conditions, then say which you actually break in practice and why:
consistent lock ordering, because the other three are either inherent to locking
or expensive to arrange. Then the detail that shows experience: mention
`jstack`, or the database equivalent where the engine detects the cycle and kills
one transaction as the deadlock victim. Candidates who can name the diagnostic
tool sound like people who have met the problem.
