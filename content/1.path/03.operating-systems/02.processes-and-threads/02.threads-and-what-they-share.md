Something much cheaper. A **thread** is another line of execution inside the same
process: it gets its own stack and its own registers, and it shares everything
else with its siblings.

That sharing is the entire point, and the entire problem.

## Why this matters in a job

Because every web application you will ever write is multithreaded whether you
asked for it or not. A server handling forty simultaneous requests is running
forty threads through your code at once, and if your code has one shared mutable
field in it, you have a bug that appears under load and never in testing.

::pull-quote
The single most expensive category of bug in my career has been code that was
correct when one person used it.
::

| | Process | Thread |
| --- | --- | --- |
| Memory | Its own | **Shared** with its siblings |
| Heap objects | Private | **Shared** |
| Stack | Its own | Its own |
| File descriptors | Its own | Shared |
| Cost to create | Expensive: copy everything | Cheap: a stack and some registers |
| A crash | Kills that process only | **Kills the whole process** |
| Talking to a sibling | Needs the kernel: pipes, sockets, shared memory | Just a variable |

That last row is why threads exist and why they are dangerous. Communication is
free, which means accidental communication is also free.

## Watch it break

The university's admissions service counts applications as they arrive. Two
threads, each counting five thousand.

```java [ApplicationCounter.java]
public class ApplicationCounter {
  static int received = 0;                       // shared: it lives on the heap

  public static void main(String[] args) throws Exception {
    Runnable intake = () -> {
      for (int i = 0; i < 5_000; i++) {
        received++;                              // ← the whole bug is this line
      }
    };

    Thread a = new Thread(intake);
    Thread b = new Thread(intake);
    a.start(); b.start();
    a.join();  b.join();

    System.out.println("Applications received: " + received);
  }
}
```

```text [Output — four runs]
Applications received: 7421
Applications received: 10000
Applications received: 8933
Applications received: 9564
```

It should be 10,000 every time. It is 10,000 sometimes, which is the worst
possible behaviour: it will pass your testing and fail in March.

## Why. The one line is three instructions

`received++` looks atomic. It is not. It is read, add, write, and a thread can be
interrupted between any two of them.

::

Two increments happened. The counter went up by one. That is a **race condition**:
the result depends on the order two threads happened to be scheduled in, and the
scheduler will not reproduce that order for you on request.

## Three fixes, and when each is right

```java [Fix1.java]
// 1. A lock. Only one thread inside the block at a time.
static int received = 0;
static final Object lock = new Object();

synchronized (lock) {
  received++;
}
```

```java [Fix2.java]
// 2. An atomic. The hardware does read-add-write as one indivisible step.
static final AtomicInteger received = new AtomicInteger();

received.incrementAndGet();
```

```java [Fix3.java]
// 3. Do not share it. Each thread counts its own, add up at the end.
long mine = 0;
for (int i = 0; i < 5_000; i++) mine++;
total.addAndGet(mine);                  // one shared write instead of five thousand
```

::pros-cons
---
title: Which of the three to reach for
pros:
  - Atomic (2) for a single counter or flag, simplest and fastest for this exact case
  - A lock (1) when several fields must change together and stay consistent with each other
  - No sharing (3) whenever you can arrange it: the only one with no cost and no subtlety
cons:
  - A lock is where deadlocks come from, and holding one while doing input or output is a classic mistake
  - Atomics only help one variable at a time; two atomics are not atomic together
  - Not sharing sometimes costs memory, and sometimes the problem genuinely needs shared state
---
::

::warning{icon="i-lucide-alert-triangle"}
`volatile` is not a fix for this. It guarantees that threads see each other's
writes; it does not make read-add-write indivisible. `volatile int received` with
`received++` has exactly the same bug and is a favourite interview trap.
::

## What confuses people here

That this is an exotic concern for people building databases. It is not. Every
Spring controller, every servlet, every request handler you write runs on a
thread from a pool, and a field on a controller is shared by every request in
flight.

::real-life{title="The bug that only existed on results day" source="A student portal"}
A controller kept the current student in a field so several methods could use it
without passing it around. It worked for a year. On results day, under real
concurrency, students began seeing each other's marks, because one request
overwrote the field between another request reading it and using it. One shared
mutable field, and a data-protection incident.
::

You can say exactly what threads share, write the three-instruction explanation

## Your turn

Run the broken counter above on your own machine, five times. Write down the five
numbers.

Then change `5_000` to `50` and run it five times again.

::accordion
  :::accordion-item{label="What you will see, and why it matters so much" icon="i-lucide-eye"}
  With 5,000 you will usually get wrong answers. With 50 you will almost always
  get the right one, because the threads are so short that one finishes before
  the other starts.

  That is the whole reason these bugs reach production. **The bug is invisible at
  small scale.** Your test with two requests passes. Your demonstration passes.
  It fails on the day four thousand students load the page at once, which is the
  day it matters most, and by then it is not reproducible on your laptop.

  This is why concurrency is reasoned about rather than tested into correctness,
  and it is a genuinely good thing to say in an interview.
  :::

## The interview question this answers

**"What is the difference between a process and a thread?"**

The most-asked operating systems question in existence. Answer with the table:
threads share the heap, the code and the file descriptors, and get their own
stack and registers. Then the two consequences that show you have been bitten:
communication between threads is free, which is why a shared mutable field is a
race condition; and a crash takes the whole process down with it, which is why
one bad thread can kill a server that was serving forty other requests
correctly.
