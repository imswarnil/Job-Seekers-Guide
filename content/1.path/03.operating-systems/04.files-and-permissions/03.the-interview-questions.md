The last set of questions in this track, and two of them appear in almost every
backend interview in this market.

::accordion
  :::accordion-item{label="1. What is virtual memory?" icon="i-lucide-message-circle"}
  **Weak:** "using the disk as RAM." That is swap, which is one consequence.

  **Strong:** every address a program uses is virtual, translated by hardware
  through a per-process page table. That buys isolation, process A's table
  simply has no entry pointing at B's frames, so it is a mechanism rather than a
  rule: a continuous view of scattered physical frames, shared read-only pages,
  and the option of keeping cold pages on disk.

  Then the symptom, which is what makes it sound lived-in: thrashing looks like a
  crash with an idle processor, and you confirm it by watching major page faults
  rather than processor use.
  :::

  :::accordion-item{label="2. Stack or heap?" icon="i-lucide-message-circle"}
  The **stack** is per thread, holds one frame per method call with its
  parameters and local variables, is freed automatically when the method returns,
  and is small, about 1 MB. Exhaust it and you get `StackOverflowError`, almost
  always from unbounded recursion.

  The **heap** is shared by every thread in the process, holds everything made
  with `new`, is reclaimed by garbage collection rather than by returning, and is
  large.

  The follow-up worth pre-empting: *"which is why a local variable is inherently
  thread-safe and a field on a shared object is not."* That connects this
  question to the concurrency one and very few candidates do it.
  :::

  :::accordion-item{label="3. Can a garbage-collected language leak memory?" icon="i-lucide-message-circle"}
  **Yes**, and answering "no" is the fastest way to reveal you have only read
  about this.

  Collection removes one kind of leak, forgetting to free, and leaves the other
  untouched: holding a reference you no longer need. Give the example: a `static
  Map` used as a cache with no eviction. Every entry is reachable from a static
  root forever, so nothing can ever be collected, and the service dies in the
  third month rather than in testing.
  :::

  :::accordion-item{label="4. How do you investigate an OutOfMemoryError?" icon="i-lucide-message-circle"}
  First, read which one: `Java heap space`, `unable to create new native thread`
  and `StackOverflowError` are three different investigations.

  For the heap one, the question is leak or sizing. A class histogram:
  `jcmd <pid> GC.class_histogram`, shows a count that makes no sense against the
  domain if it is a leak. Four million `Applicant` objects in a system with forty
  thousand applicants is not a sizing problem. And post-collection usage climbing
  over hours means a leak; returning to a baseline and spiking during one job
  means streaming, paging or batching.

  Then say what you would not do: raise `-Xmx` first. If it is a leak, that only
  changes the day it happens.
  :::

  :::accordion-item{label="5. How do Linux file permissions work?" icon="i-lucide-message-circle"}
  Three sets of bits, owner, group, other, checked in that order, **first match
  wins**. Read 4, write 2, execute 1.

  Two details separate this answer from a memorised one. Execute on a *directory*
  means traverse, so a permission error is frequently about a parent directory
  rather than the file named in the message. And first-match-wins means an owner
  can be locked out of their own file, because the group bits are never consulted
  for the owner.
  :::

  :::accordion-item{label="6. The application cannot write to a directory in production. Diagnose it." icon="i-lucide-message-circle"}
  A scenario question, and they want a sequence rather than an answer.

  Which user is the process running as, `ps -o user -p <pid>`, because it is
  rarely the user you deployed as. Then `ls -ld` on the directory **and every
  parent in the path**, because execute is needed at each level. Then `id` for
  that user to see its groups. The fix is `chown` to the right user, or adding
  that user to the owning group, not `chmod 777`.

  Closing with why not `777` is the part that gets remembered: it is every user
  and every process on the machine, which on a shared server is a genuine
  vulnerability rather than untidiness.
  :::
::
