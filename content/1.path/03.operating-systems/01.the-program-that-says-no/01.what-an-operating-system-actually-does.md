It was the operating system. Every `permission denied`, every `command not
found`, every time the prompt came back after a program finished: one program was
making those decisions, and it owns the machine in a way your programs never
will.

## Why this matters in a job

Because for the rest of your career, when something fails you will need to know
**which layer failed**. Your code, the language runtime, the operating system, or
the hardware. Four suspects, and people who cannot tell them apart debug by
changing things at random.

::real-life{title="The four-hour bug that was one layer down" source="A deployment, year two"}
Our service would not start on a new server. The error was from our own code:
`Cannot bind to port 8080`. Two of us read our configuration for four hours.
The cause was an operating system rule: ports below 1024 are privileged, another
process already held 8080, and the message our framework printed described the
symptom rather than the layer. Once somebody ran `lsof -i :8080` it took nine
seconds.
::

## The four jobs

An operating system is the program that runs other programs. It has four jobs
and every one of them exists because programs cannot be trusted.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-cpu" title="Share the processor"}
  Forty programs, one or eight processors. Somebody has to decide who runs, for
  how long, and who is interrupted. That somebody is the scheduler.
  :::
  :::feature{icon="i-lucide-memory-stick" title="Hand out memory"}
  Every program believes it has the machine's memory to itself. It does not, and
  keeping that illusion intact is most of what an operating system does.
  :::
  :::feature{icon="i-lucide-folder" title="Own the devices"}
  Disk, network, keyboard, screen. Your program never touches any of them. It
  asks, and the answer is sometimes no.
  :::
  :::feature{icon="i-lucide-shield" title="Keep programs apart"}
  Your program cannot read another program's memory, cannot open another user's
  files, cannot stop the machine. This is the job that produces "permission
  denied".
  :::
::

## Watch it say no

Three commands, three refusals, three different reasons. Run them.

```bash [Terminal]
cat /etc/shadow
```

```text [Output]
cat: /etc/shadow: Permission denied
```

`cat` did not refuse. `cat` asked the kernel to open a file and the kernel
checked who you are against who owns it, and returned an error. The program is
blameless; it is reporting somebody else's decision.

```bash [Terminal]
kill -9 1
```

```text [Output]
-bash: kill: (1) - Operation not permitted
```

Process 1 is the first process the system started and the parent of everything.
You are not allowed to kill it, and the refusal is not a policy in `kill`. It is
in the kernel.

```bash [Terminal]
mkdir /university
```

```text [Output]
mkdir: /university: Read-only file system
```

A third kind of no. Not who you are, but what the device allows. Same shape:
your program asked, the kernel decided.

::pull-quote
Your program never does anything. It asks, and something with more authority
either does it or refuses.
::

In user mode, the instructions that would let a program talk to the disk
**literally do not work**. The processor refuses them. So your program's only
route to anything outside its own memory is to ask the kernel, and the asking has
a name: a **system call**.

## What confuses people here

That the operating system is "running alongside" your program. It is not a
program sitting next to yours. It is the thing that starts yours, decides when it
runs, holds its memory, and can stop it. There is no negotiation.

::side-note{kind="go-deeper"}
This is also why a crashing program does not crash the machine. Your Java program
dividing by zero is a fault inside one user-mode process; the kernel notices,
kills that process, and everything else continues. A fault inside the kernel is a
different matter entirely, and that is what a kernel panic or a blue screen is.
::

## Where you have already seen this

Everything you learned in the terminal track was an operating system feature that
nobody named as one.

| What you learned | What it actually was |
| --- | --- |
| `chmod`, `chown`, `rwx` | The kernel's permission check on every file operation |
| `ps`, `kill`, a prompt that comes back | The process abstraction and the scheduler |
| `sudo` | Temporarily becoming a user the kernel trusts more |
| `Ctrl+C` stopping a program | A signal, delivered by the kernel |
| A pipe between two commands | A kernel-provided buffer connecting two processes |

## What you can do now

You can read a failure and say which layer produced it, and you know that
"permission denied" is one program's decision rather than a property of the
universe.

## Your turn

Run each of these and say, for each one, whether the refusal came from the
program, the kernel's permission check, or the device.

```bash [Terminal]
touch /usr/bin/hello
echo $?
ls --applicants
echo $?
```

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  `touch /usr/bin/hello` fails with `Permission denied`, exit status 1. That is
  the **kernel**: `/usr/bin` is owned by root and you are not root. `touch` asked
  and was refused.

  `ls --applicants` fails with `unrecognized option`, exit status 2 (or 1 on
  macOS). That is the **program**: `ls` read its own arguments, did not recognise
  one, and gave up before making any system call at all. The kernel was never
  involved.

  `echo $?` prints the exit status of the last command, which is the habit worth
  taking from this exercise: zero means success and anything else means a
  failure, and scripts everywhere depend on it.
  :::
::

## Check yourself

1. Why can a program not simply write to the disk itself and skip the kernel?
2. **An interviewer asks: "what does an operating system do?"** Answer with the
   four jobs rather than a textbook definition, and give one example of each.

## The interview question this answers

**"What is an operating system?"**

The weak answer is "it is an interface between the user and the hardware", which
is memorised and says nothing. The strong answer is the four jobs plus a concrete
example: "it shares the processor, hands out memory, owns the devices and keeps
programs apart. The last one is what you are seeing when a program gets
permission denied: the program did not refuse, it asked the kernel to open a
file and the kernel checked the owner."
