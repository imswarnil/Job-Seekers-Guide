title: Interview questions
description: Six questions on kernels, system calls and boot, each answered with something you can demonstrate rather than a definition you memorised.
minutes: 10
kind: quiz
---

The vocabulary is yours. Here is what gets asked about it, and what a good answer
contains.

::accordion
  :::accordion-item{label="1. What is an operating system?" icon="i-lucide-message-circle"}
  **Weak:** "An interface between the user and the hardware." Memorised, and
  every candidate says it.

  **Strong:** the four jobs, with an example. *"It shares the processor between
  programs, hands out memory, owns the devices, and keeps programs from touching
  each other. The last one is what you see when a command gives you permission
  denied: the command did not refuse, it asked the kernel to open a file and the
  kernel checked the owner against you."*
  :::

  :::accordion-item{label="2. What is the difference between user mode and kernel mode?" icon="i-lucide-message-circle"}
  It is a **processor** feature, not a software convention, which is the part
  that makes the answer sound real. In user mode the privileged instructions do
  not execute. So a user-mode program physically cannot talk to the disk; it can
  only trap into the kernel and ask.

  The follow-up is usually "why bother?" Answer: so that a bug in one program
  cannot take down the machine or read another program's data. It is why your
  Java program dividing by zero kills one process rather than the computer.
  :::

  :::accordion-item{label="3. What happens when you call read()?" icon="i-lucide-message-circle"}
  Walk the sequence: arguments into registers, trap instruction, processor
  switches to kernel mode, kernel saves your state, checks the file descriptor
  and permissions, copies bytes into your buffer (possibly waiting on the disk),
  restores your state, and returns to user mode on the next instruction.

  Then the sentence that gets you the follow-up you want: *"and that whole round
  trip costs roughly a microsecond even when nothing waits, which is why an
  unbuffered read of a 60 MB file took 47 seconds on my machine and the buffered
  version took 0.38."*
  :::

  :::accordion-item{label="4. Why is BufferedReader faster than FileReader?" icon="i-lucide-message-circle"}
  Not "because it buffers". Because an unbuffered read is one system call per
  call, and a buffer turns 60 million crossings into 7,500 by bringing back
  8 KB at a time and serving the rest from user memory.

  The generalisation is what marks you out: the same arithmetic is why you batch
  database inserts and why you do not call an HTTP API inside a loop. It is one
  idea, not three.
  :::

  :::accordion-item{label="5. What is process 1?" icon="i-lucide-message-circle"}
  The first user-mode process the kernel starts, and the ancestor of every other
  process on the machine, `systemd` on most Linux systems, `launchd` on macOS.
  You cannot kill it; the kernel refuses.

  Two things hang off it and both are worth mentioning. Orphaned processes are
  re-parented to it so somebody collects them when they exit. And in a container,
  *your application* is process 1, which is why a container stops the instant
  your main process exits.
  :::

  :::accordion-item{label="6. Container or virtual machine?" icon="i-lucide-message-circle"}
  Answer with the boot sequence rather than with "containers are lighter".

  A virtual machine runs the whole sequence: its own firmware, bootloader,
  **kernel** and process 1. A container skips the first three and shares the
  host's kernel, starting straight at process 1 with an isolated view of the file
  system, the network and the process table.

  Consequences, which is where the marks are: containers start in under a second,
  they are all just processes on the host so you can see them in the host's `ps`,
  and a Linux container needs a Linux kernel, so on macOS or Windows there is a
  Linux virtual machine underneath doing exactly what you said containers avoid.
  :::
::

## What all six have in common

::feature-list{columns="2"}
  :::feature{icon="i-lucide-eye" title="They are answered from something seen"}
  Every strong answer above contains an observation: a command that was refused,
  a number that was measured, a container that exited. Definitions are
  indistinguishable from memorisation, which is what the question is screening
  for.
  :::
  :::feature{icon="i-lucide-layers" title="They name the layer"}
  "The kernel refused, not the command" is the shape of every answer in this
  chapter. Being able to say which layer did something is the whole skill.
  :::
::
