Somebody is lying, and it is the most elegant lie in computing. Every process on
your machine believes it has a private, continuous block of memory starting at
address zero. Four hundred processes, eight gigabytes, and all of them are
telling the truth about what they can see.

## Why this matters in a job

Because three things you will meet constantly are all this one idea: why a
process cannot read another's memory, why your machine goes from fast to
unusable rather than gradually slowing when memory runs out, and what the
difference is between "my program uses 2 GB" and "my machine has 2 GB free".

## The idea

Every address your program uses is fake. The hardware translates it.

Memory is handed out in fixed-size blocks called **pages**, almost always 4 KB.
Physical memory is divided into **frames** of the same size. A page table maps
one to the other, per process, and a piece of hardware called the MMU does the
translation on **every single memory access** without your program knowing.

## What this buys

::feature-list{columns="2"}
  :::feature{icon="i-lucide-shield" title="Isolation, for free"}
  Process A's page table has no entry pointing at frame 22. So A cannot reach
  B's memory, not "is not allowed to", *cannot*, because the address does not
  translate to anything.
  :::
  :::feature{icon="i-lucide-shuffle" title="Continuous from scattered"}
  Your program sees one continuous block. The frames behind it are scattered all
  over physical memory. Nobody has to find a contiguous gap.
  :::
  :::feature{icon="i-lucide-hard-drive" title="More memory than you have"}
  A page that has not been touched recently can be written to disk and its frame
  given to somebody else. The program does not notice, except in time.
  :::
  :::feature{icon="i-lucide-copy" title="Sharing without copying"}
  Two processes running the same program can point at the *same* frames for the
  code. One copy of the JVM's instructions in memory, forty JVMs running.
  :::
::

## Watch a page fault

Your program touches an address whose page is not in physical memory. The MMU
cannot translate it, so it raises a **page fault**: an interrupt into the
kernel.

::flow{numbered direction="vertical" caption="A page fault. Steps 1 to 4 are microseconds; step 5 is milliseconds, which is why it matters."}
  :::flow-step{label="Your program reads an address" icon="i-lucide-mouse-pointer"}
  An ordinary instruction. Nothing special in your code.
  :::
  :::flow-step{label="The MMU finds no mapping" icon="i-lucide-x"}
  Page fault. The processor traps into the kernel, mid-instruction.
  :::
  :::flow-step{label="The kernel decides what kind" icon="i-lucide-git-branch"}
  Is this a page that was swapped out, a page of a file not read yet, or an
  address that is genuinely invalid?
  :::
  :::flow-step{label="Invalid → the program dies" icon="i-lucide-skull"}
  Segmentation fault. In Java you rarely see this, because the JVM checks first
  and gives you a `NullPointerException` instead.
  :::
  :::flow-step{label="Valid → fetch it, then resume" icon="i-lucide-download" highlight}
  Find a free frame, read the page in from disk, update the page table, restart
  the instruction. Your program continues, none the wiser, several milliseconds
  older.
  :::
::

::side-note{kind="performance"}
A page fault that has to read from disk costs roughly 100,000 times more than a
normal memory access. One is not a problem. A thousand a second is a machine
that has stopped working while still appearing busy.
::

## Thrashing: why it falls off a cliff

This is the part worth internalising, because it explains a behaviour everybody
has seen and few can account for.

When memory gets tight, the kernel writes least-recently-used pages to disk to
free frames. Fine, up to a point. Past that point, every process's *working set*
the pages it actually needs, no longer fits, so every process faults
immediately after being given the processor, and the kernel spends its time
moving pages rather than running anything.

::compare{caption="What you see, and what is happening."}
  :::compare-side{label="What it looks like" verdict="wrong"}
  The machine was fine. Then, over about ten seconds, it became completely
  unresponsive. The mouse moves, nothing else does, and the processor graph is
  low. It feels like a crash.
  :::
  :::compare-side{label="What it is" verdict="right"}
  **Thrashing.** The processor is idle because everything is blocked on disk.
  The machine is working extremely hard at moving pages and doing no useful work
  at all. Performance does not degrade smoothly here; it falls off a cliff.
  :::
::

::real-life{title="Why the server died at 40,000 rows and not at 4,000" source="A results export"}
An export loaded every `ExamResult` into a list before writing the file. At 4,000
rows it was 200 MB and fine. On results day it was 40,000 rows, about 2 GB, the
machine had 4 GB, and it began swapping. The job never finished and the whole
server became unresponsive, taking the student portal down with it. The fix was
to stream the rows instead of collecting them, which is a one-line change and a
concept you meet properly in the Java track.
::

## What confuses people here

That "virtual memory" means "using the disk as memory". Swap is one *consequence*
of virtual memory, not what it is. Virtual memory is the address translation, and
it is on all the time, on every machine, whether or not any swapping happens.

## What you can do now

You can explain process isolation as a mechanism rather than a rule, and you can
recognise thrashing from the symptom that gives it away: an unresponsive machine
with an idle processor.

## Your turn

Look at your own machine's memory and answer two questions.

::tabs
  :::tabs-item{label="Linux" icon="i-simple-icons-linux"}
  ```bash [Terminal]
  free -h
  # Faults for one process: minor need no disk, major do.
  ps -o pid,comm,min_flt,maj_flt -p $$
  ```
  :::

  :::tabs-item{label="macOS" icon="i-lucide-command"}
  ```bash [Terminal]
  vm_stat
  # "Pageins" are pages fetched from disk. "Swapins" mean real pressure.
  sysctl vm.swapusage
  ```
  :::
::

1. Add up the memory used by every process in `ps aux`. Is it more than your
   machine has? Why is that not a contradiction?
2. What is the difference between a minor and a major page fault?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1. It is almost certainly far more**, often several times. Three reasons,
  and all of them are this lesson: shared pages are counted once per process but
  exist once in RAM; pages that have been allocated but never touched have no
  frame at all; and some pages are on disk rather than in memory. "Virtual size"
  is what a process *can* address, and "resident size" is what is actually in
  RAM. `RSS` in `ps` is the second one, and it is the number that matters.

  **2. A minor fault** is resolved without touching the disk: the page is
  already in memory, it just was not mapped into this process yet: a shared
  library somebody else already loaded, or a page being allocated for the first
  time. Cheap, and there are millions of them.

  **A major fault** requires a disk read. Thousands of times more expensive.
  Thrashing is a machine doing nothing but major faults, which is why watching
  `maj_flt` climb is the direct way to confirm it.
  :::
::

## Check yourself

1. Why can process A not read process B's memory, stated as a mechanism rather
   than as a permission?
2. **An interviewer asks: "the machine is unresponsive but the processor is at
   ten per cent. What do you check?"**

## The interview question this answers

**"What is virtual memory?"**

Weak: "it is when the disk is used as RAM." That is swap, and it is a
consequence. Strong: every address a program uses is virtual and is translated
by hardware through a per-process page table, which gives isolation, a continuous
view of scattered frames, sharing of read-only pages, and the option of keeping
some pages on disk. Then the symptom, which is what makes it real: thrashing
looks like a crash with an idle processor, and the way to confirm it is major
page faults rather than processor use.
