Inside your process, something else is handing out smaller pieces. The kernel
deals in 4 KB pages; your program allocates a 40-byte `Applicant`. The thing in
between is the heap allocator, and in Java it also frees things without being
asked.

## Why this matters in a job

Because `OutOfMemoryError` is the most common way a Java service dies in
production, and there are three completely different causes with the same
headline. Telling them apart is a real skill and it is asked about directly.

## What garbage collection actually decides

Not "is this object still needed". A machine cannot know that. The rule is
narrower and entirely mechanical: **can this object still be reached by following
references from a root?** Roots are things like local variables on a live thread's
stack and static fields.

If nothing reaches it, nobody can ever use it again, so its memory can be reused.
That is the whole idea.

```java [Unreachable.java]
Applicant a = new Applicant("Anita Rao");   // reachable: `a` points at it
a = new Applicant("Vikram Shah");           // the first one is now unreachable
                                            // → collectable, at some future moment
```

::warning{icon="i-lucide-alert-triangle"}
"Unreachable" is not the same as "you have finished with it". An object you will
never look at again but which is still in a `static Map` is **reachable**, so it
is never collected. That is the definition of a memory leak in Java, and it is
the one people think cannot happen in a garbage-collected language.
::

## The three errors that look the same

```text [Output]
java.lang.OutOfMemoryError: Java heap space
```

**The heap is full and collection cannot free enough.** Two causes, and they are
opposite. Either you genuinely need more than `-Xmx` allows — loading 40,000
results into a list — or you have a leak: something reachable that should not be.
The way to tell them apart is whether usage climbs back down after collection.

```text [Output]
java.lang.OutOfMemoryError: unable to create new native thread
```

**Nothing to do with the heap.** Each thread needs about 1 MB of stack, and that
comes from the operating system, outside `-Xmx`. This is a thread leak — usually
creating threads in a loop instead of using a pool — or an operating system
limit. Raising `-Xmx` makes this *worse*, by leaving less room for stacks.

```text [Output]
java.lang.StackOverflowError
```

**One thread's stack, not the heap.** Too many nested calls, almost always
unbounded recursion. Nothing is out of memory anywhere else on the machine.

::compare{caption="Two heap exhaustions that need opposite fixes."}
  :::compare-side{label="Too much at once" verdict="neutral"}
  `resultRepository.findAll()` returning 40,000 rows into a list. Memory climbs,
  the job dies, and after a restart it is fine until the next export. Fix:
  stream, page, or process in batches. Raising `-Xmx` buys you until next year's
  intake.
  :::
  :::compare-side{label="A leak" verdict="wrong"}
  A `static Map` cache of applicants with no eviction. Memory climbs slowly over
  days, collections get longer and free less, and the service dies at 4 a.m.
  every Thursday. Raising `-Xmx` does nothing except move the day.
  :::
::

## Watch a leak happen

This is the most common real leak in a web application, and it looks harmless.

```java [ApplicantCache.java]
public class ApplicantCache {
  // "Just to avoid hitting the database twice for the same applicant."
  private static final Map<Long, Applicant> CACHE = new HashMap<>();

  public static Applicant get(long id) {
    return CACHE.computeIfAbsent(id, ApplicantCache::loadFromDatabase);
  }
}
```

Every applicant ever requested stays in that map until the process ends. One
intake is 40,000 applicants. The map is `static`, so it is reachable from a root
forever, so nothing is ever collected.

```java [ApplicantCache.java]
// The same idea with a ceiling and an eviction policy.
private static final Map<Long, Applicant> CACHE =
    Collections.synchronizedMap(new LinkedHashMap<>(256, 0.75f, true) {
      @Override protected boolean removeEldestEntry(Map.Entry<Long, Applicant> e) {
        return size() > 1_000;              // keep the 1,000 most recently used
      }
    });
```

Note it is also `synchronizedMap` now. A `static HashMap` in a web application
was two bugs: a leak and a race condition, from the previous chapter.

## Finding it, rather than guessing

```bash [Terminal]
# What the heap actually contains, live, sorted by size.
jcmd <pid> GC.class_histogram | head -15
```

```text [Output]
 num     #instances         #bytes  class name
----------------------------------------------
   1:       4128394      198162912  com.university.admissions.Applicant
   2:       4128394       99081456  java.lang.String
   3:          2041         489840  [B
```

Four million `Applicant` objects in a system with forty thousand applicants. That
is not a sizing problem, and no amount of `-Xmx` will fix it.

::side-note{kind="go-deeper"}
`jcmd <pid> GC.heap_info` shows how much is used before and after collection. The
distinguishing test: if used memory after a full collection keeps climbing over
hours, it is a leak. If it drops back to a steady baseline and only spikes during
a particular job, it is a sizing or streaming problem.
::

## What confuses people here

That garbage collection means memory leaks are impossible. It removes one kind of
leak — forgetting to free — and leaves the other entirely intact: keeping a
reference you do not need. Caches, listeners that are never removed, and static
collections are where they live.

## What you can do now

You can read the three errors apart, name the one diagnostic command that
separates a leak from a sizing problem, and recognise the `static Map` that
causes most of them.

## Your turn

For each, say which of the three errors you would expect and why.

1. A recursive method to total a department's fees, with no base case.
2. Reading a 4 GB attendance export with `Files.readAllBytes`.
3. A scheduled job that does `new Thread(task).start()` every second and never
   ends the threads.
4. A `static List<ExamResult>` that every published result is added to.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  1. **`StackOverflowError`.** One thread's stack, thousands of frames deep. The
     heap is untouched.
  2. **`OutOfMemoryError: Java heap space`**, and probably before that a
     `Requested array size exceeds VM limit`, since a Java array cannot exceed
     about 2 billion elements. A sizing problem, not a leak: stream it.
  3. **`unable to create new native thread`.** Outside the heap entirely. Use a
     pool.
  4. **`Java heap space`, from a leak.** It grows forever and is reachable from a
     static root, so collection can never free any of it. It will survive
     testing and die in the third month.
  :::

## The interview question this answers

**"How would you investigate an OutOfMemoryError?"**

Start by reading which one it is, because `Java heap space`, `unable to create
new native thread` and `StackOverflowError` need three different investigations.
For the heap one, the question is leak or sizing: take a class histogram and look
for a count that makes no sense against the domain, and watch whether post-collection
usage climbs over time or returns to a baseline. Then say what you would *not*
do, which is what marks the answer out: raise `-Xmx` first, because if it is a
leak that only changes the day it happens.
