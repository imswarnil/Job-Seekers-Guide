::accordion
  :::accordion-item{label="1. What problem does React solve?" icon="i-lucide-message-circle"}
  Not "it makes components". The imperative version makes you own every
  transition, and the bugs are the ones you **forget**: the spinner that never
  hides, the button left disabled, the error from last time still showing.

  Declaring what the screen looks like for a given state removes the category,
  because there are no transitions to forget.
  :::

  :::accordion-item{label="2. Why does mutating state not re-render?" icon="i-lucide-message-circle"}
  Because React compares references to decide what changed, so
  `applications.push(x)` then `setApplications(applications)` passes the same
  array and nothing looks different.

  Connect it back if you can: this is the stack-and-heap lesson from Java, where
  the variable holds an address and copying the variable does not copy the
  thing. Replace rather than mutate, `[...applications, x]`.
  :::

  :::accordion-item{label="3. When should you use `useEffect`?" icon="i-lucide-message-circle"}
  For synchronising with something **outside** React: a subscription, a timer, a
  browser API, focusing an element. Not for computing a value, which is just a
  calculation during render, and not for responding to a click, which belongs in
  the handler.

  Reaching for it by default is the single most common cause of confusing React
  code, and in modern React most data fetching belongs in a framework loader or
  a query library rather than in an effect at all.
  :::

  :::accordion-item{label="4. Why not use the array index as a key?" icon="i-lucide-message-circle"}
  Because the key tells React which item is which between renders. Sort or
  filter the list and React thinks item 0 is still item 0, keeps the old
  component with its old internal state, and whatever the registrar typed into
  row three's input now belongs to a different applicant.

  Say that consequence rather than "it is a warning". It is a bug where
  somebody's typed data moves to another person's row.
  :::

  :::accordion-item{label="5. This component re-renders too often. What do you do?" icon="i-lucide-message-circle"}
  A sequence, and the order is the answer. Profile first, because the guess is
  usually wrong. Then check for state that is too high in the tree, state at
  the top re-renders everything below it, and per-row pending state in a parent
  re-renders the whole table on every keystroke.

  Then check for derived state being stored rather than computed. `useMemo` and
  `useCallback` come last, when measurement says so, and saying they come last
  is the part being marked.
  :::

  :::accordion-item{label="6. How would you structure state for this screen?" icon="i-lucide-message-circle"}
  As little as possible, as low as possible. A filtered list and a count are
  **computed**, not stored, because two sources of truth will disagree. One
  `status` string beats four booleans that can be in eight impossible
  combinations.

  Then the specific one worth volunteering: per-row pending state belongs inside
  the row's own button, not in the parent. Several rows can then be saving at
  once and the table does not re-render, which is the difference between a table
  that feels fast and one that stutters at four hundred rows.
  :::
::
