Describing what the screen should look like, and letting something else work out
the difference. That is the whole idea, and everything else in React is detail
around it.

## Why this matters in a job

Because React is the most common front-end framework in this market by a wide
margin, and because the idea transfers: Vue, Svelte and Angular are all the same
sentence with different syntax.

## The problem it removes

```javascript [byhand.js]
// The imperative version: you own every transition.
async function shortlist(id) {
  button.disabled = true;
  button.textContent = 'Shortlisting…';
  spinner.hidden = false;
  errorBox.hidden = true;

  const response = await fetch(url, { method: 'POST' });

  spinner.hidden = true;
  if (!response.ok) {
    errorBox.hidden = false;
    errorBox.textContent = 'Failed';
    button.disabled = false;             // forget this one line and the button dies
  }
  button.textContent = 'Shortlist';
  row.classList.add('is-shortlisted');
}
```

Every state change is a list of instructions, and the bugs are all **forgotten
transitions**: the spinner that never hides, the button that stays disabled, the
error that shows from last time.

```jsx [Declarative.jsx]
function ShortlistButton({ applicationId }) {
  const [status, setStatus] = useState('idle');   // idle | saving | done | error

  async function shortlist() {
    setStatus('saving');
    try {
      const response = await fetch(`/api/applications/${applicationId}/shortlist`, {
        method: 'POST'
      });
      if (!response.ok) throw new Error(`Failed: ${response.status}`);
      setStatus('done');
    } catch {
      setStatus('error');
    }
  }

  return (
    <>
      <button onClick={shortlist} disabled={status === 'saving' || status === 'done'}>
        {status === 'saving' ? 'Shortlisting…' : status === 'done' ? 'Shortlisted' : 'Shortlist'}
      </button>
      {status === 'error' && <p role="alert">Could not shortlist. Try again.</p>}
    </>
  );
}
```

::pull-quote
You never say "hide the spinner". You say what the screen looks like when
`status` is `'done'`, and React works out the difference. A forgotten transition
is not possible, because there are no transitions.
::

## Components

A function that takes data and returns what the screen should look like.

```jsx [ApplicationRow.jsx]
function ApplicationRow({ application, onShortlist }) {
  return (
    <tr>
      <th scope="row">{application.applicantName}</th>
      <td>{application.score ?? 'Not marked'}</td>
      <td>{application.status}</td>
      <td>
        <ShortlistButton applicationId={application.id} onDone={onShortlist} />
      </td>
    </tr>
  );
}
```

Props go **down**, events go **up**. A child never reaches into its parent; it
calls a function the parent gave it. That one rule is most of what makes a
component tree possible to reason about.

## State: the three rules

::feature-list{columns="2"}
  :::feature{icon="i-lucide-minimize-2" title="As little as possible"}
  If a value can be **computed** from other state, do not store it. Storing
  `shortlistedCount` beside the list means two things that can disagree, which
  is the denormalisation lesson from the DBMS track.
  :::
  :::feature{icon="i-lucide-arrow-up" title="As low as possible"}
  Put it in the component that needs it. Lift it only when a sibling needs it
  too. State at the top of the tree re-renders everything below it.
  :::
  :::feature{icon="i-lucide-copy" title="Never modify it"}
  `setApplications([...applications, newOne])`, never `applications.push(...)`.
  React compares references to decide what changed, so a mutated array is the
  same reference and nothing re-renders.
  :::
  :::feature{icon="i-lucide-list" title="One variable, not four booleans"}
  `status` as `'idle' | 'saving' | 'done' | 'error'` cannot be both saving and
  done. Four separate booleans can be in eight impossible combinations, and one
  of them will happen.
  :::
::

## The three mistakes everybody makes

### 1. Mutating state

```jsx [mutate.jsx]
// Nothing happens. The array is the same object, so React sees no change.
applications.push(newApplication);
setApplications(applications);

// Correct: a new array.
setApplications([...applications, newApplication]);
setApplications(applications.filter(a => a.id !== removedId));
setApplications(applications.map(a => a.id === id ? { ...a, status: 'SHORTLISTED' } : a));
```

This is the stack-and-heap lesson from Java: the variable holds a reference, and
copying the reference does not copy the thing.

### 2. Storing derived state

```jsx [derived.jsx]
// Two sources of truth. They will disagree.
const [applications, setApplications] = useState([]);
const [shortlistedCount, setShortlistedCount] = useState(0);

// One source of truth. It cannot disagree with itself.
const [applications, setApplications] = useState([]);
const shortlistedCount = applications.filter(a => a.status === 'SHORTLISTED').length;
```

### 3. Reaching for `useEffect`

```jsx [effect.jsx]
// WRONG: an effect to compute something. Renders twice and can go stale.
const [filtered, setFiltered] = useState([]);
useEffect(() => {
  setFiltered(applications.filter(a => a.score >= cutoff));
}, [applications, cutoff]);

// RIGHT: it is just a calculation during render.
const filtered = applications.filter(a => a.score >= cutoff);
```

::warning{icon="i-lucide-alert-triangle"}
`useEffect` is for **synchronising with something outside React**: a
subscription, a timer, a browser API, focusing an element. It is not for
computing values and it is not for responding to a click — that belongs in the
event handler. Reaching for it by default is the single most common cause of
confusing React code, and in modern React most data fetching belongs in a
framework's loader or a query library rather than in an effect at all.
::

## Keys, which are not cosmetic

```jsx [keys.jsx]
{applications.map(a => <ApplicationRow key={a.id} application={a} />)}
```

The key tells React which item is which between renders. Using the array **index**
as a key breaks the moment the list is sorted or filtered: React thinks item 0 is
still item 0, so it keeps the old component with the old internal state, and
whatever the registrar typed into row 3's input now belongs to a different
applicant.

::pull-quote
`key={index}` on a list that can be reordered is not a warning to silence. It is
a bug where somebody's typed input moves to another person's row.
::

## What you can do now

You can describe a screen as a function of state, keep the state minimal and low,
and avoid the three mistakes that account for most confusing React code.

## Your turn

Build the applications table in React.

1. Load applications from your API, with loading and error states.
2. Filter by minimum score, live.
3. Shortlist a row, with its own pending state, updating from the server's
   response.
4. Then: how many pieces of state does your component actually have? Remove any
   that can be computed.

::accordion
  :::accordion-item{label="What the state should be, and the one people get wrong" icon="i-lucide-list-checks"}
  ```jsx
  const [applications, setApplications] = useState([]);
  const [loadState, setLoadState] = useState('loading');   // loading | ready | error
  const [cutoff, setCutoff] = useState(0);

  // NOT state. Calculated every render, and cannot disagree with the list.
  const visible = applications.filter(a => a.score != null && a.score >= cutoff);
  const shortlistedCount = applications.filter(a => a.status === 'SHORTLISTED').length;
  ```

  **Three pieces of state.** Most first attempts have six or seven, because
  `visible`, `shortlistedCount` and `isEmpty` all get stored.

  **The one people get wrong** is per-row pending state. Putting
  `savingId` in the parent means only one row can be saving at a time, and the
  parent re-renders the whole table on every keystroke of that state. Put the
  pending state **inside** `ShortlistButton`, where it belongs: each button owns
  its own, several can be in flight, and the table does not re-render.

  That is the "as low as possible" rule doing real work, and it is the difference
  between a table that feels fast and one that stutters at 412 rows.
  :::
::

## The interview question this answers

**"What problem does React solve?"**

Not "it makes components". The imperative version requires you to own every
transition, and the bugs are forgotten ones: the spinner that never hides, the
button left disabled. Declaring what the screen looks like for a given state
removes the category.

Then the two that follow: state must be replaced rather than mutated, because
React compares references; and `useEffect` is for synchronising with something
outside React, not for computing values, which is the mistake that makes most
React code confusing.
