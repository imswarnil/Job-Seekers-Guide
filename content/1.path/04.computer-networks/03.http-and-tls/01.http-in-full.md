The agreement. HTTP is text, and once you have seen one raw request there is
nothing mysterious left in it.

## Why this matters in a job

Because you will spend the rest of this course building things that speak HTTP,
and because "what does 401 mean versus 403" and "is PUT idempotent" are asked
constantly and have exact answers.

## A request is four parts

```http [Request]
GET /api/applicants?minScore=60&programme=CSE HTTP/1.1
Host: university.edu
Authorization: Bearer eyJhbGciOiJIUzI1...
Accept: application/json
User-Agent: Mozilla/5.0

```

::code-trace{caption="Four parts, and the blank line is load-bearing."}
```http [Request]
GET /api/applicants?minScore=60&programme=CSE HTTP/1.1
Host: university.edu
Authorization: Bearer eyJhbGciOiJIUzI1...
Accept: application/json

(body would go here)
```

  :::code-trace-step{lines="1" caption="The request line: what to do, what to do it to, and which version of the protocol. The bit after ? is the query string."}
  :::
  :::code-trace-step{lines="2" caption="Host. Mandatory since HTTP/1.1, and the reason one IP address can serve a thousand websites: the server reads this to know which site you meant."}
  :::
  :::code-trace-step{lines="3-4" caption="Headers. Who you are, what formats you can handle. Any number of them, one per line."}
  :::
  :::code-trace-step{lines="5-6" caption="A blank line, then the body. The blank line is how the server knows the headers ended — a GET has nothing after it."}
  :::
::

And a response is the same shape with a status line instead of a request line.

```http [Response]
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 1842
Cache-Control: max-age=60

[{"applicantId":4182,"name":"Anita Rao","score":78}, ...]
```

## Send one by hand

This is worth doing once, because it makes the protocol concrete forever.

```bash [Terminal]
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80
```

```text [Output]
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
...
```

You just spoke HTTP with no library, no browser and no framework. That is the
entire protocol.

## The methods that mean something

Two properties decide most API arguments, and they are not opinions.

| Method | Safe? | Idempotent? | Use it for |
| --- | --- | --- | --- |
| `GET` | Yes | Yes | Reading. Must never change anything. |
| `POST` | No | **No** | Creating something new, where twice means two |
| `PUT` | No | Yes | Replacing a resource entirely at a known address |
| `PATCH` | No | Usually not | Changing some fields |
| `DELETE` | No | Yes | Removing. Deleting twice leaves it deleted. |

**Safe** means it changes nothing. **Idempotent** means doing it twice has the
same effect as doing it once.

::compare{caption="Why idempotency is not academic."}
  :::compare-side{label="POST /applications" verdict="wrong"}
  The network drops the response. Your app retries. The applicant now has two
  applications and pays twice. POST is not idempotent, so a retry is a second
  action.
  :::
  :::compare-side{label="PUT /applications/APP-2026-00417" verdict="right"}
  The same retry replaces the same resource with the same content. Doing it five
  times leaves exactly one application. The client chose the id, which is what
  makes it addressable.
  :::
::

::side-note{kind="go-deeper"}
This is why real payment APIs make you send an **idempotency key** with a POST: a
unique string you generate, which the server remembers, so a retry with the same
key returns the original result instead of charging again. It is POST made
idempotent by hand, and it exists precisely because "the request succeeded and
the response was lost" is a real and common event.
::

## The status codes worth knowing

Ranges first: **2xx** worked, **3xx** go elsewhere, **4xx** you made a mistake,
**5xx** the server made a mistake. That division is the answer to most of the
question.

| Code | Means | The distinction that gets asked |
| --- | --- | --- |
| `200 OK` | Here it is | |
| `201 Created` | Made it, and the `Location` header says where | The correct reply to a successful POST |
| `204 No Content` | Worked, nothing to send back | The usual reply to a DELETE |
| `301` / `302` | Moved permanently / temporarily | 301 is cached, sometimes forever. Be careful. |
| `304 Not Modified` | Your cached copy is still good | The server sent no body at all. This is most of what makes the web fast. |
| `400 Bad Request` | Malformed. I cannot parse this. | |
| `401 Unauthorized` | **I do not know who you are** | Badly named: it means unauthenticated |
| `403 Forbidden` | I know who you are and you may not | ⚠️ The pair 401 vs 403 is asked constantly |
| `404 Not Found` | No such thing | Sometimes deliberately returned instead of 403, so you cannot tell whether it exists |
| `409 Conflict` | Clashes with the current state | Duplicate application number |
| `422 Unprocessable` | Parsed fine, failed validation | Score of 150 |
| `429 Too Many Requests` | Slow down | Comes with `Retry-After` |
| `500 Internal Server Error` | We broke. Unhandled exception. | |
| `502 Bad Gateway` | A proxy could not reach the thing behind it | |
| `503 Service Unavailable` | Up, and refusing right now. Overloaded or in maintenance. | |
| `504 Gateway Timeout` | A proxy waited for the thing behind it and gave up | |

::real-life{title="Why 502 and 504 are the two you will actually see" source="Every production incident"}
You almost never see your application's 500 directly, because there is a load
balancer or a reverse proxy in front of it. When your app crashes, the proxy
cannot connect and you get **502**. When your app is alive but a query is taking
ninety seconds, the proxy gives up and you get **504**. Those two codes tell you
which it is before you open a single log, and that is a diagnosis most people
guess at.
::

## Stateless, and what that forces

HTTP has no memory. Two requests from the same person are unrelated as far as the
protocol is concerned, which is why every request has to carry its own proof of
identity: a cookie, or an `Authorization` header.

That constraint is what makes it possible to run four copies of your application
behind a load balancer, because any of them can serve any request. It is also
what breaks the moment you keep a user's state in a field on a controller, which
is the concurrency lesson from the previous track arriving in a new costume.

## What you can do now

You can read a raw request and response, choose a method for a reason rather than
by habit, and pick the correct status code, which is one of the more visible
signs of an engineer who knows what they are doing.

## Your turn

```bash [Terminal]
curl -i https://api.github.com/users/imswarnil
curl -i https://api.github.com/users/definitely-not-a-real-user-91723
curl -i -X DELETE https://api.github.com/users/imswarnil
```

1. What status does each return, and what does the third one tell you about
   authentication versus authorisation?
2. In the university system, which status for: an applicant who does not exist;
   a score of 150 submitted; a staff member trying to shortlist for another
   department; the same application submitted twice?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  1. `200`, then `404`, then `404` again rather than `403` or `405`. GitHub
     deliberately returns 404 where you are not permitted, so an unauthenticated
     caller cannot use the response to learn what exists. That is a real
     security decision and a good thing to mention in an interview.
  2. **404** for the missing applicant. **422** for score 150: the request
     parsed fine and failed a rule; 400 would say you could not parse it.
     **403** for the wrong department. You know who they are and they may not.
     **409** for the duplicate, because it conflicts with the current state, and
     the response should say which existing application it clashes with.
  :::
::

2. **An interviewer asks: "is PUT idempotent, and why does that matter?"**

## The interview question this answers

**"What is the difference between PUT and POST?"**

The weak answer is "PUT updates and POST creates", which is a rule of thumb that
falls apart immediately. The real answer is idempotency: PUT at a known address
can be repeated with the same result, POST cannot, so a retry after a lost
response creates a second thing. Then the practical consequence, idempotency
keys on payment APIs, which shows you know why anybody cares.
