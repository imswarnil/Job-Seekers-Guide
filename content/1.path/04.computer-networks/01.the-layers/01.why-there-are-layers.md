Never one machine. And the moment there are two, a problem appears that does not
exist inside a single computer: the thing in between is unreliable, and it does
not care about you.

Layers are how that is made survivable.

## Why this matters in a job

Because every network error you will ever read is a layer complaining. Once you
can place the error in a layer, you have eliminated three quarters of the
possible causes before opening anything.

::compare{caption="Four errors. Read them as layers and each one names its own suspect."}
  :::compare-side{label="What a beginner sees" verdict="wrong"}
  `Connection refused`, `Name or service not known`, `Connection timed out`,
  `404 Not Found`. Four ways of saying "the network is broken", all equally
  mysterious, all leading to the same reflex of restarting things.
  :::
  :::compare-side{label="What they actually say" verdict="right"}
  `Name or service not known` → **DNS**: the name never became a number.
  `Connection refused` → **the machine was reached** and nothing is listening on
  that port. `Connection timed out` → the packets went out and nothing came
  back; a firewall or a dead machine. `404` → everything worked perfectly and
  the *application* says there is no such thing.
  :::
::

That last one matters most. A 404 means the network succeeded. People restart
servers over 404s constantly.

## Each one exists because of the one below

This is the part worth understanding rather than memorising. Read it bottom-up
and each layer is a fix.

::flow{numbered direction="vertical" caption="Bottom to top. Every layer is a complaint about the one beneath it."}
  :::flow-step{label="Link: I can reach the next device" icon="i-lucide-cable"}
  Wifi or a cable gets bits to your router. That is all it can do. **Problem it
  leaves:** the machine you want is nine hops away and the link layer has never
  heard of it.
  :::
  :::flow-step{label="Internet: I can reach any machine" icon="i-lucide-globe"}
  IP gives every machine an address and every router a rule for which way to
  pass a packet. **Problems it leaves:** packets can be lost, duplicated,
  reordered, and there is no way to say which program on that machine.
  :::
  :::flow-step{label="Transport: every byte, in order, to the right program" icon="i-lucide-arrow-down-up" highlight}
  TCP numbers the bytes, acknowledges them, resends the lost ones and puts them
  back in order; ports say which program. **Problem it leaves:** you now have a
  reliable stream of bytes and no agreement about what they mean.
  :::
  :::flow-step{label="Application: we both know what the bytes mean" icon="i-lucide-message-square"}
  HTTP says the first line is a method and a path, then headers, then a blank
  line, then a body. Both ends agree, so the bytes become a request.
  :::
::

::side-note{kind="go-deeper"}
The seven-layer OSI model is what your syllabus will examine you on, and you
should know the names, physical, data link, network, transport, session,
presentation, application. It is a reference model rather than a description of
anything that was built. The internet runs on the four above, session and
presentation never became real separate layers, and an interviewer asking about
networks in a job context means the four.
::

::real-life{title="Why this diagram saves you an afternoon" source="A service that could not reach a database"}
Our application could not connect to the database. The error was
`Connection timed out`. Because that is a *transport* error rather than a DNS
one, we knew the name had resolved, so it was not DNS; and because it timed out
rather than being refused, we knew the packets were leaving and nothing was
coming back, which means something is silently dropping them rather than the
database being down. It was a security group rule. Ten minutes, because the
error named its own layer.
::

## What confuses people here

That layers are a diagram in a textbook. They are the actual implementation: TCP
is code in your kernel, IP is code in your kernel and in every router between
here and there, and HTTP is a library in your program. When people say
"somewhere in the network", they usually mean they have not decided which of
these is the suspect.

## What you can do now

You can read four common network errors and name the layer each one came from,
which is most of the diagnosis.

## Your turn

For each error, name the layer and say what you would check first.

1. `java.net.UnknownHostException: db.university.internal`
2. `java.net.ConnectException: Connection refused`
3. `java.net.SocketTimeoutException: Read timed out`
4. `HTTP 503 Service Unavailable`
5. `javax.net.ssl.SSLHandshakeException: PKIX path building failed`

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  1. **Application layer, DNS.** The name never became an address. Check the
     spelling, then whether this machine can resolve it at all: `dig` or
     `nslookup`. Nothing has been sent to any database.
  2. **Transport.** The machine was reached and actively said no, which means
     nothing is listening on that port. Either the database is not running or you
     have the wrong port. A refusal is good news: it means everything below
     worked.
  3. **Transport.** The connection was established and then the other end went
     quiet. Usually a slow query or an overloaded server, not a network problem
     at all. Note the difference from a *connect* timeout, which is packets
     vanishing on the way.
  4. **Application.** The whole network worked. The server is up, reachable and
     telling you it cannot serve right now. Restarting the network changes
     nothing.
  5. **Between transport and application: TLS.** The connection was established
     and the certificate could not be trusted. Usually a self-signed or expired
     certificate, or a missing intermediate. Chapter three.
  :::
::

## Check yourself

1. Why is `Connection refused` better news than `Connection timed out`?
2. **An interviewer asks: "what are the layers of the network stack?"** Name the
   four and say what problem each one solves for the one below.

## The interview question this answers

**"Explain the OSI or TCP/IP model."**

Almost every candidate lists the layers and stops, which sounds exactly like
memorisation because it is. The answer that works explains each layer as a fix
for the one below: the link layer reaches the next device, so IP adds addressing
for any machine anywhere; IP can lose and reorder packets, so TCP adds ordering,
acknowledgement and ports; TCP gives you bytes with no meaning, so HTTP agrees a
format. Then the pay-off: name an error for each layer.
