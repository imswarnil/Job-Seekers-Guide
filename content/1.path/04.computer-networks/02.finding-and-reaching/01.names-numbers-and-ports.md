The network has no idea what names are. It moves packets between numbers.
So before anything can happen, `university.edu` has to become `93.184.216.34`,
and that translation is a distributed database older than the web.

## Why this matters in a job

Because DNS is the first thing to fail and the last thing people check. "It works
on my machine" is a DNS answer more often than any other single cause, and
"have you tried it by IP address" is the question that splits a network problem
from a naming one in ten seconds.

A port is a 16-bit number, so 0 to 65535. The ones you will meet constantly:

| Port | What listens | Note |
| --- | --- | --- |
| 22 | SSH | How you reach a server with no screen |
| 80 | HTTP | Privileged: below 1024, so it needs elevated rights to bind |
| 443 | HTTPS | Same, and where essentially all real traffic goes |
| 3306 | MySQL | |
| 5432 | PostgreSQL | |
| 6379 | Redis | |
| 8080 | "HTTP, unprivileged" | Why every development server uses it: no `sudo` needed |
| 3000 | Node and friends | Convention, nothing more |

::side-note{kind="security"}
A database port open to the internet is one of the most common serious
misconfigurations there is. 5432 and 3306 should be reachable from your
application's machines and from nowhere else. This is a firewall rule, not
something the database is responsible for, and it is a real interview question in
its own right.
::

## How a name becomes a number

DNS is a hierarchy, read right to left, and the answer is cached at every step.

::flow{numbered direction="vertical" caption="The first time. Every later lookup usually stops at step one or two."}
  :::flow-step{label="Your own machine" icon="i-lucide-laptop"}
  The browser's cache, then the operating system's, then `/etc/hosts`: a plain
  text file that overrides everything, which is how you point a name at your own
  laptop for testing.
  :::
  :::flow-step{label="Your resolver" icon="i-lucide-server"}
  Your router or your provider, or one you chose such as 1.1.1.1. If it has the
  answer cached, you get it here, in a millisecond.
  :::
  :::flow-step{label="A root server" icon="i-lucide-globe"}
  Thirteen addresses, known to every resolver. It does not know
  `university.edu`. It knows who is responsible for `.edu`.
  :::
  :::flow-step{label="The .edu servers" icon="i-lucide-signpost"}
  They do not know the answer either. They know who is responsible for
  `university.edu`.
  :::
  :::flow-step{label="The authoritative server" icon="i-lucide-check" highlight}
  The one that actually holds the record. It answers `93.184.216.34`, with a
  time-to-live saying how long the answer may be cached.
  :::
::

## Watch it happen

```bash [Terminal]
dig +short github.com
```

```text [Output]
140.82.121.4
```

```bash [Terminal]
# The whole journey, one step at a time.
dig +trace github.com | head -20
```

The record types you will actually meet:

| Type | Means | Example |
| --- | --- | --- |
| `A` | This name is this IPv4 address | `university.edu → 93.184.216.34` |
| `AAAA` | The same, for IPv6 | |
| `CNAME` | This name is an alias for that name | `www.university.edu → university.edu` |
| `MX` | Send mail for this domain here | |
| `TXT` | Arbitrary text. Used for domain verification and mail policy | |
| `NS` | These servers are authoritative for this domain | |

## The cache, and why a change takes hours

The TTL is why a DNS change is not instant.

```bash [Terminal]
dig github.com | grep -A1 "ANSWER SECTION"
```

```text [Output]
;; ANSWER SECTION:
github.com.		42	IN	A	140.82.121.4
```

That `42` is seconds remaining before this cached answer expires. If a record's
TTL is 3,600 and you change it, resolvers that already answered will keep giving
the old address for up to an hour, and there is nothing you can do about it.

::real-life{title="Why you lower the TTL before you move anything" source="A domain migration"}
We moved a site to a new server on a Saturday, changed the DNS record, and half
the traffic kept arriving at the old machine until Monday. The record's TTL was
86,400: one day. The correct sequence, learned the hard way: lower the TTL to
60 seconds a day *before* the move, make the change, watch the traffic shift in
a minute, then put the TTL back up. Everybody learns this once.
::

## What confuses people here

That DNS is part of the connection. It is not. DNS is a completely separate
conversation, usually over UDP on port 53, that finishes before any connection to
your actual server is attempted. That is why an `UnknownHostException` means
nothing was ever sent to the server, and why a DNS failure and a server failure
are entirely different investigations.

## What you can do now

You can turn a name into an address by hand, read the record types, and explain
why a DNS change is not instant.

## Your turn

```bash [Terminal]
dig +short news.ycombinator.com
dig +short www.github.com          # note what type comes back
dig university.edu | grep -E "ANSWER SECTION" -A2
cat /etc/hosts
```

1. What record type does `www.github.com` return first, and what does that tell
   you?
2. Add a line to `/etc/hosts` pointing a made-up name at `127.0.0.1` and `ping`
   it. Which step of the five did that intercept?
3. Your laptop can reach a server by IP but not by name. Which layer is broken,
   and what is the next command you run?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  1. A `CNAME`, pointing at another name, which then resolves to an address.
     That is how a site puts a content delivery network in front of itself
     without changing addresses: the alias target changes and the name you use
     does not.
  2. **Step one.** `/etc/hosts` is consulted before any resolver is asked, which
     is exactly why it is the standard way to test a site locally before
     pointing its real DNS at anything. It is also a genuinely useful debugging
     tool: point a production hostname at a staging server for your machine only.
  3. **DNS, in the application layer.** Next command: `dig <name>`. If that fails
     but `dig @1.1.1.1 <name>` succeeds, your resolver is the problem rather
     than the record.
  :::
::

## Check yourself

1. What does a port identify, and what identifies the machine?
2. **An interviewer asks: "you changed a DNS record an hour ago and some users
   still reach the old server. Why?"**

## The interview question this answers

**"What is DNS and how does it work?"**

Walk the hierarchy right to left, root, then the top-level domain, then the
authoritative server, and mention that every step caches with a TTL. Then the
operational consequence, which is where the marks are: a change is not instant,
you lower the TTL before a migration rather than after, and `UnknownHostException`
means nothing ever reached your server so the server is not the suspect.
