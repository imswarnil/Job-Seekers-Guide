IP will happily lose your packet, duplicate it, or deliver it third. TCP is the
agreement that turns that into a stream of bytes that arrive once, in order.

It is not free, and the price is round trips.

## Why this matters in a job

Because "the API is slow" is usually not about bandwidth. It is about how many
times something had to cross an ocean and back, and once you can count round
trips you can explain performance that otherwise looks like magic.

Both sides pick a starting number and acknowledge the other's. From then on every
byte has a number, which is how "in order" and "did it arrive" are both solved.

## How a lost packet is noticed

```text [What the sender sees]
sent bytes 1000-1499  → ACK 1500 received      ✓
sent bytes 1500-1999  → (nothing)
sent bytes 2000-2499  → ACK 1500 received      ← "still waiting for 1500"
sent bytes 2500-2999  → ACK 1500 received      ← again
sent bytes 3000-3499  → ACK 1500 received      ← three duplicates: resend now
```

The receiver keeps saying "I am still expecting 1500". Three duplicate
acknowledgements and the sender retransmits without waiting for a timeout. This
is why a lossy connection is *slow* rather than broken: nothing is lost from your
program's point of view, it just takes longer.

::side-note{kind="go-deeper"}
TCP also slows down when it detects loss, because loss historically meant
congestion. It starts cautiously, doubles its sending rate each round trip until
something is lost, then backs off, "slow start" and "congestion avoidance". The
practical consequence is that a brand new connection is slower than a warmed-up
one for the first few round trips, which is one of several reasons connection
reuse matters.
::

## Latency is not bandwidth

The single most useful idea in this lesson, and one most developers never state
clearly.

::compare{caption="Bangalore to Frankfurt, a 1 MB response."}
  :::compare-side{label="Bandwidth" verdict="neutral"}
  How much fits through per second. A 1 MB response on a 100 Mbps link takes
  about 80 ms of actual transfer. Buying a faster connection improves this.
  :::
  :::compare-side{label="Latency" verdict="right"}
  How long one trip takes: about 140 ms each way, limited by the speed of light
  in fibre and the routers along the way. **Nothing you buy makes this shorter.**
  Six round trips is 1.7 seconds before a single byte of content.
  :::
::

Count what a first page load actually costs on a fresh connection:

| Step | Round trips |
| --- | --- |
| DNS lookup (uncached) | 1 |
| TCP handshake | 1 |
| TLS handshake (1.3) | 1 |
| HTTP request and response | 1 |
| **Total before any content** | **4** |

At 140 ms each, that is 560 ms of waiting for a page that transfers in 80 ms.
This is why performance work is largely about *removing round trips*: connection
reuse, caching, putting servers nearer the user, and not calling an API in a loop.

::real-life{title="The dashboard that took nine seconds and transferred 40 KB" source="A report screen"}
The dean's dashboard made 34 separate API calls, one per widget, in sequence. On
the office network that was fine. Opened from home it was nine seconds, and the
total data was 40 kilobytes. Nothing was slow. Thirty-four sequential round trips
were slow. Fetching them in parallel took it to 1.1 seconds, and combining them
into one call took it to 300 milliseconds.
::

## TCP or UDP

::pros-cons
---
title: TCP
pros:
  - Every byte arrives, once, in order. You never handle loss yourself
  - Flow control, so a fast sender cannot drown a slow receiver
  - What HTTP, SSH and every database connection use
cons:
  - A handshake before any data
  - Head-of-line blocking: one lost packet stalls everything behind it
  - Retransmission is wrong for anything where late data is useless
---
::

::pros-cons
---
title: UDP
pros:
  - No handshake, no ordering, no retransmission, send and forget
  - Right when late data is worthless: live video, voice, game position updates
  - What DNS uses, because a query and a reply fit in one packet each
cons:
  - You handle loss, ordering and duplication yourself, or accept them
  - No congestion control by default, so it can be antisocial
---
::

::note
The honest summary for an interview: TCP when every byte must arrive, UDP when
arriving *late* is worse than not arriving. A dropped frame in a video call is
invisible; a frame delivered 400 ms late is a stutter.
::

## What you can do now

You can count round trips, explain why a page is slow from another country
without blaming bandwidth, and say when UDP is the right answer.

## Your turn

```bash [Terminal]
# Round-trip time to a few places. Look at the time, not the packet loss.
ping -c 4 1.1.1.1
ping -c 4 github.com

# Watch the handshake itself.
curl -w "dns %{time_namelookup}s | connect %{time_connect}s | tls %{time_appconnect}s | first byte %{time_starttransfer}s | total %{time_total}s\n" \
     -o /dev/null -s https://github.com
```

1. Which part of that `curl` output is the TCP handshake, and which is TLS?
2. Run the `curl` twice in a row. Which number drops, and why?
3. A page makes 30 sequential API calls of 2 KB each to a server 150 ms away.
   How long does it take, and what is the one change that helps most?

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  1. `connect` minus `dns` is the TCP handshake. `tls` minus `connect` is the
     TLS handshake on top of it. Being able to read this one line is genuinely
     useful in an interview and in a job.
  2. `dns` drops to almost zero, because the answer is now cached locally. This
     is the cheapest demonstration of DNS caching there is.
  3. **About 4.5 seconds**, 30 × 150 ms, and the data is 60 KB, so bandwidth is
     irrelevant. The biggest single win is doing them in parallel, which takes it
     to roughly 150 ms. The better fix is one call that returns everything, which
     also removes 29 opportunities for one of them to fail.
  :::
::

## Check yourself

1. Why does a new TCP connection cost a round trip before any data moves?
2. **An interviewer asks: "why is our API slow for users in another country when
   the payload is tiny?"**

## The interview question this answers

**"TCP or UDP, and why?"**

Give the trade rather than the list: TCP guarantees delivery and order at the
cost of a handshake and head-of-line blocking; UDP gives you neither and costs
nothing. Then the rule that decides it: use UDP when late data is worse than
missing data, such as voice or live video, and TCP for everything where every
byte must arrive. Mentioning that DNS uses UDP because a query and a reply each
fit in one packet shows you know a real example rather than a category.
