Your request succeeded perfectly and the reply never came back. This is the
failure mode that separates code that works from code that works in production,
and almost nobody meets it until it has already cost them something.

## Why this matters in a job

Because every client you write calls something that can be slow, and the default
behaviour of most libraries, wait forever, is the worst available choice.

::real-life{title="How one slow database took down a website that did not use it" source="A results portal"}
A reporting query started taking ninety seconds. The report page had no timeout,
so its threads waited. The thread pool filled with threads waiting on that one
query. New requests for *every other page* queued behind them, and the whole
site went down, including the student login that never touched that database. The
root cause was one slow query; the outage was caused by an absent timeout.
::

## The two timeouts, which are different

Most libraries have both and most people set neither.

::compare{caption="Two settings, two completely different failures."}
  :::compare-side{label="Connect timeout" verdict="neutral"}
  How long to wait for the TCP handshake. Should be **short**: a second or two.
  If a machine has not answered a SYN in two seconds it is not going to; it is
  down, or a firewall is dropping packets silently.
  :::
  :::compare-side{label="Read timeout" verdict="neutral"}
  How long to wait for a response after connecting. Depends on what you are
  calling: a fast API, two or three seconds; a report that legitimately takes
  thirty, thirty.
  :::
::

```java [ApplicantClient.java]
// Both set, explicitly, with a reason for each number.
HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(2))       // it answers fast or it is down
    .build();

HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://university.edu/api/applicants"))
    .timeout(Duration.ofSeconds(5))              // this endpoint is normally ~200 ms
    .GET()
    .build();
```

::warning{icon="i-lucide-alert-triangle"}
A timeout you have not set is not "no timeout". It is the operating system's,
which on Linux can be over two minutes for a connect. Two minutes is long enough
for your entire thread pool to fill, which is how one slow dependency takes down
a service that had nothing to do with it.
::

## The retry problem

A timeout fires. Now what? The honest answer is that **you do not know what
happened**, and that is the whole difficulty.

So the rule is narrow and it follows directly from the previous chapter:

::pull-quote
Retry anything idempotent, freely. Never blindly retry anything that is not.
::

`GET`, `PUT` and `DELETE` are safe to repeat. `POST` is not, unless you have made
it safe with an idempotency key the server remembers.

## Retry properly, or not at all

```java [Retry.java]
// Exponential backoff with jitter. Three numbers, three reasons.
int attempt = 0;
while (true) {
  try {
    return client.send(request, BodyHandlers.ofString());
  } catch (IOException e) {
    if (++attempt >= 3) throw e;                       // a ceiling, always

    long base = 200L * (1L << (attempt - 1));          // 200, 400, 800 ms
    long jitter = ThreadLocalRandom.current().nextLong(base / 2);
    Thread.sleep(base + jitter);
  }
}
```

::feature-list{columns="2"}
  :::feature{icon="i-lucide-trending-up" title="Backoff: wait longer each time"}
  If the server is overloaded, retrying immediately makes it worse. Doubling the
  wait gives it room to recover.
  :::
  :::feature{icon="i-lucide-shuffle" title="Jitter: randomise the wait"}
  Without it, a thousand clients that failed together retry together, in a
  synchronised wave, forever. This is a real and famous failure mode.
  :::
  :::feature{icon="i-lucide-octagon-x" title="A ceiling: give up"}
  Three attempts, not "until it works". Retrying forever converts a brief outage
  into a permanent one by keeping the load on.
  :::
  :::feature{icon="i-lucide-shield" title="A circuit breaker, eventually"}
  After enough consecutive failures, stop calling entirely for a while and fail
  fast. Better to answer "unavailable" in one millisecond than to wait five
  seconds to find out the same thing.
  :::
::

## What confuses people here

That retrying is obviously good. A retry storm is a genuine cause of outages: the
dependency has a brief problem, every client retries three times, the dependency
now has four times the load, and it stays down. Backoff, jitter and a ceiling are
what make a retry helpful rather than an attack.

::side-note{kind="go-deeper"}
The same reasoning applies to the database connections your application holds. A
pool of ten connections and a thread pool of two hundred means that once ten
queries are slow, the other 190 threads are queued waiting for a connection, and
the health check times out, so an orchestrator kills a service that was working
correctly and slowly. Pool sizes are a networking decision even though they do
not look like one.
::

## What you can do now

You can set both timeouts deliberately, decide whether a call is safe to retry
from the HTTP method, and write a retry that helps rather than one that piles on.

## Your turn

For each, say: what timeouts would you set, is it safe to retry, and what do you
do after the last attempt fails?

1. `GET /api/applicants?minScore=60`: a list for a screen, normally 200 ms.
2. `POST /api/fee-payments`, takes a payment.
3. `POST /api/reports/results`, generates a PDF, legitimately takes 45 seconds.
4. A nightly job importing 40,000 attendance rows from another system.

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** Connect 2 s, read 3 s. Safe to retry, it is a `GET`. After three
  failures, show the user an error with a retry button rather than an empty
  table: an empty list and a failed call must never look the same.

  **2.** Connect 2 s, read 10 s. **Not safe to retry** as written. Either send an
  idempotency key the server records, or on timeout do not retry: query the
  payment by that key to find out whether it went through, and act on the answer.
  Charging twice is far worse than telling somebody to check.

  **3.** Connect 2 s, read 60 s, but this is the wrong shape. A 45-second
  request occupies a connection and a thread the whole time and dies to any proxy
  timeout in between. Better: `POST` returns `202 Accepted` with a job id
  immediately, and the client polls or is notified. That is the standard answer
  and a good thing to propose unprompted.

  **4.** Generous timeouts, and the important part is elsewhere: it must be safe
  to run twice, because it will be. Key each row by something stable and use an
  upsert, so re-running after a half-finished import corrects rather than
  duplicates.
  :::
::

## Check yourself

1. Why can a client never tell the difference between "it never arrived" and "it
   succeeded and the reply was lost"?
2. **An interviewer asks: "what happens if your payment API call times out?"**

## The interview question this answers

**"How do you handle failures when calling another service?"**

Timeouts on both connect and read, set deliberately rather than left to the
library. Retries only for idempotent calls, with exponential backoff, jitter and
a ceiling. And for the non-idempotent case, the specific answer: an idempotency
key, or a follow-up query to find out what actually happened rather than guessing.
Mentioning jitter is a small detail that reliably signals you have read about
real outages.
