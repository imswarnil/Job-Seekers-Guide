Prove it. A test is a small program that runs your program and complains if the
answer is wrong, and it is the difference between changing code confidently and
changing it hopefully.

## Why this matters in a job

Because every real codebase has tests and you will be expected to write them from
week one. Because "how do you test your code" is asked in most interviews. And
because a project with tests on your GitHub is a visible signal that almost no
fresher has.

## The shape

```java [ShortlisterTest.java]
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class ShortlisterTest {

  @Test
  void shortlistsApplicantsAtOrAboveTheCutoff() {
    // Arrange: set up exactly the situation being tested
    List<Application> applications = List.of(
        application("Anita Rao", 78),
        application("Vikram Shah", 64),
        application("Priya Nair", 75));

    // Act: one call, the thing under test
    List<String> shortlisted = new Shortlister().shortlist(applications, 75);

    // Assert: what must be true
    assertEquals(List.of("Anita Rao", "Priya Nair"), shortlisted);
  }
}
```

Arrange, act, assert. Every test you will ever write has these three parts, and a
test with two "act" steps is two tests.

::pull-quote
The name of a test is documentation that cannot go out of date. Not `test1`.
`shortlistsApplicantsAtOrAboveTheCutoff` tells the next reader the rule, and when
it fails the build output names the broken rule.
::

## What to test: the boundaries

Do not test that 78 is above 75. Test the places where the rule changes.

::feature-list{columns="2"}
  :::feature{icon="i-lucide-move-horizontal" title="Exactly at the boundary"}
  75 against a cutoff of 75. This is the one that produces a telephone call from
  a parent, and the one the original test data never contained.
  :::
  :::feature{icon="i-lucide-circle-slash" title="Empty"}
  No applications at all. Does it return an empty list or throw?
  :::
  :::feature{icon="i-lucide-circle-dot" title="One"}
  A surprising number of loops and averages are wrong at exactly one element.
  :::
  :::feature{icon="i-lucide-ban" title="Invalid"}
  A null score, a negative cutoff, a withdrawn applicant. What *should* happen
  is a decision you have to have made.
  :::
::

```java [ShortlisterTest.java]
@Test
void includesAnApplicantExactlyOnTheCutoff() {
  var result = shortlister.shortlist(List.of(application("Priya", 75)), 75);
  assertEquals(1, result.size(), "75 is 'at or above' 75");
}

@Test
void returnsEmptyListWhenNobodyApplied() {
  assertTrue(shortlister.shortlist(List.of(), 75).isEmpty());
}

@Test
void excludesUnmarkedApplications() {
  var result = shortlister.shortlist(List.of(application("Rahul", null)), 75);
  assertTrue(result.isEmpty(), "an unmarked application is not above any cutoff");
}

@Test
void rejectsANegativeCutoff() {
  var e = assertThrows(IllegalArgumentException.class,
      () -> shortlister.shortlist(List.of(), -1));
  assertTrue(e.getMessage().contains("-1"));
}
```

::tip
The third argument to `assertEquals` and `assertTrue` is a message shown when it
fails. Use it to say *why the rule is what it is*. Six months later, when
somebody changes the cutoff comparison, the failure says "75 is 'at or above' 75"
rather than "expected 1, got 0".
::

## Parameterised tests

The same rule at several values, without four copies of one test.

```java [GradeTest.java]
@ParameterizedTest
@CsvSource({
    "100, A", "90, A", "89, B", "80, B",
    "79, C", "70, C", "40, E", "39, F", "0, F"
})
void assignsTheCorrectGrade(int marks, String expected) {
  assertEquals(expected, Grades.of(marks));
}
```

Nine boundaries in ten lines, and each failure names the exact value.

## Watch a test fail before you trust it

This is the step everybody skips and it is the most important one.

```java [ShortlisterTest.java]
// Run this. It should pass.
@Test
void includesAnApplicantExactlyOnTheCutoff() { ... }
```

```java [Shortlister.java]
// Now break the code on purpose.
if (a.getScore() > cutoff) {        // was >=
```

```text [Output]
ShortlisterTest > includesAnApplicantExactlyOnTheCutoff() FAILED
    org.opentest4j.AssertionFailedError: 75 is 'at or above' 75 ==>
    expected: <1> but was: <0>
```

::warning{icon="i-lucide-alert-triangle"}
A test that has never failed proves nothing. It might be asserting something
that is always true, testing the wrong object, or not running at all. Break the
code, watch it go red, put it back, watch it go green. Thirty seconds, and it is
the only thing that makes the test worth having.
::

## What not to test

::compare{caption="Two tests. One of them is worse than nothing."}
  :::compare-side{label="Testing the language" verdict="wrong"}
  ```java
  @Test void getterReturnsTheName() {
    var a = new Applicant("Anita Rao");
    assertEquals("Anita Rao", a.getFullName());
  }
  ```
  This tests that assignment works. It will never fail for a real reason, and it
  has to be maintained forever.
  :::
  :::compare-side{label="Testing a rule" verdict="right"}
  ```java
  @Test void aWithdrawnApplicantCannotBeShortlisted() {
    var a = application("Anita Rao", 92);
    a.withdraw();
    assertThrows(IllegalStateException.class, () -> a.shortlist(registrar));
  }
  ```
  This encodes a decision somebody made about how the university works. If it
  fails, something real is broken.
  :::
::

Test the logic, the boundaries and the rules. Do not test getters, the framework,
or that Java's `List` works.

## Running them from the terminal

```bash [Terminal]
# With Maven
mvn test

# One class
mvn test -Dtest=ShortlisterTest
```

```text [Output]
[INFO] Tests run: 12, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

::side-note{kind="go-deeper"}
Coverage — the percentage of lines a test suite executes — is a useful signal and
a terrible target. It is easy to reach 90% by calling every method and asserting
nothing. Low coverage genuinely tells you something is untested; high coverage
tells you almost nothing about whether the assertions are any good. If an
interviewer asks about coverage, saying this is a stronger answer than naming a
number.
::

## What you can do now

You can write a test that encodes a rule rather than an implementation detail,
choose the values that actually matter, and prove the test works by watching it
fail.

## Your turn

Write the tests for this before reading the answer. Aim for six, and at least
three of them boundaries.

```java [Attendance.java]
public class Attendance {
  /**
   * Percentage of classes attended, rounded to one decimal place.
   * A student below 75% is short of attendance and may not sit the exam.
   */
  public static double percentage(int attended, int held) { ... }

  public static boolean isShort(int attended, int held) { ... }
}
```

::accordion
  :::accordion-item{label="Eight tests, and the two design questions they force" icon="i-lucide-check"}
  ```java
  class AttendanceTest {

    @Test void calculatesAStraightforwardPercentage() {
      assertEquals(75.0, Attendance.percentage(18, 24), 0.01);
    }

    @Test void roundsToOneDecimalPlace() {
      assertEquals(66.7, Attendance.percentage(2, 3), 0.01);
    }

    @Test void exactlySeventyFiveIsNotShort() {
      assertFalse(Attendance.isShort(18, 24), "the rule is BELOW 75%");
    }

    @Test void justUnderSeventyFiveIsShort() {
      assertTrue(Attendance.isShort(17, 24));          // 70.8%
    }

    @Test void fullAttendanceIsOneHundred() {
      assertEquals(100.0, Attendance.percentage(24, 24), 0.01);
    }

    @Test void noClassesAttendedIsZero() {
      assertEquals(0.0, Attendance.percentage(0, 24), 0.01);
    }

    @Test void rejectsMoreAttendedThanHeld() {
      assertThrows(IllegalArgumentException.class,
          () -> Attendance.percentage(25, 24));
    }

    @Test void handlesNoClassesHeld() {
      // See below. This test is the question, not the answer.
    }
  }
  ```

  **Design question one: what is 0 classes held?** Zero divided by zero. It is
  not 0%, it is not 100%, and it is not an error caused by the student. The
  honest answers are to throw, or to return an `OptionalDouble`, or to define it
  as "not short" so nobody is penalised for a subject that never ran. **All three
  are defensible and somebody at the university has to choose.** Writing the test
  is what forces the question, which is the real reason to write tests first.

  **Design question two: comparing doubles.** Note the third argument, `0.01`.
  From the primitives lesson: never compare doubles with `==`. `assertEquals` for
  doubles takes a tolerance, and a test that omits it will fail unpredictably.

  **And the third thing, which is the most important:** every one of these tests
  is a sentence about how the university works. Together they are the
  specification, written in a form that complains when somebody breaks it.
  :::
::

## The interview question this answers

**"How do you test your code?"**

Arrange, act, assert, and one behaviour per test with a name that states the
rule. Then the part that shows you have actually done it: you test the
boundaries, the empty case, the single-element case and the invalid input, not
the happy path with a comfortable value. And you watch each test fail once,
because a test that has never been red proves nothing.

Closing with the coverage observation — a useful signal and a terrible target —
is a strong finish, because it shows you have seen a suite gamed.
