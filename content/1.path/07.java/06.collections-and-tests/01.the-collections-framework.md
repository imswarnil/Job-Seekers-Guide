An entire library, and you already know what is inside it. Every class here is
one of the structures from the data structures track, and choosing between them
is the same decision you already learned to make.

## Why this matters in a job

Because this is the part of Java you will touch in every single method you write,
and because "which collection would you use" is a question whose answer reveals
immediately whether you think about cost.

## Choosing, in one table

| The requirement | Use |
| --- | --- |
| An ordered list of things, read by index | `ArrayList` |
| No duplicates, order does not matter | `HashSet` |
| No duplicates, insertion order preserved | `LinkedHashSet` |
| No duplicates, sorted | `TreeSet` |
| Look something up by a key | `HashMap` |
| Look up by key, and iterate in insertion order | `LinkedHashMap` |
| Look up by key, sorted, or need ranges | `TreeMap` |
| Add and remove at both ends; a stack or a queue | `ArrayDeque` |
| Highest priority first | `PriorityQueue` |

::warning{icon="i-lucide-alert-triangle"}
Three classes to avoid in new code: `Vector` and `Hashtable` are the original
synchronised versions from 1996, and you pay for locking you almost never need;
`Stack` extends `Vector` and exposes indexed access that breaks the abstraction.
Their modern replacements are `ArrayList`, `HashMap` and `ArrayDeque`. If you
genuinely need thread safety, `ConcurrentHashMap` and
`Collections.synchronizedList` are the right answers, not these.
::

## Generics, and why they exist

```java [Generics.java]
// Before generics, and this compiled:
List applicants = new ArrayList();
applicants.add(new Applicant("Anita Rao"));
applicants.add("oops, a String");
Applicant a = (Applicant) applicants.get(1);     // ClassCastException at run time
```

```java [Generics.java]
List<Applicant> applicants = new ArrayList<>();
applicants.add("oops, a String");                // compile error. Caught at 9am.
```

Generics move a whole class of error from run time to compile time, and they
remove the casts. `<>` on the right is the diamond operator: the compiler infers
it from the left.

```java [Generic.java]
// Writing your own. T is a placeholder for a type the caller chooses.
public class Repository<T> {
  private final Map<Long, T> byId = new HashMap<>();

  public void save(long id, T item) { byId.put(id, item); }
  public Optional<T> findById(long id) { return Optional.ofNullable(byId.get(id)); }
}
```

```java [Bounded.java]
// Bounded: T must be something that can be compared.
public static <T extends Comparable<T>> T highest(List<T> items) {
  T best = items.get(0);
  for (T item : items) if (item.compareTo(best) > 0) best = item;
  return best;
}
```

::side-note{kind="go-deeper"}
Generics are **erased** at compile time: the bytecode for `List<Applicant>` and
`List<String>` is identical, both just `List`. That is why you cannot write
`new T[10]`, why `list instanceof List<String>` does not compile, and why two
methods differing only in their generic parameter clash. Type erasure exists so
that generic code could run on older JVMs, and it is a standard interview
follow-up.
::

## The methods you will actually use

```java [Daily.java]
List<Application> apps = new ArrayList<>();
apps.add(a);  apps.get(0);  apps.size();  apps.contains(a);   // contains is O(n)
apps.removeIf(x -> x.isWithdrawn());                          // no iterator needed
apps.sort(comparing(Application::getScore).reversed());

Map<Long, Applicant> byId = new HashMap<>();
byId.put(4182L, anita);
byId.getOrDefault(9999L, UNKNOWN);          // no NPE on unboxing
byId.computeIfAbsent(4182L, this::load);    // load once, cache
byId.merge("CSE", 1, Integer::sum);         // count occurrences in one line

for (var entry : byId.entrySet()) {         // the way to loop a Map
  System.out.println(entry.getKey() + " → " + entry.getValue());
}
```

::tip
`merge` and `computeIfAbsent` replace the most-written five lines in Java:
"get it, if null create it, put it back". `counts.merge(key, 1, Integer::sum)` is
a whole word-count in one line, and using them is a small, visible sign of
fluency.
::

## Streams

Not a data structure. A pipeline over one, and it is how modern Java expresses
"filter, transform, collect".

```java [Streams.java]
// The loop version
List<String> names = new ArrayList<>();
for (Application a : applications) {
  if (a.getScore() != null && a.getScore() >= 75 && !a.isWithdrawn()) {
    names.add(a.getApplicant().getFullName());
  }
}
names.sort(naturalOrder());
```

```java [Streams.java]
// The stream version: the same three decisions, each on its own line
List<String> names = applications.stream()
    .filter(a -> a.getScore() != null)
    .filter(a -> a.getScore() >= 75)
    .filter(a -> !a.isWithdrawn())
    .map(a -> a.getApplicant().getFullName())
    .sorted()
    .toList();
```

```java [Grouping.java]
// Where streams genuinely win: grouping and summarising.
Map<String, Long> countByProgramme = applications.stream()
    .collect(groupingBy(Application::getProgrammeCode, counting()));

Map<String, Double> averageByProgramme = applications.stream()
    .filter(a -> a.getScore() != null)
    .collect(groupingBy(Application::getProgrammeCode,
                        averagingInt(Application::getScore)));

String shortlist = applications.stream()
    .filter(a -> a.getScore() >= 75)
    .map(a -> a.getApplicant().getFullName())
    .collect(joining(", "));
```

That grouping in a loop is fifteen lines with a `computeIfAbsent` in the middle.
This is the case where a stream is simply better.

::pros-cons
---
title: Streams
pros:
  - Grouping, counting and averaging are one line and read like the requirement
  - Each step is separate, so the intent is visible without tracing a loop
  - Lazy: filter then findFirst stops as soon as it finds one
cons:
  - A debugger cannot step through it the way it steps through a loop
  - A stack trace from inside a stream is considerably harder to read
  - `.parallelStream()` is almost never the win people expect and is easy to misuse
  - A simple loop is clearer than a simple stream, and plenty of streams are simple
---
::

::note
Use a stream when you are filtering, transforming or grouping. Use a loop when
you are doing something to each element for its side effect, or when the logic
has early exits and branches. "Streams everywhere" and "loops everywhere" are
both positions held by people who have not maintained the other one.
::

## What you can do now

You can choose a collection for a stated reason, use the four methods that
replace most hand-written map code, and write a grouping in one line instead of
fifteen.

## Your turn

::runner{lang="java"}
```java
import java.util.*;
import java.util.stream.*;
import static java.util.stream.Collectors.*;

public class Main {
  record Application(String name, String programme, Integer score, boolean withdrawn) { }

  public static void main(String[] args) {
    List<Application> apps = List.of(
        new Application("Anita Rao",   "CSE", 78,   false),
        new Application("Vikram Shah", "CSE", 64,   false),
        new Application("Priya Nair",  "ECE", 81,   false),
        new Application("Rahul Verma", "CSE", null, false),
        new Application("Sneha Iyer",  "ECE", 92,   true));

    // 1. Names of everyone scoring 75 or more, not withdrawn, alphabetical.
    // 2. How many applications per programme.
    // 3. Average score per programme, ignoring unmarked and withdrawn.
    // 4. The highest scorer overall.
  }
}
```
::

::accordion
  :::accordion-item{label="Answers, and the trap in number three" icon="i-lucide-check"}
  ```java
  // 1
  List<String> shortlisted = apps.stream()
      .filter(a -> !a.withdrawn())
      .filter(a -> a.score() != null && a.score() >= 75)
      .map(Application::name)
      .sorted()
      .toList();                                  // [Anita Rao, Priya Nair]

  // 2
  Map<String, Long> perProgramme = apps.stream()
      .collect(groupingBy(Application::programme, counting()));   // {CSE=3, ECE=2}

  // 3
  Map<String, Double> averages = apps.stream()
      .filter(a -> !a.withdrawn())
      .filter(a -> a.score() != null)
      .collect(groupingBy(Application::programme,
                          averagingInt(Application::score)));     // {CSE=71.0, ECE=81.0}

  // 4
  Optional<Application> top = apps.stream()
      .filter(a -> a.score() != null)
      .max(comparing(Application::score));                        // Sneha, 92
  ```

  **The trap in three:** the null filter must come before `averagingInt`, or it
  throws an NPE on unboxing — the same trap as the previous chapter, now inside a
  stream where the stack trace is much harder to read. Order matters in a
  pipeline, and null handling belongs at the front of it.

  **The trap in four:** it returns Sneha, who has **withdrawn**. The filter for
  withdrawal was left out, and nothing about the code looks wrong. That is the
  real lesson of this exercise: a stream reads so well that a missing filter is
  invisible, which is exactly why each requirement deserves its own line and its
  own test.
  :::

## Check yourself

1. Why is a `Map` not a `Collection`?
2. **An interviewer asks: "ArrayList or LinkedList?"** and then **"HashMap or
   TreeMap?"**

## The interview question this answers

**"Which collection would you use, and why?"**

Answer with the requirement first, then the class, then the cost you are
accepting. "A `HashMap`, because I need lookup by applicant id and O(1) matters
more than ordering here, and I am accepting that iteration order is undefined."
Naming the cost is what distinguishes the answer.

Follow-ups worth having ready: `ArrayList` over `LinkedList` because of
contiguity and cache behaviour; `HashMap` over `TreeMap` unless you need ranges
or ordering; and `ArrayDeque` rather than `Stack` because `Stack` extends
`Vector`.
