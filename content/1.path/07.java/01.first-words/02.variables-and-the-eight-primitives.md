A place to remember things. A variable is a named piece of memory with a declared
type, and in Java the type is checked by the compiler before the program ever
runs.

## Why this matters in a job

Because two of the eight primitives will produce silently wrong numbers in your
first month if you do not know what they do, and both of those mistakes reach
production regularly in systems handling money and marks.

## Declaring one

```java [Applicant.java]
int score = 78;          // type, name, value
score = 81;              // reassignment: same box, new value
int cutoff;              // declared, not yet given a value
cutoff = 60;
```

```java [Applicant.java]
final int MAXIMUM_SCORE = 100;    // final: assigned once, never again
MAXIMUM_SCORE = 120;              // compile error, and that is the point
```

`final` is not decoration. A value that should never change and cannot change is
one fewer thing to reason about, and it is how every constant in a real codebase
is declared.

## The eight

These eight are **not objects**. They hold a value directly rather than a
reference to one, which is the subject of the next lesson.

| Type | Size | Holds | Use it for |
| --- | --- | --- | --- |
| `byte` | 8 bits | −128 to 127 | Raw data, rarely |
| `short` | 16 bits | ±32,767 | Almost never |
| **`int`** | 32 bits | ±2.1 billion | **The default for whole numbers** |
| **`long`** | 64 bits | ±9.2 quintillion | Ids, timestamps, money in paise |
| `float` | 32 bits | ~7 digits of precision | Almost never |
| **`double`** | 64 bits | ~15 digits | Measurements, averages. **Never money.** |
| `char` | 16 bits | One character, `'A'` | Single letters |
| **`boolean`** | 1 bit of meaning | `true` / `false` | Conditions |

Four of them matter: `int`, `long`, `double`, `boolean`. The others exist and you
will rarely choose one deliberately.

## Trap one: integer division

```java [Average.java]
int totalMarks = 245;
int subjects   = 3;
int average    = totalMarks / subjects;
System.out.println("Average: " + average);
```

```text [Output]
Average: 81
```

It should be 81.67. Java divided two `int` values, so the result is an `int`, and
the fraction was **discarded before anything else happened**. Not rounded.
Truncated.

::compare{caption="The fix is not what most people try first."}
  :::compare-side{label="Still wrong" verdict="wrong"}
  ```java
  double average = totalMarks / subjects;   // 81.0
  ```
  The division still happens between two ints. The `double` only receives the
  already-broken answer. This is the version people write and then cannot
  explain.
  :::
  :::compare-side{label="Right" verdict="right"}
  ```java
  double average = (double) totalMarks / subjects;   // 81.666…
  ```
  One operand is now a `double`, so the division itself is done in floating
  point. **The types of the operands decide the arithmetic**, not the type you
  are assigning into.
  :::
::

## Trap two: floating point is not exact

```java [Fees.java]
double paid = 0.1 + 0.2;
System.out.println(paid);
System.out.println(paid == 0.3);
```

```text [Output]
0.30000000000000004
false
```

This is not a Java bug. A `double` stores numbers in binary, and 0.1 has no exact
binary representation, exactly as 1/3 has no exact decimal one. The error is tiny
and it accumulates.

```java [Fees.java]
double fee = 45000.0;
double total = 0;
for (int i = 0; i < 1000; i++) total += fee / 1000;
System.out.println(total);
```

```text [Output]
44999.99999999967
```

A thousand instalments of a ₹45,000 fee, and the university is ₹0.0000003 short.
Multiply by forty thousand applicants and by a year of interest calculations, and
an auditor will find it.

::warning{icon="i-lucide-alert-triangle"}
**Never use `double` or `float` for money.** Two correct answers: store an
integer count of the smallest unit — `long amountPaise = 4_500_000L` for ₹45,000
— or use `BigDecimal` constructed from a **String**, never from a double.
`new BigDecimal(0.1)` gives you
`0.1000000000000000055511151231257827021181583404541015625`, because the double
was already wrong before `BigDecimal` saw it.
::

```java [Money.java]
// The pattern used by essentially every real financial system.
long feePaise    = 4_500_000L;          // ₹45,000.00
long paidPaise   = 1_500_000L;
long balance     = feePaise - paidPaise;
System.out.printf("Balance: ₹%d.%02d%n", balance / 100, balance % 100);
```

```text [Output]
Balance: ₹30000.00
```

Exact, always, and the `L` suffix is required: without it the literal is an `int`
and 4,500,000 happens to fit, but a larger one would overflow silently.

## Overflow, which is silent

```java [Overflow.java]
int applications = 2_147_483_647;    // the largest int there is
applications = applications + 1;
System.out.println(applications);
```

```text [Output]
-2147483648
```

No error, no warning. It wrapped around to the most negative value. This is why
ids and timestamps are `long`, and why a count that could ever be large should
not be an `int`.

## `var`, and when to use it

```java [Var.java]
var score = 78;                          // an int, inferred
var applicants = new ArrayList<Applicant>();   // saves repeating the type
var x = someMethod();                    // ← now the reader has no idea
```

`var` infers the type at compile time. It is still strictly typed; you simply did
not write it. Use it where the type is obvious from the right-hand side, and
never where it hides something the reader needs.

## What you can do now

You can declare a variable with the right type, explain integer division without
guessing, and state the rule about money that separates careful code from code
that fails an audit.

## Your turn

::runner{lang="java"}
```java
public class Attendance {
  public static void main(String[] args) {
    int classesHeld = 24;
    int classesAttended = 18;

    // 1. This prints 0. Fix it so it prints 75.0
    double percentage = classesAttended / classesHeld * 100;
    System.out.println("Attendance: " + percentage + "%");

    // 2. Predict this before running it.
    System.out.println(0.1 + 0.2 == 0.3);

    // 3. This fee is stored wrongly. Rewrite it in paise.
    double feeRupees = 45000.50;
    System.out.println("Fee: " + feeRupees);
  }
}
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** `18 / 24` in integer arithmetic is 0, and 0 × 100 is 0. Two fixes, and
  the second is better:

  ```java
  double percentage = (double) classesAttended / classesHeld * 100;   // 75.0
  double percentage = classesAttended * 100.0 / classesHeld;          // 75.0
  ```

  The second multiplies first, so it never divides two ints at all. Doing the
  multiplication before the division is a habit worth forming: it avoids both
  truncation and precision loss.

  **2.** `false`. And the real lesson: **never compare doubles with `==`.** If
  you must, compare the difference against a small tolerance.

  **3.** `long feePaise = 4_500_050L;` — ₹45,000.50. Print it by dividing and
  taking the remainder, as in the example above. If the university later needs
  fractions of a paisa, that is `BigDecimal` from a String, and it is still not a
  `double`.
  :::
::

## Check yourself

1. Why does `(double) total / count` work when `double avg = total / count` does
   not?
2. **An interviewer asks: "how would you store a currency amount?"** Answer, and
   say why.

## The interview question this answers

**"Why should you not use float or double for money?"**

Because binary floating point cannot represent most decimal fractions exactly, so
0.1 + 0.2 is 0.30000000000000004 and errors accumulate over many operations. The
two correct answers are an integer count of the smallest unit, or `BigDecimal`
constructed from a `String`. Adding the `new BigDecimal(0.1)` trap shows you know
why the String part matters, and that detail is what makes the answer memorable.
