Identical syntax, opposite result. This lesson is the single most important
picture in the track, and everything from `equals` to `NullPointerException` to
"why did my list change" rests on it.

## Why this matters in a job

Because "pass by value or pass by reference" is one of the most-asked Java
questions, because the mutation bug it explains is one of the most common in real
code, and because you cannot reason about `null` until you know what a reference
is.

## Watch the two behave differently

```java [Copying.java]
// A primitive.
int scoreA = 78;
int scoreB = scoreA;      // copy the VALUE
scoreB = 92;
System.out.println(scoreA);   // 78 — untouched
```

```java [Copying.java]
// An object.
Applicant a = new Applicant("Anita Rao", 78);
Applicant b = a;              // copy the REFERENCE
b.setScore(92);
System.out.println(a.getScore());   // 92 — changed
```

Same shape, opposite outcome. The reason is what each variable contains.

::pull-quote
An object variable never holds an object. It holds the address of one. Copying
the variable copies the address, not the thing at the end of it.
::

## Pass by value, always

Java is **pass by value**, without exception. The confusion comes from the fact
that when you pass an object, the *value being copied* is an address.

```java [Passing.java]
static void raise(int score) {
  score = 92;                       // changes the local copy only
}

static void raise(Applicant a) {
  a.setScore(92);                   // follows the address, changes the object
}

static void replace(Applicant a) {
  a = new Applicant("Someone Else", 0);   // changes where the LOCAL copy points
}                                         // the caller's variable is untouched
```

```java [Passing.java]
int score = 78;
raise(score);
System.out.println(score);        // 78

Applicant anita = new Applicant("Anita Rao", 78);
raise(anita);
System.out.println(anita.getScore());   // 92 — the object was modified

replace(anita);
System.out.println(anita.getName());    // Anita Rao — the reference was not
```

::code-trace{caption="The third case is the one that settles the argument."}
```java [Passing.java]

  a = new Applicant("Someone Else", 0);
}
```

## The bug this explains

The most common accidental mutation in real code, and it looks completely
innocent.

```java [Shortlist.java]
// WRONG: the caller's list is modified without anybody asking.
static List<Applicant> shortlist(List<Applicant> applicants, int cutoff) {
  applicants.removeIf(a -> a.getScore() < cutoff);   // ← mutates the CALLER's list
  return applicants;
}
```

```java [Shortlist.java]
List<Applicant> all = loadApplicants();      // 40,000
List<Applicant> top = shortlist(all, 75);    // returns 1,840
System.out.println(all.size());              // 1,840 — the original is gone
```

```java [Shortlist.java]
// RIGHT: build a new list, leave the caller's alone.
static List<Applicant> shortlist(List<Applicant> applicants, int cutoff) {
  return applicants.stream()
      .filter(a -> a.getScore() >= cutoff)
      .toList();
}
```

::real-life{title="How this actually reaches production" source="A reporting job"}
The shortlisting method was written by one person and called by another, six
months apart. The caller assumed a method called `shortlist` would *return* a
shortlist, not destroy the list it was given. The report that ran afterwards over
"all applicants" quietly reported over 1,840 of them for three weeks. Nothing
crashed. A method that modifies its arguments and does not say so in its name is
the shape of this entire category of bug.
::

## What `null` is

Not zero, not empty, not an object. It is a reference pointing at nothing.

```java [Null.java]
Applicant a = null;          // the variable exists; there is no object
System.out.println(a.getName());
```

```text [Output]
Exception in thread "main" java.lang.NullPointerException:
Cannot invoke "Applicant.getName()" because "a" is null
```

Read that message literally and it is complete: you tried to follow an address
that is not an address. Modern Java tells you exactly which variable, which is a
relatively recent and very welcome improvement.

::side-note{kind="go-deeper"}
A primitive can never be `null`, because it holds a value rather than an address.
`int score = null;` does not compile. But `Integer score = null;` does, and
`int s = score;` then throws a `NullPointerException` at the moment it unboxes.
That is one of the sneakiest NPEs in Java: the line that throws has no `.` in it
at all.
::

## What you can do now

You can draw the stack-and-heap picture, explain pass-by-value with the
`replace` proof, and recognise the accidental-mutation bug before writing it.

## Your turn

Predict every line of output before running it.

::runner{lang="java"}
```java
import java.util.*;

public class References {
  public static void main(String[] args) {
    int[] scores = {78, 64, 81};
    int[] copy = scores;
    copy[0] = 92;
    System.out.println(scores[0]);                 // 1

    List<String> names = new ArrayList<>(List.of("Anita", "Vikram"));
    addName(names);
    System.out.println(names.size());              // 2

    String s = "Anita";
    change(s);
    System.out.println(s);                         // 3

    StringBuilder sb = new StringBuilder("Anita");
    change(sb);
    System.out.println(sb);                        // 4
  }

  static void addName(List<String> list) { list.add("Priya"); }
  static void change(String s) { s = s + " Rao"; }
  static void change(StringBuilder sb) { sb.append(" Rao"); }
}
```
::

::accordion
  :::accordion-item{label="Answers, and the one that surprises everyone" icon="i-lucide-check"}
  **1. `92`.** An array is an object. `copy` holds the same address, so there is
  one array and both names reach it.

  **2. `3`.** Same reason. `addName` follows the address and modifies the list
  the caller still holds.

  **3. `Anita`.** The surprise. `change` received a copy of the address, then
  `s + " Rao"` created a **new** String and pointed the local copy at it. The
  caller's variable never moved. Strings are immutable, so this is the only thing
  that could have happened.

  **4. `Anita Rao`.** `StringBuilder` is mutable, so `append` modifies the object
  at the address rather than making a new one.

  Three and four together are the whole lesson: what matters is not whether you
  passed an object, it is whether the method **mutated** the object or
  **reassigned** its own local variable.
  :::
::

## The interview question this answers

**"Is Java pass by value or pass by reference?"**

Always pass by value. The confusion is that for an object the value being copied
is a reference, so the method can follow it and modify the object. The proof,
which is what turns a memorised answer into a demonstrated one: assign a brand
new object to the parameter inside the method and the caller sees nothing. If
Java were pass by reference, the caller's variable would have been replaced.
