Something expensive. Every `+` on a String creates a new object and copies
everything so far, so building a report line by line is quadratic without looking
like it.

## Why this matters in a job

Because this is the second hidden quadratic in the language after
`List.contains`, and because a loop boundary is where almost every logic bug you
will write actually lives.

## Measure the quadratic

```java [BuildReport.java]
// O(n²): each + copies the entire string built so far.
String report = "";
for (ExamResult r : results) {
  report += r.getRollNumber() + "," + r.getMarks() + "\n";
}
```

```java [BuildReport.java]
// O(n): one growing buffer, no copying until the end.
StringBuilder report = new StringBuilder();
for (ExamResult r : results) {
  report.append(r.getRollNumber()).append(',').append(r.getMarks()).append('\n');
}
String out = report.toString();
```

```text [Measured, same machine]
   1,000 results:   concat   12 ms   ·  builder   1 ms
  10,000 results:   concat  890 ms   ·  builder   3 ms
  40,000 results:   concat 14,100 ms ·  builder   9 ms
```

Ten times the input, roughly a hundred times the work, and the two versions are
the same length. This is the whole of chapter one's big-O lesson, in the language.

::note
A single `+` outside a loop is fine, and the compiler often turns it into a
`StringBuilder` for you. What it cannot do is hoist the builder *out of a loop*,
because each iteration is a separate statement. The rule is narrow: building text
in a loop means `StringBuilder`.
::

## Formatting, rather than joining

```java [Format.java]
// Readable, and it keeps the shape of the output visible.
String line = "%s scored %d (%.1f%%)".formatted(name, marks, percentage);

// Straight to the console
System.out.printf("%-20s %5d %6.1f%%%n", name, marks, percentage);
```

```text [Output]
Anita Rao               78   75.0%
Vikram Shah             64   62.5%
```

`%-20s` is left-aligned in twenty characters, `%5d` is right-aligned in five, and
`%n` is a newline that is correct on every platform. That is how a console report
gets columns that line up, and you will build exactly this later in the track.

## The three loops

```java [Loops.java]
// for — when you know the count, or need the index
for (int i = 0; i < applications.size(); i++) {
  System.out.println((i + 1) + ". " + applications.get(i).getName());
}

// enhanced for — when you just need each element. Prefer this.
for (Application a : applications) {
  process(a);
}

// while — when the end condition is not a count
while (scanner.hasNextLine()) {
  process(scanner.nextLine());
}

// do-while — when the body must run at least once. Rare, and honest about it.
int choice;
do {
  choice = menu();
} while (choice != 0);
```

::tip
Reach for the enhanced `for` by default. It cannot go out of bounds, it cannot
have an off-by-one, and it says "every element" rather than "these indices". Use
the indexed form only when you genuinely need the index, which is less often
than people think.
::

## The boundary, where every bug lives

```java [OffByOne.java]
int[] marks = {78, 64, 81, 55, 92};       // valid indices: 0, 1, 2, 3, 4

for (int i = 0; i <= marks.length; i++)   // ← runs six times
  System.out.println(marks[i]);
```

```text [Output]
78
64
81
55
92
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException:
Index 5 out of bounds for length 5
```

::compare{caption="Two characters, and they are the difference between correct and crashing."}
  :::compare-side{label="`i <= length`" verdict="wrong"}
  Five elements, indices 0 to 4, and the loop reaches 5. Java counts from zero,
  so the last valid index is always `length - 1`.
  :::
  :::compare-side{label="`i < length`" verdict="right"}
  Stops at 4. This is why `<` is the default in a counted loop and `<=` should
  make you look twice.
  :::
::

::side-note{kind="go-deeper"}
The same boundary is why the attendance bug from the English track existed: a
rule that says "below 75%" written as `<= 75` flags a student at exactly 75.
Boundaries are `<` against `<=`, `0` against `1`, `first` against `second`, and
they are where you should always write your first test.
::

## `break` and `continue`

```java [Control.java]
// break: stop the loop entirely
for (Application a : applications) {
  if (a.getScore() > 95) {
    topper = a;
    break;                 // found it, no reason to look further
  }
}

// continue: skip this one, keep going
for (Application a : applications) {
  if (a.getScore() == null) continue;      // unmarked, not our problem here
  total += a.getScore();
}
```

::warning{icon="i-lucide-alert-triangle"}
A `break` inside a nested loop only breaks the **inner** one. This is a real and
common surprise. Labelled breaks exist and are usually a sign the loop should be
a method with a `return` instead, which is clearer and testable.
::

## Watch a loop, one step at a time

::code-trace{caption="Counting applicants above the cutoff. Follow the two variables."}
```java [Count.java]
int cutoff = 75;
int shortlisted = 0;
for (Application a : applications) {
  if (a.getScore() >= cutoff) {
    shortlisted++;
  }
}
System.out.println(shortlisted + " above " + cutoff);
```

  :::code-trace-step{lines="1-2" caption="Both set once, BEFORE the loop. A counter declared inside the loop would reset every iteration, which is the other classic beginner bug."}
  :::
  :::code-trace-step{lines="3" caption="Each element in turn. No index, so no boundary to get wrong."}
  :::
  :::code-trace-step{lines="4" caption=">= not >. 'Above the cutoff' in English is ambiguous, and somebody with exactly 75 is going to telephone about it. Ask."}
  :::
  :::code-trace-step{lines="5" caption="shortlisted++ is read, add, write. In a single thread that is fine; in the concurrency lesson it was the whole bug."}

## What you can do now

You can build text without accidentally writing a quadratic, choose the right
loop, and state where the bug in a loop almost always is.

## Your turn

::runner{lang="java"}
```java
public class Practice {
  public static void main(String[] args) {
    int[] marks = {78, 64, 81, 55, 92, 45, 88};

    // 1. This misses the last mark. Fix it.
    int total = 0;
    for (int i = 0; i < marks.length - 1; i++) total += marks[i];
    System.out.println("Total: " + total);

    // 2. Count how many are at or above 75. Expected: 4
    int passed = 0;
    for (int m : marks) if (m > 75) passed++;
    System.out.println("At or above 75: " + passed);

    // 3. Build "78, 64, 81, 55, 92, 45, 88" with no trailing comma.
    StringBuilder sb = new StringBuilder();
    for (int m : marks) sb.append(m).append(", ");
    System.out.println(sb.toString());
  }
}
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **1.** `i < marks.length`. The `- 1` is a boundary error in the other
  direction: it stops one early. Both directions are off-by-one and both are
  worth being able to spot instantly.

  **2.** `m >= 75`. As written it gives 3, because 78, 81, 92 and 88 are above 75
  and… actually that is 4 already. The real trap: there is no mark of exactly 75
  in this array, so the bug is **invisible in this test data**. Add a 75 and it
  appears. That is why boundary tests use the boundary value, and it is the single
  most valuable testing habit in this course.

  **3.** Three ways, and the third is the one to use:

  ```java
  // Trim afterwards — works, slightly sloppy
  String out = sb.substring(0, sb.length() - 2);

  // Separator before all but the first — the classic manual fix
  for (int i = 0; i < marks.length; i++) {
    if (i > 0) sb.append(", ");
    sb.append(marks[i]);
  }

  // Let the library do it
  String out = Arrays.stream(marks).mapToObj(String::valueOf)
                     .collect(Collectors.joining(", "));
  ```
  :::

## The interview question this answers

**"String, StringBuilder or StringBuffer?"**

`String` is immutable, so building in a loop copies everything each time and is
quadratic. `StringBuilder` is mutable and not synchronised, and is what you use.
`StringBuffer` is the same thing with every method synchronised, which was the
original and is now almost never right, because a builder used across threads is
a design problem rather than something a lock on `append` fixes. Quote the
measurement if you have it: 14 seconds against 9 milliseconds at 40,000 lines.
