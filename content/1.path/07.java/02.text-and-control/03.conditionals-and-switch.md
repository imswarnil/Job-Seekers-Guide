Ten `else if` lines that nobody will maintain. There is something built for
exactly that shape, and the modern form of it is one of the better things to
happen to Java recently.

## Why this matters in a job

Because a condition that cannot be read is a bug waiting to happen, and because
the status ladder in the university system — `RECEIVED` → `UNDER_REVIEW` →
`SHORTLISTED` or `REJECTED` → `ACCEPTED` — is exactly the shape `switch` exists
for, and you will build it later in this track.

## Conditions a human can read

```java [Eligibility.java]
// Technically correct, and nobody can check it by reading.
if (a.getScore() >= 60 && a.getProgrammeId() == 1 && !a.isWithdrawn()
    && (a.getCategory().equals("GEN") || a.getScore() >= 55)) {
  shortlist.add(a);
}
```

```java [Eligibility.java]
// Identical behaviour. Each line is now a sentence you can verify separately.
boolean meetsGeneralCutoff  = a.getScore() >= 60;
boolean meetsRelaxedCutoff  = a.getScore() >= 55 && !a.getCategory().equals("GEN");
boolean appliedToThis       = a.getProgrammeId() == programmeId;
boolean stillInTheRunning   = !a.isWithdrawn();

if (appliedToThis && stillInTheRunning && (meetsGeneralCutoff || meetsRelaxedCutoff)) {
  shortlist.add(a);
}
```

::pull-quote
Naming a condition costs one line and buys the ability to check the rule against
the policy document without holding four things in your head.
::

## Short-circuiting, which is a feature

```java [ShortCircuit.java]
// If applicant is null, the second half is never evaluated. No exception.
if (applicant != null && applicant.getScore() >= 60) { ... }

// Swap them and it throws. Order matters and is not stylistic.
if (applicant.getScore() >= 60 && applicant != null) { ... }
```

`&&` stops at the first `false` and `||` stops at the first `true`. That is why
the null check goes first, and it is a genuine interview question.

::side-note{kind="go-deeper"}
`&` and `|` also exist and do **not** short-circuit: both sides are always
evaluated. You will essentially never want them for booleans, and seeing one in
code is usually a typo rather than a decision.
::

## The ternary, used sparingly

```java [Ternary.java]
String result = marks >= 40 ? "PASS" : "FAIL";        // good: one small choice

// Bad: nested ternaries. Nobody reads these correctly under pressure.
String grade = m >= 90 ? "A" : m >= 80 ? "B" : m >= 70 ? "C" : m >= 60 ? "D" : "F";
```

One ternary is a readable expression. Two nested is a puzzle. That second line
wants to be a `switch` or a small method.

## `switch`, the modern form

The old `switch` needed `break` on every branch, and forgetting one caused
fall-through, which was a famous and expensive bug source. The arrow form does
not fall through at all.

```java [Status.java]
// Old form. Note the breaks, and imagine forgetting one.
switch (status) {
  case "RECEIVED":
    message = "We have your application.";
    break;
  case "SHORTLISTED":
    message = "You have been shortlisted.";
    break;
  default:
    message = "Status unknown.";
}
```

```java [Status.java]
// Arrow form: no break, no fall-through, and it is an EXPRESSION that returns.
String message = switch (status) {
  case "RECEIVED"      -> "We have your application.";
  case "UNDER_REVIEW"  -> "Your application is being reviewed.";
  case "SHORTLISTED"   -> "You have been shortlisted. Check your email.";
  case "REJECTED"      -> "Your application was not successful this intake.";
  case "ACCEPTED"      -> "Congratulations. Please pay the fee to confirm.";
  default              -> throw new IllegalArgumentException("Unknown: " + status);
};
```

::feature-list{columns="2"}
  :::feature{icon="i-lucide-check" title="No break, no fall-through"}
  The single largest source of `switch` bugs is gone by construction.
  :::
  :::feature{icon="i-lucide-equal" title="It is an expression"}
  It produces a value, so the variable can be `final` and is assigned exactly
  once. You cannot accidentally leave a branch that assigns nothing.
  :::
  :::feature{icon="i-lucide-shield" title="Exhaustive over an enum"}
  Switch over an `enum` with no `default` and the **compiler** checks every
  constant is handled. Add a new status later and it will not compile until you
  handle it, which is the feature.
  :::
  :::feature{icon="i-lucide-list" title="Several labels per branch"}
  `case "SHORTLISTED", "ACCEPTED" -> ...` for cases that share behaviour.
  :::
::

That third point is worth dwelling on, and it is the reason the next lesson but
one is about enums.

```java [Status.java]
// With an enum and no default, adding ON_HOLD later breaks the BUILD
// rather than silently falling through to a wrong message.
String message = switch (status) {
  case RECEIVED     -> "We have your application.";
  case UNDER_REVIEW -> "Your application is being reviewed.";
  case SHORTLISTED  -> "You have been shortlisted.";
  case REJECTED     -> "Not successful this intake.";
  case ACCEPTED     -> "Congratulations.";
};
```

::tip
Prefer no `default` when switching over an enum. A `default` silences the
compiler's exhaustiveness check, which is the main reason to be using an enum in
the first place. This is a small, specific piece of advice that sounds senior in
a code review.
::

## When a block is needed

```java [Block.java]
int seatsToRelease = switch (status) {
  case REJECTED, WITHDRAWN -> 1;
  case ACCEPTED -> {
    audit.record(applicationId, "SEAT_CONFIRMED");
    yield 0;                      // `yield`, not `return`: return exits the METHOD
  }
  default -> 0;
};
```

`yield` gives the value of the block. Using `return` there would return from the
enclosing method, which is a different and usually wrong thing.

## What you can do now

You can write a condition somebody else can verify, choose between `if` and
`switch` for a reason, and use exhaustiveness to make the compiler catch a
missing case.

## Your turn

::runner{lang="java"}
```java
public class Grades {
  public static void main(String[] args) {
    int[] marks = {95, 82, 74, 61, 38, 40};
    for (int m : marks) {
      System.out.println(m + " -> " + grade(m));
    }
  }

  // Rewrite this as a switch expression. Careful: switch compares equality,
  // so think about what you switch ON.
  static String grade(int marks) {
    if (marks >= 90) return "A";
    else if (marks >= 80) return "B";
    else if (marks >= 70) return "C";
    else if (marks >= 60) return "D";
    else if (marks >= 40) return "E";
    else return "F";
  }
}
```
::

::accordion
  :::accordion-item{label="The answer, and the trap in the question" icon="i-lucide-check"}
  **The trap:** `switch` matches equality, not ranges, so you cannot switch on
  `marks` directly. You switch on something derived:

  ```java
  static String grade(int marks) {
    return switch (marks / 10) {
      case 10, 9 -> "A";
      case 8     -> "B";
      case 7     -> "C";
      case 6     -> "D";
      case 5, 4  -> "E";
      default    -> "F";
    };
  }
  ```

  `marks / 10` is integer division, so 95 becomes 9 and 74 becomes 7. `case 10`
  handles a perfect 100.

  **And the honest verdict:** the `if`/`else` chain was clearer. This is a good
  exercise and a bad refactor, because the reader now has to work out what
  `marks / 10` means. Knowing when *not* to apply a technique is worth more than
  knowing the technique, and saying so in an interview is a strong signal.

  Note also that 40 correctly gives "E" and 38 gives "F" — check the boundary
  every time, because that is where the telephone call comes from.
  :::
::

   if-else?"**

## The interview question this answers

**"When would you use switch instead of if-else?"**

For a fixed, known set of values compared by equality. Then the reasons that are
specific to modern Java: the arrow form cannot fall through, it is an expression
so the result can be `final` and every branch must produce a value, and over an
enum without a `default` the compiler enforces that every constant is handled.
That last one converts a future bug into a build failure, which is the strongest
argument available for any language feature.
