Not your mistake, and the program still dies. Exceptions are how Java separates
"this went wrong" from "here is the answer", so that a failure cannot be mistaken
for a result.

## Why this matters in a job

Because the checked-versus-unchecked distinction is asked constantly, because
`catch (Exception e) {}` is the single most damaging line a junior can write, and
because an exception with a good message is the difference between a five-minute
fix and an afternoon.

| | Checked | Unchecked (`RuntimeException`) |
| --- | --- | --- |
| Compiler forces handling | **Yes** | No |
| Means | Something outside your control failed | A bug in the code |
| Examples | `IOException`, `SQLException` | `NullPointerException`, `IllegalArgumentException`, `IllegalStateException` |
| You should | Handle it or declare it | Fix the code so it cannot happen |

::pull-quote
Checked means "this can reasonably fail and you must decide what to do".
Unchecked means "somebody wrote this wrong". Catching the second kind to keep
going is hiding a bug.
::

## try, catch, finally

```java [ImportResults.java]
public void importResults(Path file) {
  Scanner scanner = null;
  try {
    scanner = new Scanner(file);
    while (scanner.hasNextLine()) {
      results.add(parse(scanner.nextLine()));
    }
  } catch (NoSuchFileException e) {
    throw new ImportFailedException("No results file at " + file, e);
  } catch (IOException e) {
    throw new ImportFailedException("Could not read " + file, e);
  } finally {
    if (scanner != null) scanner.close();      // runs whatever happens
  }
}
```

## try-with-resources, which replaces all of that

```java [ImportResults.java]
public void importResults(Path file) {
  try (Scanner scanner = new Scanner(file)) {        // closed automatically
    while (scanner.hasNextLine()) {
      results.add(parse(scanner.nextLine()));
    }
  } catch (IOException e) {
    throw new ImportFailedException("Could not read " + file, e);
  }
}
```

Anything implementing `AutoCloseable` is closed when the block exits, in reverse
order, even if an exception is thrown. It also handles a case the manual version
gets wrong: if both the body *and* `close()` throw, the close exception is
attached as suppressed rather than replacing the real one.

::tip
Use try-with-resources for every file, stream, connection and statement. A
resource leak does not fail immediately; it fails after four hours of production
traffic with "too many open files", and the stack trace points at whatever was
unlucky enough to be next.
::

## The line that does the damage

```java [Awful.java]
try {
  importResults(file);
} catch (Exception e) {
  // ignore
}
```

::warning{icon="i-lucide-alert-triangle"}
This catches everything including bugs, discards the reason, and continues as
though the work succeeded. The import silently did nothing, the results page is
empty, and there is no trace anywhere of why. I have lost a full day to one of
these written by somebody else. If you genuinely must swallow an exception,
**log it with the exception object**, and write a comment saying why swallowing
is correct here.
::

```java [Better.java]
try {
  importResults(file);
} catch (ImportFailedException e) {
  log.error("Results import failed for {}", file, e);   // the object, not e.getMessage()
  throw;                                                 // or handle it deliberately
}
```

Passing `e` rather than `e.getMessage()` is what preserves the stack trace. This
one detail is worth more than most of this lesson.

## Your own exceptions

Java's exceptions describe Java's problems. "This applicant has already applied
to this programme" is not in the JDK.

```java [DuplicateApplicationException.java]
public class DuplicateApplicationException extends RuntimeException {
  private final long applicantId;
  private final long programmeId;

  public DuplicateApplicationException(long applicantId, long programmeId) {
    super("Applicant %d has already applied to programme %d"
        .formatted(applicantId, programmeId));
    this.applicantId = applicantId;
    this.programmeId = programmeId;
  }

  public long getApplicantId()  { return applicantId; }
  public long getProgrammeId()  { return programmeId; }
}
```

::feature-list{columns="2"}
  :::feature{icon="i-lucide-tag" title="Named for the situation"}
  A caller can catch exactly this and nothing else, which is impossible with a
  generic `RuntimeException`.
  :::
  :::feature{icon="i-lucide-database" title="Carries the data"}
  The ids are fields, so the handler can build a useful response without parsing
  the message string.
  :::
  :::feature{icon="i-lucide-message-square" title="The message is a sentence"}
  With the actual values in it. Somebody reading a log at 2 a.m. can act on it.
  :::
  :::feature{icon="i-lucide-git-branch" title="Unchecked, deliberately"}
  This is a bug in the caller's logic, not an environmental failure. A checked
  exception here would force every caller to write a try-catch for something
  that should never happen.
  :::
::

## Checked or unchecked: the decision

::compare{caption="Ask: can the caller sensibly do something about it?"}
  :::compare-side{label="Checked" verdict="neutral"}
  The caller has a real alternative. The file is missing, so ask for another
  one. The network failed, so retry. Forcing them to decide is useful.
  :::
  :::compare-side{label="Unchecked" verdict="right"}
  The caller cannot fix it and should not have caused it. A duplicate
  application, a negative score, an invalid state transition. Let it propagate to
  one place that turns it into an error response.
  :::
::

::side-note{kind="go-deeper"}
Most modern Java leans unchecked. Checked exceptions were a good idea that in
practice produced `throws Exception` on every signature and `catch (Exception e)
{}` at the bottom. Spring wraps `SQLException` into unchecked
`DataAccessException` for exactly this reason. Knowing that this is a genuine
debate, rather than a settled rule, is a good thing to be able to say.
::

## Does `finally` always run?

The trick question, and the answer is "almost".

```java [Finally.java]
static int tricky() {
  try {
    return 1;
  } finally {
    return 2;        // ← wins. The 1 is discarded.
  }
}                     // returns 2
```

`finally` runs after the `return` value is computed and can replace it. This is
legal, extremely confusing, and should never be written. The two cases where
`finally` does **not** run: `System.exit()` inside the try, and the JVM being
killed.

You can catch the right exception at the right level, preserve a cause, design an

## Your turn

Fix every problem in this method. There are five.

```java [FeeImport.java]
public void importFees(String path) {
  try {
    FileReader reader = new FileReader(path);
    BufferedReader br = new BufferedReader(reader);
    String line;
    while ((line = br.readLine()) != null) {
      String[] parts = line.split(",");
      feeRepository.record(parts[0], Double.parseDouble(parts[1]));
    }
  } catch (Exception e) {
    System.out.println("error");
  }
}
```

::accordion
  :::accordion-item{label="The five, and the rewrite" icon="i-lucide-check"}
  1. **Nothing is closed.** Two readers leak on every call and on every exception.
  2. **`catch (Exception e)`** catches bugs as well as I/O failures, including
     the `NumberFormatException` and `ArrayIndexOutOfBoundsException` that a
     malformed line will throw.
  3. **The cause is discarded.** `"error"` on standard output, no stack trace, no
     file name, no line number.
  4. **The failure is swallowed**, so the caller believes the import succeeded.
  5. **`Double` for money.** From the primitives lesson: this must be paise as a
     `long`.

  ```java
  public ImportSummary importFees(Path path) {
    List<String> rejected = new ArrayList<>();
    int imported = 0;

    try (BufferedReader br = Files.newBufferedReader(path)) {
      String line;
      int lineNumber = 0;

      while ((line = br.readLine()) != null) {
        lineNumber++;
        String[] parts = line.split(",");
        if (parts.length != 2) {
          rejected.add("line %d: expected 2 columns, got %d"
              .formatted(lineNumber, parts.length));
          continue;
        }
        try {
          feeRepository.record(parts[0].strip(), Long.parseLong(parts[1].strip()));
          imported++;
        } catch (NumberFormatException e) {
          rejected.add("line %d: '%s' is not an amount in paise"
              .formatted(lineNumber, parts[1]));
        }
      }
    } catch (IOException e) {
      throw new ImportFailedException("Could not read " + path, e);
    }

    return new ImportSummary(imported, rejected);
  }
  ```

  **The design decision worth defending:** one bad line no longer destroys the
  whole import. Good rows are imported, bad rows are collected with their line
  numbers, and the caller gets both numbers back. That is the Margaret Hamilton
  lesson from the orientation track: decide in advance what should happen under
  failure, rather than discovering it.
  :::
::

## The interview question this answers

**"Checked versus unchecked exceptions"** and **"what is wrong with catching
Exception?"**

For the first: checked is enforced by the compiler and means an environmental
failure the caller can act on; unchecked means a programming error. Choose by
asking whether the caller can sensibly do anything about it. Add that modern Java
leans unchecked and that Spring wraps `SQLException` for that reason.

For the second: it catches bugs as well as failures, so a `NullPointerException`
gets treated as a network problem; and combined with an empty block it destroys
the evidence. Say what you do instead: catch the specific type, log the exception
object rather than its message, and let anything you cannot handle propagate.
