Two objects with identical details, and Java says they are different. You already
know why from chapter one: `equals` inherited from `Object` compares addresses,
and these are two objects.

## Why this matters in a job

Because this is the other half of the data structures lesson on hash tables, seen
from the language side, and because "what is the contract between equals and
hashCode" is one of the three most-asked Java questions in this market.

## What every class inherits

Every class extends `Object`, whether you say so or not, and inherits these:

| Method | What the default does | When to override |
| --- | --- | --- |
| `toString()` | `Applicant@4617c264` — the type and a hash | Essentially always. This is what logs and debuggers print. |
| `equals(Object)` | Reference comparison, same as `==` | Whenever two distinct objects can be meaningfully "the same" |
| `hashCode()` | Derived from the object's identity | **Always, if you override `equals`** |

## Watch it break

```java [Equality.java]
Applicant a = new Applicant("Anita Rao", "anita@university.edu");
Applicant b = new Applicant("Anita Rao", "anita@university.edu");

System.out.println(a.equals(b));        // false
System.out.println(a);                  // Applicant@4617c264

Set<Applicant> unique = new HashSet<>(List.of(a, b));
System.out.println(unique.size());      // 2 — a "set" with a duplicate in it
```

## Overriding equals

```java [Applicant.java]
@Override
public boolean equals(Object o) {
  if (this == o) return true;                    // fast path: same object
  if (!(o instanceof Applicant other)) return false;   // handles null too
  return email.equals(other.email);              // email IS the identity here
}
```

::feature-list{columns="2"}
  :::feature{icon="i-lucide-zap" title="`this == o` first"}
  Cheap, and it also makes an object equal to itself even if a field is null.
  :::
  :::feature{icon="i-lucide-shield" title="`instanceof` handles null"}
  `null instanceof Applicant` is `false`, so the null case is covered without a
  separate check. `equals(null)` must return false, never throw.
  :::
  :::feature{icon="i-lucide-target" title="Compare what is the identity"}
  Not every field. Two applicant records with the same email are the same
  applicant even if one has a newer phone number. Decide deliberately.
  :::
  :::feature{icon="i-lucide-lock" title="Use immutable fields"}
  If the fields `equals` uses can change, the object's identity can change while
  it sits in a set, which is the mutable-key bug.
  :::
::

## And now the part that catches people

```java [Broken.java]
// equals overridden, hashCode NOT.
Map<Applicant, Integer> scores = new HashMap<>();
scores.put(new Applicant("Anita Rao", "anita@university.edu"), 78);

Integer score = scores.get(new Applicant("Anita Rao", "anita@university.edu"));
System.out.println(score);        // null
System.out.println(a.equals(b));  // true
```

The two objects are equal, and the map cannot find the entry. From the data
structures track you know exactly why: the map computes the hash first to choose
a bucket, the two hashes differ, it looks in the wrong bucket, and `equals` is
never called at all.

::pull-quote
The contract: if two objects are equal, their hash codes must be equal. Break it
and a map will look in the wrong bucket for an entry that is sitting in it.
::

```java [Applicant.java]
@Override
public int hashCode() {
  return Objects.hash(email);        // the SAME fields equals uses
}
```

::warning{icon="i-lucide-alert-triangle"}
The reverse is not required: two unequal objects may share a hash code. That is a
collision, it is normal, and it is why `hashCode() { return 1; }` is technically
legal. It also turns every lookup into a linear scan, which you measured in the
data structures exercises.
::

## `toString`, which you will use most

```java [Applicant.java]
@Override
public String toString() {
  return "Applicant[%s, %s, score=%s]"
      .formatted(fullName, email, score < 0 ? "unmarked" : score);
}
```

```text [In a log, at 2 a.m.]
Failed to shortlist: Applicant[Anita Rao, anita@university.edu, score=unmarked]
```

Against `Failed to shortlist: Applicant@4617c264`, which tells you nothing. This
is the single highest-return method to override and the one people forget.

::tip
Never put a password, a token or a full identifier in `toString`. Logs are
copied, shared and stored for years, and `toString` is called by logging
frameworks automatically. This is a real and common data-protection failure.
::

## Records write all three

Since Java 16, a class whose job is to hold data can be one line.

```java [ExamResult.java]
public record ExamResult(String rollNumber, String subjectCode, int marks) { }
```

That gives you, generated and correct:

- `private final` fields
- a constructor taking all three
- accessors `rollNumber()`, `subjectCode()`, `marks()` — no `get` prefix
- `equals` comparing **all** components
- `hashCode` consistent with it
- a readable `toString`

```java [Records.java]
var r1 = new ExamResult("2026CSE0184", "CS-201", 78);
var r2 = new ExamResult("2026CSE0184", "CS-201", 78);

System.out.println(r1.equals(r2));   // true
System.out.println(r1);              // ExamResult[rollNumber=2026CSE0184, ...]
System.out.println(Set.of(r1, r2).size());   // 1
```

Sixty lines of boilerplate that could each be subtly wrong, replaced by one line
that cannot be.

### Validating in a record

```java [ExamResult.java]
public record ExamResult(String rollNumber, String subjectCode, int marks) {
  public ExamResult {                       // compact constructor: no parameters
    if (marks < 0 || marks > 100) {
      throw new IllegalArgumentException("Marks must be 0–100, got " + marks);
    }
    rollNumber = rollNumber.strip();        // normalise before assignment
  }
}
```

### When a record is the wrong choice

::pros-cons
---
title: record
pros:
  - Immutable by construction, so it is safe as a map key and across threads
  - equals, hashCode and toString are generated and consistent with each other
  - The intent is visible: this type carries data, it does not have behaviour
cons:
  - Fields are always final, so it cannot model something that changes
  - It cannot extend a class, so it will not fit into an existing hierarchy
  - equals uses every component, which is sometimes not what identity means
---
::

That last point is the real one. An `Applicant` identified by email should not
have `equals` comparing the phone number too, and a record gives you no choice.
Records are for values; classes are for things with identity and a life cycle.

## What you can do now

You can override the three inherited methods correctly, state the contract and
its consequence, and use a record where the class exists only to carry data.

## Your turn

::runner{lang="java"}
```java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    Subject a = new Subject("CS-201", "DBMS");
    Subject b = new Subject("CS-201", "Database Management Systems");

    System.out.println(a.equals(b));                 // 1
    System.out.println(new HashSet<>(List.of(a, b)).size());  // 2
    System.out.println(a);                           // 3

    Map<Subject, Integer> credits = new HashMap<>();
    credits.put(a, 4);
    System.out.println(credits.get(b));              // 4
  }
}

class Subject {
  final String code;
  final String name;
  Subject(String code, String name) { this.code = code; this.name = name; }

  @Override public boolean equals(Object o) {
    return o instanceof Subject s && code.equals(s.code);
  }
  // hashCode deliberately missing
}
```
::

Predict all four, then fix the class two ways: by hand, and as a record.

::accordion
  :::accordion-item{label="Answers, and why the record version is not a free win" icon="i-lucide-check"}
  **1. `true`** — `equals` compares only the code.
  **2. `2`** — the set should hold one. Different hashes, different buckets,
  `equals` never consulted.
  **3. `Subject@4617c264`** — no `toString`.
  **4. `null`** — the entry is in the map and cannot be found.

  **By hand:**
  ```java
  @Override public int hashCode() { return Objects.hash(code); }
  @Override public String toString() { return "Subject[" + code + " " + name + "]"; }
  ```

  **As a record:**
  ```java
  record Subject(String code, String name) { }
  ```

  **And why that is not simply better here:** the record's `equals` compares
  **both** components, so `a.equals(b)` becomes `false`, because the two have
  different names for the same subject code. The hand-written version says two
  subjects are the same when their codes match, which is probably what the
  university means.

  That is the whole decision, and it is a good thing to be able to say: a record
  is right when every component is part of the identity. When identity is one
  field and the rest is descriptive, write the class.
  :::
::

## The interview question this answers

**"What is the contract between equals and hashCode?"**

Equal objects must have equal hash codes; unequal objects may share one. Then the
consequence, which is what they are listening for: a `HashMap` hashes first to
pick a bucket, so if the hashes differ it looks in the wrong bucket and never
calls `equals`. The entry is in the map and `get` returns null.

Follow-ups to have ready: why map keys should be immutable, why `hashCode()
{ return 1; }` is legal and catastrophic, and why a record is the right answer
when the type is pure data and the wrong one when identity is a single field.
