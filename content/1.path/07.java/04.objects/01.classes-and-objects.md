Names in one array, scores in another, matched by position. Sort one and forget
the other, and every student gets somebody else's marks.

::warning{icon="i-lucide-alert-triangle"}
**This is the hardest conceptual jump so far, and it took me weeks.** I could
write the syntax in my second week and I did not understand what I was doing for
about two months. If it does not click immediately, that is the normal
experience and not a signal about you. Read it twice, build something small, and
it arrives.
::

## Why this matters in a job

Because every Java system you will ever read is made of objects, because the
object-oriented round is a fixed part of interviews in this market, and because
the alternative — data scattered across parallel structures — is the source of an
entire category of bug that simply cannot happen once the data is bundled.

## The problem, made concrete

```java [Parallel.java]
String[] names  = {"Anita Rao", "Vikram Shah", "Priya Nair"};
int[]    scores = {78, 64, 81};
boolean[] withdrawn = {false, false, true};

// Sort by score. Now what?
Arrays.sort(scores);
```

```text [After]
names      = ["Anita Rao", "Vikram Shah", "Priya Nair"]
scores     = [64, 78, 81]
withdrawn  = [false, false, true]
```

Anita now has Vikram's score and Priya is still marked withdrawn while holding
somebody else's marks. Nothing crashed. Nothing is detectable. The three arrays
were only ever related by a convention nobody enforced.

## A class is that convention, enforced

```java [Applicant.java]
public class Applicant {
  String fullName;
  int score;
  boolean withdrawn;
}
```

```java [Admissions.java]
Applicant a = new Applicant();
a.fullName = "Anita Rao";
a.score = 78;

Applicant[] applicants = { a, b, c };
Arrays.sort(applicants, comparing(x -> x.score));   // the name travels with it
```

One object holds the facts that belong together, so sorting cannot separate them.
That is the whole idea, before any of the vocabulary.

::pull-quote
A class is a description. An object is one actual thing made from it. The class
`Applicant` is written once; there are forty thousand `Applicant` objects.
::

## What `new` really does

Three steps, and you already know the picture from chapter one.

::flow{numbered direction="vertical" caption="`new Applicant()` — and the reference is the only part that lands on the stack."}
  :::flow-step{label="Allocate space on the heap" icon="i-lucide-box"}
  Enough for every field in the class, found by the JVM.
  :::
  :::flow-step{label="Fill the fields with defaults" icon="i-lucide-circle-dot"}
  Numbers 0, booleans false, **objects null**. Never random memory, which is a
  genuine improvement over some other languages.
  :::
  :::flow-step{label="Run the constructor" icon="i-lucide-hammer" highlight}
  Your chance to make the object valid before anybody can use it.
  :::
  :::flow-step{label="Return the address" icon="i-lucide-link"}
  Which is what the variable on the stack holds.
  :::
::

```java [Defaults.java]
Applicant a = new Applicant();
System.out.println(a.score);      // 0
System.out.println(a.fullName);   // null
System.out.println(a.fullName.length());   // NullPointerException
```

An object born with all-default fields is almost never a valid anything. A score
of 0 is indistinguishable from "not marked yet", and a null name will throw the
moment somebody prints it.

## Constructors, so it is born correct

```java [Applicant.java]
public class Applicant {
  private final String fullName;
  private final String email;
  private int score;
  private boolean withdrawn;

  public Applicant(String fullName, String email) {
    if (fullName == null || fullName.isBlank()) {
      throw new IllegalArgumentException("An applicant must have a name.");
    }
    if (email == null || !email.contains("@")) {
      throw new IllegalArgumentException("A valid email is required: " + email);
    }
    this.fullName = fullName;      // `this.` distinguishes field from parameter
    this.email = email;
    this.score = -1;               // -1 means "not marked", distinct from 0
    this.withdrawn = false;
  }
}
```

```java [Admissions.java]
new Applicant("", "anita@university.edu");
```

```text [Output]
Exception in thread "main" java.lang.IllegalArgumentException:
An applicant must have a name.
```

::pull-quote
An object with a constructor that validates cannot exist in an invalid state.
That is not a convenience. It removes an entire class of "how did this row get
into the database" from the rest of the program.
::

::side-note{kind="go-deeper"}
Note `score = -1` rather than 0. A default of 0 is a real mark, so "not marked"
and "scored nothing" would be indistinguishable, and the average would be wrong
in a way nobody notices. This is the same `NULL`-versus-zero distinction as the
DBMS track, in the language rather than the schema, and it is worth seeing twice.
::

## Constructor chaining

```java [Applicant.java]
public Applicant(String fullName, String email) {
  this(fullName, email, -1);          // must be the FIRST statement
}

public Applicant(String fullName, String email, int score) {
  // one place where the validation actually lives
  ...
}
```

One constructor does the real work and the others delegate to it. That way the
validation cannot drift apart between them, which it always does otherwise.

## `static`, and what it means now

```java [Applicant.java]
public class Applicant {
  private static int totalCreated = 0;      // ONE, shared by every Applicant
  private final String fullName;            // one PER object

  public Applicant(String fullName) {
    this.fullName = fullName;
    totalCreated++;
  }

  public static int getTotalCreated() {     // called on the CLASS, not an object
    return totalCreated;
  }
}
```

```java [Admissions.java]
new Applicant("Anita Rao");
new Applicant("Vikram Shah");
System.out.println(Applicant.getTotalCreated());   // 2
```

`static` means "belongs to the class". It is why `main` is static — the JVM calls
it before any object exists. And from the operating systems track you already
know the other half of the sentence: one per class **per process**, which is why
a static cache stops working the moment you run a second server.

::warning{icon="i-lucide-alert-triangle"}
A `static` field that changes is shared mutable state, which in a web application
means every request in flight sees it. That is the concurrency lesson arriving in
a new costume, and it is why a mutable static field is a code smell rather than a
technique.
::

## What you can do now

You can bundle related data so it cannot be separated, write a constructor that
refuses to build something invalid, and say what `static` means precisely.

## Your turn

::runner{lang="java"}
```java
public class Main {
  public static void main(String[] args) {
    // 1. This compiles and is wrong in three ways. Find them.
    Subject s = new Subject();
    System.out.println(s.code + " has " + s.credits + " credits, " + s.name.length());
  }
}

class Subject {
  String code;
  String name;
  int credits;
}
```
::

Then rewrite `Subject` so that:
- it cannot be created without a code and a name
- `credits` must be between 1 and 6
- the fields cannot be changed from outside afterwards

::accordion
  :::accordion-item{label="The three problems, and the rewrite" icon="i-lucide-check"}
  **The three:** `code` is null, `credits` is 0 which is not a legal number of
  credits, and `s.name.length()` throws a `NullPointerException` because `name`
  is null. All three come from the same cause: an object was allowed to exist
  before it was valid.

  ```java
  public class Subject {
    private final String code;
    private final String name;
    private final int credits;

    public Subject(String code, String name, int credits) {
      if (code == null || code.isBlank()) {
        throw new IllegalArgumentException("A subject needs a code.");
      }
      if (name == null || name.isBlank()) {
        throw new IllegalArgumentException("A subject needs a name.");
      }
      if (credits < 1 || credits > 6) {
        throw new IllegalArgumentException(
            "Credits must be between 1 and 6, got " + credits);
      }
      this.code = code;
      this.name = name;
      this.credits = credits;
    }

    public String getCode()    { return code; }
    public String getName()    { return name; }
    public int    getCredits() { return credits; }
  }
  ```

  **Notice what `final` bought:** there is no way to set a field after
  construction, so every `Subject` that exists anywhere in the program has been
  through that validation. You never have to wonder. That property is called an
  invariant, and it is the subject of the encapsulation lesson next.

  **And notice the error messages.** `"Credits must be between 1 and 6, got 0"`
  tells whoever hits it what to do. `"Invalid input"` does not, and you will meet
  it at 2 a.m. in a log with no other context.
  :::
::

## Check yourself

1. What are the three things `new` does before your constructor runs?
2. **An interviewer asks: "what is the difference between a class and an
   object?"** Answer without saying "blueprint".

## The interview question this answers

**"What is a class and what is an object?"**

Everybody says blueprint and house, which is fine and says nothing about whether
you have used them. Better: a class is a description written once, an object is
one instance of it with its own copy of the instance fields, and `static` members
belong to the class rather than to any object. Then the *reason*, which is the
part that lands: bundling related data means it cannot be accidentally separated,
and a validating constructor means an invalid object cannot exist. Give the
parallel-arrays example. It is concrete and everybody has written that bug.
