Copy three fields into two more classes, or say "the same as that one, plus a
few extras". Inheritance is the second option, and it is both the most taught and
the most over-used idea in this language.

## Why this matters in a job

Because polymorphism is the mechanism behind essentially every framework you will
use, because "overloading versus overriding" is asked in almost every Java
interview, and because knowing when *not* to inherit is what separates a
maintainable design from a hierarchy nobody can change.

## What is shared

```java [Person.java]
public abstract class Person {
  private final String fullName;
  private final String email;
  private String phone;

  protected Person(String fullName, String email) {
    if (fullName == null || fullName.isBlank()) {
      throw new IllegalArgumentException("A person needs a name.");
    }
    this.fullName = fullName;
    this.email = email;
  }

  public String getFullName() { return fullName; }
  public String getEmail()    { return email; }

  /** Every kind of person describes themselves differently. */
  public abstract String describe();
}
```

```java [Applicant.java]
public class Applicant extends Person {
  private int score = -1;

  public Applicant(String fullName, String email) {
    super(fullName, email);            // must be first: the parent is built first
  }

  @Override
  public String describe() {
    return getFullName() + ", applicant, score " + (score < 0 ? "not marked" : score);
  }
}
```

```java [Faculty.java]
public class Faculty extends Person {
  private final String department;

  public Faculty(String fullName, String email, String department) {
    super(fullName, email);
    this.department = department;
  }

  @Override
  public String describe() {
    return "Dr " + getFullName() + ", " + department;
  }
}
```

## Construction order, which is asked about

::flow{numbered direction="vertical" caption="`new Applicant(...)` builds from the parent down. Always."}
  :::flow-step{label="Fields get their defaults" icon="i-lucide-circle-dot"}
  Everything in the whole chain: 0, false, null.
  :::
  :::flow-step{label="The parent constructor runs" icon="i-lucide-arrow-up" highlight}
  Explicitly with `super(...)`, or implicitly with `super()` if you write
  nothing. A parent with no no-argument constructor and no explicit `super(...)`
  call is a compile error, and it catches everybody once.
  :::
  :::flow-step{label="Field initialisers run" icon="i-lucide-equal"}
  `private int score = -1;` happens here, **after** the parent is finished.
  :::
  :::flow-step{label="The child's constructor body runs" icon="i-lucide-hammer"}
  By now the parent half of the object is fully valid, which is exactly why the
  order is this way round.
  :::
::

::warning{icon="i-lucide-alert-triangle"}
Never call an overridable method from a constructor. The parent constructor runs
before the child's field initialisers, so an overridden method called from the
parent sees the child's fields still at their defaults. It is a genuinely
confusing bug and a favourite interview question.
::

## Polymorphism: one call, several behaviours

```java [Directory.java]
List<Person> everyone = List.of(
    new Applicant("Anita Rao", "anita@university.edu"),
    new Faculty("Iyer", "iyer@university.edu", "Computer Science"),
    new Applicant("Vikram Shah", "vikram@university.edu"));

for (Person p : everyone) {
  System.out.println(p.describe());     // which describe() runs?
}
```

```text [Output]
Anita Rao, applicant, score not marked
Dr Iyer, Computer Science
Vikram Shah, applicant, score not marked
```

The variable is declared `Person`. The method that runs is the one belonging to
the object **actually there**, decided at run time. That is **dynamic dispatch**,
and it is the single most important mechanism in object-oriented programming.

::pull-quote
The declared type decides what you are allowed to call. The actual object decides
what happens when you call it.
::

This is why frameworks work. Spring holds a `List<Filter>` and calls
`doFilter` on each, having never heard of the filter you wrote last week.

## Overloading and overriding, told apart

The question asked in every Java interview.

| | Overloading | Overriding |
| --- | --- | --- |
| What | Same name, **different parameters**, same class | Same signature, **subclass** replaces the parent's version |
| Decided | At **compile** time, from declared types | At **run** time, from the actual object |
| Return type | Can differ, and does not distinguish them | Must be the same or a subtype |
| Access | Anything | Cannot be **more** restrictive than the parent's |
| `static` methods | Can be overloaded | **Cannot be overridden** — see below |

```java [Hiding.java]
class Parent { static String who() { return "parent"; } }
class Child extends Parent { static String who() { return "child"; } }

Parent p = new Child();
System.out.println(p.who());       // "parent" — NOT "child"
```

A `static` method belongs to the class, so the call is resolved from the
**declared** type at compile time. This is called *hiding*, not overriding, and
it is a favourite trick question. The answer to "can you override a static
method" is no, and the reason is that dispatch needs an object.

::tip
Always write `@Override`. It is not decoration: if you get the signature wrong —
`equals(Applicant)` instead of `equals(Object)` — the compiler tells you
immediately instead of you silently creating an overload that is never called.
That single annotation prevents one of the most confusing bugs in the language.
::

## The honest cost

Inheritance is taught as the centrepiece of object-oriented design and is usually
the wrong tool.

::pros-cons
---
title: extends
pros:
  - Genuinely models "is a" — an Applicant really is a Person
  - Shared behaviour in one place, and polymorphism through the parent type
  - One `describe()` call handles every kind, with no if-else on type
cons:
  - Only one parent, ever, and you cannot change it later without breaking callers
  - The child depends on the parent's internals, so changing the parent breaks children
  - Deep hierarchies become impossible to reason about, and they always deepen
  - It is frequently used for code reuse where the "is a" is simply not true
---
::

::compare{caption="The classic mistake, and it looks reasonable at the time."}
  :::compare-side{label="Inherited for reuse" verdict="wrong"}
  ```java
  class FeeReport extends ReportFormatter { }
  ```
  A fee report is not a kind of report formatter. It *uses* one. This compiles,
  works, and in two years `FeeReport` has inherited twenty methods that make no
  sense on it and cannot be removed.
  :::
  :::compare-side{label="Composed" verdict="right"}
  ```java
  class FeeReport {
    private final ReportFormatter formatter;      // "has a"
    FeeReport(ReportFormatter formatter) { this.formatter = formatter; }
  }
  ```
  The formatter can be swapped, tested separately, and none of its methods leak
  onto `FeeReport`.
  :::
::

::pull-quote
The test: can you say "a Y is a X" and have it be true of every Y, forever? If
you find yourself saying "a Y has an X" or "a Y uses an X", use a field.
::

## Casting, and where ClassCastException comes from

```java [Casting.java]
Person p = new Applicant("Anita Rao", "anita@university.edu");
p.setScore(78);                       // compile error: Person has no setScore

// Getting back down. This is where it goes wrong.
Applicant a = (Applicant) p;          // fine, p really is an Applicant
a.setScore(78);

Person f = new Faculty("Iyer", "iyer@university.edu", "CSE");
Applicant bad = (Applicant) f;        // compiles, throws at run time
```

```text [Output]
Exception in thread "main" java.lang.ClassCastException:
class Faculty cannot be cast to class Applicant
```

```java [Casting.java]
// Modern Java: test and bind in one step.
if (p instanceof Applicant applicant) {
  applicant.setScore(78);             // `applicant` only exists inside the if
}
```

::side-note{kind="go-deeper"}
A cast is usually a design smell. If your code is testing "what kind is this" and
branching, the branching probably belongs in a method on the type itself, which
is what polymorphism is for. `instanceof` chains are the most common way an
object-oriented design quietly becomes a switch statement.
::

## What you can do now

You can share behaviour without copying it, explain dynamic dispatch, tell
overloading from overriding with the static-method trick, and argue for
composition where the "is a" does not hold.

## Your turn

::runner{lang="java"}
```java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    List<Person> people = List.of(
        new Applicant("Anita Rao"),
        new Faculty("Iyer", "Computer Science"),
        new Student("Vikram Shah", "2026CSE0184"));

    for (Person p : people) System.out.println(p.describe());

    // 1. Why does this not compile? Fix it two ways.
    // people.get(2).getRollNumber();
  }
}

abstract class Person {
  private final String name;
  protected Person(String name) { this.name = name; }
  public String getName() { return name; }
  public abstract String describe();
}

class Applicant extends Person {
  Applicant(String name) { super(name); }
  public String describe() { return getName() + " — applicant"; }
}

class Faculty extends Person {
  private final String dept;
  Faculty(String name, String dept) { super(name); this.dept = dept; }
  public String describe() { return "Dr " + getName() + ", " + dept; }
}

class Student extends Person {
  private final String rollNumber;
  Student(String name, String rollNumber) { super(name); this.rollNumber = rollNumber; }
  public String getRollNumber() { return rollNumber; }
  public String describe() { return getName() + " (" + rollNumber + ")"; }
}
```
::

::accordion
  :::accordion-item{label="Answers" icon="i-lucide-check"}
  **Why it does not compile:** the list is `List<Person>`, so the compiler only
  allows methods declared on `Person`. It has no idea that element 2 happens to
  be a `Student`. The declared type decides what you may call.

  **Fix one, the cast:**
  ```java
  if (people.get(2) instanceof Student s) {
    System.out.println(s.getRollNumber());
  }
  ```

  **Fix two, and it is the better one:** do not reach for the subtype at all. If
  the caller needs a roll number from a `Person`, either the loop should be over
  `List<Student>`, or whatever the roll number was *for* belongs in `describe()`
  or another method on `Person`.

  **The design question this is really asking:** every time you cast, ask whether
  the behaviour you are about to perform could live on the type instead. Usually
  it can, and then the `instanceof` disappears along with the next four that were
  going to follow it.
  :::
::

1. Why does calling a `static` method through a parent-typed variable run the
   parent's version?
2. **An interviewer asks: "what is the difference between overloading and
   overriding?"** Answer with when each is resolved.

## The interview question this answers

**"Overloading versus overriding"** — near-universal, and the discriminating
detail is *when* each is decided. Overloading is compile time from the declared
types; overriding is run time from the actual object. Then the follow-ups you can
pre-empt: a static method cannot be overridden because dispatch needs an object,
and `@Override` exists so a mistyped signature fails the build instead of
silently becoming an unused overload.

If they ask "inheritance or composition", the answer is the "is a" test, plus the
honest observation that inheritance is frequently used for reuse where the
relationship is not true, and that a hierarchy is far harder to change later than
a field.
