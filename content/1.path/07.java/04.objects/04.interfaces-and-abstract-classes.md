One parent, ever. An interface is how something can be several things at once,
and it is the mechanism behind almost every design decision you will be asked to
justify.

## Why this matters in a job

Because "interface or abstract class" is a standard interview question with a
clear answer, and because the real reason interfaces matter in a job is one that
tutorials rarely give: they are what makes code testable without a database.

## An interface is a contract

```java [Notifiable.java]
public interface Notifiable {
  String getEmail();
  String getPreferredName();

  /** A default method: shared behaviour with no state. */
  default String greeting() {
    return "Dear " + getPreferredName() + ",";
  }
}
```

```java [Scoreable.java]
public interface Scoreable {
  int getScore();
  boolean isEligible(int cutoff);
}
```

```java [Applicant.java]
public class Applicant extends Person implements Notifiable, Scoreable {
  // one parent class, as many interfaces as it needs
}
```

An `Applicant` is a `Person`, and it can be notified, and it can be scored. Those
last two have nothing to do with each other and neither belongs in `Person`,
because a `Faculty` is notifiable and not scoreable.

## What an interface may contain

| | Interface | Abstract class |
| --- | --- | --- |
| Instance fields | **No** | Yes |
| Constructor | No | Yes |
| Abstract methods | Yes | Yes |
| Method bodies | Yes, as `default` or `static` | Yes |
| How many per class | **As many as you like** | Exactly one |
| Constants | Yes, implicitly `public static final` | Yes |

The first two rows are the whole difference. An interface cannot hold state and
cannot control construction; an abstract class can do both.

## The decision, stated plainly

::compare{caption="Ask one question: is there shared state, or only shared capability?"}
  :::compare-side{label="Abstract class" verdict="neutral"}
  Use it when subtypes share **state and construction**. `Person` holds a name
  and an email, validates them in its constructor, and every subtype needs
  exactly that. There is a real "is a" and there is data.
  :::
  :::compare-side{label="Interface" verdict="right"}
  Use it when types share a **capability** and nothing else. `Notifiable` says
  "this can receive a message". A `Faculty`, an `Applicant` and a `Department`
  can all do that and are otherwise unrelated. **Prefer this by default.**
  :::
::

::pull-quote
An abstract class says what something is. An interface says what something can
do. A class has one identity and any number of capabilities, and that asymmetry
is the entire answer.
::

## The reason that matters in a job

This is the part tutorials leave out, and it is the reason interfaces are
everywhere in real code.

```java [Shortlister.java]
// Tied to a real database. Impossible to test without one.
public class Shortlister {
  private final PostgresApplicationRepository repo = new PostgresApplicationRepository();

  public List<Applicant> shortlist(int cutoff) {
    return repo.findAll().stream()...
  }
}
```

```java [Shortlister.java]
// Depends on the CAPABILITY, not on the implementation.
public interface ApplicationRepository {
  List<Application> findByIntake(String intake);
}

public class Shortlister {
  private final ApplicationRepository repo;

  public Shortlister(ApplicationRepository repo) {     // handed in, not created
    this.repo = repo;
  }
}
```

```java [ShortlisterTest.java]
// A test with no database, no network and no waiting.
@Test
void shortlistsOnlyAboveTheCutoff() {
  ApplicationRepository fake = intake -> List.of(
      application("Anita", 78), application("Vikram", 64));

  List<Applicant> result = new Shortlister(fake).shortlist(75);

  assertEquals(1, result.size());
  assertEquals("Anita", result.get(0).getFullName());
}
```

The fake repository is one line, because the interface has one method. The test
runs in a millisecond and cannot fail because somebody changed a row in a shared
database.

::real-life{title="Why every framework you will meet is built this way" source="Spring, and everything like it"}
Handing a dependency in rather than creating it inside is called dependency
injection, and it is the whole of what Spring does. `@Autowired
ApplicationRepository repo` is Spring deciding, at start-up, which implementation
to hand you: the real one in production and a fake in a test. Understanding this
lesson is understanding the framework, and most people learn the annotation first
and the reason years later.
::

## `default` methods, and what they are for

```java [Notifiable.java]
public interface Notifiable {
  String getEmail();
  String getPreferredName();

  default String greeting() {
    return "Dear " + getPreferredName() + ",";
  }
}
```

A `default` method lets an interface gain a method without breaking every class
that already implements it. That is why they were added: `List` gained
`sort`, `forEach` and `removeIf` in Java 8 without any existing implementation
having to change.

::note
Use them for behaviour derivable from the interface's own methods, as above.
Do not use them to smuggle in an abstract class: an interface still cannot hold
state, so a `default` method that wants a field is telling you it belongs
elsewhere.
::

## Functional interfaces

An interface with exactly one abstract method can be implemented by a lambda,
which is why the fake repository above was one line.

```java [Functional.java]
@FunctionalInterface
interface EligibilityRule {
  boolean test(Application application);
}

EligibilityRule aboveCutoff   = a -> a.getScore() >= 60;
EligibilityRule notWithdrawn  = a -> !a.isWithdrawn();

List<Application> eligible = applications.stream()
    .filter(aboveCutoff::test)
    .filter(notWithdrawn::test)
    .toList();
```

Rules are now values: they can be stored, passed and combined. The whole
`java.util.function` package, `Predicate`, `Function`, `Supplier`, `Consumer`:
is this idea, and it is what the streams lesson is built on.

## What you can do now

You can choose between an interface and an abstract class for a reason, and you
can write a class that is testable without a database, which is the practical
pay-off for all of it.

## Your turn

The university needs to send messages: email now, SMS later, and a printed letter
for applicants with no email.

1. Design the interface.
2. Write two implementations.
3. Write the `Shortlister` so a test can use a fake without sending anything.

::accordion
  :::accordion-item{label="One answer, and the design note that matters" icon="i-lucide-check"}
  ```java
  public interface MessageSender {
    void send(String to, String subject, String body);
  }

  public class EmailSender implements MessageSender {
    public void send(String to, String subject, String body) { /* SMTP */ }
  }

  public class SmsSender implements MessageSender {
    public void send(String to, String subject, String body) {
      /* subject ignored: SMS has none. See the note below. */
    }
  }

  public class ShortlistNotifier {
    private final MessageSender sender;
    public ShortlistNotifier(MessageSender sender) { this.sender = sender; }

    public void notifyShortlisted(List<Applicant> shortlisted) {
      for (Applicant a : shortlisted) {
        sender.send(a.getEmail(), "Shortlisted",
                    "Dear " + a.getFullName() + ", you have been shortlisted.");
      }
    }
  }
  ```

  ```java
  // The test. No SMTP, no network, and it asserts on what was sent.
  @Test
  void sendsOneMessagePerShortlistedApplicant() {
    List<String> sent = new ArrayList<>();
    MessageSender fake = (to, subject, body) -> sent.add(to);

    new ShortlistNotifier(fake).notifyShortlisted(List.of(anita, vikram));

    assertEquals(List.of("anita@university.edu", "vikram@university.edu"), sent);
  }
  ```

  **The design note worth making in an interview:** `SmsSender` ignoring
  `subject` is a smell. An interface whose implementations must ignore parameters
  is slightly wrong, and the honest fixes are either a `Message` object that
  carries what each channel needs, or separate interfaces. Noticing that out loud
  is worth more than the code, because it shows you evaluate a design rather than
  only produce one.
  :::
::

## The interview question this answers

**"Interface or abstract class?"**

Abstract class when subtypes share state and construction; interface when they
share a capability. A class has one identity and any number of capabilities, so
prefer the interface by default.

Then the answer that separates you: say *why it matters in practice*. Depending
on an interface rather than a concrete class means the dependency can be handed
in, so the class can be tested with a one-line fake instead of a database. That
is dependency injection, it is what every Spring application is doing, and being
able to explain the reason rather than the annotation is unusual in a fresher.
