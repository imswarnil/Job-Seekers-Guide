The guarantee lasted exactly as long as construction. A constructor that
validates is worth nothing if the next line can undo it.

## Why this matters in a job

Because "why do we use getters and setters" is asked constantly and the usual
answer, "for encapsulation", is circular. The real answer is about invariants,
and it is the difference between a class that protects itself and one with
ceremony bolted on.

## The problem

```java [Applicant.java]
public class Applicant {
  public String fullName;
  public int score;        // validated in the constructor. And then?
}
```

```java [Anywhere.java]
Applicant a = new Applicant("Anita Rao", "anita@university.edu");
a.score = -50;             // nothing stops this
a.fullName = null;         // nor this
```

Every validation you wrote is now a suggestion. And the damage is not only that
the data is wrong: it is that when you find a score of −50 in the database, **any
line in the codebase could have done it**, so there is nowhere to look.

## An invariant

A fact about an object that is true from the moment it is created until it is
destroyed. For an `Applicant`:

- the name is never null or blank
- the score is either −1 (not marked) or between 0 and 100
- a withdrawn applicant can never be shortlisted

::pull-quote
Encapsulation is not about hiding data. It is about there being exactly one place
that can break each rule, so that when a rule is broken you know where to look.
::

## The fix

```java [Applicant.java]
public class Applicant {
  private final String fullName;      // private: nobody outside can touch it
  private int score;
  private boolean withdrawn;

  public Applicant(String fullName, String email) { ... }   // validates

  public String getFullName() { return fullName; }
  public int getScore()       { return score; }
  public boolean isWithdrawn(){ return withdrawn; }

  /** The ONLY way a score can change. */
  public void setScore(int score) {
    if (score < 0 || score > 100) {
      throw new IllegalArgumentException("Score must be 0–100, got " + score);
    }
    if (withdrawn) {
      throw new IllegalStateException("Cannot score a withdrawn applicant.");
    }
    this.score = score;
  }

  public void withdraw() {
    this.withdrawn = true;
  }
}
```

Now `-50` is impossible, and if a bad score ever appears there is exactly one
method to examine.

::compare{caption="Two setters. Only one of them is doing anything."}
  :::compare-side{label="Ceremony" verdict="wrong"}
  ```java
  public void setScore(int score) { this.score = score; }
  ```
  Identical to a public field, with three more lines. This is what people mean
  when they say getters and setters are pointless, and for this one they are
  right.
  :::
  :::compare-side{label="A guard" verdict="right"}
  ```java
  public void setScore(int score) {
    if (score < 0 || score > 100) throw new IllegalArgumentException(...);
    if (withdrawn) throw new IllegalStateException(...);
    this.score = score;
  }
  ```
  This one enforces something. It is the reason the field is private.
  :::
::

## Better still: methods that mean something

The strongest version is not a setter at all. It is a method named after what is
actually happening.

```java [Application.java]
// Setters: the caller has to know the rules and the order.
application.setStatus("SHORTLISTED");
application.setShortlistedOn(LocalDate.now());
application.setShortlistedBy(registrar);

// A method: the object knows its own rules.
application.shortlist(registrar);
```

```java [Application.java]
public void shortlist(User by) {
  if (status != Status.UNDER_REVIEW) {
    throw new IllegalStateException(
        "Only an application under review can be shortlisted, not " + status);
  }
  if (score == null) {
    throw new IllegalStateException("Cannot shortlist an unmarked application.");
  }
  this.status = Status.SHORTLISTED;
  this.shortlistedOn = LocalDate.now();
  this.shortlistedBy = by;
}
```

The three fields can no longer drift apart, the status ladder cannot be skipped,
and the rule lives with the data rather than being copied into every caller.

::real-life{title="What this prevents, concretely" source="A status field, and six callers"}
An `Application` had a public `status` string set from six different places. Over
two years, one of them set `"Shortlisted"` with a lowercase L, one set
`"SHORT_LISTED"`, and one skipped `UNDER_REVIEW` entirely. The dashboard grouped
by status and reported four categories that should have been three. Nothing was
broken enough to notice, which is why it lasted two years.
::

## The four access levels

| Modifier | Reachable from |
| --- | --- |
| `private` | This class only. **The default choice.** |
| *(none)* | This package. Called package-private, and rarely deliberate. |
| `protected` | This package, plus subclasses anywhere. |
| `public` | Everywhere. A promise you cannot take back. |

::tip
Start everything `private` and widen only when something outside genuinely needs
it. Widening later is easy; narrowing a `public` method that six teams now call
is a negotiation. This is the single most useful default in the language.
::

## The leak nobody notices

```java [Leaky.java]
public class Programme {
  private final List<Applicant> applicants = new ArrayList<>();

  public List<Applicant> getApplicants() {
    return applicants;                  // ← handed out the actual list
  }
}
```

```java [Anywhere.java]
programme.getApplicants().clear();      // legal, and the field is private
```

The field is private and the encapsulation is gone, because you returned the
reference. This is the stack-and-heap lesson biting again.

```java [Programme.java]
  public List<Applicant> getApplicants() {
    return List.copyOf(applicants);     // unmodifiable snapshot
  }

  public void addApplicant(Applicant a) {   // the controlled way in
    if (applicants.size() >= seats * 10) {
      throw new IllegalStateException("Applications closed for " + code);
    }
    applicants.add(a);
  }
```

## Your turn

::runner{lang="java"}
```java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    FeeAccount acc = new FeeAccount(45000_00L);
    acc.pay(15000_00L);
    System.out.println("Balance: " + acc.getBalancePaise());

    // 1. Each of these should be impossible. Which currently are not?
    acc.pay(-100_00L);
    acc.pay(999999_00L);
    acc.getPayments().clear();
  }
}

class FeeAccount {
  private long totalPaise;
  private long paidPaise;
  private final List<Long> payments = new ArrayList<>();

  FeeAccount(long totalPaise) { this.totalPaise = totalPaise; }

  void pay(long amountPaise) {
    paidPaise += amountPaise;
    payments.add(amountPaise);
  }

  long getBalancePaise() { return totalPaise - paidPaise; }
  List<Long> getPayments() { return payments; }
}
```
::

::accordion
  :::accordion-item{label="The three holes, and the fix" icon="i-lucide-check"}
  **All three are currently possible.** A negative payment increases the balance,
  an overpayment is accepted silently, and `getPayments().clear()` erases the
  record of every payment while the field is private.

  ```java
  class FeeAccount {
    private final long totalPaise;                 // final: the fee does not change
    private long paidPaise;
    private final List<Long> payments = new ArrayList<>();

    FeeAccount(long totalPaise) {
      if (totalPaise <= 0) {
        throw new IllegalArgumentException("A fee must be positive.");
      }
      this.totalPaise = totalPaise;
    }

    void pay(long amountPaise) {
      if (amountPaise <= 0) {
        throw new IllegalArgumentException("A payment must be positive.");
      }
      if (amountPaise > getBalancePaise()) {
        throw new IllegalArgumentException(
            "Payment of %d exceeds the balance of %d"
                .formatted(amountPaise, getBalancePaise()));
      }
      paidPaise += amountPaise;
      payments.add(amountPaise);
    }

    long getBalancePaise()   { return totalPaise - paidPaise; }
    List<Long> getPayments() { return List.copyOf(payments); }   // a snapshot
  }
  ```

  **The invariants now stated plainly:** the total never changes, the paid amount
  only ever increases, it never exceeds the total, and the payment history can be
  read and not altered. Each of those is one guard, and together they are the
  reason the field is private.
  :::
::

## Check yourself

1. What is an invariant, and why does a private field with a plain setter not
   protect one?
2. **An interviewer asks: "why not just use public fields?"** Answer with a
   consequence rather than a principle.

## The interview question this answers

**"What is encapsulation and why does it matter?"**

Avoid "it hides the data". Say: it means there is exactly one place that can
break each rule, so when a rule is broken there is one place to look. Then the
example: a public status field set from six places drifted into four spellings
over two years. And then the detail almost nobody adds, returning a mutable
collection from a getter undoes it entirely, so `List.copyOf` or an explicit
add method is part of the answer.
