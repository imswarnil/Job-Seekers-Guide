Two hundred lines and the same block three times. Giving work a name sounds like
tidiness and is most of what the job actually is: the difference between a
program you can change and one you can only rewrite.

## Why this matters in a job

Because every code review you will ever receive is partly about this, and because
"how do you decide what goes in a method" is a design question that sounds simple
and separates people immediately.

## Arrays first

```java [Marks.java]
int[] marks = new int[5];            // five ints, all 0
int[] scores = {78, 64, 81, 55, 92}; // declared and filled

scores[0]                            // 78
scores.length                        // 5 — a field, not a method. No brackets.
scores[scores.length - 1]            // 92, the last one
```

Three facts that cause most array bugs:

::feature-list{columns="2"}
  :::feature{icon="i-lucide-hash" title="Indices start at 0"}
  Five elements means valid indices 0 to 4. The last is always `length - 1`.
  :::
  :::feature{icon="i-lucide-lock" title="The size is fixed forever"}
  `new int[5]` is five, permanently. Needing more means a new array and a copy,
  which is exactly what `ArrayList` does for you.
  :::
  :::feature{icon="i-lucide-circle-dot" title="Defaults are not empty"}
  `int[]` fills with 0, `double[]` with 0.0, `boolean[]` with false, and any
  object array with **null**. An unfilled `String[]` is full of nulls.
  :::
  :::feature{icon="i-lucide-copy" title="An array is an object"}
  So `int[] b = a` shares one array, and `a.equals(b)` compares references.
  `Arrays.equals(a, b)` compares contents.
  :::
::

```java [ArrayUtils.java]
Arrays.toString(scores)        // "[78, 64, 81, 55, 92]" — for printing
Arrays.sort(scores)            // sorts in place, returns nothing
Arrays.equals(a, b)            // contents, not references
Arrays.copyOf(scores, 10)      // a longer copy, padded with 0
Arrays.fill(marks, -1)         // "not marked yet", distinguishable from 0
Arrays.stream(scores).sum()    // 370
```

::warning{icon="i-lucide-alert-triangle"}
`System.out.println(scores)` prints `[I@4617c264`, which is the type and a hash,
not the contents. Every beginner hits this. Use `Arrays.toString`, and
`Arrays.deepToString` for a two-dimensional one.
::

## A timetable is a grid

```java [Timetable.java]
// 5 days, 6 periods.
String[][] timetable = new String[5][6];
timetable[0][0] = "CS-201";              // Monday, period 1

for (int day = 0; day < timetable.length; day++) {
  for (int period = 0; period < timetable[day].length; period++) {
    System.out.printf("%-8s", timetable[day][period] == null
        ? "free" : timetable[day][period]);
  }
  System.out.println();
}
```

Note `timetable[day].length` rather than a fixed 6. Java's rows can be different
lengths, and reading the row's own length is the habit that survives that.

## Methods

```java [Shortlister.java]
//  visibility  returns          name        parameters
    public      List<Applicant>  shortlist(List<Application> applications, int cutoff) {
      List<Applicant> result = new ArrayList<>();
      for (Application a : applications) {
        if (a.getScore() != null && a.getScore() >= cutoff) {
          result.add(a.getApplicant());
        }
      }
      return result;
    }
```

::pull-quote
A method signature is a promise. Given these inputs, you get this back. A reader
should be able to believe it without opening the body.
::

That promise is broken by two things, and both are common:

::compare{caption="The same method, one of them lying."}
  :::compare-side{label="Breaks its promise" verdict="wrong"}
  ```java
  List<Applicant> shortlist(List<Application> apps, int cutoff) {
    apps.removeIf(a -> a.getScore() < cutoff);   // mutates the caller's list
    emailService.notifyAll(apps);                // and sends 1,840 emails
    return apps.stream().map(...).toList();
  }
  ```
  It is named `shortlist`. It destroys the input and sends email. Nobody reading
  the call site could know.
  :::
  :::compare-side{label="Keeps it" verdict="right"}
  ```java
  List<Applicant> shortlist(List<Application> apps, int cutoff) { ... }
  void notifyShortlisted(List<Applicant> shortlisted) { ... }
  ```
  Two names, two jobs. The caller decides whether to send email, which is where
  that decision belongs.
  :::
::

## What makes a method good

::feature-list{columns="2"}
  :::feature{icon="i-lucide-tag" title="The name is a verb phrase"}
  `shortlist`, `calculateAttendance`, `isEligible`. If you cannot name it
  without "and", it is two methods.
  :::
  :::feature{icon="i-lucide-eye-off" title="No surprises"}
  It does what the name says and nothing else. No hidden writes, no email, no
  mutation of its arguments.
  :::
  :::feature{icon="i-lucide-minimize-2" title="Few parameters"}
  Past three or four, it is usually a missing object. `shortlist(cutoff,
  programmeId, intake, includeWithdrawn, sortBy)` wants to be a
  `ShortlistCriteria`.
  :::
  :::feature{icon="i-lucide-undo" title="Same input, same output"}
  Where possible. A method that depends only on its parameters can be tested
  in one line and reasoned about without context.
  :::
::

## Overloading

Same name, different parameters. The compiler picks by the argument types.

```java [Overload.java]
double average(int[] marks)     { ... }
double average(double[] marks)  { ... }
double average(List<Integer> m) { ... }
```

```java [Overload.java]
// NOT overloading — this does not compile. The return type is not part of
// what distinguishes them.
int    parse(String s) { ... }
double parse(String s) { ... }
```

::side-note{kind="go-deeper"}
Overloading is resolved at **compile time** from the declared types, which
produces a genuine surprise: `remove(int)` on a `List<Integer>` removes by
*index* and `remove(Object)` removes by *value*, so `list.remove(2)` and
`list.remove(Integer.valueOf(2))` do completely different things. That is a
real bug and a favourite interview trick.
::

## Recursion, seen rather than described

A method calling itself. Two parts, and missing the first is fatal.

```java [Hierarchy.java]
// Total the fee for a department and everything under it.
static long totalFee(Department d) {
  long total = d.getOwnFee();                 // 1. the base: no recursion here
  for (Department child : d.getChildren()) {  // 2. the recursive step
    total += totalFee(child);
  }
  return total;
}
```

```java [Countdown.java]
// No base case. Watch what happens.
static int countdown(int n) {
  return countdown(n - 1);
}
```

```text [Output]
Exception in thread "main" java.lang.StackOverflowError
	at Countdown.countdown(Countdown.java:3)
	at Countdown.countdown(Countdown.java:3)
	at Countdown.countdown(Countdown.java:3)
	... (about 11,000 more)
```

Each call pushes a stack frame. About a megabyte of stack divided by the frame
size is roughly eleven thousand frames, and then it stops. That is the same stack
from the operating systems track, and this is what filling it looks like.

::memory{kind="stack" caption="factorial(4), at its deepest. Each frame waits for the one above it to return."}
---
frames:
  - label: "Going down"
    cells: [{ value: "factorial(1) → 1", label: "top", state: "active" }, { value: "factorial(2)" }, { value: "factorial(3)" }, { value: "factorial(4)", label: "bottom" }]
  - label: "Coming back up"
    cells: [{ value: "returns 1" }, { value: "2 × 1 = 2", state: "active" }, { value: "3 × 2 = 6" }, { value: "4 × 6 = 24", label: "the answer" }]
---
::

::tip
Recursion is right when the **data** is recursive: a department containing
departments, a folder containing folders, a tree. For a simple count or a loop
over a list, a loop is clearer and cannot overflow. "Use recursion when the shape
of the problem is recursive" is a better rule than any example.
::

## What you can do now

You can use arrays without falling into the four traps, split a long method into
named pieces, and say what makes a method signature honest.

## Your turn

::runner{lang="java"}
```java
import java.util.*;

public class Split {
  public static void main(String[] args) {
    int[] marks = {78, 64, 81, 55, 92, 45};
    System.out.println(report(marks));
  }

  // One method doing four things. Split it into four, then rebuild report()
  // as four calls. Name each one so the body is not needed to understand it.
  static String report(int[] marks) {
    int total = 0;
    for (int m : marks) total += m;
    double avg = (double) total / marks.length;

    int highest = marks[0];
    for (int m : marks) if (m > highest) highest = m;

    int passed = 0;
    for (int m : marks) if (m >= 40) passed++;

    return "Average: " + avg + ", highest: " + highest + ", passed: " + passed;
  }
}
```
::

::accordion
  :::accordion-item{label="One answer" icon="i-lucide-check"}
  ```java
  static String report(int[] marks) {
    return "Average: %.2f, highest: %d, passed: %d"
        .formatted(average(marks), highest(marks), countAtLeast(marks, 40));
  }

  static double average(int[] marks) {
    if (marks.length == 0) return 0;          // the edge case the original ignored
    return (double) sum(marks) / marks.length;
  }

  static int sum(int[] marks) {
    int total = 0;
    for (int m : marks) total += m;
    return total;
  }

  static int highest(int[] marks) {
    int highest = Integer.MIN_VALUE;          // not marks[0] — see below
    for (int m : marks) if (m > highest) highest = m;
    return highest;
  }

  static int countAtLeast(int[] marks, int threshold) {
    int count = 0;
    for (int m : marks) if (m >= threshold) count++;
    return count;
  }
  ```

  **Two things the split revealed**, which is the real reason to do it. The
  original divided by `marks.length` with no check, so an empty array was a
  division by zero. And `highest` started from `marks[0]`, which throws on an
  empty array. Neither was visible while all four jobs were tangled in one
  method, and both are now one line each to fix and one line each to test.

  Note `countAtLeast(marks, 40)` took the threshold as a parameter rather than
  hard-coding 40. Now the same method answers "how many above the cutoff" too.
  :::
::

## The interview question this answers

**"What makes code maintainable?"**

Answer with methods rather than with adjectives. One job each, a name that is a
verb phrase and makes the body unnecessary, no side effects the name does not
announce, and few enough parameters that you are not hiding a missing object.
Then the example that proves you have done it: splitting a long method revealed
two edge cases that were invisible while everything was tangled together. That
is a concrete claim and almost nobody makes it.
