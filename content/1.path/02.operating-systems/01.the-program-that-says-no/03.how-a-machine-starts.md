Before the processes, one short lesson on where all of this comes from. A
machine with the power off has no operating system in memory at all, so
something has to load the thing that loads everything, and the chain is shorter
than you would expect.

## Why this matters in a job

Directly, because containers are this sequence with most of it removed, and you
will spend the back half of this course deploying things into them. Indirectly,
because "what is process 1" and "what does init do" are real interview questions
with short, satisfying answers that almost nobody has.

## The six steps

::flow{numbered direction="vertical" caption="Power to prompt. Each step's only job is to load something more capable than itself."}
  :::flow-step{label="Firmware" icon="i-lucide-power"}
  Code on a chip on the motherboard, UEFI on a modern machine, BIOS on an old
  one. It tests the hardware and looks for something to boot from.
  :::
  :::flow-step{label="The bootloader" icon="i-lucide-hard-drive"}
  A small program on the disk, such as GRUB. Its entire job is to find a kernel
  and load it into memory. It is why a machine can offer you a choice of
  operating systems.
  :::
  :::flow-step{label="The kernel starts" icon="i-lucide-cpu" highlight}
  It initialises memory management, sets up the scheduler, detects devices and
  loads drivers. From this moment there is an operating system.
  :::
  :::flow-step{label="Process 1" icon="i-lucide-git-commit"}
  The kernel starts exactly one user-mode process, `systemd` on most Linux
  systems, `launchd` on macOS. Everything else on the machine is a descendant of
  it. This is why you could not kill process 1 in the previous lesson.
  :::
  :::flow-step{label="Services" icon="i-lucide-server"}
  Process 1 starts everything else: networking, logging, the database, your
  application. This is what `systemctl start` is talking to.
  :::
  :::flow-step{label="A login prompt" icon="i-lucide-terminal"}
  Which starts a shell, which is where three weeks of the last track happened.
  :::
::

## Watch it on your own machine

Every process has a parent, and if you follow the parents up you arrive at 1,
always.

```bash [Terminal]
ps -o pid,ppid,comm -p $$
```

```text [Output]
  PID  PPID COMM
 8421  8398 -zsh
```

`$$` is your shell's own process id. `PPID` is its parent. Follow it up:

```bash [Terminal]
ps -o pid,ppid,comm -p 8398
```

```text [Output]
  PID  PPID COMM
 8398     1 login
```

There it is. Two steps from your prompt to process 1.

::tabs
  :::tabs-item{label="Linux" icon="i-simple-icons-linux"}
  ```bash [Terminal]
  # The whole tree, from process 1 down.
  pstree -p | head -20
  # What the kernel said while it was starting.
  dmesg | head -20
  ```
  :::

  :::tabs-item{label="macOS" icon="i-lucide-command"}
  ```bash [Terminal]
  # No pstree by default; this shows the same parent relationships.
  ps -axo pid,ppid,comm | head -20
  # Process 1 on macOS is launchd, not systemd.
  ps -o comm -p 1
  ```
  :::
::

## Why a container is this, shortened

This is the part that pays off later, so it is worth seeing now.

::compare{caption="A container is not a small virtual machine. It is a process tree with a different view of the world."}
  :::compare-side{label="A virtual machine" verdict="neutral"}
  Runs all six steps. Its own firmware, its own bootloader, **its own kernel**,
  its own process 1. Complete isolation, and it costs a gigabyte and thirty
  seconds to start.
  :::
  :::compare-side{label="A container" verdict="right"}
  Steps one to three are skipped entirely: it uses the **host's kernel**. It
  starts at step four, with your application as its process 1. That is why a
  container starts in under a second and why a Linux container cannot run on a
  Windows kernel without a Linux virtual machine underneath.
  :::
::

::real-life{title="Why your container exits immediately" source="Everyone's first Dockerfile"}
A container lives exactly as long as its process 1. Start a container whose
command is `bash` with nothing attached to it, and bash finds no input, exits,
and the container stops, which looks like a crash and is not one. The fix is
always the same: process 1 must be the thing you actually want running, in the
foreground. This single fact explains most of the confusion in somebody's first
week with containers.
::

## What confuses people here

That the kernel is "running" in the way a program runs. It is not a process and
does not appear in `ps`. It is code that gets entered when a system call or an
interrupt happens, does its work in the context of whichever process triggered
it, and returns. There is no kernel process waiting its turn in the scheduler.

## What you can do now

You can explain what process 1 is, why a container starts in a second when a
virtual machine takes thirty, and why your container exited the moment it
started.

## Your turn

Find out, on your own machine, what process 1 is and how many processes are
running. Then answer: what happens to a process whose parent is killed before it
is?

```bash [Terminal]
ps -o pid,comm -p 1
ps ax | wc -l
```

::accordion
  :::accordion-item{label="The orphan, and why it matters" icon="i-lucide-git-branch"}
  It is **re-parented to process 1**. Its parent slot is set to 1, and process 1
  is written to collect children when they eventually exit.

  This matters because of what happens when nobody collects them. A process that
  has exited but whose parent has not read its exit status stays in the table as
  a **zombie**: no memory, no execution, just a row holding an exit code. A few
  are normal and transient. Thousands mean a parent program that is not calling
  `wait`, and they will eventually exhaust the process table so that nothing new
  can start.

  This is also the other half of the container problem above: if your process 1
  is a shell script that spawns children, it is now responsible for reaping them,
  and most shell scripts are not written to do that.
  :::
::

## Check yourself

1. What is process 1, and why can you not kill it?
2. **An interviewer asks: "what is the difference between a container and a
   virtual machine?"** Answer with the boot sequence.

## The interview question this answers

**"How does a container differ from a virtual machine?"**

Almost everybody answers "containers are lighter" and stops, which is the
conclusion rather than the reason. The reason is that a virtual machine boots its
own kernel and a container shares the host's, so a container is a process tree
with an isolated view rather than a machine. Then the consequence, which is what
makes it sound like experience: that is why containers start in under a second,
why they are all Linux processes on a Linux host, and why a container dies when
its process 1 exits.
