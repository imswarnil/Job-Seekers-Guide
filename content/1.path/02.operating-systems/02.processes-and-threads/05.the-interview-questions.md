This chapter produces more interview questions than any other in the track.
Process versus thread alone is asked in a majority of entry-level technical
rounds in this market.

::accordion
  :::accordion-item{label="1. Process versus thread" icon="i-lucide-message-circle"}
  **The structure, then the consequence.** Threads share the heap, the code and
  the file descriptors; each gets its own stack and registers. A process shares
  nothing.

  Then the two things that show you have met this rather than read it: *"because
  communication between threads is free, a shared mutable field is a race
  condition by default, which is why a field on a Spring controller is a bug.
  And because they share a process, one thread crashing takes down every other
  request in flight."*
  :::

  :::accordion-item{label="2. Why is i++ not thread-safe?" icon="i-lucide-message-circle"}
  Because it is three instructions, not one: read, add, write. A thread can be
  pre-empted between any two of them.

  Then walk it: both threads read 4,100, both add one, both write 4,101. Two
  increments, counter up by one. Say the number, "my test lost about 2,500 of
  10,000 increments", because a candidate who has actually run it is rare.
  :::

  :::accordion-item{label="3. Does volatile fix it?" icon="i-lucide-message-circle"}
  **No**, and this is a deliberate trap. `volatile` guarantees visibility: a
  write by one thread is seen by others, rather than sitting in a processor
  cache. It does nothing about atomicity, so `volatile int x` with `x++` has
  exactly the same bug.

  What it is genuinely for: a `volatile boolean running` flag used to stop a
  loop from another thread. Single write, single read, no read-modify-write.
  :::

  :::accordion-item{label="4. synchronized or AtomicInteger?" icon="i-lucide-message-circle"}
  `AtomicInteger` for one variable. It uses a hardware compare-and-swap and is
  faster under contention because nothing blocks. `synchronized` when several
  fields must change together and stay consistent with each other, which an
  atomic cannot do.

  The sentence that lands: *"two atomics are not atomic together. If the fee
  total and the receipt count must agree, an atomic each is not enough and you
  need one lock over both."*
  :::

  :::accordion-item{label="5. What is a deadlock and how do you prevent it?" icon="i-lucide-message-circle"}
  Four conditions: mutual exclusion, hold and wait, no pre-emption, circular
  wait. All four must hold, so breaking any one prevents it.

  In practice you break circular wait by taking locks in a consistent order, by
  id, by name, by anything total and stable. Then name the diagnostic: `jstack`
  prints "Found one Java-level deadlock" and names both threads. In a database
  the engine detects the cycle itself and kills one transaction as the deadlock
  victim.
  :::

  :::accordion-item{label="6. Concurrency or parallelism?" icon="i-lucide-message-circle"}
  Concurrency is several things in progress; parallelism is several things
  executing at the same instant. One core can be concurrent and cannot be
  parallel.

  The practical edge: *"which is why raising a thread pool from 50 to 500 on an
  eight-core machine made our service slower. The work was processor-bound, so
  we bought context switches and stack memory and no extra throughput."*
  :::

  :::accordion-item{label="7. How many threads should a pool have?" icon="i-lucide-message-circle"}
  It depends on what the threads do, and saying so precisely is the answer.

  **Processor-bound** work, calculations, parsing, image work: about the number
  of cores. More threads means more switching and no more work.

  **Blocking** work, waiting on a database, an HTTP call, a disk: many more,
  because those threads are in the blocked state and not competing for a
  processor. A server handling four hundred simultaneous requests on eight cores
  works precisely because nearly all of those threads are waiting.

  If they push for a formula, the classic one is threads ≈ cores × (1 + wait time
  ÷ compute time), and the honest follow-up is that you measure rather than
  calculate.
  :::
::

## The pattern in all seven

::feature-list{columns="2"}
  :::feature{icon="i-lucide-layers" title="Structure, then consequence"}
  Every good answer above says what the thing is and then what it causes. The
  consequence is what separates reading from experience.
  :::
  :::feature{icon="i-lucide-hash" title="A number, where you have one"}
  "We lost 2,500 of 10,000." "50 threads to 500 made it slower." Numbers are
  unfakeable and they are remembered.
  :::
::
