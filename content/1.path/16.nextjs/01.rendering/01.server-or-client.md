A blank page until JavaScript loads, invisible to a search engine, and every
piece of data a second round trip after the page arrived. Three problems, one
fix: do the work on the server.

## Why this matters in a job

Because "server component or client component" is the decision a modern Next.js
codebase asks you to make in every file, and because getting it wrong is how a
fast framework produces a slow site.

## The three problems

::flow{numbered direction="vertical" caption="A pure client-rendered app, from the user's point of view."}
  :::flow-step{label="HTML arrives: an empty div" icon="i-lucide-file"}
  Nothing to see. On a slow connection this lasts seconds.
  :::
  :::flow-step{label="JavaScript downloads and parses" icon="i-lucide-download"}
  Often several hundred kilobytes, and parsing is slower on a cheap phone than
  downloading.
  :::
  :::flow-step{label="React starts and asks for data" icon="i-lucide-send" highlight}
  A **second** round trip, which could not begin until the first finished. From
  the networks track, that is another 140 milliseconds each way, at least.
  :::
  :::flow-step{label="Finally, content" icon="i-lucide-eye"}
  A search engine crawler may have given up. A user on a bad connection
  certainly has.
  :::
::

```jsx [Server.jsx]
// A server component. This is the default in the Next.js app router.
async function ApplicationsPage({ searchParams }) {
  const applications = await db.query(
    `SELECT a.application_id, ap.full_name, a.score, a.status
       FROM Application a JOIN Applicant ap USING (applicant_id)
      WHERE a.intake = $1 AND a.status <> 'WITHDRAWN'
      ORDER BY a.score DESC NULLS LAST
      LIMIT 100`,
    [searchParams.intake ?? '2026']
  );

  return (
    <main>
      <h1>Applications</h1>
      <ApplicationsTable applications={applications} />
    </main>
  );
}
```

That component **queries the database directly** and runs only on the server. The
browser receives finished HTML on the first response: no empty div, no second
round trip, and a crawler sees the content.

::pull-quote
The query is in the component, and the query never reaches the browser. That
feels wrong the first time and it is the whole point: this code runs where the
database is.
::

## The decision

::compare{caption="Default to the server. Opt into the client, for a reason you can name."}
  :::compare-side{label="Server component (the default)" verdict="right"}
  Fetching data, reading the database, rendering content, anything using a
  secret. **Its code is never sent to the browser**, so a large formatting
  library used here costs the user nothing.
  :::
  :::compare-side{label="Client component (`'use client'`)" verdict="neutral"}
  Anything needing `useState`, `useEffect`, an event handler, or a browser API.
  A button that does something. A form that validates as you type. Its code
  **is** downloaded.
  :::
::

The test: **does it need to react to the user, or remember something between
renders?** If not, it is a server component.

```jsx [Mixed.jsx]
// Server: fetches, renders the table, sends no JavaScript for any of this.
export default async function Page() {
  const applications = await getApplications();
  return (
    <table>
      <tbody>
        {applications.map(a => (
          <tr key={a.id}>
            <th scope="row">{a.fullName}</th>
            <td>{a.score ?? 'Not marked'}</td>
            <td><ShortlistButton id={a.id} /></td>     {/* ← the only client bit */}
          </tr>
        ))}
      </tbody>
    </table>
  );
}
```

```jsx [ShortlistButton.jsx]
'use client';                       // this file, and what it imports, ships

export function ShortlistButton({ id }) {
  const [status, setStatus] = useState('idle');
  ...
}
```

The table is server-rendered and free. Only the button's code is downloaded, and
it is perhaps two kilobytes. That granularity is the actual advantage.

::warning{icon="i-lucide-alert-triangle"}
`'use client'` marks a **boundary**, not a file. Everything imported below it
becomes client code too. Putting it at the top of your root layout because an
error told you to makes the entire application a client application, and this is
the single most common way a Next.js codebase loses the benefit it was adopted
for.
::

## The two rules that keep you out of trouble

::feature-list{columns="2"}
  :::feature{icon="i-lucide-arrow-down" title="Push `'use client'` down"}
  Not the page, not the layout, just the button. When an error says a hook needs
  a client component, extract the interactive part into its own small component
  rather than marking the parent.
  :::
  :::feature{icon="i-lucide-key" title="Secrets stay on the server"}
  An API key in a server component is safe; the same key in a client component
  ships to every visitor. In Next.js anything prefixed `NEXT_PUBLIC_` is
  deliberately public, and everything else is not, reading the wrong one is how
  keys leak.
  :::
::

## Mutations, without an API route

```jsx [actions.jsx]
// A server action: a function that runs on the server, called from a form.
async function shortlist(formData) {
  'use server';

  const id = Number(formData.get('applicationId'));
  const user = await currentUser();

  if (!user.canShortlistFor(id)) {              // the check that matters, server side
    throw new Error('Not permitted');
  }

  await db.query(
    `UPDATE Application SET status = 'SHORTLISTED', shortlisted_on = CURRENT_DATE
      WHERE application_id = $1 AND status = 'UNDER_REVIEW'`,
    [id]
  );

  revalidatePath('/applications');              // the page's cached data is stale
}
```

```jsx [Form.jsx]
<form action={shortlist}>
  <input type="hidden" name="applicationId" value={application.id} />
  <button type="submit">Shortlist</button>
</form>
```

That works **without JavaScript**, because it is a real form posting to the
server. With JavaScript it is upgraded to a fetch with no page reload. Both
paths, one piece of code.

::side-note{kind="security"}
A server action is a real HTTP endpoint whether or not it looks like one. Every
rule from the earlier tracks applies: authenticate, authorise, validate the
input, and never trust that the form is the only caller. The permission check
above is not decoration; it is the entire security of the feature, because
anybody can post to that endpoint directly.
::

## Caching, and the thing that will confuse you

::caution{icon="i-lucide-octagon-alert"}
Next.js caches aggressively and by default. Your data changes and the page does
not, and this is the single most confusing thing about the framework for
somebody new to it.

Three things to know: `revalidatePath` and `revalidateTag` after a mutation;
`export const dynamic = 'force-dynamic'` for a page that must never be cached;
and that in development the caching behaves differently from production, so
"it works locally" is not evidence.
::

## What you can do now

You can decide where a component should run and say why, keep the client bundle
small by pushing the boundary down, and mutate data with a server action that is
secure and works without JavaScript.

## Your turn

Rebuild the applications screen.

1. The table as a server component, querying directly.
2. The filter as a URL search parameter, so the page is linkable and shareable.
3. Shortlisting as a server action, working with JavaScript switched off.
4. Then: switch JavaScript off in developer tools and use the whole page.

::accordion
  :::accordion-item{label="Why step four is the real exercise" icon="i-lucide-power-off"}
  With JavaScript off, a well-built version still works: the table renders, the
  filter form submits and reloads with the filtered list, and shortlisting posts
  and redirects back.

  That is not about users with JavaScript disabled, who are rare. It is a proxy
  for three things that are common: **a slow connection** where JavaScript has
  not arrived yet, **a crawler** that will not run it, and **a script that failed
  to load** because of a bad network or a blocked CDN. A page that works without
  it degrades gracefully in all three.

  The thing that usually fails: the filter is a controlled React input with an
  `onChange`, so it does nothing. Making it a real `<form>` with a `GET` action
  and the value in the URL fixes it, and as a bonus the filtered view becomes a
  link somebody can send to the registrar. That is a genuine feature you get for
  free by doing it the older way.
  :::
::

## The interview question this answers

**"Why server-side render?"**

Three reasons, and give all three: the first paint is content rather than an
empty div, a crawler sees the page, and the data comes in the first response
instead of a second round trip after JavaScript has loaded.

Then the modern nuance, which is what shows you have used it recently: it is per
component rather than per page, so the table is server-rendered and free while
only the button's code ships. And the trap: `'use client'` is a boundary that
spreads to everything imported below it, so putting it in a layout turns the
whole application back into a client application.
